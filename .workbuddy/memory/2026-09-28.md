### 关键实测坑（本次新增）
1. **同名 `const` 重复声明 = 整函数 TDZ**：报错是 `Cannot access 'X' before initialization`，
   但**只在运行到那行才抛**，`node --check` 完全通过 → 静态检查抓不到。诊断靠拦 `window.api` +
   拦 `toast`，看到 toast 里那句错误才定位。改完必须跑一次**真实提交路径**的断言。
2. **`selectConv` 会用后端值覆盖前端 pending**（`03-chat.js:398`）：测试里先 `setPendingClarify`
   再 `selectConv` 会被自己的调用覆盖 → 历史还原永远落回只读分支。
   要验历史还原必须**让后端真有 pending**（临时会话 + 一条 `msg_type='clarify'` 消息）。
   ⚠️ 只插会话不插消息也没用 —— `05-markdown.js` 的还原分支挂在「消息 msg_type==='clarify'」上。
3. **多行 `eval` 作 argv 时第二段不生效**：`ab("eval", 多行脚本)` 里若脚本自身带换行/嵌套，
   实测第二段静默不执行（两次截图字节完全相同才发现）。**payload 一律走文件读入**。
4. **python 子进程偶发 SIGTERM**：`python tmp/x.py` 偶发被信号杀掉（空输出、exit=1），
   同构的 **node 单进程脚本**跑得稳 → 本项目验证脚本统一用 node 写（与 `shots_*.js` 同构）。
5. **断言别用旧连接读清理结果**：DELETE 前打开的 sqlite 连接读的是旧事务视图 →
   "无残留"断言假 FAIL。复核残留**必须开新连接**。

### B-0 会话流下方（状态栏 / 输入区）与会话消息列宽度对齐
- 文件：`static/css/app.css`
  - `#chat-area{scrollbar-gutter:stable both-edges;}` —— 让滚动条占位**左右对称**。
  - `#chat-col > .chat-input-dock, #chat-col > .chat-status-bar{ width:100%; max-width:min(100%, 998px);
    padding-left:39px; padding-right:39px; margin:0 auto; }`
- **为什么是 998 / 39**（不是 968 / 24）：
  - 参照物是 `#chat-area` 内被 `max-width:920px` 收窄的 **.msg**，不是通栏的 `#chat-area`（1308px）。
  - 内衬 39 = `#chat-area` 的 24px padding + 15px（对称 gutter 半宽）；
    998 = 920(内容轨) + 39×2。**全局 box-sizing:border-box**，故 920 是内容轨、边框盒 998。
  - 结果：内容盒三者**零偏差**（宽态 920/l=417；窄态 906/l=262；恢复态 920/l=417）。

### B 批新增关键坑
6. **CSS 断言对象必须"内容盒"，且别拿通栏容器当参照物**：
   - 一稿按"#chat-area 左右各 24px padding"推 968px（920+48）→ **错**。.msg 边框盒=920、left=410，
     968px 的状态栏 left=393 → 两者左右各差 17~24px，**边框盒根本没对齐**；它只让状态栏和输入区
     **彼此**对齐了。用户反馈依旧成立。**定性前先量 .msg 的实际盒**。
   - `#chat-area` 是 inline-style 的**通栏 flex 容器**，量它等于量错对象（1308 ≠ 920）。
   - **overflow-y:auto 的滚动条只吃右侧**（Windows 实测 15px）→ 消息列在「padding-box − 右 gutter」
     里居中，而下方元素在 `#chat-col` 里居中 → **居中心线差 ~6.5px**（实测 left 410 vs 417）。
     宽度一样却看着不齐，就是这个原因。修法：`scrollbar-gutter:stable both-edges`。
   - **box-sizing 是 border-box 时，加 padding 不会让边框盒变窄** —— 我先后试了
     `padding:24px`（无效）、`content-box`（边框盒变成 998，更糟），都没抓住要点；
     正解是「把 padding 计入后**相应放大 max-width**」（920+78=998）。
7. **变异测试"变异太弱"≠"断言空转"**：`_condense_conclusion` 对"名词性结论误命中"有**两层独立防御**
   （① 正则要求 `结论` 带 是/为；② 标记后紧跟标点则放弃截取）。只还原 ① 时 ② 仍兜住 → 断言 PASS。
   这不是空转断言，而是**退防不彻底**；必须同时还原两层才观测得到 bug。
   **推论**：看到"变异没被抓"先问「我退的是不是全部防御路径」，再怀疑断言。
8. **断言不要耦合"环境里恰好有什么"**（同型第二次）：C 项只扫真实会话时，退防后**照样 PASS**
   （恰好没有会话触发该形态）→ 必须补**受控坏样本**，两者任一命中即 FAIL。
9. **本机 http_proxy 会拦截 127.0.0.1 请求**（实测 `127.0.0.1:59906`）：
   urllib 走代理 → 得到 `502 upstream connect failed`，**看起来像服务挂了**，实为代理拦截。
   验证脚本必须 `build_opener(ProxyHandler({}))` 显式禁代理；curl 用 `--noproxy '*'`。
10. **Bash 工具里 `(cmd &)` / `nohup ... &` 起的服务会被回收**：本轮服务两次"启动成功后被静默杀掉"
    （日志显示 `Application startup complete` 但端口随后消失）。正解：用 **run_in_background 前台常驻**
    方式跑服务（`python main.py` 直接作后台任务），不要指望 shell 后台化。
11. **两入口一致性对照必须用"同一会话"**：未分组集合 {1,385,375…} 与项目分组集合 {495,491,485…}
    **无交集**，拿两条不同会话逐字段比必然全 FAIL —— 那是**夹具缺陷**不是产品缺陷。
    正解：把同一条会话在两个入口各渲染一次（克隆节点挂到另一容器）再比。
12. **降级摘要"结论"段曾把客套开场带进来**（"直接回答您的问题：…"）→ 等于把"硬切前 140 字"换成
    "硬切后 120 字"，用户观感不变。修法：`_strip_chatty` 剥客套 + `_condense_conclusion` 优先取
    结论标记之后的要点；**标记后若紧跟标点则判为误命中、放弃截取**。
    实测 `_CONCL_MARK` 首版写成 `结论(?:是|为)?`（可选后缀）→ 命中正文里的**名词性「结论」**
    （"…（t1 结论）检索到的互联数据为空"）→ 收敛成 `结论：。` / `结论：）`。
