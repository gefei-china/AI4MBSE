### 关键技术决策
1. **T3 的 replace 范围基准 = 全部非终态任务**（不是 target_keys）：T3 语义是
   "推翻划分重做整图"，**被替代对象由 LLM 自己决定**；基准给窄 ⇒ LLM 合法替代被判
   `lineage.from ∉ failed` ⇒ 恒 T4。done 仍排除（不变量 1）。
2. **DAG 级指令只读 followup 队列**（`peek_text` 不 pop）：两条通道各司其职，
   单 Agent 的 follow-up 语义是"重启一轮 tool 循环"，被抢走会双写。
3. **确认卡 TTL 超时维持原计划**（v1 R10），不改图、不推进轮次，只留痕。
4. **中文序数指代按整张图计数**（"第三部分" ⇒ 图上第 3 个），不是按未执行任务数。
5. **T3 落库顺序：先改下游 deps 再 `create_plan`**（同 P2 重量级）—— 反序会把
   刚写的 `t2_r1` 依赖当场丢掉（`create_plan` 会过滤"计划外 key"）。
6. **`parse_llm_plan` 只认命名证据**（`<旧key>_rN` 前缀）判定替代关系；配对不到
   就不填 `lineage.from`（宁可让 Q3 拦，不给质量门开后门）。

### 实施期抓到的 8 个真 bug（都是"看起来对、实际不生效"那一类）
1. `wait_for` 跨线程竞态：应答早于进入循环 ⇒ 报"无待确认决策" ⇒ **用户点批准却
   静默不重画**。修法：`resolve` 成功时写 `_DECIDED` 留痕，`wait_for` 的入口/循环/
   收尾三处都先查留痕。**单线程假时钟测不出来**，靠跨线程实测抓到。
2. `plan_llm_redraw` 的 remap 方向写成恒等映射 ⇒ 下游 deps 指向已删旧 key ⇒ 恒 T4。
3. replace 范围锁定被"顺序配对兜底"破掉 ⇒ LLM 凭空新增的任务也认成替代品，
   `insert` 从后门溜进来且 **Q1~Q5 全绿、日志无异常**。
4. 点名未命中误判 T0 ⇒ 用户真实修改被**静默吞掉**（"用户以为改了、实际没改"）。
5. `parse_llm_plan` 的 `lineage.from` 填成新 key 自己 ⇒ 全部判越界。
6. **T3 主链路从未接线**（只写"判定+留痕"，声称由调用侧回灌 —— 没有调用侧）：
   单元测试与门禁全绿，但真实编排里 T3 永远不落库。补齐后新增探针 G1~G3 段
   （注入式假 LLM 端到端验证）。
7. **T3 范围基准给窄**（传 target_keys）⇒ LLM 合法替代被判越界 ⇒ 恒 T4。
8. **既存缺陷**：子任务嵌套编排以 `conversation_id=0` 写主会话消息 ⇒ FOREIGN KEY
   失败 ⇒ "编排流式失败，回落单 Agent 直行"，且**子任务编排产出整段丢失**。
   修法：会话号无效 ⇒ 不写主会话消息，但**仍写 `summary_written`**（否则 resume
   误判"可只重做汇总"），且**不得 `return`**（会丢 stage/agent/done 事件）。
