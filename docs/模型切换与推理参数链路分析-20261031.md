## 1. 架构链路总览

```
[会话入口 chat bar]
  └─ #llm-providers (select)  ──仅此一个模型控件──► 发送 body.provider_id
        │
        ▼  POST /api/conversations/{cid}/chat/stream   (ChatIn: 仅 provider_id)
[后端 pipeline]
  └─ execute.py: effective_provider = provider_id or registry.get_provider_id(intent)
        │
        ▼  llm_client.chat(messages, provider_id=..., _intent=..., _model_params=_agent_mp)
[LLM 装配层]
  └─ llm/__init__.py _load_provider_cfg(provider_id) → dict(row)  // 含 model_params JSON
        │
        ▼  openai_compat.OpenAICompatProvider.chat(...)
        ├─ temperature   ← cfg.temperature 或 调用方显式
        ├─ max_tokens    ← cfg.max_tokens 或 调用方显式（默认 4096）
        ├─ context_window← cfg.context_window（用作上限守卫 clamp/warn）
        ├─ top_p         ← model_params.top_p   ✅ 写入 payload
        ├─ top_k         ← model_params.top_k   ⚠️ 非标准参数（隐患 1）
        └─ thinking      ← model_params.thinking_mode + per-intent policy + 形态规则（三态）
        │
        ▼  payload → POST {base_url}/chat/completions
```

## 2. 逐能力链路分析

### 2.1 ① 模型切换 —— ✅ 链路完整
- **前端**：`static/index.html:222` 的 `#llm-providers` 下拉，选项来自模型配置接口。
- **传输**：`static/js/mods/12-chatsend.js:421` 发送 `provider_id` 入 `body`。
- **后端**：`models/conversation.py:24` `ChatIn.provider_id` 接收；`agent/pipeline_parts/execute.py:197` `effective_provider = provider_id or self.registry.get_provider_id(intent)`（显式 > Agent 绑定 > 全局默认）。
- **消费**：`execute.py:540` 起所有 `llm_client.chat(..., provider_id=effective_provider)` → `llm/__init__.py:_load_provider_cfg` 按 id 查 `llm_providers` 真实配置。
- **结论**：UI → API → DB → LLM 全链路闭环，真实生效。

### 2.2 ② 温度 / MaxTokens / 上下文窗口 —— ✅ 链路完整（全局）
- 控件位于**模型配置弹窗**（`01-core.js:448-450` 的 `f-ctx`/`f-maxt`/`f-temp`），**非会话入口**。
- 持久化：`30-agents.js:1704 saveLLM()` 将 `context_window/max_tokens/temperature` 写入 `llm_providers` 表对应列。
- 消费：`openai_compat.py:342-355` 读取 `cfg.context_window/max_tokens/temperature` 并写入 payload；`context_window` 另作上限守卫（clamp/warn/off 三档，受 `llm.context_window_guard` 控制）。
- **结论**：配置→落库→调用链路完整，但为**全局 per-model**，对所有会话统一生效，**不能在会话入口按轮调整**。

### 2.3 ③ top_p / top_k / thinking_mode —— ⚠️ 链路部分通
- 控件：`01-core.js:451-454` 的 `f-top-p`/`f-top-k`/`f-thinking`（模型配置高级设置）。
- 持久化：`30-agents.js:44-45` 经独立 `PATCH /api/llm/providers/{id}/params` 写入 `llm_providers.model_params` JSON（列如 `{"top_p":null,"top_k":null,"thinking_mode":"模型默认"}`）。
- 消费：`openai_compat.py:411-432` 解析 `model_params`，将 `top_p`/`top_k` 写入 payload；`thinking_mode` 经三态逻辑（开启/关闭/默认）+ per-intent `thinking_policy` + 形态规则层（`_decide_by_shape`）决定 `payload["thinking"]={"type":"enabled"/"disabled"}`。
- **Agent 级覆盖**：`execute.py:540` 透传 `_agent_mp`，`openai_compat.py:420-432` 浅合并（Agent > Provider），链路**现已通**（registry.py 旧注释"无消费点"已过时）。
- **结论**：管道齐备，但见下方隐患 1/2。

### 2.4 ④ 会话入口级「思考强度」 —— ❌ 链路缺失
- 入口无控件；`ChatIn` 不接收 thinking 字段；无前端→后端透传；`conversations` 表无每会话参数列。
- 现有"思考强度"只能通过**全局模型配置**的 `thinking_mode` 设定，无法在会话入口按轮切换。

### 2.5 ⑤ 会话入口级「上下文大小」 —— ❌ 链路缺失
- 同④：仅在全局 `context_window` 配置；无会话级入口、无 `ChatIn` 字段、无 `conversations` 参数列。

### 2.6 ⑥ 模型介绍 —— ❌ 完全缺失
- `llm_providers` 表**无 description/intro 列**（`PRAGMA table_info` 实测列：id/name/provider_type/base_url/api_key/model_name/max_tokens/temperature/is_default/status/created_at/model_params/model_type/context_window/tags/priority/budget_tokens`）。
- `routers/llm*.py:list_providers` 返回字段不含介绍类字段。
- 前端**无任何模型介绍 UI**（搜索"模型介绍/模型说明/model_intro"无命中）。

## 3. 链路完整性隐患（"通但可能不实"）

**隐患 1 — top_k 是 OpenAI 兼容接口的非标准参数**
`openai_compat.py:432` 直接 `payload["top_k"]=int(...)`。标准 OpenAI / DeepSeek / DashScope 网关会**静默忽略未知键**，导致 top_k 配置**不报错也不生效**（典型"配了像没配"）。实测库内 10 个 provider 的 `top_k` 均为 `null`，功能未被实际验证。

**隐患 2 — thinking 下发格式仅适配 Qwen/DashScope 与 DeepSeek-v3.1+**
`openai_compat.py:524-528` 使用 `payload["thinking"]={"type":"enabled"/"disabled"}`。该格式对 Qwen3 / DeepSeek-v3.1+ 正确；对 **OpenAI o-series（o1/o3）需用 `reasoning_effort`**。平台主用 DeepSeek/Qwen 故当前可用，但**不可移植**到 OpenAI 系模型。

**隐患 3 — 全局 vs 会话级语义混淆**
思考/上下文当前是"全局 per-model"语义，但用户预期是"会话入口 per-turn"语义。若不改链路，仅在全局配置处调参会**影响所有会话**，与"在入口临时调"的预期不符。

## 6. 实施记录（2026-10-31 当晚落地，本节取代第 4 节的"待决策"）

第 1~5 节是**改造前**的现状分析，保留作为对照。以下为实际落地内容与验收证据。

### 6.1 问题一：思考强度到底怎么控制的（原逻辑 + 改造后）

**改造前的三级决策链**（`llm/providers/openai_compat.py`）：

| 层级 | 依据 | 粒度 | 问题 |
|---|---|---|---|
| ① `thinking_mode`（模型默认/开启/关闭） | `llm_providers.model_params` | **per-model** | 只能表达"开不开"，**表达不了"开多大"** |
| ② `llm.thinking_policy`（on/off 名单） | 全局配置 JSON | per-intent（Agent 名） | 对 27 个 Agent 名覆盖率 0/27，纯名单必然漂移 |
| ③ 形态规则 `_decide_by_shape` | 任务形态（带 tools / max_tokens 小 / 要求输出 JSON） | per-request | 只能"关"，不能"给多少" |

判定后统一落到 `payload["thinking"] = {"type":"enabled"|"disabled"}`，**"模型默认"时一个字段都不发**。
根因问题：思考与正文**共享 max_tokens**，实测思考占比 **63%~99.2%**（极端 143s 那次 completion=6425 / reasoning=6322），
⇒ 只控开关控不住成本与耗时（曾现 541s 超时、用户只拿到 103 token）。

**改造后新增第 ④ 层：`thinking_level` 五档（优先级最高）**

```
用户显式档位 > 策略名单/形态规则 > thinking_mode 三态
```

档位 → 预算 → 实际下发字段（按厂商家族分流，发错即 400）：

| 档位 | 预算 tokens | deepseek / anthropic / generic | qwen（DashScope） | openai o系/gpt-5 |
|---|---|---|---|---|
| 模型默认 | — | **不发**（零漂移） | 不发 | 不发 |
| 关闭 | 0 | `thinking:{type:disabled}` | `enable_thinking:false` | `reasoning_effort:low` |
| 低 | 1024 | `thinking:{type:enabled,budget_tokens:1024}` | `enable_thinking:true` + `thinking_budget:1024` | `reasoning_effort:low` |
| 中 | 4096 | 同上 budget 4096 | 同上 budget 4096 | `reasoning_effort:medium` |
| 高 | 8192 | 同上 budget 8192 | 同上 budget 8192 | `reasoning_effort:high` |

附带**正文保底**：当档位预算 + 1024 > 当前 `max_tokens` 时自动扩容 `max_tokens`
（否则"给了 8192 给思考、正文只剩 0"——这正是历史上思考吃光额度的机制）。

家族判定：`_provider_family(cfg)` 按 `base_url` / `model_name` / `provider_type` 识别，
识别不出就退回 `{"type":...}`（= 旧行为），**绝不猜着发**（发错字段是硬 400，本地 mock 测不出来）。

### 6.2 问题二：上下文档位 1M / 600K / 300K

- `context_window` 列本来就有，**上限卡在 1,000,000**（`routers/llm.py:_check_context_window`）
  ⇒ **1M = 1,048,576 恰好被 400 拦掉**（"选了 1M 保存报错"）。
- 已把上限提到 **2,000,000**，并在模型配置页提供档位下拉：
  `1M(1,048,576) / 600K(614,400) / 300K(307,200) / 256K / 128K / 64K / 32K / 16K / 8K / 自定义`。
- 真值仍写在 `#f-ctx` 数字框（单一事实源），档位下拉只做"快捷赋值 + 反向回显"
  （按现有 `context_window` 自动匹配档位，无匹配则显示"自定义…"）。

### 6.3 问题三：模型描述与标签，也是每个模型单独设置

| 字段 | 列 | 改造前 | 改造后 |
|---|---|---|---|
| 模型描述 | `llm_providers.description`（新增） | **不存在** | 迁移已加列；配置页有 textarea；接口 `ProviderIn` 透传；会话入口卡片展示 |

## 7. 真实任务执行差异实测（2026-10-31 晚，第二轮）

第 6 节只证明了"字段发出去了"，**没证明"行为变了"**。本节是真实调用实验。
实验对象：`provider#71 deepseek-v4-flash`（当时唯一连通的对话模型；qwen 两家 403）。

> 先说一条方法论教训（本轮又踩了同一族的坑）：
> **第一版实验测错了对象**，得出两个假结论。
> ① E2 假设"context_window 会截断超长输入"，于是拿 1.7k tokens 的材料比 8K/32K/128K，
>    三档全答对 → 差点写成"上下文设置无影响"。读代码后才确认：**我方不截断输入**
>    （超限交上游报错），`context_window` 的真实作用是①夹 `max_tokens` ②决定历史/检索预算。
> ② B 组第一版只造 user/assistant 消息，压缩后"裁掉 0 tok"→ 差点写成"总闸空转"。
>    读 `_apply_total_budget` 才确认：压缩**只裁 system 区的历史块**
>    （`【话题：`/`【相关历史片段（第`/`【本会话既有产物】`），**user/assistant 永不裁**（设计如此）。
> 两次都是"验证对象选错"，症状与"功能没做"完全一致。下面全部是**修正后**的数据。

### 7.1 思考强度：五档在真实任务上**单调可分**（有明确代价）

同一道多步可靠度计算题（3 通道 2oo3 表决），每档重复 2 次取均值：

| 档位 | 实际生效方式 | reasoning tokens | 耗时均值 | 正文长度 |
|---|---|---|---|---|
| 模型默认 | （不发字段） | 3269 | 22.79s | 626 |
| **关闭** | api:off | **0** | **6.47s** | 1900 |
| 低 | prompt:brief | **1884** | 13.64s | 312 |
| 中 | api:on | 3140 | 21.44s | 371 |
| **高** | prompt:deep | **4096**（触顶） | 27.65s | 0 → 修后 1308 |

**结论（可直接对外说）**：
- **关闭**：真实有效，思考归零，耗时 **6.47s vs 22.79s（-72%）**，且正文更长（不必边想边写）。
- **低**：真实有效但**靠提示词**（deepseek 无预算能力），思考 **-42%**，耗时 -40%。
- **中**：≈ 默认（因为 deepseek 默认就开思考），实测 3140 vs 3269，**无显著差异**。
- **高**：真实有效，思考 **+25%** 且触顶 4096（吃满 `max_tokens`），耗时 **+21%**。

⚠️ **发现并修复的真实事故**：高档在 `max_tokens=4096` 时思考吃到 **4095/4096**，
**正文 0 字** —— 用户会看到"想了半天什么都没答"。两次实测都复现。
修复：高档强制把 `max_tokens` 提到 `8192 + 1024 = 9216`（预算 + 正文保底），
修后同题 reasoning 6305、**正文 1308 字**。这条已写成门禁断言。

### 7.2 上下文窗口：差异在「历史预算」，不在「输入截断」

同一份**真实结构**会话（1 条 system 本体 + 3 条历史块 + 40 轮对话，共 **59530 tokens**）：

| context_window | 总预算(=cw×0.75) | 压缩前 | 压缩后 | 裁掉 | 裁掉比例 |
|---|---|---|---|---|---|
| 8K（8192） | 6144 | 59530 | 47955 | 11575 | **19.4%** |
| 32K（32768） | 24576 | 59530 | 47955 | 11575 | **19.4%** |
| 128K（131072） | 98304 | 59530 | 59530 | 0 | 0% |
| 600K（614400） | 460800 | 59530 | 59530 | 0 | 0% |
| 1M（1048576） | 786432 | 59530 | 59530 | 0 | 0% |

**三条硬结论**：
1. **档位不是线性生效的**。8K 与 32K 的最终结果**完全相同（47955）**，
   因为压缩有**地板**：system 本体与 user/assistant 历史永不裁，
   最高档（4/4，历史块上限 200 tok）也只能裁到 47955。⇒ **8K 与 32K 在实际行为上无区别**。
2. **预算不保证达得到**。8K 档预算 6144，但压完仍 47955（超预算 **7.8 倍**）。
   若上游真实窗口是 8K，该请求会被拒/超时——**总闸只能"尽力裁"，不能"保证合规"**。
3. **跨过 59530 就不裁**。要"完全不动历史"，`cw` 需 ≥ 79373（59530/0.75）。
   所以 128K / 600K / 1M 在本会话规模下**行为完全相同**。
   ⇒ 用户在 128K/600K/1M 之间切换，**感受不到差异**（除非会话本身超过对应预算）。

另：材料规模只有 1764 tokens 时，8K/32K/128K 三档**都能正确答出埋在第 52 节的指标** ——
这与上面一致（远未触预算），说明"小材料下档位无差异"是**正常**，不是没生效。

## 8. 三问的完整答案（2026-10-31 23:20，含本轮新增实测）

### 8.0 一句话结论

| 问题 | 答案 |
|---|---|
| 思考强度是不是每个模型都能这样控制？ | **不是。** 只有"认这个字段"的模型才行；字段形态按厂商不同，且**发错形态多数是静默忽略，不是报错** |
| 上下文窗口的原理与影响？ | 原理=**夹 max_tokens + 定历史预算(cw×0.75)**；影响=**档位非线性**（8K≡32K、128K≡600K≡1M），且**大概率压不到预算** |
| 真的在生效吗？ | **分层看**：字段层 100%、真实上游层已证（deepseek）、全链路 3/3=100%。**但只有 deepseek 系列经过真实上游实测**；qwen/openai 仅代码路径对，未实测 |

### 8.1 思考强度的实现原理（四层决策链）

调用链：`provider.model_params.thinking_level` → `_provider_family()` 判家族 → `_apply_thinking_payload()` 落字段

```
优先级（高→低）：
  ① 本轮覆盖 o_think（会话入口临时）
  ② 模型配置 thinking_level（低/中/高/关闭）
  ③ llm.thinking_policy 的 on/off 名单（per-intent）
  ④ 形态规则 _decide_by_shape（带 tools+小 max_tokens+探针名 / 要求输出 JSON ⇒ 关）
  ⑤ provider 级 thinking_mode（模型默认/开启/关闭）
  ⑥ 模型默认（一个字段都不发）
```

**为什么必须判家族**（这一步不能省）：`thinking` 不是 OpenAI 标准字段。
同一句"关思考"，三家写法完全不同：

| 家族 | 关闭 | 开启+预算 |
|---|---|---|
| deepseek / anthropic / generic | `thinking:{type:disabled}` | `thinking:{type:enabled, budget_tokens:N}` |
| qwen（DashScope） | `enable_thinking:false` | `enable_thinking:true` + `thinking_budget:N` |
| openai o系 / gpt-5 | `reasoning_effort:low` | `reasoning_effort:low/medium/high` |

### 8.2 「是每个模型都可以这样控制吗」——**不是**，三种情况要分开说

**(a) 模型本身有没有"思考"这件事**
实测 3 个 deepseek（2026-10-31 23:08，同一道水池题）：

| 模型 | 不发字段 | thinking:enabled | thinking:disabled |
|---|---|---|---|
| DeepSeek-V3（**默认不思考**） | reasoning=None，正文528 | **reasoning=95，能打开** | reasoning=None，正文869 |
| deepseek-v4-flash（默认思考） | reasoning=95 | 104（≈无变化） | **reasoning=None** |
| deepseek-v4-pro（默认思考） | reasoning=240 | 202（≈无变化） | **reasoning=None** |

⇒ 结论：**同一个字段在三个模型上都有效**，但效果不同：
- 默认不思考的（V3）→「开启」才看得出差别
- 默认思考的（flash/pro）→ 只有「关闭」看得出差别，「开启」≈no-op

**(b) 上游对"不认识的字段"是什么态度**——这决定"配了不生效"能不能被发现
实测 deepseek：

| 发送内容 | HTTP | 含义 |
|---|---|---|
| `{"__totally_bogus_param__": 123}` | **200** | 完全不存在的键被**静默忽略** |
| `{"thinking":{"type":"NOT_A_REAL_TYPE"}}` | **422** | 枚举值错**会报错**（说明 `thinking` 是它认识的规范字段） |
| `{"thinking":{"type":"enabled","budget_tokens":256}}` | 200 | `budget_tokens` 在对象内被**忽略** |
| `{"enable_thinking":true}`（qwen 字段发给 deepseek） | 200 | 不认识的键，静默忽略 |
| `{"thinking_budget":256}`（顶层） | 200 | 静默忽略 |

⇒ **最危险的组合：字段名认、值域不认 ⇒ 200 通过但完全无效**。
这正是 `budget_tokens` 的处境：发出去有 200，reasoning 却乱跳（58/167/69/64）。
⇒ 所以我在实现里加了 `_BUDGET_HONORED` 白名单：**只对声明确认支持的家族发预算**，
  其余走提示词，并在 `_meta.thinking.applied` 里写明实际生效方式。

**(c) 当前代码支持范围 vs 实测覆盖范围**（必须分开说，否则就是夸大）

| 家族 | 代码支持 | 真实上游实测 | 依据 |
|---|---|---|---|
| deepseek（V3 / v4-flash / v4-pro） | ✅ | **✅ 已实测** | 本文 8.2(a)，reasoning 真的变了 |
| qwen（DashScope） | ✅ | ❌ **未实测** | 两家均 403：一家配额耗尽、一家无权 |
| openai o系 / gpt-5 | ✅ | ❌ **未实测** | 无可用 key |
| anthropic / claude | ✅ | ❌ **未实测** | 无可用 key |
| generic（未知端点） | ⚠️ 退回 `thinking:{type}` | ❌ 未知 | 无样本 |

⇒ **不能对外说"每家都能控"**。准确表述：**deepseek 系列已证有效；其余按官方字段形态实现，待联网验证。**

### 8.3 上下文窗口的原理与影响

**两个作用点，都不在"截断输入"**：

1. **夹 max_tokens**（`openai_compat.chat`）：`if mt > cw: mt = cw`（clamp 档）
   ⇒ 影响：`context_window` 填小了，**max_tokens 会被静默压低**，配置里写 32768 实际只给 8192。
   这是"配置谎言"，现象与"模型本来就写不长"完全一样。
2. **定历史/检索预算**（`history._total_budget_cap`）：`预算 = cw × 0.75`
   ⇒ 影响：决定能塞进多少轮历史与多少检索片段，超了触发五档压缩。

**带来的四个真实影响（都有实测数字）**：

| 影响 | 证据 | 用户感受 |
|---|---|---|
| **档位非线性** | 8K 与 32K 压缩后**都是 47955**（完全相同） | "我调到 32K 了怎么没变化" |
| **大档位完全无差异** | 128K/600K/1M 都**不触发压缩**（59530 原样） | "选 1M 和 128K 一模一样" |
| **预算压不到** | 8K 档预算 6144，压完仍 **47955（超 7.8 倍）** | 真撞上游硬限时**直接报错**，不是优雅降级 |
| **调小会砍历史** | 8K/32K 裁掉 19.4% 历史块 | 长会话里 AI"忘了前面说过什么" |

**为什么会这样（原理层）**：压缩有**地板**——
`system` 本体（建模规则）任何档都不裁、`user/assistant` 对话历史**永不裁**（保护 tool_call 配对）。
可裁的只有三类 system 历史块（历史块上限 900→200 tok）。
⇒ 59530 里能裁的只有约 11575，压到底也是 47955。**这是设计取舍，不是 bug。**

### 8.4 「真的在生效吗」——三层证据，逐层说

| 层 | 验法 | 结果 | 能证明什么 |
|---|---|---|---|
| ① 字段层 | `verify_thinking_level.py` 截 payload | **14/14** | 该发的字段发出去了，不该发的没发 |
| ② 真实上游层 | `experiment_thinking_vs_context.py` 打真 API | 关闭 reasoning **0**、高 **4096**、耗时 6.47s vs 27.65s | **模型行为真的变了**（仅 deepseek） |
| ③ 全链路层 | `verify_turn_override_e2e.py` 走真实路由+pipeline 截 payload | **6/6，覆盖 3/3=100%** | 用户在界面点一下 → 真的到了上游 |

**③ 的明细（这是"端到端"唯一的硬证据）**：

| 场景 | 对话调用 | 带 thinking | off / on | max_tokens 被覆盖 |
|---|---|---|---|---|
| 不传覆盖 | 3 | 2（`chat_probe` 命中 off 名单，系统既有策略） | off=2 on=0 | 0 |
| 关闭 + ctx8192 | 3 | **3** | **off=3** | **3** |
| 高 + mt512 | 3 | **3** | **on=3** | **3** |

⇒ "关闭"多关掉 1 次（就是面向用户的 `chat_answer`），"高"把策略的 2 次 off 也翻成 on
（证明**覆盖 > 策略名单**的优先级是对的）。

### 8.5 本轮又修的一个真缺陷：覆盖跨线程丢失

**发现过程**：e2e 第一次统计说"38 次调用只有 3 次带覆盖（8%）"。
**第一反应**是"覆盖只覆盖主路径"——但继续查发现更根本的问题：

```
主线程 set 覆盖后，ThreadPoolExecutor 子线程读到的全是 {}
（threading.local 不跨线程，且 copy_context 不会复制 thread-local）
```

编排子任务跑在 `ThreadPoolExecutor`（`stream.py:_submit_with_ctx` 已有 `copy_context()`），
⇒ **thread-local 的覆盖对子任务完全不可见**。
**修法**：`llm_overrides` 从 `threading.local` 改为 **`ContextVar`**，
让既有的 `copy_context()` 机制自动把覆盖带进子任务。实测验证：
`copy_context` 两个子线程都读到覆盖，裸 `submit` 仍为空。

**然后发现统计也错了**：那 38 次里 **38 次是 `/embeddings`**，真 chat 只有 2 次且都带覆盖。
⇒ "8% 覆盖率"是**我的统计口径错**（把向量化算进分母），不是实现问题。
修正后：**3/3 = 100%**。

> 这已经是本任务里第 **3** 次"验证器/口径错"看着像"功能没生效"。
> 已形成判据：**看到"没生效"先查三件事** —— ①我测的是不是生产同源路径
> ②分母/分子口径对不对（把 embedding 混进 chat 了？）③跨线程后状态还在不在。

### 8.6 仍未验证 / 未解决（如实清单）

1. **qwen / openai / anthropic 全部未做真实上游验证**。代码按官方字段形态实现，
   `verify_thinking_level.py` 只证明"字段名对了"，**不证明上游认**。
   联网后必须补：每家各跑一次"关/开"对比 reasoning_tokens。

## 9. 语义修正：从「单轮」改为「会话维度」（2026-10-31 23:40）

### 9.1 米爸的澄清（这是唯一口径）

> 「思考强度，上下文是在会话中**基于会话维度**进行设置的，**模型维度的是系统默认的**，
>  当基于会话进行设置时，**只会对当前会话有影响，不会反向影响 LLM 维度的配置**」

第 6~8 节做的是 **per-turn（单轮）** —— 设置只对下一次发送生效。
那**不是**这个语义，必须改。

| 维度 | 存哪里 | 作用范围 | 谁能改 |
|---|---|---|---|
| **模型维度 = 系统默认** | `llm_providers` 行 | 所有会话共用 | 能力中心 → 模型配置 |
| **会话维度 = 本会话设置** | `conversations.llm_overrides`（新增列） | **只影响本会话** | 会话入口「本会话设置」 |
| （单轮临时，保留但界面不用） | 请求体 `ChatIn.o_*` | 仅当次请求 | 程序调用 |

### 9.2 为什么必须落库，不能靠前端内存

单轮实现的问题是**结构性**的，不是参数没传对：
- 前端内存 → 刷新即丢、切走切回即丢、第二轮就丢；
- 而"会话设置"的定义就是**跨轮持续、切回仍在**。

⇒ 必须存服务端。新增列：`conversations.llm_overrides TEXT DEFAULT '{}'`
（只存用户显式改过的键；`{}` = 全部沿用系统默认 ⇒ 与改动前逐字节等价）。

### 9.3 优先级（严格分层）

```
单轮临时（o_*，程序调用才用）
  > 会话设置（conversations.llm_overrides）
  > Agent 级 model_params
  > provider 级（系统默认，llm_providers）
  > 模型默认
```

⚠️ 必须**先读会话设置、再叠单轮**。只读单轮的话，"会话里设了关闭思考"从第二轮起就丢——
这正是"设置不持久"的症状。

### 9.4 两个写入口在代码层就分开（防止串写）

| 动作 | SQL | 文件 |
|---|---|---|
| 改系统默认 | `UPDATE llm_providers SET ...` | `repositories/llm_repo.py` |
| 改本会话 | `UPDATE conversations SET llm_overrides=?` | `repositories/conversation_repo.py` |

刻意**不做成同一个"保存参数"函数**：共用就迟早有人把会话设置写进 provider
（本仓已多次记录"同一语义两处实现，只改一处"的事故）。

### 9.5 接口

| 方法 | 路径 | 说明 |
|---|---|---|

## 11. 入口"消失"的真根因 + 思考控制方式（2026-11-01 00:10）

### 11.1 米爸反馈：「现在没有会话修改上下文大小和思考强度的入口了」

**先说结论：功能一直在，是布局把它挤出了可视区。**

排查过程（不是猜，是量）：
1. 静态门禁 63 项全绿 ⇒ 说明 DOM 里确实有这两个下拉。
2. 但用户说"没有"，两者矛盾 ⇒ **必须量像素**，不能只断言存在性。

真机量取（1600×900 视口）：

| 项 | 实测值（修前） |
|---|---|
| `.llm-pick-panel` | `max-height:440px; overflow-y:auto` |
| 模型列表 7 行 | ≈ 490px |
| `.llm-turn-box`（会话设置） | 排在列表**之后** ⇒ 被推到滚动区底部 |

⇒ 打开面板看到的是前 5~6 个模型，**会话设置必须手动滚动才出现**，观感等于"没有入口"。

这属于本仓已记录的「**元素在 DOM 里、class 也对 ≠ 用户看得见**」（位置型 bug）。

### 11.2 修法：三段式 flex（不是把 max-height 调大）

```css
.llm-pick-panel{display:flex;flex-direction:column;max-height:560px;}
.llm-pick-conv{flex:0 0 auto;}          /* 会话设置固定，不参与伸缩 */
.llm-pick-list{flex:1 1 auto;overflow-y:auto;min-height:72px;}  /* 只有列表滚动 */
```

结构顺序也改成 **head → 会话设置 → 模型列表**。
理由：会话设置是"当前会话的即时操作"（高频），选模型是低频动作，不该把高频入口压到下面。

> ⚠️ 为什么不用"把 max-height 从 440 调到 800"：模型再多一次又会被挤出去。那是治标。

### 11.3 静态门禁抓不到的第二个坑：内联 display 压过样式表

上面 CSS 改完后，**CSS 断言全绿，但真机仍然坏** —— 实测：

| 指标 | 修 CSS 后 / 修 JS 前 |
|---|---|
| `getComputedStyle(panel).display` | **`block`**（不是我写的 `flex`） |
| panel rect | top=45, bottom=605, h=560 |
| list rect | top=265, **bottom=716** ⇒ **溢出面板 111px** |
| `listScrollable` | **false**（不滚动） |

根因：`toggleLLMPicker()` 里写的是 `panel.style.display = 'block'`，
**内联样式优先级高于样式表** ⇒ 把 `display:flex` 覆盖掉 ⇒ 列表既不收缩也不滚动。

修法：改成 `panel.style.display = 'flex'`（与样式表同值）。

**已加静态哨兵**（读 JS 源码断言）：
- 必须存在 `panel.style.display = 'flex'`
- 必须**不存在** `panel.style.display = 'block'`

这是本仓「坑 1：内联样式压过样式表」的同族，且**只有量像素才能发现**。

## 12. 语义再修正：从「会话维度」改为「会话 × 模型」（2026-11-01 00:20）

### 12.1 米爸的第二次澄清

> 「会话中的设置是按照（会话+模型）维度来设置的，**不是一个会话中所有模型按照同一套设置控制**」

§9 做的是**会话维度**（一个会话一套，不分模型）。问题是：
在会话里给 deepseek 设了「关闭」，切到 qwen **还是关闭** —— 那不是（会话×模型）维度。

### 12.2 三层语义（最终口径）

| 维度 | 存储 | 作用范围 | 谁能改 |
|---|---|---|---|
| 模型维度 = 系统默认 | `llm_providers` | 所有会话共用 | 能力中心 → 模型配置 |
| **会话 × 模型** | `conversations.llm_overrides.by_model[<pid>]` | 只影响「本会话 + 该模型」 | 会话入口 |
| 单轮临时 | `ChatIn.o_*` | 当次请求 | 程序调用（界面不用） |

存储结构升级：
```json
{"by_model": {"71": {"thinking_level":"关闭","context_window":8192},
              "104":{"thinking_level":"高","context_window":131072}}}
```

### 12.3 关键：读取必须在「确定 effective_provider 之后」

这是本次改造最容易做错的地方。
`_chat_overrides()` 原来在**路由层**读会话设置 —— 但那时 `provider_id` 可能还是 `None`
（真实值要等意图识别后 `registry.get_provider_id(intent)`）。
在路由层读 ⇒ 只能读到"会话级"，或者读错模型桶。

**改法**：路由层只传**单轮临时**（`_turn_overrides`），会话设置**下沉到 execute/stream**，
在 `effective_provider` 确定之后再读并合并：

```
会话设置(by_model[effective_provider]) → 叠加单轮临时 → 登记到 ContextVar
```

### 12.4 `provider_id` 必填，缺了直接 400

不传 `provider_id` 就退化成"整个会话一套"——那正是要修正的旧语义。
**宁可报 400 也不静默按会话维度写**：
静默写错比报错难查得多（本仓反复踩过"静默兜底把错误变成不可见"）。

错误文案刻意写清维度：`provider_id 必填（会话参数是「会话 + 模型」维度，不能只按会话设置）`。

### 12.5 老数据兼容（实测存量 0 行，仍保留）

旧格式是扁平 `{"thinking_level":"高"}`。处理原则：
- **读**：按"该会话所有模型共享"处理（升级不丢用户已做的设置）；
- **写**：一律升级为 `by_model`；首次写入时把旧值**带到当前模型桶**，
  避免"改一个模型，之前的设置凭空消失"。

### 12.6 验收

新增两套门禁（**接口层 + 执行层**必须都验，只验接口不够）：

#### `verify_conv_model_scoped.py`（接口层，12 项全过）

## 13. 设置改为「二级树」（2026-11-01 00:40，米爸）

### 13.1 需求

> 「设置的位置放在每个模型的后面，按照二级树方式进行设置，不要放在模型列表的上方」

§12 之前是「列表上方一块公共设置区」，有两个问题：
① 语义上设置是**该模型**的，放上方会被误读成"整个会话共用"；
② 模型越多，公共区离具体模型越远，用户要来回对照。

### 13.2 结构

```
面板
├─ head（选择模型 · N 个可用 ｜ 改系统默认 ↗）
└─ list（内部滚动）
   ├─ item[模型 A]
   │  ├─ row  ← 一级：名称/描述/标签/档位 + 「⚙ 设置」
   │  └─ sub  ← 二级（展开时）：本会话 · A 的参数
   │             ├ 思考强度下拉
   │             ├ 上下文档位下拉
   │             └ ✕ 该模型恢复系统默认
   ├─ item[模型 B]  （默认收起）
   └─ ...
```

视觉从属：`.lp-sub{margin-left:20px; border-left:2px solid; padding-left:8px}` —— 左侧竖线 + 缩进。

交互细节：
- **手风琴**：只允许一个展开（同时展开多个会把面板撑高，也让人分不清在改哪个）。
- 展开态存 `_expandedPid`，**render 后保留**（保存一次就收起会让人以为没生效）。
- 收起态下，被单独调过的模型行显示 **「本会话已设」** 黄标 —— 不用展开也知道哪个模型动过。

### 13.3 数据链路完整性的核心风险（本轮重点）

二级树带来的真风险：**展开的行可能不是当前选中的模型**。
若保存时用 `_currentProviderId()`（选中模型），就会出现：
> 在 A 行展开设置 → 实际存进了 B 的桶

**界面看着对、数据落错桶** —— 这是最难查的一类错，且接口层/单元测试都发现不了。

处置（三重）：
1. **所有控件的 onchange 显式传该行 pid**：
   `saveConvLLM('thinking_level', this.value, ${pid})`、`clearConvLLM(${pid})`；
2. `saveConvLLM(key, value, pid)` 内部不再回落 `_currentProviderId()`（只在未传时才回落，用于兼容）；
3. **门禁加正反两条**：
   - 必须命中 `saveConvLLM('thinking_level', this.value, \d+)`
   - **不得**出现 `saveConvLLM('thinking_level', this.value)`（无 pid 的旧写法）
