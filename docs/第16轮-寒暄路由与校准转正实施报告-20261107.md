## 1. P1：`llm_conflict` 25% 的根因是**寒暄被判成知识问答**

### 错例逐条（真库 confirmed 回放，4 条 1 对 3 错）

| 原话 | 人工标签 | 实际判定 | 问题 |
|---|---|---|---|
| MBSE方法论包含哪些建模活动 | knowledge_qa | knowledge_qa | ✅ 唯一正确 |
| **你好** | chat | **knowledge_qa** | 寒暄被答成知识问答 |
| **谢谢** | chat | **knowledge_qa** | 同上 |
| 帮我看看这个系统的接口设计是否合理 | design | review | 族边界歧义（见 §1.4） |

### 探测发现比错例更严重的一条

直接探测（不走缓存）：

| 输入 | 修前 | 严重性 |
|---|---|---|
| `你好` | knowledge_qa / llm_conflict / 0.60 / **需澄清** | 中 |
| `谢谢` | knowledge_qa / llm_conflict / 0.60 | 中 |
| **`你好！`** | knowledge_qa / llm_first / **0.90 / 不澄清** | **最糟：高置信答错且不给纠正机会** |

根因：寒暄句没有任何领域词 → 规则层/语义层无信号 → 全靠 LLM 猜；
而 LLM 在「MBSE 平台助手」角色设定下倾向判 `knowledge_qa`。
`llm_conflict` 分支（语义与 LLM 互斥时采纳 LLM）反而**帮它压过了语义层的正确判断**。

### 修法：纯寒暄前置判定（`_is_pure_smalltalk`）

纯规则白名单，零延迟、可单测：
- 归一化后长度 ≤ 10
- 去掉标点/空白后**整句被寒暄词完整覆盖**（贪心最长匹配，不留残余）
- 不含任何疑问/任务信号（`怎么/帮我/生成/？/介绍`…）

位置：`continue_inherit` **之后**（有上下文的「好的」仍按续句承继）、explain/规则/LLM 之前。
回退位：`intent.smalltalk_route=False`。

### 验证（`verify_smalltalk_route.py`，8/8）

| 组 | 结果 |
|---|---|
| A1 寒暄集 15 条判真 | 全过，漏判 0 |
| A2 带任务集 10 条判假 | 全过，**误伤 0**（含「你好，帮我看看这个模型」） |
| B1 寒暄全部落 chat | 15/15 |
| B2 寒暄不弹澄清 | 0 条弹澄清 |
| C1/C2 48 条真库 confirmed | **83.3% → 83.3%（不降）** |
| C3 域内变化只指向 chat | ✅（`谢谢` knowledge_qa→chat） |

### 1.3 门禁自身的两次假红（都已修，必须记）

1. 首版 C3 写 `for (t,a),(t2,b) in zip(...)` —— `d_*` 元素是三元组，解包直接
   `ValueError`，门禁自己崩了。
2. 第二版 C3 判「ON/OFF 任何一条不同就 FAIL」，抓到两条：
   `帮我看看这个系统大概是怎么设计的` design→chat、`帮我写一首诗` chat→knowledge_qa。
   查证：两条**都不是纯寒暄**（含「帮我」「写」被规则排除），寒暄规则根本没触发
   ⇒ 变化来自 **LLM 兜底的非确定性**。**把随机性判成回归会让门禁永远红、掩盖真信号**。

### 1.4 未修的一条（如实说明）

`帮我看看这个系统的接口设计是否合理`（人工标 design，实际 review）**没有修**。
理由：这是**族边界歧义**而非缺陷——「接口设计是否合理」确实既像评审也像设计，
人工标签选 design 说明用户期望产出设计建议而非评分；硬改会伤到真实的预评审请求。
建议靠样本累积后再看是否形成稳定倾向。

## 2. P0：shadow 转正（只改展示，不改判定）

### 为什么选「展示值」作为转正入口

`needs_clarification` 依赖 **route 白名单**（`_clarify_routes`），并不直接依赖
confidence 数值 ⇒ 把校准值灌进判定链，收益小、风险大。
真正对用户不诚实的地方在**界面**：`rule_scored` 的 confidence 写死 0.95，
而真库回放真实准确率只有 **70%** ⇒ 前端「把握 95%」是在撒谎。

### 实施
- `stream.py`：`stage`（意图识别）与 `clarify` 两个 SSE 事件**新增**
  `calibrated_confidence` 字段；原 `confidence` 不动 ⇒ 判定链零回归。
- `11-pipeline.js`：`pct` 优先读 `ev.calibrated_confidence`，缺失回落原值（老服务端兼容）。

### 验证（进程内 + 真实 HTTP）

| 原话 | route | 原 confidence | 校准后 | 真库该 route 命中率 |
|---|---|---|---|---|
| 这个模型语法上有问题吗…打个分 | rule | 0.95 | **0.9675** | 1.00（14/14） |
| 改了发动机的接口定义…影响范围 | rule_scored | 0.95 | **0.7867** | 0.70（7/10） |
| 校验一下这段 V2 代码是否符合规范 | rule | 0.95 | 0.9675 | 1.00 |
| SysML v2 里 part def 和 part 区别 | explain | 0.80 | 0.835 | 1.00（2/2） |

真实 HTTP SSE 实测：`calibrated_confidence` 字段已下发（寒暄三句 `conf=0.9 / calib=0.9`）。
**`rule_scored` 从「把握 95%」改成「把握 79%」，与真实准确率 70% 相符。**

### 没有做的事（避免过度承诺）
- 未把校准值接入 `needs_clarification` / `llm_first` 门槛 —— 那是改判定，
  需要更大样本与单独 A/B，本轮不做。
- 未改 `confidence` 本身 —— 缓存指纹、编排信任度都依赖它。

### 打分维度（可解释）

| 维度 | 权重 | 理由 |
|---|---|---|
| 频次 `seen_count`（取 log） | 3.0 | 同一说法越常出现，标它越划算 |
| **标签为空** | 2.5 | 系统无结论，标了立刻可用 |

| 系统自认不确定 | 1.5 | conf 0.4~0.7 / inherit / chat 兜底 |
| 强信号但无标签 | 1.5 | route=rule 0.95 却没落标签，值得核 |

「请检索标准库并生成视图」出现 **61 次**却没有标签 —— 这是当前性价比最高的一条。

> **❌ 上面这段是错的（2026-11-07 第 17 轮纠正）**：
> 该句**不是用户输入**。`messages` 表里它作为 `role='user'` 只出现 **2 次**

> 反复回填累加出来的。全池 **390/547 条（71%）** 的 `seen_count` 都高于真实次数
> （seen 总和 1098 vs 真实 473）。
> ⇒ 用 `seen_count` 排序会把测试脚本刷出来的句子排到第 1。
> 已修：回填不再累加（`bump_seen=False`），清单排序改用**真实频次**
> （新第 1 名：`请输出一段内容用于验证断点保护`，真实 22 次）。
