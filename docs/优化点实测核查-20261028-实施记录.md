### 1.2 三条关键设计判断（不是顺手加的）

**① 告警里刻意保留探针。**
`core/alert_evaluator.py` 原有注释写着「含探测——探测失败同样是 provider 故障信号」。这是**对的**：为了让指标好看而屏蔽故障信号，等于把监控做瞎。⇒ 告警不动，只在**能力度量 / 自进化 / 报表**处排除。

**② 在线评测（`chat_eval` / `gen_faithfulness`）不标探针。**
它们消费真实回答，属业务成本的真实组成；排除会让单轮成本偏低——那是另一种失真。

**③ `sane_latency_where` 与 `probe_where` 正交。**
库里有 2 行 `file_read`（2026-10-07、`user_name=测试`、`args.path="/x.md"`）记了 **56.8 年**延迟——这是**真工具计时溢出**，不是探针。按用户名「测试」过滤会误伤真实用户，故改用**量纲守卫**（>1 小时视为计时异常）。

### 1.3 实测效果

| 指标 | 实施前 | 实施后（业务口径） |
|---|---|---|
| 工具失败率 | **15.04%**（559/3716） | **12.06%**（431/3575） |
| `MAX(latency_ms)` | 1,793,176,874,690 ms | **83,650 ms** |
| LLM 成本 | 6.7855 USD（探针占 24.7%） | 业务 **5.1068** USD |
| 探针标记量 | — | 工具 **142** 行 / LLM **2,228** 行 |

> ⚠️ 口径必须带窗口：探针占成本 **24.7%**（全量历史），但**近 7 天窗口是 51%**（`chat_probe` 集中在最近几天）。两个数都对。

### 1.4 实施中踩到并修正的 3 个问题（如实记录）

| # | 问题 | 怎么发现的 | 修正 |
|---|---|---|---|
| 1 | 首版门禁用**单行正则**匹配 `num_sql="..."`，而实现写的是 `"...>=?" + _PROBE`（`_PROBE` 在引号外）⇒ 假红 **0/6** | 门禁报红后**先查实现**：逐 `SignalSpec` 块验证 **4/4 都带** `_PROBE` | 断言改为**块级判定**（按 `SignalSpec(` 切块）。纪律：门禁断言写错 ≠ 实现错 |
| 2 | `kind_coverage` 的**分子**漏改、只改了分母 ⇒ 覆盖率会算出 **>100%** | 改完做一致性复核时，发现分子 SQL 跨两行被替换脚本漏掉 | 分子分母同时拼 `_PROBE` |
| 3 | 排除探针后 `MAX(latency)` 仍是 1.79e12 | 验证脚本做了**双守卫对照**（只排探针 vs 排探针+量纲）才暴露 | 定位到 `file_read` 脏行，新增 `sane_latency_where()` |

## 2. S3 · 技能提示词总量预算

### 2.1 改动落点

| 文件 | 改动 |
|---|---|
| `core/config.py` | 新增 `agent.skill_prompt_max_chars`（int，默认 12000，`<=0` 关闭） |
| `agent/pipeline_parts/skills.py` | `_build_skill_prompt_uncached` 内加**预估式**总量闸；超预算技能降级；记录 `_skill_budget_trimmed` / `_skill_budget_used` / `_skill_budget_limit` |
| `agent/pipeline_parts/skill_body_on_demand.py` | 新增 `build_terse_reference()`（**77 字符**极简引用） |

### 2.2 定位过程（为什么「单条太长」是错的判断）

初判以为是单条正文太长。实测发现 `skills.body_offload_cap` 默认 **600 字符**、单条早已 offload ⇒ **单条不是瓶颈**。

真因是 `build_head()` 生成的**头部摘要实测 2,449 字符/技能**且**无上限**：

| 量 | 值 |
|---|---|
| `变更影响分析` 正文 | 11,757 字符 |
| `offload_body(cap=0)` 返回的引用块 | **2,578 字符**（其中 head 2,449） |
| 30 个已发布技能正文合计 | 80,565 字符 |

⇒ 命中 6 个技能 ≈ 15K 字符，命中 14 个 ≈ 35K 字符 —— 与实测峰值 **48,813 字符（34,761 tok）** 完全吻合。

### 2.3 ⚠️ 关键教训：降级必须**真的变短**

第一版实现「超预算 → 直接用 `offload_body` 的返回值（带 head 的引用块）」，实测：

```
预算=12000 → 注入 19,616 字符
预算=0(不限) → 注入 19,616 字符     ← 完全一样
```

而 `_skill_budget_trimmed` **非空**（显示裁了 5 个）——**闸门触发了，注入量却一点没降**。这就是「看起来改了、实际没生效」的教科书案例。

**修正**：新增 `build_terse_reference()`，只给「技能名 + 正文长度 + fetch id」，**77 字符**（vs 2,578）。同时降级分支**跳过**元数据 / 轮次说明 / 资源清单（实测这三项 ≈ 830 字符/技能）。

修正后：**19,616 → 6,913 字符（-65%）**。

### 2.4 实测效果

| 场景 | 注入量 | 命中数 |
|---|---|---|
| 不限预算 | 19,616 字符 | 6 |
| 预算 12000 | **6,913 字符（-65%）** | **6（完全一致）** |

**命中结果不变**是硬约束：预算只影响「注入多少」，不影响「命中哪些」——否则 agent 行为会随预算漂移。门禁 C1 专门断言这一点。

### 2.5 降级不丢能力

被裁技能全部保留 `skill_body_fetch(id)` 通道（复用既有 `tool_result_offloads`，**未新造机制**）。门禁 B1/B2/B3 断言此类闭环。

### 3.3 一个执行教训

首版用 `while read` 从临时清单文件逐行删 `backups`：**循环没有执行**（输出为空、文件也未删），而我在同一命令块末尾把清单 `rm` 了 ⇒ **无从复核，看起来像成功**。
⇒ 改为 **Python `os.remove` + 逐条打印文件名与体积**，才可靠并留下证据。

> 通则：**破坏性操作不要用 shell 循环读清单文件**；解析/编码/路径任一处出问题都会静默变成"什么都没做"。用 Python 直删并逐条打印。

| **新代码独有特征** | `/api/capabilities/trace` 返回 **`excludes_probe: true`**；`/api/monitor/dashboard` 返回 **`llm_calls_biz` / `llm_calls_probe` / `llm_tokens_biz`** |

| 回归 | pytest **50 passed / 1 skipped / 0 failed**（与实施前完全一致） |

> 为什么必须用「新代码独有特征」而不是 HTTP 200：
> 旧代码的 `INSERT` 列清单里没有 `is_probe`，而该列有 `DEFAULT 0` ⇒ **旧代码同样能插入成功、也写 0**。光看「调用成功」或「行数增加」**无法区分新旧代码**。只有响应里新出现的字段（`excludes_probe` / `llm_calls_biz`）才是判据。

### 4.1 重启环节的一次事故（如实记录）

首次用「后台任务 + shell 重定向」起服务，验证通过后该后台任务被判 **failed (exit 1)**，而 8000 端口**仍在应答 200** —— 子进程成了孤儿并继续服务。

**真正的风险不是"服务挂了"，而是"服务活着、日志已瞎"**：
`logs/server_s0_s3_20261028.log` 最后写入 **23:57:29**，此后进程照常处理请求（含 `/chat/stream`），**一行日志都不再落盘**——父 shell 被回收后，子进程继承的 stdout 句柄失效，写入静默失败。端口探测、HTTP 200 这些检查**全都显示正常**，但出问题时已无任何可查证据。

**判据（已加入本仓重启纪律）**：不要只看端口和 200，要「**记日志文件大小 → 打请求 → 再测大小**」确认在增长。本次实测 2 次请求增长 **148 bytes** 才敢下结论。

**根治**：新增 `tmp/_serve.py` 启动器，进程自己 `open(log)` 并 `os.dup2(fd, 1/2)`，日志只依赖本进程持有的句柄，与父 shell 生死无关。重启用它启动后，日志已确认持续增长。

**最终进程态**：启动器 **89952** / 监听 **89260**（旧的 89636、83548、90072 均已清理）。
运行期日志：`logs/server_restart_20261028_2359.log`（**注意：UTF-8 无 BOM，读取需显式指定 UTF8，否则中文乱码——属读侧问题**）。

## 5. 未做项与理由

| 项 | 为什么不本轮做 |
