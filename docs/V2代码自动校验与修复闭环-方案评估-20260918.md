# V2 代码自动校验与修复闭环 — 方案评估（v2 修订）

> **修订说明**
>
> 本文件上一版基于已移除的 `org.wrxt.sysml.parser-0.0.1-SNAPSHOT.jar`。该 jar 存在两处硬缺陷：
> ① manifest 的 `Main-Class: org.xtext.sysml.parser.Parser` 与 jar 内实际类路径（`org/wrxt/sysml/parser/Parser.class`）**不一致**；
> ② 随附 `sysml.library` 是**空壳**——58 个 `.sysml` 全为 0 字节、`.index.json` 的 checksum 是空字符串的 SHA-256、`.kpar` 是只含 `project.json` 的合法 zip。
>
> 米爸已替换为 `checker.jar` + 完整标准库。**旧版结论整段作废。** 本版所有结论均来自对 `checker.jar` 的实机取证（2026-09-18），取证脚本与原始输出见文末 §10。

## 1. 结论先行

### 1.1 三层载体分工

| 环节 | 载体 | 依据 |
|---|---|---|
| **判错**（唯一事实来源） | **工具** `checker.jar` | 只有它掌握 SysML v2 真语法。AI 自judge不可信——实测工程里 84 个语法错，**肉眼看起来全部像对的** |
| **调用 / 解析 / 门控 / 确定性修复** | **硬编码** Python 模块 | 零 LLM 成本、确定性、可测试、可复现 |
| **残余修复** | **LLM**（带预算上限） | 只处理确定性规则覆盖不到的语义错 |
| **开发期复现取证** | **Skill** | 让后续会话能重跑同一套实验；**不进运行时链路** |

**核心判断：不要把校验做成"让模型自己调用的工具"。** 模型的自我校验不可信（它会认为自己写的 `refines` 是对的）。校验必须是**流水线里一个确定性的门**，模型只能看到门后的诊断。

### 1.2 三条最重要的实测结论

1. **`checker.jar` 完全可用**，词法/语法/语义三层都能检出，且退出码可直接做 CI 门禁（ERROR>0 → `rc=1`）。
2. **工程现有 V2 代码语法错误率极高**：6 个文件 / 19,270 B，**项目级 ERROR=47（语法 33 / 语义 14）**。根因是 **AI 在大量使用 SysML v1 风格语法**（`connector ... from ... to ...`、`refines`、`traces`、`satisfaction`、`if...then...else`）。
3. **纯正则修复能消掉 91% 的语法错**：3 条规则改写 25 处，项目级语法错 **33 → 3**，其中 `05_internal_block` 从 44 ERROR 直接清零。

### 2.2 调用契约（由字节码常量池还原，非猜测）

```java
if (!args[0].equals("-i")) {
    System.err.println("用法: SysMLValidator -i <file.sysml> [sysml.library路径]");
    System.exit(2);
}
String content = Files.readString(Path.of(args[1]));
if (new File("sysml.library").isDirectory())          // 第二参数优先，缺省回退 ./sysml.library
    SysMLInteractive.getInstance().loadLibrary(absPath);
SysMLInteractive.getInstance().parse(content);
List<Issue> issues = SysMLInteractive.getInstance().validate();
for (Issue i : issues) {
    if (i.getSeverity() == Severity.ERROR) { /* 计数 */ }
    else if (i.getSeverity() == Severity.WARN) { }
    System.out.printf("[%s] stdin:%d:%d: %s%n", sev, i.getLineNumber(), i.getColumn(), i.getMessage());
}
System.exit(errCount > 0 ? 1 : 0);                    // ← 实测行为
```

### 2.3 行为矩阵（全部实机验证）

| 场景 | rc | 行为 |
|---|---|---|
| `-i <file>`，无 ERROR | **0** | stdout 仅 `Reading ...` 噪声行 ✅ 可做门禁 |
| `-i <file>`，有 ERROR | **1** | 诊断行 + `Reading` 噪声 |
| 无参数 / 缺 `-i` | **2** | stderr 打印用法（GBK 编码） |
| `--help` / `-h` | 1 | `NoSuchFileException: --help`（被当文件路径，**不支持 help**） |
| `-i <目录>` | 1 | `AccessDeniedException`（**不支持目录输入**） |
| 第二参数指向不存在目录 | 1 | 不崩，正常输出（只是库没加载） |
| 空文件 | 0 | 0 诊断（**空文件是"通过"的**，不能当有效产出） |

### 2.4 输出格式

```
[ERROR] stdin:<行>:<列>: <消息>
[WARN]  stdin:<行>:<列>: <消息>
```

**三个必须知道的坑**：

1. **文件名硬编码为 `stdin`**（该工具原本从 stdin 读），**诊断里没有真实文件名**——多文件校验时靠自己按顺序对齐。
2. stdout 前面有 **100+ 行 `Reading <库文件路径>...` 噪声**（每次加载 121 个库文件全打一遍）。解析时必须过滤，否则诊断会被淹没（我第一次就是被这个坑了：ERROR 行排在 100 行之后，脚本只取前 40 行 → 详情全丢）。
3. stderr 有固定噪声：JDK 25 的 `sun.misc.Unsafe` 弃用告警（4 行）+ `log4j:WARN No appenders`（3 行）。**不是错误，不要据它判失败** —— 必须以退出码和 `[ERROR]` 行为准。

### 2.5 三层校验能力实证

| 层 | 探测样例 | 检出结果 |
|---|---|---|
| **词法** | `attribute q$ : Real;` | ✅ `no viable alternative at input '$'` |
| | 未闭合字符串 `"abc` | ✅ `mismatched character '<EOF>' expecting '"'` |
| | 中文标识符 `attribute 温度 : Real;` | ✅ `no viable alternative at character '温'` |
| | 文件带 UTF-8 BOM | ✅ `no viable alternative at character '?'` |
| **语法** | `first evaluate if C then cool;` | ✅ `mismatched input 'if' expecting 'then'` |
| | `connector c1 from a to b;` | ✅ `no viable alternative at input 'from'` |
| | 缺 `}` | ✅ `missing EOF at '}'` |
| **语义** | `attribute z : NoSuchType;` | ✅ `Couldn't resolve reference to Type 'NoSuchType'` |
| | `satisfy R1 by Body;`（Body 是 def） | ✅ `Must be a valid feature` |
| | 重名成员 | ✅ `[WARN] Duplicate of other owned member name` |

**编码层两条硬约束（生成器必须遵守）**：
- **文件不能带 UTF-8 BOM**（会被判词法错）
- **标识符只能 ASCII**（中文名直接词法报错）；Tab 缩进合法

### 2.6 性能

| 项 | 实测 |
|---|---|
| 单次校验（含库加载） | **4.0 ~ 6.1 s** |
| 其中库加载固定开销 | **约 2.3 s**（库路径不存在时降到 1.70 s） |
| 项目级合并校验（6 文件 / 19 KB） | **5.5 s**（vs 单文件 6 次 ≈ 28 s） |

**成本结论：合并校验既更准（消除跨文件伪错）又更省（1 次 vs N 次）。** 库加载是固定开销，文件越多人均越便宜。

口径：`sysml_models/ev_thermal_mgmt/` 六个文件，合计 19,270 B。

### 3.1 双层口径对照（重要）

| 口径 | ERROR | 语法错 | 语义错 | WARN |
|---|---|---|---|---|
| **单文件**（逐文件校验，合计） | **137** | 84 | 48 | 98 |
| **项目级**（6 文件合并后一次校验） | **47** | 33 | 14 | 48 |

**单文件口径有 2/3 是"伪错"** —— `00_master.sysml` 的 5 个 ERROR 全是 `Couldn't resolve reference to Namespace 'EVTM_*'`，因为那 5 个包在别的文件里。**评估与门禁必须用项目级口径**，否则会误报一片。

### 3.2 错误画像

| 文件 | 大小 | ERROR | 语法 / 语义 | WARN | 代表问题 |
|---|---|---|---|---|---|
| `00_master.sysml` | 804 B | 5 | 0 / 5 | 0 | 跨文件 import（单文件无解） |

| `02_architecture.sysml` | 4,502 B | 19 | **18** / 1 | 22 | `satisfaction satisfy` 非法前缀 |
| `03_use_cases.sysml` | 3,306 B | 16 | 3 / **11** | 0 | `extend X : Y;` + 跨文件类型引用 |

### 3.3 根因：AI 在用 SysML **v1** 语法写 v2

真实错误行（原文摘录）：

```sysml
// 01_requirements.sysml:66-71
requirement ReqBatteryTempDelta refines ReqBatteryTempRange;   // refines 非法
requirement ReqReliability traces ReqBatteryTempRange;          // traces 非法

// 02_architecture.sysml:112
satisfaction satisfy ReqBatteryTempRange by BatteryThermalManagement;  // satisfaction 非法

// 03_use_cases.sysml:69
extend energyMode : EnergySavingMode;                            // extend 后不能跟名字

// 04_activity.sysml:84-94
first evaluate if evaluate.isOverLimit then cool;                // guard 位置非法
first evaluate else passive;                                     // else 非法

// 05_internal_block.sysml:77
connector c_coolant_in from coolantIn to pump.inlet;             // v2 没有 from ... to
```

**这些错误的危险之处：肉眼全部像对的。** 正是这一点决定了"必须上真解析器"，而不是靠 prompt 里写"请注意语法正确"。

## 4. 合法写法速查表（实测验证，可作为生成器硬约束）

> 全部由"同一语义、多种候选写法逐个实机校验"得出。✅ = ERROR 0；❌ = 实测报错。

### 4.1 导入

| 写法 | 结果 |
|---|---|
| `import ScalarValues::*;` | ❌ `mismatched input 'import' expecting '}'` |
| **`private import ScalarValues::*;`** | ✅ |
| **`public import ScalarValues::*;`** | ✅ |
| `private import ScalarValues::Real;`（具名） | ✅ |

**权威旁证**：官方标准库 121 个文件共 **582 个 import，裸 import = 0**（`private` 539 / `public` 43）。**前缀是语法要求，不是 checker 的 bug。**

### 4.2 连接器（→ 修 `05` 的 44 个错）

| 写法 | 结果 |
|---|---|
| `connector c1 from a.p1 to b.p2;` | ❌ |
| **`connect a.p1 to b.p2;`** | ✅ **唯一合法形式** |
| `connector c1 connect a.p1 to b.p2;` | ❌ |
| `connector : FluidPort connect a.p1 to b.p2;` | ❌ |
| `connect c1 : FluidPort from a.p1 to b.p2;` | ❌ |

### 4.3 需求关系（→ 修 `01` 的 12 个错）

| 写法 | 结果 |
|---|---|
| `requirement R2 refines R1;` | ❌ |
| `requirement R2 traces R1;` | ❌ |
| **`requirement R2 :> R1;`** | ✅ |
| **`connection : Derivation connect R1 to R2;`** | ✅（需 `private import RequirementDerivation::*;`）**语义最正确** |
| `refine requirement R2 :> R1;` | ❌ |
| `derivation connect R1 to R2;` | ❌ |
| `@derive requirement R2 :> R1;` | ❌ `Cannot annotate Package` |
| `dependency from R2 to R1;` | ❌ |

**官方库证据**：`refines` / `refine` / `traces` / `trace` 在 121 个库文件中 **0 命中** —— 都是臆造关键字。需求派生的官方机制是 `DerivationConnections` 库里的 `abstract connection def Derivation` + `<derive>` metadata。

### 4.4 需求满足（→ 修 `02` 的 18 个错）

| 写法 | 结果 |
|---|---|
| `satisfaction satisfy R1 by body;` | ❌ |
| **`satisfy R1 by body;`** | ✅ |
| **`satisfy requirement R1 by body;`** | ✅（2 WARN） |
| **`satisfy R1 by body { }`** | ✅ |
| **`assert satisfy R1 by body;`** | ✅ |
| `satisfy R1 by that;`（在 part 体内） | ✅ |

⚠️ **`by` 后面必须是 feature（usage），不能是 definition。** 实测 `satisfy R1 by Body;`（`Body` 是 `part def`）报 `Must be a valid feature`——**这不是语法错，是语义错，纯文本替换修不了**。官方示例即用 `by that`。

### 4.5 顺序与条件行为（→ 修 `04`）

| 写法 | 结果 |
|---|---|
| **`first a1 then a2;`** | ✅ **合法**（我之前误判为 v1 风格，实测纠正） |
| `succession first a1 then a2;` | ✅ |
| `first a1 if cond then a2;` | ❌ `mismatched input 'if' expecting 'then'` |
| `first a1 then a2 if cond;` | ❌ |
| `succession a1 then a2;` | ❌ `expecting 'first'` |
| `if cond then a1 else a2;` | ❌ |
| **`action d; first a1 then d; first d then a2; first d then a3;`** | ✅ **用中间 action 替代 guard** |
| `first a1 then a2 when cond;` | ❌ |

> **待确定项**：带 guard 的条件 succession 的官方写法未找到（已试 6 种）。当前可用的替代是"中间 action + 多条 `first...then`"，但**语义上不等价**（丢失 guard 约束）→ 归入 §6 的"LLM 修复"或"人工确认"。

## 5. 修复闭环设计

### 5.1 确定性修复 vs LLM 修复的分界线

**判据：修复是否改变模型语义？**

| 类别 | 例子 | 处置 | 实测效果 |
|---|---|---|---|
| **纯文本改写（不动语义）** | `connector N from A to B;` → `connect A to B;` | **自动修** | `05`：44 → **0** |
| | `requirement X refines Y;` → `requirement X :> Y;` | **自动修** | `01`：12 → **0** |
| | `satisfaction satisfy` → `satisfy` | **自动修** | `02` 语法错 18 → 0 |
| **需要语义判断** | `satisfy X by <part def>;` → 需改成 usage | **只报告 / 交 LLM** | 结论：`Must be a valid feature` |
| **需要重写结构** | `first X if C then Y;` → 中间 action | **只报告 / 交 LLM** | 语义不等价，不自动改 |
| **未知形式** | `extend X : Y;` | **只报告** | 本轮未找到合法对应 |

### 5.2 三条必须遵守的铁律（由实测教训得出）

**铁律 1：不能用"ERROR 总数下降"判定修复有效。**
实测反例：`02_architecture.sysml` 删掉 `satisfaction` 前缀后，ERROR **19 → 37（变多）**。原因是语法错**遮蔽**了语义错——语法修好后，`satisfy` 后面的引用解析才真正开始执行，于是暴露出 37 条语义错。
→ **必须分"语法错 / 语义错"两路计数，只对语法路要求单调收敛。**

**铁律 2：必须先修语法，项目级校验才有效。**
实测：`04_activity.sysml` 的括号不匹配（`missing EOF at '}'`）导致其后的 `05` 的 package **没有被建立**，于是合并校验里 `00_master` 仍报 `Couldn't resolve reference to Namespace 'EVTM_InternalBlocks' / 'EVTM_Activities'`——而这 2 个包明明在合并文件里。
→ **语法错会级联污染后续文件的命名空间。语法修复是语义校验的前置条件。**

**铁律 3：`Reading ...` 噪声会淹没诊断。**
stdout 前 100+ 行是库加载日志。第一版解析脚本取前 40 行 → **ERROR 详情全丢，只剩计数**。
→ **解析器必须先过滤噪声行，再提取 `[ERROR]`/`[WARN]`。**

### 5.3 闭环形态

```
            ┌─────────────────────────────────────────────────────┐
生成        │ 1. LLM 生成 V2 代码（携带 §4 速查表作为硬约束）        │
            └───────────────────────┬─────────────────────────────┘
                                    ↓
判断        ┌─────────────────────────────────────────────────────┐
（确定性）  │ 2. 编码规范闸（零成本）                              │
            │    · 无 BOM · 标识符纯 ASCII · 裸 import → private   │
            └───────────────────────┬─────────────────────────────┘
                                    ↓
            ┌─────────────────────────────────────────────────────┐
            │ 3. 项目级合并 → checker.jar 一次校验                 │
            │    rc=0 → 通过；rc=1 → 分离语法错 / 语义错            │
            └───────────────────────┬─────────────────────────────┘
                                    ↓
修复        ┌─────────────────────────────────────────────────────┐
（预算内）  │ 4. 确定性修复（正则，仅 §5.1 第一类）→ 回第 3 步      │
            │    ⛔ 门控：最多 1 轮 · 语法错必须严格下降 · 否则停   │
            └───────────────────────┬─────────────────────────────┘
                                    ↓
            ┌─────────────────────────────────────────────────────┐
            │ 5. 残余语法错 → LLM 修复（带诊断 + 速查表）→ 回第 3 步 │
            │    ⛔ 门控：最多 1 轮 · 总耗时上限 · 仍失败则标记待人工 │
            └───────────────────────┬─────────────────────────────┘
                                    ↓
            ┌─────────────────────────────────────────────────────┐
            │ 6. 语义错：默认只报告（不自动改），随产出交付给人看     │
            └─────────────────────────────────────────────────────┘
```

### 5.4 预算门控（回答"不能无限校验"）

| 门控 | 阈值 | 依据 |
|---|---|---|
| 合并校验次数上限 | **1 次**（基线条） | 项目级 5.5 s，1 次足够拿到全貌 |
| 确定性修复轮次上限 | **1 轮** | 实测 1 轮即把语法错从 33 降到 3（-91%），边际收益已基本耗尽 |
| LLM 修复轮次上限 | **1 轮**，且仅当语法错 > 0 | 语义错不自动修 |
| 收敛判据 | 每轮语法错必须**严格下降**，否则立即停 | 防"修了更糟"的抖动 |
| 总耗时预算 | 建议 **≤ 30 s / 次生成**（≈ 5 次校验） | 单次 4~6 s；超预算即返回"未收敛 + 最后诊断" |
| 短路 | 代码内容 hash 未变 → 不重跑 | 编辑往返中大量重复校验 |

### 5.5 关键边界：**在哪修，不在哪修**

| 场景 | 处置 | 理由 |
|---|---|---|
| **生成流水线**（AI 刚产出、未入库） | **可自动修 + 重校验** | 产物本来就是待定稿的草稿 |
| **已有资产**（`sysml_models/` 里已入库的模型） | **只报告，不改写** | 那是米爸的模型资产，自动改写等于篡改 |

本次评估对 `sysml_models/` 的改写**全部发生在 `tmp/` 下的副本**，原文件未被触碰。

## 6. 实施步骤（建议）

### 阶段 1：确定性门禁（无需 LLM，收益最大）

1. 新增 `sysml_v2_check.py`（工程根，与 `model_quality.py` 同级）：
   - `check_project(files, *, lib_dir, timeout) -> CheckResult`
   - 内部：合并 → 写临时文件 → subprocess 调 `java -jar checker.jar -i <tmp>` → 解析 → 分类
   - 解析器要点：先过滤 `Reading`/`Finished`/`log4j`/`WARNING` 噪声；提取 `[ERROR|WARN] stdin:行:列: 消息`；按 `SYNTAX_SIGNS` / `SEMANTIC_SIGNS` 双路分类（两张特征表已在 §2.5 给出）
2. 新增编码规范闸（零成本，前置）：BOM、非 ASCII 标识符、裸 `import` 三项
3. 接入"生成后"钩子：生成 → 门禁 → 校验 → 报告

**预期效果（按本次实测外推）**：项目级语法错 33 → 3，ERROR 47 → 26。

### 阶段 2：确定性修复

4. 落地 3 条已验证规则（正则 + **逐条断言命中数**，命中 0 也不报错但要记录）
5. 落地门控与短路（§5.4）

### 阶段 3：LLM 修复（可选，需你先拍板）

6. 残余语法错（本次仅剩 3 条）→ 交给 LLM，prompt 携带：
   - 诊断原文（`[ERROR] stdin:行:列:消息`）
   - §4 速查表（合法/非法对照，few-shot）
   - 该行所在代码片段
7. 修复后**必须重跑校验**，不通过则回滚并标记待人工

### 阶段 4：生成端前置约束（预防 > 治疗）

8. 把 §4 速查表与两条编码约束（无 BOM / ASCII 标识符）**写进生成 V2 代码的 prompt**
   —— 这是把 84 个语法错从源头压下去的最有效手段，成本远低于事后修复。

### 阶段 5：把取证过程固化为 Skill

9. 校验器身份识别、调用契约、噪声过滤、双层口径、三个铁律 → 存为 skill，避免下次重新踩坑。

## 8. 未验证项与风险（如实披露）

### 8.1 未验证

| 项 | 说明 |
|---|---|
| **常驻进程模式** | jar 内 `org/omg/sysml/api/*`（Project/Query/Element API）+ Jupyter kernel + zeromq + okhttp 提示**可能存在服务化入口**，能把每次 2.3 s 的库加载摊薄。**未探测**。若能启用，单次校验可望从 4~6 s 降到 <1 s |
| **不收敛场景** | 本次只验证了"1 轮确定性修复"的收敛。**多轮 LLM 修复是否收敛未验证** |
| **语义错的修复** | 23 条残余语义错中，`by <def>` → usage 类需要引入新元素，**未设计具体修复策略** |
| **条件分支标准写法** | `first X if C then Y;` 的合法对应未找到（6 种候选全失败），当前替代方案**语义不等价** |
| **`.index.json` 作用** | 6.69 MB 索引文件是否被 `loadLibrary` 使用、能否加速，未探测 |
| **非法 UTF-8 字节** | `0xFF 0xFE` 场景 rc=1 但 **0 条诊断**（静默失败），原因未查 |

### 8.2 风险

| 风险 | 等级 | 说明 |
|---|---|---|
| **校验只覆盖语法语义，不覆盖"模型对不对"** | **高** | 一个 100% 通过校验的模型，仍可能是业务上错误的热管理设计。本闭环**不能替代**工程评审 |
| **合并校验会引入"合并伪影"** | 中 | 简单拼接 6 个文件后，`00_master` 的 `private import EVTM_X::*;` 与同文件内的 package 并存，可能产生 `Duplicate` 类 WARN。**需确认合并策略**（是否剥离主包的 import） |
| **`stdin` 无文件名** | 中 | 多文件诊断需按合并顺序反查行号 → 文件映射 |
| **jar 体积 126.79 MB** | 低 | 若需入版本库会显著增大仓库；当前它是**未跟踪文件**，建议先明确其归属（是否入库） |
| **语法实现与最新 OMG 规范可能有差异** | 中 | 本次结论全部基于 **jar 内实现**（`org.omg.sysml.model-0.61.0` / Build-Jdk 21 时代的语法）。若未来 OMG 放开裸 `import`，速查表需同步更新 → **速查表必须标注"以 jar 实测为准，随 jar 版本重新验证"** |

## 9. 需要米爸拍板的三件事

1. **是否自动修复已入库的模型？** 我的建议：**不改写，只报告**（本期实测严格遵守此边界）。
2. **是否上 LLM 修复轮？** 本期确定性修复已把语法错从 33 降到 3，**LLM 轮边际收益很小**。建议**先只做确定性门禁 + 修复**，观察一段时间再决定。
3. **是否投入探测常驻进程模式？** 若校验进在线链路（每次生成都跑），4~6 s 可能偏慢，值得探；若只做离线/CI 门禁，5.5 s 完全够用。
