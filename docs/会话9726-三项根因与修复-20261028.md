## 1. 问题 1：目标包「不存在」

### 1.1 真实证据（同一条会话，同一轮）

| 调用 | 时间 | 参数 | 回执 |
|---|---|---|---|

| #5512 `query_data_tree` | 16:26:50 | `parentId=2115359040604536832` | `items: []`（**它是空包，这是正常的**） |

⇒ **工具回执与最终结论直接矛盾**，且矛盾发生在"证据就在上一屏"的情况下。

### 1.2 三处可确定的成因（都不是"多加一句提示词"能治的）

1. **空 ≠ 不存在**：`items: []` 与"查不到这个节点"在回执里长得一模一样，回执又**不回显被查节点**，
   模型只能猜。本次它猜成了"不存在"。
2. **命中不显眼**：7 条同构 JSON 里要肉眼比对中文包名；`search_model_elements` 的命中也没有一句
   "命中即存在"的判定。模型漏读了。
3. **同义重查冲掉记忆**：`pageSize` 不同 ⇒ 去重键不同 ⇒ 短路不触发（`dup_short_circuits=0`），
   模型拿到的是"又一份空白"，于是把第 7 轮里出现过的目标包忘干净了。

### 1.3 修复

## 2. 问题 2：失败后没有持续完成

### 2.1 第一层：两个开关在服务端**实际是关的**

| 证据 | 值 |
|---|---|
| `GET /api/system/config`（重启前的进程） | `agent.todo_enabled=false`、`agent.harness_enabled=false` |
| `~/.workbuddy/mbse_config.json` | 323 字节，仅 6 个 `agent.*` 键，两值皆 `false` |
| 该文件 `mtime` | **13:23**，而会话 9726 发生在 **16:25–16:27** ⇒ 会话期间不存在"用户已开启"的落盘记录 |
| `tool_call_logs` 中 conv 9726 | **没有一次 `todo_write`**；`agent_todos` 表该会话 0 行 |

**为什么界面看起来是开的**：`35-ctxconfig.js` 里布尔项是
`<select onchange="ctxRecheck()">` —— `onchange` 只做**联动预览**，真正落盘要另外点
`💾 保存配置`（`index.html:1393`）。改了没点，界面显示"开启"、服务端读 `false`。

> 这一条的危害不是"配置没保存"，而是**安全闸静默失效**：有未完成的活也不会被拦，
> 而用户以为自己开了。⇒ 已修（见 2.3）。

### 2.2 第二层：即使开关开了，预算耗尽时也拿不到"待续清单"

`agent/auto_continue.py:decide()` 的闸顺序原来是：

```python
if not budget_left:            # ← 预算耗尽先返回
    return False, "token 预算已耗尽，停止续跑"
if _br >= _dr:                 # ← P1-1 的"降级收尾"永远进不到（条件恰恰是预算快用完）
    return False, "... ⇒ 降级收尾"
```

conv 9726 的阶段原文正是 `detail = "token 预算已耗尽，停止续跑"`
⇒ `build_degrade_notice()`（待续清单）**一次都没被调用**
⇒ 用户看到的正是"做到一半突然断了"——P1-1 要治的就是这个症状。

### 2.3 修复

| 改动 | 文件 | 判据 |
|---|---|---|
| 布尔开关**改完立即落盘 + 回读校验 + 失败回退界面** | `static/js/mods/35-ctxconfig.js`（`ctxAutoSaveBool`） | 回读不一致就报错（不信 PUT 的 200）；失败回退 `data-prev` |
| 全局保存同样回读核对 | 同上（`saveCtxConfig`） | toast 文案从"已保存"改为"已回读核对" |
| **闸门生效值随消息落库** | `agent/pipeline_parts/stream.py` + `common.py:gates_snapshot()` | 卡片 `exec.gates` 含三项开关 + **读取的配置文件绝对路径** |
| 诊断信息 fail-safe | `stream.py:_gates_safe()` | 第一版写成未定义函数名 ⇒ conv 9728 落库 `NameError`、卡片退化成 `[]`（**本轮自己踩的坑，已登记为判据 D3b**） |
| 降级闸顺序修正 | `agent/auto_continue.py:decide()` | 预算耗尽时给出的原因**必须含「降级收尾」** |

### 2.4 真机复验

## 3. 问题 3：为什么调用了这么多次

### 3.1 真实数字（`orch_stream_events` 阶段原文）

```json
{"calls": 18, "distinct": 18, "tokens_used": 316885, "token_budget": 300000,
 "dup_short_circuits": 0, "timeouts": 0, "tool_retries": 3, "stop_reason": "token_budget"}
```

- 撞的是 **token 预算**，不是"工具调用次数上限"（模型在答复里写错成后者 ⇒ 已由 `69403fe` 修文案）。
- `distinct = calls = 18` 说明**没有一次被去重挡住**；其中 #5513/#5514 与 #5501/#5502 是同义重查。
- 单轮上下文随轮次重复发送 ⇒ 18 次调用 ≈ 6 轮，每轮都把全量历史 + 大 JSON 回执重发一遍，
  token 近似二次增长。

### 3.2 修复

1. **语义去重**（§1.3）：只差 `pageSize` 的重查现在会被短路，并且回喂的是**那份含目标包的结果**。
2. **回执瘦身**：判读句把"7 条 JSON"压成"一行清单 + 明确结论"，模型不必再为确认一个名字爬第二遍树。
3. **停止原因双向透传**（`69403fe` 已有）：`exec_notices` 给用户、`messages` 给模型，明确禁止它再归因为"次数上限"。

### 3.3 未做（如实登记）

- 树查询仍**逐层展开**（`query_data_tree` 是平台侧工具，无 `depth` 参数）⇒ 深树仍要 N 次调用；
  本轮只把"重复的第二次"省掉，没有把"必要的第一次"变便宜。
- `loop_token_budget=300000` 未调整。是否该调大属**产品取舍**（调大=更少分段、更贵），需实测再定。
