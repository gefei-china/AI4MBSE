## 0. 先给结论

**生成器负责「写」，校验器负责「判」。两者在当前链路里没有接线。**

- 生成器**不知道**校验器的规则 —— 它的语法约束只有 `prompt.py` 里约 200 字的笼统要求，
  知识文档里的规则一条都不在里面；
- 校验器**不在生成现场** —— 唯一的自动语法检查在**最后一步**（写智源前），
  从"LLM 生成"到"人工采纳"之间全程无人校验。

**实测代价**：一次真实建模会话产出的 156 行模型，**语法错 0、语义错 7**，
7 条全是同一类**肉眼完全看不出问题**的写法 —— 若没有校验器，它们会一路走到写智源那一步才炸。

```
LLM 生成 ──► 抽代码 ──► 投影视图 ──► 版本入库 ──► 人工采纳 ──► 写智源(远程 check)
    ▲              ▲          ▲            ▲            ▲           ▲
    │              │          │            │            │           └─ 唯一的自动校验点
    └──────────────┴──────────┴────────────┴────────────┘
                    这一段全程无校验（本次 7 条 ERROR 就诞生在这里）
```

## 1. 「生成器」是什么？—— 不是一个东西，是三层

| # | 层 | 形态 | 位置 | 会执行动作吗 |
|---|---|---|---|---|
| ① | **提示词侧** | **pipeline 里硬编码的提示词片段**（既不是工具，也不是技能） | `agent/pipeline_parts/prompt.py::_build_model_code_req`（`prompt.py:86`） | 否，只是文本 |
| ② | **平台侧** | **系统工具**（`tools.kind='http'`, `status=active`） | `tools.id=37` → `zhiyuan_sysmlv2_gen` → 智源 `POST /api/project/ai/sysmlv2/gen` | 是，真实 HTTP 调用远程平台 |
| ③ | **编排侧** | **技能（skill）** | `skills.id=95`「智源平台管理」，其 `allowed_tools` 含 `zhiyuan_sysmlv2_gen` | 否，是**数据驱动的内容注入层**，自己不执行动作 |

### 1.1 ① 的真实全文（这是 AI 生成 V2 代码时唯一的语法侧约束）

```python
# agent/pipeline_parts/prompt.py:86
def _build_model_code_req(self, intent: str) -> str:
    """建模类意图：要求 LLM 在正文末尾输出完整 SysML v2 (KerML) 模型代码块..."""
    ...
    return ("\n【建模输出要求】当前为系统建模任务，请在正文末尾以天然语言围栏代码块输出一份完整、"
            "可直接导入建模工具的 SysML v2 (KerML) 模型代码，代码块统一使用 ```sysml 语言标签包裹；"
            "内容覆盖：包(package)、块定义(part def/part usage)、接口(interface def/usage)、"
            "需求(requirement def)+满足关系(satisfies)、以及必要的结构或行为语义；"
            "代码用于自动投影 BDD/IBD/REQ 等视图与前端「代码/视图」切换查看，请确保代码语义完整、可解析。\n")
```

**约 200 字，不含任何具名语法规则**（没写 `private import` 必填、没写 `satisfy` 只能引用 usage、没写 `doc` 用 `/* */`……）。

> ⚠️ **顺手发现的一处**：这段提示词里写的是 `满足关系(satisfies)` —— `satisfies` 是 **SysML v1** 的说法；
> v2 是 `satisfy … by …`。**提示词自己就在用 v1 术语**，与 `docs/` 里"AI 主要失分点是用 v1 语法写 v2"的结论方向一致。

**为什么改它收益最大**：它是**流式与非流式两条路径的唯一共用注入点**
（`stream.py:992`、`execute.py:215` 调同一个方法）—— 改一处，两条路径同时生效。

### 1.2 形成完整链路要三层都有

单看任一层都不完整：**skill 编排 + tool 执行 + pipeline 硬编码**。
`tools.id=38`（check）、`39`（import）、`40`（project_list）、`41`（project_tree）与
`9711`（`mbse_pull_ingest`，内部工具）同属这套编排。

## 2. 「校验器」是什么？—— 三处，其中两处真在用、一处零引用

| # | 校验器 | 调用形式 | 位置 | 在链路里的角色 |
|---|---|---|---|---|
| ① | **本地 `checker.jar`** | `java -jar checker.jar -i <模型.sysml> sysml.library` | 工程根目录（**不进版本库**，见根 `README.md`「离线校验器资产」） | ⛔ **零引用** —— 全仓 Python 代码 **0 处**调用，只在离线取证时用 |
| ② | **智源远程 check** | 系统工具 `zhiyuan_sysmlv2_check`（`tools.id=38`） | 智源 `POST /api/project/ai/sysmlv2/check`（OMG SysMLInteractive 解析器） | ✅ 可用，由 skill 编排调用 |
| ③ | **入库门禁里的硬编码调用** | `norm_apply.py::push_version_to_zhiyuan`（`norm_apply.py:471`，check 在 `:500`） | 写智源**之前** | ✅ **当前链路里唯一自动执行的语法检查** |

### 2.1 三者的分工（不要互相替换）

| | 本地 `checker.jar` | 智源 `sysmlv2_check` |
|---|---|---|
| 时机 | 可在**生成后立刻**跑 | 只在**写入前**跑 |
| 依赖 | 离线、零配置（自带 `java-runtime/` + `sysml.library/`） | 需要 `base_url` + `token`，有网络/鉴权风险 |
| 能力 | 词法 / 语法 / **语义**（ECS 校验），**分路计数** | 词法 / 语法 / 语义，返回结构化错误列表 |
| 定位 | **早发现**（前置闸门） | **最后一道保险**（还能校验智源侧的上下文） |

> 结论：**不是替代关系，是前后两道闸门**。前置闸门做好后，第 ③ 处应当几乎不再触发失败。

## 3. 「生成器 × 校验器」的关系 —— 生产者 vs 质检员

```
┌──────────────────────────────┐        ┌──────────────────────────────┐
│  生成器（写）                 │        │  校验器（判）                 │
│  ────────────────            │        │  ────────────────            │
│  ① 提示词：_build_model_code_req│  ？   │  ① 本地 checker.jar（0 引用）│
│  ② 工具：zhiyuan_sysmlv2_gen  │ ────►  │  ② 远程 zhiyuan_sysmlv2_check │
│  ③ 技能：智源平台管理(skill 95)│  断点   │  ③ 门禁：norm_apply.py:500   │
└──────────────────────────────┘        └──────────────────────────────┘
        ▲                                            │
        │            【闭环缺的那一段】                │
        └──────────── 错误列表 → 带错重生成 ◄──────────┘
              [ERROR] file:line:col: message
```

### 3.1 三层含义

**① 职责不同，不可互相替代。**
生成器管"写得快、写得全"，受 LLM 能力 + 提示词约束；
校验器管"写得合不合法"，受**规范 + 实现**约束，与 LLM 能力强弱无关。
（实测支撑：100% 通过校验的模型仍可能是业务上错误的热管理设计 —— 校验器不替代工程评审。）

**② 当前的核心问题是"信息不对称"，不是"能力不足"。**
本次实测里，知识文档 §7「EV TMS 完整模型示例」**被检索命中并注入了提示词**（命中第 1 名），
AI 的正文也明显读懂了它（用了串联单回路、膨胀水箱置于泵前、12 L/min 量级估算等同一套思路），
**但仍然写出了 7 条非法语句**。

原因不是 AI 不懂，而是：
- 检索注入的是**"参考材料"**（system prompt 的「检索数据区」），不是**"硬约束"**；
- 而 `_build_model_code_req` 那段**每轮都注入**的静态模板里，一条语法规则都没有。

→ **规则必须写进"每轮必注入"的位置**，否则能不能生效靠检索运气。

**③ 两者的接口就是"错误列表"，这决定了闭环的形状。**
校验器输出的 `[ERROR] stdin:143:35: Cannot override a binding feature value`
**正是生成器最需要的再生成输入**：

```
生成 ──► 校验 ──► 有 ERROR？ ──► 把 (代码 + 错误列表) 一起回喂 LLM 重生成 ──► 再校验 ──► 收敛
                        └── 无 ERROR ──► 放行（投影视图 / 入库 / 采纳）
```

**这个环现在缺一段**：错误列表没有任何地方流向生成器。

**7 条 ERROR 全部指向 `satisfy` 那几行，而且这些代码肉眼挑不出任何毛病**：

```sysml
// 第 129-131 行（requirement 实例，显式绑了 subject）
requirement coolingCapacityReq : CoolingCapacityRequirement {
    subject = thermalSystem;
}
// 第 143 行 —— 报错就在这里

按 `docs/SysML-v2-知识文档与校验器-工程落地集成指南.md` §2.2 的门禁判据：
**`rc=1` 且 `n_syntax=0` → 报告但不阻断**（属语义路，很多语义错改文本解决不了，须人判断）。
本次这 7 条**恰好是"能靠改文本解决"的那一类**，见 §4.5。

### 4.4 真因定位（A/B/C/D 对拍，全部单文件口径、统一 `cwd=工程根`）

| 变体 | 改动 | ERROR | 结论 |
|---|---|---:|---|
| **A** | 原样 | **7**（语法 0/语义 7） | 基线 |
| **B** | 把 `satisfy r by thermalSystem.coldPlate;` 的**限定名去掉** | **14**（0/14） | ❌ 更糟。新增 7 条 `Couldn't resolve reference to Element 'coldPlate'` —— `coldPlate` 只存在于 `part def BatteryThermalSystem { … }` 体内。**真因不在限定名** |
| **C** | B + 把 `attribute x : Power = 5;` 改量写法 `:> ISQ::power` | **14**（0/14），但 **WARN 10 → 7** | 量写法确实消掉了 3 条类型绑定 WARN（独立有效），但没解决主体问题 |
| **D** | **删掉 4 处 `subject = thermalSystem;`**（保留 `satisfy` 限定名） | **0** ✅ | **真因确认** |
| **E** | D + 量写法（即最优组合） | **0** ✅，WARN 7 | 最终可用写法 |

**真因**：`satisfy r by <路径>;` 的语义动作是**给 requirement 绑满足对象**（本质是对 `subject` 的绑定）——
当 `requirement` 实例体内**已经**用 `subject = …` 显式绑定过，再 `satisfy` 就冲突 → `Cannot override a binding feature value`。

**修法（二选一）**：

```sysml
// ✅ 推荐：让 satisfy 负责绑定，不写 subject —— 实测 0 ERROR
requirement coolingCapacityReq : CoolingCapacityRequirement;
satisfy coolingCapacityReq by thermalSystem.coldPlate;

// ✅ 或者：只绑 subject，完全不用 satisfy
requirement coolingCapacityReq : CoolingCapacityRequirement { subject = thermalSystem; }
```

> ⚠️ **不要靠"去掉限定名"绕过** —— 实测 ERROR 从 7 **涨到 14**（见变体 B）。
>
> 证据文件：`tmp/v2docs/_ab_{A_原样,B_去限定名,C_B且量写法,D_去subject绑定,E_去subject且量写法}.sysml` 及同名 `.txt`。

## 5. 这次实测对"生成器 × 校验器"的三条启示

**① 校验器的价值不是"拦得住"，而是"看得见"。**
这 7 条 ERROR 的共同点是**肉眼无感**。工程上真正危险的从来不是"一眼错的代码"，
而是"看起来全对、实际不合法"的代码 —— 它们的排查成本远高于生成成本。
**没有校验器，"AI 建模能不能用"就只能靠人的经验判断。**

**② 只报告总数会误判修复效果。**
本次 `n_syntax=0 / n_semantic=7`。而集成指南 §4 已记录一条反例：
某文件删掉非法前缀后 ERROR **19 → 37（变多）**，因为语法修好后原本被遮蔽的语义错才暴露。
**所以修复效果只能看"对应那一路"的计数，不能看 ERROR 总数。** 本次的 7 → 0 之所以可信，
是因为它是**同一条错误消息**在同一批行上归零（不是总数下降）。

**③ 规则要"每轮注入"，不要指望检索。**
第 4.2 节证明了检索命中质量很好（第 1 名就是同领域示例），第 4.3 节证明了**照样出错**。
检索负责"给材料"，硬约束负责"划红线" —— **两件事不能互相替代**。
这也是集成指南把「L0 硬约束卡」列为 **P0（性价比最高）** 的原因。
