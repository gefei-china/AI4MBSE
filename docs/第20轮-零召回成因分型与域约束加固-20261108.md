# 第 20 轮 · 零召回成因分型与域约束加固

日期：2026-11-08　分支：`eval/eval-baseline-wiring`

## 0. 结论先行

| 结论 | 依据 |

## 1. 起点：一个被推翻两次的判断

上一轮我在分析「NVIDIA auto-ontology 可否接入」时提了 P0：借鉴它的 `check_answerable` 做覆盖度判定。
米爸追问：「如果提出的问题不在知识库就会判为不合格吗，这样会不会带来负面作用」。

为回答这个问题，我拿 `query_trace`（6530 条）统计，发现零命中 473 条 = **7.24%**，
并抽到一条关键样本：

```
错误 3.1：混淆 part 和 ref part     ← hit=0
```

而 `document_chunks` 里 `LIKE '%ref part%'` 有 **17 个 chunk**（OMG SysML v2 规范原文）。
⇒ 知识在库里。若把"零命中"判成"知识缺失"，这条会被归因于**知识库没有**，
于是没人会去查召回 —— 一个合理但完全错误的产品解释。

**但接下来我连着推翻了自己两次**，过程比结论更有用：

| # | 我的假设 | 怎么被推翻 |
|---|---|---|
| 1 | 零召回兜底 `_retry_with_keywords` 没生效，因为 `high_signal_terms` 要求"含中文"，`part`/`ref` 被过滤 | 假设**部分成立**（实测该函数返回空元组），但**不是根因** —— 兜底未启动不等于召回失败 |
| 2 | 存在系统性召回缺失 | 假设**错**：直接 `hybrid_search('ref part')` → 5 条；`hybrid_search('混淆 part 和 ref part')` → 5 条，内容正确 |
| 3 | —— | 查 `query_trace.detail` 发现**同一查询 4 分钟内记录了 20 / 0 / 20** ⇒ 是抖动，不是缺失 |
| 4 | 抖动的成因 | 复跑：`domain='satellite_comms'` **稳定 0 条**，`domain=None` **稳定 5 条** |

`detail` 里 `glossary: ["PA"]` —— 与 `_retry_without_domain` docstring 记录的
2026-10-16 事故**完全同因**：Glossary 把 `PA`（part 的缩写）判成卫星通信术语
→ `force_domain='satellite_comms'` → 跨域过滤把正确内容全滤掉。

而真实库里：`SELECT COUNT(*) FROM document_chunks WHERE domain='satellite_comms'` = **0**。

## 2. 缺陷：域约束被施加到一个没有数据的域

```
glossary            : 能力中心 15（库内 0 chunk） / satellite_comms 3（0） / sysml_norm 6 ✓ / thermal_mgmt 1 ✓
glossary_concepts   : satellite_comms 30（0） / loitering_munition 12（0） / sysml_norm 6 ✓ / unknown 2 ✓
```

任何被这些术语 `force_domain` 的查询，**第一步必然零命中**。

平台原本已有 P1-7 的 `_retry_without_domain`（零命中后撤域重查一次），但它是**事后补救**：

- 多付一轮检索（零命中是 7.24% 的常态，不是异常）；
- 若撤域后恰好命中别的域，撤销分支根本不触发 ⇒ **召回被污染**，且无人知晓。

### 修法（`agent/rag.py`）

新增 `_domain_usable(conn, domain, scope_docs, inc_dep)`：在施加域约束**之前**，
按与 `hybrid_search` **完全相同的过滤口径**（`doc_names` / `lifecycle_status`）问一次
「该域在目标范围内有没有 chunk」，没有就不施加。

| 设计选择 | 理由 |
|---|---|
| 不删词表 | 删词表是数据治理（会随文档导入回退）；代码层加固对所有域自动生效 |
| 不维护域名白名单 | 判据是"域内有没有数据"，数据驱动 |
| 与 `hybrid_search` 同口径 | 少带 lifecycle 子句会出现「校验说有、实际过滤后没有」的假阴性 |
| 不做进程内缓存 | 文档导入/下线会改变结论，缓存即 stale；`domain=? LIMIT 1` 在 7k 行表上 <1ms |
| 校验失败返回 True | 加固手段不该成为新的拒答来源 |

配套：`_retry_without_domain` 的命中打 `recall_via='domain_retry'`（此前不标记，
"域误判被救回"在结果侧完全不可见，无法统计误判率）；被放弃的域写进
`trace.detail.domain_skipped`。

### 实测效果

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `错误 3.1：混淆 part 和 ref part` | 0 条（`domain=satellite_comms`） | **20 条**，`vec 0.74/0.751` |
| trace 可观测字段 | 只有 `domain=all`（丢失原本想施加什么域） | `domain=all` + `domain_skipped='satellite_comms'` |
| 同一查询稳定性 | 4 分钟内 20 / 0 / 20 | 稳定 20 |

## 3. 分型信号（`agent/retrieval_gap.py`）

零命中时判四态，**只写 trace，不参与任何决策**：

| 态 | 判据 | 典型样本 |
|---|---|---|
| `recall_miss` | 连续**短语**在库内且文档频次 ≤50 | `混淆 part 和 ref part` → 命中 `ref part`（df=17） |
| `grounding_miss` | 词被 `ontology_types` / `intent_taxonomy` 认识，但正文无依据 | 「转发器」 |
| `knowledge_gap` | 短语与词都不在库 | 宽带载荷 / 红烧肉怎么做 / 今天北京天气 |
| `indeterminate` | 只有**孤立单词**在库 | Python（在 OMG 规范里顺带提及） |

**为什么必须是四态**：`Python` 在规范里出现，若按"单词命中"就断言 `recall_miss`，
等于把域外问题"救"成有答案 —— `query_keywords.py` 记过同一个坑（gate 拒答准确率 1.000 → 0.800）。
第四态是在说"目前分不出来"，硬塞进前三态就等于用猜的结论掩盖缺失的区分能力。

实测 10/10 与预期一致。两个踩过的实现坑已写进注释：

1. **短语必须 2-gram 优先**：原先"越长越靠前"，`错误 3.1：混淆 part 和 ref part` 切出 7 段后
   前 5 个 3-gram 用尽配额，能命中的 `ref part` 排第 10 位、根本没被探到 → 误判 `indeterminate`。
2. **短语与词必须各有独立配额**：共用 5 个名额时同样把 `ref part` 挤掉。

### 接线时的口径陷阱

第一版把"零命中"判成 `not chunk_hits`，结果**有答案的查询也被打标**：

| 查询 | 真实命中 | `chunk_hits` | 说明 |
|---|---|---|---|
| 宽带载荷 | 16（route=mixed） | 0 | 命中在 `graph_results` |
| 红烧肉怎么做 | 0 | 0 | 但 `vector_results` 过滤前有 20 条垃圾 |

trace 的 `hit_count` 用的是第三种表达式（`_hit_src`）。**同一语义三份口径** ⇒
打标与统计永远对不上。修法：分型计算移到 `_hit_src` 定稿之后，与 `hit_count` **同源**。

## 4. 判据（这是本轮最该记住的部分）

新增 2 条门禁：359 → **361**（`verify_rag_domain_guard` local、`verify_retrieval_gap_shadow` **pr**）。

`verify_rag_domain_guard.py` **16/16**，核心是 P2：对夹具里每个域同时问
`_domain_usable` 与 `hybrid_search(domain=X)`，断言两者**逐项相等**。
任一侧单独改动（校验漏 lifecycle、检索新增过滤）都会红 —— 这是"两套实现口径必须同源"的可执行版本。

`verify_retrieval_gap_shadow.py` **14/14**，核心是**反向判据**：

- **P8** `_gap_info` 在 `rag.py` 里除「赋值」「写 detail」外**不得出现**；
- **P9** 不得被任何 `if` / `return` / `continue` 消费。

如果只断言"分类正确"，那么把分类接进门禁**反而全部通过** —— 等于用门禁为"误伤用户"背书。
所以判据必须反向写：**断言的是"它不会影响回答"，不是"它判得准"**。

变异自证（两个都真的翻红）：

| 变异 | 结果 |
|---|---|
| M1 `_phrases` 恒返回 `[]`（砍掉强证据来源） | P2 红 |
| M2 把单词命中当 `recall_miss` | P3 红（`Python` 被判成 `recall_miss`） |

> M2 我最初写成「去掉 `df_cap` 约束」，实测**不生效** —— `df_cap` 只作用于短语探针，
> 而 `Python` 的病因是"没有短语命中"，不是"频次约束太松"。变异选错靶子会假装通过。

## 6. 没做 / 待决

1. **60+ 条指向空域的术语没有清理** —— 那是数据治理（删了之后文档导入可能又回来），
   本轮只做了代码层加固。建议运营侧确认 `satellite_comms` / `loitering_munition` /
   `能力中心` 是"还没有语料"还是"域定义废弃"。
2. **`top_score` 仍是混合口径**（`graph` 的 conf 与 `chunk_hits` 的 score 写在同一个字段），
   不能当统一阈值用。本轮未动，因为它牵涉面大于本次范围，已记入 §1 的旁证。
3. **分型只在零命中时算**，7.24% 的样本才付这份开销。若要统计全量分布，需要另加抽样。
4. **`trace_query` 的 `except Exception:` 静默兜底**（`glossary.py:244`）仍在 ——
   写库失败时连记录都没有，意味着 7.24% 这个**分母本身偏小**。真实零命中率不低于 7.24%。
5. `verify_no_mutation_residue` 提示 4 个历史变异备份文件不一致
   （`pipeline_parts/tools.py` / `migrations/columns.py` ×2 / `routers/sysml_versions.py`），
   与本轮无关，属历史遗留，未处理。
