# 编排 partial 补齐决策机制 — 对标调研与方案

> 2026-10-22 · 承接 `AgentLoop优化方案-对标行业标杆-20261007.md`  
> 那份管的是**单次 Agent 轮内**的 loop；本文管的是**跨子任务、编排层**的"该不该重跑"。  
> 触发：米爸「是否重跑需要一个健全的机制」。

---

## 0. 结论先行

**一句话**：主流平台没有一家做"失败了就重试"，全都做「**病因分类 → 动作分级 → 预算封顶**」三段式。  
我们缺的不是重试能力，是**分类**。

四条结论：

1. **`partial` 现在是一个标签承载三种完全不同的病**（瞬时故障 / 客观缺口 / 质量不足 / 阻塞），  
   而这四种的"可重跑性"完全相反。一刀切重跑 = 对其中一半纯烧钱。
2. **我们其实已经有 80% 的底座**：`orch_checkpoint` 的 `policy_classify` 已经实现了 LangGraph  
   的"幂等复用 + 只重跑失败分支"，`_MAX_ATTEMPTS=5` 就是 `maxTurns` 的等价物。  
   **只缺两件**：① partial 无病因分类；② 收尾前无外部验证闸。
3. **健全机制的关键不是"重试几次"，而是"什么时候判定为需要重跑"**。  
   Anthropic 的 harness 分析指出：**agent 失败模式里有整整三分之一是 verification 问题** ——  
   agent 认为自己完成了，其实没有。反过来同样成立：子任务**自报** partial，也可能其实够用。
4. **不建议引入 LangGraph / 新框架**。我们的 `orch_checkpoint` 已经是同一套语义的轻量实现，  
   缺的部分是纯函数级别的增量，**P0 可以做到零风险**（只加纯函数 + 改汇总文案，不动执行路径）。

## 1. 五家平台怎么做的

### 1.1 Claude Code：`stop_reason` 七值 → 五种处置

这是最值得抄的一份设计。核心是**把"模型为什么停"拆成七个值，分别给不同处置**，  
而不是笼统地"看它停没停"。

| `stop_reason`                   | loop 动作                                                     |
| ------------------------------- | ----------------------------------------------------------- |
| `tool_use`                      | 忽略该值，只看 content 里有无 tool_use 块 → 执行工具 → 继续                  |
| `end_turn`                      | 正常完成 → 结束                                                   |
| `max_tokens`                    | **可恢复信号**：escalate 上限 → 注入 continue → 重试，**最多 3 次** → 才抛给用户 |
| `model_context_window_exceeded` | reactive compact 压缩历史 → 重试（继续跑）                             |
| `refusal`                       | 生成错误消息结束，**不重试**（模型主动拒绝，自动重试无意义）                            |
| `stop_sequence`                 | fall through 到 content 检查（实际很少命中）                           |
| `pause_turn`                    | loop 层**无处理**（源码中找不到分支）                                     |

三条可直接借用的设计：

**(a) 完成判据不看 `stop_reason`，看 content 有无 tool_use。**  
`stop_reason` 只用于错误 UX，不作为分派依据 —— 因为它的语义太细，而"还有没有工具要调"  
才真正决定 loop 走不走。

**(b) `max_tokens` 是三级恢复，不是终止。** 顺序固定、强度递增、次数封顶：

```
escalate（上调输出上限） → inject「[Output token limit hit, continue]」→ 最多 3 次 → 抛给用户
(MAX_OUTPUT_TOKENS_RECOVERY_LIMIT = 3)
```

**(c) Stop hook 有最终否决权。** 即使没有 tool_use、`stop_reason` 也不需要恢复，  
还有最后一道闸：Stop hook 返回 `decision: block` ⇒ **loop 不许结束，必须再跑一轮**。  
它能实现的策略正是我们最缺的那种：

> 「测试没跑完不许结束」「还有相关改动没提交不许结束」

完整的"结束判定"要过三闸：

```
① content 里没有 tool_use 块
② stop_reason 不需要任何恢复路径
③ 没有任何 Stop hook 投否决票
→ 才真正 completed，交还控制权
```

**(d) `maxTurns` 是硬上限，且命中要留痕。** 超限时往历史 append `[max_turns_reached]`，  
SDK 返回 `error_max_turns` —— **用户能明确知道"是安全阀停的"，不是"干完了"**。

### 1.2 LangGraph：checkpoint + 幂等 + 只重跑失败分支

| 机制                        | 要点                                                                                                 |
| ------------------------- | -------------------------------------------------------------------------------------------------- |
| durable checkpoint        | 每个 superstep 边界快照全量状态；三档 durability：`sync`（写后才下一步）/ `async`（边写边跑，有崩溃窗口）/ `exit`（只在退出时写，**无中途恢复**）  |
| **pending writes ledger** | 并行分支部分失败时，**成功分支的产出存为 pending writes**，resume 只重跑失败分支                                              |
| RetryPolicy               | 默认 `max_attempts=3`、`initial_interval=0.5s`、`backoff_factor=2.0`、`max_interval=128s`、`jitter=True` |
| 副作用包装                     | 外部可见操作（发邮件、扣款）必须包 `@task`，resume 时从 checkpoint 返回值而**不重复执行**                                       |
| 恢复粒度                      | **从"节点开头"恢复，不是从节点中间** —— 这是它要求节点幂等/确定性设计的根因                                                        |

> 关键一句（官方文档）：resume 会因为 checkpoint 重放而**重复执行 LLM 调用、API 请求**，  
> 所以工具调用必须幂等。这是所有"能续跑"的系统都要付的账。

### 1.3 OpenAI Agents SDK：默认就设栅栏

一句对照最能说明"默认值就是产品"：

| SDK               | `max_turns` 默认                              | 姿态       |
| ----------------- | ------------------------------------------- | -------- |
| Claude Agent SDK  | **无上限**（`max_turns` / `max_budget_usd` 都不限） | 信任你自己围栏  |
| OpenAI Agents SDK | **10**，超限抛 typed `MaxTurnsExceeded`         | 先围栏，你再去掉 |

同概念、相反默认，**都不算错**，但如果你没读过这一行就选了其中一个，就是背了个不知道的生产风险。

它对"命中上限"的处置要求很明确：

> 达到 `max_turns` 时**不要静默报错**，应返回**标明 partial completion 的结构化结果**，  
> 而不是丢掉任务或返回空。

### 1.4 Devin / AutoGPT：这里踩过的坑最多

| 平台                | 失败模式                                                                                              |
| ----------------- | ------------------------------------------------------------------------------------------------- |
| Devin             | Plan→Act→Observe→Correct 递归循环；两大失败模式 **loop of death**（同一修复反复失败）与 **cost with no ceiling**（无上限烧钱） |
| AutoGPT / BabyAGI | ① 无完成度判据的无限任务生成 ② 记忆汤 ③ 误差复利 ④ 无上限成本                                                              |

沉淀下来的铁律：

> **「run until done」→「run within limits」—— 循环的每个维度都要有天花板。**

### 1.5 Anthropic：harness = budget + brake + witness

| 要素          | 含义                 |
| ----------- | ------------------ |
| **budget**  | 成本/回合上限            |
| **brake**   | 危险动作前的闸（权限门）       |
| **witness** | **验证"它说自己做完了"这件事** |

最关键的一段（决定本文方案的核心逻辑）：

```
CLAIM（模型声称完成） → VERIFY（对照目标验证：跑测试 / 验收标准 / judge model）
                        → 实际达成了吗？
                           ├─ 没达成 → 带着"缺口叫什么"回去接着干
                           └─ 达成 → 结束
```

三条硬话：

- **「模型不再请求工具」和「任务完成了」是两个不同的声明，只有一个值得拿去交付。**
- 判据的选择**本身就是设计工作**：代码看测试/构建（agent 争不过的检查）；开放任务看**事先承诺的验收标准**。
- judge model 可以用（判据清晰时与人工评审一致率不低），但**不能是同一个模型给自己盖章**。

## 2. 提炼：六条可执行原则

| #      | 原则                      | 来源                                                     | 对我们的含义                           |
| ------ | ----------------------- | ------------------------------------------------------ | -------------------------------- |
| **P1** | **先分类，再动作**             | Claude Code`stop_reason` 七值→五处置                        | `partial` 必须拆子类，否则无法决定动作         |
| **P2** | **完成判定要有外部锚**           | Anthropic witness / Stop hook                          | 不能只信子任务自报；优先用产物存在性、校验器结果         |
| **P3** | **重跑必须幂等，且只重跑缺口**       | LangGraph pending writes / `policy_classify` 的 `reuse` | 绝不允许"整轮重来"，已完成的一律复用              |
| **P4** | **同一故障动作强度递增、次数封顶**     | Claude Code `escalate→inject→give up`（3 次）             | 重跑要有"第 2 次加大预算"这一级，而不是同样参数重来 3 遍 |
| **P5** | **上限是消防栓，不是解法；命中必须说清楚** | OpenAI `error_max_turns` / `[max_turns_reached]`       | partial 汇总**绝不能读起来像 full**       |
| **P6** | **fail-safe 方向 = 停**    | AutoGPT boundedness / 本仓 `auto_continue` 既有选择          | 交付"半成品 + 明确缺口清单" > 无限重试          |

## 4. 诊断：我们的 `partial` 其实是四种病

用真实数据支撑这个判断（会话 9587，2026-10-22）：

```
4 个子任务自报 status=partial  →  orchestrated_status=partial
但最终汇总 21628 字，章节 1.1/1.2/2.x/3.x/4/5 齐全，结尾完整代码块
```

**自报 partial ≠ 产出不可用。** 反过来，历史上也出现过"自报 full 但 reflection 62 分"。  
这说明：**自报的状态与真实可用性之间，相关性比想象的低**（P2 的直接证据）。

| 病因                | 典型证据                                                     | 能否重跑     | 重跑有无效              | 处置                    |
| ----------------- | -------------------------------------------------------- | -------- | ------------------ | --------------------- |
| **transient**（瞬时） | 工具错误 `timeout` / `rate_limit` / `connection reset` / 5xx | ✅ 能      | **高**（重跑大概率必成）     | 退避重跑，只重跑该子任务          |
| **gap**（客观缺口）     | 声明的必需产物 key 缺失；`sysmlv2_check` 未通过；必需字段空                 | ✅ 能      | **高**（有靶子，知道缺什么）   | 带缺口说明重跑，只重跑该子任务       |
| **quality**（质量不足） | 仅 `reflection.passed=false` / `score=62`，无客观缺口           | ❌ **不能** | **低**（无靶，重跑退化为随机）  | 不重跑；降级可见 + 给出改进建议     |
| **blocked**（阻塞）   | 缺关键信息 / 需用户拍板 / 不可解错误（权限、外部依赖不可用）                        | ❌ **不能** | **零**（重跑 100 次也一样） | 转 `ask_user`，生成明确澄清问题 |

> 这张表是本文的核心。**"是否重跑"的答案不取决于 partial 的严重程度，取决于它有没有靶子。**

## 5. 推荐方案：分类 → 决策 → 执行 → 验证

### 5.1 整体结构

```
编排收尾
  │
  ├─① 聚合三态（既有 summarize_status + apply_quality_gate）
  │
  ├─② 【新增】病因分类 classify_partial()  —— 纯函数
  │      对每个非 full 子任务判定 transient/gap/quality/blocked + 证据
  │
  ├─③ 【新增】补齐决策 decide_fill()  —— 纯函数
  │      四类 × 四闸 → (action, reason, budget_hint)
  │      只有 transient / gap 会产生 requeue
  │
  ├─④ 【新增】执行补齐 apply_fill()
  │      复用 orch_checkpoint.prepare_resume/apply_resume
  │      已 done 的一律 reuse（P3 幂等）
  │      升级序列：第1次原参 → 第2次加大预算 → 第3次人工
  │
  └─⑤ 【新增】收尾闸 completion_gate()
        补齐后仍 partial ⇒ 汇总**开头**写清缺口 + 建议（P5：不许读起来像 full）
```

### 5.2 分类器：判据优先级（外部锚 > 自报）

这是 P2 的落地。**按序取第一个有证据的**：

| 优先级 | 判据来源                                                      | 命中则判为         | 说明                    |
| --- | --------------------------------------------------------- | ------------- | --------------------- |
| 1   | 工具层 `error_kind ∈ {timeout, rate_limit, connection, 5xx}` | `transient`   | 硬证据，最可靠               |
| 2   | 子任务声明的必需产物 key ∉ 实际产出                                     | `gap`         | 硬证据（比"自报"强一个量级）       |
| 3   | `sysmlv2_check` 等校验器返回未通过                                 | `gap`         | 硬证据                   |
| 4   | 错误信息含"缺少/需要确认/无权限/不可用"且无产物                                | `blocked`     | 半硬                    |
| 5   | 仅 `reflection.passed=false`，以上全无                          | `quality`     | **弱证据 → 判"不重跑"**      |
| 6   | 子任务自报 `partial`，以上全无                                      | `quality`（保守） | 自报是最弱证据，**不单独构成重跑理由** |

> 第 6 条是最重要的取舍：**"自报 partial 但没有任何客观缺口" ⇒ 不重跑。**  
> 理由：没有靶子的重跑是随机扰动，反而可能把一份可用的产出改坏（误差复利）。

### 5.3 决策器：四道闸

沿用 `auto_continue` 的纯函数 + fail-safe 风格（**任何输入异常 ⇒ 不重跑**）：

| 闸          | 判据                                   | 默认                                     |
| ---------- | ------------------------------------ | -------------------------------------- |
| ① 子任务级次数   | 该子任务已重跑次数 ≥ `N`                      | `N=2`（第 3 次转人工）                        |
| ② run 级总次数 | 该 run 补齐轮次 ≥ `_MAX_ATTEMPTS`（复用既有 5） | 复用                                     |
| ③ 成本闸      | 本 run 已耗 token 超过补齐预算                | 建议 `原 run 消耗 × 30%`                    |
| ④ 空转闸      | 同一子任务、同一缺口、连续两次 ⇒ 停                  | 复用 `normalize_step` + `is_spinning` 思路 |

### 5.4 升级序列（对齐 Claude Code 的三级恢复）

| 轮次    | 动作                                                              | 对应 Claude Code     |
| ----- | --------------------------------------------------------------- | ------------------ |
| 第 1 次 | 原参数重跑 + 注入缺口说明                                                  | `inject「continue」` |
| 第 2 次 | **加大预算**（子任务 `max_tokens` / `max_tool_rounds` 上调一档）+ 注入"上次为何失败" | `escalate`         |
| 第 3 次 | **放弃自动，转人工**：交付半成品 + 明确缺口清单 + 建议动作                              | `give up after 3`  |

> 为什么第 2 次要加大预算：同一参数重跑，成功率不会更高。  
> Claude Code 对 `max_tokens` 的处理正是"先上调上限，再注入继续"，**不是**"同样上限再来一次"。

### 5.5 收尾闸（对齐 Stop hook）

在汇总生成**之前**插一道检查，等价于 Stop hook 的否决权：

| 检查                       | 不通过时                                |
| ------------------------ | ----------------------------------- |
| 是否还存在 `gap` 类未补          | 先走补齐（受四闸约束）                         |
| 补齐后是否仍 partial           | 汇总**开头**写：「本次 N 项未达要求：X（原因），建议 Y」   |
| 是否只有 `quality`/`blocked` | 不补齐，但汇总开头写明 + 给用户一个可点的动作（重跑 / 补充信息） |

**硬要求（P5）**：`orchestrated_status=partial` 的汇总，**第一段必须出现缺口说明**。  
现状是缺口信息散落在卡片 bullet 里（`cards.py` 有 `orchestrated_status == "partial"` 分支），  
正文却读起来像完成 —— 这正是"失败被记录成成功"的文案版。

## 6. 落地路径（按 收益÷成本 排序）

| 批次       | 内容                                                          | 改什么                                          | 风险     | 可验证性       |
| -------- | ----------------------------------------------------------- | -------------------------------------------- | ------ | ---------- |
| **P0-a** | `partial_policy.py` 纯函数（`classify_partial` / `decide_fill`） | **新增文件，不接生产路径**                              | **零**  | 单测 + 变异自证  |
| **P0-b** | 汇总文案前置缺口说明                                                  | `stream.py` / `orchestration.py` 的汇总字符串      | 低（纯文案） | 快照对比       |
| **P1**   | 接 requeue（仅 transient/gap），**先 dry_run 观察**                 | 收尾段插 `apply_fill`（默认 `dry_run=True`，只记日志不重跑） | 中      | 观察日志 N 天再开 |
| **P2**   | 升级序列（第 2 次加大预算）                                             | 补预算传递                                        | 中      | A/B 对比成功率  |
| **P3**   | 子任务级 attempt 记账                                             | 表结构（`orch_tasks.attempt_count`）              | 中      | 迁移脚本       |
| **不做**   | quality 类自动重跑 / 整轮重来 / 无上限重试                                | —                                            | —      | —          |

P0 两批能在**完全不动执行路径**的前提下交付，先拿到"分类的可观测性"，

### 8.3 真实数据验证（全库，非构造样本）

> `quality` 22 个里有 **21 个是老数据（无协议摘要）** —— 只有 `result` 文本、没有任何

### 8.4 判据覆盖的真实教训：**输入方不止「用户」**

首版正则把"用户/您"当成唯一输入方，实测全库后暴露 **7 个有摘要的 quality 里 5 个其实是 blocked**：

| 真实措辞                 | 首版判定    | 应为          | 漏判原因        |
| -------------------- | ------- | ----------- | ----------- |
| 「需人工确认(L1)」          | quality | **blocked** | 没写"人工确认"    |
| 「请**客户**确认二者层级关系」    | quality | **blocked** | 只认"请用户"     |
| 「请**客户方**提供正式清单」     | quality | **blocked** | 同上          |
| 「由**业务方**补充量化判据」     | quality | **blocked** | 只认"负责人/工程师" |
| 「客户名单/车型…**输入缺失待补**」 | quality | **blocked** | 没写这个句式      |

修正后 `blocked` 从 3 → **8**，`quality` 从 28 → 22。**这一类漏判的代价是"把缺输入的任务  
说成质量不足"——用户拿不到可执行的动作项（该去补什么资料），只会觉得系统在敷衍。**

同批还修了一处 `gap` 漏判：`未产出**任何可校验的**视图代码`（中间夹修饰语）——  
原正则写死 `未产出(代码|模型)` 匹配不到，导致该补的不补。已放宽为 `未产出.{0,16}(代码|…)`。

> 教训记为：**正则判据必须在全库上回放一遍才算写完**。  
> 只在 1 个会话上调通的判据，覆盖面大概率只有一半。

### 8.5 已知边界（不装作支持）

- **非流式路径（`orchestration.py`）不自动重跑**：它没有 `_run_subtask` 的上下文快照与  
  事件通道，重跑只能另起一次完整编排（成本翻倍且重复汇总）。该路径只做分类 + 缺口前置说明。
- **补跑不做跨批次依赖修复**：若 t5 依赖 t4 而 t4 本身 full 但产出不完整，补 t5 仍可能失败。  
  这类情况会被计入"仍失败"并转人工，不会无限重试。

### 8.7 端到端实测（真实编排请求，2026-10-22 19:xx）

用会话 514 发真实编排请求（3 个子任务：需求条目化 → BDD 骨架 → validate 校验修复），  
**全链路 18m51s 跑通**：

| 环节        | 实测输出                                                                                      |
| --------- | ----------------------------------------------------------------------------------------- |
| t1 需求条目化  | 182s · `full`                                                                             |
| t2 BDD 骨架 | 250s · **`partial`**（"本轮工具轮次耗尽，未调用 sysml_v2_validate"）                                    |
| t3 校验修复   | 189s · `full`                                                                             |
| 分类事件      | `未完成子任务病因分类：执行中断 1 / 客观缺口 0 / 待用户输入 0 / 质量不足 0`                                           |
| 决策事件      | `自动补齐 1 项：t2`                                                                             |
| 执行事件      | `补齐 t2 完成（11078 字）`                                                                       |
| 最终状态      | `orchestrated_status` **partial → full**                                                  |
| card_data | `fill_causes: [{key:"t2", cause:"transient", evidence:"…工具轮次耗尽，未调用 sysml_v2_validate…"}]` |

**这条链路的价值**：`partial` 不再是终点。以前 t2 报 partial，用户拿到的是一份  
"部分完成"的汇总；现在系统自己识别出"只是没跑校验"，补跑一次，最后交付 `full`。

**同时实证了一个设计权衡**（如实记下）：t2 的中断原因是"未调用 validate"，  
而 t3 的任务定义本来就是"运行 validate 并修复" —— 从产出角度，t3 已经覆盖了 t2 的缺口，  
补 t2 在某种意义上属于重复劳动。

本方案的选择是**仍然补**，理由：

- `transient` 是执行中断，**中断点不确定**，产出可能不完整（t2 补齐后 11078 字，  
  与中断前的产出长度差异未知），补一次换来"确认完整"；
- `gap` 才应用"下游覆盖闸"（`decide_fill(covered=...)`）—— 因为 `gap` 明确指向"某一步没做"，  
  交给下游是编排设计本意；`transient` 指向"执行被打断"，语义不同；
- 成本有天花板：`fill_max_tasks=2` + `fill_deadline_s=300`。

> 若后续希望更省，可把下游覆盖闸扩展到 `transient` 且 `artifacts` 非空的情形  
> （本次实测：t2 有 1 份 artifacts）。这是一个**可调的取舍**，不是缺陷。

### 8.8 第二次端到端（修复后复验，14m55s）

第一次 E2E 暴露了一处**自相矛盾**：整体 `orchestrated_status=full`、`fill_filled=['t2']`，  
但 `plan` 里 t2 的 `summary.status` 还是 `partial`、`ui_summary` 还是"因工具轮次已达上限…"。

根因：**同一个语义在三个字段各存一份，补跑只更新了其中一个**。  
前端徽章读 `summary_status`、卡片文案读 `ui_summary`、存档读 `summary` —— 少更任何一处都会矛盾。  
（这与本仓已记的「同一个数字在四个环节各写一份，最后必然对不上」是同一族问题。）

修复后第二次真实编排复验：

| 字段                    | 修复前（消息 4780）            | 修复后（消息 4782）                           |
| --------------------- | ----------------------- | -------------------------------------- |
| `orchestrated_status` | full                    | full                                   |
| t2 `summary.status`   | **partial** ← 矛盾        | **full** ✓                             |
| t2 `ui_summary`       | 旧的"因工具轮次已达上限…"          | "上一轮中断在『代码已生成但未经校验器确认』这一步，本轮已把缺口闭环…" ✓ |
| t2 `summary_status`   | full                    | full ✓                                 |
| 事件序列                  | 分类→补齐 1 项→补齐完成（11078 字） | 分类→补齐 1 项→补齐完成（10111 字）                |

> 顺带记一条**判据脆弱性**：`gap` 的识别依赖 `summary.risks` 存在。  
> 同样的"未调用校验器"文本，如果没有 risks 段，会被判成 `quality`（不可补）。  
> fail-safe 方向是对的（不乱补），但这说明**协议里的 risks 是必填而非可选** ——  
> 生成侧若省略它，补齐能力就会静默退化。

## 9. P2/P3 补齐：升级序列 + 子任务级记账（2026-10-22 续）

上一轮留下两项未做：**升级序列**（第 2 次换策略）与 **子任务级 attempt 记账**（D5/P3）。  
本轮落地，且 **D5 以零表结构改动完成** —— 复用既有的 `agent_tasks.retry_count`。

### 9.1 为什么能零成本做 D5

`agent_tasks` 早就有 `retry_count` 字段（真库分布：257 个为 0、14 个为 1），  
replanning（P1 T1 补跑）一直在用它。所以：

- **不建新表、不迁移、不改 schema**；
- 语义统一为「这个子任务总共被重试过几次」，**补齐与 replanning 共享同一个 2 次天花板** ——  
  避免出现「replanning 补 1 次 + 补齐再补 2 次」的合计超限。

> 原先判断"D5 要动表结构、放 P3"是**看漏了**：以为需要新字段，实际已有字段可用。  
> 记一笔：动手前先 `PRAGMA table_info` 看现有列，别急着设计新表。

### 9.2 记账为什么**前置**（fail-safe 向停）

补跑前先 `retry_count + 1`，跑完不收回：

| 放哪            | 后果                                                  |
| ------------- | --------------------------------------------------- |
| 成功后 +1        | 补跑**异常/超时**就不计数 ⇒ 同一任务可被无限重补（Devin 的 loop of death） |
| **前置 +1**（采用） | 失败也计数 ⇒ 最多 2 次，之后转人工                                |

### 9.3 升级序列（对齐 Claude Code 的 escalate → inject → give up）

| 轮次     | `retry_count` | 动作                                                              |
| ------ | ------------- | --------------------------------------------------------------- |
| 第 1 次  | 0             | 原参补跑，指令只讲"缺口是什么、先补哪一步"                                          |
| 第 2 次  | 1             | **升级**：指令追加「上一次以相同方式补跑未成功，说明原做法本身不可行，请**更换策略**（换工具/换分解方式/缩小范围）」 |
| 第 3 次起 | ≥2            | 不再补，转人工，并在汇总里写明原因                                               |

为什么需要第 2 次升级：真机两次 E2E 的 t2 **都**因「工具轮次耗尽」中断 ——  
同样参数再来一次，大概率还是耗尽。第 2 次必须换策略（例如把 validate 提到第一步、  
不要从零重新查标准库）。

真实数据演示（取消息 4780 l t2）：

```
retry_count=0 → 补（第 1 次，escalate=False）
retry_count=1 → 补（第 2 次，escalate=True）
      【升级说明】上一次以相同方式补跑未成功，这说明原做法本身不可行。
      本次请**更换策略**（换工具/换分解方式/缩小范围），不要重复上一次的做法。
retry_count=2 → 不补：该子任务已补 2 次，达上限（2 次），转人工
```

## 10. missing[] 升为第一判据（2026-10-22 续，生成侧 + 判定侧同改）

上轮我说“`gap` 判据依赖模型写 `risks`，建议把 risks 加进生成侧硬约束”。
实测数据把这个判断**修正了一半，也翻出一个更大的漏子**。

### 10.1 数据修正：risks 覆盖率其实是 100%

带协议摘要的 22 个 partial/failed，**全部写了 risks**。所以脆弱点不在 risks，
而在另外 21 个**老数据根本没有 summary**（那是历史包袱，改不动，只能靠 `evidence_thin` 标注）。

### 10.2 真正的漏子：`missing` 是最强判据，却只被用了 3 次

协议本来就支持 `summary.missing`（`subtask_protocol.py:395`，仅 partial 时保留），
而 `classify_partial` **完全没读它**。这 3 次的内容恰好是正则最难稳抓的：

```
（会话 3987 t4）missing = [
  't3 骨架原文与既有包结构',
  '模型校验结果（未执行 sysml_v2_validate）',   ← 夹在修饰语里，正则会漏
  '结构视图的视图类型确认']
（会话 3987 t1）missing = ['客户提供的利益相关方名单', '客户具体车型信息']
```

⇒ **模型显式声明的缺口清单，比从正文里猜可靠得多。**

### 10.3 改动

**判定侧**（`classify_partial`）：`missing` 升为**第一判据**，先于一切文本猜测：

| missing 内容 | 判定 | 理由 |
|---|---|---|
| `模型校验结果（未执行 validate）` | `gap` 可补 | 自己能补，靶子明确到条目 |
| `客户提供的利益相关方名单` | `blocked` 不补 | 外部输入，补跑拿不到 |
| （无 missing）| 走原有 transient/gap/blocked/quality 链 | 冗余兜底 |

**新增 `evidence_thin` 信号**：既无 missing 又无 risks ⇒ 标记"证据不足"。
为什么不改 cause：**宁可标"证据不足"让人复核，也不要为了显得有据就乱补**。
该信号透出到进度事件与 `card_data.fill_causes`，用户能看到"其中 N 项按最保守口径判定"。

**生成侧**（子任务 prompt 契约）：`missing` 从"顺带一提"升为硬约束：

```
**status=partial 或 failed 时必须写 missing[]**，逐条列出缺什么（缺的产物/数据/步骤/结论）；
missing 与 risks 的分工：**missing=缺什么，risks=已有什么风险及缓解建议**，两者都要写。
特别注意：缺**自己就能补的**（如某一步校验没跑）与缺**需要客户/用户/外部提供的**
（如名单、口径、指标区间）都必须如实写进 missing，不要因为「怕显得没做完」而省略。
```

> 只改判定器不改 prompt = 让模型继续不喂最关键的那个字段。两侧必须一起改。

| gap | 4 | **7**（+3，正是那 3 个带 missing 的）|

### 10.5 踩到的一个**假判据**（值得记）

给 missing 写变异自证时，E6b 一开始用 `S_MISSING_EXTERNAL` 做样本，**变异后仍然判 blocked** ——
因为那个样本的 `risks.advice` 里已写了"请客户提供名单"，**被另一条判据兜住了**，
变异体行为根本没变，等于假通过。

修法：另造一个 `S_MISSING_EXTERNAL_ONLY`（advice 写中性的"资料齐备后再复核"），
**只有 missing 能把它判成 blocked**，并加一条 E6c 反向确认原版确实靠 missing 判出。
这同时证明了一件事：**判据之间有冗余兜底是好事，但变异自证必须用"单路径样本"**。
