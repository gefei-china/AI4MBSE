# 持续自主执行能力：机制诊断与落地方案

> 日期：2026-10-28
> 问题：**Agent 遇到一个问题就终止，而不是持续推进到任务完成**——这能力如何实现？
> 性质：**诊断 + 标杆调研 + 方案**（未实施）
> 数据来源：`mbse.db` 真实生产数据（只读统计）+ `agent/` 代码走查 + Anthropic 官方工程文档

## 一、问题定性：不是"没有循环"，是"每个出口都写了 stop"

本工程已有的持续执行设施（都已实现，不是空白）：

| 设施 | 位置 | 作用 |
|---|---|---|
| `_LoopGuard` | `agent/loop_guard.py` | token 预算 / 失败轮上限 / 重复调用检测 / `undo_dup_count` |
| 自主续跑外层循环 | `stream.py:4524` `while True` | round 1 原始请求；round 2+ 由评估器放行 |
| 完成度评估器 | `agent/auto_continue.py` + `autopilot.py` | LLM 判 done / needs_user / next_step |
| 四道续跑闸 | `auto_continue.decide()` | 次数 / 墙钟 / token / 空转 |
| 收尾修复轮 | `stream.py:5117` `lacks_deliverable` | 缺交付物时追加提示再生成 |
| 编排检查点 | `agent/orch_checkpoint.py` | save / load / touch / bump_attempt / policy_classify |
| 工具级重试 | `tool_resilience.retry_exec` | T1 级重试 |
| 写操作回灌 | `loop_protocol.write_ops_digest` | 已成功写操作显式注入（修"虚构未完成"） |

**所以问题不在"没有循环"，而在：每个判定点的失败方向都默认指向"停"。**

## 二、诊断：四层结构各缺一块（含真实数据）

### 2.1 触发层：最常见的失败模式被"闸"整类排除

评估器有**五重触发条件**（全满足才评估）：

```python
if (_ac_cfg["enabled"] and not dry_run
        and (exec_tools or _cont_input or _cont_cue or _awaiting)   # ← 关键
        and _auto_continues < _ac_cfg["max"]):
```

其中 `exec_tools` 非空 = **本轮必须调过工具**。旧注释的理由是：

> 「纯问答轮没有『剩余步骤』可言，且省评估器成本」

**但这个前提是错的**。实测最常见的失败恰恰是：**模型把剩余步骤写进正文、却没执行**（例如"建议下一步执行校验"）——这类轮次 `exec_tools` 为空 ⇒ **整类不评估**。

2026-10-27 已补两个更宽信号（`_cont_cue` / `_awaiting`），但：
- `_cont_cue` 要求用户输入**以续作动词开头**
- `_awaiting` 依赖 `looks_awaiting_permission` 命中**中文标记词表**（26 个短语）

⇒ 模型换个说法（"是否需要""我可以先…也可以…"）就漏检。

### 2.2 计划层：**完全没有计划外化**（结构性缺失）

| 检查 | 结果 |
|---|---|
| `grep -rn "todo_write\|TodoWrite\|plan_steps"` | **无结果** |
| DB 中 TODO/plan 类表 | 无（`agent_tasks` 是编排用、`flow_run_steps` 是 flow 引擎、都不是会话内待办） |

**后果**：评估器判"是否完成"时，**只能读答复正文猜**还剩什么。
⇒ 这正是它把「建议下一步」误判成「已完成」的结构性原因（它没有对照清单可查）。

**标杆对照**：Anthropic 官方给出的第一大 failure mode 是
> "**Claude declares victory on the entire project too early**"
对策是 **feature list file（结构化 JSON）+ 自验证通过才算 passing**。

### 2.3 障碍层：只有"工具级重试"，没有"任务级恢复"

| 层 | 现状 |
|---|---|
| 工具级 | `tool_resilience.retry_exec`（T1：同 key 补跑一次） |
| 任务级 | `replan_decisions` 表存在，但**全库只有 1 行** ⇒ 几乎从未触发过 |

⇒ 工具报错会重试；但"**这条路走不通**"（凭据失效、包不存在、API 不返回）时，**没有换路径/降级/重规划**，只能停下来告诉用户。

**实测样本**（msg 3173）：
> 评估器给出的 next_step 是「刷新平台访问凭据并确认目标工程标识后，重新调用…」
> —— 这是一个**可恢复的障碍**，但系统里没有任何"换凭据路径 / 降级查工程列表"的策略。

### 2.4 判定层：**"完成"的定义权在模型手里**（最致命）

用 4 条真实历史答复跑评估器（只读，未改库）：

| msg | 答复实质 | 评估器判定 | `decide()` | 问题 |
|---|---|---|---|---|
| **3985** | 「本视图代码尚未校验…**建议**下一步执行校验」 | **`done=true`** | 停 | 把「可执行动作降级成建议」当成**已完成** |
| **2731** | 「若需生成报告…请**转交**对应建模/变更分析 Agent」 | **`done=true`** | 停 | 把「责任转嫁」当成**已完成** |
| 3970 | 「是否现在推进到结构视图，还是先定稿需求视图？**确认后我继续**」 | `done=false` + `needs_user=true` | 停（转澄清卡） | 有最优解却二选一，被当成"必须问人" |
| 3173 | 「口径以 g/(kW·h) 还是 kg/(kW·h)」 | `done=false` + next_step | **continue=True** | ✅ 机制判对了 |

**结论**：机制本身能工作（3173 证明了），但有两处系统性偏差：

1. **评估器 prompt 规则 1 的漏洞**：
   > 「用户请求中的每项要求都已满足，或**剩余工作只是可选润色/增强** ⇒ done=true」
   —— "建议下一步做校验"被归入"可选增强"，而它其实是**请求范围内的必做步骤**。
2. **`needs_user` 门槛虽标注"要严"，但实际操作中被判宽** —— 只要答复里出现"还是/是否"，就容易被判成"需拍板"。

**代码自认的缺口**（`stream.py:5238` 原文）：
> `⚠️ 这只纠正「虚构未完成」；「虚构已完成」由工具自身回执 + 技能纪律承担。`

⇒ **"虚构已完成"没有任何机制承担**，只靠提示词纪律。这正是 Anthropic 官方第一大 failure mode。

### 2.5 资源层：12% 的停是"没预算继续"

`orch_stream_events` 里 89 条评估结论的分布：

| 结论 | 次数 | 占比 |
|---|---|---|
| 续跑（任务未完成） | 41 | 46% |
| **判停：任务已完成** | 31 | **35%** |
| **判停：token 预算耗尽** | **11** | **12%** |
| 转澄清卡（needs_user） | 6 | 7% |

- 「任务已完成」31 次里必然含误判（4 样本中 2 例误判）
- **token 预算耗尽 11 次**是**物理硬停**：agent 不是不想继续，是**没预算了**
- 续跑上限默认 3 次（`auto_continue_max`），墙钟 600s（`auto_continue_deadline_s`）

### 2.6 补充：两个"该触发却没触发"的同源缺陷

| 机制 | 触发条件 | 缺陷 |
|---|---|---|
| 完成度评估器 | `(exec_tools or _cont_input or _cont_cue or _awaiting)` | 纯文本轮可能整类跳过 |
| **收尾修复轮** | `if tool_injected and _lproto.lacks_deliverable(...)` | **同样要求"调过工具"** ⇒ 纯文本"我建议下一步…"不触发修复 |

⇒ 两个机制犯同一个错：**假设"没调工具 = 没活可干"**。

## 三、标杆产品怎么做的（Anthropic 官方原文）

### 3.1 核心文献：《Effective harnesses for long-running agents》

Anthropic 工程博客直接列出 **4 个 failure mode + 对策**：

| Problem（官方原文） | 对策（Initializer Agent） | 对策（Coding Agent） |
|---|---|---|
| **Claude declares victory on the entire project too early** | 建立 **feature list 文件**（结构化 JSON，端到端描述每个特性） | 会话开始先读 feature list，**一次只做一个特性** |
| Claude leaves the environment in a state with bugs or undocumented progress | 初始 git repo + **progress notes 文件** | 开始先读 progress notes + git log，跑基础测试抓未记录 bug；**结束写 commit + progress 更新** |
| **Claude marks features as done prematurely** | 建立 feature list 文件 | **Self-verify all features. Only mark features as "passing" after careful testing.** |
| Claude 要花时间搞清怎么跑起来 | 写 `init.sh` | 开始先读 `init.sh` |

来源：https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents

> **这三条正好逐条对上本工程的三个缺口**：
> "declares victory too early" = §2.4 的 done=true 误判
> "marks features done prematurely" = 同族
> 两者的解法都是 **feature list + 自验证**，而不是"改进评估器 prompt"

### 3.1.1 ★ 官方最重要的一条：**给 agent 一个能跑的 pass/fail 检查**

Claude Code 官方 best practices 原文（逐字）：

> "**Claude stops when the work looks done. If it has nothing to run that tells it whether the work
> actually *is* done, "looks done" is all it has to go on.** In practice that makes you the test suite,
> and every mistake sits there until you happen to notice it."
>
> "If you give it something that comes back **pass or fail**, Claude can **close that loop itself**.
> It makes the change, runs the check, and if something broke it reads the output and fixes it
> before running the check again."

来源：https://code.claude.com/docs/en/best-practices

**这句话精确描述了本工程的现象**：模型说「建议下一步执行校验」= 它手里**没有"能跑的检查"**
⇒ "looks done" 就是它唯一依据 ⇒ 评估器也只能跟着判 done。

### 3.1.2 三层强制程度（官方原话，按确定性递增）

| 层 | 机制 | 官方原文 | 确定性 |
|---|---|---|---|
| 提示层 | 在 prompt 里要求跑测试 | 模型自行判断 | 非确定性 |
| **目标层** | `/goal <条件>` | "sets a condition that a **separate model** checks against the conversation after every turn, and Claude keeps going until it's met... **where Claude sometimes ends a turn with a progress summary while items are still open, and the goal sends it back**" | 半强制 |
| **harness 层** | `Stop` hook | "runs your script whenever Claude tries to end its turn, and **sends Claude back to work if the script exits with code 2**... **the turn doesn't end until the typecheck passes** or the block limit is reached"；**连续 8 次阻断后强制放行**（`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`） | **确定性** |

> 🔑 `/goal` 那句 **"ends a turn with a progress summary while items are still open"**
> 就是本工程 msg 3985（"建议下一步执行校验"）的**精确同义词**。

### 3.1.3 ⚠️ 官方明确列出的反模式（直接否定"加强提示词"路线）

Claude Code 官方"过时建议表"原文：

| 过时建议 | 官方给出的原因 |
|---|---|
| "**Tell Claude to keep going, loop until done, don't be lazy**" | "Current models usually carry on through an agreed task without being told, and **lines like that are more likely to cause over-work than fix a stall**. **Giving Claude a check to pass is different, and still worth doing.**" |

⇒ **不要走"提示词加压"路线**；正解是"给一个能通过的检查"。

### 3.1.4 量化背书：MAST 失败模式研究（arXiv:2503.13657）

首个多 agent 系统失败分类学（**1642 条真实 trace**，7 个 SOTA 框架，Cohen's κ=0.88）：

| 失败模式 | 出现率（prevalence） |
|---|---|
| FM-3.1 **Premature termination**（目标未达成就结束） | **6.20%** |
| FM-3.2 No or incomplete verification | 8.20% |
| FM-3.3 Incorrect verification | 9.10% |
| **FM-1.5 Unaware of termination conditions**（**该停不停**） | **12.4%** |

- **任务验证类（FC3）合计 23.5%**
- 整体失败率：7 个开源 MAS 上 **41% ~ 86.7%**
- **★ 干预效果**："adding a **high-level task objective verification step** to ChatDev yields a **+15.6%** improvement in task success on ProgramDev"
- 论文原话："many existing verifiers perform only **superficial checks, despite being prompted to perform thorough verification**"

来源：https://arxiv.org/abs/2503.13657（v3）

> 🔑 **两条关键推论**：
> ① **"+15.6%" 是"加验收步骤"的直接实验证据** —— 不是理论推演；
> ② **FM-1.5（12.4%）比 premature termination（6.20%）更高** ⇒
> 方案必须**双向管**：既要有"不达条件不许停"，也要有"条件已达成必须停"，
> 否则会从一种错误变成另一种。

### 3.2 结构化笔记（agentic memory）

《Effective context engineering for AI agents》原文：

> "**Structured note-taking, or agentic memory**, is a technique where the agent regularly writes notes persisted to memory outside the context window... **Like Claude Code creating a to-do list, or your custom agent maintaining a NOTES.md file**, this simple pattern allows the agent to **track progress across complex tasks, maintaining critical context and dependencies that would otherwise be lost across dozens of tool calls**."

> "After context resets, the agent **reads its own notes and continues** multi-hour training sequences... This coherence across summarization steps enables **long-horizon strategies that would be impossible when keeping all the information in the LLM's context window alone**."

来源：https://www.anthropic.com/research/effective-context-engineering-for-ai-agents

### 3.3 TODO 的生命周期（官方文档）

Agent SDK 的 todo tracking 文档定义了**四态生命周期**：

| 状态 | 语义 |
|---|---|
| Created | `pending` |
| Activated | `in_progress` |
| Completed | 任务**成功结束**后才置 |
| Removed | `deleted`（不再需要） |

何时创建（官方）：
> "**Complex multi-step tasks requiring three or more distinct actions**" / 用户给出的多条目任务 / 需要进度跟踪的长时间操作 / 用户明确要求

来源：https://docs.anthropic.com/en/docs/agent-sdk/todo-tracking

### 3.4 其他可对照的机制

| 机制 | 出处 | 解决什么 |
|---|---|---|
| **Sub-agent 架构**（子 agent 各自上下文，只回 ~1-2k token 摘要） | context engineering 博客 | 主上下文不被工具输出撑爆 ⇒ 长任务不因上下文耗尽而断 |
| **Compaction / tool result clearing** | 同上 | 同上 |
| **独立 evaluator agent（fresh context 打分）** | 官方 repo `anthropics/cwc-long-running-agents` | 评估者不共享被评者的上下文 ⇒ 不被其自述带偏 |
| **commit-on-stop hook**（停止时强制留痕） | 同上 | 中断也有 durablestate |

> ⚠️ **未核实项**（不编造）：METR 的 task-horizon doubling 具体数字、OpenAI/LangChain/AutoGen 的官方表述 —— 本轮未取得原文，属未查证。

## 四、方案

### 4.0 设计原则（三条，来自诊断）

1. **完成 = 验收通过**，不是模型说完成，也不是评估器读答复猜完成
2. **失败不是终止条件，是分类输入**（可重试 / 可换路径 / 可降级 / 必须问人）
3. **判定权归系统，执行权归模型**（模型可以申请，不能自封完成）

### 4.0.1 ⚠️ 优先级已按官方依据重排（初版排序有误）

初版把"todo 外化"排 P0-1。**按 Claude Code 官方文档，这个排序是错的**：

| 官方口径 | 含义 |
|---|---|
| "**Give Claude something it can run that comes back pass or fail**" | **能跑的验收检查**才是第一优先 |
| todo tools "**aren't available... unless you opt in**"；"**Claude tracks multi-step work without a written todo list**" | todo 在新模型上**默认关闭**，主要用于"render progress for the user" ⇒ **不是解决的必需品** |

⇒ **修正后的优先级**：

| 新编号 | 项 | 依据 | 原编号 |
|---|---|---|---|
| **P0-1** | **可执行验收检查**（`verify` 可运行、返回 pass/fail） | 官方"check to run" | 原 P0-2 升级 |
| **P0-2** | **harness 级强制**（不达条件不许结束 + 上限） | 官方 Stop hook | **新增**（初版漏了这层） |
| **P0-3** | 计划外化（todo，多步跟踪 + 用户可见） | 官方 note-taking | 原 P0-1 降级 |
| **P0-4** | 评估器硬信号（辅助，**单独无效已实证**） | — | 原 P0-3 |
| **P0-5** | 障碍恢复矩阵 | — | 原 P0-4 |

**为什么必须新增 P0-2（harness 级）**：官方把"提示层 / 目标层 / harness 层"的确定性写得极清楚 ——
`Stop` hook 是 **"the turn doesn't end until the typecheck passes"**，由 harness 执行，
**不依赖模型配合**。本工程当前**完全没有这一层**：所有"是否继续"都由 LLM（评估器）判断
⇒ 确定性天然不足。

**同时必须双向管**（MAST 数据）：FM-1.5「该停不停」**12.4%** > FM-3.1「过早终止」**6.20%**
⇒ P0-2 的强制必须有**上限**（官方也是连续 8 次阻断后强制放行），
否则会从"早停"变成"停不下来"。

### 4.1 P0-3 计划外化：`todo` 表 + `todo_write` 工具（原 P0-1）

**对齐官方四态生命周期**，但加一个本工程必需字段：

```sql
CREATE TABLE agent_todos (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    conversation_id INTEGER NOT NULL,
    run_id INTEGER DEFAULT 0,
    seq INTEGER,                        -- 顺序
    subject TEXT NOT NULL,              -- 待办标题（具体到对象）
    status TEXT DEFAULT 'pending',      -- pending|in_progress|completed|blocked|deleted
    verify TEXT DEFAULT '',             -- ★ 验收方式（可执行：工具名+参数 / 检查项）
    verify_result TEXT DEFAULT '',      -- 验收回执
    blocked_by TEXT DEFAULT '',         -- 依赖
    note TEXT DEFAULT '',
    created_at TEXT DEFAULT CURRENT_TIMESTAMP,
    updated_at TEXT DEFAULT CURRENT_TIMESTAMP
)
```

**关键设计（这是与"加个 TODO 就行"的区别）**：
- `verify` 字段**必填**才能置 `completed`（否则只能 `pending`）—— 直接照抄官方"Only mark as passing after careful testing"
- `completed` 的判据是 `verify_result` 非空且通过，**不由模型自我声明**
- 约束：同一时刻**至多一个** `in_progress`（官方 "Maintain single active task"）

**落点**：
| 文件 | 改动 |
|---|---|
| `database/schema.py` + `migrations/columns.py` | 新表 |
| `agent/pipeline_parts/tools.py` | `todo_write` 工具（action: create/update/list） |
| `agent/pipeline_parts/autopilot.py` | 评估器改为**读 todo 清单**判完成度，不再只读答复 |
| 提示词 | 复杂任务（≥3 步）强制先建 todo |

**验收判据**：造一个 5 步任务，断言 ① 建了 5 条 todo ② 逐步推进 ③ 每条 completed 都有 verify_result ④ 全程 ≤1 个 in_progress。

### 4.2 P0-1 完成判定改为"验收驱动"（原 P0-2，**现为第一优先**）

**现状**：`decide()` 只看 `verdict["done"]`（模型/评估器的主观判断）。

**改法**（判定优先级）：

```
done? = ① 所有 todo 都 completed 且每项 verify_result 通过
      → ② 若存在未 completed 的 todo ⇒ done=False，next_step = 第 1 个 pending 项
      → ③ 若无 todo（简单任务）⇒ 退回 LLM 评估器（现状行为，逐字节兼容）
```

**这一条直接消灭"把建议当完成"**：
答复里说「建议下一步执行校验」⇒ todo 里有「校验」这条且 `status != completed` ⇒ **强制 done=False**，不再依赖评估器理解语义。

**落点**：`auto_continue.decide()` 前置一个 `todo_gate()`（纯函数，可单测）。

### 4.3 P0-4 评估器盲区修正（原 P0-3；补四条硬信号，**仅作辅助**）

在 `EVAL_SYS` 加**显式负面清单**（对应我诊断出的四类停法）：

```
判定 done=false 的硬信号（任一命中即 done=false，不受"可选增强"例外影响）：
 · 答复中出现"建议/可以/下一步应/若需要请"等**未执行的动作** 
 · 答复把工作**转交**给其他 Agent / 其他系统 / 用户自己去操作
 · 答复以征求意见/等拍板结尾，而该问题**可由现有工具自行查明**
 · 答复自述"尚未校验/尚未验证/未测试"
```

同时把规则 1 的"可选润色/增强"**收窄**为：仅限措辞、排版、补充示例；
**任何"需要调用工具才能完成的事"都不算可选增强**。

### 4.3.1 ⚠️ 实证：**只改 prompt 只修好 1/2**（所以 P0-1 不可省）

本轮做了最小实证（只 monkey-patch 内存里的 `EVAL_SYS`，**未改生产文件**）：
用 4.2 节的修正版 prompt 重跑同样 4 条真实样本。

| msg | 类型 | 旧 prompt | 新 prompt | 结果 |
|---|---|---|---|---|
| 3985 | 动作降级成建议 | `done=True` | **`done=True`** | ❌ **仍误判** |
| 2731 | 推给别的 Agent | `done=True` | `done=False` | ✅ 修好 |
| 3970 | 伪阻断二选一 | `done=False` | `done=False` | 不变 |
| 3173 | 真该问（对照） | `done=False` | `done=False` | 不变 |

**纠正率 = 1/2。**

> 🔑 **这个"部分失败"是本方案最重要的实证**：
> 「建议下一步执行校验」（3985）这句话，即使明确写进负面清单 a，
> 评估器仍认为"用户要的东西已经给了"——因为**它没有对照清单**可查，只能凭语义猜
> "校验"算不算用户的原始要求。
>
> ⇒ **因此 P0-4（改 prompt）不能单独上线**。
> 必须由 P0-1（可执行验收检查）+ P0-3（todo 外化）提供**客观依据**：
> todo 里有「校验」这条且 `status != completed` ⇒ 直接强制 `done=False`，
> **完全不需要评估器理解语义**。
>
> 这也修正了决策点 D-5 的表述：不是"建议一组做"，而是
> **"只做 P0-4 已知无效（实测 1/2）；P0-1 + P0-3 是 P0-4 生效的前提"**。

### 4.3.2 P0-2（新增）harness 级强制：不达验收条件不许结束

**对应官方 `Stop` hook**。本工程等价实现：在"最终生成之后、persist 之前"插一个**确定性闸**：

```
if 存在未 completed 的 todo:
    if verify 可运行且未通过:
        → 不结束本轮，把 verify 的失败输出回灌，继续 ReAct（相当于 exit code 2）
        → 连续阻断计数 +1；达 8 次（配置化）⇒ 强制放行并如实说明"未完成，卡在 X"
    else:
        → 允许结束
```

**三条关键设计（缺一即退化成"又一个评估器"）**：
1. **判据是 `verify` 的实际执行结果**，不是 LLM 判断 ⇒ 确定性
2. **必须有上限**（对齐官方 8 次）⇒ 防 FM-1.5「停不下来」
3. **强制放行时必须如实告知**（"未完成，卡在 X"）⇒ 不能伪装成完成

**落点**：`stream.py` 在 `_write_ops` 注入点附近（已在"最终生成之前"验证过该位置可用）。
**验收判据**：构造一个 verify 必失败的 todo ⇒ 断言 ① 本轮不结束 ② 阻断 8 次后放行
③ 最终答复明确写"未完成"（不含"已完成"字样）。

### 4.4 P0-5 障碍恢复：把 `replan_decisions` 接进主循环（原 P0-4）

**现状**：表存在，全库 1 行 ⇒ 未接线。

**失败分类矩阵**（新增纯函数 `classify_obstacle()`）：

| 障碍类型 | 判据 | 恢复动作 |
|---|---|---|
| `transient` | 网络/超时/5xx | 重试（已有） |
| `auth` | 凭据失效/401/STALE_READ | **刷新凭据 → 重试一次**（不直接问人） |
| `not_found` | 404/包不存在/ID 无效 | **换路径**：改用 list/search 先定位 |
| `precondition` | 父容器已变/版本过期 | **重新取坐标 → 重放** |
| `capability` | 工具不支持该操作 | **降级**：换等价工具或缩小范围 |
| `user_only` | 信息只有用户有（如口径选择） | 问人（唯一合法停下） |

**关键**：`auth` / `not_found` / `precondition` **都不该问人** —— 现有工具都能自己解决。
实测样本 3173 的 next_step「刷新凭据后重新调用」正属 `auth` 类。

### 4.5 P1-1 预算感知（消灭 12% 的硬停）

**现状**：token 预算耗尽 ⇒ 硬停（11/89）。

**改法**：预算用到 **70%** 时触发"**降级收尾**"：
1. 停止新开子任务
2. 把未完成 todo 列入"待续清单"（写入 progress notes）
3. 明确告知用户"已做到哪、还差哪、下一条消息我继续"

⇒ 用户感知从"突然断了"变成"分段推进"。

### 4.6 P1-2 `needs_user` 分级（消灭"可自决却问人"）

**现状**：`needs_user` 一律转澄清卡 ⇒ 用户感知"停"。

**改法**：二分为

| 类型 | 处理 |
|---|---|
| `user_only`（信息只有用户有，如工况口径） | 转澄清卡（现状） |
| `has_default`（有合理默认值） | **按默认推进 + 在答复里显式标注"按 X 默认处理，如需改请说"** |

对齐官方 CISA 口径"审批决策由设计者定"与 D-6 纪律"可独立判断时直接给结论"。

### 4.7 P2 跨会话续跑（对齐官方 progress notes）

`orch_checkpoint` 现在只服务编排。扩到普通会话：
- 每轮结束写 progress notes（已做到 / 待办 / 关键决策）
- 下次会话开始**自动读取**（而非用户重新描述）
- 这一条对应官方 "progress notes file + git log" 模式

> ⚠️ 本工程是**单会话内多轮**场景，跨会话收益小于 Anthropic 的"跨天开发"场景 ⇒ 排 P2。

## 六、优先级与预期收益（基于本工程实测数据）

- ❌ 让评估器自己决定要不要继续 —— 评估器是"判定者"，不能同时是"当事人"

| # | 决策 | 建议 | 理由 |
|---|---|---|---|
| **D-1** | 引入什么作为"完成"依据 | **可执行验收检查（verify）优先**，todo 表作多步跟踪的载体 | 官方："Give Claude something it can run that comes back pass or fail"；todo 在新模型已默认关闭 |
