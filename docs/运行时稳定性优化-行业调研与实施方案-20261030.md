# 运行时稳定性优化：行业调研与实施方案

> 日期：2026-10-30
> 依据：《运行时评估》（2026-10-30 上午）指出的三项硬缺口 + 长任务编排 54.5% 成功率
> 原则：**先调研、再评估、后实施**；每项改动须有可回退开关与变异自证

---

## 0. 结论先行

| 项 | 行业主流做法 | 本工程适配结论 | 是否采纳 |
|---|---|---|---|
| 优雅关闭 | uvicorn `timeout_graceful_shutdown` + lifespan 收尾 + readiness 503 | 全部可落地，**成本低、收益直接** | ✅ 采纳 |
| 并发背压 | 生成器内持有 `asyncio.Semaphore` + 快速失败 429 | **关键细节**：信号量必须在**生成器生命周期内**持有 | ✅ 采纳 |
| 单请求墙钟上限 | deadline 传播（gRPC/Temporal 式），到点强制收尾 | 现有只有"自动续跑"的闸，无整轮上限 | ✅ 采纳 |
| 长任务编排 | Durable Execution（Temporal/DBOS/LangGraph checkpointer） | **不引入引擎**——本工程已有 80% 要素，缺口在"超时丢产出" | ✅ 只补缺口 |
| 多进程/横向扩展 | uvicorn `workers=N` | **暂不采纳**：SQLite 单写者 + 进程内状态（信号量/熔断器）会失真 | ❌ 明确不做 |

**最重要的发现**：长任务失败的头号原因不是"跑得久"，而是**"超时后把已产出的内容整块丢掉"**——63/76 次失败全是这一类，而丢弃是纯信息损失，不是能力不足。

## 1. 调研：三个缺口的行业做法

### 1.1 优雅关闭

**共识做法**（FastAPI/uvicorn/K8s 三方一致）：

```python
# ① uvicorn 原生支持，无需自己写 signal handler
uvicorn.run(app, host=..., port=..., timeout_graceful_shutdown=30)

# ② lifespan 的 yield 之后才是收尾入口（不是 @app.on_event("shutdown")）
@asynccontextmanager
async def lifespan(app):
    ...startup...
    yield
    # SIGTERM 后：uvicorn 已停止接新连接，此处做收尾
    draining.set()                      # ① 先关入口
    while inflight and not deadline:    # ② 有界等待在途请求
        await asyncio.sleep(0.2)
```

**三个必须知道的细节**（都是踩坑点，不是理论）：

1. **`timeout_graceful_shutdown` 不设 = 收到 SIGTERM 立即退出**，在途请求直接断。默认值不是"无限等"，是"不等"。
2. **shutdown 预算取 `max(drain, lifespan)` 而非两者之和**——uvicorn 排空 HTTP 连接与 lifespan 收尾**并行**执行。
3. **长任务（>10s）不该靠调大 timeout 解决**。原文：*"If you have endpoints that run longer than 10 seconds, the problem can't be solved by increasing the timeout — you need to rework them into a 202 Accepted scheme with subsequent polling."* 本工程的整套 SSE 就是长任务，所以**必须有"到点固化已产出"的兜底**，不能指望排空完成。

**readiness 与 liveness 必须分开**：关闭过程中要 `/ready` 返 503（让 LB 摘流量）但 `/live` 仍 200（让进程别被杀）。合并成一个端点会导致"要摘流量就得杀进程"。

**本工程现状**：`lifespan` 的 `yield` 之后**一行代码都没有**；`uvicorn.run` 未设 `timeout_graceful_shutdown`；无 SIGTERM 处理；SSE worker 是 `daemon=True` ⇒ 进程停时被硬杀，`route_persist_gone` 兜底不触发。

### 1.2 并发背压

**核心共识**：*"Hold the semaphore inside the generator. Otherwise your limiter is measuring the wrong thing."*

这条直接决定实现位置——信号量若在端点函数里 `async with sem:` 然后 return `StreamingResponse(gen())`，函数返回时信号量就释放了，**流的整个生命周期根本没被限流**。必须写在生成器内部。

**快速失败优于排队**：*"Requests beyond that get a 429 immediately instead of queueing up and causing cascading timeouts."*
排队会让 p99 雪崩（所有人都在等），429 至少让调用方知道该重试。

`asyncio.Semaphore.acquire()` 加 `asyncio.wait_for(timeout=2.0)` 是常见折中：给 2 秒排队窗口，超时才拒。对交互式对话更友好。

**本工程现状**：只有 per-agent `Semaphore`（默认 2），且**仅在编排分支**生效；会话直答路径无任何并发上限。N 个并发长任务 = N 个 daemon 线程 + N 份 LLM 连接。

### 1.3 单请求墙钟上限

行业做法是 **deadline 传播**（不是"每层各自设超时"）：
- 入口算出 `deadline = now + budget`
- 每层只问"还剩多少"，不自己定
- 到点后**不是 kill，是收尾**（保留已产出，标注 partial）

**本工程现状**：`auto_continue_deadline_s=600` 是"自动续跑"的闸（控制续跑几轮），不是整轮上限；`subtask_idle_timeout_s=240` / `subtask_timeout_s=600` 是**子任务**级。**整轮无上限**——实测有 run 跑到 918s（15 分钟）仍算正常返回。

### 1.4 长任务编排：Durable Execution

行业分三档，**选择取决于"最长运行时长"与"副作用是否可逆"**：

| 档 | 代表 | 适用判据 |
|---|---|---|
| 检查点（framework 内） | LangGraph checkpointer（Postgres/SQLite） | 图就是产品，最长运行分钟级 |
| 持久化执行引擎 | Temporal / DBOS / Restate / Inngest | 最长运行>10 分钟，或跨系统副作用不可逆 |
| 托管 agent 运行时 | Bedrock AgentCore | 会话隔离优先，但**会话不是 durable**（超时即结束） |

**明确的判据**（原文）：*"if your agent's longest expected run is under ten minutes and every side effect is reversible, a retry wrapper and a dead-letter queue are enough, and an engine is ceremony."*

**Retrofit 三步法（关键，决定了我们该做什么）**：

1. **先给所有写类工具加 idempotency key** —— 工具层改动，**不需要引擎**，且让任何未来的 resume 都安全
2. **外部化任务图** —— 哪怕只是"一张有 status 的 steps 表"，也能把"重跑全部"变成"从 step 14 resume"
3. **前两步成立后**，才把循环搬进引擎

**LangGraph 的 durability 三档**（值得借用为配置）：
- `exit`：只在结束/异常时写 → 最快，崩溃丢全程
- `async`：下一步运行期间写 → 崩溃丢一小段
- `sync`：每步前写 → 最 durable，开销最大

**Temporal 的两条硬约束**：
- **LLM 调用必须包在 activity 里**，不能放在 workflow 逻辑里——因为 workflow 要求确定性，而 LLM 恰好是最不确定的。引擎记录首次输出，replay 时复用。
- **`start_to_close_timeout` 是"一次往返"而不是"整个 job"**，重试次数按失败类型分开。

**Continue-as-New**：history 无限增长时，原子结束当前 run、以同一 ID 开新 run，只带关键状态。对应到我们就是**上下文压缩**（已有 `compression.py`）。

**本工程既有对照**（这决定了"不引入引擎"的判断）：

| Durable 要素 | 本工程现状 | 缺口 |
|---|---|---|
| 任务图外部化 | `agent_tasks` 表：`task_key/status/deps/result/error_class/retry_count` | 无 |
| 检查点 | `orch_checkpoints`（phase + touch 心跳，每 5s） | 无 |
| 断点续跑 | `prepare_resume` / `apply_resume`（最多 5 次防死循环） | 无 |
| 孤儿回收 | `reap_orphans`（30 分钟无进展 → interrupted） | 无 |
| 失败分类重试 | `failure_class.classify` + `is_retryable_class` + 指数退避 | 无 |
| DAG 级补跑 | `_t1_retried` + `_redraw_hist` 台账 | 无 |
| 后台作业队列 | `job_queue`（租约 lease + heartbeat，可回收） | 无 |
| **超时保留产出** | **`last_res = (tkey, ttitle, False, "", [], ...)` ← payload 为空** | **★ 这是缺口** |
| 幂等键（写类工具） | 部分（`write_target_resolver`） | 有缺口 |

**⇒ 结论：本工程已有 durable execution 的骨架，不需要 Temporal。真正的缺口是"超时即丢弃产出"。**

## 2. 归因：长任务 54.5% 的真实构成

数据来源：`agent_tasks` 全量 300 条（done 224 / failed 76）。

| error_class | 条数 | error 原文 |
|---|---|---|
| `(空)` | **63** | `timeout（240s 无产出）` / `timeout` |
| `interrupted` | 11 | 编排中断：超过 30 分钟无任何进展，判定为孤儿运行 |
| `internal` | 2 | — |

按 Agent：`design` 28、`review` 11、`结构视图生成` 7、`智源平台管理` 6、`report_generation` 5。

**83% 的失败是 `timeout（240s 无产出）`，且集中在 design（长推理型）。**

代码侧确认（`stream.py:1215-1218`）：

```python
else:
    # 超时：不等待线程（后台继续运行），标记 error 含 "timeout"
    last_res = (tkey, ttitle, False, "", [], _stall, ...)
    #                                ^^ payload 空字符串
```

**这条路径把子任务已产出的全部内容丢掉了。** 而子任务的 token 产出是实时的（`_hb[tkey]` 在每次 token/reasoning/tool 都更新），也就是说：**超时那一刻，产出很可能已经有几千字，但被当成了"什么都没做"**。

这解释了为什么 `run` 层成功率低（54.5%）而 `task` 层还有 91%：**失败的子任务拉垮整批汇总，而它其实产出了东西**。

同时纠正一个此前的判断：`subtask_idle_timeout_s` 从 150 调到 240 是"功能优先，防长推理期被误判停滞"（`config.py:212` 注释）。**继续调大是错的方向**——原文判据：*"If an operation doesn't fit into the allotted budget, make it smaller rather than giving it more time."* 240s 已经足够长，问题不在阈值。

## 3. 实施方案

### 3.1 ① 优雅关闭（P0）

| 改动 | 位置 | 说明 |
|---|---|---|
| `timeout_graceful_shutdown` | `main.py` `uvicorn.run` | 默认 30s，走 config `runtime.shutdown_drain_s` |
| `draining` 标志 + in-flight 计数 | 新增 `core/runtime_state.py` | 进程内单例（单进程部署下正确） |
| 入口拒新请求 | `routers/conversations.py` 两个端点 | draining 时 SSE 返一帧 error + 关闭（不用 503，因为 SSE 头已发） |
| lifespan 收尾 | `main.py` `yield` 之后 | 置 draining → 有界等在途 → 停后台线程（job_queue / alert / mcp_health） |
| `/api/health/live` + `/ready` | `main.py` | ready 在 draining 时返 503 |

**为什么用 `timeout_graceful_shutdown` 而不自己装 SIGTERM handler**：uvicorn 已处理 SIGTERM 并会跑 lifespan shutdown；自己装会与之竞争。

**关闭预算**：`drain(30s)` 与 `lifespan 收尾` 并行，取 max。长任务不可能在 30s 内跑完 ⇒ 所以 lifespan 收尾里**必须主动触发"固化在途产出"**，而不只是"等"。

### 3.2 ② 全局并发闸 + 单请求墙钟上限（P0）

| 改动 | 位置 | 说明 |
|---|---|---|
| 全局并发闸 | `core/runtime_state.py`（`asyncio.Semaphore`） | 默认 8，config `runtime.max_concurrent_streams` |
| **在生成器内持有** | `routers/conversations.py` `event_stream` | 关键：不在端点函数里 acquire |
| 排队窗口 + 快速失败 | 同上 | 等 2s（`runtime.queue_wait_s`）拿不到 → 发 `error` 帧（`code=busy, retry_after=5`） |
| 单请求墙钟 | `execute_stream(deadline_ts=...)` | 从入口算 `now + runtime.chat_deadline_s`（默认 900s），传给编排与 ReAct 循环 |
| 到点收尾 | `stream.py` 主循环边界 | 不用 kill，走"收尾 + 保留已产出 + 标注 interrupted" |

**墙钟与 idle 的关系**（两者都要，各管一段）：

| 闸 | 管什么 | 到点行为 |
|---|---|---|
| `subtask_idle_timeout_s` 240s | 子任务"卡死"（无任何事件） | 判 stall → 重试/失败（**本轮改为保留产出**） |
| `subtask_timeout_s` 600s | 单子任务硬上限 | 同上 |
| `runtime.chat_deadline_s` 900s | **整轮**（所有子任务 + 汇总） | 强制收尾，输出 partial 汇总 |

### 3.3 ③ 长任务编排：只补三个缺口（P0）

**缺口 1：超时丢弃产出（最严重，改动最小）**

```python
# 改前
last_res = (tkey, ttitle, False, "", [], _stall, ...)
# 改后：把最后一次心跳时的累积正文塞回去
last_res = (tkey, ttitle, False, _hb_text.get(tkey, ""), [], _stall, ...)
```

配套：`_hb[tkey]` 更新时同步累积正文（已有产出点：token / reasoning / tool），新增 `_hb_text` 字典。

**为什么这是对的而不只是"多留点字"**：行业明确要求 *"OpenAI Agents SDK：命中 max_turns 不许静默，要返回标明 partial 的结构化结果"*。丢弃 = 让下游汇总误判"这个子任务什么都没做"，从而整批降级。

**缺口 2：重试不带上下文（重复同样的 240s）**

现状：重试是"同 key 原地重派"（`UPDATE agent_tasks`），上下文完全相同 ⇒ 同样的 prompt、同样的规模、大概率同样的超时。

改法：重试时在 `tk["config"]["query"]` 前追加**缩减指令**：
```
【第 N 次尝试 · 上一次因超时中断】
请缩小范围、优先输出可独立使用的最小完整结果；不要追求完整覆盖。
```

**缺口 3：超时预算不分类**

现状：所有子任务共用 240s。而 `design`（长推理）与 `query_projects`（工具查询）的合理预算差一个数量级。

改法：按 intent 分档（config 可覆盖）：
```
delegation.idle_timeout_by_intent = {
  "design": 360, "review": 300, "report_generation": 300,
  "__default__": 240
}
```
**注意**：这不违反"make it smaller"原则——原则针对的是"跑不完的活"，而不是"本来就需要更长的推理"。真正的解法是缺口 1+2（保留产出 + 缩小重试）。

## 4. 明确不做的事（及理由）

| 不做 | 理由 |
|---|---|
| 引入 Temporal / DBOS | 本工程已有任务图外部化 + checkpoint + resume + 租约队列。引引擎=加一个必须运维的系统，而缺的只是一个字段（超时产出） |
| `uvicorn workers=N` | **会引入三类新 bug**：① 进程内 `asyncio.Semaphore` 各自计数 ⇒ 实际并发 = N 倍；② 熔断器状态不共享 ⇒ 一个进程熔断不影响其他；③ SSE 长连接被 LB 随机分配，断连重连落到不同进程 ⇒ 内存态全丢。**当前 SQLite 单写者也不支持多进程写** |
| 把 SSE 改造为 `202 Accepted + 轮询` | 这是"长任务"的正确终局（行业原文），但会推翻整个前端交互模型（打字机效果）。**代价过大，且已有 SSE 心跳 + 断点固化缓解**。列为长期方向 |
| 调大 `subtask_idle_timeout_s` | 方向错。实测 240s 已远超单轮 LLM（p99 126s）；调大只会让真卡死的任务更晚失败 |
| 引入 Redis 分布式信号量 | 单进程部署下无收益；且引入 Redis 依赖违反本项目"单机可跑"约束 |

## 5. 验收判据

| 项 | 判据 |
|---|---|
| ① 优雅关闭 | 发 SIGTERM 后在途 SSE 请求收到终态帧；`/ready` 返 503、`/live` 仍 200；进程在 `drain_s + 5s` 内退出 |
| ② 并发闸 | 并发 > 上限时新请求 2s 内收到 `error(busy)`；并发 = 上限时全部正常完成；**验证信号量真的覆盖流生命周期**（生成器未结束时占用数不回落） |
| ③ 墙钟 | 注入 `chat_deadline_s=20` 跑长任务 ⇒ 20s 内收尾、输出 partial、`span.status=error, reason=deadline` |
| ③ 超时保留产出 | 构造 idle 超时 ⇒ `agent_tasks.result` 非空（改前为空串） |
| 全局回归 | `verify_pipeline_concurrency` 9/9、`verify_sse_heartbeat`、`verify_conv_failure_attribution` 21/21 全绿 |

每项新断言均须**变异自证**（改回旧行为 ⇒ 判据必须判红）。

| 长文本请求 + 墙钟 8s | **61s / 101s，多数无终态帧** | **18s 收尾**，日志 `timeout 180.0s → 7.8s`、`→ 3.9s`、`入口拦截 rl=deadline` |

### 6.3 三处实测纠偏（都是我先判断错、被数据推翻的）

**① `planner` 的 57s 不是"cap 没生效"，是我在跑旧代码**
   一度以为 `cap_timeout` 有 bug。加诊断日志后看到 `timeout 180.0s → 7.8s` ——
   逻辑一直是对的，那几次 57~101s 的测量都在**旧进程**上完成（重启失败、端口被僵尸进程占用）。

**② 墙钟检查放在 `if not tools_def` 之后 ⇒ 该分支完全绕过**
   conv 9772/9773 连续两次 90s 未收尾，根因是无工具场景先 `break` 出去了。
   已移到**之前**，并在门禁里加位置判据 + 顺序颠倒的变异自证。

**③ `httpx` 的 timeout 压不住流式长文本**
   `httpx.stream(timeout=N)` 的 N 是**每次读操作**超时；逐帧都很快时总时长不受限。
   conv 9772 实测：墙钟 8s、`cap_timeout` 生效，仍连续吐 19 个 token。
   ⇒ 必须在**流式消费循环**每帧判一次（`llm/__init__.py:_stream_wrapped`）。

**④（补充）压单次 timeout ≠ 压总量**
   `cap_timeout` 只压**单次**；`llm.retry_times=2` 会让总耗时至多 ×3，叠加退避。
   ⇒ 在 `_chat_with_retry` 每轮重试前再判一次（剩 <3s 即停）。

### 6.4 如实交代：Windows 下 SIGTERM 不触发优雅关闭

- **已验证的是代码逻辑**：`TestClient` 进入/退出 app 上下文时，`[shutdown]` 四条日志全部输出、
  三个后台线程正常停止、draining 期间 `ready=503` / `live=200`。
- **未能在本机验证的是 OS 信号链路**：Windows 上 Git Bash 的 `kill -TERM` 被映射为
  `TerminateProcess`（硬杀）或静默失败，Python 的 signal handler 收不到 ⇒ 不会触发 lifespan shutdown。
- **影响面**：仅影响"本机 Windows 上用 kill 停服务"这一种方式。
  Linux / 容器（Docker/K8s）/ `Ctrl+C` 下 uvicorn 正常处理信号，本机制生效。
- **本机替代做法**：`Ctrl+C` 停止，或直接结束进程（此时断点固化仍由 `route_persist_gone` 兜底）。

### 6.5 明确未做（与 §4 一致）

- 未引入 Temporal/DBOS：本工程已有任务图外部化 + checkpoint + resume + 租约队列，缺的只是"超时保留产出"。
- 未启用 `uvicorn workers=N`：进程内信号量/熔断器会失真，且 SQLite 单写者不支持多进程写。
- 未改 SSE 为 202+轮询：会推翻前端打字机交互，代价过大。
