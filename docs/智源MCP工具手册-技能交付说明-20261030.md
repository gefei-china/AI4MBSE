# 智源 MCP 工具手册（技能）交付说明 · 2026-10-30

## 一句话

为 `zhiyuan-dev-mcp` 的 **71 个 MCP 工具**生成了一份可检索的技能包：
**有哪些工具、各自干什么、必填什么、怎么调用**，并带一个按说法检索的脚本。

## 为什么不能手写

71 个工具、每个都带真实 `inputSchema`（必填项、枚举、`additionalProperties:false`）。
手写必然发生两类漂移：

1. **服务端加/改工具后，文档静默过期** —— 没人会主动回来改 71 条；
2. **参数名靠记忆写** —— 错一个字就变成"文档教模型传错参数"，比没文档更糟。

⇒ 真相只有一个：`mcp_servers.tool_meta`（MCP `list_tools` 的落库结果）。
`references/` 全部由 `tools/gen_zhiyuan_mcp_skill.py` 从它生成，
并把**分类覆盖**做成硬断言（新增工具未归类 ⇒ 生成直接失败，不会漏在文档外）。

## 包结构

```
static/skill_packages/zhiyuan_mcp_tools/    ← 产物（.gitignore，可重建）
    skill.md                     3.3KB  入口：职责边界 + 3 条参数铁律 + 按任务找工具表
    references/工具目录.md        82KB  71 个工具的完整契约（11 个功能组）
    references/参数速查.md        2.4KB workspace / requestId / readToken / 分页 / 同义参数
    references/任务配方.md        6.4KB 10 条端到端调用链（含每步的坑）
    scripts/lookup.py            19KB  按说法检索（产物，源自 tools/）
    scripts/dump_tools.py        26KB  重生成器（产物，源自 tools/）

tools/gen_zhiyuan_mcp_skill.py              ← 源头（入 git）：从 tool_meta 生成 references
tools/zhiyuan_mcp_lookup.py                 ← 源头（入 git）：检索器
tools/register_zhiyuan_mcp_skill.py         ← 源头（入 git）：包 → skills 表（幂等）
tools/verify/verify_skill_package_sync.py   ← 门禁：包 ↔ DB 内容一致
```

**为什么源头在 `tools/` 而不是包里**：`static/skill_packages/` 在 `.gitignore`
（既定约定，git 里 0 个文件）。手写在包里的脚本会随机器丢失 ——
源头入 git + 产物不入 = 包任何时候都能重建：

```bash
./.venv/Scripts/python.exe -X utf8 tools/gen_zhiyuan_mcp_skill.py    # 重生 references
./.venv/Scripts/python.exe -X utf8 tools/register_zhiyuan_mcp_skill.py  # 入 skills 表
```

## 怎么用

**模型侧（渐进披露，不要一次读完）**
1. `skill.md` 的「按任务找工具」表 → 定位工具名；
2. `references/工具目录.md` 的对应分组 → 查完整参数；
3. 公共参数（workspace 等）→ `references/参数速查.md`；
4. 端到端顺序 → `references/任务配方.md`。

**人侧**
```bash
python tools/zhiyuan_mcp_lookup.py 导入源码      # → 确定映射，直给契约
python tools/zhiyuan_mcp_lookup.py 把源码塞进平台  # → 模糊，标注「请核对」
python tools/zhiyuan_mcp_lookup.py --list         # 全部 71 个工具名
python tools/zhiyuan_mcp_lookup.py --selftest     # 检索质量自证
```

## 检索设计（两段式，这是它可信的原因）

| 段 | 机制 | 输出标记 | 依据 |
|---|---|---|---|
| ① 确定映射 | `ALIAS` 表（111 条「说法 → 工具」，人工审过） | `【确定】` | 来自任务配方与 skill 表格 |
| ② 模糊匹配 | 意图词表 + 名字/描述打分 | `【模糊】…请核对` | 兜底探索 |

**为什么必须要意图词表**：工具名是英文，而服务端描述未必含用户的中文说法 ——
`import_sysml_text` 的描述是"新增文本包或覆盖明确目标包"，**一个字都没有"导入"**。
纯文本检索永远排不到它（实测：查「导入源码」top1 是无关工具）。

**为什么分成两段而不是一律打分**：早先用纯打分给确定答案，实测 24 条常见说法里
**7 条 top1 是错的**，而输出看起来同样"言之凿凿" —— 这是最坏的失败形态（错得很自信）。
现在模糊结果明确标注"请核对"，并且 `--selftest` 用两套判据：
- ALIAS 自洽（111/111）—— 只证明表里写的查得到，**不证明泛化**；
- 泛化（8/8）—— 故意用**不在 ALIAS 里**的口语措辞，要求正确工具进 top3。

## 顺带修掉的缺陷

**技能包磁盘文件与 `skills` 表内容漂移**（本轮实证）：
「智源平台管理」磁盘 `skill.md` 是 **v1.0**（1677 字，讲已失效的
`zhiyuan_sysmlv2_*` HTTP 工具），DB `content` 是 **v1.3**（4830 字，MCP 版）。
后果：改文件不影响模型、改库不影响文件，且**无任何报错**。
已以 DB 为准回写磁盘（旧版留 `skill.md.v10.bak`），并新增门禁
`verify_skill_package_sync.py`（S1 内容一致 / S2 manifest 文件真实存在 /
S3 生成型包的新鲜度 / S4 变异自证，16 项）接进 CI。

## 本轮踩的坑（都写进代码注释了）

1. **`content` 与 `frontmatter` 传反**：前者要全文、后者只要 YAML 头。
   传反后 frontmatter 变成 3518 字 ⇒ `verify_skill_frontmatter` 当场判红（门禁救了一次）。
2. **`frontmatter` 要含首尾 `---`**：只取块内文本会让「与 content 的 YAML 头同源」判红。
3. **元组解析写反**：`("validate", 0)` 里的 `0` 被当成片段去做 `in` 判断 ⇒ `TypeError`。
4. **frontmatter 超 400 字注入上限**：triggers 列太多（23 个）⇒ 精简到 13 个。
5. **只改 DB 不改文件**：见上一节，这是本轮最重要的一条教训。

## 术语速查（给接手的人）

- **`tool_meta`**：`mcp_servers` 表里的一次 `list_tools` 快照，含每个工具的
  `description` + `inputSchema`。文档的唯一真源。
- **`workspace`**：`{projectId, branchId, versionId}`，71 个工具里 66 个需要它。
- **`version` vs `workspace`**：同一台 server 内两种字段名并存（查包树用 `version`），
  值都是同一个三元组对象。
- **`requestId`**：写入类幂等键；**`readToken`**：写快照票据，默认省略。
