## 1. Step1 · 分块 token 归因（P0-2）

### 动机

`llm_usage_stats` 只记**整包** `prompt_tokens`（生产 `chat_probe` 均值 12,511 / 峰值 64,552），
**无分块归因** ⇒ 无法回答"这轮 token 花在哪"。

历史上两次真实损失都因"看不见"而延迟发现：
- 2026-10-11 总闸静默空转（pressure=1.37 却"裁掉 0 tok"）
- 2026-10-11 流式路径腰斩 82% Agent prompt（切掉 `## 约束` / `## 输出示例`）

旧方案 §4 已把"上下文可观测"列为 P1-2，**至今未实施** —— 本步是它的落地，
也是后续所有调优的**前提**（没有归因，其余三项都是盲改）。

### 实现

| 文件 | 变更 |
|---|---|
| `agent/context_audit.py`（新增） | 块级归因模块：进程内聚合 → 请求收口 flush |
| `database/schema.py` | 新建 `context_audit`（块级）+ `context_audit_summary`（每 trace 聚合 + 去重后指标） |
| `agent/pipeline_parts/common.py:255` | `assemble_system_prompt` 记录每块 token（**零额外切分成本** —— 块边界本就已知） |
| `routers/conversations.py:496` | SSE `finally` 统一 flush（一次请求 = 一次装配） |
| `agent/pipeline_parts/execute.py:403` | 非流式路径装配后立即 flush |
| `core/config.py` / `core/setting_keys.py` | 配置组 + 运行时可调键白名单登记 |

**关键设计**：
- 归因点在 `assemble_system_prompt` —— 该函数**本来就按块遍历** `PROMPT_BLOCK_ORDER`，
  记录每块 token 的边际成本 ≈ 一次 `count_tokens`，**不需要重新分词、不需要二次分块**。
- `trace_id` 与 `llm_usage_stats.trace_id` **同源**（`core.audit.begin_trace`）⇒ 可直接 JOIN，
  于是「这轮花了多少」与「花在哪个块」可按同一 trace 聚合。
- **不存 prompt 正文**，只存块名与 token 数 ⇒ 不落任何用户内容。
- 观测**异常一律吞掉**，绝不阻断主流程。
- 开关 `context_audit.enabled`（默认开）；关闭时**零开销且拼装结果逐字节不变**（门禁 [6] 断言）。

## 2. Step2 · 检索注入多样性约束（P0-3）

### 问题（实测，生产库快照 8 个 query）

`context.py` 注入检索结果时**只取前 `rag.inject_k`（3）条**，无任何多样性约束
（全仓 grep `MMR|diversif|near_dup` **零命中**）。

| query | top3 文档数 | 槽间最大重叠 | 有效条数 |
|---|---|---|---|
| 如何定义 SysML v2 的活动图 | 3 | 0.21 | 3.00 |
| 需求追溯矩阵怎么构建 | 3 | — | 3.00 |
| **parameter 属性定义方式** | **1（同文档）** | 0.74 | **1.14** |
| **ISO 29148 需求质量准则** | **1（同文档）** | 0.47 | **1.00** |
| **block definition 端口定义** | **1（同文档）** | 0.53 | **1.57** |

⇒ **3 个注入槽实际只换来 1.00~3.00 条信息**。

**根因（语料侧实测）**：
- `document_chunks` 共 **7,177 块 / 仅 14 个文档**，**top2 文档占 64.3%**
- **相邻 chunk 字符集 Jaccard 中位数 0.659、p90 0.816**（7,144 对样本）
  —— 切片 `overlap=90` 所致 ⇒ 检索 top3 常落在同一文档的连续 §

### 方案（**无损去重** —— 对齐 Deep Agents「先无损、后有损」）

`agent/retrieval_diversity.py`（新增）：

1. **per-doc 配额**：同一 `source_doc` 最多占 N 槽（默认 2）
2. **近邻合并**：同文档且 `|Δchunk_index| ≤ 2` ⇒ 合并为一条，标注 `§a-b` 区间
   （**合并无损**：两段内容都在，按 chunk_index 逐段留存）
3. **补位**：多样性过滤后槽位不足 ⇒ 从 RRF 池（`rag.top_k=20`，尚有 17 条落选）补齐
   ⇒ **条数只增不减**

### 硬约束：不破坏引用编号对齐

`【来源n】` 编号与前端 `citations` 数组**1 基对齐**（`context.py:187` 明确）。
本步只做**条目筛选与合并**，**不改编号语义**：合并后条目仍占**一个**编号位，
编号顺序 = 注入顺序。

### 实测效果（真实生产库）

**初版口径（8 个 query，存在选择偏差 —— 已被 24 query 复测修正）：**

```
有效条数：2.17 → 2.72（+25.3%）
文档数  ：1.88 → 2.38
最坏情况：1.00 → 2.41
```

**修正后的口径（24 个真实 query 复测，2026-10-26）：**

| 指标 | 数值 |
|---|---|
| **真正产生差异的 query** | **12 / 24 = 50%** |
| 另 12 个 | **改动前后逐字节相同**（merged=0、docs 不变、选中 chunk 一致）|
| 生效的 12 个 | 有效条数 2.27 → 2.68（**+0.41**）|
| **全部 24 个平均** | **2.53 → 2.73（+0.20，约 +8%）** |
| **反向下降的 case** | **4 / 24（17%）**：接口块 −0.07、验证用例 −0.09、视图规范 −0.15（合并拉低了 Jaccard 估算） |

> ⚠️ **必须修正初版结论**：`+25.3%` 是在"人工挑的 8 个高重叠 query"上算的，
> 有选择偏差。真实覆盖是 **约 50% 的 query**，平均增益 **约 +8%**，且有 **17% 的 case 轻微下降**。
>
> 为什么会下降：合并把两条相邻 chunk 拼成一条，条目数从 3 变成 2，
> 按"1 − 两两重叠"折算时 Jaccard 分母变大 ⇒ 指标下降。
> 但**信息量未必下降**（原文都保留了，只是并到一个槽位）。这说明**该指标本身是代理量**，
> 不能单独作为"是否变好"的判据 —— 真正的判据是下游任务正确率。

**结论修正**：Step2 是**局部收益 + 零风险兜底**（条数只增不减、内容无损、编号语义不变），
不是"普适的 25% 提升"。价值真实但**小于初版评估**。

### 实施中发现并修正的两个真 bug（门禁抓出）

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| 1 | 合并后**丢正文** | 用 `txt not in prev` 判断"是否已收录" —— 正文相同的不同 chunk 被误判为已收录 | 改用**已登记 chunk_index 集合**判断（正文相同但 chunk 不同 = 两个不同来源位置） |
| 2 | 候选不足时**少返回条目** | 补位去重用"正文相等" —— 同文档近邻 chunk 高度相似（实测 Jaccard 0.659）被误判为同一条 | 补位去重改用 **chunk 位置**（doc + chunk_index） |

另修正一处**指标口径**：有效条数原先对**跨文档**条目也按字符重叠扣减，导致
"换到跨文档条目 ⇒ 指标反降"的假象（实测 1.57→1.50，实际文档数 1→2 是提升的）。
现改为**跨文档不扣减** —— 不同文档即使字符相似也是两份独立证据。

## 3. Step3 · 记忆注入噪音闸门 + 单一真源（P0-4）

### ⚠️ 评估报告的结论需要修正

原报告称"同一条记忆双路注入，最多 1,760 字/轮重复"。**实施时实测该结论不成立**：

生产库 8 个 query 实测，两条路径的召回 id **重叠率 = 0%**。
原因：路径①用 `query = user_input + ' ' + intent`，路径②用裸 query 且带噪音闸门 + 跨域兜底，
两者构造不同 ⇒ 召回结果实际不重叠。

**但顺藤摸瓜发现了两个真实缺陷**：

| # | 真实缺陷 | 实测证据 |
|---|---|---|
| **①** | **路径① 缺噪音闸门，注入寒暄话术** | 路径①注入了 id=170（395 字"你好，我是 MBSE 平台的通用助手…"），经 `_is_noise` 判定为 **True（噪音）**；路径②正确排除了它 |
| **②** | **同一张表查两遍** | 路径①（`MemoryService.search`）与路径②（`recall_memories`）各自独立召回，重复的向量/BM25 计算 |

另：路径①截 160 字、路径②**完全不截断** ⇒ 同一记忆在两个块里长度不同（长版 + 短版），
短版被长版完全覆盖 ⇒ 160 字截断是纯冗余。

### 实施内容

| 文件 | 变更 |
|---|---|
| `agent/pipeline_parts/memory.py:13` | ① core 层加 `_is_noise` 闸门；② recall 层改为**消费 RAG 侧 `memory_hits`**（不重复查库）；③ 跨路按 id 去重；④ 截断统一为 `memory_max_chars`（默认 200） |
| `agent/pipeline_parts/context.py:205` | 记忆块补上截断（此前无截断） |
| `agent/pipeline_parts/stream.py:3964` / `execute.py:338` | 把 `retrieval.memory_hits` 挂到 `self._rag_memory_hits`（单一真源） |
| `agent/pipeline_parts/stream.py:3473` / `execute.py:87` | **每轮重置** `self._rag_memory_hits`（防跨轮串味 —— 实例状态残留是真隐患） |

**core 层仍由 memory 路径独立查** —— 它的语义是"无条件常驻"，RAG 侧不提供这一层。

### 开关

`context_audit.memory_single_source`（默认 True）/ `context_audit.memory_max_chars`（默认 200），
置 `memory_single_source=False` 即退回改动前行为（门禁 [5] 断言）。

## 4. Step4 · JIT 空回退改语义 top-N（P0-5）

### 问题（实测，生产库）

`tools.py:417` 的空回退逻辑：

```python
chosen = {s[1]["name"] for s in scored if s[0] >= _th}
if not chosen:
    candidates = [c for c in candidates]      # ← 全量注入
```

**根因：把「阈值」当成了「开关」。** 阈值是**质量线**，不是**开关** ——
弱相关时排序**仍有信息量**（最不相关的排在后面）。

实测「帮我把活动图生成出来」⇒ **24 个工具 / 7,487 字符 / 4,162 token**，
而该任务实际只需 sysml 视图类工具；同族意图载荷波动 5→24 个。

### 实施内容

1. 空回退改为**取语义 top-N**（`context_audit.jit_fallback_top_n`，默认 8）
2. `core_keep` 保底**两条分支都并入**（读类核心工具 + 显式绑定的 MCP 不受影响）
3. `rank` 的 `top_k` 随回退 N 调整（`max(jit_top_n, _fb_n)`）——
   否则 `semantic.rank` 返回 `scored[:top_k]` 会提前截断，回退 N 形同虚设
4. 记录 `jit_fallback_full` / `jit_fallback_top_n` / `tool_candidates` 到 `context_audit_summary`
   ⇒ **回退率可观测**

### 实测效果（真实生产库，6 query）

| query | 新（工具数/token） | 旧（工具数/token） | 降幅 |
|---|---|---|---|
| 帮我把活动图生成出来 | 10 / 2,171 | 24 / 4,162 | **−47.8%** |
| 把状态机视图生成出来 | 11 / 2,391 | 24 / 4,162 | **−42.6%** |
| 其余 4 个（本就命中阈值） | 不变 | 不变 | 0% |
| **平均** | **1,713 token** | 2,340 token | **−15.1%** |

### 实施中发现并修正的两个真 bug（门禁抓出）

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| 1 | `jit_fallback_top_n=0` 时工具被**全部清空**（而非全量） | 空回退分支只置了"走全量"的标记，但 `chosen` 仍为空 ⇒ 后续 `candidates = [c for c in candidates if c[0] in chosen]` 把候选全滤掉 | 全量分支必须显式 `chosen = {c[0] for c in candidates}` |
| 2 | bigram 降级时**回退 N 失效**（仍全量） | `semantic.rank(threshold=0)` 会把 0 分条目全过滤 ⇒ `scored` 为空 ⇒ top-N 分支进不去 | `scored` 为空时改用**候选集原始顺序**取前 N（顺序本身携带优先级：内置 → 技能白名单 → 显式绑定） |

## 5. Step6/8 · MCP 工具真实元数据 + 按需暴露（P0-6）

### ⚠️ 评估报告里这一项的判断需要修正（两处）

**修正一：评估报告说"71 工具全量下发 ≈8k token/轮"——生产当前其实一个都没下发。**

`repositories/agent_repo.py:bound_tools_for` 的判据是
`row.get("status") == "online" and row.get("enabled", 1)`，
而生产库 4 个 agent 绑定的 MCP server **全部 `status='offline'`**
（`zhiyuan-dev-mcp` 71 工具、`AI4MBSE 领域能力` 等）⇒ **没有任何 agent 实际注入了 MCP 工具**。

所以"8k token/轮"是**潜在**成本（server 一旦恢复 online 就会发生），不是当前在烧的钱。
这一条对优先级判断很重要：它不是"正在失血"，而是"一旦恢复就失血"。

**修正二：真实成本是 5,467 token，但更严重的问题不是 token 而是可用性。**

模拟 server online 后实测：

| 项 | 实测值 |
|---|---|
| MCP 工具注入数 | 71 个 |
| MCP 部分 token | **5,467**（占整包 71~80%） |
| 单工具 payload | 224 字符 / 77 token |
| **description 去重后种类数** | **1 种**（全是同一句 `MCP 工具（zhiyuan-dev-mcp），端点 ...`） |
| parameters | 全是 `{"type":"object","properties":{},"additionalProperties":true}` |

即：**模型拿到 71 个工具名，但没有一个工具知道是干什么的、参数怎么传**。
这既是 token 浪费，更是**功能可用性问题**——它只能靠名字猜，猜错就调用失败。

### 根因：发现流程**主动丢弃**了 description 与 inputSchema

`mcp_health.discover_server()`：

```python
json.dumps([t.get("name") for t in tools], ensure_ascii=False)   # ← 只存名字
```

而 `mcp_client.list_tools()` 明明返回 `[{name, description, inputSchema}]`。
schema 在**发现那一刻**就丢了，后续所有环节都无米下锅。

### 这也解释了 2026-10-16 的那次决策

代码注释里写着"绑定即全量、JIT 无权裁剪"，事故依据是"绑 71 个只露 6 个、
工程列表查不到"。现在看得很清楚：**那次事故的根因不是 JIT 太狠，而是 MCP 工具
description 全是同一句模板 ⇒ JIT 打分零区分度 ⇒ 只能二选一（全给 / 全裁）**。
把元数据修好之后，这个二难就自然消失了。

### 实施内容（两段式，对齐「先无损、后有损」）

**第 1 段：把丢掉的东西存回来（修数据，不改行为）**

- `mcp_servers` 新增 `tool_meta` 列（JSON：`[{name, description, inputSchema}]`）
- `schema.py` 建表 + `migrations/columns.py` 幂等补列（存量库自动升级）
- `discover_server` 落库时**同时**写 `tools`（原字段不变，兼容既有消费点）与 `tool_meta`
- `repo.update_mcp_discovery` 新增 `tool_meta=""` 参数：**空值不覆盖已有值**
  （防旧调用方把已发现的 schema 抹掉）

**第 2 段：按需暴露（减少注入量 + 提升可用性）**

- 新增 `agent/mcp_tool_meta.py`：`save_tool_meta` / `load_tool_meta` / `pick_for_injection`
- 注入侧（`tools.py`）有 `tool_meta` 时：
  - description 用**真实描述**（模型终于知道工具干什么）
  - parameters 用**真实 inputSchema**（参数契约，不再"任意参数"）
  - 每个 server 只暴露 `mcp_min_keep`（默认 8）个——按语义排序取前 N
- `core_keep` 粒度**前移**：筛选只在 `pick_for_injection` 做一次，
  选出的集合整集进 `core_keep`，JIT 不得二次裁剪
  （否则 `mcp_min_keep` 的"至少露 N 个"保证会被 JIT 再削掉）

**第 3 段（关键，否则整套改动空转）：机会式回填**

`check_all` 巡检此前**只做 initialize 握手，不调 tools/list**
⇒ 存量 server 的 `tool_meta` 永远是空的 ⇒ 注入侧永远走旧分支
⇒ **改了个寂寞**（本仓已经吃过两次这种亏："看起来绿但实际空转"）。

现在：巡检发现某 server `online` **且** `tool_meta` 为空时，自动补跑一次完整 discover。
成功 ⇒ `tool_meta` 非空 ⇒ 触发条件自然失效（数据自驱，无额外状态）。
失败 ⇒ 记 `backfill_error` 留痕 + **1 小时冷却**（否则持续故障的 server 会被每轮巡检反复打）。

### 实测效果（模拟 server online，真实 71 个工具名，12 组 agent×query）

| 指标 | 改动前 | 改动后 | 变化 |
|---|---|---|---|
| 整包 token | 7,241 | **2,200** | **−69.6%** |
| MCP 部分 token | 5,467 | **683** | **−87.5%** |

### 实施中发现并修正的三个真 bug

| # | bug | 后果 | 修法 |
|---|---|---|---|

## 5b. Step9 · role 块内工具手册按需裁剪（P0-7）—— **本轮单项收益最大**

### 怎么发现的：不是读代码，是端到端实测的块分布

用 `context_audit` 在**真实 `execute` 链路**上量出块分布后，看到两件事：

| 现象 | 数据 |
|---|---|
| system 占整包 **98%** | system 4,401 tok vs messages 89 tok |
| `role` 在 chat 场景只有 859 tok | 但 `智源对接agent` 的 `system_prompt` 是 **14,538 字符** |

顺着"为什么差 17 倍"查下去，得到**决定性事实**：

| Agent | system_prompt | 其中工具手册 | 手册占比 | 非工具叙述 |
|---|---|---|---|---|
| **智源对接agent** | **14,538 字符 / 8,995 tok** | **14,531 字符 / 8,987 tok** | **100.0%** | **仅 7 字符** |
| 其余 16 个 active Agent | 144 ~ 2,583 字符 | 0 | **0.0%** | 全部 |

即 `智源对接agent` 的 system_prompt **实质上是一份 58 个 MCP 工具的使用手册容器**，
没有任何身份/职责描述。这不是"写得长"，而是**内容类型错了**。

### 为什么这是浪费（比 token 数字更本质）

1. **与工具暴露粒度脱节**：上一轮已把 MCP 工具按需暴露到 8 个（`mcp_min_keep=8`），
   而 role 里仍是 58 个工具的全文说明 ⇒ **50 个工具的用法对应的工具本轮根本没进 payload**。
2. **MCP offline 时 100% 死重**：生产库该 server `state='offline'` ⇒ 一个 MCP 工具都不可用
   ⇒ 这 8,987 tok **完全无用**，却每轮照付。
3. **信息密度恶化**：模型要在 14,531 字符里找"本轮能用的 8 个工具"的说明，
   信噪比约 8:58。

### 实施（保守：只裁能可靠识别的段）

新增 `agent/role_manual_filter.py`（纯函数，可单测）：

1. **识别**：工具名**独占行首**才算段落起点（`re: ^工具名[ \t]*$`），
   只对 `mcp_servers.tools` 里登记的工具名做匹配（名字来源确定，不靠猜）。
   正文里"用 query_projects 查询"这类**提及不会误切**（门禁 [7] 专测）。
2. **保留**：非手册段（`__prose__`）**永远保留**；手册段仅保留本轮暴露工具对应的。
3. **兜底**（任一情形 ⇒ **逐字节原样返回**）：
   · 开关关闭（默认）· 未识别到手册段 · 暴露集为空 · 切分拼回 ≠ 原文

> ⚠️ 关键取舍：**"暴露集为空"时绝不删光手册**。
> 无法区分"真的没暴露"和"没算出来"，此时删手册是把**信息缺失**变成**指令缺失**。

### 复算暴露集，而不是重排主流程

`build_prompt_blocks` 在 `execute` 里**先于** `_build_tools_def` 执行（`:400` vs `:469`），
此刻还没有 tools_def。两个选项：

| 方案 | 代价 |
|---|---|
| 把 tools_def 提前 | 动主流程，风险高 |
| **复算（采用）** | 读一次 tool_meta + 纯字符串打分，无 DB 写、无模型调用 |

复算用与 `tools.py` **同一个纯函数** `pick_for_injection`，结果确定（门禁 [5] 验确定性）。

### 实测效果（真实 execute 链路，forced_intent=智源对接agent）

| 指标 | A 全关 | B 元数据开·裁剪关 | **C 元数据开·裁剪开** |
|---|---|---|---|
| role | 8,996 tok | 8,996 tok | **697 tok** |
| system 合计 | 12,677 tok | 12,677 tok | **4,378 tok** |
| 块数 | 13 | 13 | 13（不变） |

- **role −92.3%**，**system 合计 −65.5%**
- 归因：`role_manual_dropped_chars=13,602`、`role_manual_kept=8`、`role_manual_exposed=8`

### 为什么默认关闭

这是**改模型可见内容**，风险等级高于前几项（那些只改注入量/去重/去冗余）。
必须先在生产看到 `role_manual_dropped_chars` 有值、且**任务正确率不掉**，再逐 Agent 打开。
开关：`context_audit.role_manual_filter`（默认 **False**）。

### 顺带修掉的一个真 bug：纯指标归因从未落库

`record_blocks({}, phase=..., extra={...})` 在**入口** `if not blocks: return 0` 就被丢弃
⇒ **带 extra 的纯指标归因一条都没写进库**。这影响：

- 本轮的 `role_manual_*`
- 上一轮的 `jit_fallback_full` / `mcp_*`（**同样从未落库**）

即"记录了但查不到" —— 与本仓反复出现的"看起来绿实际空转"同族。
已修为"`blocks` 与 `extra` **皆空**才返回"，并同步修 `flush()` 里的 `if not blocks: continue`。

> 这个 bug 是**写门禁时被"归因落库"这条判据抓到的**（门禁 [12] 一开始 FAIL）。
> 如果只做单元测试不查库，它会一直隐身。

### 配套工具

`tools/analyze_role_manual.py` —— 只读诊断，供运营评估：

```bash

```

## 9. 后续建议（基于 Step1 新增的观测能力）

现在 `context_audit` 已能回答"每轮 token 花在哪"。建议下一步做：

1. **先跑一周生产数据**，用 `context_audit_summary` 的 `metrics` 字段量化：
   - `retrieval_effective` vs `retrieval_nominal` ⇒ 检索多样性改动的真实收益（生产口径）
   - `jit_fallback_full` 占比 ⇒ 空回退的实际发生率（决定 `jit_fallback_top_n` 该设多少）
   - `memory_unique` ⇒ 记忆去重的实际收益
   - `mcp_total` / `mcp_selected` / `mcp_injected` ⇒ MCP 暴露比例（决定 `mcp_min_keep` 该设多少）
2. **按块看 token 分布**，找出真正的头部消耗块（可能不是 `role` 而是 `retrieval`）
3. **确认 MCP 回填已发生**：巡检日志应出现
   `[mcp-health] 已回填 <server> 的工具元数据（N 个工具：description + inputSchema）`。
   若某 server 一直是 `[mcp-health] 回填工具元数据失败 ...`，说明它 `list_tools` 不通，
   此时注入侧仍走旧分支（全量 + 模板描述）——**不会坏，但也没收益**。
4. 基于实测再决定是否做「MCP 按语义族分层」（上表 #6）

> **纪律**：后续任何调优都应保持"**先观测 → 再改 → 用同一批任务 A/B**"的顺序，
> 判据三件套：**token 消耗 + 任务正确率 + 要求保留率** ——
> "省 30% token 却遗漏关键要求 = 没达到目的"。

## 10. Step10 · 上下文归因查询接口 + 报表（P0-8）

### 动机

`context_audit` 自 Step1 起已在真实链路落库，但**没有任何消费方**：
`routers/` 下只有 `conversations.py:510` 一处 `flush()`，无查询接口、无报表。
⇒ 数据在库里、业务方看不见、开关取舍靠猜（盘点文档 §2.2 记为"本期最大交付缺口"）。

### 新增

| 文件 | 作用 |
|---|---|
| `repositories/context_audit_repo.py` | 只读聚合：`blocks` / `daily` / `conversations` / `switches` / `ready` |
| `routers/diagnostics.py` | 5 个只读端点（`/api/diagnostics/context-audit/*`） |
| `tools/report_context_audit.py` | 命令行报表（`--all` / `--json` / `--conversation`） |
| `tools/verify/verify_context_audit_api.py` | 21 项验收 |

### 三处设计要点

**① 就绪自检（`ready()`）而不是让 SQL 抛错**

建表在 `init_db()` 里，**只在应用启动时执行**。⇒ 任何"离线读库"场景
（命令行报表 / 运维脚本 / 指向旧快照的只读连接）都会撞
`no such table: context_audit`。实测本仓生产快照正是如此。
`ready()` 把它变成一句可操作提示（含修复命令），而不是一堆 traceback。

**② 「块合计 < 计费 prompt_tokens」不是 bug，报表显式标注**

`context_audit` 只记 system prompt 的块，messages / tools payload 不在其中。
`conversations?conversation_id=` 端点**显式给出差额** `delta_messages_tools`，
避免被误读成"归因漏了"。

**③ 归因指标只支持数值，mode 用 `xxx: 1` 编码**

`record_blocks(extra=...)` 内部按累加计数处理，字符串会被记成 `1`
（Step9 踩过：`role_manual_mode: "applied"` 落库后变成 `1`）。
现在统一成 `role_manual_applied: 1` 这种**可自解释的键名**。

### 实测输出（真实链路产生 2 轮数据后）


## 11. Step11 · 语义缓存接入流式路径（P1-1）—— 顺带修掉**三个死代码**

### 发现 1：`semantic_cache` 在 `stream.py` **0 处引用**

实测：`grep -c semantic_cache agent/pipeline_parts/stream.py` = **0**；
而生产 SSE 入口（`routers/conversations.py:391`）走 `execute_stream`
⇒ **主对话完全不享受语义缓存**。而 `chat_probe`（主对话）占真实 token 的
**51%**（15.6M / 30.47M）。

### 发现 2：原闸门 `not tools_def` **恒为 False** —— 该特性从未命中过一次

```python
if intent in ("chat","knowledge_qa") and not att_blocks and not att_images and not tools_def:
```

实测 `chat` intent **恒注入 8 个工具**：

```
intent='chat' q='什么是 SysML v2 的活动图'
  tools_def 条数=8 names=['sysml_ast_extract','sysml_stdlib_meta','sysml_v2_project_check',
                          'sysml_v2_validate','graph_retrieve','impact_analyze','validate','ask_user']
  ⇒ 闸门 not tools_def = False
```

原因：`core_keep` 的 3 个读类核心工具 + `ask_user` **无条件注入**。
⇒ 该闸门在 `execute.py` 与 `stream.py` **两条路径上都是死代码**，
语义缓存自上线以来**一次都没命中过**。

**修法**：去掉 `not tools_def`，把安全性交给**写入侧** ——
只有「本轮实际没调任何工具（`exec_tools` 空）、无附件、无澄清」的纯问答答案才入库
⇒ 任何命中天然是"无需工具"的结论。读取侧再用 `tools_def` 把关只会误杀。

### 发现 3（位置陷阱）：不能放在 `not tool_injected` 分支里

第一版把缓存判定放在"生成段"前（`if not tool_injected:`），实测**永不执行**：
ReAct 探测轮即使无 `tool_calls` 也会 `tool_injected = True`（`stream.py` 探测轮分支）
⇒ 该判定恒为假。**与发现 2 是同一种错**：把某个变量的"某个取值"当成"必然状态"。

**修法**：判定前移到 **ReAct 之前**，命中则**短路整轮**：

```python
llm_content = _cache_answer
tool_injected = True       # 让下方生成段跳过
tools_def = None           # 让 ReAct 立即 break
```

后续落库 / done / 审计 / citations **全部沿用原路径**（零分叉）。
不做早期 `return` —— 那需要复制上百行收尾逻辑，必然与主路径漂移。

### 实测（打桩验证接线，不依赖 embedding 服务）

```

runB: token事件=4 正文=93 provider=semantic-cache  hit=True tokens={0,0}   get=2 put=1
```

- **不谎报**：`latency_ms=0`、`tokens` 全 0、`used_mock=False` ✅

## 12. Step12 · P0-9：MCP 显式绑定被技能白名单**静默清零**（本轮最严重的发现）

### 怎么发现的

Step10 的报表里出现一行反常数据：**`mcp_selected=8` 但 `mcp_injected=0`** ——

## 19. Step17 · P4 动态区缓存友好重排（**零内容变化**，已落库）

### 动机：实现与自身声明的原则不一致

`common.py:228` 早就写了动态区的排序原则：

> 元组顺序 = 实际拼装顺序（**层内按「依赖的易变度」升序**，让相对稳定的块尽量靠前）

但 `skill_prompt` 依赖 `user_input`（每轮可能变），却**排在第 3 位**，把它之后的
`memory` / `model_context` / `project_memory` / `slots` / `user_ctx` 一起拖成缓存 miss。

这次改动**不是引入新原则，是让实现符合注释**。

### 调研：先证明「哪个块真的会变」

同一会话（conv=9571）× 8 个不同 query，逐块 md5：

| 区块 | 均 tok | 唯一值 | 判定 |
|---|---|---|---|

## 20. 本轮否证：三个原计划项被数据推翻（重要，防止重复投入）

### 20.1 P1「history 超预算，需压缩」——**前提不成立**

| 项 | 实测 |
|---|---|
| history 预算 `ctx_budget_tokens("history", …)` | **32,000 tok**（`budget_history_ratio=0.25` × 128k） |
| 最大会话实际装配用量（6 个大会话） | **4,166 ~ 7,779 tok** |
| 结论 | **根本没超预算**，不存在"被预算逼着压"的情形 |

`_load_history` 已是**四通道混合**（产物 digest → 话题摘要 → 语义拉回 → 当前话题原文），
每条长消息过 `clip_hist_msg`（保留头部 + 明示标记 + 章节提纲）。这是 2026-10-22
针对真实事故（会话 9587 消息 4776：模型以为报告中途断了，把后半篇重写一遍）修出来的。

**再压缩不是"省预算"，是"主动牺牲已验证的平衡点"。** 在没有质量验证手段时不建议动。

### 20.2 P2「`skill_prompt` 可瘦身」——**内容已是最小必需**

拆开 2,271 tok 看：

| 组成 | tok | 可否砍 |
|---|---|---|
| 未命中技能的一行目录 | **6** | 太小，无可拆 |
| 命中技能详情 | **2,265（99.7%）** | 其中正文已 `offload`（原 9,396 字符→引用块），剩下的是**元数据 + 轮次预算 + 头部摘要（含「本视图硬约束（违反即不合格）」）** |

⇒ **剩下的是必需内容，砍它等于砍约束**。P2 无空间。

### 20.3 P4 原设计「拆稳定目录 + 动态详情」——**无可拆**

稳定目录只有 6 tok（上表）。故改为**只重排、不拆分**（见 §19）。

### 20.4 附带发现：历史里代码块"完整保留率 0%"，但**已有兜底，不是缺陷**

40 条 >1,500 字 assistant 消息实测（`clip_hist_msg` 后按 `(首行, 末60字)` 精确匹配）：

| msg_max | 章题保留 | **代码块完整保留** | 数字保留 |
|---|---|---|---|
| 1500（当前） | 40.8% | **0.0%** | 61.8% |
| 1000 | 30.9% | 0.0% | 53.6% |
| 800 | 26.9% | 0.0% | 49.2% |

`sysml_versions.element_summary` → `session_artifacts.build_digest` 注入「本会话既有产物」

⇒ **模型不需要从历史消息里读代码**，所以历史里的代码块丢失不影响任务。

## 21. Step18 · 观测面板前后端（2026-10-27）

### 21.1 先修语义（不修则面板首屏就是错的）

原 `switches()` 对**所有**指标一律累加。但指标分两类语义：

| 类型 | 含义 | 累加是否合理 |
|---|---|---|
| `count` | 一次装配里"发生了几次" | ✅ 合理（窗口内总次数） |
| `gauge` | 一次装配里"当时是多少" | ❌ **完全错误** |

实测后果：`mcp_selected=8`（每轮暴露 8 个工具）经 4 轮累加成 **32**，
前端若显示「MCP 32/71」会让人误判"暴露了近一半工具"，真实是「每轮 8/71」。
**观测工具变成误导工具，比没有观测更糟。**

**修法**：`METRIC_KINDS` 显式登记计数型（7 项），**其余默认 `gauge`**（保守：
不理解语义的指标宁可给均值，也不给会翻倍的和）。每项返回
`{kind, value, sum, avg, max, last, samples, unit}`，`value` = count→sum / gauge→avg。
前端**不自己判断**语义 —— 判断逻辑只存一份，避免前后端各写一遍必然漂移。

**`samples` 必须是「该指标实际出现次数」**，不是窗口内 summary 总行数：
`retrieval_effective` 只在 8 轮里的 2 轮出现 ⇒ 分母应为 2 而非 8，
否则均值被系统性算小。

### 21.2 实测抓到的两个真缺陷（都会让首屏数字失真）

**① `total_hits` 不是装配次数，是块行数之和**

```
实测（8 轮真实装配）：total_tokens=52,473 / total_hits=106 / assemblies=8
正确均值 = 52473/8   = 6,559 tok/轮
错误均值 = 52473/106 =   495 tok/轮   ← 小了 13.2 倍
```

106 = 每轮约 13 个块 × 8 轮。拿它当分母算"每轮 system 均值"，首屏第一个
数字就错一个数量级。**新增 `assemblies`（`COUNT(DISTINCT trace|conv|phase)`）
与 `avg_system_tokens`，前端改用前者。**

**② 「缓存断点」被按 token 大小判定，而非 prompt 拼接顺序**

`blocks()` 的行是 `ORDER BY tokens DESC`，所以"第一个 dynamic 行"只是
**最大的动态块**，不是顺序最靠前的。实测两者不同：

```
按 token 降序首块 = model_code_req（1,092 tok/轮）
prompt 顺序首块   = intent_line   （  241 tok/轮）  ← 真正的断点
```

**修法**：后端按 `PROMPT_DYNAMIC_KEYS` 顺序算出 `cache_boundary` 下发，
并附 `dynamic_order` 供核对。
