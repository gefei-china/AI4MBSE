# 导航侧「项目（工程）」入口 · 调研与产品设计方案

> 议题：很多 AI 平台在导航侧都有"项目"入口 —— 它的目的是什么？本项目怎么实现更合理？
> 角色：AI 产品经理视角 ｜ 日期：2026-09-17
> 结论先行：**"项目"的本质是「上下文容器 + 数据边界」，不是一个列表页。** 而本系统**已经有工程概念**（顶栏"当前工程"、分支、项目记忆、工程入库、智源 projectId/branchId），只是它是**运行时单值、未实体化、查询未隔离**。
> 因此正解不是"引入新概念"，而是：**把工程实体化，并在导航侧给它一个入口 + 一个切换器**。

---

## 1. 外部调研：AI 平台的"项目"到底在解决什么

### 1.1 两个基准产品的事实

| 产品 | 项目的构成 | 目的（官方表述） | 来源 |
|---|---|---|---|
| **ChatGPT Projects** | ① 专用**会话容器**（同项目多会话归组）② 集成**文件仓库**（对话中可"Save to project"回存为项目源）③ **项目级指令**（覆盖全局 custom instructions）④ **项目专属记忆**（只从本项目对话取上下文） | "smart workspaces that keep everything related to a long-running effort in one place"；"Files, instructions, and chats live in one place so ChatGPT stays on-topic"；可**把已有聊天拖进项目**（Move to project，移入后继承项目的指令与文件上下文） | OpenAI Help Center「Projects in ChatGPT」；OpenAI Academy「Projects」 |
| **Claude Projects** | ① 自定义指令（等价 system prompt）② 知识文件（约 200K tokens 上限）③ 会话分组 | 消除"每次重复粘贴同样的上下文"；项目内**每个会话彼此独立**，但共享同一套指令与知识 | Anthropic/多个第三方评测（prismix.dev、producttalk.org） |

### 1.2 归纳："项目"的四个本质目的

| # | 目的 | 说明 | 对本系统的意义 |
|---|---|---|---|
| **P-1** | **上下文复用** | 指令/文件/知识一次配置，多会话继承，免重复粘贴 | 工程的本体、词典、分支、项目记忆天然属于这一层 |
| **P-2** | **边界隔离** | 记忆/知识/权限限定在项目内，不串味、不越权 | 直接对应本系统的**会话串号缺陷**（见 §2） |
| **P-3** | **工作组织** | 长周期、多会话的工作归到一个容器里 | 左侧任务列表需要按工程收敛 |
| **P-4** | **协作与复用** | 团队共享同一份上下文，形成可重复工作流 | 对应现有角色权限（设计师/知识工程师/管理员） |

> 关键结论：**"项目"放在导航侧，是因为它是"作用域切换"（scope switch），而不是一个功能页。** ChatGPT 侧边栏的项目列表本质是"切换上下文边界"的快捷方式 —— 这一点决定了本项目的实现形态：**入口 + 切换器 > 管理页**。

## 2. 本系统现状：有"工程"，但是"假工程"

经代码核实（证据均为 `文件:行`）：

| 现状事实 | 证据 | 问题 |
|---|---|---|
| `conversations` 表**已有 `project_id` 列**，迁移时回填为 `1` | `database/schema.py:257`、`database/migrations.py` 回填语句 | 字段存在但形同虚设 |
| **3 处写入全部硬编码 `1`**，没有任何业务逻辑 | `routers/conversations.py:93, 95, 116` | 所有会话永远属于"1 号工程" |
| 会话查询**完全没有按 project_id 过滤** | `routers/conversations.py:44–52` `list_conversations()` 无 WHERE | 切换到任何工程，任务列表都不变 |
| 前端"当前工程"靠**偷一条会话**反查 | `static/js/mods/03-chat.js:128` 请求 `/api/conversations?limit=1` 后取 `project_id` | **多工程时会串号**：并发写入下取到别的工程的会话，顶栏显示错误工程 |
| **不存在 projects 表**；没有工程资产、成员、生命周期 | 全库 grep 无 `CREATE TABLE projects` | 工程无法被管理（建/改/归档/授权） |
| "当前工程"实为**智源连接器运行时状态**：调 `projects.project_list` → 取首条 → 写 settings | `zhiyuan_client.py`、能力中心→工具与MCP→智源连接器→「检测连接」 | 切换入口藏在 4 层深处；工程不是一等公民 |
| 知识库数据（glossary / entities / chunks / documents）**基本无 project 列** | 仅 `kb_category.project_id` 一处孤例 | 知识资产谈不上按工程隔离 |
| 分支（branches）是自有分支树，非 git 分支；本体/图谱受工作分支约束 | `branch_guard`、`sync_scope` | 分支 ≠ 工程，两者是不同维度 |
| **无鉴权**：`/app.js`、`/app.css` 等静态资源直出 | `routers/meta.py:972, 978`；用户已确认单用户内网免登录 | 权限设计保持"预留不实现" |

**一句话诊断**：**工程是"显示用的标签"，不是"约束数据的作用域"。** 这正好是外部产品里"项目"要解决的四件事一件都没做到的形态。

## 3. 设计目标 / 非目标

**目标（可验收）**

1. 导航侧**一键看到并切换**工程，切换后**会话列表、知识入口、当前分支**全部跟随（≤2 次点击）。
2. 任一时刻系统**只有一个明确的当前工程**，且**不再靠偷会话反查**（消除串号缺陷）。
3. 工程成为可管理实体：新建 / 重命名 / 归档 / 设置默认分支 / 关联智源 projectId+branchId。

**非目标（明确不做）**

- 不做多租户 SaaS、不做工程级 RBAC 完整实现（仅预留字段与入口）；
- 不做 git 式分支管理（已有 `branches`）；
- 不把工程做成"第二个知识库"（知识库是工程的作用域对象，不是替代品）。

## 4. 方案

### 4.1 信息架构（IA）

```
左侧导航（mainnav）
├─ ＋ 新建任务
├─ 💬 AI 建模
├─ 📁 项目（工程）★新增入口
│     ├─ 当前：星网宽带通信系统
│     └─ hover/点击 → 工程切换浮层（切换器）
│            ├─ 🔍 搜索工程
│            ├─ 🕘 最近使用（≤5）
│            ├─ 📋 全部工程 →　
│            └─ ＋ 新建工程
├─ 📖 术语词典
├─ 🧬 本体模型
├─ 🕸 知识中心
├─ 🤖 能力中心
└─ ⋯ 更多

顶栏：当前工程标签（ai-project-tag）→ 变为**可点击切换器**（与导航项同一个浮层组件）

工程中心页（点击「📋 全部工程」进入，新增 pg-project）
├─ 头部：当前工程卡片（名称/代号/智源 projectId+branchId/默认分支/成员数）
├─ 工程卡片列表：名称 · 代号 · 最近活动 · 会话数 · 文档数 · 状态（活跃/归档）
├─ 操作：进入（切换）/ 重命名 / 归档 / 新建
└─ 空态：卡片式引导「新建第一个工程」
```

### 4.2 关键交互

| 场景 | 交互 | 设计理由 |
|---|---|---|
| 看当前工程 | 导航项常驻显示**当前工程名**（不是泛化的"项目"二字）；顶栏标签同步 | 让"作用域"始终可见 —— 这是外部产品的共同做法（ChatGPT 顶栏始终显示所在项目） |
| 切换工程 | 点导航项 → 右侧/上方浮层（搜索 + 最近 + 全部 + 新建）；选中即切换，**先给确认提示**："切换将重置当前工作上下文（会话/知识/图谱按新工程加载）" | 切换有成本，必须显式告知 |
| 切换后的联动 | ① 任务列表刷新为该工程会话 ② 知识中心/本体按工程策略加载 ③ 顶栏工程名与分支同步 ④ 记入最近使用 | 一次切换多面跟随，避免"只换了个标签" |
| 会话归属 | 新建会话自动归属当前工程；会话行右键「移入其他工程」（对齐 ChatGPT 的 Move to project） | 复用外部产品已验证的心智 |
| 工程创建 | 名称 + 代号（key）+ 可选关联智源项目；创建后可选「按模板生成资料库目录骨架」（与议题 1 的 A1 联动） | 一次创建即就绪 |
| 归档 | 归档后不在切换器默认列出，但可搜索到；其会话只读 | 防误删，保留历史 |
| 工程与分支 | 工程设"默认分支"，知识库工具行分支切换器仍可用（手动覆盖） | 两个维度正交，不互相取代 |

### 4.3 数据模型

```sql
CREATE TABLE projects(
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  key TEXT UNIQUE,                 -- 代号，如 satnet-broadband
  name TEXT NOT NULL,
  description TEXT,
  zy_project_id TEXT,              -- 智源 projectId（现散落在 settings.ZY_STATE）
  zy_branch_id  TEXT,              -- 智源 branchId
  default_branch TEXT,             -- 默认知识分支（可空）
  status TEXT DEFAULT 'active',    -- active / archived
  created_by TEXT, created_at TEXT, updated_at TEXT
);
-- 会话已有列，改为真实使用（无需 DDL）
-- conversations.project_id  → 外键语义指向 projects.id（SQLite 宽松，不加约束亦可）
-- 用户当前工程（服务端单值，单用户内网场景）
CREATE TABLE user_state(k TEXT PRIMARY KEY, v TEXT);   -- key='current_project_id'
```

### 4.4 隔离策略：**分层隔离，不一刀切**（最重要的设计判断）

| 资产 | 隔离策略 | 理由 |
|---|---|---|
| **会话** | **强隔离（P0）** | 会话是个人上下文，串号是缺陷不是特性；且 `project_id` 列已就绪 |
| **资料库文档 / 目录** | 目录支持 `project_id`（可空），**默认跟随工程、允许"共享目录"** | 型号间引用同一份国家标准是常态，硬隔离会逼用户重复上传 |
| **本体 / 术语词典** | **默认共享（全工程共用），不隔离** | 本体是组织级标准资产（Schema 层），按工程复制会立刻产生多份不一致的"标准" |
| **图谱实例 / 模型** | **按工程隔离（P1）** | 模型实例是型号专属产物 |
| **项目记忆** | 已按 project 维度存储 → 直接接入（P1） | 现有能力 |

> 若采用"全部强隔离"，代价是标准资产无法复用、且会与《AI4MBSE 平台：知识库分支为单一事实源（D-3 决策）》冲突——这是必须避免的方向性错误。

### 4.5 迁移（零数据损失）

1. 建 `projects` 表，插入一条 `id=1`、`key='default'`、`name='默认工程'` → **现有全部会话（project_id=1）无缝归位**。
2. 若当前已从智源取到工程信息，则把该工程的 `name/key/zy_project_id/zy_branch_id` **回填到 id=1 这条记录**（而不是新建，避免历史会话孤儿）。
3. 前端"当前工程"改为读 `GET /api/projects/current`，删除 `?limit=1` 偷取逻辑。
4. 任务列表查询加 `project_id` 过滤（后端 `list_conversations` 增加可选参数，默认取当前工程）。

## 5. 分期

| 期 | 范围 | 验收标准 |
|---|---|---|
| **P0（基础实体化 + 消除缺陷）** | `projects` 表 + `id=1` 迁移回填；`GET/POST /api/projects`、`GET /api/projects/current`、`POST /api/projects/switch`；导航新增「项目（工程）」入口 + 切换浮层；顶栏工程标签变切换器；任务列表按当前工程过滤；删除 `?limit=1` 反模式 | 新建 2 个工程、各自开会话 → 切换工程时任务列表**只显示本工程会话**；顶栏工程名始终与任务列表一致；无串号 |
| **P1（联动与组织）** | 工程中心页（pg-project）+ 会话「移入其他工程」+ 资料库目录挂工程 + 项目记忆接入 + 模型实例按工程隔离 | 切换工程后，会话/文档/记忆三处内容同步变化 |
| **P2（治理）** | 工程成员与角色映射、归档策略、工程模板（预置目录骨架 + 本体子集）、智源双向同步（工程级） | 归档工程只读；模板创建即就绪 |

## 6. 风险

| 风险 | 应对 |
|---|---|
| 切换工程的认知成本高（用户点了才发现"全空了"） | 切换前显式提示 + 浮层里在每个工程卡片上显示"会话数/文档数"，让用户预判 |
| 隔离过度 → 标准资产重复建设 | 采用 §4.4 分层策略，本体/词典默认共享 |
| 命名双口径（"项目" vs "工程"） | **统一叫「工程」**——理由：代码与既有文案（当前工程 / 工程入库 / 检测连接）全部用"工程"，且今日导航口径审计暴露的 P1 问题**正是双口径引起**（详见 `导航结构与整合残留审计-20260917.md` §3）。如坚持叫"项目"，则必须**一次性全量替换**，不可混用 |
| 智源连接器把工程写进 settings，形成第二份事实源 | 以 `projects` 表为唯一事实源，智源字段作为工程的属性写入，不再单独存 settings 单值 |
