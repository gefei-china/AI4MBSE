## 一、原理：HITL 要解决哪三个矛盾

写前确认不是"加个弹窗"，而是解决三组**互相拉扯**的矛盾。方案里每一条设计都要能指回其中一条。

| 矛盾 | 表现 | 设计对策 |
|---|---|---|
| **① 授权 vs 效率** | 每个写操作都问人 ⇒ 建模流程被切成几十步，人烦到直接点"全同意"，HITL 退化成形式主义 | **分级 + 批次合并**（§4.1、§4.4）：只对"最终生效且不可逆"的操作逐条问；连续同类写合并成一个确认单 |
| **② 模型自律 vs 系统强制** | 技能正文写"写操作前必须获用户确认"，实测模型**会绕过**（直接 `create_model_elements`） | **判定下沉到执行侧**（§4.2）：模型不参与决策，能否执行由代码决定 |
| **③ 事实 vs 陈述** | 工具已成功，模型却说"尚未写入"（E8）；或反之 | **回执回灌**（§4.8）：把真实执行结果作为事实注入，而非让模型从长 messages 里"看漏" |

**一句话**：HITL 的本质是**把授权决策从模型手里挪到系统手里**，再用**确定性的回执**把结果还给模型。

## 二、现状勘察：三道闸与三处断链

## 三、目标机制

### 3.1 三泳道数据流

```
模型泳道              系统泳道                        人泳道
─────────────────────────────────────────────────────────────────
tool_call 请求 ──▶ ② 统一 HITL 闸
                    │  双源判定写类 + 查策略
                    ▼
                  ③ 生成确认单 ──── hil_confirm 事件 ──▶ 确认卡
                    （参数完整快照）                    （展示影响面）
                    │                                    │
                    │                              批准 / 拒绝
                    ▼                                    │
                  ④ 执行或标记拒绝 ◀──────────────────────┘
                    │  幂等键防重复执行
                    ▼
⑤ 回灌真实回执 ◀── 写入 result_json
   （新的一轮）
```

### 3.2 状态机

```
tool_call
  └─▶ classify_write()  →  level
        ├─ auto    → 直接执行 → done
        ├─ notify  → 执行 + 留痕（前端可追溯） → done
        └─ confirm / approve
              └─▶ queue_confirmation()  → status=pending
                    └─▶ 发 hil_confirm 事件，ReAct 循环 break（挂起）
                          └─▶ 用户决定
                                ├─ approve → status=approved
                                │             └─▶ 统一执行器 → status=executed (+result_json)
                                │                   └─▶ 回灌 LLM（新的一轮）
                                ├─ reject  → status=rejected
                                │             └─▶ 回灌 LLM（拒因）
                                └─ timeout → status=expired
                                              └─▶ 回灌 LLM（未响应）
```

`status` 扩展：`pending / approved / rejected / executed / expired / failed / superseded`
（现状只有 `pending / approved / rejected`，**缺 `executed` ⇒ 无法区分"批了但没跑"与"跑成了"**）

## 四、具体方案

### 4.1 分级策略（执行侧口径）

| level | 判定 | 动作 | 对应 `agents.hil_level` |
|---|---|---|---|
| `auto` | 只读 | 直接执行 | L0 |
| `notify` | 可逆写、低影响 | 执行 + 留痕 + 可事后追溯 | L1 |
| `confirm` | 写库但可逆（create / update / move / clone / annotate） | **进确认队列，逐条或按批审批** | L2 |
| `approve` | 不可逆 / 破坏性（delete / import / apply / undo / overwrite） | **进确认队列 + `hil:approve` 权限门 + 超时兜底** | L2 + 策略升级 |

> ⚠️ **执行侧口径严于注入侧，这是有意的**：
> 注入侧动词闸只挡 5 族（`mcp_tool_meta.py:353`），因为它问的是"**这一轮该不该把这个工具递到模型眼前**"（恰当性）；
> 执行侧要挡 create/update，因为它问的是"**这个操作要不要人点头**"（授权）。
> 两者**正交**，不是同一件事。

### 4.2 拦截点与双源判定

**拦截点**：`tools.py::_exec_tool_call`（`:760`）内部，插在 **RBAC 闸之后（`:904`）**、
**Hook 闸之前（`:985`）**。

为什么是这里：
1. **唯一收口点** —— stream 主路径（`:4743`）、stream 收尾修复轮（`:5110`）、
   execute 非流式（`execute.py:652`）、异步续跑（`agent/async_jobs.py:319/400`）全部经它
   ⇒ **一次实现覆盖四条路径**
   （全仓 grep `_exec_tool_call` 调用点：**仅这 4 处** + 定义处，无遗漏）
2. **参数已解析** —— `arguments` 已是 dict，可完整展示给人看
3. **三类执行全在其下游** —— MCP（`:1115`）/ HTTP（`:1141`）/ local（`:1166+`）
4. **保留既有不变量** —— `tools.py:870-876` 明确写"顺序刻意在 Hooks / HIL / destructive 三道闸之前，
   无权限的人不该让工具走到"要不要人工确认"这一步" ⇒ HITL 闸**必须在 RBAC 之后**

**双源判定**（复用 `stream.py:104-121 _is_write_tool` 的既有范式）：

```python
def classify_write(pipe, name: str) -> tuple[str, str]:
    """返回 (level, reason)。level ∈ {auto, notify, confirm, approve}。"""
    # ── 源 1：tools 表 side_effect（本地工具）──
    se = pipe._tool_side_effect(name)
    if se == "destructive":
        return "approve", "tools.side_effect=destructive"
    if se == "write":
        return "confirm", "tools.side_effect=write"

    # ── 源 2：MCP 动词族（MCP 工具不在 tools 表，源 1 恒判 read）──
    from agent.mcp_tool_meta import mcp_write_group, MCP_DESTRUCTIVE_GROUPS
    grp = mcp_write_group(name)
    if grp in MCP_DESTRUCTIVE_GROUPS:      # delete/import/apply/undo/overwrite
        return "approve", f"mcp_verb={grp}"
    if grp:                                 # create/update/move/clone/...
        return "confirm", f"mcp_verb={grp}"

    return "auto", "read_only"
```

> ⚠️ 动词族判定是**子串匹配**（`if grp in n`）⇒ 存在误判可能（如 `apply` 命中 `applier`）。
> **缓解**：命中 `approve`/`confirm` 后，回填**工具真实描述与参数预览**给人看，
> 由人做最终判断 —— 误判只影响"多问一次"，不会造成"漏问写操作"。

### 4.3 数据模型改造

`hil_confirmations` 新增 8 列（`database/schema.py` + `migrations/columns.py`）：

| 列 | 类型 | 用途 | 缺了会怎样 |
|---|---|---|---|
| `tool_type` | TEXT | `local` / `mcp` / `http` | **批准后不知道该走哪个执行器**（现状只支持 http） |
| `tool_call_id` | TEXT | 对齐前端 SSE 节点 | 前端无法把确认卡挂到对应工具节点上 |
| `level` | TEXT | `confirm` / `approve` | 无法区分普通确认与高危审批 |
| `batch_id` | TEXT | 同批次合并键 | 无法合并 ⇒ 每步都问人 |
| `batch_count` | INT | 批次内操作数 | 用户不知道要批多少条 |
| `timeout_at` | TEXT | 超时时刻 | 超时不可控 |
| `result_json` | TEXT | 执行回执 | **无法区分"批了但没跑"与"跑成了"** |
| `exec_idem_key` | TEXT | 执行幂等键 | 用户点两下 ⇒ 执行两次 ⇒ 重复包 |

`payload` 列**已有完整未截断参数快照**（`hil_service.py:131`）⇒ 批准后按原参数执行即可，
**不需要新的参数存储**。这是本方案能低成本落地的关键。

### 4.4 批次合并（效率保护 —— 没有这条，方案不可用）

**问题**：实测一次建包请求 = 19 次工具调用。若每次都要人点，HITL 直接崩掉。

**规则**：同一 ReAct 批次内，`(conversation_id, agent_id, tool_family, run_id)` 相同且未终结的
写操作**合并进同一个确认单**；一次批准覆盖整批。

- `tool_family`：动词族（`create` / `update` / `delete` …），同族才合并
- 合并触发点：第 2 笔同类写操作出现时，把第 1 笔挂起
- 卡片展示：`batch_count` + 受影响对象清单摘要
- **边界**：跨 `run_id` 不合并（不同建模阶段的语义不同）；`approve` 级**不合并**（每条都要单独看）

### 4.5 API 契约

| 方法 | 路径 | 改动 |
|---|---|---|
| GET | `/api/studio/hil-confirmations` | 现有，不改 |
| GET | `/api/studio/hil-confirmations/{cid}` | **新增**：单条详情（含完整参数） |
| POST | `/api/studio/hil-confirmations/{cid}/decide` | **扩展 body**：`{approve, note, expected_version}` |
| POST | `/api/conversations/{id}/hil-resume` | **新增**：决定后触发回灌 |

**`expected_version` 乐观锁**（重要）：确认单生成后、用户批准前，平台上的版本可能已被改动
（versionId 变了 / 父容器被删）。批准时必须比对 payload 里的坐标与平台当前状态，
不一致 ⇒ **拒绝执行并要求模型重新定位**，避免"批了但写到错的地方"。

### 4.6 SSE 事件协议

新增事件类型 `hil_confirm`（**不再靠正则从工具结果文本抠确认单号**）：

```json
{
  "type": "hil_confirm",
  "confirmation_id": 42,
  "tool": "create_model_elements",
  "tool_type": "mcp",
  "level": "confirm",
  "title": "确认新增模型元素",
  "impact": "在「通信子系统用例图」下创建 1 个包（通信子系统测试）",
  "arguments": { "...": "完整参数" },
  "batch_count": 12,
  "conversation_id": 9696,
  "can_approve": true,
  "expires_at": "2026-10-28 06:00:00"
}
```

**兼容性**：`handleSSE`（`11-pipeline.js:1228`）是纯 `if/else if` 链且**末尾无 else 兜底**
⇒ 老前端静默忽略新事件，行为与从前完全一致。
既有先例：`redraw_confirm`（`:1276`）与 `clarify_ask`（`:1347`）都是后加事件类型。

**双写保险**：工具结果文本里**仍保留**"确认单 #N"字样 ⇒ 老前端仍能出卡（兼容期做法）。

### 4.7 前端确认卡

复用 `procAddConfirmGate`（`11-pipeline.js:560`）+ `hilInlineDecide`（`:580`），但改两处：

1. **数据源**：从正则抠号改为直接读事件字段 `ev.confirmation_id`
2. **展示影响面而非裸参数**：卡片头部显示「目标容器路径 + 操作对象 + 影响数量」，
   参数 JSON 折叠在「查看参数」里。**只给 JSON 让人批 = 没让人批**（人看不懂就不会认真看）

### 4.8 批准后执行与回灌（最难、也最关键）

**现状问题**：批准 → 带外 `exec_http_tool` → LLM 收不到回执 ⇒ 模型会重发或宣称未执行（E8 同族）。

**目标三步**：

**Step 1 · 统一执行器**
decide 端点批准后调用**与工具执行同一份代码**：
```python
pipe._exec_tool_call(action, payload)   # ← 复用 stream 侧的执行路径
```
⚠️ **必须开旁路**：`_exec_tool_call` 内部会再进 HITL 闸 ⇒ 需一个
`_hil_authorized_conf_id` 标志，命中该确认单 id 时**不再二次入队**（否则无限循环）。
（MCP 工具走 `tools.py:1115`，HTTP 走 `:1141`，local 走 `:1166+` —— 全部自动覆盖。）

**Step 2 · 回写回执**
`result_json` ← `{"ok": true, "result": {...}, "executed_at": "..."}`；`status` → `executed`。

**Step 3 · 回灌 LLM**
向会话注入一条消息并发起**新一轮** stream，复用 `ask_user` 的 `resume_text` 范式
（`routers/conversations.py:695`）：

```
【人工确认结果】你请求的写操作「create_model_elements」已获用户批准并执行。
执行回执：{"status":"SUCCEEDED","dataId":"2115079578924417024"}
请据此继续，**不要重复发起该操作**。

原请求：在通信子系统用例图包下新建一个名为 E2E验证包 的子包
```

拒绝时：
```
【人工确认结果】用户**拒绝**了写操作「create_model_elements」。
原因：包名已存在
请不要重试该操作，直接向用户说明。
```

> ⚠️ **必须带「原请求」复述**：因为 `messages` 表**不存 tool_calls / tool_result**
> ⇒ ReAct 状态是纯内存 ⇒ 恢复必然是"重新起一轮"，不是"恢复同一个状态机"。
> `ask_user` 范式里已经这么做了（`conversations.py:695` 拼了 `原请求：...`）—— 沿用。

### 4.9 幂等与并发

| 层 | 现状 | 处置 |
|---|---|---|
| **入队幂等** | ✅ 已有 `idem_key` + 24h 窗口（`hil_service.py:92-99`） | 直接用 |
| **执行幂等** | ❌ **无** | **新增 `exec_idem_key = sha1(conf_id + payload)`**；执行前查 `result_json` 非空 ⇒ 直接返回缓存结果 |
| **并发批准** | ❌ 两个请求同时 decide | 决定端点加 `UPDATE ... WHERE status='pending'` 的条件更新，靠 `rowcount` 判定谁抢到 |

> 执行幂等不是可选项：用户点两下"批准"就会执行两次写操作 —— **这正是上一轮实测「重复包」风险的具体形态**。

### 4.10 权限

- decide 端点已有 `require_permission("hil", "approve")`（`flows.py:338`，权限门在 `:335` 的装饰器上）—— 保留
- `approve` 级（破坏性）建议再加一道独立权限位（如 `hil:approve_destructive`）
- `decided_by` 取**已认证用户身份**（现有实现已改）—— 保留，不要退回 body 自报

### 4.11 超时与降级

- `timeout_at` 默认 24h（沿用 `IDEM_WINDOW_HOURS` 口径）
- 超时 → `status=expired` + 回灌 LLM「用户未响应，未执行」
- `fallback_level`（策略表已有字段）默认 `confirm` ⇒ **不降级为 auto**（超时 ≠ 默许）

## 六、灰度与验证

### 6.1 灰度顺序（三档，逐档放开）

| 档 | 范围 | 观察指标 | 回滚 |
|---|---|---|---|
| 1 | `notify` —— 只留痕不拦 | 写操作量、参数完整性、是否误判为写 | 关策略即可 |
| 2 | `confirm` —— 挡 create/update | 建包类请求的人工点击次数、是否成批 | 降级回 notify |
| 3 | `approve` —— 挡 delete/import/apply | 高危操作拦截率、误拦率 | 降级回 confirm |

### 6.2 真机 E2E 判据（复用 `tmp/e2e_zhiyuan.py` 增加 HITL 用例）

| # | 判据 | 为什么重要 |
|---|---|---|
| H1 | 确认单生成后，**平台独立回读证实写操作尚未发生** | 证明"拦住了"而不只是"问了" |
| H2 | 批准后**只执行一次**（平台回读元素数 +1，不是 +2） | 验证执行幂等 |
| H3 | LLM 最终答复与平台事实**一致**（不再"尚未写入"，也不再谎称已建） | 与 E8 的修法同源，回归验证 |
| H4 | 拒绝后 LLM **不重试**该操作 | 验证回灌文本生效 |
| H5 | 批次场景：N 个同类写只弹 **1** 张卡 | 验证效率保护 |

### 6.3 专项门禁建议（`tools/verify/verify_hil_write_gate.py`）

- 断言：stream 路径 `_hil_level` 有赋值（AST 判，别按行号）
- 断言：统一闸位置在 RBAC 之后、Hook 之前（行号比较）
- 断言：`classify_write` 对 MCP 写工具**不漏**（用真实 71 工具目录跑）
- 断言：`hil_confirmations.status` 含 `executed`
- 断言：无 `exec_idem_key` ⇒ 拒绝执行（幂等是硬要求）
- **变异自证**：移除统一闸 ⇒ 上述判据必须翻红

## 七、风险与代价（诚实登记）

| 风险 | 后果 | 缓解 |
|---|---|---|
| **每步都问 ⇒ 效率崩** | 一次建包 19 次点击，不可用 | 批次合并 + 分级（只问最终生效且不可逆的） |
| **确认期间参数过期** | 批准后写到错误的 version / 已删的父容器 | `expected_version` 乐观锁，不一致则要求重新定位 |
| **用户重复点批准** | 重复创建（实测平台已有 3 个测试包就是这类残留） | `exec_idem_key` 执行幂等 |
| **回灌是新一轮而非恢复状态机** | 模型丢上下文 / 重发同一操作 | `resume_text` 带原请求复述 + 明确"不要重复发起" |
| **老前端不认新事件** | 确认卡不显示 | 双写：工具结果文本仍带"确认单 #N" |
| **闸门位置太靠后** | UI 先亮"调用中…"再被拦 | 可接受（现状 HIL 也是这个行为）；若要"先拦后亮"需前移到 `stream.py:4724` 并在 2 个调用点重复实现 |
| **策略表接线后行为突变** | 9 条种子一启用就可能拦住大量既有流程 | 按 §6.1 三档灰度 |

## 八、决策点（待米爸拍板）

| # | 决策 | 我的建议 | 理由 |
|---|---|---|---|
| **D-1** | 执行侧是否对 **create/update 也要求确认**？（注入侧只挡 5 族） | **要**，但**必须配批次合并** | 智源平台的写操作是**外部真实平台**，误写代价高；且不确认则"人在回路"名存实亡 |
| **D-2** | 批准后是否**自动回灌并让模型续跑**？ | **要**，与 E8 的 `write_ops_digest` 共用同一通道 | 否则模型永远不知道结果，会重发或谎报 —— 这正是 E8 的根因 |
| **D-3** | 灰度顺序 | **notify → confirm(create/update) → approve(delete/import)** | 先只留痕观察，确认误判率后再收紧 |
| **D-4** | 智源 MCP 写操作是否**单独一档**（比本地写更严）？ | **建议单独一档**（智源全部 confirm 起，delete/import 到 approve） | 外部平台写入不可回滚，本地写大多可 undo |
| **D-5** | 是否**现在就实施**？ | **先只做 P0 骨架 + notify 档** | 成本低、可回滚；等 observe 数据再开 confirm |
