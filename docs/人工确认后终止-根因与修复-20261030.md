# 人工确认后「无辜终止」根因与修复（2026-10-30）

> 现象：最近两次会话，**每次经过人工确认（HIL / clarify）就终止**；刷新后只剩一段
> 「⏸ 暂停等你确认…本轮已完成 23 次工具调用」的旧消息。用户原话：「无辜终止」。

---

## 1. 现场（真库，不是推测）

| 证据 | 内容 |
|---|---|
| `orch_checkpoints` id=41 | run=564 / conv=9779 / phase=`planned`，13:27:36 创建，updated 13:29:51 —— **从未走到完成** |
| `tool_call_logs` 13:27:46–13:30:36 | 子任务全部以 **`conversation_id=0` / `run_id=0`** 落库（`工程建模方案设计Agent`、`智源对接agent`）|
| `tool_call_logs` id=6225 / 6241 | `todo_write` → **「todo_write 无会话上下文，无法建待办」** |
| `tool_call_logs` id=6238 / 6254 | `tool_result_fetch` → **「offload #2608 不存在」**（而 #2608 **确实存在**、内容 8177 字）|
| 模型自述（msg 5316）| 「本轮所有读接口回执均为**「前序工具结果已省略」**——即没有拿到任何一个可核验的元素明细」「连续失败轮达到 **3 / 3** 的上限，被强制收尾」|
| 全库 conv=0 留痕 | **1478 条**（从 2026-09-11 起持续累积）|

`max_failed_rounds` 默认 3 ⇒ 连续 3 个失败轮就强制收尾。用户看到的"终止"就是这个。

---

## 2. 根因（三条，全部是"为省 token 把可寻址性一起省掉"）

### 根因 A（直接原因）：跨轮省略把工具结果**连 offload 编号一起抹掉**

`stream.py` 每轮结束前把上一轮所有 tool 消息替换为：

```python
{"ok": True, "result": "", "note": "前序工具结果已省略——其结论已体现在后续推理中"}
```

后果（从第 3 轮起全部成立）：

1. **明细没了** —— 模型看不到任何元素、坐标、回执内容（它是靠上一轮读的数据在做下一步判断）；
2. **编号也没了** —— `tool_result_fetch` 是"按编号重读全文"的唯一通道，
   而编号原本写在引用块里（`[工具结果已 offload #2608 …]`），抹空即失联；
3. **只能猜** —— 实测 id=6238 猜的是 `#2608`，而 #2608 是**下一笔**调用的编号（差一位）；
4. **猜错算失败轮** —— 撞 3 次上限 ⇒ 强制收尾 ⇒ 用户看到「无辜终止」。

这不是"省略策略偏激进"，而是**把 offload 模块的价值抵销掉了**：
offload 的整个设计前提是"引用块 + 按 id 重读"（`tool_offload.py` 文件头），
抹掉编号等于把它降级成纯丢弃。

另外 `tool_result_fetch` 的错误文案也在**误导**：

```python
result = {"ok": True, "result": _off[:20000]} if _off else {"ok": False, "result": "不存在"}
```

`if _off` 把「行不存在」与「行存在但内容为空」合并 ⇒ 模型判定"编号被删了"，改为乱试。

### 根因 B：编排子任务以 `conversation_id=0` 运行 ⇒ 会话级工具必然失败

子任务按约定用 `execute_stream(query, 0, …)`（0 = 不落 messages），
但 `_tool_conv_ctx`（会话级能力的归属）**也取自这个参数** ⇒ 子任务里：

- `todo_write` 直接报「无会话上下文」（它是无条件注入的工具，模型第一步就会调）；
- `tool_call_logs.conversation_id=0` ⇒ 用户在「执行过程」里看不到子任务的工具；
- 技能反馈（`_record_skill_feedback`）同样落到 0；
- HIL 确认单 / 写入闸也挂错会话。

这些失败**又计入失败轮** ⇒ 与根因 A 叠加，3 次上限几乎必到。

### 根因 C：一条**早就红着**的门禁被忽略了

`verify_token_budget.py` 断言 `_TOOL_RESULT_CAP==6000 / _TOOL_MODEL_CAP==3000 /
_ATT_INJECT_CAP==4000`，而 37780d3「截断清单 P0/P1/P2 全量落地」已把三者统一提到 8000。
⇒ 这条门禁**自 37780d3 起一直红在 CI 里**。红了太久的门禁等于没有门禁 ——
它本来最该在"省略策略被改动"时发出声音。

## 3. 修法

### A. 省略改为「保留窗口 + 可寻址摘要」

`stream.py`：

- 新增 `_KEEP_TOOL_ROUNDS`（配置 `agent.tool_result_keep_rounds`，默认 **1**）：
  **最近 N 轮的原文原样保留**（多步核对天然要回看上一轮）；
- 窗口外仍省略，但省略件里**保留**：工具名、轮次、头部 400 字、**offload 编号**与重读指引：
  ```json
  {"ok": true, "result": "", "head": "...400字...", "offload_id": 2608,
   "note": "前序工具结果已省略（工具 get_model_elements，第 2 轮）；**全文可直接重读**：tool_result_fetch(id=2608)"}
  ```
  没 offload 时如实说"该结果未 offload，如需请重新调用 X"，而不是留空让模型猜；
- 省略按**轮次**而不是按条数：一轮里的证据是整体，切一半反而更难推理。

省 token 的性质没丢：3 轮场景实测回填体积 9078 → 3026 字（**省 67%**）。

### B. `tool_result_fetch` 回执分三态

新增 `tool_offload.offload_exists()`：
- 取到内容 → 正常返回；
- 行在但内容空 → 「存在但内容为空，请勿改用其他编号猜测」；
- 行不存在 → 「编号只能从结果提示原文读取，**不要按顺序猜**，查不到就重新调用该工具」。

### C. 子任务会话归属与消息落库解耦

`execute_stream(..., session_conv_id: int = 0)`：

- `conversation_id` 管**消息落库**（子任务仍传 0，语义逐字节不变）；
- `session_conv_id` 管**会话级能力归属**（子任务传父会话 id）；
- 缺省 0 ⇒ 回落 `conversation_id`，非编排路径行为不变；
- 编排两处子任务调用点已传 `session_conv_id=conversation_id`；
- 统一成函数内 `_sess_conv` 一次定值，工具留痕 / 技能反馈 / HIL / 写入闸一律引用它
  （第一版只改了 `_tool_conv_ctx`，技能反馈仍用 `int(conversation_id or 0)`
  ⇒ 实测还有 2 行落到 conv=0，被新门禁 B1 抓出）。

### D. 把过期门禁改成不变量

`verify_token_budget.py` 不再断言快照数字，而断言**不变量**：
展示上限 ≥4000、回填上限 ≤ 展示上限、注入上限 ≤8000；
`(a)` 的"砍掉 ≥80%"改为"截断后长度 == cap 且 cap < 原文"。39/39 通过。

## 5. 诚实说明

1. **我没有复现那条"23 次工具调用 + 人工确认"的完整链路**（需要真实平台 + LLM 跑十几分钟）。
   我复现并证明了每一个**失效环节**（省略抹空、编号失联、子任务无会话、猜编号），
   根因链条完整且与库里证据逐条对应；但"修完就一定不再终止"这句话只能由你下一次真实使用来确认。
2. `max_failed_rounds=3` 本身没改：它是必要的失控防线。这次修的是**为什么会出现连续 3 个
   失败轮**（拿不到证据 ⇒ 只能重试/猜）。如果之后仍撞到，`stop_reason=failed_rounds`
   会在 done 事件里如实给出，届时可据此继续收窄。
3. 省略窗口默认 1 轮，可在「设置 → 配置」调 `agent.tool_result_keep_rounds`；
   设为 0 即回到旧行为（保留回退路径）。

## 6. 遗留

- 老数据：`tool_call_logs` 里 1478 条 conv=0 是历史累积，**未回填**（无法可靠推断父会话，
  强填会造假数据）。它们只影响历史统计，不影响现在。
- 若后续要更省 token，可把"保留 1 轮"改为"保留到某个字符预算"（按 token 而非轮次），
  但这属于调优，不是缺陷。
