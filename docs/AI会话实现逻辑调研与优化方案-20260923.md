## 0. 结论摘要

1. **系统真正的意图路由是好的，问题出在"入口默认值把它短路了"。**
   后端三层路由（规则快筛 → 语义 → LLM 精排）+ 意图缓存 + DST 继承 + 置信度三档，设计完整；
   但会话入口的「智能体」下拉**默认选中列表第一个 Agent**（= 需求分析Agent，`/api/studio/agents` 按 id 升序），
   把下拉值当 `forced_intent` 发给后端，而 `intent = forced_intent or _detected` 是**恒覆盖**语义
   → 用户"问什么都以需求分析Agent作答"。这不是写死的逻辑，也不是 Agent 团队配置问题，
   是**前端默认值 + 后端"显式定向优先"策略**叠加出的定性缺陷。

2. **同一根因还免费送了一个次生灾害**：`_needs_orchestration()` 里 `if forced_intent: return False`
   （这是**刻意的设计**：指定了 Agent 就别自动编排）。于是"默认定向"把**自动编排也一起关掉了** ——
   这是"AI 建模看起来只会做需求分析、从不走多 Agent 编排"的完整解释。

3. **「都会查询知识库」是两件事拼出来的错觉**：
   ① 单 Agent 侧检索是**配置驱动**（`agent_def.kb_required`；需求分析Agent=0 不检索，design/impact/knowledge_qa/chat=1 必检索）；
   ② 编排侧有一条**写死的** `{"stage","知识库检索","done","retrieved":False}` 阶段事件，无条件推送 →
   UI 上恒定出现"知识库检索"环节。前者正常，后者已按"不发假状态"处置。

4. **需求分析卡（0 条候选条目 / ✓无冲突 / 暂无候选条目 / 查看完整报告）本身有设计用途，但数据源恒空。**
   它是 FR-MG-2 / FR-HIL-1 的"候选需求逐条确认"入口，数据来自
   `entities(entity_type='需求', status='candidate', branch=当前分支)` + `relations(CONFLICTS, status='candidate')`。
   **实测全库该查询恒 0 行**（口径见 §2.2）→ 卡片永远是空态。已按「空态不渲染」处置：
   能力保留，候选需求生产链路跑通后自动恢复。

5. **对标结论（一句话）**：行业标杆的共识是「**默认自动路由 + 显式指定可覆盖但必须可见可撤销 + 产物与对话分离 + 高风险动作人工确认**」。
   本工程缺的正是前两条的"可见/可撤销"与第三条的"产物独立面板"。

6. **多轮上下文的断链不在"历史注入"，而在"产物没有通道"**（2026-09-30 取证，§6）。
   历史注入（v2 话题感知）本身设计完整、且实测**在真实生效**（长会话折算 token 后确实超 2000 tok 预算，
   靠"当前话题原文 + 语义拉回 + 分话题摘要"降维）；真正缺的是**产物（`sysml_versions` / `artifacts`）
   只有写、没有读回** —— 全仓读它们的生产代码只有 `agent/utils.py`，且全在归档写入路径。
   于是「第 2 轮把第 1 轮建好的模型当成不存在」。已按四个落点补上只读的**会话产物摘要**通道
   （§6.4），验收 53 项断言 0 FAIL（§6.5）。**同时仍有执行层的独立故障**：t1 超时
   （241s > `delegation.worker_timeout_s=120`）使后继子任务全 `blocked`，需单独处理（§6.6-1）。

## 1. 现状调研：AI 会话是怎么跑起来的

### 1.1 请求契约（前端 → 后端）

`static/js/mods/12-chatsend.js::sendChat()` → `POST /api/conversations/{id}/chat/stream`：

| 字段 | 来源 | 语义 |
|---|---|---|
| `message` | 输入框（含 `@` 会话文件 / `#` 知识库引用折叠成文本块） | 用户输入 |
| `attachments` | 待发附件 | 附件优先作依据 |
| `scope_ids` | 建模范围多选（全局） | **硬锁**检索文档范围 |
| `branch` | `getCurrentBranch()` | 输出侧工作分支（默认 `dev`；`release` 只读） |
| **`forced_intent`** | **`#quick-agent` 下拉值** | **显式定向 Agent**（本次缺陷的入口） |
| `skill_name` | `#quick-skill` 下拉值 | 指定技能（独占式工具白名单） |
| `team` | `#quick-team` 下拉值 | 团队模式：主 Agent 强制编排 |
| `provider_id` | 模型下拉 | 指定 LLM |

后端 `routers/conversations.py::chat_stream` → `agent/pipeline_parts/stream.py::execute_stream`。

### 1.2 意图识别：三层 + 缓存 + DST（`agent/intent.py`）

```
detect(text, conn, prev_intent)
 ├ ① 意图缓存 L1（query_hash + index_fp 双键，命中直返，跳过全链路）
 ├ ② 建模强信号（正则）：(生成|给出|输出|编写|创建).{0,24}(sysml|建模|视图|代码) → design 0.95   [:175]
 ├ ③ Glossary 术语归一化强制路由（CIA 强信号让路）                          [:179]
 ├ ④ 报告命令优先 → report_generation 0.95                               [:196]
 ├ ⑤ 变更影响强信号 → impact 0.95                                        [:201]
 ├ ⑥ 需求质量（高特异词才触发）→ requirement_quality                       [:204]
 ├ ⑦ DB 规则表 intent_rules（**实测 0 行**）→ ⑧ DB Agent 关键词 → ⑨ 内置关键词
 ├ ⑩ 语义兜底（VectorEngine 余弦，≥0.70 = semantic，否则 semantic_weak → 会话继承）
 └ ⑪ LLM 兜底（<0.85 且有 prev_intent → 继承）→ ⑫ 无信号 → 继承 → chat
```

- **置信度三档**：`_done()` 里 `needs_clarify = route ∈ {semantic_weak, inherit} or (llm 且 conf<0.85)` → 前端澄清条（可点选改选重发）。
- **会话级 DST**：`_load_conversation_dst()` 读会话当前意图做 `prev_intent`（追问/续写不被误判）。
- **缓存毒化防线**：只对 `requirement_quality`（[:157]）与 `impact`（[:164]）做了"缓存命中也必须过强信号词校验"；
  **`design` / `requirement_analysis` 没有这道防线** —— 见 §2.5。

### 1.3 三条执行路径（决定"输出什么样"）

| 路径 | 触发条件 | 落库卡片指纹（判路径的硬判据） |
|---|---|---|
| **单 Agent 直行** | 默认；或 `forced_intent` 非空（强制不走编排） | 含 `citations` / `submitted_by`，**无** `orchestrated` |
| **自动编排** | `not forced_intent` 且 `_needs_orchestration()` 为真（多步规则信号 / LLM 判复杂） | 含 `orchestrated`/`plan`/`orchestrated_status`/`run_budget` |
| **团队强制编排** | `team` 非空且解析到 `agent_role='main'` 的启用 Agent | 同编排 + `team=<主Agent意图名>` |

`_needs_orchestration()` 的判据（`orchestration.py:154`）：
`forced_intent` 非空 → **直接 False**；意图不在 6 类内 → False；多步正则（先…再…/然后…）或"两域关键词+连词" → True；
短噪声(<6 字) → False；带附件 → False；仅 `requirement_analysis`/`design` 才继续走 LLM 复杂度判定。

> ⚠️ `_stream_orchestrated_flow` 计划失败时的**降级直行把意图硬编码成 `requirement_analysis`**（`stream.py:108`）。
> 这是一个"降级也走需求分析"的死角：计划解析失败时，无论原意图是什么，都会以需求分析Agent 兜底作答。

### 2.1 默认定向覆盖（已修）

**证据链（四段互相独立）**：

### 3.2 五条可迁移结论

1. **"自动路由"必须是默认值，"显式指定"必须是**用户主动动作**。**
   标杆产品里没有任何一个把"某个具体 Worker"设为默认选中项；默认永远是 auto。
   → 对应本工程 §2.1（已修）。
2. **显式覆盖必须可见、可撤销、可解释。**
   本工程已有雏形（`stream.py:878` 会在 reasoning 里说"已按显式选择执行 X；语义识别为 Y"），
   但**只在流式思考里一闪而过**；而且默认值造成的"隐式定向"根本没触发这条提示。
   → 建议：`card_data` 增加 `intent_override:{forced, detected}`，在**消息落款行**常驻显示可点击撤销（§4）。
3. **产物与对话分离**（Claude Artifacts / ChatGPT Canvas / Perplexity 报告页）。
   本工程已具备原料（`sysml_versions` 版本链、`reports` 表、`artifacts` 产物库）与视图面板，
   但"AI 建模产物"仍主要躺在消息流里 → 建议把 SysML 代码/视图升级为**可独立版本化、可回滚、可 diff** 的右侧面板（§4）。
4. **高风险动作人工确认是产品点，不是摩擦。**
   Claude Code 的逐命令 allowlist 在敏感工程语境是**特性**。MBSE 语境对应的"高风险动作"=
   写图谱 / 发布分支 / 改本体 / 覆盖模型版本 —— 本工程 `_orch` 子任务已有"写操作受控上下文"的雏形，
   建议显式化为**统一确认闸**（§4）。
5. **可配置的生命周期钩子**（hooks + Skills）是"可运营"的关键。

### 8.2 超时判据修订（问题 ① 的根因不是配置，而是**判据本身**）

**先纠正一条早前的误归因**：`delegation.worker_timeout_s=120` **不是**流式编排的真凶 ——
它只在**非流式 planner 的并行分支**（`workflows/planner.py:309`）使用。流式路径的真凶是
`agent/pipeline_parts/skills.py:195` 的**硬编码类属性** `_ORCH_SUBTASK_TIMEOUT = 120`
（配 `_ORCH_MAX_RETRIES = 1` → 2 次尝试 ≈ 240s，正好对上实测的 241s）。

**更关键的是判据语义错了**：原判据是**固定 wall-clock**，而 t1 当时**一直在产出**。
按"是否还在产出"判才符合直觉 —— 真卡死应快速失败，活跃生成不该被误杀。

修法（`stream.py`）：新增 `_hb = {task_key: 最近产出时刻}` **活性心跳表**，任何产出

**"停滞为主 + 硬上限兜底"**：

- 无产出 > `subtask_idle_timeout_s`（默认 **150**）→ 判 `timeout（N 秒无产出）`，**快速失败**；
- 总时长 > `subtask_timeout_s`（默认 **300**）→ 兜底 `timeout（超过 N 秒硬上限）`
  （防"持续滴 token 永不结束"）；

`accuracy` 恒为 `0.9545` / 2 错例，差异只在**错的是哪两条**（accuracy 相同而 `macro_f1` 不同
⇒ 错例集合必然不同）。已排除意图缓存干扰：`eval_intent_routing.py:82` **每次评测前
`DELETE FROM intent_cache`**（实测该表 0 行）。故**判据是「与本批对照基线一致」，不是「与某个绝对值一致」**：
P0-7 与 P1-4 两次回归都是 `0.9691` ⇒ 零回归；**若拿隔离单跑的 0.9652 去比，会把它误判成漂移**。

### 8.8 实跑中发现并一并修复：质量评审被 `max_tokens` 截断 → 误报「解析失败」0/100

**现象**：实跑里 `reflection = {score: 0, passed: false, issues: ["解析失败"]}` →
`quality_gate_gaps = ["质量评审未通过（0/100）：解析失败"]` → `orchestrated_status` 被
**降级为 `partial`**。即**一个解析 bug 把"质量正常"报成了"门禁未通过"**
（与 §8.4 的"话说得不准"同族，方向相反）。

**根因**：`workflows/nodes.py` 的 `_evaluate_content` 原用 `max_tokens=1024`，
而当前 provider 是**思考模型**（`deepseek-v4-flash`，回包含 `reasoning_content`）——
**推理与正文共享同一个上限**。大输入（`refine.eval_in_chars=24000`）下 `reasoning_tokens`
吃掉大部分额度 → JSON 被 `finish_reason="length"` 从中间截断、**闭合 `}` 丢失** →
正则 `\{[\s\S]*\}` 匹配不到 → 走硬编码兜底判 0 分「解析失败」。

**决定性复现**（`tmp/mt_ctx/probe_eval_parse_big.py`，输入 ~24000 字符）：

| max_tokens | finish_reason | reasoning_tokens / completion | content 有闭合 `}` | 生产判据 |
|---|---|---|---|---|
| **1024**（改前口径） | **length** | 789 / 1024 | ❌ | **「解析失败」0/100** |
| 4096 | stop | 941 / 1233 | ✅ | 正常评分 |
| 8192 | stop | 502 / 814 | ✅ | 正常评分 |

**修法（三处，缺一不可）**：

1. **上限配置化且给足**：新增 `refine.eval_max_tokens`（默认 **3072**；标定依据 =
   实测 reasoning 峰值 941 + 正文 JSON ≈ 350 ≈ 1300，取 3072 留 >2x 余量）。
2. **解析改「完整优先、截断兜底」**：新增 `_parse_eval_json` —— 先试完整 JSON；
   失败则按字段**宽松抽取** `"score"` / `"passed"`（**抽到即认、抽不到返回 `{}`、绝不臆造分数**），
   并在 `issues` 里**如实标注"被截断"**（不静默）。
3. **成因不混**：`score` 未取到时按三种情形分开报 ——
   空内容 → 「评审无输出（max_tokens 可能被 reasoning 占满）」／
   `finish_reason=='length'` → 「解析失败（输出被 max_tokens 截断，未见 score 字段）」／
   其余 → 「解析失败」；并把 `finish_reason` 挂进 `_meta` 便于现场判读。

**回归断言**：`verify_orch_reliability.py` 新增 **[J] 组 12 条**（`J1~J10`，含端到端桩驱动）
+ **M4 变异自证**（把宽松抽取退回"只认完整 JSON" → J2 与 J5 必须翻，
且 M4b **复用 J5 的同一条判据函数** `_j5_ok`，不另写近似判据）。

### 9.2 三层根因（同一现象的三个独立成因）

**L3（上游，主源）—— 澄清续答文本「整段」进 `task_decompose`。**
`routers/conversations.py` 构造的续答文本形如：

```

```

只有 `原请求：` 之后是用户本意，但 `task_decompose(user_input, intent)` 拿的是**整段**
（`prompt.py:16`）→ 把「问题「…」/回答：…」的**元对话壳**当任务描述拆解。
实测 conv=514 的落库原文里这段 132~133 字符文本**出现了 3 次**（id 3002/3010/3012），
产出的 constraints 中 7~8 条来自它。

**L1（实现）—— 去重按精确字符串。** 三轮拆解表述各异（LLM 非确定性），
`SysML v2 模型` / `SysML v2模型` 因一个空格绕过去重。

**L2（设计，登记项本体）—— 纯并集、无上限、无清空。** entities/constraints 单调增长、
永不衰减；跨话题也一路累积。

### 9.3 修法

| 层 | 落点 | 做法 |
|---|---|---|
| **L3** | `common.py::extract_original_request` → `prompt.py::task_decompose` 首行 | 抽取 `原请求：` 之后内容（**取最后一次出现**防嵌套；抽空则回退原文，绝不把输入清空） |
| **L1** | `common.py::norm_slot_item` / `merge_slot_items` | 判重前归一化（全角→半角、只留字母数字汉字）→ `SysML v2 模型` 与 `SysML v2模型` 同键；子串包含合并（`先理解用户意图` ⊂ `需先理解用户意图`，留信息更全者） |

### 9.4 L2 清空判据：为什么**不能**直接复用 `_tag_topics`

初版设计是复用既有话题判据（`messages.topic` + `_tag_topics` + `context.topic_sim_threshold=0.15`），
**实测两次推翻**（"读代码推断不如 A/B 实测"的又一例）：

1. **`shared` 条件恒假**：`_tag_topics` 的段代表向量是**全段 user+assistant 累加**且随对话无限增长
   —— conv=514 达 **7879 个 bigram**，于是「无共同 bigram」对任何输入都成立
   （异话题句也命中 `分析`/`报告`/`项目` 等泛词）→ 判据永不触发。
   佐证：conv=514 全程只被分成 **1 个**话题段。
2. **阈值 0.15 不适用**：它是在**大词袋**下标定的；同话题句被稀释到 0.09~0.19，
   实测**误切 4/7**（会把追问轮的对象清掉）。

**改判据**（`tmp/mt_ctx/calib2_variants.py`，四种构造对比，conv=514 真实段 + 8 同话题 / 8 异话题）：

| 构造 | 同话题区间 | 异话题区间 | 间隙比 | 词袋 |
|---|---|---|---|---|
| A 全段累加（`_tag_topics` 现状） | [0.0922, 0.1889] | [0.0000, 0.0475] | 1.94× | 7879 |
| B 段内最近 6 条 | [0.0919, 0.2214] | [0.0000, 0.0249] | 3.69× | 3603 |
| **C 段内 user 消息累加（采用）** | **[0.1342, 0.4813]** | **[0.0000, 0.0350]** | **3.83×** | **310** |
| D 与段内单条 max | [0.1684, 1.0000] | [0.0000, 0.0806] | 2.09× | — |

取 C + 新键 `slots.topic_switch_threshold=0.08`（落在分离带内）→ **8/8 同话题不切、8/8 异话题切**。
**只累加 user 消息**的理由：话题由用户说的话定义；assistant 的长篇产出把词袋从 ~300 撑到 ~8000，
既稀释相似度又让 `shared` 恒真。

判据抽成纯函数 `common.py::is_topic_switch(..., use_shared=True)`：
`_tag_topics` 走默认（`use_shared=True`，**与原实现逐字等价、零回归**），
`_is_topic_switch` 走 `use_shared=False`（词袋小时 `shared` 只带来漏切风险）。

**另一处必须修的接线细节**：`_is_topic_switch` 初版取「最后一条消息的 topic」，
而 `_tag_topics` 是**惰性全量重算**、与落库之间存在窗口 —— 实测 conv=514 最后 4 条
（3010~3013，正是最近一轮）topic 为空 → 判据在这些会话上**恒为 False**、L2 形同未接。
改为「取**最后一条已打标**消息的 topic，其后的未打标消息并入该段」。

## 10. 会话产物摘要：引导语压缩 + 零信息量事实过滤（P1-7，2026-10-01）

### 10.2 两个独立根因（实测分离，不是同一问题的两种说法）

| # | 根因 | 坐标 | 判据 |
|---|---|---|---|
| ① | 引导语**固定长度**，不随事实量收缩 | `agent/session_artifacts.py:_LEAD`（原 126 字符） | 压缩到 54 字符 ⇒ `≥60%` 归零 |

## 11. 历史「输入/输出」都按相关性进上下文（P1-8，2026-10-01）

### 11.1 触发

需求原文：

> 多轮对话中上下文不仅仅基于产物文档，之前的输入，输出内容都应该基于相关性评估是否放进下一轮对话的上下文中。

即：历史**消息**（用户输入 + 助手输出）不能只靠"最近 N 条"进上下文，**每一条都要过相关性评估**；
而 P1-7 刚打通的产物摘要只是第四条通道，不构成替代。

### 11.2 改动前的四通道与预算（`agent/pipeline_parts/history.py::_load_history`）

| 通道 | 内容 | 预算 | 是否评估相关性 |
|---|---|---|---|
| ① 近因窗口原文 | 当前话题最近 `topic_current_max_msgs`(=8) 条 | `raw_cap = 50%` = 1000 tok | **否** |
| ② 相关性拉回 | 与当前输入语义相近的片段（top-`topic_retrieve_topk`=6） | 累进到 `pull_cap = 75%` = 1500 tok | 是 |
| ③ 其他话题摘要 | 分话题独立 LLM 摘要 | 剩余 | 否（按话题切分） |
| ④ 会话产物摘要 | P1-7 新增 | 剩余 | 否（按事实列举） |

`budget_history_tokens` 默认 **2000**。输出顺序 `_digest + sum_blocks + pull_blocks + raw_list`。

**关键点：① 是"近因"不是"相关"** —— 长会话里"更早但更相关"的输入/输出**唯一的**进入机会就是 ②。
本轮实测证明：② 被两个独立缺陷双双打穿。

### 11.3 两个独立病灶（实测分离，不是同一问题的两种说法）

| # | 病灶 | 坐标 | 机制 |
|---|---|---|---|
| H1 | **「吃满为止」独占预算** | 旧 `push_raw(m)` = `_clip(content, max(raw_cap-used, 16))` | newest-first 取到 `raw_cap` 满为止 ⇒ 预算被**最新一条长回复**独占 |
| H2 | **`used_ids` 记的是「被考虑过」而非「已注入」** | 旧代码多写一行 `used_ids.update(m["id"] for m in cur_group["msgs"][-cur_max:])` | 因预算不足没进去的消息被标成"已用" ⇒ **既不在①原文、也不在②拉回** ⇒ 彻底消失 |

**H1 铁证**（真库 conv=514）：一条 **4843 字符**的助手回复占 **994 tok**，紧接着的**最新用户输入**
只拿到 `max(1000-994, 16) = 16` tok（残句「按上述方案落地：在既有」），更早 3 条用户输入**整条消失**。
—— 而用户输入是**意图与约束**的载体，本就是短文本，几乎不占预算。

**H2 铁证**：conv=1 里相似度 **0.988** 的用户输入、conv=325 里 **0.927** 的那条，都是这么丢的
—— **被吞掉的恰恰是最该被拉回的内容**（分数最高的先被"标记已用"再被排除）。

> 判据纪律：**证明"某条历史消息被吞了"必须同时证明"它本该被拉回、且是最高分"**。
> 手法：用同一打分器单独跑 `_search_history(候选, query, topk=50)` 断言 `score ≥ 0.9`，
> 再断言它**不在**出块里。只断言"不在出块里"是**恒真**的（任何消息都可能因为别的原因不在）。

### 11.4 修好 H2 后暴露的第三个问题：短文本余弦系统性偏高

`used_ids` 修正后，conv=1 的混合 top-6 **全是 user**（助手历轮结论一条都进不来）。
原因是**模长归一化后短文本的语义方向更"纯"**：13 字符追问得 **0.988**、4 字符「继续优化」得 **0.66**，
而助手数千字的结论只有 **0.5~0.6**。

**结论：「高相似度 ≠ 有信息量」** —— 需要一条**与分数无关**的结构性配额来兜底。

### 11.5 修法（五处，`history.py`）

1. **① 两级分配（均分 + 余量回填）**，替代"吃满为止"：
   ```python
   _share = max(raw_min_share, raw_cap // max(len(_rcands), 1))
   for m in reversed(_rcands):        # newest-first：预算真不够时优先保最新
       push_raw(m, _share)            # push_raw 的第二个参数是**上限**（min(share, room)）
   raw_list.reverse()
   ```
   第一级先保**条数**（谁也不许独占）；第二级把 `raw_cap - used` 的**余量按 newest-first 回填**
   给被截断的条目（上不封顶至原文全长）。只做第一级会把短会话里唯一那条长回复白切一半；
   只做"吃满为止"就是本批要修的病灶 —— **两者组合**才同时满足"条数覆盖"与"不浪费"。
2. **`used_ids` 只记真正注入的**：删掉超额 `used_ids.update(...)`，改为
   `used_ids = {m["id"] for m in raw_list if m.get("id")}`。
3. **② 候选层丢弃「回声」**：与当前输入**逐字重复**（去空白后相等）的历史消息**不参与相关性评估**。
   ⚠️ 必须在**候选层**过滤，不能只丢块 —— 它分数最高，先占掉一个配额槽再被丢弃，等于白瞎一个名额。
4. **② 分角色配额**：`_search_history(..., per_role_cap=N)` —— user/assistant **各自的**名额上限；
   名额没满时再按分数补齐（防单角色减产）。
5. **② 块头可追溯**：`【相关历史片段（第 N 轮 · 用户，相关度 0.988）】`
   —— 不再是没出处的"相关历史片段"（延续 §7 可追溯纪律）；轮次表由 `_turn_of`（user 消息序号）生成。

**新增三个配置键**（`core/config.py`，`DEFAULT_CONFIG.context` 与 `CONFIG_SCHEMA.context` 各一份）：

| 键 | 默认 | 语义 |
|---|---|---|
| `history_raw_min_share_tokens` | `96` | ① 每条的最小 token 份额（均分的下限） |
| `topic_retrieve_per_role_cap` | `3` | ② 分角色配额（user/assistant 各 ≤N，`0` = 不限制） |
| `topic_retrieve_drop_echo` | `True` | ② 丢弃与当前输入逐字重复的拉回块 |

### 12.4 命名规则（`core/artifact_titles.derive_title_from_content`）

顺序（信息密度由高到低）：

| # | 取法 | 例 |
|---|---|---|
| ① | 首个 markdown 标题行（`#`~`####`） | `# 巡飞弹参数变更影响分析报告（…）` → `巡飞弹参数变更影响分析报告（…）` |

### 13.3 定位（py-spy 原生栈）

### 13.4 根因

**关键误区**：Python 层 `sitecustomize._safe_remove`（同出自 WorkBuddy shim）对 `%TEMP%` 有旁路，
但**旁路之后调用的仍是原生 `DeleteFileW` —— 照样被 tsbx.dll 拦截**。「临时目录旁路」救不了这一层。
这解释了为什么 `sysml_v2_check`（用 `os.unlink`）此前看似正常——同族风险，只是没在编排链路上被触发成死锁。

| `sysml_v2_check.py` | `_run` finally | 同类：checker 临时 .sysml |
| `knowledge_pipeline/ingest.py` | 孤儿副本清理 | 本就是 best-effort，失败不阻断 |

真正根治在 WorkBuddy 沙箱层修 tsbx 死锁（已登记）。

## §15 移除写死意图：建 requirement_quality Agent + 降级 builtin 层（P1-15）

### 15.1 触发

用户四问：① 回填自建 Agent 关键词（同意）；② 为啥必须基于关键字/名称/描述；③ 移除内置写死意图（建对应 Agent）；

### 15.2 回答「当前规划下一步采用哪个模式」

结论：**混合模式**，按任务复杂度分岔，且规划是「一次性 + 事后反思」，非「边做边重新规划」。

| 路径 | 触发 | 规划方式 | 对标 |
|---|---|---|---|
| 编排路径 | 命中可编排意图（复杂任务） | **Planner-Executor-Verifier**：planner 一次 LLM 生成完整 DAG（key/agent/deps/task_type/context/expected_output/tools/skills）→ TaskQueue 按 deps 执行（ready>1 并行 ≤3）→ 汇总后 RefineGate 反思（max_rounds+2 轮 eval/refine） | Manus 三 Agent + 质量门 |
| 单 Agent 路径 | 简单任务 | 一次 LLM（带 tools）→ 有 tool_calls 则执行工具回填观察再生成，**最多 3 轮 ReAct** | Claude Agent SDK |
| 编排子任务 | 子任务 task_type | agent（完整管线）/ react（多步思考-工具）/ llm（纯生成）/ tool | — |

关键区别：**planner 一次性出整个 DAG，执行中不据中间结果动态重规划；反思在全部执行完后做**。标杆里
Claude 是「无显式 planner 的纯 ReAct」，Manus 是「多 Agent 分工 + CodeAct 一等动作」。本平台是两者混合，

## 19. P1-21：estimated_cost 缓存折扣计价 + 行业标杆调研（为优化方案提供支撑）

### 19.1 (a) `estimated_cost` 改为区分缓存命中/未命中单价

此前 `estimated_cost` 把 `prompt_tokens` **全按 input 混合价**估算 → 缓存折扣被抹平，
**命中越多、成本数字虚高越严重**（与 P1-20「缓存实际省 62%」自相矛盾）。改为：

| 场景 | 计价 |
|---|---|
| provider 返回 hit/miss（真实调用） | `miss(及余量) × input价 + hit × cache_hit价 + ct × output价` |
| 未返回（hit=miss=0，含 Mock / 无 usage） | 退回原式 `pt × input价 + ct × output价`（**零漂移**） |

`PRICE_PER_1M` 增补 `cache_hit: 0.015`（≈ input 的 10%）。依据与标杆口径一致：
DeepSeek hit $0.014/M vs miss $0.14/M（约 1/10）、Anthropic cache read = 0.10× input。

自检 `tools/verify/verify_llm_cost_cache.py` **5 PASS**：折扣后成本比混合价**省 40%**、
无缓存字段时与原式逐位一致、异常余量（hit+miss > pt）兜底不为负、M1 变异（取消折扣）被抓住。

### 19.2 (b) 行业标杆调研：prompt caching 做法对照

| 标杆 | 机制 | 控制方式 | 生效门槛 | 单价（读 / 写） |
|---|---|---|---|---|
| **Anthropic Claude** | 显式 `cache_control` 断点（**最多 4 个**） | 开发者标记断点 | 建议静态前缀 ≥1024 tokens | read **0.10×**、write 1.25×（5min TTL）/ 2.0×（1h TTL） |
| **OpenAI** | 自动前缀缓存 | 无需配置 | 静态前缀 **≥1024 tokens** | 无写溢价；read 0.50×（部分新模型 0.90× 折扣） |
| **DeepSeek**（本平台在用） | 自动磁盘缓存 | 无需配置 | **64 tokens** 为存储单位 | hit $0.014/M vs miss $0.14/M（≈1/10） |
| **Google Gemini** | 显式缓存对象 + TTL | 创建 named cache 后按名引用 | — | 90% 折扣 |
| **阿里云百炼（DashScope）** | 上下文缓存 | 按模型支持列表 | — | 折扣按模型 |

**断点放置的最优实践（Anthropic）**：① system prompt 末尾、② 工具定义末尾（**这两者跨查询最稳定、
收益最大**）、③ 长对话历史末尾、④ 最新 user 消息末尾（第 4 个几乎无用，user 每轮都变）。

### 19.3 最权威的一条纪律：Anthropic Claude Code 团队官方博客

> "The best way to do this is **static content first, dynamic content last**."

Claude Code 自述 "we build our **entire harness** around prompt caching"，并对命中率
**跑告警、命中率过低直接 declare SEV**——缓存命中率在他们那里是一级可观测指标。
其 prompt 分层（越靠前越稳定、越该被缓存）：

1. **Static system prompt & Tools**（全局缓存）→ 2. **CLAUDE.md**（项目内缓存）
→ 3. **Session context**（会话内缓存）→ 4. **Conversation messages**（每轮增长）

他们还主动公开了**自己踩过的坑**（说明这条纪律有多 fragile）：

- 把**详细时间戳**放进 static system prompt → 前缀每次都变，命中率崩；
- **非确定性 shuffle 工具定义顺序**；
- **更新工具参数**（例如修改 Agent 工具可调用的 agent 列表）。

另两条配套纪律：**"Use messages for updates"**（信息过期时不要改 system prompt，改为在下一轮
message 里带更新，以保住缓存）、**"Don't change models mid-session"**（缓存是模型 scoped 的，
中途换模型必须重建缓存，反而更贵）。

### 19.4 通用反模式（会让命中率归零）

多来源一致结论，可直接当 checklist 用：

1. **易变值进 system prompt**（时间戳、用户名、当前日期）→ 前缀每次都变。
2. **非确定性序列化**：Python dict / JSON 键顺序随机 → 内容逻辑相同但字节不同 → miss。
   修法：`json.dumps(schema, sort_keys=True)`，system prompt 模板用原始字符串字面量。
3. **system prompt 不在 position 0**（历史消息被 prepend 到 system 之前）→ 把 system 挤出可缓存的前缀位置。
4. **工具定义顺序非确定性**。

### 19.5 与本平台的映射：问题定位（这正是 19.3 的反模式）

当前 `execute.py:242-274` 的 `system_prompt` 拼接里混入的**每轮都变**的块：

| 动态块 | 变化来源 |
|---|---|
| `_build_memory_hint` | 长期记忆，随检索结果变 |
| `_build_model_context` | 建模上下文，随建模进展变 |
| `context_text` | 检索到的互联数据，每轮检索结果不同 |
| `slots`（任务拆解） | 每轮不同 |
| `_build_project_memory` | 带 `user_input` 相关性，随输入变 |

→ 与 Anthropic 官方点名的「把易变内容放进 system prompt」**是同一类问题**。

需要说明的是，**结构位置本身是对的**：`messages = [system] + hist + [user]`（`execute.py:294-297`），
system 确实在 position 0（符合反模式 3 的要求）。问题**不在位置，而在 system 的内容每轮都变**。

### 19.6 优化方案建议（对标 Claude Code 分层）

把 `system_prompt` 按「稳定/易变」拆成两段，**稳定段留在 position 0，易变段挪到 messages 尾部**
（作为独立的 user 侧上下文块，对标 Anthropic 的 "Use messages for updates"）：

```
[静态·缓存前缀] 角色块 + 输出规则 + 引用规则 + 技能/团队名册 + 本体边界
[半静态]        会话级上下文
[动态·尾部]     检索结果 / 长期记忆 hint / 建模上下文 / slots / 项目记忆
[动态·尾部]     历史消息 + 当前 user 输入
```

### 19.7 风险与验收判据（**先有基线再动结构**）

| 风险 | 说明 |
|---|---|
| 语义权重变化 | LLM 对 system 与 user 的遵循强度不同；约束类内容挪到 user 侧可能被降权 |
| 角色混淆 | 检索结果/记忆挪到 user 块，可能被误当作「用户说的话」而非「系统约束」 |

验收判据（缺一不 Merge）：

1. **缓存命中率显著提升**——现在已可观测（P1-20 新列），这是主判据；
2. `eval_intent_routing` accuracy **不低于 0.955** 基线；
3. verify 全家桶不回归（`verify_multiturn_context` 132 / `verify_intent_db_kw` 9 等）；
4. 人工抽检：引用规范、输出格式约束是否仍被遵守。

### 19.8 真实结构命中率实测（**结论修正了优化方向**）

对照基线（P1-20）：**完全静态** system 前缀（745 tokens）连发 → 命中 **68.7%**。
真实业务结构走真实 API（合成会话，连发 2 轮，12 次 LLM 调用）：

| 调用类型 | prompt_tokens | 占比 | 命中率 |
|---|---|---|---|
| 主对话生成（`intent=-`，pt≈4200–4600） | 13,067 | **60%** | **50.9%**（其中**第 2 轮达 95.0%**） |
| 辅助调用（`rag_rerank`/`rerank`/`skill_route`/`memory_deposit`） | 8,764 | 40% | **2.9%**（重排类恒 **0%**） |
| **合计** | **21,831** | 100% | **31.7%** |

**这个分布推翻了「重构主 system prompt 能大幅省钱」的直觉**：

1. **主调用（占 token 60%）其实已经不错**——第 2 轮命中 **95%**（前缀因历史累积而变长变稳），
   整体 50.9%。把它的动态块挪到尾部**有提升空间，但不是数量级**。
2. **真正的浪费在辅助重排/路由调用（占 40%，命中≈0）**。但深挖 `services/rag_rerank.py:31-36`
   发现其 prompt **结构本就是对的**（稳定指令在 `system`、动态候选在 `user`，符合 19.3 的纪律）。
   命中为 0 的原因是**内容性质**：稳定指令仅 ~80 tokens，而候选片段（8 段 × 300 字）占了
   prompt 的绝大部分且**每次都不同**——这类调用「输入本身就是内容」，缓存天然指望不上。
3. 因此**辅助调用的正确优化方向不是缓存**，而是**减少调用次数 / 精简候选**
   （如 `max_candidates` 8→5、每片段截断 300→200 字），或按场景关闭 `rag.rerank_enabled`。

### 19.9 结论与建议（按实测重排优先级）

**已做的两步（观测先行，正确）**：

1. ✅ P1-20：把命中率变成可观测指标（没有这一步，下面所有结论都无从谈起）；
2. ✅ P1-21：成本估算反映缓存折扣，避免「省了钱但账上看不出来」。

**按 19.8 实测重排后的优化优先级**（原「重构主 system prompt」由 P1 降为 P2）：

| 优先级 | 方向 | 依据 |
|---|---|---|
| **P1** | **精简/限流辅助重排调用**（`max_candidates`、`rerank_enabled` 按场景开关、片段截断长度） | 占 token 40% 且命中恒 0，是**纯浪费**；改配置即可，零行为风险 |
| **P2** | 主 `system_prompt` 动态块挪尾部（19.6 方案） | 占 token 60%，命中 50.9%→有空间，但**非数量级**；需按 19.7 严格 A/B 验收 |
| P3 | 给短指令类辅助调用补足稳定前缀（使其 >64 tokens 缓存单位） | 收益小，可能「为缓存而加长 prompt」，得不偿失 |

**关键方法论**：这一轮再次验证「**先观测、后优化**」——若跳过 P1-20 的观测直接按 19.6 重构主 prompt，
会花掉最大的改造风险，却只拿到次要收益（真正的大头在辅助调用，且解法只是改配置）。

**不建议照搬的**：Anthropic 的显式 `cache_control`（DeepSeek 是**自动**缓存，没有断点概念，
照搬无意义）；Gemini 的显式缓存对象（引入额外状态管理与 TTL 成本）。

## 20. P1-22：关闭两级 LLM 重排（实测：召回零收益、慢 7 倍）

### 20.1 触发与问题定位

P1-21 实测发现辅助重排调用占 token 40% 且缓存命中恒 0 后，深挖发现系统里**不是一次重排，

### 20.2 A/B 实测（官方评测 `tools/eval/run_eval.py`）

## 22. P1-24：`system_prompt` 静态约束块前移（提升缓存命中率）

### 22.1 问题根因（前缀在第 11 位就断了）

DeepSeek 缓存按**前缀完整匹配**（从第 0 token 起）。改动前 `execute.py:242-274` 的
拼接顺序里，**动态块排在了静态块之前**：

| 序 | 块 | 性质 |
|---|---|---|
| 1 | `role_block` | 静态 |
| 2 | 当前意图 / Agent / HIL | **动态**（每轮可能变） |
| 3–10 | 工具 / skill / 名册 / 模板 / 建模代码要求 / 本体 / 边界 | 静态 |
| **11–15** | **记忆 hint / 建模上下文 / 项目记忆 / slots / user_ctx** | **★动态** |
| **16–17** | **`_build_output_rules` / `_build_citation_rules`** | **静态（却被挤到动态块之后）** |
| 18–20 | 附件 / 检索结果 / report | 动态 |

⇒ 前缀在第 11 位（记忆 hint）就断了，**明明是静态的输出/引用规则却进不了可缓存前缀**。

### 22.2 改动（只调顺序，不改任何块的内容）

把两块静态规则（`output_rules`、`citation_rules`）**提到动态区之前**，动态块统一下沉尾部：

```
[静态前缀] role_block → 意图 → 工具 → skill → 名册 → 模板 → 建模代码要求
           → 本体 → 边界 → 输出规则 → 引用规则
[动态尾部] 记忆 hint → 建模上下文 → 项目记忆 → slots → user_ctx → 附件 → 检索结果 → report
```

依据：Anthropic Claude Code 官方纪律 **"static content first, dynamic content last"**。
保守取舍：**不动「当前意图」**（它在第 2 位，也是动态的，但属于核心上下文）。

### 22.3 A/B 实测（真实 API）

**基线**（改动前，关重排后同口径）：第 1 轮主调用 **30.8%**、第 2 轮 **56.3%**，均值 43.6%。

**改动后**（本次 3 个主调用，轮 1 触发多阶段）：

| 主调用 | pt | hit | 命中率 |
|---|---|---|---|
| 第 1 轮 | 3936 | 2432 | **61.8%**（基线 30.8%，**+31 个点**） |
| 第 2 轮 | 5187 | 512 | 9.9% |
| 第 3 轮 | 5604 | 5376 | 95.9% |
| **均值** | — | — | **55.9%**（基线 43.6%） |

**第 1 轮是最干净的对比**（此时无历史消息干扰，命中几乎全部来自 system_prompt 静态部分）
→ **30.8% → 61.8%，静态前缀变长确实生效**。

> ⚠️ **判据口径教训**：逐位对比「第 N 个主调用」会**错位** —— 不同会话触发的主调用
> **次数不同**（本次轮 1 触发多阶段 → 3 个；基线只有 2 个），第 N 个未必对应第 N 轮。
> 首版脚本据此报了 FAIL（第 2 轮 9.9% vs 56.3%），实为苹果比橘子。
> 修法：**只硬断言第 1 轮 + 整体均值**，不做逐位对比。
> （第 2 轮 9.9% 的成因是两轮「当前意图」不同 → 前缀在第 2 位断裂，与本次改动无关。）

### 22.4 质量验证（零回归）

| 项 | 结果 |
|---|---|
| `eval_intent_routing` | accuracy **0.955**（错 2/44），macro_f1 0.9652 —— **与基线逐位一致** |
| `verify_multiturn_context` | 132 / 0 |
| `verify_subtask_isolation` / `verify_intent_kw_layers` | 10 / 10 |
| `verify_intent_db_kw` / `verify_orch_whitelist` | 9 / 9 |
| `verify_memory_tier` / `verify_rag_config` | 8 / 31 |

只调顺序、不改块内容，且「约束规则更靠前」通常权重更高 —— 实测也确认质量未降。

### 22.5 遗留

- **「当前意图」仍在动态区之前（第 2 位）**：它每轮可能变，是前缀的第二大破坏者。
  若把它也下沉到动态区，前缀可进一步变长，但它是核心上下文，需单独 A/B 验证质量后决定。
- 缓存命中率受「历史长度」与「意图是否变化」影响很大，单次 A/B 波动较大；
  规模化收益应以长期 `llm_usage_stats` 的 `prompt_cache_hit_tokens` 聚合为准。

## 23. P1-25：`当前意图` 行下沉 —— 并由此挖出「真正的破坏者」

### 23.1 动机与量化前提

P1-24 把两块静态规则提前后，`当前意图` 这行仍卡在 system_prompt **第 2 位**：

```python
f"{role_block}\n"
f"当前意图：{intent}（Agent: {agent_def.name}，HIL 人机协作级别：{hil_level}）。\n"   # ← 第 2 位，动态
```

它每轮可能变，而 DeepSeek 按**前缀完整匹配**缓存 ⇒ 前缀在第 2 个块就断，后面 9 个静态块
（工具/skill/名册/模板/建模要求/本体/边界/输出/引用规则）内容不变却无法命中。

**先量化「意图到底多频繁变化」**（`tmp/mt_ctx/probe_intent_churn.py`，对真库 4 个多轮会话逐条跑 `detect`）：

| 会话 | 轮数 | 相邻轮意图变化率 |
|---|---|---|
| conv=1 | 20 | 63.2% |
| conv=514 | 10 | 66.7% |
| conv=325 | 10 | 44.4% |
| conv=326 | 3 | 0% |
| **总体** | 39 对 | **56.4%**（约每 1.8 轮变一次） |

### 23.2 改动

把 `当前意图` 行从第 2 位**下沉到动态区最前**（仍在记忆/检索之前，避免沉得太深）。
只移动这一行，不改任何块内容。

### 23.3 A/B 结果与**两个必须说明的口径问题**

| 主调用 | pt | hit | 命中率 |
|---|---|---|---|
| 第 1 轮 | 3944 | 2688 | **68.2%**（P1-24 基线 61.8%，**+6.4 个点 / +256 tokens**） |
| （空调用） | 0 | 0 | 0.0% |
| 第 3 轮 | 5518 | 384 | 7.0% |

**口径问题 1（缓存重建污染）**：改了 prompt 结构 ⇒ 之前建立的缓存前缀**全部失效**，
首次跑必然偏低（需重新建缓存）。故**单次 A/B 的均值不可直接与改动前比**。

**口径问题 2（pt=0 空调用）**：本轮出现一个 `pt=0` 的空调用（异常/空响应），
它把「均值」判据拉到 25.0% ⇒ 该判据在本批**不可用**。

**唯一干净的可比项是第 1 轮**（无历史干扰，命中几乎全来自 system 静态部分）：
**61.8% → 68.2%**。

### 23.4 关键发现：真正的破坏者不是这一行

第 1 轮只 **+256 tokens**，远低于「9 个静态块入前缀」的预期（应有 +2000 量级）。
追查代码后找到原因：

**`_build_model_code_req(intent, agent_def)`（`prompt.py:138`）的内容依赖 intent**——
建模类意图（`design`/`requirement_analysis`/`impact`/`review` 或含"建模"/"sysml"）
输出**一大段建模要求 + L0 硬约束卡**；非建模意图**返回空串**（`:163 return ""`）。

⇒ 只要意图在「建模类 ↔ 非建模类」之间切换，该块内容就变，**前缀在它那里就断了**
（尽管它排在静态块之前）。这才是「前缀无法覆盖后续静态块」的**主因**，
下沉 `当前意图` 这一行只解决了一小半。

### 23.5 质量验证（零回归，本批的保留依据）

只移动一行、不改内容，且意图信息仍在 system 中前部 —— 质量未降。

### 23.6 遗留（下一步方向）

**把 intent-定制块也下沉**（`_build_model_code_req` 为主，可能还有 `_build_skill_prompt`），

另：`_build_prompt_template` 虽也按 intent 匹配，但 `prompts` 表当前为空 → 返回空串，暂无影响。

# 24. system_prompt 四层分层与拼装单一真源（P1-26）

> 本批起因是用户的一句批评：**「我希望你基于行业标杆产品调研后再下结论，不要亦步亦趋改动，
> 导致整个系统越来越不稳定，产出质量下降」**。批评成立——P1-24/P1-25 是**碎片化的顺序微调**
> （每轮挪一个块），其中 P1-25 移动「当前意图」时**只有命中率依据、没有标杆依据**。
> 本批改为：先调研标杆 → 做一次依赖审计 → **一次性**按四层重排 + 收敛为单一真源 + 加守护。

## 24.1 标杆调研结论（三条硬证据）

| 来源 | 结论 |
|---|---|
| Anthropic Claude Code 源码架构（`src/constants/prompts.ts`，system prompt 15k–40k tokens 拼装） | 用**显式常量分界线** `SYSTEM_PROMPT_DYNAMIC_BOUNDARY` 切开：线上是全局可缓存的静态层（身份/规则/工具/风格），线下是动态层（会话指导/Memory/环境/语言偏好）。**动态内容仍在 system 内部**，只是排在分界线之后。配套 `DANGEROUS_uncachedSystemPromptSection(name, compute, reason必填)` 命名约定 —— 任何破坏缓存的函数必须在命名上可见、必须写明理由。 |
| Anthropic 官方 prompt caching 指南 | **"static content first, dynamic content last"**；并自曝踩坑：把时间戳放进 system prompt、工具定义顺序非确定性、中途换模型。 |
| 独立工程复盘（长时 agent + 缓存） | **「在运行中反复改 system prompt 的 agent，开启缓存后反而更差」**——每次改动都让缓存全废、反复付写入成本。**这正是 P1-24/P1-25 的形态。** |
| ProjectDiscovery Neo agent（20k system prompt） | 命中率 **7% → 84%**、成本 **−59%**，靠的不是调参，而是**一次性把动态工作记忆移出 system prompt**。 |

**结论**：分层是**显式架构**（显式边界 + 块的层分类 + 破坏可见），不是「手改拼接顺序」。

## 24.2 依赖审计：三个此前的误判/硬伤

对 20 个块按「依赖什么」审计（`_build_*` 是否读 `user_input` / `intent` / 检索 / 建模态）：

| 层 | 判定依据 | 块 | 实测变化频率 |
|---|---|---|---|
| **L2 身份层** | 只依赖 `agent_def` | role、可用工具、工具约束、团队名册 | **agent 由 intent 选出 ⇒ ≈ 意图变化率 56.4%** |
| **L1 全局静态** | 无参方法，跨 agent 完全一致 | ontology、boundary、output_rules、citation_rules | 0（跨 agent/会话不变） |
| **L3 会话级** | 依赖 `intent` | 当前意图、model_code_req | 56.4% |
| **L4 每轮级** | 依赖 `user_input`/检索/建模态 | skill_prompt、skill_block、template、memory、model_context、project_memory、slots、user_ctx、attachment、retrieval、report | **≈100%** |

审计出的三个硬伤：

1. **两条路径各写一份拼接顺序** ⇒ 已发生口径漂移。**实测确认：P1-24/P1-25 只改了
   `execute.py`（非流式），`stream.py`（流式主路径）完全未生效**——此前那两批报的
   「命中率提升」在流式路径上并非来自该改动。这正是 `prompt.py:231-233` 早已警告过的
   「两侧只负责拼接顺序 ⇒ 改一处漏一处」。
2. **`_build_skill_prompt(intent, user_input, user)` 排在第 3 位**（`skills.py:112`，
   第 135 行读 `user_input`）⇒ **几乎每轮都变**，其后 4 个 L1 全局静态块（本体/边界/
   输出/引用规则）从未进入可缓存前缀。这比 P1-25 盯着的「当前意图」严重得多。
3. **P1-25 对 L0 卡位置的判断有误**：`model_code_req` 改动前在第 8 位、改动后在第 10 位，
   只跨过 ontology/boundary 两个块 ⇒ **「L0 卡被大幅后置」的风险被高估**；真正发生大位移的是
   `skill_prompt/skill_block/template`（第 4–7 位 → 第 11–13 位）。

## 24.3 方案：四层显式分层 + 拼装单一真源 + 守护脚本

**① 单一真源**（`agent/pipeline_parts/common.py`）：

```python
PROMPT_CACHEABLE_KEYS = ("role", "tools", "tool_rules", "roster",          # L2
                         "ontology", "boundary", "output_rules", "citation_rules")  # L1
PROMPT_DYNAMIC_KEYS   = ("intent_line", "model_code_req",                   # L3
                         "skill_prompt", "skill_block", "template", "memory", "model_context",
                         "project_memory", "slots", "user_ctx", "attachment", "retrieval", "report")  # L4
PROMPT_BLOCK_ORDER = PROMPT_CACHEABLE_KEYS + PROMPT_DYNAMIC_KEYS
PROMPT_LAYER_BOUNDARY = "── SYSTEM_PROMPT_DYNAMIC_BOUNDARY ──"   # 仅代码层标记，不进入 prompt 文本

def assemble_system_prompt(blocks: dict) -> str:   # 顺序的唯一真源
    ...
```

**② 两条路径只收集块内容**：`execute.py` / `stream.py` 各改为传一个 dict，顺序交给单一真源。
块内容与文案**一字未改**（唯一内容差异：stream 的 role 与 intent 之间补了 `\n`，修正原先粘连）。

**③ 质量优先取舍（写进代码注释）**：`role`（Agent 身份）**保持最前** —— 身份是 LLM 的首要
上下文，标杆一致把身份放静态层最前。代价是 agent 变化时前缀立即断（见 24.4 场景2），
**不靠挪身份来省缓存**。

**④ 守护脚本** `tools/verify/verify_prompt_layering.py`（等价 `DANGEROUS_` 约定的自动化替代）：
判据**绑定源码事实**而非手写清单——用 AST 从两条路径抽取 `assemble_system_prompt({...})` 里
每个 key 的 value 表达式及其引用的变量名，据此断言：

- **C6（主判据）**：可缓存区的块**不得引用**任何动态变量（`user_input`/`intent`/`slots`/
  `context_text`/附件/…）；
- **C7（反向）**：动态区的块**必须引用**至少一个动态变量（防静态块被误放动态区而白丢缓存）；
- **C1/C2**：两条路径都调用单一真源、且**无 ad-hoc 顺序拼接残留**（防回退）。

该设计使「把动态块塞回前缀」**必然被抓红**，而不依赖人去维护一份会漂移的分类名单。

## 24.4 验证（一）：确定性判据 —— 跨轮公共前缀（不依赖缓存/LLM/网络）

命中率实测受两个噪声污染（改结构 ⇒ 旧缓存全失效；意图缓存在 DB 里持久化 + LLM 兜底有随机性），
故先用**纯字符串测量**给出机制性结论（`tmp/mt_ctx/probe_prefix_stability.py`）：

| 场景 | OLD 跨轮公共前缀 | NEW 跨轮公共前缀 | 收益 |
|---|---|---|---|
| 意图变、**同 agent**（保守上界） | 397 字 | **2145 字** | **+1748 字（5.4×）** |
| 意图变、**agent 也变**（实测 56.4% 的轮次） | 2 字 | 2 字 | 0（身份首位代价，未变） |

静态块实测长度：`ontology` 719 字 / `boundary` 652 字 / `output_rules` 158 字 / `citation_rules` 103 字。

**解读**：改动后，只要 agent 不变，跨轮前缀从「role 块」扩到「role + 工具 + 工具约束 + 名册 +
本体 + 边界 + 输出规则 + 引用规则」——**这 1632 字的全局静态内容从此不再被 intent/user_input
的变化踢出前缀**。这就是 P1-26 相对改动前的机制性收益，与缓存温度、LLM 随机性无关。
agent 变化的轮次两版都断在第 0 位（身份首位的既定成本），**未变好也未变坏**。

## 24.5 验证（二）：端到端命中率 A/B —— **因外部余额耗尽未完成（如实登记）**

设计：`tmp/mt_ctx/probe_p1_26_ab.py`（三轮不同输入）+ `probe_p1_26_ab2.py`（两轮**同构输入**、
跑前精确清掉这两个输入的 `intent_cache`，专测「跨轮前缀复用」这一条通路）。

已取到的有效数据：

| 轮次 | before（旧顺序，前缀已被更早实验缓存） | after（新顺序，**冷启动**） |
|---|---|---|
| 主调用命中率序列 | 73.1% / 43.2% / 97.3% / 5.0% | 0.0% / 5.3% / 94.9% / 26.6% |
| 整体 | 50.3%（hit 11904 / miss 11782） | 33.3%（hit 7808 / miss 15632） |

1. **缓存重建**：改 prompt 结构 ⇒ 旧前缀全部失效，after 的首轮必然冷启动（实测 `hit=0`）；

## 25.1 审计方法

用 AST 抽取 `execute.py` / `stream.py` 各自的**调用集合**（`self._xxx` 自有方法 + 裸函数名），

是否在两处各写一份。**判据绑定源码事实**，不靠人工回忆。

## 25.2 发现一（最重要）：`execute.py` 的 **HTTP 端点**无前端调用（但作为"执行器"仍被消费）

| 事实 | 证据 |
|---|---|
| 前端**只调** `/chat/stream` | `static/js` 全仓仅一处 chat 请求：`11-pipeline.js:936`、`12-chatsend.js:248` |

**结论（必须带限定条件）**：
- **两侧产出的代码块 errors 均为 0**，且"哪侧出码"互有胜负（任务1 EARLY 出、任务3 LATE 出）

  无法交付完整 SysML 代码**。

## 26.3 ⚠️ 探针踩坑（值得单独记住）：显式 `max_tokens` 会顶掉 DB 配置，推理模型下正文全空

L0 微基准首跑 8 次调用**全部空输出**。诊断（同一 prompt，只变 `max_tokens`）：

| max_tokens | finish | completion | reasoning | content |
|---|---|---|---|---|
| 2048（探针显式传） | length | 2048 | **2048** | **0 字** |
| 8192（探针显式传） | length | 8192 | **8192** | **0 字** |
| **不传**（用 DB 16384） | **stop** | 14604 | 11471 | **11818 字**（含 10799 字 sysml 代码块） |

根因两层：
1. `llm/providers/openai_compat.py:91` 的优先级是「**调用方显式值 > DB 配置 > 4096**」——
   探针传 8192 反而**把 DB 的 16384 顶掉了**（服务侧不显式传，所以用 16384、一切正常）；
2. 默认 provider（id=71 `deepseek-v4-flash`）是**推理模型**：`reasoning_tokens` 与正文**共享同一配额**，
   推理未收敛时正文一个字都拿不到（表现为 `finish=length` + `content=""`）。

**⚠️ 顺带暴露一个生产隐患**：该建模任务实测 `completion=14604`，其中 **reasoning 占 11471（78%）**，
而 DB 的 `max_tokens=16384` **只剩 1780 余量（约 12%）**。更复杂的建模任务很可能撞上限 ⇒ 输出截断或为空。
**建议**（已登记，未擅自改 DB —— 属成本/质量权衡，需定夺）：把 `llm_providers.max_tokens`（id=71）
提高到 32768；或对「长输出建模任务」改用非推理模型。

## 26.4 下一步的真正大头：把 L1 静态块放到 `role` 之前（量化预期）

由 26.1 的原因分析直接可得：当前 **56.4% 的轮次（intent/agent 变）命中几乎为 0**，

（`ontology`+`boundary`+`output_rules`+`citation_rules` = **1632 字 ≈ 1100 tokens**）
**跨 agent 完全一致**。

⇒ 若把 L1 放到 `role` **之前**，这 56.4% 的轮次也能命中约 1100 tokens，
**预期平均收益 ≈ 0.564 × 1100 ≈ 620 tokens/轮**（约为本批 +128 的 5 倍）。
代价：`role`（身份）不再最前，可能因首位效应影响角色遵循 ⇒ **必须先做质量 A/B**
（判据：`eval_intent_routing` accuracy 不降 + 建模输出语法/语义错误率不升）。
**未擅自实施**（质量优先原则）。

## 29.2 上游实测（探针 `tmp/probe_health/probe_stream_usage.py`）

先测再改，四个问题一次问清：

| 问题 | 实测答案 |
|---|---|
| 带 `stream_options.include_usage` 会被拒？ | **否**（HTTP 200） |
| usage 出现在帧里吗？ | **是** |
| **不带**该字段时 usage 还在吗？ | **在**（DeepSeek 流式默认就发 usage 帧） |
| `finish_reason` / `reasoning_content` 可取吗？ | **都可取** |

⇒ 关键结论：**零额外请求**即可拿到真实 token 与截断信号，不必为"能观测"付任何成本；
`stream_options` 只需作为**可选开关**（`llm.stream_include_usage`，默认关）留给不带该帧的兼容端点。

## 29.3 修法（4 处，均在 `llm/`）

1. **`llm.parse_stream_frame(raw)`**（新）——逐帧解析 `data: {...}` → `{usage, finish_reason, text_chars}`。
   任何异常/非 data 帧/`[DONE]` → `{}`，**绝不抛**（解析失败不该影响正在进行的回复）。
2. **`LLMClient._stream_resp(usage, finish, chars)`**（新）——包装成 `_record_usage` 认识的形态。
   有 usage 帧则原样透传；无则按 `(reasoning_content + content) 字符数 // 2` 兜底估算。
   ⚠️ **必须含 reasoning**：实测 reasoning 占 completion 79~98%，只按正文估会严重低估
   （本次实测真实 `ct=108`，正文仅 1 字符）。
3. **`_warn_if_truncated(...)`**（新）——`finish_reason='length'` 时**当场 WARNING 留痕**，
   并区分两档：`reasoning/completion ≥ 90%` 报「**正文被推理吃光**」（用户拿到空回复，
   即 P1-26 实测 8 次空输出的形态），其余报一般截断。**从"事后猜"变为"发生时可见"**。
4. **`openai_compat._stream_api` 非 200 立刻抛错**（第二个静默失败点）——
   此前不分状态码直接 `iter_lines()`，而上游 400（余额/参数/鉴权）的正文不带 `data:` 前缀
   ⇒ **零帧输出且不抛异常** ⇒ 生成器"正常结束" ⇒ 上层落一条**成功**记录、用户看到**空回复**。
   P1-26 的 402 正是走过的这条路。

> 附带发现并修复（自检 G 组抓出）：`GeneratorExit` 继承 `BaseException`，`except Exception`
> **抓不到** ⇒ 用户点「停止」/关页面的**高频场景完全不记账**（token 已真实计费）。现单独接住并落库。

## 29.4 实施中被自检抓出的两个缺陷（都是我自己写的）

1. **解析顺序错**：初版把解析放在 `yield ev` **之后** → 最后一帧"已发给客户端但未解析"就遇到
   close ⇒ 整段 usage 丢失（实测 usage 帧恰为倒数第二帧，`pt/ct` 全丢）。改为**先记账再透传**，
   使"已收到的帧"与"已记账的帧"恒等。
2. **变异方向错**：`NEAR_LIMIT_RATIO` 初版变异成 `-1`，而判据是 `mx >= limit * ratio` ⇒
   负值让判据**恒真**（不是被打破，是变成永远命中）；且截断率样本取了对称的 2+2，
   变异前后同为 0.5 ⇒ **空转断言**。两处均被"变异必须能被抓住"这条纪律逼出来。

## 29.8 新坑（写进技能）

1. **新增观测列时必须同时问两个问题**：「谁写它」**和**「主路径是谁」。P1-27 只做了前者
   （加了列 + 透传代码），而主路径走的是另一条腿（流式空 dict 落库）⇒ 列加了但永远空。

## 30.2 等价性怎么证明（本批最值得复用的部分）

"抽取前后行为不变"**不能靠读代码**，也**不能在测试里手抄一份旧逻辑**（那样源码被改坏照样绿）。
本批的做法是：

1. `git show HEAD:<file>` 取**重构前**的 `execute.py` / `stream.py` 源码；
2. AST 定位其中 `assemble_system_prompt({...})` 的 dict 字面量、`skill_block` 赋值链，
   `ast.get_source_segment` 抽出**那段原文**；
3. 在受控命名空间 `exec` 它（stub `self` + 全部局部变量）⇒ **旧行为基线**；
4. 与新函数在等价参数下的输出**逐字节比对**。

⇒ **判据来自旧源码本身**，不是第二份实现。stub 的每个 `_build_*` 返回**带调用指纹**的字符串
（`<<_build_role_block|a=[...]|kw={'cap':1200}>>`），因此"`cap` 传没传、传多少"这类**参数差异
会被逐字节捕获**，不会被"反正都返回一个字符串"抹平。

**结果**：`verify_prompt_blocks.py` **59 PASS / 0 FAIL**（6 组 ctx × 两模式 + 4 种 skill 形态 +
slots 4 态 + 2 条反证 + 4 条变异）；真实链路（`execute` / `execute_stream` 均 `dry_run=True`，
零污染）**12 PASS / 0 FAIL**。

**一条把"严格"落到实处的细节**：初版新代码写 `_build_role_block(ctx.agent_def, cap=ctx.role_cap)`，
而旧 execute 写的是 `_build_role_block(agent_def)`（不传）⇒ 等价测试**立刻抓出**这一"调用形态
差异"。虽然 `cap=0` 与不传在实现上等价，但本批承诺"零行为变动"，就**不该依赖"我知道默认值是 0"**
这个隐含前提 —— 改成 `_role_kw = {"cap": ctx.role_cap} if ctx.role_cap else {}`，
让新旧**连调用形态都逐字一致**。

| 合计 | — | **6,320,833** | **3,011,535** | 19,803 |

**三个结论**：

1. **成本加权后输出占 65.6%**（输入:输出单价 1:4，而量比是 67.7%:32.3%）。
2. **主对话的输入是绝对大头**：772 次吃掉 **426 万输入 token（占总输入 67.5%，单次均 5527）**。
   ⇒ **成本优化的主战场是"压输入总量"，不是"挪块蹭缓存"**。L1 前置只影响其中 1489 tokens
   的**计价方式**（10% 价），完全不动总量；而单次 5527 里，`role`(流式 cap 1200 字≈600) +
   L1(1489) 之外还有 **≈3300 tokens** 来自**检索 / 历史 / 记忆 / 建模上下文** —— 那里才有空间。
3. **`reasoning_tokens` 全量只有 19,803（占输出 0.66%）是"假象"**：该列在**流式路径上此前
   根本不采集**（P1-26 的流式采集缺口，P0-a 刚修）⇒ **真实的推理占比必须等流式数据积累后**
   才能定，不能拿这 2 万去否定/确认 §28 说的"reasoning 占 83%"（那是单次建模任务的观测）。
   —— 这恰好是"先观测、再优化"的价值。

## 32.5 处置

- **§28 的「L1 静态块前置」关闭（不做）**，理由与数据见上。维持 P1-26 的"身份首位"。
- 成本优化的**下一站改为「压主对话输入总量」**（检索/历史/建模上下文占单次输入约 3300 tokens）
  —— 但**必须先积累 P0-a 的流式数据**（现在才知道每轮的输入构成与 reasoning 占比），
  否则又是"凭估算挑一个假目标"。

| 层 | 文件 | 内容 |
|---|---|---|
| 仓储 | `repositories/memory_admin_repo.py`（新） | 列表 / 统计 / 导出 + **三种删除语义**（真删 / 软删 / 恢复） |

**两条删除语义刻意分开**（合规语义，不是冗余）：

- 🗑 **删除 = 真删**（`DELETE`，不可恢复）= 用户行使「被遗忘权」；
- 📦 **归档 = 软删**（`forgotten=1`，检索跳过、可恢复）= 与遗忘引擎同语义。

处置纪律：**用户主动点删除 → 真删；自动/渐进式淘汰 → 软删**。

## 33.4 过程中发现的三个问题（两个真缺陷 + 一个环境坑）

1. **`list()` 硬列了迁移补的列 → 老库直接崩**（我自己的缺陷，被自检 C 组抓出）：
   `source/relevance/activation/access_count/forgotten/tier` 都是 `migrations/columns.py` 补的，
   老库只有最小基表 → `no such column: source`。已改为**按实际列动态拼 SQL** + 逐项降级
   （缺 `forgotten` = 全部存活；缺 `tier` = 按 P1-18 规则推断展示值，不写库）。
2. **记忆无用户维度隔离**（已知缺口，登记在案）：`agent_memory` 无 `user` 列
   （实测 `scope_type` 仅 `''`/`'project'`）⇒ 本页操作的是**全局记忆**。多用户部署前必须补
   user 维度，否则 A 用户能看到并删除 B 用户的记忆。
3. **本机 httpx 会走代理，localhost 也走**（环境坑，害我误判一轮）：本机有
   `HTTP_PROXY=http://127.0.0.1:61433` 且**无 `NO_PROXY`** → httpx 默认 `trust_env=True`
   把 localhost 请求也发给代理 → 代理把绝对 URL 编码成路径 → 服务端收到
   `GET http%3A//127.0.0.1%3A8000/api/...` → **404**。表象像"路由不存在"，极易误判成服务端 bug。
   实测特征：**同一 URL 第 1 次 200、第 2 次 404**。修法：验证脚本用 `httpx.Client(trust_env=False)`。
   （生产代码里的 httpx 调用都是必须走代理的外部域名或用户配置 URL，**不能**全局关掉 `trust_env`。）
