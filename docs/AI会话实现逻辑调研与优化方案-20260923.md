## 0. 结论摘要

1. **系统真正的意图路由是好的，问题出在"入口默认值把它短路了"。**
   后端三层路由（规则快筛 → 语义 → LLM 精排）+ 意图缓存 + DST 继承 + 置信度三档，设计完整；
   但会话入口的「智能体」下拉**默认选中列表第一个 Agent**（= 需求分析Agent，`/api/studio/agents` 按 id 升序），
   把下拉值当 `forced_intent` 发给后端，而 `intent = forced_intent or _detected` 是**恒覆盖**语义
   → 用户"问什么都以需求分析Agent作答"。这不是写死的逻辑，也不是 Agent 团队配置问题，
   是**前端默认值 + 后端"显式定向优先"策略**叠加出的定性缺陷。

2. **同一根因还免费送了一个次生灾害**：`_needs_orchestration()` 里 `if forced_intent: return False`
   （这是**刻意的设计**：指定了 Agent 就别自动编排）。于是"默认定向"把**自动编排也一起关掉了** ——
   这是"AI 建模看起来只会做需求分析、从不走多 Agent 编排"的完整解释。

3. **「都会查询知识库」是两件事拼出来的错觉**：
   ① 单 Agent 侧检索是**配置驱动**（`agent_def.kb_required`；需求分析Agent=0 不检索，design/impact/knowledge_qa/chat=1 必检索）；
   ② 编排侧有一条**写死的** `{"stage","知识库检索","done","retrieved":False}` 阶段事件，无条件推送 →
   UI 上恒定出现"知识库检索"环节。前者正常，后者已按"不发假状态"处置。

4. **需求分析卡（0 条候选条目 / ✓无冲突 / 暂无候选条目 / 查看完整报告）本身有设计用途，但数据源恒空。**
   它是 FR-MG-2 / FR-HIL-1 的"候选需求逐条确认"入口，数据来自
   `entities(entity_type='需求', status='candidate', branch=当前分支)` + `relations(CONFLICTS, status='candidate')`。
   **实测全库该查询恒 0 行**（口径见 §2.2）→ 卡片永远是空态。已按「空态不渲染」处置：
   能力保留，候选需求生产链路跑通后自动恢复。

5. **对标结论（一句话）**：行业标杆的共识是「**默认自动路由 + 显式指定可覆盖但必须可见可撤销 + 产物与对话分离 + 高风险动作人工确认**」。
   本工程缺的正是前两条的"可见/可撤销"与第三条的"产物独立面板"。

6. **多轮上下文的断链不在"历史注入"，而在"产物没有通道"**（2026-09-30 取证，§6）。
   历史注入（v2 话题感知）本身设计完整、且实测**在真实生效**（长会话折算 token 后确实超 2000 tok 预算，
   靠"当前话题原文 + 语义拉回 + 分话题摘要"降维）；真正缺的是**产物（`sysml_versions` / `artifacts`）
   只有写、没有读回** —— 全仓读它们的生产代码只有 `agent/utils.py`，且全在归档写入路径。
   于是「第 2 轮把第 1 轮建好的模型当成不存在」。已按四个落点补上只读的**会话产物摘要**通道
   （§6.4），验收 53 项断言 0 FAIL（§6.5）。**同时仍有执行层的独立故障**：t1 超时
   （241s > `delegation.worker_timeout_s=120`）使后继子任务全 `blocked`，需单独处理（§6.6-1）。

## 1. 现状调研：AI 会话是怎么跑起来的

### 1.1 请求契约（前端 → 后端）

`static/js/mods/12-chatsend.js::sendChat()` → `POST /api/conversations/{id}/chat/stream`：

| 字段 | 来源 | 语义 |
|---|---|---|
| `message` | 输入框（含 `@` 会话文件 / `#` 知识库引用折叠成文本块） | 用户输入 |
| `attachments` | 待发附件 | 附件优先作依据 |
| `scope_ids` | 建模范围多选（全局） | **硬锁**检索文档范围 |
| `branch` | `getCurrentBranch()` | 输出侧工作分支（默认 `dev`；`release` 只读） |
| **`forced_intent`** | **`#quick-agent` 下拉值** | **显式定向 Agent**（本次缺陷的入口） |
| `skill_name` | `#quick-skill` 下拉值 | 指定技能（独占式工具白名单） |
| `team` | `#quick-team` 下拉值 | 团队模式：主 Agent 强制编排 |
| `provider_id` | 模型下拉 | 指定 LLM |

后端 `routers/conversations.py::chat_stream` → `agent/pipeline_parts/stream.py::execute_stream`。

### 1.2 意图识别：三层 + 缓存 + DST（`agent/intent.py`）

```
detect(text, conn, prev_intent)
 ├ ① 意图缓存 L1（query_hash + index_fp 双键，命中直返，跳过全链路）
 ├ ② 建模强信号（正则）：(生成|给出|输出|编写|创建).{0,24}(sysml|建模|视图|代码) → design 0.95   [:175]
 ├ ③ Glossary 术语归一化强制路由（CIA 强信号让路）                          [:179]
 ├ ④ 报告命令优先 → report_generation 0.95                               [:196]
 ├ ⑤ 变更影响强信号 → impact 0.95                                        [:201]
 ├ ⑥ 需求质量（高特异词才触发）→ requirement_quality                       [:204]
 ├ ⑦ DB 规则表 intent_rules（**实测 0 行**）→ ⑧ DB Agent 关键词 → ⑨ 内置关键词
 ├ ⑩ 语义兜底（VectorEngine 余弦，≥0.70 = semantic，否则 semantic_weak → 会话继承）
 └ ⑪ LLM 兜底（<0.85 且有 prev_intent → 继承）→ ⑫ 无信号 → 继承 → chat
```

- **置信度三档**：`_done()` 里 `needs_clarify = route ∈ {semantic_weak, inherit} or (llm 且 conf<0.85)` → 前端澄清条（可点选改选重发）。
- **会话级 DST**：`_load_conversation_dst()` 读会话当前意图做 `prev_intent`（追问/续写不被误判）。
- **缓存毒化防线**：只对 `requirement_quality`（[:157]）与 `impact`（[:164]）做了"缓存命中也必须过强信号词校验"；
  **`design` / `requirement_analysis` 没有这道防线** —— 见 §2.5。

### 1.3 三条执行路径（决定"输出什么样"）

| 路径 | 触发条件 | 落库卡片指纹（判路径的硬判据） |
|---|---|---|
| **单 Agent 直行** | 默认；或 `forced_intent` 非空（强制不走编排） | 含 `citations` / `submitted_by`，**无** `orchestrated` |
| **自动编排** | `not forced_intent` 且 `_needs_orchestration()` 为真（多步规则信号 / LLM 判复杂） | 含 `orchestrated`/`plan`/`orchestrated_status`/`run_budget` |
| **团队强制编排** | `team` 非空且解析到 `agent_role='main'` 的启用 Agent | 同编排 + `team=<主Agent意图名>` |

`_needs_orchestration()` 的判据（`orchestration.py:154`）：
`forced_intent` 非空 → **直接 False**；意图不在 6 类内 → False；多步正则（先…再…/然后…）或"两域关键词+连词" → True；
短噪声(<6 字) → False；带附件 → False；仅 `requirement_analysis`/`design` 才继续走 LLM 复杂度判定。

> ⚠️ `_stream_orchestrated_flow` 计划失败时的**降级直行把意图硬编码成 `requirement_analysis`**（`stream.py:108`）。
> 这是一个"降级也走需求分析"的死角：计划解析失败时，无论原意图是什么，都会以需求分析Agent 兜底作答。

### 2.1 默认定向覆盖（已修）

**证据链（四段互相独立）**：

### 3.2 五条可迁移结论

1. **"自动路由"必须是默认值，"显式指定"必须是**用户主动动作**。**
   标杆产品里没有任何一个把"某个具体 Worker"设为默认选中项；默认永远是 auto。
   → 对应本工程 §2.1（已修）。
2. **显式覆盖必须可见、可撤销、可解释。**
   本工程已有雏形（`stream.py:878` 会在 reasoning 里说"已按显式选择执行 X；语义识别为 Y"），
   但**只在流式思考里一闪而过**；而且默认值造成的"隐式定向"根本没触发这条提示。
   → 建议：`card_data` 增加 `intent_override:{forced, detected}`，在**消息落款行**常驻显示可点击撤销（§4）。
3. **产物与对话分离**（Claude Artifacts / ChatGPT Canvas / Perplexity 报告页）。
   本工程已具备原料（`sysml_versions` 版本链、`reports` 表、`artifacts` 产物库）与视图面板，
   但"AI 建模产物"仍主要躺在消息流里 → 建议把 SysML 代码/视图升级为**可独立版本化、可回滚、可 diff** 的右侧面板（§4）。
4. **高风险动作人工确认是产品点，不是摩擦。**
   Claude Code 的逐命令 allowlist 在敏感工程语境是**特性**。MBSE 语境对应的"高风险动作"=
   写图谱 / 发布分支 / 改本体 / 覆盖模型版本 —— 本工程 `_orch` 子任务已有"写操作受控上下文"的雏形，
   建议显式化为**统一确认闸**（§4）。
5. **可配置的生命周期钩子**（hooks + Skills）是"可运营"的关键。

### 8.2 超时判据修订（问题 ① 的根因不是配置，而是**判据本身**）

**先纠正一条早前的误归因**：`delegation.worker_timeout_s=120` **不是**流式编排的真凶 ——
它只在**非流式 planner 的并行分支**（`workflows/planner.py:309`）使用。流式路径的真凶是
`agent/pipeline_parts/skills.py:195` 的**硬编码类属性** `_ORCH_SUBTASK_TIMEOUT = 120`
（配 `_ORCH_MAX_RETRIES = 1` → 2 次尝试 ≈ 240s，正好对上实测的 241s）。

**更关键的是判据语义错了**：原判据是**固定 wall-clock**，而 t1 当时**一直在产出**。
按"是否还在产出"判才符合直觉 —— 真卡死应快速失败，活跃生成不该被误杀。

修法（`stream.py`）：新增 `_hb = {task_key: 最近产出时刻}` **活性心跳表**，任何产出
（token / reasoning / tool 事件）都刷新心跳；worker 等待循环改为
**"停滞为主 + 硬上限兜底"**：

- 无产出 > `subtask_idle_timeout_s`（默认 **150**）→ 判 `timeout（N 秒无产出）`，**快速失败**；
- 总时长 > `subtask_timeout_s`（默认 **300**）→ 兜底 `timeout（超过 N 秒硬上限）`
  （防"持续滴 token 永不结束"）；
- 三个阈值**全部接 config**（`delegation` 组），不再硬编码。

根因是**评测harness 的数值抖动**：同一 `fp=a4c91a24` 候选集下，稠密语义路的 `conf`
在运行间有第 3~4 位差异（实测 `0.8502901887601901` vs `0.852019387201989`）——
边界样本可能换类，于是 **accuracy 不变而 `macro_f1` 在 0.965~0.969 间摆动**。
判据以 `[RESULT]` 行 + 隔离重跑为准；**下次看到 `macro_f1` 在此区间波动，先按本口径排除，别当回归**。

### 8.8 实跑中发现并一并修复：质量评审被 `max_tokens` 截断 → 误报「解析失败」0/100

**现象**：实跑里 `reflection = {score: 0, passed: false, issues: ["解析失败"]}` →
`quality_gate_gaps = ["质量评审未通过（0/100）：解析失败"]` → `orchestrated_status` 被
**降级为 `partial`**。即**一个解析 bug 把"质量正常"报成了"门禁未通过"**
（与 §8.4 的"话说得不准"同族，方向相反）。

**根因**：`workflows/nodes.py` 的 `_evaluate_content` 原用 `max_tokens=1024`，
而当前 provider 是**思考模型**（`deepseek-v4-flash`，回包含 `reasoning_content`）——
**推理与正文共享同一个上限**。大输入（`refine.eval_in_chars=24000`）下 `reasoning_tokens`
吃掉大部分额度 → JSON 被 `finish_reason="length"` 从中间截断、**闭合 `}` 丢失** →
正则 `\{[\s\S]*\}` 匹配不到 → 走硬编码兜底判 0 分「解析失败」。

**决定性复现**（`tmp/mt_ctx/probe_eval_parse_big.py`，输入 ~24000 字符）：

| max_tokens | finish_reason | reasoning_tokens / completion | content 有闭合 `}` | 生产判据 |
|---|---|---|---|---|
| **1024**（改前口径） | **length** | 789 / 1024 | ❌ | **「解析失败」0/100** |
| 4096 | stop | 941 / 1233 | ✅ | 正常评分 |
| 8192 | stop | 502 / 814 | ✅ | 正常评分 |

**修法（三处，缺一不可）**：

1. **上限配置化且给足**：新增 `refine.eval_max_tokens`（默认 **3072**；标定依据 =
   实测 reasoning 峰值 941 + 正文 JSON ≈ 350 ≈ 1300，取 3072 留 >2x 余量）。
2. **解析改「完整优先、截断兜底」**：新增 `_parse_eval_json` —— 先试完整 JSON；
   失败则按字段**宽松抽取** `"score"` / `"passed"`（**抽到即认、抽不到返回 `{}`、绝不臆造分数**），
   并在 `issues` 里**如实标注"被截断"**（不静默）。
3. **成因不混**：`score` 未取到时按三种情形分开报 ——
   空内容 → 「评审无输出（max_tokens 可能被 reasoning 占满）」／
   `finish_reason=='length'` → 「解析失败（输出被 max_tokens 截断，未见 score 字段）」／
   其余 → 「解析失败」；并把 `finish_reason` 挂进 `_meta` 便于现场判读。

**回归断言**：`verify_orch_reliability.py` 新增 **[J] 组 12 条**（`J1~J10`，含端到端桩驱动）
+ **M4 变异自证**（把宽松抽取退回"只认完整 JSON" → J2 与 J5 必须翻，
且 M4b **复用 J5 的同一条判据函数** `_j5_ok`，不另写近似判据）。
