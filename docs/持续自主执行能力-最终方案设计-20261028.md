## 一、问题定性（承接诊断，一句话）

> 不是"没有循环"，是"**每个出口都写了 stop**"。
> 本工程有 ReAct 循环、有自主续跑评估器，但：完成度由 LLM 主观判定、
> 计划从未外化、失败没有恢复矩阵、预算耗尽即硬停 ——
> 于是模型一旦"觉得做完了"，系统没有任何机制说"还没完"。

官方原话（Claude Code best practices）：
> *"Claude stops when the work **looks** done… 'looks done' is all it has to go on."*

⇒ 解法不是"叮嘱模型别停"，而是**给它一个能跑的检查**，让它有别的东西可依据。

## 三、标杆依据（逐字核实，非转述）

| 官方表述 | 对本方案的作用 |
|---|---|
| *"Give Claude something it can run that comes back **pass or fail**"* | ⇒ P0-1 的全部设计依据 |
| *"Only mark as passing after **careful testing**"* | ⇒ todo 的 `completed` 必须有 `verify_result` |
| *"Maintain **single active task**"* | ⇒ 至多一个 `in_progress` |
| *"the turn doesn't end until the **typecheck passes**"*（`Stop` hook，由 harness 执行） | ⇒ P0-2 必须是 harness 层，不能靠提示 |
| *"Claude stops when the work **looks** done"* | ⇒ 问题定性 |
| 反模式 *"loop until done, don't be lazy"* → *"more likely to cause **over-work** than fix a stall"* | ⇒ P0-2 必须有次数上限 |
| 连续 **8** 次阻断后强制放行 | ⇒ P0-2 上限取值 |

**量化背书（MAST，arXiv:2503.13657）**：

| 失败模式 | 占比 |
|---|---|
| FM-1.5 **该停不停** | **12.4%** |
| FM-3.1 过早终止 | 6.20% |
| 验证缺失 | 8.20% |
| 验证错误 | 9.10% |
| FC3（验证类合计） | 23.5% |
| **加高层目标验证后的提升** | **+15.6%** |

⇒ **双向都要管**：只堵"早停"会加剧"停不下来"（12.4% > 6.20%），
这是 P0-2 必须带上限的原因。

## 四、设计内核（已实现并真跑通过）

### 4.1 模块定位

```
agent/auto_continue.py    ← 现有：评估器「说什么」（LLM 判定，有盲区）
agent/agent_todo.py       ← 新增：客观判据「是什么」（纯函数、零 IO、可单测）★本轮已实现
```

**分层理由**：`auto_continue.py` 管"评估器的结论"，`agent_todo.py` 管"**客观判据**"。
后者是前者的**上位约束** —— 评估器说 done，若 todo 里还有没验收的项，
`todo_gate` 直接强制 `done=False`，**不再需要评估器理解语义**。

这正是原文档 4.3.1 的核心实证所指向的解法：
> 3985 那类误判，**即使把「建议下一步执行校验」写进负面清单，评估器仍判完成** ——
> 因为它没有对照清单可查，只能凭语义猜"校验算不算用户的原始要求"。
> ⇒ 必须由 `todo_gate` 提供客观依据。

### 4.2 三块能力

**① todo 状态机**

```
pending ──→ in_progress ──→ completed
   │            │              │
   │            ↓              ↓
   └────────→ blocked ←────────┘（需说明原因）
   └────────→ deleted（撤销误建）→ 终态
```

两条硬约束（缺任一则 todo 表退化成"又一个勾选框"）：
1. 置 `completed` **必须**同时有 `verify`（验收方式）与 `verify_result`（验收回执）
2. 置 `blocked` **必须**说明阻塞原因（否则上层给不出可执行的恢复动作）

未知状态**抛异常**而非静默忽略 —— 我写错了不能变成"静默无效果"。

**② `todo_gate()`：验收驱动的完成判定**（P0-1 内核）

判定优先级（严格按序）：

| 情形 | 判定 |
|---|---|
| 无 todo（简单任务） | `fallback=True` ⇒ **退回 LLM 评估器旧路径**（逐字节兼容 98.4% 只读问答） |
| 有 todo 且全部 completed（每项有回执） | `done=True` |
| 有 todo 且存在未完成 | `done=False`，`next_step` = 第一个 pending 项 |

**关键区分**：「有 todo 但清单全被删」≠「没有 todo」。
前者是**未完成**，后者才走旧路径 —— 用 `has_todos` 参数显式区分，
避免"删光待办就变成自动完成"这个后门。

**③ `classify_obstacle()`：障碍分类**（P0-5 内核）

| 障碍类型 | 判据 | 恢复动作 | 允许问人？ |
|---|---|---|---|
| `transient` | 网络/超时/5xx/429 | 重试 | ❌ |
| `auth` | 401/403/STALE_READ/凭据失效 | **刷新凭据 → 重试一次** | ❌ |
| `not_found` | 404/包不存在/ID 无效 | **换路径**：list/search 先定位 | ❌ |
| `precondition` | 版本过期/父容器已变 | **重新取坐标 → 重放** | ❌ |
| `capability` | 工具不支持该操作 | **降级**：换等价工具或缩小范围 | ❌ |
| `user_only` | 信息只有用户有 | 问人 | ✅ **唯一合法停下** |

未识别错误 ⇒ **保守当 `transient`**（可重试），**不**当 `user_only` ——
误判成 user_only 正是要消灭的失败模式（可自解决却问人）。
