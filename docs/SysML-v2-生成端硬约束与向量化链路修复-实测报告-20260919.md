## 3. 新发现并修复：embedding 单批上限导致「语义匹配」静默退化成「词面匹配」

### 3.1 怎么发现的

P0 A/B 的 stdout 开头有两行：

```
embedding API 调用失败，降级 bigram: Client error '400 Bad Request' for url
 'https://...maas.aliyuncs.com/compatible-mode/v1/embeddings'
```

检索本身是成功的，所以这 400 来自别的调用。用 `probe_embed_callsite.py`
（包一层 `Embedder._embed_api`，记录**每次调用的条数与调用栈**）跑一次真实会话，抓到：

```
#   条数  结果      调用点
1    19   !! 降级   embedder.py:122 <- semantic.py:87 <- semantic.py:70 <- semantic.py:128
                  <- agent/pipeline_parts/context.py:104 <- execute.py:103
```

> 注：上面的行号是**修复前**那棵树的。修复后 `_embed_api` 里插入了切分器，
> 同一调用点变成 `embedder.py:140` / `semantic.py:91`（§3.6 的重跑日志用的是新行号）。
> **行号会随补丁位移，别拿它当跨版本定位依据** —— 认函数名 `_rank_dense` / `_embed_api`。

### 3.2 根因

`semantic.py::_rank_dense` 把「**所有 items + query**」塞进一次
`embed_with_version(texts, batch_size=0)`（`batch_size=0` = 一次全发）：

```python
texts = [t for _, t in pairs] + [query]
vecs, version = ed.embed_with_version(texts, batch_size=0)   # semantic.py:87
```

而服务端对单次 `input` 有硬上限，实测（`probe_embed400.py` 直接打 HTTP）：

```
12 条 → HTTP 400  {"error":{"message":"<400> InternalError.Algo.InvalidParameter:
        Value error, batch size is invalid, it should not be larger than 10.: input.contents"}}
```

`Embedder.embed()` 的 `except` 把异常吞成 `logger.warning` 后**返回 bigram 降级**，
`_rank_dense` 拿到 `version == "bigram-tf"` 就 `return None` → `rank()` 走词法 bigram。
**"语义匹配"于是悄悄变成"词面匹配"，全程无报错。**

**暴露点不止一处**（都经 `semantic.py:87`，规模随库增长而放大）：

| 调用点 | 一次发送条数（本机实测） | 是否触发 |
|---|---|---|
| `agent/pipeline_parts/context.py:104`（流程匹配语义精排） | **19 + 1 = 20** | ✅ 触发 |
| `agent/intent.py:305`（意图语义兜底路由） | **20 agents + 1 = 21** | ✅ 触发（`forced_intent` 时跳过） |
| `agent/pipeline_parts/tools.py:196`（工具 JIT 预筛） | 6 | 未触发（但已贴边） |
| `agent/pipeline_parts/skills.py:69/87`（技能/团队语义匹配） | 10 | 未触发（**正好压线**） |
| `agent/pipeline_parts/orchestration.py:423`、`agent/rag.py:472` | 随候选数 | 潜在 |

### 3.3 修法（在 embedder 层兜底，护住所有调用方）

| 文件 | 变更 |
|---|---|
| `knowledge_pipeline/embedder.py` | `_embed_api` 拆为 `_embed_api`（内部按 `api_batch_max` **切分**、顺序不变）+ `_embed_api_once`（原来那段）；新增 `_api_batch_max()` |
| `core/config.py` | 新增 `embedding.api_batch_max`（默认 **10**，`<=0` = 不切分），DEFAULT_CONFIG + CONFIG_SCHEMA 同步 |
| `semantic.py` | `_rank_dense` 处补注释，说明"一次全发"依赖 embedder 层切分，禁止在此处"优化掉" |

**为什么修在 embedder 层而不是 `semantic.py`**：这一层是所有调用方的必经之路，
一次修复同时覆盖 intent / tools / skills / orchestration / rag，
也保护未来任何传 `batch_size=0` 的新调用方。

> 实现时踩了一个自己的坑：`int(v or 10)` 会把「`0` = 不切分」吃掉（0 是 falsy），
> 导致我的 A/B 开关失效、"修复前"那列其实也在切分。已改为显式 `if v is None: return 10`。

### 7.2 对账踩的坑（写给下一个做同类对账的人）

- **索引行有三种写法**：`` `name.md` ``、`` `docs/name.md` ``、`` `../AGENTS.md` ``。
  按**全名**比对会把 `docs/代码优化方案-20260917.md` 误判成"幽灵条目"（文件明明在 `docs/` 顶层）
  → **必须归一化到 basename**。我第一次就是这么误报的。
- **判"是否一致"要用计数断言而不是肉眼看**：README 表格 66 行，
  用脚本 `os.path.getsize` 逐行对拍，输出 `66 行 / 0 不一致` 才算过（§5 同源：工具返回值也是"自述"）。

> ⚠️ 注意 `verify_run3_numbers.py` 里的期望值是**本文写作时点的快照**。
> 若之后又删/加了文档，脚本会如实报 `!! 不一致` —— **那是它在正常工作**，
> 此时要么更新期望值，要么确认是新的变更，**不要让脚本替你决定哪个数对**。
