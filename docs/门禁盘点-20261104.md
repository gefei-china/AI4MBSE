# 门禁盘点（2026-11-04）

> 触发：米爸问「为啥系统老出问题，不能从设计-开发-测试形成闭环吗」→ 上一轮补了「最终正文形态契约」门禁后，提出做一次门禁健康盘点，让"CI 绿灯"重新变得可信。
>
> **一句话结论**：这个工程不缺门禁（381 个脚本、193 个写进 CI），缺的是**"门禁真的跑过"这件事的可验证性**。CI 已连续一个月全红，而因为 GitHub Actions 遇错即停，**90% 的门禁在这一个月里一次都没执行过**。所有人（包括我）都以为它们在守。

## 1. 五个硬事实（都可复核，不靠推断）

### 事实 1：CI 最后一次绿是 2026-10-04 15:47

| 项 | 数据 | 来源 |
|---|---|---|
| 总 run 数 | 43 | GitHub Actions API `/actions/runs` |
| 成功数 | **8**（全部在 10-04 及之前） | 同上 |
| 失败数 | **35**（连续） | 同上 |
| master 最后一次成功 | **#18 · 2026-10-04 15:47** | 同上 |

| PR 分支 `eval/eval-baseline-wiring` | 10 次 **全部 failure** | 同上 |

⇒ 从 10-04 到今天（11-04），**整整一个月，主分支没有一次绿灯**。

### 事实 2：CI 只跑了前 11 步，后面全部 skipped

| run | 分支 | 总步数 | 成功 | 失败 | **跳过** | 失败步骤 |
|---|---|---|---|---|---|---|
| #33 | master | 187 | 11 | 1 | **175** | 第 10 步 · `Guard context_window 守卫` |
| #43 | PR | 208 | 10 | 1 | **197** | 第 9 步 · `Guard S4 调用契约` |

GitHub Actions 的默认语义：**某个 step 失败 ⇒ 后续 step 全部 skipped**。
ci.yml 把 193 个门禁写成 193 个独立 step ⇒ **第一个红门禁把后面全部挡掉**。

⇒ `ci.yml` 里写着 193 条 `python tools/verify/xxx.py`，**实际每次只可能执行到前 8~11 条**。
「接线」列表看起来极完整，覆盖率实际接近 5%。

### 事实 3：`continue-on-error` 一个都没有

207 个 step 里 `continue-on-error` = **0**、`if: always()` = **0**。
⇒ 没有任何"失败也继续"的兜底，上述中止是必然，不是偶发。

### 事实 4：本地全量跑一遍，52 红 / 3 超时（193 个）

| 状态 | 数量 |
|---|---|
| PASS | 138 |
| FAIL | 52 |
| TIMEOUT | 3 |
| **串行总耗时** | **28.0 分钟** |

⇒ 也解释了为什么 CI 47 秒就结束：**它根本没跑这些**（193 个门禁串行需要 28 分钟）。

### 事实 5：元门禁自己也在红，而且从没执行过

`verify_gate_wiring`（管"每个门禁要么进 CI、要么写豁免"）当前判红：

## 2. 根因链（为什么"有门禁"却"没有防护"）

```
① 判据面选错        元门禁数的是「ci.yml 里有没有这行」，不是「跑过没」
                    ⇒ 它一直是绿的（写在里面就算接线）
② 执行链断裂        193 个独立 step + 失败即停 ⇒ 第一个红门禁吞掉后面 175~197 个
③ 红灯不可见        因为②，红灯只暴露第 9/10 步那一个，其余 50 个红从未被看见
④ 归因不落地        2026-10-05 做过一次「20 个红灯逐项归因」，修完 5 个、列了 15 个，
                    但没有变成常设机制 ⇒ 一个月后再次积累
⑤ 夹具自行其是      62 个门禁自带 CREATE TABLE，只有 5 个用统一夹具助手
                    ⇒ schema 一加列，夹具就漂移 ⇒ 假红（把门禁问题当产品缺陷修）
```

**最隐蔽的是 ①**：一个判据面选错的元门禁，比没有元门禁更糟——
它提供"已经有人管了"的错觉。

## 3. 这次盘点做了什么（不是只出报告）

### 3.1 让"跑没跑"变成可断言的事：`if: ${{ !cancelled() }}`

ci.yml 的每个门禁 step 加 `if: ${{ !cancelled() }}` ⇒ **无论前面成败都执行**。
这是本轮最关键的改动：它不修任何门禁，但把"红灯"从 1 个变回 52 个——
**看不见的红灯，等于没有红灯**。

### 3.2 已知红必须记账，不能"搬走换绿"：`tools/gates_manifest.json`

321 个门禁逐个分层（依据：真库 + 干净库双环境实测，见 §4）：

| tier | 含义 | 处理 |
|---|---|---|
| `pr` | 干净库绿 + 单条 ≤15s | 每次 push/PR 必跑，**必须绿** |
| `nightly` | 干净库绿但慢（>15s） | 夜间/手动 |
| `local` | 需真实服务/LLM/真库金标 | 开发机跑，必须写理由 |
| `broken` | **两库都红** | 显式记账（带失败签名），不进 pr，`continue-on-error` 容错 |
| `backlog` | 从未接线 | 待评估，必须写理由 |

`broken` / `backlog` 的数量写进 `budget`，**只降不升**。
把红门禁挪出 CI 换绿灯是最容易也最坏的作弊；账要记下来。

### 3.3 元门禁：`tools/verify/verify_gate_manifest.py`

它守的不是"有没有写进 yml"，而是四件更硬的事：

| 判据 | 防的是什么 |
|---|---|
| G2 每个 script 文件存在 | 清单里写幽灵条目 |
| G3b 非 pr 层必须写理由 | 随手排除 |
| G5 每个门禁都被分类 | 漏网 |
| **G6a 清单 pr 层 ⊆ ci.yml 执行行** | 清单说该跑、CI 没跑 |
| **G6b `continue-on-error` 步数 ≤ `budget.tolerated_steps`** | 用容错静默吞红 |
| G7 pr 层非空 | 一键全降级 |
| G8 pr 层不含外部依赖 | 把需要服务的塞进 pr，让 CI 恒红 |
| **G9 broken/backlog ≤ budget** | 债务膨胀 |

并带 5 组变异自证（删条目 / 改 local 无理由 / 加幽灵文件 / 清空 pr / 债务越界），
每组都必须被判红 —— 判据本身也要能被击穿，否则就是空转。

### 3.4 清账：修掉的与记账的

见 §4。

### 4.1 证据确凿、可直接修的 5 处（本轮**不改**，等米爸拍板）

盘点中遇到 5 处证据完整、修法明确的问题。**都没有动**——它们是产品行为变更，
不该在"盘点"里顺手改（本仓纪律：改用户可见行为前先问）。

| # | 门禁 | 问题 | 建议修法 | 副作用 |
|---|---|---|---|---|
| 1 | `verify_s4_calls` | `rerank_max_candidates=25 > top_k=20`，而 `hits` 在重排前已被 `scored[:top_k]` 截断 ⇒ **该上限永远不可达**（配置注释自己写着"应 ≤ top_k，否则形同虚设"） | `core/config.py` 默认值 25 → 20 | 默认路径行为不变；仅当 API 调用方传 `top_k>25` 时重排窗口 25→20（`inject_k=5`，影响可忽略） |

| 5 | `verify_event_type_split` / `verify_reasoning_kind` | `reasoning` 站点仍有 **54 处** `kind=progress` 残留（拆型不彻底） | 按两门禁给的行号逐处改 | 影响流式事件类型（前端消费方需同步） |

前 2 处我可以立刻改并回归；后 3 处涉及能力/部署决策，建议单独一轮。

### 4.2 顺带发现的四个结构性问题

| 问题 | 证据 | 后果 |
|---|---|---|
| **门禁互相污染** | 有门禁把报告写进仓库（`verify_s4_calls_report.txt`）⇒ `verify_sandbox` 报"工作树在评估期间被修改" | 洁净类判据随机红 |
| **「工作区洁净」判据过宽** | 该步原本 `git status` 有任何输出就红，但门禁**本来就会写报告** ⇒ 该步恒红（CI 长期全红的成因之一） | CI 必红 |
| **共用库锁竞争** | 120 个门禁串行共用一份库 ⇒ `database is locked`（`verify_memory_conflict_gate` 首跑 PASS、二跑 FAIL、隔离后 PASS） | 随机红，最容易被误当缺陷 |
| **ci.yml 重复步骤** | 9 个脚本被引用多次（`verify_layering` 在主 job 出现 2 次＝两种模式） | 耗时翻倍 + 债务计数失真 |

处置：
- 执行器增 `--isolate-db`（每个门禁独立库副本，从同一基准状态出发）；但**不作默认**——
  `verify_curriculum` 这类"断言真库零写入"的门禁在隔离后前提不成立，隔离只作定位工具。
- 「工作区洁净」判据改为：只拦**源码类**改动，忽略 `tmp/`、`outputs/`、`docs/评测/`、`*_report.txt`、`*.log`。
  它真正要守的是**变异体残留**（门禁变异自证被强杀会把产品源码留在变异态），不是门禁产物。

## 7. 为什么这次不会又烂掉（与上次归因的区别）

2026-10-05 那次归因做得很扎实（20 个逐项定性、修了 5 个、列了 15 个），
但**没有留下任何"会自己叫的机制"**，所以一个月后就积累到 52 个。

这次的四道闸：

| 闸 | 拦什么 | 失效时会怎样 |
|---|---|---|
| `if: !cancelled()` | 首个红灯吞掉后面全部 | 不可能——它是 YAML 语义，不依赖人 |
| 元门禁 G5 | 新门禁写了没分类 | 判红（M1 已证明能抓住） |
| 元门禁 G9 + budget | 把红门禁搬走换绿 | 判红（M5 已证明） |
| 元门禁 G6b | 用 `continue-on-error` 静默吞红 | 判红（超出预算即红） |

另外 `broken` / `backlog` 的每一条都带**失败签名与理由**，
`gate_runner --tier broken` 随时可复现——债务是可见的，不是消失了。

## 9. 一句话给米爸

**这个系统的闭环不是缺在"没有测试"，而是缺在"测试有没有跑"这件事无人验证。**

CI 是 9-20 建的，前半个月还是绿的（#14~#18 连续成功）。
从 10-04 之后的一个月里 **35 次连续失败，而没人知道**——因为红在第一屏就被吞掉了。

今天补的不是 52 个门禁，而是**让"没跑"和"跑了但红"都能被看见**的那道闸。
