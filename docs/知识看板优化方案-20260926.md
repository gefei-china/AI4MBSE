# 知识看板优化方案

> 版本：v1.0 ｜ 日期：2026-09-26 ｜ 状态：待评审
> 对象：知识中心 › **数据看板**（`#pg-kb` › `#kb-a`，前端 `static/js/mods/15-kb.js`）
> 依据：① 甲方技术要求书 `XW-W-1AJB003`（★ 强制项）② 产品 PRD v1.0 §2.2 量化目标 + §3.1 产品定位 ③ 行业标杆调研（Neo4j Enterprise Studio / Collibra Data Catalog / Atlan / Google Cloud Knowledge Catalog / KG 生产运维指标体系）
> 方法：**先实测取证再出方案**——本次现状数字均来自 2026-09-26 对本机 `127.0.0.1:8000` 真实渲染页面的抓取（Playwright，非源码推断），复现命令见 §8。

## 0. 结论先行

**一句话**：当前看板是一条**面板堆叠列表**（9 个 `panel` 纵向串），不是仪表盘；它最大的问题不是"缺图"，而是**三件事**——**同一屏三套口径互相打架**、**关键治理水位一个都没有**、**有一半指标不能指导任何动作**。

| # | 结论 | 严重度 |
|---|---|---|
| **C1** | **口径漂移（同屏数字打架）**：同一次渲染中「已评审元素 61」与生命周期「已评审(未发布)122 + 已发布 61」、「关系总数 83」与总览「关系 249」、「已废弃 2」与「已废弃 6」**同时出现**。根因是 `stats` 带分支过滤、`overview`/`lifecycle` 走全局原生 SQL，**两套口径并存且界面未标注**。 | ★★★ P0 |
| **C2** | **看板不承载治理闭环**：甲方 FR-UI-6 要求"看板编辑 → 变更申请 → 评审 → 合并"，但看板上**没有任何一项**变更/评审水位（无待我评审、无平均评审时长、无闸门状态）。 | ★★★ P0 |
| **C3** | **红线指标缺位**：甲方 FR-KG-15 的「未评审数据不得进 release」是本系统最核心的治理红线，看板无从观测；同时 `chunk 链接率 0/5758＝未链接 100%` 这条"追溯链在数据上未跑通"的硬事实，被混在一段说明文字里，**没有升级为告警**。 | ★★★ P0 |
| **C4** | **指标失效（有值无用）**：类型覆盖率显示 93%（26/28），空类型只剩「系统元素/需求」——分母用"全部实体类型 28"，与 PRD 认可的 SysML v2 元素类型口径（7/22 → ≥18/22）**不是一回事**；指标已饱和，丧失指导增量抽取的区分度。 | ★★ P1 |
| **C5** | **fallback 主题词被内部提示词污染**：实测 TOP 里 `禁止虚构 50 / 交付规范 48 / 团队目标 48 / 任务上下文快照 47` 全是系统提示词与内部上下文片段，`sysml 553 / v2 264 / bdd 81` 是通用词。**知识缺口分析被噪声淹没**。 | ★★ P1 |
| **C6** | **双引擎面板把"快与准"讲反了**：纯向量 65.2% 的请求走的是**平均置信 0（未记录）· 3895ms** 的路线；混合路线 7052ms 置信仅 0.555；最快的纯图路线 166ms 置信 0.849。看板只摊裸值，**没有目标线、没有 SLO/分位**，读者会误判向量是主力路线。 | ★★ P1 |
| **C7** | **约 1/3 面板是"常量空洞"**：「图数据库」面板实测整块显示"未启用"；三个待评审队列同屏全部"暂无待评审"，占掉一个大面板却零信息。 | ★★ P1 |
| **C8** | **视觉与既有设计层次不足**：首页 4 个 `.kpi` 卡与总览 4 个 `.asset` 卡**形式与信息双重重复**；生命周期用 `flex:1` 等宽色块，**0 值仍占 1/5 宽度**导致比例失真；面板标题行挂着 `FR-KG-8/11` 这类**内部编号**（对外演示零价值）却与标题同权重。 | ★ P2 |

**优化主轴（一句话）**：把看板从「知识图谱内容统计页」升级为 **「建模→入库→审核→发布→追溯」全链路治理态势仪表盘**，用**一个聚合端点 + 一套指标六要素 + 三色阈值**收口，并把每一项指标都能点进下钻视图。

## 1. 现状盘点（实测取证）

### 1.1 信息架构现状：9 个面板纵向堆叠

```
知识中心 › 📊 数据看板（#kb-a）  ← 页内首个 Tab，默认落点
├─ ① KPI 行（4×.kpi）        已评审 / 候选 / 关系总数 / 已废弃     ← /api/knowledge/stats?branch=
├─ ② 知识库总览               4×.asset KPI + 三列待评审队列 + 来源分布 + 图谱缩略   ← /api/knowledge/overview
├─ ③ 数据生命周期             5 段等宽色块 + 来源/类别/发布记录      ← /api/knowledge/lifecycle
├─ ④ 知识完整度               1 条全宽进度条 + 空类型 + fallback 主题 ← /api/knowledge/coverage
├─ ⑤ 知识引擎双引擎消费       累计查询 + 三条路由卡 + 最近查询        ← /api/knowledge/engine-stats
├─ ⑥ 图数据库                 状态 + SPARQL 输入框 + 结果表          ← /api/graph-db/*
├─ ⑦ 命中预览（分块检索）     检索框 + 命中卡片                      ← /api/knowledge/chunks/search
├─ ⑧ 向量→图谱转化（半自动）  抽取候选 / 确认入库 / 候选列表          ← /api/knowledge/v2g/*
└─ ⑨ 知识实体浏览             筛选 + 表格 + 分页                     ← /api/knowledge/entities
```

**问题**：⑤ 才是"知识资产被 AI 消费得怎么样"的**最关键证据**，却掉到第二屏；⑥⑦⑧ 是**作业动作**（查询、抽取、确认入库），不是**态势观测**，却和 KPI 混在同一层。看板没有"簇"、没有"下钻"、没有时间窗。

### 1.3 视觉与交互现状（截图取证）

以 2026-09-26 `kb_a_full.png`（1680×1050，full_page）为地面真相：

1. **首屏信息密度错配**：首屏只装下 ①②③④；⑤双引擎（最关键）在第二屏。
2. **双重重复**：① 的 `.kpi` 行与 ② 的 `.asset` 行是**两排几乎一样的数字卡**，视觉上像"同一件事说了两遍"。
3. **比例失真**：③ 的 5 段色块 `flex:1` 等宽，`0 原始切片 0%` 占的宽度与 `122 已评审 65%` 完全相同。
4. **图表缺失**：全页**零趋势图、零环形/占比图、零矩阵**；唯一的进度条（④）孤零零横跨整幅宽度。
5. **标题行权重失衡**：`.ph` 内 `badge`（`FR-KG-8/11`）与 `tag`（长中文说明）与标题同排同权，**内部需求编号出现在演示界面上**。
6. **大面积空白**：② 的中段（三列待评审全空）+ ⑥（未启用）合计约 1/3 纵向空间零信息。

### 2.2 产品 PRD v1.0

**§3.1 产品定位**（原文）："面向复杂装备研制团队（航天、航空、汽车等）的 **MBSE 知识图谱构建平台**，以 AI 建模为入口，以知识图谱为统一数据底座，以本体管理为 schema 约束，以分支审核为治理手段，覆盖**建模→入库→审核→发布→追溯**全链路。"

→ **推论**：看板的定位应是**这条全链路的态势仪表盘**，主指标必须**按链路分段**（建模产出 / 入库候选 / 审核积压 / 发布水位 / 追溯覆盖），而不是按"图谱内容类型"分段（实体/关系/文档）。

**§2.2 量化目标**：5 条目标中，**4 条当前看板无法观测**——

| PRD 量化目标 | 目标值 | 看板当前可观测性 | 应落位置 |
|---|---|---|---|
| AI 建模入库审核率 | 0% → **100%** | ❌ 来源分布分不出 `ai_model`（C5） | 治理总览 · 链路分段 |
| 中英文实体互认率 | ~30% → **≥90%** | ❌ 无别名覆盖率指标 | 数据质量簇 |
| 本体类型覆盖率 | 7/22 → **≥18/22** | ⚠️ 有 93%，但口径不符（C4） | 数据质量簇（改口径） |
| 标注审核流程完整度 | 五区显式可见 | ✅ 基本达标（页面外） | 治理总览 · 闭环态势 |
| 实体消歧准确率 | 未量化 → **≥85%** | ❌ 无指标（`entity_dup_candidates` 0 行） | 数据质量簇 |

## 3. 产品定位对齐（看板为谁而设）

| 角色 | 场景 | 看板要回答的问题 | 对应视角 |
|---|---|---|---|
| **知识工程师** | 每天开工 | 我今天该审什么、该补什么？积压涨了还是降了？ | **作业视角**（待办驱动） |
| **评审人 / 管理员** | 变更评审 | 闸门是否会被拦？有没有未评审数据在往 release 走？ | **治理视角**（红线驱动） |
| **项目管理者 / 甲方验收** | 阶段汇报 | 5 条量化目标各自到哪了？达标线在哪？ | **验收视角**（目标线驱动） |

→ 结论：看板需要**双视角切换**（作业 / 治理），且**验收视角**要把甲方 7.1 的 6 项 + PRD §2.2 的 5 项**同屏集中**，因为它就是验收现场要投屏的那一页。

## 4. 行业标杆调研与对标

### 4.1 指标体系（KG / 数据治理生产环境通用做法）

| 标杆做法 | 来源 | 本系统对应 | 现状 |

| **validation failure rate**（SHACL 拒收率） | 同上 | `governance.py` 已实现 `shacl_violations`（近 7 天） | ✅ 后端有，**看板未上** |
| **duplicate candidate queue depth**（消歧队列深度） | 同上 | `entity_dup_candidates` / `v2g_candidates` | ⚠️ 未上板 |
| **staleness**（陈旧度） | 同上 | 无（实体无 updated 时效指标） | ❌ 缺 |
| **attribute completeness**（属性完整度） | 同上 | 无 | ❌ 缺 |
| **ontology version drift**（本体版本漂移） | 同上 | `ontology_snapshots` 0 行 | ❌ 缺 |
| **分层看板**：executive（信任/业务影响）→ ops（管道健康/入图滞后/慢查询）→ on-call（告警/owner map）+ SLO/error budget | KG 运维框架 | 本系统无分层，全部平铺 | ❌ 缺分层 |
| **健康度 = 值 + 状态色 + 阈值** 三件套 | 通用 | `governance.py::_status(value, ok, warn)` **已实现** | ✅ 可直接复用 |

### 4.2 产品形态对标

| 标杆产品 | 关键形态 | 可对标项 | 本系统差距 |
|---|---|---|---|
| **Neo4j Enterprise Studio** | Query（查询调试）+ **Bloom**（零代码图探索，**Perspective＝可共享的"视觉语言"**，按角色授权）+ **Dashboards**（表格/图/柱/线/地图，可分享、可从 Query 直接投到 Dashboard） | 看板 → 下钻到图探索的**联动**；口径/视图**可配置可共享** | 无下钻；看板无视图/口径配置 |
| **Collibra Data Catalog** | **Catalog Home**（landing，快速发现）+ **Metrics 页**（资产使用统计）+ Data Profiling charts + Data Classification dashboard + Lineage | "发现入口 + 使用统计 + 剖析图 + 分类仪表盘"四件套 | 只有"统计"，无发现入口/使用统计 |

| **Google Cloud Knowledge Catalog** | 四件套：Knowledge Graph（元数据图）+ Enrichment Engine（自动打标/实体抽取/词表生成）+ Business Semantics（统一词表/verified queries 语义护栏）+ **Governance Engine**（策略质量检查/异常检测/血缘） | 正对应本系统「图谱 + 抽取 + 术语词典 + 门禁」；看板应给**四件套各一块健康度** | 四件套齐全，但看板未按此分簇 |

**对标结论**：成熟产品的一致范式是 **「首屏=信任与采用（水位+红线+目标线） → 分簇健康度（值+状态色+阈值） → 逐项下钻到作业面」**。本系统恰好**后端能力齐全（`governance.py` 六项健康指标已实现且带阈值），缺的是看板这一层收口**——这是本次优化投入产出比最高的判断。

## 5. 优化方案

### 5.1 信息架构重构：从「面板列表」到「1 顶栏 + 3 簇 + 下钻」

```
知识中心 › 📊 知识看板（#kb-a）
┌───────────────────────────────────────────────────────────────────────────┐
│ 顶栏（吸顶，16px 高密度单行）                                                │
│ 角色视角[作业|治理|验收] · 工程/分支 · 时间窗[近7天|近30天|全部] · ⟳刷新      │
├───────────────────────────────────────────────────────────────────────────┤
│ 首屏 · 健康分与红线（4 张卡 + 1 条红线横条）                                  │
│ ┌─────────┬─────────┬─────────┬─────────┐                                 │
│ │ 知识健康分│ 待审积压 │ 发布水位  │ 追溯覆盖 │   ← 值 + 目标线 + sparkline    │
│ │  76/100 │  0 条    │ 61 条    │ 0.0%   │                                 │
│ │ ▂▃▅▅▆  │ ● ok    │ ● ok    │ ● alert │                                 │
│ └─────────┴─────────┴─────────┴─────────┘                                 │
```

* **簇1 治理总览**（作业视角默认）：链路五段漏斗（建模产出 → 入库候选 → 审核中 → 已发布 → 已废弃）+ 三列待评审队列（**空态收成一行**）+ 变更闭环态势（我的变更 / 待我评审 / 平均评审时长 / 驳回率）+ 来源分布（**按 `ai_model`/`doc_extract`/`manual` 三分**）。
* **簇2 数据质量**：类型覆盖率（**改口径**）+ chunk 追溯覆盖率 + 别名覆盖率 + 消歧队列深度/准确率 + 孤立节点率 + SHACL 拒收率 + 属性完整度 + 陈旧度 —— **一律「值 + 状态色 + 阈值 + 下钻」**，复用 `governance.py::_status`。
* **簇3 消费与性能**：双引擎路由分布（**叠目标线**）+ RT 分位（p50/p95）+ 慢查询 TOP + 知识获取 P/R/F1（读 `eval_reports`）+ 服务健康探活 + 审计活跃度。
* **簇4 验收对照**：甲方 7.1(a~g) 六项 + PRD §2.2 五项，**同屏一张表**：`指标 | 目标 | 实测 | 判定 | 证据/复现命令`。
* **下钻**：每个数字/色块可点 → `go('kb','kb-b'|'kb-d'|'kb-e')` 并**带筛选参数**（状态/类型/时间窗），落到治理中心/图谱/文档库的对应视图。
* **移出/降级**：⑥ 图数据库（未启用时收成顶栏一个状态点，不占面板）、⑦ 命中预览、⑧ v2g 转化、⑨ 实体浏览 → 属**作业动作**，移入治理中心/文档库；看板只保留"入口 + 计数"。

## 7. 风险与边界

| 风险 | 对策 |
|---|---|

### 9.4 P0 期间发现并修复的新缺陷（暗色可读性）

**现象**：暗色下「治理红线」三行的指标名与数值不可读（白底浅字）。
**取证**：元素级截图 + 计算样式 + WCAG 对比度 —— `color=rgb(229,233,240)` on `bg=#fff` → **1.22:1**（正文阈值 4.5:1）。
**根因**：`--blue-l/--line/--mut/--blue-d` **不随主题翻转**、`.panel` 暗色下**仍是白底**；而**正文继承色会翻转**为浅色 → 面板内"裸文本"（未显式指定颜色）必然白底浅字。
**修复**：面板内文本一律显式使用**不翻转的 token**（`--mut` / `--blue-d`）或自带颜色的类（`.tag` / `.l` / `.n` / `.st`）——与本仓既有面板同口径。
**护栏**：`kb_ui_check_kb_dashboard.py` 步骤 [11] 在暗色下实测新增区块全部文本对比度（现 48 个节点全部 ≥4.5:1，红线行 9.84:1），低于阈值即失败。

> 影响面提示：本仓仍有其它位置使用「裸文本 + 继承色」的写法（例如工作台 `.todo-item` 的 `<span>`）。本次只修了本方案新增的区块，**未动既有页面**（避免越界）；建议作为独立小任务按同一口径清扫。

## 11. 图谱数据分支口径核查 + UX 优化（2026-09-27）

### 11.1 结论先行：图谱数据只应按分支统计，"全局行数"是错的

**提问**：图谱数据是按分支统计还是全局统计？
**结论**：**必须按分支**；此前看板上的"全局"口径是**跨分支行数累加**，会把知识量虚报 3 倍。

实测证据（`entities` 主键是 `(id, branch)`）：

| 口径 | 实体 | 关系 | 说明 |
|---|---|---|---|
| 跨分支行数（旧"全局"口径） | **183** | **249** | 同一逻辑对象在 dev/release/personal **各存一行** |
| 跨分支去重（**知识总量**） | **61** | **83** | 实体按 `id`、关系按 `(source_id, relation_type, target_id)` |
| 重复倍数 | 3.0× | 3.0× | 61 个逻辑实体恰好分布在 3 个分支 |

> "183 / 249" 既不是"知识总量"、也不属于任何分支 —— 它是行数累加，对外展示会误导。

   `documents`/`chunks`（真全局）、`entities_dedup`/`relations_dedup`（知识总量）、
   `entities_rows`/`relations_rows`（行数，仅供对账）。

3. `lifecycle` 补 `scope_note`：它是**跨分支行数口径**（同一实体在 release 记 published、
   在 dev/personal 记 reviewed），故 `total` 是行数不是实体数。
4. 前端第二处对照改为「**知识总量（跨分支去重）**」并带对账 tooltip。

### 11.12 统计指标「计算说明」（2026-09-27，已做）

**需求**：说明页面哪些统计指标是真实计算结果、怎么算的；**默认不展示，提供 icon，hover 展示**。

**实现（说明与指标同源，前端不手写口径）**：

| 层 | 内容 |
|---|---|
| 后端 | 每个指标新增 `calc` 字段：**来源表/函数 → 过滤条件 → 公式 → 阈值**；未落地指标如实写明「未落地/未评测/未计算/无从评估」。**38 项全部登记**，未登记会落到显式兜底文案（不是静默留空） |
| 验收对照 | 每行 `calc` 说明「本行实测直接引用指标 X，口径完全一致」；无同源指标的行写明「属需专项压测/立项项，不是从库中算出来的值」 |
| 前端 | 指标卡 / 北极星卡 / 治理红线行 / 验收表实测列 均挂 `ⓘ`；hover（或键盘聚焦）弹出浮层 |

**三个实现要点**（都是踩过的坑）：
1. 浮层用 `position:fixed` 且挂到 `document.body` —— 若放在面板内会被滚动容器裁剪；
2. `ⓘ` 自带 `onclick="event.stopPropagation()"` —— 指标卡本身可点击下钻，点图标不应触发下钻；
3. 浮层用 `.panel` 类 + `--mut` 文字（不随主题翻转）—— 白底浮层在明暗两色下都可读。

**典型说明举例**：
- `type_coverage_sysml`：「分母＝sysml_ast.NODE_KINDS 归并的 14 类；分子＝有实例的类型数。⚠️ 不用
  ontology_types 的 entity 类型总数做分母，那里面有 25 个是领域业务类型，会把覆盖率撑成 93% 假绿」
- `eval_precision`：「eval_reports 的 precision/f1 列值 0.0 **是未计算**（评测脚本只算了召回），
  不是精确率为 0 → value=None，避免把未计算误读为极差」
- `alias_coverage`：「entity_aliases 当前 0 行 ⇒ 未落地，value=None（不报 0%，否则会被误读为"做得差"）」
- `slow_query_share`：「直接用计数相除，不先取整 rate 再乘 100（否则双重取整，280/471 显示 59.5% 而真值 59.4%）」

### 10.6 未落地指标的处理原则（本轮固化）

> **基础表为空 / 无评测集时，`value` 必须为 `null`（前端显示「—」、状态 `warn`），严禁报 0%。**

理由：0% 会被读成"做得差"，而事实是"这项能力还没跑起来"——**两者的处置动作完全不同**
（前者要整改质量，后者要先把能力落地）。同时 `save_snapshot` **只写有值的指标**，
避免把 `null` 当 0 画出假趋势。
