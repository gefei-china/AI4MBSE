## 1. 标杆调研（2026-09~2026 公开资料）

### 1.1 Anthropic《Effective Context Engineering for AI Agents》

| 要点 | 原文主张 | 对本仓的含义 |
|---|---|---|
| 上下文排序 | system 指令 → 记忆/知识 → 工具定义 → 对话历史 | ✅ 已符合（`messages=[system]+hist+[user]`） |
| **Compaction** | 到 **~70% 预算**就压缩，保留决策/未解问题/当前计划，丢弃探索痕迹与冗余工具输出 | ⚠️ 本仓触发线是 100% 才压，且压缩对主路径无效 |
| **结构化笔记** | 长任务维护 scratchpad（当前目标/已完成/关键发现/待解问题） | ❌ 缺（Manus 叫 `todo.md`） |
| **子 Agent 隔离** | 子任务干净上下文，返回 1000~2000 tok 摘要 | ✅ 已具备（Component Factory / 子任务） |
| JIT 检索 | 不预塞全量，只放轻量标识（路径/查询），运行时按需加载 | ✅ 语义拉回 + 工具 offload 已具备 |

> 关键论断（Claude-Mem 归纳）：**"10K 高信噪上下文优于 100K 含噪上下文"**；"context rot"（上下文腐烂）与 lost-in-the-middle 是能力上限问题，不是容量问题。

### 1.2 Manus《Context Engineering for AI Agents》（季逸超，2025-07）

| 法则 | 主张 | 本仓对照 |
|---|---|---|
| **KV-cache 为王** | 输入:输出 ≈ 100:1，**KV 命中率是生产第一指标**（缓存价差 10×）；前缀必须稳定（禁时间戳进 system）、严格 append-only | ❌ 缺：system 每轮注入检索/历史块 → **前缀每轮都变，KV 必然失效** |
| **Mask, don't remove** | 工具不全量给，用 logit 掩码禁用 | ⚠️ 本仓每轮动态组装 tools，未做掩码 |
| 文件系统即上下文 | 上下文只存路径/URL，实体在外部存储 | ✅ 已有 `tool_result_offloads` |
| **通过复述操控注意力** | 维护 `todo.md` 并反复重写，把全局计划顶到上下文末尾 | ❌ 缺 |
| **保留错误** | 错误与栈**留在上下文里**，让模型学到"别再犯" | ⚠️ 本仓压缩会吃掉部分诊断信息 |

### 1.3 LangChain《Context Management for Deep Agents》

| 机制 | 阈值（默认） | 本仓 |
|---|---|---|
| 大工具结果 offload | **> 20,000 token** | ✅ 已有（阈值不同） |
| 旧工具**输入** offload | 超阈值时把 write/edit 参数挪到文件 | ❌ 缺 |
| Summarization | 超阈值**且无可 offload 后**，总结历史 | ⚠️ 有五档压缩，但锚点错（见 §2） |
| 压缩后 | 保留原全量记录在库，摘要作为工作表示 | ✅ 符合（细节在 messages 表） |

### 1.4 Letta / MemGPT

三级内存模型，**最通用的可借鉴结构**：

| 层 | 语义 | 本仓对应 |
|---|---|---|
| Core memory（RAM） | 常驻、字符上限、**始终可见** | ✅ Agent 的 `system_prompt`（27 个，合计 46706 字符） |
| Archival（Disk） | 外部向量库，**必须显式检索**才进上下文 | ✅ `tool_result_offloads` + 知识库 |
| Recall | 全量历史，可搜索 | ⚠️ 有 messages 表但**无对话内检索工具** |

自动溢出：超限时 70% 消息递归摘要驱逐；另有 **sleep-time compute**（空闲期后台整理记忆）。

### 1.5 标杆共识（三家一致）

1. **上下文是有预算的资源，不是 transcript**（LangChain："responsibility 从模型移到 harness"）
2. **压缩要"结构化摘要"而非"叙事式摘要"**（决策 / 已做 / 未做 / 失败尝试 / 相关文件）
3. **原始记录与工作表示分离**（压缩后仍可回溯）
4. **先最大化 recall，再提 precision**（Claude-Mem：调优顺序）

## 2. 本仓实测诊断

### 2.1 真实会话上下文结构（conv=514，架构设计场景）

```
[0]  system   11,692 tok   ← Agent 定义本体（system 本体）
[1]  system      413 tok   【本会话既有产物】
[2]  system      326 tok   【相关历史片段（第 5 轮 · 助手，相关度 0.476）】
[3]  system      203 tok   【相关历史片段（第 3 轮 · 助手，相关度 0.459）】
...  user/assistant 交替（约 2,000 tok）
合计 13,692 tok   （总闸上限 10,000）
```

### 2.2 发现的 P0 缺陷：总闸静默失效

**实证**（`tools/verify/_probe_context_audit.py 514`）：

```
[context_total] 总闸触发：估算输入 13746 > 预算 10000，
               五档压缩档位 2/2，降档后 13746（裁掉 0 tok，messages=14 条）
```

**根因（三重叠加）**：

| # | 原因 | 位置 |
|---|---|---|
| 1 | 压缩器锚点只认 `【更早对话摘要】/【历史对话概览】`，而这两个块**只在旧三层窗口回退路径**产出（打标失败才走） | `compression.py` vs `history.py:760/764` |
| 2 | **主路径**产出的是 `【话题：…摘要】`/`【相关历史片段…】`/`【本会话既有产物】`，压缩器一个都不认 | `history.py:448/467`、`session_artifacts.py` |
| 3 | 主路径历史是**多条独立 system 消息**，而 `_apply_total_budget` **只裁 `messages[0]`** | `history.py:930-940` |

**后果**：生产里话题打标基本都成功 ⇒ **总闸 ≈ 恒空转**，只在日志留一行"裁掉 0 tok"。
直接违反本仓既定纪律：**"总闸若静默，等于没做"**。

### 2.3 大头定位：system 本体

| Agent | system_prompt | ≈token |
|---|---|---|
| 活动图生成 | 7981 字符 | **5956** |
| 参数视图生成 | 5458 字符 | 4110 |
| 需求视图生成 | 4811 字符 | 3403 |
| 状态机视图生成 | 4279 字符 | 3021 |
| **27 个 active 合计** | **46706 字符** | — |

⇒ 单个 Agent 的 system 本体就占掉超窗总量的 **85%+**。这是"最通用"的优化切口。

## 3. 本次已实施（P0，含门禁）

### 3.1 修复一：补齐压缩锚点 + 新增主路径块裁剪

`agent/pipeline_parts/compression.py`：

- 登记 3 个主路径块头常量（`HIST_TOPIC_PREFIX` / `HIST_FRAGMENT_PREFIX` / `ARTIFACT_HEADER`）
- `_NEXT_BLOCK_MARKERS` 补入这些块头（否则会把整段历史误算进上一块正文）
- 新增 `cut_history_main_path_blocks()`：逐块截断，**保留块头**（块头带"第 N 轮 · 相关度 0.476"是模型判断价值的唯一依据）
- `collapse_summary_block()` 扩展为同时折叠 `【话题：…摘要】` 块

### 3.2 修复二：档位重分配（关键）

**原设计的历史区截断挂在档 2**，而 conv=514 的 pressure=1.37 只进**档 1**
⇒ **最常见的超窗区间（100%~130%）恰好是总闸完全空转的区间**。

```
TIER_HIST_BLOCK_TOKENS = (900, 600, 400, 200)   # 档 1 起即生效，逐档收紧
```

### 3.3 修复三：总闸覆盖 `messages[1:]` 的历史 system 消息

`history._apply_total_budget`：逐条识别 `role=system` 且 `is_main_path_hist_block()` 为真的消息，
逐条走同一套档位动作。**只动历史块，`user`/`assistant` 永不裁**（保对话连续性与 tool_call 配对）。

## 4. 待实施方案（按优先级）

### P1-1 system 本体按需加载（**收益最大**）

**问题**：单 Agent system 本体 5956 tok，任何任务都整份下发。
**标杆做法**：Anthropic JIT retrieval / Manus 文件系统即上下文。
**方案（最通用、风险最低）**：把长 `system_prompt` 拆为
```
[基础段（必留，~800 tok）] + [按意图触发的技能段（工具调用时才注入）]
```
触发词复用现有 `intent_keywords` 与 Skill 机制，不引入新框架。

**收益估算**：5956 → ~1200 tok，超窗量下降 ~40%，**总闸从"必然触发"回到"极少触发"**。

### P1-2 上下文可观测（**没有它就无法持续优化**）

每轮落库一行 `context_audit`：各区 token（本体/检索/历史/工具）、档位、裁剪前后、耗时。
→ 配套 UI 展示，复用现有 `compact` 事件通道。

> 优先级理由：本轮 2 次"看起来绿但实际空转"全部因为**看不见**而延迟发现。

### P1-3 KV-cache 前缀稳定性

system 本体里禁插时间戳/动态检索结果；历史块统一追加到**尾部**。
预期：命中缓存后首 token 延迟与成本下降一个量级（Manus：10×）。

### P1-4 结构化摘要 schema

`context_summaries` 落库改固定字段：
```
目标 / 已完成 / 未完成 / 关键决策 / 失败尝试（保留）/ 相关文件
```
对齐 Anthropic "结构化而非叙事式"、"保留错误"。

### P2-1 全量历史检索工具（Recall memory）

给 Agent 一个 `conversation_search` 工具（复用现有 Embedder + 检索路由），
把"全量历史"从上下文搬到外部存储，按需取——Letta 模式。

### P2-2 修 `verify_token_budget.py` 的锚点漂移

**已确认该门禁在本次改动前就失败**（同一 `ValueError: substring not found`），
与 §2.2 同类：门禁/代码锚点不同步。需一并修正。

## 5. 经验沉淀（可复用）

1. **锚点漂移是本仓的头号复发缺陷**：压缩器裁 A 块、组装器产 B 块，总闸静默失效。
   ⇒ 必须有"从组装侧反向提取块名、比对压缩侧锚点"的门禁（已落地）。
2. **门禁样本必须含"生产的真实形态"**：首版样本混了旧块名，`[2]` 假绿。
   ⇒ 对照样本要**只含主路径块**。
3. **"总闸静默"的判据是日志里的 tok 数字**，不是"函数被调用了"。
   ⇒ 判据必须是"delta 出现负值"。
4. **先量出大头再动手**：如果大头是 system 本体（85%），裁历史区收益有限，
   优化方向应是**按需加载**而非更聪明的裁剪。
