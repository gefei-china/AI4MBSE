# 意图识别与匹配的缺陷分析与优化方案

> 2026-11-07 · 基于本工程真库实测 + 国内外三平台（Anthropic Claude Agent SDK / OpenAI Agents SDK / Dify）× 三条产品线对照
> 工程：`mbse_system`（FastAPI + 原生 JS）· 实测库 `mbse.db`

---

## 一、先给结论

**「每次都匹配到具体的 Agent」不是识别不准，是架构决定的必然结果。**

当前路由是**三层单标签分类器**，三层都在做同一件事：**在 22 个 active Agent 里选 1 个**。

| 层 | 实现位置 | 做什么 | 候选池 |
|---|---|---|---|
| 关键词层 | `intent.py::_db_kw_priority` | 按 `agents.intent_keywords` 打分取最高 | 22 |
| 语义层 | `intent.py::_semantic_*` + `semantic.py` | 按 `display_name+description+keywords` 算余弦取最高 | 22 |
| LLM 层 | `intent.py::detect_llm` + `llm_first` | 把 22 个名字+描述喂给 LLM，让它选 1 个（≥0.75 直接采纳） | 22 |

三层都是「22 选 1」⇒ **输出必然是"某个具体 Agent"**，不存在"这轮需要 3 个能力"或"这轮谁都不用"的表达能力。

**但这不是唯一的病根。** 实测发现更严重的一条：

> **这 22 个 Agent 之间并不互斥。** 路由是"互斥选择"问题，可候选池里塞了大量近义 Agent
> ⇒ 分类器再准也只能在一个**本身有歧义的标签集**上选。

---

## 二、实测证据（不是推理）

### 2.1 候选池实测：22 个 active，其中至少 6 个是近义/重复

| 域 | Agent | 问题 |
|---|---|---|
| 需求 | `requirement_analysis` / `requirement_quality` / `requirement_structuring` | **3 个**；关键词实测已互撞（`需求条目`/`条目化需求` 被 structuring 占用） |
| 建模方案 | `design`（disp=工程建模方案设计Agent）/ `工程建模方案设计Agent` | **display_name 完全相同、prompt 逐字相同**，是重复行 |
| 多方案 | `多方案设计`（main）/ `多方案生成`（sub） | 名称近义 |
| 平台操作 | `chat` / `knowledge_qa` | 两者描述都写了"操作指引/怎么用"⇒ 实测互抢 |

### 2.2 11 条路由用例实测：9 过 / 2 错，两个错都在 LLM 层

```
OK   design              ← rule_scored 0.95
OK   review              ← rule 0.95
OK   impact              ← rule_scored 0.95   （本轮修好，原判 knowledge_qa@0.8）
OK   report_generation   ← rule_scored 0.90
DIFF requirement_analysis → 实得 requirement_quality@0.86  (llm_first)
OK   knowledge_qa        ← explain 0.80
DIFF chat                 → 实得 knowledge_qa@0.62        (llm_first_weak)
OK   review              ← rule 0.95
OK   requirement_structuring ← rule_scored 0.95
OK   knowledge_qa        ← rule_scored 0.90
OK   requirement_quality ← rule 0.95
```

**关键观察**：两个 DIFF 都走 `llm_first`，即"确定性层拿不到强信号 → 交给 LLM 在 22 个里选"。
改 description 已经把确定性层从 6/9 提到 9/11，但**LLM 层选不动** —— 因为它面对的仍是 22 个近义标签。

两条错例的成因（复现原话）：

| 输入 | 实得 | 为什么 LLM 会这么选 |
|---|---|---|
| 「我有个需求描述得很模糊…这条需求怎么定？验收标准怎么写？」 | `requirement_quality` | LLM 看到"模糊"→ 关联到 quality 的"检测模糊词"。语义上**并非无理**，只是用户要的是"帮我生成"而非"帮我挑错" |
| 「这个平台怎么新建一个工程？在哪个菜单」 | `knowledge_qa` 0.62 | 两类都自称能"给操作指引"。0.62 属弱采纳，**已触发澄清**（这是现有机制唯一做对的地方） |

### 2.3 历史真实分布：33 个不同 intent 值，长尾明显

近 30 天 `tool_call_logs.intent` 分布（前 12）：

```
智源对接agent 1151 · view_expansion 664 · knowledge_qa 597 · design 499
requirement_analysis 430 · architecture_skeleton 429 · (空) 429
model_validation_repair 373 · chat 316 · review 296
requirement_structuring 188 · requirement_quality 152
```

⇒ 22 个 Agent 中头部 6 个吃掉大部分流量，尾部 Agent 极少命中。
**尾部 Agent 的存在不增加能力，只增加分类器的干扰项**（每多一个近义标签，top1 正确率就下降一点）。

## 三、三家平台的意图识别逻辑（对照）

### 3.1 Anthropic Claude Agent SDK —— **不做前置分类，用"模型自主委派"**

| 维度 | 做法 |
|---|---|
| 路由主体 | **主 Agent 自己决定**：通过 `Task`/`subagent` 机制，在 ReAct 循环里按需委派 |
| 前置分类器 | **没有**。没有"先把用户话分成 N 类"这一步 |
| 工具选择 | **Tool Search Tool**（2025-11 发布）：所有工具标 `defer_loading: true`，模型先**搜**再加载。实测上下文从 77K → 8.7K token（-85%），MCP 评测准确率 79.5% → 88.1% |
| 关键洞察 | "The most common failures are wrong tool selection and incorrect parameters, **especially when tools have similar names**"（官方原文）⇒ 他们的解法是**让模型按需搜**，而不是**让分类器预先选** |
| 子 Agent 上下文 | 每个 subagent 独立 context window，只把**结论**回传给 orchestrator（上下文隔离） |

**对本工程的启示**：`view_expansion`、`architecture_skeleton` 这类"细粒度执行 Agent"，在 Claude 的模型里根本不该是路由候选 —— 它们应该是主 Agent 手里的**工具**（`agent-as-tool`），由主 Agent 在执行中按需调用。

### 3.2 OpenAI Agents SDK —— **两种编排模式，明确分工**

| 模式 | 机制 | 适用 |
|---|---|---|
| **Agents as tools** | 主 Agent 把专家 Agent 当工具调（`Agent.as_tool()`），**主 Agent 保留最终答复权** | 需要一个 Agent 拥有最终答案、汇总多个专家输出、统一 guardrail |
| **Handoffs** | triage Agent 把控制权**移交**给专家，专家接管本轮剩余对话 | 路由本身是工作流的一部分，希望专家直接面对用户 |

官方明确的两条判据（原文）：

> "Use agents as tools when a specialist should help with a bounded subtask but should **not** take over the user-facing conversation."
> "Use handoffs when **routing itself is part of the workflow** and you want the chosen specialist to own the remainder of the current turn."

以及一条反面警告：

> "Manager must understand all sub-agent capabilities, **doesn't scale well beyond 3-5 sub-agents**"

**对本工程的启示**：22 个候选已远超"3-5 个子 Agent"的适用上限。这解释了为什么"LLM 在 22 个里选"效果差 —— 不是模型不行，是**超出了这个模式的适用范围**。

### 3.3 Dify / Coze —— **分层漏斗 + 结构化输出，但路由目标是"分支"不是"人"**

| 层 | 做法 |
|---|---|
| 第 1 层 规则优先 | 关键词/正则快速拦截高频意图（快、零成本） |
| 第 2 层 LLM 分类 | Question Classifier 节点：每类给「类名 + 描述 + 关键词」，`temperature 0.2~0.3`，输出 `intent / confidence / slots` 结构化 JSON |
| 第 3 层 外部模型兜底 | HTTP 节点接自有 BERT 分类服务 |
| **路由目标** | **工作流分支节点**，不是"某个 Agent 人设" |

一条关键设计（Dify 官方文档原文）：

> "Each class has two independent pieces of text: **Class description** (what the LLM reads when choosing) and **Class title** (the label shown on the canvas). **boundary phrases like 'anything related to…' or 'excluding…' help when classes overlap.**"

**对本工程的启示**：① "描述是给 LLM 读的、标题是给人看的"——两者要分开；② **重叠类别必须显式写 `excluding`**，这正是我本轮在 description 里加"不负责 X（交给 Y）"的依据；③ 但 Dify 的候选是**分支**（5~10 个），不是 22 个 Agent。

### 3.4 三家共性（这是最重要的部分）

| 共性 | 含义 |
|---|---|
| **都不做"22 选 1"** | 候选集都在 3~10 量级；超出就换模式（Claude 用 Tool Search 让模型搜，OpenAI 用 agents-as-tools 让主 Agent 调） |
| **分类目标是"能力/分支"，不是"人设"** | Dify→工作流分支；Claude→工具；OpenAI→专家 Agent 但主 Agent 保留答复权 |
| **都有"不选"的出口** | Claude 可自己答；OpenAI triage 可 `chat`；Dify 有 `other` 兜底类 |
| **模型只做"消费分类结论"，不重复分类** | 分类一次、编排按结论走；不会在每次工具调用前重新判"我是谁" |

## 四、缺陷归因（三类，按修法不同分开）

| 类 | 症状 | 根因 | 能否靠调参解决 |
|---|---|---|---|
| **A. 标签集本身有歧义** | 需求域 3 个 Agent 互撞、`design` 有重复行、平台操作 2 个互抢 | 候选池未做互斥化整理 | ❌ 必须清池 |
| **B. 单标签分类器撞上近义标签** | LLM 在 quality/analysis 之间摇摆（0.86） | 三层都是"选 1 个"，LLM 面对 22 个近义名字 | ❌ 必须换模式（多标签 / 分层） |
| **C. 分类粒度选错** | 用户问"建个报告+审一下模型"，只能选 1 个 | 候选是"人"（执行者），而不是"任务类型+能力" | ❌ 必须改路由对象 |

> **A/B/C 都不是"分类器不够准"**，所以"换更强的 LLM"或"再调阈值"都不会有效。
> 这正是我上一轮只改 description/keywords 能到 9/11、但**再也上不去**的原因。

## 五、优化方案

### 5.0 设计原则（先定原则，再谈实现）

1. **路由对象改成「意图族」而不是「Agent」** —— 族是互斥的（可穷举），Agent 不是
2. **单标签 → 单标签 + 能力多标签** —— 先定"要做什么"，再定"要哪些能力"，最后才装配 Agent
3. **保留"不选"的出口** —— 主 Agent 可以直接答、可以自己调工具，不必落到某个专家
4. **细粒度执行 Agent 降级为工具** —— `view_expansion`/`architecture_skeleton` 等 8 个建模子 Agent 不该是路由候选

### 5.1 目标架构：三层（把"22 选 1"改成"族 → 能力 → 装配"）

```
用户输入
   │
   ├─ L0 硬规则（确定性，零成本，先跑）
   │    · 平台读取类前置（已有）
   │    · 变更影响语境（本轮已加）
   │    · 显式点名（「用 X 技能/工具」—— 已有"点名即注入"）
   │
   ├─ L1 意图族分类（互斥，8 个族，不是 22 个 Agent）
   │    requirement / design / verify / change / report / knowledge / platform_op / chat
   │    · 输出：族 + confidence + slots（对象/动作/约束）
   │    · 族内**不再区分** analysis/quality/structuring —— 那是执行分工，不是意图
   │
   ├─ L2 编排决策（三选一，显式出口）
   │    ① direct      ：主 Agent 直接答（知识问答、闲聊、简单查询）
   │    ② single      ：委派给 1 个专家 Agent（该族只有一个执行者时）
   │    ③ team        ：走编排，多成员按依赖串行/并行（复合任务）
   │
   └─ L3 Agent 装配（族内选执行者，允许"多个"）
        · 依据 **capabilities**（不是 description）匹配 → 可以是 1 个或 N 个
        · 装配结果落 `plan.tools` 白名单，父池收窄（复用既有 side_effect 机制）
```

**关键变化**：L1 的候选从 22 个降到 **8 个互斥族**；L3 在族内做多选，允许"需求分析 + 需求质量"同时上。

### 5.2 落地步骤（按风险从低到高，每步独立可回退）

| 步 | 做什么 | 判据 | 风险 |
|---|---|---|---|
| **P0** | **清池**：合并重复 Agent、把 8 个建模执行子 Agent 标记为 `role=worker`（不进路由候选池） | 路由候选从 22 → ≤10；11 条用例不降 | 低（只改 `agent_role`/`status`，可回退） |
| **P1** | **加 `intent_family` 字段**（表列 + 8 个族定义），路由先出族、再出 Agent（族的判定复用现有三层，只是标签集换成 8 个） | 族级准确率 ≥ 95%（族比 Agent 粗，应当更容易判准） | 中（新增一层，需灰度开关） |
| **P2** | **L2 编排决策显式化**：把"direct/single/team"作为路由输出的一部分落库 | 复合任务（含"并/同时/然后"）能判为 `team` 而非硬选 1 个 | 中 |
| **P3** | **L3 按 capabilities 多选装配**：族内允许多个执行者，按 capabilities 与 slots 匹配 | 需求类复合任务能同时调 analysis + structuring | 高（改装配逻辑） |

### 5.3 为什么 P0 必须先做（不能跳过）

实测：`design` 与 `工程建模方案设计Agent` 的 `display_name` **完全相同**、`system_prompt` **逐字相同**。
只要这两行都在 active 状态，语义索引里就有**两条几乎一样的向量** ⇒ 无论分类器多准，二者之间永远是 50/50。

这不是"分类器问题"，是**数据问题**。同理，需求域 3 个 Agent 的关键词已经互撞（`需求条目` 被两个占用）。

> **通则**：标签集里的重复项无法靠算法消解 —— 算法只能在给定集合上做最优选择，
> 集合本身有冗余时"最优"是未定义的。清池成本最低、收益最直接。

### 5.4 与既有实现的衔接（不推翻已有工作）

| 已有 | 如何复用 |
|---|---|
| 三层（关键词/语义/LLM） | **全部保留**，只是标签集从 22 Agent 换成 8 族 |
| `llm_first` + few-shot + 澄清 | 保留；族粗化后 LLM 判定更容易达到 >0.85 |
| `detect_multi` 多意图切分 | 升级为 L2 的 `team` 判据（已有基础） |
| `side_effect` + 计划 `tools` 白名单 | 作为 L3 装配后的**能力收窄**机制（子 ⊆ 父） |
| `capabilities` 字段 | 当前只被编排器 planner 消费（`orchestration.py:93`）⇒ 本轮已完成填充，可直接用于 L3 匹配 |
| description 三段式 + `excluding` 边界 | 保留（Dify 官方推荐做法），但**服务对象从"22 选 1"变为"8 选 1 + 族内多选"** |

## 六、本轮已实施的部分（前置工作，不是方案本身）

| 项 | 内容 | 结果 |
|---|---|---|
| 能力定义自检器 | `tools/verify/verify_agent_spec.py`（A/S/T 三组 15 条判据 + 变异自证） | 全库 ERR 15 → **0** |
| description 重写 | 7 个 Agent 改为三段式（动作+对象+输出 / 触发话术 / **边界"不负责 X 交给 Y"**），补 `capabilities` | 24~36 字符 → 140~200 字符 |
| 关键词清理 | 删泛词（`设计/建模/校验/报告/…`），补 4 字独有词（`架构设计/模型校验/…`） | 泛词清空且各 Agent 保留 5~15 个独有词 |
| 触发词清理 | 4 个技能删泛词（`校验/建模/报告/方法论`），补专有词 | 过度召回下降 |
| **explain 短路修复** | 「改了X的接口**定义**，会影响什么」里的"定义"是名词，被当成"请解释定义"⇒ 短路成知识问答。新增 `_CHANGE_ACT × _IMPACT_WORD` 组合豁免 | 该句 route `explain@0.8` → `rule_scored@0.95 impact` |
| 门禁接入 | `verify_agent_spec.py` 登记进 `gates_manifest.json`（local 层）；顺带补齐 13 个未登记门禁 | 元门禁 17/17 通过 |

**这轮做的是"把标签集里的脏数据清干净"（对应 5.3），不是方案主体。**
清完之后 11 条用例 9 过 —— 剩下 2 条错的都在 LLM 层，**已到当前架构上限**，继续调 description 无效。

| # | 决策 | 选项 | 我的建议 |

| 1 | **8 个建模执行子 Agent 是否降为 worker** | A. 降（不进路由候选，只能被主 Agent 当工具调）<br>B. 保留在候选池 | **A**。依据：OpenAI 官方"manager 不宜超过 3-5 个子 Agent"；Claude 把执行能力当工具。降级后候选池 22→9 |
