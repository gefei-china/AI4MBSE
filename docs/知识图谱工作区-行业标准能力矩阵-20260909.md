## 0. 核心认知转变（先说结论）

**前两版方案的根本问题：把"图谱工作区"理解成"画布 + 三元组 + 推理"三件事，这是典型的"工具视角"而非"平台视角"。**

**行业主流的知识图谱工作区是「管理 + 呈现 + 推理 + 检索」四位一体的完整平台**，不是三个 Tab 就能概括的。

## 1. 管理范式（Management）：知识图谱不是"图数据库"

### 1.1 行业主流管理能力矩阵

| 能力域 | 行业标准做法 | 典型平台 |
|---|---|---|
| **本体管理** | 类型定义 + 版本管理 + 结构变更检测 + CI 校验 | TopBraid EDG / metaphactory / PoolParty |
| **实例管理** | 实体/关系增删改查 + 批量操作 + 审核工作流 | Stardog Studio / WebProtege |
| **数据同步** | CDC + 批量 + 增量 + merge(UPSERT) + tombstone | Oracle / Actian / Neo4j |
| **实体解析** | sameAs + 置信度 + 合并拆分 + 跨源对齐 | Stardog / Actian / Neo4j |
| **治理** | SHACL 校验 + 审核工作流 + 细粒度访问控制 + 审计日志 | TopBraid EDG / metaphactory |
| **版本管理** | 本体语义化版本（SemVer）+ 下游 pin + 迁移指南 | Enterprise KG Architecture |
| **溯源** | 每条三元组带 source / timestamp / quality flag | Stardog / GraphDB |
| **多租户** | 命名图隔离 + 行级/列级安全 + 审计 | Stardog / Neptune |

### 1.2 管理范式的关键洞察

**洞察 1：本体是"代码"，不是"数据"**
- 行业标准：本体定义走 **Git 版本控制 + CI 校验 + PR 审核 + 语义化版本**
- 变更流程：change request → impact analysis → steward review → Git PR with CI validation → staging deploy → golden query tests → production release tag
- **米爸团队现状**：本体编辑在 Web UI 直接改，无版本管理，无 CI 校验

**洞察 2：实例是"数据"，需要审核工作流**
- 行业标准：staging（raw）→ curated（已审核）两层分离
- 审核单元：**三元组级**（不是实体级），支持批量审核 + 判重提示
- **米爸团队现状**：已有 `triple_store.py` + 审核工作流，**符合行业标准**

**洞察 3：数据同步是"持续过程"，不是"一次性导入"**
- 行业标准：CDC（Change Data Capture）+ 增量 upsert + tombstone（删除标记）
- **米爸团队现状**：批量导入，无 CDC，无增量

**洞察 4：实体解析是"长期战争"**
- 行业标准：sameAs + 置信度 + 候选对齐 + 人工仲裁
- **米爸团队现状**：已有 `entity_resolver.py`，但**未在 UI 层暴露**

## 2. 呈现范式（Presentation）：不是"画布"，是"探索界面"

### 2.1 行业主流呈现能力矩阵

| 能力域 | 行业标准做法 | 典型平台 |
|---|---|---|
| **布局算法** | Force-directed / Hierarchical / Radial / Circular / Geographic / Timeline / Matrix | yFiles / ArcGIS Knowledge / Linkurious |
| **视觉编码** | 颜色=类型 / 形状=语义 / 大小=重要性 / 边粗=强度 / 虚线=推断 | yFiles / Cambridge Intelligence |
| **交互范式** | Overview → Zoom → Filter → Details on Demand（Shneiderman mantra） | 所有主流平台 |
| **渐进披露** | 默认展示 20-50 节点，通过交互逐步展开 | yFiles / Neo4j Browser |
| **Focus+Context** | 焦点区域详细 + 周边压缩（鱼眼镜头） | yFiles Wonderlens |
| **语义缩放** | 不同缩放级别展示不同信息（Overview → Relationships → Content） | yFiles / ArcGIS |
| **多视图联动** | 画布 + 表 + 时间轴 + 地图，brushing & linking | Linkurious / ArcGIS |
| **搜索导航** | 实体查找 + 谓词筛选 + 邻域扩展（"show 2-hop part-of"） | Neo4j Browser / Stardog |

### 2.2 布局算法的选择逻辑（行业标准）

| 数据结构 | 推荐布局 | 理由 |
|---|---|---|
| **DAG / 本体层级** | Hierarchical（层级） | 编码方向与因果关系 |
| **未知结构探索** | Force-directed（力导向） | 自然聚类浮现 |
| **单中心实体** | Radial（径向） | 聚焦 + 邻域展开 |
| **聚类社区** | Circular（环形） | 社区结构清晰 |
| **地理位置数据** | Geographic（地理） | 空间上下文 |
| **时序数据** | Timeline（时间轴） | 时间流清晰 |
| **密集图（>15% 边密度）** | Matrix（矩阵） | 节点链接图会成"毛线团" |

**米爸团队现状**：
- 只有一种布局（自研简单布局）
- 骨架模式 L1/L2/L3 是**层级布局的变种**，但未明确对应
- **缺失**：Radial（单实体聚焦）、Timeline（时序）、Matrix（密集场景）

### 2.3 交互范式：Shneiderman 的 Visual Information-Seeking Mantra

**行业标准流程：**
```
Overview first（总览）
    ↓
Zoom and Filter（缩放与筛选）
    ↓
Details on Demand（按需查看详情）
```

**对应到图谱工作区：**
1. **Overview**：默认展示类型骨架（L1）或 Top-N 节点
2. **Zoom and Filter**：类型图例筛选 + 状态筛选 + 命名图切换
3. **Details on Demand**：单击节点 → 右栏详情

**米爸团队现状**：**已符合**（骨架模式 + 筛选 + 右栏详情），**这是优势**。

### 2.4 渐进披露（Progressive Disclosure）：避免"毛线团"

**行业标准：**
- 默认展示 **20-50 个节点**，不是"全图"
- 通过交互逐步展开：
  - 双击节点 → 展开 1-hop 邻域
  - 右键 → "Expand 2-hop"
  - 筛选 → 动态加载

**反模式：**
- ❌ 一上来展示"全图"（几千节点 = 毛线团）
- ❌ 无筛选 / 无层级聚合

**米爸团队现状**：
- 骨架模式 L1（类型聚合）**符合**渐进披露
- 但 L2/L3 下钻后**无返回机制**（用户迷失）
- **缺失**：双击展开 1-hop（当前是单击详情，无展开）

## 3. 推理能力矩阵（Reasoning）：不是"5 项检查"，是"三大流派"

### 3.1 行业主流推理能力全景

| 推理流派 | 代表技术 | 适用场景 | 典型平台 |
|---|---|---|---|
| **逻辑推理（Logical Inference）** | OWL 2 RL / SWRL / SHACL Rules | 分类 / 传递 / 对称 / 一致性 | Stardog / GraphDB / Jena |
| **路径推理（Path-based Reasoning）** | PRA / DeepPath / MINERVA / AMIE | 关系预测 / 规则挖掘 | 学术界 / 部分商业平台 |
| **嵌入推理（Embedding-based）** | TransE / RotatE / GNN / Node2Vec | 链接预测 / 相似度计算 | Neo4j GDS / TigerGraph |
| **神经符号推理（Neural-Symbolic）** | Neural Theorem Provers / ExpressGNN / LTN | 复杂推理 + 可解释性 | 学术界 / 前沿研究 |
| **GraphRAG（混合）** | 向量检索 + 图遍历 + LLM | 多跳问答 / 关系密集型查询 | Oracle / Neo4j / Microsoft |

### 3.2 推理能力的三个层次

#### 层次 1：演绎推理（Deductive Reasoning）——"必须成立"
- **定义**：基于本体公理的逻辑推导
- **例子**：
  - 分类推理：`部件A rdf:type 部件` + `部件 rdfs:subClassOf Thing` ⇒ `部件A rdf:type Thing`
  - 传递推理：`A contains B` + `B contains C` + `contains transitive` ⇒ `A contains C`
  - 对称推理：`A connects B` + `connects symmetric` ⇒ `B connects A`
- **特点**：确定性 / 可解释 / 依赖本体质量
- **行业标准**：OWL 2 RL / SHACL Rules
- **米爸团队现状**：**已具备**（`ontology_reasoning.py` 5 项推理），**符合行业标准**

#### 层次 2：归纳推理（Inductive Reasoning）——"可能成立"
- **定义**：基于统计学习的模式发现
- **例子**：
  - 链接预测：`部件A` 和 `部件B` 都与 `部件C` 相连 ⇒ 可能相连（置信度 0.8）
  - 社区检测：Louvain / Leiden 算法发现隐含社区
  - 中心性分析：PageRank / Betweenness 发现关键节点
- **特点**：概率性 / 不可解释 / 依赖数据量
- **行业标准**：Neo4j GDS / TigerGraph / NetworkX
- **米爸团队现状**：**缺失**

#### 层次 3：溯因推理（Abductive Reasoning）——"最佳解释"
- **定义**：从结果反推最可能的原因
- **例子**：
  - 故障诊断：`系统X 失效` + 已知故障模式 ⇒ 最可能原因
  - 影响分析：`需求Y 变更` ⇒ 影响哪些下游组件
- **特点**：假设生成 / 需要领域知识 / 半自动化
- **行业标准**：规则引擎 + 图遍历 + 专家系统
- **米爸团队现状**：**部分具备**（`impact.py` 影响分析）

### 3.3 推理呈现的行业标准

| 呈现方式 | 行业标准 | 例子 |
|---|---|---|
| **推断三元组标记** | `status='inferred'` + 来源推理类型 | Stardog / GraphDB |
| **推断边样式** | 虚线 + 不同颜色（如橙色） | yFiles / Neo4j |
| **推断路径展示** | hover 显示完整推导路径（A → B → C） | Stardog Studio |
| **推理依据透明化** | 显示 OWL 公理 / 规则来源 | WebProtege / TopBraid |
| **推理结果物化** | 推断三元组写入图库（可选） | Stardog / GraphDB |
| **推理性能监控** | 耗时 / 推断数量 / 违规数量 | Stardog Studio |

**米爸团队现状**：
- 后端已有推理函数，但**前端零呈现**
- 无推断三元组标记
- 无推断边样式
- 无推理路径展示

## 4. 检索能力矩阵（Retrieval）：不是"SPARQL 查询"，是"五种检索方式"

### 4.1 行业主流检索能力全景

| 检索方式 | 定义 | 适用场景 | 典型平台 |
|---|---|---|---|
| **关键词检索** | 全文索引 + BM25 | 文档查找 / 实体名搜索 | Elasticsearch / Solr |
| **结构化检索** | SPARQL / Cypher / Gremlin | 精确模式匹配 | Stardog / Neo4j / Jena |
| **语义检索** | 向量嵌入 + 相似度 | 模糊匹配 / 同义词扩展 | Pinecone / Weaviate / Neo4j Vector |
| **图检索** | 路径查询 + 邻域扩展 | 多跳关系 / 影响分析 | Neo4j / TigerGraph |
| **自然语言检索** | NL → SPARQL/Cypher | 业务用户查询 | Stardog / Neo4j / Microsoft GraphRAG |
| **GraphRAG** | 向量 + 图遍历 + LLM | 多跳问答 / 关系密集型 | Oracle / Neo4j / Microsoft |

### 4.2 检索方式的组合策略（行业标准）

**策略 1：分层检索**
```
用户查询
    ↓
第 1 层：关键词检索（快速召回）
    ↓
第 2 层：语义检索（扩展同义词）
    ↓
第 3 层：图检索（关系遍历）
    ↓
融合排序
```

**策略 2：GraphRAG（2026 主流）**
```
用户查询
    ↓
向量检索（Candidate Set A：语义相似）
    ↓
实体抽取（从查询和 Top chunks 提取实体）
    ↓
图遍历（Candidate Set B：图连接）
    ↓
融合（A + B）→ LLM
```

**策略 3：自然语言查询（NL Query）**
```
用户输入自然语言
    ↓
LLM 解析 → 生成 SPARQL/Cypher
    ↓
执行查询
    ↓
结果 + 查询语句展示（透明化）
```

### 4.3 检索呈现的行业标准

| 呈现方式 | 行业标准 | 例子 |
|---|---|---|
| **搜索框** | 顶部全局搜索 + 自动补全 | Neo4j Browser / Stardog |
| **查询编辑器** | Monaco Editor + 语法高亮 + 自动补全 | Stardog Studio / Neo4j Browser |
| **查询模板** | 预定义常用查询（"查找所有部件"） | Linkurious / Stardog |
| **结果多视图** | 表 / 图 / JSON / 时间轴 | Stardog Studio |
| **结果导出** | CSV / JSON / N-Triples | 所有平台 |
| **查询历史** | 保存 + 重放 + 分享 | Stardog Studio / Neo4j Browser |
| **查询计划可视化** | 树形展示执行计划 | Stardog Studio |

**米爸团队现状**：
- 有 SPARQL 查询接口（`/api/graph-db/query`）
- **缺失**：搜索框 / 查询编辑器 / 查询模板 / 结果多视图 / 查询历史

## 6. 真正的优化方向（基于行业标准）

### 6.1 不是"3 Tab"，是"能力矩阵"

**前两版方案的根本错误：把"图谱工作区"理解成"画布 + 三元组 + 推理"三个 Tab，这是工具视角。**

**行业标准的知识图谱工作区是「管理 + 呈现 + 推理 + 检索」四位一体的完整平台**，应该用**能力矩阵**而非 Tab 数量来定义。

### 6.2 真正的 P0 能力（行业标准 vs mbse_system 差距）

| 能力域 | P0 缺失项 | 行业标准做法 | 实施成本 |
|---|---|---|---|
| **呈现** | 搜索框 + 自动补全 | 顶部全局搜索，支持实体名 / IRI / 类型 | 低 |
| **呈现** | 查询编辑器（Monaco） | SPARQL/Cypher 语法高亮 + 自动补全 | 低 |
| **呈现** | 结果多视图（表/图） | 查询结果可切换表格 / 图谱 | 中 |
| **推理** | 推断三元组标记 | `status='inferred'` + 来源推理类型 | 低 |
| **推理** | 推断边样式 | 虚线 + 橙色 + hover 显示路径 | 低 |
| **推理** | 推理结果物化 | 推断三元组写库（可选） | 低 |
| **管理** | 本体版本管理 | Git 化本体定义 + 语义化版本 | 中 |

### 6.3 真正的 P1 能力

| 能力域 | P1 缺失项 | 行业标准做法 |
|---|---|---|
| **呈现** | 布局算法扩展 | Radial（单实体聚焦）+ Timeline（时序） |
| **呈现** | 渐进披露完善 | 双击展开 1-hop + 返回机制 |

## 7. 结论：什么才是真正的优化

### 7.1 前两版方案的错误

| 错误 | 表现 | 后果 |
|---|---|---|
| **工具视角** | 把"图谱工作区"理解成"3 个 Tab" | 忽略了管理 / 检索两大能力域 |
| **增量思维** | 只想着"加什么"，不想"对标什么" | 漏掉了搜索框 / 查询编辑器 / 布局算法等行业标准 |
| **技术驱动** | 纠结 Reagraph / ELK / owlready2 | 没问"米爸团队真正的工作流是什么" |
| **炫技倾向** | 矩阵视图 / MiniMap / 公理视图 | 忽略了搜索框这种基础能力 |

### 7.2 真正的优化原则

1. **能力矩阵视角**：管理 + 呈现 + 推理 + 检索 四位一体
2. **行业标准对标**：不是"mbse_system 缺什么"，而是"行业主流怎么做"
3. **用户工作流驱动**：米爸团队是系统工程师，工作流是"探索 → 查询 → 推理 → 验证"
4. **渐进披露**：默认 20-50 节点，交互展开，避免"毛线团"
5. **推理透明化**：推断三元组标记 + 推断边样式 + 推导路径
6. **检索多模态**：关键词 + 结构化 + 图检索 + 自然语言

### 7.3 真正的 P0 优化清单（1 天工作量）

| 优化项 | 实施成本 | 业务价值 |
|---|---|---|
| 搜索框 + 自动补全（实体名 / IRI / 类型） | 低 | ⭐⭐⭐⭐⭐ |
| 查询编辑器（Monaco + SPARQL 高亮） | 低 | ⭐⭐⭐⭐⭐ |
| 查询结果多视图（表 / 图切换） | 中 | ⭐⭐⭐⭐ |
| 推断三元组标记（`status='inferred'`） | 低 | ⭐⭐⭐⭐ |
| 推断边样式（虚线 + 橙色） | 低 | ⭐⭐⭐⭐ |
| 推理结果物化（可选写库） | 低 | ⭐⭐⭐ |
| 本体版本管理（Git 化 + SemVer） | 中 | ⭐⭐⭐⭐⭐ |

**总计：1 天工作量，7 项 P0 能力，全部对齐行业标准。**
