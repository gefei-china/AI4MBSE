## 1. R1：491 条「待审」是口径错误，不是工作量

### 1.1 三个同时为真的数字

用户侧看到的是「485 条待我审」。同一时刻库里：

| 口径 | 数字 | 出处 |
|---|---|---|
| `status='suggested'` 行数 | **491** | `intent_samples` 直查 |
| 其中已是银标（双视图独立标注一致，且非合成） | **164** | `created_by='dual_label_v1'` 减 aug 重叠 |
| 其中已是合成样本（手写改写） | **200** | `source='aug'`（其中 **183** 行同时是双视图 ⇒ **按 aug 归 synth**） |
| 真正待人工 | **127** | `491 − 164 − 200` |

⇒ 页面把**三档已定档的样本**算成了人工待办，待办数**虚高 3.8 倍**（491 / 127 ≈ 3.87）。

> 拆账时必须先解重叠：`created_by='dual_label_v1'` 共 **347** 行，其中 **183** 行 `source='aug'`。
> 把 347 直接当"银标"会与 synth 的 200 行**重复计数**（347 + 17 = 364，与 164 + 200 恰好同和 ——
> 数字对得上但**归属全错**）。这也是 §1.4 判定顺序必须 `aug` 优先的实测依据。

### 1.2 根因：样本状态与评测口径不同构

评测跑批器（`intent_eval_snapshot`）早就按 **gold / silver / synth** 三集分报，而样本池只有
`new / suggested / confirmed / rejected` 四态，银标与合成**寄生在 `suggested` 里**，
靠 `created_by` / `source` 两个**隐式字段**区分。

⇒ 同一语义（"这条样本属于哪一档"）在**两个地方各写一份判据**，必然漂移。
修法不是"提醒用户别多算"，而是**让状态与评测同构**。

### 1.3 改了什么

| 文件 | 改动 |
|---|---|
| `repositories/intent_sample_repo.py` | `VALID_STATUS` 增加 `silver`/`synth`；`STATUS_TIER`（`confirmed→gold`、`silver→silver`、`synth→synth`）单一真源；新增 `tier_of(source, created_by)`；`stats()` 增 `by_tier` + `pending_human`；`list()` 排序 `new=0,suggested=1,silver=2,synth=3` |
| `tools/intent_sample_tier_migrate.py`（新） | 一次性归位：复用 `tier_of`，**只动 `new`/`suggested`**，逐 id UPDATE，dry-run 默认 |
| `tools/_intent_silver_label.py` | 写库改为 `CASE WHEN status IN ('confirmed','rejected') THEN status ELSE 'silver' END` —— **人工结论不被机器降级** |
| `tools/intent_eval_snapshot.py` | 三集改为**按各自 status 取**（原口径靠 `created_by` + 排除 `aug`，会让一条被人工确认的银标同时出现在 gold 与 silver 两集） |
| `static/js/mods/42-intent-samples.js`、`static/index.html` | 状态徽章/筛选加 `silver`/`synth`；待办数**只读后端 `pending_human`**（禁止页面自己拼 `new+suggested`）；对照列判据改 `status !== 'confirmed' && status !== 'rejected'` |

### 1.4 `tier_of` 的判定顺序是有牙齿的

```python
def tier_of(source="", created_by=""):
    if (source or "").strip() == "aug":      # ★ 必须先判 aug
        return "synth"
    if (created_by or "").strip() == "dual_label_v1":
        return "silver"
    return "suggested"
```

**必须先用 `aug` 判定**：库里存在 **183 行同时满足 `source='aug'` 且 `created_by='dual_label_v1'`**，
顺序反了会让同一批样本**同时进 silver 与 synth 两集** ⇒ 回归集与边界集互相污染。

### 1.5 实测（真库，迁移前后）

| status | 迁移前 | 迁移后 |
|---|---|---|
| `suggested` | 491 | **127** |
| `silver` | — | **164** |
| `synth` | — | **200** |
| `confirmed` | 48 | 48（未变） |
| `rejected` | 13 | 13（未变） |

合计 552 行不变（**归位不是增删**）。二次运行 `0 变更`（幂等）。

三集（评测口径，要求 `intent`/`text` 非空）：**gold 48 / silver 164 / synth 200**。

### 1.6 顺带修掉的死区：118 条卡在中间态

`status='suggested'` 但 `intent` 为空的行有 **118 条**：
`/suggest` 只扫 `status='new'`（扫不到它们），而 `update()` 又要求 confirmed 必须有标签
（点「确认」报 `confirm_requires_intent`）⇒ 这批行**永远卡住**。

修法：判据从「看状态」改为「**看有没有标签**」：

```python
PENDING_SUGGEST_SQL = (
    "SELECT id, text FROM intent_samples "
    "WHERE status='new' OR (status='suggested' AND COALESCE(intent,'')='') "
    "ORDER BY seen_count DESC, id LIMIT ?")
```

### 1.7 判据：`verify_intent_sample_tiers.py` —— 15/15

覆盖 T1 六档枚举、T2 `tier_of` 六组判定表（含优先级）、T3 三集按**各自** status 取、
T4 真库不变量（silver 必来自双视图 / synth 必来自 aug / **三集文本两两无交**）、
T5 `pending_human` 单一口径、T7 死区夹具，以及 M1~M3 变异自证：

| 变异 | 期望 | 实测 |
|---|---|---|
| M1 交换判定顺序（银标优先） | 用例表翻红 | ✅ `[('aug','dual_label_v1','synth','silver')]` |
| M2 砍掉 `aug` 分支 | 用例表翻红 | ✅ 两行不符 |
| M3 补建议 SQL 退回只认 `new` | 死区用例翻红 | ✅ 只剩 `new 有 hint` |

> 判据写过一次假红：T3 最初写成 `"status='%s'" % k`，而**集合名 `gold` ≠ 状态名 `confirmed`**。
> 用 `STATUS_TIER` 反查修正。这次假红本身证明了断言有牙齿 —— 但记下来：**三集名与状态名不是同一套词**。

## 2. R2：词表自举（`aliases` / `examples` 从数据派生）

### 2.1 为什么不能"把空的手写填上"

22 条意图字典里 13 条 `aliases` 或 `examples` 为空。手工补写的代价不是工作量，而是**污染**：

- `aliases` 与 `agents.intent_keywords` 是**同一件事的两份副本** ⇒ 手写必然漂移；
- `examples` 被 `agent/intent.py::fewshot_map` **直接喂 LLM few-shot** ⇒ 编造的示例会改变识别结果。

⇒ 只做**派生**，两个来源都是库里既有的真实数据：

| 字段 | 来源 | 为什么是它 |
|---|---|---|
| `aliases` | `agents.intent_keywords`（按 `agent_name` 关联） | 那就是"用户会怎么称呼这个能力"的词表，已经在维护，不该有第二份 |
| `examples` | `intent_samples` 中 `status='confirmed'` 的**原话** | 人工确认过的真实说法，零编造；不足 `min_confirmed=2` 就**不填** |

`core/intent_taxonomy.py` 加**溯源列**（这是"机器补的"与"人改过的"唯一可分之处）：

```sql
aliases_src  TEXT NOT NULL DEFAULT '',
examples_src TEXT NOT NULL DEFAULT '',
```

规则：`*_src` 为空 = 人工维护（**永不覆盖**）；等于本来源 = 机器派生（可刷新）。
人工在页面上显式改一项时，`upsert()` 同步把 `*_src` 清空 ⇒ **双向判据只在写入侧一处**。

> 自愈：`ensure_table()` 里补 `_ensure_columns()` —— 本模块被 CLI / 门禁在**裸连接**上调用，
> 不能只依赖启动期迁移，否则老库上 `no such column: aliases_src`。

### 2.2 实测

| 指标 | 值 |
|---|---|
| 字典条数 | 22 |
| 可自动补 | **11 条**（10 条补别名 + 1 条补示例） |
| 缺口 | **13 条** |
| 配置漂移 | **0** |
| 二次运行 | **0 变更**（幂等） |
| 当前别名覆盖 | 20/22 = **90.9%**（其中 10 条来自派生、10 条人工） |
| 当前示例覆盖 | 9/22 = **40.9%**（其中 1 条来自派生、8 条人工） |

### 2.3 缺口不是缺陷，缺口要能解释

13 条缺口里 **12 条是「examples:无 confirmed 样本」**、1 条是「别名:Agent 未配 intent_keywords」。

这句话很重要：**它不是代码问题，是标注运营问题** —— 那 12 个意图（8 阶段建模流水线 + 智源对接等）
在 `intent_samples` 里**一条人工确认样本都没有**。所以页面必须把"原因"显示出来，
否则每个看到空示例的人都会来问一遍"为什么这里是空的"。

### 2.4 页面入口（本轮新增）

`routers/intent_samples.py`：

- `GET /api/intent-taxonomy/coverage` —— 只读快照（覆盖率 + 缺口 + 漂移 + 可补条数）
- `POST /api/intent-taxonomy/sync` —— `apply=false`（默认）**只返回计划**；`apply=true` 才落库并 audit

`static/index.html` + `42-intent-samples.js`：意图字典区新增「📊 覆盖度」「⚡ 从数据派生补齐」。
补齐是**两步**：先 dry-run 出计划 → 确认框里列明细（前 6 条 + 总数）→ 才写库。
理由：这是写库动作且**会改变喂给 LLM 的 few-shot**，不给明细的"一键补齐"等于让用户盲签。

## 3. R3：`ontology_profiles` 0 行 ≠ 没有本体知识

### 3.1 真因

`ontology_types` 里有 **52 条真实类型**（entity 28 / relation 13 / attribute 11，全部 `released`），
但**从未投影成画像**（`ontology_profiles` 0 行）。而 `seeds.py` 里那两条示范 profile 被

### 3.2 做法：派生 + 前缀认领（不写死种子）

`services/ontology_profile_service.py`（新）：

- `ID_PREFIX = "profile-derived-"`、`DEF_NAME = "当前本体快照"`

### 3.3 B 层恒空的真因（顺手修掉）

回退时 `how='derived_fallback'` 并**显式给 warn + `resolved_by`**（回退必须可见）。

## 4. R4：SHACL「0 违规」的取证与阈值分档决策

### 4.1 `shacl_findings` 0 行有两种可能，必须区分

「0 违规」与「门禁根本没跑」在日志上**完全不可区分**。所以 P5 的判据不是"有没有违规"，而是
**"门禁跑起来了"**：

| 判据 | 实测 |
|---|---|
| P5a `gate_mode` 不是 `off` | `warn` |
| P5b 未因缺依赖/空 shapes 被跳过 | `skipped=False` |
| P5c 实际比对了数据三元组 | `total_checked=302` |
| P5d shapes 非空（由 `ontology_types` 派生） | `672` 三元组 |

⇒ 真合规（`conforms=true`），不是静默降级。参考值「本次违规数 = 0」**不作门禁判据**（随数据变化）。

### 4.2 阈值分档：48 条样本下不可区分 ⇒ 保持关闭

| 配置 | 准确率 | ECE | 澄清次数 |
|---|---|---|---|
| OFF（现状） | 87.5% | 0.0822 | 10 |
| ON | 85.4% | 0.0807 | 9 |

48 条样本下 **1 例 = 2.08pp**，两者差值**落在噪声内**。分档的价值必须在更大样本上才可判别，
所以结论是 `keep_off`（`verify_router_quality` E7/E8 已钉住：**未证明净正前不打开**）。

> 反过来记一条：如果这轮我"顺手打开"了分档，指标会掉 2.1pp 而**没人能证明是分档造成的** ——
> 这类"看起来有改善"的开关必须在**能被证伪**的条件下才动。

数据层（**迁移工具本身没有 `--rollback`，回退须显式写 SQL**）：

```sql
-- ① 三档折回：把派生出来的两档并回 suggested（confirmed/rejected 不动）
UPDATE intent_samples SET status='suggested' WHERE status IN ('silver','synth');
-- ② 本体画像：派生行可整行删除，人工画像（id 不带前缀）不受影响
DELETE FROM ontology_profiles WHERE id LIKE 'profile-derived-%';
-- ③ 字典派生项：只清机器派生（*_src 非空）的那部分，人工维护的别名/示例保留
UPDATE intent_taxonomy SET aliases='[]',  aliases_src=''  WHERE aliases_src  ='agents.intent_keywords';
UPDATE intent_taxonomy SET examples='[]', examples_src='' WHERE examples_src='intent_samples.confirmed';
```

> ②③ 的正确性依赖"溯源列"：**只删派生的**。这也正是加 `*_src` 的第二个用处 ——
> 没有它，回退只能连人工数据一起删，或者干脆不敢回退。
