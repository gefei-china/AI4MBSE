# 门禁分层与「克隆绿」判据 — 2026-11-05

> 本文回答一个问题：**为什么 185 条门禁在本机全绿，在 CI 上却红 37 条？**
> 以及：降级到 `local` 的那些，什么时候能收回来。

---

## 1. 判据变更（本轮唯一的方法论改动）

| | 旧判据 | 新判据 |
|---|---|---|
| pr 层准入 | 开发机上跑绿 | **全新克隆 + `init_db()` 空库**上跑绿 |
| 为什么 | —— | 开发机有 `mbse.db`、`.venv`、`outputs/`、`checker.jar`、全 git 历史；CI 全都没有 |
| 后果（旧） | 本机永远绿 ⇒ 没人会去修；CI 一开跑就红，且"第一红挡掉后面 190 条"掩盖了多数红 | 判据与 CI 同构 |

**这条判据的成本很低、价值很高**：`git clone` + `init_db()` + `gate_runner --tier pr`，
5 分钟就能在推送前知道 CI 会不会绿。

## 2. 实测数据（同一份代码，三种口径）

| 口径 | 声明/执行 | PASS | FAIL | 用时 |
|---|---|---|---|---|
| 开发机 · 真库 | 185/185 | **185** | 0 | 409s |
| 全新克隆（`--depth 1`）· 空库 | 185/185 | 138 | 47 | 319s |
| 全新克隆（全历史）· 空库 | 185/185 | 137 | 48 | 307s |
| 全历史 + `MBSE_DB_PATH` 统一补丁 | 186/186 | 159 | 27 | 309s |
| 再降级 26 条 + 补 uninstall | 159/159 | **159** | 0 | — |

> ⚠️ 第 2/3 行差 1 条（`verify_prompt_blocks`）是**探测环境缺陷**：
> 我一开始用 `--depth 1` 克隆，`git show <基线sha>` 自然失败。
> 这正是 CI 上的那条红 —— 修法是 `actions/checkout` 加 `fetch-depth: 0`。
> **探测方式本身也可能是错的那一个**（与"验证器会骗人"同族）。

## 3. 三类根因（37 条 CI 红的分解）

| 类 | 条数 | 实例 | 修法 |
|---|---|---|---|
| A 写死开发机环境 | 8 | `os.chdir("C:/Users/<user>/...")`、`.venv/Scripts/python.exe`、`NODE=C:\Users\<user>\...\node.exe` | 按 `__file__` 推导 / `sys.executable` / `shutil.which("node")` |
| B 依赖未入库的配置/资产 | 2 | `data/modeling_nodes.json`（89KB **代码级配置**）、`checker.jar`/`sysml.library` | B1 定向放行入库；B2 属随包运行时 ⇒ 降 `local` |
| C 依赖真库存量数据 | 27 | 断言「真库有 N 条 failed 记录 / 会话 #9779 / run 531」 | 见 §4 |

### 3.1 最隐蔽的一条：`sqlite3.connect()` 会静默建空库

40+ 条报的是 `no such table: agents`，但那个空库**明明有 `agents` 表**。
真因是它们连的是 `os.path.join(ROOT, "mbse.db")` —— 干净克隆里没有这个文件，
而 `sqlite3.connect(不存在的路径)` **不报错，直接新建一个空库**。
于是「库不存在」被伪装成「表不存在」，排查方向从一开始就偏了。

> 与 `except: return ""` 同族：**静默兜底把错误变成不可见**。
> 修法：`(os.environ.get("MBSE_DB_PATH") or os.path.join(ROOT, "mbse.db"))`
> —— 不设环境变量时行为逐字不变，设了就走指定库。
> 这一条修好后，空库红从 48 降到 27（**修好 22 条**）。

### 3.2 但有 2 处**故意不能**跟随 `MBSE_DB_PATH`

`verify_agent_archive` 的「真库只读：复制一份做收敛」、`verify_orch_failure_class` 的
「F 段真库 failed 记录分解」—— 它们要的是**生产库长什么样**（金标），
不是「用哪个库跑门禁」。误改成 env 优先后立刻红（受控 A/B 已证），已回退并注释。

> **两种语义必须分开命名**：`DB`（可被 env 覆盖）vs `_real_db`/`_PROD`（金标，不可覆盖）。

## 4. 降级清单（27 条 → `local`）与**回收条件**

降级不是"搬走换绿"，每条都在 `gates_manifest.json` 写了 reason。
回收（改回 `pr`）的条件列在下面 —— 达成任一条即可回收。

| 组 | 条数 | 回收条件 |
|---|---|---|
| 真库金标（读 `ROOT/mbse.db` 取证） | 16 | 改成「自建夹具 + `MBSE_DB_PATH`」，把断言从「真库有这个会话」改成「造一个会话后断言」 |
| 随包运行时资产（`checker.jar` / `sysml.library`） | 2 | 资产入库（不建议，126MB），或在 CI 上跳过并显式标注口径（`verify_sysml_check_gate` 已是这个做法，可照抄） |
| 本机浏览器证据（`outputs/_verify_cv_fixed.json`） | 1 | 证据改由门禁自己生成（起服务 + 截图）或改成「证据缺失 ⇒ SKIP 并打印生成命令」 |
| MCP「发现」产物（`tool_meta` / skill 包目录） | 3 | 门禁内自行做一次 MCP 发现（离线桩）再断言 |
| 空库种子量不足 | 4 | 提升 `init_db` 种子规模，或把断言改成「比例/结构」而非「绝对数量」 |
| 真库市场状态（`uninstall_flow`） | 1 | 与产品口径确认「卸载后是否允许重装未上架能力」，再决定修代码还是改判据 |

## 5. 本轮顺带发现、但**尚未修**的真实缺陷（下一轮）

1. **`llm_usage_stats.context_window` 列缺失（schema 漂移）**
   真库有该列，`init_db()` 建的空库没有 ⇒ `verify_context_utilization` 在干净库上红。
   这是「环境可重建」的第三个缺口（前两个：资产快照、3 个 agents 列）。
2. **`verify_session_monitor`：同一会话的 weight 详情 40 ≠ 列表 45**
   两处公式相同，是**输入口径不同**（详情走明细行、列表走聚合 SQL）。
   属「同一语义两处各算一遍」—— 修法是抽成单一函数，两处同源。
3. **`verify_uninstall_flow`：卸载后重装被拒**（`install()` 报「未上架市场」）
   可能是真缺陷，也可能是产品有意（未上架不允许装）。待口径确认。

## 6. 防复发（常驻门禁）

`tools/verify/verify_gate_portability.py`（P1~P4，已进 `pr` 层）：

| 判据 | 防的是 |
|---|---|
| P1 pr 层脚本的**取值字符串**不含本机绝对路径 | A 类复发 |
| P2 不含平台特定解释器 | A 类复发 |
| P3 引用的 `data/**` 文件必须已被 git 跟踪 | B1 类复发（`modeling_nodes` 那次） |
| P4 合成样本一绿一红 + docstring 不误报 | 判据写成恒真/恒假，或被噪音淹没后关掉 |

> 为什么用 AST 而不是 grep：本仓 69 个脚本的注释/docstring 里写着
> `.venv\Scripts\python.exe ...`（用法说明）。grep 会把这 69 个全判红，
> 而噪音门禁的下场是被加 `# CI-OPTIONAL` 关掉 —— 等于没写。

## 7. 复现命令

```bash
# 1) 全新克隆（模拟 CI checkout）
git clone --depth 1 file:///<repo> /tmp/probe && cd /tmp/probe

# 2) 空库（模拟 CI 的 init_db）
MBSE_DB_PATH=/tmp/probe.db python -c "from database.schema import init_db; init_db()"

# 3) 跑 pr 层，看是否全绿
MBSE_DB_PATH=/tmp/probe.db python tools/gate_runner.py --tier pr --json /tmp/report.json
```
