# LLM Wiki（Karpathy 模式）与常规 RAG 的对比调研
## ——兼 mbse_system 知识库优化落点分析

- **日期**：2026-09-29
- **范围**：调研 Karpathy `LLM Wiki` 模式（GitHub Gist，2026-04-04）+ 社区正反分析；对比本工程现有 RAG 实现；给出可落地优化建议
- **结论先行**：本工程**规模恰在 LLM Wiki 甜区**（6 篇源文档 / 5758 chunk / 189 实体），且**累积层已存在但未被检索消费**（`agent_memory` 125 条、`project_memories` 24 条，`rag.retrieve()` 零引用）。最优解不是二选一，而是 **"Wiki 编译层 + RAG 长尾层" 的混合架构**，且第一步应做**低风险、高收益**的部分。

---

## 一、先把两件事讲清楚

### 1.1 Karpathy 的 LLM Wiki 是什么

Karpathy 在 Gist《LLM Wiki》中提出的核心命题：

> 要求 LLM 为**每一次查询**都从原始源重新发现知识，本质上效率极低——如同把轮子重新发明数千次。

他的方案极简——**三个文件夹加一个配置文件**：

```
llm-wiki/
├── raw/          # 素材全扔进去，不用整理（不可变证据）
├── wiki/         # LLM 编译后的结构化知识页（Markdown）
├── outputs/      # 对 wiki 的回答存这里
└── CLAUDE.md     # 告诉 LLM 规则（Schema / 宪法）
```

配套三条工作流：

| 工作流 | 做什么 | 关键点 |
|---|---|---|
| **Ingest（摄取）** | 读新源 → 识别受影响页面 → 更新多页 | **单个源可触及 10–15 个页面**；不像 RAG「分块即遗忘」，摄取**永久丰富** wiki |
| **Query（查询）** | 先读 `index.md` → 沿交叉引用取页 → 综合回答 → 好的回答**存回 wiki** | 答案**反吸收**（re-absorption）——今天的回答变成明天的知识 |
| **Lint（体检）** | 定期扫孤儿页 / 断链 / 页面矛盾 / 缺失交叉引用 | Karpathy 明确要求，是 Wiki 能长期可用的前提 |

两层特殊文件：`index.md`（内容目录，每条一行摘要）+ `log.md`（按时间追加的摄取/查询/体检流水）。

**一句话对比**（社区原话，精准）：

> RAG 是**翻书**，LLM Wiki 是**翻笔记**。一个每次从零检索文本片段，一个先让 LLM 读完理解完，再基于理解回答。

### 1.2 常规 RAG 是什么

本工程现有实现（`knowledge_pipeline/search.py` + `knowledge_engine.py`）已经是**工业级 RAG**，不是玩具：

```
上传 → 抽取(extract/OCR) → 分块(chunking) → 向量化(BGE-M3，降级 bigram)
                              ↓
查询 → Glossary 归一化 → ① GraphRAG 实体链接+子图遍历（置信≥阈值则短路）
                        → ② BM25 稀疏检索
                        → ③ 向量稠密检索（矩阵化 numpy 余弦）
                        → ④ Reverse HyDE 兜底（chunk 假设问题匹配）
                        → RRF 融合 → LLM Rerank → 返回 hits
```

RAG 的本质特征：**无状态（stateless）**。每次查询重新检索、重新生成，对话结束一切丢失。它的强项是**精确定位**，弱项是**跨文档综合**与**知识演化**。

## 二、核心区别：一张表看透

| 维度 | 常规 RAG | LLM Wiki（Karpathy） |
|---|---|---|
| **状态** | 无状态，每次查询重置 | 有状态，持久化累积 |
| **知识流向** | Source → LLM → 答案 | Source → LLM → **Wiki** → LLM → 答案 |
| **累积性** | 无复合效应，第 100 次问和第 1 次一样笨 | **复合知识效应**，越用越厚 |
| **跨文档综合** | 弱项（靠 rerank 硬凑 top_k 片段） | **强项**（页面级交叉引用 + 矛盾页） |
| **知识演化** | 加新源**不更新**旧理解 | 新源**丰富**既有页面 |
| **维护开销** | 人工整理摘要/标签/连接 | **LLM 自动维护** |
| **可解释性** | 分块级溯源（chunk → source） | 页面级溯源，**但摘要会抽象掉原文** |
| **主要风险** | 知识不沉淀，"每天从零读同一本书" | **幻觉污染固化**、质量控制、上下文窗口 |
| **产物** | 一次性答案 | 可版本控制、可人工审阅的**持久工件** |
| **规模甜区** | 1,000+ 文档（规模越大越划算） | **几十 ~ 几百篇**（~100 源 / 数百页） |
| **成本模型** | Embed 一次，检索多次（低延迟高吞吐） | LLM 每查询读文件（**token 重**） |

## 三、优劣分析：谁的短板在哪

### 3.1 LLM Wiki 的四个真优势

1. **复合知识效应** —— 知识随每个新源累积深化。第 10 篇关于同一主题的论文不只是"能回答一次查询"，而是**通过比较分析加深既有页面**。
2. **维护自动化** —— 摘要、标签、交叉连接由 LLM 自动生成维护，人工从"整理员"变成"审阅员"。
3. **自动交叉引用** —— 页面间连接由 LLM 主动发现（这正是人做不动、RAG 也不做的事）。
4. **实现 Memex 愿景** —— 呼应 Vannevar Bush 1945 年设想的个人知识机器：**可追溯、可生长、可对话**的知识网络。

### 3.2 LLM Wiki 的四个真风险（必须正视，不是"缺点"是"约束"）

1. **幻觉污染固化** ⚠️ **最致命** —— RAG 的错误是**一次性**的，下次查询就没了；LLM Wiki 的错误会**写进页面、被后续引用、指数级扩散**。RAG 错了是「回答错了」，Wiki 错了是「知识错了」。
2. **可扩展性天花板** —— `index.md` 塞不进上下文窗口时，纯 Compile 模式就崩了。**约 100 篇舒适，500 篇紧张，1000+ 必须上检索层**。
3. **质量控制挑战** —— LLM 自动生成内容质量难保；需要 Lint + 人工审阅双保险。
4. **人工监督复杂度** —— "谁来审、审什么、审到什么粒度"没有现成答案。

### 3.3 RAG 的三个被低估的真价值

1. **精确溯源** —— 逐 chunk 对应原文，监管/合规场景**必须**能引用具体段落。Wiki 的摘要天然抽象掉原文。
2. **低延迟 / 高吞吐** —— 预计算 embedding，查询 O(向量检索)；Wiki 每查询要 LLM 读文件，**token 消耗高一个量级**。
3. **多团队访问控制** —— RAG 可在检索层做 per-document ACL；扁平 Wiki 没有权限模型。

### 3.4 关键校准：Karpathy 不是"否定了 RAG"

社区分析给出了最清醒的一句总结：

> **Karpathy 跳过 RAG 不是因为它不好，而是因为他的规模不需要。** 随着规模增长，RAG 不是替代品而是**互补品**。

这一点很重要——把 LLM Wiki 当成"RAG 杀手"来理解是**误读**。

| `document_chunks` | **5758** | 平均 438 字符/块，最大 5681 |
| `entities` | **189** | 需求类为主（子系统需求 24 / 验证用例 24 / 单元需求 21…） |

**源文档分布（关键发现）**：

```
OMG SysML V2 (1).pdf        2606 块  ← 规范原文，占 45%
Kernel Modeling Language.pdf 2011 块  ← 规范原文，占 35%
Guide to writing Requirements 855 块
SysML-v2-AI建模知识文档.md     270 块  ← 这才是"人写的知识页"
```

**判断**：**6 篇源 → 5758 块的"薄素材、碎切分"形态**。两个官方规范 PDF 占 80% 的块，是典型的**需要"编译"而不是"检索"**的素材：SysML v2 规范适合被提炼成"语法要点 / 建模惯例 / 常见错误"的**结构化页面**，而不是 2606 个待检索的碎片。

**这个规模（6 源 / 数千块 / ~200 实体）正落在 LLM Wiki 甜区（几十~几百源），同时又没大到必须纯 RAG。**

### 4.2 已有能力盘点（重要：累积层已存在）

| LLM Wiki 要素 | 本工程现状 | 位置 |
|---|---|---|
| `raw/` 不可变证据 | ✅ 已有 | `document_chunks` + `data/uploads/` 源文件副本（`source_copy_path`） |
| `wiki/` 编译页 | ⚠️ **部分** | `SysML-v2-AI建模知识文档.md`（270 块）是唯一"知识页"；`agent_memory`/`project_memories` 是**非页面形态的编译产物** |
| Schema / 宪法 | ✅ 已有 | `AGENTS.md`（58KB）+ `core/config.py`（rag.* 参数组） |
| Ingest 工作流 | ✅ 已有且更强 | `knowledge_pipeline/ingest.py` + `knowledge_reflow.py`（经验回流） |
| Query 工作流 | ✅ 已有 | `agent/rag.py::retrieve()` GraphRAG+混合检索 |
| **答案反吸收** | ❌ **缺失** | 检索结果**不回流**为知识页 |
| `index.md` 目录 | ⚠️ 弱 | 有 `glossary` 词典、无页面级目录 |
| **Lint 体检** | ❌ **缺失** | 无矛盾检测（`ConflictDetector` 只在建模写入侧用，不扫知识页） |
| 交叉引用 `[[page]]` | ❌ **缺失** | 无页面间链接 |

### 4.3 最关键的发现（这是本次分析的靶心）

**累积层已经建好，但检索侧完全不消费它。**

实测证据：

- `agent/rag.py::retrieve()` 全文件搜索 `memory` —— **仅 1 处命中**，且是 `config.get("graph_db", "use_memory", False)`（图谱侧的开关，与 `agent_memory` 表无关）。
- `agent_memory`（125 条）、`project_memories`（24 条）的消费者在 **`agent/pipeline_parts/memory.py`**（pipeline 注入 Constitution 块），**不在 RAG 检索链路上**。
- `knowledge_reflow.py`（经验回流）确实在**写**记忆，但**没有任何检索路径把它读回来参与召回**。

**后果**：`knowledge_reflow.py` 的模块 docstring 写着「知识层是**活资产**——每次会话/评审/变更产生的结论不流失，成为下次任务的记忆上下文」，但**结论只被 pipeline 一次性注入，不参与 RAG 的召回排序**。也就是说——

> 系统具备了"摄取→沉淀"的半条链路，但缺了"沉淀→被下次检索消费"的闭环。

这正是 LLM Wiki 相对纯 RAG 的**核心增益点**（复合知识效应），也是**本工程投入产出比最高的落点**。

### 4.4 现有 RAG 的其他可优化点（顺带核查）

| 现象 | 证据 | 影响 |
|---|---|---|
| **chunk 粒度偏碎** | 2606 块/规范，平均 438 字符 | 语义不完整，rerank 难判相关性 |
| **top_k 偏小** | `rag.top_k=4`、`chunk_hits[:3]` | 跨文档综合时上下文不足 |
| **有 rerank 无"选页"** | `services/rag_rerank.py` 只做相关性打分 | 缺少"该看哪几页"的**导航层** |
| **矛盾只在写入侧检测** | `ConflictDetector` 用在建模写入 | 存量知识页之间的矛盾无人扫（=缺 Lint） |
| **双引擎路由统计存在** | `query_routing_stats` | ✅ 这个已有，可用于识别"哪些查询反复出现"→**该编译成页** |

最后一条其实是**已经埋好的金子**：`query_routing_stats` 记录了每次查询的 route/命中数/延迟，**这正是识别"高频问题 → 该沉淀为 Wiki 页"的数据源**，现在没人用它。

## 五、优化建议：混合架构（Wiki 编译层 + RAG 长尾层）

### 5.1 总架构

```
┌──────────── raw / 不可变证据 ────────────┐
│ document_chunks (5758) + data/uploads/   │
└──────────────────┬───────────────────────┘
                   │ Ingest（已有）
                   ▼
┌────────── Wiki 编译层（新增/强化）──────────┐
│ knowledge_pages（页面级结构知识）           │
│  ├─ 语法要点 / 建模惯例 / 常见错误          │
│  ├─ 交叉引用 [[page]]  + index 目录         │
│  └─ 矛盾页（contradictions）                │
│ ↑ 复用已有的 agent_memory / project_memories│
└──────────────────┬───────────────────────┘
                   │ Query：**wiki 先答，RAG 兜底**
                   ▼
┌──────── RAG 长尾层（已有，保留）────────────┐
│ GraphRAG + BM25 + 向量 + HyDE + RRF + Rerank│
│ 用途：精确定位、逐句溯源、长尾事实查询       │
└─────────────────────────────────────────────┘
                   │ Lint（新增）
                   └→ 孤儿页 / 断链 / 矛盾 / 缺失引用
```

**分层原则**（社区总结的最实用三条）：

1. **Hot / Cold 分离** —— 高频引用的核心知识 → Wiki 层；不常访问的长尾 → RAG 层。
2. **Wiki-first, RAG-fallback** —— 先查 Wiki，答案不足才落到 RAG；RAG 捞出有价值内容 → **回流进 Wiki**。
3. **Compile 管综合，RAG 管定位** —— 跨文档分析走 Wiki，具体段落/事实精确定位走 RAG。

### 5.2 分阶段落地（按性价比排序）

#### P0：把"检索消费记忆"接上（低风险、当天可做、收益最大）

**做法**：在 `agent/rag.py::retrieve()` 里，把 `agent_memory` / `project_memories` 的检索结果作为**一路召回源**并入 RRF 融合（与 BM25/向量/HyDE 并列，权重可配 `rag.memory_weight`）。

**为什么这是 P0**：
- 累积层（125 + 24 条）**已经存在**，只差读取；
- 改动面小（加一路召回 + 一个配置项），不动 schema、不动前端；
- **立刻兑现 `knowledge_reflow.py` 的设计承诺**——"结论不流失，成为下次任务的记忆上下文"。

**验收判据**：构造一个"上次会话已沉淀结论"的查询，断言命中结果里出现该记忆条，且 `recall_reason` 标注"记忆"；同时做**变异测试**（把消费关掉，断言该条不再出现）——避免写出空转断言。

#### P1：建立页面级编译层（`knowledge_pages`）

**做法**：对每篇源文档（尤其两个规范 PDF）生成**结构化知识页**：

```markdown
# SysML v2 建模惯例

**来源**：OMG Systems Modeling Language V2 (1).pdf（chunk 序列 1200-1800）
**更新**：2026-09-29

## 概览
...

## 核心要点
- 包结构约定 → 见 [[package-structure]]
- 变体点定义 → 见 [[variants]]

## 常见错误
- ...

## 存疑 / 待确认
- ...

## 相关页面
- [[kerml-basics]]
```

**关键改动**：`document_chunks` 加 `page_id` 外键（或建 `knowledge_pages` + `page_chunks` 关联表），**chunk → page 双向可达**，保留逐句溯源能力（这是 RAG 的强项，不能丢）。

**注意（避坑）**：本项目此前在"AI 产物收编"上已经踩过 model collapse 的坑，所以**编译产物必须标注 `origin='ai_generated'`**，且检索默认排除（`_ai_clause` 已实现）——**页面层要放在"人工/AI 混合审核"之后才进主检索**，否则幻觉污染固化会立刻发生。

#### P2：加 Lint 体检（对付幻觉污染的唯一系统性手段）

**做法**：新增 `knowledge_lint.py`，定期检查：

| 检查项 | 判据 | 动作 |
|---|---|---|
| 孤儿页 | 无任何页引用、不在 index | 提示补链或删除 |
| 断链 | `[[page]]` 指向不存在 | 报错 |
| **页面矛盾** | 复用 `ConflictDetector` 扫页面间陈述冲突 | **人工审阅队列** |
| 缺失交叉引用 | 提到某主题但未链接 | 建议补链 |
| **无源锚点** | 页面陈述找不到对应 chunk | **高风险，直接标记不可信** |

最后一条是**幻觉污染的探测器**——LLM 编造的内容找不到源 chunk，这是最硬的判据。

#### P3：答案反吸收（`outputs/` → `wiki/`）

**做法**：把高质量查询回答（经用户确认/评分）沉淀为新页面或并入既有页。

**数据源现成**：`query_routing_stats` 已记录每次查询——**统计高频 query，优先把它们的答案编译成页**，这是"该编译什么"的客观依据，不是拍脑袋。

**必须设闸门**：反吸收**绝不能自动生效**，必须走"候选 → 人工审阅 → 发布"，理由同 P1（model collapse）。

### 5.3 不建议做的事（明确排除）

| 不做 | 理由 |
|---|---|
| ❌ 用 LLM Wiki **替换** RAG | 违反社区共识；精确定位/逐句溯源是 RAG 不可替代的强项 |
| ❌ 全量重编译（每次新增源重建所有页） | token 成本高且质量方差大，应做**增量 ingest** |
| ❌ Wiki 页面直接进主检索 | 幻觉污染固化风险；必须先过 `origin='ai_generated'` + 审核闸门 |
| ❌ 为"更先进"而引入向量 DB 换 Sqlite | 当前 5758 块规模，Sqlite + numpy 矩阵化完全够；换库是纯负债 |

## 六、回到最初的问题：区别与优劣

### 6.1 本质区别（一句话）

> **RAG 问"给定一个查询，哪些片段最相似？"；LLM Wiki 问"给定所有源，什么是结构化的知识？"**
>
> 前者是**检索**，后者是**编译**。RAG 是**翻书**，Wiki 是**翻笔记**。

### 6.2 优劣势总表

| | 常规 RAG | LLM Wiki |
|---|---|---|
| **最擅长** | 精确定位、逐句溯源、大规模（1000+ 文档）、低延迟高吞吐 | 跨文档综合、知识演化、小规模（几十~几百源）、越用越厚 |
| **最怕** | 跨文档综合、知识不累积 | **幻觉污染固化**、规模超窗、token 成本 |
| **错误代价** | 一次性（下次查询即消失） | **持久性（写进页面后扩散）** |
| **维护** | 人工整理 | LLM 自动维护 + Lint 体检 |
| **产物** | 一次性答案 | 可版本化、可审阅的持久工件 |

### 6.3 对本工程的最终判断

**三句话结论**：

1. **规模上，本工程在 LLM Wiki 甜区**（6 源 / ~200 实体），但也**没有大到可以丢掉 RAG** —— 两个规范 PDF 的 4617 个块需要精确检索与溯源。
2. **能力上，本工程缺的不是 RAG，是"编译层 + 闭环"** —— 累积层（`agent_memory`/`project_memories`）**已建成但检索不消费**，这是最高性价比的修复点。
3. **架构上，正解是混合** —— Wiki 编译层（跨文档综合、惯例沉淀）+ RAG 长尾层（精确定位、逐句溯源），**Wiki-first, RAG-fallback**，并用 Lint 守住幻觉污染这条唯一红线。
