## 三、embedding 可用性实测（上一轮结论是错的）

### 探针先踩了一个坑

第一版探针用 `/chat/completions` 测 embedding provider（108）⇒ 得到 **404**。
⚠️ **那是探针用错端点，不是服务不可用** ——
embedding 服务通常只暴露 `/embeddings`。
（与 MEMORY「变异未生效 ≠ 门禁没抓住」同族：**探针的错 ≠ 被测物的问题**。）

### 正确端点复测

| id | 名称 | 端点 | 结果 |
|---|---|---|---|
| 106 | qwen3.7-text-embedding（公网阿里云） | `/embeddings` | ❌ 403 Free quota exhausted |
| **108** | **Qwen3-Embedding-0.6B（内网 192.168.100.202:8004）** | `/embeddings` | ✅ **可用 dim=1024（116ms）** |

### 又发现一个探针用法错误（值得记）

用 `Embedder()` 不传 `conn` 构造 ⇒ `_api=None` ⇒ 直接降级 `bigram-tf`。
一度以为"内网 embedding 也没用上"，但真实原因是
**`__init__` 只在 `conn is not None` 时才 probe**。

查证：`grep -rn "Embedder("` ⇒ 生产代码**8 处全部传了 conn**
（`semantic.py:72`、`knowledge_engine.py:312/378`、`ingest.py:429`、
`search.py:132/323`、`history.py:642`、`memory_service.py:36`）
⇒ **生产链路确实会用 108**。

### 用生产调用方式复验

```
probe _api = ('http://192.168.100.202:8004/v1', 'Qwen3-Embedding-0.6B')
版本 = openai-compat | 向量数 = 3 | 维度 = 1024
```

⇒ **embedding 完全正常，走真向量**（不是降级）。

★ 选路 SQL 是 `ORDER BY is_default DESC, id LIMIT 1`，
108 的 `is_default=1` ⇒ 正确选中。

## 四、多用户并发：实测风险并改造

### 4.1 风险实测（决定性证据）

方法：8 线程 + `barrier` 放大竞态窗口（所有线程写完再统一读）。
每线程写入自己的标记，看有多少被别的线程覆盖。

| 模式 | 标记被覆盖 | ctx 归属错误 |
|---|---|---|
| **模块级单例**（原生产） | **7/8** | **7/8** |
| **每请求新建** | **0/8** | **0/8** |

### ★ 关键认知：清零不能替代新建

上一轮为此加的 `reset_request_state`（入口清零）只解决**顺序执行**下的
"上一轮残留"，**解决不了并发**：

```
线程 A：写 self._sysml_last_pass_code = "A的代码"
线程 B：入口 reset_request_state() → 把 A 的字段抹成 None
线程 A：收尾取回 →拿到 None ⇒ 本次产出丢失
```

⇒ 这是**两个不同维度**的问题：清零防"历史残留"，新建防"并发串味"。

### 4.2 成本实测（为什么可行）

| 项 | 实测 |
|---|---|
`AgentPipeline()` 构造 | **0.002 ms**（`__init__` 只建 5 个轻量对象） |
`_load_db_agents()` | ≈25 ms/请求，**本来就每请求跑**（无缓存白拿） |
DB 层| **每请求独立连接** + WAL + busy_timeout=30s ⇒ 并发安全，无需改 |

⇒ 额外成本 ≈0.002 ms，相对一次 LLM 调用（3~60 s）**完全可忽略**。

### 4.3 改造内容

| 文件 | 改动 |
|---|---|
| `agent/__init__.py` | 新增 `get_pipeline()` 工厂（含构造耗时观测，超过 50ms告警）；**模块级 `agent` 保留**（既有脚本/测试向后兼容） |
| `routers/conversations.py` | `from agent import get_pipeline`；chat 端点与 SSE 端点各在**函数体内**取实例 |

⚠️ **位置纪律**：实例必须在 handler / 生成器**体内**取。
提到模块级就等于退回单例（已作为门禁 A3）。

### 4.4 真实并发端到端验证（4 并发，真实 LLM）

```
#0 ✅ 22.7s  md5 各不相同
#1 ✅ 22.7s
#2 ✅ 28.0s
#3 ✅ 90.5s
成功 4/4 | 产出雷同=False ⇒ ✅ 并发下产出未串味
```

### ⚠️ 必须说明的性能观察

并发下有一个请求耗时 **90 秒**，而单请求基线是 **24~25 秒**。
已排除改造因素：
- Pipeline 构造仅 **0.002 ms**；
- DB 是每请求独立连接；
⇒ **是模型侧排队/吞吐限制**（104 单请求本身 10.7 秒），
不是并发改造引入的。若并发用户变多，需考虑多 provider 负载均衡。

### 4.5 门禁 `tools/verify/verify_pipeline_concurrency.py`（9 断言 / 变异 3-3 判红）

| 判据 | 内容 |
|---|---|
| A1 | 路由用 `get_pipeline()`，且无裸用 `agent.execute*`（正则+ 源码扫描） |
| A2 | 工厂连调两次返回**不同实例** + 构造成本 <50ms |
| A3 |调用点在**函数体内**（AST 定位，防提到模块级） |
| A4 | **双向实测**：共享单例**必须**观测到覆盖（证明风险真实）+ 新建必须 0 覆盖 |
| A5 | 模块级 `agent` 仍保留（向后兼容） |

★ A4 的双向设计是关键：**如果单例测不出覆盖，说明风险不成立，门禁就该撤**——
而不是让一个基于错误前提的门禁长期存在。
