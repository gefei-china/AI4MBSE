## 2. 文章思想 → 本系统的逐条判据

先对齐**适用边界**（避免把不适用的条目当缺口）：

- ✅ **适用**：上下文多次交接失真、Subagent 蔓延、Frankenprompt、评估局部化、渐进式披露、单变量迁移纪律。
- ⚠️ **部分适用**：文章面向「企业级客服/研究类 Agent」，控制逻辑可交给模型动态决定。本系统是 **MBSE 平台**，带 SysML v2 校验器、本体一致性门禁、SHACL、HIL 三级确认、分支/项目权限等**硬约束**——这些必须留在 Harness 里写死，不能因为「模型更强了」就下放。文章自己也说「验证、审批等硬性限制通过 Tools 处理」，与本平台兼容，但**不能照搬「把审批交给模型」**。
- ❌ **不适用**：文章把「项目/分支隔离」当作可以合并的上下文；本平台的 `branch`/`project_id` 是甲方需求里的硬隔离维度，且用户既定政策是「不强制、不默认提供」（§6.5），不能一刀切合并到单上下文。

### 13.3 三个真实缺口（都是「设计了但从未跑过」的产物）

1. **断流样本被当作有效样本静默进基线**。`_live_case` 原来只把 `done` 记进 `sse_done` 字段、不参与判定
   ⇒ 一次异常被吞、流提前结束的会话，会拿着「空会话」的评分进基线（假红），或恰好命中历史残留（假绿）。
   现在一律判无效并写明原因。
2. **`--mode live --save` 能伪造出 live 基线**。`score_dataset()` 的 `conv_id_map` 为空时会回退
   `case["conv_id"]`（历史会话），却照样把 `mode=live` 写进 `eval_reports` ⇒ P1 前置可被「一条假报告」满足。

3. **live 跑完不落 `eval_reports`**。`run` 只写 `tmp/*.json`，而前置判据要查库 ⇒ 结构上永远无法判定满足。
   补齐路径固定为 `run_arch_ab.py run --mode live` → `golden_e2e.py --mode live --conv-map <map>.json --save`；
   门禁按「库内 `detail` JSON 的 `mode` + 每例 `conv_id ≠ source_conv_id`」双重判定。
4. **补齐路径本身也是断的**。`run --mode live` 的结果里有每例 `conv_id`，但从不导出
   `case_id→conv_id` 映射，而 `golden_e2e --conv-map` 正需要这份文件 ⇒ 上面那条「补齐路径」
   照着敲会卡在中间（本批自查发现，已补）。现新增 `run --emit-conv-map <path>`：
   同例多轮优先取「最后一次通过的」，全都没通过则取最后一次（如实反映），产出 LF-only JSON；
   offline 下使用该参数直接 `rc=2`（没有新会话就没有映射）。

> **「合格 live 基线」的机器定义**（`valid_live_report()`，门禁与变异共用同一处实现，防两份漂移）：
> `mode == 'live'` **且** `dataset_id` 与当前数据集一致 **且** 例数一致 **且** 每一例 `conv_id != source_conv_id`。

**D1 只清了 `agents` 表与资产快照，插件库没动。** 实测退役后仍有 8 条

### 14.2 能力承接评估（不是比描述字数）

比对基准取 **D1 前的备份库** `backups/mbse.db.bak-before-p0-d1-20261116_005133.db`

唯一未覆盖的硬规则是需求视图的「只输出代码，不输出解释性文字」。**判定不补**，理由是它已失效：

### 14.3 实际改动（软删除，照抄仓库既有范式）

参照已退役的 `plugin#56/94/96/97/146` 的写法（`plugins.status='removed'`
+ `capability_registry` 转 `disabled/deprecated` + **`plugin_versions` 不动**）：

| 表 | 改动 | 行数 |
|---|---|---|
| `plugins` | `status` published → **removed** | 8（id=46~53） |
| `capability_registry` | `active/published` → **disabled/deprecated** | 8 |
| `plugin_versions` | **不动**（既有 5 个 removed 插件的版本记录仍是 published） | 0 |

历史审计 24 行完整 —— 可单步回滚（回滚 SQL 见留痕 JSON）。

**为什么必须是 `removed` 而不是 `disabled`**（这一条容易踩错）：
`plugin_system/store/queries.py::list_market` 的 where 是
`scope='public' AND status IN ('published','disabled')` ⇒ **改成 `disabled` 市场照样显示**。
`list_mine` 的 where 是 `status!='removed'` ⇒ 只有 `removed` 能同时从两个入口消失。
新门禁的 X6 变异就是专门守这个陷阱的。
