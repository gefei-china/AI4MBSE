# 知识治理模块问题诊断与优化方案（代码与架构层）

> 版本：v1.0 | 日期：2026-08-18 | 方法：全量代码走查（entity_resolver / vector2graph / ontology 系列 / knowledge_engine / knowledge_pipeline / knowledge_reflow / glossary / services / routers / repositories / migrations）
> 定位：与《知识管理模块对比分析与优化方案》（功能层 Gap）互补，本报告聚焦**代码质量与架构根因**。

---

## 0. 结论先行

1. **架构级根因只有一个：融合在写后（post-write），与"Staging 写前融合"标准架构相反。** 实体经 `confirm_candidates` 直接写入 entities 主表，再由 entity_resolver 全量扫描事后消歧/合并。v2g_candidates 是最接近 Staging 的结构，但其中不做 canonical 归并，只是"待确认暂存"。
2. **发现 2 个正确性级 Bug（P0 立即修）**：① `entity_resolver.rollback_merge` 回滚时把关系两端都改成 dup_id（数据损坏）；② `embedder._embed_bigram` 返回 `Counter.values()`，向量维度随词表漂移，bigram 降级通道的向量**跨文本不可比**——降级检索结果在数学上是错的。
3. **1 个数据安全隐患（P0）**：`search.retry_document` 先 DELETE chunks 再重新 ingest，无事务包裹，中途失败文档数据全丢。
4. **分层名存实亡**：routers/knowledge.py 1874 行（40+ 端点）vs services/knowledge_service.py 97 行；entity_resolver / vector2graph / glossary / knowledge_reflow / ontology_semantics 五个模块全部绕过 Repository 直接裸 SQL。
5. **两处循环依赖**（entity_resolver ↔ vector2graph；knowledge_engine ↔ knowledge_pipeline），靠函数内延迟 import 掩盖，是模块边界错误的信号。
6. **性能地雷**：实体检测/冲突检测 O(n²) 全表配对、`_disambiguate` O(N×M)、`hybrid_search` 全量 chunks 入内存 + BM25 索引每查询重建。数据量上万后全部不可用。

## 1. 现状链路盘点

```
ingest_document (ingest.py:114)
 → extract_text → chunk_text_structured → Embedder.embed_with_version
 → document_chunks (parse_status 状态机)
 → vector2graph.extract_candidates (:410, LLM 受本体 schema 约束)
 → v2g_candidates (pending)
 → 人工 confirm_candidates (:667) → GraphStore.create_node/edge
 → entities / relations（复合主键 id+branch，分支级版本行 ✓）
 → 【写后】entity_resolver 全量扫描消歧 / merge_entities / conflict_detect
```

**已具备（亮点，不要推翻）**：候选暂存 + 人机审核闭环（review_candidate / domain_review_queue / conflict_adjudicate）、候选级置信度与来源字段、分支级版本行、审计埋点（core.audit）、本体校验（validate_node）、发布门禁（_release_guard）。

**缺失（对照标准治理架构）**：独立 Staging schema 与写前融合闸、入库质量闸（无质量分拦截）、Mention/Canonical 双层模型、精确到 chunk 的溯源（当前所有候选统一挂 `chunk_ids[0]`，vector2graph.py:548/566）、实体级置信度写入（entities.confidence 流水线不写）、实体时态版本链。

## 3. 架构问题：依赖环与分层失效

```
当前（坏味道）：
  entity_resolver ←→ vector2graph        ← 互相 import，函数内延迟引用掩盖
  knowledge_engine ←→ knowledge_pipeline ← engine 反向 import pipeline
  5 个引擎 ──裸SQL──▶ entities/relations ← KnowledgeRepo 被架空
  routers/knowledge.py (1874行) ──▶ 直连引擎，service 仅 97 行空转

目标：
  routers(薄) → services(编排) → engines(纯算法) → repositories(唯一SQL出口) → DB
                   ↕
              Staging 融合区（写前）──质量闸──▶ 主图（写后只读调和）
```

**循环依赖的根因**：entity_resolver 需要 vector2graph 的 `_normalize_mentions`（归一化逻辑放错了位置），vector2graph 又需要 resolver 的消歧判定。**归一化/规范化函数应下沉到独立 `text_normalize.py` 工具模块**，两引擎都依赖它，环自然解开。knowledge_engine ↔ pipeline 同理：embed_with_version 的降级策略配置应放 config 层而非互相引用。

## 4. 优化方案

### 4.1 P0 修复包（1-2 天，先止血）

| 项 | 动作 | 文件 |

| F1 | 修 rollback_merge：回滚 UPDATE 分两条，分别处理 source_id / target_id 端点，补 WHERE 条件；补事务包裹 | entity_resolver.py:341 |
| F2 | 修 _embed_bigram：构建持久化固定词表（vocab 表或 vocab.json），bigram 特征 → 固定维度映射（哈希 trick 也可：feature → md5 % 4096 维） | embedder.py:118 |
| F3 | retry_document / merge_entities / reindex_document 全部包事务（BEGIN IMMEDIATE + try/rollback） | search.py:151/:218, entity_resolver.py:225 |
| F4 | 全局清理 `except: pass`，至少记日志 + 审计事件 | 全模块 |
| F5 | 删除死代码（_mock_extract、find_duplicates、441-443 死赋值） | vector2graph.py, entity_resolver.py |
| F6 | 人名默认值改从 current_user 上下文取，禁止 '李工'/'王工' 字面量 | knowledge_repo.py, knowledge_service.py |

### 4.2 P0-P1 架构改造：Staging 写前融合（对齐标准治理架构）

> 与《本体交互设计与数据融合详细设计》§2 的双阶段架构对齐，落到本代码库的最小改造路径：

1. **v2g_candidates 升级为真 Staging**（不新建表群，最小改动）：
   - 拆语义：加 `candidate_kind` 列（entity/relation/reflow），解决一表三义
   - 加 `mention_json` 列：保留原始提及文本 + 精确 chunk_id + 行号区间（修 C10 溯源）
2. **写前融合闸**：confirm_candidates 之前插入 `staging_fuse()` 步骤——批内 Blocking（normalized_name + 嵌入近邻）→ 四路加权相似度 → 三阈值分流（auto-merge / 人工队列 / 新实体），阈值入 config 表（修 C7）
3. **Canonical 层**：entities 表加 `canonical_id` 列指向黄金实体（暂不拆表，一期够用），别名入 `entity_aliases` 独立表（替代 properties.aliases 冗余与硬编码别名表）
4. **入库质量闸**：批次级抽检接口 + 精度 < 90% 禁止批量 confirm（修 B5 的闸口）
5. **写后调和降级为定时作业**：entity_resolver 的全量扫描改为 nightly job + Blocking 化（修 C1）

## 5. 明确不做

- 不推翻现有候选-审核-确认闭环（人机协同骨架是对的，只是融合位置错了）
- 一期不引入独立 Mention 表（用 v2g_candidates.mention_json 过渡，数据量验证后再拆）
- 不替换 SQLite（私有化约束不变，性能问题靠 Blocking + 索引解决，不靠换库）
- 不动 ontology_blueprint / ontology_owl / ontology_reasoning 的主体（相对干净，仅 P2 补强）
