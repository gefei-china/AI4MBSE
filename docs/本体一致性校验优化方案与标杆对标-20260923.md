## 0. 结论摘要

1. **骨架是对的，而且它已经干成了活**：6 类规则 + 双重身份（结构体检 + 发布硬门禁），真库实测 **52 类型 / 12 问题 / 高 9**，确实拦住了带病发布。
2. **但"报了不能修、修了不留痕、拦了没有出路"**：高危只报不改；结果不落库、无历史；报错文案让用户"确认风险后豁免"，而**全仓不存在任何豁免实现**（`ontology_version.py:294` 是唯一一处字符串）。
3. **比"9 条高危"更重的一条（本轮新查明）**：把校验器对**存量 249 条边**全量重放 → **141 条（56.6%）被判非法**；**13 个关系类型里 9 个在 28 个注册类型中不存在任何合法组合（完全不可用）**。也就是说，问题不只是"本体发不出去"，而是**规则与存量数据互相矛盾**——这正是上位文档 §2.6 提出的"SHACL 向后兼容检查：shape 变化须**对存量图重放校验**"要防的事，而我们只做了前半句（校验 schema，从不校验"规则 vs 存量"）。

**本文的核心主张**：这项能力的优化重点**不是"再加几条规则"，而是三件事**——
① 把"报告"升级为**可解释、可修、可留痕、可豁免**的闭环；
② 增加一个**新视角**：规则与存量数据的自洽性（`data_rule_conflict`），并以存量数据为金标；
③ 把校验从"事后的按钮"前移到**写入时 + 发布前 + CI**。

### 1.2 事实 A：9 条悬空是「两段漂移」，不是随机脏数据

**三态盘点**（13 个关系类型）：`BAD 9` / `MISS 2`（`执行`、`连接` 无 dom/range）/ `OK 2`。

**干净对照**：OK 的 2 个（`DERIVES`、`VERIFIED_BY`）恰好**只引用通用需求类**；BAD 的 9 个**全部引用域特有硬件类**（`巡飞弹`/`光电吊舱`/`战斗部`/`引信`/`弹翼`/`飞控计算机`…）。

**批次证据**（`ontology_types.created_by` + `project_id`）：

| 批次 | entity | relation | attribute |
|---|---|---|---|
| 演示初始化 | 10 | **11** | 0 |
| 领域切换 | 17 | 0 | 11 |
| （空） | 1 | 2 | 0 |

- 52 个类型 **全部** `project_id='project-satnet-broadband'`（**无**多项目混装问题）；
- **关系类型 100% 来自「演示初始化」**，其 dom/range 是一套**当前域不存在的巡飞弹（UAV）词表**；
- 「领域切换」替换/补充了 entity 与 attribute，**完全没有碰 relation 的 dom/range**。

**根因**：`演示初始化` 用 UAV 词表建关系约束 → `领域切换` 换域时只处理实体类型与属性 → 关系约束悬空。**两段漂移叠加。**

**并且写入方已不可考**：`created_by='领域切换'/'演示初始化'` 在**代码里查无此串**（全仓 `grep` 含 js/html/json/md 为空）、**在 git 全历史里也查无此串**（`git log -S` 两次均空）、`users` 表无同名账号。
→ 结论：**不能靠"修调用方"根治**，只能"**修数据 + 加守卫**"（守卫即 §1.3 导出、§4 O1-2 落地的"规则 vs 存量自洽"）。

> 这一条同时纠正了上一轮核查报告里的一个措辞：那 9 条不是"历史演示残留的脏数据"，而是**换域链路不完整留下的半截约束**——定性从"数据脏"改为"链路缺陷"。

### 1.3 事实 B：存量数据与规则互相矛盾（本轮最重）

把当前 `OntologyValidator.validate_edge` 对**全部存量边**重放一遍：

```
存量边全量重校验： 249 条，其中 141 条按当前本体校验器【非法】（56.6%）
按关系类型分布： SATISFIES 54 · CONTAINS 48 · ALLOCATED_TO 18 · COMPOSED_OF 12 · TRACE 6 · VERIFIED_BY 3
```

**关系类型可用性**（是否存在任一"注册类型组合"能通过）：

| 判定 | 关系类型 |
|---|---|
| ❌ **任何注册类型组合都被拒 → 完全不可用**（9 个） | `ALLOCATED_TO` `COMPOSED_OF` `CONNECTS` `CONTAINS` `DEPENDS_ON` `FLOW_TO` `REALIZES` `SATISFIES` `TRACE` |
| ✅ 部分可用 | `VERIFIED_BY`（声明 src=系统需求，但存量 src 还有 利益相关方需求/单元需求/子系统需求 → **3 条存量边非法**） |
| ✅ 完全一致 | `DERIVES`（声明 == 存量，**13 个里只有它一个**） |

**关键含义**：这不只是"本体发不出去"，而是——
- 这 9 类关系（**组成 / 包含 / 分配 / 满足 / 追溯 / 连接 / 依赖 / 流 / 实现**）**今后任何新边都写不进去**（`GraphStore.create_edge:535` 先过校验）；
- 库里已有的 **141 条边**一旦被"重新写入"（改实体后重存、`confirm_candidates` 入库、merge/sync 重放、全量重校验、迁移重跑）就会被自家校验器拒绝——**数据与规则互相判非法**；
- 而 `_ontology_check` 只看 schema 结构，**永远看不到这 141 条**（它不查"规则 vs 存量"）。

> 纪律沿用：**规则应当受存量数据约束**。新增规则不得让"昨天还合法的边"变成非法，除非显式声明迁移方案——这正是上位文档 §2.6「SHACL 向后兼容检查：shape 变化须 diff + **对存量图重放校验**，阻断破坏性变更」的工程含义。

## 2. 标杆怎么做的（专项：**校验能力本身**）

> 上位模块调研已覆盖各家的"平台形态"；本节只取**校验 / 约束 / 修复**这一点，且优先取能直接落地的具体机制。

### 2.1 报告契约 —— W3C SHACL

- **报告是结构化的、字段固定的**：`sh:focusNode`（哪个节点）/ `sh:resultPath`（哪个属性）/ `sh:sourceConstraintComponent`（哪条约束）/ `sh:resultSeverity` / `sh:resultMessage`；顶层 `sh:conforms` 布尔。
- **三档 severity 是规范内建的**：`sh:Violation`（必须修）/ `sh:Warning`（应修）/ `sh:Info`（提示）；流水线**只对 Violation 阻断**。
- **shape 即契约**：shapes 与本体同仓版本化；**shape 的改动 = 数据契约的改动，要和改 API schema 一样走评审**；把 SHACL 文件交给供应商 = 给对方一份"**可执行的验收规格**"。
- **shapes-as-tests 是最高价值的习惯**：shapes 进 CI；每个 PR 触发校验；违规 fail build；**必须维护"已知坏样本"（known-bad fixture）——它必须挂，否则说明 shape 没瞄准**。
- **头号坑：shape 没有 target = 静默假通过**（什么都不查却报"通过"）。
- **2025–2026 的新共识（LLM 场景）**：模型提三元组 → SHACL 校验 → **把违规报告回灌进 prompt** → 模型在预算内重试。

**可抄**：① 报告字段固定成契约（含 `code`/`target`/`message`）；② severity 三档内建而非写死；③ **金标 fixture（好的必过、坏的必挂）**；④ **"报告回灌"**——我们已有 `schema_text()` 注入 LLM prompt，把**违规清单**也回灌就是同一机制的低成本版。

### 2.2 规则目录 —— OOPS!（OntOlogy Pitfall Scanner）

- **29 条坑位目录（P1~P29）**，每条含：名称、说明、**受影响元素清单**、**严重度（Critical / Important / Minor）**、**修复建议**；报告**按坑位分组**、每组可折叠。
- 报告用"坑位 × 案例数 + 严重度徽章"呈现，**同一坑位的所有违例聚在一起**（而不是按元素平铺）。
- **提供 REST Web Service**，供外部工具/CI 直接调用。
- 设计目标明写两条："**给每条坑位补充 how-to-solve 指南**，以便诊断后便于修复"、"**允许用户按类别或单条坑位选择检查哪些**"。
- 与我们的对应关系很直接：`cycle`≈P6、`isolated`≈P4、`missing_dom_range`≈**P11**、`bad_dom_range`≈P19/P11 邻域、`duplicate`≈P7 邻域。

**可抄**：① **规则目录化**（每条规则一个条目：code / 名称 / 维度 / 严重度 / 解释模板 / 修复建议 / 开关）；② **按规则分组展示**；③ **规则可勾选启停**；④ REST 化（我们已有端点，补参数即可）。

### 2.3 解释机制 —— Protégé Explanation Workbench

- 推理机不只回答"不一致"，还给出 **justification（依据）**：**使该结论成立的最小公理子集**；可浏览、可对比多个 justification。
- 两个精细化概念：**Laconic**（去掉公理里的冗余部分）/ **Precise**（进一步最小化到公理内的最小片段）。动机写得很清楚：**冗余会误导用户，并导致"过度修复"**（删掉了比必要更多的东西）。
- 修复流程就是"**看 justification → 从中挑一条公理断掉它**"。

**可抄（"可解释 + 安全修复"的范式）**：报告不能只说"`CONTAINS` 的定义域指向不存在的类型"，要能给**依据链**：`依据 = 声明 src=[…] × 注册实体类型集合 × 存量边端点`。本轮我把三份清单并排摊开（§1.3）就是这个思路的雏形；**过度修复的反面教训**也直接适用——不要为了让校验过关就清空 dom/range，那等于砍掉约束语义。

### 2.4 工单化修复 —— Stardog ICV

- 约束是**数据**（SHACL 存在命名图里，可 SPARQL 查询、可导出）；
- **两种模式**：默认"跑一遍看违例"，**`guard mode` 在写入时强制**；
- CLI 动作面直接给出了产品化词汇：**`icv explain`（解释违规）/ `icv fix`（生成修复计划）/ `icv report`（出标准报告）/ `icv validate`（校验）**；
- 报告是规范 SHACL 报告（`sh:conforms` + 逐条 `sh:result`）。

**可抄**：**"explain / fix / report / validate 四动词"就是一个校验功能的完整 API 面**。我们缺的正是 `explain`（为什么）与 `fix`（怎么修）；而 `fix` 的落点本工程**已经建好表了**（`ontology_instance_migrations` + dry-run + apply + 状态机）。

### 2.5 约束即数据 + 例外机制 —— Wikidata 约束体系

- 约束作为**维基数据本身**存在：`property constraint (P2302)` + 约束类型项 + **参数**（允许值清单、`class` 等）。
- 三个治理参数直击我们的痛点：
  - **`constraint status = mandatory`** —— 违例分"强制 / 非强制"两档严重度；
  - **`exception to constraint (P2303)`** —— **例外白名单**，列在其中的条目不检查该约束；
  - **`constraint clarification (P6607)`** —— 写明"这条约束**为什么存在** + **建议怎么解决**"；
  - 另有 `group by`（聚合报告维度）、`constraint scope`（作用在主值 / 限定符 / 引用）。
- 违规报告**按实体页内联提示**（登录用户可见），另有 `Special:ConstraintReport` 全量页 + 机器人定期全量扫描的**专题报告页**供社区复核。
- 其自我克制值得记下：Property Validation 约束**必须足够宽松**以容纳既有/预期用法（"约束的作者未必知道该属性在其他 class 上的用法"）——**约束比数据严格就会伤到存量**，这正是我们 141 条边的写照。

**可抄**：① **豁免机制 + 强制档位**（让"本体发不出去"变成"可控发布"）；② **约束自带解释与解决建议**；③ **例外要显式登记，而不是偷偷放宽规则**；④「约束必须容纳既有数据」这条自律。

### 2.6 前移与留痕 —— Palantir Foundry

- **没有通用写入路径**：所有写必须走 `Action Type`，由 **submission criteria（旧称 validations）** 决定"这次提交能不能发生"；
- 拒绝给**机器可读错误码**（例：`SHIPPED_ORDER_CANNOT_BE_CANCELLED`），便于上层解析、恢复与解释；
- **每次尝试都留痕**（**含被拒的尝试**）：action log 记录提交者 ID、时间戳、被改对象主键，回答"谁、何时、改了什么"；
- 编辑写入 writeback 数据集，**原始数据与编辑后数据同时保留**（可对比、可回滚）；
- 组织上设 **Ontology 管理者**角色：**接变更请求、triage、评估对整体本体的影响**，并沉淀"治理检查的可扩展流程"。

**可抄**：① **拒绝也要留痕**（我们现在被 `validate_edge` 拒绝的写入**完全没有记录** → 用户只看到失败，管理者看不到"多少人卡在哪条规则上"）；② **机器可读错误码**（前端才能给出"去修 XXX"的动作）；③ **变更请求 triage 角色**（对应上位文档差异矩阵"协作与审计"行的差距）。

### 2.7 治理工作流与一键处置 —— TopBraid EDG

- 变更走**工作流状态机**：`Uncommitted → Frozen for Review → Approved → Committed`（可 reject / request further changes），权限档 viewer / editor / manager；
- **导入新版本词表自动 diff**：列出 **Added / Changed / Deleted** 术语 + **指向已用术语的失效引用**，并支持**一键处置**（移除废弃项 / 重新挂到新父级 / 整体接受新增）；
- 有 "Problems & Suggestions" 面板 + **apply-all**（建议批量采纳）；
- 把 **SHACL ↔ OWL 双向转换**、**从样本数据自动生成 shapes** 作为产品能力。

**可抄**：① **"较上次体检"的 diff（新增 / 已修 / 未动）+ 一键处置**——我们已有 `_snapshot_diff:367` 的同款思路，只是**没用在本体体检上**；② **失效引用清单**（我们的 `bad_dom_range` 就是它的"invalid references to terms you already use"）；③ 建议 → 批量采纳的交互形态。

## 3. 最值得抄的三件事

**① 约束即数据 + 例外机制（Wikidata / Stardog）**
规则、严重度、豁免、强制档位都应是**可查、可版本化、可审计的数据**，而不是写死在 `if` 分支里的常量。
→ 落点：`core/ontology_rules.py` 规则目录 + 豁免登记表 + 门禁档位对齐。
→ **收益**：本体从"被 9 条漂移锁死"变成"**可控发布**"。

**② 报告要"可解释"，修复要"最小"（Protégé justification）**
不要说"这里错了"，要能回答"**凭什么这么说、改了会怎样**"；修复要从**最小依据集**里下手，**防止过度修复**（反面就是"一怒清空 dom/range"，等于砍掉约束语义）。
→ 落点：issue 增 `evidence`（依据链）+ `fix.hint`（最小动作集）。

**③ 校验前移 + 全程留痕（Palantir / SHACL-in-CI）**
"体检按钮"是最后一道，不是第一道。标杆都是**写入时拦 + 被拒也留痕 + 规则与存量对齐 + 进 CI**。
→ 落点：拒绝留痕 + 门禁档位 + `tools/verify/verify_ontology_rules.py` 进常驻自检。
→ **收益**：从"事后体检"变成"**免疫系统**"。

## 4. 优化方案（三批，逐条给落点 / 验收 / 风险）

> **批次原则**：O0 当天可交、零风险；O1 是本轮主体（把报告升级成闭环）；O2 把它变成工程纪律。
> 每条都带**可执行验收**与**变异自证**要求（沿用本工程既有纪律：断言必须能被变异击穿）。

### O0 快赢（零风险，每条约 1–2 小时）

#### O0-1 消灭前后端双份标签（`bad_dom_range` 界面显示英文的根因）
- **问题**：后端产 6 种 `type`，前端 `TYPE_LABEL`（`09-impact.js:1140`）只映射 5 种，**缺 `bad_dom_range`** → `TYPE_LABEL[x.type]||x.type`(`:1154`) → 真库那 9 条高危**全显示英文原文**。
- **做法**：**backend 单一真源**——issue 直接带 `code` + `label`（中文）；前端 `TYPE_LABEL` 降级为兜底（或删除）。
- **理由**：与 P0-2 那次"两处只读判定副本"是**同型问题**（前端/后端各持一份清单，必然漂移）。
- **落点**：`shared.py:303 _ontology_check` 返回体；`09-impact.js:1140/1154`。
- **验收**：新增 `tools/verify/verify_ontology_check_report.py`（静态 + 真库快照）：
  ① 每种 issue 必带 `code`/`label`；② 前端不再持有规则清单（grep 断言）；③ 真库 9 条高危渲染为中文。
- **风险**：无（纯展示 + 加字段）。

#### O0-2 门禁档位对齐 + 删掉不存在的"豁免"承诺
- **问题**：本体检查硬编码 `high>0 → 400`，而自家 SHACL 门禁有 `off/warn/enforce`；报错文案承诺"确认风险后豁免"**但没有实现**。
- **做法**：`high>0` 改为**读 `gate_mode`**（复用 `ingest_gate.gate_mode` 语义），**默认 `enforce`**（零行为变更）；同时把那句文案改为**指向即将实现的豁免**（O1-5），或先删掉。
- **落点**：`ontology_version.py:121`（publish）、`:289`（release）、`:294`（文案）。
- **验收**（**行为等价性**）：`enforce` 下仍 400；`warn` 下放行但写审计；`off` 下不校验。**变异**：把档位读取打回硬编码 → 断言必 FAIL。
- **风险**：低。`warn/off` 会让"带病本体"可发布 → 必须**同时**落地 O1-3 留痕（谁在什么档位下放行的），否则等于开了口子没记账。

#### O0-3 报告可复现
- **做法**：返回体补 `ts` / `branch` / `ontology_version_id` / `total_types` / `rule_version`；前端显示"体检于 X · 规则版本 vN"。
- **理由**：SHACL 报告与 OOPS! 报告都是**可复现报告**（同一输入 → 同一结论）。
- **验收**：连跑两次，除 `ts` 外字段完全一致。
- **风险**：无。

### O1 结构化（本轮主体）

#### O1-1 规则目录化 `core/ontology_rules.py`
- **做法**：把 6 条规则从函数体抽成目录，每条：
  `{code, label, dimension, severity(high/warn/info), why_template, fix_hint, applies_to(entity/relation/attribute/graph), enabled}`
  `_ontology_check` 改为**遍历目录**；severity 由"写死在分支里"改为"目录里声明"。
- **承接**：这正是上位文档 **P2-4**（"按类型声明 severity"）的落地形态，只是把范围从"按类型"扩到"**按规则**"。
- **落点**：新增 `core/ontology_rules.py`（**只依赖标准库**，被 `shared.py` 与前端/验证脚本复用，避免循环导入——沿用 `core/branch_rules.py` 的成功范式）；`shared.py:303`。
- **验收**：目录 ↔ 实现**双向**一致（每条目录项都能被触发，每个产出的 code 都在目录里）；**变异**：目录里改一条 severity → 真库报告分档必随之变化。
- **风险**：低（纯重构 + 单一真源）。

#### O1-2 判据补齐（分两类，避免"规则比数据严"）
**(a) 补盲区（结构性）**
| 新规则 | 说明 |
|---|---|
| `attr_domain_missing` | 属性 `domain_classes` 为空。当前**完全无检查**（`missing_dom_range` 只对 relation 生效）；真库此刻恰好 0 违例，但**规则缺失**意味着今后新增属性会静默漏过 |
| `multi_domain_range` | 一个 side 声明多个类型 → OWL 语义是**交集**（OOPS! 定为 Critical）。**但我们设计上就用列表承载"允许的类型集合"** → **以 `info` 报出并登记设计意图**，不照搬 Critical（沿用"判缺陷前先找设计声明"纪律；若确认是有意为之，则该规则长期只做提示） |
| `rule_data_conflict` ⭐ | **本轮新视角**：声明 dom/range 与**存量边端点**不一致。这正是 §1.3 抓出 141 条的那条规则，**也是"换域不完整"这类缺陷的守门人**。默认 `warn`（因为它命中面广，先观察再提档） |

**(b) 接上已有的存量实例体检（聚合成一个入口，不重写）**
`ontology_migration.validate_relation_instances:101` / `validate_attribute_instances:154` / `scan_dangling_instances:191` 已具备 `required / unique / allowed_values / cardinality / xsd / 悬空实例` 的**存量**扫描能力，但**只在"改那个类型时"被调用**；`OntologyValidator.validate_node:166` **只在写入时**调用。
→ 新增全量入口 `ontology_check_instances(conn, scope)`，逐个类型调用**现成函数**，产出**同一份报告结构**。
- **验收**：**金标 fixture**——好本体必过；**每个坑各造一个坏样本必挂**（对齐 SHACL 的 known-bad fixture 纪律）+ 变异自证。
- **风险**：中。全量实例扫描有性能成本 → 必须支持 `scope`（按类型/分支）与"快速模式（仅结构）/完整模式（含实例）"。

#### O1-3 报告留痕与趋势（对齐 EDG 自动 diff）
- **做法**：新增表 `ontology_check_runs`（`ts / actor / branch / version_id / high / warn / info / report_json`）；`/validate` 每次写一行；新增 `GET /api/knowledge/ontology/validate/history` 返回与上次的 diff：**新增 / 已修 / 未动**；前端显示"较上次：已修 2 · 新增 0"。
- **理由**：现在既不能回答"这个坑存在多久了"，也不能回答"改完好了没有"——而这正是 EDG"导入新版本自动 diff + 一键处置"的核心价值。
- **落点**：`database/schema.py` + 新 migration（沿用 `_migrate_*` 幂等范式）；`shared.py` / `ontology_version.py`。
- **验收**：跑两次 → 第二次 diff 全为"未动"；修一条 → diff 出现"已修 1"；**变异**：把写库去掉 → 断言 FAIL。
- **风险**：低（新增表，零改动既有表）。

#### O1-4 把 issue 接到**已有**的工单队列（对齐 `icv fix` / EDG apply-all）
- **做法**：issue 带 `fix{hint, auto, actions[]}`；`flag_*` 类问题一键生成 `ontology_instance_migrations` 工单（复用 `build_plan → dry_run → apply`，**状态机与幂等守卫都已完备**）；结构类高危给"跳到该类型编辑 / 一键改名 / 清空悬空值"的动作，**不静默改数据**。
- **注意**：该表**真库 0 行**（从未使用）→ 首次落地要确认前端是否已有入口；若无，需要配一个最小"工单列表"视图，否则工单生成了也没人看得见。
- **验收**：一键生成工单后：`affected` 行数 == 实际受影响行数；`dry_run` 抽样 ≤10 条；`apply` 后 `status='applied'` 且 `applied_by/applied_at` 有值。
- **风险**：中。写操作必须有**备份 + dry-run + 抽样确认**三道闸（本工程已有 `ontology_instance_migrations` 的 `sample` 列就是为此设计的）。

#### O1-5 豁免机制（让本体能发布；对齐 Wikidata `exception to constraint`）
- **做法**：新增豁免登记（`ontology_check_exceptions` 表或复用 `settings`）：`{code, target, reason, expires_at, created_by}`；读取时过滤已豁免项；**豁免必须留痕 + 到期自动失效**；同时把 `ontology_version.py:294` 那句文案变成**真功能**。
- **这一条是"解锁发布"的关键**：现在 9 条漂移把整条发布链锁死，而唯一的出路（豁免）只存在于文案里。
- **验收**：豁免一条 → 报告分档随之变化且**审计有记录**；过期后**自动重新生效**；**变异**：把过滤去掉 → 断言 FAIL。
- **风险**：中（治理严肃性）。缓解：**豁免必须填理由 + 有效期**，并在报告与发布日志里**显式引用豁免清单**（不允许"静默放过"）。

#### O1-6 原位定位与过滤（对齐 CATIA"视图内高亮"）
- **做法**：问题项点击 → 切到本体页并**高亮**该类型 + 只显示该类型问题；报告支持按 `dimension` / `severity` 过滤 + 导出 JSON。
- **验收**：真库 9 条高危逐条点击均可定位并高亮（截图证据）。
- **风险**：低（纯前端）。

### O2 体系化（把校验变成工程纪律）

#### O2-1 CI 门禁 + 金标 fixture
- 常驻 `tools/verify/verify_ontology_rules.py`：**好本体必过 / 坏本体逐坑必挂 / 变异自证**；并入发布前检查与 `tools/verify/` 家族（与既有 5 个验证脚本同一纪律）。

#### O2-2 SHACL 双轨交叉验证
- 已有 `ontology_semantics.shacl_export:312` → 可选跑 `pyshacl` 做**外部**交叉验证（缺库降级 `off`，与 `ingest_gate` 同款策略）。
- **价值**：把"内部 JSON 约束"变成"**外部可执行契约**"（一份可以交给供应商的规格），并暴露内部实现与标准语义的偏差。

#### O2-3 口径统一（**架构决策，需拍板**）
- `_ontology_check` / `OntologyValidator(conn)` 默认读**编辑态** `ontology_types`；而 `_active_ont_rows:464` 的 docstring 明写"**消费类端点（语义注入 / 图谱 Schema / 导出）用此读取**"，实际 `/schema`、`/graph`、`/shacl`、`/export` 走快照，**但 AI 建模语义注入没走**（`prompt.py:72` 无 rows → 读编辑态）。
- 后果：「一致性检查的问题集」**未必等于**「AI 建模 / 导出真正吃到的那份 schema」。
- 三选一：① 统一读**快照**；② 统一读**编辑态**并订正 docstring；③ 双口径并存但**在报告里显式标注**。

#### O2-4 写入前置与拒绝留痕（对齐 Palantir / Stardog guard mode）
- `GraphStore.create_node/create_edge` 已**强制**校验（好），但**被拒的尝试没留痕**。
- 补：拒绝事件记录（**谁、何时、试图写什么、被哪条规则拒**）→ 管理者才能看到"卡点分布"，也才能反过来改进规则。

## 5. 明确不做 / 不建议照搬

| 不做 | 理由 |
|---|---|
| 引入 HermiT / ELK / Pellet 做 OWL DL 一致性推理 | 本工程是**闭世界形状校验**场景，SHACL 式判据能覆盖绝大多数真实缺陷；引 Java 推理机成本高、与单进程 Python+SQLite 架构不匹配。**只在导出/离线体检路径可选** |
| 把 Java 工具链（ROBOT / Protégé）放进主链路 | 同上；上位文档 §2.1 也指出 <1000 概念 / <5000 实例时用 Protégé 足够——那是**编辑器**场景，不是运行时门禁场景 |
| 照搬 OOPS! 把"多值域/多定义域"定为 **Critical** | 我们 `allowed_values.src/tgt` **天生用列表承载**多类型；先 `info` 报出 + 登记设计意图，确认后再定档 |
| 把 `isolated`（孤立类）提为 high | 它本质是**风格/结构**维度（OOPS! 中同类也属 Minor 档）；提为 high 会**误锁发布**。对齐 SAIC 的"语言类 vs 风格类"分层 |
| 一键静默改数据 | 所有自动修复必须走 **dry-run + 抽样预览 + 工单**（`ontology_instance_migrations` 的 `sample` 列本就是这个设计意图） |
| 把体检结果塞进 `ontology_change_logs` | 那是**类型级变更**语义（before/after）；混用会污染变更历史。用独立表 `ontology_check_runs` |

1. **那 9 条漂移（+141 条存量边）怎么处置**——三选一，见附录 A：

### 7.6 本轮自查揪出的自身缺陷：留痕 `before` 被浅拷贝污染

**现象**：10 条留痕的 `before` 与 `after` **完全相同** → "可追溯、可回退"名存实亡。
历史留痕 `before != after`，故这是本轮新脚本引入的缺陷。

**根因**（`_ontology_dom_range_repair.main()`）：`before = dict(c)` 是**浅拷贝**，
紧接着 `av = c["allowed_values"]` 与 `before["allowed_values"]` 指向**同一个 dict**，
原地写 `av["src"]/av["tgt"]` 把 `before` 一起改掉了。修法：`copy.deepcopy(c)`。

**同时暴露了一条空转断言**：验证脚本原判据只断言"存在一条 update 留痕" →
留痕被污染时**照样 PASS**。已把判据换成
「`before != after` 且端点集合确有变化」（`O40`），
并用坏样本自证可被击穿（`O37`）。

**真 before 的恢复来源**：apply 前的 WAL 保真备份
`backups/mbse.db.bak-before-ontology-domfix-20260923_205431`（`sqlite3.backup()` 产物）。
这正是当初坚持"WAL 保真备份而非文件拷贝"的价值兑现。
新增幂等补救模式 `--fix-log-before`（**保守**：只重写 `before == after` 的污染行，
`before != after` 的真实历史留痕一律不碰），实测回填 10 条、复跑 0 改动。

**回填后复核**：10 条全部 `before != after`；其中 **9 条 `before` 含修复前悬空名**
（`ALLOCATED_TO` 6 / `COMPOSED_OF` 11 / `CONNECTS` 2 / `CONTAINS` 29 / `DEPENDS_ON` 2 /
`FLOW_TO` 3 / `REALIZES` 5 / `SATISFIES` 5 / `TRACE` 3），
唯一无悬空名的是 `VERIFIED_BY` —— 它修复前**本就无悬空**，只是 `src` 增量补齐需求四类
（与附录 A "不影响存量 3 条边，纯增量" 一致）。

**修正后的口径**：附录 A 提到的"9 条漂移"= **9 个悬空关系类型**；
`TARGETS` 共 **10** 条 = 9 个悬空修复 + 1 个（`VERIFIED_BY`）纯增量补齐。两处说法现已对齐。
