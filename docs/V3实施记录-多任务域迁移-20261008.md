## 4. 实施中抓到的两个真错误

### 4.1 严重：`LIKE 'sys_%'` 通配符陷阱（**dry-run 救了一条命**）

SQL `LIKE` 里 `_` 是**单字符通配符**。实测：

```sql
SELECT DISTINCT tool_name FROM agent_tools WHERE tool_name LIKE 'sys_%';
-- sys_query_audit / sys_query_convs / sys_query_monitor
-- sys_query_perms / sys_query_roles / sys_query_users
-- sysml_v2_validate      ← 误伤！视图 Agent 唯一的建模工具
```

若直接 `--apply`，会删掉 8 个视图 Agent 的 `sysml_v2_validate`。而 `agent/pipeline_parts/prompt.py:104` 的 `_is_v2_code_agent` 正是靠这个绑定决定**是否注入 L0 硬约束卡** —— 后果是 8 个视图 Agent 全部失去 SysML 语法约束，生成质量崩塌。

**修正**：改用显式白名单 `IN (6个sys_query_*)`。
**并补了一条回归断言**：`8 视图 Agent 仍绑 sysml_v2_validate = 8（期望 8）`。

**为什么这次没出事**：迁移脚本默认 dry-run，且 verify 段会回读校验。如果直接 apply 再看输出，也可能已经写库了。
**推广**：任何 `LIKE 'xxx_%'` 都要检查 `_` 是否会误伤；`sys_` / `sysml_` 这类前缀尤其危险。

### 4.2 `INSERT` 占位符数不匹配
`VALUES (?,?,?,1)` 传了 2 个绑定 → `ProgrammingError`。dry-run 第一遍就暴露。
**修正**：补上 `tool_type` 参数（`"tool"`）。

### 4.3 自检判据自身写错
第一版 verify 用「`task_domain != 'general'` 即已回填」判定，把正确归为 `general` 的 `requirement_quality` 误报为未回填。
**修正**：改为以 `TASK_DOMAIN_MAP` 为准逐个比对期望值 —— 判据必须锚定"我声称做了什么"，而不是"看起来对不对"。

## 5. 顺带发现的既有质量问题（非本次引入）

### 5.1 工程样例 5/6 过不了官方校验器

用 `sysml_v2_check.check_code` 跑 `sysml_models/ev_thermal_mgmt/*.sysml`：

| 文件 | verdict | n_error |
|---|---|---|
| 00_master.sysml | report | 5 |
| 01_requirements.sysml | **block** | 12 |
| 02_architecture.sysml | **block** | 19 |
| 03_use_cases.sysml | **block** | 16 |
| 04_activity.sysml | **block** | 41 |
| 05_internal_block.sysml | **block** | 44 |

根因（`02_architecture` L112起）：样例里写了 `satisfaction satisfy ReqX by Y;`。

> `satisfaction` 是中间表示的节点名，**被误写进了 .sysml 文本**。这与 L0 硬约束卡里「引用类语法只能引用 usage」是同类错误。

**归因**：git 确认这些文件**未被本次迁移改动**（`git status` 空，最近提交是 `b3846b2` 基线重建）。

**影响**：N4 门禁一旦上线，这批样例会全部判 block ⇒ **不能拿它们当回归基准**。
**建议**：① 修正样例语法；② 或另建一套「已知通过」的小型基准集（3~5 个最小合法片段）专供门禁回归。

### 5.2 意图识别 6 条语料 5 条落 `chat`

| 语料 | 识别结果 | 期望 |
|---|---|---|
| 生成活动图 | `chat` | 视图生成 |
| SysML 2 是什么 | `knowledge_qa` | ✅ 知识问答 |
| 查一下有谁有权限 | `chat` | 系统管理 |
| 帮我导出一份报告 | `chat` | 报告生成 |
| 改一下电池温度需求会影响什么 | `chat` | 变更影响 |
| 你好 | `chat` | ✅ 闲聊 |

**归因判定（关键）**：用备份库（迁移前）跑同样 6 条，**结果逐条完全一致** ⇒ **既有问题，非本次迁移引入**。

根因：v3.0 §0.2 已记录的实测事实 —— **`intent_keywords` 全库 19 个 Agent 全部为 0 条**，关键词路由失效，只能靠语义向量兜底。

**影响**：这直接卡住 v3.0 的 V2（顶层分流）。**分流判据依赖 `operation` 槽位，而 operation 的识别质量现在是 1/6。**
**处置建议**：先做 roadmap 的 **V7**（确认 `intent_keywords` 路由侧是否消费该列；未接则接上），再动 V2。否则 V2 建在流沙上。
