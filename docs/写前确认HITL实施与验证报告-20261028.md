## 一、理论依据与行业标杆（每个设计决策的出处）

> ⚠️ **编号纠错（方案里要写对）**：OWASP 的 Excessive Agency 在 **2026 版从 LLM06 升为 LLM03**，
> 是全表最大上升幅度（第 6 → 第 3）。排名方法学首次纳入真实事件数据
> （6,639 起已分类事件占 25%，专家投票占 75%）。

### 1.1 直接背书「分级而非一律确认」

| 来源 | 原文 | 落到本方案 |
|---|---|---|
| **OWASP LLM03:2026** 缓解 #7「Complete mediation」 | "Implement authorization **in logic rather than relying on an LLM to decide** if an action is allowed... **A graduated enforcement policy (audit, warn, block, escalate)** permits low-consequence or easily reversible actions to auto-approve, while high-consequence or irreversible ones route to human review. For example, a customer service chatbot can auto-process a refund as store credit (which is recoverable), while an irreversible action such as an external payout routes to human approval." | ① 判定下沉到**执行侧代码**（不让模型自判）② 四级档位 auto/notify/confirm/approve ③ 智源可逆写先 notify、破坏性写 confirm |
| **OWASP Agentic AI T10**「Overwhelming Human in the Loop」 | "**low-risk decisions are automated, and human intervention is prioritized for high-risk anomalies**" | 同上。官方立场就是**分级**，不是全量确认 |
| **NIST AI 600-1**（GenAI Profile）MAP 阶段 | "document the intended autonomy level of each deployed agent, **specifying which action categories may be taken without human confirmation, which require approval**, and which are outside the agent's permitted scope" | 策略表 `hil_policies` 即这张"动作类别 → 档位"的映射 |
| **CISA/NSA + 五眼联合指引**（2026-05-01） | "**Ensure decisions about when human approval is required are determined by system designers or operators, not delegated to the agentic AI system.**" | 档位写在 `hil_policies` 表（**人工维护**），模型无权改；`escalate()` 只能收紧不能放宽 |
| **EU AI Act Art. 14(4)(b)** | 监督者须"aware of the possible tendency of automatically relying or over-relying on the output... (**automation bias**)" | **法定义务**：把审批做成例行点击，在法律上不满足"effective human oversight" |
| **MCP 规范**（server/tools） | "there **SHOULD** always be a human in the loop with the ability to deny tool invocations"；"**Show tool inputs to the user before calling the server**" | 确认卡展示独立计算的事实（§1.3） |

### 1.2 反面证据：为什么不能"每步都问"（这决定了灰度顺序）

| 证据 | 数据 | 对本方案的影响 |
|---|---|---|
| **Anthropic 受控实验**（n=1,053，编码场景） | 人只拦下 **13.6%** 的危险命令（143/1053），自动分类器拦 **89%**；**会话越长越差：17% → 50+ 次提示后约 5%** | 逐条确认**几乎没有筛选力** |
| 同上（生产遥测） | 用户**批准 97%** 的权限请求；单个权限请求**拒绝率仅 3%** | 弹窗密集 ⇒ 退化为例行点击 |
| 同上 | **计划级审批拒绝率 39% vs 逐条 3%（差 13 倍）**；生产数据：人工批准会话出现"用户未明确要求的伤害性操作"是 auto mode 的 **2.6 倍**（6.3% vs 2.4%） | **必须做计划级/批次摘要**，不是逐条参数 |
| **arXiv:2604.04918**（n=48，192 次会话，四种监督策略对照） | plan-based 把问题动作 odds **降 76%**（OR=0.24, p<.001）；但**动作一旦执行，人只拦下 21%**，四策略间**无可靠差异**；最佳策略下仍有 **45.8%** 会话以未纠正问题动作结束 | ① 上游减动作有效 ② "人守执行关"这一环本身失效 ⇒ 价值在**授权留痕 + 否决权**，不在"人能看出危险" |
| 同上 | "**upfront approval inhibited runtime scrutiny**"；"participants often treated subsequent actions as falling within an already authorized course of action" | **计划外动作必须重新审批** ⇒ 批次键含动词族，跨族不合并 |
| **arXiv:2608.27443**（n=113，HITL vs AUTO vs 预授权规则） | 预授权规则组拦截越界动作**比逐条确认少 20.1 个百分点**（95% CI [-32.1, -8.1]）；140 条规则里用户选了 114 条 "ask" | **不能把分级交给用户随手改**；判定权必须在策略侧 |
| **AgentDojo**（arXiv:2406.13352，629 个安全用例） | 工具过滤器把攻击成功率从 **57.69% → 6.84%**，且效用**不降反升**（73.13% vs 69.0%），**全程无人在环** | **确定性执行侧闸比弹窗更有效** ⇒ 本方案的核心闸放执行侧是对的 |
| **Progent**（arXiv:2504.11703，UC Berkeley） | AgentDojo ASR **39.9% → 1.0%**，效用 76.3% vs 79.4%；"只有权限**扩张**才需显式批准" | 同上 |
| **Anthropic 沙盒化** | 沙盒使权限提示**减少 84%**；"approval fatigue showed up within weeks... a feature originally designed to provide oversight could arguably have the **opposite effect**" | HITL 必须配套"减少需要人判断的量" |

### 1.3 确认卡的设计依据（为什么是"影响面"而不是"参数 JSON"）

| 来源 | 原文 | 落地 |
|---|---|---|
| **OWASP Top 10 for Agentic Apps ASI09**（Human-Agent Trust Exploitation） | "**A human in the loop is not a control if the UI conceals the exact effect or trains users to approve automatically.**" / "**Separate agent-generated rationale from independently computed facts.** Use diffs/previews for writes." / "**Prevent the agent from choosing its own risk tier or approval requirements.**" / "**Measure comprehension and rejection, not just dialog display.**" | 卡片展示：动作 + 目标对象 + **影响面摘要** + **可逆性（系统算的，不是模型说的）** + 批次数；原始参数折叠在 details 里 |
| **arXiv:2604.04918** | "Even when control arrived at the right moment, **users judged whether the agent acted correctly, not whether the action was safe.**" | 卡片**不展示 agent 的理由**，只展示系统算出来的事实 |
| **从业者方法论**（scixa.com，非受控研究） | "outliers break out of the batch into individual review... a stratified sample of batch items is surfaced inside the digest"；"a reviewer who approves a 200-item digest unread is rubber-stamping with **200 times the blast radius**" | 批次摘要 + `batch_items` 存受影响对象清单（本方案已实现 `batch_items` 列） |

## 二、实施内容

### 2.1 三处断链的修复（这是"为什么不拦"的根因）

| 断链 | 根因（实测） | 修法 |
|---|---|---|
| **① L2 闸永不触发** | `self._hil_level` 全仓只有 `common.py:644`（置 None）与 `execute.py:195`（赋值）两处；`stream.py:3802` 只取**局部变量** ⇒ stream 主路径恒为 `None` ⇒ `== "L2"` 恒 False | stream 路径补 `self._hil_level = agent_def.hil_level`；且让它只作**下限**参与 `escalate()`（只收紧不放宽） |
| **② MCP 工具全部漏闸** | `_tool_side_effect` 查不到返回 `"read"`，而 MCP 工具**不在 `tools` 表** ⇒ destructive/write/L2 三闸对 `create_model_elements` 等**全部失效** | 新增**双源判定** `hil_service.classify_action`（`tools.side_effect` ∪ MCP 动词族） |
| **③ 批准后也不执行** | decide 端点只真执行 `kind='http'` + `save_artifact` + `eval_label`，其余（含**全部 MCP 工具**）落 else 分支「非 HTTP 集成类型不支持自动执行」 | 新增统一执行器 `hil_service.execute_confirmation`，走 `_exec_tool_call`（与模型调用工具**同一份代码**） |

### 2.2 执行侧分类判据（纯结构，零硬编码工具名）

真实 71 个 MCP 工具目录实测暴露两个硬伤：

| 问题 | 例子 | 处置 |
|---|---|---|
| **漏判（更危险）** | 6 个 `set_*` 工具（`set_model_expression` 等）名字无 create/update 动词，旧表**全判 read** | 补 `set`/`remove`/`generate`/`run` 四个动词族（**追加在表尾** ⇒ 注入侧零回归） |
| **误判** | `get_model_delete_impact` 名字含 delete 但**只读**（删除影响分析）；`preview_model_changes` 描述含"删除/写入/执行"却**纯只读** | **读前缀优先**（`get_/query_/preview_/export_/…` 即判 read）；**描述一律不参与判定**（实测不可靠） |
| **子串陷阱** | `remove_view_presentations` 里 `present` 是 `presentations` 子串 ⇒ 按长度优先会把"删除"判成"可逆写" | **破坏族整族先判**，再判写族 |

**实测结果**（71 个工具）：`read 30 / write 34 / destructive 7`，关键 11 个用例 **11/11 正确**。

破坏族全清单（7 个，需 approve 级确认）：
`delete_model_elements` `delete_model_relationships` `import_sysml_text`
`apply_model_changes` `undo_model_operation` `remove_view_presentations` `manage_model_imports`

### 2.3 统一 HITL 闸的位置与判据

```
白名单(最小权限) → RBAC(这个人准不准) → Hook(管理员配的细粒度规则) → ★统一 HITL 闸★ → 执行(MCP/HTTP/local)
```

- **RBAC 之后**：`tools.py:870-876` 既定不变量——"无权限的人不该让工具走到『要不要人工确认』这一步"
  （把"他本来没资格"伪装成"他够格但需要审批"更糟）
- **Hook 之后**：Hook 是**确定性细粒度**规则（可带参数条件），比策略层的粗分档更具体
- **执行之前**：唯一能保证"**没有副作用发生**"的位置
- **唯一收口点**：全仓 grep 确认 `_exec_tool_call` 只有 **4 个调用点**
  （stream 主路径 / stream 收尾修复轮 / execute / async），一次改造全覆盖

### 2.4 四级档位（策略即数据，灰度 = 改表不改代码）

| level | 判定 | 动作 |
|---|---|---|
| `auto` | 只读 | 直接执行 |
| `notify` | 可逆写、低影响 | 执行 + 留痕（**灰度第 1 档的采集点**） |
| `confirm` | 写库但可逆 / 不可逆动作 | 进确认队列，逐条或按批审批 |
| `approve` | 影响外部系统 | 进队列 + 更高权限位 |

**当前生效档位**（`hil_policies`，11 条）：

| match_key | level | 覆盖 | 理由 |
|---|---|---|---|
| `mcp_destructive` | **confirm** | 智源 7 个破坏性工具 | 数量少、不可逆、**改动前零拦截** = 最大安全缺口 |
| `mcp_write` | **notify** | 智源 34 个可逆写 | 数量大，先采数据校准分类准确性（Anthropic：逐条拒绝率仅 3%） |
| `destructive` / `write` | confirm | 本地工具（tools 表） | 沿用既有语义 |
| `read` | auto | 只读 | 仅审计 |

### 2.5 批次合并（approval fatigue 防线）

- **合并键**：`sha1(conversation_id | agent | match_key | trace_id | run_id)`
- ⚠️ **键含 `match_key`（动词族）⇒ 跨族不合并**：依据 arXiv:2604.04918「upfront approval 抑制运行时再审查」
  ⇒ **计划外的新动作类型必须重新审批**
- `batch_items` 列累积受影响对象清单（计划级摘要要展示"这轮要动哪些东西"）
- 真机实证：连续两个 delete 类工具合并为**同一张确认单，「同批共 2 项」**

### 2.6 三道保护（每道都对应一个真实的失败模式）

| 保护 | 失败模式 | 实现 |
|---|---|---|
| **执行幂等** | 用户点两下「批准」⇒ 写两次 ⇒ **平台重复包**（真库已积累 3 个重复测试包） | `result_json` 非空 ⇒ 直接返回缓存结果，不重复执行 |
| **乐观锁** `expected_version` | 确认单挂起期间版本已变 ⇒ 批准后**写到错的地方** | 递归提取 `version:{...}` 嵌套坐标比对（顶层 `versionId` 查不到会**静默跳过**，实测踩到） |
| **条件更新防并发** | 两个并发 decide 请求都"成功" ⇒ 执行两次 | `UPDATE ... WHERE status='pending'` + `rowcount` 判定谁抢到 |

### 2.7 回灌闭环（D-2，本轮最容易被忽略的一环）

批准执行发生在**原 ReAct 循环之外**（一次独立 HTTP 请求）⇒ **LLM 永远收不到回执**
⇒ 它会重发同一操作，或宣称"尚未执行"（真机 E8 实测：回执 `SUCCEEDED`、平台回读证实已建成，
模型却断言「尚未写入平台……因轮次用尽，写操作没有执行」—— **与事实相反**）。

回灌文案（`hil_service.build_resume_text`）**必须含两条**（都有实测依据）：
1. **"不要重复发起"** —— 否则模型把"已执行"当"没执行"再跑一遍 ⇒ 重复包
2. **"原请求"复述** —— `messages` 表**不存 tool_calls / tool_result** ⇒ ReAct 状态是纯内存
   ⇒ 回灌必然是"**重新起一轮**"而非"恢复状态机" ⇒ 不复述就丢上下文

## 五、局限与风险（如实登记）

### 5.1 本轮未闭合

1. **"写前必须征得用户同意"仍是系统强制，但"用户是否真的看懂"未度量**
   OWASP ASI09 要求"**Measure comprehension and rejection, not just dialog display**"、
   NIST AI RMF Appendix C 要求采集"人类推翻 AI 输出的频率与理由" ⇒
   **本方案只埋了 `confirm_shown` / `confirm_decided` 两个点，缺"理解度"与"推翻理由"的采集**。
2. **未做拒绝率/推翻率的基线对比** —— 当前没有"改动前 vs 改动后"的对照数据，
   无法证明拦截有效性的**统计显著**改善（只有功能正确性证据）。
3. **`notify` 档的数据尚未采集** —— `mcp_write` 现为 notify，需跑真实会话积累
   "哪些写操作实际发生、误判率多少"，才敢升到 confirm（这正是 D-3 的第 2 档）。
4. **只验了智源对接 agent 的单 Agent 直行主链路**；编排路径 / 多轮会话 / 其他 agent 未跑真机。
5. **前端 `hil_confirm` 卡片未做真实浏览器验证** —— 只做了 `node --check` 语法检查与括号配平，
   **没有截图证据**（这是当前最大缺口）。
6. **并发场景未做压力测试** —— 条件更新 `UPDATE ... WHERE status='pending'` 的逻辑正确性靠代码审查，
   没有真并发打点。

### 5.2 已知风险

| 风险 | 后果 | 缓解 |
|---|---|---|
| **审批疲劳**（最大风险） | 确认卡密集到例行 ⇒ 从安全控制退化为"安全剧场"，审计上有批准记录但监督已消失 | ① 批次合并 ② 分档只在破坏性拦 ③ `batch_items` 摘要让人看清影响面。**但这条无法靠代码根治**——只能靠"少问、问得有意义" |
| **一次批准覆盖整批** | 若批次里混入意外对象，会整批放行 | `batch_items` 存全量对象清单；跨动词族不合并；`approve` 级不合并 |
| **确定性策略判定错了就是全错** | 分类误判会导致"该拦的没拦"或"不该拦的拦了" | 读前缀优先 + 破坏族先判 + 真实 71 工具逐个核对；误判只影响"多问一次/少问一次"，且影响面摘要让人可纠正 |
| **回灌是新一轮而非恢复状态机** | 模型可能丢上下文 | 回灌文案强制带"原请求"复述 + "不要重复发起" |
| **平台侧遗留测试数据** | 真机上跑 E2E 会在平台上留下测试包 | 本轮 E2E **自建自删**（create → delete），最终状态干净；上一轮的 3 个测试包仍在（未擅自删） |

### 12.2 ⚠️ 本轮抓到的**真实前端缺陷**（X3）

**现象**：`t1` 首跑全部 19 条断言返回 `false`，而 `_procS.timeline` 长度 = 2（状态里明明有 2 张卡）。

**根因**：`procRender()` 渲染的卡片是 `<div class="proc-block" data-pid="hil_<cid>">` ——
**元素没有 `id` 属性，只有 `data-pid`**。而我在三处写了 `getElementById('hil_' + cid)`：

| 位置 | 后果 |
|---|---|
| `hil_confirm` 事件的「滚到可见」 | **静默失效** —— 卡片弹出但视口不跟随，用户可能完全看不到 |
| 批准后回灌续跑取 `_card` | 拿到 `null` |
| 断言本身 | 全红（**验证器也错了**） |

**修法**：新增 `_hilCardEl(cid)` → `document.querySelector('[data-pid="hil_'+n+'"]')`，三处统一。

**方法论价值**：
① 这是**位置/选择器型缺陷**，`node --check` 与 DOM 状态断言都查不出（状态在 `_procS` 里是对的）；
② 它同时说明「**验证器和产品可能都错**」—— 首跑全红时，我第一反应是"产品没生效"，
   实为**断言用了错的选择器**；两边一起修才收敛。

## 十四、真机清库任务抓到的 2 个新缺陷（X1 / X2）

> 场景：清理平台侧 3 个 E2E 测试残留包（`E2E验证包` / `测试` / `通信子系统测试`）。
> **顺手用真实清理任务验证批次合并的生产行为** —— 结果抓到两个只有真跑才暴露的缺陷。

### X1（严重）批次合并只合"计数"，后 N-1 笔**永不执行**

| 项 | 实测 |
|---|---|
| 现象 | 3 次 delete 合并成确认单 #34，`batch_count=3` |
| 但 | `payload` 只存**第 1 笔**；`batch_items` 只存 `{tool,preview,target}` —— **没有完整参数** |
| 后果 | 批准 1 次只删 1 个包，**后 2 个永远不删**，而用户以为"批准了 3 项" |
| 性质 | **数据丢失型**（静默少做），比"多问一次"严重得多 |

**修法**：
1. `batch_items` 每条存完整 `args`
2. `execute_confirmation` **逐条执行** `batch_items`，汇总 `{seq, tool, target, ok, result}`
3. 无 `args` 的老数据自动退回单条 payload（逐字节兼容）

**修复后实测**（确认单 #35，真实清理 3 个包）：

```
批次执行完成：3/3 项成功
[{"seq":1,"target":"#578924417024","ok":true,...},
 {"seq":2,"target":"#858535739392","ok":true,...},
 {"seq":3,"target":"#874346688512","ok":true,...}]
```

**平台独立回读**：3 个包全部消失，父容器子级 **3 → 0**。

### X2（严重）批次摘要**无信息量** ⇒ 用户盲批

| 项 | 实测 |
|---|---|
| 现象 | `batch_items` 的 `target` 全是空串，预览渲染成「删除「（未命名对象）」× 3」 |
| 根因 | `_batch_target` 只查 `name/title/label/...`，而**删除类工具的参数里只有 `dataId`** |
| 后果 | 三行一模一样的"未命名对象" ⇒ **等于盲批** |
| 性质 | 正是 OWASP **ASI09** 点名的失效模式：「**A human in the loop is not a control if the UI conceals the exact effect.**」 |

**修法**：`_batch_target` 与 `_impact_preview` 同步补 **ID 类键**（`dataId/elementId/viewId/id/uuid/...`），
显示 `#尾号12位`。修复后：`#578924417024` / `#858535739392` / `#874346688512` —— 三行可区分。

### 14.1 这两个缺陷的方法论价值

🔑 **「合并」这个动作天然有两个环节：入队时"存"、批准时"跑"。只测其中一个必然留盲区。**
本轮门禁的演化正好证明这一点：

| 断言组 | 覆盖 | 对 X1 的鉴别力 |
|---|---|---|
| [J2] 源码断言「有 `"args": payload`」 | 存 | ✅ 变异后红 |
| [J4] 手工构造 `batch_items` 后执行 | 跑 | ❌ **变异后仍绿**（它不经过入队路径） |
| **[J5] 走真实 `queue_confirmation` 入队 → 执行** | **存 + 跑端到端** | ✅ **变异后 3 条全红**（`['J5-BBB']` 精确复现"只跑 1 条"） |

> **J4 的假绿是本轮最有价值的一课**：它看起来"端到端"，实际上绕过了被变异的那一环。
> 只有 J5 走**真实生产路径**才有鉴别力。
