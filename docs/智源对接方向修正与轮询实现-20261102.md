## 1. 实现了什么

### 1.1 轮询锚点选型（有依据，不是随便挑）

智源 71 个工具里，能当"变更锚点"的只有几个：

| 工具 | 能否当锚点 | 原因 |
|---|---|---|
| `query_model_versions` | ✅ **选它** | **按发布时间倒序** ⇒ 新出现的 versionId = 变更，天然有序、可做增量断点 |
| `query_data_tree` | ❌ | 只能逐层展开（`keyword/type` 只过滤当前层，不能跨层查） |
| `preview_model_changes` | ❌ | 需要**明确的命令**，不是"发现变更" |
| `export_sysml_v2` | ❌ | 是导出动作，不是变更探测 |

### 1.2 参数不猜（这条很重要）

`mcp_servers.tool_meta` 里只有 `name` + `description`，**没有 `inputSchema`**。
而此刻智源 502，参数名无从核实。

⇒ 做法：
- `versions_args` 从配置**透传**（配置里写什么就传什么，不硬编码参数名）
- 提供 `probe_zhiyuan_schema()`：服务恢复后先拉真实 `tools/list` 把 schema 落库

**为什么不猜**：猜错不会报错，只会**静默拉不到数据**——
症状是"轮询是空的"，看起来像"智源没有变更"，实际是参数名错了。
这正是本仓反复踩的"静默失效"型缺陷。

### 1.3 默认关 + 必须显式配工程

```python
events.zhiyuan_poll_enabled = False          # 默认关
events.zhiyuan_poll_projects = []            # 空 = 不扫描
events.zhiyuan_poll_interval_s = 600
events.zhiyuan_poll_mcp_server = "zhiyuan-dev-mcp"
```

没配 `projects` ⇒ **直接拒绝**（`no_projects_configured`），不让它全库扫描。

### 1.4 一个 kind，两条通道

推送式（智源报给我）与轮询式（我去拉）**共用同一个 `zhiyuan` kind**：

```
                    ┌─ 推送：真人事件 → 白名单 + @ 判定
svc.receive("zhiyuan", ...) ─┤
                    └─ 轮询：系统事件（actor_type=system）→ admit() 豁免分支
```

理由：准入规则 / 幂等口径 / 工单形态必须一致，否则规则分叉、面板分裂。

⚠️ **本模块不定义 SourceSpec** —— 一个 kind 只能有一个 spec，否则会互相覆盖
（这点在代码注释里写了警告）。

## 2. 端到端实测抓到的最严重缺陷

### 「拉不到」被伪装成「没有变更」

第一版轮询实测返回：

```json
{"ok": true, "emitted": 0, "branches_scanned": 0}
```

**看起来完全正常**——「没有变更」。

**实际是**：智源 502，一次都没拉到。

**根因**：`MCPClient.call_tool` 失败时**不抛异常**，而是返回
`{"ok": False, "result": "错误描述", "is_error": True}`。
我的代码只做 `_tool_json(res)` 然后 `or []` ⇒ 502 的错误文本解析不出 list
⇒ 空列表 ⇒ 被判成"该工程没有分支"。

**后果比报错严重得多**：
> 智源停服期间的所有变更会被**永久漏掉**，而台账显示一切正常。
> 没人会发现，直到某天问"为什么这次变更没做影响分析"。

### 修复

新增 `_call_tool_checked()`，三层判据缺一不可：

| 层 | 判据 | 防的是什么 |
|---|---|---|
| ① | `res.ok is True` | MCP 执行失败 |
| ② | `res.is_error` 为假 | 服务端声明的 tool 错误 |
| ③ | 解析结果不含 `_parse_error` | 拿到响应但不是 JSON（如 nginx 错误页） |

任一不过 ⇒ 抛 `ZhiyuanCallError` ⇒ 记进 `errors` ⇒ `ok=False`。

### 修复后实测

```json
{
  "ok": false,
  "emitted": 0,
  "branches_scanned": 0,
  "errors": ["query_branches 调用失败: MCP 调用失败: Server error '502 Bad Gateway' ..."],
  "note": "**拉取失败**（不等于没有变更）—— 恢复后必须重跑，否则停服期间的变更会永久漏掉"
}
```

**M11 变异守住这条**：去掉 ok 检查 ⇒ 实测 502 被吞成 `ok=True errors=0` ⇒ 断言翻红。

> 这条变异守的是"**不报错但结果全错**"的缺陷——比崩溃危险得多。

## 3. 新增的 3 个端点

```bash
# ① 服务恢复后第一件事：探测真实 schema
curl -X POST http://<本平台>:8012/api/events/zhiyuan/probe -H 'X-User-Id: <id>'
#   智源 502 时 → HTTP 502 + {"ok": false, "error": "HTTPStatusError: ... 502 ..."}

# ② 手动跑一轮轮询（排障 / 首次接入）
curl -X POST http://<本平台>:8012/api/events/zhiyuan/poll -H 'X-User-Id: <id>' \
  -H 'Content-Type: application/json' -d '{"projects":["2084931257631305728"]}'

# ③ 状态（含 MCP 连通性，has_auth 可见）
curl http://<本平台>:8012/api/events/zhiyuan/status -H 'X-User-Id: <id>'
```

status 实测输出（截取）：

```json
{
  "running": false,
  "config": {"enabled": false, "interval_s": 600},
  "mcp_server": {
    "name": "zhiyuan-dev-mcp",
    "endpoint": "http://xuanyi-dev.huilingyun.com/mcp",
    "status": "offline",
    "last_error": "HTTPStatusError: Server error '502 Bad Gateway' ...",
    "has_auth": true
  },
  "note": "轮询式：本工程作为 MCP 客户端主动拉智源变更。拉取失败 ≠ 没有变更；恢复后需重跑"
}
```

## 4. 智源恢复后的操作顺序（三步）

```bash
# 第 1 步：确认通了
curl -s --noproxy '*' -X POST http://xuanyi-dev.huilingyun.com/mcp \
  -H 'Content-Type: application/json' -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}' | head -c 200
#   期望：返回 71 个工具的 JSON

# 第 2 步：探测 schema 落库（这样才知道 query_model_versions 的真实参数名）
curl -X POST http://<本平台>:8012/api/events/zhiyuan/probe -H 'X-User-Id: <id>'

# 第 3 步：手动跑一轮验证
curl -X POST http://<本平台>:8012/api/events/zhiyuan/poll \
  -H 'X-User-Id: <id>' -H 'Content-Type: application/json' \
  -d '{"projects":["2084931257631305728"]}'
#   期望：{"ok":true,"emitted":N,"branches_scanned":M}
#   若 branches_scanned=0 但该工程确实有分支 → 看返回的 note（权限/ID/草稿）
```

确认无误后再开自动轮询：

```python
# 配置
events.zhiyuan_poll_enabled = true
events.zhiyuan_poll_projects = ["2084931257631305728"]
events.zhiyuan_poll_interval_s = 600
```

> ⚠️ **本机有 `HTTP_PROXY`**，所有本地探测必须带 `--noproxy '*'`，
> 否则 127.0.0.1 也会被代理（本轮踩过，症状是 `upstream connect failed`）。

## 6. 本轮又踩的验证器自坑（第 N 次）

验证脚本**缺 `import json`** ⇒ 假 MCP client 里 `json.dumps` 抛 `NameError`
⇒ 被 `poll_once` 的 `except Exception` 当成"智源调用失败" ⇒ **G43 假红**。

耗时约 3 轮排查才发现（先怀疑产品实现、再怀疑断言、最后才查到 import）。

⇒ **纪律（已反复验证）**：假红/假绿**先怀疑验证器**。
判据：「我验的是不是真东西」——依赖齐全吗？夹具字段齐吗？被调用的是我以为的那个函数吗？
