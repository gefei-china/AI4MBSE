## 二、② 分数口径：从"择一取值"到"三路都记"

### 2.1 实测：不是"量纲略有差异"，是"根本没取到"

`agent/rag.py` 原实现：

```python
_hit_src = (graph_results if route in ("graph","mixed") else (chunk_hits or vector_results)) or []
_top = _f0.get("score") or _f0.get("conf") or 0
```

但 `graph_results` 的元素是**图谱实体**（字段 `id` / `name` / `type`…），
既没有 `score` 也没有 `conf`；图路的真分数是独立变量 `graph_confidence`
（`_graph_confidence` 多因子加权：覆盖度 0.50 + 关系连接性 0.30 + 类型匹配 0.20）。

⇒ **凡 `route ∈ {graph, mixed}`，`top_score` 恒为 0。**

存量实测（修复前，6541 条）：

| route | n | top_score 范围 | 0.036 阈值命中率 |
|---|---|---|---|
| vector | 6514 | 0 ~ 0.632 | **20.0%** |
| mixed | 27 | **0 ~ 0**（全 0） | **100%** |
| graph | **0** | — | —（见第三节：从未写入） |

### 2.2 危害不是"数字不准"，是"方向反了"

`core/online_eval._cand_low_conf` 的职责是挑"最没底的查询"送人工标注：

```sql
SELECT ... FROM query_trace WHERE top_score < 0.036 ORDER BY top_score ASC LIMIT ?
```

两个后果叠加：

1. **mixed 那 27 行恒占榜首**（值恒 0），每次采样都采同一批 ⇒ 采样偏置，且看板上一片正常；
2. **graph 路的低质量查询永远采不到**——图置信度 0.3 也远大于 0.036，尽管它在图路里已属最差。

### 2.3 修法：加列 + 分路 + 区分 NULL 与 0

`query_trace` 新增 4 列（老库 ALTER 自愈，`CREATE TABLE IF NOT EXISTS` 对已存在表是空操作）：

| 列 | 含义 |
|---|---|
| `score_kind` | 这个数是哪种分：`graph_conf` / `chunk_score` / `vec_score` / `legacy_*` / `''` |
| `top_graph` | 图置信度（0~1） |
| `top_chunk` | 融合检索首条 score（实测 0~0.63） |
| `top_vec` | 向量首条相似度 |

三条设计纪律：

- **三路都记，不择一**。择一本身就是信息丢失——`mixed` 路由同时有 `graph=0.3 / chunk=0.136`，只留一个就再也无法事后区分量纲。
- **`top_*` 允许 NULL 且刻意不给 `DEFAULT 0`**。`NULL` = 该路本次无结果，`0` = 有结果但分数为 0。旧 bug 的形态正是"没取到"被写成 0，然后 0 被当成"最差"。
- **`top_score` 原义保留**（兼容既有消费方），但 `score_kind` 明确标注它不可跨 route 比较。

`rag.py` 侧：

```python
_top_graph = round(float(graph_confidence or 0.0), 4) if graph_results else None
_top_chunk = _first_score(chunk_hits)
_top_vec   = _first_score(vector_results)
if route in ("graph","mixed"): _top, _kind = _top_graph, "graph_conf"
elif chunk_hits:               _top, _kind = _top_chunk, "chunk_score"
else:                          _top, _kind = _top_vec,   "vec_score"
```

修复后实测：`graph` → `top=0.96 kind=graph_conf`；`mixed` → `graph=0.3 / chunk=0.136 / vec=0.136`；
零命中 → 三列全 `NULL` + `score_kind=''`。

### 2.4 消费方：从"绝对阈值"改成"组内分位"

```python
# 旧
WHERE top_score < 0.036 ORDER BY top_score ASC
# 新
_LOW_CONF_KINDS = ("graph_conf", "chunk_score", "vec_score", "legacy_fusion")
# 按 kind 分组 → 每组取 ceil(n*q) 条最低分 → 按「组内相对位次」混排
```

关键点：**跨组不比较绝对值，只比较"在本组里有多差"**。
`graph_conf` 组的最差（0.1）会入池，尽管它比 `chunk_score` 组的**最高值**（0.04）还大。
阈值完全由分布决定（`low_conf_quantile=0.25`），不维护任何魔法数字。

`low_conf_threshold` 标为 **@deprecated**（键保留以兼容配置文件，代码不再引用）。

实测效果（真库 30 天窗口，`sample_candidates(apply=False)`）：

| 项 | 修复前 | 修复后 |
|---|---|---|
| 低置信候选 | 12 条，**全部单一量纲** | 12 条：`legacy_fusion 9 / graph_conf 2 / chunk_score 1` |
| `legacy_zero`（缺值冒充的低分） | 恒占榜首 | **0 条**（明确排除） |

### 2.5 历史行回填（幂等）

回填规则全部由已存的 `route/top_score` 反推，不猜、不补数：

| 条件 | 归入 | 理由 |
|---|---|---|
| `vector` 且 `top>0` | `legacy_fusion` | 融合检索分；历史行无法区分 chunk/vec，故不冒充 `chunk_score` |
| `top=0` | `legacy_zero` | 缺值或零命中 —— **都不是"最低分"** |

实测：`legacy_fusion 6035 / legacy_zero 508`，二次运行 0 变化。
不回填的话，新逻辑面对 6541 条 `score_kind=''` 的历史行会"无数据"——
从"统计不全"变成"统计为零"，那看起来像业务量消失。

## 三、③ 观测留痕：不冒泡，但不静默

### 3.1 为什么"静默"的代价比想象大

原实现 `except Exception: return 0`。后果不是"少一条日志"，而是：

- 所有基于 `query_trace` 的比率（零命中率 7.24%、低置信采样、路由统计）
  **分母只是"成功写入的行"**，真实值只会更高，而看板上它长得像"已统计全量"；
- 失败被吞后，**下一次同一个失败也不会有人知道**（没有计数、没有日志、没有告警）。

还有一个隐性风险一并修掉：`commit()` 失败会**留下未提交事务**，
此后同一连接上的每次写入都继续失败 ⇒ 失败被一次次吞掉 ⇒
表现为 **trace 从某一刻起整体消失**（而不是报错）。故失败时尽力 `rollback()`。

### 3.2 新工具 `core/observe_fail.py`

三条纪律：

1. **不冒泡**：`note()` 自身绝不抛（连 `exc.__str__` 坏掉、连 `BaseException` 都不抛）；
2. **不丢计数**：先计数、再取消息——计数不依赖消息字符串化成功；
3. **不编造**：没失败就是 0，不返回"看起来健康"的估算值。

提供 `snapshot()`（供门禁与健康检查读）与 `reset()`（仅测试用）。
日志限速：首次必打，之后每 50 次打一次（故障时不刷屏）。

接入点三处：`glossary.trace_query`、`agent/rag.py` 的 trace 兜底、`agent/rag.py` 的路由统计兜底。

### 3.3 它当场抓到的真 bug

加完留痕后第一次跑真实检索就报：

```
观测失败 rag.trace（累计 1 次）：UnboundLocalError:
cannot access local variable 'force_domain' where it is not associated with a value
ctx={'qlen': 14, 'route': 'graph'}
```

`force_domain` 只在 `if graph_confidence < self.confidence_threshold:` 分支内赋值，
而 trace 块**无条件**读 `force_domain or "all"` ⇒ 凡走 graph 路由（置信度够、不进该分支）
必然抛异常 ⇒ 被 trace 的 `except: pass` 吞掉 ⇒ **graph 路由一条 trace 都没有**。
存量实测：`vector 6514 / mixed 27 / graph 0`，正是这个 bug 的指纹。

> ⚠️ 这条要单独记：**上一轮我在紧邻的注释里就写了"必须在 try 之前初始化，
> 否则后续异常会让 trace 块因 UnboundLocalError 反过来吞掉整次检索"，
> 却只初始化了 `_domain_skipped` 一个变量，没初始化 `force_domain`。**
> 风险写进了注释，没写进代码。⇒ 纪律：注释里点名的风险，必须当场落成断言或初始化，
> 否则那条注释只是"我知道会出事"的自证。

修复：在该分支前一次性初始化 `force_domain = None` / `boost = 1.0`。
修复后 `graph` 路由 trace 恢复：`top=0.96 kind=graph_conf hit=5`，`observe_fail.total()==0`。

## 六、未做 / 风险

1. **`top_score` 仍是"按 route 择一"**——为兼容既有消费方保留原义。若后续有新的分析需求，
   应当**直接读 `top_graph/top_chunk/top_vec`**，不要读 `top_score`。这一点靠 `score_kind` 标注，
   但**没有强制手段**（没法阻止有人写 `WHERE top_score < X`）。
2. **`trace_query` 的 `query` 列传的是归一化后文本**（实测 `宽带载荷` 落库为 `宽带通信载荷`），
   而 `normalized` 列传的是同一个值。这会让低置信采样送出的"原始查询"其实是替换过的文本。
   属既有行为，本轮未动（会改变 `online_eval` 的样本语义，需单独评估）。
3. **`legacy_zero` 与新写入的 `score_kind=''` 语义重叠**（都是"无分可用"），
   两者都不参与低置信判断，但名称不统一。保留是为了让"历史推断"与"当场记录"可区分。
4. **①（60+ 条空域术语）按你的判断不实施**。前提已记录：那些是测试数据，不是真实业务缺口。
   `satellite_comms` / `loitering_munition` / 能力中心 三个域在库内 **0 chunk**，
   但 Glossary 仍会为其施加域约束——`_domain_usable` 前置校验已经在运行时挡住（第 20 轮），
   所以**不影响检索正确性**，只是术语表里有噪声。
