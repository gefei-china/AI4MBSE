# P0-C 第二步：长任务业务端点接入作业队列（2026-10-04）

## 结论先行

上一轮交付了进程内异步作业队列（`core/job_queue.py`），但**全仓没有任何业务端点调用它**
—— 能力齐备，最后一公里没通。本轮把6 类长任务接到队列，并补齐队列自身的两处语义缺陷。

**实测对比（同一份真实文档 `800_SysML-v2-AI建模知识文档.md`，146836 字节）**：

| 路径 | 提交返回耗时 | 完成耗时 | HTTP 连接占用 |
|---|---|---|---|
| 同步（改造前） | 13.4 min 量级（三份规范合计） | 同左 | 全程占用 |
| **异步（本轮）** | **0.034 s** | 178.1 s（后台） | 0.034 s |

即：**接口返回快了约 4万倍**，长任务转移到后台，用户可随时离开、随时回来查进度。

## 二、新增端点（`routers/jobs.py`）

| 端点 | 用途 |
|---|---|
| `GET /api/jobs/kinds` | 可提交的业务作业类型 + 必填 payload 字段（前端据此渲染，不硬编码 kind） |
| `POST /api/jobs` | 提交作业，立即返回 `{job_id, status, deduped}` |
| `GET /api/jobs/{job_id}` | 状态 / 进度 / 结果（含 `terminal`、`cancelable`、`lease_expired` 派生字段） |
| `POST /api/jobs/{job_id}/cancel` | 取消（**只对未开始或租约已过期生效**） |
| `GET /api/jobs` | 列表（按 kind/status 过滤） |
| `GET /api/jobs/stats` | 队列概览 + worker 配置 |

权限：读走`current_user`；写（提交/取消）走 `config:write` 同档 ——
提交会**真的触发写库与 embedding 调用**，匿名可提交等于把"跑入库"的算力对外开放。

## 三、本轮修掉的**两个真实语义缺陷**（都是门禁逼出来的，不是代码review 看出来的）

### 缺陷 1：幂等判据锚错 —— 双击防线在真实时序下**完全失效**

第一版 `submit()` 的去重判据是 `WHERE job_key=? LIMIT 1`（精确匹配那一行）。
真实时序下会这样坏掉：

```
① 用户点「入库」→ job#1（key="doc_retry:7"）→ 跑完 done
② 用户再点「重试」→ 判据命中 job#1（终态）→ 按 reuse_terminal=False 换新 key → job#2 在途
③ 用户手抖双击 → 判据 WHERE job_key="doc_retry:7" 命中的**仍是 job#1（done）**
   → 判它终态 → 又建 job#3
   ⇒ job#2 完全没被去重 ⇒ 两条在途作业抢同一个 doc_id ⇒ 写类副作用重复
```

**根因**：判据锚的是"**这一行**"，而它必须锚"**这一族里在途的那些**"。
这与本仓反复踩过的"兜底判据锚错"是同一型（判据恒真或恒假，功能被焊死）。

**修法**（`core/job_queue.py`）：
```python
fam = conn.execute(
    "SELECT ... FROM job_jobs WHERE job_key=? OR job_key LIKE ? ESCAPE '\\' ORDER BY id",
    (k, _like_prefix(k))).fetchall()
# reuse_terminal=False ⇒ 只对家族内 **ACTIVE**（queued/running）去重；
# 家族内全终态 ⇒ 换新 key 新建（挡手抖双击，但不挡合法重跑）
```
配套：新增 `reuse_terminal` 参数，业务端点一律传 `False`；默认值 `True` 保持向后兼容。

### 缺陷 2：长作业会被**自己的 worker** 重领并双跑

`pick_next` 把「running 且租约过期」当作崩溃残留回收 —— 这是崩溃恢复的正确设计。
但入库实测 13.4 min > 默认租约 300 s ⇒ **不续租的话，租约在作业跑完前就过期了**，
单 worker 也会把它当残留重新捞回：候选表写两次、embedding 白烧一次、audit 出现两条。

**修法**：新增 `core/job_handlers.LeaseKeeper` —— 长handler 一律包在
```python
with LeaseKeeper(job_id, lease_s=900):
    ...
```
它起后台 daemon 线程，**自开连接**（不复用业务连接，避免与长事务互锁），
按 `lease_s/3` 周期调`job_queue.heartbeat`。租约配置也同步放大到 900 s
（`jobs.worker_lease_s`），因为默认值必须大于最长单作业耗时。

### 顺带修掉的门禁缺陷

`tools/verify/verify_job_queue.py` 的 D1 变异锚点因`submit` 改写而失效
（`assert old in src` 直接抛 AssertionError，门禁崩溃）。重打锚点时又暴露一层：
变异打在 `ACTIVE→TERMINAL` 上时红灯 0 条 —— 因为 Q1 走的是默认
`reuse_terminal=True` 分支，那条路径根本不会被触到。**变异必须打在判据真正走到的代码上**，
否则门禁只是"看起来有变异自证"。

## 四、管道逻辑不二次实现（避免同步/异步行为漂移）

异步入库**没有复制一份管道代码**：

```
stage_upload_document()   HTTP 侧：建 documents 行 + 源文件副本落盘（毫秒级）
        ↓ 提交作业
run_staged_ingest()       worker 侧：复用 retry_document（既有"从副本读回并重跑"实现）
        ↓
auto_extract_stage()      同步 ingest_upload_document 与异步 run_staged_ingest **共用**
```

- 为什么把字节**落盘**而不是塞进 `job_jobs.payload`：payload 是 JSON 文本列，
  大文件既撑爆它，又让"提交"这一步本身变慢（违背"提交即返回"）。
  且这样 worker 走的路径与失败重试**完全相同**，行为天然一致。
- 抽取段抽成 `auto_extract_stage`：若同步/异步各写一份，
  漂移后果是"**异步上传的文档不进治理面板待办**"，且这种漂移只在真数据上才显形。

新增状态 `parse_status='queued'`（已复核前端只判 failed/completed，新增状态不会让旧前端报错）。

---

## 五、失败语义：管道失败**不重试**

扫描件 / 损坏文件的解析失败，重试多少次都是同一结果，白烧 embedding 额度。
所以 `doc_ingest` 的 handler 在 `parse_status == 'failed'` 时**返回而非抛异常**：
返回 ⇒ worker 判`done`；抛异常 ⇒ 推高 `attempt` 并最终 `failed`。
只有**环境性失败**（工程不存在、无可入库版本）才抛，让队列的有上限重试发挥作用。

## 七、配置（`core/config.py` → `jobs` 段）

| 键 | 默认 | 说明 |
|---|---|---|
| `worker_enabled` | `True` | 与 `orchestration.auto_resume_enabled` 默认关**刻意相反**：worker 只执行用户显式提交的作业，空转成本仅每轮一次 SELECT |
| `worker_count` | `1` | SQLite 单写者，多 worker 加剧写锁竞争 |
| `worker_interval_s` | `2` | 轮询间隔（首轮立即执行，不等） |
| `worker_lease_s` | `900` | **必须大于最长单作业耗时**，否则作业会被自己重领 |

关掉 worker 时提交仍会成功（作业留queued），只是没人执行 —— 端点会把这点明示出来。

## 八、遗留与建议

1. **前端未接进度轮询**：当前异步只开后端能力，前端仍走同步路径。
   建议下一批在 `20-docs.js` 上传成功后按 `poll` 字段轮询 `/api/jobs/{id}`，
   把现有 4 段进度条映射到 `progress`/`stage`。
2. **`queued` 状态的前端文案**：`documents` 列表需要把 `queued` 渲染成"排队中"
   （当前只判 failed/completed，不会报错，但会显示成空态）。
3. **多副本部署需换外部队列**：进程内队列**不跨进程**。单副本下完全够用
   （`docker-compose.yml` 明写单副本是硬约束，理由就是 SQLite 单写者）。
   上多副本时 `job_jobs` 表可平滑迁为"任务登记表"，但 worker 领取机制要重做。
4. **PostgreSQL 迁移仍应独立立项**：见 `docs/P0-3-换PostgreSQL-立项评估-20261004.md`
   （实测约 1634 处直连 SQL / 625 次 commit，建议暂不迁）。
