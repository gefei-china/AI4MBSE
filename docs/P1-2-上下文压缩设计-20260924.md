## 0. 结论（v2）

| 主张 | 判断 |
|---|---|
| 本仓没有上下文预算 | ❌ 错（v1 论断）。**早有 token 预算制**：`_apply_context_budget` 按预算裁检索区（≤4k tok）与历史区（≤3k tok），execute 与 stream 两路径都在调 |
| 附件全文直接进 prompt | ❌ 错（v1 论断）。注入侧有 `_ATT_INJECT_CAP=4000` 封顶（取前 4 块再截断），全文只用于召回 |
| **各段预算之和可以超窗，且没有总闸** | ✅ **真缺口**。检索 4k + 历史 3k + system 本体（视图类 agent 8k 字符 ≈ 4~5k tok）+ 附件 2.7k + v2 约束 1.3k ≈ **12~16k**，叠加后超出窗口时由输出侧 `_ctx_guard` 把 `max_tokens` 夹小 ⇒ **输出被悄悄截短**（"报告在结论前中断"的症状，本仓 S4 注释已登记过同族现象） |

**v2 方案**：不做新的压缩机制，**给已有分段预算加一个"总闸"**——
发送前用现成的 `count_messages_tokens` 预检；超 `input_budget` 时**降档重裁**
（复用 `_apply_context_budget`，用更紧的检索/历史预算再跑一遍），必要时裁附件。零新概念、零新依赖。

## 3. 压缩的逻辑（v2）：总闸 + 降档重裁

```
发送前：
  total = count_messages_tokens(messages)          # 现成函数，含多模态图片块
  budget = input_budget(cw, mt)                    # 现成函数：cw - max_tokens - safety
  total <= budget → 原样发送（常态零开销）
  total >  budget → 降档重裁（复用 _apply_context_budget，预算参数收紧）：
      档1：检索 4k→2.5k、历史 3k→1.8k（×0.6）
      档2：检索→1.5k、历史→1k（×0.35），并裁附件段到 2.5k 字符
      降档后重算，够即发；仍超则保持最紧档 + 留痕（输出侧 guard 仍兜底）
```

**为什么降档重裁而不是新写裁剪**：`_apply_context_budget` 已实现"检索保头/历史保尾"的语义，
降档只是**换一组预算参数再跑**——不引入第二套裁剪逻辑，行为可预期。

**为什么 system 本体不压**：视图类 agent 的 8k 字符是建模规则（v2_constraints 也明确"只裁检索区与历史区"），
压它会直接改变产出质量——宁可让输出侧 guard 兜底。

## 7. 一句话回答

> **逻辑**：分段预算本就有（token 制、保头保尾），缺的是总闸——发送前算总账，超了就用**同一套**
> `_apply_context_budget` 换更紧的参数重裁一遍（检索/历史降档，system 永不动），输出侧 guard 继续兜底。
> **触发**：常态零开销（预算内不触发）；只有超 `input_budget` 才降档，每档动作留痕。
> **评估**：基线峰 14.2k / Mock 率 10.9% 已存档；用变异自证证明总闸真的会触发，
> 上线后看 M2（峰值）与 M3（输出被截短的次数）。
