# P1-2：上下文压缩 —— 逻辑 / 触发时机 / 效果评估（2026-09-24 设计）

> **回答三个问题**：压缩的逻辑是什么？什么时候触发？效果怎么评估？
> **方法**：先拿 `llm_usage_stats` 的真实 token 分布定位压力点，再盘本仓已有的散点式裁剪，
> 最后给出方案——**不重造轮子，把散点收拢成预算制**。

---

## 0. 一句话结论

本仓**不缺截断手段，缺统一的"输入预算管理"**：现有 7+ 处散点截断各自为政，
而唯一**完全不设防**的一段（附件全文）恰恰是峰值的最大来源。
方案 = 「发送前预检 + 分段预算 + 三级降级（截断→摘要→卸载）」，预计峰值场景 14.2k → 6~8k token。

---

## 1. 先定位压力：真实 token 分布（`llm_usage_stats`，1598 条真实调用）

```
平均 1,768 ／ 最大 14,213
按 intent 聚合（平均 prompt_tokens）：
  （空 = 主对话链路）   419 条   平均 4,582   峰值 14,213   ← 压力全在这
  plan_refine            46 条   平均 3,557   峰值  8,154
  plan_summary           33 条   平均 1,439
  rag_rerank            572 条   平均   865   （量大但小）
  memory_deposit         47 条   平均   767
  planner                37 条   平均   609
```

**读法**：上下文压力**集中在主对话链路**（平均 4.6k、峰值 14.2k）。
编排子链路（planner/plan_refine/plan_summary）已有预算管理（见下），不是主要矛盾。

---

## 2. 主链路的上下文构成（4.6k 平均是什么组成的）

| 段 | 现状 | 风险 |
|---|---|---|
| **Agent system prompt** | `cap=0` 不截断；视图生成类 **3.6k~8k 字符**（活动图生成 7,981） | 稳定大头，但是"规则"，**不该压** |
| 输出/引用/附件规则块（prompt.py） | 共用实现，随 agent 注入 | 中 |
| **检索注入**（`_build_context`） | chunk 每条 180 字，有 rerank 控条数 | 可控 |
| **附件全文**（`execute.py:117`） | **"完整全文（供附件语义/词法召回）"——不截断直接注入** | ⚠️ **最大风险点**：传一个大文档，全文进 prompt——峰值 14.2k 大概率来自这里 |
| 对话历史 | **已有 LLM 摘要**（`history.py:565`，"输出 200 字以内"）；片段每条截 200/300 字 | 已治理 |
| 子任务交付物（编排） | `_head_tail_clip` + `_summarize_item_budget` + `summary_max_tokens=3000` | 已治理 |
| DST 槽位 / 长期记忆 | 每条 160 字 | 可控 |

**关键发现：已有的压缩是"散点式"的**——7+ 处各截各的（180/200/300/400/500/2000/2500 字），
没有一处知道"别的段占了多少"。而**唯一没有设防的段（附件全文）恰好没有上限**。

---

## 3. 压缩的逻辑：预算制 + 三级降级

借鉴 Deep Agents 的两招（summarization + 工具输出卸载到文件），但按本仓构成裁剪：

### 3.1 分段预算（各段一个 token 上限，发送前统一校验）

```
总预算 llm.context_budget（默认 12k，可配）
  ├─ system（规则类）        固定，不压 —— 压了会改变模型行为，得不偿失
  ├─ 检索注入                预算 2k（已有 rerank 控条数，只调条数）
  ├─ 附件                    预算 3k —— 超了走三级降级（见 3.2）
  ├─ 对话历史摘要            预算 1k（已有 200 字摘要，基本够）
  └─ 用户输入                不压（本来就是用户说的话）
```

### 3.2 三级降级（对超预算的段，按顺序降级，而不是一刀切）

| 级 | 手段 | 保留什么 | 丢弃什么 |
|---|---|---|---|
| 1 **截断** | 头尾保留（head_tail），中间裁 | 开头（定义/结论）+ 结尾（最新内容） | 中段细节 |
| 2 **摘要** | LLM 把该段压成 ≤N 字摘要（`intent=ctx_compress`，复用现有 usage 统计） | 结构化要点 + "完整版在 artifact #x" | 细节 |
| 3 **卸载** | 原文全文落 artifact（复用现有产物表），prompt 里只留引用指针 | 可追溯性（判据要求"关键信息可追溯"） | —— |

**为什么三级而不是直接摘要**：摘要本身要花一次 LLM 调用（钱+延迟）。
小超预算时截断就够；大超预算（附件）才值得摘要+卸载。

### 3.3 与现有 `_ctx_guard` 的关系（互补，不冲突）

现有 `_ctx_guard`（clamp/warn/off）管的是**输出侧**：按 `context_window` 预留输出额度，
超了就把 `max_tokens` 夹小（且实测 DB 里的 cw 可能是保守配置，"假天花板"）。
本方案管的是**输入侧**：发送前把输入压进预算。两者各管一头，合起来才是完整的上下文管理。

## 4. 触发时机（两个触发点）

| # | 触发点 | 逻辑 | 说明 |
|---|---|---|---|
| **T1 发送前预检**（主） | messages 拼装完、调用 provider 之前 | 用**已有的** `count_messages_tokens(messages)` 算总量；≤ 预算 → 原样发送（**零开销**）；> 预算 → 按段优先级走三级降级，压完再发 | 常态路径零成本：预算内完全不触发 |
| **T2 失败后重试前**（辅） | provider 返回"context length exceeded / maximum context length"类错误 | 与 P1-1 的重试机制衔接：识别这类错误 → 预算降一档（如 12k→8k）重试一次；**不做**通用重试（参数类错误重试无意义） | 兜住"预检估算不准"的情况（估算器是近似） |

**明确不做**：
- ❌ 后台异步压缩历史——本仓历史已有摘要，收益小、复杂度高
- ❌ 每轮都压缩——预算内就不动（"零开销常态"是设计红线，否则为了省 token 反而多花钱）

## 5. 效果评估（可量化判据）

| # | 指标 | 基线（今天实测） | 目标 | 取数方式 |
|---|---|---|---|---|
| **M1 主链路平均 prompt_tokens** | 4,582（intent='' 419 条） | ≤ 4,000 | 同一 SQL 对比 |
| **M2 主链路 P95 prompt_tokens** | 峰值 14,213 | ≤ 8,000 | 同上 |
| **M3 超窗守卫触发率** | `_warn_context_once` 日志（"假天花板"出现即说明输入+输出顶到 cw） | 0 次 | 日志 grep |
| **M4 Mock 回落率**（压缩不得引入新失败） | 10.9%（压缩前基线） | 不回退 | `used_mock` 占比 |
| **M5 可追溯性**（质量守恒） | —— | 压缩掉的附件全文 100% 有 artifact 引用 | 抽查 artifact 表 |
| **M6 任务完成质量** | —— | 压缩前后同一任务的产出结构不回退（卡类型/章节完整） | 人工 + 卡片字段 |

**评估方法**：
1. **A/B**：同一输入（带大附件）开/关压缩各跑一次，对比 M1/M2 与产出内容；
2. **纵向**：上线前后各取 N 天，用同一条 SQL 对比 M1/M2/M4（我已把基线 SQL 存档在本文件 §1）；
3. **变异自证**（本仓纪律）：把 `context_budget` 设成极小值（如 500）→ 预检**必须**触发且产出带 artifact 引用；设回正常 → 不触发。**不做这一步，"触发逻辑"就可能是空转的**。

**预期收益**（基于构成推算，非承诺）：
- 峰值场景（大附件）：14.2k → 6~8k（摘要 3k 预算 + 卸载全文）
- 常态（无附件）：基本不变（预算内零触发）——**这是设计目标，不是缺陷**

## 6. 实施路径（按性价比排序）

| 优先级 | 事项 | 为什么 |
|---|---|---|
| **P1** | 附件"摘要化 + 全文卸载" | 唯一不设防的段、峰值来源、改动面小（只动 `_load_attachment_text` 之后的注入段） |
| **P2** | T1 发送前预检 + 分段预算 | 通用兜底；`count_messages_tokens` 已有，成本主要是分段优先级逻辑 |
| **P3** | T2 失败后降预算重试 | 与 P1-1 重试衔接；等真实发生一次"超窗报错"再做也来得及 |

---

## 7. 一句话回答

> **逻辑**：把 7 处散点截断收拢成「分段 token 预算 + 三级降级（截断→摘要→卸载）」，
> 其中 system 规则段永不压、附件段从"完全不设防"变为"摘要+卸载"。
> **触发**：发送前用现成的 `count_messages_tokens` 预检（预算内零开销），失败后识别超窗错误降档重试一次。
> **评估**：M1~M6 六个量化指标，基线已存档（平均 4.6k / 峰值 14.2k / Mock 率 10.9%），
> 方法是 A/B + 纵向 SQL 对比 + 变异自证——**没有变异自证的"触发逻辑"不算做完**。
