## 一、现状：机制是什么（实测）

### 1.1 触发条件（`agent/pipeline_parts/execute.py:207`）

```python
should_retrieve = (bool(req_scope and req_scope.get('ok'))   # ① 用户打了 #知识库/#工程数据 标签
                   or bool(kb_tags)
                   or bool(agent_def.kb_required)            # ② Agent 配置启用
                   or (intent == "report_generation"
                       and report_type in ("impact", "review")))  # ③ 报告类意图自动带素材
```

三条任一成立 → 走 `GraphRAG.retrieve()`；否则注入一句明确的话：
> 「未引用知识库——可在输入加 #工程数据 / #知识库 标签主动引用，或由 Agent 配置启用知识库依赖」

**这个设计是对的**：附件上传**不**默认触发检索（避免"贴了个文件就全库召回"），
知识库消费必须**显式**。

### 1.2 检索范围（`agents.kb_scope`）

```json
{"mode": "custom", "branches": ["release"], "docs": ["...视图规范元素要求.md"]}   // design
{"mode": "all_release"}                                                          // 其余 3 个
{}                // kb_required=0 的 23 个 Agent
```

⚠️ 实测两个问题：
- `design` 的 `docs` 里**同一个文件名重复两次**（`知识库_运行视角_视图规范元素要求.md`）；
- 过滤维度只有 **branch**（分支），**没有"领域/文档类型"这一层**。

### 1.3 现状盘点（实测 `documents` 表）

| 类别 | 文档 | chunks |
|---|---|---|
| OMG 规范 | SysML v2 / KerML / Requirements Guide / AI建模知识文档 | **5472** |
| 客户方法论 | 广汽方法论-260813 | 180 |
| 场景知识库 | 热管理建模 / 混动仿真 / 座舱空调 | 383 |

全部 `branch=global`、15/16 为 `lifecycle_status=stored`，另有 1 份 `uploaded` 且 chunks=0（未解析完）。

### 1.4 关键缺口

**8 个流水线节点全部 `kb_required=0`、`kb_scope={}`**（实测）：

```
N0 methodology_resolver  N1 requirement_structuring
N2 architecture_skeleton N3 view_expansion
N4 model_validation_repair N5 trace_verification
G change_safety_gate     N6 model_release
```

⇒ **建模主链从不读知识库**。广汽方法论（180 chunks）、OMG 规范（5472 chunks）、
场景知识库（383 chunks）都在库里，但没有任何节点会消费。

**这直接解释了一个产品问题**：模型产出的 SysML 语法是对的（checker 判 pass），
但**不符合客户方法论**——因为方法论就在 `documents.id=812`，
而 N0「方法论解析」节点自己都不读它。

（与前几轮的关联：`sysml_view_generation_*` 系列 skill 只承载**通用 SysML 语法**，
客户方法论与通用语法在两套资产里，此前没有任何一根线把它们接起来。）

## 二、标杆产品的做法

### 2.1 Anthropic：上下文工程的六条转向（2026-07-24 官方博客）

来源：*The new rules of context engineering for Claude 5 generation models*

最重要的一条量化结论：
> Anthropic **删掉了 Claude Code 80% 的 system prompt**，在编码评测上**无可测量损失**。

原因是"过度约束会让模型把算力花在消解冲突上"。六条转向里，与本项目直接相关的三条：

| 旧做法 | 新做法 | 对本项目的含义 |
|---|---|---|
| Everything upfront | **Progressive disclosure**（按需加载） | 已做对：skill 摘要 + `skill_body_fetch` 取回 |
| Repetition | **同一指令只说一次**（放在工具描述里） | ⚠️ 本项目 skill 正文与 frontmatter 元数据曾重复注入同一段，已修 |
| Simple specs | **Rich references**（代码/测试用例优于 markdown 描述） | 对 MBSE：**checker.jar 就是可执行的 rich reference** |

另一条关键建议：
> "Skills should encode particular opinions, knowledge, or best practices that are
> particular to **you, your team, or product**."
> （skill 应承载"属于你们团队/产品"的知识）

⇒ 这一条直指本项目的缺口：**`sysml_view_generation_*` 写的是通用 SysML，
不是"智源/广汽的 SysML 写法"**。客户方法论不该放在知识库等检索，
而该**落进 skill 正文**（因为它是"每次都要遵守的规矩"，不是"偶尔查的资料"）。

### 2.2 企业级 RAG：三条硬约束

综合多份企业 RAG 架构资料（Farm Press / Spectrum / XBSTACK / Buzzi）：

**① 检索决策权归 Agent（Retrieval as a Tool）**
> "Agents must possess self-decision-making capabilities for on-demand retrieval.
> It is strictly prohibited to initiate invalid RAG retrievals for simple rewrites,
> casual chit-chat, or requests where the context is already sufficient."

即：检索是 Agent 的一个**工具**，由它自己判断要不要调，而不是每轮无条件查库。
**本项目的 `should_retrieve` 三条路径正是这个模式**，方向正确。

**② 检索前过滤（Pre-retrieval Filtering），不是生成后过滤**
> "ACL conditions must be forcibly injected at the very first step of retrieval;
> relying on soft interception via prompts during generation is strictly prohibited."

关键论据：**后过滤会让 LLM 拿到空上下文**（top-5 全被过滤掉 ⇒ 管线失败）。
⇒ 对本项目：若要做"按领域过滤知识库"，必须在 **SQL where 条件**里做，不能先召回再筛。

**③ 检索前分派（Knowledge Source Router）**
> "If you dump a dozen types of documents—which vary completely in format,
> permissions, and authority—into a single vector collection, the limitations of
> vector similarity will lead to widespread cross-contamination."

对 MBSE 的含义（这是本项目最该抄的一条）：
- 5472 chunks 的 OMG 规范（**权威标准**）
- 180 chunks 的广汽方法论（**客户规矩**）
- 383 chunks 的场景知识（**领域事实**）

三者的**权威性、时效、冲突裁决规则完全不同**，混在一个召回池里，
向量相似度分不清"规范说的"和"客户说的"，**冲突时不知道该听谁的**。

### 2.3 引用可审计（Citation Mandate）

> "In an enterprise setting, an answer without a citation is a liability."
> 评测用 RAG Triad：**Context Relevance / Groundedness / Answer Relevance**，
> 且 "If the Groundedness score drops, the build fails."

⇒ 对 MBSE 的意义：**模型生成的每个视图要素，都应能指回"依据哪条规范/哪份文档的第几节"**。
这与本项目已有的 `sysml_v2_validate`（可执行判据）是一体两面：
**语法靠校验器，语义依据靠引用**。

## 三、差距清单（按性价比排序）

| # | 差距 | 现状 | 标杆做法 | 收益 | 成本 |
|---|---|---|---|---|---|
| 1 | **方法论不入 skill** | 客户方法论在 documents，等检索 | 方法论属"每次都要遵守的规矩"，应落进 skill 正文 | 高 | 中 |
| 2 | **知识库无分派层** | 16 份文档单池，5472+180+383 混召 | Knowledge Source Router（按权威性/领域分派） | 高 | 中 |
| 3 | **流水线不读知识库** | 8 节点 kb_required=0 | 按节点职责逐个启用 + 配窄 scope | 高 | 低 |
| 4 | **过滤维度只有 branch** | 无领域/类型层 | 多维 metadata 过滤（**必须在 SQL 里做**） | 中 | 中 |
| 5 | **design 的 docs 重复项** | 同名文件列了两次 | 配置去重 | 低 | 极低 |
| 6 | **无引用回溯** | 产出无"依据哪条" | Citation + Groundedness 门禁 | 中 | 中高 |

## 四、建议的下一步（不含具体实现，待拍板）

### 立即可做（不需设计决策）
- **#5**：`design.kb_scope.docs` 去重。
- **#3**：给 N0~N6 逐个开 `kb_required` 并配**窄 scope**（这一步只改配置，不改代码）。

### 需要一次设计决策
- **#2（推荐先做）**：知识库分派层。形态建议——
  给 `documents` 增加 `authority`（`standard` / `customer` / `domain`）与
  `applies_to_stage`（哪些 pipeline 节点消费）两个维度，检索时按节点角色过滤。
  **理由**：这是"少加限制"的正解——不靠给每个 skill 加约束，
  而是让模型在**正确的时机看到正确权威性**的材料。
- **#1**：把广汽方法论的**可执行部分**（命名规约、视图元素要求、禁止项）
  从 180 chunks 里提炼成 `sysml_methodology_*` skill 正文，
  参照 `sysml_methodology_profile_guide`（id=114，已存在但未绑定到 N0）。
- **#4**：过滤下推到 SQL。**不能后过滤**（会拿到空上下文）。

### 暂不建议
- **#6 引用门禁**：成本较高（要改产出结构 + 建评测集），
  且需要先有 #2 的分派层，否则"引用哪份文档"本身就答不清。
