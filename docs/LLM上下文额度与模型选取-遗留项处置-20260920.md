### 1.3 新发现 ①：`route_tags` 在生产链路 **0 个调用点**

```
grep -rn "route_tags" --include=*.py（排除 .venv/tmp/skill_packages）
  → llm/__init__.py（定义与内部使用）
  → tests/manual_verify/verify_llm_route_d10.py（唯一传参处）
```

含义：`LLMRouter.route()` 只在**测试**里被跑到。于是 `priority` / `tags` / `budget_tokens`
这三个列**连同「预算耗尽自动降级」整条能力**，在生产链路上**从未生效过**。
这比「默认选取不看 priority」更严重 —— 后者只是没用上，前者是**一个已实现的能力根本没接线**。

### 1.4 新发现 ②：id=1 的 token 预算已超支

`usage_of()` 的判据是 `SUM(total_tokens) WHERE provider_id=? AND used_mock=0`：

| provider | 实耗 token | budget_tokens | 结论 |
|---|---|---|---|
| 1 | **1,355,177** | 1,000,000 | **超支 35.5%** |
| 71 | 1,779,409 | 0（不限） | 正常 |

后果：一旦有人传 `route_tags`（或将来把默认路径接到路由上），id=1 会**立刻**被判
「预算耗尽」→ 静默改选 id=71。也就是说这两条新发现**互相勾连**：预算超支平时看不出来，
恰恰是因为路由根本没被启用；路由一旦启用，行为会在无预警的情况下换模型。

## 2. 7.1 的处置

### 2.1 代码侧（确定性缺陷，逐项对应报告的三条指控）

| 报告指控 | 处置 | 文件 |
|---|---|---|
| `input_budget` 生产链路根本没调用（死代码） | **接线**：作为「输入余量」判据进入守卫告警，`count_messages_tokens` 同时接线 | `llm/providers/openai_compat.py` |
| 静默 `mt > cw → mt = cw` 把保守配置当硬上限 | 改为**三档可配置**：`clamp`（默认，**与改动前逐字节等价**）/ `warn`（只告警不截断）/ `off`（不介入），且触发时**留痕** | 同上 |
| 默认 provider 查询无 `ORDER BY` | 加 `ORDER BY priority DESC, id ASC LIMIT 1`（确定性 + 让 `priority` 在该路径真正生效） | `llm/__init__.py`（2 处） |
| —— | 新增配置键 `llm.context_window_guard` + `CONFIG_SCHEMA` 登记；同步更正因解锁而失效的旧注释 | `core/config.py` |

### 2.2 为什么默认 `clamp`（零回归优先）

`clamp` 与改动前**逐字节等价**：超窗照旧截到 cw，只是**多打一条 WARNING**。
要真正放开天花板，**不用改代码、不用换模型**，只改一个配置：

```jsonc
// ~/.workbuddy/mbse_config.json
{ "llm": { "context_window_guard": "warn" } }   // 或 "off"
```

并把 `refine.max_tokens` / `delegation.summary_max_tokens` 一并上调 —— **否则那两个才是真正的瓶颈**。

### 2.3 必须说清的一笔账（避免误读本次收益）

> **本次解锁 `context_window` 本身，今日不产生任何输出变化。**

推导：`refine.max_tokens = 8000`、`delegation.summary_max_tokens = 8000`，
而 id=1 的 `max_tokens = 8192`。`8000 < 8192` ⇒ 原来的 `mt > cw` **从未触发过**。
所以当前实际输出上限一直是 **8000（配置值）**，不是 8192，也不是 cw。

本次买到的是：**把「假天花板」从隐式变成显式** —— 现在任何人把
`refine.max_tokens` 提到 12000 都不会再被一个写错的 cw 悄悄截回 8192，且真被截时会有日志。
若目标是「让报告更长」，还需要**下一步**：把 `refine.max_tokens` 与 id=1 的 DB `max_tokens`
一起上调（属成本决策，本次未动）。

## 4. 7.2 / 7.3 的定性（不动作，但固化下来）

### 4.1 7.2 release 分支领域素材错位 —— 属**正确降级**，不是缺陷

既有资产 / 检索 / 本体仍是巡飞弹演示数据，子 Agent 因此「拒绝虚构」并给出空交付 →
完成度矩阵大量「未交付」。按 `AGENTS.md` 的政策，这是**期望行为**：
宁可空着，也不拿默认内容硬凑。

若将来要真正提升完成度，路径是**补该分支的领域素材**（数据侧），**不是**放宽降级
（那只会把「没数据」伪装成「有内容」，把问题推到更晚才暴露）。

### 4.2 7.3 内容厚度 ≠ 链路自洽 —— 读报告时的口径

`conv 373 gaps=[]` 与「t1 交付物仅 874 字符」**并不矛盾**：

- 门禁判的是「三子任务是否 done + 反思是否过」，**不判**交付物内容厚度；
- 报告正文自己也如实写了「t1 实际可见内容主要为『校验状态说明』与『下一步』两节」。

**`full` 只证链路自洽，不证内容丰沛。** 内容侧缺口要看完成度矩阵，别把 `full` 当质量满分。
