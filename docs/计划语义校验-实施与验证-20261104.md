# 计划语义校验（Plan Guard）：实施与验证

> 日期：2026-11-04
> 上游：`docs/编排流水线与多方案权衡-标杆实现对标-20261103.md` §7 第 1 条（**最高杠杆项**）
> 范围：只做"计划进入执行前的**语义**校验"。**不做**阶段清单表化、不做 sweep、不改 UI。

---

## 0. 一句话

把「阶段顺序不得倒序」从**提示词里的一句话**，变成**代码可报、可阻断、可审计的判据** ——
且默认只告警不阻断，**零行为变化**上线。

---

## 1. 为什么做（问题不是"缺校验"，是"缺语义校验"）

`agents.id=160` 的 `system_prompt` 第 2 条写着「阶段顺序固定…**不得跳步、不得倒序**」。
但全仓 `grep 阶段序` 命中的 11 处**全是往提示词拼字符串**，没有一处校验。

后果与「名册漂移」同族：**prompt 写了约束，代码不认，模型违反也不留痕**。
上一轮已实证过一次：160 的 prompt 要求填 `display_name`，而 `registry.get()` 只认 `name`
⇒ 整条流水线派给零工具 Agent，任务照跑照标 done。

**但"再加一道校验"不是正解** —— 计划进入执行前**已经有两道**校验，重复造只会漂移：

| 层 | 实现 | 覆盖 | 缺失后果 |
|---|---|---|---|
| **结构层** | `TaskQueue.validate_plan`（2026-10-13 B1-8） | 空 key / 重复 key / 自环 / 依赖环 | `ready_tasks` 恒空 → 整批**静默阻塞** |
| **路由层** | `TaskQueue.create_plan`(strict)（2026-10-29 P0-1） | agent 名解析不到在役 Agent | 静默回落零工具 Agent，**任务照标 done** |
| **语义层**（本批新增） | `core/plan_guard.py` | 阶段序 / 完备性 / 覆盖性 / 声明失效 / 外部依赖 / 必需标注 | **能跑完，但跑的不是用户要的顺序** |

三层**正交**：前两层答"能不能跑"，本层答"跑得对不对"。所以本批**不重写**任何既有校验，
只补语义层，并把三层的结果**串到同一条可观测链路上**。

## 2. 做了什么（四件事）

### 2.1 新增纯函数内核 `core/plan_guard.py`

零 IO、可单测；**不改图**（只报问题，不静默删边/改序 —— 静默改图等于替模型猜意图）。

七条规则，与 Capella 规则族对应（依据见上游对标文档 §3.1）：

| code | 严重度 | 检查什么 | Capella 对应 |
|---|---|---|---|
| `stage.order_reversed` | **error** | `X deps [Y]` 但 stage(X) 早于 stage(Y) ⇒ 后面的阶段挡着前面的 | `TC_*` Transition Consistency |
| `stage.required_missing` | warn | 必需阶段缺席 | `DCOM_*` Completeness |
| `stage.mentioned_missing` | warn | 用户点名的阶段未被覆盖 | `DCOV_*` Coverage |
| `route.unresolved` | **error** | 声明的 Agent 解析不到在役 | 无对应（本仓路由特有） |
| `route.missing` | warn | `task_type=agent` 但 agent 为空（走意图识别，属**合法用法**） | — |
| `route.ignored_by_type` | warn | 声明了 agent，但该 `task_type` **不读取** agent | — |
| `deps.external` | warn | 依赖计划外 key（落库时被静默过滤 ⇒ 任务提前就绪） | — |
| `plan.no_required` | warn | 无任何 `required=true` ⇒ early_stop 恒不动作 | — |
| `plan.empty` | **error** | 空计划 | — |

**不猜的三条边界**（防误报 —— 误报会让人关掉整个校验）：
- 不传 `resolve` ⇒ 跳过路由校验
- `stage_order` 为空 ⇒ 跳过阶段序与覆盖性校验
- `mentioned_stages` 为空 ⇒ 跳过覆盖性校验

### 2.2 接进 `_planner_core`（一处覆盖四条路径）

`workflows/planner.py::_planner_core` 是 `run_planner_plan` 的唯一实现，
被会话流式 / 非流式 / Flow planner 节点共用 ⇒ **一处接线，四路生效**。

接线位置：**计划已产出、落库之前**（技能校验之后，`TaskQueue.create_plan` 之前）。

三档模式（读 `generate_rules.pipeline_guard_mode`）：

| 模式 | 行为 |
|---|---|
| `off` | 逐字节回旧行为 |
| **`warn`（默认）** | 违规进 `warnings` + `data.plan_guard` + 日志，**不阻断** |
| `block` | 存在 error 级违规 ⇒ 返回 `blocked=True`，**不落库、不执行**，并把原因写进正文 |

默认 `warn` 是刻意的：**当前状态是完全不可见**，先让它可见，跑一段看真实分布再决定是否收紧。

### 2.3 修掉"校验原因被吞"（观测缺陷）

`create_plan` 抛的 `ValueError`（含"计划引用了无法解析的 Agent：xxx"这种极有价值的诊断）
被 `except Exception as e: executed.append({"error": ...})` 接住，而 `executed`
**既不进 content 也不进 data** ⇒ 用户只看到 **"（计划已执行，但无成功交付物）"** 这句误导文案。

改：`_plan_error` 留全量（400 字）→ 进 content 与 `data.plan_error`，并落一条 `error` 日志。

> 这是本批**最有价值的顺手修复**：既有的路由校验一直是对的，但它的结论用户从来没看见过。

### 2.4 统一两处 Agent 名解析器（口径分裂）

| 解析器 | 改前 | 改后 |
|---|---|---|
| `AgentRegistry.resolve()` | 认 `name` + `display_name` 兜底（上一轮加的） | 不变 |
| `task_queue.resolve_agent_name()` | **只认 `name`** | 加 `display_name` 兜底 |

改前同一个名字在两条路径上**结论相反**：规划器能派（resolve 通），落库却整批中止
（`create_plan` 抛 ValueError）。**口径分裂比两边都严格更糟** —— 它让"为什么这次编排没跑"无从解释。

真库实证：`agent_tasks.agent_id` 里 **78 行**是 `工程建模方案设计Agent`（`design` 的显示名）。
安全性已验：`display_name` 全库无重名、与任何 `name` 无跨字段冲突 ⇒ 反查唯一。

## 3. 验证

### 3.1 离线自检 `tools/verify/verify_plan_guard.py` —— **56 PASS / 0 FAIL**

7 组，含 **5 条变异自证**（改坏实现 ⇒ 判据必须翻红）：

| 变异 | 期望翻红 |
|---|---|
| M1 逆序判据 `<` 改 `>` | 真逆序不再被报 |
| M2 `off` 档早退失效 | off 也变得会报错 |
| M3 不报"声明失效" | `route.ignored_by_type` 消失 |
| M4 默认阶段序被清空 | 默认值判据翻 |
| M5 `blocked` 恒 False | `block` 档失效 |

⚠️ 沿用本仓铁律：**判据抽成 lambda**，正确实现求值 True、变异实现必须 False
（写成"变异后仍应通过"等于自证形同虚设）。

另含**反向用例 8 条**（不该报的必须沉默）：同阶段互依赖、非阶段 Agent、不传 resolve、
未配置 stage_order、点名阶段不在表内、`required` 为字符串 `"true"` 等。

以及**分工断言**（不越界）：有环的计划 `guard` **不报** cycle，`TaskQueue.validate_plan` **能报**。

## 4. 实施中发现的问题（如实登记）

### 4.1 `_exec_react` **完全不读取 `agent`** —— 文档与实现不符

`workflows/nodes.py:845` 的 docstring 写着：

> `agent: 可选，思考由指定 Agent 体系驱动（forced_intent）`

但实现里从未取过 `cfg["agent"]`，只用 `provider_id` 调 LLM。
⇒ **react 任务声明的 agent 是假的**，不会生效，而审计会误以为派给了它。
本批不修（改它等于改 react 的执行语义，属独立决策），改为**报 warn 让声明失效可见**（`route.ignored_by_type`）。

### 4.2 `react` 在生产里事实上从未被用过

`agent_tasks` 全表 **355 行**：

| task_type | 次数 | 结果 |
|---|---|---|
| `agent` | **352** | 263 done / 87 failed / 2 cancelled（成功率 74.7%） |
| `llm` | 2 | 1 done / 1 failed |
| `react` | **1** | **failed** |

唯一那条（2026-10-27，`按三次 offset 读取 SysML 导出文件`）失败原因是
「编排中断：超过 30 分钟无任何进展，判定为孤儿运行」—— **不是 react 逻辑错**，是进程重启。

⇒ 结论：react 是"**有实现、有接线、但从未产生过价值**"的能力。
要它有用，得先补 4.1 的 agent 语义，并给它明确适用场景（多步工具求解），否则它是维护负担。

### 4.3 失败的主因不是"跑错"，是"跑丢"

89 条失败中 **80 条（90%）是孤儿运行**（>30 分钟无进展，进程重启或执行线程丢失），
7 条 timeout，1 条"子任务未产生输出"。

**没有一条是"路由键非法"导致的失败** —— 因为非法路由键**根本不失败**，它静默降级。
这恰好从反面证明本批的必要性：**能被指标看见的失败只是少数，看不见的那类才是主要风险**。

### 4.4 历史孤儿引用

`agent_id` 无法解析的历史任务 **37 行**：`zhiyuan_mgmt` 29 行（该 Agent 已被移除）、
`智源平台管理` 8 行（从未是任何 Agent 的 name 或 display_name）。

⇒ 本批**不修历史数据**（改历史等于篡改"当初派给了谁"的存证）。
但校验器会拦住**新的**非法路由，不会再产生新的孤儿。

## 5. 配置与使用（都不改代码）

| 想做的事 | 怎么做 |
|---|---|
| 换阶段序 | 改 `generate_rules.pipeline_stage_order` 的 JSON 数组 |
| 改必需阶段 | 改 `generate_rules.pipeline_required_stages` |
| 停用校验 | `pipeline_guard_mode = off` |
| **收紧成拦截** | `pipeline_guard_mode = block` |
| 只关阶段序 | `pipeline_stage_order = []`（其余规则照常） |
| 灌回默认 | `python tools/seed_pipeline_guard_rules.py --apply --force` |

读配置是**每轮编排即时读**（`load_pipeline_config(conn)`）⇒ 改完**不用重启**。

## 6. 边界与未做

1. **只校验"计划层"，不校验"执行层"**：子任务真跑起来后是否按 deps 顺序收敛，
   仍由 `TaskQueue` 的状态机保证，本模块不介入。
2. **阶段序只在 deps 上判，不判"实际执行顺序"**：若两个阶段任务无 deps 关系而并行执行，
   本模块不报（并行是合法设计，判它等于削掉并行能力）。
3. **不做自动修复**：不重排、不删边、不改 agent。报问题 + 给 fix 建议，改不改由人或 planner 决定。
4. **不替模型猜意图**：`stage_order` / `required_stages` 没配就跳过，不推断"应该是什么顺序"。
5. **与上游对标文档的差距仍然存在**：候选方案关联模型（`model_ref`）、空间 sweep、
   阶段清单表化（4 处代码常量）三项**未做**，仍是下一阶段。
