## 1. S1 · 会话级失败归因

### 1.1 根因（两个错误叠在一起）

1. **失败不带原因**：调用侧 `meta=dict(_conv_meta)`，而 `_conv_meta` **只在 done 帧**里回填
   intent/route；失败的流根本没有 done 帧 ⇒ 传进去的就是空 dict。
   `end_conversation` 对 `status != ok` 且 meta 为空也**不做补充** ⇒ 实测 73 条 error 的
   `meta_json` 全是 `{}`。
2. **真异常被记成 ok**（本轮新发现）：旧判定 `"ok" if _terminal else "error"`，
   而 `except` 分支会把 `_terminal` 置 True（它表示"**已通知前端**"）⇒ 抛出异常的一轮
   在 span 里显示 **ok**。`_terminal` 的语义与"这轮成功"被混用了。

### 1.2 修法

| 文件 | 改动 |
|---|---|
| `routers/conversations.py` | 引入 `_fail_reason`（枚举）、`_last_event`（死在哪一步）、`_sent_any`（有无输出）；`except` 分支记 `exception:<类型>`；**状态判定改为优先级链**：`client_gone` → `exception:*` → 已发 done → `no_terminal_frame` |
| `services/orch_span.py` | `end_conversation` 在 `status!=ok` 且无 `reason` 时补 `no_reason_recorded` + note，**明确表示"原因缺失"而非冒充根因** |

状态语义（新）：
```
client_gone        用户/网络主动断开（与服务端故障分开统计）
exception:<类型>   真异常
（已发 done）       ok
no_terminal_frame  流悄悄结束、前端会一直转圈 ← 最需要归因的一类
```

### 1.3 验证

`verify_conv_failure_attribution.py` **21/21**，含：
- 四个场景**真实落库**（自建临时库 + 真实 `flush(conn)` 路径，不 mock）
- **保护性断言**：具体原因不被兜底覆盖；`client_gone` 不被并进"服务端故障"
- 源码级：断言可执行代码里**不再出现**旧的单一哨兵（剥离注释后判，避免误伤）

> 首版门禁有 3 处假红，都是**我写错了而非实现错**：
> ① `flush()` 漏传 conn（`conn=None` 时直接返回 0，观测丢弃且不报错）⇒ A~D 全读不到行；
> ② E5 断言命中了**我自己写的注释**（注释里引用了旧写法作反例）⇒ 改为剥离注释后判。

## 2. S2 · 参数错误可执行化 + 学到就用

### 2.1 先核查别人做了什么（避免重复劳动）

工作区有另一会话的提交 `68c8714`（MCP 工具 required 参数校验）。核对覆盖度：

| 事实 | 结论 |
|---|---|
| 12 个报参数错的工具里 **11 个**在 `mcp_servers.tool_meta` 中 | 68c8714 **覆盖**这些 |
| `ask_user`（builtin）不在 | 但它**本身已有点名缺失项**的校验，不算缺口 |
| **`query_data_tree` 等 5 个工具的 schema 是空的**（`required=None` / `properties=0`） | ⚠️ 本地校验**根本没有判据** ⇒ 21 次失败一条都拦不住 |

⇒ 补口方向不是"再加一层本地校验"，而是**用远端返回的权威契约**。

### 2.2 远端报文其实信息很足，问题在没被采纳

真实报文（`tool_call_logs` id=5935）：
```json
{"code":"INVALID_ARGUMENTS","retryable":false,
 "fields":[{"expected":"keyword, pageNum, pageSize, parentId, type, version",
            "constraint":"KnownField","field":"value",
            "message":"此字段未在工具中声明，请删除或改用 expected 中的字段"}],
 "recovery":{"action":"CORRECT_ARGUMENTS","instructions":"…"}}
```
**决定性证据**：46 条参数错里 `field=value` 占 18 条，且 **8/12 个会话在重复犯**
（conv 9629 犯 **11 次**、conv 9736 犯 9 次）⇒ 说明"把原报文追加在结果**末尾**"模型根本没采纳。

### 2.3 修法（新增 `agent/tool_arg_hint.py`）

| 动作 | 说明 |
|---|---|
| `parse_arg_error()` | 从报文提取 `fields[]` + `allowed`（只认**有 field 名**的条目；`expected` 只取像字段名的 token，避免把类型当字段） |
| `format_hint_zh()` | 转成中文祈使句：**点名必删字段** + **列出唯一可用字段** + 服务端要求（252 字符 vs 原 399） |
| `lead_with_hint()` | **前置**（不是末尾），原文完整保留供核对 |
| `learn()` / `recall()` | 落 `tool_arg_hints` 表（`ON CONFLICT` 累加 `hit_count`） |
| `describe_suffix()` | 工具定义构造时把"只接受 X；**不要**使用 Y（曾被拒）"注入 description |
| `tools.py` 接线 | 失败汇合点（`_exec_tool_call_impl` 方法级，覆盖全部 10+ 失败出口）+ 工具定义构造处；置 `retryable=False`（服务端已标不可重试，同参重试必再错） |

开关：`tool_jit.inject_arg_hints`（默认开，关=完全回旧行为）。
**刻意不挂在 `obstacle_recovery_enabled` 下**：那个是"猜类别给建议"（默认关是合理的），
本项是**转述服务端断言**，无猜测成分。

### 2.4 验证

`verify_tool_arg_hint.py` **36/36**：真实报文解析、中文指令要点、5 个不误判负例、
learn→recall→describe 闭环、接线源码断言。

> 首版门禁**污染了生产库**（`os.environ` + `importlib.reload` 没生效，`learn()` 写进了 `mbse.db`，
> 且连跑两次 `hit_count` 累加 ⇒ E4/E5 假红）。改为直接替换 `tool_arg_hint._conn`，
> 并在断言前 `DELETE` 清表 ⇒ **连跑两次均 36/36、生产库零写入**。

## 3. S4 · 检索观测口径

### 3.1 修的是什么

`trace_query(...)` 原先放在**向量兜底分支内部**且 `"route": "vector"` **硬编码**
⇒ `query_trace` 3,484 条**全是 vector**，图/混合路由零 trace。

**危害不是少几行，而是据错数据得出相反结论**：上一轮我据此判"图路由零命中"，
查 `query_routing_stats` 才发现图路由占 **264/1867（14%）**。

### 3.2 修法

移到 `router.decide()` **之后**统一写，`route` 用真实值，`detail` 增加
`reason` / `graph_count` / `vector_count` ⇒"为什么走这条路"可按列聚合。

### 3.3 零命中：结论要修正（本轮最重要的判断翻转）

上一轮写"检索 **21% 零命中**"暗示召回质量差。逐条看过后：

| 构成 | 条数 | 占比 | 性质 |
|---|---|---|---|
| 指令性文本（`请生成…`/`澄清补充…`） | 26 | **44%** | **本就不该走知识库** |
| 业务数据查询（`工程列表`/`projectId`/`包结构`） | 7 | 11% | 应走工具 |
| 过短噪声（`q0`/`工程`） | 5 | 8% | 统计污染 |
| **真·召回缺口**（语料里没有，如飞控系统） | 21 | 35% | 这才是召回问题 |

⇒ **≥55% 的"零命中"不是检索错了，是检索被用在了不该用的地方。**
把两类混算会把人引向"去调向量阈值"这条错路。

**本轮的处置是只改归因、不改行为**（新增 `agent/retrieval_reason.py`）：
细分 `no_hit_directive` / `no_hit_biz_query` / `no_hit_tiny` / `no_hit_corpus_gap`，
并提供 `is_real_recall_problem()`（只有 `corpus_gap` 才算）——否则看板负责人会继续把 55% 错配算进召回失败率。
是否要在检索前就跳过这类查询，**等有真实分布数据再决定**（先观测后优化）。

### 3.4 分类器标定（踩了一个真实的误伤）

首版 `_KB_TERMS` 含裸 **`定义`** ⇒ 样本 `块定义图_BDD`（Block **Definition** Diagram）
的「定义」命中，把一句指令误判成知识提问。建模语境里「定义」是**产物名的一部分**。
已改为只认明确提问搭配（`定义是什么` / `的定义是`），并补入 `目标是生成` / `生成…（视图|模型|代码|图）`。

### 3.5 验证

`verify_retrieval_observation.py` **39/39**，含**保护性负例**（真实知识提问必须仍算 `corpus_gap`：
"什么是需求定义"、"如何生成状态机视图"、"块定义图与内部块图的区别是什么"）。
真实样本回放 154 条：directive 58 / biz 10 / tiny 24 / corpus_gap 62。

现网验证：`POST /api/knowledge/retrieve` 产生 `query_trace` id=3826，
`route=vector`、`reason=graph_no_hit`、`graph_count=0`、`vector_count=20`
—— 这三字段是**新代码独有**（旧代码 detail 只有 glossary 三项）。

## 4. S5 · 编排子任务失败归因

### 4.1 先纠正上一轮的结论

上一轮报"编排子任务失败率 **20.6%**"，读起来像"编排逻辑不可靠"。
实测全量 65 条 failed：

| 原因 | 条数 | 占比 |
|---|---|---|
| 「编排中断：超过 30 分钟无任何进展，判定为孤儿运行（进程重启…）」 | **57** | **87.7%** |
| `timeout` / `timeout（240s 无产出）` | 8 | 12.3% |

⇒ 绝大多数是**宿主重启的副产品**（孤儿回收是防僵尸任务的正常设计），
不是 7 个独立失败，而是同一个根的 7 次表现。

### 4.2 真缺口：`error_class` 填充率只有 3%

`services/failure_class.py` **早已把 `interrupted` 单列一类**并与 `timeout` 区分
（一个宿主挂了、一个逻辑停滞），且对存量 100% 覆盖。缺的只是
`core/run_registry.py` 那条 `UPDATE agent_tasks SET status='failed', error=?` **没写 `error_class` 列**
—— 典型「能力在、没接线」。

### 4.3 修法 + 一个自己差点引入的坑

```python
# 先试带 error_class，失败则退不带
try:
    UPDATE ... SET status='failed', error=?, error_class=? ...
except Exception:
    UPDATE ... SET status='failed', error=? ...      # ← 老库无列时的降级
```
**为什么必须有降级**：若无条件写 `error_class=?`，极老库会抛 `no such column`
⇒ **整批孤儿一条都收不掉**（僵尸任务永久堆积）—— 这比"少一列归因"严重得多。
与 `task_queue.fail()` 的既有写法保持一致（同一词表、同一降级口径）。

### 4.4 验证

`verify_orch_failure_class.py` **21/21**，核心是 **C 组负例**：
在**没有 `error_class` 列**的库上跑回收，断言「仍成功回收、状态仍 failed、error 仍写入、不报错」。
端到端实测：造 40 分钟前停住的 running 任务 ⇒ `reaped=1`、`error_class=interrupted`。

## 6. 顺手清掉一处存量门禁红（非本轮引入，先证后改）

`verify_failure_class.py` 长期 **EXIT=1**（48/49）。查明 D2 断言把变量名写死成
`as _fc` + `_fc = None`，而实现早已演进为 `as _fc_main` + `_FC_MAIN_OK` 标志，
且 2189 行 `if _FC_MAIN_OK else "internal"` 才是真降级 —— **实现比旧断言要求的更健壮**。

- 先证：用 `git show HEAD:...stream.py` 复现，确认 HEAD 版本同样不满足旧正则（**存量红**）。
- 再修：断言改为按**语义**判（try 内 import + except 置 `*OK` 标志），不抠变量名。
- 结果：**49/49 + 变异自证，EXIT=0**。

> 纪律：门禁断言写错 ≠ 实现错。改断言前必须先证明实现是对的。
