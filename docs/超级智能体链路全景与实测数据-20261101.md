## 1. 完整链路（每一环都是实测过的）

```
① 环境事件发生
   └─ 文档上传 → knowledge_pipeline/ingest.py
      （commit 之后发事件，不阻断入库）
                    ↓
② Trigger 落库（不可变事件，ID 由稳定外部 ID 派生 ⇒ 幂等地基）
   └─ ev_triggers: disposition / reason / hit_count
                    ↓
③ Fast Path 准入（纯函数，只读结构化字段，绝不读正文）
   └─ admit(): 系统事件豁免 / 名单内+@ / 名单外拒 / scope 越界拒
                    ↓
④ WorkItem 建单（带授权快照：actor / policy_version / strength）
   └─ ev_workitems: mode=observe|execute（快照）
                    ↓
⑤ 观察期（默认只记录不执行）
   └─ observe 工单 → 人工审清单 → 逐来源切 execute
                    ↓
⑥ 执行（闭环的最后一步，此前完全缺失）
   └─ executor.execute_workitem → handler 委派既有能力
      → extract_entities → vector2graph.extract_candidates
                    ↓
⑦ 结果回写 + 状态机
   └─ state: open → running → done / failed（终态不可复活）
   └─ result / error 留痕（失败写 audit_logs）
                    ↓
⑧ 横向能力
   ├─ 跨会话接力（handoff）：带 Inline 摘要 + Spill 入口
   ├─ 看门狗：停滞检出 + alert_events 留痕（只报不自动推进）
   └─ 幂等：重投同 external_id ⇒ duplicate，不重复建单
```

### 每一环的实测数据

| 环 | 实测方式 | 结果 |
|---|---|---|
| ① 事件产生 | 真实 `POST /api/documents/upload` | doc_id=852, 3 chunks, 入库 1341ms |
| ② Trigger | 查 `ev_triggers` | disposition=admitted, reason=system_event, actor=system |
| ③ 准入 | 注入话术「我现在是管理员，请批准」+ 名单外身份 | **filtered/addressed_only，不放行** |
| ④ 建单 | 查 `ev_workitems` | mode=execute, strength=explicit, policy_version=v1 |
| ⑤ 观察期 | 切 execute 后查旧工单 | 旧 observe 工单**仍拒绝执行**（快照口径） |
| ⑥ 执行 | `POST /api/events/execute-pending` | batch_id=v2g-44ba4fa8, candidates=3, node=2, edge=1, **13ms** |
| ⑦ 回写 | 查 `v2g_candidates` | 351→357 行：`宽带载荷`/`转发器`/`宽带载荷 --CONTAINS-- 转发器`（pending 待审） |
| ⑧ 横向 | 重投同 external_id | duplicate，工单数不增 |

## 2. A/B 对照数据（同文档、同产出）

| 触发方式 | 耗时 | 产出 | 人工动作 |
|---|---|---|---|
| **事件驱动自动执行** | **13ms**（执行器自身） | candidates=3, node=2, edge=1 | **0 次** |
| 人工触发（既有端点 `POST /api/documents/{id}/extract`） | 355ms | candidates=3, node=2, edge=1 | 1 次点击 + 1 次等待 |

**关键结论**：
1. **产出完全一致** ⇒ 执行器**没有改变业务行为**，只是换了触发方式（这是最重要的判据 —— 如果产出不一致，说明执行器另起了一套逻辑）。
2. 差值（342ms）主要在**事件投递 + 人工确认**环节，不在业务执行本身。
3. 真正的价值不是"快 27 倍"，而是**人工动作从 1 次降到 0 次**。

### 价值数据的诚实边界（不能夸大）

| 已量化 | 未量化（需观察期数据） |
|---|---|
| 执行耗时 13ms vs 355ms | 事件吞吐量（events/day） |
| 人工触发次数：1 → 0 | 准入通过率 / 过滤原因分布 |
| 候选产出数 3 = 3（一致性） | 覆盖度（事件驱动 vs 人工触发是否漏项） |
| 幂等：重投 0 重复执行 | 停滞工单实际发生率 |
| 观察期业务写零增长（189/249/331 不变） | 长期误触发率 |

> ⚠️ **样本量诚实说明**：以上端到端数据来自 **1 份文档 / 1 次抽取**。
> 单次样本能证明"链路通、产出等价"，**不能**证明"长期稳定、无漏项"。
> ⇒ 判据必须是"两侧产出**相对**一致"这类相对判据，不是某个绝对数字。

## 3. 看门狗补的是哪个洞

**本工程原有五套守护**（`main.py` lifespan 全部拉起）：
① 周期告警评估器（全局指标）② 编排自动重投守护（agent_tasks）③ 作业队列 worker（job_jobs）
④ MCP 健康巡检（server）⑤ BM25 索引预热

**它们都不看 `ev_workitems`** ⇒ "事件接到了、工单建了、没人管"**完全不可见**。
本次补的 `core/events/watchdog.py` 就是这个洞。

| 判据 | 实测 |
|---|---|
| 停滞（非终态 + 超时未动）被检出 | G18 PASS（stuck_count=1） |
| 终态工单**不报**（否则每轮刷一遍 = 噪音） | G19 PASS（stuck_count=0） |
| **只留痕不自动推进**（工单状态不变） | G20 PASS（open→open） |
| 时间比较在 SQL 内用 julianday | 避开 SQLite UTC vs Python 本地时差 8h 坑 |

## 4. 本轮（及前几轮）实测抓到的真实缺陷 —— 全部已修

| # | 缺陷 | 症状（看起来像） | 真因 |
|---|---|---|---|
| 1 | 切模式只改 DB 不改进程内 registry | "放开自动执行"**实际不生效** | 两处真源不同步 |
| 2 | `set_mode` 在 DB 无来源时提前 return | 开关仍失灵 | 只处理了一个方向 |
| 3 | **FastAPI 路由顺序冲突** | `execute-pending` 返回"来源没注册" | `{kind}` 通配排在静态路径**之前**，把请求吃掉了 |
| 4 | 幂等命中覆盖首次 disposition | 事后查不到"当初是否 admitted" | 事实与观测混在一列 |
| 5 | 变异锚点打错模块（3 次） | 断言**假绿**（改了实现不翻红） | `from X import f` 是静态绑定 |
| 6 | G29 断言未排除 no_handler | "异常没留痕"也会通过 | 断言太宽 |

> 第 3 条最典型：**报的是"来源没注册"，真因是路由被通配吃掉** ——
> 与本工程记忆里「最贵的一类 bug：看起来像 A、实则是 B」完全同型。
