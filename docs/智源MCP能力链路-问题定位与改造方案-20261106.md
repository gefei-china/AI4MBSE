## 二、关键数据（决策依据）

### 2.1 MCP 工具构成（71 个，实测）

按「名称 + 平台契约」双判据派生：

| 档位 | 数量 | 占比 | 判据来源 |
|---|---|---|---|
| `destructive` | 3 | 4% | `delete_*` / `remove_*` 命名 |
| `write` | 39 | 55% | `approvalId` 38 + `commands` 1 |
| `read` | 29 | 41% | 默认只读（`query_*` / `get_*` / `list_*` / `export_*`） |
| **非只读合计** | **42** | **59%** | — |

> 关键发现：智源平台**自带审批契约**——38 个工具的 `inputSchema` 带顶层 `approvalId`（`readToken` 也是 38 个）。这比命名规则可靠，因为它是平台契约而非猜测。纯命名规则只能覆盖 67/71，4 个判不出来（`place_model_activity_nodes`、`present_model_elements`、`present_model_relationship`、`run_modeling_automation`）——恰好都被 `approvalId` 判据救回。

### 2.3 行业对标（2026-09 五框架实测，脚本化模型、直接打印工具函数体是否运行）

| 框架 | 子继承父工具 | 委派时能否扩大权限 | 内置收窄 |
|---|---|---|---|
| **Claude Code / Agent SDK** | **是，默认继承** | 工具：**不能**（CLI 拒绝池外工具） | **有**（池上限=父池） |
| LangGraph / Deep Agents 0.7.6 | 否 | **能** | 无 |
| CrewAI 1.15.16 | 否 | **能**（实测子跑了父没有的 `crm_export`） | 无 |
| OpenAI Agents SDK 0.22.0 | 否 | **能** | 无 |
| Google ADK 2.7.1 | 否 | **能**（2.10.0 实测 transfer target 跑了 coordinator 从未持有的工具） | 无 |

**判据**：四家「子跑自己的」都没防住权限扩大；只有 Claude Code 的「继承 + 上限」能保证 **子 ⊆ 父**。

Claude Code 的实现要点（可直接对标）：
- 子默认继承 built-in + MCP，再用 `tools`（allowlist）/ `disallowedTools`（denylist）收窄；两者都给时**先 deny 再 allow**。
- 支持 MCP **服务器级**模式：`mcp__server` / `mcp__server__*`；`mcp*` 移除全部。
- 源码注释：「replaces ALL allow rules so the agent only has what's explicitly listed (parent approvals don't leak through)」——**替换而非合并**。
- **子不能比父更宽**；`forks` 例外（拿主会话完整池）——对应我们「主 Agent 本体直行拿全池」。
- 列表解析为空时**拒绝启动并列出未解析项**（v2.1.208 前是静默启动，已作为事故修复）。

合规侧：OWASP **LLM08 Excessive Agency** 在 2026 版从第 6 升到**第 3**（因新部署基本都是带工具的 Agent）。核心不是「少给工具」，而是**授权要在下游执行层落实，不能靠模型自觉**。AWS 的落地是 Cedar 策略在**推理循环之外**授权每次工具调用 + 分层 IAM + 审批闸。

## 三、方案：A 先落地，B 定为目标态

### 方案 A（推荐先做）：一次解析 + 继承收窄

**一句话**：把「执行主体能拿到什么工具」变成**一个纯函数**，直行与编排共用；默认继承主 Agent 的池，按执行者职责收窄，**永不超出父池**。

| 改动点 | 位置 | 内容 |
|---|---|---|
| ① 收敛解析 | 新增 `agent/tool_scope.py` | 现逻辑散在 `pipeline_parts/tools.py:240`（直行）+ 编排侧无 |
| ② 统一调用 | `stream.py:5284` + `planner.py:894` | 编排侧传入主 Agent |
| ③ 空池报错 | 复用 `registry.resolve` 的 `hint` | 解析为空→拒绝执行并列出未解析项，不静默降级 |

**不需要新增 `mcp_profile` 字段**——已有两套机制就是它：

- `side_effect` 驱动的「写类默认不注入」（`tools.py:646`）
- 计划里的 `tools` 白名单只能**收窄**不能扩大（`tools.py:625` 在 Agent 自己的候选集上过滤，LLM 写它没有的工具只会被滤掉）

### 方案 B（目标态）：能力信封

委派时**显式签发**凭证，执行层在执行前核对，模型说了不算。

- 信封：`{env_id, issuer, subject, tools[], side_effect_max, data_scope, ttl, approved_by}`
- 强制点：`_exec_tool_call`（直行与编排共用入口）
- **fail-closed**：`side_effect` 未登记的工具默认拒绝
- 审计：`tool_call_logs` 增 `envelope_id`，整链回溯

### 为什么是 A 先 B 后（不是折中）

两者的**数据依赖是同一条**：都必须先有 `side_effect` 标注。但 A 在标注完成前就能靠「子 ⊆ 父 + 统一解析」立刻修好编排断链，B 不能。

顺序：**补标注（P0）→ 方案 A（P1）→ 方案 B（P2）**

## 四、要做的改动（分优先级）

### P0 · 数据地基：`side_effect` 自动派生

**目标**：让 71 个 MCP 工具有副作用档位，且**不依赖人工维护**（MCP 升级后自动跟进）。

| 项 | 内容 | 规模 |
|---|---|---|
| P0-1 | `tools` 表加两列：`side_effect_source`（`auto`/`manual`）、`rule_version` | 迁移脚本 ~10 行 |
| P0-2 | 新增 `agent/tool_side_effect.py`：纯函数 `derive(tool_meta) → (side_effect, rule, version)` | ~40 行 + 单测 |
| P0-3 | `mcp_health.discover_server()` 落库后同步到 `tools` 表（当前只写 `mcp_servers.tool_meta`，**完全不碰 `tools`**—这就是 0/71 的根因） | ~40 行 |
| P0-4 | `register_http_tools._upsert_tool` 加**来源保护**（`manual` 不覆盖） | ~10 行 |

**派生判据（三级，顺序敏感）**：

```
① delete_/remove_/drop_/purge_ 前缀          → destructive
② inputSchema.properties 含 approvalId       → write
③ 含 commands（批量变更，票据在每条命令内）  → write
④ 写前缀命名 create_/update_/set_/...        → write
⑤ 其余                                        → read
```

实测覆盖率：**71/71 自动定档，需人工裁决 0 个**（`validate_sysml_text` 抽查确认为 read，正确）。

**适配四种变更加载场景**：

| 场景 | 行为 | 是否要人工 |
|---|---|---|
| MCP 升级新增工具 | discover 自动登记并定档 | 不用 |
| MCP 升级删除工具 | 标 `status=deprecated`，**不物理删除**（绑定靠 name 引用，删行会悬空） | 不用 |
| 工具语义从读变写（新增 approvalId） | `auto` 项自动改档；`manual` 项保持原判但**审计告警** | 看告警 |
| 人工判定某工具需更严 | UI 改 → `source=manual`，此后永不被覆盖 | 一次 |

### P1 · 修编排断链

编排路径传入主 Agent，复用既有 `_team_main_agent` 继承机制。当前 `planner.py:894` 每次 `AgentPipeline()` 新建，无人赋值 ⇒ 5/7 成员零平台工具。

| 能力信封 | 见方案 B | 治理阶段 |

| # | 风险 | 等级 | 说明与缓解 |
|---|---|---|---|

### 必须说清的一件事（关于「价值与风险」）

**当前最高风险不是代码，是 R3 这个产品决策。**

如果采纳「主 Agent 绑所有」，那么：
- P0 做的读写分级**不会生效**（因为写类会被下放给所有成员）
- 方案 A 的核心保证（子 ⊆ 父）**归零**
- 与 OWASP LLM08 的方向**正好相反**

正确的绑定口径是：**主 Agent 绑「这类任务需要的平台能力」，成员绑「自己的领域技能」**。技能不需要主 Agent 绑——默认 `bound_first` 下未绑定技能仍能从全局池命中（`skills.py:186-208`），绑了只影响优先级，反而增加误命中。

## 9.6 第 4 问的实测结论：子 Agent 的 MCP 是否受限 / 主 Agent 未绑会怎样

**结论：子 Agent 自己的绑定不受主 Agent 影响；主 Agent 未绑 MCP 时，只有「自己也没绑 MCP」的子 Agent 会失去平台能力。**

实测（读类查询，`_team_main_agent` 有/无两组对比）：

| 执行者 | 自身绑定 MCP | 主 Agent 有 MCP | 主 Agent 无 MCP |
|---|---|---|---|
| design | 有 | 总 12 / MCP 6 | 总 12 / MCP 6（**不变**） |
| knowledge_qa | 无 | 总 11 / MCP 6 | 总 4 / MCP 0 |
| impact | 无 | 总 12 / MCP 6 | 总 5 / MCP 0 |

子 Agent 的 MCP 工具**确实受限**，共 6 道闸（按触发顺序）：

| # | 闸 | 说明 |
|---|---|---|
| 1 | `status='online'` | 服务离线则整台 MCP 的工具全部不注入（硬闸门） |
| 2 | `enabled=1` | 停用即不参与 |
| 3 | 技能白名单 `_tool_whitelist` | 会裁 MCP；但 `mcp_exempt_skill_whitelist=True` 默认**豁免 MCP** |
| 4 | **`side_effect` 写意图闸（本次新增生效）** | 写/破坏性工具默认不注入，除非输入含写意图词 |
| 5 | MCP 动词闸 `filter_mcp_by_intent` | 按工具名动词族判断"这轮该不该递到眼前" |
| 6 | 计划里的 `tools` 白名单 | **只能收窄**（在自身候选集上过滤），LLM 写它没有的工具会被滤掉 |
| 7 | JIT 语义预筛 | 会裁，但**显式绑定的 MCP 工具**列入保底不裁 |

> 所以"子 Agent 绑了 MCP 就能用"并不完全成立 —— 还要过 4/5 两道**恰当性**闸（权限 vs 恰当性是两件事）。

# 十一、本轮顺带修的两个真 bug

## 11.1 `delete_skill` 删同名草稿会误清正式版绑定（严重）

```python
# 修前
DELETE FROM agent_tools WHERE tool_type='skill' AND tool_name=?   # 只按 name
```

`skills.name` 不唯一（实测「智源平台管理」3 份：1 published + 2 draft_revision）。
删任意一份草稿 → 按 name 把**全部**绑定清掉，而 published 那份还活着。

**实测证据**：删 id=133（草稿）时清理了 3 条绑定，而 id=95（published）仍在库。
用户视角是"我删了个重复项，怎么技能全没了"。

修法：先数同名剩余份数，**只有一份都不剩**时才清绑定。

```
修复后实测：DELETE 133 → {"same_name_left":2,"bindings_cleared":0}
           DELETE 136 → {"same_name_left":1,"bindings_cleared":0}
           最终 3 条绑定全部保留
```

## 11.2 正式版技能缺「禁止空回复」铁律

「智源平台管理」三份正文各不相同：

| id | 状态 | 长度 | 有无输出铁律 |
|---|---|---|---|
| 95 | **published**（运行时实际注入） | 4958 | **无** |
| 133 | draft_revision（ai_improve v2） | 6043 | 有（7 条 + 固定话术） |
| 136 | draft_revision（ai_improve v3） | 5456 | 有（缩写版） |

所以「哪个更佳」不能简单答「保留 published」——**published 恰恰缺了最有价值的那部分**（正是「空回复」痛点的解法）。

处置：把 133 的「★ 输出铁律」整段 + description 补充**合并进 95**（4958 → 5744 字，铁律置于最前），再删两个草稿。三份原文已备份到 `docs/skill_backup/`。
