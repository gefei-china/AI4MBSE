## 3. C-1：汇总阶段断点恢复

### 3.1 交付

| 文件 | 改动 |
|---|---|
| `agent/orch_checkpoint.py` | 新增 `summary_written` 相关三件：`mark_summary_written` / `summary_only_eligible` / `prepare_resume` 增加 `mode`（`tasks`\|`summary`）；`resumable()` 收录"仅汇总"型批次 |

| `routers/orchestration.py` | `mode=summary` 时不重排任务；详情端点暴露 `resume_mode` / `resume_detail` |
| `static/js/mods/03-chat.js` + `chat.css` | 两种恢复模式用**不同文案与配色**（"继续编排" vs "重新生成汇总"） |

### 3.2 关键设计：标记必须与消息 INSERT 同事务

若分两次提交，崩溃会留下"消息已落但标记为 0" → resume 误判可重做 → **同一份汇总在会话里出现两次**。
所以 `mark_summary_written(conn2, run_id)` 写在同一个 `with db_conn() as conn2:` 块内（C-1b3 断言其位置）。

### 3.3 顺带修掉的自查缺陷：resume 插入空 user 消息

批次 2 的 resume 走 `execute_stream("")`，而该函数入口**无条件**落一条 user 消息
⇒ 每次恢复都会在会话里留下一条空消息。已加 `and not resume_run_id` 排除，并锁成断言 C-1b1/b2。

### 3.4 端到端验证抓到的**第二个真缺陷**（最重要）

第一版 `summary_only_eligible` 的兜底判据是"**该会话**是否已有 assistant 消息"。
端到端一跑就发现 summary 型批次**永远不出现**在清单里 —— 因为任何走到编排阶段的会话
都已有历史 assistant 消息（会话 514 实测 ≥6 条）。**这条兜底判据让功能彻底失效，却看不出来。**

修法：判据必须与"**这一次编排**"绑定 ⇒ 改为
`m.created_at >= checkpoint.created_at`（编排开始之后是否新增消息）。

> **教训**：兜底判据也必须锚定当次操作。锚错了，它不是兜底，是一堵墙。
> 已加两条回归断言：**编排之前**的历史消息不阻断（C-1j）、**之后**的消息仍阻断（C-1k）。

### 4.5 追查根因：删项目不留引用完整性（真缺陷，已修）+ 顺带查出 `execute` 语义缺陷

**根因**：`repositories/project_repo.py:165` 的 `delete_project` 是裸 DELETE。
删除路由只解绑了 `conversations` 与 `settings.default_project_id`，**不管 `entities`/`relations`**
⇒ 删项目必然留下悬空引用。种子项目 `project-satnet-broadband`（`database/seeds.py:249` 建的）
被删后，189 实体 + 249 关系全部指向一个 `projects` 表里已不存在的 id。
写入侧早已修好（`KnowledgeRepo.create_entity:281` 走 `resolve_project_id`），**不会产生新孤儿**。

**修法**（不删内容，符合"项目=任务容器、不级联删"的既定语义）：

| 改动 | 位置 |
|---|---|
| 新增 `detach_project_references()`：一次解绑 conversations / entities / relations | `repositories/project_repo.py` |
| 新增 `count_project_assets()`：删除前的影响面提示 | 同上 |
| 路由改为**先解绑、后删容器**（顺序不能反），并回报三张表的解绑数 | `routers/projects.py` |
| `task-count` 端点补 `entities`/`relations` 数（原先只报任务数，提示不完整） | 同上 |

**顺带查出的更大缺陷**（写 D3 运行时测试时被撞出来，**与隔离无关**）：

```python
# repositories/base.py::BaseRepo.execute
return cur.lastrowid or cur.rowcount     # ← 原实现
```

`lastrowid` 对 UPDATE/DELETE **无意义**（它是本连接最近一次 INSERT 的 rowid）。内存库实测：
先 INSERT 一行，再 `UPDATE ... WHERE id=999`（影响 0 行）⇒ 返回 **1**，`bool()` 为真；
影响 1 行时返回值**也是 1** —— **两种情形完全无法区分**。由此两个真实缺陷：

1. `unassign_project_tasks` / `detach_project_references` 的"解绑 N 个"**计数恒为脏值**
   ⇒ 删除项目的影响面提示一直是错的；
2. `ConversationRepo.assign_project` 用 `bool(n)` 判"会话是否存在"，路由据此返 404
   ⇒ **对不存在的会话 id 赋项目也会返回成功**。

修法：按语句类型分流（INSERT 取 lastrowid，其余取 rowcount）。安全性已复核：
全仓 `self.execute(...)` 的返回值消费点**只在 INSERT 处**需要 lastrowid，
UPDATE/DELETE 调用点绝大多数丢弃返回值 ⇒ 纯收益、无回归
（回归证据：`pytest 34 passed + 1 skipped`，与基线一致）。

## 7. 前端真机验证（并抓到一个只有真机能抓的缺陷）

用真实浏览器（agent-browser，1600×900，light）打开会话 514 验证恢复提示条。

### 7.1 抓到的缺陷：DOM 全绿但用户完全看不见

| 指标 | 修前 | 修后 |
|---|---|---|
| `getBoundingClientRect().top` | **-2948** | **87** |
| `inViewport` | **false** | **true** |
| `position` | static | **sticky** |

**根因**：提示条被 `insertBefore` 到 `#chat-area`（**可滚动容器**）的首位，
而会话默认滚到底部（还带 8 秒 `pinChatBottom` 钉底窗口）⇒ 它被顶到视口之外。
**修法**：`position: sticky; top: 0; z-index: 30`，语义仍是"顶部提示"，滚动时始终可见。

> 这与批次 1 记录的"位置型 bug"同族：**"元素在 DOM 里、class 也对" ≠ "用户看得见"**。
> DOM 断言 100% 全绿，而用户感知为 0。
