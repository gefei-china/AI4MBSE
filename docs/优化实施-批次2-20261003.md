## 2. 关键设计决策（与标杆做法的对齐与取舍）

### 2.1 为什么**不**做整图状态快照

LangGraph 的 checkpointer 存 `(thread_id, ns) → state`。直接照搬会在这里变成双份账本 ——
因为 **`agent_tasks` 已经是逐行 commit 的 state store**（每个任务的 status/result/metadata/retry_count）。
再存一份必然漂移。所以本批次只补原系统真正缺的那几项：

```
崩溃现场缺的不是"任务状态"，而是"这次编排原本要跑什么"：
    原始用户输入 · 意图 · 分支 · provider · 原始计划 · 执行阶段 · 心跳
```

沿检查点重进同一张图后，由 `agent_tasks` 自己决定还差什么 —— 这就是复用的依据。

### 2.2 resume 必须绕过 planner（最容易被做错的一处）

直觉做法是"把用户原话再发一遍"。它是错的：

1. 重跑意图识别（启发式，结论可能不同 → 直接走单 Agent 直行）；
2. **再调一次 planner LLM** → 得到不同任务拆分 → 旧任务的 `task_key` 对不上 → 复用失败；
3. 可能触发内容级澄清，把执行拦回去。

所以 resume 走**直达通道**：唯一依据是 `run_id` + 检查点，`planner` 调用被 `if not _resume_ck:` 守卫住，
`TaskQueue.create_plan` 落在 `else` 分支（I10c/I10d 锁成结构断言）。

### 2.3 三道闸门 + 幂等红线

| 闸门 | 作用 | 缺了会怎样 |
|---|---|---|
| 存活闸门 | 心跳未超时 ⇒ 拒绝接管 | 两个进程同时跑同一任务，写工具产生**重复实体** |
| 次数闸门 | attempt ≤ 5 | 「恢复 → 再崩 → 再恢复」自愈死循环 |
| 幂等闸门 | `done` 恒复用；`failed` 默认跳过 | 重跑已完成任务 ⇒ 不可逆的数据重复 |

`failed` 默认不自动重跑是本批次最保守的一条：它可能已经把副作用写了一半。
想重跑必须显式 `?include_failed=true`。

### 2.4 默认**不做**启动自动重投

`orchestration.auto_resume_on_startup` 默认 `False`。理由写进配置注释也写在这里：
① 中断前执行过的写类子任务可能已落一半副作用；② 崩溃若系统性（如 provider 配额耗尽），
自动重投会把剩余配额打得更干净。策略是**给入口，等人点**。

## 4. 过程中揪出的问题

1. **SQLite `CURRENT_TIMESTAMP` 是 UTC，Python `datetime.now()` 是本地时间**（UTC+8 差 8 小时）。
   取回 Python 做差会让心跳判定"永远活着"或"永远超时"。
   **修法：所有时间比较一律在 SQL 内用 `julianday` 完成**，并写成 I11 三条断言防回归。
2. **心跳不节流会打满 SQLite 单写者**：主循环每 50 ms 转一圈，长编排 20 分钟会产生海量 UPDATE。
   加了 `every_s=5.0` 节流，并用变异 M5 证明该断言非空转。
3. **变异 M3 首次判 VACUOUS** —— 不是 bug 而是**夹具不够真实**：`running` 任务没有 result，
   "被清空"看不出来。补成"崩溃往往发生在已写出半截结果之后"，变异才显形。
4. **验证脚本意外写到了生产库**（见下节）。

## 5. 生产库事件（必须披露）

`verify_orch_resume.py` 首跑时试图用环境变量切换 DB，但 `database.schema` 在 **import 期**就把
`core.config.DB_PATH` 绑进了模块作用域 —— 脚本顶部已 import 过 `core`，环境变量设置得太晚，
`init_db()` 于是直接在**生产 `mbse.db`** 上跑了一遍幂等迁移。

**取证（与批次 1 备份 `backups/pre-reap-20261003.db` 逐表比对）：**

```
新增表: ['orch_checkpoints']        ← 空表，本批次本就需要（下次启动也会建）
消失表: []
行数变化的表: [('audit_logs', 2277 → 2278), ('orch_checkpoints', None → 0)]
                 └ init_db 自身写的一条迁移审计
```

结论：**业务数据零漂移**，`agent_tasks` 212 行不变、非终态残留 0。
但这仍是一次"验证脚本写生产库"的纪律事故，已修：改为 **monkeypatch `schema.DB_PATH`**（I12f 注释留痕）。
