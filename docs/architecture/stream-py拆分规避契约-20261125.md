# stream.py 拆分规避契约（2026-11-25）

> 目的：P1 剩余收敛**不得**在未来拆 `stream.py` 时返工。
> 本文件是约束，不是设想；改动前先读。

## 一、已查证的阻塞事实

| 事实 | 数量 | 证据 |
|---|---:|---|
| 门禁直接读取 `agent/pipeline_parts/stream.py` **源码文本**做断言 | **105**（其中 104 在 `gates_manifest.json`） | `grep -rl 'stream.py' tools/verify/` 再筛 `_read(` / `open(` / `read_text(` |
| 门禁 monkeypatch `agent.pipeline_parts.stream` 的模块级全局 | 2 | `verify_code_fence_and_partial_archive.py:274`、`verify_dedup_and_finalize_hint.py:90` 都设 `SM.db_conn` |
| `StreamMixin` 的方法数 | 6 | `_stream_orchestrated_traced`(40) / `_stream_orchestrated_flow`(4020) / `_persist_partial_stream`(147) / `_clarify_finish_events`(42) / `_hil_confirm_finish_events`(40) / `execute_stream`(3488) |
| 两个巨型方法把三类职责**交织在同一函数作用域** | — | SSE / 编排 / 续传的局部变量互相引用，不能按方法边界干净切开 |

⇒ 一旦把方法搬走，那 105 个源码断言会失效，且**极可能静默变成假绿**——
这比 623 KB 单文件本身更危险。

## 二、本批（以及后续 core 收敛）承诺遵守的五条

1. **不改 `agent/pipeline_parts/stream.py` 本体**——包括 import、docstring、行尾。
   判据：`git diff -- agent/pipeline_parts/stream.py` 必须为空。
2. **不改任何门禁里针对 `stream.py` 的源码断言**（包括变异锚点字符串）。
   判据：`git diff -U0 -- tools/verify/ | grep '^[+-].*stream\.py'` 必须为空。
3. **不改变 `stream.py` 直接依赖的公开 API 名称与签名**：
   `core.audit.audit / audit_user`、`core.config.config`、`core.plan_guard.*`。
   这些模块若要收敛，只能**内部改依赖方向**（依赖注入），不能改导出名。
4. **不把 `stream.py` 依赖的模块物理搬走**——`core/audit.py`、`core/config.py`、
   `core/plan_guard.py` 在拆分批次启动前保持原位。
5. **新增门禁一律不写死 `stream.py` 的单文件路径**，统一走未来的源码视图入口
   （见第三节），避免继续扩大 105 这个数字。

> 2026-11-25 实际执行：已从 `core` 归位 16 个模块到 `services` / `core/domain`，
> 其中**刻意排除了** `core/audit.py`、`core/config.py`、`core/plan_guard.py`；
> 迁移脚本还显式跳过 `agent/pipeline_parts/stream.py`。上述五条已逐条自证。

## 三、未来拆 stream.py 的路线（两步走，顺序不可颠倒）

### 第一步：给 105 个门禁提供统一「源码视图」

建立 `tools/stream_source.py`，暴露：

```python
def read_stream_source() -> str:
    """按固定顺序拼接 stream.py 拆分后的各模块源码，供源码断言门禁使用。"""

def module_for(anchor: str) -> str:
    """给定断言锚点，返回该锚点所在的真实文件路径（用于变异写回）。"""
```

然后把 105 个门禁里的 `open("agent/pipeline_parts/stream.py")` / `_read(...)` 统一换成
`read_stream_source()`；把需要写回变异的 2 处 `SM.db_conn` 注入改成显式参数传递，
不再依赖模块全局。

**验收**：105 个门禁在「未拆分」状态下全绿，且 `read_stream_source()` 的逐字节内容
与当时的 `stream.py` 完全一致（哈希自证）。这一步完成后，拆分对门禁不可见。

> **2026-11-25 实际执行结果**：门禁侧收口已完成，**86 个门禁文件 / 132 个调用点**，
> 读侧「真正 open stream.py」的调用点 = **0**（由 `verify_stream_source_view.py` 的
> V9 判据持续钉住，不是一次性结论）。
>
> 精确口径与早期估算的差异（**四**次修正）值得记下来，因为每一版脚本都漏了一种写法：
>
> | 版本 | 认的形态 | 漏掉什么 | 后果 |
> |---|---|---|---|
> | v1 | `open(<含 stream.py 的字面量>)` | 门禁自定义 `def read(rel)` 辅助函数 | 11 个门禁（6 个 pr 级）仍读真实单文件 |
> | v2 | 上 + `Path(...).read_text()` | `sp = os.path.join(...); open(sp)` 变量间接 | 33 个文件 / 52 处仍直读（`verify_orch_interrupt` 的 W1/M3 就在其中） |
> | v3 | 上 + 一层变量传播 | — | 读侧归零 |
> | v4 | 上 + **二进制语义**（`open(...,"rb")` → `read_stream_source_bytes()`） | 3 个文件把 bytes 换成 str ⇒ `AttributeError`（`orig.decode(...)`） |
>
> ⇒ 三条纪律：
> ① **「扫干净了」是断言，不是事实**；判据必须是可复核的脚本 + 归零这个数字；
> ② 「文件数」要按**调用点**再核一遍（31→86 的差距就是这么出来的）；
> ③ 替换读取表达式时**必须保住类型**：`"rb"` 给 bytes、文本模式给 str，混了就是运行时崩。
>
> **写侧已知债（拆分第二步之前必须清）**：7 个变异点仍在做「整文件改写 → 回滚」
> （`open(fp,"wb").write(whole_src)`，共 14 次调用，见上表预算）。拆分后这类写法会把
> 「拼接后的全文」写进某一个分片 ⇒ 直接写坏源码。现由 V8 棘轮钉住数量（只降不升），
> 正确的收口方式是使用时按锚点定位分片读写（`module_for` + 新增 `read_part`）。


### 第二步：按 mixin 分文件，再拆巨型方法

1. 用 AST 把 6 个方法按职责分到 `stream_sse.py` / `stream_orchestration.py` /
   `stream_checkpoint.py`，`stream.py` 退化为组合入口（`StreamMixin` 继承三个 mixin）。
2. 更新 `read_stream_source()` 的拼接顺序与 `module_for()` 的锚点映射。
3. 105 个门禁**不改一行**，应自动全绿。
4. 再考虑把两个 4000/3500 行的方法内部按阶段拆函数——这是更小的后续批次。

## 四、为什么不用「直接拆 + 同步改 105 个门禁」

- 改动面 105 个文件，且断言失败与静默假绿难以区分；
- 一旦某个门禁漏改，它会**继续绿着但什么都没验**——这正是 P0 在治的病；
- 两步走把风险集中在第一步的「视图等价性」上，而这一步有可验证的硬判据（哈希一致）。

## 五、同族设施：`tools/module_source.py`（垫片穿透）

stream 视图解决的是「**一个文件拆成多个**」；P1 归位已经先制造了它的孪生问题
——「**文件搬到新位置、旧路径留 5 行垫片**」。94 个旧路径现在都是：

```python
import sys as _sys
from services import orch_supervisor as _impl
_sys.modules[__name__] = _impl
```

门禁按旧路径读源码 ⇒ 读到这 5 行。两种后果**不对称**：
  * `"X" in src` ⇒ 恒红（吵，能发现 —— 本轮实测 4 个门禁因此红）；
  * `"X" not in src` ⇒ **恒绿**（静默假绿，不会自己暴露）。

⇒ `tools/module_source.py` 提供 `resolve_source()` / `read_module_source()`，
读之前先把垫片解析到真实实现。换行语义刻意与 `open(..., encoding=).read()` 对齐
（与 stream 视图同一个坑：不一致会批量假红）。

拆分第二步之后，`stream.py` 也会变成"组合入口 + 若干 mixin 文件"；
若届时为了让旧路径 import 继续可用而留垫片，**同一套解析规则直接复用**。
这也是本节与第一节并列为「规避契约」的原因：两条都是"让源码断言与物理布局解耦"。

守卫门禁：`verify_module_source_resolution.py`（8 项 + 2 变异），钉住
「每个垫片都能解析到非垫片/存在/>12 行的真实实现」+「门禁里不得出现
`open(垫片字面量)`」（静态 AST 扫描，**精确等值**匹配 —— 早期用 `endswith`
把 `services/task_queue.py` 误判成根部垫片 `task_queue.py`，实测 18 处假违规）。
