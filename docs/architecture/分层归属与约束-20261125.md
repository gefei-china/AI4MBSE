### 三个命名决策（都不是随手起的）

1. **`adapters/` 而不是报告里写的 `integrations/`**：仓库根的 `integrations/` **已经是一个配置数据目录**
   （`register_http_tools.py:123` 在那里扫 `*.json` 外部集成清单，内含 `modeling_software.example.json`）。
   往数据目录里塞 Python 包会造成"同名不同物"，所以代码层叫 `adapters`，并在包 docstring 里写明冲突。
2. **`services/tools/` 与 `services` 同层**，不构成新的依赖约束。理由是被实测依赖逼出来的：
   `services/requirement_postprocess.py` 直接消费 `requirement_itemize_tools`（服务→工具），
   若把工具放成"更下层"，这条真实依赖立刻变成越界。
3. **`core/domain` 是闭包**：12 个模块互相只依赖 `core.*`。这不是设计出来的，是**先量后分**：
   先跑依赖图（`tmp/p1_layer/analyze.py`），发现 `entity_resolver` / `triple_store` / `vector2graph` /
   `sysml_importer` 都直接依赖 `knowledge_engine`（服务）⇒ 它们**不能**进域层，只能进 `services/`。

## 二、怎么保证搬完不出事（四条机制，缺一不可）

### 1. 兼容垫片：根目录同名文件 = 6 行 `sys.modules` 别名

```python
import sys as _sys
from adapters import graph_db as _impl
_sys.modules[__name__] = _impl        # 旧路径 import 拿到的就是新模块对象
```

为什么必须留垫片（实测理由，不是保守）：

| 消费者 | 规模 | 为什么不能一次改完 |
|---|---|---|
| `tools/` 脚本 | 750 个 | 其中 106 个含**路径式**引用（`read("graph_db.py")`），改 import 不够 |
| 门禁 / 测试 | 85 个文件 | 同样读源码文本做断言 |
| 字符串导入 | `routers/graph_db.py:21` 用 `__import__("graph_db", fromlist=[...])` | 不走 import 语句，只能靠 `sys.modules` |
| 插件发现 | `memory_backend.py` 用 `import_path("memory_backend_" + name)` | 按名字约定找模块 |
| CLI 入口 | 17 个模块有 `__main__` 块 | 垫片用 `runpy.run_module(..., alter_sys=True)` 转发，`python X.py` 照常 |

关键点是**模块身份唯一**：垫片不是"复制一份再 re-export"，而是把 `sys.modules` 指向同一对象，
所以改 A 文件一定生效，不会出现"两份实现必然漂移"（本仓历史踩过）。

### 2. 产品代码改真路径（AST 级，不是正则）

`agent/ core/ services/ adapters/ routers/ repositories/ workflows/ llm/ knowledge_pipeline/ database/ models/ main.py`
里的 import 全部改成新路径。实测 **380 处 / 136 文件**（两个 phase 分别 95 → 243 → 二次补刷 42）。
`tools/`、`tests/`、`static/` 保留旧路径走垫片（它们不是产品代码，改了要牵动 106 个门禁）。

### 3. `__file__` 当仓库根 → `core.paths.repo_root()`（**这次最险的一处**）

实测 **11 个模块 / 13 处**用 `os.path.dirname(os.path.abspath(__file__))` 拼仓库根下的资产：

| 资产 | 消费方 | 搬目录后写错的后果 |
|---|---|---|
| `checker.jar` / `sysml.library` / `java-runtime` | `sysml_v2_check` / `sysml_ast` / `sysml_stdlib_tools` | **校验器返回 `unavailable` 被放行**（不是报错，是静默变不可用） |
| `sysml_models/` | `sysml_check_tools` / `sysml_project_check_tools` | 样例模型读不到 |
| `mbse.db` | `methodology_profile_tools` | 连到不存在的库 |
| `integrations/*.json` | `register_http_tools` | 外部集成扫 0 条 |
| `tmp/vec_cache` | `vector_index` | 缓存静默写不出 |

这类错误的共同形态是「路径拼错 → 文件不存在 → 被上层 `except` 吞掉」，正是 P0 在治的那个病。
故收敛到 `core/paths.py`，并在门禁 [E] 段永久禁止该写法回到已归位模块。

**真机自证**（搬完当天跑）：


⇒ 校验器**真的跑起来了**（rc=1 + 真实诊断），不是 `unavailable`。

### 4. 新层必须登记进**各处扫描器白名单**（这次最隐蔽的一处，已做成 [F1]）

搬完当天回归 P0 门禁，`verify_silent_except_ledger` **全绿且「变好了」**：

| 口径 | 静默兜底总数 |
|---|---|
| 基线（迁移前） | 2564 |
| 迁移后实测 | **2508** |
| 差值 | **−56** |

差点被读成「治理见效」。实际是 `adapters/` 单独扫出来的 `silent = 56`（`except=76 / strict=10`）
**正好等于**这个差值 —— 那 56 条不是消失了，是**整个目录从统计范围里掉了出去**。

根因：`tools/scan_silent_except.py` 的 `PRODUCT_DIRS` 是**白名单**，只有 `agent/core/services/...`；
而 P1 把 10 个模块搬进了一个**名单里不存在的新目录** `adapters/`。
同族问题另有三处，一并补齐：

| 文件 | 白名单 | 漏登记后的后果 |
|---|---|---|
| `tools/scan_silent_except.py` | `PRODUCT_DIRS` | 静默兜底账本**静默缩水 56 条**，且门禁全绿 |
| `tools/verify/verify_gate_portability.py` | `APP_DIRS` | P5/P6 绝对路径扫描对 `adapters/` **空转** |
| `tools/verify/verify_no_fake_actor.py` | `SCAN_DIRS` | 假人物串无人过问 |
| `tools/verify/verify_no_mutation_residue.py` | `_scan_dirs` | 自注入注释残留无人过问 |

补完后实测：`silent_total` 回到 **2564 / 基线 2564（逐位相等）** ⇒ 反证迁移前后**一条都没变**。

**真实树变异自证**（`tmp/p1_layer/probe_adapters_coverage.py`，4/4）：
往 `adapters/sandbox.py` 注入探针，要求四处门禁都变红，再逐字节还原。

```
scan_silent_except             静默计数 2564 → 2565（应 +1）   抓到=True 还原逐字节=True
verify_gate_portability        rc 0 → 1                       抓到=True 还原逐字节=True
verify_no_fake_actor           rc 0 → 1                       抓到=True 还原逐字节=True
verify_no_mutation_residue     rc 0 → 1                       抓到=True 还原逐字节=True
```

> 🔑 **纪律**：**「账本数字变好」先问一句「扫描范围是不是变小了」**。
> 白名单式扫描器的失败形态不是报错，而是**悄悄少扫一块还照样给绿**。
> 判据要写成「**覆盖范围**断言」（[F1]：归属层必须出现在每个白名单里），
> 而不是「总数没超基线」—— 后者对「范围缩小」完全无感。
> 另：写注入探针时**不要写字面 `\n`**（本机 Git Bash heredoc 会吃成 `/n`），
> 探针会变成语法错、整个文件掉出扫描，症状和「门禁没覆盖」一模一样（这次误判了一轮）。
