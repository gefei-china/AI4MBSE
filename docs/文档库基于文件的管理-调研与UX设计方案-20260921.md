## 1. 现状盘点（问题即需求）

当前文档库是**记录中心（record-centric）**形态，"文件"只是文档记录的一个属性：

| # | 现状 | 后果 |
|---|------|------|
| 1 | `documents` 表平铺，**无目录/层级**；仅 `domain`（领域）、`knowledge_category` 两个扁平维度 —— 另有 `branch` 列但**恒为 `global`（内部哨兵，不构成管理维度）**，见 §1.1 | 文档一多只能靠筛选拖动，无法按工程/专业组织（例：`sysml_norm` 4 份规范与测试小文件混排） |
| 2 | **无版本链**：同名文件重复上传产生两条独立记录（实测：`pipe_test.txt`×2、`样例部件库.md`×2），互不关联 | "哪个是最新"靠文件名猜；旧版下线（`deprecate`）后新关系无从追溯 |
| 3 | 源副本 `data/uploads/<doc_id>_<filename>` **平铺 41 份**，id 前缀即物理路径 | 无法用文件管理器/同步盘直接镜像管理；删除文档后孤儿副本需手工清理 |
| 4 | 上传即入库：**无暂存/草稿态目录**，解析失败（`parse_status='failed'`）的文件与正常文件同列 | 失败件缺乏"重试工作台"的聚集视角（retry 端点已有，缺 UX） |
| 5 | 文件名是**检索侧的身份键**：`chunk.source_doc`、`entities.source_doc`、`kb_scope.docs` 白名单均按文件名硬过滤 | **任何重命名功能都必须同步三处冗余**，否则检索静默归零（KB-S 白名单失效的同款事故面） |
| 6 | UI 无批量操作、无回收站、无移动/排序 | "清理测试垃圾文件"只能逐条点 |

### 1.1 前置更正：文档库是**全局资产**，不按建模分支切分（2026-09-21 落地）

> **缘起**：用户指出「文档库应该是全局的，不基于分支切分吧」→ 核查结论是**用户判断正确**，
> 代码里残留的"按分支隔离"属历史实现，与设计意图不符。
> **本文档 §4 / §7.2 / §8 / §10 里凡把 `branch` 当作文档管理维度的部分，均应据此作废**（见本节末尾）。

**设计事实**（三条互相印证）：
1. **入库即写 `branch='global'`** —— `knowledge_pipeline/ingest.py::ingest_document` 的 `branch` 默认值就是 `global`；
2. **存量已归一** —— 迁移把历史文档的 `branch` 统一为 `global`；
3. **消费侧本就忽略分支** —— 文档列表接口与检索接口都不按 `branch` 过滤文档。

→ **`branch`（release / dev / personal）是"图谱实体与关系"的版本轴，不是文档的版本轴。**
文档是跨分支共享的**全局资产**；实体/关系才按分支隔离（AI 建模默认只消费 release，
见 `agent/rag.py::_release_branches()`）。

**但代码里有 4 处仍按旧模型工作** —— 均已对齐并加护栏，自检 `tools/verify/verify_doc_global.py` **18/18**：

| 落点 | 旧行为（缺陷） | 现行为 |
|---|---|---|
| `knowledge_pipeline/search.py::_branch_clause` | 生成的 `branch IN (...)` 子句**不保护 `global`** → 调用方一旦给了分支，全局文档整片被滤掉 | 改为结构性不变量 `branch IN (...) OR branch = 'global'`；docstring 注明**只作用于 `document_chunks`** |
| `repositories/knowledge_repo.py::count_documents` | 按 `branch=?` 统计 → `/api/knowledge/stats?branch=release` 的 `total_docs` **恒 0** | 去掉分支过滤；docstring 注明「实体/关系仍按分支、只有文档全局」 |
| `repositories/branch_repo.py::delete_branch` | 删分支**连带删 `documents` / `document_chunks`** → 删 `dev` 会把全局文档一起删掉 | 加护栏 `if name != "global":`；`snapshot_documents` 标为已废弃（全局化后恒为空操作） |
| `static/js/mods/20-docs.js::doUploadDoc` | 上传前判 `branchWritable()` → 在只读的 `release` 分支上**无法上传资料** | 移除该门禁（文档不归属分支，不该受分支可写性约束） |

**端到端验证**（口径：全库，2026-09-21 14:3x，服务已重启）：
`/api/knowledge/stats` 的 `total_docs` 在 `release` / `dev` / `personal` / `global` / 不传 五种入参下**均为 6**
（修复前 `release` 为 **0**）。自检含 **5 处变异自证**（还原旧写法 → 相关断言必须转 FAIL）。

**⚠️ 对本方案自身的影响（落地前须修订）**：

| 位置 | 现写法 | 应改为 |
|---|---|---|
| §4 `doc_folders` DDL | `branch TEXT DEFAULT 'dev'` | **删除该列**（目录不归属分支） |
| §4 唯一约束 | `UNIQUE(name, parent_id, branch)` | `UNIQUE(name, parent_id)` |
| §4 版本判定键 | `(filename, folder_id, branch)` | `(filename, folder_id)` |
| §7.2 同名上传提示 | "同目录同分支" | "同目录" |
| §8 与发布/分支的咬合 | "目录带 branch，本期目录限本分支" | **作废**（目录全局；"发布快照不含目录"一条不变） |
| §10 开放问题 | "检索仍按 domain/branch" | 检索**只按 `domain`**（`branch` 对文档无意义） |

## 2. 行业对标（取各家之长）

| 产品 | 可借鉴点 | 本案取舍 |
|------|----------|----------|
| **SharePoint 文档库** | 库-文件夹-文件三级 + 版本历史 + 签出机制 | 取"文件夹+版本"；**不做签出/锁**（单人建模场景过度设计） |
| **Confluence 附件** | 附件挂在页面下、版本自动 v1/v2… | 取"版本自动递增 + 历史可下载"；不挂页面（我们挂目录） |
| **Dropbox/坚果云** | 面包屑 + 拖拽移动 + 右键菜单 + 回收站 | 全取——这是"文件感"的核心交互 |
| **GitHub 仓库浏览** | 路径面包屑 + 最近提交 + README 预览 | 取"列表内联元信息"（大小/时间/状态徽章一行可见） |
| **VS Code 资源管理器** | 树形折叠、拖放目标高亮、F2 重命名 | 取交互细节（见 §7.4） |
| **Notion 数据库** | 视图切换（列表/表格/画廊）+ 多维筛选 | P2 再考虑多视图，本期只做列表 |

**结论**：目标形态 = 「**轻量 Dropbox 目录树 + Confluence 式版本链 + 本库已有的解析/向量化/发布流水线**」。

## 3. 目标形态（一句话北极星）

> 用户像管理本地文件夹一样管理资料库：**建目录、传文件（含拖拽/批量）、移动/重命名/下线可逆、
> 同名文件上传自动成版本链、双击即预览、右侧随时看解析/分块/实体产物**——
> 而底层检索、向量化、发布、kb_scope 白名单全部无感兼容。

## 4. 数据模型设计（增量，不动现有列）

> ⚠️ **2026-09-21 更正（见 §1.1）**：文档库是**全局资产**，不按建模分支切分 →
> 下方 `doc_folders.branch` 列、含 `branch` 的唯一约束与版本判定键**均已作废**，落地时去掉 `branch`。

```sql
-- ① 目录树（虚拟目录，物理上不建目录——源副本仍平铺，见 §6 方案 B）
CREATE TABLE IF NOT EXISTS doc_folders (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL,                       -- 目录名
    parent_id INTEGER REFERENCES doc_folders(id) ON DELETE CASCADE,  -- NULL=根
    domain TEXT DEFAULT '',                   -- 目录级默认域（可选，上传时预填）
    -- ⚠️ 已作废（§1.1）：目录不归属分支。落地时删除本列。
    -- branch TEXT DEFAULT 'dev',
    created_by TEXT DEFAULT '',
    created_at TEXT DEFAULT CURRENT_TIMESTAMP,
    -- ⚠️ 已修订（§1.1）：原为 UNIQUE(name, parent_id, branch)
    UNIQUE(name, parent_id)                   -- 同级同名禁止
);

-- ② 文档挂目录（列级增量，向后兼容：NULL = 根目录，旧行为不变）
ALTER TABLE documents ADD COLUMN folder_id INTEGER REFERENCES doc_folders(id) ON DELETE SET NULL;

-- ③ 版本链（同名同目录成链；当前记录即"最新版"，历史版只读）
CREATE TABLE IF NOT EXISTS doc_versions (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    document_id INTEGER NOT NULL REFERENCES documents(id) ON DELETE CASCADE,  -- 当前版
    version_no INTEGER NOT NULL,              -- 1,2,3…（同链递增）
    filename TEXT NOT NULL,
    file_size INTEGER DEFAULT 0,
    source_copy TEXT DEFAULT '',              -- 历史版源副本路径（data/uploads/…）
    chunk_count INTEGER DEFAULT 0,
    ingested_by TEXT DEFAULT '',
    created_at TEXT DEFAULT CURRENT_TIMESTAMP
);

-- ④ 回收站（软删除；documents 不加列则用独立表，推荐加列更简单）
ALTER TABLE documents ADD COLUMN deleted_at TEXT DEFAULT '';   -- 空=正常
```

**要点**：
- **版本链挂在"当前记录"上**（Confluence 模式），不引入"文件 ID"新实体——`document_id` 继续是全库
  （chunks/citations/preview/openCitation）的外键锚，**检索与引用链路零改动**。
- 同名上传判定键 = `(filename, folder_id)` 相同 → 走"新版本"而不是新记录（⚠️ 原含 `branch`，该维度已作废，见 §1.1）；旧版当前行数据
  快照进 `doc_versions`，`documents` 行被新文件覆盖（重新走完整 retry 管道）。
- 软删除 `deleted_at`：所有列表/检索查询统一追加 `AND deleted_at=''`（**检索侧必须加**，回收站文件不可被 RAG 召回）。

## 5. API 设计（REST，全部增量）

| 端点 | 方法 | 说明 |
|------|------|------|
| `/api/doc-folders` | GET/POST | 树查询（含各节点计数）/ 新建 |
| `/api/doc-folders/{id}` | PUT/DELETE | 重命名 / 删除（空目录才可删；非空提示或级联进回收站） |
| `/api/documents/{id}/move` | POST | `{folder_id}` 移动（0=根） |
| `/api/documents/{id}/rename` | POST | **重命名**：同步更新 `documents.filename` + `document_chunks.source_doc` + `entities.source_doc` + `kb_scope.docs` 白名单引用（事务内三写）——见 §8 风险 |
| `/api/documents/{id}/version` | GET | 版本链列表（含历史版下载） |
| `/api/documents/{id}/upload-version` | POST | 同名新版本上传（走完整 retry 管道，成功后旧版快照入 `doc_versions`） |
| `/api/documents/{id}/trash` | POST | 软删除（进回收站） |
| `/api/documents/{id}/restore` | POST | 恢复 |
| `/api/documents/trash` | GET | 回收站列表（30 天后物理清理：源副本 + chunks 级联） |
| `/api/documents/batch` | POST | `{action: move|trash|commit, ids:[...]}` 批量操作 |

## 6. 源副本物理布局（两案，推荐 B）

- **方案 A（物理镜像）**：`data/uploads/<folder_path>/<doc_id>_<filename>`。直观，但目录改名/移动要搬文件，
  Windows 路径长度、并发迁移都是坑。
- **方案 B（虚拟树 + 平铺存储，推荐）**：目录树只存 DB，源副本维持现有 `<doc_id>_<filename>` 平铺。
  理由：① 现有 `retry_document`/预览/下载全部按 id 寻址，**零改动**；② 移动/改名是纯 DB 事务；
  ③ "文件感"由 UX 层完整提供（用户感知不到物理平铺）。备份也简单（一个目录 + 一个 db）。

## 7. UX 设计（本期重点）

### 7.1 信息架构：三栏工作台（替换现有单列列表）

```
┌──────────────────────────────────────────────────────────────────────────────┐
│  📚 资料库        [⬆ 上传] [+ 新建目录] [🔍 搜索…]        [⚙ 抽取设置] [🗑 回收站(3)] │
├──────────────┬───────────────────────────────────┬───────────────────────────┤
│ 📁 目录树      │  星网宽带通信 > 规范文档 (12)        │  📄 OMG SysML V2 规范.pdf   │
│ ▾ 🗂 星网宽带  │  ────────────────────────────────  │  ───────────────────────  │
│   ├ 📁 规范(4) │  ☑ 名称            大小   版本 状态 │  [🖼 原件] [📝 文本]        │
│   ├ 📁 需求(6) │  ☑ OMG_SysML…pdf  8.2MB  v3  ✅完成 │  （38-filepreview 面板）    │
│   └ 📁 接口(2) │    KerML…pdf      4.5MB  v2  ✅完成 │                           │
│ ▸ 🗂 测试素材  │    需求规格V6.3.docx 1.1MB v1 ⏳解析 │  解析：✅ 2,606 块          │
│ ▸ 🗂 方法论(4) │    …                              │  实体：38 · 已提交          │
│              │                                   │  [🔄 重试] [📦 提交] [⋯]    │
│ (可折叠)      │  多选浮动条：已选 2 → [移动][下线][提交] │  版本历史：v3←v2←v1        │
└──────────────┴───────────────────────────────────┴───────────────────────────┘
```

- **左栏（220px，可折叠）**：目录树 + 各级计数徽章；"未分类"(无 folder_id) 是一等节点（迁移期兜底）；
  拖拽目标行高亮（`--blue-l` 背景 + 虚线框）。
- **中栏（弹性）**：文件列表（表格）+ 面包屑；列 = 复选框 / 名称（含扩展名图标与类型色，复用现有
  `TYPE_COLORS`）/ 大小 / 版本号 / 解析状态徽章（复用 `lifecycleBadge`）/ 更新时间 / 行内操作。
- **右栏（360px，选中即出）**：不弹窗、就地详情——上半 `38-filepreview` 双视图（**P1-5 的引用锚点
  高亮直接复用**），下半产物摘要（chunk 数/实体数/提交状态）+ 操作按钮 + 版本时间线。

### 7.2 上传：把"文件感"做在入口

1. **拖拽上传**：拖文件到中栏空白区 = 传到当前目录；拖到左栏某目录行 = 传到该目录
   （拖悬时目录行高亮，`drop-effect: copy`）；拖到目录树上文件夹图标 = 新建子目录并落入。
2. **多选批量**：`<input multiple>`；上传队列浮层逐个显示 解析→分块→向量化 三阶段进度
   （复用现有 `setUploadStage`），失败项聚合并给「全部重试」。
3. **同名即版本**：拖入与现有文件同名（**同目录**；⚠️ 原写「同目录同分支」，`branch` 维度已作废，见 §1.1）时，浮层提示
   「检测到 v2 存在 → 将创建 **v3**」；用户可展开选择「覆盖为新版本（推荐）/ 另存为新文件 / 取消」。

### 7.3 文件操作语义（对齐本地文件习惯）

| 操作 | 交互 | 语义 |
|------|------|------|
| 移动 | 拖行到目录树 / 多选浮动条「移动」 | 纯 `folder_id` 更新；检索无感（文件名未变） |
| 重命名 | 行内 F2 / 右键 | **硬操作**：三处冗余同步（§8）；弹确认框列出受影响面（chunks N 条、实体 M 条、白名单 K 处） |
| 下线/删除 | 多选浮动条 / 右键 | 一律**进回收站**（软删除）；toast 提供撤销；30 天物理清理 |
| 下载 | 右键 / 详情栏 | 单文件下载源副本（复用 `pvDownload`） |
| 提交/发布 | 批量条 | 复用现有 `commitDoc`/`batchCommitSelected` |

### 7.4 键盘与细节（VS Code 级手感）

- `Enter` 预览选中件 / `F2` 重命名 / `Delete` 进回收站 / `Esc` 清除多选；
- 排序：名称/大小/时间点击表头切换，状态列固定置尾（失败/解析中置顶可开关）；
- 空态：目录空 → 「拖文件到这里上传」虚线大热区；库整体空 → 引导三步（建目录→上传→去建模）；
- 所有新控件只用现有 CSS 变量（`--line/--blue-l/--mut`），不引依赖（本仓铁律）。

### 7.5 回收站页

入口为工具栏图标 + 计数徽章；列表显示 原目录/删除时间/可恢复倒计时；行操作 [恢复] [彻底删除]；
顶部「清空回收站」需二次确认。物理清理 job 挂在现有启动流程（无定时器依赖）。

| `domain_review_queue` / glossary | 不受影响（按 document_id/文件名读，rename 同步后自洽） | — |

## 9. 分期路线

| 期 | 内容 | 规模 |
|----|------|------|
| **P0（先做）** | doc_folders 表 + 目录树左栏 + 上传挂目录 + 移动/软删除/回收站 + 批量下线 | 后端 1 天 + 前端 1.5 天 |

**验收口径**（延续本仓验证纪律）：① rename 后对 `chunk.source_doc`/`entities.source_doc`/白名单做
三处对拍断言；② 软删除文件在检索链路 0 召回（夹具断言）；③ 同名上传产生 vN 且旧版可下载；

## 10. 开放问题（需拍板）

1. **目录是否参与检索过滤**？（目录→domain 推断，或保持 domain 独立）——倾向：目录只是组织维度，检索仍按 `domain`。（⚠️ 原文为「按 domain/branch」，`branch` 对文档无意义，见 §1.1）
2. **重命名放开程度**：是否允许改名后仍保持白名单自动同步？（涉及 agents 配置写入，需谨慎）——倾向：允许，但带影响面确认框。
3. 版本保留策略：全量保留 vs 每文件最多 N 版（源副本体积增长）——倾向：P0 全量，P2 加配置 `doc.version_keep`。
4. 「未分类」是否常驻树顶？（迁移期友好，但可能养成惰性）——倾向：常驻但置底。
