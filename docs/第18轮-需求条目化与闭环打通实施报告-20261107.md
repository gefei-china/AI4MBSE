## 1. R1：`requirement_itemize` 从「孤儿模块」到可用链路

### 1.1 三个同时成立的矛盾事实（这就是缺陷本体）

| 事实 | 证据 |
|---|---|
| 模块实现完整（切句/分类/gaps/需求视图骨架） | `requirement_itemize_tools.py` 300+ 行，`__main__` 自带 demo |
| **没有任何分发点 import 它** | `grep -rn "requirement_itemize_tools"` 只命中迁移脚本与文档 |
| tools 表有行、agent 635 有绑定、技能正文教模型调用 | 46 次真实调用 **全部**返回「未知工具」 |

⇒ 第三次同型事故（前两次：`code_exec`、`save_artifact`）：**注册了 ≠ 接线了**。

### 1.2 改了什么

| 改动 | 位置 | 关键设计 |
|---|---|---|
| 接线（主链路） | `agent/pipeline_parts/tools.py` | 按 `save_artifact` 同款分支，传 `conversation_id=conv_ctx` 与真实操作者 |
| 接线（编排侧） | `workflows/tools.py` | **必须先登记 `BUILTINS`**：`_do_execute` 对非 BUILTINS 名字先走 HTTP/MCP 再返回「未知工具」，分支写在下面对未登记名字是**不可达**的 |
| 需求实体表 | `database/schema.py` | `requirement_items`（幂等键 = 归一化文本 sha1；`kind=item|gap`；`status=active|merged|retired`） |
| 仓储 | `repositories/requirement_repo.py` | `req_id` 首次分配后**永不变**（追溯引用不能漂移）；`retire`/`merge` 只改状态不删行 |
| 读/写分离 | `requirement_itemize_tools.py` | 新增 `requirement_commit`（`side_effect=write` ⇒ 走写前确认闸）；`itemize` 保持只读 |
| 资产迁移 | `tools/migrate_requirement_assets.py` | 启用工具 + 新增 `requirement_commit` 行 + 绑定 agent 635 + 补技能 `allowed_tools`；**幂等可重跑** |
| 说明书同步 | `tools/upgrade_requirement_skill_body.py` | 技能 `sysml_requirement_structuring_guide` v1.0→v1.1，补第 5 步「落库」（说明书写什么，模型才做什么） |

### 1.3 为什么拆成两个工具（不是「加个 persist 参数」）
合成一个只有两种结局：**只读也要逐条确认**（确认疲劳，OWASP 点名的失效模式），或**写库不确认**（绕过写前闸）。两者都不可接受。这与本仓既有的 `capability_query`/`capability_apply` 同构。

### 1.4 会话入口真机验证（`verify_requirement_chat_e2e`，6/6 ALL_OK）

| 判据 | 实测 |
|---|---|
| C1 模型真调 `requirement_itemize` 且成功 | `['requirement_itemize','requirement_commit']`，不再「未知工具」 |
| C2 模糊句不得作为条目落库 | 模糊句入条目=0；确认前库内不变 |
| C3 `requirement_commit` 被写前确认闸拦住 | 拦截=True，**批准前零副作用** |
| C4 批准后条目落到会话所属工程 | 7→8，本轮唯一用例 → `REQ-F005` |
| C5 库内 REQ 与视图 `reqId` 一致 | `REQ-F004/F005/I003/I004/P001~P003` 全部在骨架代码中 |

> 真机还抓到一处**新缺陷**：模型把 `project` 参数当「包名前缀」传了 `EVTM`（规约卡默认包名），

### 1.5 验证时踩到的判据坑（写下来防复犯）
- 首版 C2/C3/C6 三条全部**假红**：C2 拿"模型是否 ask_user"当判据（问不问是模型自由，写不写错才是安全性质）；C3 拿 `ok` 当判据（**闸门拦截时工具刻意返回 ok=1**，文本已写明"不会产生任何副作用"，置失败会让模型重试造第二张单）；C6 拿"与历史库对比"当判据（第一次提交里的 gaps 是新行，被误判成幂等失效）。
- C4 第二轮假红：用例文本固定 ⇒ 幂等使"数量增加"必然失败。⇒ **判据要对环境稳健**，不能假设"每次都是干净库"（改法：每轮插入一条带随机数值的唯一可验证需求）。

## 2. R2：闭环可推进 + 孤儿归属可自救

### 2.1 先纠正一个我自己上一轮的错误结论
上一轮报告把 `sysml_versions.adopted=0` 当作"闭环断"的核心证据。**这是错的**：`adopted` 列已于 **2026-09-24** 随「📌 采纳」入口一并下线，仅作历史留痕、**无写入方**（见 `routers/sysml_versions.py` 文件头）。
真正的闭环标记是四段：`imported_batch`（候选批次）→ `review_status=submitted` → `triples approved` → `entities`，最后才是 `zhiyuan_imported_id`。这四段的实测是 **0 / 0 / 30 条三元组 / 189 实体**，即**从未被完整走过**。

### 2.2 新增 `/api/sysml-versions/{id}/closure`
只读端点，逐段报"做到没有 / 卡在哪 / 下一步做什么"，并且：
- 写回段不只报闸门，还检查**配置就绪度**（`base_url`、`vc`）—— 闸门通过 ≠ 能写回，实测这台机器 `base_url` 为空，只报"闸门通过"是误导；
- 明确声明 `adopted` 不参与判定，防止下一个人再拿它当指标。

### 2.3 新增 `/reattribute` + 闸门 code 细分
- 孤儿归属从 `PROJECT_NOT_BOUND` 拆出 **`PROJECT_ORPHANED`**：两者自救路径不同（"还没归入"vs"归入的没了"），同一个 code 只能给一句笼统提示。
- `POST /reattribute`：只改 `project_id`，不动 `zhiyuan_imported_id`/`imported_batch`/`status`；目标工程必须存在；全量审计 `sysml_reattribute`。实测：合法工程 → `changed=true`；不存在 → 400 `PROJECT_NOT_FOUND`；空串 → 退出工程。

### 2.4 生产库副本 + 真实版本验证（`verify_closure_on_prod_copy`，6/6 ALL_OK）
样本 `v1000355`（7503 字符真实模型）：

| 判据 | 实测 |
|---|---|
| B1 未候选化版本如实报卡点 | `next=candidates` |
| B2 孤儿版本写回闸给可执行动作 | `PROJECT_ORPHANED` + 指向 `/reattribute` |
| B3 可重新归属且拒无效工程 | `bad_rejected=True`、`after=p1a0d2e694af` |
| B4 走完 ①→④ | 候选 **46 节点/89 关系** → 实体 **189→235（+46）** |
| B5 前四段全绿、next 只剩写回 | `{candidates:True, review:True, triples:True, graph:True, zhiyuan:False}` |
| B6 重复候选化幂等 | 同批次、`dup=True` |

> 为什么用**生产库副本**：空库能证明"代码能跑"，证明不了"现有 128 个真实版本能否走下去"。
> 副本跑完即删，生产库不动。

## 4. 顺手修掉的真实缺陷

### 4.1 资产快照漂移检查**只比 agents**
后果：当天新增 `requirement_commit` + 一条绑定后，`--drift` 仍报"**一致**"（库 122 工具 / 快照 121，库 254 绑定 / 253）。
⇒ 工具/技能/绑定的漏导出**完全不会被发现**，而它们正是"空库能否重建出同一平台"的主体 —— 只看 agents 等于把可重建性检查缩到 1/4。
现覆盖 agents/tools/skills（同一套 `_keep_row` 过滤）+ `agent_tools` 集合比对，字段比对补 `description/input_schema/side_effect/risk_level`。

### 4.2 `relation_drift` 算出来却不打印
绑定漏导出时只显示"不一致"而**没有任何条目**，把人挡在"看不出来哪里不一致"里。已补打印。
### 4.3 绑定比对的键名写错（本轮自捕）
快照里是 `agent` 不是 `owner` ⇒ 集合恒为空、比对**永远无声通过**。已修，并复测到那条真实缺失。
