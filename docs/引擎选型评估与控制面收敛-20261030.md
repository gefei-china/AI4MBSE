# 能否直接用成熟引擎？—— 选型评估与本工程适配测算

> 日期：2026-10-30
> 问题：*"运行时可以直接用成熟的引擎吗，这样可以规避自己开发带来的问题"*
> 结论先行：**可以用，但要分清"引擎替代什么"。本工程的痛点不是"自研引擎不够成熟"，
> 而是"同一语义在 12 处各自实现"。引擎能解决后者的一部分，但会带来更重的三样新约束。**

---

## 1. 你的直觉有实质依据——先把自研债量化

### 1.1 控制面语义严重分散

本工程涉及"时间/预算/重试"的配置键共 **38 个**，分散在 **12 个配置段**：

| 段 | 键数 | 代表键 |
|---|---|---|
| `context` | 8 | `budget_window_tokens` / `budget_history_ratio` / `total_budget_window_ratio` |
| `agent` | 7 | `auto_continue_deadline_s` / `fill_deadline_s` / `harness_max_stall` / `loop_token_budget` |
| `llm` | 5 | `http_timeout_s` / `retry_times` / `total_timeout_budget` |
| `delegation` | 4 | `subtask_idle_timeout_s` / `subtask_timeout_s` / `worker_timeout_s` / `total_time_budget_s` |
| `replanning` | 4 | `probe_time_budget_sec` / `confirm_ttl_sec` / `retry_once` |
| `runtime` | 3 | `chat_deadline_s` / `queue_wait_s` / `shutdown_drain_s` |
| 其余 7 段 | 各 1 | `integration.timeout` / `mcp.timeout` / `sysml.check_timeout` / `zhiyuan.timeout` / `sandbox.gate_timeout_s` / `refine.max_rounds` / `database.connect_timeout` |

### 1.2 已经付出过"配置谎言"的代价

这不是理论风险，仓库里有**两类已确证实例**：

| 实例 | 表现 | 代价 |
|---|---|---|
| `delegation.total_time_budget_s` | 注释写"超限终止剩余任务降级汇总"，**但全仓零消费点** ⇒ 改了不起任何作用 | 配置谎言（2026-10-02 审计发现，一直没处理） |
| 11 个 `context_audit.*` 键 | 经 settings 表写入返回 `ok=True`，**但消费点只读配置文件** ⇒ 静默无效 | "写成功却无效果"的旁路（2026-10-29 修复） |

**⇒ 这就是你所说的"自己开发带来的问题"的最硬证据：不是能力不足，而是同一语义被反复实现，口径必然漂移。**

### 1.3 本轮我自己也犯了这个错（必须承认）

上一轮我新增了 `runtime.chat_deadline_s`（整轮墙钟），**这让预算键从 37 变成 38、语义分散度进一步上升**。
它本身是对的（整轮墙钟此前完全缺失），但做法上应当先收敛既有键、再加新键，而不是并列增加。
本轮已用行动部分纠正：把 `delegation.total_time_budget_s` 从**死配置复活为真实闸**（见 §4）。

## 2. 引擎到底能替代什么、不能替代什么

### 2.1 引擎真正提供的是"控制面"

Durable execution 引擎（Temporal / DBOS / Restate / LangGraph checkpointer）的核心抽象只有 6 项：

| 引擎能力 | 本工程现状 | 是否值得换 |
|---|---|---|
| **持久化检查点** | ✅ 已有 `orch_checkpoints`（phase + 5s 心跳） | 否 |
| **断点续跑** | ✅ 已有 `prepare_resume` / `apply_resume`（最多 5 次） | 否 |
| **durable timer** | ⚠️ 分散在 6 处各自实现 | **是** |
| **signal（外部事件唤醒）** | ⚠️ 已有 `replan_signal`，但自研 | 部分 |
| **exactly-once 副作用** | ❌ **缺失**（写类工具无幂等键） | **是（但引擎不替你做）** |
| **停滞自动重驱** | ⚠️ 已有 `reap_orphans` + `orch_supervisor`（默认关） | 部分 |
| **版本化（部署兼容在跑的 run）** | ❌ 缺失 | 是（仅大团队/频繁发布才痛） |

### 2.2 引擎**不能**替代的

- 意图识别、工具集、领域知识、提示词工程——**这是本工程的产品本体**，任何引擎都替不了。
- **工具副作用的幂等性**：引擎保证"已记录的步骤不重跑"，但**工具调用本身的幂等键要你自己加**。
  行业文档反复强调：*"Every engine here behaves the same way for an unfinished step, so pass an idempotency key to anything with side effects."*
  ⇒ 这件事**换引擎不会自动获得**。

## 3. 四个引擎的适配测算

### 3.1 本工程的硬约束

| 约束 | 事实 | 影响 |
|---|---|---|
| 单机部署 | `uvicorn.run(app, ...)` 无 workers | 需引擎自带 server 的方案要多一套运维 |
| SQLite 存储 | WAL + busy_timeout，单写者 | **只支持 Postgres/SQLite 的引擎才有优势** |
| 编排逻辑自研且非标准 | planner + DAG + `TaskQueue` + replanning(T1 补跑/T2 轻量重画) + harness 待办闸 + 无进展检测 | 用通用引擎表达会非常别扭 |
| **编排逻辑内嵌 LLM 调用** | `workflows/planner.py` 有 **4 处** `llm_client.chat`（plan_summary / planner / task_llm / 直答） | **与引擎的确定性要求正面冲突** |
| 任务状态直接读写 | `stream.py` 里 **36 处** `TaskQueue.` | 引擎接管后这些要换成引擎 API |

### 3.2 逐个评估

| 引擎 | 基础设施 | 与本工程匹配 | 改造量 | 判断 |
|---|---|---|---|---|
| **DBOS (Transact)** | **只需 SQLite 或 Postgres** | ★★★★★ 零新服务 | 中：4 处 LLM 调用要挪进 step；36 处状态读写要换 | **最佳候选**（若要引） |
| **LangGraph checkpointer** | SQLite，零服务 | ★★★☆ | **高**：编排要改写成 Graph（本工程不是 Graph） | 不建议 |
| **Temporal** | 独立 server（Temporal Server / Cloud） | ★★☆ | **最高**：确定性要求最严 + server 运维 + 版本化 | 仅在"跨天等待 / 多实例 / 不可逆副作用"时 |
| **Restate** | 独立 server，**BSL 1.1**（非 OSI 开源） | ★★ | 高 | 不建议（授权 + server） |

### 3.3 关键冲突：确定性要求

所有 durable execution 引擎都要求 workflow 代码**确定性**——不能调 LLM、不能读当前时间、不能随机。

本工程编排逻辑里：
- planner **本身**是 LLM 生成的 DAG（`_intent="planner"`）
- `plan_summary`、`task_llm`、直答都是 LLM 调用

⇒ 接引擎必须**把所有 LLM 调用从编排逻辑挪进 activity/step**。
这在概念上是清晰的（行业标准做法：*"the agent loop becomes a workflow, and each model call and tool call becomes a durable activity"*），
但对本工程意味着**编排控制面重写**，不是增量。

## 4. 我的建议：分两步，而不是二选一

### 第一步（现在做，零风险）：把自研控制面收敛成"引擎形状"

引擎的价值是"单一真源 + 明确层级"。这些**不需要引擎就能拿到**，而且成本极低：

| 动作 | 本轮已完成 | 说明 |
|---|---|---|
| 消除死配置 | ✅ | `delegation.total_time_budget_s` 复活为真实闸（默认 0=不启用，零行为变更） |
| 明确预算层级 | ✅ 见下表 | 38 个键归为 4 层，每层一个真源 |
| 幂等键 | ⬜ 待做 | 写类工具加幂等键（**引擎也要求，但必须自己做**） |
| 停滞自动重驱 | ⬜ 待做 | `orch_supervisor` 默认关，打开即可（已有实现） |

**收敛后的预算层级**（收敛目标，不是现状）：

| 层 | 唯一真源 | 覆盖范围 | 当前其它同层键 |
|---|---|---|---|
| L1 整轮 | `runtime.chat_deadline_s`（900s） | 意图识别 + 编排 + 汇总 | `agent.auto_continue_deadline_s`(600) `agent.fill_deadline_s`(300) |
| L2 编排批次 | `delegation.total_time_budget_s`（0=不启用） | 单次编排批次 | `replanning.probe_time_budget_sec` |
| L3 子任务 | `delegation.subtask_timeout_s`(600) / `subtask_idle_timeout_s`(240) | 单个子任务 | `delegation.worker_timeout_s` |
| L4 单次调用 | `llm.http_timeout_s`(180) + `llm.total_timeout_budget` | 一次 LLM 调用（含重试） | `integration/mcp/sysml/zhiyuan.timeout` |

**收敛原则**：同层只留一个真源；下层不得严于上层（否则上层的"更严格者先生效"语义失效）；不同层的键要能从名字看出层级。

### 第二步（条件触发）：按需引入引擎，只接控制面

**触发条件**（满足任一才值得）：
1. 单次运行需要**跨天等待人工审批**
2. 需要**多实例**部署（配合把 SQLite 换成 Postgres）
3. 写类工具出现**不可逆外部副作用**（发邮件、部署、工单）且幂等键已加
4. 停滞自动重驱成为高频需求（当前 `orch_supervisor` 默认关）

**选型**：满足 1/2 → **Temporal**（成熟度最高）；只满足 3/4 且不想加服务 → **DBOS**（只需 SQLite）。
**接入姿态**：编排逻辑作为 workflow，每个子任务作为 activity/step，**不重写领域逻辑**。

### 4.1 一句话结论

> **引擎值得用来替代"控制面"，但本工程现在最该做的不是换引擎，而是把控制面收敛成"引擎形状"。**
> 因为：改造量最大的是编排确定性（引擎的核心约束），而那不是本工程当前的痛点来源；
> 死配置、预算分散、幂等缺失——这些引擎不解决，但自研可以立刻解决；
> 而一旦控制面已经是"引擎形状"（单一真源 + 层级清晰 + 幂等键），
> 将来迁到 DBOS/Temporal 就是**替换实现**而不是**重写系统**。
