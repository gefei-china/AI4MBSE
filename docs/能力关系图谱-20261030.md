# 能力中心的数据关系与「绑定是否生效」（2026-10-30）

> 回答三个问题：**现在有哪些实体和关系？**、**一条绑定到底有没有生效、凭什么判断？**、
> **卸载 / 删除 / 下线 / 停用之后，界面怎么让人知道"哪些关系和能力已经不在生效"？**

---

## 1. 实体与关系（真库结构，不是设想）

```
                        ┌─────────────────────────────────────────┐
                        │ plugins（能力中心卡片的数据源）          │
                        │  plugin_id / name(slug) / status        │
                        │  manifest.runtime.legacy_table/legacy_id│
                        └───────────────┬─────────────────────────┘
                                        │ 同步桥（legacy_sync）
              ┌─────────────────────────┼──────────────────────────┐
              ▼                         ▼                          ▼
        skills（技能）            tools（工具）              mcp_servers（MCP）
         id / name / status        id / name / status          id / name / status
         enabled / content         source / config             enabled / tool_meta(71)
              ▲                         ▲                          ▲
              └──────────┬──────────────┴──────────────┬───────────┘
                         │  agent_tools（关系表，**按 name 关联**）
                         │  (agent_id, tool_type ∈ skill|mcp|tool, tool_name, enabled)
                         ▼
                      agents（Agent：main/sub，status=active|disabled）
                         │
                         └── agents.intent_keywords / name ──> 意图路由（"意图名 == Agent 标识名"）
```

补充三条容易被忽略的"隐式关系"：

| 隐式关系 | 载体 | 影响 |
|---|---|---|
| 技能 → 工具白名单 | `skills.allowed_tools`（JSON 数组） | 命中技能时，白名单里的 MCP 工具**强制并入**候选（绕过语义预筛） |
| 技能 → 依赖 | `skills.dependencies` | 发布时校验（必须存在且已发布） |
| 能力 → 度量 | `capability_registry`（skill/tool/mcp_server/mcp_tool/plugin 五类投影） | `call_count / last_used_at` = "到底有没有被用过" |

**关系键是 `name`，不是 id** —— 这是后面第 5 节所有坑的根源：`skills.name` 不唯一。

## 2. 一条绑定要过四道闸（分散在四个文件）

| # | 闸门 | 判据（代码位置） | 不通过的表现 |
|---|---|---|---|
| ① | Agent 在路由池 | `agents.status='active'`（`agent/registry.py` load_from_db） | 整个 Agent 不参与，绑定全死 |
| ② | 绑定行启用 | `agent_tools.enabled=1` | 静默跳过 |
| ③ | 目标端可用 | 技能 `enabled` + 正文非空 / MCP `status='online'`+`enabled` / 工具 `status='active'`（`tools.py:425`） | 静默跳过 |
| ④ | 插件可消费 | `plugin_system.store.consumable_filter`（`tools.py:515`） | 静默剔除（只有一条 logger.warning，页面无感知） |

**关键结论：看状态字段 ≠ 看生效。** 实测存在两类"判据旁路"：

- 内置工具注入走 `BUILTIN_DESC` 字典（`tools.py:416` 按**名字**），**不看 `tools.status`**
  ⇒ `review` 绑的 `validate`（status=disabled）照样注入。
- 插件「自动消费」通道（`tools.py:495`）同样不看 `tools.status`
  ⇒ `requirement_analysis` 绑的 `modeling_coverage`（status=disabled）照样注入。
- 技能的绑定注入只看 `enabled`+正文（`agent_repo.bound_tools_for`），**不看插件状态**
  ⇒ 插件已下架（`plugins.status='draft'`）的技能仍然生效（实测 2 条）。

所以本模块把"生效"定义为**运行时口径**，状态字段只作为**原因**。

---

## 3. 三种"生效"必须分开说

| 层 | 含义 | 判定方式 | 在哪看 |
|---|---|---|---|
| 配置层 | `agent_tools` 里有这一行 | 直接查表 | Agent 编辑页勾选 / API `bindings` |
| 装配层 | 这一轮它会不会进模型上下文 | `services/capability_graph.judge_binding` | Agent 编辑页「已选 N · 生效 M」、能力中心体检行 |
| 运行层 | 真的被调用过 | `capability_registry.call_count / last_used_at`、`tool_call_logs` | 能力账本、能力卡片 |

**"装上了但 30 天零调用"和"绑定失效"是两件事。** 混在一起，用户会把"没用过"当成"坏了"。
MCP 还有第三层细节：绑定生效 ≠ 71 个工具全注入 —— 每轮 `pick_for_injection` 会按语义挑子集，
所以「生效」只保证"服务器可用、工具可被发现"。

## 4. 状态枚举（`state`，前端统一上色）

| state | 人话 | 生效? | 处置建议 |
|---|---|---|---|
| `effective` | 生效 | ✅ | — |
| `inactive` | 所属 Agent 已停用 | ❌ | 启用 Agent 或清掉绑定 |
| `dangling` | 目标行已不存在（悬空） | ❌ | 解绑；删除路径应级联 |
| `off` | 目标已停用 | ❌ | 启用目标或解绑 |
| `offline` | MCP 不在线 | ❌ | 先「测试连通」 |
| `unready` | 工具配置未就绪（如 `zhiyuan.base_url` 为空） | ❌ | 补配置 |
| `draft` | 技能处于草稿修订（**仍会注入**） | ✅ | 确认后发布 |
| `bypass` | 目标已停用，但内置/插件通道仍注入 | ✅ | 要真停用只能解绑/停插件 |
| `plugin_off` | 插件已下架，但旧表仍 enabled | ✅ | 同时停用旧表行 |

`effective = state ∈ {effective, draft, bypass, plugin_off}`。
把后三者算成"失效"会得出"看板说失效、AI 却真的在调"的自相矛盾结论。

## 5. 真库体检结果（178 条绑定）

```
绑定关系：178 条 · 生效 121 · 需处理 12
（悬空 0 · 目标停用 11 · MCP 离线 0 · 未就绪 1 · 所属 Agent 停用 45）
另：17 条「已停用但仍会被注入」；2 条「插件已下架但旧表仍启用」
```

| 状态 | 数量 | 说明 |
|---|---|---|
| effective | 102 | 正常 |
| inactive | 45 | 挂在 **10 个已停用 Agent** 上（需求视图生成 / 结构视图生成 / 交互视图（IBD）生成 等） |
| bypass | 17 | 12 条插件自动消费 + 5 条内置名字通道 |
| off | 11 | `gap_summary`、`scene_coverage`、`trace_chain_check` 等 |
| plugin_off | 2 | 技能插件侧已是 `draft`，旧表仍 `enabled=1` |
| unready | 1 | 工具必需配置为空 |
| dangling | 0 | 原有 1 条 `sysml_requirement_structuring_guide`（技能不存在，2026-10-08 起）已清理 |

### 五个实测发现

1. **45 条绑定挂在停用的 Agent 上**（25%）。这些 Agent 不参与路由，绑定是纯噪声；
   界面此前完全不显示，用户以为"这个 Agent 还带着这些能力"。
2. **`停用` 对内置工具与插件工具无效**（bypass 17 条）。用户点了停用、界面显示"已停用"，
   运行时照旧注入。这是**产品语义缺陷**，不是数据问题；本轮的选择是**如实标注**（不谎报失效），
   而不是偷偷改运行时行为（会改变 5 个 Agent 的工具集）。
3. **插件下架 ≠ 技能失效**（plugin_off 2 条）。`plugins.status='draft'` 时，
   技能绑定注入仍生效——因为 `bound_tools_for` 只看 `skills.enabled`。
4. **关系键 `name` 不唯一**：3 组重名（`行业调研` ×5、`Requirement_Analysis_Pre-check` ×4、
   `智源平台管理` ×3），每组都有 3 条 `enabled=1` 且**正文互不相同**。
   `SELECT * FROM skills WHERE name=?` 无 `ORDER BY` ⇒ **哪一份被注入由 rowid 决定**：
   - `行业调研` 的 rowid 最小行是 `enabled=0` ⇒ 一旦有人绑定它，会**静默失效**（绑定"看起来在"）；
   - `Requirement_Analysis_Pre-check` 取到的是 154 字那份，而页面上还有 266/244 字的两份草稿。
   本轮已把 `bound_tools_for` 改为**确定性排序**（启用 → 已发布 → 无草稿 → id 小），
   并在判定结果里暴露 `duplicates`（几份、几份启用、正文是否不同）。**没解决**的是"name 作为键"本身。
5. **悬空绑定确实存在**（已清 1 条）。删技能/删 MCP 的接口会级联 `DELETE FROM agent_tools`，
   但**删工具没有级联**，且历史删除已经留下过孤儿行。

## 7. 生命周期动作 → 关系与提示

| 动作 | 关系（agent_tools） | 运行时 | 界面现在会显示 |
|---|---|---|---|
| 停用技能 | 保留 | 立即不注入 | 编辑页 `off`；停用前弹影响面；能力中心 `目标停用 +1` |
| 停用 MCP | 保留 | 立即不注入（该服务器全部工具对所有 Agent 不可见） | `offline/off`；停用前弹影响面 |
| 停用工具（自定义） | 保留 | 不注入 | `off` |
| 停用工具（内置/插件来源） | 保留 | **仍然注入** | `bypass`（如实标注） |
| 停用 Agent | 保留 | 整个 Agent 不路由 | `inactive`（45 条现状） |
| 卸载插件 | 保留 | 走 §4 的可消费过滤 → 多数不注入 | 卸载提示（`plugin_installs` 维度）；关系侧标 `plugin_off/off` |
| 下架（unpublish） | 保留 | **技能/MCP 仍生效**（旁路） | `plugin_off` |
| 删除技能 / MCP | 接口级联删除绑定 | 无 | 不存在；历史孤儿由门禁 G2 拦截 |
| 删除工具 | **不级联** | 无 | `dangling`（门禁 G2 会判红） |
| 删除 Agent | 不清理 `agent_tools` | 无 | 关系表残留（建议后续加级联） |

## 8. 已知未修（如实列出）

1. **`停用` 对内置工具 / 插件自动消费不生效**。修它会改变 5 个 Agent 的实际工具集，
   属于产品决策，本轮只做"如实标注 + 门禁锁定标注正确"。
2. **`name` 作为关系键不唯一**。彻底修需要给 `agent_tools` 增加目标 id 列并迁移；
   本轮只把"随机命中"改成"确定性命中"，并把歧义暴露出来。
3. **`usage_of` 的调用计数**取 `capability_registry`，对 `mcp_tool` 粒度**未做逐工具统计**
   （registry 里 `mcp_tool` 的 `call_count` 全 0，聚合走 `mcp_server`）。
4. **角色过滤（`tools.allowed_roles`）不参与判定**：它依赖当前用户，
   同一绑定对不同用户可能不同，界面按"无用户"口径显示。

## 9. 门禁

`tools/verify/verify_binding_graph.py`（9 项 + 变异自证，已接入 CI）：

| 断言 | 防的失效 |
|---|---|
| G1 覆盖率 | 新增绑定类型未被判定（未知状态当成生效） |
| G2 无悬空 | 删能力不清关系 |
| G3 判死不得被注入 | 判定与运行时漂移（**与真 pipeline 对拍**） |
| G4 技能判定 ↔ `bound_tools_for` | 两套口径 |
| G5 反向关系自洽 | 影响面查询失真 |
| G6 变异：停用技能 ⇒ 判定翻转 | 判据空转 |
| G7 bypass 机制成立 | 过度断言（把活的判成死的） |
| G8 重名歧义暴露 | 指向不确定却装作确定 |

运行：

```bash
./.venv/Scripts/python.exe -X utf8 tools/verify/verify_binding_graph.py
```

## 10. 一句话总结

> **"绑定"只是配置层的一行；"生效"要过四道闸，而且存在两条判据旁路。**
> 现在这三件事在界面和 API 上是分开显示的：
> 配置层看「已选 N」，装配层看「生效 M / 失效 K / 待治理 J」，
> 运行层看「调用次数、最后调用时间」——
> 停用/删除前会先告诉你"有几个 Agent 依赖它"。
