# MR 对比分析·图谱化差异呈现与人工确认效率提升设计方案

> 项目：mbse_system 知识流水线（分支管理模块）
> 日期：2026-09-03 ｜ 状态：**待确认后实施**
> 前置：GitHub 对标后端 P0-1/P0-2/P1-1/P1-2 已全部落地（38/38 验证通过）

---

## 0. 结论先行

1. **图谱呈现完全可行且成本低**：diff 数据（实体字段级 changes + 关系 added/removed）后端已齐备，前端已本地 vendor `cytoscape.js + cytoscape-dagre`（离线可用，SysML 视图已在用），P0 改动集中在前端新增 1 个图谱 Tab，**无需后端加表**。
2. **业界已验证该方向**：本体/知识图谱领域的 diff 工具（OntoDiffGraph、OWLDiff、GO）均采用"图谱着色 + 最小视图 + 列表↔图谱联动"范式；KGCL 用户调查显示 **82% 用户认为高层变更呈现极重要，仅 8% 对纯文本 diff 满意**——现有文本列表正是那 92% 的痛。
3. **推荐组合**：三层呈现体系（图谱总览 → 分组清单 → 字段详情）+ 确认工作流，P0 先做图谱 Tab 与联动，P1 做逐项确认，P2 做合并结果预览图。
4. **比 GitHub 更强的一点**：本系统是图谱模型，可做 **"合并结果预览图"**（合并后 dev 长什么样）——GitHub 文本 diff 做不到的事，这是差异化亮点。

## 1. 业界调研（来源见文末）

| 工具/研究 | 核心做法 | 对本方案的借鉴 |
|---|---|---|
| **OntoDiffGraph** (2017, VOWL 记法) | 变更元素彩色边框：绿=新增、蓝=修改、红=删除；边同样着色；"Show Minimal View" 只显示变更；左侧文本列表点击 → 图谱自动定位居中 | **核心交互范式**：最小视图 + 列表↔图谱双向联动 |
| **GO 分层着色图** (Gene Ontology) | 同布局叠加：红=删除、粉=修改、蓝=新增、**灰=未变更上下文** | 配色语义、未变更节点灰显衬托变更 |
| **OWLDiff** (2011) | 并排双树 overlay 视图，变更高亮 | P2 双栏对比的参照 |
| **KGCL / 用户调查** (Oxford Database, 2024) | 知识图谱变更语言标准化；调查：82% 用户要求高层变更呈现，仅 8% 满意纯文本 diff | 论证图谱呈现价值；变更应按"实体"聚合而非逐字段 |
| **OnDeT** (IEEE Access, 2025) | 多版本 diff 时间轴探索 + 变更语义化 | 提交链时间轴可作为辅助导航（P2） |

**共性结论**：① 变更必须着色编码到图元；② 必须有"只看变更"的最小视图；③ 文本清单与图谱必须双向联动；④ 变更按实体聚合呈现，字段细节放详情层。

## 2. 现状与差距

### 2.1 现有能力（已落地）

| 能力 | 现状 | 位置 |
|---|---|---|
| diff 数据 | `diff_branches` 返回 entities{added/modified(含逐字段 changes)/removed} + relations{added/removed} + summary，支持 full/merge-base 三点式 | `repositories/branch_repo.py:156` |
| MR 对比抽屉 | 统计卡片（5 张）+ 分类筛选 chips + 关键词搜索 + **文本列表**（＋/✎/－ 前缀 + 字段值对比） | `static/index.html` loadMergeDiff 系列 |
| 冲突面板 | 冲突列表 + 三选一解决 + delete_modify 双选卡 + conflict_changed 引导 | 同上 |
| 图谱引擎 | cytoscape.js + dagre 已本地 vendor（`static/vendor/`），SysML 视图渲染在用；零外部依赖 | `static/index.html:9-11` |

### 2.2 差距（本方案要解决的）

| # | 差距 | 影响 |
|---|---|---|
| G1 | 差异只有文本列表，**看不到结构影响**：改了 1 个实体的属性 vs 断了 1 条关键依赖关系，列表里权重一样 | 评审者无法快速判断"这次合并动了系统的骨架还是皮肉" |
| G2 | 逐字段确认效率低：变更按"字段"平铺，没有风险分级，重要变更（status 语义、deprecated）淹没在属性值微调里 | 误通过 / 遗漏关键变更 |
| G3 | 关系 diff 只有 added/removed 三元组，**没有挂在受影响实体上** | 确认"新增关系"时需要脑补两端的实体 |
| G4 | 无确认状态追踪：评审者看完列表记不住哪些看过、哪些有疑问 | 重复劳动，协作时无交接 |

## 3. 设计方案

### 3.1 三层差异呈现体系（总架构）

```
┌─ L1 图谱总览 ──────────────────────────────────────┐
│  差异叠加图谱（变更子图+1hop 上下文灰显）              │
│  回答："动了系统的哪些结构？影响范围多大？"             │
└──────────────┬────────────────────────────────────┘
               │ 点节点 ↔ 点列表项（双向联动定位）
┌──────────────▼────────────────────────────────────┐
│  L2 分组清单（增强现有列表）                          │
│  按实体聚合 + 风险分级排序 + 确认状态标记              │
│  回答："哪些变更需要我确认？哪些已确认？"              │
└──────────────┬────────────────────────────────────┘
               │ 点实体展开
┌──────────────▼────────────────────────────────────┐
│  L3 字段详情（增强）                                 │
│  base/head 双栏对齐 + 关系变化挂载 + 冲突解决入口      │
│  回答："这个实体到底改了什么值？"                     │
└───────────────────────────────────────────────────┘
```

三层在同一抽屉内切换/联动，不新增页面。图谱作为**新增 Tab**（图谱 / 差异清单 / 冲突解决 三个 Tab 并列）。

### 3.2 L1 图谱叠加图设计（核心）

#### 变体决策

| 变体 | 说明 | 建议 |
|---|---|---|
| **A. 差异叠加图** | 单图：以 diff 实体集合为骨架，画变更节点（着色）+ 其 1-hop 未变更邻居（灰显） | ✅ **P0 采用** |
| B. 并排双图对比 | 左=目标分支现状图、右=源分支图，同布局对照 | P2（迁移语义下价值有限） |
| C. 合并结果预览图 | dry-run 合并 → 渲染"合并后目标分支"图谱 | P2 立项，**差异化亮点** |

#### 视觉规范（沿用项目现有语义色）

| 图元 | 样式 | 语义 |
|---|---|---|
| 新增实体节点 | 绿实线边框 + ＋ 角标 | 仅源分支有 |
| 修改实体节点 | 橙实线边框 + ✎n 角标（n=变更字段数） | 两边都有但字段不同 |
| 移除实体节点 | 红虚线边框 + 50% 透明度 + － 角标 | 仅目标分支有 |
| 冲突实体节点 | **紫色加粗描边 + 呼吸动画**（覆盖基础色） | 有未解决冲突 |
| 未变更上下文节点 | 灰色淡显（opacity 0.35），不可交互聚焦时加深 | 1-hop 邻居，提供结构语境 |
| 新增关系边 | 绿实线 | — |
| 移除关系边 | 红虚线 | — |
| 不变关系边 | 浅灰细线 | — |

#### 布局策略

- **dagre 确定性分层布局**（沿用 SysML 视图已验证的 `svmCytLayoutFor` 机制）：相同图结构 → 相同布局结果，评审者两次打开抽屉看到的图谱稳定一致（对标 GitHub 文件树顺序稳定性）。
- 边方向：以"需求→功能→组件"追溯方向为层级依据（dagre rankdir=LR），与系统既有 BDD/TRACE 视图习惯一致。

#### 图谱范围控制（防"500 节点一锅粥"）

| 档位 | 内容 | 默认 |
|---|---|---|
| 最小视图 | 仅变更实体 + 其间关系 | — |
| **变更+1hop** | 最小视图 + 变更实体的直接邻居（灰显） | ✅ 默认 |
| 全图 | 分支全量图谱（淡显变更之外一切） | 可切换 |

超阈值保护：变更实体 > 80 时图谱默认折叠为聚类节点（按 entity_type 分组），点击展开——对齐 OntoDiffGraph 的 Minimal View 思路。

#### 交互设计

| 交互 | 行为 |
|---|---|
| 点击变更节点 | 右侧滑出 L3 字段详情面板（base/head 双栏） |
| 点击冲突节点 | 直接切到冲突解决 Tab 并滚动到该冲突 |
| 列表点击实体（L2） | 图谱 `cy.$id(id).animate` 居中放大 + 高亮闪烁 |
| 图例 | 常驻左下角，点击图例项 = 按类型筛选（如只看新增） |
| 悬停节点 | tooltip：实体名 / 类型 / 变更摘要（"spec: A0→B1"） |
| 框选/滚轮缩放 | cytoscape 原生能力，直接可用 |

### 3.3 L2 分组清单增强（人工确认效率核心）

#### E1 按实体聚合（对齐 KGCL 结论）

关系变化不再独立成条，挂载到两端实体条目下展开显示：
```
✎ 制动控制器（部件） · 2 字段变更 · 1 条新增关系      [已确认▾]
   ├ spec: "A0" → "B1"（属性）
   ├ status: candidate → reviewed（状态 ⚠）
   └ ＋ 关系: 制动控制器 —[satisfies]→ 需求 REQ-101
```

#### E2 风险分级排序（P0）

| 风险级 | 判定规则 | 排序权重 |
|---|---|---|
| 🔴 高 | status 变更（涉及发布/deprecated 语义）、被冲突实体、removed 实体（连带其关系全部失效） | 最上 |
| 🟠 中 | 属性值变更、新增实体 | 中 |
| 🟡 低 | 仅名称/类型变更 | 下 |

高分变更默认展开详情，低分默认折叠为一行——评审注意力按风险分配。

#### E3 默认 merge-base 模式（P0）

MR 抽屉内 diff 请求默认 `mode=merge-base`：只显示本次待合并的增量（自上次合并以来），避免重复评审已合入内容。保留"查看全量"切换。

#### E4 逐项确认工作流（P1）

- 每个实体条目三态：`待确认 / 已确认无异议 / 标记关注`（关注需填一句话备注）。
- 确认状态**仅存前端 localStorage（按 MR id）**，不进后端——评审是个人行为，通过/驳回才进后端记录，避免过度设计。
- 可选开关：开启"确认全覆盖"后，未全部确认时「通过合并」按钮给出黄色提醒（不硬拦，保留强制通过权）。

#### E5 键盘导航 + 批量确认（P1）

- `j/k` 上下切换、`Enter` 展开/折叠详情、`c` 确认、`f` 标记关注。
- 筛选出某类变更后（如"仅属性默认值微调"）一键批量确认。

#### E6 图谱定位联动（P0）

L2 每个实体条目带「📍定位」按钮 → 图谱 Tab 内居中高亮；反向图谱节点点击 → 清单滚动定位。冲突节点在图谱上呼吸动画常显，解决一处冲突图谱实时去紫。

### 3.4 后端改动评估（很少）

| 项 | 需求 | 评估 |
|---|---|---|
| P0 图谱数据 | 变更实体 + 1-hop 邻居关系 | **现有 diff 接口 + 现有图谱查询接口可组装**，前端拿 diff 实体 id 集合过滤即可；若性能不足再加 `include_context=1` 参数 |
| P1 确认状态 | 无 | localStorage，后端零改动 |
| P2 合并预览 | dry-run 合并 API | `POST /api/branches/merge-requests/{id}/preview`，复用 `resolve_merge` 的合并计算逻辑但只算不写，返回预览快照 + diff；单独立项评审 |

### 3.5 分期路线（P0 → P2）

| 期 | 内容 | 改动面 | 预估 |
|---|---|---|---|
| **P0** | ① 图谱 Tab（叠加图 + 1hop + dagre + 图例 + 三档范围）② L2 风险分级排序 + 实体聚合 ③ 双向定位联动 ④ 冲突节点高亮 ⑤ 默认 merge-base | 前端 `static/index.html` 为主，后端零改动 | 前端 1 个大改动包 |
| **P1** | ① 逐项确认三态工作流（localStorage）② 键盘导航 ③ 批量确认 ④ 全覆盖提醒 | 纯前端 | 小 |
| **P2** | ① 合并结果预览图（dry-run API + 渲染）② 并排双图对比 ③ 提交链时间轴联动 | 前端 + 后端 1 个只读接口 | 中，单独立项 |
