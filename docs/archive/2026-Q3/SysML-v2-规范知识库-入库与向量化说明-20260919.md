## 2. 为完成入库必须先修的三处（都有实测依据）

入库前工程对**所有 PDF 都无法解析**（`documents` 表 5 份 PDF 全是 `parse_status='failed'`）。
逐层定位到三个真实缺陷，已修：

### 2.1 根因：`pdfplumber` 未安装 → 所有 PDF 入库静默失败

- `knowledge_pipeline/extract.py` 的 `_extract_pdf` 把 `import pdfplumber` 包在 `try/except` 里，
  库缺失时**返回空串**；上层 `ingest_document` 见文本为空，判 `parse_status='failed'`，
  报错文案是「无法从该格式提取文本（支持 txt/md/pdf/docx/csv/json）」——**指向格式，实为缺依赖**，极易误诊。
- 该依赖在 `requirements.txt` 里本来就是「**已 import 但本机 .venv 未安装**」的可选依赖（第 50-54 行）。
- **修**：`pip install pdfplumber`（0.11.10）→ 转显式依赖并补入其传递依赖
  （`cffi` / `cryptography` / `pdfminer.six` / `pycparser` / `pypdfium2`），
  `requirements.txt` 与 `.venv` 实测 `pip freeze` 完全一致（44 / 44 条，零差异）。

### 2.2 PDF 抽取硬编码「只取前 50 页」→ 规范类文档只能入库 ~17%

- `_extract_pdf` 原为 `for page in pdf.pages[:50]`，对页数多的规范是灾难性的：

  | 文档 | 总页数 | 全量字符 | 截 50 页后 | **覆盖率** | 全量抽取耗时 |
  |---|---|---|---|---|---|
  | KerML 规范 | 454 | 937,320 | 172,773 | **18.4%** | 17.6 s |
  | SysML v2 规范 | 691 | 1,229,260 | 215,265 | **17.5%** | 23.6 s |

- 即：**原来即使装好 pdfplumber，也只能入库规范的前 1/5**，且抽取根本不是瓶颈（691 页仅 23.6 s）。
- **修**：改为可配置 `extract.pdf_max_pages`（`core/config.py`，默认 **1200**，`<=0` 不限制），
  保留上限以防超大文件拖垮入库。
- **修后复测（同一棵最终树，`pdf_recap.py`）**：`extract` 段配置读出 `{"pdf_max_pages": 1200}`、
  `_pdf_max_pages()` 返回 **1200**；两份文档覆盖率 **100.0% / 100.1%**（字符 937,320 / 1,229,260），
  耗时 19.0 s / 24.3 s —— **配置确实被读取，修复在最终树上生效**（非"改完即忘"）。

### 2.3 hyde 问题向量「一次全发」→ 大文档必然降级并污染向量维度

- `ingest.py` 里 hyde 向量的调用原本传 `batch_size=0`（语义=不分批、一次全发）。
  hyde 条数 = chunk 数（数百上千），远超服务端单批上限。
- 实测 `text-embedding-v3` **单批 >10 条即 400**：`batch size is invalid, it should not be larger than 10`。
  失败后被 `embed_with_version` 静默降级为 **4096 维 bigram**，
  而主向量是 **1024 维真向量** —— 同表两个维度、不可比，污染 `hyde_embedding`。
- **修**：与主向量路径一致改为 `batch_size=8`（<10 上限）。

> 这三处都是**产品缺陷**，不是本次任务的临时绕过：修完后从 UI 上传 PDF 走的是同一条已修好的路径。

## 3. 怎么在 AI 建模里消费（关键）

### 3.1 链路（无需新增接线；**类名与行号均为 2026-09-19 实测**）

```
「资料库」上传/入库（本次已做）      →  documents + document_chunks（含 1024 维真向量）
                                            ↓
建模会话 POST /api/conversations/{id}/chat   →  agent.execute(_stream)
                                            ↓
范围解析 _resolve_req_scope（tools.py:621，读 modeling_scopes）
                                            ↓
★ GraphRAG.retrieve()（agent/rag.py:15 类 / :29 方法） ← 建模会话的真实检索入口
      ├ knowledge_engine.hybrid_search（rag.py:122；BM25 + 向量 + RRF + HyDE，top_k=4）
      └ 异常兜底 knowledge_pipeline.search_chunks（rag.py:154）→ vector_search_embed
                                            ↓
返回 retrieval：{route, route_reason, entities, relations, vector_docs,
                 chunk_hits[4], hyde_score, latency_ms, knowledge…}
                                            ↓
ContextMixin._build_context（context.py:176-182）拼「检索数据区」：
      【来源1】{source_doc} §{chunk_index}: {content}     ← 取 chunk_hits[:3]
                                            ↓
注入 system prompt（budget_retrieval_tokens=2600 / budget_retrieval_chars=4000 裁剪）
                                            ↓
响应同时回传 citations（execute.py:389 / :440，与【来源n】1 基对齐）
```

- **类名/方法名（别记错）**：检索入口是 `agent.rag.GraphRAG.retrieve(query, branch, attachment_text, kb_scope)`
  —— **不是** `agent/rag.py` 里某个 `KnowledgeRetriever`（该名字全仓 0 命中，是凭记忆写错的典型）。
  真实调用点：`agent/pipeline_parts/execute.py:126`（同步）与 `stream.py:901`（流式）。
- 真向量检索引擎：`knowledge_pipeline.search_chunks` → `vector_search_embed`
  （只与**相同 `embed_version`** 的块比对，从机制上杜绝 bigram 与真向量混比）。
- 提示词预算：`context.budget_retrieval_tokens`（默认 **2600**，优先）/ `budget_retrieval_chars`（默认 4000，回退），
  超限**从尾部裁剪、保留最相关头部**（`history.py:423`，对齐 Lost-in-the-Middle）。
- 可选 `context.rerank`（默认 False）：命中后用 LLM 粗筛→细排（`context.py:192-200`）。

### 3.2 建模范围：把这三份文档"圈"成建模知识源

已建范围（`modeling_scopes`，幂等，同名覆盖）：

| name | mode | 含文档 |
|---|---|---|
| `SysML v2 规范知识源（官方标准 + AI 建模知识文档）` | `doc` | 三份 |

- 建/改：`services.scope_service.save_scope(conn, name, mode='doc', doc_names=[...])`
- 展开：`scope_service.resolve_scope(conn, scope_id)` → `{mode, docs, fragments, chunk_ids}`
- 作用：检索时把 `doc_names` 传给 `search_chunks(..., doc_names=scope_docs)`
  → **硬过滤到这三份文档**（`_doc_clause`），避免被库里其它文档稀释。
- 三种模式：`doc`（整篇）/ `fragment_group`（第 N 节）/ `chunk`（指定块谱）。

### 3.3 自测检索（跑过的命令）

```python

conn = get_db()

# → 命中 KerML / SysML v2 规范 / AI 建模知识文档 的对应分块（实测见 §5）
```

### 3.4 两条容易踩的消费规则

1. **必须真向量**：`vector_search_embed` 只与同 `embed_version` 的块比对；一旦入库降级成 bigram，
   检索会**整体退化到词面 bigram**（召回质量断崖式下降）且不与真向量混比 —— 所以入库完成必须核对
   `embed_version='openai-compat'` 与维度 1024。
2. **AI 产物隔离**：`origin='ai_generated'` 的文档默认被 `exclude_ai` 排除（防 model collapse），
   `kb_scope.include_ai_generated=true` 才纳入。**这三份是外来权威资料，`origin='upload'`，正常参与检索。**

## 8. 附：AI「生成」与「校验」在产品里是什么形态？（工具 / 工具 / 技能，三层）

结论先行：**不是"二选一"，而是三种形态并存；并且本地的 `checker.jar` 完全没有接进产品。**

| 能力 | 形态 | 落点（可定位） | 说明 |
|---|---|---|---|
| **AI 生成 SysML 代码**（提示词侧） | **既不是工具也不是技能** —— 是**流水线里硬编码的提示词片段** | `agent/pipeline_parts/prompt.py` → `_build_model_code_req(intent)`；由 `stream.py` / `execute.py` 两处拼进 system prompt | 全文约 200 字，只要求"在正文末尾用 ```sysml 输出完整模型代码"，**不含任何语法规则** |
| **AI 生成**（平台侧导出源码） | **系统工具**（`tools.kind='http'`） | `tools.id=37` → `zhiyuan_sysmlv2_gen` | 配置驱动（`config` JSON），由通用执行器按 config 调智源 `/api/project/ai/sysmlv2/gen` |
| **语法校验** | **系统工具**（同上）**＋** 入库门禁里的**硬编码调用** | 工具：`tools.id=38` → `zhiyuan_sysmlv2_check`；门禁：`norm_apply.py:500` `cli.sysmlv2_check(...)` | 两条路都调**智源远程** `/api/project/ai/sysmlv2/check`（OMG SysMLInteractive 解析器） |
| **本地 `checker.jar`** | **零注册** | — | 全仓 Python 代码** 0 处引用**；仅离线取证（本知识文档的实测依据）时使用 |
| **技能（skill）** | **数据驱动的内容注入层** | `skills` 表（11 条）+ `plugins` 表；装载/匹配见 `agent/pipeline_parts/skills.py` | 三级匹配（triggers → 语义 → LLM 兜底）＋渐进披露＋`allowed_tools` 工具白名单；**本身不执行任何动作** |

**三者如何咬合**（以"智源"链路为例）：

- 技能 `智源平台管理`（`skills.id=95`，`skill_type='package'`，`status='published'`）
  的 `allowed_tools` = `[zhiyuan_sysmlv2_gen, zhiyuan_sysmlv2_check, zhiyuan_sysmlv2_import,
  zhiyuan_project_list, zhiyuan_project_tree, mbse_pull_ingest]`；
  它给模型的是**流程规范与工具映射表**（"写回前必做 check""gen → 改 → check → import → gen 复核"）。
- 真正执行的是 **`tools` 表里的 5 个 `zhiyuan_*` HTTP 工具**（`agent_tools` 绑定到 Agent `zhiyuan_mgmt`）。
- 而"生成一段 V2 代码"这件事的**输出格式要求**，则写在 **pipeline 的 `_build_model_code_req`** 里。

**一句话**：**skill 编排 + tool 执行 + pipeline 硬编码** —— 三层，缺一层链路就不完整。

**与本次入库的关系（重要）**：新入库的三份文档走的是**检索层**（RAG 命中 → 注入提示词），
**不会**自动进入 `_build_model_code_req` 那段静态模板。因此：
- 想要"AI 生成时就被规则约束" → 需按《SysML-v2-知识文档与校验器-工程落地集成指南》把 **L0 硬约束卡**注入生成端；
- 想要"生成后被真实检出" → 需把本地 `checker.jar` 接进 `cards.py::_gen_sysml_views`（5 个调用点的收敛处），
  因为目前唯一的校验在**最后一步**（写智源前的远程 check），生成后到入库前**没有任何校验**。

### 9.3 ⚠️ 一个必须记住的坑：`reindex` 不能用来**更新文档内容**

我起初调的是 `POST /api/documents/800/reindex` —— **返回 200、`chunk_count=267`，看起来成功，
但新内容 0 命中**，白跑一次。

原因：`knowledge_pipeline/search.py::reindex_document` 是「**按新 embedder 重新向量化已有块**」，
它从 `document_chunks` 读 `content`，**根本不重新解析源文件**。

> **更新文档内容的正确顺序**：
> ① 先把新内容**同步到源副本** `data/uploads/<doc_id>_<filename>`；
> ② 再调 `POST /api/documents/{id}/retry`（走完整管道：解析 → 分块 → 向量化 → 入库）。
>
> **只改 `docs/*.md` 而不动源副本时，任何 reindex / retry 都不会生效** —— 源副本才是入库的事实依据。
