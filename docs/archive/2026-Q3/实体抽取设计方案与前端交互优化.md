## 一、现状与问题诊断

### 1.1 现有实体抽取能力（代码现状）

**后端链路（已实现，逻辑完整）**：

| 环节     | 实现                                                        | 位置                                    |
| ------ | --------------------------------------------------------- | ------------------------------------- |
| 文本解析   | 按格式分派（txt/md/docx/pdf/xlsx/pptx/csv/json）                 | `knowledge_pipeline/extract.py`       |
| 分块/向量化 | chunking + embedder + ingest                              | `knowledge_pipeline/`                 |
| 候选抽取   | LLM 按本体 schema 抽取 / Mock 规则兜底 → `v2g_candidates`（pending） | `vector2graph.py: extract_candidates` |
| 人工确认   | 勾选确认 → 图谱入库（过本体校验）+ chunk↔entity 溯源链接                     | `vector2graph.py: confirm_candidates` |
| 手动补抽   | `/api/documents/{id}/extract`（上传失败/未触发时用）                 | `routers/meta.py`                     |
| 上传即抽取  | 上传管道完成自动触发 v2g 候选抽取                                       | `routers/meta.py: upload`             |

**前端入口（4 条路径，相互割裂）**：

| 入口         | 位置             | 交互                                   | 体验问题                     |
| ---------- | -------------- | ------------------------------------ | ------------------------ |
| ① 文档管道上传   | 知识浏览→文档管道 kb-e | 上传→5 阶段进度→抽取结果内嵌展示（分类统计+按类型分组+关系三元组） | 结果一次性展示，之后只能靠记忆去审核       |
| ② 待审候选     | 标注审核→待审候选 kb-b | 表格勾选→批量确认入库/驳回                       | 见下方痛点                    |
| ③ 知识浏览手动抽取 | 知识浏览→向量图谱转化    | 输入查询→抽取→表格勾选确认入库                     | 与文档管道体验不连贯               |
| ④ NLP 文本抽取 | 本体管理→导入→NLP 抽取 | 粘贴文本→预览三元组→确认入库                      | 生成 Turtle 视角，与 v2g 候选两条线 |

### 1.2 前端交互具体痛点

1. **候选列表无检索与筛选**：`v2gReviewLoad` 一次拉 300 条，全量表格展示；无搜索、无按实体类型/来源文档/状态/批次的筛选、无分页（记忆：列表上限文案「显示前 300 条，全选仅作用于当前列表」本身就是妥协）。
2. **无单条候选操作**：只有「整批勾选→确认/驳回」二元操作；无法「查看某条候选的来源片段原文」「编辑属性后再确认」「单条驳回并写明原因」。
3. **无来源可追溯面板**：候选表格有「来源文档」列，但点击不能查看对应 chunk 原文片段；确认入库后 chunk↔entity 溯源链接已建立，前端却无查看入口。
4. **无置信度 / 无消歧匹配状态**：候选无置信度列；抽取时未与已有图谱做重复检测，同义实体/同形词无人提示（行业标准：无重复/疑似重复/高度重复三态）。
5. **无批次（任务）管理视角**：批次号只存在 `window._lastV2GBatch` 内存变量，无「抽取任务一览」（批次号/时间/来源文档/实体数/关系数/状态），跨批次无从定位。
6. **关系候选确认缺引导**：关系候选入库依赖两端节点已在图谱中，失败时报「源/目标节点未入库（需先确认节点候选）」，前端无前置提示与引导。
7. **无质量反馈**：抽取完成不展示通过率/拒绝率/误抽情况，无法评估抽取质量与提示优化本体。
8. **4 条入口体验割裂**：文档管道结果、标注审核列表、知识浏览手动抽取、NLP 抽取互不打通，无统一「抽取治理」视角。

## 二、用户需求调研（角色 × 场景）

| 角色    | 核心诉求                                      | 对应能力                 |
| ----- | ----------------------------------------- | -------------------- |
| 知识工程师 | 快速消化文档抽取的大量候选；批量处理 + 精确处理结合；知道候选来自哪个文档哪段话 | 检索筛选 + 单条溯源 + 批量确认   |
| 评审专家  | 对抽取质量负责：高置信直接过、低置信重点核、误抽要能驳回报错            | 置信度排序 + 单条驳回原因       |
| 设计师   | 文档里的模型元素（载荷/转发器/需求…）能进知识库、能被图谱检索到，对过程不敏感  | 上传即抽取 + 一键确认 + 闭环可视化 |

通用高频场景：

* 「刚上传的文档抽出了什么」→ 上传即展示 + 一键去审核。

* 「哪些候选还没处理」→ 待审候选（按文档/类型/时间筛选 + 计数）。

* 「这条候选凭什么抽出来」→ 来源片段溯源（chunk 原文）。

* 「会不会和已有知识重复」→ 消歧匹配状态。

* 「这次抽取质量怎么样」→ 批次统计（通过/拒绝/错误原因）。

## 三、行业方案调研（2026）

### 3.1 行业共识

1. **人工验证是抽取瓶颈，不是图数据库**：LLM 无微调下关系抽取准确率约 75–85%，知识图谱期望 95%+ 精度 → 必须 HITL（Human-in-the-loop），抽取永远不是"全自动一步到位"。
2. **Provenance（来源可审计）是底线**：每个三元组需携带 来源文档 / 抽取模型版本 / 审核人 / 审核时间 / 置信度，否则错误声明无法追溯撤回。
3. **置信度分级 + 阈值机制**：85% 以上置信走快审通道，底部 15% 自动要求澄清/驳回，让人工审核量保持在可处理范围。
4. **消歧是独立一等能力**：同形词（如 SysML v2 与 V 波段）单遍抽取约 30% 会失败，须标注"无重复/疑似重复/高度重复"三态由人工决策。
5. **任务/批次化**：一次上传 = 一次抽取任务，任务列表可搜索/重命名/查看状态（阿里云 Dataphin 模式）。

### 3.2 对标产品实践

| 产品/方案                  | 做法                                                                                                                              | 可借鉴点                                 |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| 阿里云 Dataphin 智能知识抽取    | 上传文件 → LLM 智能解析 → 候选项列表；按实体类型/名称搜索、按来源文档/审核状态/置信度筛选；每条展示名称/来源详情（可点开看来源文档与片段）/置信度/匹配状态（无重复/疑似/高度重复）/审核状态；操作=编辑/应用/弃用；有「添加记录」任务列表 | ①候选多维筛选 ②来源详情面板 ③消歧三态 ④编辑后应用 ⑤任务记录管理 |
| 学术知识图谱构建（PubMed 系）     | 解析 → LLM 抽取 → 专家人工审核 → 带 provenance 入库；85% 阈值 + 底部 15% 自动处理                                                                     | 置信度阈值快审通道；审核人/时间落库                   |
| GraphRAG 构建            | 文档 → 分块 → 实体抽取 → 关系抽取 → 验证/规范化 → 图谱                                                                                             | 分阶段可观测，每步可干预                         |
| Label Studio / Argilla | schema 驱动定制标注界面；状态流转（未标/已标）                                                                                                     | 单条样本聚焦式审核界面                          |

### 3.3 对本系统的适用结论

本系统 `vector2graph.py` 已具备 解析→抽取→确认→入库→溯源 主链路，缺的是**治理层体验**：检索筛选、单条溯源/编辑、消歧三态、批次管理、质量反馈。按行业标准补齐即可，无需重写抽取引擎。

## 四、优化方案（目标架构）

### 4.1 总体定位

> **把「待审候选」升级为「抽取治理中心」**：一次上传 = 一个抽取批次（任务）→ 候选按文档/类型/时间可检索 → 单条可溯源可编辑 → 批量与精确结合确认 → 消歧三态 + 置信度辅助决策 → 入库后图谱可回溯来源。

### 4.2 页面结构（标注审核→待审候选 升级）

```
┌──────────────────────────────────────────────────────────────┐
│ 抽取批次卡（最近 N 批）：batch_id · 来源文档 · 时间 · 实体/关系数 · 状态 │
│  [批次1 星网宽带…v2g-xxxx 08-11 实体12/关系3 ✓] [批次2 …]          │
├──────────────────────────────────────────────────────────────┤
│ 候选治理工具栏                                                │
│  🔍 搜索名称 │ 类型▾ │ 来源文档▾ │ 状态▾ │ 批次▾ │ 仅关系 ☐  │ 分页 │
├──────────────────────────────────────────────────────────────┤
│ 候选表格（分页，每行）                                          │
│  ☑ 候选名(类型tag)  来源文档[查看片段] 置信度 消歧状态 批次  操作  │
│       └ 关系候选：A —[包含]→ B（建边，两端未入库时黄色提示）        │
├──────────────────────────────────────────────────────────────┤
│ 底部批量条：全选/选中 n 条 → ✅ 确认入库 / 🚫 批量驳回           │
└──────────────────────────────────────────────────────────────┘
```

### 4.3 交互设计细节（对齐系统现有风格：panel/ph/pb、tag、table.t、右侧 #modal、居中 #lbx）

1. **批次一览**：待审候选面板顶部横向滚动批次卡；点击批次 → 候选列表按批次过滤；「全部」= 全部批次。
2. **候选检索筛选**：工具栏一行式（搜索 input + 类型 select + 来源文档 select + 状态 select + 关系过滤 checkbox），复用文档库工具栏样式（`doc-search` 同款）。
3. **来源片段溯源**：每行「📄 来源」可点 → 右侧 `#modal` 打开「候选来源」详情（候选名/类型/属性/来源文档 + chunk 原文片段高亮候选词 + 入库后显示已链接实体 ID）。复用 `showModal()` 业务表单模式。
4. **单条操作**：

   * 「✏️ 编辑」→ 右侧 `#modal` 编辑候选（名称/类型/属性 JSON）→ 保存后仍为 pending（改完再确认）。

   * 「👁 查看」→ 来源详情。

   * 「✅ 确认」「🚫 驳回」→ 居中 `#lbx` confirmDialog；驳回支持原因输入（promptDialog 多行）。
5. **消歧三态 + 置信度**（P1）：抽取时对已有图谱按名称/向量相似度打标 `无重复 / 疑似重复 / 高度重复`（`matching_status` 列），疑似/高度重复行黄色警示 + 提示「与 ENT-00X 疑似重复，请确认」。
6. **关系候选引导**：表格中关系候选显示 `A —[包含]→ B`；若两端实体均未在图中（`rel_source`/`rel_target` 不在 entities）→ 行内黄色 tag「先确认节点」+ 提示；确认按钮点击后仍失败 → toast 给出缺哪端。
7. **质量反馈**（P1）：批次卡显示 抽取 n / 待审 n / 已确认 n / 已驳回 n；列表顶部可选「只看被拒绝」查看拒绝原因分布（用于优化本体）。

### 4.5 验收标准

1. 上传文档后：抽取结果内嵌展示 + 一键进待审候选可定位到该批次。
2. 待审候选支持搜索/类型/来源/状态筛选与分页，>300 条不截断。
3. 每条候选可查看来源片段（chunk 原文 + 高亮），可编辑属性后确认，可单条驳回并留原因。
4. 候选展示置信度与消歧匹配状态，疑似/高度重复有警示。
5. 批次卡展示抽取/待审/已确认/已驳回统计，可点击按批次过滤。

## 六、已落地内容（P0+P1，2026-08-11）

* **抽取治理中心**：标注审核→待审候选升级为「🕘 抽取治理中心」。`v2g_candidates` 新增列 confidence / matching\_status / match\_entity\_id / reject\_reason（`_migrate_columns` 幂等加列 + 建表同步）。

* **后端**：`vector2graph.py`——`extract_candidates` 输出 confidence（LLM prompt 增加 confidence 字段，Mock 规则确定性打分 实体 0.8 / 关系 0.85）并做消歧打标（`_disambiguate`：同名=高度重复、包含/重叠=疑似重复、关联已有实体 ID）；新增 `batch_stats`（批次聚合）与 `update_candidate`（单条编辑+重校验+消歧重算）。`KnowledgeService` 新增 v2g\_batches / v2g\_update，v2g\_reject 支持 reason。路由：`GET /api/knowledge/v2g/batches`、`PUT /api/knowledge/v2g/candidates/{cid}`、`GET /api/knowledge/v2g/candidates` 附带 chunk\_content、v2g/reject 带 reason。

* **前端**：批次卡（来源文档/实体数/关系数/✓确认/待审/✗驳回统计，点击按批次过滤）；检索工具栏（搜索名称 + 类型/来源/状态筛选 + 仅关系 + 只看被拒）；前端分页（每页 15 条）；候选表新增 置信度/消歧/来源/状态/操作 列；单条操作 确认/来源/编辑/驳回（居中 `#lbx` confirmDialog/promptDialog，驳回带原因留痕）；来源溯源右侧详情面板（属性 + chunk 原文 + 已入库关联实体）；关系候选「⚠ 两端节点未入库」警示（对齐既有实体名称集合）；消歧警示（⚠ 疑似重复 / ⚠ 高度重复 + 关联实体）；「只看被拒」查看驳回原因分布。

* **与标准审核协调**：两级审核链明确——抽取候选确认入库后生成 candidate 实体并自动进入「实体关系审核队列」（`loadReviewQueue` 计数联动），UI 文案与 toast 均提示「确认后进入正式审核队列」。待审候选（v2g）与标准审核（candidate）互不混淆、流程衔接。

* **验证**：playwright 全流程——批次卡渲染/过滤、搜索与类型/来源/状态筛选、分页、来源溯源面板、单条编辑（PUT 改名+消歧重算）、单条确认（实体 candidate 落库 + 审核队列联动 39 条）、单条驳回（reject\_reason 落库）、新上传文档抽取（实体 5/关系 3，置信度 0.80，消歧打标高度重复警示）、关系候选两端未入库警示、「只看被拒」驳回原因分布。

## 七、已落地内容（P2 + 交互体验升级，2026-08-11）

* **上传批次任务式呈现**（用户反馈「抽取治理中心作为上传批次呈现」）：批次区升级为「📦 上传批次」面板——批次聚合摘要（共 N 批 · 待审 X · 已确认 Y · 已驳回 Z）+ 批次状态过滤 chips（全部/待审/已确认/已驳回）+ 批次搜索（文档名/编号）+ 任务式批次卡片（文档名 · batch 尾号 · 时间 · 待审徽章 · 实体/关系数 · ✓✗ 统计，点击过滤候选、当前高亮）。

### 9.5 行业调研要点（本次新增参考资料）

1. **默认不自动合并**：合并是破坏性且近乎不可逆的操作，规则永远只产出 proposal 推给人审（同名异人常见，「提议 + 人审」是地基）
2. **guard 否决层**：规则之外独立否决（跨域/冲突属性），被拦下的提议留痕可复查
3. **幸存值规则**：合并 = 「是否同一实体」+「哪些值存活」两个决定，合并前必须定规则（非空优先、来源优先、最早创建保留归因、合并所有关联）
4. **置信度自动处理**：高置信（>0.85）可自动批准、低置信（≤0.5）自动驳回，人工只处理中间地带
5. **质检工作台**：默认聚焦待办，已完成按状态筛选/折叠查看；审核三步 Accept / Fix\&Accept / Reject；任务锁定防重复操作；状态全可视
6. **审核抽样与一致性**：小型项目 100% 全量审核，中型分层抽样，高一致性低风险批量通过
