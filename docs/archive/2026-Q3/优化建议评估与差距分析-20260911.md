## 二、逐条详评（证据 + 差距 + 落地方向）

### A. 模块命名规范

**A1 核心模块加「模型」前缀** — `static/index.html:73-83`
现状导航：新建任务 / 术语词典 / 本体模型 / 图谱工作区 / 资料库 / 能力中心 / 更多。
「本体模型」已带前缀；若全量执行，「图谱工作区→模型图谱」「资料库→模型资料库」。
*评估*：纯文案改动（含 title、KB_TAB_TITLES、03-chat.js 角色快捷入口约 15 处），零风险。
*建议*：执行前先拿到单位命名语境（A4），一次改到位，避免两次刷新用户认知。

**A2 废弃「分支管理」「配置管理」→ 统一「版本管理」** — `index.html:707-720`、`routers/branches.py`
UI 层已达成：分支功能已收敛为右上角 GitHub 式分支选择器（含搜索/类型徽章/新建）+ MR 全局入口，
「配置管理」已于 09-04 下沉能力中心/账号抽屉（index.html:82 注释）。
*差距*：仅代码层——`routers/branches.py`、页面标题「合并请求」、`go('branch')`。
*建议*：路由不改（破坏性变更不值），页内标题与入口文案改「版本管理」即可，P2。

**A3 取消治理工作台 → 「候选本体识别」** — `19-governance.js`、`kb-a 治理队列`（index.html:394-405）、kb-b（已隐藏）
*评估*：建议描述的功能（从文档抽取实体/关系/属性→候选）**已经存在**，就是 9/10 刚做过状态机收口的
kb-b 抽取-审核流水线，且其入口昨天刚按你指令隐藏。真正的问题不是"有没有"，而是**定位与命名**：
- 治理（19-governance.js：健康度/消歧/SHACL/发布）与抽取审核（kb-b）职责边界清晰，不建议合并；
- 「候选本体识别」若作为正式模块名恢复 kb-b 入口，需同步解决"隐藏后 candidate 积压无提醒"问题
  （待办红点计数，02-shell.js 知识评审待办已有雏形）。
*建议*：kb-b 改名「候选本体识别」恢复主导航入口 + 待办计数徽章，P1。**这是本批建议中对当前结构最有价值的一条。**

**A4 知识库表述本地化** — 全局文案
术语词典 title 已带专业表述（index.html:75「词条 ↔ 本体类型归一映射（Schema 命名层 · 主数据）」）。
*评估*：方向对但**缺少输入**——需要单位术语对照表（哪些词要改、改成什么）。
*建议*：先出术语对照清单让业务方勾选，再批量替换，P2。

### B. UI 交互与展示设计

**B1 本体视图对齐 Protege** — `21-ontology.js:50-104, 555-559`
*已具备*：中栏四视图（edit/graf/owl/cl），OWL 序列化含 RDF/XML·Turtle·SHACL 三格式（节点级+全局），
公理以 chip 编辑（equivalent_to / disjoint_with / axioms）。
*与 Protege 的实质差距*（按影响排序）：
1. **无 Instance（个体）管理**——本体只有 TBox 没有 ABox 视图，图谱里的实体未回链到类型视图；
2. 左栏是单棵类型树，非 Protege 式 Class / Object Property / Data Property 分标签（当前靠顶部维度 Tab 切换，语义等价但组织方式不同）；
3. 公理编辑是 chip 列表，无结构化表达式编辑器（无 DL/Manchester 语法解析、无合法性校验）；
4. 无推理机集成（SHACL 校验已有，可覆盖大部分约束场景，DL 推理为空白）。
*评估与建议*：**同意方向，不建议照搬**。Protege 是桌面单机范式，直接移植四标签布局会与本系统
「顶部维度 Tab + 左树 + 中栏视图」已收敛的三栏结构冲突（上一轮 UI 评估刚收敛过导航轴）。
落地顺序：P2-① Instance 视图（中栏第五视图，按类型列个体，复用图谱实体查询）；
P2-② 公理表达式编辑器（Manchester 语法解析 + 实时校验，工作量大，单独立项）；
P2-③ 推理：优先复用已有 SHACL，DL 推理评估owlready2（Python 侧，离线可装）。
同时**保留反对意见**：Protege 的低信息密度恰是其 Web 化移植的缺点，「移除花哨提升密度」这半句完全同意。

**B2 文档切片圈定交互** — `20-docs.js:724-730`
*现状*：`viewDocSource` → openPanel 只读预览（源文件副本或分块拼接），**无任何选中交互**。
*落地设计*（P1，工作量中）：
- 预览面板监听 `selectionchange`，松开鼠标浮出「→ 加入对话」按钮；
- 选中片段携带 `{doc_id, chunk_id, char_range}` 锚点（分块拼接模式可直接定位 chunk）；
- 发送时作为消息引用注入（附件栏加引用 chip，复用 10-chatinput.js attach-bar）；
- 产物代码局部选中同理：对话消息代码块 + artifacts 预览加同一交互，选中行号区间发起修改。
*依赖*：与 B4（跨会话产物引用）共用 attach-bar 扩展，建议一并做。

**B3 插件市场精简** — `index.html:821-993`
*现状*：能力中心单入口 + plugins 表单一事实源（09-04 已重构），Agent/Skill/Tool/MCP 四页
**顶部重复渲染 st-market/st-model tab 头 5 次**，管理页还有「市场在售/分享管理」子 tab。
*差距*：结构已接近建议的「共享插件库」，剩余是**视觉收敛**：四页重复 tab 头收敛为页级公共组件，
市场内区分「本地安装区 / 公共市场区」两个锚点区（数据模型已支持，来源字段 market/custom/builtin）。
*评估*：P1，低工作量，纯前端。

**B4 跨会话文件引用** — `10-chatinput.js:291-333`、`routers/artifacts.py`
*现状*：`/api/upload` 仅支持本地文件选择上传；artifacts 表（artifacts.py 有完整 CRUD）与上传链路**零打通**。
*落地设计*（P1，工作量低-中）：
- attach-bar 加「📦 历史产物」按钮 → 弹层列出 artifacts（本会话优先 + 其他会话可搜索）；
- 选中后不复制文件，记录 `artifact_ref`（来源会话 id + artifact id），消息引用渲染时标注来源；
- 后端只需一个 `GET /api/artifacts?search=`（已有）+ 上传链路接受 artifact_id 复用。
*价值*：这是"AI 建模产物进资料库"（此前 F7 提案，待拍板）的**前置依赖**，两条应合并为一个决策包。

### C. 数据流转与构建逻辑

**C1 产物→映射规则→三元组** — `14-sysml.js`（SysML 通道）、`docs/sysml-profile-本体转换详细设计.md`
*现状*：文档抽取（chunk→LLM→v2g_candidates→triples）与 SysML 导入通道（锚点直通）均已存在；
但"映射规则"是**隐式的**——埋在 LLM 抽取 prompt 里，没有可配置、可审计的规则表。
*差距*：① 通用产物（代码/报告/artifacts）无转换通道；② 映射规则不可配置不可版本化。
*落地设计*（P1）：`ontology_mapping_rules` 表（触发条件/实体模式/关系模式/置信度权重）+ 规则管理 UI
（挂能力中心或候选本体识别模块）+ 转换引擎按规则表执行，LLM 仅做规则未覆盖部分的兜底。

**C2 入库前冲突检测** ⚠️ 本批最关键差距
*现状证据*：
- 消歧（entity_dup_candidates + LLM 成对判定，19-governance.js:149）发生在 staging 之后——**入库后**；
- 冲突合并走 MR 层（branches.py:138 merge_conflicts）——**入库后**；
- SHACL 校验（governance.py:36 shacl-check）是治理阶段体检——**入库后**；
- `knowledge_conflicts` 表已建（migrations.py:1020）但插入点缺失，基本空转。
*评估*：建议"入库前检测文件间不一致冲突"**完全成立**，且与 9/10 状态机天然衔接——
`stored → committed` 的人工闸门正是插入点。
*落地设计*（P0）：commit 时（单个/批量）前置执行**一致性预检**：
① 批内实体名/IRI 冲突；② 与目标分支既有图谱的冲突预检（同名不同义、关系矛盾）；
③ 检测结果写入 knowledge_conflicts（表已在，补插入点）并生成冲突报告页；
④ 有未裁决冲突时阻断 commit（force 管理员跳过，与生命周期 force 语义一致）。
*工作量*：中，复用消歧 LLM 判定与 SHACL，只是把调用时机前移。

**C3 AI 经 MBSE 工具落图（MagicDraw 真相源）** — `docs/AI原生架构_澄清与补充设计_20260831.md`
*现状*：MagicDraw 仅存在于设计文档，图库 SQLite 是当前真相源。
*评估*：方向正确但**远期**。MagicDraw 自动化需要 CLI/COM/OSLC 桥接，私有化离线部署约束下
集成成本高；且"真相源外移"与现有 Git 式分支图库架构（已高度可用）存在架构级冲突，需重新论证。
*建议*：P2，维持"导入通道"中间态（SysML XML 导入→抽取→审核），不承诺真相源外移时间表。

**C4 每项目一个 Subgraph 树状层级** — `graph_db.py`、index.html:298
*现状*：命名图按分支 `http://www.xingwang.mbse/graph/{branch}`，项目与分支是两级表
（projects/branches），但命名图 scheme 未含 project 维度。
*评估*：当前单项目（星网）运行下无实际痛点；多工程方案文档已存在（多工程数据体现设计方案_20260831.md）。
*建议*：P2，待第二个真实项目接入时一并迁移 `graph/{project}/{branch}`（需 SPARQL 兼容层迁移说明）。

**C5 个人分支直接覆盖免审** — `branches.py:29 _check_writable_branch`、`governance.py:20 gate-mode`
*现状*：全局治理闸门（gate-mode 可切换），但**未按分支类型区分审核策略**。
*落地设计*（P1，小改动）：personal/* 分支写入跳过 candidate 审核直接落图（保留审计日志与撤销窗口），
release 保持只读、dev 保持闸门。改动点：写入路径按 `branch.startswith('personal/')` 分流。
*⚠️ 需要拍板*：这与现行「candidate 审核是入图唯一人工闸门」的收口语义（9/10 定稿）**有意冲突**——
本质是把"数据来源可信度"作为审核豁免条件（个人分支=个人实验区，污染面可控）。确认后即可实施。

**C6 Git/GitLab 标准工作流** — `branches.py`（diff/conflicts/integrity_report/MR）、状态机文档
*评估*：**已高度达成**，release 只读、检出、MR、冲突检测、完整性报告俱全，本条建议实为对现状的确认。
*剩余补充*（P2）：保护分支配置化（谁可发起 release 合入）、MR 审批人多级。不急。

**C7 术语词典→本体（最大候选来源）** — `18-glossary.js:274,369,593`
*现状*：概念审批流（candidate/approved，ISO 704 定义约束）+ 词条↔本体类型映射（datalist 联动）已有。
*差距*："服务本体经抽象总结形成"——**缺批量抽象链路**：从 approved 概念集合自动归纳出本体类型建议
（含上位概念聚合、属性归纳、关系发现），现在只能逐条映射。
*落地设计*（P2）：「概念→本体类型」批量向导：多选 approved 概念 → LLM 聚类归纳 → 生成本体类型草案
（进候选本体识别队列复用审核流水线）。与 A3、C1 形成闭环：**词典是本体的最大候选源 → 抽取候选 → 规则转换 → 入库前预检**。

## 三、建议未覆盖、评估中新发现的不足

1. **F7 决策悬置**：「AI 建模产物进资料库 + 来源元数据」（已提案待拍板）与本批 B4/C1 是同一依赖链，
   建议合并为一个决策包，避免三次返工。
2. **candidate 积压无感知**：kb-b 入口隐藏后（09-11），审核积压只靠深链发现，无红点/计数（见 A3）。
3. **镜像落图队列无自动重试**：governance mirror_sync 指标显示 triples→图库存在水位差，但无补偿任务，
   积压靠人工发现。
4. **文件级冲突语义未覆盖**：MR 冲突检测是实体/关系级，同一源文档被两个分支修改的场景无版本树追踪。
5. **运维操作无保护**：库清理/恢复（如 09-11 手工操作）无自动化与二次确认框架，建议备份任务化
   （每日增量 + 清理前强制快照）。
