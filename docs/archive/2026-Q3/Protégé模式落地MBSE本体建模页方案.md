# Protégé 模式落地 MBSE 本体建模页方案

- 文档版本：v1.0
- 日期：2026-08-20
- 关联文档：`本体建模页面布局交互优化方案.md`、`知识图谱构建平台对标分析与优化方案.md`、`入库流程状态机审批策略与暂存分支设计方案.md`
- 参考：《Protégé / WebProtégé 本体建模产品流程与交互调研》（Protégé 与 WebProtégé 双引擎、流程主线、协作治理）

## 1. 背景与目标

MBSE 本体管理模块（KB-C「本体管理」页）目前以"单屏 + 左右分栏 + 约束图谱"为主：左侧实体/关系列表（已支持收起/搜索/维度过滤/批量操作/未实例化角标），右侧详情（已支持属性折叠、版本历史），中部约束图谱（已支持分层/分组/搜索命中高亮/拖拽）。

Protégé 作为本体建模的事实标准工具，其**核心范式没有过时**：把"建模 + 验证"编排成显式可操作流程，并且用"声明式建模 + 推理验证 + 双层级并存"让复杂本体**可见、可解释、可追溯**。本方案把其中最值得引入 MBSE 平台的模式落到本体建模页，分阶段实施。

借鉴两大主轴：
1. **流程主线化**：建模→定约束→推理校验→查询审视→发布→迭代，作为显式环节而非被动拼装的功能。
2. **可见性/可解释性**：`声明层级(Asserted) vs 推得层级(Inferred)` 双层级并存、反向引用(Usage)追溯、推理结论可解释。

## 2. 总体设计原则

- **不复刻 Protégé 的复杂配置**（如图形公理编辑、大规则语言的全面语法），只吸收其"稳健、主线清晰、可解释"的交互范式。
- **沿用现有技术底座**：`ontology_types`、`OntologyValidator`、约束图谱(renderOntGraph)、分支/合并/审核队列、实体审核流程，全部在其上增强，不另起炉灶。
- **落地优先级**：遵循"低风险纯前端先行、后端校验增强次之、协作治理最后"的节奏，与既有 P0/P1/P2 排期衔接。

## 3. 分阶段实施

### P0-1 反向引用 Usage（被谁引用）
- **问题**：本体详情目前只展示正向前置：类型自身属性、子类型、父类型、实例数。缺乏"**这个类型/属性/关系被哪些其他类型、哪些约束引用**"的反向视角，定位"删了这个会影响谁"很难。
- **方案**：详情区新增「引用 Usage」折叠块（复用属性折叠交互 `ont-att-` 模式）：
  - 该类型被作为其他类型的父类型/属性值类型/关系端点引用的条目；
  - 该类型的属性被哪些约束/规则引用；
  - 每条引用可点击跳转到对应类型并高亮。
- **落点**：前端 `renderOntDetail` 增 `usage` 块 + `ontData` 侧维护反向索引（或后端一次查询聚合）；纯前端可先用现有 `types/relations/binding` 数据计算，后端可选加 `/api/knowledge/ontology/types/{id}/usage` 聚合接口。
- 备注：TypeScript 侧无涉，改动集中在 `static/index.html`；若追加后端接口则改 `routers/knowledge.py`。

### P0-2 双层级并存：Asserted vs Inferred
- **问题**：本体一致性/约束校验目前是"静默通过或报错"，看不到"由约束推导出的隐含层级"。
- **方案**：
  - 约束图谱与实体树增加「声明层级 / 推得层级」两种渲染视角；
  - 推得层级由 `OntologyValidator` 全量校验后产出（非声明继承，而是由属性约束/关系规则**推导**出的父子/归属关系）；
  - 两视角差异高亮：仅出现在推得层级的边、与声明层级冲突的边（冗余/矛盾）用不同标记。
- **落点**：
  - 后端：`ontology_semantics.py` 的 validator 增加"推理产物导出"（`inferred_edges` 结构），或新建轻量推导函数；
  - 前端：图谱工具栏加「Asserted / Inferred / 对比」切换，对比态用橙色标差。
- 备注：这是本方案最核心的差异化能力，也是收益最大的一环；建议先出后端推导、再接图谱叠加。

### P0-3 推理结论解释 / 冲突定位
- **问题**：`validate_node/validate_relation` 只返回"不通过"，用户不知道因为哪条约束、哪个实例。
- **方案**：校验结果追加解释字段：命中约束、涉及实例、冲突原因（如"属性 X 必填 于类型 Y，实例 Z 缺失"）。校验失败可在图谱/详情上直接定位到相关节点与约束，供删除或修正。
- **落点**：后端 `OntologyValidator` 的失败路径携带 `explain`（约束名 + 断言内容 + 定位节点）；前端将校验失败以 toast/面板形式展示"原因定位"并可点击跳转。
- 备注：与已有的 `allowed_values`/方向校验天然衔接，改动小、收益直观。

### P1-1 约束表达式编辑器（即时校验 + 自动补全）
- **问题**：约束当前以 JSON 形式编辑，语法门槛高、无辅助、易出错。
- **方案**：将类型约束编辑升级为"约束表达式编辑器"：
  - 实时**语法/引用校验**（引用的属性、类型是否存在）；
  - **自动补全**属性名、类型名、关系类型；
  - 错误内联标红，并复用 P0-3 的"定位"能力。
- **落点**：前端新增或改造 `ontEditTypeById` 的约束编辑弹层；引用字典取自 `ontData.types/relations/binding`；校验实时调用现有 validator（防抖）。
- 备注：建议在 P0-3 解释层就绪后再做，保证"边写边校验、校验可解释"闭环。

### P1-2 批量重命名（联动约束引用）
- **问题**：目前类型改名是单点、且不追溯引用它的约束/关系端。
- **方案**：批量操作追加「批量重命名」——重命名后自动遍历并更新引用该类型的父引用、属性值类型、关系端点与约束中的名称；改名产生一条变更记录进入审计。
- **落点**：前端批量条加 "批量改名" 入口（复用 `ontBatch` 选中）；后端新增批量改名 + 引用联动事务，写入变更历史。
- 备注：与既有批量删除、未实例化角标同一操作区，交互一致。

### P2-1 实体级变更与快照回放
- **问题**：版本历史在分支/合并层级，未到"单实体维度的变更列表 + 任意时刻快照下载/回放"。
- **方案**：本体实体页增加按实体过滤的变更列表（谁、何时、改了什么）、快照对比与下载回放（复用版本历史与 `knowledge_commits`）。
- 落点：`static/index.html` 详情「变更/历史」区增强；后端复用既有 version/commit 基础设施。
- 备注：属于协作治理，放 P2。

### P2-2 讨论波纹 / Watch 订阅 / 权限分级
- **问题**：多角色协作时缺少"本条实体被谁质疑、有没有人在跟"的信号。
- **方案**：对齐 WebProtégé 协作范式——
  - 实体/分支上的**线程化讨论**（与本方案外的"评审备注线程"打通，见 P1 评审设计）；
  - **Watch 订阅 + 变更通知**；
  - 对齐为"查看者-评论者-编辑者-评审者"四级权限，与分支合并/审核队列衔接。
- 备注：与标注审核模块的评审员分配/备注线程设计相互印证，建议作为跨模块协作主线统一推进。

## 4. 与既有能力的衔接

| 本方案能力 | 复用的既有底座 |
|---|---|
| P0-1 Usage | 详情折叠交互、`ontology_binding`、类型/关系数据 |
| P0-2 双层级 | `OntologyValidator`、约束图谱 `renderOntGraph` |
| P0-3 解释定位 | `validate_node/validate_relation`、详情/图谱跳转 |
| P1-1 约束编辑器 | 既有约束编辑弹层、`ontData` 字典 |
| P1-2 批量重命名 | 批量操作区、变更历史 |
| P2-1 快照 | 版本历史、`knowledge_commits` |
| P2-2 协作 | 分支合并/审核队列、评审备注设计 |

## 5. 落地路径与验收要点

建议顺序：**P0-1 → P0-2 → P0-3 →（P1-1 依赖 P0-3）→ P1-2 → P2 项**。

- **P0-1 验收**：选任一被引用的类型，详情可列出"被谁引用"并可点击跳转高亮。
- **P0-2 验收**：图谱可在声明/推得/对比三视角切换，推得边与冲突差异有明确区分；推得层级与手工断言互不影响。
- **P0-3 验收**：构造一条必填/方向违规，校验失败给出约束名 + 涉及实例 + 冲突原因，并定位到图谱/详情。
- **P1-1 验收**：约束编辑器实时校验引用是否存在；输入属性名有补全；错误内联标红并可定位。
- **P1-2 验收**：批量重命名后引用的约束/关系端点同步更新；产生一条变更记录。
- **P2-1 验收**：实体级变更列表可按实体过滤，快照可对比/下载回放。
- **P2-2 验收**：实体可发起/参与讨论、可订阅并收到变更通知；四角色权限下读写行为符合预期。

## 6. 风险与规避

| 风险 | 规避 |
|---|---|
| 双层级推导在复杂约束下成本高、难收敛 | P0-2 先限定由现有 validator 能产出的有限推导边，再逐步扩展；推导结果本身标记"由约束推得"防止被误当声明 |
| 约束表达式编辑器范围失控 | 限定语法子集，不引入完整 DL 语言；错误校验复用现有 validator，避免双实现 |
| 批量重命名误伤引用 | 改名走"预览受影响引用清单 → 确认"两步，且写入变更记录可回滚 |
| 协作功能侵蚀核心建模稳定 | P2 项独立开关、默认低侵入，逐步灰度 |

## 7. 未纳入 / 刻意搁置

- 图形化公理编辑、完整 DL 查询语言（Manchester 全量）等 Protégé 重度能力——当前平台以 AI 建模为主入口，维护成本高于收益。
- 虚拟滚动：数据规模（~37 实体 / 866 关系）下收益低，保留为远期。
- 双层级仅服务"可见性/解释"，**不改变现有分支与幂等发布**语义，避免与审核队列/发布门禁相互干扰。
