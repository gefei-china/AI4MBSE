## 1. 文章核心方案解读

文章将设计知识库定义为"**结构化、可检索、可被 AI 消费的知识集合**"，由两类知识构成：

| 类别 | 内容 | 作用 |
|---|---|---|
| 设计方法知识 | 设计流程、设计准则、规则约束、最佳实践、模板方法 | 告诉 AI"该怎么做"以及**不可违反的规范**（规范约束源） |
| 设计资产 | 已有模型、可复用构件、设计方案、案例库、参数设计 | 告诉 AI"已有过什么成果"（增量设计源） |

16 条需求（FR-KG-1~16）落到六大模块与四个产品逻辑：

1. **知识获取引擎**（FR-KG-1/3）：多源接入 + NLP 抽取 + 消歧归一
2. **审核工作流**（FR-KG-2/8/10/11）：未评审/已评审分离、生命周期状态、来源追溯、软删除审计
3. **双库存储底座**（FR-KG-5/6/12/13）：向量库临时快速检索 + 图库权威底座 + 半自动转换 + 增量更新
4. **本体管理**（FR-KG-4/9）：可视化本体编辑、导入导出 SysML Profile、双向一致
5. **分支版本管理**（FR-KG-14/15/16）：三类分支、冲突分析、合并历史、回滚
6. **知识消费服务**（FR-KG-6/7）：SysML 双向映射、GraphRAG、影响分析、模型问答

四个产品逻辑：**"快与准"分级**（向量快、图库准，动态协同）、**"脏数据不过评审关"**（默认进未评审区）、**"增量而非全量"**（只更新差异）、**"闭环自增强"**（评审权威知识反哺 GraphRAG）。

核心架构规则——**评审×分支四象限正交治理**：

| 象限 | 允许性 |
|---|---|
| 未评审 + 开发分支 | 默认落点，脏数据隔离 |
| 已评审 + 开发分支 | 允许 |
| 已评审 + 发布分支 | 权威基线，只读，唯一被消费的基线 |
| **未评审 + 发布分支** | **禁止（被规则拦截）** |

数据流向：多源数据 → ①未评审+开发分支（默认入口）→ 评审通过 → ③已评审+开发分支 → 合并（冲突分析+人工评审）→ ④已评审+发布分支 → 消费 → 增量回流到 ①。

## 4. 主要不足（Gap 明细，按优先级）

### P0（治理闭环硬缺口，直接影响"权威基线可信度"）

#### G1 未评审数据可直通 release —— 四象限规则未落地 ★核心

- **证据**：[branch_repo.py](file:///c:/Users/gefei/WorkBuddy/2026-08-04-19-05-52/mbse_system/repositories/branch_repo.py#L255-L360) `resolve_merge` 发布语义分支将 dev 实体**原样复制**（含 `status`）到 release；[routers/branches.py](file:///c:/Users/gefei/WorkBuddy/2026-08-04-19-05-52/mbse_system/routers/branches.py#L212-L232) 审批时只检查冲突未解决，不检查实体审核状态。candidate（未评审）实体可进入权威基线，AI 建模默认只消费 release 分支（[rag.py](file:///c:/Users/gefei/WorkBuddy/2026-08-04-19-05-52/mbse_system/agent/rag.py#L169-L179)）→ 脏数据被 AI 消费，违反 FR-KG-15 与"脏数据不过评审关"。
- **影响**：权威基线质量失控，与文章最核心的机制相悖。

#### G2 v2g 确认入库不做已存在实体去重 —— 增量而非全量未实现

- **证据**：[vector2graph.py](file:///c:/Users/gefei/WorkBuddy/2026-08-04-19-05-52/mbse_system/vector2graph.py#L375-L455) `confirm_candidates` 对每个节点候选无条件 `gs.create_node` 新建；`name_to_id` 仅用于关系候选两端定位，不做节点去重。抽取时 `_disambiguate` 打的 dup 标记仅在前端警示，确认时仍会重复创建。
- **影响**：同一实体反复抽取 → 重复节点累积 → 图谱膨胀、消歧合并负担加重（FR-KG-3/12/13 均未闭环）。

#### G3 知识分类未建模 —— 文章核心定位缺失 ★核心

- **现状**：知识库只有"文档 + 图谱实体"两个层次，实体 `entity_type` 来自本体类型（需求/部件/功能/接口…），无"设计方法知识 vs 设计资产"这一知识类别维度；设计准则/规则约束没有结构化载体（glossary 是术语表不是准则库）；设计模板/案例库/参数设计无建模。
- **影响**：AI 无法区分"规范约束源"（必须遵守）与"增量设计源"（可参考复用），"既遵守规范、又基于成果增量设计"的产品目标缺少数据支撑。

#### G4 生命周期状态机缺"发布"环节

- **现状**：实体状态 candidate/reviewed/deprecated（[knowledge_repo](file:///c:/Users/gefei/WorkBuddy/2026-08-04-19-05-52/mbse_system/repositories/knowledge_repo.py)）；发布只体现在分支维度（release），实体层面无 published 标记/发布记录/发布时间；无生命周期分布统计。
- **文章**：原始切片 → 候选元素 → 审校 → 入库 → **发布** → 废弃，配合按状态过滤（FR-KG-8）与总览页生命周期分布。
- **影响**：无法回答"哪些知识已进入权威基线、何时发布、当前各阶段分布"，治理看板缺关键维度。

## 5. 优化方案设计

### P0-1 合并发布门禁：评审×分支四象限治理落地

> ✅ 已实施（2026-08-13）：`repositories/branch_repo.py` 新增 `pending_review_entities`/`_gate_error`，`create_merge_request` 创建即拦截、`resolve_merge` 审批硬门禁（返回 dict）；`routers/branches.py` 透传 `blocked_pending_review` + audit `merge_gate_rejected`；冲突检测排除 deprecated 实体。验证 45/45 + approve 冒烟 + UI toast 实测通过。

**目标**：candidate（未评审）数据永远进不了 release；发布走"评审通过 → 已评审+开发分支 → 合并 → 已评审+发布分支"唯一通道。

**后端**：
- [branch_repo.py](file:///c:/Users/gefei/WorkBuddy/2026-08-04-19-05-52/mbse_system/repositories/branch_repo.py) `create_merge_request` 增加目标分支为 release 时的**未评审实体检查**：`SELECT id,name FROM entities WHERE branch=? AND status!='reviewed' AND status!='deprecated'`，存在则在返回 `blocked_pending_review: [ids]`（**创建即拦截**，优于审批时兜底）。
- `resolve_merge` 发布语义分支前再加一层硬门禁（防御审批环节绕过）：任何 `status != 'reviewed'` 的实体不得复制进 release，违者返回错误并记录审计 `merge_gate_rejected`。
- [branches.py](file:///c:/Users/gefei/WorkBuddy/2026-08-04-19-05-52/mbse_system/routers/branches.py) `resolve_merge` 审批接口复用同一检查，返回 `{"error": "还有 N 个未评审实体（…），请先到标注审核完成审核"}`。
- 新增审计事件：`merge_gate_rejected`（记录被拦实体清单）。

**前端（分支管理页，保持现有面板风格）**：

### P0-2 v2g 确认入库增量对齐（去重 + 属性融合提示）

**目标**：确认候选时先对已有 reviewed 实体做同名/同类型匹配，提供"跳过（已存在）/新建/对齐更新"三种动作，杜绝重复节点（FR-KG-12/13）。

## 7. 明确不做 / 观察项

- **真图数据库（Neo4j）替换**：GraphStore 抽象已预留，但 SQLite 满足当前规模（千级实体），列为观察项——数据量 >5 万节点或需 Cypher 多跳查询时再切换。
- **OWL DL 推理器（HermiT/Pellet）**：当前 4 项简化推理 + SHACL 已覆盖核心校验场景；引入推理器属架构级决策，列为观察项。
- **文章 8 节私有化/国产化/信创**：属部署合规范畴，独立于知识管理功能设计，不在此方案范围。
- **总览页图谱缩略**：采用静态 top-N 渲染（复用 graph_entities），不做实时力导向重排，控制首屏开销。
