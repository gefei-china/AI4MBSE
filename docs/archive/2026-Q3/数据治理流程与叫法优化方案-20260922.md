# 数据治理流程合理性与叫法优化方案（含前端布局与交互）

> **时点**：2026-09-22 · 对象：知识中心「标注审核」页（kb-b）四站流程  
> **触发**：米爸反馈「候选批次→灰区裁决→冲突裁决→物化入图都不好理解，是实体抽取的标准处理流程与叫法吗？」  
> **方法**：全部结论基于当前代码实测（`15-kb.js` / `17-v2g.js` / `19-governance.js` / `21-ontology.js` / `routers/knowledge_parts/pipeline.py` / `vector2graph.py` / `entity_resolver.py`）+ 业界标准调研（KG 构建综述 MDPI Information 2024、record linkage clerical review、MDM survivorship 惯例、中文社区「抽取—融合—加工」三阶段法）。

## 0. 结论先行

**一句话**：这套治理流程的**骨架是对的**——顺序、分流闸、survivorship/lineage 都与业界实体解析（Entity Resolution）标准做法同构；问题出在**叫法全是实现视角的内部隐喻**、**UI 流水线暗示与真实数据流不符**、**批次维度被折叠隐藏**三点，导致"不好理解"。

| # | 判断                                 | 依据                                                                                                                |
| - | ---------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 1 | **流程骨架合理，不需要重排**                   | 验收→消歧→冲突→发布，与业界「抽取→审核→消歧→融合→发布」同构；融合闸三分流（自动合并/人工复核/直接新建）正是 record linkage 的 blocking→matching→clerical review 三段式 |
| 2 | **叫法是主要理解障碍**                      | 「灰区」是相似度阈值(0.62~0.92)的内部隐喻；「物化」在语义网语境另有所指（推理闭包）；「候选批次」是实现词（v2g=vector-to-graph）泄漏                                 |
| 3 | **一个更深的隐患：UI 暗示与数据流不符**            | 界面把「物化入图」画成终点站，但**实现里第 0 站点"确认"就已经建实体/建边入图**；灰区/冲突是"入图后修正"。用户的心智模型被 UI 带偏                                         |
| 4 | **建议叫法**：抽取审核 → 重复消歧 → 属性融合 → 确认发布 | 与需求书 FR-KG-2/3 措辞（归一、消歧、属性值对齐与融合）对齐，验收可对照；业界均有标准英文对应词                                                             |

**建议路径**：先做 P0 改名（纯文案层，半天）+ 管线总览条（1 天）；三栏工作台重排（P2，3~5 天）**排在 P1 数据链路跑通之后**——流程没真实数据流过之前，重排交互是空中楼阁。

## 2. 合理性评估

### 2.1 站对了的地方（不要动）

1. **顺序合理**。验收 → 消歧 → 属性冲突 → 发布，与 MDPI KG 构建综述的标准任务序（Knowledge Extraction → Entity Resolution & Fusion → Quality Assurance）及中文社区"抽取—融合—加工"三阶段完全同构。
2. **融合闸三分流是教科书做法**。auto_merge / review_queue / new_entity 对应 record linkage 的 match / clerical review / non-match 三分类（Fellegi–Sunter 框架）；阈值三段（≥0.92 自动、0.62~0.92 人工、<0.62 新建）是业界惯例的阈值带设计。
3. **survivorship + lineage 是 MDM 标准能力**。属性择优合并（幸存者规则）、`graph_edit_logs` 全程留痕、可撤销——比很多同类产品完整。
4. **人在回路覆盖完整**（FR-HIL-1 的"逐条确认、修改、拒绝"在四站都有落点）。

### 2.2 造成"不好理解"的四个根源

| #      | 根源                  | 例证                                                                                                                                          |
| ------ | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| **R1** | **UI 隐喻与数据流不符（最伤）** | 界面画成流水线、"物化入图"是终点站 → 用户以为最后一站才入图；实际 confirm 第 0 站就建实体建边（`knowledge_service.v2g_confirm` docstring："人工确认候选 → 图谱入库"）。用户会问"我怎么在第 1 站看到图里已有数据？" |
| **R2** | **实现术语泄漏到 UI**      | 「候选批次」（v2g = vector-to-graph 实现缩写）；「灰区」（相似度中间带的内部隐喻，业务用户无感）；「物化」（semantic web 里 materialization 指推理闭包，此处实为"合并发布"）                           |
| **R3** | **隐喻混杂**            | 同一界面混用三种隐喻：车站（第 0 站/终点站）、闸门（身份闸/字段闸）、工厂（原料验收/流水线收敛）。每种单看都通，拼在一起互相打架                                                                         |
| **R4** | **与需求书措辞脱节**        | FR-KG-3 要求「实体归一、实体消歧、属性值对齐与融合」、BR-5 要求「消歧、归并、拉齐」——UI 叫法与之对不上，验收时需要口头解释映射关系                                                                  |

### 2.3 顺带的两个交互问题（与叫法无关但同域）

1. **批次维度被折叠**：批次是贯穿四站的主线数据维度（每站都按批次过滤/确认），但批次选择器藏在「高级搜索」折叠区里且默认收起——用户常常不知道自己当前在看哪个批次的数据。
2. **无总览**：一次只看一站（fusNav 切 pane），四站各有多少待办、整体收敛到什么程度，界面上没有一个一眼可见的答案（`fus-n-*` 角标只有数字、无完成度语义）。

## 3. 业界对标与叫法建议（核心产出）

### 3.1 业界标准流程（调研结论）

- **KG 构建管线**（MDPI Information 2024 综述，§任务清单）：Data Acquisition → Knowledge Extraction（NER/实体链接/关系抽取）→ **Entity Resolution & Fusion**（含 conflict resolution）→ Quality Assurance → 存储。明确指出"抽取中的实体链接做好了，ER 这步可以省"。
- **Record Linkage / ER**（Fellegi–Sunter 框架，澳洲 AIHW 等权威实践）：Blocking → Matching → **Clerical Review（人工复核，对机器不敢判的记录对逐对裁决）** → **Survivorship（幸存者合并）**。这与本项目"融合闸→灰区→survivorship"一一对应——**流程是标准流程，只是没穿标准衣服**。
- **中文社区惯例**（百度智能云等）：知识图谱构建 = **「知识抽取 → 知识融合 → 知识加工」**&#x4E09;阶段；融合阶段含实体对齐、属性融合、冲突检测——恰好覆盖本工程第 1、2 站。
- **MDM 惯例**（Informatica/IBM）：Match → Merge/Purge → Survivorship Rules → Publication（发布）。

### 3.2 叫法映射表（建议采纳）

| 现 UI 叫法          | 实现本质        | 业界标准词                                  | 需求书措辞                | **建议 UI 叫法** | 一句话注解（挂 tooltip）                             |
| ---------------- | ----------- | -------------------------------------- | -------------------- | ------------ | -------------------------------------------- |
| 候选批次（第 0 站·原料验收） | AI 抽取结果人工验收 | Extraction Review / Clerical Review    | 待审核区（FR-KG-2）        | **① 抽取审核**   | "AI 从文档里抽出的知识候选，逐条验收：确认、修改或驳回"               |
| 灰区裁决（第 1 站·身份闸）  | 重复记录对人工判定   | Entity Disambiguation / Merge Review   | 实体消歧（FR-KG-3）        | **② 重复消歧**   | "判定两条记录是否指向同一个实体；合并时属性自动择优"                  |
| 冲突裁决（第 2 站·字段闸）  | 属性值矛盾处置     | Conflict Resolution / Attribute Fusion | 属性值对齐与融合（FR-KG-3）    | **③ 属性融合**   | "同一实体的同一属性出现矛盾值时，逐字段裁定取值"                    |

| （缺失）             | 抽取管道        | Knowledge Extraction                   | 知识抽取                 | **⓪ 知识抽取**   | 在管线总览中补上第 0 步——现在四站从"审核"开始，抽取这一步在资料库页，心智模型断头 |

**命名原则**：①每个名字都是一个动宾结构，回答"这一步做什么"；②顺序念出来就是一句话："**先审核抽取结果，再消重，再融属性，最后发布**"；③与需求书 FR-KG-2/3 的词根（审核、消歧、融合、合并同步）一一对得上，验收不用翻译。

### 3.3 标杆产品对标（2026-09-22 补充调研）

两张业界最权威的 MDM 治理流程与本项目四站逐站对照：

**SAP MDG Consolidation**（官方流程：Select → Standardize → **Match** → **Best Record Calculation** → **Validate** → **Activate**，全程 audit trail）：

| SAP MDG 步骤                  | 做什么                                     | 本工程对应                             | 对标结论                            |
| --------------------------- | --------------------------------------- | --------------------------------- | ------------------------------- |
| Standardize                 | 地址/名称规范化                                | 词典归一（glossary 自动归一 + 高置信挂靠）       | ✅ 有，且做成了自动闸                     |
| **Match** + Match Review    | 规则+相似度找重复组 → **人工复核 match groups**      | 融合闸 Blocking→四路相似度→三阈值 + **灰区裁决** | ✅ 同构；SAP 也把"机器不敢判的"交给人工         |
| **Best Record Calculation** | 按 survivorship 规则（来源可靠性/新近度/字段完整度）算最佳记录 | **survivorship 择优 + 属性融合站**       | ✅ 同构；SAP 的规则类型可借鉴为阈值配置项         |
| **Validate**                | 校验能否激活                                  | 本体校验 + ingest_gate 门禁             | ✅ 有，位置不同（我们在确认时，SAP 在激活前）       |
| **Activate**                | 进入 active 区供使用                          | **确认发布（物化入图）**                    | ✅ 同构；SAP 叫"激活"——比"物化"更直白，佐证改名建议 |

**Informatica MDM**（官方流程：Land → Stage → Load → Tokenise → **Match** → **Consolidate** → **Publish**）：

| Informatica 步骤             | 本工程对应                 |
| -------------------------- | --------------------- |
| Land / Stage / Load        | 文档上传 → 解析/分块/向量化（资料库） |
| Tokenise（分块配键加速匹配）         | 融合闸 Blocking（分块召回候选）  |
| **Match**                  | 融合闸四路相似度              |
| **Consolidate**（重复合并、择优取值） | 灰区裁决 + survivorship   |
| **Publish**（批处理完成后发布到下游）   | 确认发布                  |

**其它领域标杆**（交互参考）：

- **OpenRefine Reconciliation**：候选列表 + 匹配置信度 → 人工 **choose match / create new** ——与第 0 站"确认/新建/跳过"（dup_action）逐项对应；
- **Label Studio / Prodigy**（HITL 标注审核）：accept/reject/fix 队列 + **键盘快捷键流 + 裁决后自动跳下一条** ——方案 B 交互升级的直接参照；
- **Collibra / Alation**（数据治理平台）：stewardship 任务收件箱（按角色分派、SLA、催办）——多角色协作场景可后续借鉴；
- **Wikidata**：statement 级引用溯源 + 机器人辅助例行审核——对应本工程的 chunk 溯源与 reflow 回流。

**对标总结**：本工程的**能力覆盖面不输上述产品的对应环节**（闸门分流、survivorship、lineage、溯源、门禁全有）；差距集中在两点——①叫法是自造隐喻而非业界通用词（SAP 用 match/survive/activate，Informatica 用 match/consolidate/publish，本工程用"灰区/物化"）；②总览与批次维度的呈现（SAP 每步有 process-step specific KPI 可视化，本工程只有数字角标）。这正好印证 §4 的改造方向：**改名 + 总览条是向业界收敛，不是发明新东西**。

### 3.4 必须同步修正的一处**事实性误导**

「确认发布」若继续叫"物化入图"并画成入图前最后一关，就是在向用户承诺一个与实现不符的模型。两个选择：

- **方案一（改叙述，零代码）**：在第 0 站面板加一句明示："确认后知识即入图（可在后续环节修正）"，终点站改名"确认发布"——入图是**分批即时**的，第 0 站确认只是生效单位的一部分，终点站是**批次收口**。
- **方案二（改实现，大动）**：把 confirm 改为"入暂存区"，到终点站才真正建实体——**不建议**。这会推翻 survivorship/融合闸现有时序，重构成本高、收益只有概念纯洁性。

采纳方案一。

### 3.5 深挖：「第 0 站确认即入库」合理吗？行业怎么做？（2026-09-22 追加核查）

**先把事实核准**（实测 `vector2graph.py:884/969/1033`、`repositories/branch_repo.py:1028`、`services/knowledge_service.py:227`）：

```
第0站确认 ──► 实体/关系写入 personal 分支                     ← 个人工作区（create_node/create_edge
                │                                               显式传 "personal"，确认打点
                ▼                                               kind=import, branch=personal）
        MR：冲突分析 + 人工评审 ──► dev 分支                    ← 集成区（branch_repo._merge_commit）
                ▼
        MR：评审 ──► release 分支                              ← 准发布区
                ▼
        triples 审核 → commit（graph_stored 0→1）──► 图数据库     ← 消费区（"三元组唯一图写入源"，
                                                                mirror_sync 指标监控水位差）
```

> ⚠️ **分支落点修正（2026-09-22，米爸纠正 + 代码证实）**：confirm 的落点是 **`personal` 分支**（`vector2graph.py:969` `gs.create_node(..., "personal", ...)`、`:884` 建边同理、`:1033` 注释"确认入库提交打点 kind=import, branch=personal"）。`schema.py:171` 的 `branch TEXT DEFAULT 'dev'` 只是**表默认值**，实际写入路径显式传 personal —— 初版分析被这个 DEFAULT 误导，特此更正。整条链路是完整的 **personal → dev → release → 图库** Git flow。

**结论：不是"一步到位入库"，而是 Git 式多层——第 0 站确认写的是个人分支，不是集成区更不是发布区。** 最终生效要过两道闸：MR 人工评审（FR-KG-15 本来就要求"合并到发布必须冲突分析+人工评审"）+ triples commit 落图。

**行业对照**——两种主流模式，本工程各占一半：

| 模式            | 代表                                                          | 做法                        | 本工程对应                                                         |
| ------------- | ----------------------------------------------------------- | ------------------------- | ------------------------------------------------------------- |
| **Git/代码评审式** | Git flow、Wikidata（即时生效+回滚）                                  | 写入工作分支无需审批，**合并到主干才需要评审** | confirm 入 personal = commit 到个人 feature branch；MR = PR review |
| **MDM 两段式**   | SAP MDG（Validate→Activate）、Informatica（Consolidate→Publish） | 生效区（active area）之前必须有人工关  | release + 图落库 = Activate/Publish                              |

即：**"确认即入个人工作区"在 Git 模型里天经地义；"最终生效前有人工关"本工程也有**（MR + 落图）。混合模型对"增量持续流入 + 需要人的即时反馈"场景是合理折中——比 SAP 那种每条都过 change request 快得多，比纯 Wikidata 式先写后修多了发布闸。⚠️ **注意（2026-09-22 米爸纠正，代码证实）**："即时"只到**个人分支可查**为止——`agent/rag.py:63` 明确「消费侧：默认只查已发布(release)分支」，即 **AI 建模 / 问答（RAG）只消费 release**；知识从确认到进入 AI 消费视野的完整链是 personal→dev→release 全部 MR 评审完毕。⚠️⚠️ **AI 建模链路再修正（2026-09-22 米爸第二次纠正，代码全部证实）**：上一版说「AI 建模批次确认后自动发起 personal→dev 发布 MR」**不对**——`ingest.draft_flow` 配置在 settings 表中**不存在**（`config.as_bool(...,False)`），门禁**从未启用**，自动 MR 从未发生。**真实 AI 建模链路**（每环节都有代码）：
> ① AI 生成 V2 源码（`sysml_versions`）→ ② AI 建模页面内归一/消歧/校验（norm_apply + checker.jar）→ ③ **人工点击** push-zhiyuan（闸口②，`norm_apply.py:471`）把 V2 源码写入**智源建模软件**（国产 MBSE 工具，`zhiyuan_client.py` 279 行 HTTP 客户端，先语法检测后覆盖导入）→ ④ **人工发起** pull-ingest（`/api/knowledge/sysml/pull-ingest`，`pipeline.py:942`）从智源拉取建模数据 → **直接转三元组 → 存个人分支图库**（`target_branch` 默认 personal）。
> 注意 ④ 的注释原文：「后端编排全程直通（候选化→融合闸→自动批准→落图），**不产生数据治理审核面板待办**」——**智源拉取链路绕过治理四站**，分支中的数据以三元组形态进入（米爸：「分支中的数据就是按照三元组的形式呈现的，具体数据落到图数据库」）。治理四站服务的是**文档抽取 / 对话回流**等其它来源。

**仍然存在的三个真实风险**（如实列出，不粉饰）：

1. **个人分支内脏读窗口**：personal 分支内确认即被同分支 RAG 检索到，若该条后来在灰区被裁决"应合并"，中间态已被消费过一次。Git 模型固有属性，靠 lineage 撤销兜底——但 UI 应展示"该数据曾经历过的裁决"。
2. **行级 vs 批次级粒度混淆**：confirm 是行级入图，终点站是批次级 survivorship 收口——两个粒度在 UI 上没有区分，是"物化入图"让人费解的另一半原因。
3. **水位差**：审核通过但未落图（graph_stored=0）期间，关系库与图库不一致——已有 `mirror_sync` 治理指标监控，需保持盯着。

**对 UI 的推论**：不用改时序（方案二依然不建议），但第 0 站的说明条应写成——  
「确认后知识进入**你的个人分支**（图谱工作区可切换查看）；**AI 建模 / 问答默认只消费 release 分支**——须经 MR 评审合并（personal→dev→release）后才进入 AI 消费视野；写入图数据库由三元组 commit 驱动（全程可追溯、可撤销）」。  
> 已按此实施到 index.html 抽取审核面板说明条（AI 批次确认后由 ingest_gate 自动发起 personal→dev MR，文档批次留人工）。

### 3.6 「确认即入图，治理在图上修」——这个模式行业有先例吗？（2026-09-22 追加核查）

**先厘清「图谱」的双层歧义**（实测）：

| 层 | 载体 | confirm 后 | 治理操作（归一/消歧/融合） |
|---|---|---|---|
| **图模型层**（逻辑图） | 关系库 `entities`/`relations`（分支化，主键含 branch） | **✅ 即入**（personal） | **全部在这层做**：灰区合并 = `UPDATE entities SET properties/status`（`entity_resolver.py:234/245/378`），纯关系库行操作 |
| **图数据库层**（物理图库） | Fuseki/pyoxigraph（`triples` commit 镜像） | ❌ 不入（`graph_stored=0`） | **治理站代码零处引用 Fuseki**；图库由 triples commit 单向驱动，只读消费 |

即：**确认后进入的是"分支化的图模型"（关系库承载），后续归一/消歧/融合都基于这个模型修正；真正的图数据库是 commit 之后的只读镜像**。「图谱」一词在 UI 上没有区分这两层，是理解障碍的又一根源。

**这个模式行业有没有？有，且能点名：**

1. **SAP MDG「Consolidation of Active Records」**——官方流程，与"先入后修"**逐字对应**：对**已激活**的数据再次跑 Select→Match→Best Record→Validate→Activate，官方策略就叫 "Improve best record" / "Remove duplicates"。即 SAP 明确支持"已生效数据持续再治理"，与本项目灰区/冲突站同构。
2. **Salesforce Duplicate Jobs**——记录**先创建**，后台异步跑匹配识别重复，人工/自动事后合并。CRM 行业的"先入后修"标准实现。
3. **Wikidata**——编辑即时生效（写后修），靠版本历史、回滚机器人、社区复核兜底。
4. **Databricks Medallion（bronze→silver→gold）**——"先落库再逐层炼"的现代数据平台主流架构，本工程的 候选→personal→release→图库 与之同构。

**但也要说清另一面**：抽取型 KG 的主流管线（LinkedIn KG、Google KG、Microsoft GraphRAG indexer）是**入前 ER**——extract→resolve→load 一次成型，图里永远是"干净"的。本工程实际是**混合**：融合闸在 confirm 时做了一次入前消歧（auto_merge/灰区分流/新建三分流），灰区/冲突站是入后修。两种时序的取舍：

| | 入前 ER（管线型） | 入后修（本工程/SAP active records） |
|---|---|---|
| 适合 | 批量一次性构建、数据不再变化 | **增量持续流入、AI 抽取质量参差、需要人即时反馈** |
| 图中数据质量 | 永远干净 | 有中间态（脏读窗口），靠 lineage/撤销兜底 |
| 延迟 | 批次级停等 | 个人分支即时可查；进入 AI 消费视野仍需 MR 到 release |

本工程的场景（文档持续上传 + AI 抽取 + 设计师即时问答消费）属于"增量持续流入"，选入后修 + 融合闸前置兜底是**合理选型**——前提是治理队列真的被运营（这正是 348 条 pending 暴露的问题：模式合理，但治理动作至今零次发生）。

**分支化图模型的标杆**：**Palantir Foundry Ontology**——pipeline branch → ontology branch → proposal → review → merge（writeback），是"分支化本体/图 + 提案评审合并"的最著名产品实现，与本工程 personal→dev→release + MR 同思想。Stardog 的 named graphs / Neo4j Fabric 提供的是物理分层，粒度不如 Foundry 的分支语义。

**结论**：①"确认进图模型、治理在图模型上修"**有官方级先例**（SAP MDG active records consolidation、Salesforce Duplicate Jobs）；②主流抽取型管线是入前 ER，本工程是混合（闸前置 + 事后修），对自身场景选型合理；③图数据库层与治理解耦、作为 commit 镜像——这是 CQRS 式读优化，也是 lineage 可撤销的物理基础；④UI 必须把"图模型（已确认，可修正）"与"图库（已发布镜像）"两种状态区分呈现——`graph_stored` 就是现成的状态字段。

**概念三层澄清（米爸追问「图模型是不是本体」）**——实测数据（2026-09-22）：

| 层 | 是什么 | 载体 | 数据量（实测） | 写入时点 |
|---|---|---|---|---|
| **L0 本体 / Schema** | **类型定义**：有哪些类别的实体/关系/属性、取值约束 | `ontology_types`（entity 28 / relation 13 / attribute 11）+ OWL 导出 + SHACL 约束 | 52 个类型 | 本体管理页定义、Profile 导入——**与抽取/确认流程无关，先于一切实例存在** |
| **L1 逻辑知识图谱（实例图）** | **具体实例**："宽带载荷"、"转发器"这类一个个实体/关系/属性值，分支化 | `entities` / `relations` / `triples`（主键含 branch） | 184 实体 / 133 三元组 | **第 0 站确认那一刻**（personal 分支，即刻可被图谱工作区/RAG 消费） |
| **L2 物理图数据库** | RDF 三元组镜像（消费侧） | Fuseki / pyoxigraph（`graph_stored` 标记） | **133 条三元组仅 25 条 graph_stored=1、108 条=0** | triples 审核 → **commit**（批次收口，即原"物化入图"站） |

类比：**L0 本体 = 类定义（Class），L1 图模型 = 对象实例（Object），L2 图数据库 = 序列化存储**。所以"图模型"不是本体——本体是 L0 的类型系统，图模型是按本体约束装载了实例的 L1。而"什么时候进知识图谱"取决于问的是哪层：**L1 在确认那一刻进，L2 在三元组 commit 那一刻进**。25/108 的水位差证明两层是真实分离的——当前 Fuseki 里只有 25 条三元组，而 L1 已有 184 个实体、348 条候选待审。

**UI 推论（补强）**：总览条除四站外应加"发布水位"段（graph_stored 1/N），让"L1 已确认多少、L2 已落图多少"一眼可见——这就是 `mirror_sync` 治理指标的前端化。

**两问两答（米爸 0922 追问）**：
- **Q：三元组核实后就直接入个人分支图谱吗？** A：不。核实（approved）只是审核状态变更；**commit 才把 approved 三元组反写为实体/关系**（进 personal 分支图模型）。实操：审核通过 → commit（前端 tripleAct 通过后自动触发；batch-review 后需手动）。Fuseki 物理图库另由 graph_db sync 独立驱动。
- **Q：确认发布针对什么数据、发布到哪里、和分支合并是一回事吗？** A：针对"批次维度的剩余候选"，以指定消歧策略重放 confirm；**不是发布动作，也与分支合并（MR personal→dev→release）完全不是一回事**——MR 是分支间发布（RAG 消费的前提），确认发布只是图数据批次收口。两者分属图数据层与分支层。

**形态视角的三个要点**（做 UI 呈现时值得显性化；第 3 条按三元组唯一写入源修正）：

1. **候选阶段没有图身份**——它只是一行文本+JSON，这正是第 0 站编辑候选可以随意改名改类型的原因；确认那一刻才"变身"为图节点。UI 上可以把这个转换点做出来（确认前显示"未定身份"，确认后显示图谱位置）。
2. **灰区/冲突存的是元数据（对/矛盾），不是知识本身**——裁决动作改的是 `entities` 侧，这两张表是裁决依据与台账。
3. **图库是镜像不是源头**——source of truth 在关系库的分支体系里，图库由 `triples` commit 单向驱动。这意味着"撤回"永远可做（分支回滚 + graph_stored 重置），这是 lineage 可撤销承诺的物理基础。

**补充：「分支图谱」的物理形态——不经序列化，行分区 + 账本（2026-09-22 追加核查）**

> 回应问题：「L1 必须经过序列化才进分支图谱吗？」实测：**不需要，L1 的当前态就是结构化行，序列化不在它的进出路径上**。

- **主存储**：`entities`/`relations` 结构化行 + `branch` 列（confirm 实际写 personal）——分支图谱的"当前态"就是这些行，查询/检索直接 `WHERE branch=?`。
- **版本账本（有 Git 的形，非 Git 的实）**：`knowledge_commits`（`id`/`parent_id`/`branch`/`kind`/`changes`/`snapshot`）+ `branches.head_commit` 指向链尾（实测 593/592/595）。但 **`changes` 只是涉及的实体 id 增量清单**（如 `{"entities": ["S-f6499a05", ...]}`），**`snapshot` 是轻引用**（39 字节级，非全量图快照）；回滚走 `merge_requests.prev_release_snapshot`（MR 级 id 清单），按清单反向操作行——**当前态永远以行分区为准，账本只服务审计与回滚**。
- **序列化只发生在三处**：①账本打点（轻量 JSON）；②MR 回滚快照（id 清单）；③L2 发布时 RDF 序列化进 Fuseki。**L1 的进与出都不经过序列化。**

**两种合法架构的对照**（"序列化后才进分支"的理解对应后者，并非错，是另一种实现）：

| | 行分区式（本工程） | 序列化提交链式（TerminusDB / Dolt / Git 式版本化图库） |
|---|---|---|
| 当前态存储 | 结构化行 + branch 列 | 序列化 commit 链（快照/delta），checkout 展开 |
| 查询 | SQL 直接 `WHERE branch=?` | 需解析链或物化视图 |
| 分支/合并语义 | 自研（`_merge_commit` 手写） | **原生**（diff/merge 是库能力） |
| 历史/回滚 | 账本 + id 清单（较薄） | **原生**（回到任意 commit，语义完整） |
| 写入前序列化 | 否 | 是 |
| 实现复杂度 | 低 | 高 |

选型判断：本工程取"行分区 + 账本"换实现简单与查询直快，代价是分支/回滚语义自研且较薄（`_merge_commit` 手写、回滚仅 MR 级）。若未来分支操作复杂度上升（跨分支 diff、原子多分支事务），TerminusDB/Dolt 式"版本化图库"是升级方向——但那是一次存储层重构，当前不值得。

### 4.3 方案 B：三栏治理工作台（P2，3~5 天，**排在数据链路跑通之后**）

```
┌─────────────┬──────────────────────────────┬───────────────┐
│ 管线 (左栏)  │ 工作区 (中栏)                  │ 上下文 (右栏)   │
│             │                              │               │
│ 当前批次卡片  │  当前阶段条目列表/裁决卡片流      │ 选中项详情：     │
│ ⓪抽取  3 批  │  ┌────────────────────────┐  │ · 来源文档+原文chunk │
│ ①审核  ▓▓░ 8 │  │ 条目 · 类型 · 置信度      │  │ · 重复候选对照      │
│ ②消歧  ░░ 12 │  │ [确认] [编辑] [驳回]      │  │ · graph_edit_logs  │
│ ③融合  ░░ 5  │  └────────────────────────┘  │ · 图谱位置预览      │
│ ④发布  ✓    │  批量操作底栏（常驻）            │               │
└─────────────┴──────────────────────────────┴───────────────┘
```

- **左栏竖向 stepper** 替代横排 chip：每段徽章（待办数）+ 完成度环；点击切换中栏内容；批次维度在左栏顶部选择、全局生效；
- **中栏**复用现有 renderTable/卡片流（`v2gRenderTable`、`dup-panel`、`conflict-panel`、`fus-confirm-body`），只是挂载点重排；
- **右栏**把现有"来源查看"（`v2gViewSource`）与 lineage 信息从弹窗改为常驻面板——裁决时**并排看证据**，不用开开关关；
- **交互升级**：键盘流（j/k 移动、1=确认 2=驳回 3=转人工）、裁决后自动跳下一条、批量操作底栏常驻；
- 工作量评估：前端为主（复用全部现有 API），3~5 天；**前置条件**：P1 数据链路已跑通、有真实批次流转数据可测。

### 4.4 明确不建议做的

- **不改后端阶段结构**（不把 confirm 改成暂存制）：现有"确认即入图 + 事后修正"模型与 survivorship 时序耦合深，重写风险大收益小（见 §3.4 方案二）。
- **不引入新隐喻**：不再加"闸/站/舱/池"类比喻，统一用"审核/消歧/融合/发布"动宾词。
- **不把术语词典搬回治理页**：2026-08-31 已归位本体模型页，保持。
