# P1-1 可行性验证报告：system 本体按需加载

> 日期：2026-10-11　方式：**不落库可行性验证**（只读生产库，拆分只在内存演算）
> 结论：**建议做，但不是"按需加载"，而是"按结构装配 + 按段裁剪"** —— 理由见 §4
> 复现：`./.venv/Scripts/python.exe -X utf8 tools/verify/_probe_sys_split.py`

---

## 1. 一句话结论

原本设想的方案是"基础段 + 按需段（工具按需取回）"，验证后发现**这条路走不通**（§3），
但验证过程暴露了一个**更严重且已在生效的缺陷**：流式路径正在**无脑腰斩 Agent prompt，砍掉 74~82%**，
把唯一的语法权威（`## 输出示例`）整段切掉（§2）。

**因此建议改为：按段结构装配（段级白名单 + 段级预算），而非按需加载。**

---

## 2. 最重要发现：流式路径已在"无脑截断"，且砍掉了最关键的段

`common.py:112` 定义 `_AGENT_ROLE_CAP = 1200`，流式路径调用
`_build_role_block(agent_def, cap=_AGENT_ROLE_CAP)`，
而该实现是**纯字符截断**（`prompt.py:245`：`raw[:cap] + "…"`）。

实测后果（`活动图生成`）：

| 项 | 值 |
|---|---|
| 完整 system 本体 | 5956 tok |
| 截断后 | **1098 tok（-82%）** |
| 截断点落在 | `## 工作流程` 第 3 条中间（`将顶层活动与各步骤组织为嵌套的 actio…`） |
| 被整段切掉的部分 | **`## 约束`（906 tok）、`### 视图规范参考`（844 tok）、`## 输出示例`（2309 tok）** |

8 个视图 Agent 的截断降幅：

| Agent | 完整 tok | 截断后 tok | 降幅 |
|---|---|---|---|
| 活动图生成 | 5956 | 1098 | **-82%** |
| 需求视图生成 | 3403 | 1092 | -68% |
| 参数视图生成 | 4110 | 1061 | -74% |
| 状态机视图生成 | 3021 | 1075 | -64% |
| 顺序视图（时序图）生成 | 2820 | 1078 | -62% |
| 交互视图（IBD）生成 | 2834 | 1085 | -62% |
| 结构视图生成 | 2450 | 1082 | -56% |
| 用例视图生成 | 2361 | 1085 | -54% |

**这解释了为什么 system 本体占用与实际体验不匹配**：
省下的 token 是"把最有约束力的部分删掉"换来的。

> ⚠️ 这是**当前生产行为**，不是本次引入。之所以一直没被发现：
> `verify_sysml_baseline_cases.py` 只校验 L0 卡内容，**不校验 Agent prompt 是否被腰斩**。

### 落地要求（硬约束）

新装配器必须保证：**`## 输出示例` 与 `## 约束` 永不被截断**。
`## 输出示例` 是这些 Agent 唯一的语法权威（prompt 里明写"语法形式以【输出示例】为唯一依据"），
砍掉它 = 模型自由发挥 = 回到"每轮重复犯同样的语法错"的老问题（v2_constraints 模块注释里的原始事故）。

---

## 3. 为什么"按需加载（工具取回示例）"走不通

假设把示例/规范挪进"按需段"，让 Agent 调工具取回。三个否决理由：

| # | 理由 | 证据 |
|---|---|---|
| 1 | **模型一次性输出，没有"第二次机会"** | `prompt.py:164` 要求"在正文末尾输出完整代码块"；prompt.py:28（活动图）明写"一旦开始输出就持续写到结束"。示例必须在**生成前**在场 |
| 2 | 这些 Agent **`kb_required` 多数为 0 / L0**，无检索习惯 | `活动图生成`：`hil_level=L0, kb_required=0`。指望它主动调工具取示例，与 L0 定位冲突 |
| 3 | **新增"取示例"工具 = 新增失败模式** | 取不到就退化成无示例生成 ⇒ 比现在更差。而现在示例是**确定必然在场**的 |

⇒ **按需加载方案否决。**

---

## 4. 推荐方案：按段装配（段级白名单 + 段级预算）

### 4.1 段名契约（8 个视图 Agent 实测**完全一致**）

```
职责 / 输入 / 输出 / 工作流程 / 约束 / 视图规范参考 / 输出示例
```

**⚠️ 落地硬坑（已实测踩到）**：Markdown 写法**不统一**，且是 **mixed**：

| Agent | 写法 |
|---|---|
| 活动图生成、需求视图、IBD、结构、用例 | `## 职责`（二级+空格） |
| 参数视图、状态机、顺序视图 | `#职责`（一级+无空格），但 `## 视图规范参考` 又是二级 |

首版解析器正则 `#{2,3}\s+` ⇒ **3 个 Agent 整段解析为空**（Q2 表里"全 0"就是这个原因）。
⇒ 新解析器必须容忍两种写法，且门禁要**逐个覆盖 8 个 Agent**（否则半数静默失效，
与刚修的压缩锚点事故同类）。

### 4.2 装配规则

| 优先级 | 段 | 处理 |
|---|---|---|
| P0 必留 | 职责 / 输入 / 输出 | 全量，长度可控（合计 3.3k tok / 8 Agent） |
| P0 必留 | **约束** | 全量（语法硬约束，砍了必犯同样的错） |
| P0 必留 | **输出示例** | 全量或按 `输出` 段的元素清单**裁剪到相关子集** |
| P1 可裁 | 工作流程 | 超预算时保留，压缩比最低的裁剪对象 |
| P2 可裁 | 视图规范参考 | 与示例高度重叠，可整段留占位 |

### 4.3 预期效果（以活动图生成实测）

| 方案 | system 本体 | 叠加 L0 卡(1979) | 相对现状 |
|---|---|---|---|
| 现状（无脑截断 1200 字符） | 1098 tok | 3077 tok | 基线（**但丢了示例**） |
| 全量下发 | 5956 tok | 7935 tok | +149% |
| **段级装配（必留段全量）** | **~4700 tok** | **~6680 tok** | +117% vs 现状 |

**注意：方案会让 token 比现状高**——因为它**把被砍掉的示例和约束还回去**。
这不是倒退：现状是"省 token 但产出质量受损"，方案是"多花 token 换正确率"。
若要同时控 token，走 §5 的 P1-2（示例按元素清单裁剪）。

## 6. 本次验证数据一览（全部实测）

```
L0 硬约束卡                     1979 tok（共享注入）
Agent system 本体合计          36624 tok（27 个 active）
8 视图 Agent 合计              26955 tok
  ├─ 职责 1272 / 输入 2939 / 输出 11831 / 工作流 2500
  └─ 约束+规范+示例            20145  ← 砍掉这 74% 就是现状
Agent 自带「约束」段与 L0 卡重复率  0%   ⇒ 二者互补，都不能删
```

**"约束段与 L0 卡重复率 0%"是一条重要负面结论**：
说明 L0 卡不能替代 Agent 自带约束，反之亦然。想省 token 不能从这里下手。
