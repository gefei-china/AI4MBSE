## 1. 六层成因（每层都有实证，不是推测）

### L1 `nightly-evals`：评测脚本硬编码本机绝对路径（既有，2026-10-07 起）

```
FileNotFoundError: [Errno 2] No such file or directory:
  'C:\\Users\\gefei\\WorkBuddy\\2026-08-04-19-05-52\\mbse_system'
```

`tests/manual_verify/eval_intent_routing.py` 第 17 行写死本机路径 + `os.chdir(ROOT)`，
Linux runner 必崩。改为从 `__file__` 向上两级推导（与 `tools/verify/*` 同写法）。

### L2 `tests-and-guards`：pytest 的 `test_p4_team_direct_notice_is_persisted`（本轮引入）

**判定方法（关键）**：对比两次 run 的失败**步骤号** ——
`88317a5` 挂 step **7**（说明 step 6 pytest 当时能过），`fcaeba2` 挂 step **6**
⇒ 是本次改动引入的，不是既有。

根因：测试锚**展示文案** `src.find('已定向到团队成员')`，而我在 54219fb 把文案改成
「（团队路由）主 Agent「Y」将本次请求定向给成员「X」」——
功能没坏、反而更准确（补上了主 Agent 是谁），但文案一变 `idx=-1`。
改锚**代码结构不变量**（`_subj_note` 邻近必须同时有 `exec_notices.append` 与 `"delta": _subj_note`）。

**变异自证**：删掉 `exec_notices.append(...)` ⇒ pytest rc=1 且报的正是该断言。

### L3 G0 静态哨兵：判据的**跨函数误报**（既有，2026-10-07 起）

```
FAIL G0 无「模块别名被遮蔽」（扫描 92 个文件）
  | agent/pipeline_parts/tools.py:2012 _exec_tool_call_impl 遮蔽 _h   (×5)
```

`danger` 集合把**全文件所有函数**的 import 名并成一个，再给**每个** scope 用：

```python
danger = _imported_names(tree)
for fn in fns:
    danger |= _imported_names(fn)      # ← 全文件合并
for scope in [tree] + fns:
    _shadow_sites(scope, danger)       # ← 每 scope 都用这个合并集
```

`_hil_gate` 有**函数局部** `import hashlib as _h`，于是 `_exec_tool_call_impl` 里
`for _i, _h in enumerate(_top, 1)` 的 `_h`（本函数局部循环变量）被判成"遮蔽模块别名"。

改为**分两层**：模块作用域只用模块级；函数作用域 = 模块级 ∪ **该函数自身**。

**变异自证（四形态新旧对比）**：

| 例 | 形态 | 旧 | 新 | 期望 |
|---|---|---|---|---|
| m1 | 函数内绑定遮蔽**模块级**别名 | RED | RED | RED ✅ |
| m2 | 正常 import 后立即用 | GREEN | GREEN | GREEN ✅ |
| m3 | **别的函数**的局部 import 与本函数循环变量同名 | **RED** | **GREEN** | GREEN ✅ ← 误报消除 |
| m4 | 同函数内绑定遮蔽**自身** import | RED | RED | RED ✅ |

### L4 `verify_llm_context_guard`：夹具 8 列 + 一个**真实产品崩溃**

两处夹具缺失（`api_key` / `context_window`）让 [7] 段验 LLMRouter 的断言跑不到。

但剥到最里面是**真缺陷**：

```python
mt = max_tokens if max_tokens is not None else cfg.get("max_tokens", 4096)
```

`dict.get(k, default)` 的默认值**只在键不存在时生效**。provider 的该列常常
**存在但为 NULL**（新建 provider 没填 / 迁移补列留空）⇒ `.get` 返回 `None`
⇒ 紧随其后的 context_window 守卫做 `mt > cw` ⇒
`TypeError: '>' not supported between NoneType and int` ⇒ **整轮对话失败**。

紧邻上一行 `cw = cfg.get("context_window") or 8192` 用的正是 `or` 兜底 ——
同一段两种兜底语义并存，这次统一。**这是会影响生产的真 bug**，不是门禁问题。

顺带修：`verify_s4_calls` 的 3.4b 锚整行源码字面量（与 L2 同类），
改为断言优先级语义三段，并新增 3.4b2 专守"DB 值为 NULL 必须退回内置默认"。

### L5 `verify_context_scope_guard`：[2] 段裸调真实库（既有）

```
FAIL count（默认）只报数量、不列具体实体名  | ''      ← 空串
FAIL 预算极小（40 字符）时范围声明仍完整保留  | ''
```

CI 干净库 `entities` 空 ⇒ `_build_model_context` 正确返回 `""`。**产品无误、判据错**。

讽刺之处：**同一文件 [3] 段的注释早就写明这条教训**
（"本段不得对真实库断言语义 … 属误报，现改为夹具驱动"），[2] 段漏改。

改为夹具驱动（只建该函数真正 SELECT 的 4 张表），并新增一条断言钉住被掩盖的分支
「无任何既有资产 ⇒ 返回空串」。

**环境无关性验证**（这才该门禁的本质）：

| 环境 | 结果 |
|---|---|
| 生产库 | 53/53 |
| **干净库**（`init_db()` 新建空库，模拟 CI） | 53/53 ← 修前此处必红 |

### L6 ci.yml：三处 `run:` 行末反斜杠被 YAML 折成字面 token（既有）

```yaml
run: python tools/verify/verify_rag_eval_gate.py --allow-missing \
  --report docs/评测/nightly/latest-rag-report.json
```

`run:` 是 **plain scalar**，其"换行+缩进"折叠成**一个空格** ⇒ 反斜杠不是续行符，
而是**字面 token** ⇒ argparse `unrecognized arguments: --report ...` ⇒ exit 2。
**门禁一个断言都没跑。**

同类写法 3 处（RAG / 生成质量 / Trace 三个评测门禁）全部从未执行 ———
"门禁写了、接进 CI 了、但一句都没跑过"，与配置谎言同型。
改用 block scalar（`run: |`）。

## 4. 方法沉淀（这轮最有价值的三条）

1. **判定"是不是我引入的"看失败步骤号，不看结论**：
   `88317a5` 挂 step 7 / `fcaeba2` 挂 step 6 ⇒ step 6 曾通过 ⇒ 本次引入。
   只看"两次都 failure"会得出错误结论。

2. **修判据前先分类三种"红"**：
   - 产品错（本例 `max_tokens` NULL → 真崩溃）
   - 判据错（锚文案 / 锚整行源码 / 裸调真实库）
   - 环境错（硬编码路径 / YAML 语义）
   混为一谈就会"改产品迁就门禁"或"放宽门禁让产品过关"，两者都错。

3. **改判据必须做变异自证**：本轮 G0 的四个形态 + 3.4b2 + p4 都做了。
   没有变异自证的判据修改，等于把门禁改成"永远绿"——比红更危险。
