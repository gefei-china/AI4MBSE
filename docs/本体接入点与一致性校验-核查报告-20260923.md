## 2. 文档上传 → 实体抽取：是否消费本体？

### 2.1 链路

```
文档上传  POST /api/documents（upload）
   → knowledge_pipeline.ingest.ingest_document（解析 → 分块 → 向量化 → document_chunks）
   → [开关 file_auto_extract_enabled]  →★ extract_candidates(conn, query, doc_id, top_k=5)
        → vector2graph（候选）→ v2g_candidates（pending）
   → 人工确认（POST /api/knowledge/v2g/confirm）
        → GraphStore.create_node/create_edge（再校验）→ entities / relations
```

### 2.2 两个必须先知道的开关（真库实测）

| 开关 | 真库实测值 | 含义 |
|---|---|---|
| `file_auto_extract_enabled` | **`'0'`** | **上传后自动抽取默认关闭**（`database/migrations/documents.py:111` 注释："0关/1开，默认关"）。关闭时上传**不会**抽取；可在「抽取设置」开启，或用 `POST /api/documents/{id}/extract` 手动补抽（`meta.py:254` 同样受此开关拦截） |
| `entity_candidate_source` | **`'sysml'`** | 候选来源默认 `sysml` = 以 AI 建模入库的 SysML 元素做**确定性词表匹配**（**不调 LLM**）；设为 `llm` 才走 LLM 自由抽取（`vector2graph.py:380/540`） |

> 含义：**默认配置下，"上传即抽实体"并未运行**；开启后，默认走词表匹配而非 LLM 抽取。

### 2.3 抽取链路消费本体的**四层**（这是本问的核心答案）

| 层 | 落点 | 消费什么 | 作用 |
|---|---|---|---|
| ① **抽取输入·词表** | `vector2graph.py:277`（`_resolve_coref`） | `ov.entity_types()` + glossary 术语 | 指代消解（"该设备/其…"→最近实体名），消掉无效三元组 |
| ② **抽取提示·schema** | `vector2graph.py:532-535` | `ov.entity_types()` / `relation_types()` / **`schema_text()`** | LLM 路径：**把本体 Schema 文本写进 prompt**（system："严格按本体类型抽取，输出合法 JSON"）；sysml 路径用 `relation_types[0]` 做关系兜底类型 |
| ③ **候选落库·预校验** | `vector2graph.py:594` | **`ov.validate_node(entity_type, props)`** | **有错即标 `status='rejected'`**（`errors` 列留痕），**不进人工确认池** —— 抽取阶段的提前拦截 |
| ④ **确认入库·再校验** | `confirm_candidates:740` → `GraphStore.create_node:520` / `create_edge:554` / `bulk_create:562` | `validate_node` / `validate_edge` | 最后一道闸：类型合法性（含子类）、必填、唯一、白名单、xsd、抽象类型不可实例化、关系的源/目标类型约束 |

另有候选编辑侧校验：`vector2graph.py:684`（`update_candidate`）重新 `validate_node`。

**结论**：**是**，抽取全过程消费本体做约束校验，且是"提示词约束 + 落库前预校验 + 入库再校验"三重。但对**默认配置**而言，这条链**默认未启用**（见 §2.2）。

## 3. 本体管理中的「一致性校验」

### 3.1 入口与调用链

| 环节 | 落点 |
|---|---|
| 前端按钮 | `static/index.html:595`「🩺 一致性检查」（本体页 `kb-c` 工具行） |
| 前端函数 | `static/js/mods/09-impact.js:1122 oeConsistency()` |
| 后端端点 | `GET /api/knowledge/ontology/validate`（`routers/knowledge_parts/ontology_version.py:8`） |
| 实现 | `routers/knowledge_parts/shared.py:303 _ontology_check(conn)` |

> 注：函数体虽落在 `09-impact.js`（模块归属是历史包袱），但 DOM 与入口均属**本体页**；按钮文案是「一致性**检查**」，日志/注释里写作「一致性**校验**」。

### 3.2 它到底做什么：**本体 Schema 的结构体检**（6 类）

| type | 级别 | 判据 |
|---|---|---|
| `cycle` | high | 循环继承（沿 `parent_id` 上溯命中自身，跳数上限 50） |
| `dangling_parent` | high | `parent_id` 指向不存在的类型 |
| `isolated` | low | 实体类型既无实例（`entities.entity_type` 计数=0）又无子类 |
| `missing_dom_range` | low | **关系**类型未定义定义域/值域（读 `constraints.allowed_values.src/tgt`，兼容旧 `domain`/`range`） |
| `bad_dom_range` | high | **关系**的定义域/值域指向**不存在的实体类型** |
| `duplicate` | high | `(type_kind, name)` 重名 |

**第二重身份（更重要）**：它是**发布前置硬门禁** ——
`POST /version/publish`（`ontology_version.py:121`）与 `POST /version/release`（`:289`）都在 `high > 0` 时返回 **400「禁止发布」**（"防带病发布"）。

### 3.3 真库实测（2026-09-23 21:0x，只读）

```
类型总数 = 52 ｜ 问题 = 12 ｜ 高 = 9 ｜ 低 = 3
分布：bad_dom_range 9 ／ missing_dom_range 2 ／ isolated 1
```

9 条高危**全部**是关系的 `bad_dom_range`，涉及 `CONTAINS`/`COMPOSED_OF`/`SATISFIES`/`ALLOCATED_TO`/`FLOW_TO`/`CONNECTS`/`DEPENDS_ON` 等（13 个关系类型中 **9 个**含悬空值）。

**这些悬空名字的性质（已查实，三条都不成立）**：
- 不是本体的实体类型（28 个已注册类型里没有）
- 不是库内任何实体的 **name**（0 命中）
- 不是库内任何实体的 **entity_type**（0 命中）

典型值：`巡飞弹`、`光电吊舱`、`任务载荷分系统`、`动力分系统`、`卫星导航接收机`、`飞控计算机`、`地面控制站`、`战斗部`、`引信`…

**疑似来源（未定论）**：这批词与 `docs/本体属性domain绑定问题说明-20260910.md` 里那张"巡飞弹系统指标"表**同源**（该文把「巡飞弹/红外热像仪/光电吊舱」当作实体类型处理）。
- **属性侧已闭合**：实测 11 个属性类型 `domain_classes` **为空 0 个、指向未注册类型 0 个** → 09-10 文档描述的问题已被修复。
- **关系侧未闭合**：同一批词仍留在 9 个关系类型的 `allowed_values.src/tgt` 里 → 至今悬空。
- ⚠️ 未在 docs 中找到"关系 dom/range 允许填非注册名"的设计声明 → **按现象报告，定性待确认**（是历史演示数据残留，还是有意留待治理，需米爸判定）。

**直接影响**：本体当前 **无法发布新版本**（publish/release 均被 high 门禁 400 拦下）。

## 4. 完备性评估：5 处缺口（均带证据）

### 4.1 🔴 前端标签漏一种（可复现 UX 缺陷）

- 后端可产出 **6 种** `type`（`shared.py` 内 6 处 `"type":` 字面量）。
- 前端 `TYPE_LABEL` **只映射 5 种**（`static/js/mods/09-impact.js:1140`）：`cycle / dangling_parent / isolated / missing_dom_range / duplicate` —— **缺 `bad_dom_range`**。
- 渲染用 `TYPE_LABEL[x.type] || x.type`（`:1154`）→ **真库那 9 条高危全部显示为英文原文 `bad_dom_range`**，而不是中文"定义域/值域无效"。

### 4.2 只报告、不修复、不给修复建议

面板只展示"问题 + 影响实体名"（点名字 `_locateOntType` 可定位到类型），**没有**"实际应为 `部件`"这类对照或一键修复。
对比：`POST /api/knowledge/ontology/impact-preview`（`ontology.py:22` → `services/ontology_migration.impact_preview`）**已具备** `severity/auto_fix/rename/violations` 与 L1 内联迁移能力，**但没有接到「一致性检查」这个入口**。

### 4.3 结果不留痕、无历史

`_ontology_check` 返回 dict，**不落库**；`ontology_change_logs` 只记类型变更（实测 37 行：update 36 / delete 1），**不记校验结果**。
→ 无法回答"上周 12 项、本周 9 项"这类趋势问题；也无法审计"某次发布前到底查出了什么"。

### 4.4 只查 Schema 结构，**不查「本体 vs 实例数据」**

`_ontology_check` **完全没有**触及存量实例的合规性：

| 本体已支持的约束 | 一致性检查是否覆盖 | 现存的替代实现（未聚合到此入口） |
|---|---|---|
| `required` 必填（实例层缺失） | ❌ | `OntologyValidator.validate_node:184`（仅**写入时**） |
| `unique` 唯一（实例层重复） | ❌ | `validate_node:187`（仅写入时） |
| `allowed_values` 越界 | ❌ | `validate_node:196` / `ontology_migration.validate_attribute_instances:154` |
| `cardinality` 与实际数量矛盾 | ❌ | 仅 `shacl_export` 生成 `sh:maxCount`，**无存量体检** |
| `disjoint_with` 被同时实例化 | ❌ | `shacl_export` 生成 `sh:not`，**无存量体检** |
| `abstract` 被直接实例化 | ❌ | `validate_node:179`（仅写入时） |
| `xsd_type` 类型错 | ❌ | `validate_node:228 _xsd_type_errors` / `ontology_migration._xsd_check:48` |
| **属性 `domain_classes` 为空** | ❌ | 无（`missing_dom_range` 仅对 `relation` 生效）——**实测属性侧当前 0 问题，属侥幸** |

**实证**：本次 validate 报告里出现的实体名与 11 个属性名**交集为空** → **属性侧完全未被体检**。

### 4.5 ⚠️ 口径分裂：校验读**编辑态**，部分消费侧读**已发布快照**

- `_ontology_check`（`shared.py:308`）与 `OntologyValidator(conn)` 默认（`ontology_semantics.py:75`）都直读 **`ontology_types` 当前表（编辑态）**。
- 消费侧按设计走快照：`_active_ont_rows`（`shared.py:464`）docstring 明写"**消费类端点（语义注入/图谱 Schema/导出）用此读取；编辑/校验类仍读当前表**"，实际使用于 `/schema`（`ontology_version.py:410`）、`/graph`（`:344`）、`/shacl`（`:424`）、`/export`（`:463`）。
- **但 AI 建模的语义注入没有走快照**：`agent/pipeline_parts/prompt.py:72` 是 `OntologyValidator(conn).schema_text()`（**无 `rows` 参数 → 读编辑态表**）。
- → 结果：**"一致性检查"看到的问题集，未必等于 AI 建模/导出真正吃到的那份 schema 的问题集**。是否有意为之，需确认。
