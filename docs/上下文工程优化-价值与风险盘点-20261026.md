## 1. 本期最终价值，逐项核账

### 1.1 逐项状态表

| 步骤 | 改动 | 开关默认 | **生产是否已生效** | 实测证据 | 证据强度 |
|---|---|---|---|---|---|
| Step1 | 分块 token 归因 | `enabled=True` | ✅ 已落库 | 真实 `execute` 链路落 12 块 + summary | **强**（真实链路） |
| Step2 | 检索多样性 | `per_doc_max=2`, `merge=True` | ✅ 已生效 | 24 query 复测：**50% 生效，平均 +8%，17% 反向** | **强**（真实语料） |
| Step3 | 记忆噪音闸门 + 单一真源 | `memory_single_source=True` | ✅ 已生效 | 两路召回 **id 重叠 0**；注入块噪音行 **0** | **强**（真实链路） |
| Step4 | JIT 空回退 top-N | `jit_fallback_top_n=8` | ✅ 已生效 | 最重场景 24→10 工具（−47.8%） | 中（单元 + 探针，真实链路未单独 A/B） |
| Step6/8 | MCP 元数据 + 按需暴露 | `mcp_meta_enabled=True` | ❌ **未生效**（server `offline`） | 模拟 online 时 71→8、−72.3% | 中（模拟态，非生产态） |
| Step9 | role 手册裁剪 | `role_manual_filter=**False**` | ❌ **未生效**（默认关） | 真实链路 −92.3% / system −65.5% | **强**（真实链路三态对比） |

### 1.2 关键：两项最大收益为什么"还没兑现"

**MCP（Step6/8）—— 收益为 0 的原因**

生产库 4 个绑定 MCP 的 agent，其 server `zhiyuan-dev-mcp` 的 `status='offline'`。
`repositories/agent_repo.bound_tools_for` 的判据是 `status=="online" and enabled`，
⇒ `bound` 里没有 mcp 项 ⇒ **零注入** ⇒ 本改动收益 **0**。

但**代码已就绪**：server 恢复 online 后，巡检会自动回填 `tool_meta`
（日志出现 `[mcp-health] 已回填 ...`），下一轮即生效。**不需要人工操作**。

**role 裁剪（Step9）—— 收益为 0 的原因**

`context_audit.role_manual_filter` 默认 **False**（刻意如此，见 §1.3）。
打开它只需一次配置变更，但**必须先做质量 A/B**。

### 1.3 为什么 role 裁剪刻意默认关闭

它是唯一**改模型可见内容**的改动（其余都只改注入量/去重/顺序）。
风险不对称：收益是 token，代价可能是**任务正确率**。

具体风险：`智源对接agent` 的 system_prompt 里那 14,531 字符手册，虽然本轮 50 个工具
不可用，但**其中的跨工具约定/顺序要求/注意事项**可能对剩余 8 个工具仍有指导意义。
裁掉后模型可能不会再主动"先 preview 再 apply"这类隐含流程。

⇒ 必须先跑同一批任务 A/B（token + 任务正确率 + 要求保留率），确认不掉才开。

### 1.4 影响面量化（历史真实流量，2026-09-11 ~ 10-26）

`llm_usage_stats` 真实调用 13,229 次 / **30.47M** prompt token。按 `chat_probe`（主对话）归属：

## 2. 价值如何体现 —— 度量口径与当前缺口

### 2.1 已有的度量链路（可用）

```
一次请求
  ├─ context_audit（块级）      → block_name / layer / tokens / chars / trace_id
  └─ llm_usage_stats（整包）    → prompt_tokens / cache_hit / cache_miss / trace_id
        ↓ 按 trace_id JOIN
  每轮 token 的「块级归因」+「实际计费」+「缓存命中」
```

可回答的问题：
- 每轮 token 花在哪个块（`SELECT block_name, SUM(tokens) ... GROUP BY 1`）
- 归因总量 vs 实际计费差额（= messages + tools payload）
- 静态区（可缓存）vs 动态区占比
- 各项改动的归因指标：`retrieval_effective`、`jit_fallback_full`、`mcp_selected`、
  `role_manual_dropped_chars`

### 2.2 **当前缺口（重要）：`context_audit` 没有任何消费方**

实测：`routers/` 下只有 `conversations.py:510` 一处调用 `flush()` 落库，
**没有查询接口、没有前端页面、没有报表脚本**。

⇒ 数据在库里，但**业务方看不见**。这直接导致：
- "价值如何体现"这个问题，现在只能用 SQL 手工回答；
- 开关该开还是关，运营没有可视化依据；
- 一旦无人查看，这张表会退化成"又一个没人用的日志表"。

**这是本期最大的交付缺口**（不是技术问题，是**闭环缺最后一段**）。

### 2.3 建议的最小补齐（1 个只读接口 + 1 个报表）

| 件 | 形态 | 成本 | 解决什么 |
|---|---|---|---|
| `GET /api/diagnostics/context-audit` | 按 trace / 按块 / 按日聚合 | 小（纯 SELECT） | 让数据可见 |
| `tools/report_context_audit.py` | 命令行打印"块分布 + 各项归因指标 + 缓存命中" | 小 | 上线前后对照 |

> 本盘点**未实施**这两件（超出"价值分析"范围），列为**下一步第一优先**。
> 理由：没有它，后面所有开关的取舍都只能靠猜。

### 2.4 必须说清的三条验证边界

| 边界 | 说明 |
|---|---|
| **① 全部在 mock LLM 下验证** | `MBSE_LLM_FORCE_MOCK=1`。真实 provider 下的**任务正确率、要求保留率从未测过**。token 类结论可信（`token_counter` 与 provider 无关），质量类结论**未验证** |
| **② "真实链路"= 真实 `execute()`，但仍是离库副本** | 用生产库快照 + 真实 pipeline，不是线上服务。并发、连接池、SSE 长连接行为**未覆盖** |
| **③ 效果类结论多为"机制性"而非"统计性"** | 如 "24→10 工具" 是单场景实测；"占总量 11%" 是外推估算。仅 Step2 做了 24 query 的分布统计 |

## 3. 剩余优化项：价值与风险矩阵

按「价值 ÷ 风险」排序。风险 = 改坏的可能 × 改坏后多难发现。

### 3.1 `semantic_cache` 接入 `stream.py` —— **价值最高，风险最低**

| 项 | 内容 |
|---|---|
| **实测事实** | `semantic_cache` 只在 `execute.py:477/795` 使用，**`stream.py` 一次都没有**。而生产 SSE 入口（`routers/conversations.py:391`）走的是 `execute_stream` |
| **⇒ 真实后果** | **语义缓存对生产主对话完全无效** —— 它只对非流式的 execute（Studio 试跑 / 工作流节点）生效 |
| **价值** | 高。主对话 `chat_probe` 占 51% token（15.6M），且大量重复问法（问同一模型的同类问题）。命中一次即省整轮 |
| **风险** | 中低。机制已存在于 execute 路径，是从"已跑通的实现"移植；主要风险是 SSE 首包延迟与事件序列（缓存命中要构造等价的流式输出） |
| **难点** | 不是缓存本身，而是**缓存命中时如何伪装成流式**（分块 yield、`done` 事件、usage 上报口径） |
| **建议** | **优先做**。先只对 `intent in ("chat","knowledge_qa")` 且无附件、无工具调用的场景命中（与 execute 路径同一闸门），风险面最小 |

### 3.2 `execute` 路径 role/skill 截断对齐 —— **价值中，风险中高**

| 项 | 内容 |
|---|---|
| **现状** | `execute.py:392-412` 明确：`role_cap=0`（不截断）、`include_tool_rules=False`（无 tool_rules 块）、skill `content_cap=0`（不截断）、`require_content=False`（正文空也注入）。注释写「不要顺手改成与流式一致，那是需质量 A/B 的独立决策」 |
| **价值** | 中。影响 Studio 试跑 / 工作流 LLM 节点。**生产 chat 走流式，不受影响** ⇒ 对主盘 token 无贡献 |
| **风险** | **中高**。三条差异各有理由：`role_cap=0` 是因为试跑要"所见即所得"（用户改完 prompt 就想看完整效果）；`require_content=False` 是因为空正文技能在试跑时也要能看到骨架 |
| **判断** | **不建议动**。价值集中在非主路径，而"试跑看全量"是产品语义。若真要动，应做成**试跑专用开关**而不是改默认行为 |
| **替代** | 若目的是省 token，`semantic_cache` 的收益/风险比远优于这项 |

### 3.3 存量 `scope_type=''` 记忆回填作用域 —— **价值中，风险低但需谨慎**

| 项 | 内容 |
|---|---|
| **实测** | `agent_memory`：`scope_type=''` **125 条**、`'project'` 85 条、`'user'` 1 条（原估 72 条，已修正） |
| **问题** | 空作用域的 125 条仅按 `agent_id` 过滤 ⇒ **跨项目可见**。若两个项目都有"字段命名约定"类记忆，会互相串味 |
| **价值** | 中。属于**正确性**问题而非成本问题：串味的记忆会误导建模输出（比多花 token 更严重） |
| **风险** | 低-中。**回填什么值**是判断，不是技术：这 125 条是"全局通用经验"还是"某项目的"？判错方向会把**该全局可见的**锁进单一项目 ⇒ 表现为"记忆突然不生效了"，且**很难被发现** |
| **建议** | 先**只读盘点**（按 `content` 聚类看这 125 条讲什么），再决定回填策略。不要批量 UPDATE |
| **注意** | 本仓已有先例：`rag.tenant_isolation` 的注释明确写着"打开隔离的真实危害不是多看到别人的数据，而是**看不到本该可见的公共资产**" —— 同一个陷阱 |

### 3.4 MCP 工具按语义族分层 —— **价值中，风险中**

| 项 | 内容 |
|---|---|
| **现状** | 已做到"按相关度取前 N（默认 8）"，未做"按族分组"（查询族 / 写族 / 危险族） |
| **价值** | 中。当前 `pick_for_injection` 可能选出 `delete_project` 这类危险工具（门禁实测：问"删除项目"时 `delete_project` 正确入选，这是**对的**；但问"查询工程"时不会选它，也是对的）。真正的收益是**在意图模糊时降低误调危险工具的概率** |
| **风险** | 中。需要先有工具分类元数据（`mcp_servers.tool_meta` 里没有 `readOnlyHint`）。MCP 协议本身有 `annotations.readOnlyHint` / `destructiveHint`，但当前 `save_tool_meta` **只存了 name/description/inputSchema** |
| **前置** | 先扩 `save_tool_meta` 存 `annotations`，**数据齐了再谈分层**。否则分类靠猜关键词（`delete`/`create`），必然误判 |
| **建议** | **暂缓**。等 MCP 恢复 online、`tool_meta` 有真实数据后再做 |

### 3.5 KV-cache 前缀稳定性 —— **价值可能最大，风险低，但已基本满足**

| 项 | 内容 |
|---|---|
| **实测** | 静态区（`PROMPT_CACHEABLE_KEYS`）**逐字节稳定**，与用户输入无关（门禁 3 组判据全通过）；静态区占 system **85.5%** |
| **⇒ 结论** | **本仓这块已经做对了**。块顺序是"静态前置 + 动态后置"，且没有时间戳/随机量混入静态区 |
| **价值** | 剩余价值在"减少动态区体积"（因为动态区一变，缓存从该点起全失效）。而动态区最大块是 `skill_prompt`（1,457 tok，占 33%） |
| **风险** | 低（结构已正确） |
| **建议** | 不用做"稳定性改造"。真正该做的是 **`skill_prompt` 瘦身**（见 3.6） |

### 3.6 结构性项：`skill_prompt` 瘦身 —— **实测推翻了初版建议，但挖出另一个真 bug**

| 项 | 内容 |
|---|---|
| **实测** | 真实链路块分布：`skill_prompt` **1,457 tok（33.1%）**，是 system 第一大块 |
| **初版建议** | "看未命中技能的**资源清单**（`📄 参考文档` / `📝 示例` / `⚙ 脚本`）是否必要" |
| **实测推翻** | `skill_prompt`（3,435 字符）里这三类标记出现 **0 次** —— 技能根本没有 `references`/`examples`/`scripts` 元数据，**这条瘦身路径不存在** |
| **真正占用** | ① frontmatter 头部（见下方 bug）② 正文头部摘要（`offload_body` 的 `build_head`，约 900 字符）③ **示例代码片段**（实测尾部约 700 字符，已被截断但仍注入） |

#### 顺带发现（未修，需业务决策）：`skills.frontmatter` 字段被污染成整份正文

| 项 | 实测 |
|---|---|
| **字段本意** | 只存 YAML frontmatter 头（约 300 字符） |
| **实际内容** | **整份正文**，最长 `sysml_view_generation_activity` = **9,383 字符** |
| **污染范围** | 24 个发布技能里 **21 个** 的 `frontmatter` 超 400 字符；多数与 `content` 几乎等长（差 −13 字符） |
| **注入方式** | `skills.py:181` `meta = (s.get("frontmatter") or "").strip()[:400]` ⇒ **按字符硬截** |
| **后果 1：句子腰斩** | 截断点常落在句中。实测：`- 如需查标准库（\`sysml_stdlib_me` ← 被切断 |
| **后果 2：指令冲突（更严重）** | `frontmatter` 是**旧版正文**（"工具调用轮次上限为 **3**，耗尽即中断"），而 `content` 已更新为"轮次有限……**以运行时注入为准**"。同一段 prompt 里同时出现 **"上限为 3"** 与 **"运行时真值，共 6 轮"** ⇒ 模型无法判断哪个为准 |

**风险判断**：这不是 token 问题（400 字符 × 命中技能数，量小），而是**指令质量**问题 ——
模型拿到两个矛盾的轮次上限，行为不可预测。属"改了技能正文但模型看到的还是旧版"这类静默失效。

**建议**：**先只读盘点**（哪些技能 `frontmatter` 与 `content` 不同步），再决定：
- 若 `frontmatter` 只该存 YAML 头 ⇒ 批量重建为 `content` 的 YAML 段（**不可盲目截 400**）
- 若业务确实把 `frontmatter` 当"正文快照"用 ⇒ 则应在 `content` 更新时同步刷新它（当前没有）

> ⚠️ 本节**未实施任何修改**。数据清洗属业务资产变更，且本仓有"批量 UPDATE 前必须先只读盘点"
> 的纪律（见 §3.3 的同族教训）。

| — | `execute` 路径截断对齐 / `ontology` 裁剪 | **不建议**（价值低或风险高） |

> **执行后的关键认知变化**：

> （技能白名单把 MCP 工具清零）。这说明**"配置对了"≠"链路通了"** ——
