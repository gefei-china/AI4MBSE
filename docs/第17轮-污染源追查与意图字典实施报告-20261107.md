## 1. 「请检索标准库并生成视图」溯源

### 1.1 它**不是**系统内置、也不是提示词

证据（逐项可复现）：

| 检查 | 结果 |
|---|---|
| 全仓 grep `检索标准库` | 只出现在 `backups/cleanup_test_convs_*.json`（测试会话备份）与 `docs/评测/datasets/`，**代码/提示词里没有** |
| `_SEMANTIC_UTTERANCES`（意图示例表，8 条） | 不含该句 |
| 技能正文 grep `标准库` | 无该句 |
| `messages` 表作为 `role='user'` | **仅 2 次**，来自 `verify_failed_budget` 会话（验证脚本建的） |

### 1.2 为什么 `seen_count=61`

`intent_samples.upsert` 对已存在行执行 `seen_count=seen_count+1`，
而 `import_source`（从历史回填）**每跑一次就给每条已存在的行 +1**。
`created_at=2026-10-30`、`updated_at=2026-11-06` ⇒ 期间被反复回填。

**全池污染面（实测）**：

| 指标 | 数值 |
|---|---|
| `seen_count` 高于真实次数的条目 | **390 / 547（71%）** |
| `seen_count` 总和 vs `messages` 真实 user 消息数 | **1098 vs 473** |
| 最极端 | 「请检索标准库并生成视图」seen=**61** / real=**0** |

⇒ **我上一轮审核清单用 `seen_count` 排序是错的**：把测试脚本刷出来的句子排到了第 1。
已修（见 §3）。

### 1.3 但你的直觉指对了：「总是查标准库」真有一个驱动源

真凶不是那句话，而是一个**技能在强制要求调用一个已禁用的工具**：

| 位置 | 内容 | 状态 |
|---|---|---|
| 工具 `sysml_stdlib_meta` | status=**disabled**，执行返回 `{'ok':false,'result':'未知工具'}` | 不可用 |
| 技能 `sysml_stdlib_reference_guide`(id=118) | description + 正文：「**生成任何属性/类型引用前先查标准库**」+ 步骤 1「调 `sysml_stdlib_meta`」 | **published，绑给 architecture_skeleton / view_expansion**（正是产码两阶段） |
| `v2_constraints.py` 工具协议第 2 步 | 「sysml_stdlib_meta —— 可选，最多 1~2 次」+ 教了参数名 | 每次产码注入 |

⇒ 每次产码都被注入「先查标准库」，模型去调一个不存在的工具 ⇒
白花工具轮次 + 拿到「未知工具」后可能转入臆造成员名。
这与 `sysml_stdlib_tools.py` 文件头的记录一致：该工具曾占工具调用 **32%（13/41）**。

**修法**（不动工具状态，只让说明书与实物一致）：
- 技能 id=118 正文改为 v2.0：「查询工具**当前已停用**，不要再调用；标准库成员事实以
  `sysml_v2_validate` 的语义诊断为准，禁止臆造」
- `v2_constraints.py` 第 2 步改为「已停用，不要调」

这与上一轮处理「智源对接agent prompt 引用 disabled 工具」的口径一致。

## 2. 意图字典：从「只能单选」到「可新增/编辑/停用」

### 2.1 根因
意图清单此前是 `agents.status='active'` **派生**的；中文名硬编码在前端
`IS_INTENT_LABEL`；示例说法硬编码在 `agent/intent.py::_SEMANTIC_UTTERANCES`（只有 8 个意图）。
⇒ 没有可维护实体，自然「只能单选、无法新增和编辑」。

### 2.2 做法（对齐行业受控词表实践）
新表 `intent_taxonomy`：

| 字段 | 作用 |
|---|---|
`name` | **canonical 名**（机器用、新增后不可改、路由与历史样本的键）
`label` | 中文显示名（下拉里显示的就是它）
`scope_note` | 一句话定义 + **什么不属于我**（防类别漂移）
`aliases` | 别名表 → 归一化（用户说「需求分析」自动归到 `requirement_analysis`）
`examples` | 示例说法 → **直接并入 LLM few-shot**
`cluster` / `agent_name` | 归属能力族 / 映射的 Agent（**可空 = 纯分类标签**）
`status` / `merged_into` / `version` | 弃用路径：活跃 → 弃用 → 并入，历史标注仍可解析

种子 22 条（含 8 个建模流水线阶段，此前前端下拉**选不到**）已入库。

### 2.3 关键收益：示例说法补上了 few-shot 缺口
实测 few-shot 覆盖从 **8 个意图 / 2 条每意图** → **9 个意图 / 5~6 条每意图**。
这正对着上一轮发现的「confirmed 只有 2.29 条/意图（标杆 ≥20）」的缺口——
字典示例是人工写的，质量高于采集样本，且**可随时编辑**。

### 2.4 交互设计取舍（为什么不做成下拉内自由输入）
canonical 名是路由键，随手输入的自由文本会**立刻造成同义分裂**
（`需求分析` / `需求解析` / `requirement_analysis` 三份并存）。
所以样本行的下拉旁是「＋」入口 → 打开表单，**强制填中文名 + 建议填示例说法**，
从源头收敛而不是事后合并。

### 2.5 真实 HTTP 验证（全通过）
1 新增纯分类意图 → 2 编辑中文名与示例 → 3 查回确认（示例 3 条）→
4 别名归一化（`探针别名甲` → `__gate_probe_intent`）→ 5 停用。清理探针。

## 3. 顺手修掉的两个数据缺陷

### 3.1 `seen_count` 被回填刷高（71% 条目）
- `upsert` 新增 `bump_seen` 参数，`import_source` 传 `False`（回填是"发现新说法"，不是"用户又说了一次"）
- 新增 `real_usage_counts()`：从 `messages` 表 `role='user'` 统计**真实次数**（排除测试会话）
- 新增 `usage_audit()`：量化虚高程度（门禁与页面都用它）
- 审核清单排序改用 `real`；页面同时显示「真实次数 / 采集次数」两列

**排序变化（实证）**：
| | 旧（seen_count） | 新（real） |
|---|---|---|
| 第 1 名 | 请检索标准库并生成视图（seen 61 / real **0**） | 请输出一段内容用于验证断点保护（real 22） |

### 3.2 `list_all` 对 tuple 行崩溃
`dict(r)` 在调用方没设 `row_factory` 时抛
`cannot convert dictionary update sequence`。已改为按 `description` 取列名兜底——
本模块被路由/门禁/脚本多处调用，不能靠"大家都记得设 row_factory"来保证。

### 3.3 我自己的脚本坑：`sqlite3.connect('file:mbse.db')` 漏 `uri=True`
SQLite 把整个字符串当文件名，**新建了一个空库文件**，导致"表不存在"的假象。
已删垃圾文件，验证脚本统一用 `file:...?mode=ro` + `uri=True`。
