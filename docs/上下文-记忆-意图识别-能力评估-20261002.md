# 上下文管理 / 记忆 / 意图识别 —— 能力评估与标杆差距（2026-10-02）

> **评估口径**：全部结论都附**实测证据**（真库查询 / 巡检脚本 / eval 基线 / 标杆公开资料），
> 不接受"代码里写了"作为"能力已达标"的证据 —— 这是本仓一条反复付过代价的纪律。
> 本次实测时间：2026-10-02；数据窗口：近 7 天（`llm_usage_stats` 共 4661 次真实调用，19 个活跃日）。

---

## 0. 一句话结论

**三者都已"能用且不弱"，短板不在算法而在"运行时治理"**：

| 维度 | 现状评级 | 最短的那块板 |
|---|---|---|
| 上下文管理 | 中上 | **没有"按 token 压力触发"的分层压缩**（只有固定 keep-last-N + 摘要）；工具结果无 offload |
| 记忆 | 中上 | **用户不可见、不可管理**（标杆已是标配：查看/编辑/删除/隐身）；无"删对话即删派生记忆" |
| 意图识别 | 好（准确率维度） | **语义层结构性降级（embedding 403 → bigram）**；**意图缓存命中率实测 0** |

## 1. 实况（实测，非推断）

### 1.1 上下文管理

| 指标 | 实测值 | 来源 |
|---|---|---|
| system_prompt 分层 | 四层（L2 身份 / L1 全局静态 / L3 会话 / L4 每轮），**顺序+内容均已单一真源** | `common.py` + `verify_prompt_layering` 28/0 |
| prompt 缓存命中率 | **47.9%**（主对话 59.6%） | `tools/llm_health.py --days 7` |
| 主对话单次输入 | **5527 tokens**（772 次共 426 万输入 token，占总输入 67.5%） | 真库聚合 |
| 历史保留策略 | `keep_last_n_turns=4`（标定值）+ 跨话题摘要 + 语义拉回 | `agent/pipeline_parts/history.py` |
| 超窗治理 | `context_window_guard`（clamp/warn/off）+ `_apply_context_budget` 分区裁剪 | `core/config.py` / `openai_compat.py` |
| 子任务上下文隔离 | conversation_id=0 fresh + 摘要≤400 字 + artifact_digest 注入，**已固化为契约** | `verify_subtask_isolation` 10/0 |
| 判据覆盖率 | **2.4%**（71/2951）—— 流式 `finish_reason` 采集刚修（P0-a），正在积累 | 巡检 |

**结论**：**静态结构做得比多数产品好**（分层 + 单一真源 + 契约化验证），
但**动态治理缺一层** —— 见 §2.1。

### 1.2 记忆

| 指标 | 实测值 |
|---|---|
| 记忆条目 | **141 条**（experience 118 / fact 16 / preference 3 / skill 4） |
| 分层（tier） | **core 3 / recall 83 / archival 55** ✓ 三层生效 |
| 来源 | llm_agent 77 / reflow 56 / rule_agent 8 |
| **是否真被用** | **82/141（58%）被访问过**，单条最高被访问 **133 次** ✓ |
| 遗忘机制 | `forgotten` 列 + 时间/使用证据驱动 |
| 提取门控 | 长度带 / 噪声门 / 经验信号门（三门控） |

**结论**：**"提取 → 分层 → 召回 → 遗忘"闭环是通的，且被真实使用**（58% 命中、单条 133 次访问
说明召回确实在复用）。这块比多数自建系统扎实。

**但**：整条链路对用户是**黑盒** —— 见 §2.2。

### 1.3 意图识别

| 指标 | 实测值 |
|---|---|
| 准确率 | **accuracy 0.9545 / macro_f1 0.9652**（n=44，错 2 例，与历史基线逐位一致） |
| 架构 | 三层：规则/关键词（db 驱动）→ 语义（embedding）→ LLM 兜底 |
| 错例 | ①「帮我看看这个系统大概是怎么设计的」期望 design → 实得 chat（llm_weak 0.5）②「…接口设计是否合理」期望 design → 实得 review（llm 0.9） |
| **语义层状态** | **降级 bigram**（阿里云 embedding 403 熔断中）—— 本次 eval 输出中**没有任何 `route=semantic`** |
| **意图缓存** | `intent_cache` 表仅 1 行、`hit_count` 总和 **0** ⇒ **实际零命中** |
| LLM 兜底调用量 | `intent_detect` **1620 次 / 7 天**（≈232 次/天） |
| 样本池 | 279 条（全 `suggested`，待人工确认） |

**结论**：**准确率维度是达标的**（0.955 在 44 例集上），但有两个**成本/工程层面的实质短板**：

- **语义层不可用**：bigram 是字符级量纲，dense 阈值（0.49）在它上面**结构上不可达**（实测最高 0.204）
  ⇒ 语义层事实上**没有在工作**，压力全压在规则层与 LLM 兜底。
- **意图缓存是"精确文本匹配"**（`query_hash` + `index_fp` 双匹配，见 `agent/intent.py:309`）
  ⇒ 自然语言对话里用户几乎不会说一模一样的话 ⇒ **命中率天然接近 0**。
  这不是 bug（P0-3 已修过 key 大小写口径），而是**设计选错了缓存粒度**。

## 2. 与标杆的差距（逐项）

> 标杆素材来源：ChatGPT/Claude/Gemini 记忆能力对比（2026）与 agent 上下文压缩最佳实践（2026），
> 链接见文末。差距等级：**P0** = 影响正确性/合规；**P1** = 影响成本或体验；**P2** = 锦上添花。

### 2.1 上下文管理

| 能力 | 我们的现状 | 标杆做法 | 差距 |
|---|---|---|---|
| **分层压缩（按压力触发）** | ❌ 无。只有固定 `keep_last_n_turns=4` + 会话/历史摘要 | 五阶段渐进压缩：70% 告警 → 80% 观测脱敏 → 85% 快速剪枝 → 90% 激进脱敏 → 99% 全量压缩（ACC, 2026） | **P1（最大缺口）** |
| **工具结果 offload** | ⚠️ 部分：`_TOOL_MODEL_CAP=3000` 纯截断，**剪掉即丢失** | Tier 1：大工具响应**落盘 + 引用**，需要时按需重读（可寻址召回，非破坏性） | **P1** |
| **压缩时保缓存前缀** | ⚠️ 未做（压缩只影响动态区，未显式对齐 cache_control 断点） | 把 cache breakpoint 放在 system prompt 末尾，压缩只让新摘要成为新条目 | **P2** |
| 按 **token 压力**而非消息数触发 | ❌ 未做（固定轮数） | "Message count is a lie"：按 token 预算的 70% 触发 | **P1** |
| 摘要内容结构 | ⚠️ 有摘要但未见"目标/状态/约束/下一步"四段式契约 | 摘要必须含 Objective / State / Constraints / **Next steps**，否则目标漂移 | **P1** |
| 结构化状态与叙事摘要分工 | ✅ 部分有（slots + project_memory + model_context） | typed SessionState 承载精确值，摘要只承载叙事 | 基本达标 |
| 静默丢约束防护 | ⚠️ 无显式防护 | 明确列出"反模式"：过早压缩、静默丢约束、mid-tool-chain 压缩 | **P2** |
| prompt caching | ✅ 47.9%（主对话 59.6%） | 同 | 达标 |

**量化参考**：标杆实测「剪枝到最近 5 个工具调用对 + 摘要」→ **91.6% 任务完成率 vs 全上下文 71%**，
且 token 与耗时大幅下降。这说明**分层压缩不只是省钱，还提升任务完成率** ——
对我们是"正确性 + 成本"双收益，故列 P1 而非 P2。

### 2.2 记忆

| 能力 | 我们的现状 | 标杆做法 | 差距 |
|---|---|---|---|
| **用户可见/可管理** | ❌ **完全没有界面**：用户看不到系统记住了什么、不能编辑/删除单条 | ChatGPT：设置→个性化→记忆，可查看/删单条/整体关闭；**Claude：直接展示"它了解你的摘要"，可查看+编辑** | **P0（合规与信任）** |
| **隐身 / 临时对话** | ❌ 无 | ChatGPT「临时聊天」、Claude「隐身聊天」：不写入记忆库 | **P1** |
| **删除对话即删除派生记忆** | ❌ 无（删对话不影响已沉淀的记忆） | **Claude 明确规则：删除某次对话，其派生记忆也从摘要中消失**（ChatGPT 不会 —— 这是 Claude 更透明的点） | **P1** |
| 分层 / 遗忘 | ✅ 三层 tier + 遗忘引擎（比多数产品细） | 多数产品只有"存/不存"两态 | **领先** |
| 冲突消解（新旧记忆矛盾） | ❌ 未见机制 | 先进实现（Mem0 类）做冲突检测与覆盖 | **P2** |
| 记忆是否真被使用 | ✅ 58% 被访问，单条 133 次 | 多数产品无此可观测性 | **领先**（可作对外卖点） |

**为什么"用户可见"是 P0**：记忆会存下用户偏好与项目信息（我们 141 条里含 3 条 `preference`、
16 条 `fact`）。**用户无法查看/删除**意味着：① 用户无法纠正错误记忆；② 涉及个人信息时**无
"被遗忘权"的落点**。标杆三家**全部**提供了查看+删除入口，且 Claude 还把"删除对话 ⇒ 删除派生记忆"
写成明确规则 —— 这不是"锦上添花"，是基本盘。

### 2.3 意图识别

| 能力 | 我们的现状 | 标杆做法 | 差距 |
|---|---|---|---|
| **语义层可用性** | ❌ **降级 bigram**（403 熔断），`route=semantic` 在 44 例评测中**零出现** | 语义路由是标配 | **P0（能力缺失）** |
| **缓存粒度** | ❌ 精确文本匹配 ⇒ 实测零命中 | ① 前缀缓存（省钱不省调用）② 语义缓存（相似问复用判定）；**但更主流是"不做判定缓存，改用小模型判定"** | **P1** |
| 分层路由 | ✅ 三层（规则/语义/LLM） | 常见：小模型先筛 + 大模型兜底 | 达标（但中间层失效） |
| 准确率 | ✅ 0.9545 / macro_f1 0.9652 | — | **达标** |
| 意图与参数一次出 | ⚠️ 分开：先判 intent，再 `task_decompose` 抽 slots | function calling / structured output：**一次调用同时给意图与参数** | **P2** |
| 样本池闭环 | ⚠️ 有 279 条但**全为 suggested（未确认）** | 持续人工确认 → 回流评测集 | **P2**（闭环未合拢） |
| 全链路零写死 | ✅ 已彻底移除代码内意图词表（P1-16/17） | — | **领先** |

## 3. 已达标、**不建议**再动的部分

避免"把好的也改坏"（本仓有过 P1-24/25 只改单路径的教训）：

- **prompt 四层分层 + 顺序/内容单一真源**：与 Claude Code 的
  `SYSTEM_PROMPT_DYNAMIC_BOUNDARY` + 命名约定**同构**，且我们用自检脚本把它变成了**可执行判据**
  （26 → 28 条断言 + 变异自证）。**别为了缓存把身份后置**（§32 已用数据否决：月省 $0.16）。
- **记忆三层 tier + 遗忘引擎 + 可观测的访问计数**：比多数产品细，且**真实在用**（58% 命中）。
- **意图识别"零写死"**：代码里没有意图词表，全靠 Agent 配置驱动。
- **子任务上下文隔离契约**：已有 10 条断言守着，别退化成"靠约定"。

## 4. 优先建议（按性价比排序）

| # | 事项 | 等级 | 理由 |
|---|---|---|---|
| 1 | **记忆的用户可见 + 可删除**（最小版：一个列表页 + 删除按钮 + "删除对话即删派生记忆"） | **P0** | 合规与信任的落点；标杆三家全有；纯新增，零回归风险 |
| 2 | **恢复 embedding 语义层**（阿里云额度） | **P0** | 一句话就能恢复一层能力（403 非代码问题）；恢复后需重标定阈值 |
| 3 | **意图缓存的粒度改对**：要么改语义缓存，要么**明确降级为"不缓存"并把规则层覆盖率提上去** | P1 | 现状是"有缓存表但零命中"＝纯粹的复杂度负担 |
| 4 | **分层压缩（先做 Tier 2 摘要的"四段式契约" + 按 token 压力触发）** | P1 → **暂缓** | ⚠️ 经实测复核**降级**：已有话题摘要 + 三层窗口 + 两级预算分配（比本表描述更完整），且输入仅占窗口 **41.8%**、从未触达 ⇒ 见 §35 |
| 5 | **工具结果 offload**（落盘 + 引用 + 按需重读） | P1 → **暂缓** | ⚠️ 经实测**推翻**：553 次工具调用结果最大 2000 字、**超 3000 的 0 次**（从未被截断）⇒ 当前零收益；见 §35 |
| 6 | 隐身对话 / 删除对话联动 | P1 | 记忆 P0 的配套 |
| 7 | 记忆冲突消解、意图+参数一次出、样本池确认闭环 | P2 | 有则更好 |

**执行顺序建议**：`1 + 2`（互相独立、零/低风险）→ `3`（先定性再改）→ `4 + 5`（同一主题，一起做）。

## 5. 本次评估过程中发现的两个"指标缺陷"（顺带记录）

1. **`generic_trap_acc = 0.0000` 是假象**：`eval_intent_routing.py:128` 在"泛词陷阱子集无样本"时
   `mac = 0.0` 并照样写进 `[RESULT]` JSON ⇒ 会被读成"泛词陷阱全错"。
   **这正是本仓 P0-a 定的纪律的反例：「数据不足必须报 unknown/None，不许报 0」**。建议改为 `null` + 打印 `n=0`。
2. **`intent_cache` 的 `hit_count` 恒 0 却仍在写库**：缓存**写入了但从不命中**，
   表面看"有缓存能力"，实际是**纯开销**。要么修粒度，要么显式停用以降低复杂度。
