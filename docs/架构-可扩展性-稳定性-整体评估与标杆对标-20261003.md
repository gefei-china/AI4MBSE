## 0. 结论摘要

**一句话判断**：这是一个「**领域纵深顶尖、平台工程底座薄弱**」的系统 ——
在 SysML v2 语义闭环、本体治理、上下文工程三个点上做到了多数商业 AI 平台做不到的深度，
但在**执行引擎韧性、存储与并发模型、多租户隔离、前端工程化**四项上仍是**单进程原型形态**，
距"可交付的企业级 AI 平台"存在**结构性代差**，而非功能缺失。

## 2. 架构评估

### 2.1 分层：名义四层，实际两层半

```
routers/(559 端点) ─┬─→ services/ + repositories/（539 方法）  ← 名义通道
                    └─→ conn.execute(...)                      ← 实际通道：1017 处 / 49 文件
                              ↓
                        SQLite (mbse.db)
```

- **分层绕过 1017 处**（口径：`conn.execute(|db_session`，2026-10-03 实测；序列 959→1089→1003→**1017**）。
  最集中：`routers/glossary.py` 103 处、`graph_workspace.py` 49、`knowledge_parts/ontology.py` 38。
- 后果：**"改一个查询要扫 49 个文件"**；任何跨切面能力（审计、软删除、租户过滤、分页）都**无法在单一注入点生效** ——
  这正是 §3.1 多租户隔离做不了的物理原因。
- 已知纪律（`AGENTS.md` 铁律 3）：存量不强行搬，只做新老划断。**方向正确，但 1017 处意味着新代码也在继续绕过。**

### 2.2 执行与并发模型：🔴 最大的架构缺陷

```
浏览器 ──fetch──▶ POST /api/conversations/{id}/chat/stream
                    │  def chat_stream(...)            ← 同步 def（非 async）
                    ▼
        FastAPI/Starlette 把同步端点丢进 anyio 默认线程池（默认上限 40）
                    ▼
        同步生成器 execute_stream() —— 单轮实测 344s / 849s / 1155s
                    │  ├─ 编排：planner 一次出 DAG
                    │  ├─ 子任务：ThreadPoolExecutor(max_workers=3~4)  ← 池套池
                    │  └─ refine：反思 1~3 轮
                    ▼
        阻塞该线程直到流结束
```

**实测支撑**：
- `routers/conversations.py:215` 为 **`def chat_stream`**（同步）；`agent/pipeline_parts/stream.py` 内**无 `async def`**（既有结论，见工程基线 §5）。
- `main.py:218` `uvicorn.run(app, host, port)` —— 单进程、无 worker、无并发限制。
- 全仓（排除 venv/tmp）**无 Celery / RQ / BackgroundTasks / 任何任务队列**；并发原语仅 3 处 `ThreadPoolExecutor`（stream 2 处 + workflows 3 处）+ 2 个守护线程（告警、fs_guard）。

**四个直接后果**：
1. **并发上限 ≈ 40 个长任务**（anyio 默认线程池），第 41 个请求排队 —— 而单轮编排占用线程 5~19 分钟。
2. **进程重启 = 全部在飞任务丢失**，无 checkpoint、无 resume。实测 `agent_tasks` 共 60 个批次，其中 **16 个批次残留 `planned/ready/blocked` 未收敛任务**（27%），这些任务永远不会再被拾起。
3. **无法水平扩展**：无共享队列，第 2 个实例无法接管第 1 个实例的任务。
4. **池套池**：FastAPI 线程 → 编排线程 → `max_workers=3` 子任务池，线程数放大且无全局配额。

### 2.3 存储：SQLite 单文件是正确选择，但已到边界

| 已做对的 | 边界 |
|---|---|
| WAL + `busy_timeout` + `check_same_thread=False` | **单写者**：入库持写事务分钟级 → 工程纪律要求"大批量入库必须先停服务" |
| 129 表 / 158 索引，无外键（改造友好） | `mbse.db` 321 MB，`backups/` 1.5 GB —— 无归档/冷热分离策略 |
| 迁移机制完善（`database/migrations/` 13 文件） | 无读写分离、无连接池、无分区；`document_chunks` 6,459 行已撑起 300 MB（embedding 列） |

**embedding 入库实测成本**（既有结论）：三份规范文档 = 4,884 块 / **约 13.4 分钟**，且必须停服务。
新增一个领域包的知识库 = 一次停服窗口，这与"可扩展"直接冲突。

且无法做类型检查、无法做单测、无法 tree-shake。

### 2.5 领域纵深：本工程真正的护城河（不是客套）

|---|---|---|

## 3. 可扩展性评估

### 3.1 🔴 多租户/项目隔离：**检索链路上根本不存在这道闸**

```
管理侧：GET /api/projects/{id}/entities   → 按 project_id 过滤  ✅ 有
检索侧：agent/rag.py                       → project_id 出现 0 次 ❌ 无
         只按 branches + source_docs 过滤
分支模型：branches 表无 project_id 列      → 分支是"全局版本轴"，与项目正交
```

**实测**：
- `projects` 表 **1 行**（`project-satnet-broadband`）；`entities` 189 条 100% 属该项目。
- release 分支 54 条实体全部是 `source_type='演示数据集'`，`published_at` **全部同一时间戳**，
  `merge_requests` 无任何 target=release 的记录 → **发布基线内容建设尚未发生**（既有结论）。
- 后果：**接入第 2 个项目/第 2 个领域时，AI 建模必然读到第 1 个项目的全局数据**。
  这不是"配置没配好"，是 `retrieve()` 里没有 `project_id` 参数位 —— **加配置修不好，必须改签名**。

### 3.2 🔴 领域包（Domain Pack）机制缺失

- 本体有版本与快照（`ontology_versions` 70 / 快照 193），但**没有"领域包"这一级装载单元**。
- 实测换域后果（既有结论）：**13 个关系类型中 9 个 dom/range 悬空**（entity/attribute 已换成卫星域、
  relation 仍引用巡飞弹词表），存量 249 条边中 **141 条（56.6%）被自家校验器判非法**。
  → 换一次域 = 半截约束 + 存量数据自相矛盾。**这是"可扩展性"最硬的实测证据。**

### 3.3 生态扩展：协议层已备，运行时未隔离

| 项 | 现状 | 缺口 |
|---|---|---|
| MCP（**对外供给**领域能力） | `routers/mcp_gateway.py` + `mcp_client.py` + `mcp_health.py`（5 分钟健康巡检） | 已落地 ✅ |
| 工具 | 33 个；`agent_tools` 表绑定；`tool_hooks` 4 条种子（block/require_confirm/warn） | 无 SDK、无契约版本管理 |
| Agent | 21 个（含 DB 自建）；意图路由已从硬编码 `INTENTS` 完全迁移到 `agents.intent_keywords`（P1-16） | ✅ 这块做对了 |
| 插件 | `plugins` 83 / `plugin_versions` 83 | **进程内直通执行**，无沙箱、无资源配额 |
| 技能包 | `static/skill_packages/` 583 个目录（**生成物，已 gitignore**） | 无运行时隔离与生命周期管理 |

### 3.4 评测能力：跑道修好了，但从没当门禁跑过

- `tools/eval/` 五件套 **1,286 行** + 三域 **46 例**评测集（含负对照、两层漏斗、语料指纹）。

## 4. 稳定性评估

### 4.1 🔴 鉴权：已建体系，但门未上锁

| 事实 | 实测 |
|---|---|
| RBAC 模型 | `roles.permissions` = JSON `{domain:[ops]}`；3 个 preset 角色 |
| 门的实现 | `require_permission(dom,op)`；全仓 **72 处 Depends + 7 处函数内调用**（均在 `branches.py`） |
| **致命点 1** | `core/deps.py` 匿名（`user is None`）**直接放行** → 未登录调用永远 200 |
| **致命点 2** | 身份靠请求头 **`X-User-Id` 自报**，`auth.enforce_login=False` → 任意人可冒充任意用户 |
| **致命点 3** | `users` 表**无口令列**；SSO 代码就绪但 `mode=local` **免校验**（任意显示名进入） |
| 已知安全隐患 | `routers/sparql.py:80` 注释自陈：Fuseki 一旦起来 = **开放任意图写** |

**判定**：权限矩阵设计是完整的，缺口只是"没强制"——**这是 P0 里成本最低、收益最高的一项**
（改 `enforce_login=True` + 移除 `X-User-Id` 兜底即可，但需先做前端登录态改造）。

### 4.2 🔴 无恢复能力：durable execution 完全缺失

| 标杆（LangGraph 1.x） | 本工程 |
|---|---|
| 每个节点迁移落 checkpointer（Memory/SQLite/Postgres），**崩溃后从检查点恢复** | 无。任务状态写 `agent_tasks` 表，但**执行上下文在线程栈里**，进程一死全没 |
| `interrupt()` 暂停 → 人工审批 → `Command(resume=...)` 从原处继续 | HITL 是**同步等待**（`hil_confirmations` 0 行，L2 Agent 一个都没有） |
| time-travel：回退到任意检查点重放 | **元素时态历史空转**：`entities` 主键 `(id,branch)` 使 `valid_to` 恒 NULL（实测 **0/189**）、同键多行 **0 组** → `/history` 恒 1 行、`/at?as_of=` 恒命中当前行。**时态列与主键自相矛盾** |
| 横向可扩展任务队列 + 后台运行 + cron + webhook（Platform） | 无队列；后台仅 2 个守护线程（告警 / fs_guard） |

### 4.3 韧性的"半截"状态

| 已做对的 ✅ | 缺失的 ❌ |
|---|---|
| LLM 重试（指数退避，非重试标记 400/401/403/404/422）+ **provider 回退**（`llm.fallback_provider_id`） | **限流/配额完全没有**：全仓 0 处 rate_limit/throttle |
| HTTP 超时已设（chat 180 s / stream 120 s / 探测 10~15 s） | 全局预算早先超支 35%（`budget_tokens` 100 万 vs 实耗 135 万），现置 0 = 不限 |
| embedding 403/429 类级熔断 10 分钟降级 bigram | **DeepSeek 402 余额不足 → 服务静默回落 Mock**：用户看到"正常返回"，内容是假的（P1-26 实测） |
| 工具重试策略可配（`tool_resilience.py`，默认关） | SSE **无心跳**：实测无 heartbeat/keepalive 代码 → 反向代理/浏览器空闲超时会断流，且**断流后不可续** |
| `core/fs_guard` 看门狗（绕开沙箱 `DeleteFileW` 死锁） | **异常吞噬 1,336 处** `except Exception`（排除 tests/tools/static/tmp）→ 历史上多次遮蔽真 bug |

### 4.4 稳定性数据的诚实边界

**本平台尚未经历真实负载**：`conversations` 全库 **15 行**，近 7 天 `messages` **41 条**。
近 7 天 LLM 调用 2,561 次中 `intent_detect` 占 **1,736 次（68%）**，而同期真实用户消息仅 41 条 ——
按天看 09-30 单日 1,056 次是**评测脚本刷的**（既有结论 §4）。
→ **"稳定性"目前只有功能正确性证据，没有容量/长稳证据。** 任何"能扛多少并发"的结论今天都给不出。

### 5.3 三条最值钱的差距结论

1. **差距不在"功能"，在"执行语义"。**
   本工程的编排**能跑通**（实测 3~6 子任务、全 done、产物落库），但它跑在**线程栈 + 单进程**里；
   LangGraph/Temporal 的差别是"**进程死了任务还在**"。
   → 这是**原型 vs 产品**的分界线，不是"再写个功能"能补的。

2. **上下文工程是本工程唯一"超标杆"的维度，但超在"工程纪律"而非"架构"。**
   Manus 用 todo.md 复述 + 文件系统外置上下文（官方博客自陈，~50 次工具调用/任务）；
   Anthropic 的纪律是 "static content first, dynamic content last"。
   本工程做到了**可量化**（cache hit/miss 落库、四层分层有守护脚本），
   但它是**手写拼接**（P1-26 之前两份内联顺序，流式路径完全没生效过）——
   **优势是"人盯出来的"，不是架构保证的**，一旦换人维护就会退化。

3. **领域纵深是护城河，但被单体绑架。**
   `checker.jar` + 本体 + SysML v2 闭环是 Dify/Coze/LangGraph 都给不了的；
   但它现在只能被这个 FastAPI 进程调用，**没有独立服务/SDK/契约**，
   所以"把 MBSE 语义能力卖给别的平台"这条路今天是走不通的 —— 这是**商业可扩展性**的问题。

## 7. 整改路线建议

### 7.1 阶段划分（依赖顺序不可颠倒）

```
第 0 步（1~2 天，零风险）
  ├─ 磁盘清理（P2-3）· override 镜像清理（P2-6）
  └─ 建立"现状看守"：eval 三条基线进 CI（P1-8，只跑不门禁）

第 1 步（1~2 周，不动架构）
  ├─ P0-5 鉴权强制（改配置 + 前端登录态）        ← 收益/成本比最高
  ├─ P1-3 降级显式化 + P1-4 兜底留痕
  └─ P1-2 SSE 心跳

第 2 步（3~5 周，架构第一刀）
  ├─ P0-1 + P0-2：编排改「提交—异步执行—订阅」     ← 真正的分水岭
  │    · 引入任务表 + worker 进程（不必上 Celery，进程内 worker + DB 轮询即可）
  │    · 状态落库 + 启动 orphan 回收 → 先拿到"重启不丢"
  └─ P0-6 时态历史（影子表方案，主表不动）

第 3 步（4~6 周，可扩展性）
  ├─ P0-4 检索侧 project 维度（签名级）
  ├─ P1-9 领域包机制
  └─ P1-7 领域能力服务化（mbse-core 包 + MCP）

第 4 步（持续）
  ├─ P0-3 存储冷热分离 / 入库队列化
  ├─ P1-6 前端命名空间治理
  └─ P1-10 分层热点收口
```

### 7.2 明确**不做**的事（避免无效投入）

| 不做 | 理由（实测） |
|---|---|
| **为提速重构编排 DAG / 提高并行度** | 实测 849 s 中 t3/t4 完成时刻几乎相同 = 已在并行（`agent_tasks.updated_at`）；瓶颈是 LLM 推理延迟，改代码无可落地提速 |
| **引入 Celery / Redis 重做队列** | 当前真实负载 `conversations` 15 行；先做"进程内 worker + DB 轮询"即可拿到 80% 收益，避免运维复杂度 |
| **重建 `entities` 主键做时态** | SQLite 无 ALTER PK，需手抄 26 列；影子表 `entity_versions` 方案 0 处 SQL 需审查，可回滚 |
| **前端整体重写 / 引入构建链** | 既定决策；1,118 全局函数的风险用"命名空间 + 重复定义自检"压住即可 |
| **搬走 release 分支的演示数据** | 用户已定口径"不强制提供内容、不断构建完善"；迁走 = release 变空，建模照样没料 |
