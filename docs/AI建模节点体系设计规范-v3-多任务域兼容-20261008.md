# AI 建模节点体系设计规范 v3.0 — 多任务域兼容

> v3.0 ｜ 2026-10-08 ｜ 仓库 `mbse_system`
> v2.0 提出「按阶段纵切 M0→N6」，但**未回答非建模任务如何处理**。v3.0 补上多任务域兼容层，并**修正 v2.0 的一处设计错误**。
> 全部现状数字为本轮实测。

---

## 0. 先说结论

**能兼容，但 v2.0 有一句写错了，必须改。**

| 问题 | 结论 |
|---|---|
| 知识问答、系统管理会被流水线拖累吗？ | **不会** —— 它们已在编排黑名单里，实测走直答 |
| 报告生成、变更影响分析能接入吗？ | **能**，且**不该塞进流水线**，应作为旁路消费建模产物 |
| v2.0 有错吗？ | **有** —— 「N6 是唯一落库出口」写窄了，实测 write 工具 7 个只有 2 个属建模 |

### 0.1 v2.0 的错误（实测发现，靠推理发现不了）

v2.0 §1.2 写「**N6 是唯一落库出口**」。实测：

```
write 工具共 7 个：entity_create / zhiyuan_sysmlv2_import / file_write /
                   file_append / file_mkdir / report_export / mbse_pull_ingest
建模相关只有 2 个：entity_create / zhiyuan_sysmlv2_import
```

**其余 5 个是跨域写**（文件操作、报告导出、知识拉取）。若按 v2.0 字面实施，会给非建模任务凭空加一道建模门禁 —— 报告生成完文件还要先跑 `methodology_resolver` 才能落盘，这是错的。

**修正**：N6 是「**模型图谱实体（entities/relations）的唯一落库出口**」，而非「唯一写出口」。

### 0.2 第二个发现：`intent_keywords` 实际未使用

实测 19 个 active Agent 的 `intent_keywords` **全部为 0 条**，而 v1.0/v2.0 的所有新 Agent 定义都认真填了 `intent_keywords`。

真相是：关键词路由的唯一来源是 `agents.intent_keywords`（`intent.py:148` `_kw_layers`），但**库里一条都没填**，实际靠 `INTENTS` 语义向量 + LLM 裁决兜底。

**含义**：v1.0/v2.0 里的 `intent_keywords` 字段是**正确的设计方向但当前无效**。落地时必须同时确认路由侧是否已消费该字段，否则写了也不生效。

## 1. 五任务域划分

### 1.1 任务域与路由

| 任务域 | Agent | 是否走流水线 | 门禁需求 | 依据 |
|---|---|---|---|---|
| **建模域** | M0→N1..N6 | ✅ 全程 | 阶段顺序 + 唯一图谱落库口 | 产出模型文件与图谱元素 |
| **知识问答域** | `knowledge_qa`(9 图谱工具) / `chat`(MCP文档解析) | ❌ 直答 | 无 | 零建模产物 |
| **系统管理域** | `system_mgmt`(6 个 `sys_*`，**全 read**) | ❌ 直答 | 无 | 与建模零交集 |
| **报告生成域** | `report_generation`（⚠️ 实测 **0 工具绑定**） | 🔀 **旁路** | 无（消费已校验产物） | 报告是建模产物的投影 |
| **变更影响域** | `impact`(L1，5 工具已绑) | 🔀 **旁路** | HIL L1 | 能力已在库，v2.0 只是接进删除路径 |

### 1.2 编排黑名单已有前三项

`orchestration.py:19` 实测：

```python
_ORCH_EXCLUDE_INTENTS = ("chat", "system_mgmt", "requirement_quality")
# 注释原文：chat=通用入口本身就该直答；system_mgmt=系统数据查询（单任务）；
#           requirement_quality=单交付物质量分析（execute 里有专门双通道，不编排）
```

**这三项已经在黑名单里，说明现有架构早就承认「不是所有任务都该进流水线」**。v3.0 只是把这个既成事实显式化。

### 1.3 四个非建模域的详细处理

#### 域 A：知识问答（`knowledge_qa` / `chat`）

| 字段 | 值 |
|---|---|
| 是否进流水线 | **否**，直答 |
| 是否需 M0 方法论 | **否** —— 回答"什么是 MBSE"不需要知道客户用 MagicDraw 还是 SysML |
| 是否需门禁 | 否 |
| 工具 | `knowledge_qa` 已绑 9 个（coverage_matrix / gap_summary / graph_db_nlquery / graph_db_query / graph_db_stats / graph_retrieve / modeling_coverage / scene_coverage / trace_chain_check）；`chat` 绑 MCP-文档解析 + graph_retrieve |
| 风险 | **`gap_summary` 在 knowledge_qa 上有语义冲突** —— 它是建模域 N5 的工具，要求「必须最后调、必须消费前三者结果」。单独调用会遗漏 |

**处置**：给 `knowledge_qa` 绑 `sysml_trace_coverage_analysis` skill，约束 gap_summary 的调用序；或从该 Agent 解绑 `gap_summary`（问答场景不需要"缺项汇总"）。**建议后者，更干净**。

#### 域 B：系统管理（`system_mgmt`）

| 字段 | 值 |
|---|---|
| 是否进流水线 | **否**，直答 |
| 是否需 M0 | 否 |
| 工具 | 6 个 `sys_query_*`，**全部 read 工具，零副作用** |
| 风险 | **`sys_*` 被绑给了 12 个 Agent**（含 8 个视图 Agent + 工程建模方案设计 + 预评审），不只是 system_mgmt |

**实测发现的风险**：`sys_query_audit` / `sys_query_convs` 暴露在 8 个视图 Agent 上。虽为 read，但会挤占工具预算（33 个工具里占 6 个），且 JI 语义预筛（`tools.py:178`）`core_keep_extra` 若含它们，会挤掉建模工具的注入位。

**处置**：建模节点（v1.0/v2.0 的 8 个节点）**一律不绑 `sys_*`**；并把 `sys_*` 从 `tool_jit.core_keep_extra` 移除。

#### 域 C：报告生成（`report_generation`）—— **实测缺口**

| 字段 | 值 |
|---|---|
| 是否进流水线 | **否**，作为**旁路**消费建模产物 |
| 是否需 M0 | 否 |
| 绑工具 | **实测 0 个**（`group_concat` 返回 `None`） |
| 工具表里的 `report_export` | **未绑给任何 Agent** |

**这是实测发现的真实缺口**：报告生成 Agent 没有任何工具，只能纯文本输出。

**处置**：绑 `report_export` + `graph_db_query` + `coverage_matrix`。并加一条关键约束：

```
报告 Agent 只消费已有建模产物（TraceMatrix / ViewBundle / ValidationResult），
禁止自行重跑建模流水线。
```

理由：报告是**建模产物的投影**，不是新的建模活动。重跑会（a）浪费 token（b）产生与图谱不一致的第二份事实。

#### 域 D：变更影响（`impact`）—— **能力已在，只差接线**

| 字段 | 值 |
|---|---|
| 是否进流水线 | **否**，独立触发 |
| 绑工具 | 5 个已绑（graph_db_nlquery / graph_db_query / graph_retrieve / impact_analyze + skill「前端验证SkillD4」） |
| HIL | L1（需人工确认） |
| 与 v2.0 的关系 | v2.0 的 G `change_safety_gate` **不是替代它，是复用它** |

**关键澄清**：v2.0 新增 G 节点容易造成误解（"又加了一个影响分析 Agent"）。正确关系是：

| | `impact` Agent（已有） | G `change_safety_gate`（v2.0 新增） |
|---|---|---|
| 触发 | 用户显式问"改了 X 影响谁" | 流水线内检测到破坏性操作 |
| 位置 | 独立入口，可单独用 | N5 之后的条件节点 |
| 输入 | 任意元素 | pipeline 的 `operation` 槽位 |
| 输出 | 影响面报告 | `proceed_allowed` 判据（门禁语义） |

**建议**：`change_safety_gate` 绑 `impact_analyze` 但**不绑任何其他工具**，保持轻量；复杂影响分析仍路由到 `impact` Agent。

## 2. 统一入口：三标识决定走哪条路

### 2.1 顶层分流（新增，早于 M0）

```
用户请求
  ↓
[三标识解析] operation / target / location
  ↓
┌─────────────────────────────────────────┐
│ operation 是否属于建模域？                │
├──────────┬──────────┬─────────┬──────────┤
│ 建模动作  │ 只读分析  │ 系统查询 │ 报告/影响 │
│ ↓        ↓          ↓         ↓        │
│ M0→N6   │ 直答Agent │ 直答    │ 旁路Agent │
│ 流水线    │ (无门禁)  │ (无门禁) │ (无建模) │
└──────────┴──────────┴─────────┴──────────┘
```

**关键**：`operation` 的判定复用 v2.0 的 `intent_slots.operation` 枚举，**不新增字段**。映射规则：

| operation | 域 | 通路 |
|---|---|---|
| `create` / `modify` | 建模 | **M0 → N1..N6** |
| `verify` | 建模 | M0 → N3(已有视图) → N4 → N5 |
| `delete` / `refactor` | 建模 | M0 → G（安全门）→ 视情况 N6 |
| `analyze` / `explain` | 视 target | target 是模型元素 → 知识问答域；否则直答 |
| `view` | 建模 | M0 → N3(该 view_type) → N4 |
| （系统类） | 系统管理 | **直答 system_mgmt** |

### 2.2 M0 只在建模域触发

**这一点必须写进实现约束**：

```
M0 methodology_resolver 的触发条件 = operation ∈ {create, modify, verify, delete, refactor, view}
                                        AND target ∈ 建模元素集

若 operation=analyze/explain 或 target 非建模元素 → 跳过 M0，直接进对应域
```

理由：回答「SysML 2 是什么」「帮我看看有谁有权限」不需要解析方法论。**M0 无条件前置会凭空增加一次 LLM 调用 + 一次 profile 加载。**

### 2.3 门禁的适用边界

| 门禁 | 适用域 | 不适用域 |
|---|---|---|
| 阶段顺序（M0→N6） | 建模 | 其余全部 |
| `sysml_v2_validate` | 建模 N2/N3/N4 | 其余全部 |
| 追溯覆盖率阈值 | 建模 N5 | 报告（只引用数值，不判定） |
| 变更安全门 G | 建模的破坏性操作 | `impact` Agent 独立调用时**不强制** |
| HIL L2 人工确认 | **不限于建模** —— 已全局生效 | — |
| RBAC + 写意图闸 + Hook | **不限于建模** —— 已全局生效 | — |

**这一节很重要**：权限链（`tools.py` RBAC → `tool_hooks` → HIL L2 → destructive）是**平台级基础设施，与任务域无关**。所以非建模任务的安全保障**不需要新建机制**，只需确保不误绑 write 工具。

## 3. Agent 定义补充：新增 `task_domain` 字段

### 3.1 字段设计

```sql
ALTER TABLE agents ADD COLUMN task_domain TEXT DEFAULT 'general';
-- 取值：modeling | qa | system | report | impact | general
```

| task_domain | Agent | 是否进流水线 | 是否需 M0 |
|---|---|---|---|
| `modeling` | M0, N1..N6, G | ✅ | ✅（M0/G 除外） |
| `qa` | `knowledge_qa`, `chat` | ❌ | ❌ |
| `system` | `system_mgmt` | ❌ | ❌ |
| `report` | `report_generation` | ❌ 旁路 | ❌ |
| `impact` | `impact` | ❌ 旁路 | ❌ |
| `general` | 其余 builtin | ❌ | ❌ |

**与 `stage_order` 的关系**：
- `task_domain='modeling'` **且** `stage_order` 非空 → 流水线节点
- `task_domain='modeling'` **且** `stage_order` 为空 → 独立触发的建模 Agent（如 `impact`）
- `task_domain != 'modeling'` → 一律不进流水线（`stage_order` 强制为 NULL）

**回填规则**：现有 19 个 active Agent 全部显式赋值，**不猜**。`8个视图 Agent` 标 `modeling`（迁 disabled 前），`design`/`requirement_analysis` 标 `modeling`（将迁入 N1/N2），其余按上表。

### 3.2 平台级 Agent（不属任何域）

`MBSE建模总体负责人`（id=160）设 `task_domain='modeling'` + `agent_role='main'`。它**只调度建模域**，不接管其他域 —— 其他域由会话入口路由直接命中对应 sub Agent。

⚠️ 风险：若主 Agent 的意图识别能力覆盖全意图，可能把系统管理请求也吸进编排。**处置**：`team_router` 已按主 Agent 名册（v2.0 收敛为 8 节点）路由，名册外的意图走 C4/C2/C3 档直答 sub Agent。

## 6. v3.0 落地增量（在 v2.0 的 14 项之上）

| 序 | 事项 | 收益 | 成本 | 优先级 |
|---|---|---|---|---|
| **V1** | `task_domain` 字段迁移 + 19 个 Agent 显式回填 | 高 | 低 | P0 —— 不做则分流无法实现 |
| **V2** | 顶层分流逻辑（三标识 → 域 → 通路） | 高 | 中 | P0 |
| **V3** | `report_generation` 补绑工具 | 中高 | 极低 | P0 —— 修实测缺口 |
| **V4** | `knowledge_qa` 解绑 `gap_summary` | 中 | 极低 | P0 —— 修语义冲突 |
| **V5** | `sys_*` 从建模节点解绑 + 移出 `core_keep_extra` | 中 | 低 | P1 |
| **V6** | 跨域 skill 的「只解释不生成」iron_rules | 中 | 低 | P1 |
| **V7** | 确认 `intent_keywords` 路由侧是否消费 | 高 | 低 | P0 —— 写了不生效等于没写 |

**V7 特别说明（2026-10-08 实测后更正）**：~~v1.0/v2.0 认真填的 `intent_keywords` 目前是**死字段**（库里 19 个 Agent 全空）~~ → **此判断有误**。

实测：库里 `intent_keywords` **本来就有 112 个词、19/21 条非空**（`design` 10 词、`knowledge_qa` 15、`system_mgmt` 13、8 个视图 Agent 各 3 词……），仅主 Agent 与测试 Agent 为空数组（符合预期）。
**误判根因**：我用 `isinstance(r[4], list)` 判断，而 sqlite3 对 JSON 列返回的是 **`str`**，故恒为 False，被误读成"全空"。

**V7 仍撤销，但理由改为三条**：
1. 路由基线**已达标**：内置集 accuracy=1.000、真实样本池 44 条 accuracy=0.955 / macro-F1=0.965（门禁 `tools/verify/verify_intent_routing_baseline.py`）。
2. 8 个视图 Agent 名称近义，`_kw_score` 的「长词优先」会让它们**互抢** —— P1-13/P1-14 反复加守卫正为防此。
3. 现有 2 个错例是 `design ↔ review` 语义摇摆，填词会把错例**固化成系统性错误**。
