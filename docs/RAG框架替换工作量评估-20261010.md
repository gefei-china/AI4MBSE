# RAG 框架替换 · 工作量评估（2026-10-10）

> 结论先说：**能替换，但不该"整体替换"**。
> 推荐**路线 A（只换解析/切片）**：3~5 天、风险最低、回退成本≈0，且拿到了框架最大的价值（文档解析）。
> 若坚持整体替换 RAGFlow：6~8 周，且要接受三条硬门槛（见§4）。

---

## 1. 实测的耦合面（不是估的）

| 项 | 实测值 | 位置 |
|---|---|---|
| `GraphRAG().retrieve()` 调用点 | **13 处** | 生产 6（`stream.py:1584` / `execute.py:259` / `tools.py:725,747,760` / `routers/knowledge_parts/pipeline.py:798` / `routers/mcp_gateway.py:137`）+ 评测 7 |
| 检索相关配置项 | **30 个** | `rag` 8 / `context` 9 / `embedding` 6 / `memory` 2 / 其他 5 |
| `retrieve()` 返回契约 | **17 个键** | `chunk_hits`(8次消费) / `source`(7) / `vector_count`(5) / `graph_count`(5) / `confidence`(5) / `attachment_hits`(5) / `route`(4) / `entities` / `relations` / `memory_hits` / `knowledge` / `kb_scope_warn` / `route_reason` / `vector_docs` … |
| 待迁移数据 | 分块 **6,727** / 文档 **12** / 实体 **189** / 三元组 **137** / `entity_versions` **189** / `sysml_versions` **262** | `mbse.db`（只读实测） |

★ **17 键契约是替换的核心成本**：任何框架的返回结构都不是这17 个键，
必须写适配层把框架输出映射回来，否则 13 个调用点全要改。

## 2. 不可替代的部分（框架换不掉）

`entities` 表 **27 列**，其中这些是 **MBSE 工程治理语义**，不是 RAG 检索问题：

| 列| 语义 | 通用框架有无 |
|---|---|---|
| `valid_from` / `valid_to` / `is_current` | **双时态**（业务时间 + 事务时间） | ❌ 无 |
| `review_status` / `reviewed_by` / `review_decision` | 人工**审核流** | ❌ 无 |
| `sysml_version_id` / `canonical_id` | 模型**版本对齐** | ❌ 无 |
| `graph_x` / `graph_y` | 画布**布局坐标** | ❌ 无 |
| `confidence` / `source_type` / `branch` | 证据强度与来源治理 | 部分（通常只有一个 score） |

⇒ 换框架后这层**仍要自研**，框架只接管"文档 → 分块"和"检索打分"。

## 3. 当前真正的瓶颈（换框架不解决）

`query_routing_stats` 实测 1,188 次查询：

| 路线 | 次数 | 置信均值 | graph | vector |
|---|---|---|---|---|
| graph | 202 | **0.87** | 5.4 | 0 |
| mixed | 63 | 0.56 | 2.0 | 8.4 |
| **vector** | **923** | **0.15** | 0 | 16.1 |

⇒ **78% 的查询走向量路线，而它的置信均值只有 0.15。**
根因在两处（**都在自研侧**）：
1. `vector_index.py:4` —— embedding 以 **JSON 文本**存储，检索时**逐行 `json.loads`** + 双重 sqrt；
2. 没有真正的 ANN 索引（6,727 行全表扫）。

⇒ 换 LlamaIndex + 真正的向量库**能改善这一项**，换 RAGFlow（也是自建索引）
**不一定改善** —— 它解决的是解析，不是索引。

## 4. 三条路径的工作量

### 路线 A ·只换「文档解析 + 切片」（★推荐）

**做法**：保留全部自研检索/图谱/编排，只把 `knowledge_pipeline/extract.py` +
`chunking.py` 的输出换成 RAGFlow 的 DeepDoc 解析结果（通过它的 HTTP API）。

| 项 | 评估 |
|---|---|
| 工作量 | **3~5 天**（适配层 1 模块 + 双跑对比+ 判据脚本） |
| 风险 | 低。回退成本≈0（一个开关） |
| 收益 | 拿到框架最大价值：**复杂 PDF / 扫描件 / 表格**解析（实测当前OCR 慢 50~200 倍/页） |
| 铁律 4 | ⚠️ 仍需 Docker + ES + MySQL + Redis ⇒ **要么破例、要么这条也不做** |

⚠️ **路线 A 的隐藏门槛**：RAGFlow 要 **4核/16GB/50GB 磁盘 + Docker 24+ / Compose 2.26+ / x86**
+ `vm.max_map_count ≥ 262144`。这**与 AGENTS.md 铁律 4（私有化离线、不引外部依赖/构建链）冲突**。
⇒ 若铁律不可破，路线 A 需改为"**只借鉴它的解析算法**"（MinerU / Docling 思路），而非部署整套。

### 路线 B · 换检索内核，保留自研编排与图谱

**做法**：LlamaIndex / 自建向量库（sqlite-vec、FAISS、Qdrant）替换 `vector_index.py`，
外面套一层适配器维持 17 键契约。

| 项 | 评估 |
|---|---|
| 工作量 | **3~4 周**（适配层 + 30 个配置项映射 + 保住双时态/审核语义 + 回归） |
| 风险 | 中。**换了库，置信度未必改善**（要靠 ANN + 重排才有实际收益） |
| 收益 | 解决 §3 的真实瓶颈（0.15 置信 + 全表扫） |
| 铁律 4 | 纯库依赖（sqlite-vec 是C 扩展、FAISS 是 C++）⇒ 相对可控，**不需 Docker** |

### 路线 C · 整体替换为 RAGFlow（你说的"直接替换"）

| 项 | 评估 |
|---|---|
| 工作量 | **6~8 周**（适配层 + 迁数据 + 双跑 + 全量回归） |
| 硬门槛 1 | **4 核/16GB/50GB + Docker 24+ / Compose 2.26+ / x86**（无 ARM64 镜像） |
| 硬门槛 2 | compose 要起 **RAGFlow + MySQL + Redis + 对象存储 + Elasticsearch** |
| 硬门槛 3 | ★ **v0.27 已从 UI 移除 GraphRAG 与 RAPTOR** ⇒ 图谱能力要靠 `knowledge compilation` 重建 |
| 回退成本 | **高**（数据已迁走，回退要迁回） |
| 结论 | **不建议**。它解决的是"文档问答"，你的核心资产是"图谱 + 追溯 + 审核 + 版本" |

## 5. 我的建议（供拍板）

若目标是"**用成熟框架把检索质量提上去**"⇒ **路线 B**（3~4 周，纯库依赖不破铁律，直击 0.15 置信瓶颈）。
若目标是"**省掉自研维护成本**" ⇒ 先算一笔账：自研检索栈（`knowledge_engine.py` 24.7KB +
`agent/rag.py` 48KB + `vector_index.py` + `fts_search.py`）**约 8 万行字符、零第三方依赖**，
维护成本其实是**零依赖升级负担**，换框架反而引入版本升级/兼容性负担。

⇒ **推荐组合**：**路线 B 优先**（提质量），**暂不做路线 A/C**（破铁律 + 换不回图谱）。

## 6. 无论选哪条，建议先做的一件事（1~2 天）

**先建检索质量基线**，否则换完无法判断"变好还是变坏"。

⚠️ **实测澄清（避免推荐不存在的工具）**：
- `tools/eval/probe_qrel.py`（2.8KB）**不是 nDCG 评测工具**——
  它是「`_graph_confidence` 相关性因子（qrel）**可行性探测**」，
  只算 "query-bigram 在命中实体文本中的覆盖率（qrel）"，看两组分布是否可分。
- **真库里没有任何 qrel / 相关性标注表**（实测 `qrel`/`qrels`/`retrieval_qrel`/`search_qrel` 均不存在）。
- `tools/eval/calibrate_routing.py`（11.5KB）是**路由阈值标定**，不是检索质量评测。

⇒ 所以**基线目前不存在**，需要新建：

| 步骤 | 内容 | 产出 |
|---|---|---|
| 1 | 选 30~50 条**真实查询**（从 `messages` 表的用户提问里抽，不手编） | 查询集 |
| 2 | 人工标注每条的**相关 chunk_id**（建议 2~3 位标注者取交集，先小样本） | qrel 文件（JSON/CSV） |
| 3 | 写 `tools/eval/retrieval_bench.py`：算 Recall@k / MRR / nDCG@k | **基线数字** |
| 4 | 固化成门禁（`tools/verify/verify_retrieval_regression.py`），改检索逻辑必须过 | 回归保护 |

⚠️ **没有基线就换框架 = 无法证明收益**，
这是本工程既有门禁方法论（`tools/verify/*` + 变异自证）最看重的一环，
也是我上面所有"能改善/不一定改善"判断的**前提**。

## 7. 需要米爸拍板的三个点

1. **铁律 4 能不能破？**（是否允许引入 Docker + ES + MySQL + Redis）
   - 不破 ⇒ 只能走**路线 B**（纯库依赖）
   - 可破 ⇒ 路线 A/C 才成立
2. **目标是"提检索质量"还是"省维护成本"？** 两者对应不同路线（见 §5）。
3. **能否接受"图谱层仍自研"？** 无论选哪条，`entities` 27 列的
   双时态/审核/版本语义都没人能接管 —— 这部分工作量在任何方案里都省不掉。
