## 3. P0 · 影响"结论可信度"的三项

> 这三项的共同后果：**你能跑的每个数字都可能被污染或无法归因**。它们不是功能缺陷，是"度量地基"缺陷。

### 3.1 测试/探针数据混入生产统计

| 证据 | 实测值 | 影响 |
|---|---|---|
| `fake_tool` 调用 | **126 次**（近 7 天），失败 112（89%） | `tool_call_logs` 失败率虚高 |
| `fake_tool` 记的 latency | **1,793,164,758,196 ms**（≈ 56 年） | 任何 `AVG(latency_ms)` 统计报废 |
| `definitely_not_a_real_tool_xyzzy` | **14 次** | 同上 |
| `chat_probe` | **1,186 次**，`prompt_tokens` 19,793,861 | 占近 7 天 LLM 成本 **0.9043 / 1.7716 = 51%** |
| `conv=1` 的 error span | **60 次**，平均耗时 **1.0 ms** | 会话错误率被算成 31%，真实值约 **7.5%** |

**后果链**：`tool_call_logs` 全量失败率 15.0%（559/3,716）看起来是"工具很不可靠"，其中 **140 次是假工具**；剔除后真实失败率约 **11.8%**（419/3,576）——量级不同，处置方式也不同。

**建议（低成本）**：给 `tool_call_logs` / `llm_usage_stats` 加 `is_probe` 标记（或写独立库），所有统计与看板默认排除；探针工具名统一前缀（如 `_probe_`），在写入侧硬拒非前缀的假工具名。

### 3.2 工具调用因参数不符 schema 失败（真实失败的主因）

近 7 天失败 264 次按 `failure_kind`：`internal` **137**、`permission` 89（其中 **84 是 fake_tool**，测试噪声）、`business` 35、`transient` 3。

`internal` 137 次的真实构成（剔除测试工具后）：

| 工具 | 次数 | 错误 |
|---|---|---|
| `query_data_tree` | 22 | `INVALID_ARGUMENTS` |
| `query_projects` | 8 | `INVALID_ARGUMENTS` |
| `search_model_elements` | 8 | `INVALID_ARGUMENTS` |
| `file_list` | 7 | `INVALID_ARGUMENTS` |
| `get_modeling_capabilities` | 5 | `INVALID_ARGUMENTS` |
| `requirement_itemize` | 5 | `INVALID_ARGUMENTS` |
| `ask_user` | ≥3 | `缺少 question（要问的问题）` |

原始报文：`{"code":"INVALID_ARGUMENTS","message":"参数不符合工具定义；按 fields 提示修正字段后重新调用","retryable":false}`

**判读**：`retryable:false` 意味着**模型没法通过"再试一次"救回来**，只能靠喂回"可用字段清单"。这类失败是纯 token 与轮次浪费，且当前不区分"可重试/不可重试"。

**建议**：① 参数错误回喂时附带该工具 `required` + `fields` 的**最小值域清单**（不是整份 schema）；② 对 `INVALID_ARGUMENTS` 计入"不可恢复"，直接终止该工具分支而非重试。

### 3.3 会话级失败零归因（73 次失败查不到原因）

`orch_run_spans` 近 7 天：`conversation` ok 160 / **error 73**。但 `meta_json` **全部是 `{}`**。

| 真实失败（剔除 conv=1 噪声 60 次） | 耗时 |
|---|---|
| conv 9630 | **399,412 ms**（6.7 分钟） |
| conv 9632 | 269,346 ms |
| conv 9709 / 9722 / 9723 | 118,374 ~ 119,300 ms（三段高度一致，疑似同一固定阈值） |
| conv 9660 ~ 9664 | 28,341 ~ 40,211 ms |

**根因（代码）**：`services/orch_span.py::flush()` 对未闭合 span 会 `status="error"` 且 `meta.setdefault("note","unclosed_at_flush")`；实测 73 条里**没有一条带 note**，说明是**被显式 `close(status="error")` 但未传 meta** 的路径——错误原因在写入侧就丢了。

**后果**：`conversation` 是用户可见的最高层失败，却**没有任何一条能回答"为什么失败"**。这直接导致排查只能靠翻日志猜。

**建议**：① `close()` 在 `status != "ok"` 且 `meta` 为空时**强制写入** `{reason, stage, err_type}`；② 把 `119,3xx ms` 这一簇单独归因为"超时"，与业务异常分开计。

## 8. 局限声明（必须与结论一起读）

1. **样本量小**：近 7 天真实用户消息 **168 条**，`graph` 路由样本仅 **8 次** ⇒ 不足以判定"图检索无效"，只能判"图召回未生效/触发率低"。
