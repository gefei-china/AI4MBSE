# 「刷新后环节全丢 / 答复不见了」根因（2026-10-30 18:30）

## 0. 用户看到的现象

> 上一轮失败后，刷新页面 AI 只有这点内容了，之前这么多环节的内容都不见了
> ⚠️ 本轮未产出正文内容　原因：AttributeError：'LoopGuard' …

## 1. 先排除「数据真的没了」

| 检查 | 结果 |
|---|---|
| `messages` 表 | **11 条全在**：5227（18611 字）/ 5254（5689 字）/ 5260（4109 字）/ 5262（147 字） |
| `/api/conversations/9779/messages` | 11 条全返回，`card_data.exec` 也在（22382 / 8685 字） |
| `orch_stream_events` | 该轮 19 条事件（stage / tool）都在 |

⇒ **库没丢、接口没截断**。丢的是**呈现**，而且是两个独立缺陷叠加。

## 2. 缺陷 A（主因）：失败轮固化时，`card_data` 写死 `"{}"`

`agent/pipeline_parts/stream.py` 的 `_persist_partial_stream`：

```python
conn.execute("INSERT INTO messages (... card_data) VALUES (?,?,?,?,?)",
             (conversation_id, "assistant", text, "text", "{}"))   # ← 恒为空卡
```

而前端历史还原**只认 `card_data.exec`**（`05-markdown.js` 的 `_procHtmlNow`：
`(cd && cd.exec) ? procBlocksHtml(cd.exec) : ''`）。

⇒ 那一轮 `_lg` 循环里跑的意图识别 / 22 次工具调用 / 阶段卡片，
**在线时靠 SSE 现场渲染，一刷新就因为没有 `exec` 而全部消失**，只剩那句说明。

**判据（真机，同一会话内对照）**：

| 消息 | 类型 | `card_data` | 刷新后执行过程 |
|---|---|---|---|
| 5227 | 成功轮 | 带 `exec`（22382 字） | ✅ 有 |
| 5260 | 成功轮 | 带 `exec`（8685 字） | ✅ 有 |
| **5257 / 5262** | **失败轮** | **`{}`** | **❌ 全无** |

更糟的是那句文案：**「本轮的执行过程（工具调用 / 阶段）已记录」** —— 它在撒谎。
这次不是"没实现"，而是"实现了、也写了提示，就是没存"。

## 3. 缺陷 B：`_clarify_prev` 合并把 clarify 消息的**正文**丢了

`03-chat.js` 的 `_mergeClarifyTurns` 把 `msg_type='clarify'` 并入后一条 assistant 消息，
`05-markdown.js` 只渲染它的 `questions` / `answered`（确认环节卡片），
**从不渲染 `content`**。

真机实证：msg 5254 是 `clarify` 类型，正文 **5689 字**（「针对上一轮遗留的两大阻塞项，
我立即启动执行清单……」整段排查结论）。合并后页面只剩 **311 字** —— 5689 字整段蒸发。
它没被发现，是因为这条 clarify 同时是**实质答复**（不只是提问）。

## 4. 修复

| # | 文件 | 改动 |
|---|---|---|
| A1 | `stream.py` | `_persist_partial_stream` 新增 `exec_card` 参数；把快照**嵌在 `{"exec": {...}}`** 下写库（顶层写等于白写，见 §6）；文案按"到底存没存"分岔 |
| A2 | `stream.py` | 新增模块级 `_partial_exec_card(scope)`：与成功路径同构（reasoning / notices / tools / agent / brief / gates），传 `locals()` 进来自带 fail-safe；三个 except 出口全部接上 |
| A3 | `tools/_backfill_exec_card.py` | 修复前已写空的历史消息，从 `tool_call_logs` + `orch_stream_events` **按相邻消息切窗**重建（默认预演、只填空卡、幂等） |
| B | `03-chat.js` | 合并时把 clarify 正文并入后继消息；**纯占位语（以 `⏸` 开头）不并**，避免与确认卡重复 |

## 6. 过程中自己踩的坑（都写进代码注释了）

1. **`card_data` 顶层 vs `.exec`**：第一版把 `exec` 字段摊在 `card_data` 顶层 ⇒
   库里"有数据"、页面"什么都没有"。被 `verify_partial_exec_persist` 的 P2 断言抓出。
   这是"看起来已经修了"的典型形态。
2. **两张表时区口径不同**：`messages`/`tool_call_logs` 是 **UTC**，
   `orch_stream_events`/`orch_run_spans` 是**本地时间（+8）**。
   回填脚本第一版用同一窗口查 events ⇒ 恒 0 行 ⇒ 回填结果"只有工具、没有阶段"，
   而且完全静默。现按本机偏移两窗口各查一次取命中多的。
3. **`tool_call_logs` 没有 `error` 列**（只有 `result` / `failure_kind`）：
   照着前端 schema 的字段名写 SQL 直接 `OperationalError`。
4. **E2E 夹具打早了**：第一版按"第 N 次 LLM 调用"抛异常 ⇒ 炸在 `CHAT_TASK_PROBE`，
   那时 `exec_tools` 还是空的 ⇒ 断言恒红，看着像"修复没生效"。
   判据改成"**历史消息里已出现 tool 结果**"，等价于"至少一个工具真的跑过"。
5. **夹具选错意图会伪装成缺陷**：`chat` 意图的白名单不含 `sysml_stdlib_meta` ⇒
   工具被最小权限拒掉、走"跳过"分支、不进 `exec_tools`。改用 `view_expansion`。

## 7. 防复发

- `tools/verify/verify_partial_exec_persist.py`（真链路，本机真库，不进 CI）：
  P1 落库 / P2 **exec.tools 非空** / P3 文案与事实一致 / P4 JSON 合法 /
  M 变异（摘掉 `exec_card` ⇒ P2、P3 必红）。
- 回填脚本 `--apply` 前强制预演，且**幂等**（已有 exec 一律跳过）。

## 8. 遗留

- 修复前**已写空**的历史消息只能靠回填补"工具 + 阶段"，补不回模型当时的完整 CoT
  （`exec.reasoning` 多数为空 —— 那条通道本来就没落过库，不是本次丢的）。
  回填数据里带 `"backfilled": "..."` 标记，事后能分清"当时真存的"与"事后还原的"。
- 历史 clarify 消息若正文以 `⏸` 开头但其实是真实答复（占位语缀在长正文前），
  会被判为占位而不合并 —— 当前库内无此形态（已核 5254/5259 两条）。
