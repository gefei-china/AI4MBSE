## 三、发现的缺陷：能力中心账本对 `plugin` 类**结构性假阴性**（已修）

### 3.1 现象（修前，实测）

```
/api/capabilities/ledger → plugin 127 行：unused 126 / in_use 1
   agent-735（智源对接agent）  verdict=unused  calls=0   entries=[]
   file-ops（文件操作）        verdict=unused  calls=0
   唯一 in_use 的：validate    verdict=in_use  calls=24  src=name
```

`agent-735` 在 `orch_stream_events` 里有 **1491 条事件**，是全平台最常执行的执行主体；
`file-ops` 对应「文件操作」技能，`use_stats.uses=13`。而唯一被判"在用"的 `validate`，
只是因为**某个插件恰好叫这个名字**，被 `usage_by_name` 撞上。

### 3.2 根因

`build_ledger` 只对 `kind ∈ {skill, mcp_tool, mcp_server}` 做了专用入口匹配；
`kind='plugin'` 落到 else 分支按**工具名**查用量，而插件的 `display_name` 是**插件名**
（`agent-735`/`file-ops`），与 `tool_call_logs.tool_name`（`query_projects`/`file_read`）**永不相等**
⇒ `calls=0`、`entries=[]` ⇒ verdict 恒为 `unused`。

**这正是该模块 docstring 自己警告的"治理视图与事实相反"**，只不过这次发生在它自己的 plugin 分支上。

### 3.3 修法

新增 `core/capability_effective.py::collect_plugin_usage(conn)`：按**插件类型**解析到运行时行后取真实用量。

| 插件类型 | 用量来源 |
|---|---|
| `tool` | `tool_call_logs`（按 legacy 工具名） |
| `skill` | `skills.use_stats.uses` |
| `agent` | `orch_stream_events.agent` + `messages.card_data.exec.agent`（`name` 与 `display_name` **都算**——事件里存的是显示名） |
| `mcp` | 该 server 全部工具在 `tool_call_logs` 的合计 |
| `prompt` | **没有用量事实源** ⇒ verdict=`unknown`（"无可判据"），不谎报"未使用" |

前端 `50-capregistry.js` 同步加 `unknown: '无可判据'` 一档；KPI 卡片在存在 unknown 时标注数量
（此前 prompt 类与"真没人用"同显「未使用」，用户会把还在用的 prompt 当垃圾清掉）。

### 3.4 修后（实测）

```
plugin 127 行：in_use 80 / unused 22 / unknown 25
   agent-735       in_use   calls=1591
   file-ops        in_use   calls=13
   zhiyuan-dev-mcp in_use   calls=668
   validate        in_use   calls=38
   prompt-86       unknown  calls=0
整体 matrix：in_use 150 / declared_unused 75 / runtime_only 12 / unused 25 / unknown 25
```

### 4.1 页面本身：正常

| 检查项 | 结果 |
|---|---|
| 渲染入口 | `static/js/mods/35-ctxconfig.js`，`GET /api/system/config/schema` 取元数据 |
| 覆盖 | **58 字段 / 7 段**（rag / context / memory / embedding / agent / extract / vision） |
| 类型对齐 | 58 字段全部是 `int/bool/float/str`，**无 dict/secret/url**（渲染分支只处理这 4 种，是对的） |
| schema 一致性 | 簇里登记的键 **全部存在于 CONFIG_SCHEMA**（0 个幽灵键） |
| 保存往返 | `PUT /api/system/config/static {"rag.recall_k":26}` → 读回 26；改回 20 → 读回 20 ✅ |
| 拼错防护 | `{"rag.recall_kk":20}` → `ok=false, error=未知配置项: rag.recall_kk` ✅ |
| 布尔即时落盘 | `ctxAutoSaveBool` + `data-prev` 失败回退（2026-10-28 已修） |

### 4.2 缺陷①：11 个 `context_audit.*` 经 settings 表写入**静默无效**（已修）

**实测（修前）**：

| 路径 | 操作 | 结果 |
|---|---|---|
| settings 表 | `PUT /api/system/config/runtime {"context_audit.mcp_min_keep":77}` | `ok=True, updated=[...]`；但 `config.get(...)` 读到 **8** ❌ |
| 配置文件 | `PUT /api/system/config/static {"context_audit.mcp_min_keep":99}` | `config.get(...)` 读到 **99** ✅ |

**根因**：`context_audit.*` 的消费点是 `config.get("context_audit", ...)`（读配置文件 / DEFAULT_CONFIG），
而**全仓不存在 settings 表 → config 的合并**（`runtime_settings()` 只把行读出来给页面看，不回填 `_CONFIG`）。
上一版把它们登记进 `core/setting_keys.py::EXACT_KEYS`，是把「有消费点」与「经 settings 表可达」两个判据混为一谈：
前者真、后者假。

仓库自己的门禁 `verify_settings_data_audit.py --strict` 早就报出来了：
`白名单键 context_audit.* 已无消费点（白名单腐烂，应除名）` × 11 —— 但一直没处理。

**修法**：从 `EXACT_KEYS` 除名（保留 `memory.project_memory_*` 等**真正从 settings 表读**的键）。
注释里写清证据链，避免后人再加回来。

**修后实测**：

```
PUT runtime {"context_audit.mcp_min_keep":77} → ok=False
  error=未知配置键 ['context_audit.mcp_min_keep']（无消费点，写了也不会生效）。合法键：…
PUT static  {"context_audit.mcp_min_keep":8}  → ok=True        （正确入口不受影响）
PUT runtime {"default_branch":"dev"}          → ok=True updated=['default_branch']  （合法键回归）
verify_settings_data_audit --strict：白名单 9 精确键 · 无效键 0 · 双向校验 通过 · exit=0
```

> 影响面：设置页「参数设置」走的是 `/static`（配置文件），所以**界面侧一直是有效的**；
> 本次关掉的是那条"返回成功却什么也没发生"的旁路。

### 4.3 缺陷②：41 个键界面看不到（未修，属功能范围）

`DEFAULT_CONFIG` 有、`CONFIG_SCHEMA` 无 ⇒ `schema()` 不返回它 ⇒ 界面不渲染、`save_override` 也拒绝改。

| 段 | 数量 | 举例 |
|---|---|---|
| `auth` | 9 | `enforce_login`、`mode`、`session_ttl_hours`、`sso_base`、`client_secret` |
| `orchestration` | 9 | `checkpoint_enabled`、`auto_resume_enabled`、`resume_max_attempts` |
| `rate_limit` | 5 | `enabled`、`chat_per_min`、`read_per_min` |
| `jobs` | 4 | `worker_enabled`、`worker_count`、`worker_interval_s` |
| 其它 | 14 | `rag.tenant_isolation`、`runtime.reap_on_startup`、`web_search.provider`、`embedding.quota_block_sec` 等 |

这不是"未生效"（代码里读得到），而是**"改不了"**：只能改配置文件或代码。
其中 `auth.enforce_login`（登录强制）值得单独关注 —— 安全相关开关却没有界面入口。

### 4.4 缺陷③：`agent` 段 16 个键在接口里 `current=null / default=null`（未修）

```
max_tool_rounds      current=None default=None
fill_enabled         current=None default=None
auto_continue_max    current=None default=None
team_member_inherit_mcp current=None default=True   ← 实际生效 True，界面却显示空
```

原因：`DEFAULT_CONFIG` **没有 `agent` 段**（整个段为 `None`），这些键只在 `CONFIG_SCHEMA` 里定义且
meta 未写 `default` ⇒ `schema()` 的回流逻辑拿不到默认值。
后果：界面显示"默认 —"，但代码用 `get(..., 硬编码默认)` 兜底 ⇒ **界面无法反映实际生效值**。

> 注：`harness_max_blocks`/`todo_enabled` 这类 meta 里写了 `default` 的键显示正常。
> 修法有两条：给这 16 个键补 `default`，或给 `DEFAULT_CONFIG` 补 `agent` 段。
> 后者影响面更大（26 个键的取值优先级会变），故本轮**未擅自改**，只记录。

## 五、验证：开关到底有没有生效（行为 A/B）

**为什么不用静态 grep**：本仓配置读取有 **5 种形态**（同行直取 / 段级读取后按键取 /
段名隐含的 `_cfg_get` / 各模块自带小工具 `_gate`·`_cfg_int`·`_mem_cfg_bool` / 键名变量化）。
我的静态探针改了三轮判据，数字从 129 → 81 → …**每修一次就变一次** ⇒ 静态判定不可作为结论。
**能证明"生效"的只有行为**：同一函数、同一输入，配置不同则输出必须不同。

| 开关 | A 值 → 观测 | B 值 → 观测 | 结论 |
|---|---|---|---|
| `intent.speech_act` | True → `knowledge_qa` | False → `design` | ✅ 生效 |
| `intent.multi_same_intent_stage` | True → `['design','design']` | False → `None` | ✅ 生效 |
| `intent.explain_preempt` | True → `knowledge_qa`/`explain` | False → `impact`/`rule_scored` | ✅ 生效 |
| `agent.team_member_inherit_mcp` | True → 31 个工具 | False → 8 个 | ✅ 生效 |
| `context_audit.memory_identity_strip` | True → 注入不含「米巴」 | False → 含「米巴」 | ✅ 生效 |
| `agent.harness_max_stall` | 2 → 2 | 5 → 5 | ✅ 生效 |
| `eval_gates.intent_min_cases` | 20 → 20 | 99 → 99 | ✅ 生效 |
| `skill.improve_idle_days` | 30 → 30 | 7 → 7 | ✅ 生效 |
| `memory.deposit_trigger_enabled` | True → True | False → False | ✅ 生效 |

**9/9 全部生效**。其中 3 个最初被判"无差异"，逐个查明是我的**观测口径错**，不是开关失效：

1. `explain_preempt`：True/False 都会给出 `route=explain`（一个前置短路、一个末尾兜底），
   差异只体现在"中间层能否抢走" ⇒ 必须用会被 `impact`/`glossary` 抢的输入
   （`变更影响分析的用途` → False 时变 `impact`）。
2. `memory_identity_strip`：我直接测了纯函数 `_strip_identity_claim`（它不读配置），
   开关判据在**调用点** ⇒ 必须走 `_build_memory_hint`。
3. `skill.improve_idle_days`：我找错了类名（是 `SkillImprover._cfg`，不是模块级函数）。
