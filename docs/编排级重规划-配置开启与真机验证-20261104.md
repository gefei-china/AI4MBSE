## 1. 配置在哪里设置（三条路径，同一真源）

配置真源是 **`~/.workbuddy/mbse_config.json`**（系统级），生效优先级：

```

  > env
  > system_config_file（就是上面那个 json）
  > DEFAULT_CONFIG（core/config.py 里的默认值）
```

| 路径 | 怎么做 | 适用 |
|---|---|---|
| **前端页面** | 设置 → 🧠 **AI 上下文** → 末尾「🔁 执行中重规划」簇（本轮新增，11 项） | 日常调参，改完即时生效（布尔项改完立即落盘） |

| **改文件** | 直接编辑 `~/.workbuddy/mbse_config.json` 的 `replanning` 段，然后 `POST /api/system/config/reload` | 服务起不来时的兜底 |

**只读接口**：`GET /api/system/config`（当前生效值）、`GET /api/system/config/schema`（54 个分段的元数据，前端表单的数据源）。
**改完生效**：`save_override` 内部 `reload()` ⇒ 即时生效，**不用重启**；`host/port/database.path` 例外（启动级）。

> 本轮所有改动都走 **API**（与前端保存是同一条链路：`save_override` → 写文件 → reload），

## 2. 一个必须纠正的点：`health_probe` 单独开是**空转**

上一轮我给的建议「先开 `health_probe`、`enabled` 保持 False」**是错的**。代码里的闸是：

```python
if _RH_OK and _rp_enabled and (_rp_hp or _rp_early):
```

`_rp_enabled`（总闸）在前 ⇒ **总闸不开，巡检和早停都不会跑**，`health_probe=True` 纯空转。

### 更麻烦的是：总闸一管三件事

`enabled=True` 同时放行三类动作：

| 分闸 | 动作 | 默认 |
|---|---|---|
| `health_probe` / `early_stop` | 巡检（可精修剩余任务 context）、提前收敛 | 关 |
| **`redraw_on_stall`** | **停滞重画（会改计划）** | **开** ⚠️ |
| `user_directive` | 消费 DAG 级用户指令 | 关 |

⇒ **只想"观测 + 早停"、不想重画，必须显式把 `redraw_on_stall` 设为 `false`**，
否则开总闸会连带开启重画。这是**一个总闸管两件事**的配置陷阱。

## 4. 真机验证

同一目标、同一团队（`MBSE建模总体负责人`），两次独立会话：

> 目标：`对某型无人机地面控制站做需求条目化和架构骨架两步，完成后可选给一份评审建议（非必需）。`

### 4.1 阶段 A（只巡检）

| 项 | 值 |
|---|---|
| 会话 | 10019 |
| 计划 | 3 任务：`t1 requirement_analysis`(必需) / `t2 architecture_skeleton`(必需) / `t3 review`(**非必需**) |
| 任务结局 | **3 个全部 done**（`t3` 照跑完） |
| `replan_decisions` | **1 条**：`T0 / none / source=health`，理由「巡检未超阈（M1 50%/M2 0/M4 8%）⇒ 计划仍健康」 |

⇒ 巡检启动、留痕、判定"健康"、**什么都没改**。而改造前这条记录根本不会产生。

### 4.2 阶段 B（加早停）

| 项 | 值 |
|---|---|
| 会话 | 10020 |
| 计划 | 5 任务：`t1~t4` 全为必需，**`t5 review` 非必需** |
| 任务结局 | `t1~t4` done；**`t5` = `cancelled`**，错误信息「目标已达成提前收敛（主动放弃非必需任务）」 |
| `replan_decisions` | **4 条**：3 条巡检 `none` + **1 条 `action=early_stop`** |
| SSE 事件 | 发出 **`plan_revised`** |

`plan_revised` 原文：

```json
{"type":"plan_revised","run_id":576,"level":"T0","action":"early_stop",
 "reason":"required 产出已全部达成（t1,t2,t3,t4）⇒ 提前收敛，主动放弃 1 个非必需任务（t5）",
 "signals":[],"retry_keys":[],"skipped":["t5"]}
```

**这就是编排级 ReAct 的完整闭环**：观察（必需全完成）→ 再决策（早停）→ 调整计划（取消 t5）→ 通知前端。

### 4.3 全库对照

| 时点 | `replan_decisions` 总数 | 构成 |
|---|---|---|
| 本轮之前 | 7 | 4×retry + 3×none，**0 条早停** |
| 本轮之后 | **12** | 4×retry + 7×none + **1×early_stop** |

### 4.4 判定逻辑的确定性验证（13/0）

真机能否早停还取决于**时序**，所以先用纯函数把判定钉死（`tmp/alt_probe/verify_early_stop_logic.py`）：

- 必需全 done + 零 failed ⇒ `action=early_stop`，取消的**只有非必需**
- 有必需未完成 / 有非必需失败 / 无 `required` 标注 / 空计划 / 非必需已完成 ⇒ 一律 `none`（保守）
- `enabled=False` ⇒ `none`（零行为变化）

## 5. 一个真发现：默认 `probe_every_tasks=3` 让早停**几乎不可能触发**

早停判定的时机由 `probe_every_tasks` 决定。而典型计划就是 **3 个任务**（需求 + 架构 + 评审）——
第 3 个任务完成时才巡检，此时**已无剩余任务可取消** ⇒ 早停结构上不可能发生。

⇒ 这不是"逻辑没写对"，是**默认参数与典型计划规模不匹配**。
本轮把它调成 `1`（每完成一个任务判一次）。巡检是纯规则判定（`health_probe_llm=false`，不发 LLM），
成本可忽略；换来的是早停在第一个可行点就能生效。

## 8. 边界（如实登记）

1. **只在流式编排路径生效**：`_planner_core`（非流式 / Flow 节点）**没有 replan**。
   同一句话走两条路径，一条会重规划、一条不会 —— 这是既有口径分裂，本轮未修。
2. **非流式路径 `config.required` 是死数据**：prompt 让模型标了，但只有 stream 的早停消费它。
3. **S10 精修会改 `context`**：不改拓扑，但确实改了剩余任务的输入。
4. **两次真机计划规模不同**（A=3 任务 / B=5 任务），不是严格同图对照；
   B 的 `t5 cancelled` + `early_stop` 决策是直接证据，但"省了多少时间"未做同图对比测量。
5. **未开**：`llm_redraw`（T3）、`heavy_redraw`、`user_directive`、`user_confirm_redraw`。
