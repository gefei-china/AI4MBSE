## 1. P0-5 鉴权强制（对标 Dify：工作区多租户 + RBAC）

### 1.1 实测出的三条漏洞（评估 §4.1）

| 编号 | 漏洞 | 实测证据 |
|---|---|---|
| D1 | 身份可自报 | `X-User-Id` 请求头自报即被采信；叠加 `enforce_login=False` 与 `users` 表无口令列 ⇒ 匿名一路 200 |
| D2 | **token 无效仍回落 X-User-Id** | 旧实现「token 查得到就用，查不到继续读 X-User-Id」⇒ **随手伪造一个 session token 就能把 X-User-Id 通道重新打开**。加了锁、留了窗 |
| D3 | RBAC 对匿名放行 | `require_permission` 里 `if user is None: return user` ⇒ 门没问题，门闩没插 |

### 1.2 落地改造

**`core/deps.py`** —— 判定顺序严格串行，**弱凭据永不兜底强凭据**：

```
① X-Session-Token（唯一强身份）→ 命中即用
   带了 token 但无效 ⇒ 直接判无身份，**不再读 X-User-Id**（堵 D2）+ 写 `auth_identity_reject` 审计
② 仅当"完全没带 token" 且 auth.trust_user_id_header=True 时读 X-User-Id（兼容期）
③ enforce_login=True 且仍无身份 ⇒ 401
   ⇒ 此时 require_permission 的匿名分支**不可达**，D3 自动闭合（不引入第二个语义打架的开关）
```

新增配置 `auth.trust_user_id_header`（默认 `True` = 兼容期；上线 checklist 置 `False` 即完成加固，**改配置不用动代码**）。

**为什么不直接把 `enforce_login` 置 True**：现有自检脚本与前端尚在迁移期，直接开会让所有无 session 的调用 401。现在**机制先到位**，开关在上线清单里翻转。

### 1.3 前端配套（否则一开强制就废）

发现并修了一处**真实事故隐患**：`11-pipeline.js`（续答）与 `12-chatsend.js`（发送）**各自手拼 headers 且都漏了 `X-Session-Token`**（只有后者带了 `X-User-Id`）。
一旦 `enforce_login` 打开，**全站最常用的两条路径直接 401**。收口成 `01-core.js:streamHeaders()` —— 身份头的唯一真源。

## 2. P1-2 / P1-3 流式链路（对标 OpenAI SSE / Vercel AI SDK / Dify workflow SSE）

### 2.1 心跳（P1-2）

流式端点是**同步生成器**，单次 `next()` = 一次完整 LLM/工具调用，实测单轮编排 344 / 849 / 1155 s，等待首 token 期间零字节输出。
nginx `proxy_read_timeout` 默认 60 s ⇒ 静默掐断；且本工程 SSE **断流不可续**，用户看到的就是"回答一半卡住然后报错"。

`core/sse.py:iter_with_heartbeat` —— 判据不是 passthrough：
- 为什么**必须跨线程**：源生成器正阻塞在 `next()`，没人能插进去产帧 ⇒ 源挪到 worker 线程，主线程 `Queue.get(timeout=15)`，超时即产 `: ping\n\n` 注释帧（SSE 协议保证客户端忽略，不污染 `data:` 解析，前端 `handleSSE` 已验证会忽略空 data 帧）；
- 首帧 `retry: 3000` 显式声明重连节奏；
- **异常必须回传**：worker 异常放 box、主生成器重抛（静默吞掉 = 把 bug 藏进线程）；
- **断连止损**（实测踩出来的坑）：对"正在另一个线程栈上执行"的 generator 调 `close()` 抛 `ValueError: generator already executing` ⇒ 改为消费侧置 `stop` 标志、worker 在**帧边界**安全关闭源，最多滞后一帧。

### 2.2 降级显式化（P1-3）

DeepSeek 402 余额不足 / 无 api_key / 调用异常三条路径都**静默回落 Mock**。而且实测发现编排链路把 `llm_info` 的 `used_mock` **硬编码为 False**（`stream.py:878`）⇒ 就算有降级，done 事件也永远说"没有"。

改造：
- `llm.stats` 新增累计计数语义（`fallback_total`，与既有 `real`/`mock` 一起）；
- 收尾时以**差值**判定（不用瞬时值 `last_used_mock`：子任务在线程池并发跑，瞬时值会被互相覆盖）；
- 触发 ⇒ 流尾补发 `event: degraded`（含 mock/fallback 次数），前端挂橙色警示条：*"本次回答中有 N 次调用未真实到达模型、由本地兜底（Mock）生成"*。
- 判定抽成纯函数 `core/sse.py:snapshot/degrade_delta`，可零 LLM 断言（不写在路由里 — 内联算术没法验证）。

## 3. P0-2 孤儿回收（对标 LangGraph checkpointer / Temporal timeout 的第一步）

### 3.1 为什么先做回收而不是直接做 resume

LangGraph（checkpointer + resume）与 Temporal（timeout + 自动重投）的**共同前提**是"先能识别死掉的运行"。
本工程卡在这一步：实测 `agent_tasks` 60 批次里 **16 批残留 planned/ready/blocked，最老 14.1 天**无人管，且**没有任何界面能看到它们卡着**。
第一步做三件**不改任何执行路径**的事（零回归风险）：① liveness 判据；② 显式失败化 + 保上下文；③ 可观测。

**诚实的边界**：这一步**不是**自动 resume（那要有独立 worker 队列，属第二步）。它把"永远转圈"变成"明确失败 + 可重跑"。

### 3.2 实现

`core/run_registry.py`：
- 判据 `status ∈ {planned,ready,running,blocked}` 且 `updated_at < datetime('now', -TTL)`，TTL 默认 1800 s（依据：实测单轮最长 1155 s，留 1.5 倍余量）；
- **时间口径**：`updated_at` 默认 `CURRENT_TIMESTAMP` = **UTC**，判据必须用 `datetime('now')`，误用 `localtime` 会让阈值整时区偏移 8 小时（I5 锁了这条）；
- 端点：`GET /api/monitor/orphan-runs`（非终态批次 + 是否超时的判定一起给，便于判断 TTL 合不合理）、`POST /api/monitor/orphan-runs/reap?dry_run=true`（灰度止损）；
- 启动挂载（`main.py` lifespan，开关 `runtime.reap_on_startup`）。

## 4. P1-1 入口限流（对标 Dify 配额 + Anthropic/GitHub `X-RateLimit-*` 契约）

评估实测：全仓 0 处限流；`budget_tokens` 曾超支 35%（设 100 万、实耗 135 万），后被置 0 ⇒ 完全无闸。
叠加 P0-1（同步阻塞 + anyio 线程池上限 40）：连点 10 次发送就占掉 1/4 线程，其余用户的列表请求开始排队。

`core/rate_limit.py`：
- **按"单次占用多少线程时间"分桶**，不是按 HTTP 方法：`chat` 5/min（含 `/chat`、`/chat/stream`、`/api/studio/flows/{id}/run` 这类带 id 的长执行端点）、`write` 60/min、`read` 300/min；
- 主键 = 用户（无则会话/匿名），**不同用户、不同桶互不挤占**（I3 锁住，"限错对象 = 线上事故"）；
- 超限返回 **429 + `Retry-After` + `X-RateLimit-Limit/Remaining/Bucket`**，**不排队** —— 排在队里 = 用户看着转圈却不知道发生了什么；
- 豁免 `/api/monitor`、`/api/auth`、`/static`、`/api/health`、`/api/ux-metrics`（监控被限 = 自锁）；
- 纯 ASGI 中间件（与既有审计中间件同一理由：不用 `BaseHTTPMiddleware`，避免包装 SSE 响应体）。

**边界**：进程内计数，多实例时总量 = 实例数 × 阈值；真正的分布式配额需 Redis（评估 §7.2 已列"暂不做"）。

> 自检意外收获：`verify_rate_limit.py` 的 I7a（脏配置容错）**抓到一个真缺陷** ——
> `limit=None` 时 `limit <= 0` 抛 `TypeError`，而它在请求入口 ⇒ **配错一次限流全站 500**。
> 已修：阈值脏值时按"放行"处理并在 `hit()` 内做类型防御（限流自己是保护设施，**绝不能成为故障源**）。

## 8. 局限声明

1. **限流为进程内计数**：多实例部署时各算各的，需 Redis 才能做全局配额。
2. **降级判据用进程单例计数**：并发会话会互相计入 —— 取"宁可多报不可漏报"方向；彻底隔离要 request-scoped 上下文（入口需带 conversation_id）。
3. **本次改造未动执行路径**：P0-1（同步阻塞 → 异步）与完整 resume 属下一批次，本次所有改动均 conductor 未触碰 `agent/pipeline_parts/*` 的控制流。
