## 1. 问题定义（先对齐"要解决什么"）

现状经代码核实为**"扁平可用、但无骨架"**：

| 维度 | 现状（已复核） | 代码依据 |
|---|---|---|
| **无层级** | `documents` 表建表 13 列、运行库 26 列，**零层级字段**（无 `folder_id` / `parent_id` / 路径树）；不存在 `doc_folders` 表 | `database/schema.py::init_db`（`CREATE TABLE IF NOT EXISTS documents`）；`PRAGMA table_info(documents)` |
| **过滤/分页：已具备** | 服务端 11 个筛选参数 + 前端筛选控件齐全；分页由前端组件实现（`_docSize` 默认 15，可切页大小） | `routers/meta.py::list_documents`、`repositories/meta_repo.py::MetaRepo.list_documents_with_meta`、`static/js/mods/20-docs.js::{loadDocs, renderDocs}`、`static/js/mods/15-kb.js::renderPagerBar` |
| **筛选面的真实缺口** | 缺的是「**层级/父级路径筛选联动**」与「**目录作用域搜索**（含子目录 / 仅当前目录）」；其余维度（时间范围、标题搜索、状态、来源、上传人、格式）**均已具备** | 同上 |
| **元数据：部分具备** | `doc_metadata`（标题/作者/版本/标签）与 `knowledge_categories`（9 条内置分类）**已存在**，列表已展示「作者 / 上传人 / 知识类别 / 版本 / 块数」列；**但**全部 9 条现存文档的 `knowledge_category` 均为空（未打分类） | `database/schema.py`（`doc_metadata` / `knowledge_categories` 建表）；只读查询 `mbse.db` |

**"无骨架"的三个真实代价**（不是审美问题）：

1. **找不到**：文档按上传时间倒序平铺，**无法按"工程 / 分系统 / 需求规范"这类系统层级收敛**；筛选条件虽然齐全，但都建立在扁平维度上（来源、状态、格式、时间），缺少"这份文件属于哪个系统"这一最符合 MBSE 心智的轴；文档量到 100+ 后靠搜索和翻页找文件仍然低效。
2. **管不了**：无法表达"这批是 XX 分系统的接口文档""这份已作废"的**归属**与**成组治理**。生命周期状态机（`lifecycle_status`）与分类（`knowledge_categories`）都已存在，但缺少"一次整理一组"的位置维度。
3. **接不上**：与已有能力断链——知识分类、生命周期状态机、工程（`projects`，见同级 B 文档）都已存在或已规划，却无法在列表里按"目录"这一维度看见、用不上。

**目标（可验收）**：在资料库内，任意文档**≤3 次点击可达**；任意目录**一键看到"未归类 / 未入库 / 解析失败 / 未分类"**四类待办；文档**版本与状态一眼可见**。

## 2. 方案：双轨组织（目录树 + 元数据），目录只是逻辑视图

### 2.1 为什么不是"纯目录树"

行业实践里有一条明确的反面证据：**纯文件夹层级会让用户不知道该把文件放哪**（同一份"退换货流程"放客服还是售后？）——这是传统文件夹系统在企业知识库中失败的主因。MBSE 场景更严重：一份文档可能同时属于"某型号项目""某分系统""某标准体系"。

因此采用**双轨**，并各司其职：

| 轨道 | 承担 | 谁维护 | 回答的问题 |
|---|---|---|---|
| **目录树（位置维度，唯一归属）** | 人找东西的心智；工程/系统层级结构 | 人工（可拖拽） | "文件放在哪" |
| **元数据（标签维度，可多值）** | 检索过滤、权限边界、版本治理 | 人工 + AI 预填 | "这类文件有哪些" |
| **智能视图（自动聚合，只读）** | 待办收口 | 系统 | "现在有什么要处理" |

> 关键取舍：**目录 ≠ 分类**。`knowledge_categories`（知识分类，**标签维度**）与 `documents.knowledge_category`（文档的分类取值）属于标签维度，目录是位置维度，两者不可混用、不可互相替代。

### 2.2 信息架构（IA）

```
知识中心（nav-kbhub）
└─ 📁 资料库（kb-e）
   ├─ ① 目录树（左，~220px，可折叠）
   │   ├─ 结构目录（人工维护，支持多级 + 拖拽）
   │   │   └─ 例：星网宽带通信系统 / 需求规范 / 接口定义 …
   │   ├─ 智能视图（系统聚合，只读，不可拖入）
   │   │   ├─ 📥 未归类（folder_id 为空）
   │   │   ├─ ⏳ 未入库（lifecycle_status ≠ committed）
   │   │   ├─ ⚠ 解析失败（parse_status = failed）
   │   │   └─ 🏷 未分类（knowledge_category 为空）
   │   └─ 🗑 回收站（P2）
   ├─ ② 文档列表（右）
   │   ├─ 顶部：路径面包屑（资料库 / 需求规范 / 接口定义） + 搜索框
   │   │         搜索范围切换：仅当前目录 ▾ / 含子目录
   │   │         （现有筛选控件——状态 / 上传人 / 格式 / 来源 / 起止日期——原样保留在同一行）
   │   ├─ 列：☑ / 文件 / 所属目录 / 知识分类 / 版本 / 块数 / 状态 / 操作
   │   └─ 批量条：移动 / 打标签 / 入库 / 删除（勾选后出现；复用现有 `#doc-batch-bar`）
   ├─ ③ 文档详情抽屉（复用现有抽屉组件 `openPanel`）
   │   └─ 概览 · 分块 · 抽取实体 · 溯源 · 版本 · 操作（入库/重解析/移动）
   └─ ④ 上传入口（右上「📤 上传文件」）
       └─ 默认落点 = 当前选中目录（记忆上次选择）+ 可选同时打标签
```

### 2.3 关键交互（含边界与空态）

| 场景 | 交互设计 | 设计理由 |
|---|---|---|
| 新建目录 | 目录树顶部 `+ 新建目录`；选中某目录时建子目录；**同时在树上支持右键菜单**（新建子目录 / 重命名 / 移动到 / 删除） | 与本体模型左栏树保持同一交互语言（`static/js/mods/21-ontology.js` 的 `renderOntTree()` / `ontTypeTree()` 手写递归树 + `#ont-left-collapse` / `ontToggleLeft()` 折叠记忆，可直接借鉴） |
| 移动文档 | 列表多选 → 批量条「📁 移动到…」弹目录选择器；**也支持把列表行拖到树上** | 批量优先：整理已有 9+ 文档时逐条拖拽效率不可接受 |
| 上传 | 上传即落**当前选中目录**；拖拽文件到树上某目录 = 上传到该目录（P1） | 消除"上传后再整理"的二次劳动 |
| 未归类兜底 | 智能视图「📥 未归类」常驻，数量以 badge 显示；点进去可批量移动 | 保证"不整理也能被发现"，而非静默沉底 |
| 删除目录 | 二次确认 + 明示策略：**仅删除目录，文档回到「未归类」（不级联删文档）** | 防误删；文档是重资产，目录是视图 |
| 空目录 | 空态含「📤 上传到此目录」按钮 | 空态即入口 |
| 搜索 | 顶部搜索框；默认**含子目录**，可切"仅当前目录"；命中高亮。**复用现有 `#doc-search` 与 `?search=` 参数**，新增的只是"作用域"这一维 | 现有搜索是全局 `LIKE`（`MetaRepo.list_documents_with_meta` 对 `filename/title/author/tags` 匹配）；目录树减小了检索面，搜索必须能穿透层级，否则又回到"不知道放哪就找不到" |
| 长名/深路径 | 面包屑超长时中间省略、hover 显示全路径；列表「所属目录」列窄时 tooltip | 避免布局被长路径挤坏 |

### 2.4 数据模型（改动最小、可回滚）

```sql
-- 新增：目录表（逻辑视图，不映射物理文件系统）
CREATE TABLE doc_folders(
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  parent_id INTEGER,                 -- NULL = 根级；不用文本 path 存父子（重命名难维护）
  name TEXT NOT NULL,
  path TEXT NOT NULL,                -- 物化路径 "/12/45/"，用于前缀查询与面包屑
  sort INTEGER DEFAULT 0,
  project_id INTEGER,                -- 预留：与「工程」联动（见同级 B 文档）
  created_by TEXT, created_at TEXT,
  UNIQUE(parent_id, name)            -- 同层不重名
);
-- documents 增加 1 列（向后兼容）
ALTER TABLE documents ADD COLUMN folder_id INTEGER;   -- NULL = 未归类
```

> 建表与加列请落在 `database/migrations/` 下的域文件（现有文档相关迁移集中在 `database/migrations/documents.py`，其 `_add()` 辅助函数可直接复用），不要改 `database/schema.py` 的历史建表语句。

**三条硬约束**：

1. **物理存储不动**：`data/uploads/` 维持现有扁平 `{doc_id}_{safe}` 命名（`knowledge_pipeline/ingest.py::_save_source_copy`），**目录仅存在于数据库**。→ 好处：不触发重解析/重向量化，零数据丢失风险，目录重构随时可做。
2. **迁移零风险**：现存文档 `folder_id` 全为 NULL → 自动落入「未归类」智能视图，用户手动整理，**不做自动猜目录**。
3. **重命名级联**：目录 `rename` 时同步更新自身与所有子孙的物化 `path`（单事务）。

## 3. 分期（MVP 优先，先可验收）

> **范围说明（重要）**：P0 **不含**"补过滤与分页"——这两项**已具备**（见 §0）。P0 的唯一主题是**补齐层级维度 + 文件结构管理**。

| 期 | 范围 | 交付物 | 验收标准 |
|---|---|---|---|
| **P0** | `doc_folders` 表 + `documents.folder_id` + 目录树 + 上传落当前目录 + 列表「所属目录」列 + 面包屑 + 批量移动 + 未归类视图 | 可用的整理能力 | 现存文档全部归入目录后，"未归类"归零；关掉浏览器重开，目录结构、折叠态、上次上传目录全部保留 |
| **P1** | 目录作用域搜索（含子目录 / 仅当前目录）+ 解析失败/未入库/未分类智能视图 + 拖拽到树上传 + 详情抽屉「移动」 | 检索与待办收口 | 从任意文档 3 次点击内可定位到其所在目录；未分类待办可见 |
| **P2** | 目录模板（按工程类型预置骨架）+ 目录级权限 + 回收站 + 与工程联动（工程创建时自动建目录骨架） | 治理能力 | 新建工程时目录骨架自动生成 |

## 4. 风险与反面清单

| 风险 | 应对 |
|---|---|
| 目录与知识分类语义混淆，用户两头维护 | 列表同时显示两列，命名上区分「所属目录（位置）」与「知识分类（标签）」，并在首次使用加一句说明气泡 |
| 目录越建越深，最后又找不到 | 默认允许 4 级；超过则提示；智能视图与"含子目录搜索"保证穿透 |
| 用户期望"目录=磁盘目录" | UI 文案统一用「目录」而非「文件夹」，删除确认里明示「文档不会被删除」 |
| 误以为"平铺列表还需要救（缺分页）" | **无需处理**：分页已落地（`_docSize=15` + `renderPagerBar`）。真正要救的是"缺归属"，不是"缺分页" |

**明确不做（本轮）**：文件内容全文检索（已有 RAG 检索层，不重复）；目录拖拽排序的跨窗口多选；物理文件搬迁；自动分类（AI 猜目录准确率不足会制造新的混乱，先做"AI 预填分类"标签提示）；**补过滤与分页（已具备）**。

## 5. 待拍板决策点

| 编号 | 决策点 | 选项 | 我的建议 |
|---|---|---|---|
