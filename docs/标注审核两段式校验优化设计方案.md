# 标注审核两段式校验优化设计方案

> 版本：v1.1（2026-08-17）
> 背景：用户反馈「标注审核」页校验阶段拆成多个 tab，步骤割裂、体验差；同时要求移除「抽取质量评估」模块。经确认，主 Tab 收敛为 **4 个（按"上游 → 下游"工作流排）**：① 抽取预览（待审）→ ② 融合工作台 → ③ 实体审核队列 → ④ 关系审核队列；其中「融合工作台」后台自动运行两段式（工序① 规则预处理免费层 ＋ 工序② LLM 实体解析成对判定）。

---

## 1. 现状与痛点

### 1.1 现状（kb-b 标注审核页）

当前 [static/index.html](file:///c:/Users/gefei/WorkBuddy/2026-08-04-19-05-52/mbse_system/static/index.html#L885-L1023) 页内共有 6 个 tab：

| Tab | 职责 | 数据来源 | 去处 |
|---|---|---|---|
| 🕘 待审候选 v2g | 文档自动抽取候选，人工确认入库 | v2g_candidates | 确认 → entities/relations(candidate) |
| 🔀 实体消歧与合并 dup | 已入库实体重复对检测，人工合并 | entity_dup_candidates | 合并 → keep + dup deprecated |
| ✅ 实体审核队列 review | 实体候选正式审核 | entities(status=candidate) | reviewed / deprecated |
| 🔗 关系审核队列 rel | 关系候选正式审核 | relations(status=candidate) | reviewed / deprecated |
| ⚔️ 冲突消解 conflict | 同归一名称/同三元组的矛盾属性裁决 | conflicts | 采纳 A/B / 忽略 |
| 🎯 抽取质量评估 eval | golden set P/R/F1、A/B 评测（**本次移除**） | eval_reports / golden_samples | — |

### 1.2 痛点

1. **入口割裂**：同一批数据要依次经过「候选确认 → 消歧 → 实体审核 → 关系审核 → 冲突裁决」5 个独立操作区，来回切换 tab，认知负担重。
2. **步骤重复**：消歧、审核、冲突裁决本质都是「判断两条/多条的异同与取舍」，却拆成 3 个独立入口、3 套列表、3 个按钮组。
3. **无分层、全量 LLM**：当前实体消歧（[entity_resolver.py](file:///c:/Users/gefei/WorkBuddy/2026-08-04-19-05-52/mbse_system/entity_resolver.py#L88-L165)）对**所有**已入库实体做 blocking + 双判据评分，简单情况（大小写/全半角/空格差异）也走全量配对，费算力且 O(n²)。
4. **判定无理由**：消歧/冲突只给分数与证据，没有可溯源的判定理由；审核人难以快速理解「为什么判为同一实体/采纳哪侧」。
5. **抽取质量评估与主流程无关**：属离线评测看板，且用户明确要求移除。

### 1.3 目标（4 Tab 上游 → 下游工作流）

```
① 抽取预览（待审） ──▶ ② 融合工作台（后台自动两段式） ──▶ ③ 实体审核队列 ──▶ ④ 关系审核队列 ──▶ 发布
     整批粗筛决策          规则预处理 + LLM 实体解析         合并候选子分组进入      含冲突待审项
                          合并建议 + 待裁决冲突
```

| 新 Tab | 职责（用户定义） | 取代的原 Tab |
|---|---|---|
| ① 抽取预览（待审） | 整批文档抽取后，用户先粗筛决定是否进入下一步（**原「待审候选（文档自动抽取）」重新定义并更名**） | 🕘 待审候选 v2g |
| ② 融合工作台 | 后台**自动运行**两段式（工序① 规则预处理＋工序② LLM 实体解析）；展示：自动运行状态 + 合并建议列表 + 待裁决冲突 | 🔀 实体消歧与合并 dup ＋ ⚔️ 冲突消解 conflict |
| ③ 实体审核队列 | 实体候选正式审核；**合并候选作为子分组进入这里** | ✅ 实体审核队列 review |
| ④ 关系审核队列 | 关系候选正式审核；**含冲突待审项** | 🔗 关系审核队列 rel |
| （移除）抽取质量评估 | — | 🎯 eval |

| 产品/方案 | 做法 | 本方案借鉴 |

## 3. 两段式引擎设计（融合工作台后台自动运行）

### 3.1 总览

```
文档/SysML/AI生成 ─▶ 抽取 ─▶ v2g_candidates（实体+关系候选）
                                    │
                                    ▼  ① 抽取预览：粗筛 → 进入下一步
        ┌───────────────────────────────────────────────┐
        │ 工序① 规则预处理（免费·秒级·自动）                 │
        │  · 字符归一化：大小写/全半角/空格/标点统一            │
        │  · 别名表 / 简全称表 / 格式规范化                  │
        │  · Canopy 粗筛：名称+别名+向量相似度 → 候选对       │
        │  · 三态出口：                                    │
        │      ├ 完全一致 → 自动对齐（auto-resolve，留痕）    │
        │      ├ 高相似   → 生成候选对 → 工序②               │
        │      └ 无关联   → 不生成候选对（省 LLM 调用）       │
        └───────────────────────────────────────────────┘
                                    │ 候选对（规则判不了的）
                                    ▼
        ┌───────────────────────────────────────────────┐
        │ 工序② LLM 实体解析（成对判定·自动）                │
        │  · 一次输出：消歧 + 对齐 + 冲突裁决 + 理由 + 置信度  │
        │  · 结果 → 合并建议列表 / 待裁决冲突                 │
        └───────────────────────────────────────────────┘
                                    │
                                    ▼
       ③ 实体审核队列（合并候选子分组）／④ 关系审核队列（含冲突待审项）
                                    │
                                    ▼
              入库（reviewed）／驳回（deprecated）／合并（keep+deprecated）
                                    │
                                    ▼
                              发布（权威基线）
```

### 3.2 工序① 规则预处理（免费）

**归一化规则链**（新增 `entity_resolver.py` 的规则预处理管道，复用既有 `normalize_name` 思路扩展）：

1. 大小写统一（英文转小写）
2. 全半角统一（全角 → 半角）
3. 空格/空白统一（连续空白 → 单空格、去首尾）
4. 标点统一（中文标点 ↔ 英文标点、括号类型）
5. **别名表**：`alias` 为 key，指向规范名（如 `卫星系统` ↔ `卫星`、`载荷` ↔ `有效载荷`），用户可维护
6. **简全称表**：缩写 ↔ 全称（如 `KB` ↔ `知识库`、`REQ` ↔ `Requirement`），用户可维护
7. 格式规范化（数字/单位/序号后缀统一）

**三态出口**：

| 判定 | 条件 | 动作 |
|---|---|---|
| auto-resolve（自动对齐） | 归一化后字符串完全相等 或 别名/简全称命中规范名一致 | 自动生成对齐建议并落库（`entity_dup_candidates` method=rule，状态可直接 auto-merged，留痕可撤销） |
| candidate pair（候选对） | Canopy 桶内相似度 ≥ 阈值（复用 fuzzy + 向量双判据） | 生成候选对 → 工序② LLM 成对判定 |
| 无关联 | 不在同一 Canopy 桶 / 相似度低于阈值 | 不生成候选对 |

**Canopy 粗筛（避免 O(n²)）**：

- Blocking key：归一化名称 token（首字/首词）+ 实体类型 + 别名族（复用 [entity_resolver.py](file:///c:/Users/gefei/WorkBuddy/2026-08-04-19-05-52/mbse_system/entity_resolver.py#L81-L85) `_blocking_key` 思路，扩展别名/简全称展开后的 key）。
- 仅在**同一桶内**两两比较（N 个实体 → 候选对从 N² 降到 ~K·N，K=桶平均大小）。
- 向量相似度仅对桶内对计算（粗筛），避免全量 embedding 两两比对。
- 命中别名/简全称的**强规则对**直接进 auto-resolve，不送 LLM。

### 3.3 工序② LLM 实体解析（成对判定）

**输入**：工序① 生成的候选对（规则判不了的），每对携带：
- 实体A/B：名称、别名、类型、属性、来源文档、置信度
- 证据：归一化结果、别名命中情况、向量/模糊相似度

**LLM 单次输出（结构化 JSON，一次完成三类判定）**：

```json
{
  "pairs": [
    {
      "pair_id": "cand-123",
      "verdict": "merge | separate",
      "disambiguation": "两实体指向同一概念/不同概念，理由…",
      "alignment": { "keep": "实体A", "reason": "A 字段更全且来源更权威，B 并入 A" },
      "conflict": [
        { "field": "状态", "take": "a|b|merge", "reason": "以更高时效来源为准…" }
      ],
      "confidence": 0.92
    }
  ]
}
```

- 一次输出覆盖「消歧（是否同一实体）＋ 对齐（keep/dup 取舍）＋ 冲突裁决（矛盾属性采纳侧）」，理由内置，直接落 `entity_dup_candidates.evidence` 供审核溯源。
- 支持批量成对输入（控制 token 预算，分批调用）。
- **自动触发**：工序① 完成后自动调度工序②（后台异步），无需人工点击。
- **降级**：LLM 不可用时，工序① 仍产出候选对，融合工作台展示「无 LLM 建议」候选，人工直接裁决（流程不中断）。
- 关系候选对同样进入工序② 成对判定（同三元组消歧），输出复用同一结构。

## 4. 前端 UI 设计（kb-b 主 Tab 4 个，按上游 → 下游排列）

### 4.1 页面结构

```
kb-b 标注审核
├─ 顶部：🔄 知识治理全链路 进度条（① 抽取预览 → ② 融合工作台 → ③ 实体审核 → ④ 关系审核 → 已发布）
├─ Tab ①：🕘 抽取预览（待审）
├─ Tab ②：🧬 融合工作台
├─ Tab ③：✅ 实体审核队列
├─ Tab ④：🔗 关系审核队列
└─ 右上：🔄 全部刷新
```

### 4.2 Tab ① 抽取预览（待审）

- **原「待审候选（文档自动抽取）」更名而来**，职责重定义为「整批粗筛决策」：
  - 批次卡（复用现有 v2g 批次结构）：文档名 / 抽取实体数 / 关系数 / 高置信占比
  - 操作：`✔ 进入融合`（整批进入下一步）/ 单条 `跳过` / `驳回`
- 目标：用户先看整批抽取概况，粗筛后放行进入融合工作台，避免逐条确认的负担。

### 4.3 Tab ② 融合工作台（后台自动两段式）

- **自动运行状态卡**：两段式引擎状态（🔄 运行中 / ✅ 已完成 / ⚠ 降级）+ 统计（输入候选 N · 规则自动对齐 M · 候选对 K · LLM 已判 J）+ 手动 `▶ 触发运行`（兜底）
- **合并建议列表**：LLM/规则产出的候选对卡片（复用现有 dup 卡片风格）：
  - 头部：`keepName ← 合并 dupName · 相似度 X` ＋ 判定徽章（`🤖 合并建议` / `✅ 不同实体` / `⚔️ 冲突`）
  - 证据区：归一化结果、别名命中、向量/模糊相似度
  - **LLM 判定区**：消歧理由 / 对齐建议（keep 选择 + 理由）/ 冲突裁决（字段级 采纳A/B/合并 + 理由）＋ 置信度
  - 操作：`✅ 采纳`（按判定执行 merge/separate）／`✏️ 修改裁决`／`🚫 驳回`；高置信（≥0.85）可批量采纳
- **待裁决冲突**：冲突卡内嵌展示 A/B 侧值 + LLM 采纳建议 + 人工裁决按钮（采纳 A/B/忽略，审计留痕）
- 取代原「实体消歧与合并」「冲突消解」两个 tab。

### 4.4 Tab ③ 实体审核队列

- 保留现有实体审核列表（待审/已通过/已驳回 分区、高置信建议、重复簇标签）
- **新增子分组**：合并候选作为子分组进入本队列——`全部 / 待审 / 合并建议（N）/ 已通过 / 已驳回`，合并建议组内逐条 `采纳/修改/驳回`（复用融合工作台判定卡）
- 顶部保留筛选（类型/置信度/搜索）与批量操作。

### 4.5 Tab ④ 关系审核队列

- 保留现有关系审核列表（待审/已通过/已驳回、刷新、状态筛选）
- **含冲突待审项**：同三元组的矛盾关系值作为冲突卡内嵌展示（LLM 裁决建议 + 人工裁决按钮）
- 合并/对齐操作复用关系去重合并（`edges/merge`）与消歧对齐语义。

### 4.6 移除项

- 移除 `kb2-pane-eval` 整块 DOM 与 tab（`🎯 抽取质量评估`）
- 移除 eval 相关 JS 函数：`evalLoadDocs / evalGoldenHint / evalParseLines / evalRun / evalRenderResult / evalClearResult / evalLoadReports / goldenSample / loadGoldenSamples / goldenRun / evalAb / evalDashboard`
- 移除 `switchKB2Tab` 中 eval 分支（[index.html](file:///c:/Users/gefei/WorkBuddy/2026-08-04-19-05-52/mbse_system/static/index.html#L6714-L6729)）
- 后端：移除 routers/knowledge.py 中 6 个 eval 路由（`eval/run`、`eval/reports`、`eval/golden/*`、`eval/dashboard`、`eval/ab`）及 `knowledge_eval.py`（确认无其他引用）；`eval_reports`/`golden_samples` 表保留（历史数据不动，避免迁移风险）

7. 回归：实体/关系审核通过/驳回、合并、发布门禁、图谱可视化均无回归（复用 `verify_rel_dup_p0.py` 等调整后回归）。
