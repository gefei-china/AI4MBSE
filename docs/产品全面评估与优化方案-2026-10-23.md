## 0. 执行摘要（结论先行）

**一句话判断：产品的"引擎"是一流的（自研 Agent 体系 + HIL 四道面 + 评测纪律 + MBSE 领域纵深），"门店"是三线的（能力中心五类能力五张表、度量大面积空白、监控守护面窄于采集面）。行业标杆的共识恰好都长在产品的短板处。**

| # | 结论 | 依据 |
|---|---|---|
| 1 | **产品功能面极宽且真实**：十域齐全（知识/图谱/本体/SysML/Agent/插件/监控/评测/自进化/项目），629 个端点、151 张表，且指标基本真数据（2026-10-23 刚完成假数据清理）——这不是 demo，是重装产品 | 摸底报告 §2/§9 |
| 2 | **核心引擎设计成熟度高于多数同类自研**：IntentRouter 三层路由、Pipeline 十二 Mixin、团队四档路由、DAG 十五节点、自研 checkpointer、HIL 四道面（L0-L2 分级 + 确认队列 + 确定性钩子 + ask_user）——对齐 Claude PreToolUse 合同级门控 | 摸底 §3；对标 Claude SDK |
| 3 | **最大结构性问题：能力中心未统一**。工具/技能/插件/MCP/提示词五类能力各建表、各启停、各度量；`plugin_call_logs` 0 行、技能 `use_stats` 15/25 为空、**27 个 Agent 中 15 个从未被调度**——"建完了"与"用起来"之间断档 | 摸底 §5/§10；对标 Coze 资源库 / Dify Marketplace |
| 4 | **第二大问题：监控守护面窄于采集面**。审计/UX/归因/trace 采集齐全，但告警规则仅 **1 条**、BadCase **0 行**、链路追踪只覆盖编排流量不覆盖会话直答；且**缺在线评测闭环**（生产流量→dataset→人工标注→回归），这正是 LangSmith/Coze 罗盘的核心 | 摸底 §7；对标 LangSmith/Coze |
| 5 | **差异化壁垒真实存在**：MBSE 领域纵深（SysML V2 原生、五元素追溯、8 视图、本体推理、确定性质量工具）+ 私有化离线 + 中国标准合规——恰是 Siemens（INCOSE 规则+LLM）、IBM（用例发现 agent）正在走的方向，也是通用平台（Coze/Dify）结构性进不来的领域 | 摸底 §6/§8；对标 §8 MBSE |

**优化主线（对应本次要求的三大中心 + 横切）**：

| 模块 | 主线 | 行业锚点 |
|---|---|---|
| **能力中心** | 五类能力收敛为「统一注册 + 统一市场 + 统一版本 + 统一度量」，消灭零调度/零调用 | Coze 资源库与发布即生效；Dify Marketplace |
| **资料中心** | RAG 流水线工程化（接入前检索测试）+ Agentic RAG（检索质量评估回退）+ 知识运营编排化 | Dify Knowledge Pipeline；Coze 知识库节点 |
| **运行监控** | 采集面→守护面：告警规则体系化 + BadCase 真实入库 + **在线评测闭环** + 会话级全链路 trace | LangSmith thread 评测/Engine；Coze 罗盘三段式 |
| 横切 | 上下文工程指标化、推理策略插件化、部署矩阵补全 | Manus 六原则；Dify 策略开放标准；LangGraph 部署矩阵 |

## 1. 产品现状评估

### 1.1 形态与规模

单进程 FastAPI + 单文件 SQLite（379 MB / 151 表）+ 无构建 SPA（47 个 JS 模块）+ 私有化离线部署。外部依赖：智源平台（5 个 SysML v2 接口）、DeepSeek/Qwen LLM、内网 bge-m3 embedding、可选 Fuseki、checker.jar（126 MB，需单独挂载）。**单副本约束**（SQLite 单写者）。

### 1.2 能力矩阵总览（十域）

| 域 | 现状 | 成熟度 | 证据 |
|---|---|---|---|
| 对话/会话 | SSE 主路径 + 澄清 + 中断固化 + 追问 + 反馈 | ★★★★☆ | routers/conversations.py |
| Agent 编排 | 自研三层（意图→pipeline→团队/DAG）+ 自研 checkpointer | ★★★★☆ | 摸底 §3.2 |
| 知识库 RAG | FTS5+向量+HyDE 三路 → RRF → LLM rerank → GraphRAG | ★★★★☆ | knowledge_pipeline/ |
| 知识图谱 | entities/relations 治理权威源 + 三元组唯一写入 + 推理批次 + provenance | ★★★★☆ | graph_db.py / vector2graph.py |
| 本体/术语 | 52 类型/72 版本/OWL 导入导出/轻量推理/SHACL/术语三域置信度 | ★★★★☆ | ontology_*.py |
| SysML V2 | 导入（74K 行解析器）+ 8 视图 + 版本管理 + 官方 checker 校验 | ★★★★☆ | sysml_importer.py |

| 评测 | 意图 374 样本 + 检索/生成/记忆/追溯四类评测 + 189 门禁 0 未接 | ★★★★☆ | tools/eval/ |
| 自进化 | 提案/课程/档案/周报（只提议不执行，数据 0） | ★★★☆☆ | routers/proposals.py 等 |

### 1.3 核心优势（本方案的"不许改坏"清单）

1. **HIL 四道面**：L0-L2 分级、L2 写库逐条确认队列（幂等键）、工具钩子确定性门控（对齐 Claude PreToolUse 合同语义）、ask_user 可点选澄清卡。行业里只有 LangGraph（approve/edit/reject/respond）比它表达力强，Coze 都没有工具级审批文档。
2. **评测纪律**：意图评测只消费人工 confirmed（拒绝自我循环）、覆盖性计算写死不允许 LLM 即兴算数、空窗口≠0 分、189 门禁全接线。这是多数团队做不到的工程文化。
3. **grounded + 可追溯**：citation 完整性/无据声称密度已有确定性指标；实体五元素追溯；审计哈希链。工业 AI 的硬要求，产品已占位。
4. **领域纵深**：SysML V2 原生 + 本体推理 + INCOSE 类确定性质量工具（model_quality/requirement_quality/coverage）——Siemens/PTC 的"规则+LLM 混合质量门"同款思路，产品已有雏形。
5. **诚实的数据治理**：2026-10-23 主动清理 53 条测试会话/8 个测试账号/2,399 行假归属，下线纯前端假审批页——产品自己拆假能力，这在行业里罕见。

### 1.4 结构性问题（按严重度排序）

| # | 问题 | 现状数据 | 行业对标差距 |
|---|---|---|---|
| P-1 | 能力中心五类能力不统一 | 4 张能力表 + agent_tools 汇合；度量大面积空白；15/27 Agent 零调度 | Coze 资源库统一复制/转移/导入；Dify Marketplace 统一安装+审批复用 |
| P-2 | 守护面窄于采集面 | 告警规则 1 条 / BadCase 0 行 / trace 仅编排流量 | LangSmith 在线评测+Engine 闭环；Coze 罗盘评测集/评估器/实验 |
| P-3 | 能力"发布即生效"语义缺失 | 插件/技能版本在表但无热更新语义；调用方版本绑定不清 | Coze：插件发布新版本→调用方自动用最新版 |
| P-4 | 无"接入前测试" | 数据源/知识接入无检索测试门；Agent 无发布前试运行门 | Dify Knowledge Pipeline 检索测试；Coze 发布绑定测试集 |
| P-5 | 上下文工程未指标化 | 有 memory/offload/压缩，无 token 经济学/压缩可恢复性/目标重述的度量与约束 | Manus 六原则（KV-cache、mask don't remove、可恢复压缩、recitation） |
| P-6 | 推理策略硬编码 | ReAct/团队路由/DAG 引擎写死在 pipeline | Dify：Agent Strategy 可插拔 + 开放标准（YAML+CLI） |
| P-7 | 部署形态单一 | 仅单副本私有化 | LangGraph 4 模式（SaaS/混合/全自托管/单容器） |
| P-8 | 前端工程债 | 1,118 全局函数无命名空间；拆分即静默失效 | —（不影响本方案三大中心，列风险） |

### 2.1 六平台 × 九维横评（摘要，详表见调研底稿）

### 2.2 行业共识（8 条，本方案的"必做"判据）

1. **双模编排**：确定性工作流 + 自主 Agent 节点并存互调（产品已有 DAG+pipeline，✅）
2. **能力中心四件套**：统一注册 / 市场双轨 / 版本语义 / 审批授权（产品 ✗——P-1）
3. **RAG 流水线工程化**：分块/索引/检索参数可调 + **接入前检索测试**（产品 ✗——P-4）
4. **可观测三件套 + 评测闭环**：trace/日志/指标底线 + **离线+在线双轨评测**（产品半 ✅——P-2）
5. **工具级 HITL**：approve/edit/reject 语义 + 风险评级（产品 ✅ L0-L2 + 钩子；缺 edit 语义）
6. **沙箱隔离执行**（产品部分：sandbox.py + 无 stdio MCP；缺工具执行级沙箱）
7. **多形态交付**：API/SDK/嵌入/MCP server（产品 ✅ 有 MCP 服务端雏形）
8. **grounded + 可追溯**（产品 ✅ 行业里属于前排）

# 4. 产品优化方案

> 设计原则：① 每项优先**复用现有资产**（不推倒重来）；② 判据可验证（验收标准写成可跑的门禁）；③ 不碰 §1.3 优势清单的行为。

## 4.1 能力中心（Capability Center）——「一个注册处、一个市场、一套版本、一套度量」

### 4.1.1 统一能力注册处（P0）

**现状病灶**：`tools`/`skills`/`plugins`/`mcp_servers` 四张表 + `prompts` 各自建表，启停/版本/度量各写一套；Agent 侧靠 `agent_tools`（164 行绑定）汇合。

**方案**：新增**逻辑统一层**（不动存量表结构，零迁移风险）：

```
capability_registry（新表，逻辑视图，行由各源表投影/双写维护）
  capability_id   统一 ID（tool:{id} / skill:{id} / plugin:{id} / mcp:{server}:{tool} / prompt:{id}）
  kind            tool | skill | plugin | mcp_tool | prompt
  source_table / source_id   投影回源表的指针（权威数据仍在原表）
  status          active | disabled（由源表 status 同步）
  version         语义化版本（源表 version 缺省补 1.0.0）
  publisher       作者（个人/团队/官方/市场）
  visibility      private | team | public（权限分流基础）
  risk_level      read | write | destructive（驱动 HIL 审批强度，对标 OpenAI 风险矩阵）
  metrics_json   {calls, successes, failures, avg_latency, last_used_at}（统一度量投影）
```

- **双写收口**：所有能力调用必经 `core/capability_gate.py` 一个函数（现有 tool 调用/MCP/skill 注入全部收拢到该门）→ 落 `capability_call_logs`（一张表度量全部五类能力，直接消灭 plugin_call_logs 0 行/use_stats 空白）。
- **零调度治理**：`metrics_json.last_used_at` 为空且创建 >90 天的能力，自动进「长尾清单」（复用 evolution_report 周报出口），由人决定停用/下架——对标 LangSmith Engine 聚类，但**只提议不自动执行**（延续本产品自进化纪律）。
- **验收判据**：`verify_capability_registry.py` 断言四源表每行在 registry 有投影、调用日志五类齐（tools/verify 门禁体系 +1，现有 189 门禁同款模式）。

### 4.1.2 版本语义与发布即生效（P0）

**方案**：
- 能力版本改为「发布态」：draft → published（发布时冻结 manifest 快照存 `capability_versions`）；Agent 绑定记录 `pinned_version`，**缺省跟随最新 published**（对标 Coze 发布即生效）。
- 技能 ZIP/插件 manifest 发布时跑**发布前检查**（对标 Coze 发布绑定测试集 + Dify 接入前测试）：schema 校验 + 冒烟用例（skill 跑内置 example、plugin 跑 dry-run invoke）→ 不过不发。
- 回滚 = 改绑定 pinned_version（已有 plugin_versions 表可直接复用）。

### 4.1.3 市场双轨与授权（P1）

- 复用现有 `studio/market` + `share`：personal space → team space → **enterprise space** 三档可见性（对齐 Coze 个人/企业工作空间语义 + Dify workspace 复用），敏感能力（写智源/改图库）默认 enterprise-only。
- 审核流已有（plugin_review_policy=forced），扩展到技能/工具市场上架。

### 4.1.4 HIL 审批强度矩阵（P1，低成本高价值）

- 现有 `tool_hooks`（4 条确定性规则）+ HIL L0-L2 分级 + `risk_level` 新字段 → 组合成**审批强度矩阵**（对标 OpenAI 风险评级 + LangGraph 四级决策）：
  - read + L0 → 直出；write + L1 → 草稿预览；destructive（覆盖导入/删图/发布）→ **require_confirm 卡片**（已有 ask_user/hil_confirmations 承载，无需新建）
  - 补 LangGraph 式 **edit 语义**：确认卡支持"改参数后批准"（hil_confirmations.payload 已是快照，扩展 edited_payload 字段即可）。

## 4.2 资料中心（Knowledge Hub）——「接入有门、检索有评、运营可编排」

### 4.2.1 知识接入流水线 + 检索测试门（P0）

**现状病灶**：ingest 管道（解析→分块→embed）很强，但**接入前没有检索测试**——分块烂不烂、检索准不准，要到对话里翻车才发现。

**方案**（对标 Dify Knowledge Pipeline）：
- 新增 `kb_pipeline_runs` 表 + `/api/knowledge/pipeline` 端点：一次接入 = 一条 pipeline run，记录 5 个阶段的产物与指标（抽取字符数/分块数/空块率/embed 覆盖率）。
- **接入门禁**：run 结束自动跑探测集（每个知识库维护 5-20 条「问题→期望命中 chunk」探针，可人工维护或从 query_trace 高频 query 自动生成）→ 产出 Recall@k/MRR；**低于阈值（默认 Recall@5<0.6）标黄警告**，允许强制接入但留痕（不硬拦——本产品纪律：宁可提示不静默）。
- 检索参数（chunk_size/overlap/top_k/rerank 开关）从代码常量上移为**库级可配**（复用 settings 白名单机制），A/B 留痕。

### 4.2.2 Agentic RAG：检索质量评估-改写-回退环（P1）

**现状病灶**：QueryRouter 按 graph 置信度 0.75 路由 graph/mixed/vector 是静态分流；无"这次检索质量不行→改写 query→换源"的循环。

**方案**（对标 Dify Agentic RAG）：
- 在 RAG 链路末级加**检索自评**：rerank 后 top1 分数分布 + 引用覆盖度 → 质量信号（高/中/低）。
- 低质量触发一次**自动改写重检**（HyDE 已有，扩为 query rewrite：同义改写/拆子问/去噪）→ 仍低则**回退到图谱子图遍历**（GraphRAG 已有）→ 仍低则**如实回答"资料不足"**（与 citation 无据声称指标闭环，防编造）。
- 全程入 `query_trace`（已有 3,270 行留痕），新增 `rag_quality` 列。

### 4.2.3 知识运营编排化（P1）

- 把知识库的**增/删/查**暴露为 DAG 节点（对标 Coze 知识库节点）：FlowExecutor 15 种节点新增 `knowledge_read`/`knowledge_write`（写走 HIL L2 队列，天然复用确认机制）——典型场景："每周一从飞书同步新规范→入库→重建索引→通知"变成一条可编排 flow（现有 agent_flows 69 行的直接扩展）。

### 4.2.4 多模态与压缩纪律（P2）

- 多模态（图片/音频）入 ingest：MinerU 已有图片解析能力，扩 embedding 侧（Qwen-VL 类）——P2，客户场景驱动再做。
- 压缩纪律落地 Manus「可恢复压缩」：memory 注入预算（已有 memory.project_memory_chars=600）+ tool_result offload（已有 TTL 30 天）→ 补一条纪律：**压缩/淘汰必须保留可取回引用**（offload 已有 path，memory 归档 tier=archival 已有）——把已实现的机制写成显式不变量并加门禁。

## 4.3 运行监控（Ops Center）——「从采集面到守护面，接通生产回流」

### 4.3.1 告警规则体系化（P0）

**现状病灶**：`alert_evaluator` 300s 周期在跑，但 `alert_rules` 仅 1 条 active——守护面覆盖极窄。

**方案**：预置 **10 条规则**（全部基于已有真数据表，零新采集）：
| 规则 | 数据源（已有） | 默认阈值 |
|---|---|---|
| LLM 失败率突增 | llm_usage_stats（13,352 行） | 5min 失败率 >30% |
| 成本突增 | llm_usage_stats token 聚合 | 小时成本 >3× 7日均值 |
| 延迟劣化 | llm_usage_stats latency | P95 >2× 7日均值 |
| 编排批次停滞 | flow_runs/orch_checkpoints | running >30min 无事件 |
| 确认队列积压 | hil_confirmations（10 行 pending） | pending >20 或最老 >24h |
| 审计链破损 | audit_logs 哈希链 | 任何断点（即时） |
| 检索质量下滑 | query_trace.rag_quality（4.2.2 新增） | 低质量占比 >40%/h |
| 意图误判上升 | intent_samples/eval_reports | macro-F1 <0.85 |
| BadCase 增速 | bad_cases（4.3.2 入库后） | 同类 >5 条/天 |
| 登录失败突增 | auth 日志 | 5min >10 次 |

每条规则带 cooldown（已有 30min）+ ack（已有）+ **通知出口**（现有 SSE/审计；补飞书 webhook——用户已有 Hermes 飞书集成资产可复用）。

### 4.3.2 BadCase 真实入库（P0）

**现状病灶**：badcase.py 检测器注册表设计良好，但 `bad_cases` 0 行——dry-run 从未 apply。

**方案**：默认 dry-run 保留（安全），但**把"从未 apply"变成可见状态**：周报展示"检测到 N 条候选未入库"，一键 apply（进 hil 式人工确认）；入库后按 error_profile 聚类（attribution.py 已有）驱动 4.3.1 的 BadCase 规则 + 进 4.3.3 的 dataset 回流。

### 4.3.3 在线评测闭环（P0，本方案最高杠杆项）

**现状病灶**：评测全离线（意图样本池/检索 qrels/生成质量指标），**生产流量不回流**——行业核心闭环（LangSmith Engine、Coze 罗盘人工校准）整段缺失。

**方案**（对标 LangSmith thread 级评测 + Coze 罗盘三段式，全部复用现有资产）：
```
生产流量（messages 377 + query_trace 3,270 + llm_usage_stats 13,352）
   │  ① 采样器：按策略采样（负反馈优先/低置信优先/随机 5%）——复用 ux_metrics 负向信号
   ▼
online_eval_queue（新表，候选样本，含完整 trace 引用）
   │  ② 自动评估器（reference-free）：citation 完整性/无据声称/格式合规/延迟
   │     ——eval_generation_quality 的确定性指标直接搬来确定性子集
   ▼
人工标注队列（复用 hil_confirmations 交互模式：确认卡 = 评分+原因）
   │  ③ 转正：人工确认的样本 → intent_samples/检索 qrels/生成质量 dataset
   ▼
回归门禁：下次相关发布自动跑 dataset（evaluation.py 门禁接线已有 189 个门禁的同款机制）
```
- **关键纪律延续**：系统自动打分只进"建议"，人工确认才转正为标签（同 intent_samples 的 confirmed 纪律，防自我循环）。
- **验收判据**：`verify_online_eval_loop.py` 端到端夹具跑通「采样→自动评→人工转正→进 dataset→门禁可见」。

### 4.3.4 会话级全链路 trace（P0）

**现状病灶**：`orch_run_spans` 仅 57 行且只覆盖编排流量；**会话直答（chat 主路径）无 span**。

**方案**：OpenTelemetry 兼容的轻量 span 模型（不自建 OTel collector）：
- 每次 `/chat/stream` 建 conversation span，ReAct 每轮/每工具调用/每次 RAG/每次 LLM 建子 span → 落 `run_spans`（扩展现有表，加 `kind='conversation'`）。
- 步骤级归因（attribution.py「哪一步开始错」）从编排扩展到会话。
- trace 查询进 monitor 页「会话下钻」（已有入口，补数据）。

### 4.3.5 评测资产产品化（P1）

- 对标 Coze 罗盘：评测集（版本管理）/评估器（LLM+Code 双型）/实验（多实验横向对比）三段式产品化——现有 eval_reports 25/eval_metrics 53 是数据底，缺的是**版本与对比 UI**（monitor 页 pg-eval 已有雏形，扩）。
- 人工校准入口 = 4.3.3 的标注队列（同一套交互，不建第二套）。

## 5. 实施路线图

| 阶段 | 周期量级 | 内容 | 出口判据 |
|---|---|---|---|
| **P0-a 度量收口** | 2-3 周 | capability_registry + capability_call_logs 双写收口 + 版本发布态 + 告警 10 条 + BadCase 入库 | 五类能力调用同表可查；`plugin_call_logs` 类空白消灭；告警覆盖 10 规则 |
