### 1.2 工程纪律（本计划所有改动必须遵守）

1. **换行符 LF**：新增/改写文件一律 LF；写盘后 `file` + `git diff --stat` 复核，禁止 CRLF 入库。
2. **文本级改写两道门**：锚点命中数断言（防重复命中）+ 落盘后语法终检（`python -m py_compile` / `node --check`）。
3. **静态断言必须做变异自证**：断言"跑通了"不证明断言有效，必须把 bug 还原回去看断言是否 FAIL。
4. **有可达后继才删代码**：删任何函数前先跑全仓引用扫描，确认无调用点。
5. **动数据前必须先备份**：`sqlite3.Connection.backup()` 到库副本，在副本上验证通过才碰真库。
6. **验收判据用绝对量**：禁止「A + B == 总量」这类语义恒等式（会被"两边同时错"骗过）。

## 4. B1 · P0 正确性与合规

### 4.1 P0-1 时态主键解耦 —— 本轮最高价值项

#### 4.1.1 问题的精确形态（比"时态空转"更具体）

七个环节**全部就位**，断在第八环（物理约束）：

| # | 环节 | 落点 | 状态 |
|---|---|---|---|
| 1 | 双时态列 | `migrations/ontology.py:199-203`（`valid_from/valid_to/is_current/tx_from/tx_to`） | ✅ |
| 2 | 性能索引 ×3 | `ontology.py:216-218` | ✅ |
| 3 | 时态视图 ×2 | `ontology.py:230/233`（`v_current_entities` / `v_temporal_entities`） | ✅ |
| 4 | **历史写入函数** | `knowledge_repo.py:98 update_with_history`（:111 置 `valid_to` + :116 插新行） | ✅ 但**死代码（0 调用）** |
| 5 | 查询端点 | `entities.py:70 /history`、`entities.py:81 /at?as_of=` | ✅ |
| 6 | 仓储查询 | `knowledge_repo.py:72 list_entity_history`、`:82 get_entity_as_of` | ✅ |
| 7 | 时态 SPARQL 代理 | `services/temporal_sparql.py` 经 `routers/sparql.py:30/63` 接线 | ✅ |
| 8 | **主键允许版本行共存** | `PRIMARY KEY (id, branch)` | ❌ **阻塞点** |

**推论（三条，均可证）**：

1. `update_with_history` 一旦被调用 → INSERT 第二行 → **UNIQUE 冲突**。所以主路径 `update_entity`（`knowledge_repo.py:192`）只能走 `:204` 的原位 UPDATE → **永不产生历史行**。
2. 实测 `valid_to IS NOT NULL` = **0/189**、同 `(id,branch)` 多行组数 = **0** → 与推论 1 一致。
3. `/history` 恒返 1 行；`/at?as_of=` 对任意历史时刻命中的都是当前行 → **时态 SPARQL 的 `asOfProxy` 也同步空转**。

**杠杆点**：修此一项，第 4/5/6/7 环**同时复活**。

#### 4.1.2 方案 B（推荐）：影子历史表

**设计**：

```
entities           语义不变 = 仅当前行（主键 (id,branch) 保持原样）
                   → 320 处引用零改动，v_current_entities 恒等主表（兼容）

entity_versions    新增 = 历史行（每次变更追加一行）
  id TEXT           — 实体 id（与 entities.id 同体系）
  branch TEXT       — 分支
  version_no INTEGER— 该 (id,branch) 内递增序号（1,2,3…）
  valid_from TEXT   — 本版本生效时间（= 变更时刻）
  valid_to TEXT     — 本版本失效时间（NULL = 当前版本）
  is_current INTEGER— 1=当前行镜像，0=历史（便于与主表对拍）
  tx_from/tx_to     — 事务时间
  name / entity_type / properties / status / knowledge_category / project_id …
                    — 版本快照字段（与 entities 同名同型）
  change_kind TEXT  — create | update | review | category | merge
  changed_by TEXT
  PRIMARY KEY (id, branch, version_no)
  UNIQUE (id, branch, valid_from)
```

**写入路径改造**（把死代码接上，而不是新写）：

| 改动 | 落点 | 说明 |
|---|---|---|
| W1 | `knowledge_repo.py:98 update_with_history` | 改写为：① 读旧行 → ② `INSERT INTO entity_versions`（旧值快照，`valid_to = now`, `is_current=0`）→ ③ `UPDATE entities`（新值，主表原地）→ ④ `INSERT INTO entity_versions`（新值，`valid_to=NULL`, `is_current=1`） |
| W2 | `knowledge_repo.py:192 update_entity` | 由"直接 UPDATE"改为**委托 `update_with_history`**（两处写路径合一） |
| W3 | `knowledge_repo.py:233 review_entity` | 状态流转同样落版本（`change_kind='review'`） |
| W4 | `create_entity`（`:172`） | 建实体时写首版本（`version_no=1`） |

**查询路径改造**：

| 改动 | 落点 | 说明 |
|---|---|---|
| R1 | `knowledge_repo.py:72 list_entity_history` | 改读 `entity_versions`（按 `version_no` 倒序） |
| R2 | `knowledge_repo.py:82 get_entity_as_of` | 查 `entity_versions WHERE valid_from <= as_of AND (valid_to IS NULL OR valid_to > as_of)`；**查不到则 fallback 主表**（兼容未初始化场景） |
| R3 | 新增视图 `v_entity_versions_current` | 可选，供 SPARQL 代理统一入口 |

**数据初始化（关键，不可省）**：现有 189 行**必须灌入历史表作为初始版本**，否则 `/at` 对"当前时刻"会 fallback，语义不一致。

```sql
-- 幂等：仅在目标 (id,branch) 无任何版本行时插入
INSERT INTO entity_versions (id, branch, version_no, valid_from, valid_to, is_current,
                             tx_from, tx_to, name, entity_type, properties, status,
                             knowledge_category, project_id, change_kind, changed_by)
SELECT e.id, e.branch, 1,
       COALESCE(e.valid_from, e.created_at), NULL, 1,
       COALESCE(e.tx_from, e.created_at), NULL,
       e.name, e.entity_type, e.properties, e.status,
       e.knowledge_category, e.project_id, 'init', COALESCE(e.created_by, '')
FROM entities e
WHERE NOT EXISTS (SELECT 1 FROM entity_versions v WHERE v.id = e.id AND v.branch = e.branch);
```

**为什么 B 优于 A（量化对比）**：

| 维度 | A：改主键为 `(id, branch, valid_from)` | B：影子历史表 |
|---|---|---|
| 必须审查的 SQL | **48 处** `WHERE id=? AND branch=?` 需补 `AND is_current=1` | **0 处** |
| 漏改的后果 | 更新命中历史行 → **静默数据损坏**（最难发现的一类） | 无此风险 |
| 需重建表 | 是（SQLite 不支持 ALTER PK），需手抄 **26 列** | 否（仅新增表） |
| 漏列的后果 | 列丢失 → **静默数据丢失** | 无此风险 |
| 可回滚性 | 差（需反向重建） | 好（删表即回滚，主表未动） |
| 可增量/可开关 | 否 | 是（可先写不读） |
| 行业实践 | 少见（主表混版本） | 常见（Stardog/Foundry 版本独立存储） |
| 代价 | — | `/history` `/at` 各改 1 函数；需一次性初始化灌数据 |

**A 的适用条件**（记录备查）：若未来要求"单表 SQL 时间旅行自然化"（如任意 SQL 加 `AS OF` 即得历史态），则 A 才有必要性，且**必须配套**：① 逐处审查 48 处 SQL；② 全量回归测试；③ `_rebuild_entities_pk` 范式的列清单从 DDL 自动生成而非手抄。

### 4.2 P0-2 分支保护规则配置化

**现状**：`PROTECTED = {DEV_BRANCH, RELEASE_BRANCH, PERSONAL_BRANCH}`（`routers/branches.py:23`）是**分支名硬编码集合**；`_check_writable_branch`（`:31`）只护 `release`。使用点 `:124`（同步）、`:431`（改名）、`:456`（删除）。

**方案（按 D5：按类型给默认 + 分支级覆盖）**：

- `branches` 增列 `protection_rules TEXT DEFAULT '{}'`（JSON）。
- 规则 schema：

```json
{
  "writable": true,          // 是否允许直写实体/文档
  "deletable": false,        // 是否允许删除分支
  "renamable": false,        // 是否允许改名
  "required_reviews": 0,     // 合并前必需评审数（0=不要求）
  "allow_direct_push": true  // 是否允许绕过 MR 直接提交
}
```

- 类型默认值：`release` → `{writable:false, deletable:false, required_reviews:1}`；`dev` → `{writable:true, deletable:false}`；`personal`/`local` → `{writable:true, deletable:true}`。
- `PROTECTED` 常量**保留为兜底**（读不到规则时回退），`_check_writable_branch` 改为读规则。
- 迁移落点：`database/migrations/columns.py` 的 `_add("branches", "protection_rules", "TEXT DEFAULT '{}'")`（该文件已有 `_add` 幂等范式）。

**验收**：① 改 `dev.protection_rules.deletable=true` 后能删 dev（副本验证）；② **既有保护行为零回归** —— `release` 直写仍被拒、`release/dev/personal` 仍不可删；③ 规则变更写审计。
**改动规模**：1 列迁移 + 1 常量改造 + 3 处使用点读规则。
**风险**：低。

### 4.3 P0-3 commit 内容哈希

**现状**：`knowledge_commits` 无 `content_hash`（列实测：`id, branch, parent_id, kind, message, changes, snapshot, created_by, created_at, source_branch, source_head_commit`）。**写入路径唯一**：`commit_repo.py:17 create_commit`（`:29` INSERT）。

**方案**：
- 增列 `content_hash TEXT DEFAULT ''`；算法 `sha256(f"{branch}|{parent_id}|{kind}|{changes}|{snapshot}")`（`changes`/`snapshot` 用**规范化 JSON**：`sort_keys=True, separators=(',',':')`，否则键序变化会误报）。
- `create_commit` 写入时计算；新增自检端点 `GET /api/branches/commits/verify`（全量重算比对）。
- 回填：489 行按上述算法补齐（一次性脚本，幂等）。

**验收**：① 篡改任一行的 `changes` → 自检端点**报告该行不匹配**；② 未篡改时全绿；③ 变异自证：把哈希改为不含 `snapshot` → 篡改 snapshot 用例**必须 FAIL**。
**改动规模**：1 列 + 1 函数 + 1 端点 + 1 回填脚本。
**风险**：低。**注意**：`changes` 若含未排序键序，回填与运行时算法必须一致（同一函数复用）。

### 4.4 P0-4 权限门补齐 —— 最省力项（建议最先做）

**为什么说最省力**：实测 `roles.permissions` **已经定义好权限域与 op**，只是路由**没挂装饰器**：

| 角色 | `branch_dev` | `branch_release` |
|---|---|---|
| 设计师 | `['create','switch','merge_request']` | `['view']` |
| 知识工程师 | `['create','switch','merge_request']` | `['view','review_merge','rollback']` |
| 系统管理员 | `[]`（但 `admin` 域非空 → 超级用户） | `[]` |

**现状缺口**（实测 `require_permission` 在 `routers/branches.py` 只有 2 处：`:286` 审批、`:399` 回滚）：

| 端点 | 行 | 语义 | 应挂门 | 现权限是否已覆盖 |
|---|---|---|---|---|
| 建分支 | `:72` | `POST /api/branches` | `branch_dev:create` | ✅ 设计师/知识工程师已有 |
| 建 MR | `:223` | `POST /api/branches/merge-requests` | `branch_dev:merge_request` | ✅ 已有 |
| 解决冲突 | `:188` | `POST .../resolve-conflict` | `branch_dev:merge_request` | ✅ 已有 |
| 删分支 | `:454` | `DELETE /api/branches/{name}` | `branch_dev:delete`（**新 op，需补授权**） | ⚠️ 需给设计师/知识工程师补 `delete` |

**方案**：前 3 处直接加 `user=Depends(require_permission(...))` —— **零行为回归**（现有角色已覆盖）。删分支因 `delete` 是新 op，需同步在角色权限矩阵补键（`roles.permissions` 的 `branch_dev` 数组加 `"delete"`），**否则设计师/知识工程师会被 403** —— 这是唯一的行为变更点，必须显式确认。

**两个必须记录的设计事实**：
1. `require_permission` 对**匿名请求直接放行**（`core/deps.py:94` docstring 明写"向后兼容"）。这意味着**未登录仍可绕过**。是否收紧（改为默认拒绝）属产品决策，本计划**不改**，但需在上位文档标注为已知取舍。
2. 角色 `107-112`（`载荷审评专家*`，custom 类型）**权限为 NULL/空** → 这些账号挂门后将全部 403。需确认是否为废弃测试账号（实测 `users` 表有大量 `chen*` 测试账号 `role_id=1` 无法解析角色）。

**验收**：① 设计师调建分支 → 200；② 无权限角色 → 403 且带 `需要 branch_dev:create 权限`；③ 匿名仍 200（现状保留）；④ 审计留痕。
**风险**：低（除删分支的授权补键需确认）。

### 5.3 P1-3 开发分支细分（FR-KG-14）

## 7. 验收门禁（DoD）

**每个批次完成的定义**：

| 批次 | DoD |
|---|---|
| **B0** | 3 文档状态回写 + 3 处注释修正；`git diff` 仅涉及注释与文档；无行为改动 |
| **B1** | ① 4 项各自的验收判据全绿；② **每项静态断言附变异自证**（回退实现 → 断言 FAIL）；③ P0-1 的库副本 PoC 记录留档；④ 真库改动前有备份文件；⑤ 既有保护/权限行为零回归测试通过 |
| **B2** | ① 5 项验收判据全绿；② 产生**真实数据**（非夹具）；③ 涉及本体/模型的项先确认再执行 |
| **B3** | 各自独立立项，单独定义 DoD |

**通用门禁（所有批次）**：

1. 换行符：新增/改写文件 `file` 检为 LF。
2. 语法：`.py` 过 `py_compile`，`.js` 过 `node --check`。
3. 文本改写：锚点命中数断言 + 落盘后语法终检。
4. 数据变更：先备份、后验证、再落库。
5. 提交：按批次独立提交，提交信息带需求编号。
