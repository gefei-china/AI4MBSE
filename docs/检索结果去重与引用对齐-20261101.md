## 一、"只引用三条"的真实原因

**不是模型偷懒，是它物理上只能引 3 条。**

`rag.inject_k=3` 控制最终注入 prompt 的片段条数。模型看到的【来源n】**最大编号就是 3**，
而引用规则明令禁止标注不存在的编号 ⇒ 结构上引不出第 4 条。

### 铁证：366 条历史助手消息统计

| 界面 citations | 消息数 | 日期范围 | 正文完全没标注 | 正文最大编号分布 |
|---|---|---|---|---|
| **8 条**（写死 `[:8]`） | 33 | 09-10 ~ 10-14 | 22 条 | 11 条打满 **3** |
| **3 条**（改为同源后） | 25 | 10-16 ~ 10-29 | 9 条 | 11 条打满 **3** |
| 0 条（未触发检索） | 187 | — | 186 条 | — |

关键：界面给 8 条的那 33 条消息里，**正文编号从来没有一次超过 3**。
说明模型不是"少引"，而是**每次都把上限用满**（25 条里 11 条打满 3）。

而界面那 8 条里的后 5 条，编号在 prompt 里根本不存在 ⇒ 是一排**点不动的死编号**。

**处置**：`inject_k` 3 → 5（`core/config.py`），`_citations_payload` 早已改为读同一项。
实测一次真实检索：注入 5 条 / citations 5 条。

## 二、重复副本占满配额槽（新发现）

`mbse.db` 里 id=847 与 id=848 是**同一份 PDF 导入两次**：

- 同名、同 `file_size=513027`、55 个 chunk **逐条比对 0 处差异**
- 但 `source_doc` 形态不同：`847_Print_xxx.pdf` vs `Print_xxx.pdf`

后果（query `自主可控 部署 数据存储`）：

```
注入 5 条，文档分布 = {847_xxx: 2, xxx: 2, 热管理.md: 1}
⇒ 5 槽里 4 槽是同一份物理文件，界面看着引了 3 个文档、实际只有 2 个真实来源
```

根因：`select_diverse` 的 `per_doc_max` 按 `source_doc` **字符串**计数，两个副本名字不同
⇒ 被当成两个独立文档，各占 2 槽。

### 修法（不动任何数据，纯读取态变换）

新建 `agent/retrieval_dedup.py`：

| 函数 | 判据 | 为什么这样判 |
|---|---|---|
| `dedupe_exact` | **正文逐字相同**且 `document_id` 不同 ⇒ 判副本 | 同文档相邻 chunk 有重叠但绝不会逐字相同（Jaccard 中位数 0.659）⇒ 零误伤 |
| `normalize_doc_names` | 前缀数字 **== 该条 `document_id`** ⇒ 剥掉 `{id}_` | 若按"去前缀后名字也在本批"判，去重删掉副本后对照物就没了，**归一化永远不生效**（踩过） |

位置：`agent/rag.py` 拒答判定**之后**统一执行一次，原始命中与关键词重试捞回命中一视同仁。

**效果**：命中 20 → 13，文档数从"名义 3 / 实际 2" ⇒ **4 个真实文档**。

## 三、零召回救回（bigram 降级态）

### 现象

```
信息安全有哪些要求      → 0 条
信息安全               → 2 条   ← 正文是技术要求书 7.4 的信息安全条款，内容完全正确
这个系统对可靠性有什么要求吗 → 0 条
```

根因：embedding 三家全挂 → bigram-tf 降级 → 问句里"有哪些/怎么/吗"把 2-gram 重叠比例稀释掉。

### 三层闸门（每一层都是踩坑换来的）

1. **只在零召回时触发** —— 实测 `需求应该怎么写才规范` 原本 13 条，重试反而变 0 条。
2. **只收实词且长度 ≥ 3** —— 2 字的 `要求` 参与拼接会让命中从 0 涨到 19 条噪声。
3. **只收含中文的词** —— 这一条把域外拒答准确率从 1.000 拉回：
   `如何用 Python 写一个网页爬虫` 抽出 `Python` → 召回 **17 条** SysML 规范里"顺带提到 Python"
   的段落，relevance 高达 0.34，越过了域外拒答线 ⇒ 把域外问题救成"有答案"。

另有一条坑：jieba 把 `这个系统对…` 切成 `系统对/l`（习用语），用它会召回 20 条噪声。
所以词性白名单必须排除 `l`。

### 位置很关键

一开始放在 `hybrid_search` 之后判断 `if not chunk_hits` —— **永远不会触发**，
因为降级态下 hybrid_search 总能返回 20 条字面巧合，"零召回"在过滤前几乎不成立。

正确位置：**域外拒答判定内部**。当分数低到要拒答时，用关键词再确认一次；
重试仍能命中 ⇒ 说明查询携带的领域实词在库里有对应内容 ⇒ 域外的前提不成立。

**效果**：

| query | 修复前 | 修复后 | 内容是否相关 |
|---|---|---|---|
| 信息安全有哪些要求 | 0 | **1 条** | ✅ 7.4 信息安全条款 |
| 这个系统对可靠性有什么要求吗 | 0 | **1 条** | ✅ "异常处理、平滑降级、重试"条款 |
| 今天北京天气怎么样 | 0 | 0 | ✅ 仍拒答 |
| 红烧肉怎么做 | 0 | 0 | ✅ 仍拒答 |
| 如何用 Python 写网页爬虫 | 0 | 0 | ✅ 仍拒答 |

## 四、引用逐位错位（最严重，既有缺陷）

### 现象

`_citations_payload`（界面引用数据）一直用**原始** `chunk_hits[:k]`，
而 prompt 里的【来源n】用的是 `select_diverse` **之后**的结果（受 per_doc 配额、近邻合并影响）。

实测 query「自主可控在部署和数据存储方面有什么要求」：

```
【来源3】= 广汽方法论 §1.2.1.2.3  (chunk 12)
citations[3] = 技术要求书 §5.3.1   (chunk 26)     ← 位次 3/4/5 全错
```

后果：模型写 `[3]` 指的是广汽方法论，用户点界面第 3 条看到的是技术要求书
—— **引用指向错误的证据**，比"少引几条"严重得多。

### 修法

在 `agent/retrieval_diversity.py` 新增**共用选择器** `select_for_injection()`，
`context.py`（prompt 注入）与 `agent/utils._citations_payload`（界面引用）都只调它。

不复用不行：两边各抄一份相同参数，早晚因单边改参数再次错位
（这正是 B5-10「四处各写一份数字」的同族问题）。

**效果**：逐位一致（chunk 51/24/12/19/26 两侧完全相同）。

## 九、`inject_k` 的 A/B 标定（把"5 合理"从推断变成实证）

### 为什么必须另建用例集

既有评测集 `retrieval_baseline.py` 判的是**文档级命中**（`source_doc` 含关键词），
而 `inject_k` 影响的是**文档内部的注入截断** —— 文档召回到了、答案所在的 chunk 被截在第 k 条之外，
模型照样看不到。所以既有评测集对 `inject_k` **天生不敏感**。

这一点早有记载（`docs/AI上下文配置项-依据与行业对标-20260921.md` §8.7）：
> `inject_k` 未被直接测到：doc 域 gold 是"章节内全部 chunk"（平均 6.5 条），
> 3 条注入量下 recall 对"注入截断"不敏感；要测 `inject_k` 需另建"单答案"用例集。

### 新建的"单答案"用例集

`tools/eval/eval_inject_k_ab.py`，17 条用例，每条 = (问题, **答案锚点**, 期望文档)。

- 锚点取该章节的**独有短语**（如 §7.3 的 `99.9%`、§7.2 的 `平滑降级`）
- **脚本自动校验锚点只出现在 1~3 个 chunk**，不满足即 `exit 1` —— 不静默跳过
  （第一次就抓出 5 条不合格用例：`MagicDraw`/`OAUTH2`/`OpenAI API`/`HTTP/REST` 各 4 chunk、
  `问题域和方案域` 8 chunk，已替换成合格锚点）
- 指标 **anchor_hit@k**：注入的前 k 条里，是否真的出现了承载答案的那个 chunk

### 实测结果（17 条，同一批候选，唯一变量是 k）

| inject_k | anchor_hit@k | 平均注入字数 | 平均文档数 | 噪声率 |
|---|---|---|---|---|
| 3 | **16/17 = 0.941** | 1611 | 1.88 | 0.333 |
| **5（当前生效）** | **17/17 = 1.000** | **2444** | 2.82 | 0.494 |
| 8 | 17/17 = 1.000 | 3697 | 3.47 | 0.478 |

### 漏答案明细（区分"没召回到"与"召回到被截断"）

```
inject_k=3  「验收交付要求交付哪些文档」 锚点=源代码使用说明
            → 候选池里有、被第 3 条截断挡住 ← inject_k 太小（池 15 条）
inject_k=5  无漏答案
inject_k=8  无漏答案
```

### 结论

1. **3 确实不够**：有一条答案**已经召回到**，却因为排在第 4 位之后进不了上下文。
   这是"只引三条会漏答案"的**直接实证**（此前只是推断）。
2. **5 是合理档位**：17/17 全中，成本 2444 字（约 +1.5k token），可接受。
3. **8 是纯浪费**：anchor_hit **零提升**（都是 1.000），字数再 +51%。
   ⇒ 不要再往上加，这有数据支撑，不是凭感觉。

当前生效配置实测：`rag.inject_k=5 ⇒ anchor_hit=1.000、平均注入 2444 字`。

复跑：`./.venv/Scripts/python.exe -X utf8 tools/eval/eval_inject_k_ab.py --tag <标签>`

## 十、对话级验证（真实 HTTP 链路，2026-11-01 17:30-18:00）

> 米爸问：「有直接在 AI 对话中实际验证效果吗」
> 诚实回答：**之前没有**。前面所有验证都是脚本级（直接调 `retrieve()` 看注入内容），
> 那只证明"答案有没有进上下文"，不证明"模型有没有因此答对"。本节补上。

### 10.1 为什么脚本级不够

`anchor_hit@k` 是中间指标，它与最终回答之间至少隔着三处失效：

1. 答案进了上下文，但模型没读/没引用（Lost-in-the-Middle）；
2. 答案进了上下文，但模型用自身知识答成另一种说法（看似答对、与本次改动无关）；
3. **上下文里没有答案，模型照样编出一个很像的回答** —— 脚本测不出来。

### 10.2 实验设计（`tools/eval/eval_inject_k_chat_ab.py`）

- 真实 `POST /api/conversations/{id}/chat`，走完整链路（意图 → 检索 → prompt → LLM → 引用回填）
- 每档**新建独立会话**（复用会话会让历史消息进上下文，两轮起点不一致就不是公平对比）
- 唯一变量 `inject_k`，经 `PUT /api/system/config/static` 切换并**回读校验**
- 判据改为**四态**，而不是"答对/答错"：

| 状态 | 含义 | 为什么单独列 |
|---|---|---|
| `grounded` | 答对 + 上下文里有依据 | 真答对 |
| `ungrounded` | 答对 + **上下文里无依据** | **幻觉式引用，最危险** |
| `missed` | 答错/拒答 | |
| `--` | 配置或链路错误 | |

### 10.3 结果（3 例 × 2 轮 × 2 档 = 12 次真实对话）

| 问题 | inject_k=3 | inject_k=5 |
|---|---|---|
| 技术要求书验收交付要求交付哪些文档 | **有依据 0 / ⚠无依据 2** | 有依据 2 |
| 技术要求书要求的全年可用性是多少 | 有依据 2 | 有依据 2 |
| 自主可控要求对组件部署有什么限制 | 有依据 2 | 有依据 2 |

```
inject_k=3  共 6 例：有依据答对 4 / ⚠无依据答对 2 / 答错 0
inject_k=5  共 6 例：有依据答对 6 / ⚠无依据答对 0 / 答错 0
```

### 10.4 关键发现：`inject_k=3` 是**无依据答对**，比"答错"更危险

`inject_k=3` 时，模型完整列出了 6 种交付文档（含 `源代码使用说明`），还标注了 `[1] [3]`。
但**那两条引用的实际内容里根本没有这份清单** —— 答案来自模型自己的推断，
引用编号指向的内容与答案不符。用户点进去核对会发现文不对题，且**无法分辨这是真的检索结果还是编的**。

而 `inject_k=5` 时 `[1]` 是 380 字的完整片段（合并了 §45+§47+§49），**含原文的完整文档清单**，有据可查。

根因（chunk 级实证）：

```
inject_k=3  [1] len=153  ← 只合并了 §45+§47，答案在 §49（没进来）
inject_k=5  [1] len=380  ← 合并了 §45+§47+§49，答案在
```

> 教训：**"答对了"不等于"检索有效"**。若只看回答表面，`inject_k=3` 的表现是"完全正常"，
> 甚至比 `inject_k=5` 更快（20s vs 97s）。这正是脚本级指标测不出、只有对话级四态判定能抓到的东西。

### 10.5 本轮顺带修掉的两个真 bug（都是对话级验证才暴露的）

验证过程中该问题连续两次返回 **500**，顺着服务日志挖出两个**既有缺陷**：

#### Bug A：思考模式多轮 400（阻塞级）

```
LLM API 400: The `reasoning_content` in the thinking mode must be passed back to the API.
```

最小复现钉死的**精确**触发条件：

| assistant 消息形态 | 结果 |
|---|---|
| 带 `tool_calls`，**缺** `reasoning_content` 字段 | **400** |
| 带 `tool_calls`，`reasoning_content=""` | OK |
| 带 `tool_calls`，`reasoning_content="有内容"` | OK |
| 不带 `tool_calls` | OK（不需要） |

⇒ 缺字段报错、空串合法。修法：在**唯一出站口**（`payload` 构造前）给 deepseek 系的
`assistant && tool_calls && 缺字段` 消息补空串。
修在 provider 层而不是逐个调用点，是因为会拼 assistant 消息的调用点有多处
（`execute.py` 续跑轮/harness 闸、`stream.py` 同构两处、workflows），逐个修**会漏**。
门禁：`tools/verify/verify_reasoning_passthrough.py`（12 项）。

#### Bug B：DSML 行内工具调用 —— 参数全丢 + 标记漏进正文

模型输出（会话 9911 原文）：

```
<｜｜DSML｜｜ calls> <｜｜DSML｜｜ invoke name="file_list"> <｜｜DSML｜｜ parameter
name="path" string="true">C:/.../mbse_system</｜｜DSML｜｜ parameter> ...
```

旧实现两个后果：

1. **参数退化成 `{}`** ⇒ 工具用空参数调用 ⇒ 必然查不到东西，且看不出是参数丢了
2. **标记漏进正文** ⇒ 用户直接看到这串乱码（全库 6 条含 DSML，2 条是这种残留）

根因（这次终于查清了，不是玄学）：旧正则写的是
`<｜｜DSML｜｜ parameter>`，而**实际结束标签带斜杠**：`</｜｜DSML｜｜ parameter>`。
**漏了 `/`，所以永远匹配不到**。

修法：参数值取到"下一个 DSML 标记之前"（lookahead），不依赖结束标签的具体词；

## 十一、扩样本后的定论（17 条用例 / 34 次真实对话）

### 11.1 修正后的结果

| inject_k | 有依据答对 | ⚠无依据答对 | 答错 |

| 3 | **14 / 17** | 3 | 0 |

### 11.2 5 不是万能药：剩下 2 条失败在召回层

### 11.3 0 条"答错"才是最该警惕的

17 条 × 2 档，**没有一条是"答错/拒答"**。模型在依据不完整时**从不承认"我没找到"**，
而是给一个结构完整、措辞专业、还带引用编号的答案。
⇒ `ungrounded`（答对但无依据）是本系统的主要风险形态，**不是"答不出来"，而是"答得很像"**。

### 11.4 我自己犯的两个测量错误（都差一步导出错误结论）

#### 错误 1：上下文口径 —— 回查原文反而丢内容

第一版判"依据在不在上下文"时，用 `(document_id, chunk_index)` 回查 `document_chunks` 取全文。
但检索的**近邻合并**会把多个相邻 chunk 拼成一条，`chunk_index` 只保留**第一个**：

```
conv=9954 [1]:  citations.content = 380 字（§45+§47+§49 合并）
                回查 (847, 48)     = 52 字  ← 合并进去的段落全丢了
```

⇒ 回查结果比 citations 里还短 ⇒ 锚点丢失 ⇒ **假 ungrounded**。
34 条里 **21 条**命中"合并导致回查丢内容"。
修正：取 `citations.content ∪ 回查全文` 的并集。

#### 错误 2：一个锚点同时承担两个互斥的职责

同一个字符串既判"答案对不对"，又判"依据在不在"，而这两件事对文本形态的要求**正好相反**：

| 职责 | 要求 | 原因 |
|---|---|---|
| 判答案对不对 | **宽松**（同义词/多候选） | 模型一定会改写措辞 |
| 判依据在不在 | **严格**（原文短语） | 要确认这条证据真的进来了 |

后果：**4/17 条被误判"失败"，而回答其实全对**：

- `整车需求VR为输出` → 模型答"以**整车黑盒需求（VR）**为输出"（措辞改写）
- `子系统需求SSR为输入` → 模型答"输入是子系统需求（SSR）"
- `制动功率` → 库里是"正**制动功率**区"（BSFC 适用条件），**与问的指标无关**，锚点选偏了

修正：拆成 `ctx_anchor`（严格，判依据）+ `answer_keys`（宽松，判答案）。

#### 这两个错误叠加的后果有多严重

如果不修正，结论会变成「两档 12/17 完全一致 ⇒ `inject_k` 无影响」，
我差一步就**去纠正一个原本正确的结论**。
最终判定：`inject_k=3` 的缺陷是真实的，只是它的**影响面比第一版以为的小**（1/17 而非"普遍问题"）。

#### 为什么用库里的旧回答重算，而不是重跑 LLM

若重跑，就有两个变量同时变化（判据修正 + 模型随机性），**无法归因**。
用同一批回答只改判定逻辑 ⇒ 变量唯一。这也让本轮省下 10 分钟。
复算脚本：`tools/eval/recalc_inject_k_chat.py`。

## 十二、召回失败的根因与解法（本轮只做诊断，未改产品代码）

### 12.1 先分清「没召回」和「排序靠后」

这两类修法完全不同，混在一起会改错地方：

| 类型 | 该修什么 |

`tools/diag/diag_recall_miss.py` 对每条 query 输出金标在 **BM25 单路 / 宽融合池 / 最终返回** 三处的名次。

**结论：没有一条是"未召回"。** 17 条金标在 BM25 里全部能被召回（命中数 219~478 条不等），
问题全在"排在第几"。

### 12.2 金标名次分布（`tools/diag/diag_gold_rank.py`）

|---|---|---|---|---|

### 12.4 `per_doc_max` 配额：救一条、坏一条，净收益 0

`混动` 那条：金标 RRF 名次 **4**，但前 5 名**全是同一文档**（814），

这是「多样性约束 vs 单主题查询」的固有冲突：配额防一份文档灌满上下文（多文档场景正确），

交叉测试 `pd ∈ {2,3,0}` × 重排开关（`tools/diag/diag_perdocmax.py`）+ 全量验证：

| per_doc_max | 覆盖 | 变化 |
|---|---|---|
| 2（现状） | 14/17 | — |
| 3 | 14/17 | 0 |
| 0（不限） | 14/17 | **救回「混动」但弄坏「工具架构」，净 0** |

⇒ **配额不要动**。它是在保护另一条（`工具的系统架构应包含哪些接口`）。

> 方法论：单点测「混动」时会得出"`pd=0` 能救它"的结论，**全量一跑才发现净收益为 0**。
> 任何参数改动都必须看**全量净变化**（救回数 − 弄坏数），不能凭"救回了某条"下结论。

avg 高于阈值 ⇒ 不拒 ⇒ 仍能救回）。

### 14.5 P1：hit@5 归因 → 发现 `rrf_k` 是主因

修完拒答后 hit@5 仍 0.7407。逐条查失败样本，全部落在 `ISO 29148` / 技术要求书，
且这些命中 `bm25_score=20+ / vec_score=0.000`（纯 BM25 命中）。

**根因是 RRF 的经典缺陷被真向量放大**：

```
rrf_k = 60 时
  BM25 第 1 名（单路）RRF = 1/61 = 0.01639
  向量第 1 名（单路）RRF = 1/61 = 0.01639   ← 完全相同！
  第 1 名 vs 第 25 名 只差 1.39 倍 ⇒ 名次信息被抹平
```

⇒ **BM25 绝对第一名的强命中，与向量侧任意一条打得平手**，被大量向量条目淹没出前 20。

扫描（27 条可答 query，进程内改不落盘）：

| rrf_k | hit@5 | MRR |
|---|---|---|
| 60（原） | 0.7407 | 0.9500 |
| 20 | 0.8148 | 0.9470 |
| **10** | **0.8519** | **0.9783** |
| 8 | 0.8519 | 1.0000 |
| 5 | 0.8889 | 0.9028（第 1 名不稳） |

取 **10**：hit@5 与 k∈{8,12,15} 并列最高，MRR 接近满分，且不在极值上（留余量）。

> 行业常用 60 的前提是"两路质量相当、候选池都很大"。本工程 BM25 强命中绝对分很高（20+），
> 而向量分区间很窄（0.54~0.61）⇒ **两路质量并不相当**，照搬 60 是错的。
> ⚠️ 降级态下不宜过低：那时 vec_score 不可信，压低 k 会让噪声向量挤占排名 ⇒ 若 embedding 再次不可用，回调 30 更稳。

   ⇒ 探测恒失败 ⇒ 误判"不可用"。

## 十五、评测判据升级（文档级 → 块级/注入级），2026-11-02

### 15.1 旧判据的两个结构性缺陷（不是"不够准"，是"测错对象"）

```python
# tools/verify/retrieval_baseline.py

```

| 缺陷 | 后果 | 实测证据 |
|---|---|---|
| ① 文档级粒度 | **块级排序改动完全测不出** | `rrf_k` 60→10 时该指标只从 0.7407 动到 0.8519，而实际变化是"BM25 头号命中从第 20 名外回到第 1 名" |

### 15.2 三层指标

| 层 | 指标 | 含义 |
|---|---|---|
| **L2 块级** | hit@5 / hit@10 / MRR@10 / nDCG@10 | 承载答案的块有没有排进前 k、排第几 |
| **L3 注入级** | `inject_cov` | 走完整消费链（低置信过滤→去重→配额→取 inject_k）后，答案块是否真的进了 prompt |

L3 是新增的关键一层：`retrieve()` 返回 20 条 ≠ 用户看到 5 条，中间还有三道消耗。

### 15.3 金标设计：用 marker 运行时解析，不写死索引

```json
{"id": "iso-verification", "query": "ISO 29148 里 requirements verification 的定义是什么",
 "marker": "requirements verification confirmation by examination", "doc": "ISO 29148"}
```

- **不写死 `(document_id, chunk_index)`**：重新分块/重建索引后旧索引会**静默失效**（全不命中或全命中，且不报错）
- marker 解析到 **0 块 → exit 1**；解析到 **>4 块 → exit 1**（太泛，"命中"没有判据）—— **不允许静默跳过**
- 匹配前统一 `re.sub(r"\s+", " ")`：PDF 抽取的换行会把跨行短语切断
  （`requirements verification confirmation\nby examination` 裸匹配为 0 条，归一化后 1 条）

### 15.4 判据自身的三个错（本轮全部是"我错、产品对"）

| # | 错误 | 症状 | 修法 |

| 1 | **M2 变异断言恒假** | 断言"top5 倒序后金标名次为 None"，但第 1 位倒序后落在**第 5 位**，仍在 top5 内 ⇒ 变异永远不触发，门禁"全绿"其实什么都没测 | 改为"名次必须从 1 变为非 1" |
| 2 | **按块索引判命中** | `req-srcdoc` 金标 `847:49`，检索 top1 是 `847:48`（52 字，内容以"包含"截断）——但**近邻合并**会把 §45+§47+§49 拼成一条、只保留第一个 index ⇒ 答案文本已在结果里，却判"未命中" | 改为**按内容判命中**（`marker in content`），对重分块天然免疫 |

## 十六、P3-a：元数据块不参与排序

### 16.1 证据

块级评测里出现"占着名次、却不可能回答任何问题"的块：

```
Q「SysML v2 的 binding 和 succession 是什么」
  rank2 = [818:0] "> 所属方法论：… > 适用范围：… > 更新日期：2026-04-18---"
  rank3 = [817:0] 另一份文档的文档头
Q「验收交付要求交付哪些文档」
  rank4 = [847:1] "编制单位 网络系统总体设计室 会 签 …"（签批表）
```

它们靠**文档标题里的关键词**空降（"运行视角""视图""技术要求书"），即此前记的"标题词稀释"。

### 16.2 判定（`agent/metadata_blocks.py`）：宁可漏判，不可误杀

误杀一个能回答问题的块，比漏掉一个元数据块严重得多 ⇒ 规则全部是强特征组合：

| 规则 | 条件 |
|---|---|
| 单条强特征 | `中国星网受控信息` / `Important Notice …copyrighted` / `Copyright protected document` / `> 所属方法论：` |
| 结构词密度 | ≥3 个（`文档编号/版本号/编制日期/文件编号/工程阶段/编制单位/会 签/编 写/校 对`） |
| 目录 | 连续 4+ 个点 ≥2 处 **且点占字符 ≥20%** |
| 引用块式文档头 | 以 `>` 开头 + ≤120 字 + 含"更新日期/整理日期" |

保护：`filter_metadata(min_keep=3)` —— 过滤后不足 3 条就**放弃过滤**（绝不清空结果）。

### 16.3 第一版误杀了真内容（两个必须记住的坑）

| 误杀 | 原因 | 修正 |
|---|---|---|

## 十七、顺带修掉：正文出现越界引用编号（模型编编号）

### 17.1 现象（端到端验证抓到）

```
Q「ISO 29148 对需求标识符的唯一性有什么规定」
  注入【来源1-5】  citations=5
  正文编号 = [1,2,3,4,5,6,7,8]     ← [6][7][8] 在 citations 里不存在
```

用户点后三个编号**没有任何反应** —— 与此前修的"界面 8 条、prompt 3 条"是同一类"死编号"，
但这次不是代码错位，而是**模型自行续编号**。

### 17.2 根因与修法

根因：prompt 里只有"编号与 citations 对齐"的**隐含约定**，没有给出**范围**。
长回答里模型会自然地继续编号。

修法（零副作用，不改写模型原文）：在【来源n】块后追加一行显式约束，上限取自**实际注入条数**：

```
（引用规则：正文中的 [n] 只能取 1–5，分别对应上面的【来源n】；
 不得写超出该范围的编号，也不要为未列出的材料编号。
 若要用的证据不在这 5 条里，请直说「现有材料未覆盖」。）
```

**为什么不用后处理删标记**：删标记会改动模型原文，且代码块里的 `[n]`（数组下标）难与引用区分，
有把代码改坏的风险 —— 先用零副作用的那种。

### 17.3 验证

同一问题复测：`citations=5 | 正文编号=[1,4,5] | 越界=无`。

门禁 `verify_citation_alignment` 新增 E1/E2（范围文案存在 + 上限取自 `min(len(_sel), _inject_k)` 而非写死）。

### 19.3 根因：陈旧磁盘缓存（两条缺陷叠加）


| # | 缺陷 | 说明 |
|---|---|---|
| ① | `_load_binary()` 成功即用，**不校验行集** | 只看 shape；注释写"精确一致性由 invalidate() 保证" |
| ② | `invalidate()` **只清内存、不清磁盘** | 清完内存下次仍从同一 `.npy` 重载 ⇒ **永远用旧向量**；`_rows_fingerprint()` 定义了从未被调用 |

### 19.4 影响面（必须如实认账）

- **上一轮"重算 720 条向量"从未生效过**（报告成功、审计通过，但检索用的是 10-28 的旧矩阵）
- 因此"hit@5 下降与重算无关""rrf_k 才是主因"等**基于该数据的归因需要重新审视**
  （rrf_k 的扫描结论是当时的真实测量，成立；但"重算无收益"的前提是错的）
- 我当时还把这个坑记进了记忆（"重算工具没刷缓存"同类）——**自己又踩了一遍**

**为什么难发现**：缓存加载成功、检索不报错、分数"看起来只是低"。

### 19.5 修复（`vector_index.py`）

| # | 修法 | 为什么 |
|---|---|---|
| ① | `_ensure_group` 加**行数校验**：缓存行数 ≠ 数据库同版本行数 ⇒ 丢弃缓存走 JSON 重建 | 挡住本次事故（新增/删除/版本迁移都会变行数）；代价是进程首次加载多一次 `COUNT(*)` |

| ③ | `tools/reembed_degraded.py` 写完后调 `bump_epoch()` + **自检缓存行数与数据库一致** | 写入路径的责任；自检让"重算是假的"不可能再静默通过 |
