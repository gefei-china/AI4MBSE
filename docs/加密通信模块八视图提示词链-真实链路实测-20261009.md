## 1. 环境层：3 个先于建模的问题

### 1.1 默认 provider 缺失（P0）

会话初期只读查询显示 `id=104 qwen3.8-max` 为 `is_default=1`；
几分钟后同一 SQL 返回 **`id=107 ds-v4-flash-neibu`**；再之后 107 **整行消失**，
期间又冒出一个 `id=109`。⇒ **有另一个会话正在改`llm_providers` 表**。

实测 `get_default_provider()` 返回 **107**，而 107 的配置是：

```
max_tokens = 128000, context_window = 128000
```

`context_window_guard=clamp` 会把输出上限压到 cw，输入余量只剩 **1024** ⇒ 任何稍长的请求必然
`400 This model's maximum context length is 135168 tokens. However, you requested 128000 output tokens`。

**受影响 provider（实测）**：

| id | 名称 | 状态 |
|---|---|---|
| — | （无 `is_default=1` 行） | 默认解析返回 None → `chat()` 抛「未配置 API Key」 |
| 1 | DeepSeek-V3 | 402 余额不足 + `max_tokens == context_window` |
| 71 | deepseek-v4-flash | 402 + `max_tokens == context_window` |
| 72 | deepseek-v4-pro | 402 余额不足 |
| 103 | qwen3.8-omni-flash | 403 Free quota exhausted |
| **104** | **qwen3.8-max** | **可用** |
| 109 | ds-v4-flash-neibu | 可用但同样 `max_tokens == context_window` |

> **可复用修法**：`<repo>\tmp\crypto\chain.py::resolve_provider()`
> —— 预筛 `max_tokens < context_window`，再**逐个真实探针**（`finish=stop` 且非 Mock），
> 探不过就换下一个。**不要靠 `is_default=1` 推断可用性。**

### 1.2 `max_tokens == context_window` 的 provider 结构性不可用

`clamp` 守卫把输出上限压到 cw 后，输入余量 = 1024 token。
**只要输入超过 1024 token 就必然 400**。这类 provider 不是"偶尔失败"，是**结构性不可用**。

### 1.3 embedding 额度耗尽（不影响本链路）

`Free quota exhausted` → 检索降级 bigram。**建模产出未受影响**（7 个视图照样产出），
但检索质量下降，会影响模型能否查到规范细节（见 §3.2）。

## 5. P0 缺陷：超时 545 秒 + 静默回落 Mock

### 5.1 现象（v4 活动图，993 秒零产出）

`llm_usage_stats` 里 conv 9244 的最后一条：

```
id=9661  provider=qwen3.8-omni-flash  latency_ms=545171
         used_mock=1  prompt_tokens=0  completion_tokens=0  finish_reason=''
```

⇒ **用户等了 9 分钟，系统交出一段编造内容。**

### 5.2 根因（算得出来，不是猜的）

| 参数 | 值 | 来源 |
|---|---|---|
| `httpx.post(timeout=180)` | 180s | `llm/providers/openai_compat.py:254` |
| `llm.retry_times` | 2 | 配置 |
| 退避 | 500ms × 2ⁿ ≈ 1.5s | `_chat_with_retry` |
| **合计最坏** | **≈ 541.5s** | **与实测 545s 吻合** |

`ReadTimeout` 属 `_retryable`（非 4xx 参数错）⇒ 重试耗尽后进 `except` 分支。

### 5.3 ⚠️ `used_mock=1` 这个字段会误导排查（必须澄清，且我首版判断错了）

首版我据 `used_mock=1` 写下"系统交出编造内容"，**这是错的**。实测复核：

`llm/__init__.py` 的 `except` 分支实际做三件事：

```python
self.stats["last_used_mock"] = True
self._record_usage(provider, {"usage": {}}, True, ...)   # ← 第三个位置参数就是 used_mock
raise LLMUnavailableError(f"LLM 调用失败，本次未生成任何内容。…", reason="call_failed", …)
```

⇒ **它 `raise`，不返回 Mock 文本。**
`llm/` 全仓只有两处 `self.mock`：`:245` 注册、`:398` 的 `force_mock` 分支（实测 `force_mock=False`）
⇒ **不存在第二条 Mock 回落路径**。

**实测证据**：conv 9244（v4）**落库消息数 = 0**，内容为空 —— 用户什么都没拿到。

**但字段命名是真实的坑**：`used_mock=1` 在这一行里的语义是
**"这是一次失败的调用"**，而不是"这次回答来自 Mock"。
把两件事塞进同一列 ⇒ 查"哪些回答是 Mock 做的"会把**所有失败调用**都算进来。

**这正是我自己踩的坑**：我先信了这个字段、写下"交出编造内容"，
复核 `raise` + 落库 0 行才纠正过来。
⇒ **纪律：看到 `used_mock=1` 不能直接推"内容是编造的"，
必须回源看是 `raise` 还是 `return`，并看 `messages` 表有没有落库。**

### 5.4 建议

1. `timeout` 做成**可配置**，并给**总预算**（不是单次 180s）—— 单次超时应远小于 180s
2. `llm_usage_stats` 把 `used_mock` 拆成两个字段：
   `used_mock`（真Mock 内容）与 `call_failed`（失败调用），并加 `failure_kind`
   （timeout / 402 / 403 / 4xx）⇒ 让"545 秒零产出"**可按列聚合**
3. 前端对"零产出"应有明确提示，不能让用户对着空白页以为还在跑

### 6.2 但不是"全盘失败"—— 两处确实打通了

### 6.3 根因（不是模型不听话，是命名体系撞车）

- v1 用 `requirement <'RQ-01'> '端到端安全通信总需求'` —— **需求名**

三者**分属不同的命名空间**，`part def X` 与 `requirement def X` 是不同类型，
**同名也不会互相解析**。⇒ "上游产物直接粘给下游"这个提示词链设计，
**在 SysML v2 里需要一个显式的名字映射表**，否则结构上不可能复用。

> ⚠️ 另有一个**内容层判据与产出形态的错配**：`view_content_rules` 要求
> `use case def` / `part def`，而模型产出的是**纯实例**
> （`use case 'X' : UseCase {}`、`part 'X' : Part {}`）——
> **全篇 0 个 `def` 关键字**（v3 有 31 个 `part` + 65 个 `port`，无一个 `def`）。
> 两者都能过 `checker.jar`（语法 0 错），但**判据按 `def` 判、内容按实例写** ⇒ 判据本身要修订。

## 7. P1：`view_expansion` Agent 的 system_prompt 与提示词链**前提冲突**

`agents` 表 id=637 的 `system_prompt`：

> **只允许引用骨架中已存在的元素，禁止凭空引入部件或端口。**

但提示词链的设计是**渐进式生成**（视图 1 只有场景描述，哪有什么骨架）。

⇒ 实测确实印证：v6 的 `sysml_stdlib_meta` 有一轮就是去查
「未找到包 `StandardViewDefinitions`」—— 模型在**试图补一个不存在的骨架**。
**这条 prompt 与提示词链的适用前提不一致**，是"查标准库"这种无效预算消耗的诱因之一。

## 8. 一处方法论错误（自查，如实记录）

首轮我用了 `--fresh`（不复用上游），结果**8 个视图的上游注入全是 0 字符**
—— 也就是**提示词链的"链"根本没被测到**，测的是 8 个独立视图。
