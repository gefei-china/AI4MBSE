# 知识库检索链路诊断与优化方案

> 版本：2026-11-01 ｜ 核查方式：代码实读 + SQLite 只读实测 + 真实检索实跑（非文档自述）
> 仓库：`mbse_system` ｜ 数据库：`mbse.db`（7,179 chunks / 189 实体 / 249 关系 / 14 文档）

---

## 0. 一句话结论

**检索链路"代码上通、数据上不通"：向量侧因 embedding 服务 502 全程降级到 bigram，图谱侧因桥接字段全空成为孤岛，两者叠加后被"低置信抑制"整段清零 —— 实测 6 条典型查询仅 1 条有命中，且唯一命中的首条还是域外文档。已用 A/B 实验证实：仅把抑制改为阈值过滤，命中率即从 1/5 升到 5/5。**

| 指标 | 实测值 | 判定 |
|---|---|---|
| 路由分布 | vector 1587 (82.3%) / graph 264 (13.7%) / mixed 78 (4.0%) | 号称 graph-first，实际 vector-first |
| 路由理由 | `graph_no_hit` **1431 次（74.2%）** | 图谱基本没被用上 |
| 真实查询命中率 | 6 条典型 query → **仅 1 条有结果** | 不可用 |
| **A/B 实验（关抑制）** | **1/5 → 5/5，注入 chunk 20 → 100** | **确认抑制是直接凶手** |
| chunk↔实体桥填充率 | **0 / 7,179 = 0.00%** | 两个引擎无联动 |
| 实体来源可追溯率 | `entities.source_doc` 非空 **5 / 189 = 2.6%** | 无法回溯出处 |
| 检索延迟 | graph 616ms / vector 5,662ms / mixed 6,200ms | 慢 4~10 倍 |
| `graph_retrieve` 工具 | 609 次调用，**均 3,851ms，峰值 33.9s** | 高频且慢 |

**三个可直接修的缺陷（P0 级，成本极低）：**
1. `graph_db_nlquery` / `graph_db_stats` **成功率 0%** —— 8/8、4/4 全失败，说明工具本身是坏的，不是偶然。
2. `web_search` 调用 0 次，但对外宣称具备联网能力。
3. `knowledge_search` 在工具表里查不到，但代码/文档引用它 —— **命名不一致**，Agent 选工具时会选到不存在的东西。

### 1.2 技能（40 个技能中，检索专项 = **0 个**）

40 个技能覆盖需求分析、SysML 八视图生成、校验修复、覆盖性分析、报告生成、智源平台管理……
**没有任何一个技能是"检索策略/知识问答"专项**。

实际后果：检索完全依赖模型"自发调用工具"，没有方法论约束：
- 不知道「什么问题该走图谱、什么该走向量」
- 不知道「检索不到时该怎么改写 query」
- 不知道「多跳问题需要沿关系遍历几次」

> 对比：业界成熟产品（如 RAGFlow/Contextual AI）都有 retrieval policy 层；本系统把检索策略**隐式交给了 LLM 的随机性**。

| 场景 | query | route | 图实体 | chunk | 耗时 | 结论 |
|---|---|---|---|---|---|---|
| 图谱强相关 | 卫星通信载荷的需求有哪些 | vector | 0 | **0** | 20,243ms | 零命中 + 超慢 |
| 需求追溯 | 需求与架构元素的追溯关系 | vector | 0 | 20 | 425ms | 命中但**首条是「广汽方法论」**（域外） |

### 2.3 逐层定位：零命中**不是**召不回，是被主动丢弃

对「卫星通信载荷的需求有哪些」逐层打印：

```
entity_link 命中: 0
hybrid: hits=20  bm25=20  vec=220
   0.043  v=0.188  b=14.72  conf=低 | 847_Print_面向网络总体的AI赋能MBS... | 4.2.2 系统需求分析
   0.043  v=0.188  b=14.72  conf=低 | Print_面向网络总体的AI赋能MBSE系统设... | 4.2.2 系统需求分析
   0.040  v=0.177  b=16.46  conf=低 | 知识库_运行视角_视图规范元素要求(1).md | ### 利益相关方需求视图
suppressed? True        ← 全部被丢弃
```

**这是本轮最重要的发现：**

```
召回其实是对的（第 1、2 条正是技术要求书的「4.2.2 系统需求分析」，完全切题）
     ↓
但 vec_score 只有 0.188（因为 bigram 降级，不是真语义相似度）
     ↓
conf 判「低」（低于 confidence_mid=0.45）
     ↓
suppress_low_confidence=True ⇒ chunk_hits = []
     ↓
用户与 AI 都拿到 0 条 —— 界面正常、无报错、静默清零
```

> **这是"静默失效"的教科书案例**：`suppress_low_confidence` 的设计意图是对的
> （防止问"今天天气"也塞 20 条"相关知识"导致幻觉），
> 但它的判据建立在"embedding 可用"的隐含前提上。
> 一旦 embedding 故障 → 所有分数等比例塌陷 → 判据必然全低 → **把整条检索链路打成全空**。
> 症状与"知识库没数据"完全一样，极难归因。

- 前 3 条**全来自同一文档**（`广汽方法论-260813.docx`）—— 该文档属**广汽车辆安全**域，与"卫星网络总体"无关

- 说明：**BM25 在兜底，向量侧几乎没贡献**；同时**域约束没生效**（跨域污染）

## 4. 向量检索与图谱检索：设计关系 vs 实际关系

### 4.1 设计上：主备降级（graph-first → vector-fallback）

`agent/rag.py::GraphRAG.retrieve` 的真实控制流：

```
Glossary 归一化（v2→SysML_V2）
   ↓
实体链接（整句 LIKE + 3~4 字 token 补充）
   ↓
1 跳子图（relations where source_id or target_id in 命中实体）
   ↓
多因子置信度 = 0.5×实体覆盖度 + 0.3×关系连接性 + 0.2×类型匹配度
   ↓
conf ≥ 0.7 → route=graph，**跳过向量**（省钱省时）
conf < 0.7 → 才跑 hybrid_search（BM25 + 向量 + HyDE → RRF 融合 → LLM 重排）
   ↓
QueryRouter 落 route ∈ {graph, mixed, vector} + query_routing_stats
```

设计意图：**图谱优先，因为精确、可解释、便宜；向量兜底，因为能覆盖语义长尾。**

### 4.2 实际：两个互不知情的孤岛

| 维度 | 设计期望 | 实测 |
|---|---|---|
| 图谱能给向量提供什么 | 实体→相关 chunk（把图节点落到原文） | `linked_entity_ids` **0% 填充** ⇒ 给不了 |
| 向量能给图谱提供什么 | chunk→实体（把语义命中升维成图节点） | 无反向抽取链路 ⇒ 给不了 |
| 二者共享的实体名空间 | 同一套术语 | 图谱走 `entities.name`，文档走 chunk 文本 ⇒ **两套词表** |
| 融合方式 | RRF 融合 | 只在 `mixed`(4%) 时才发生，且是**并列拼装**不是融合 |

**所以准确表述是：**
> 不是"向量检索 + 图谱检索配合"，而是"**图检索失败后改走向量检索**"的**主备切换**。
> 二者从未在同一查询里真正互补 —— `mixed` 仅占 4%，且本质上仍是"图结果 + 向量结果"各给一半。

### 4.3 单阈值路由的结构性缺陷

`route_threshold = 0.7` 一个数字同时管：
- 图谱命不命中（`graph_confidence`）
- 要不要跑向量（省不省钱）
- 要不要混检

但**问题类型不同，正确的策略本就不同**：

| 问题类型 | 正确策略 | 当前行为 |
|---|---|---|
| 「X 的需求有哪些」 | 图优先（结构化枚举） | ✅ 但图里没这实体 → 掉向量 |
| 「可靠性指标是多少」 | 纯向量（找具体段落） | 先花 300ms 做无效实体链接 |
| 「A 和 B 什么关系」 | **多跳图遍历** | 只做 1 跳，且 `relation_relevance_gate` 还会把关系筛掉 |
| 「整体架构是怎样的」 | **社区摘要（全局归纳）** | 无此能力，只能靠 top-3 chunk 拼 |
| 「今天天气」 | 直接拒答 | ✅ 但靠"低置信清零"这种副作用实现 |

### 5.2 关键认知（避免踩"图 RAG 一定更好"的坑）

公开 benchmark 数据显示**图 RAG 并非普遍优于稠密检索**：

| 方法 | HotpotQA F1 | MuSiQue F1 | 说明 |
|---|---|---|---|
| NV-Embed-v2（纯稠密） | 61.5 | — | 纯向量在简单 QA 上很强 |
| RAPTOR | 52.3 | 28.1 | 分层抽象对多步有增益 |

**恰好是"两边优点都没拿到"的最差组合**。

## 6. 优化方案

### 设计原则（先立规矩，避免又做成"机制在数据死"）

1. **禁止静默清零**：任何过滤都必须留痕（丢了几条、为什么丢），并且**降级≠丢弃**。
2. **每一层都要能被单独测量**：没有 recall@k 就没法判断改动是否有效。
3. **桥要有填充率指标**：`linked_entity_ids` 这类字段必须有"非空率"门禁，0% 必须报红。
4. **大胆设想、谨慎落地**：先做能用现有数据验证的，架构级改造按 §7 小步试跑。

---

### P0（1~2 天，止血，不改架构）

#### P0-1 「低置信抑制」改为「分数阈值过滤」，绝不整段清零

**现状**：`suppress_low_confidence=True` + embedding 降级 ⇒ 含金标的命中被全丢。

**已用 A/B 实验验证（`tools/verify/ab_suppress_low_conf.py`，4/4 通过）**：

| 场景 | 抑制=开 chunk | 抑制=关 chunk | 抑制关时 score_max |
|---|---|---|---|
| 图谱强相关 | **0** | 20 | 0.0430 |
| 需求追溯 | 20 | 20 | 0.0350 |
| 纯文档事实 | **0** | 20 | 0.0320 |
| 抽象/同义 | **0** | 20 | 0.0370 |
| 安全要求 | **0** | 20 | 0.0640 |
| **域外噪声** | 0 | 3 | **0.0160** |

- 切题 query 命中：**1/5 → 5/5**（救回 4 条）
- 注入侧 chunk 总量：**20 → 100**
- **分数可分**：切题 `score_max` 最小值 **0.032** > 域外 `score_max` **0.016**（差 2 倍）

⇒ **结论比原设想更精确：不需要简单关掉开关，而应该改成"按 `score_max` 阈值过滤"。**

**改法**（三层，从粗到细）：
```python
# ① 一刀切 → 阈值化（阈值 0.02，取实测可分间隙 0.016~0.032 的中位偏下）
if all_low(score <= confidence_mid) :
    keep = [h for h in hits if h.score >= rag.low_conf_floor]   # 0.02
    dropped = len(hits) - len(keep)
# ② 保留的条目必须可辨识
h["degraded"] = True
h["degraded_reason"] = "embedding_unavailable" / "low_relevance"
# ③ 注入时显式标注 + 观测留痕
#    前缀「（检索降级：embedding 不可用，以下为字面匹配，置信较低）」
trace.detail = {"suppressed_count": dropped, "kept_count": len(keep)}
```

**⚠️ 必须同时做的两件事（否则会变成另一种失效）**：
1. **样本量只有 6 条，阈值 0.02 不可直接上生产**。必须先扩 qrels 到 200 条（P2-5），
   在 200 条上重算切题/域外的分数分布，取 P5 分位作阈值。当前 6 条只是「证明可分」，不是「定标」。
2. **阈值过滤只能挡住"明显无关"，挡不住"沾边但答非所问"**。域外样本
   `bm25_max=0.00` 却能进 3 条（纯字面巧合）⇒ 仍需 P1-4 的**拒答分类器**做前置拦截。

**为什么这是第一优先**：它是当前"0 命中"的**直接原因**，且**改配置即可验证**，
是全部方案里"投入产出比最高、风险最低"的一步。

#### P0-2 embedding 不可用时的降级策略升级
**现状**：502 → bigram（字面），`vec_score` 0.074~0.25，语义能力归零，且**不告知用户**。
**改法**：
1. 降级分三档并显式标注：`bge-m3(真)` → `bigram-tf(字面)` → `bm25-only`；
2. 降级时**自动放大 BM25 权重**（bigram 本就接近字面匹配，与 BM25 互补性差）；
3. 在检索结果里带 `embed_mode` 字段，前端/AI 上下文都能看到"本次是字面检索"；
4. embedding 恢复后**自动补向量**（当前有 720 条是 `bigram-tf` 版本，与 6459 条 `openai-compat` 混存，检索时按版本隔离 ⇒ 这 720 条在真向量检索时**等于不存在**）。
**验收**：`SELECT embed_version, COUNT(*)` 只剩一种；降级时 `_meta.embed_mode='bigram'` 可见。

#### P0-3 修 `inject_k=3` 的浪费
**现状**：召回 20，注入 3 —— 85% 白算。
**改法**：分层注入
```
inject_k = 3 (精确)  → 扩到 5~8，并用 select_diverse 做 per-doc 配额（已有实现）
同时把「被丢弃但高分」的记入 trace，便于事后分析
```
**验收**：`context_audit.retrieval_nominal vs retrieval_selected` 的差值从 17 降到 ≤2。

#### P0-4 修三个坏工具
- `graph_db_nlquery`（8/8 失败）、`graph_db_stats`（4/4 失败）：查异常栈，修或下架。
- `knowledge_search` 命名不一致：要么建这个名字的工具，要么改文档/提示词，**不能让 Agent 选一个不存在的工具**。

### P1（1~2 周，建桥 + 让图真正参与）

#### P1-1 **填上 chunk↔实体桥（最高杠杆，成本最低）**
**现状**：`linked_entity_ids` 0/7179，这是整条链路最致命的空洞。
**做法**（三路互补，按成本递增）：
1. **规则路（当天可做）**：用 `entities.name` 在 chunk 文本里做**最长匹配**（Aho-Corasick），
   189 个实体 × 7179 chunks 一遍即可，零 LLM 成本。
2. **词典路**：复用现有 `glossary` 的 `maps_to` 概念映射。
3. **LLM 路（可选）**：对未命中的 chunk 用 LLM 抽实体（先做 200 条抽样，估成本再全量）。
**为什么这是杠杆最大的**：一旦建桥，
- 图谱命中 → 能直接给到原文段落（可解释性）；
- 向量命中 → 能升维成图节点，再做 1~2 跳扩展（召回提升）。
**验收**：非空率 ≥ 60%（不追求 100%，规则路的天然上限），且随机抽 20 条人工核对准确率 ≥ 80%。

#### P1-2 反向抽取：文档实体进图
**现状**：189 实体几乎全是建模实体，文档知识**完全没进图** ⇒ 74% `graph_no_hit`。
**做法**：
- 每篇文档抽取 10~30 个实体（概念/指标/接口/约束）+ 关系；
- 落 `entities(source_type='doc_extracted', source_doc=..., confidence=...)`；
- **默认进 `pending`（未评审）**，与既有 FR-KG-2 门禁一致，不绕过评审。
**预期**：`graph_no_hit` 从 74% 降到 40% 以下。
**风险控制**：先只跑 2 篇文档，人工看质量再放量（用户明确要求"谨慎尝试"）。

#### P1-3 多跳：1 跳子图 → PPR（HippoRAG 思路）
**现状**：只做 1 跳，且 `relation_relevance_gate` 会把跨实体关系筛掉 ⇒ "A 和 B 什么关系"类问题答不了。
**做法**：
- 用 query 命中实体作种子，跑**带权 Personalized PageRank**（3~5 跳，衰减 0.85）；
- 取 top-k 节点 + 路径作为证据；
- 复用 `impact_engine` 已有的图遍历能力（那里已有 `analyze_graph_v2`、深度参数）。
**验收**：构造 10 条"A↔B 关系"类 query，路径命中率从当前 0 → ≥6/10。

#### P1-4 路由从「单阈值」升级为「按问题类型」
**做法**：先做**查询分类**（规则 + 小样本，不需要大模型）：
| 类型 | 判据 | 策略 |
|---|---|---|
| 枚举型（"有哪些/列出/清单"） | 关键词 | 图优先，并要求实体覆盖度 |
| 事实型（"是多少/哪个/何时"） | 关键词 | **直接向量**，跳过实体链接（省 300ms） |
| 关系型（"关系/影响/依赖/追溯"） | 关键词 | 图 + PPR 多跳 |
| 归纳型（"整体/架构/概述/总结"） | 关键词 | **社区摘要**（见 P2-1） |
| 域外 | 领域分类器 | 直接拒答 |
**验收**：`query_routing_stats` 里 `graph_no_hit` 占比下降，且 `graph` 路由的 `confidence` 中位数上升。

---

### P2（1~2 月，架构级，大胆设想）

#### P2-1 引入「社区摘要层」解决全局归纳问题
当前答不了"整体架构是怎样的"——只能拼 top-3 chunk。
**方案**：对实体图跑 Leiden 社区检测 → 每个社区用 LLM 生成摘要 → 存 `community_summaries`。
归纳型 query 走 map-reduce：社区摘要 → 汇总。
**成本**：189 实体规模下，一次性 LLM 成本可忽略（< 1 元）；增量按社区更新。

#### P2-2 分层抽象（RAPTOR 式）
当前只有 chunk 一个粒度。加入：
```
L0 chunk (7179)
L1 文档摘要 (14)          ← 已有 documents.quality_score，但无摘要
L2 章节摘要 (~200)         ← 按 section 聚合，现有 section 字段可直接用
L3 社区/主题摘要 (10~30)   ← P2-1
```
检索时**按 token 预算做 collapsed tree**：事实型下沉到 L0，归纳型上浮到 L2/L3。
**为什么值得做**：RAPTOR 在多步阅读上报告 +20pp，且本系统的 `section` 字段已经齐备，改造成本低于重做。

#### P2-3 Agentic Retrieval（把检索从函数变成策略）
当前 `graph_retrieve` 是**一次调用、一个结果**。改为：
```
检索规划 → 子问题分解 → 并行多路检索 → 证据充分性判断
   ↑                                              ↓
   └────────── 不充分则改写 query 再检一轮 ────────┘
```
**这与本系统的 Agent 架构天然契合**（已有 17+4 Agent、已有 tool 循环），
缺的只是一个**retrieval policy 技能**（= §1.2 那个空白）。
**关键设计**：必须设**预算上限**（最多 3 轮、总耗时 < 10s），否则会退化成"无限检索"。

#### P2-4 「证据账本」支撑可解释性（对应 FR-MQ-2）
每条结论记：`chunk_id → 实体 → 文档 → 章节 → 关系路径 → 检索轮次`。
前端可点开任意断言看到完整证据链；也支撑"用户修正推理路径后系统调整后续回答"（FR-MQ-2 后半句，当前未实现）。

#### P2-5 评测体系（**没有它，前面全是拍脑袋**）
**现状**：`qrels.jsonl` 25 条，首条自注"算不出 recall 分母"。
**做法**：
1. 扩到 **200+ 条**，覆盖 §4.3 五类问题（每类 ≥40 条）；
2. 指标：`recall@5`、`MRR@10`、`nDCG@10`、**拒答准确率**（域外问题必须不答）；
3. 做成 **CI 闸门**：任一指标跌超 3% 即红（本仓已有 `tools/eval/run_ci_eval.py` 可复用）；
4. 每次改检索参数，**必须附前后对比数字**。
**这是唯一能防止"改完感觉变好了但实际变差"的手段** ——
本任务历史已多次出现"看起来像功能没生效，其实是验证器错"（记录在案 7 次）。

写这份报告时，我有意区分了三种证据强度，请按此判断可信度：

**本轮我自己的两次判据错误（已修，记录以免重犯）**：
1. 第一版断言 `context_text` 增长 —— 但 `retrieve()` **没有**这个字段
   （真实上下文由 `context.py` 用 `chunk_hits` 拼 `【来源n】`）⇒ 假红。

   ⇒ 这条修正直接改变了 P0-1 的实现方式（从"降权+标注"改为"阈值过滤"）。
