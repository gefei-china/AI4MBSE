## 2. 五个核心问题（按收益排序，全部实测）

### P0-1 检索注入无多样性约束 —— 3 槽实际只换到 1.14 条有效信息

**现象**：`context.py:196` 逐条全文注入 `【来源i】{source_doc} §{chunk_index}: {content}`，
`inject_k=3`，但**无任何 per-doc 配额、无近邻 chunk 合并、无 MMR**。
全仓 grep `MMR|diversif|near_dup` **零命中**。

**实测**（真实 `hybrid_search`，6 个典型 query）：

| query | 命中 | top3 文档数 | 槽间最大重叠 | 有效条数(估) |
|---|---|---|---|---|
| 如何定义 SysML v2 的活动图 | 20 | 3 | 0.21 | 2.48 |
| 需求追溯矩阵怎么构建 | 20 | 2 | **0.81** | 1.65 |
| parameter 属性定义方式 | 20 | **1（同文档）** | 0.74 | **1.14** |
| ISO 29148 需求质量准则 | 20 | 2 | 0.47 | 1.75 |
| block definition 端口定义 | 20 | **1（同文档）** | 0.53 | 1.57 |
| 状态机 状态 转换 定义 | 20 | 2 | 0.32 | 2.44 |

**根因（语料侧）**：
- `document_chunks` 共 7,177 块 / 仅 14 个文档，**top2 文档占 64.3%**
  （`OMG SysML V2.pdf` 2,606 块 + `KerML.pdf` 2,011 块）
- **相邻 chunk 字符集 Jaccard 中位数 0.659、p90 0.816**（7,144 对样本实测）
  ⇒ 检索召回 top3 极易落在同一文档的连续 §，语义几乎重复

**后果**：3 个注入槽实际只换来 1.1~2.5 条信息，且挤掉的是"换个文档交叉验证"的机会。

**方案**（在 `context.py` 注入前加一道多样性闸）：
1. **per-doc 配额**：同一 `source_doc` 最多占 `ceil(inject_k/2)` 槽（即 3 槽时 ≤2）
2. **近邻合并**：同 doc 且 `|chunk_index 差| ≤ 2` → 合并为一条，保留 `§a-b` 区间标识
3. 补位策略：多样性过滤后槽位不足，用 RRF 池的第 4/5 名补齐（`top_k=20` 池里还有 17 条落选者）
4. 合并后**保留 300 字/条上限**不变，净效果是同样 token 预算换更高信息密度

**预期收益**：`parameter 属性定义方式` 这类 query 的有效条数 1.14 → 2.0+，**同等 token 下信息密度提升 ~75%**。

### P0-3 JIT 工具预筛在弱相关时全量回退 —— 同族意图载荷差 3.4 倍

**机制**（`pipeline_parts/tools.py:374-427`）：
```
candidates ≥ 2 且有 user_input → SemanticSearch.rank(user_input, idx, threshold=0)
  → chosen = {score ≥ _th} 的工具
  → if not chosen: 全量维持（空回退）      ← 关键
  → core_keep 无条件并入
  → candidates = candidates ∩ chosen
```

**问题**：`_th` 按后端选取（dense=0.53 / bigram=0.12）。当**全部候选都低于阈值**时，
`chosen` 为空 → 走"空回退全量"分支 → **JIT 完全失效**。

**实测**（真实调用 `_build_tools_def`，admin 角色）：

| user_input | 工具数 | payload 字符 | token | 工具名 |
|---|---|---|---|---|
| 帮我分析需求变更的影响范围，并生成追溯矩阵 | **7** | 2,616 | 1,629 | coverage_matrix, gap_summary, sysml_v2_validate, graph_retrieve, impact_analyze, validate, ask_user |
| 查询图谱中某个实体的关联关系 | **5** | 1,969 | 1,229 | sysml_v2_validate, graph_retrieve, impact_analyze, validate, ask_user |
| 帮我把活动图生成出来 | **24** | 7,487 | **4,162** | coverage_matrix, gap_summary, methodology_profile_load, modeling_coverage, requirement_itemize, scene_coverage, sysml_ast_extract, sysml_stdlib_meta, sysml_v2_lint, sysml_v2_project_check, sysml_v2_validate, trace_chain_check, file_list, file_read … |

**"生成活动图"只需 sysml 视图类工具，却拿到 24 个**（含 coverage / requirement / trace 全套）。
根因：该 query 的向量与全部候选相关性都低 → `chosen` 空 → 全量回退。
（探针环境 `httpx` 缺失导致 embedding 降级 bigram、阈值降到 0.12 仍全弱相关，
**生产环境走 dense 后端、阈值 0.53，空回退概率只会更高**。）

**方案**：
1. **空回退改为"取 top-N"而非"全量"**：`if not chosen: chosen = top_sqrt`（保留语义最相关的前 6~8 个）
   —— 弱相关场景下"相关性排序"仍有信息量，**排序 ≠ 阈值**
2. `core_keep` 保底集合**分层**：区分"必须常驻"（graph_retrieve/validate/impact_analyze）
   与"显式契约"（用户手动绑定的 MCP）——后者应**单独标注**而非混为一谈
3. 补 `tool_jit` 归因：记录"本次因空回退全量注入"的事件计数，让回退**可见**

**预期收益**：24 → 8 工具即省 ~2,700 token/轮，且降低模型误调用无关工具的概率。

### P0-4 MCP 绑定即全量下发 —— 71 个工具不可裁剪

> **✅ 已实施（2026-10-26）—— 且实测推翻了本节的两处判断，见文末「修正」。**
> 实施记录：`docs/上下文工程优化-实施记录-20261026.md` §5。

`tools.py:396-398`：
```python
if _bound_mcp_names:
    core_keep = core_keep | _bound_mcp_names   # Agent 显式绑定的 MCP 工具，JIT 无权裁剪
```

**生产库实测**：

| MCP server | 工具数 | 清单字符 |
|---|---|---|
| `zhiyuan-dev-mcp` | **71** | 1,828 |
| `AI4MBSE 领域能力（内置 MCP 供给）` | 3 | 59 |

**绑定该 MCP 的 agent（4 个）**：`system_mgmt`(7 绑定) / `methodology_resolver`(5) /
**`MBSE建模总体负责人`(14)** / **`智源对接agent`(4)**

**代码注释显示这是刻意决策**（2026-10-16，事故依据："不设这一步 ⇒ 绑 71 个只露 6 个，
工程列表查询类工具必被裁"）。**但当时的解法是二元的**——"全给"或"全裁"。
中间档位（按子任务描述动态选 MCP 工具子集）未被尝试。

**方案**（不改语义契约，只改粒度）：
1. MCP 工具同样走 JIT 打分，但**保底改为"每个 MCP server 至少露 N 个"**（N=3~5），
   而非"全露"——保留"工程列表查询类工具"能被看到，同时把 71 压到 5~10
2. 对确实需要全量的 server（如智源工程列表），用**显式白名单配置**而非"绑定即全量"
3. `zhiyuan-dev-mcp` 的 71 个工具按语义分族（查询/变更/导出/版本…），
   由 `task` 意图自动选族

#### 修正（实施时实测推翻了本节两处判断）

**修正一："每轮恒含 71 个"不成立 —— 生产当前一个都没注入。**

`agent_repo.bound_tools_for` 的判据是 `row.get("status") == "online" and row.get("enabled", 1)`，
而生产库这 4 个 agent 绑定的 MCP server **全部 `status='offline'`**
⇒ `bound` 里根本没有 mcp 项 ⇒ **当前零注入**。

本节说的"≈8,000+ token/轮"应改为：**潜在**成本（server 一旦恢复 online 即发生），
不是当前在烧的钱。这直接影响优先级判断。

**修正二：真正的成本是 5,467 token；但更严重的问题不是 token，是可用性。**

模拟 online 后实测：单工具 224 字符/77 token × 71 = **5,467 token**（占整包 71~80%）。
而 **71 个 MCP 工具的 description 去重后只有 1 种**、parameters 全是宽松空壳：

```json
{"name":"query_projects",
 "description":"MCP 工具（zhiyuan-dev-mcp），端点 http://...",
 "parameters":{"type":"object","properties":{},"additionalProperties":true}}
```

⇒ **模型拿到 71 个名字，但不知道任何一个工具干什么、参数怎么传**。

**根因与本节推断不同**：不是"没尝试中间档位"，而是 **MCP 工具的 description 全是同一句模板
⇒ JIT 打分零区分度 ⇒ 只能二元**。模板串的来源是 `mcp_health.discover_server`
落库时只存了 `name`（`json.dumps([t.get("name") ...])`），把 `list_tools()` 返回的
description / inputSchema **主动丢弃**了。

反过来说：**2026-10-16 那次事故的根因不是 JIT 太狠，而是元数据缺失**。
把元数据修好后，"全给 / 全裁"的二难自然消失。

**实际实施**（详见实施记录 §5）：修数据（存回 description + inputSchema）
→ 按需暴露（语义排序取前 N，默认 8）→ 巡检机会式回填。
实测 71→8 个工具、7,241→2,200 token（−69.6%），且首次具备真实描述与参数契约。

| **token 精确计量** | `core/token_counter.py` | usage → tiktoken → 加权估算 |
| **语义缓存** | `semantic_cache.py` | 阈值 0.95 复用答案（**默认关闭**，且只接了 `execute.py:463`，`stream.py` 未接） |
| **记忆噪音闸门** | `agent/memory_recall.py:66-85` | 6 条正则 + 长度启发式 |
| **检索低置信丢弃** | `agent/rag.py:593-624` | 注入宽度内全为「低」置信 ⇒ 整批丢弃（bm25≥40 豁免） |
| **预算分区裁剪** | `history.py:1513-1548` | 检索 0.15 / 历史 0.25 比例制 |
| **角色段级装配** | `prompt.py:305` `_assemble_role_sections` | P1-1 已实施段级（但 execute 路径 role_cap=0 不截断） |

**结论**：Deep Agents 三机制中，**Offloading 与 Summarization 本仓都已具备且做得更细**
（多了段级装配、诚实性标注、低置信丢弃）。**Isolation 部分具备**（子任务/团队路由 `agent/team_router.py`、
`workflows/` 编排），但缺少 Deep Agents 那种"子 agent 只回结论、原始资料另存"的显式契约。

#### 撤回说明（2026-10-26 实施时核实）

**第 8 项「`rerank_max_candidates` 是死旋钮」—— 判断错误，撤回。**

`core/config.py:930-935` 的注释写得很清楚：`rerank_enabled=False` 是**有 A/B 数据支撑的刻意决策**：

> 官方检索评测 `tools/eval/run_eval.py` 全量 doc 域（20 条）A/B 实测：
> 开重排 recall@3/@5 = 0.4、关重排同样 0.4（**召回零提升**）；
> ndcg@10 仅 0.227 → 0.225（**+0.002，可忽略**）；但评测耗时 196.2s → 28.1s（**慢 7 倍**），
> 且线上每轮多 2 次 LLM 往返（rag_rerank ~1775 + rerank ~810 tokens，**缓存命中恒 0**）。
> 结论：当前语料/配置下 LLM 重排是纯成本。旋钮保留，换语料或换 provider 后可置 true 重评。

⇒ `rerank_max_candidates=10` 不是"死旋钮"，而是**换语料/provider 后可立即生效的预留旋钮**，
且注释已声明约束 `recall_k ≥ top_k ≥ rerank_max_candidates ≥ inject_k`。
**不需要清理，也不需要"启用评估"**（已评估过）。

这条是本次评估**唯一的实质误判**，教训：**看到"配置项没被读取"时，先查该配置点附近的注释
是否已记录了"为什么关"** —— 否则会把"有依据的冻结"误判为"缺陷"。

## 5. 风险与验证方法

**通用纪律**（沿用本仓既有做法：口径变更必须 A/B，不靠推断）：

1. **改动前先建观测**：第 4 项（分块归因）**必须先落地**，否则后续所有优化都是盲改
2. **A/B 判据三件套**（不可只看 token）：
   - Token 消耗（prompt 总量 + 缓存命中）
   - 任务正确率（`Task Success Rate` / 现有 `online_eval` 口径）
   - **要求保留率**——"省 30% token 却遗漏关键要求 = 没达到目的"（旧方案 §7 原则）
3. **检索类改动**必须验证 citation 编号与 `【来源n】` 的对应关系不被破坏
   （`context.py` 注释明确：编号与前端 citations 一一对齐）
4. **工具类改动**必须回归 `tools/verify/verify_s4_llm_params.py`、
   工具名 ASCII 护栏（`^[a-zA-Z0-9_-]+$`，脏数据会导致整批 tools 载荷被 provider 400 拒绝 → 静默回落 Mock）
5. **记忆类改动**必须跑 `tests/manual_verify/verify_p0_memory_recall.py`
   与 `verify_memory_cross_domain.py`（跨域降权口径在 `memory_recall.py:225`）

**已知陷阱**（沿用 AGENTS.md §3）：
- 只读查询用 `file:...?mode=ro`（服务运行时 `mbse.db` 被占用）
- PowerShell 读文件必须 `-Encoding UTF8`，`>` / `>>` 禁用（UTF-16LE 污染）
- 行数用 `[IO.File]::ReadAllLines(...,UTF8).Count`（`Measure-Object -Line` 跳空行）

## 6. 与 Deep Agents 三机制的对照结论

| Deep Agents 机制 | 本仓对应 | 状态 |
|---|---|---|
| **Offloading**（>20k token 工具结果落盘留指针） | `tool_result_offloads` 表 + `tool_result_fetch` + `_TOOL_MODEL_CAP=3000` | ✅ **更细**（阈值更低 + 有 `offset/limit` 式分段） |
| **Summarization**（85% 阈值触发 + 原文另存） | 五档分层压缩 + `conversation_summaries` + `session_artifacts` | ✅ **更细**（多档 + 裁剪诚实性标注） |
| **Isolation**（子 agent 独立上下文，只回结论） | 子任务/团队路由 | ⚠️ **缺显式契约**（未强制"只回结论+证据来源+未解决问题"） |
| — （Deep Agents 未覆盖） | 检索/记忆**注入侧精度** | ❌ **本仓短板，也是本次 5 个 P0 所在** |

**借鉴的核心不是"再加一个机制"，而是 Deep Agents 的两条排序原则**：

1. **先无损、后有损**：卸载（无损，只是搬家）优先于摘要（有损）。本仓检索/记忆侧缺的正是
   "无损的**去重**"——用 MMR/配额剔除重复，是无损的；用摘要压掉重复，是有损的。
2. **任何压缩都保留回溯通道**：本仓 `_mark_budget_cut` 的诚实性标注已是范例，
   应把同一纪律用到**记忆与检索注入**上——去重时保留"被合并前的引用坐标"，
   让模型仍能追问原文档原章节。
