## 0. 结论先行

### 0.1 三句话

1. **编排定义有四种形态，我们选了最灵活也最不可校验的一种**（提示词即编排）。标杆里和我们最像的是 LangGraph / Temporal 的"代码即编排"，但它们靠**类型/确定性**补上了可校验性；我们要补的不是换形态，而是**加规则校验**。
2. **"阶段顺序"的强制力分四级，我们停在第 1 级**（提示词叮嘱）。MBSE 标杆（Capella）把它做成**工具可校验的规则族**（`TC_*` / `TJ_*` / `DCOV_*`），这是第 3 级 —— 这正是我们最该补的一级，且**不需要重构**。
3. **多方案权衡分四级，我们在第 2 级**（工具确定性打分），标杆正统在第 3 级（**候选是模型实例 + 约束求值 + 空间 sweep**）。差距不在打分算法，在**候选方案从哪来**：他们是模型实例，我们是 LLM 现编的 JSON。

### 0.2 我们的位置（一张表定位）

| 维度 | 四级谱系 | 我们在 | 标杆最佳 |
|---|---|---|---|
| 编排定义形态 | 提示词 → 数据图 → 声明式 DSL → 代码即编排 | **提示词即编排**（+ 代码通用引擎） | 声明式 DSL（Dify/ASL）或代码即编排（LangGraph/Temporal） |
| 阶段顺序强制力 | 提示词 → 结构校验 → 业务语义校验 → 类型/确定性 | **提示词** | **业务语义校验**（Capella 规则族） |
| 多方案权衡 | LLM 报分 → 工具确定性打分 → 模型约束求值+sweep → 图+确定性规则 | **工具确定性打分** | **模型约束求值 + sweep**（Cameo + MAVT） |
| 能力注册 | 硬编码分支 → 平台内置表 → **MCP 标准** | **平台内置表**（tools/skills + `if name ==` 分派） | **MCP**（SEI 三层架构的第三层） |

## 2. 谱系一：编排定义放在哪

### 2.1 四种形态与代价

| 形态 | 代表 | 可 diff / 回滚 | 静态校验能力 | 表达力 | 主要代价 |
|---|---|---|---|---|---|
| **代码即编排** | LangGraph、Temporal | ✅（就是代码） | **强**（类型检查 / 编译） | 最强 | 改流程要发版；业务人员改不了 |
| **声明式 DSL** | Dify（YAML）、Step Functions（ASL JSON） | ✅（文本） | **中**（结构 + 引用完整性） | 中（ASL 无法运行时构图） | 复杂分支时 DSL 难读难测 |
| **数据驱动图** | 我们的 `agent_flows`（83 行）、n8n | ✅（JSON） | 中 | 中 | 画布只是编辑器，需人先画 |
| **提示词即编排** | 我们（160 的 `system_prompt`） | ✅（文本） | **无** | 最强（自然语言） | **不符合约束也无痕迹** |

### 2.2 关键判据：错在哪一级会怎样

LangGraph 的 `addConditionalEdges` 第二参数是"返回值 → 节点名"的映射表，官方描述其作用是**类型提示，防止拼错后静默路由到不存在的节点**（来源见 §9）。

这正好命中我们上一轮踩的坑：160 的 prompt 要求填 `display_name`，而 `registry.get()` 只认 `name` ⇒ 静默回落"通用问答Agent（零工具）"，**任务照跑照标 done**。

**标杆的解法不是"写得更清楚"，而是"让写错变成错误"** —— 这就是"结构校验"级与"提示词"级的实质差别。

### 2.3 Dify 的 DSL 长什么样（作为我们 `agent_flows` 的参照）

```yaml
version: 0.1.5
kind: app
workflow:
  graph:
    nodes:
      - id: node_start
        type: start
        data: {title: 开始, outputs: [{variable: query}]}
        position: {x: 0, y: 0}
      - id: node_llm
        type: llm
        data: {provider: openai, model: gpt-4o-mini, prompt: "..."}
    edges:
      - id: edge_1
        source: node_start
        target: node_llm
        sourceHandle: node_start.source-1
        targetHandle: node_llm.target-1
```

要点：**节点和连线全是数据** ⇒ 可 git diff、可脚本批量改、可回滚。但边只校验"端口能对上"，
**不校验"这一步在业务上该不该在这里"** —— 与我们的 `agent_flows` 同一水平。

### 2.4 我们的实际情况（比"提示词"复杂一点）

会话编排（选主 Agent）走 **Planner-Executor**：LLM 一次产出 `tasks[] + deps`，代码按 `deps` 拓扑推进。
所以严格说我们是"**提示词决定计划 + 代码执行计划**"——
比纯提示词强（执行层是硬的），但**计划本身的合法性无人校验**。

而画布工作流走的是另一套（`workflows/engine.py` 真图执行器，`agent_flows` 表 83 行），
**会话入口不走它**。这是既有的双轨现状，不是本次引入。

## 3. 谱系二：阶段顺序的强制力（四级）

| 级 | 做法 | 违反后果 | 代表 |
|---|---|---|---|
| **1** | 提示词叮嘱（"不得跳步、不得倒序"） | 无痕，任务照标 done | **我们** |
| **2** | 结构校验（键合法 / 图可还原） | 报错或拒绝执行 | Dify（端口对不上）、LangGraph（类型提示） |
| **3** | **业务语义校验（阶段间一致性/完备性/覆盖）** | **校验项报错，带位置与修复建议** | **Capella、SysML v2 `/validate`** |
| **4** | 类型系统 / 确定性重放 | 跑不起来 | Temporal（确定性约束）、静态类型语言 |

### 3.1 Capella 的规则族（第 3 级的实证）

Capella 的 Model Validation 把规则按前缀分类：

| 前缀 | 类别 | 检查什么 |
|---|---|---|
| `I_*` | Integrity | 模型完整性（悬空引用等） |
| `Q_*` | Quality | 命名、命名规范等质量项 |
| `DWF_*` | Design · Well-formedness | 结构良构性 |
| `DCON_*` | Design · Consistency | 设计一致性 |
| `DCOM_*` | Design · Completeness | 设计完备性（该有的有没有） |
| `DCOV_*` | Design · Coverage | 覆盖性（能力是否被场景覆盖） |
| **`TC_*`** | **Transition · Consistency** | **层间迁移一致性**（逻辑层→物理层是否对得上） |
| **`TJ_*`** | **Transition · Justification** | **迁移是否有理由**（为什么这么分解决策） |

**这就是"阶段顺序"的正解**：阶段不是靠文档叮嘱，而是**方法（Arcadia）本身定义了层间关系**，
工具用 `TC_*` 检查"上一层的每个元素是否被下一层合理承接"，用 `TJ_*` 检查"这个设计决策有没有理由"。

配套机制：Capella 的 **Transitions** 会自动初始化下一层并**自动创建 realization links**，
但"功能分配、节点创建、部署"仍要人做 —— 即**机械部分自动化，判断部分留给人**。

### 3.2 SysML v2 把这个做成了标准接口

OMG 于 2025-06-30 正式采纳 SysML v2 规范（KerML 1.0 / SysML 2.0 / API & Services 1.0），
2026-03 做编辑性更新并提交 ISO。其 REST 接口族的对称性值得注意：

```
/projects  /elements  /commits  /transform  /validate  /query
```

**`/validate` 与 `/query` 是一等公民**，与增删改查平级。
Validation Service 明确分四类检查：语法、语义（关系与约束）、跨模型一致性、**项目自定义规则**，
返回 severity + 位置（行/列/元素 ID）+ **修复建议**。

### 3.3 对我们的直接含义

我们要补的不是"重写编排"，而是在 `_planner_core` 拿到 plan 之后加一道**校验器**：

- 阶段序：读 `agents` 表上的 `stage_order` 字段，检查 plan 中阶段相对顺序
- 路由键：所有 `task.agent` 必须能 `resolve()` 到 active Agent（我们已有 `_unresolved_hint`，但只是**提示**，不是**拦截**）
- 必需产出：`config.required=true` 的任务是否齐全
- 覆盖性：需求覆盖阶段是否被跳过（对应 `DCOV_*` 的思路）

**成本**：一个纯函数 + 一份规则清单，不引入新依赖。**这是我们投入产出比最高的一项。**

## 4. 谱系三：多方案权衡怎么做（四级）

| 级 | 做法 | 可复算 | 可审计 | 能枚举设计空间 | 代表 |
|---|---|---|---|---|---|
| 1 | LLM 直接报分 | ❌ | ❌ | ❌ | 多数 AI 产品 |
| **2** | **工具确定性打分** | ✅ | ✅（权重可查） | ❌ 只算给定候选 | **我们** |
| **3** | **模型约束求值 + 空间 sweep** | ✅ | ✅（权重固化在模型） | ✅ | **Cameo + MAVT + Trade Study** |
| 4 | 图 + 确定性规则 | ✅ | ✅ | ✅（变体管理） | Trace.Space Trinity |

### 4.1 Cameo 的正统做法（第 3 级）

四件事组合：

1. **候选方案 = SysML 实例模型**。Paramagic 插件通过"交换给定值与目标值"做 what-if 与参数化权衡研究，
   **不修改参数模型本身** ⇒ 候选是被建模出来的实例，不是文字描述。
2. **指标 = 约束块求值**。约束块（constraint block）定义可复用的数学表达式网络，计算 MoE：
   成本、风险、性能、可靠性等；求解器可用内置数学求解，或接 Matlab / Mathematica / OpenModelica。
3. **权重 = 模型里的一等公民**。2026 年 SAE 一篇关于产品线权衡研究的论文描述：
   用 **MAVT（多属性价值理论）实现为约束块**，做属性归一化，并把 stakeholder  elicited 的权重
   聚合为"每个配置一个总分"。
4. **枚举 = Trade Study sweep**。Cameo Trade Study 扫描设计空间，导出"配置–准则"数据集供 BI 分析；
   **选中的概念回写 Cameo 成为 feature configuration**，闭环可追溯。

> 同文还提到用 **SysML 150% 模型**承载可变性（powertrain / chassis / ADAS 的 variability +
> baseline 与细分市场需求），对每个配置计算整车级属性并施加细分市场限值。

### 4.2 我们与它的差距在哪（精确说）

| 环节 | Cameo | 我们 | 差距性质 |
|---|---|---|---|
| 候选来源 | SysML 实例模型（可被约束求值） | LLM 产出的 JSON `{name, scores}` | **结构性**：候选不是模型对象 |
| 指标计算 | 约束块求解（可接物理求解器） | 确定性归一化 + 加权（纯算术） | 可接受：我们的指标是给定原始量 |
| 权重 | 模型内约束块，stakeholder 征集 | `generate_rules` 表（可改、可查） | **已对齐**（都是可配置、可审计） |
| 空间枚举 | Trade Study sweep | 无（只算本次给到的 2~5 个） | **缺失**：不枚举空间 |
| 闭环 | 选中概念回写为模型配置 | 只到"推荐/并列/数据不足"三态，未入库 | **缺失**：上一份方案已如实登记 |

**结论**：我们的打分器本身没问题（甚至比多数 AI 产品强，因为可复算）。
真正的短板是**两头**：候选不是模型对象（进不来），选中结果不回写（出不去）。
中间那层"多算几个候选"（sweep）反而最容易补。

### 4.3 Trace.Space 的变体管理（第 4 级的思路，值得抄概念）

Trinity（2026-10 发布）的做法：**不复制整机**，而是定义"哪些共享、哪些版本分歧"；
变更时指出还影响了什么。其架构是 API-first + **可配置图**，原生支持 design parameters 与 variant management，
并强调 agent 在同一张图上、**在团队写的确定性规则下**工作，且**每个变更仍由工程师批准**。

> 这与我们早前方案文档里"方案 C：变体空间驱动"是同一个思路 —— 当时判断它"适用面窄、需先修 prompt 损坏"。
> 现在有了标杆佐证：**这个方向是对的，只是前置条件（模型层成熟 + 变体作为一等公民）我们还不具备。**

## 5. 能力注册：MCP 在哪一层

### 5.1 SEI 的三层架构（与我们最接近的公开实践）

卡内基梅隆 SEI 研究者在 2026-09 描述的实现（经二手报道）分三层：

1. **AI 编码助手**：操作**版本控制**下的产物
2. **语言感知建模工具链**：解析 SysML v2，**通过命令行接口返回诊断**
3. **知识层：经 MCP 提供**，喂给任何兼容客户端

关键点：VS Code 作为宿主，Claude Code / OpenAI Codex / Continue **同时**接
**同一个仓库、同一个 Sensmetry Syside language server、同一个 MCP server**，
**没有厂商专属集成**。

### 5.2 SEI 的实测与判词（对我们最有价值的一句）

- 实测：完整工具链（语言校验 + 精选知识 + 工作流技能）把"项目自定义模式评分"
  在大型任务上从**均值 71.7 提升到 94.1**。
- 判词：**"干净通过校验只能证明语法与语义合规；模型是否正确、是否适用，
  仍需来源核对、可执行分析、验证结果与工程评审。"**

这句话同时约束两件事：
- 对我们：**不要拿"校验通过"当"做对了"**（我们上一轮已踩过：名册漂移导致流水线全空转但照标 done）
- 对 AI 定位：**AI 是建议者，不是决定者**

### 5.3 三家一致的"人始终控制"

| 产品 | 表述 |
|---|---|
| IBM Engineering AI Hub 1.1（2025-12） | 自然语言需求 → Rhapsody 模型元素（SysML v1/v2），**keeping human experts in full control of every AI-suggested output** |
| Trace.Space Trinity | agents 在团队写的规则下工作，**engineers still approve every change** |
| Capella | Transitions 自动建链，**功能分配/部署仍手动**；`TJ_*` 要求**设计决策有理由** |

我们已有 `hil_level`（L1/L2）+ `ConfirmQueue`，方向一致；缺的是**把"确认点"定义成规则**而非散落在代码里。

### 5.4 MCP 的协议形状（作为"工具注册"的目标形态）

- JSON-RPC 2.0，host / client / server 三角色，**能力协商**
- server 提供三类能力：**Resources**（上下文数据）、**Prompts**（模板化消息与工作流）、**Tools**（可执行函数）
- client 提供 **Elicitation**（server 反向请求用户补充信息）
- 灵感来自 **LSP**（把"接一种语言"变成"接一个协议"）
- 安全原则：工具即任意代码执行，**调用前必须获得用户明确同意**

**对我们的含义**：目前新增工具必须改 `agent/pipeline_parts/tools.py` 的 `if name ==` 分支。
若要做"外部工具零代码接入"，正解是**把工具执行走 MCP server**，而不是继续加分支。
但这是一次架构改造，不是配置项 —— 应作为独立阶段评估，不宜混进当前批次。

## 6. 逐项对照：我们 vs 标杆

| 维度 | 我们（2026-11-03 实测） | 标杆最佳实践 | 差距性质 |
|---|---|---|---|
| 编排定义 | 提示词（160 的 `system_prompt` 第 2 条）+ 代码通用引擎 | DSL / 代码即编排（可静态校验） | 形态差异，**不必换** |
| 计划合法性校验 | **无**（`deps` 只保证拓扑，不保证阶段序） | Capella `TC_*`/`TJ_*`；SysML v2 `/validate` | **可直接补，性价比最高** |
| 路由键合法性 | `_unresolved_hint` **提示**，不拦截 | LangGraph 类型提示 → 编译期报错 | **一个判据即可补** |
| 候选方案来源 | LLM 产出 JSON | SysML 实例模型 | **结构性**，需模型层支持 |
| 打分 | 确定性工具，覆盖率门槛 + 并列判定 + 不推荐 | 约束块求值 + MAVT 聚合权重 | **已对齐甚至领先**（多数 AI 产品在 1 级） |
| 权重管理 | `generate_rules` 表，改文本即生效 | 模型内约束块 | **已对齐** |
| 空间枚举 | 无 | Trade Study sweep | **可补（先易后难）** |
| 选中回写 | 无（三态展示） | 回写为 feature configuration | **缺失**，属独立阶段 |
| 能力注册 | 平台内置表 + 硬编码分派 | MCP | 架构改造，独立评估 |
| HITL | `hil_level` L1/L2 + `ConfirmQueue` | interrupt()/task token/Transitions | 机制有，**规则化不足** |
| 失败可恢复 | `run_id` + `agent_tasks` 队列 | checkpointer / event history | 有雏形，弱于 Temporal |
| 可复算 | ✅ 打分器纯函数 | ✅ | **已对齐** |

## 7. 五条可取的（按投入产出排序）

### 第 1 条：给 plan 加一道校验器（最高杠杆）

- **做什么**：`_planner_core` 拿到 `plan` 后、入队前，跑一遍规则检查。
- **规则集**（对齐 Capella 分类思路）：
  - 路由键：每个 `task.agent` 必须 `resolve()` 到 active Agent（**拦截而非提示**）
  - 阶段序：若目标命中建模流水线，按 `stage_order` 检查相对顺序
  - 完备性：`config.required=true` 的任务是否齐全（对应 `DCOM_*`）
  - 覆盖性：目标提到的阶段是否都被覆盖（对应 `DCOV_*`）
- **依据**：Capella `TC_*/TJ_*/DCOM_*/DCOV_*`；SysML v2 `/validate` 的 severity + 修复建议形态
- **代价**：一个纯函数 + 规则清单，无新依赖
- **必需配套**：违规则**降级为显式告警 + 落库**，不能静默继续（否则又是一次"照标 done"）

### 第 2 条：把"阶段清单"从 4 处代码收敛成表字段

- **做什么**：`is_code_stage` / `is_standard_intent` / `stage_order` 三个字段落到 `agents` 表，代码只读表。
- **依据**：Dify / ASL 的共同点 —— **定义是数据，引擎是通用的**；我们恰好反过来（定义散在代码常量里）
- **代价**：4 处常量替换 + 一次迁移；有 `tests/test_intent_storage_hygiene.py` 可守护
- **收益**：新增阶段**零代码**

### 第 3 条：候选方案向"模型对象"靠拢（分两步）

- **第一步（轻）**：候选除 `name/scores` 外，强制带 `model_ref`（对应的 SysML 元素 ID 或版本）。
  没有模型引用也能打分，但**卡片上显式标注"未关联模型"** —— 让"这是文字方案还是模型方案"可见。
- **第二步（重）**：接入 `sysml_versions`，候选从模型实例派生（对应 Cameo 的"实例模型"思路）
- **依据**：Cameo Paramagic（交换给定/目标值，不改参数模型）；Trace.Space（变体作为图上元素）
- **代价**：第一步只要改 schema；第二步依赖模型层成熟度

### 第 4 条：加一个"空间枚举"的最小版本

- **做什么**：不打分时只算给定候选，而是允许对**离散取值维度**做组合枚举，
  按总分排序取 Top-N，再由人确认。对应 Cameo Trade Study sweep。
- **依据**：Cameo Trade Study 的 sweep + 导出"配置–准则"数据集
- **代价**：中等（要防止组合爆炸，需上限）
- **前置**：第 3 条第一步（候选要有可枚举的参数维度）

### 第 5 条：把 HITL 确认点定义成规则

- **做什么**：现在"哪些任务需要人确认"靠 `hil_level` 字段 + 代码判断；
  改为规则表（如"写操作 + L2 + 不可逆 ⇒ 必须确认"），并像 Capella `TJ_*` 那样
  **要求确认时附理由**（为什么这么选）。
- **依据**：Capella `TJ_*`；LangGraph `interrupt()` + checkpointer；Step Functions task token
- **代价**：小（复用 `ConfirmQueue`）

## 8. 三条**不该**照搬的（如实）

### 8.1 不引入 Temporal 式"确定性重放"

Temporal 要求 workflow 代码在重放时**确定性**：不能直接读墙钟、取随机数、发网络请求，
这些必须挪到 activity。我们的子任务本身就是 **LLM 调用**（天然不确定），
强行套确定性重放会得到一个"假装确定"的壳，收益为零、复杂度极高。

**可取的部分**：`run_id` + 任务状态机 + 事件历史（我们已有）。
**不取的部分**：确定性约束与 versioning 语义。

### 8.2 不做 Step Functions 式"静态图"

ASL 要求**静态定义**状态机，**不支持运行时构图**。而我们的计划本来就是
**LLM 在运行时生成**的 —— 这是我们的核心能力，不该为了可校验性牺牲它。

**正解**：保留运行时生成，**在生成后校验**（第 7 节第 1 条）。

### 8.3 不一步到位做完整 SysML parametrics

Cameo 的 trade study 能力背后是：约束块库 + 实例模型 + 外部求解器（Matlab/OpenModelica）+ 150% 模型可变性。
我们模型层还在"能产 SysML v2 代码 + checker.jar 校验"的阶段，
直接上参数求解会得到一堆**没人维护的约束块**。

**正解**：先把"候选是否关联模型"显式化（第 7 节第 3 条第一步），再谈求解器。
