- 日期：2026-09-17

## 一、总体模型：三个正交维度

插件管理**不是一个状态机，而是三个互不牵连的维度**（P1-7 解耦，2026-09-16 落地）：

| 维度 | 字段 | 取值 | 语义 | 治理动作 |
|---|---|---|---|---|
| 可用性 | `plugins.status` | draft / submitted / rejected / published / disabled / removed | 能力能不能被 AI 消费 | 发布 / 取消发布 / 审核 / 启停 / 删除 |
| 可见范围 | `plugins.scope` | personal / pending_public / public | 谁看得见、装得上 | 申请上架 / 审核 / 撤回上架 |
| 个人开关 | `plugin_installs.enabled` | 0 / 1 | **我**用不用它 | 个人启用 / 停用 |

设计约定：**一个动作只动一个维度**。
- `publish_self` / `unpublish_self` → 只动 status
- `apply_share` / `review_share` / `withdraw_share` → 只动 scope
- `set_install_enabled` → 只动 `plugin_installs.enabled`
- `set_enabled`（全局启停）→ 动 status（市场管理员专属）
- `install` / `uninstall` → 动 `plugin_installs` 行（并增减 `install_count`）

### 2.2 图论性质（静态分析结论）

```
从 draft 可达：draft, submitted, rejected, published, disabled, removed   → 6/6 全部可达
终态（无出边）：removed
非预期死锁态：无
```

**结论：status 维度无死锁、无陷阱态、无不可达状态。**
（`TRANSITIONS['removed'] = set()`，且 `get_plugin()` 默认排除 removed，因此 removed 事实上是唯一终态。）

### 2.3 可编辑性

`EDITABLE_STATUSES = (draft, rejected, published, disabled)`

| 状态 | 可编辑 | 说明 |
|---|---|---|
| draft / rejected | ✅ | 正常 |
| published / disabled | ✅ | 兑现「已发布可改」；但 **public 条目仅市场管理员可改**（防绕过审核推版） |
| submitted | ❌ | 审核中冻结 —— 本身合理，**但缺少「撤回提交」，形成单向门（见 P0-3）** |
| removed | ❌ | 已软删 |

## 三、维度 2：scope 状态机（3 态）

| 迁移 | 实现函数 | 权限守卫 |
|---|---|---|
| personal → pending_public | `apply_share` | 作者/管理员；且要求 `status='published'` |
| pending_public → public | `review_share(approve=True)` | **市场管理员** |
| pending_public → personal | `review_share(approve=False)` | **市场管理员** |
| public → personal | `withdraw_share` | **市场管理员**（2026-09-17 收权，作者不可单方下架） |

**缺口**：`SHARE_TRANSITIONS` 声明了 `pending_public → personal`（撤销申请），但**只有管理员侧的「驳回」实现了它**；作者侧没有任何入口撤回自己待审的申请（见 P1-1）。

## 四、消费判定（`consumable_plugin_ids`）

三级优先级，决定 AI 运行时能否调用：

```
前置：status == 'published'（否则一律排除）
 ① 本人存在 enabled=0 的安装记录  → 否决（优先级最高，个人停用永远生效）
 ② MAX(installs.enabled) == 1    → 可消费（系统级 user_id=0 或本人安装记录）
 ③ author_id == 0 且 inst_on is None（完全无安装记录）→ fail-open 放行
 ④ author_id == 本人             → 可消费（自建自持，无需「安装」）
```

**真实库验证**：67 条已发布插件中，0 条出现「已发布但全局装配池不可消费」的静默失效 —— 该项健康。

## 六、缺陷清单（按严重度）

### 🔴 P0-1 审核门失效：作者可自行把「待审核」条目一键发布

- **证据（实验 B5）**：`status=submitted` 的条目，作者调用 `publish_self` → `ok=True`，直接变 `published`。
- **根因**：`publish_self` 只用 `TRANSITIONS` 判合法，而 `submitted → published` 在同表中是合法边（该边本应只由管理员审核触发）；函数未限制来源状态。
- **影响**：`plugin_review_policy='forced'`（当前线上配置）下的「发布需审核」策略形同虚设 —— 任何用户提交后可自批。
- **修复**：`publish_self` 增加来源白名单，仅允许 `status in ('draft','rejected','disabled')` 且 `scope != 'public'`；`submitted` 一律拒绝并提示「请等待管理员审核或先撤回提交」。

### 🔴 P0-2 市场治理收权被绕过：作者可自行恢复「全局停用」

- **证据（实验 B1）**：`scope=public, status=disabled` → 作者 `publish_self` → `ok=True`，`status=published`，并触发 `_sync_legacy_safe(True)`。
- **根因**：`set_enabled` 对 `scope='public'` 已收归市场管理员（2026-09-17 P0），但 `publish_self` 完全没有 scope 守卫，构成同义反复的旁路。
- **影响**：市场管理员全市场停用某能力后，作者可**一键恢复**，所有已安装用户的 AI 运行时立即恢复调用 —— 治理收权与安全边界同时失效。
- **修复**：与 P0-1 同一处补丁（`scope == 'public'` → 拒绝，提示「已上架能力的全局启停请联系市场管理员」）。

### 🔴 P0-3 遗留「发布 / 分享」链路根本进不了市场，并把条目锁成不可编辑

**（a）前端「⬆ 发布」按钮**（`marketPublishFrom` → `POST /api/studio/market/{kind}/{name}/publish`）
- `policy='forced'`（线上真实值）→ `transition(→'submitted')`，**scope 完全不动** → 条目**永远进不了市场**；前端却 toast「已发布到公共市场」。
- 且 `submitted ∉ EDITABLE_STATUSES` → **条目从此不可编辑**（实验 B6：`当前状态「待审核」不允许编辑`）。
- 管理员「通过」后（实验 B4）：`status=published` 但 `scope` 仍是 `personal` → **依然不在市场**。用户既没上架，又改不了，且无「撤回提交」入口（`submitted` 出边只有 published/rejected/removed，作者侧无可用动作）。
- 若该条目已是 `published`，调用该接口还会直接报 `非法状态流转: published → submitted`。

**（b）前端「⬆ 分享」按钮**（`sharePlugin` → `POST /api/studio/share/submit`）
- 同样落 `submitted`，同样的死胡同；`published` 条目调用时报非法流转。
- 该按钮在 `28-studio.js` 的 mcp / tool 卡片上**仍然是可见入口**（第 157/159/228/230/315/317 行），并非死代码。

- **根因**：P1-7 解耦（`transition` 不再改 scope）之后，旧链路的两个入口**未迁移**，仍然指望「审核通过 = 自动上架」。
- **修复**：二选一 —— ① 删除这两个遗留入口与 `/api/studio/market/{k}/{n}/publish`、`/api/studio/share/submit`，前端「⬆ 发布/分享」统一改调 `POST /api/plugins/{pid}/share`；② 若需保留旧接口，则在其中改为调用 `apply_share`（并同步放开 `pending_public → personal` 的作者撤销）。

### 🟠 P1-1 待审申请无法作者撤回，且取消发布会造出 scope 孤儿 + 草稿被「复活上架」

三个连锁缺陷：

1. **无法撤回申请（实验 B7）**：`withdraw_share` 要求 `scope=='public'`，作者对待审条目调用报「该能力未上架市场」；`SHARE_TRANSITIONS` 声明的 `pending_public → personal` 只有管理员 `reject` 能实现。作者的申请**只能等管理员裁决**。
2. **取消发布留下孤儿（实验 B2）**：`unpublish_self` 只拦 `scope=='public'`，未拦 `pending_public` → 结果为 `scope=pending_public + status=draft`。这个组合既不在市场列表（`list_market` 要求 status ∈ published/disabled），也过不了 `apply_share`（要求 published），仍留在待审队列里。
3. **草稿被审核复活（实验 B3）**：上一步的孤儿条目，管理员 `review_share(approve)` → `scope=public`，而 `review_share` **不校验 status** → 得到 `scope=public + status=draft`。作者明确取消过发布的能力，被一次审核重新置为「市场在售」。

- **修复**：
  - `unpublish_self` 增加 `scope=='pending_public'` 处理：先撤销申请（scope→personal）再回 draft，或直接拒绝并提示先撤回申请；
  - 新增作者侧 `cancel_share`（pending_public → personal）；
  - `review_share` 增加前置校验 `status == 'published'`，否则返回「该能力已取消发布，请先由作者重新发布」。

### 🟠 P1-2 已停用条目无法「下架」（实验 B10）

- `market_unpublish` 走 `transition(→'draft')`，而 `disabled → draft` 不在 `TRANSITIONS` → 报 `非法状态流转: disabled → draft`。
- 市场管理员对已停用条目执行下架会失败，必须先「恢复上架」再「下架」。
- **修复**：`market_unpublish` 改为调用 `withdraw_share` 语义（只动 scope），或把 `disabled → draft` 补入 `TRANSITIONS`。

### 🟠 P1-3 审核队列语义分叉（同一 UI 按钮两种效果）

`/api/plugins/pending`（`pending_reviews`）同时返回：
- `scope='pending_public'`（新链，主路径）→ 通过 = `scope=public` → **入市**
- `status='submitted'`（旧链，兼容）→ 通过 = `status=published`，**scope 不变** → **不入市**

管理端「上架审核」tab 把两者渲染成同一个「通过」按钮，但结果一个上架、一个不上架，且第二种还会把条目变成不可编辑态。
- **修复**：随 P0-3 一并收敛为单一链路；过渡期至少在队列里标明 `review_kind`，并对旧链条目隐藏「通过」（或改走 `apply_share`）。

### 🟡 P2-1 `install_count` 漂移

- **实验 B8**：作者对已上架能力做个人停用 → `set_install_enabled` 派生一条安装记录 → 作者再「卸载」 → `install_count` 由 5 掉到 3。派生记录从未被计数过，卸载却递减了计数。
- **真实库（A5）**：78 条插件中 **15 条** `install_count` 与实际安装记录数不符（多为遗留工具：计数 0、实际 1~3），市场「安装 N 次」展示失真。
- **修复**：`plugin_installs` 增加 `counted INTEGER DEFAULT 0` 标记（真实 `install()` 落库才置 1），`uninstall` 仅在 `counted=1` 时递减；或直接改为按 `COUNT(*)` 实时计算。

### 🟡 P2-2 已停用条目的安装报错文案误导（实验 B9）

`list_market` 含 `disabled` 条目（用于展示「⛔ 已停用」），但 `install()` 要求 `status=='published'` → 报 **"插件不存在或未上架"**（404），实际条目就在眼前。
前端已对 `off` 条目隐藏「＋安装」按钮（`28-studio.js:470`），所以主要是 API 文案问题。
- **修复**：`install()` 对 `scope='public' and status='disabled'` 单独返回「该能力已被市场管理停用，暂不可安装」。

### 🟡 P2-3 软删除残留

- `soft_delete` 只改 `status='removed'`，不清理 `plugin_installs`（真实库存在 2 组孤儿安装记录），也不清 `install_count`。
- 真实库另有 2 条 `scope='public' + status='removed'` 的条目（e2e 测试残留）：scope 卡在 public，其 `withdraw_share` 仍可被调用。
- **修复**：软删除时同步 `DELETE FROM plugin_installs WHERE plugin_id=?`，并规整 scope 为 personal。

### 🟡 P2-4 `TRANSITIONS` 声明与实际实现不一致（文档级）

`TRANSITIONS` 在 5 个状态里声明了指向 `removed` 的边，但 `soft_delete` **不走 `transition()`**（直接 UPDATE），因此这些边永远不会被 `can_transition` 校验；另有 `draft→rejected`、`rejected→draft` 两条边无任何调用方。
不构成 bug，但会误导后续基于状态表的推导（本次分析已受影响）。
- **修复**：删除无调用方的边，或在注释中标注 `# 未使用`。

## 八、死锁 / 不可达性结论

- **status 维度**：6 态全可达，唯一终态 `removed`，**无死锁、无陷阱态**。
- **scope 维度**：3 态全可达，但 `pending_public → personal` 的作者侧实现缺失（P1-1）。
- **实际存在的「准死锁」是用户旅程级的，而非图论级的**：
  1. `submitted` 状态下作者既不能编辑（P2-1 之外）也不能撤回，只能等管理员 —— **单向门**（P0-3）；
  2. `pending_public` 状态下作者不能撤回申请 —— **只能等管理员**（P1-1）。
  两者都能靠管理员人工解开，因此不是硬死锁，但在管理员缺席时等同于卡死。
- **非法组合状态**（状态表无法表达、代码却能产生）：
  - `scope=pending_public + status=draft`（P1-1）；
  - `scope=public + status=draft`（P1-1，市场查不到但 install 会失败）；
  - `scope=public + status=removed`（P2-3，真实库已存在 2 条）。

## 九、建议修复顺序

1. **第一刀（P0-1 + P0-2）**：`store.publish_self` 补两个守卫（来源状态白名单 + `scope!='public'`）。一处补丁堵两个越权，改动最小、收益最大。
2. **第二刀（P0-3 + P1-3）**：下线遗留 `publish` / `share` 链路（前端两个按钮 + 两个后端接口），统一到 `/api/plugins/{pid}/share`；`/api/plugins/pending` 只留 `scope='pending_public'`。
3. **第三刀（P1-1 + P1-2）**：`unpublish_self` 处理 pending 态；新增作者侧 `cancel_share`；`review_share` 校验 status；`market_unpublish` 改走 scope 语义。
4. **第四刀（P2）**：安装计数改实时 `COUNT(*)` 或加 `counted` 标记；软删除清理安装记录；修正文案与状态表注释。

# 十、修复实施记录（2026-09-17 当日完成）

四刀已按顺序全部落地，并额外做了一轮前端入口治理。回归脚本 `tools/audit_plugin_state_machine.py` 由原先「登记缺陷」改为「断言修复后语义」，**11/11 全通过**。

## 10.1 第一刀：`publish_self` 守卫（堵 P0-1 + P0-2）

新增常量白名单，并在 `publish_self` 中前置校验：

```python
_SELF_PUBLISHABLE_FROM = ("draft", "rejected", "disabled")
```

- **来源状态白名单**：只有 `draft / rejected / disabled` 可走自助发布。`submitted` 被排除 → 作者无法自批跳过审核（P0-1 关闭）。
- **scope 守卫**：`scope == 'public'` 时拒绝 `publish_self`，提示「已上架条目由市场管理员治理」。作者无法一键撤销市场管理员的全局停用（P0-2 关闭）。

> 语义边界：`disabled → published`（作者恢复自己被停用的私有能力）仍允许；`public + disabled`（市场治理态）走 `/enabled` 且仅市场管理员。

## 10.2 第二刀：下线遗留双轨（堵 P0-3 + P1-3）

**后端**（`routers/studio_parts/market.py`）四个遗留端点全部改为委托受守卫的 store 函数，不再自己拼 `transition()`：

| 端点 | 改造后行为 |
|---|---|
| `POST /api/studio/market/{kind}/{name}/publish` | 委托 `share_to_market` 语义：scope → `pending_public`（受审）或 `public`（免审）；不再写 `submitted` |
| `POST /api/studio/market/{kind}/{name}/unpublish` | 改走 `withdraw_share`（scope 语义），仅市场管理员；不再要求 `status=='draft'` 合法流转 |
| `POST /api/studio/share/submit` | 同上，统一到上架申请语义 |
| `POST /api/studio/share/review` | 仅对 `scope=='pending_public'` 生效（原为 `status=='submitted'`） |

**兼容层**：`_find_plugin_by_display` 增加 plugin_id 直查分支（遗留前端传的是数值主键/plugin_id，按 name 查必 404）。

**审核队列**（`store.pending_reviews`）：返回项新增 `review_kind` 字段，区分 `pending_public`（新链，通过=上架）与 `submitted`（遗留链，通过=发布），前端提示语据此区分——消除「同一个通过按钮效果不同」的歧义（P1-3）。

**前端**：`sharePlugin` / `shareReview` 全部改指 `/api/plugins/{pid}/share` / `/review`；`loadUnifiedPending` 的 `plugin_id` 加引号（原裸写生成非法 JS）。

## 10.3 第三刀：补齐撤回与校验（堵 P1-1 + P1-2）

- **新增 `store.cancel_share()`**：作者侧撤回**待审申请**（`pending_public → personal`），关闭「只能等管理员」的用户旅程准死锁。
- **`/api/plugins/{pid}/unshare` 按 scope 分派**：`pending_public → cancel_share`（撤回申请）；`public → withdraw_share`（下架，仅市场管理员）。
- **`unpublish_self` 兼容 pending 态**：处于申请中时先撤回申请再回到 draft，不再产生 `pending_public + draft` 孤儿；同时补 `submitted → draft` 边支持「撤回提交」。
- **`review_share` 增加 status 校验**：只有 `status ∈ {published, disabled}` 的条目才能被审核上架，草稿无法被审核「复活上架」（P1-1 关闭）。
- **`market_unpublish` 改走 scope 语义**：已停用条目也能直接下架，不必「先恢复再下架」（P1-2 关闭）。

## 10.4 第四刀：P2 收尾

- **文案**：市场安装接口区分「未上架 / 已全局停用」；`install()` 对停用条目给出准确原因而非「插件不存在」。

- **新增 `store.reconcile_integrity()`**：幂等校准函数，清理历史幽灵/孤儿记录 + 全量同步计数。**已在真实库 `mbse.db` 上执行**（先备份 `backups/mbse.db.bak-20260917-reconcile`）：漂移 55 → 0，幽灵 2 → 0，孤儿 2 → 0。
