## 2. 修复前的真实问题（实测发现，非推测）

### 2.1 `confidence` 在 vector 路由下恒为 0（真缺陷，已修）

`tools/eval/preflight.py` 在 embedding 恢复后仍报 4/5 查询 `conf=0.0`：

```
query                          route    reason                       conf
测控分系统与地面控制站的关系       graph    graph_confidence_ok          0.88
卫星通信系统包含哪些分系统        vector   graph_no_hit                  0.0
OMG 规范里 requirement 的写法     vector   graph_no_hit                  0.0
属性定义与量的区别               vector   graph_no_hit                  0.0
SysML_V2 端口定义语法            vector   graph_no_hit                  0.0
```

**根因**：`agent/rag.py` 返回 `"confidence": graph_confidence`，而
`QueryRouter.decide` 在图谱未命中时给出 `route='vector'` 且 graph 置信度 = 0
⇒ **vector 路由下该字段恒为 0，置信度信号完全丢失**。
同一次 `hybrid_search` 的 `vec_score` 明明是 0.44~0.84（召回正常、命中文档正确）。

**消费点枚举**（改前必做，5 个点全是**透传**，不做阈值判断 ⇒ 改语义安全）：

| 位置 | 用途 |
|---|---|
| `agent/pipeline_parts/execute.py:458 / 514 / 549` | 写进 card / `retrieval` 段给前端 |
| `agent/pipeline_parts/stream.py:1851 / 1927` | 同上（SSE 分支） |
| `agent/rag.py` → `query_routing_stats` | 落库统计 ⇒ vector 路平均置信度**恒 0**，口径失真 |

**修法**：`confidence` 改为**按路由取值**（vector 路用向量相似度），
口径**复用 `knowledge_engine` 算 `confidence_level` 的同一算法**（`vs>0` 取相似度，
否则 `min(bs/50, 1)`）——**不另造一套量纲**。
`QueryRouter.decide` 的路由判定**仍用 `graph_confidence`**（未改，图谱侧语义不变）；
另**新增** `graph_confidence` 字段保留原值可观测。

实测效果：

| query | route | confidence（修前→修后） |
|---|---|---|
| 卫星通信系统包含哪些分系统 | vector | 0.0 → **0.441** |
| OMG 规范里 requirement 的写法 | vector | 0.0 → **0.632** |
| 测控分系统与地面控制站的关系 | graph | 0.88 → 0.88（不变） |

## 4. 根因诊断：为什么池里没有（`tools/diag_pool_miss.py`，零 API 消耗）

对 12 条 pool 未命中的 case 逐层定位：

| 判据 | 结果 | 含义 |
|---|---|---|
| gold chunk 是否在向量矩阵 | 12/12 在 | 语料完整 |
| **自查询名次**（用 gold 自己的向量查矩阵） | **12/12 = 1** | **向量索引无 bug** |
| 同文档平均相似度 | 0.520 | — |
| 跨文档平均相似度 | 0.404 | — |
| **差值** | **+0.116** | **同文档并不比跨文档"像"多少** |

⇒ 结论：**`qwen3.7-text-embedding` 对长文档内细粒度章节的区分度不足**。
gold chunk 自身能被精确检出（自查询第 1），但"章节标题"这类 query 落进 7269 条里
时，gold 章节并不比其它文档的章节更相似 ⇒ 召不回。

**这不是**代码 bug、**不是**配置不当、**不是**索引损坏。

补充证据：入库时 `embed_text = doc_title + section + content`（`chunking.py:149`，
Title-Enriched）⇒ **章节标题已进向量**，排除了"忘了加标题"这一可能。

## 8. 事故：`agent/rag.py` 被磁盘满截断为 0 字节并提交（已恢复）

**发现方式**：本轮之后跑 CI 等价回归，**14+ 门禁集体 RED**，报
`ImportError: cannot import name 'GraphRAG' from 'agent.rag'`。

**根因链**（比"磁盘满"更深一层）：

1. C 盘 100% 满（仅剩 **7.9M**）；
2. 写 `agent/rag.py` 时被截断为 **0 字节**（同批还有 `knowledge_pipeline/search.py`）；
3. 当时只发现并 `git checkout` 恢复了 `search.py`，**漏了 `rag.py`**；
4. 随后 `git add -A && commit`（`e20ff5b`）**把 0 字节文件提交进了历史**。

**为什么当时没发现**：Python 侧的表现是 `ImportError`（像"代码写坏了"），
而真实原因是"文件没了"——**磁盘满导致的截断不产生任何语法错误提示**。

**恢复**：`git show 8598866:agent/rag.py`（787 行，导入已验证），
并**重做**随截断丢失的 confidence 修复（`fc12759`，787→831 行）。

**全仓排查**：`git ls-files -s | git cat-file --batch-check='%(objectsize) %(rest)'`
批量核对每个已跟踪文件的对象大小 ⇒ **仅此一个**空文件，其余完好。
（工作区另用 `find -size 0` 交叉确认。）

**教训（已入跨项目记忆）**：

- 磁盘满 ⇒ **写文件会静默截断为 0 字节**，不报错；提交后成为历史的一部分。
- 恢复时**必须做全仓空文件排查**，不能只恢复"已知的那几个" —— 我这次就漏了一个。
- 排查手段要用**批量对象大小核对**（`cat-file --batch-check`），
  逐个 `git show` 会超时。
- 提交前 `git status` 看到"某个我改过的文件"出现在清单里时，
  **先确认它不是被截断**（`ls -l` 看字节数 / `git diff --stat` 看是否 0 行变化）。
