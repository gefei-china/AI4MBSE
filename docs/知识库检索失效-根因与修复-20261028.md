# 知识库检索失效：根因与修复（2026-10-28）

> **用户报障原话**
> 「我让 AI 从支持库检索 `perform action` 用法，AI 反馈未检索到，知识库明显有 OMG
> SysML V2 文档介绍具体用法，为啥检索不好使？」

> **AI 当时的回答**
> 「知识库检索结果：无命中。我按你的要求检索了「perform action 泳道用法」，四次检索
> 全部返回空或「未检索到实质相关内容」（词重叠 0/0、0/4），知识图谱与知识库中没有
> 关于泳道 perform action 的条文可用。」

---

## 〇、结论先行

**知识库里确实有，是检索链路有三层独立故障，任一层都足以让结果"看起来没有"。**

库中实测：**45 个切片**含 `perform action`（doc 799 = `OMG Systems Modeling Language™ V2 (1).pdf`，
7.17.6 节「Perform Action Usages」）。修复后同一条查询返回：

```
【来源 1】OMG Systems Modeling Language™ V2 (1).pdf · 7.17.6 Perform Action Usages
（相似度 0.570，置信度 中）
no such reference subsetting, then the performed action is the perform action usage itself.
part def Vehicle { perform action powerVehicle references VehicleActions::providePower; ... }
```

---

## 一、三层根因（按"被发现的顺序"倒排，按"严重程度"排序）

### R1（最严重）默认 embedding provider 与库内向量**不同源**

| 项 | 值 |
|---|---|
| 现象 | 检索返回 20 条正确命中，但**余弦只有 0.02~0.09**（正常相关应为 0.5~0.7）⇒ 全判「低置信」⇒ 被 `rag._low_conf_suppressed` 整批抑制 ⇒ 工具侧 `hits=0` |
| 根因 | `document_chunks.embed_version` 只记 **`openai-compat`**，**不记具体模型**。库中 6457 条向量由 `Qwen3-Embedding-0.6B` 生成；而 `llm_providers` 里 `is_default=1` 的却是 `bge-m3`。两者**维度都是 1024**，所以不报错、不告警，只是分数归零 |
| 判定实验 | 同一查询、同一批目标切片：`Qwen3-Embedding-0.6B` → 余弦 **0.549 / 0.601 / 0.651**；`bge-m3` → **0.037 / 0.037 / 0.019** |
| 修法 | 默认 provider 切回 `Qwen3-Embedding-0.6B`（id=108）；门禁 D3b 用**余弦实测**守住"同源"这件事 |
| 未闭合 | `embed_version` 记模型名是根本修法，需全量重嵌入 7177 条 ⇒ 本轮不做，登记于 §四 |

### R2 provider 模型名带尾随空格 ⇒ `/embeddings` 恒 404

| 项 | 值 |
|---|---|
| 现象 | 日志刷 `embedding API 调用失败，降级 bigram: Client error '404 Not Found'` |
| 根因 | `llm_providers.id=110` 的 `name` 与 `model_name` 都是 `'bge-m3  '`（**两个尾随空格**，len=8）。OpenAI 兼容协议里 model 是精确匹配，多一个空格就是另一个模型 |
| 证据 | `{"model":"bge-m3  "}` → `404 The model \`bge-m3  \` does not exist.`；`{"model":"bge-m3"}` → **200** |
| 影响 | 全库 embedding **静默降级为 bigram**（`embed()` 的 except 吞掉）⇒ 向量分全面走低 ⇒ 与 R1 叠加 |
| 修法 | ① `knowledge_pipeline/embedder.py` 读取时 `.strip()`（不假设配置干净）；② 修正库中脏数据；③ 门禁 D1b 全表扫首尾空白 |

### R3 弱相关判定三条缺陷（`agent/pipeline_parts/tools.py` 旧实现）

```python
q_tokens = set(re.findall(r"[\u4e00-\u9fa5]{2,4}", q))        # ← 只抽中文
max_score = max(h["score"] ...)                                # ← RRF 融合分
weak = (not hits) or (not q_tokens) or (ratio < 0.2 and max_score < 0.5)
```

| 缺陷 | 后果 |
|---|---|
| **只抽中文 token** | 纯英文术语查询 `q_tokens` 为空集 ⇒ `not q_tokens` **恒真** ⇒ 必判弱 |
| **overlap 跨语言恒 0** | 命中的是英文规范原文，不含中文 token ⇒ 中文查英文文档必判弱 |
| **`max_score < 0.5` 恒真** | `score` 是 RRF 融合分 `1/(60+rank)`，两路相加**理论最大 ≈ 2/61 = 0.0328**，永远到不了 0.5 ⇒ 该条件等于没写 |

⇒ 实际生效判据退化为：「查询没有中文 token，或中英文夹生」就判弱。**这正是用户看到的「词重叠 0/0」。**

**这个出口此前已修过两次、都没修到它**：

| 时间 | 修在哪 | 修了什么 |
|---|---|---|
| 2026-10-20 | `rag._low_conf_suppressed` | 加强 BM25 豁免（注释里明写"工具侧只剩词重叠 0/5"） |
| 2026-10-20 | `knowledge_engine` 定级 | `_ref = max(vs, _ref_bm25)`（两层取较强者） |
| **2026-10-28（本次）** | `tools.py` 判据本身 | 抽成纯函数 `agent/retrieval_relevance.py`，**判据换掉** |

> 🔑 教训：前两次都修了**中间层**，判据本身一直是坏的。同类症状反复出现时，
> 要顺着"症状是谁打出来的那句话"往上追，而不是在中间层加豁免。

### R4 检索到了却答不出：只给 180 字

旧成功分支：

```python
detail = f"...：{[h.get('name') or h.get('content','')[:60] for h in hits[:3]]}"
```

`hits[:3]` × **60 字符** = 180 字。而每条 chunk 实际有 300 字。
⇒ 即使判定通过，LLM 也拿不到条文全文，只能答「信息不足」。

修法：给 top 4 条的**完整切片内容**（约 1200 字）+ 来源文档 + 章节 + 相似度。

## 二、修复清单

| 文件 | 改动 |
|---|---|
| `agent/retrieval_relevance.py` | **新建**。`extract_tokens`（中英文都抽、英文停用词过滤）+ `assess_relevance`（强证据优先：高置信 / vec_score / 强 BM25 / 词重叠兜底） |
| `agent/pipeline_parts/tools.py` | `graph_retrieve` 改调纯函数；成功分支给完整条文 + 来源标注；失败文案给**可核对**的实测证据而非「词重叠 0/0」 |
| `knowledge_pipeline/embedder.py` | 读取 provider 时 `model_name.strip()` |
| `llm_providers`（数据） | id=110 的 `name` / `model_name` 去尾随空格；默认 embedding 切到 id=108（Qwen3-Embedding-0.6B） |
| `tools/verify/verify_retrieval_relevance.py` | **新建门禁 32 项**（含变异自证 + 反向自证 + 余弦同源实测 + 真实工具调用端到端） |

### 判据为什么不再用 `score`

RRF 是**排名融合**，取值区间由 `k` 决定，与"相关程度"不是同一量纲。需要"相关程度"时用
`vec_score` / `bm25_score` / `confidence_level`。门禁 C4 直接断言判定代码**不读** `score` 字段。

### 阈值来源（不引入新魔法数字）

| 证据 | 阈值 | 同源 |
|---|---|---|
| 高置信 | `confidence_level == "高"` | `knowledge_engine` 已有定级 |
| 向量 | `vec_score >= rag.confidence_mid`（0.45） | 同一个配置键 |
| BM25 | `>= 40` | `rag._low_conf_suppressed` 强命中豁免同口径 |
| 词重叠 | `>= 20%` | 原判据保留（降为兜底） |

## 四、未闭合（如实登记）

| # | 项 | 说明 |
|---|---|---|
| 1 | **`embed_version` 不记模型名** | 根本修法需全量重嵌入 7177 条切片（约 7177/10 ≈ 718 次 API 调用）。本轮用「默认 provider 切回库内同源模型 + 门禁余弦实测」兜住，但**换模型时仍会静默失效**，只靠门禁 D3b 在 CI 时发现 |
| 2 | 720 条 `bigram-tf` 切片 | 与 `openai-compat` 版本不一致 ⇒ 真向量检索路径看不到它们（走 bigram 兜底路径仍可用）。需重嵌入 |
| 3 | 图谱 0 命中 | doc 799 的 `entity_count=0`（未做实体抽取）⇒ `graph_count` 恒 0，本轮只靠向量 + BM25。属独立缺口 |
| 4 | 多语言跨语检索 | 本轮只保证「中文查英文文档」能算重叠；语义跨语（中问英答深度理解）依赖 embedding 质量，未做专项评测 |
