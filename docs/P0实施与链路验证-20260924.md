### 1.3 官方 SDK 互操作：4/4，但踩到一个真兼容坑

用 **官方 Python SDK（`pip install mcp`，1.30.0）** 的 `streamablehttp_client` 作为**第三方客户端**验证：

- ✅ `initialize` → `2025-06-18 / ai4mbse-domain`
- ✅ `list_tools` → 3 个工具，`inputSchema` 被 SDK 正常解析成结构
- ✅ `call_tool graphrag_search` → `isError=False`，返回真实实体
  `{'id':'S-f6499a05','name':'宽带载荷','entity_type':'通信载荷分系统'}`
- ✅ 未知工具 → SDK 正确抛 `McpError`

**踩坑与修法（这段最有复用价值）**：

| 现象 | 定位 | 处理 |
|---|---|---|
| SDK 1.x：第 3 次请求报 `Session terminated` | 服务端返回**纯 JSON**，SDK 的 streamable-http 客户端对"单次 JSON 响应"的处理有缺陷 | 服务端增加分支：**`Accept` 含 `text/event-stream` 时改返回 SSE**（`event: message\ndata: {json}`）。规范允许服务端在 JSON/SSE 间选择，改动合规 |
| SDK 2.x：第 2 次请求 404 | access log 显示请求行是 `POST http%3A//127.0.0.1%3A8020/mcp` —— **URL 编码的绝对 URL 当路径**，属 mcp 2.x + httpx2 的问题 | 不在服务端为此妥协；验证改用 SDK 1.x 稳定版 |

> 教训：**"符合规范"不等于"能被所有客户端消费"**。MCP 规范说服务端可选 JSON 或 SSE，
> 但实测官方 SDK 只吃 SSE。交付这类接口时，必须拿**真客户端**跑一遍，而不是只对着规范自测。

## 3. P0-3：`intent_rules` 种子规则（**挖出两个真 bug**）

### 3.1 修的两个 bug（都不是"加数据"能绕过的）

**Bug ①：失效机制作用在错误的 router 实例上**

```python
# 原实现（routers/studio_parts/shared.py）
from agent import agent as _agent
_agent.router._rules = None        # ← 改的是 agent/__init__.py 的模块级实例
```
而 `agent/pipeline.py:46` 是 `self.router = IntentRouter()` —— **每个 AgentPipeline 都新建 router**，
与 `_agent.router` **不是同一个对象**。外层还 `except Exception: pass` 把异常静默吞掉
⇒ 表现为"规则改了必须重启"，而代码注释却写着"即时生效"。

**修法**：改用**类级版本号**（与实例数无关）：
`IntentRouter._RULES_EPOCH` + `invalidate_rules()` 类方法；`load_rules()` 记 epoch，
`detect()` 比对 epoch 不符即重载；`_invalidate_intent_rules()` 改为调用类方法并把静默 except 改成留痕。

**Bug ②：指纹计算早于规则刷新 → 缓存把新规则挡在门外**

```python
fp = self._index_fingerprint()      # ← 用的是还没刷新的 _rules
cached = self._cache_get(t, fp)     # ← 命中「规则变更前」的旧条目 → 直接短路返回
...
if self._rules 过期: load_rules()   # ← 到这里才刷新，太晚了
```
指纹里含 `_rules` 本是好设计（规则变了指纹就变），但**刷新发生在指纹之后**，
于是拿旧规则算出旧指纹、精准命中旧缓存。

**修法**：把规则刷新提到 `detect()` 的**最开头**（`t = text.lower()` 之后、算 fp 之前）。

### 3.2 种子词：**不能靠读代码猜**

我最初按"内置关键词层没登记"挑了 `sysmlv2 / 校核 / 影响面 / 覆盖性`，
写了个 A/B 实测脚本（`tmp/fix_20260924/probe_seed_words.py`）后发现 —— **四个全都被排在规则层之前的层拦截了**
（Glossary 术语强制路由 / 内置关键词），它们的 route 本来就是 `rule`，写规则毫无效果。

> **这与本仓既有教训同源**：读代码判断"这里应该是空档"往往错，必须 A/B 实测。

实测筛出的 4 个**真正可被规则层接管**的种子：

| trigger | intent | weight | 无规则时 | 加规则后 | 价值 |
|---|---|---|---|---|---|
| `结构树` | design | 30 | `chat`（**误判**） | `rule/design` | 修正真实误判 |
| `追溯矩阵` | review | 30 | `llm → impact`（**误判**） | `rule/review` | 修正真实误判 |
| `接口变更` | impact | 30 | `llm`（花钱+慢） | `rule/impact` | 省一次 LLM 调用 |
| `参数图` | design | 20 | `llm` | `rule/design` | 省一次 LLM 调用 |

### 3.3 验证（4/4，未重启）

| 探针 | 规则前 | 规则后（**服务未重启**） |
|---|---|---|
| 「帮我看看这个结构树」 | `llm/design` 0.6 | `rule/design` **0.95** |
| 「整理一下追溯矩阵」 | `llm/impact` 0.85 | `rule/review` **0.95** |

探针只读到 SSE 的 `stage 意图识别/done` 事件就断连（不触发后续 LLM 生成）。
⚠️ 实现细节坑：`意图识别` 有 **两个同名 stage 事件**——`status=run`（无字段）与 `status=done`（带 intent/route/confidence），
只取 `done`，否则读到的全是 `None`。

## 4. P0-4：`multi_intent` 从「仅展示」→「驱动计划」

**改动**：`_stream_orchestrated_flow` 新增 `stage_hint` 参数；两个调用点把 `detect_multi()` 的
sequence 传进去，非空时作为**高优先阶段序约束**追加到 planner prompt。

- **不改 plan 结构契约**：仍由 LLM 生成 DAG（key/title/agent/deps/task_type），只是 prompt 多一条约束。
  没有采用"用 sequence 直接替代 plan"——那会丢掉 title/agent/deps，plan 质量反而下降。
- 实现坑：`plan_prompt` 是 f-string 且含 JSON 示例花括号，注入必须放在**构造完之后**追加。
- **范围**：仅 SSE 流式主路径。非流式 `execute()`（`execute.py:97` → `FlowExecutor.run_planner_plan`）
  **本次未改**——该路径不计算 `multi_intent`，已如实标注。

**验证（会话 #400，真实编排，550s）**：

```

plan_agents = ['requirement_analysis', 'design', '需求视图生成', '结构视图生成', '交互视图（IBD）生成', 'design']
subtask 时序：requirement_analysis(2.8→81.8s) → design(81.8→184.5s) → 三个视图生成器 → design 汇总
```

| 断言 | 结果 |
|---|---|
| A `multi_intent` 事件存在且 sequence 非空 | ✅ |
| B 真走编排（plan 6 项，degraded=False） | ✅ |
| C plan 覆盖 sequence 的阶段意图（**顺序严格对齐**） | ✅ |
| D 注入 stage_hint 后 planner 未降级 | ✅ |
| E 落库卡片为编排形态 | ✅（脚本对该端点返回类型判断有误，改由 **DB 直查确认**：`orchestrated=True`，plan 6 项，agents 与 sequence 一致） |

## 6. 局限与未做（如实披露）

1. **⚠️ 生产服务（8000）未重启**：所有验证在临时实例 8010/8020 上完成。
   生产要生效需重启，届时 `/mcp` 上线 + 内置 MCP 行被巡检刷成 online。
   **重启前**：`intent.py` 的两个修复、`stream.py` 的 stage_hint 在生产上都还没生效。
2. **P0-4 只覆盖流式主路径**：非流式 `execute()` 未同步 `stage_hint`（该路径不计算 multi_intent）。
3. **P0-4 的 E 断言**在脚本层因端点返回类型判断有误，实际结论由 DB 直查确认（见 §4）。
4. **MCP 工具仅 3 个只读能力**：未暴露写能力（刻意），也未做 authentication（与现有 `/api/*` 一致的
   `enforce_login` 开关语义）。若对外开放需先定鉴权方案。
5. **未做变异自证**：P0-3 的两个 bug 修复本质上是"还原即失败"型验证（前后对比 route 从 llm→rule 即证伪），
   但若要固化为常驻自检脚本，仍需补"注回旧写法 → 断言必须 FAIL"的完整变异流程。
6. **官方 SDK 2.x 的 URL 编码路径 404**未解决（判定为 SDK 侧问题），验证用的是 SDK 1.30.0。
