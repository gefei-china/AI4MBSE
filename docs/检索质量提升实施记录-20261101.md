## 2. S3a：域外整体拒答

### 2.1 与 S1 的分层关系（**不要混**）

```
low_conf_floor (0.15) → 逐条过滤：去掉明显无关的，留下真命中
reject_max/avg         → 整体拒答：**最好的那条都不够** ⇒ 该查询不在知识域内
```

### 2.2 标定依据（13 条样本实测）

| 组 | rel_max 范围 | rel_avg 范围 |
|---|---|---|
| 切题（7 条） | 0.405 ~ 0.739 | 0.267 ~ 0.532 |
| 域外（6 条） | **0.000 ~ 0.293** | **0.000 ~ 0.195** |

间隙 0.293 ~ 0.405 ⇒ 取 `reject_max_score=0.35`、`reject_avg_score=0.22`（中位偏保守）。
判据形态：**两者都低于阈值才拒答**（任一超标即放行），宁少拒不误杀。

### 2.3 生效范围（防止误伤）

只在 **「向量路由 且 图谱无命中」** 时生效：
- 模型域问题（"转发器 EIRP 多少"）走 `mixed`，命中 5 实体 270 关系 → 不受影响（实测 `reject=False`）；
- 附件命中优先的情况也不受此限；
- 枚举类查询（"系统有哪些需求"）实测 `reject=False`、返回 20 条，未被误杀。

### 2.4 效果

| 指标 | 修前 | 修后 |
|---|---|---|
| 拒答准确率 | **0.333** | **1.000** |
| 切题 hit@5 | 0.889 | 0.889（零损失） |
| 切题 MRR | 0.833 | 0.833（零损失） |

五条域外全部返回 0 条：天气 / Python 爬虫 / 太阳能板清洗 / 红烧肉 / 股市。

## 4. 【本轮最大发现】知识问答 Agent 根本没触发检索

### 4.1 发现过程（**不是看代码发现的，是端到端跑出来的**）

改完 S1/S3a 后，我在**运行中的服务**上实测聊天入口，结果异常：

```
retrieval.route      = "none"
retrieval.chunk_hits = 0
citations            = 0
```

但模型回答里明显提到了材料 ⇒ 它读到了东西却没走检索。查返回的 `intent` 与 `agent`：

```
intent = knowledge_qa      ← 确实是知识问答意图
agent  = 知识问答Agent
route  = none              ← 但检索被跳过
```

定位 `agent/pipeline_parts/execute.py:364`：

```python
should_retrieve = (req_scope.ok or kb_tags or agent_def.kb_required or
                   (intent == "report_generation" and report_type in ("impact","review")))
```

三个开关全为 false ⇒ 不检索。而 `agents` 表实测：

| agent | kb_required |
|---|---|
| **knowledge_qa（知识问答）** | **0** ← 异常 |
| chat（闲聊） | 0（合理） |
| impact（影响分析） | **1** |
| requirement_structuring / architecture_skeleton / model_validation_repair / trace_verification | **1** |

**一个名叫"知识问答"的 Agent，`kb_required=0`，而影响分析、追溯核验这些都要 1。**
判定为配置遗漏，不是设计意图。

### 4.2 后果（可量化）

| | 修复前 | 修复后 |
|---|---|---|
| `route` | `none` | **vector** |
| `vector_count` | 0 | **19** |
| `citations` | 0 | **5** |
| 回答质量 | "技术要求书里**没有**独立的信息安全章节"（**错误**，§7.4 就是） | "集中在 **7.4 信息安全要求**，共 5 条，覆盖传输加密/运维安全/组件安全/命令管控/审计追溯 [1]"（**正确且带引用**） |

> ⚠️ **这条最重要的教训**：前面 S1/S3a 的所有优化，在聊天入口都是"空转"——

## 5. 性能修复：BM25 索引启动预热

### 5.1 定位

`kb_required=1` 后每次问答都检索，首次实测 13~21s。cProfile（2 次 `hybrid_search` 共 48s）：

| 函数 | cumtime | 说明 |
|---|---|---|
| `hybrid_search` | 48.1s | 总 |
| **`_bm25_cache_get`** | **35.3s** | **建索引** |
| `embedder.embed_with_version` | 10.7s | embedding 超时（服务不可用） |

根因：7179 个 chunk 做 bigram 分词 ≈ **1.17 亿次函数调用**，全部发生在**首个用户请求**里。
用户看到的是"问一句等半分钟"，与"卡死"无法区分。

### 5.2 修法

`main.py::lifespan` 加**后台守护线程**预热：`_bm25_cache_get(conn, None, None, None, False)`。

- daemon 线程 ⇒ 不阻塞启动，服务立即可用
- 只预热 `branches=None`（检索侧恒用这个 key）
- 抛异常只打日志，绝不影响主流程

### 5.3 效果

| 指标 | 修前 | 修后 |
|---|---|---|
| `query_trace.latency_ms` | **17,672ms** / 13,349ms | **579 / 596 / 585 ms** |
| 首次用户查询总耗时 | 21s ~ 41s | 6.7s（含 LLM 生成） |

启动日志确认：`[startup] BM25 索引预热完成（首次检索不再等 35s）`

## 6. S3c 被证伪：chunk↔实体桥**不该填**

### 6.1 原计划

用 `entities.name` 做最长匹配，填 `document_chunks.linked_entity_ids`（当时 0/7179 = 0%）。

### 6.2 实测：填了也是假链接

| 实体名（剥离 ID 前缀后） | 在 7179 chunks 中出现次数 |
|---|---|
| 转发器 EIRP 不低于 55 dBW | **0** |
| 太阳翼输出功率不低于 15 kW | **0** |
| 转发器（最短的结构实体） | **0** |
| 行波管 / 蓄电池组 / 波束 / Ka 频段 | **0** |

61 个实体里能在文档中匹配到的：**1 个**。

### 6.3 根因：两个域词汇零交集

| 词 | chunk 数 |
|---|---|
| 转发器 | **0** |
| 卫星 | 2 |
| 太阳翼 / 行波管 / 波束 / 蓄电池 / 测控 / 星座 | 全部 **0** |

| 词 | chunk 数 |
|---|---|
| requirement | 1552 |
| action | 1096 |
| port | 897 |
| package | 248 |
| interface | 237 |
| part def | 223 |
| classifier | 176 |

**结论**：
- **图谱** = 卫星通信**型号设计**数据（AI 建模产物：转发器/太阳翼/需求条目）
- **文档库** = **SysML v2 规范** + 项目技术要求 + 车辆场景

不是"桥没接"，而是**两端本来就没有共同实体**。硬填只会造出假链接，
让"图谱命中"变成噪声源 —— 比不填更糟。**原 P1-1 在当前语料下不成立。**

### 6.4 但图谱对它自己的域是有效的（不能一并否定）

| 查询 | route | 实体 | 关系 | 置信 |
|---|---|---|---|---|
| 转发器的 EIRP 是多少 | mixed | **5** | **270** | 0.660 |
| 转发器和天线之间是什么关系 | mixed | 5 | 270 | 0.660 |
| 需求 S-09853b7a 对应的验证用例 | mixed | 1 | 108 | 0.300 |

⇒ 正确表述：**两个引擎各自有效、服务不同问题**，缺的是**域感知路由**（不是桥）。

## 7. 真正的天花板：embedding 三家全部不可用

### 7.1 实测（绕过代理后仍失败）

| provider | 地址 | 结果 |
|---|---|---|
| #108 Qwen3-Embedding-0.6B | `192.168.100.202:8004` | **ConnectTimeout** |
| #110 bge-m3 | `192.168.100.231:8001` | **ConnectTimeout** |
| #106 qwen3.7-text-embedding | 公网 | **HTTP 403 免费额度耗尽** |

> 已验证：本机 `HTTP_PROXY=http://127.0.0.1:64524`，
> 用 `httpx.Client(trust_env=False)` 绕过代理后**仍是 ConnectTimeout**
> ⇒ 不是代理问题，是内网主机不可达。

### 7.2 这解释了 4 条失败 query 的**全部**

| 期望文档 | chunks | 含中文"需求" |
|---|---|---|
| ISO 29148 | 610 | **0** |
| Guide to writing | 855 | **0** |
| OMG SysML v2 | 2606 | **0** |
| KerML | 2011 | **0** |
| 广汽（中文） | 180 | 123 |

英文文档里**一个中文字都没有**。纯中文 query 在 bigram（字面重叠）下**必然零重叠**。
唯一能跨中英的是**多语言 embedding**（BGE-M3 / Qwen3-Embedding 都支持）—— 恰恰不可用。

⇒ **跨语言检索能力目前为 0。这是第一瓶颈，且不是检索代码的问题。**

### 7.3 附带影响

`embed_version` 双版本混杂：`bigram-tf` 720 条 + `openai-compat` 6459 条。
检索按版本隔离 ⇒ **那 720 条在真向量恢复后反而"不存在"**（版本对不上）。
恢复 embedding 后必须补一次重向量化。

## 11. 第二轮：P0-1 内容预算 + P0-2 文档摘要（11:00–11:15）

### 11.1 P0-1：`content[:300]` 硬编码 → 统一长度预算

**问题（可量化）**：`content[:300]` 硬编码在 **4 处**
（`knowledge_engine.py` 1 处 + `knowledge_pipeline/search.py` 3 处），而实测：

| 指标 | 实测值 |
|---|---|
| chunk 长度 p50 | **523 字** |
| chunk 长度 avg | 432 字 |
| 超过 300 字的 chunk | **5122 / 7179 = 71.3%** |

⇒ **71.3% 的命中被砍掉一截**，模型只看到"半句条文"，于是答"信息不足"或自行补全。

**改法（不逐个调数字，而是收敛成单一实现）**：

| 文件 | 改动 |
|---|---|
| `knowledge_pipeline/textlimit.py`（新增） | `clip()` / `limit()` / `reset_cache()` —— **唯一**截断实现 |
| `core/config.py` | 新增 `rag.chunk_content_chars`（默认 **1200**，`0`=不截断） |
| `knowledge_engine.py` | `[:300]` → `_clip(...)` |
| `knowledge_pipeline/search.py` | 3 处 `[:300]` → `_clip(...)` |

> 为什么默认 1200：覆盖绝大多数 chunk（p50=523），同时挡住 p99 以上的异常长块
> （库里 max=5681 字，多为整段代码块）。
> 为什么特意抽成模块：本仓反复出现「同一语义多处各写一份常量」的坑，

**代价（实测）**：注入 5 条从上限 1500 字 → 实测 **1096 / 2722 / 3177 字**（+约 700 token）。

### 11.2 P0-2：`documents.summary` 接入检索

**问题**：LLM 摘要能力早已实现（`ingest._gen_llm_summary`，实测 160~209 字质量不错），
但 `rag.py` / `knowledge_engine.py` **完全不读它**；且 14 篇里只有 **3 篇**有值（21%）。

**改法**：

| 文件 | 改动 |
|---|---|
| `agent/rag.py` | `retrieve()` 补查**命中已出现的文档**（最多 3 个）的摘要 → 返回 `doc_summaries` |
| `agent/pipeline_parts/context.py` | 注入「文档背景」块，**排在【来源1】之前**（先语境后条文） |
| `tools/backfill_doc_summary.py`（新增） | 批量补齐工具（均匀采样拼正文，支持 dry-run / limit / force） |

**为什么只取命中文档**：避免把无关文档的摘要当噪声塞进来。
**为什么限制 3 条**：摘要 200 字 × 全部命中文档会挤占正文预算。
**为什么放在【来源n】之前**：与人的阅读顺序一致；放后面模型会先入为主只认片段。

**摘要补齐结果**：3/14 → **14/14（100%）**，全部为 LLM 真摘要。
