## 0. 结论（先看这个）

**判词：不是"词表不够大"，而是"决定『用户要什么行为』的那一层根本不存在"。**

1. **两个误判都发生在 LLM 之前**——分别是 `intent.py:638` 的 explain 前置短路、`:701` 的建模强信号正则。
   两处都是「命中即 return」的确定性硬短路，**LLM 主裁判（`llm_first`）根本没机会参与**。
2. **两个误判的共性是「言语行为」判错**：①问的是**系统自身能力**（自指元问题），没有任何一层负责它；
   ②问的是**生成物的元信息**（条件/依赖），"生成"是**名词化**用法却被当成动作词。
   即：现有全部判据都是**话题/对象匹配**，缺一维**"问 vs 做"**。
3. **为什么每轮补丁都在打地鼠**：confirmed 44 条里，走 explain 的 9 条**全是"问技术概念"**、
   走 rule 的 20 条**全是祈使句** —— 你报的两类误判在评测集里**零覆盖**，门禁拦不住。
4. **一个独立且更高优先级的问题**：`llm_first` 主裁判**当前在生产上 100% 空转** ——
   默认 provider `deepseek-v4-flash`(id=71) **402 余额耗尽**，且 `llm_client` **无 provider 降级**。
   可判集 **49.5%（137/277）** 的真实输入因此沉到 `chat` 兜底（`conf=0.0`）。
   **不修这条，所有"让 LLM 当主裁判"的方案都只是纸上的。**
5. **现成的钥匙已实测有效，但要补三个口子**：`intent.rule_llm_confirm` 实测能救回
   **44% 的非闲聊类误判**（误判②完全救回），confirmed 29 条正例**族容差口径 0 误伤**；
   但闲聊类 **0%**（候选集里没有 `chat`）、explain 短路根本不参与复核、JSON 解析失败默认"维持规则"。
   详见 §6.1。
6. **✅ 已落地并验证**：修复不是靠"再加词"，而是靠**在决策链最前面建出「问 vs 做」这一维**
   （IA-P1-甲 言语行为层）+ **修好 LLM 通道**（IA-P0-甲）+ **补上评测盲区**（IA-P0-乙）。
   **评测从 `0.9318 (41/44)` 提升到 `0.9792 (47/48)`**，你报的两类误判 4 条全部判对、**零误伤**。
   详见 §10。

**一句话**：现在要做的不是再加词，而是①先让 LLM 通道真的通、②补上"问 vs 做"这一层、
③把评测集的盲区补上，否则下一轮还是打地鼠。

## 1. 两个用例的精确根因（已复现，定位到行）

复现方式：`tmp/intent_audit/probe_repro.py`（隔离库副本 + 真实 `IntentRouter.detect`）。

| # | 输入 | 实得 | route | conf | 断链层 | 代码位置 | 命中信号 |
|---|---|---|---|---|---|---|---|
| ① | 你好 介绍下你的能力边界 | `knowledge_qa` | **explain** | 0.80 | explain 前置短路 | `agent/intent.py:638-639` | `介绍`（无 action 信号） |
| ② | 参数视图的生成条件，依赖哪些前置数据 | `design` | **rule** | 0.95 | **建模强信号正则** | `agent/intent.py:701-703` | `视图…生成`（名词化"生成条件"被当动作词） |

### ① explain 前置短路

```python
# agent/intent.py:638
if self._is_explain_ask(t):
    return self._done("knowledge_qa", "explain", 0.80, text, fp)
```

`_is_explain_ask` 的判据只有两条：含 `_EXPLAIN_SIGNALS`（`介绍/说明/是什么/有哪些/流程…`）
且**不含** `_ACTION_SIGNALS`。「介绍」命中 → 直接短路。

**这条短路的位置在缓存/关键词/规则/语义/LLM 全部之前**，是整个决策链的第一道闸门，
也是**唯一绕过 LLM 复核的确定性层**（`_done` 而非 `_rule_done`，见 §6）。

### ② 建模强信号正则

```python
# agent/intent.py:701-703
if re.search(r"(生成|给出|输出|编写|创建).{0,24}(sysml|kerml|建模|模型|bdd|ibd|视图|代码)", t) or \
   re.search(r"(sysml|kerml|建模|bdd|ibd|视图|块定义|内部块).{0,24}(生成|代码|建模)", t):
    return self._rule_done("design", "rule", 0.95, text, fp, conn=conn)
```

第二个分支 `视图…生成` 命中（`参数**视图**的**生成**条件`）→ `design@0.95` **静默执行**。
这里的"生成"是**名词化**用法（生成*条件*），不是动作。

> ⚠️ 顺带修掉的一个既有错例：`帮我校验一下这段sysml代码`（gold=review）本条也命中，
> 但真实 `detect()` 里 `:695` 的 review 强信号在前 → 实际判 review。**做层归因必须按源码顺序**。

## 2. 共性：缺"言语行为"这一维

| 维度 | 现有系统 | 你的两个用例 |
|---|---|---|
| **话题/对象**（在讲什么） | ✅ 9 个意图 + 30 个 Agent 关键词表 | 「参数视图」「你的能力」→ 都识别对了 |
| **言语行为**（要干什么） | ❌ **完全缺失**，只有零散的"动作词/说明词"子串表 | ①要**问系统能做什么**（自指元问题）②要**问生成条件**（解释型提问）→ 都被当成"做"或"查知识" |

⇒ **两个误判不是两个 bug，是同一个缺口的两个面**：
系统在"知识问答"和"设计/建模"之间，只按**对象**分，从不按**问 vs 做**分。

## 6. 现成的钥匙：`rule_llm_confirm`，以及一处架构不对称

`_rule_done`（`agent/intent.py:1169-1200`）**早已接好 LLM 复核**：

| LLM 复核结果 | 返回意图 | route | 置信 | 澄清 |
|---|---|---|---|---|
| `confirmed` | 规则意图 | `rule_llm_confirmed` | max(conf, 0.97) | 否 |
| `vetoed` | **LLM 意图** | `rule_llm_vetoed` | LLM 置信 | **强制** |
| `unavailable` | 规则意图（退回） | `rule_llm_skipped` | 原值 | 否 |
| `skipped`（开关关） | 规则意图 | 原 route（**逐字节不变**） | 原值 | 否 |

开关 `intent.rule_llm_confirm` 默认 False ⇒ 线上零回归。
**配套工具已在**：`tools/calib/eval_intent_baseline.py`（A/B 对照）。

**不对称（就是 §1 ① 的结构性原因）**：
explain 前置短路（`:638`）走的是 `_done(...)` 而不是 `_rule_done(...)`
⇒ **它永远不会进入 LLM 复核**，而它的误判率（30%）在所有确定性层里排第一。

### 6.1 决定性实验：`rule_llm_confirm` 实测（2026-10-29，隔离库，默认 provider 切到 id=104 `qwen3.8-max`）

口径：隔离库副本内把 `is_default` 切到实测可用的 `qwen3.8-max`(id=104)，**生产库零改动**；
每条样本只调 1 次 `_llm_confirm_rule`。脚本 `tmp/intent_audit/probe_rule_confirm4.py`。

**A 组：可判集里被确定性层判错的 32 条**

| 结果 | 条数 | 说明 |
|---|---|---|
| **复核救回**（vetoed 且指对） | **12** | 37.5% |
| 否决但指错 | 7 | 几乎全是**粒度冲突**（否决到 `requirement_structuring`/`trace_verification`/`architecture_skeleton`） |
| 未能救回 | 13 | 其中 **chat 类 5 条全灭** |

> **分类型看**：非 chat 类误判 **12/27 = 44% 被救回**；
> **chat 类（闲聊）5 条救回率 0%** —— 4 条复核员直接 `confirmed` 判 `knowledge_qa`，
> 1 条 `unavailable`。
> **根因是结构性的**：`_known_intents_for_review` 第 1014 行 `ks.discard("chat")`
> ⇒ **复核员的候选集里根本没有 `chat`**，自指闲聊类误判在结构上无法被否决到 chat。

**用户报的两个用例，复核员怎么说**

| 用例 | 复核结果 | 判定 |
|---|---|---|
| 参数视图的生成条件，依赖哪些前置数据 | `vetoed` → `knowledge_qa@0.78` → route=`rule_llm_vetoed` + 强制澄清 | **✔ 完全救回** |
| 你好 介绍下你的能力边界 | `unavailable`：LLM **没按 JSON 输出**，直接开始回答"你好！我可以从『能做什么 / 不擅长什么 / 使用边界』三个方面介绍我的能力边界…" | **✘ 救不回** |

> ⚠️ 误判①这一条特别说明问题：**LLM 实际认对了**（它回的是"介绍我的能力边界"，语义上就是闲聊，
> 不是知识检索），却被两件事挡住 —— ① 候选集无 `chat`；② 提示词只说"只输出一个 JSON 对象"，
> 模型仍直接去回答用户。**这说明问题不在"词表不够"，而在"复核层的接口没定义好"。**

**B 组：confirmed 中走确定性层的 29 条正例**

| 结果 | 条数 | 说明 |
|---|---|---|
| 复核确认/不可用（维持规则） | 24 | **0 误伤** |
| 被否决 | 5 | **5 条全部是粒度冲突**：`design→view_expansion`、`design→architecture_skeleton`、`review→trace_verification`、`report_generation→impact` |

⇒ **精确匹配口径：5/29 被改错（17%）；族容差口径（子意图/近邻算对）：0 误伤** ——
与《意图识别优化调研与方案-20261023》§8.1 的既有结论一致（族容差下 37/37 = 1.000）。

**综合结论**：`rule_llm_confirm` 是**对症的现成机制**（能救回 44% 的非闲聊误判、正例族容差下零误伤），
但它今天有三个必须先补的口子：
① **候选集加 `chat`**（否则闲聊类永远救不回）；
② **explain 短路改走 `_rule_done`**（否则 `:638` 永远不参与复核）；
③ **复核输出必须结构化**（JSON 解析失败不能算"同意"，也不能算"没复核成"就默认维持规则——
   现状是 `unavailable` ⇒ 退回规则结果，对高频误判等于没复核）；
④ **族容差评分**（否则 17% 正例被改成粒度更细但执行主体不同的意图）。

## 7. 优化方案

### IA-P0（今天可做，全部零回归 / 或有回退开关）

| 编号 | 动作 | 验收判据 |
|---|---|---|
| **IA-P0-甲** | **恢复 LLM 通道**：给 `llm_client` 加 provider 降级（主→备，同模型族优先），或把 `is_default` 切到实测可用的 `qwen3.8-max`(104) / `ds-v4-flash-neibu`(109) | `intent_detect` 的 LLM 调用成功率 > 99%；可判集 `route=chat & conf=0.0` 占比从 49.5% 显著下降；confirmed 44 条 accuracy **不回退** |
| **IA-P0-乙** | **补门禁盲区**：把 ①自指询问 ②解释型疑问句 两类样本（正例+负例，各 20~30 条，含你报的两条原文）补进 `intent_samples` 并标 `confirmed` | confirmed 集里 explain 正例不再 100% 问概念、rule 正例不再 100% 祈使句；新样本 A/B 前后 accuracy 有分辨率（当前 1/44 ≈ 2.3%） |
| **IA-P0-丙** | **explain 短路接上 LLM 复核**：`:638` 的 `_done` → `_rule_done`（开关关闭时 route 逐字节不变），并把 `chat` **加入复核候选集**（`_known_intents_for_review` 第 1014 行 `ks.discard("chat")`），同时要求复核输出**结构化**（JSON 解析失败≠维持规则，应重试或降级为"待澄清"） | 依据 §6.1 实测：接上复核后误判②**完全救回**；误判①需"候选集含 chat"才可能救回；confirmed 29 条正例**族容差口径 0 误伤**（精确口径 5 条粒度冲突误伤 ⇒ 需配族容差评分） |

### IA-P1（结构性：把"问 vs 做"这一维建出来）

> **IA-P1-甲 已做原型验证（2026-10-29，`tmp/intent_audit/probe_speech_act.py`，只读不改生产代码）**，
> 结论见下方「IA-P1-甲 原型实测」——**它已被证明可修好全部 4 条真实误判，且经「对强信号让位」后
> 在 confirmed 48 条上零误伤**。这是本轮最有价值的可执行产出。

| 编号 | 动作 | 要点 |
|---|---|---|

#### IA-P1-甲 原型实测（confirmed 48 条，2026-10-29）

判据：A 名词化形态（动作词+抽象后缀）/ B 疑问形态 / C 自指元问题（你/你的 + 能力类谓词 + **glossary 判无技术术语**）。

**这 2 条误伤都是仓库已有的已知例外，且已有现成防御机制**：
- 「模糊词 / 不可验证」早已在 `_ACTION_SIGNALS`（`agent/intent.py:49`，注释明写"这两个是质量问题的**专指词**，出现即'要做质量分析'而非问概念"）；

⚠️ 实现要点：①让位顺序 = 强信号 > 言语行为 > 关键词层；
②「自指元问题」必须用 glossary 判"有无技术对象"，否则「介绍一下SysML v2的作用」会被误判成 chat。

## 8. 明确"不做"的事（沿用本仓既有教训）

- ❌ **不为刷分改词表**：M1/M2a/M2b 的 A/B 已证明单纯加词的收益/副作用比很差；IA-P1-甲 要建的是**判据结构**，不是词表。
- ❌ **不手改阈值**：intent/skills/tools 的阈值是 bigram 经验值，dense 路首度生效后需重标定（见 `calibrate_intent_semantic.py`）。
- ❌ **不把 `agents.description` 直接喂给 LLM 当路由边界**：已实测**净损失 9 / 净收益 8**（P0-2 教训，见审计技能）。要喂边界得**新写负空间**。
- ❌ **不放松"历史改判"**：P0-5 已三轮实测证伪——收益 0、风险 >0。
- ❌ **不把泛化语料混进语义索引竞答名单**：只进评测集与 LLM 兜底召回池。
- ⚠️ **改动一律走"配置键 + 开关"**，保留 `--scored 0` / `--generic 0` 之类回退位。
- ⚠️ **新增断言必须做变异自证**（把旧写法注回 → 断言须 FAIL）。

### 12.1 子任务实际收到的上下文（实测，非读注释推断）

拦截 `_run_task` 的真实实参得到（探针 `tmp/intent_audit/probe_subtask_ctx.py`）：

```
[任务上下文快照]
- 任务定义：key=t2 / title=生成通信子系统的 IBD 视图
- 期望产出：SysML v2 IBD 代码 + 校验结论

  · t1（分析通信子系统的需求）：功能需求 12 条…（每项 ≤400 字）

    —— 摘要不够判断时，调用工具 tool_result_fetch {"id": 901} 取全文，不要凭摘要猜测上游结论。
- 交付规范：输出需自包含；仅基于给定上下文，禁止虚构；风险/待确认项需显式标注

任务上下文（只读，勿编造上下文外事实）：

SysML v2 IBD 代码 + 校验结论
```

传给 `AgentPipeline.execute` 的实参：`conversation_id=0`、`dry_run=True`、
`forced_intent=<member>`、`skill_name`、`tools_whitelist`、`branch`、`user`。

**合理的设计**（保留）：

| 项 | 为什么合理 |
|---|---|
| 上游交付物**摘要**（≤400 字）+ **offload 全文引用** | 摘要控上下文增长，又给"取全文"的确定性出口。此前摘要硬截 500 字导致丢弃率 60~87%，质量评审据此误报「交付物不完整」（会话 368） |
| **artifact_digest** 会话既有产物 | 子任务 `conversation_id=0` ⇒ `_load_history` 为空，多轮产物只能显式注入（会话 514：第 2 轮子任务把上一轮建好的需求模型当不存在） |
| 交付规范「禁止虚构、风险显式标注」 | 子任务无会话历史可对照，必须靠这句话约束幻觉 |
| `context` 由 planner 逐任务撰写（非复制用户全文） | 上下文隔离，避免每个子任务都背着完整目标膨胀 |
| `tools_whitelist`（Worker ⊆ Supervisor） | 最小权限 |
| `dry_run=True` | 子任务不写 `messages`/`audit`，只由编排层汇总落库（防重复） |

**不合理的设计（本轮已修 3 处）**：

| # | 缺陷 | 后果 | 修复 |
|---|---|---|---|
| 1 | 依赖只取**直接** deps | t1(需求)→t2(设计)→t3(报告) 链上，**t3 完全看不见 t1**（实测 `'R1' in 快照 == False`）。多意图输入最易产生长链，等于把多阶段做废 | `_dep_closure()` 传递闭包（带环形保护）；两处调用点传 `plan`；`plan=None` 时逐字节兼容旧行为 |
| 2 | `branch` 硬编码 `"dev"` | `branch` 用于 `rag.retrieve(query, branch, ...)`——**知识库检索范围**。会话在其它分支时，子任务检索错分支 | `_run_task`/`_planner_core`/`run_planner_plan`/`_try_orchestrate*` 全线加 `branch` 参数并透传；`nodes.py` 取 `cfg.branch` |
| 3 | `user` 未传（恒 `None`） | 子任务无用户上下文（display_name/role），**Skill 角色过滤失效** | 同上，加 `user` 并透传 |

### 12.2 多意图：支持，但此前有 4 处断链（3 处已修）

**处理链路**（实测确认）：

```
用户输入
  → detect()            单意图（主路径，决定"意图识别"那一行显示什么）
  → detect_multi()      两级切分：L1 阶段连词（先…再…/最后）→ L2 并列清单兜底
                        → _finalize_tasks 收口：映射不上意图的丢弃、同一意图去重、<2 个不同意图不算
  → multi_intent 事件   下发给前端
  → _needs_orchestration(multi=...)：multi ≥2 段是**最高优先规则信号**，直接编排
  → stage_hint          拼成 "{意图}（{该阶段原句}）"，注入 planner prompt 约束阶段序与 deps
  → planner 产出 tasks  每任务带 key/deps/context/expected_output/tools/skills
  → DAG 执行 + 汇总
```

**实测切分能力**（`detect_multi`，真实数据）：

| 输入 | 段数 | 结果 |
|---|---|---|
| 提供一段需求，进行需求分析、方案设计、代码校验 | 3 | requirement_analysis → design → review ✓ |
| 先做需求分析，再生成结构视图，最后出一份报告 | 3 | requirement_analysis → design → report_generation ✓ |
| 帮我分析变更影响，然后生成报告 | 2 | impact → report_generation ✓ |
| 生成通信子系统的IBD视图，并完成内容校验 | 2 | design → review ✓ |
| **先生成结构视图，再生成参数视图** | **0** | ✗ 两段都映射成 `design`，被「≥2 个**不同**意图」判据丢弃 |
| **请对工程数据分析，生成IBD视图，要基于知识库规范生成，并完成内容校验** | 3 | ⚠ 误切：`knowledge_qa` 那段（"要基于知识库规范生成"）是 design 的**约束**，不是独立交付阶段 |
| 分析需求并设计架构 | 0 | 靠 `_needs_orchestration` 的 `_agent_combos`（"需求"+"设计"+"并"）兜底触发编排 |

**4 处断链**：

| # | 断链 | 状态 |
|---|---|---|
| 1 | **团队模式判 direct 时多意图被截断**：`team_direct=True` + `forced_intent` 双重短路 `_needs_orchestration` ⇒ 用户写 3 个阶段，只跑 1 个成员。实测：同一请求非团队 → `True`（编排），团队 direct → `False` | **已修**：direct 且 `_multi_stages >= 2` ⇒ 改走主 Agent 编排（不放弃团队模式，而是从"定向单成员"升级为"主 Agent 分派多成员"）。端到端实测：`multi_intent sequence=['design','review']` + 说明「识别到 2 个阶段…已由主 Agent 编排分派」+ 进入 `生成与校验` |
| 2 | **非流式路径没有 stage_hint**：`_try_orchestrate` / `_try_orchestrate_team` → `run_planner_plan` 签名无 stage_hint ⇒ 阶段序约束不进 planner（流式有、非流式无） | **未修**（见 12.3） |
| 3 | **`detect()` 与 `detect_multi()` 不一致**：多意图输入时 `detect()` 返回单一意图（如"需求分析、方案设计、代码校验" → `design@0.9`），而实际走 3 阶段编排 ⇒ 界面上"意图"与"实际执行"对不上 | **未修**（属产品口径问题，见 12.3） |
| 4 | **同意图多阶段被判"非多意图"**：「先生成结构视图，再生成参数视图」→ 0 段。判据要求 ≥2 个**不同**意图，而同为 design 的两阶段是真实的两件事（两个不同视图） | **未修**（判据收紧的历史原因见 12.3） |

### 12.3 未修项及理由（如实交代）

1. **非流式无 stage_hint**：非流式路径用于 Flow 节点/试跑，而多意图的入口是会话（走流式）。
   补它需要给 `run_planner_plan` 再加一个参数并在 4 个调用点透传；收益低于风险（当前生产入口不经过它）。
2. **`detect()` 与 `detect_multi()` 不一致**：修法两种——让 `detect()` 在多意图时返回 `multi`（会影响
   下游所有按单一意图分派的代码），或让前端在 `multi_intent` 事件里覆盖显示（改动小但只是"看起来一致"）。
   这是产品口径决策，未擅自定。
3. **同意图多阶段**：`_finalize_tasks` 要求"≥2 个不同意图"是为了修三类历史错例（「先生成结构视图，再生成参数视图」
   曾产出 `['design','design']` 被当成两个阶段、「先看看再想想」映射失败、宽松映射误判）。
   放开会重现这些错例。正确解法是让判据区分"同意图不同对象"（结构视图 vs 参数视图），需要对象抽取，未做。

### 13.2 ④ 同意图多阶段 —— 尝试后实测净负，默认关闭

**原判断**：「先生成结构视图，再生成参数视图」是两个不同视图、同一 `design`，
按意图去重丢成 0 段 ⇒ 认为是判据错。

**实现**：`_finalize_tasks(allow_same_intent=...)`，仅对 L1（`先…再…/然后/最后`）放开去重，
L2（并列清单）保持去重；开关 `intent.multi_same_intent_stage`。

**实测（`tests/manual_verify/eval_multi_intent.py`，18 条）——判据打脸，为净负**：

| 指标 | 关闭（基线） | 开启 |
|---|---|---|
| accuracy | **0.944** | 0.889 |
| precision | **1.000** | 0.875 |
| recall | 0.875 | 0.875 |
| F1 | **0.933** | 0.875 |
| 阶段序列完全匹配 | **0.875** | 0.750 |

**两个具体副作用**：
1. 「先生成结构视图，再生成参数视图」由 `None` → `['design','design']`（该条标注为「负例·同意图」，
   且**确实含并列标点（逗号）**，标注与分组定义自洽 —— 我先前以为它无标点、属标注缺陷，**这个判断是错的**，已核实纠正）。
2. **连带把「先做需求分析，再进行方案设计，最后生成 sysml 代码」由 2 段拆成 3 段**
   （末段"生成 sysml 代码"与"方案设计"同属 `design`）⇒ 说明「按句切 + 同意图保留」过粗。

**处置**：`intent.multi_same_intent_stage` **默认 False**（回到改动前行为），代码与开关保留。

**为何保留而非删除**：这不是"实现做不到"，而是**产品口径未定**——
"粒度按意图还是按交付物"。单个 `design` Agent 本来就能在一次回答里产出多个视图，
拆成两个同 Agent 任务不增加能力、只增加调度开销与失败面（这是判定净负的主要理由，不只是指标）。
把它留成可 A/B 的开关，比替业务方写死一个方向更合适。
