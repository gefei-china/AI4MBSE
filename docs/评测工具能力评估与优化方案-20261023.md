# 评测工具能力评估与优化方案（2026-10-23）

> 评估对象：`mbse_system` 已实现的评测工具链（截至 2026-10-23 08:15 跑批全绿状态）
> 评估方法：**实地盘点 + 对标行业标杆**（LangSmith / Langfuse / Braintrust / MLflow / W&B Weave 的评测能力分层）
> 结论先行：能力层**已达标**（4 类确定性评测 + 1 层 LLM 语义 + 1 个供料环 + 可见性 + 10 道门禁），
> **短板不在"有没有指标"，而在三处结构性债**：① 评测资产不入库、不可追溯；② 数据模型
> 把"指标"写死成列，每加一个指标要改 8 处；③ 整个体系**不会自动跑**（nightly 未注册计划任务）。
> 框架层面（用户明确问的）：**前后端都不建议换框架**——铁律 4（私有化离线/禁 CDN/禁构建链/禁新依赖）
> 决定了换框架是负收益；真正该做的是**升级评测的数据模型与接口契约**，以及还掉前端手写 HTML 字符串的债。

## 三、框架评估（用户明确问的：前后端框架）

### 3.1 后端：**维持 FastAPI + Pydantic + 裸 sqlite3，不引入 ORM**

| 选项 | 判断 | 理由 |
|---|---|---|
| 现状（FastAPI + 裸 sqlite3） | ✅ **维持** | 只读查询为主 + 少量写入；铁律 4 禁新依赖；ORM 的收益（复杂关系映射、迁移体系）在此用不上，而代价（依赖 + 迁移心智）真实 |
| SQLAlchemy 2.x | ❌ 不建议 | 打破铁律 4；且**真正的问题不是缺 ORM**——是"指标被写死成列"（P0-3），ORM 解决不了这个 |
| Django / Rails 风格全栈框架 | ❌ 否决 | 与现有 60+ 端点、裸 JS 前端、任务队列体系全不兼容，迁移成本以月计 |
| **补 Pydantic response model + 契约门禁** | ✅ **该做** | 现在端点返回裸 dict，前端自己猜形状 ⇒ 字段改名 = 静默错位（P2-3）。OpenAPI 快照进 git + 一道"契约与实现一致"的门禁，是零新依赖的正解 |
| **补评测专用数据模型**（见 O3） | ✅ **该做** | 这是根治 P0-3 的正解，**比换 ORM 重要一个数量级** |

### 3.2 前端：**维持 vanilla JS 无构建链，但重构结构 + 引入微型渲染原语**

| 选项 | 判断 | 理由 |
|---|---|---|
| 现状（48 个 vanilla 模块 + innerHTML 字符串） | ⚠️ **维持栈、还债** | 铁律 4 明禁构建链；48 模块无构建是既有事实，引入框架=推倒重来 |
| Vue 3 / React / Svelte（vendored） | ❌ 不建议 | 破坏铁律 4；48 个模块 + 零构建的既有形态下，框架收益（组件复用/状态管理）远小于迁移与心智成本；且本项目**没有复杂状态**（评测页是"取一次数→渲染"） |
| **引入 ~100 行自研声明式渲染原语** `h(tag, attrs, children)` + 事件委托 | ✅ **该做** | 直接消灭当前最痛的三类隐患：手工 `esc()` 漏转义（XSS/内容错乱）、div 配平靠门禁兜、字符串拼接不可测。零依赖、零构建、可在 Node vm 里单测 |
| 内联 SVG 自绘图表（折线/柱/散点） | ✅ **该做** | 已证明可行（sparkline 零依赖）；不引第三方图表库 |
| 引入 ECharts/Chart.js（vendored） | ❌ 不建议 | 体量大（ECharts ~1 MB）、主题与暗色适配成本、与"只渲染不计算"纪律冲突面大；自绘够用 |

**结论：前后端都不换框架。** 该做的是 ① 后端接口契约化 + 评测数据模型升级；② 前端把"手写 HTML 字符串"换成"声明式渲染原语 + 分层文件"。

## 四、优化方案与路线（每项带验收判据）

### 批 1：可追溯性与自动化（P0，2~3 天）

| # | 方案 | 验收判据 |
|---|---|---|
| **O1** | 注册 nightly 计划任务（每日 03:17）+ 失败通知（digest 非零即发 webhook/邮件） | 计划任务存在且 `NextRunTime` 有效；人为把某个门禁阈值改坏 → 次日有失败通知 |
| **O2** | **评测集版本化**：`datasets/<kind>/<version>/` + `manifest.json`（corpus 指纹、样本 hash、条数、类别分布、构建时间、构建脚本版本）；报告行记 `dataset_id` | 任一历史报告能回答"当时用的是哪个数据集版本"；评测集变更走 PR（可 review 人工标注改动） |
| **O3** | **指标快照表**替代固定列：`eval_metrics(report_id, metric_key, value, direction, gate_key, threshold, status)`；迁移现有 19 行 | 新增一个指标**零迁移、零改 repo/前端映射**（只加一个 fixture 键）；历史趋势任意维度可比 |
| **O4** | 接口契约化：评测端点加 Pydantic response model + OpenAPI 快照进 git + 契约一致性门禁 | 字段改名会被门禁抓住（而不是静默错位） |

### 批 2：判断质量（P1，1~2 周）

| # | 方案 | 验收判据 |
|---|---|---|
| O5 | **A/B 对比进产品**：任意两次报告逐指标差 + 判定（相对上次退化即红） | 报告页能直接回答"这次比上次好在哪、哪条退化了"；门禁支持"相对基线退化"判据 |
| O6 | **统计显著性**：重跑一致性（k 次）+ 置信区间；门禁支持"劣化超过 k 个标准差" | LLM judge 的 ±1/15 波动进报告；门禁不再靠人工留余量 |
| O7 | **真实问题集 + judge 校准集**：从真实会话取"有引用有反馈"的问题，人工标注 50 条做 judge 校准集 | judge 与人类标注的一致率可测（Cohen's κ）；负反馈积累后自动升级为判别力来源 |
| O8 | 导出与通知：CSV/JSON 导出 + nightly 失败 webhook/邮件 + 前端"跑一次"触发（复用现成 job queue） | 结果可被外部消费；用户能在页面上发起一次评测并看到进度 |

| # | 方案 | 验收判据 |
|---|---|---|

## 五、给决策者的三句话

1. **框架不用换**（铁律 4 + 现状适配）：后端维持 FastAPI + 裸 sqlite3，该补的是**接口契约 + 评测数据模型**；前端维持 vanilla JS，该补的是**声明式渲染原语 + 分层**，而不是 Vue/React。
2. **最该马上做的两件**：**O1**（nightly 注册 + 失败通知——不注册的话所有评测都不自动跑）和 **O2/O3**（评测集版本化 + 指标快照表——不做的��历史分数不可比、每加一个指标要改 8 处）。
3. **最容易被误读的一件事**：忠实率 0.6、引用使用率 0.344 这些数字**不是"质量差"的定论**，而是"引用证据支撑度"与"引用被使用的程度"的度量；真正的质量结论需要 O7 的人类标注校准集与 O6 的显著性检验。
