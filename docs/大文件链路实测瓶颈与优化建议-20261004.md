# 大文件链路的实测瓶颈与优化建议（2026-10-04）

> 本文所有数字都是**本机实测**（`tmp/profile_ingest.py` cProfile + `tmp/probe_lock.py` 锁探针
> + 真实 embedding 往返），不是估算。复现命令见文末。
> **结论先行：大文件慢的主因不是"文件大"，而是三个与大文件几乎无关的缺陷** ——
> 其中 P0-1 是真缺陷（长写事务把全库写者堵死），P0-2 是配置事故（embedding 已在静默降级）。

---

## 一、先纠正一个此前的错误归因

评估文档（`docs/架构-可扩展性-稳定性-整体评估与标杆对标-20261003.md`）把大文件入库慢归因为
**"SQLite 单写者被占满，必须停服务"**。本次实测**否定了这个归因**：

| 组成成本 | 实测耗时 | 占比 |
|---|---|---|
| 分块（本地 CPU，400 块） | **0.005 s** | 0.003% |
| 落库（270 行 × 1024 维向量，单事务） | **0.010 s** | 0.006% |
| embedding（270 条，真向量 33 批） | 0.6 s（降级后）/ 约 22 s（正常） | 1%~12% |
| **LLM 摘要（5 次串行调用）** | **15 s（正常网络）~ 176 s（本次）** | **8%~99%** |
| **合计（本次实测）** | **177.1 s** | 100% |

**"必须停服务"从来不是数据量问题，是锁持有时间问题**（见 P0-1）。
单事务写 270 行只要 10ms —— 数据量根本不是瓶颈。

## 二、P0-1（真缺陷）：写事务跨越 LLM 调用，全库写者被堵死

### 实测证据

`cProfile` 对真实入库（143KB / 270 块）：

```
ncalls  tottime  cumtime  函数
   1    0.005    0.005  ingest.py:231(ingest_document)
   1    0.000    0.000  ingest.py:182(_gen_llm_summary)      ← 175.909s
   5    0.000    0.000  ingest.py:201(_ask)
   5    0.000    0.000  llm/__init__.py:209(_record_usage)   ← 161.072s
 332  161.112    0.485  sqlite3.Connection.execute           ← 161.112s（全是等待）
   5    0.000    0.000  httpx.post                            ← 15.0s（真实网络）
```

**关键读法**：`_record_usage` 自身只花 0ms，但里面的 `sqlite3.execute` 累计 **161s**，
而真实的 HTTP 请求只有 15s ⇒ 这 161s **全是在等写锁**。

`tmp/probe_lock.py` 的锁探针（直接验证机制）：

```
基线：270 行单事务（无并发）           = 0.010s
持锁事务时长                            = 6.01s
并发写者：15 次写，>0.2s 的 1 次，最大阻塞 6.07s
⇒ 验证成立：长写事务会把并发的写者全部堵在 busy_timeout 上
```

### 缺陷位置

`knowledge_pipeline/ingest.py:412-447`：`INSERT INTO document_chunks`（270 行）
+ `UPDATE documents SET parse_status='completed'` 之后，**没有 commit**，
直接进入 `_gen_llm_summary(text, filename)`（5 次串行 LLM），最后才 `conn.commit()`。

配合 `core/deps.py` 的 `db_session`（请求结束才 commit）⇒
**整个入库过程是一个跨越全部 LLM 调用的单一写事务**。

### 后果（比"慢"严重）

1. **全库所有写者被堵**：`busy_timeout=30000`（`database.connect_timeout`）⇒
   别的请求/worker 想写就得等 30s，超时即 `database is locked`。
2. **前端进度看起来卡住**：作业进度上报（`job_queue.progress`）、租约心跳
   （`LeaseKeeper`）、LLM token 记账 —— 全都是写操作，全部被堵。
   这解释了实测里 `progress` 长时间停在 5/80 不动。
3. **"必须停服务"是这个缺陷的表象**，不是 SQLite 的固有局限。
   改成"分批提交"后，SQLite 单写者完全撑得住（10ms 一批）。

### 修法（P0）

在 chunks 落库后**立刻 commit**，把 LLM 摘要挪到事务之外：

```python
conn.execute("INSERT INTO document_chunks ...")   # 270 行
conn.execute("UPDATE documents SET parse_status='completed' ...")
conn.commit()                    # ← 补这一行：先落库，先放锁

_summary = _gen_llm_summary(...)  # 5 次 LLM 在锁外跑
if _summary:
    conn.execute("UPDATE documents SET summary=? WHERE id=?", ...)
    conn.commit()                # 摘要单独一次短事务
```

更进一步（大文件建议一并做）：270 行也**分批提交**（每 50 行 commit 一次），
让锁持有时间与文件大小解耦。

**实测收益（已实施）**：**177.1s → 18.4s（9.6x）**，
且 profile 里锁等待归零（剩余 14.6s 全是 SSL 读的真实网络时间）。
配套门禁 `tools/verify/verify_ingest_tx.py`（13 条+ 3 变异，已进 CI）。

⚠️ 顺带修正了一个**语义隐患**：修复前若摘要阶段抛异常，外层 `except` 会
`conn.rollback()`，把**已插入的 270 行 chunks 一起回滚**（虽然`_gen_llm_summary`
内部已try/except 基本不会抛）。改成显式提交后，摘要失败不再连带回滚已落库内容。

## 三、P0-2（配置事故）：embedding 已在静默降级，检索质量已受损

### 实测证据

```
llm_usage_stats rows = 5023
chunk 向量分布：openai-compat 6459 / bigram-tf 810
按入库日期：
    2026-10-04 bigram-tf 810     ← 今天的全部新增都是降级的
    2026-09-29 openai-compat 717
    2026-09-19 openai-compat 5742
```

直接探 API 拿到响应体：

```
HTTP 403
{"error":{"message":"Free quota exhausted. To continue accessing the model on a paid
 basis, please add funds or disable the \"use free tier only\" mode in the management
 console."}}
```

### 这意味着什么

- **810 个 chunk（今天的 4 份文档）用的是 bigram TF 词面向量**，不是语义向量。
  混在同一张检索表里 ⇒ **语义检索被词面匹配污染**（`semantic.py::_rank_dense`
  对这些 chunk 算出的相似度不可比）。
- 更隐蔽的是：熔断只在 `_note_quota_error` 里按 `quota`/`insufficient` 关键字识别
  （`embedder.py:84-94`）。**这次 403 的 body 里有 `quota`，熔断生效了**
  （第二次调用 0.11s 直接跳过）—— 所以没有反复烧额度，这点做对了。
- 但**降级本身没有任何用户可见的提示**。今天入库的文档，
  列表页/详情页都不会告诉用户"这份文档的语义检索已降级"。

### 修法（P0）

① **充值或关闭"仅用免费额度"模式** —— 这是运维动作，不是代码问题。
② **降级必须留痕 + 显式化**：新增 `settings` 开关或复用 `documents.pipeline_detail`
   写 `embed_degraded=true`，文档列表/详情页显示"语义降级"徽章。
   理由与 `config.P1-3降级显式化` 同源：静默降级 = 用户以为有语义检索，实际没有。
③ **混用两种向量必须可检出**：检索侧加一条断言 —— 若结果集里
   `bigram-tf` 占比 > 50%，在返回里带 `degraded=true` 标记。

## 四、P1：大文件本身的三个真实问题

### P1-1 分块大小固定 600 字，与文件规模无关

实测 `chunking_params`：`size=600, overlap=85`（按扩展名分派，无自适应）。

| 文本字符数 | chunk 数 | 平均长度 |
|---|---|---|
| 3,050 | 7 | 436 |
| 12,200 | 25 | 488 |
| 48,800 | 100 | 488 |
| 195,200 | 400 | 488 |

分块成本线性且可忽略（400 块仅 0.005s），所以**分块本身不需要优化**。
但 **chunk 数 = 后续 embedding 批次数 = 检索时的向量矩阵规模**。
195K 字符 → 400 块 → 真向量模式下就是 400 次 API 批调用（50 批 × 0.44s ≈ 22s）。

**建议**：超大文件（>2000 块）改为**两级**：先按章节/section 切成"大段"，
再用检索侧的下采样策略。这属于**可选优化**，当前规模（7269 chunks 全库）不急。

### P1-2 HyDE 在真向量模式下是**第二倍 embedding 成本**

`ingest.py:397-410`：真向量模式下，每 chunk 的 HyDE 问题**也要单独向量化**
（分批 8 条）。这意味着 embedding 成本 ×2。

实测 270 块 → 主向量 33 批 + HyDE 33 批 = 66 批。

**建议**：HyDE 向量化降级到"只为前 N 块生成"（如 N=50）或
"文档级 HyDE"（整篇文档生成一组假设问题，全文共用）。后者更符合
Reverse HyDE 的原论文意图（假设问题是为了缩小查询空间，不是给每个块都造一遍）。

### P1-3 OCR 硬上限 50 页，超出部分静默不处理

`knowledge_pipeline/ocr.py:249-255`：`extract.ocr_max_pages` 默认 50。
超过 50 页的扫描件**只处理前 50 页**，且**没有在 `parse_meta` 里明确标注"只处理了 50 页"**
（`parse_meta.ocr` 有 `pages_ocr` 字段，但前端详情面板不展示它）。

⇒ 用户上传 200 页扫描 PDF，会得到"解析成功"但只有前 50 页被索引，
**且界面完全看不出来**。

**建议**：① 在 `parse_meta` 里显式记 `pages_truncated`；
② 文档详情面板展示"OCR 仅处理前 50 / 200 页"；
③ 超限时给 warning 级 toast，而不是静默。

## 五、P2：可观测性 —— 已加阶段耗时留痕

**已实施**：`_stage()` 现在记录每阶段 `ms`，落进 `pipeline_detail.timing`
（**成功与失败两条路径都写**），并随 `ingest_document` 返回值给出 `timing`。

**真机验证输出**：

```
parse  {status:done,    ms:9}
chunk  {status:done,    ms:528}
embed  {status:failed,  ms:1, error:...配额已耗尽...}
total_ms 542
```

⇒ 下次"这份文档哪一步慢"直接可查，不必再 cProfile 反推。

以下是原始问题背景（保留）：

本次定位"大文件慢在哪"花了不少时间，根因是**入库管道没有任何阶段耗时留痕**：
`documents.pipeline_detail` 只有 `parse/chunk/embed/insert` 的 `done/failed`，
**没有耗时**。

**建议**：`pipeline_detail` 每个 stage 加 `ms` 字段，
入库完成后可直接查"这份文档哪一步最慢"，不必每次都 cProfile。

（本次 cProfile 的结果也印证了这一点：`_stage()` 明明在四个阶段都调了，
但它只写状态不写耗时，于是 profile 里 177s 只能靠逐函数 cumtime 反推。）

## 六、优先级汇总

| 优先级 | 问题 | 实测依据 | 预期收益 | 改动面|
|---|---|---|---|---|
| **P0-1** ✅已修 | 写事务跨越 LLM 调用，堵死全库写者 | `_record_usage` 内 161s 全在等锁；锁探针 6s 事务把并发写者堵 6.07s | **实测 177.1s → 18.4s（9.6x）**，全库不再被堵 | 已改 `ingest.py` + 门禁 |
| **P0-2** | embedding 额度耗尽，静默降级 810 chunk | 403 `Free quota exhausted`；今日 810 chunks 全是 `bigram-tf` | 恢复语义检索质量 | 运维充值 + 降级显式化 |
| **P1-2** | HyDE 使 embedding 成本 ×2 | 270 块 = 33 批主向量 + 33 批 HyDE | embedding 耗时减半 | 降级/文档级 HyDE |
| **P1-3** | OCR 超 50 页静默截断 | `ocr_max_pages=50`，无截断标注 | 消除"静默丢内容" | `ocr.py` + 详情面板 |
| **P2** ✅已修 | 管道无阶段耗时留痕 | `pipeline_detail.timing` 已落库（parse 9ms / chunk 528ms） | 下次排查省 80% 时间 | 已改 `ingest.py` |
| **P1-1** | 分块不自适应 | 400 块仅 0.005s，**不急** | 收益有限 | 暂不动 |

**动手顺序**：P0-1 ✅**已实施并实测 9.6x** → P0-2（运维充值 + 降级显式化，**需米爸决策**）
→ P2 ✅ 已实施 → P1-3 ✅ 已实施（分段 + 断点续跑）→ P1-2（HyDE 降级，可选）。
**P1-1 不要动**，实测证明它不是瓶颈。
