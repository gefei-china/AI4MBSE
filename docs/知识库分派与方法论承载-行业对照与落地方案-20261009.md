## 二、#2 行业怎么做知识库分派（检索自 2026-10 最新资料）

### 2.1 行业共识：先治理，后检索

四份资料表述高度一致，这是**制度性共识**而非某家实现：

> 「RAG 不应让向量相似度直接决定引用版本。应**先按适用组织、业务范围、生效状态、生效时间和替代关系过滤**，再检索正文；无法判定时展示冲突来源并转交负责人确认。」
> —— 聚匠科技《企业知识库存在多份冲突制度时，RAG 应该引用哪一版》

> 「企业 RAG 必须追求**"找得准、用得对、说得稳"**，而不是普通知识库的"找得像"。」
> —— 尧图网络

> 「**Sort on authority and status, not just relevance.** A FAQ may match the question perfectly but may not be authoritative.」
> —— Cygnet《RAG System Design for Trusted Enterprise GenAI》

### 2.2 权威等级的通行划分

资料 2（治理知识库）给的是：**制度 > 标准 > 流程 > 复盘经验 > FAQ**，且「低优先级内容不能覆盖高优先级规则，避免**经验替代制度**」。

映射到 MBSE 场景：

| 权威级 | 内容 | 对应 documents |
|---|---|---|
| L1 标准（不可违背） | OMG SysML v2 / KerML / Requirements | 5472 chunks |
| L2 客户方法论（本项目必须遵守） | 广汽方法论 | 180 chunks |
| L3 客户规范约定 | 视图规范、命名与配色约定 | 52 chunks |
| L4 领域经验 | 热管理/混动/座舱场景知识 | 383 chunks |
| L5 参考资料 | 常见语法错误与修正 | 101 chunks |

**冲突裁决顺序即 L1→L5**。这与本项目现实完全吻合：checker.jar 判 pass 只能说明符合 L1，不说明符合 L2——而这正是当前"语法对、方法论不符"的根因。

### 2.3 三条硬约束

1. **权限/范围过滤必须在检索前**，不能后过滤
   > 「Post-filtering a generated answer is too late: restricted text may already be present in context, logs, caches, or model output.」（Zharf）
2. **每份资料必须带机器可判的治理字段**（不能靠文件名里的"新版"二字）

   | 字段 | 用途 | 缺失时 |
   |---|---|---|
   | `version` / `supersedes` | 替代与废止关系 | 进待治理队列 |
   | `status` | 草稿/待发布/生效/停用 | 草稿与停用不入正式回答 |
   | `effective_from` / `effective_to` | 生效边界 | 时间重叠标为冲突 |
   | `scope` | 组织/产品线/业务域 | 范围不明时向用户追问 |
   | `owner` / `approved_by` | 维护责任 | 无人负责的不上线 |

3. **拒答优于乱答**：「如果证据不足或文档冲突无法裁决，AI 不能为了显得聪明而强行给结论。」

### 2.4 落到本项目的最小改动（不新建体系）

好消息：`kb_scope` 已经是可用的**前置过滤**机制，且本次已验证零泄漏。只需在 `documents` 上补两个维度：

```
authority_rank   INTEGER   -- 1=标准 2=客户方法论 3=客户规范 4=领域经验 5=参考资料
applies_to_stage TEXT      -- 逗号分隔的节点名，如"view_expansion,model_validation_repair"
```

**复用而非新建**：过滤逻辑用现成的 `source_doc` 过滤通道（把 authority/stage 转成 `docs` 白名单即可），不引入新的检索层。

**为什么不做完整 `supersedes` 链**：库里 16 份文档暂无版本冲突实例（都是单一现行版），先把 authority + stage 落地，等真出现"同一主题两版"再补——不预先建设没人用的机制。

## 三、#3 方法论（这里指你的第 3 问：方法论由 skill 承载会不会丢信息）

### 3.1 你的担心是对的，而且比预想更严重

实测那份方法论（`documents.id=812`，180 chunks）：

| 指标 | 实测值 | 含义 |
|---|---|---|
| 总字符 | **101,803** | 一份大文档 |
| chunk 平均长度 | 564 字符（min 340 / max 600） | 机械按长度切 |
| **以标题行开头的 chunk** | **0 / 180** | **章节边界完全不存在** |
| **结尾无终止标点（腰斩）** | **105 / 180（58%）** | 超半数 chunk 句子被截断 |
| 段落数 | **1** | chunk 间无空行，段落结构已丢失 |
| 「禁止/不得/必须/严禁」 | **25 处** | 全文仅 25 条祈使句约束 |
| 层级编号 M0-M3 / IR-VR-SR-SSR-AR | 76 处 | 追溯链骨架清晰 |

**抽样证据（chunk 5）——同一句话连续出现两次：**

> "……由此可见，面向 SysML V2 的 MBSE 架构方法是一种以问题域识别为起点、以方案域逐层设计为主体、以验证确认为闭环的演化式架构方法。**由此可见，面向 SysML V2 的 MBSE 架构方法是一种带有显式反馈回路的演化式架构方法。**架构视角与视图……"

这是 **docx 解析重复 + 机械切分**双重缺陷叠加。

### 3.2 结论：三类内容必须走三条不同的路

**不能用 skill 承载整份方法论，但也不能全靠 RAG。** 行业做法（Anthropic + 检索资料）给的分法是「稳定规则进 prompt/skill，可变资料进知识库」，但对"高权威规范"还要再加一层——**编译成机器可判的检查项**：

| 内容类型 | 实测量 | 承载方式 | 理由 |
|---|---|---|---|
| **祈使句约束**（禁止/必须） | 25 处 | **编译成 `methodology_rules` 规则表 + lint 检查** | 25 条是极小的工作量，却是最该被"每次强制执行"的部分 |
| **结构骨架**（M0-M3 / IR→VR→SR→SSR→AR 追溯链） | 76 处编号 | **写进 skill 正文的必备要素** | 骨架稳定，是"这个视图该有哪些要素" |
| **叙事性论述**（为何这样分域、演进式架构的含义） | 约 10 万字符的绝大部分 | **留在知识库，按需检索** | 检索命中即可，不该每次都占 prompt |

### 3.3 为什么 skill 承载会丢信息（机制层面）

不是"skill 装不下"，而是**注入机制本身在做有损压缩**：

1. **摘要窗口有上限**——本项目实测三轮，从 600 → 1100 → 2600 → 最终改为「按段落优先级挑选」，仍只能覆盖约 30~60%。
2. **frontmatter 重复占窗**——已修（`strip_frontmatter`）。
3. **长篇规范散文挤占注意力**——实测把窗口放大到 26~60% 后，8 个视图里 5 个产出**完全相同**的照抄内容，模型直接放弃生成视图部分。**这是最硬的证据：把长规范塞进上下文，模型会更差。**

所以正解不是"把方法论写进 skill"，而是：

> **方法论 → 拆成「规则表（机器判）+ 骨架要素（模型看）+ 论述（检索取）」三层，
> 每层用各自最合适的载体，不做单一载体硬扛。**

### 3.4 落地建议（按性价比排序，零代码优先）

| 优先 | 动作 | 成本 | 收益 |
|---|---|---|---|
| **P0** | **修 chunk 边界**：按标题/段落切，不按 589 字符机械切；顺带修 docx 重复段落 | 低 | 检索召回质量的根本改善，58% 腰斩率直接归零 |
| **P0** | **抽 25 条祈使句 → `methodology_rules` 表**（`lint`/`check`/`forbid` 三级），接进 N4 | 中 | 把"客户方法论"从"模型自己看着办"变成**可回归的门禁** |
| P1 | `documents` 补 `authority_rank` + `applies_to_stage`，检索前分派 | 中 | 标准/方法论/经验不混池，冲突可裁决 |
| P1 | 追溯链 IR→VR→SR→SSR→AR 写进 N5 skill 必备要素 | 低 | 让 N5 有可检查的产出结构 |
| P2 | chunk 记录补 `section_path`（父标题路径），支持层级检索 | 中 | 检索能还原章节上下文 |
