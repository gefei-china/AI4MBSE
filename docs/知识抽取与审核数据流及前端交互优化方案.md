## 1. 当前数据流梳理（三条并行流水线）

系统知识库构建当前由**三条相互独立的流水线**组成，统一汇聚到 kb-b「标注审核」页：

### 流水线 A：抽取候选（v2g_candidates 表）——"机器抽取 → 人工确认"

```
文档/文本 ──▶ 解析→分块→向量化 ──▶ LLM 抽取（本体 schema 约束）
                                      │ 实体候选（name/type/confidence）
                                      │ 关系候选（A —[type]→ B 三元组）
                                      ▼
                              v2g_candidates(pending)
                                      │  ✅ 确认入库（GraphStore 本体校验）
                    ┌─────────────────┴─────────────────┐
              实体候选 → entities(candidate)       关系候选 → relations(candidate)
                    └─────────────────┬─────────────────┘
                                     ▼ 进入审核环节（见流水线 C / 关系审核缺口）
```

- 前端入口：kb-b「🕘 抽取治理中心」（批次卡 + 多维筛选 + 单条溯源/编辑/确认/驳回）、kb-a 半自动转化面板、文档管道「抽取」列
- **卡点 1**：确认入库生成 candidate 实体，但**关系候选确认后没有独立的批量审核入口**——关系审核只能在 kb-d 图谱页逐条审边

### 流水线 B：实体消歧合并（entity_dup_candidates 表）——"已入库实体的清理"

```
entities 表（所有 status!='deprecated' 的实体，含 candidate 与 reviewed）
        │  名称归一 + 向量相似度检测（detect_and_save_candidates）
        ▼
entity_dup_candidates（keep/dup 对 + 证据 + 三档阈值）
        │  ✅ 确认合并（merge_entities）
        ▼
保留实体吸收属性 + 关联边重指向 + 重复实体 deprecated（软删）→ entity_merges 历史（可回滚）
```

- 前端入口：kb-b「🔀 实体消歧与合并」tab
- **卡点 2（流程位置问题）**：行业标准中**消歧属于"知识融合"阶段，发生在实体入库之前**（抽取候选确认时就应对已有图谱消歧，避免重复实体先入库再清理）；本系统把消歧放在入库后对 entities 全表检测——P0-2「v2g 确认入库增量对齐」正是把这个环节前移的规划（尚未实施）

### 流水线 C：实体关系审核队列（entities 表 status=candidate）——"正式审核"

```
entities(candidate)（来源：v2g 确认 / 手动创建 / SysML 导入 / AI 生成）
        │  ✅ 通过 → reviewed（正式知识库，可被发布消费）
        │  🚫 驳回 → deprecated（软删除留痕）
        ▼
分支合并发布（P0-1 门禁：仅 reviewed 可进 release）→ release 被 AI 建模消费
```

- 前端入口：kb-b「✅ 实体关系审核队列」tab
- **卡点 3（名实不符）**：该队列实际**只审实体**（查询 `entities?status=candidate`），名称却叫"实体关系审核队列"，与关系审核无关，造成理解困惑（用户反馈即源于此）

### 当前数据流总结图

```
                    ┌─ A 抽取候选 ─┐
文档 ──▶ 抽取 ──▶ v2g_candidates ──┼── 确认入库 ──▶ entities(candidate) ──▶ C 实体审核 ──▶ reviewed ──▶ 发布(release) ──▶ AI 消费
                    │              └── 确认入库 ──▶ relations(candidate) ──▶ ❌ 无批量审核入口（缺口）
                    └─ B 消歧（对已入库实体检测，流程位置偏后）
```

## 2. 行业优秀实现方案与流程（对标）

### 2.1 知识图谱构建标准流程（学术与工业共识）

```
数据接入 → 信息抽取(NER/RE/属性) → 知识融合(共指消解·实体对齐·属性对齐) → 知识加工(本体对齐·质量评估) → 存储 → 更新
                                    ↑ HITL 人工验证贯穿：机器生成候选 → 人工审核 → 入库
```

行业关键结论：

1. **抽取永远不是一步到位**：LLM 关系抽取准确率约 75–85%，知识图谱期望 95%+ 精度 → 必须 HITL（Human-in-the-loop），机器负责吞吐、人工负责质量。
2. **知识融合（消歧）在入库前**：抽取候选 → 与已有图谱对齐（同名/同义/相似）→ 消歧决策 → 才入库。防止"先入库一堆重复、再清理"。
3. **Provenance（溯源）是底线**：每个三元组携带 来源文档 / 模型版本 / 审核人 / 审核时间 / 置信度，错误可追溯撤回。
4. **置信度分级 + 阈值快审**：高置信（≥0.85）走快审通道批量过，低置信人工重点核。
5. **关系与实体同级治理**：三元组是知识的最小单元，关系审核与实体审核处于同一治理层级（Neo4j 数据治理 / GraphRAG 构建均对"边"有独立的验证与规范化环节）。

### 2.2 行业前端交互模式（审核工作台）

| 产品/方案 | 模式 | 可借鉴点 |
|---|---|---|
| 阿里云 Dataphin 候选治理 | 任务/批次化 + 候选多维筛选 + 消歧三态 + 单条溯源/编辑 | 治理中心范式（已落地） |
| 质检工作台（行业通用） | **默认聚焦待办**，已通过/历史分区只读；待办计数徽章；批量+单条结合 | 审核队列待办优先（已落地） |
| Label Studio / Argilla | schema 驱动单条聚焦式标注界面，状态流转清晰 | 单条审核聚焦视图 |
| 数据血缘/资产治理台 | 全链路状态可视化（采集→加工→校验→发布），一眼看到卡在哪一环 | **全链路进度视图（本方案重点）** |

### 2.3 对本系统的适用结论

- 主链路（抽取→确认→入库→溯源）已完整且治理体验达行业水准（P0~P3 落地）。
- 真正缺的是**流程完整性与一致性**：① 关系候选缺批量审核入口；② 消歧流程位置偏后（未在入库前对齐）；③ 审核队列名实不符；④ 无全链路状态可视化视图。

## 3. 目标数据流设计（对齐行业流程）

```
┌─ 知识获取 ───────────────────────────────────────────────────────────┐
│ 文档/文本/SysML/AI生成 ──▶ 抽取（本体约束）──▶ v2g_candidates（实体+关系） │
│                                        │                             │
│                                        ▼                             │
│                    ① 入库前消歧对齐（新：确认时对已有图谱打标三态）            │
│                    keep / 合并 / 跳过 / 新建                          │
│                                        ▼                             │
│                    ② 确认入库（本体校验 + chunk 溯源）                   │
│              实体→entities(candidate)  关系→relations(candidate)     │
└────────────────────────────────────────┬──────────────────────────────┘
                                          ▼
┌─ 知识审核（HITL 质检）────────────────────────────────────────────────┐
│  ③ 实体审核队列（entities candidate）  ④ 关系审核队列（relations candidate，新增） │
│     批量快审(高置信) + 单条审核(低置信)       批量+单条，两端实体需已入库           │
│     ✅ reviewed / 🚫 deprecated          ✅ reviewed / 🚫 deprecated     │
└────────────────────────────────────────┬──────────────────────────────┘
                                          ▼
┌─ 知识发布与消费 ─────────────────────────────────────────────────────┐
│  ⑤ 分支合并发布（P0-1 门禁：仅 reviewed 可进 release）──▶ release 权威基线     │
│  ⑥ AI 建模消费（GraphRAG/向量，默认只读 release）+ 反馈回流（P2-13 扩展）       │
└──────────────────────────────────────────────────────────────────────┘
```

**相比当前的核心改进**：
- **消歧前移**（①）：确认入库即对已有 reviewed 实体做同名/相似度匹配 → 提供 跳过/新建/对齐 决策（P0-2，规划中），使"知识融合"发生在入库前，与行业一致。
- **关系审核补全**（④）：relations(candidate) 独立审核队列，与实体同级治理（行业：三元组最小治理单元）。
- **全链路可视化**：实体从 候选 → 确认 → candidate → reviewed → published 的状态进度（P0-4 已提供 published 维度，需前端聚合呈现）。

## 4. 前端交互逻辑设计（kb-b 标注审核 → 知识治理工作台）

### 4.1 页面结构（保持现有 panel/ph/pb、tag、table.t、右侧 #modal、居中 #lbx 风格）

```
标注审核（kb-b）
├─ ① 待办台（顶部，新增）：4 个队列待审数徽章 + 一键直达
│    [🕘 抽取候选 N] [🔀 消歧待审 N] [✅ 实体审核 N] [🔗 关系审核 N（新增）] [🔄 全部刷新]
├─ ② 🕘 抽取治理中心（现状保留）
├─ ③ 🔀 实体消歧与合并（现状保留；P0-2 落地后候选确认时联动提示"已与 ENT-XX 疑似重复"）
├─ ④ ✅ 实体审核队列（现状保留，更名"实体审核"）
├─ ⑤ 🔗 关系审核队列（新增 tab）：relations candidate 列表
│    A —[type]→ B · 两端实体名 · 来源文档 · 置信度 · 状态
│    批量快审（高置信建议通过）+ 单条通过/驳回/修正 + 📋 详情（来源+两端实体）
└─ （可选）⑥ 📈 全链路状态：抽取→确认→审核→发布 各环节计数条（消费 /api/knowledge/lifecycle）
```

### 4.2 关键交互逻辑

1. **待办台**：进页默认展示各队列待审计数（并行拉取），点击直达对应 tab（对齐工作台 .todo-item 风格）。解决"数据在哪、该去哪处理"的首要认知问题。
2. **关系审核队列**（新增，对齐实体审核范式）：
   - 列表：`A —[关系]→ B` 三元组 + 两端实体状态（未入库标黄警示）+ 来源文档 + 置信度 + 审核状态
   - 操作：批量通过/驳回（高置信阈值建议）、单条通过/驳回（confirmDialog）、修正（改关系类型，置回 candidate 重审）、📋 详情（源 chunk + 两端实体）
   - 复用后端已有接口：`POST /api/knowledge/graph/edges/{eid}/review`、`PUT /api/knowledge/graph/edges/{eid}`；需补充列表查询接口（见 §5）
3. **实体审核队列更名**：tab 标题由「实体关系审核队列」→「实体审核队列」，消除名实不符；关系审核由新 tab 承接。
4. **消歧联动提示**（P0-2 落地后）：抽取治理中心确认候选时，若候选与已有实体同名/疑似重复 → 确认弹窗（#lbx）展示匹配清单与动作选择（跳过/新建/对齐），对齐行业"入库前融合"。
5. **全链路进度条**：kb-b 顶部或 kb-a 生命周期面板展示 抽取→确认→审核→发布 各环节数量，点击任一环直达对应 tab——让用户一眼看到"数据流走到哪了、卡在哪"。

## 7. 验收标准

1. 关系候选确认入库后，在 kb-b「关系审核队列」可见并可批量/单条审核；审核后状态与图谱边状态联动（reviewed/deprecated）。
2. 「实体审核队列」tab 名称与实际内容一致（仅审实体）。
3. v2g 确认候选时对已有实体提示消歧三态并提供 跳过/新建/对齐 动作（P0-C 落地后）。
4. kb-b 顶部待办台展示各队列待审计数，点击直达；全链路状态条一眼可见数据流进度。
5. 回归：抽取治理中心 P0~P3、实体审核、消歧合并、P0-1 门禁、P0-4 生命周期均无回归。
