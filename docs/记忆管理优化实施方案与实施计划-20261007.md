## 2. ⚠️ 量化推翻了我上一轮的两个判断（先说清，避免按错误前提实施）

### 2.1 「"合并"从未实现」—— **说错了，`consolidate()` 已实现**

`memory_service.py:399` 有完整的 `consolidate()`：同`(agent_id, mem_type, scope_type, scope_id)`
内做真向量/bigram 余弦比对，超过阈值（0.85 / bigram 降级 0.5）就**保留较新、旧的标记 forgotten**
—— 已经是文章路线 4 的 **UPDATE 语义**（软式）。

**但它仍不解决冲突消解**，区别是本质的：

| | `consolidate()` 处理的 | 冲突消解要处理的 |
|---|---|---|
| 语义关系 | **高度相似**（余弦 ≥0.85） | **互斥**（"vc 格式 A" vs "vc 格式 B"） |
| 判据 | 相似度高 → 是重复 | 相似度**低**但**同键** → 是冲突 |
| 实测id 133/134/135 | 讲同一个追溯链、措辞近似 → **会被合并** ✓ |互斥事实 → **余弦低、永不触发** ✗ |

⇒ **D1 的准确定位**：不是"没做合并"，是**合并只覆盖重复、不覆盖冲突**。
这个区别很重要——它意味着 D1 是**新增一条正交通道**，不是重写既有逻辑，风险因此小得多。

### 2.2 「写入有三重门」—— **只对 LLM 路径生效，规则路径有漏**

`_extract_worthy()`（:541）三重门确实存在且质量不错，但：
- `maybe_deposit()` :649/:661/:723 **三条调用点都走它** ⇒ 这部分是好的
- ⚠️ 但 `reflow` 路径（agent_id=34 条）灌的是图谱实体 → 说明**还有一条不经过三重门的写入通道**
- 证据：库里仍有 `（来源 test-reg）` 实体 ⇒ **要么清理回滚了，要么写入源未堵**

⇒ **D7 必须先查清 reflow 写入路径是否过 `_extract_worthy`**，否则堵不住。

### D2 + D3 · 跨用户隔离（**同批交付**）

**问题**：`scope_type` 支持 `user` 但**全代码零使用**；`memory_admin.py` 的
`list`/`export` **无 `current_user`** ⇒ 任何登录用户可导出全库记忆。

⚠️ 但注意：**检索侧已有 user 槽，因写入侧从不产 user 行，该槽恒空**
⇒ 这正是"能力在、语义永不生效"（技能 §7.3-1d）。光有槽位没有任何隔离效果。

**D2-a 写入侧**：`deposit()` 已有 `scope_type`/`scope_id` 参数（`memory_service.py:241`），
`maybe_deposit()` 亦有（:608）⇒ **服务层大概率无需改，改调用方传参即可**。

⚠️ **实测发现 4 个生产沉淀调用点，作用域传参不一致**（这是 D2-a 的真正工作量）：

| # | 落点 | 现状 | 动作 |
|---|---|---|---|
| 1 | `agent/pipeline_parts/memory.py:326` | ✅ 已传 `scope_type`/`scope_id`/`user_scope` | 只需确认 user 槽取值正确 |
| 2 | `memory_service.py:656/663`（LLM 提炼路径） | 内部自调用，**透传外层参数** | 检查 `maybe_deposit` 是否把 user_scope 传下来 |

其中 #4 是真缺口（工作流路径产出记忆但无作用域，隔离做不完整）。

**D2-b管理端点过滤**：
- `list` / `export` 加 `user=Depends(current_user)`；
- 规则：**admin 角色看全量，普通用户只看`scope_type='user' AND scope_id=<自己>` + 公共槽位**
- ⚠️ 过滤**必须在服务端按已认证身份算**，不能信前端传的 `scope_id` 参数

**D2-c 存量 69 条空 `scope_type` 行怎么办**（决策点）：

| 选项 | 做法 | 影响 |
|---|---|---|
| **C-1 不迁移（推荐）** | 保持 `scope_type=''`，靠 `_scope_filter` 既有兜底（`memory_service.py:82`：空 scope 行按 agent 槽召回） | **零风险**；实测兜底路径已存在且在用；代价是这 69 条对所有用户可见（但内容是领域知识非隐私） |
| C-2 回填成 `global` | UPDATE 成 `scope_type='global'` | 语义更准，但动了 69 行数据；若 `_scope_filter` 有 bug 会一次丢 69 条召回 |

### D1 · 冲突消解（**依赖 D2**）

**定位（已修正）**：`consolidate()` 覆盖"重复"，D1 补的是**"冲突"**，两者正交。

**方案 A（推荐）：影子状态 + 召回期仲裁**

| 维度 | 方案 A | 方案 B：直接 UPDATE |
|---|---|---|
| 改动面 | 加 2 列 + 新增检测函数 + 召回期仲裁 | 改 `deposit()` UPDATE 旧行 |
| 可回滚 | ✅ **删列即回滚，旧数据零损** | ❌ 旧记忆被覆盖后**不可逆**（文章反方："错误更新→不可逆污染"） |
| 误判代价 | 两条同时召回，模型看到矛盾 | **错的那条被静默改掉**，更危险 |
| 实现复杂度 | 中 | 低 |
| 需审查的 SQL | **0 处** | 每处UPDATE 都要审查是否有别的读者依赖旧值 |
| 结论 | ✅ **推荐** | ❌ 除非确认"记忆即事实、错一条就该删" |

> ⚠️ 选 A 的核心理由：**冲突消解本身就是"判断谁对谁错"，而判断会错。**
> 直接 UPDATE = 让错误判断**不可逆**；影子法= 让错误判断**只是暂时把旧记忆排到召回后面**，可观察、可回退。
> 这与本工程其他设计的取舍一致（如 `entities` 主键宁可不改也不造双写）。

**方案 A 的三个组成部分**：

1. **A-1 影子列**（迁移，`database/migrations/columns.py`）
   - `superseded_by INTEGER DEFAULT 0`（被哪条取代，0=未取代）
   - `superseded_at TEXT DEFAULT ''`
   - ⚠️ **索引必须建在补列之后**（10-07 实测踩过：建表处建索引 → `no such column` → init_db 挂）

2. **A-2 冲突检测**（新函数 `MemoryService.detect_conflicts()`）
   - 触发条件（三者同时满足，缺一则不判）：
     ① 同 `mem_topic`（或同 `scope_type+scope_id+mem_type`）
     ② 语义相似度**低**（big ram < 0.3）⇒ 不是重复，是不同说法
     ③ LLM 抽取断言：新旧内容是否**互斥**（"是/否"、"旧/新"、"之前/现在"）
   - ⚠️ **③ 要过 LLM** ⇒ 有成本和延迟。缓解：仅当 ①② 满足才调（判据从稀到贵）
   - ⚠️ **不实现 NOOP 判定**：本仓无"重复提问"场景，收益低

3. **A-3 召回期仲裁**（`agent/memory_recall.py`）
   - 同一 `mem_topic` 命中多条且被标为冲突时：**只取最新一条**，其余不进 prompt
   - ⚠️ 注意：这是**召回层**处理，**不改库**⇒零风险、可随时关

**PoC 步骤（S1–S6）**：

| 步 | 做什么 | 通过判据 |
|---|---|---|
| S1 | 造互斥夹具：2 条同 topic、语义低相似、内容互斥的记忆 | `detect_conflicts` 返回 1 组 |
| S2 | 造**不**互斥的对照组（同 topic 但语义相近/互补） | 返回 0 组（**防误判**，这是本项最大风险） |
