## 1. 现状盘点（改动前）

代码坐标（改动前口径）：

| 能力 | 位置 | 形态 |
|---|---|---|
| 列表 | `27-branch.js::renderBranchMergeTable` → `#merge-list` | 一张表，6 列 |
| 对比分析 | `openMergeDiffDrawer()` → `#mrg-drawer`（`index.html` 尾部） | 右侧滑动抽屉 + 遮罩 `#mrg-mask` |
| 详情渲染 | `loadMergeDetail / loadMergeDiff / renderMergeDiff / mrgFocusEntity / loadMergeConflicts` | 全部写入抽屉内的 `#mrg-body` / `#mrg-field` / `#mrg-progress` |
| 冲突解决 | `renderConflictItem`（未变）+ `resolveConflict` | 渲染在 `#mrg-field` 右栏 |
| 评审意见 | `toggleMrComments` | 列表行内展开（`<tr>` 插入） |
| 合并预览 | `previewMerge` → 居中卡片 `#lbx` | 弹窗 |

问题归纳（3 条，都能在代码里指出）：

1. **把页面装进抽屉**：`#mrg-drawer` 内部结构是 `d-head + #mrg-progress + (210px 左清单 | 右字段详情) + 底操作条`——这本身就是一套完整的「头部/工具条/双栏/底部操作」页面骨架。塞进受限宽度的抽屉后，字段级 diff（`字段 base → head` 三列）被压到最窄，而右侧大片区域是遮罩。
2. **主流程被打断**：`openMergeDiffDrawer` 打开时必须先关掉列表（遮罩挡住），评审人无法「边看队列边比对」；对比 → 解决冲突 → 回到列表 → 再通过，是一次跨 3 步的来回。
3. **同一动作两套入口**：列表页有「通过/驳回」，抽屉底部也有「✅ 通过合并 / ❌ 驳回」，且抽屉里禁用态与列表页禁用态是两套独立渲染逻辑（`#mrg-approve` vs 列表行内 `approveDisabled`）。

## 2. 标杆调研

### 2.1 GitHub PR 新版「Files changed」（最接近的直接对标）

- 2026-01-22 起新版设为默认体验（`github.blog/changelog/2026-01-22`）：左**可调宽文件树**（带「有评论 / 有错误 / 有警告」标记）+ 右 diff 主区；顶部进度条显示「已查看文件数」；支持 split / unified 切换；大 PR 走虚拟化。
- 2026-03-19 起新增 **Docked panels**（`github.blog/changelog/2026-03-19`）：把 **Overview / Comments / Merge status / Alerts** 四类上下文做成**评审页内常驻侧栏**，官方措辞是「stay in flow without switching tabs or losing your place」。
- 列表页（PR 列表）**不提供** merge 按钮 —— 合并动作只在 PR 详情页完成。

**取值**：左清单 + 右主区的双栏骨架；筛选/搜索在清单头部；就绪度（Merge status）从"另一个页面"搬进评审页；合并动作唯一入口。

### 2.2 GitLab MR「Changes」

- 页签结构：Overview / Commits / **Changes** / Pipelines。Changes 页内用**文件树浏览器**（F 快捷键，Tree view / List view 切换）+ diff 主体。
- **冲突直接标注在 diff 里**（`display_merge_conflicts_in_diff`，15.8 起 GA），而不是另开一个冲突页面。
- 提供「单文件模式」（Prev/Next）与 side-by-side / inline 偏好。
- 文件头有 `Viewed` 勾选、`Expand file`（大文件折叠）、「Collapse generated files」降噪。

**取值**：冲突**就在变更视图里**出现，而不是独立窗口；大变更集要有降噪与筛选。

### 2.3 Palantir Foundry Ontology 提案 / Global Branching（**本项目的同构案例**）

这是"知识图谱/本体变更评审"这一品类里最贴近的标杆，且**刚做过与本次诉求完全相同的改造**：

- 2026-09-17 上线 **Changes tab**（`palantir.com/docs/foundry/announcements`）：
  > Previously, reviewers could only view changed resources in the proposal Overview tab and **needed to open each resource's application to review changes separately**. Reviewing proposals that span multiple resources required moving between applications, making it more difficult to understand how related changes fit together.
  > The Changes tab lets reviewers **view how modified resources changed directly from the proposal page**. Select a resource to view its changes, checks, and approval status.
- 提案页结构：**Proposal overview / Preview status / Review changes / Changelog**（四页签）。
- 每个本体资源（object type / property / …）= 一个 **task**，带审批状态标签；支持**单个资源批准/拒绝 + 批量**；右侧 **Comments sidebar** 常驻；`Review changes` 页内可邀请评审人、看审批策略。
- 冲突处理：rebase 时列出冲突，必须逐条解决后才能 `Finish rebase` 再合并；文档明确列出"选择保留分支修改会导致合并失败的已知限制"。

**取值**：①「变更必须在提案页内集中呈现」——这就是用户这次的原话；② 页签化分区（概览 / 变更 / 冲突 / 记录）；③ 冲突未清零则阻塞合并，且阻塞原因要在页面上说清。

### 2.4 metaphactory（知识图谱治理工作流）

- 本体生命周期状态机：`In development → In review → Ready to be published → Published → Archived`；进入 review 时**锁定不可编辑**，评审人在同页留评论。
- 强调 **ontology provenance**（谁在何时改了哪个 class / attribute / relation 可追溯）。

**取值**：状态机 + 评审记录 + 变更可追溯（本项目已有 `merge_requests.status` 状态机与 `comments` 时间线，本次把它呈现到页面上）。

### 2.5 调研结论（三条）

1. **"评审行为的上下文"应当与"评审主体"同屏**，这是 GitHub（docked panels）、GitLab（冲突标在 diff）、Palantir（Changes tab）三家在 2025–2026 的**共同方向**；滑动抽屉/跨应用跳转是被明确淘汰的形态。
2. **列表与详情分离**：列表负责"找与排序"，详情负责"看与判定"；合并动作收敛到详情页唯一入口。
3. **"能不能合"要显式成清单**（merge status / checks），而不是靠用户自己数冲突。

## 3. 设计方案

### 3.1 视图模型：列表 ↔ 详情同页切换（零弹层）

```
知识图谱 → 合并请求 Tab
├── #mr-list-view  列表视图（工具条 + 状态筛选 + 表格；整行可点进入详情）
└── #mr-detail-view 详情视图（头部 / 概要 / 六分区 / 底部操作条）
```
- 两个视图互斥 `display`，无遮罩、无滑出层；`#ws-mr` 改为 `overflow:hidden`，由各分区自己滚动。
- `Esc` 返回列表（焦点在输入控件时不抢 Esc）。
- 兼容别名保留：`openMergeDiffDrawer(mrId)` → `openMrDetail(mrId,'diff')`。

### 3.2 详情页布局

```
┌ ← 返回列表 │ 🔀 personal → dev #171 │ [🕐待评审]        │  📨转评审  🗑删除 ┐   ① 头部
├ personal→dev ｜ ＋0 ✎0 －61 ｜ 0/0/0关系 ｜ 👤李工·时间 ｜ 🧑⚖️评审人 ｜ ⚠1/2已解决 ┤ ② 概要条
├ 📋概览与检查   🔍变更对比   ⚠冲突处理 1待处理   🕸叠加图谱   💬评审意见   🕘变更记录      ┤ ③ 页签
├──────────────┬──────────────────────────────────────────────┬──────────────┤
│ 差异清单(300) │  字段级详情（主区）                            │  （按页签内容）│ ④ 主体
│ 筛选 chips    │  实体头 + 字段 base→head + 就地冲突解决卡        │              │
│ 搜索框        │                                              │              │
├──────────────┴──────────────────────────────────────────────┴──────────────┤
│ ⚠ 阻塞原因/可合并提示                              🔮预览  ↩回滚  ❌驳回  ✅通过合并 │ ⑤ 底部操作条
```

**六个页签的职责**

| 页签 | 内容 | 对标 |
|---|---|---|
| 📋 概览与检查 | **合并就绪度检查清单**（变更内容 / 冲突解决 / 评审状态 / 目标分支 / 风险提示）+ 差异分布（按实体类型）+ 就地合并结果预览 | GitHub Merge status、Palantir proposal checks |
| 🔍 变更对比 | 左清单（全部/＋/✎/－/⚠ 筛选 + 搜索 + 冲突与高风险置顶）↔ 右字段级详情（含就地冲突解决卡） | GitHub Files changed、GitLab Changes |
| ⚠ 冲突处理 | 进度条（已解决/总数）+ 逐条裁决卡（属性冲突三选一 / 删除-修改冲突二选一） | GitLab 冲突标在 diff、Palantir 逐 task 评审 |
| 🕸 叠加图谱 | 差异着色图谱（新增/修改/移除/冲突 + 1-hop 灰显上下文），与清单双向定位 | 本体/图谱类产品特有（本次**新增能力**） |
| 💬 评审意见 | 评审时间线（通过/驳回/裁决/评论）+ 追加意见 | GitHub PR conversation、metaphactory 评论 |
| 🕘 变更记录 | 源分支提交历史（按日期分组 + 变更摘要 + 相对时间） | Palantir Changelog |

### 3.3 关键交互取舍

1. **默认聚焦 = 清单第一条**（WYSIWYG）。清单按「冲突置顶 → 风险分降序」排序，主区默认打开同一条，避免"清单第一条和主区显示的不是同一个实体"。（首版实现里两者口径不一致，实测发现后修正。）
2. **搜索不重建工具条**：`#mr-list-slot` / `#mrd-diff-list` 与工具条/搜索框分离，`oninput` 只重刷列表容器 —— 否则每敲一个字就丢输入焦点。（已用 `document.activeElement === kw` 断言）
3. **列表页保留快捷「通过/驳回」**（不倒退既有便利性），但**详情页底部为权威入口**，带阻塞原因说明与按钮禁用联动。
4. **容器型 pane 不可被整片清空**：`mrd-pane-diff` / `mrd-pane-graph` 内部有子容器，清空其 `innerHTML` 会删掉子容器导致该页签永久空白（首版踩过，已加静态哨兵 + 变异自证）。
5. **回溯全在页面内**：`conflict_changed`（评审期间目标分支被更新）引导后直接落在「冲突处理」页签，而非再弹抽屉。

## 6. 已知局限 / 后续可做

1. **差异清单未做虚拟化**：61 条无压力，万级变更集需要像 GitHub 那样加"大 PR 实验模式"（虚拟滚动）。
2. **未做"单文件模式"**（GitLab 的 Prev/Next）：大变更集逐条评审时有用。
3. **未做资源级批准**（Palantir 的 per-task approve/reject）：本项目冲突是字段级，若将来要支持"逐实体批准"，需要后端增字段。
4. **「变更记录」为只读摘要**：行内字段级快照展开仍只在「🕘 历史」Tab（避免 `#cd-<id>` 元素 id 跨页签冲突）。
5. ~~`#lbx` 居中卡片仍用于列表页的「🔮 合并结果预览」~~ —— **§7 已删除**：左栏卡片不再承载按钮，`previewMerge`（居中卡片版）随表格一并退场，预览能力统一由详情页底部条的 `previewMergeInline`（页面内嵌展开）承载。

### 7.1 布局设计

```
#ws-mr  (height: calc(100vh - 245px); overflow: hidden)
└── #mr-split                     display:flex; flex-direction:row
    ├── #mr-list-view             宽 344px（min-width:344px）· 常驻
    │   ├── 工具条                 标题 + 计数 + 刷新 / 搜索框（整行）
    │   ├── #mr-filter-slot        状态 chips（全部/待评审/草稿/已合并/已关闭）
    │   └── #mr-list-slot          卡片列表（flex:1; overflow-y:auto）← 只有这里滚动
    └── #mr-detail-view           flex:1（实测 1010px）· 常驻
        ├── #mrd-empty            未选中时的空态（"从左侧选择一条合并请求查看详情"）
        └── #mrd-main             选中后显示：头部 / 概要条 / 六页签 / 六分区 / 底部操作条
```

标杆依据（与诉求一的调研同源，此处是"列表与详情的关系"这一维度）：

- **GitHub PR 列表页**：左边就是一张**纯列表**，没有行内操作按钮；所有动作都在 PR 页内。
  → 本页左栏卡片据此**不放置任何按钮**，只保留两类点击：点卡片=选中、点冲突徽标=直达「⚠ 冲突处理」。
- **Palantir Foundry 提案页**：左提案列表 + 右提案详情**常驻主从**，不切页。
- 与 §2 的三条结论一致：**"不切页、不丢上下文"是这类评审工作台的主流形态**，整页互斥属于把上下文扔掉。

**信息取舍（左栏卡片承载什么）**：状态徽章 + 冲突徽章（`⚠ 已解决/总数`，可点跳转）+ 源→目标 + 标题（截断）+ 时间/提交人 + `#id`；
原来表格里的「合并结果」列（如"迁入 3 / 更新 2"）**不再进卡片**——它属于明细，放「📋 概览与检查」里看，卡片只负责"扫一眼找出要评审的那条"。

### 7.2 连带的死代码清理

左栏不放操作按钮后，原表格操作列里两个实现**失去唯一调用点**。按工程「**有可达后继才删**」纪律逐个核对后删除：

### 7.3 顺手修掉的一处一致性缺陷（截图复核发现）

夹具复原后，左栏已不含被夹具造出来的那条 MR，**右栏却还在显示它的详情** = 伪状态。
真机触发路径：查看某条详情时切换工作分支（或该条被他人删除）→ 列表刷新后选中项已不在列表里。
修法（`loadMerges()` 内 3 行守卫）：拿到合法数组且其中不含当前选中项时，**收起右栏回空态**。

```js
if(mrgMrId && Array.isArray(_mrs) && !_mrs.some(m=>m.id === mrgMrId)) closeMrDetail();
```

仅在拿到合法数组时判定（接口异常返回非数组时不动），避免网络抖动误收起。
