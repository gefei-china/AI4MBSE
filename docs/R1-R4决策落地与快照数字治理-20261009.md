## 二、R1 · 移除 Mock 降级

### 改了什么

`llm/__init__.py` 新增异常类 `LLMUnavailableError`，把**三处**静默降级改为抛错：

| # | 位置（实测方法名） | 原行为 | 现行为 |
|---|---|---|---|
| ① | `chat()` 无 api_key | 回落 Mock，返回"（Mock 回答）…" | 抛 `LLMUnavailableError(reason="no_api_key")` |
| ② | `chat()` 真实调用失败 | 回落 Mock | 抛 `LLMUnavailableError(reason="call_failed")`，**自动识别 402并给出充值提示** |
| ③ | `_stream_wrapped()` 流式失败 | 只记日志，前端收到**正常结束的空气流** | 抛 `LLMUnavailableError(reason="stream_failed")` |

### ★ 为什么抛异常而不是返回错误字典

调用链有 `execute` / `execute_stream` / 编排子任务 多层。返回错误字典**极易被某一层当成正常结果继续处理**——那正是原缺陷的成因。抛异常则默认不被吞；真正需要容错的层必须显式 `except`。

⚠️ 已验证**没有任何地方吞掉它**（门禁 A3 用 AST 检查）。

### ★ 必须区分的一件事：`llm.force_mock` **保留**

| | 含义 |
|---|---|
| `llm.force_mock=True` | **显式要求** Mock（回归测试不依赖外部网络）⇒ 保留 |
| 本次移除的 | **没要求 Mock 却悄悄给了 Mock** |

删掉 `force_mock` 会让回归测试依赖外部网络，那是倒退。

### 实测验证（2026-10-09，余额恰好耗尽=天然 402 测试条件）

```
[OK] 无 api_key → 抛 LLMUnavailableError (reason=no_api_key)
[OK] 真实调用失败 → 抛 LLMUnavailableError (reason=call_failed)
    错误文案 = LLM 调用失败，本次未生成任何内容。（检测到额度/余额不足：请充值，
              或临时把 embedding/LLM 的仅用免费额度开关关闭）原因：ValueError: LLM API 402...
```

### 门禁 `tools/verify/verify_no_mock_fallback.py`（8 断言）

| 判据 | 内容 |
|---|---|
| A1 | `self.mock.chat(` 只允许出现在 `force_mock` 分支（AST 验证，限行距） |
| A2 | 三处降级点都 `raise LLMUnavailableError` + 全文件 raise 计数 ≥3 |
| A3 | 没有 `except LLMUnavailableError: pass` 之类的吞异常写法 |
| A4 | `force_mock` 开关仍在（保留能力 ≠ 保留缺陷） |
| A5 | 端到端：无 key 时抛异常且异常文案不含 Mock 占位文本 |

⚠️ **判据自己也踩了一次**：首版找 `chat_stream` 方法，源码里根本不存在（真实是 `_stream_wrapped`）⇒ 假红。**按猜的名字写判据会漏掉真正的降级点**，已改为以源码实测为准 + 加"全文件 raise 计数"反向兜底。

### ★★ 顺带查出并修掉一个真实配置错误

日志里出现这条：

```
[context_window] 估算输入 + max_tokens 超过 context_window｜provider=ds-v4-neibu
  context_window=128000 max_tokens生效=128000 估算输入=27 输入余量=1024 guard=clamp
```

**输入余量只剩 1024** —— 因为 `max_tokens` 被配得和 `context_window` 一样大。

实测阶梯加压（严格区分 402 与上下文超限，两者都是 4xx，混淆会得出完全错误结论）：

| 输入字数 | qwen3.8-max | ds-v4-neibu |
|---|---|---|
| 4000 → 64000 | ✅ | ✅ |
| **100000** | ✅ | ✅ |

⇒ **库里原配的 `cw=8192` 是误配**（保守默认值没被实测校准）。
而 `openai_compat.py` 里`if mt > cw: mt = cw` 会把它当**硬上限**
⇒ 长 prompt（skill 正文 + 骨架 + 检索结果）会被**静默截断**，
现象是"模型好像没看完材料就产出退化"——与本项目此前追查的退化现象高度相似。

**已校准**（`tools/migrate_v24_native_toolcall_providers.py`，带备份 + 回读校验）：

| id | context_window | max_tokens | tags |
|---|---|---|---|
| 103 / 104 / 107 | 8192 → **128000** | 8192 → **32768** | 加 `native_tool_calling` / `unstable_tool_calling` |

校准后截断告警消失。

### ⚠️ 本轮自踩两处，都值得记

1. **`tags` 是 JSON 数组不是逗号字符串**。库里实测值 `'[]'`、`'["vision"]'`。
   首版按逗号拼会写成 `'["vision"],native_tool_calling'` ⇒ **破坏 JSON 格式**。
   ⇒ 已改为走 `json.loads/dumps`。
2. **迁移脚本写完必须回读校验**。首版 SQL 与参数都"看起来对"，但 `max_tokens`
   实际被写成了 `context_window` 的值（128000），而脚本自己报"✅ 已更新"。
   ⇒ 加了"写完回读 DB，不一致就回滚"，正是靠它第二轮才发现 103/104 被写坏并修正。
   （MEMORY：「备份/产出成功 ≠ 结果可用」，这次是**写库成功 ≠ 写对了**。）

## 四、R3 · 新建 Pipeline：理由 / 影响 / 收益（全部实测）

### 先说结论

**不需要改成每请求新建。** 现在的"入口清零 + 门禁守住"是**低成本等价方案**。

### 实测数据

| 指标 | 实测值 |
|---|---|
`AgentPipeline()` 构造 | **0.001 ms/次**（`__init__` 只建 5 个轻量对象） |
`_load_db_agents()` | **≈ 25 ms/次**（每次请求都跑，**第二次并不更快 ⇒ 没有缓存白拿**） |
`reset_request_state()` | < 0.001 ms/次 |
`_ensure_sysml_from_tools` 残留态下 · 新建实例 | 不泄漏 ✅ |
`_ensure_sysml_from_tools` 残留态下 · 复用+清零 | 不泄漏 ✅ |

⚠️ 另注：首次构造曾测到 **19.28 ms**，那是一次性的 import/语义预热，不是稳态成本。

### 收益对比

| 维度 | 每请求新建 Pipeline | 入口清零（现状） |
|---|---|---|
| 隔离性质 | **架构级保证**（新实例天然干净） | **纪律级保证**（靠人记得调，且有门禁 AST 兜底） |
| 稳态成本 | +25 ms/请求（`_load_db_agents` 随之重建） | ≈ 0 |
| 改动面 | 需改 `routers/conversations.py` 等所有入口 | 已完成，3 个文件 |
| 并发安全 | 天然隔离 | 共享实例 + 并发请求仍可能互相踩（**清零解决不了并发**） |
| 可控性 | registry/prewarm 缓存全部失效，可能影响性能 | 保留缓存 |

### ★ 最关键的一条（容易被忽略）

**清零只解决"顺序执行"，解决不了"并发"。**

`routers/conversations.py` 是 FastAPI 同步路由。若同一进程并发处理多个请求
（多用户 / 多标签页），两个请求会**同时**写同一个 `self`：
- 请求A 执行到一半写入 `_sysml_last_pass_code`
- 请求B 的入口`reset_request_state` 把它清成 None
- 请求A 收尾取回时拿到 None ⇒ 本次产出丢失

⇒ **这不是"要不要新建"的取舍，而是"要不要支持并发"的问题。**
若产品形态确定单用户/单会话串行使用，清零足够；若要支持并发，必须新建或引入锁。

### 建议

| 场景 | 建议 |
|---|---|
| 现状（单用户建模为主） | **维持清零**，不必改。已加门禁，成本≈0 |
| 要支持多用户并发 | 改每请求新建，或给 Pipeline 加请求级锁（`threading.Lock`包住整个执行） |
| 想两全 | 保留清零（防御纵深）+ 新建（并发安全），成本 25 ms 相对 3~60 s 的 LLM 调用可忽略 |

## 五、R4 · 排查「同 key 不同初始状态静默跑旧状态」

### 背景（LangGraph 官方警告）

同一个 `thread_id` 传不同 `initial_state` **不会**重置线程，已保存状态优先、input 被忽略。

### 排查结果：**当前不存在该风险**（有证据）

| 载体 | 默认状态 | 库中存量 | 是否可能复用旧状态 |
|---|---|---|---|
| `semantic_cache`（语义缓存） | `enabled: False` | **0 行** | ❌ 不可能 |
| `intent_cache`（意图缓存） | `cache_enabled: False` | **0 行** | ❌ 不可能 |
| 记忆治理 `memory` | 活跃 | 有数据 | ✅ key 含 project + user 维度 |

记忆作用域是分层槽位：`project → user → agent → global`，key 由
`_resolve_mem_project_id(conversation_id)` + `_memory_user_key(user)` 构成
⇒ **不同项目/用户不会互相命中**，不存在"同 key 不同初始状态"。

### 顺带确认：意图缓存的设计是对的

`agent/intent.py` 里缓存指纹 `_index_fingerprint()` 由
「DB 关键词 + 语义索引文本摘要 + 规则内容」三部分 md5 组成，
且有注释记录了两次真实踩坑（explain 前置、规则 epoch）：
**缓存变更时自动失效**。这个设计正确，无需改动。

### 但有两个应记录的注意事项

1. `agent/intent.py:441` 注释指出：`intent_cache` 默认关闭的依据是
   "真库 messages 近 7 天仅 18 条用户消息、重复率 22% ⇒ 潜在命中约 17 次/月"，
   而 `intent_detect` 的 1605 次/7 天 >95% 是**评测脚本**刷的。
   ⇒ **若将来开启，需先剔除评测流量再评估收益。**

2. `set_semantic_index()` 里的 `prewarm` 有指纹守卫 ⇒ 向量不会重复计算。
   这解释了为什么 `_load_db_agents` 第二次并不快多少：**它确实每次重跑**，
   只是预热被守卫生效了。

## 六、附 · 「快照数字过期」是什么意思

### 定义

门禁（判据脚本）里把某次实测的**具体数值**写死成断言，例如：

```python
check("ERROR == 47",   base["n_error"]   == 47)
check("n_syntax == 33", base["n_syntax"] == 33)
check("WARN == 48",    base["n_warn"]    == 48)
```

这四个数字是**写它那天**、对**当时那批样例文件**跑出来的结果。

### 为什么必然会失效

它测的对象是 `sysml_models/ev_thermal_mgmt/*.sysml` —— 而**修这些样例文件的语法错误，正是这个目录存在的本来目的**。

本轮实测对照：

| 指标 | 快照写的 | 实际实测 | 说明 |
|---|---|---|---|
| ERROR | 47 | **20** | 样例已修 |
| n_syntax | 33 | **2** | 语法错几乎全修完 |
| n_semantic | 14 | **18** | 有变化 |
| WARN | 48 | **15** | 变化很大 |

⇒ 快照早就失效了，门禁却一直报红。

### ★ 为什么这是**判据的错**，不是代码的错

红的原因是「**断言方式错了**」，不是「校验器退化了」。
这两者必须分清——否则会出现两种坏结果：
- 误以为校验器坏了 → 去查代码，浪费大量时间
- 为了让门禁变绿而**改断言迁就当前数据** → 门禁从此失去保护作用

这与 MEMORY 里「清单里的数字只是写它那天的快照」是同一族问题，
只不过这次快照不在文档里，而在**判据代码里**。

### ★ 正确处理方式（本轮已实施）

分两层，把"会过期的数字"从判据里赶出去：

**① 不变量层（永真，样例怎么改都该成立）** —— 这才是"校验器行为正确"的真判据：

```python
check("n_hard == 词法 + 语法（定义自洽）", base["n_hard"] == base["n_lexical"] + base["n_syntax"])
check("三路计数自洽：lexical + syntax + semantic == error", ...)
check("verdict == block（n_hard > 0 时必为 block）", ...)
check("每条 ERROR 都带三路归属", ...)
```

**② 基线文件层（可复现、可更新、强制留痕）**：

新增 `tools/verify/sysml_check_baseline.json`：

```json
{
  "counts": { "n_error": 20, "n_syntax": 2, ... },
  "note": "2026-10-09 治理快照过期：样例已被修复（实测 ERROR 47→20…）…",
  "at": "2026-10-09 14:29:58"
}
```

更新基线**必须写原因**，否则脚本拒绝执行：

```bash
python tools/verify/verify_sysml_check_gate.py --update-baseline --baseline-note "<为什么变>"
```

未带 `--baseline-note` 时脚本直接报错并计入失败 ⇒ **禁止生成无解释的快照**。

**③ 另一处同类问题**：`v1 风格 refines 归类到语法路`原本是在**样例目录**的诊断里找
`refines`。样例修好后那条错已不存在 ⇒ 判据随样例修复而失效。
改为**条件式**判据（样例里有就检查分类，没有就说明状态），
真正的分类规则由 `[2]` 段的构造用例 `CASE_V1_REFINES` 独立验证。

### 结果

```
改造前：95/100 通过（5 项因快照失效判红）
改造后：96/96 通过（全部绿）
```

★ 顺带把 MEMORY 的一条纪律用上了：
**基线必须由判据自己跑一次得出，不凭印象填**——这里的基线就是脚本当场 `--update-baseline` 生成的。

## 附录· 执行中发现并修掉的两个额外问题

### A1· `verify_agent_loop_protocol` 从 40s 变成 >5 分钟且永不结束

**现象**：本轮回归时该门禁超时。日志里同一 `fp=d3202d0c` 的
「候选缓存未命中」重复上百行。

**根因**：`semantic.py::_embed_candidates` 里
`if version != "bigram-tf"` 才写 `_CAND_CACHE`
⇒ embedding 额度耗尽 → 走 bigram 降级 → **永不缓存**
⇒ 每个请求都重新向量化一遍候选集，并打一行日志。
（"降级不缓存"这个决策本身**正确**——降级向量进缓存没有意义。）

**修法**：**不改那个正确决策**，只加失败退避。
`_DEGRADED_BACKOFF{key: (ts, vecs, version)}` + 冷却 30s，
冷却期内直接复用降级结果。

**实测效果**：门禁日志 206 行 → **93 行**；重复"未命中"上百次 → **7 次**。

⚠️ **修法本身踩了两个坑，都值得记**：

1. **退避判断写在 `embed_with_version` 之后 ⇒ 完全没省掉开销**
   （向量化已经发生了，退避只拦住后面的日志）。
   ⚠️ 探针若只看"日志行数变少"会**误判为已生效**——
   必须统计 **Embedder 被调用次数**。
2. **写了 `fp` 但函数里的变量名是 `key`** ⇒ `NameError`，
   是探针（只 mock Embedder、不 mock 被测函数）抓出来的。

最终探针结果：`连续调用 8 次 → Embedder 实际被调用 1 次`。

### A2 · `verify_agent_loop_protocol` 的 G8~G11 是**判据过期**（非本轮回归）

`git stash` 对照显示：基线 88/0 全绿，本轮改动后 4 项红。
逐项查证后确认根因是**上一轮未提交的改动**：
`finalize_messages` 已加`extra_context` 参数
⇒ 实际调用变成 `finalize_messages(messages, extra_context=_extra)`
⇒ 而判据锁死字面量 `finalize_messages(messages)`。

**生产代码是对的，判据过期** ⇒ 按纪律**改判据**：
① 匹配去掉右括号，接受带参数形态；

★ 这也说明 **`git stash` 归因有边界**：
它回到 HEAD，而 HEAD 不含"上一轮未提交的改动" ⇒
stash 前后都绿并不代表"问题不存在"，只代表"与 HEAD 的差异无关"。
最终定位靠的是**逐项查证实际代码形态**，不是 stash 的绿灯。
