## 0. 结论先行

**链路是完整的，四环节都有实现且都有真实数据在跑；但不是闭环——有 5 处断点，其中 2 处会让治理视图与实际事实不符。**

| 环节 | 实现 | 数据现状 | 判定 |
|---|---|---|---|
| ① 注册 | 三张源表 + `capability_registry` 统一投影（P0-a） | 205 行：tool 44 / skill 31 / mcp_server 2 / plugin 127 / prompt 1 | ✅ 通，有校验缺口 |
| ② 绑定 | `agent_tools`（UNIQUE + INSERT OR IGNORE） | 163 条 enabled，**孤儿 0 条** | ⚠️ 通，但**不是消费的必要条件** |
| ③ 消费 | `tool_call_logs` 三处写入点 | 2,233 行（近 7 天 671），成功率 85.9% | ✅ 通，多入口旁路 |
| ④ 追溯 | `capability_id` → `capability_registry` 度量聚合 | capability_id 匹配率 **99.9%**，call_count 与实算**完全一致** | ⚠️ 通，任务级断链 + 无界面 |

**最值得先修的 3 件**（按影响面排序）：

1. **绑定与消费脱钩** —— 消费有 3 条入口（绑定 / 技能白名单 / 无条件注入），`file_read` 绑定 0 次却调用 25 次。治理视图说"未绑定"，能力却在实际使用 ⇒ **界面结论与事实相反**。
2. **`capability_registry` 没有 API/UI** —— 统一注册处建好了、度量也准，但只在告警循环与周报里被读，**能力中心界面看不到它**。等于"有账本没账本柜"。
3. **任务级追溯断裂** —— `run_id` 仅 23.8% 非零（主对话路径从不赋值 `_tool_run_ctx`），且与 `llm_usage_stats.trace_id` 是两套 id，**无法回答"这一轮对话花了多少钱调了哪些能力"**。

## 1. 文章框架（评估坐标）

文章给出的是**功能分层 + 治理维度**，不是"注册→绑定→消费→追溯"的链路模型：

```
Skills（方法层：一类任务怎么做）
   ↓ 指导
Tools（执行层：一个动作怎么执行）
   ↓ 通过
MCP（连接层：外部能力怎么标准接入）
   ↓ 由
Agent 运行时（协调层）+ Workflow/状态机（确定性约束）
```

治理四维（第 08 章），是我用来逐项对照的检查表：

| 治理维度 | 文章要求 |
|---|---|
| 工具权限边界 | 最小权限、限制可查范围、写操作独立授权、敏感操作审批、记录调用者与结果状态 |
| MCP 服务治理 | 并发/超时/错误明确/分页限流；"统一了协议，不解决分布式问题" |
| Skills 版本管理与测试 | 知道哪个版本改了什么、输出差异、受影响用例；固定测试集 |
| **可观测性（7 项必记日志）** | 任务关联 ID / Skill 及版本 / 模型选择的工具 / 调用参数摘要 / 耗时与状态 / 错误类型与重试 / 结果引用的数据来源 |

文章 09 章的**选型决策表**也构成一条判据：每种机制只解决自己那层的问题，不该互相替代。

## 3. 逐环节实测

### 3.1 注册：通，覆盖完整，但校验不均

| 能力类型 | 源表 | registry 投影 | 一致性 |
|---|---|---|---|
| tool | 44 | **44** | 100% |
| skill | 31 | **31** | 100% |
| mcp_server | 2 | **2** | 100% |
| plugin | 127 | 127 | — |
| prompt | 1 | 1 | — |

**校验强度不一致**（这是可以通过"注册关口"低成本补齐的）：

| 类型 | 校验项 | 缺口 |
|---|---|---|
| tool | 非空、`^[a-zA-Z0-9_-]{1,64}$`、重名 409、内置名保留、side_effect 白名单 | **description / input_schema 均非必填** ⇒ 可注册"无名之器"，模型无从判断何时用 |
| skill | 仅重名 | **无 name 格式校验**；**不解析 frontmatter**（仅 ZIP 上传路径解析） |
| mcp | 仅 name/endpoint 必填 | **无重名校验**（绑定按 name 软引用 ⇒ 重名歧义） |

**数据一致性缺口**：5 个技能 `enabled=1` 但 `status='draft'`。而全局技能池准入是
`status='published' AND enabled=1`（`skills.py:35`）⇒ 这 5 个**开不了却也不报错**。

**MCP 工具级投影缺失**：`capability_registry` 里 `mcp:{server}:{tool}` = **0 行**。
代码注释称"实测 mcp_servers.capabilities 无工具名清单 ⇒ 不展开、不造假"——这条成立，
但**真正的数据源 `tool_meta` 也是空的**（见下方 P0-0）。

**MCP 状态投影**：SQL 映射逻辑**本身正确**（`enabled=1 AND status='online' → active`），
问题是**状态变更后没有刷新**——

```
registry updated_at = 02:20:20   ← 启动时 reconcile
源 last_check       = 02:20:27   ← 健康巡检随后把 AI4MBSE 置为 online
⇒ registry 停在 disabled，直到下一次重启才纠正
```

`mcp_health.py` 里**没有** `capability_registry` / `refresh_registry_row` 调用
（全仓 grep 为空）⇒ MCP 上下线只影响源表，不影响统一注册处。**

### 3.1b ★ P0-0：`tool_meta` 回填是**死代码**（上一轮自己引入的）

`tool_meta` 列的实际存储值是 **`"[]"`（2 字符）**，不是空字符串：

```
AI4MBSE 领域能力（内置 MCP 供给）   tool_meta = '[]'
zhiyuan-dev-mcp                  tool_meta = '[]'
```

而 2026-10-26 加的机会式回填，判断条件写的是：

```python
if (ok and not (srv.get("tool_meta") or "").strip() ...):
```

求值验证：

| `tool_meta` 实值 | `not ("...").strip()` | 结果 |
|---|---|---|
| `''` / `None` / `'  '` | `True` | 触发 |
| **`'[]'`** | **`False`** | **永不触发** |
| `'[{"name":"x"}]'` | `False` | 正确（已有数据） |

⇒ **该条件在"无工具"与"有工具"两种真实取值下都为假，回填从未执行过。**
证据链闭合：`last_discover` 仍停在 `2026-09-24`（AI4MBSE）/ `2026-10-16`（zhiyuan），
37 天内没有任何一次 discover。

**这是"看起来生效实际空转"的教科书案例**：代码在、门禁绿（门禁只断言源码里有该字符串）、
日志无报错（因为分支根本没进），而功能实际是 0。**与它要防的那个问题完全同构。**

修法（1 行）：判空改为解析后判断工具数为 0，而不是判字符串非空。

```python
try:
    _has_meta = bool(json.loads(srv.get("tool_meta") or "[]"))
except Exception:
    _has_meta = False
if ok and not _has_meta and <冷却未到>:
    ...
```

**连带影响**：MCP 工具级投影（P1-1）**依赖这个数据**，所以顺序必须是「先修回填 → 再补投影」。

### 3.2 绑定：通，孤儿为 0，但不是消费的必要条件

| 指标 | 实测 |
|---|---|
| `agent_tools` enabled | **163** 条 |
| 孤儿绑定（指向不存在的 tool/skill/mcp） | **0 / 0 / 0** ✅ |
| 绑到 offline MCP | 4 条（设计允许，UI 会标灰） |
| 绑到"未发布"技能 | **3 条**（`MBSE_Requirement_Clarification` / `MBSE_Requirements_Analysis_Workflow` / `Requirement_Analysis_Pre-check`） |

**制度性矛盾**：绑定 API 对所有 `tool_type` 施加 `check_tool_name`（`^[a-zA-Z0-9_-]{1,64}$`），
但库里有 **6 个中文名技能**（`变更影响分析` / `文件操作` / `报告生成` / `智源平台管理` /
`SysML v2 校验与修复` / `覆盖性分析`）。⇒ 这些技能**无法经 API 绑定**，却存在于绑定表中
（说明走了旁路：种子/迁移脚本，或早期版本未校验）。规则与数据已经不一致。

**删除不级联**：删 skill / mcp_server 不清理 `agent_tools`（删 tool 有 409 拦截）。
当前孤儿为 0，是历史清理脚本（`cleanup_dead_capabilities.py`）跑过的结果，**不是机制保证**。

### 3.3 消费：通，但"绑定"解释不了"消费"

| 指标 | 实测 |
|---|---|
| `tool_call_logs` | **2,233** 行（2026-09-11 ~ 10-26），近 7 天 **671** |
| 构成 | `call_kind`: tool 1,762 / skill 471 ｜ `tool_type`: builtin 1,588 / http 94 / mcp 80 / skill 471 |
| 成功率 | **85.9%**（失败分类：internal 34 / permission 4 / business 4） |
| 延迟 | 均 **1,927 ms**（2 条脏值 > 1 天，占 0.09%） |
| 工具覆盖 | 消费过 **43** / 注册 44 |
| 技能覆盖 | 触发过 **28** / 可消费（published+enabled）**24** |

**★ 关键断点：绑定不是消费的必要条件。**

```
tool:file_read   注册 ✅   绑定 ⚠️ 0 个 Agent   消费 ✅ 25 次
```

原因：`file_read` 被 3 个技能（文件操作 / 行业调研 / 报告生成）的 `allowed_tools` 声明
⇒ 走白名单直接放行，不经过 `agent_tools`。

**这带来的治理后果**：从"能力中心界面"看 `file_read` 未绑定 ⇒ 像"没人用"，
实际它是被大量调用的基础能力。**能力中心的绑定视图与实际消费事实不符**，
而这正是"治理视图"最不该出错的地方。

反过来，`web_search` 绑了 1 个 Agent 但 0 次调用——这类"绑了不用"是正常冗余，
与上面的"用了没绑"性质完全不同，需要区分。

**8 个「消费了但不在 tools 表」的名字**（说明注册表不是消费的唯一来源）：
- MCP 工具 5 个：`export_sysml_v2` / `query_branches` / `query_data_tree` / `query_model_versions` / `query_projects`（在 `mcp_servers.tools` JSON 里）
- 运行时注入 3 个：`ask_user` / `read_attachment_section` / `tool_result_fetch`

### 3.4 追溯：能力级准，任务级断

**做得好的部分**（这块是真实资产，不该被低估）：

```
capability_id 匹配 registry：1,554 / 1,555 = 99.9%
call_count 对拍：graph_retrieve 442=442 / sysml_v2_validate 159=159
                 sysml_stdlib_meta 124=124 / skill:99 95=95 / skill:70 87=87
```

度量口径是**只读聚合、不双写**（避开 `skills.use_stats` 的读-改-写丢更新），这一条设计纪律是对的。

**断点**：

| 问题 | 实测 | 后果 |
|---|---|---|
| `run_id` 仅 23.8% 非零 | 1,702/2,233 为 0 | 主对话路径从不赋值 `_tool_run_ctx`（只有 `stream.py:831` 给子 Agent 赋）⇒ **主对话的工具调用无法归到任何编排批次** |
| 与 `llm_usage_stats.trace_id` 不同体系 | run_id 全为 integer，trace_id 为 text | **无法 JOIN** ⇒ 答不了"这一轮对话花了多少钱、调了哪些能力" |
| 会话级关联仅部分可用 | `conversation_id>0` 占 53.1%（1,186），其中可关联 llm_usage **923（77.8%）** | 约一半调用连会话都挂不上 |
| `task_key` 非空率 | 23.8% | 同 run_id |
| `capability_id` 非空率 | 69.6% | 30% 的调用进不了能力度量 |
| `user_name` 非空率 | 60.6% | 40% 无法归到人 |
| **无 API / 无 UI** | `routers/` 里 0 处引用 `capability_registry` | 统一账本只有告警循环和周报在读，**能力中心界面看不到** |

## 5. 与文章的差距总结

文章的分层判断在本仓**落地得比较到位**：Tools/MCP/Skills 三层都有独立实现，且
Skills 做到了渐进式披露（`offload_body` + `skill_body_fetch`），MCP 做到了 Host/Client/Server
三角色 + 工具发现，这与文章 06 章的"渐进式加载"和 03 章的三角色高度一致。

差距集中在**文章第 08 章治理**，且不是"没做"，是"做了但没有出口"：

| 文章治理要求 | 本仓状态 |
|---|---|
| 最小权限 / 写操作独立授权 | ✅ `side_effect` 白名单 + `allowed_tools` 白名单 + 技能白名单（还额外做了 MCP 豁免修正） |
| 敏感操作审批 | ✅ 有 HIL / `_orch_subtask` 写请求暂存机制 |
| MCP 服务治理（超时/限流/错误） | ⚠️ 有健康巡检 + tool_meta，未见过超时/限流 |
| **可观测性 7 项** | ⚠️ 5 项齐、2 项缺（版本、数据来源），且**填充率不足** |
| **"出了问题能够查清原因"** | ❌ 这正是 P0-3：任务级追溯断裂 + 无界面 |

文章结尾那句"一个知道该做什么、能够调用正确的能力、按照规则完成任务，

### 10.3 ★ run_id 归正（请求 3：是什么 / 影响与风险 / 系统彻底优化）

**是什么**：`run_id` 是"一轮对话的编排批次号"，由 `TaskQueue.new_run_id` 分配；此前只在 `_stream_orchestrated_flow`（编排路径）赋值。单 Agent 直行走 `run()`，从不赋值 `self._tool_run_ctx` ⇒ `_log_tool_call` 读到的 `run_id` 恒 0。原 §8.4 把此记为"设计如此"，**本轮判定为系统性缺陷**。

**影响与风险**：
- 单 Agent 直行占主对话绝大部分流量，其工具/技能调用 `run_id` 恒 0 ⇒ 任何按 run 归批的看板/统计**漏掉绝大部分流量**，产出误导性空图；
- `run_id` 与 `trace_id` 是两套体系，且主路径 `run_id` 不可用 ⇒ "按轮归批 + 成本归因"不可达，`tool_call_logs` 与 `llm_usage_stats` 只能靠 `trace_id` JOIN，run 维度断链。

## 12. 会话 9629「已取回并写入产物，产物库却是空的」+ 技能越界触发归因（2026-10-27）

用户两问：① 最新一轮提示已取回、写入产物，但产物库是空的；② 「智源对接agent」只绑了一个技能「文件操作」，为什么别的技能/agent 会被触发，「白名单」到底怎么回事。

### 12.1 问题①：真因是**响应被静默截断**，不是"归档代码没跑"

**事实（会话 9629 末轮，msg 4876）**
- 助手自述：「全文 80,543 字节，已按偏移量分三段读取并拼接完整，读取到第三段 `eof=true`……**平台已自动识别并存入产物库**，请到产物面板查看」。
- 实际：`SELECT COUNT(*) FROM artifacts WHERE conversation_id=9629` = **0**；按 `message_id=4876` 查也是 0；磁盘上**没有**该文件。**"已存入产物库"是模型的虚构陈述。**

**真因链（每一环都有实测）**

| # | 环节 | 事实 |
|---|---|---|
| 1 | `core/config.py` `mcp.max_response` | 默认 **4000** 字符 |
| 2 | `mcp_client.py :: call_tool` | `raw[:max_response]` **无标记硬截** |
| 3 | 智源 `export_sysml_v2` READ | 单段信封 32,767 字节（`{fileName,content,eof,sizeBytes,nextOffset,...}`） |
| 4 | 实测该次调用返回 | 长度**恰好 4000**、尾部断在 `...private import Parts::*;\n priv`，`json.loads` 报 **Unterminated string @ char 242** |
| 5 | `agent/utils.py :: extract_sysml_doc_from_result` | 依赖 `json.loads` 成功 ⇒ 返回 **None** |
| 6 | `_tool_sysml_docs` | 空 ⇒ `_archive_artifacts(tool_docs=[])` **一条不写** |
| 7 | 可见性 | `truncated` 标志比的是 `_TOOL_RESULT_CAP=6000` ⇒ **恒 False**，没人看得见被截 |

决定性实验（不经 LLM）：`tools/verify/probe_mcp_truncation.py` —— 直连真实 MCP 调同一个 READ，返回 4000 字符、`json.loads` 失败、归档判据 `None`。

**叠加缺陷②：分页读取被当整份文件**
该 READ 是分页协议（offset 0 / 32767 / 65534，`eof` 只在末段为真）。旧判据只看"本段 `eof`"，⇒ 即使不截断，也会把**15KB 尾巴**当成"整份 80KB"归档（比不归档更坏：产物库里出现"看起来完整"的残缺文件）。

**修法（四段，均有门禁）**
1. `core/config.py`：`mcp.max_response` 4000 → **200000**，并明确它是**内存安全上限**，与"给模型看的长度"（`_TOOL_MODEL_CAP=3000` + offload 引用块）职责分离。4000 的错不在"小"，在**它替模型侧做了截断，还把结构化载荷切碎**。
2. `mcp_client.py :: call_tool`：回传 `truncated` / `full_len` —— **截断必须可观测**，不再静默丢数据。
3. `agent/utils.py`：新增 `accumulate_paged_doc()`（按 `offset`/`bytesRead` 串成无缝链、`eof` 且无缺口才出全文）+ `collect_tool_sysml_doc()` 统一入口；`extract_sysml_doc_from_result` 对**带非零 offset 的段一律不单独归档**。
4. `stream.py` / `execute.py` 两路径同构改调统一入口，新增 `_tool_doc_pages` 累积状态（并登记进 `reset_request_state`，防单例跨轮串味）。

**真实链路验证（conv 9633，`team=智源对接agent`）**
- 模型真实调 3 次 READ（tool_call_logs 4537-4539）；
- 落库产物：`id=1500, kind=code, title=广汽方法论建模1022_master_v1_20261027044121.sysml, content_len=56991`；
- 拼接字符 56,991 → UTF-8 **80,543 字节**，与信封 `sizeBytes` **完全一致**；首行 `package '广汽方法论建模1022' {`、末行 `}` 收口正常。

> 附带发现（未改，建议立项）：`save_artifact` 工具（"把代码/文档全文保存为会话产物"）在本轮**已在工具集里**（「文件操作」命中即注入），模型却从未调用，而是宣称"平台已自动识别"。**只要自动归档失败，模型没有任何证据就敢宣布已归档** —— 这是"自述与事实不符"的独立问题。

### 12.2 问题②：`agent_tools` 的技能绑定**不是白名单**

读 `agent/pipeline_parts/skills.py :: _build_skill_prompt`：

```python
bound  = self.registry.get_bound_skills(intent)                      # 绑定技能
extra  = [s for s in self._global_skill_pool(user)                    # 全库已发布+启用！
          if s["name"] not in bound_names]
candidates = list(bound) + extra                                     # 绑定 ⊕ 全局池
```

`_global_skill_pool` 的 SQL 就是 `SELECT * FROM skills WHERE status='published' AND enabled=1`（外加插件侧 skill/bundle）。因此**「绑定」只是"优先候选 + 展示元数据"，不是准入限制**；命中后注入正文，并打标 `（全局匹配·未绑定 Agent，建议绑定）`。

**实测证据（conv 9633，该 agent 只绑了「文件操作」）**

| 技能 | 是否绑定 | status/enabled | 本轮是否注入 |
|---|---|---|---|
| 文件操作 | ✅ | published / 1 | ✅ |
| sysml_view_generation_activity | ❌ | published / 1 | ✅（被语义匹配捞进来） |
| 智源平台管理 | ❌ | published / 1 | 9629 中注入过 |
| SysML v2 校验与修复 | ❌ | published / 1 | 9629 中注入过 |
| com.zhiyuan.legacy.skill.file-ops（插件侧） | ❌ | 插件启用 | ✅ |

匹配三级：triggers 关键词 → bigram 语义（阈值 0.15）→ LLM 兜底重排。**当前 embedding 服务 404、降级 bigram**，阈值停在 0.15 ⇒ 误命中概率显著上升（`sysml_view_generation_activity` 的 triggers 是 activity/活动视图/活动图/action，与"读导出文件"毫无关系）。

**系统里真正叫"白名单"的是另一个东西（且方向相反）**
- `_tool_whitelist`（委派最小权限）：**限制**本次能调哪些工具，主会话直行路径通常为 `None`（不限制）。
- `skill.allowed_tools`（技能声明的工具集）：语义是**授权补充** —— 命中后把 `file_*`、`save_artifact` **补进候选**（`tools.py:371-386`），**不是**"撤销其它工具"。所以它既不拦技能，也不拦工具。

**可观测性缺陷（重要）**
`memory.py :: _record_skill_feedback` 把「本轮**注入**的技能」逐条写成 `tool_call_logs.call_kind='skill'`，`result` 填的是**最终答案**。实测 conv 9633 三条 skill 行（file-ops / sysml_view_generation_activity / 文件操作）`result` **完全相同且等于最终答案（1923 字符）**。
⇒ 看板/日志会把"注入了 3 个技能"显示成"调用了 3 个技能、且都产出了同一份结果"，技能效果归因彻底失真（9629 里 report-gen / 报告生成"被调用"同此）。
