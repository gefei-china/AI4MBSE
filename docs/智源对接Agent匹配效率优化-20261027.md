## 三、D1 寻址前置链闭包（代码改动）

### 3.1 根因

平台有**坐标三元组** `projectId` / `branchId` / `versionId`：
真库 71 个 MCP 工具里 **65 个**都要它（以寻址对象 `workspace` / `version` 传入），
而产出它们的是三个**逐级依赖**的查询工具：查工程 → 查分支 → 查版本。

`pick_for_injection` 的打分是「query token ∩ (工具名 + 描述) token，按 token 长度加权」：
工具名是英文、中文请求几乎不相交 ⇒ **写类请求一个坐标工具都选不中**；
而 `core_keep` 里的 `_bound_mcp_names` 只是**已选出的集合**，**救不回被裁掉的工具**。

### 3.2 规则（结构推导，与平台无关，**零硬编码工具名**）

1. **坐标轴**：被 ≥ `max(5, 工具数/3)` 个工具需要、**且成组出现在寻址对象里**的 `<x>Id` 字段。
   「成组出现在寻址对象里」这条把**客户端自造幂等键**（`requestId`，42 个工具需要）排除掉 ——
   它从不进入寻址对象，不是服务端下发的坐标。
2. **生产者**：`F` 的生产者是满足「`F` 不在自身坐标集里 ∩ 名字/描述含 `F` 的词干 ∩ 查询类前缀 ∩ **自身坐标集是轴全集的真子集**」的工具，取坐标集最小者。
   「真子集」这条把 `requestId` 的伪生产者（`get_model_operation`，坐标集 = 轴全集）排除掉。
3. **闭包**：被选工具 → 其所需轴字段的生产者 → 生产者自身所需字段的生产者（≤2 跳）。

**实测结果**：坐标轴 = `{projectId(68), branchId(67), versionId(66)}`；
生产者唯一确定 = `query_projects`(∅) / `query_branches`({projectId}) / `query_model_versions`({projectId,branchId})。

### 3.3 零变化保证

| server | 工具数 | 寻址结构 | 结果 |
|---|---|---|---|
| `zhiyuan-dev-mcp` | 71 | 有 | 补 3 个坐标工具 |
| `AI4MBSE 领域能力（内置 MCP）` | 3 | 无 | **chain = []，逐字节不变** |

## 四、D2 动词级意图闸（代码改动）

### 4.1 为什么需要

MCP 工具**不在 `tools` 表** ⇒ 后端既有的「写意图闸」（按 `tools.side_effect` 过滤）**根本管不到它们**
⇒ 读类任务被递破坏性工具。

### 4.2 规则

按**工具名里的动词族**判定（不是硬编码工具名），且**只闸破坏性/覆盖写 5 族**：
`delete` / `import` / `apply` / `undo` / `overwrite`。

> ⚠️ **为什么族集合要窄**（实测踩坑）：初版把 `create`/`update` 等也纳入，
> 结果读类请求下 MCP 工具**一个都不剩**（语义选集恰好挑中一批写类工具）⇒ 反而把能力掐死。
> ⇒ `create`/`update`/`move`/`clone` 等**常规建模动作不闸**（漏了会让建模流程做不下去），
> 只闸"误暴露代价最高"的那几族。

### 4.3 生效范围

- **主路径（stream）**：生效（`_tool_whitelist` 为空）。
- **冷路径（execute）**：跳过（技能白名单独占成 `_tool_whitelist`，与既有 `side_effect` 闸同一口径）。
- 与技能白名单的关系：白名单是**权限**（能不能用），本闸是**恰当性**（这一轮该不该递到眼前）。

### 4.4 实测对照（真实链路 `_build_tools_def`）

| 请求 | 坐标三元组 | 暴露的破坏性工具 |
|---|---|---|
| 在通信子系统用例包中新增测试包 | 齐全 | 无（`create_model_elements` 正常保留） |
| 查询智源工程列表和包结构树 | 齐全 | 无 |
| 把当前模型导出为 SysML v2 源码 | 齐全 | **无**（改前有 `delete_model_elements`） |
| 校验这段 SysML v2 代码的语法 | 齐全 | **无**（改前有 `apply_model_changes`/`import_sysml_text`） |
| 删除旧的需求包 | 齐全 | `delete_model_elements`（合理） |
| 把需求包改名成测试包 | 齐全 | `update_model_elements`（合理） |

> 本轮补 `autofix` 之所以保留，是因为它**本身无害且让白名单更完整**，
> **不是因为它修掉了那个失败**（它没修掉）。

### 11.4 抓到缺陷 E7：skill 事件**早于**技能匹配 ⇒ 事件恒空

**现象**：E2 判据恒 FAIL（`skill` 事件数 = 0），但离线探针 `_build_skill_prompt`
明明命中「智源平台管理」。

**根因**（`agent/pipeline_parts/stream.py`）：

```
旧 4165~4172   yield {"type":"skill", "names": list(self._last_skill_hits)}   ← 读命中集
旧 4254        build_prompt_blocks(...) → _build_skill_prompt(...)             ← 才产生命中集
```

`_build_skill_prompt` **全仓只有一个调用点**（`common.py:549`，在 `build_prompt_blocks` 内）
⇒ skill 事件 yield 时 `_last_skill_hits` **必然是空** ⇒ 前端「🧩 技能执行」卡永远空白。

⚠️ **该分支此前从未被执行过**（因为恒空）⇒ 里面藏着一个**潜伏的前向引用**：
`_ctx_agent` 在 4527 行（工具循环段）才定义，而 skill 事件在 4188 行用它
⇒ 修好时序后立刻报 `cannot access local variable '_ctx_agent'`。
**教训：被"永不执行的分支"掩盖的缺陷，任何静态检查与既有回归都测不出来 —— 只有真机跑才暴露。**

**修法**（不是"把事件挪到后面"，那会让事件晚于 reasoning 到达、前端顺序乱）：
1. **提前预匹配**：在 reasoning 之前调一次 `_build_skill_prompt`；
2. **本轮缓存复用**：`_build_skill_prompt` 内置 `_skill_prompt_cache`
   （键 = intent + user_input + role_name + `_skill_forced`），
   随后的 `build_prompt_blocks` **命中同一缓存** ⇒ 不重复匹配、不重复 offload
   （offload 会写 `skill_body_offloads` 表，重复做会留垃圾行；
   且匹配含 LLM 兜底 `_llm_pick_skills`，算两次 = 多烧一次 LLM）；
3. **`reset_skill_state` 同步前移**到预匹配之前（否则 `_skill_forced` 是上一轮的值
   ⇒ 缓存键错 + `_skill_allowed_tools` 被二次 reset 清零）；
4. 缓存**生命周期 = 一轮**：由 `reset_skill_state` 清零（否则跨轮复用上一轮的 offload id）。

**副作用为零**：无写操作/无技能命中时逐字节不变（缓存命中即返回原串）。

### 11.5 抓到缺陷 E8：模型**虚构未完成**（写操作已成功却声称未执行）

**现象**（conv 9698）：`create_model_elements` 回执 `status=SUCCEEDED` /
`semanticStatus=APPLIED` / 新 `dataId`，但模型最终回复断言：

> 「**尚未写入平台**：本轮我在把用于写入的「坐标」和「父容器」都定位出来之后，
> 触发了工具调用轮次上限，因此新建包的写操作**没有执行**，平台上现在**没有**这个测试包。」

**独立核实**：直连 MCP `query_data_tree` 回读 ⇒ 新包**确实存在**
（`dataId=2115077874346688512`，父容器下 total 由 1 变 2）⇒ **与事实完全相反**。

**两个机制叠加**：
① ReAct 累积 **11 轮**（其中 6 轮浪费在重复 `query_data_tree`），
   messages 极长 ⇒ 模型在收尾时**看漏**了那条成功回执；
② 收尾提示（`finalize_messages`）**只在 `lacks_deliverable` 为真时才走**，
   而本次模型**产出了 2147 字的完整回复** ⇒ 收尾提示**根本没触发**
   ⇒ 全链路**没有任何机制**能纠正它。

⚠️ 这与技能第六节纪律 4「不得虚构已完成」是**同一条纪律的两个方向**：
- 虚构已完成（声称写了但没写）—— 已有纪律覆盖；
- **虚构未完成**（声称没写但写了）—— **无任何纪律覆盖**，且看起来"诚实"，
  实际会让用户以为操作没生效而**重复操作**（造成重复包）。

**修法**：
1. `loop_protocol.write_ops_digest(ops)` —— 把**本轮已成功执行的写操作**
   （工具名 + 回执摘要）整理成显式清单；
2. **只认成功回执**（`ok=True`）—— 失败的由各自错误回执承载，
   列失败的会误导成"做过但失败"；
3. **在最终生成之前**注入（**不依赖收尾分支** ⇒ 两条路径都覆盖）：
   - `finalize_messages(..., write_ops=...)`（收尾轮）；
   - 直接追加一条 user 消息到 `messages`（正常产出轮，**本次的形态**）；
4. `_is_write_tool()` 判定写类：**本地工具**查 `tools.side_effect`，
   **MCP 工具不在 tools 表** ⇒ 必须另用 `mcp_tool_meta.mcp_write_group`（动词族，零硬编码）。

**零回归**：无写操作时 `finalize_messages` **逐字节不变**（实测 `r_none == r_empty == r_none2`）。

**实测复验**（conv 9699，同一请求，仅加上修复）：
> 「**已完成**：子包「E2E验证包」已在「通信子系统用例图」包下创建成功，
> 并已回读确认挂载到位。」+ 真实 dataId `2115079578924417024` + 完整路径链

独立回读证实：该 dataId **在平台上确实存在** ⇒ 模型陈述与事实**逐字相符**。
