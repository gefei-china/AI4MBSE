## 0. 先把盘子量准 —— 三个会误导判断的直觉

在给方案前，必须先纠正三处"看起来对、实测不成立"的直觉。否则方案会打偏。

### 直觉① "system prompt 是大头" —— 只对了一半

| 组件（`chat_probe` 单次实测） | token | 占该次 |
|---|---|---|
| system prompt | 4,401 | 30.5% |
| **history（messages）** | **4,567 ~ 8,358** | **32% ~ 58%** |
| tools payload | 1,297 ~ 1,822 | 9% ~ 13% |
| 当前输入 + 其它 | 余量 | ~5% |

⇒ **history 才是最大单项**，system 屈居第二。前几轮所有优化（MCP/role/JIT）都在 system 与 tools 侧，
history 侧**一次都没碰过**。

### 直觉② "tools payload 很大（71 个工具 5,467 tok）" —— 那是**修复前**的数

修复后实测（同一 query、真实 `_build_tools_def`）：

| 状态 | 工具数 | payload |
|---|---|---|
| MCP offline（当前生产） | 6 | **1,297 tok** |
| MCP online（修复后，`mcp_min_keep=8`） | 14 | **1,822 tok** |

⇒ 恢复 MCP online 只增加 **+525 tok**，不是 5,467。
**它是一次"花 525 tok 换回 8 个真工具"的功能恢复，不是成本优化。**

### 直觉③ "历史没管，一直在涨" —— 管得挺好（94% 压缩）

| 会话 | 原始历史 | 压缩后 | 压缩率 |
|---|---|---|---|
| 9571 | 109,329 字符 | 6,421 | **94.1%** |
| 514 | 87,502 字符 | 6,005 | **93.1%** |
| 9586 | 80,310 字符 | 8,680 | **89.2%** |
| 9360 | 46,946 字符 | 6,626 | **85.9%** |

机制：单条 `clip_hist_msg(max_chars=1500)` 保留头部 + **追加"原文未被截断"标记 + 未显示部分章节提纲**。
⇒ 这不是静默硬切，是设计过的显式裁剪（`history.py:225-245` 有完整的事故记录）。
**history 侧的空间不在"压得更狠"，而在"别把已经交付过的整篇报告再塞一遍"。**

## 3. 剩余优化项：按「价值 ÷ 风险」排序

### P1 · history 侧：已交付的整篇报告改为「摘要 + 可回读」

**为什么这是第一优先（数据支撑）**

`chat_probe` 占 75.2%，而其中 history 占 32%~58%。实测 5 个重会话装配后的历史：

```
合计 32,491 字符 ≈ 35,782 tok（5 个会话合计）
其中代码块 0 字符 —— 说明代码已被 clip 掉，剩下全是"报告开头的散文"
```

也就是说：**历史里占地方的是"上一轮那份长报告的前 1500 字"**，而那份报告的结论/产物
在 `session_artifacts.build_digest` 里**已有摘要通道**（`history.py:889-906` 已实现）。

**做法**

对「已产出 artifact / sysml_version 的 assistant 消息」，history 里不再注入 1500 字头部，
改为：`[上一轮交付：<标题>（<产物 id>），结论摘要见下]` + `build_digest` 已有摘要。
**不新增机制，只是把已有摘要通道的覆盖范围从"产物"扩到"长报告消息"**。

**预期**：重会话每轮 −3,000~5,000 tok（按 1,500 字 ≈ 750 tok/条、2~3 条长报告估）。

**风险**：中。丢掉"报告某一节的细节"可能让模型在追问时重复生产。
**必须先测**：
- 构造「第 1 轮产长篇报告 → 第 2 轮问该报告某节细节」，比对改前/改后的回答是否引用了正确内容
- 判据：**不得出现"重写一遍"**（这是 `clip_hist_msg` 当初要修的那个事故形态）

### P2 · `skill_prompt` 再瘦身（system 内第一大块）

**数据**：system 4,401 tok 中 `skill_prompt` **1,457 tok（33.1%）**；
真实装配下「生成活动图」的 `skill_prompt` = 3,241 字符 / 2,271 tok。

**已做对的部分**（不要再动）：长正文已 `offload_body`（>600 字符转引用 + 头部摘要）；
frontmatter 已重建（现在 ≤292 字符）；未命中的绑定技能只给一行描述。

**可动的一处**：**"全局命中但未绑定"的技能**目前与"绑定技能"披露深度相同
（`src_tag="（全局匹配·未绑定 Agent，建议绑定）"`）。这类技能的正文摘要其实价值较低 ——
用户并没有为该 Agent 配它。

**做法**：对未绑定命中，只披露 `description` + `triggers` + 一行"如需正文请说 X"，
不注入 `build_head` 摘要与示例片段。开关 `context_audit.skill_summary_unbound=False`。

**预期**：每次装配 −300~800 tok（取决于命中几个未绑定技能）。
**风险**：低（不改绑定技能行为）；但需确认"全局技能池自动触发"是产品想要的（它确实是，见 skills.py 注释）。
**验证**：同一批建模任务，看产出是否仍遵守未绑定技能的硬约束。

### P3 · 打开 `role_manual_filter`（阀门已装好，只差质量验证）

**已完成的可测部分**（`tools/eval/ab_role_manual.py`）：

| 指标 | 结果 |
|---|---|
| role token | 8,995 → **889（−90.1%）** |
| prose / 暴露工具段保留率 | **100% / 100%** |
| 精确口径「被裁段点名了仍暴露的工具」 | **10/300**，且样本是"暂**不**支持 apply"式否定说明 ⇒ 无害 |

**覆盖**：仅 `智源对接agent`（历史 chat 流量 5.8% / 1.77M tok）。
按 −8,298 tok/轮 估，覆盖流量可省约 **1.0M tok ≈ 7%** 的该 agent 部分。

**唯一剩下的门槛**：**任务正确率**（mock 下无法测）。
**验证方法**：真实 provider，同一批 10~15 个智源平台任务（查询/导出/预览/应用变更各几条），
开关两态各跑一遍，对比：
- 任务是否完成（工具调用成功 + 产出正确）
- **是否跳过了本该做的确认步骤**（这是手册里最可能被裁掉的跨工具纪律）

> 这条如果通过，是本期**性价比最高**的一次开关动作（改一个布尔值，省 90% role）。

### P4 · 提高 KV 缓存命中率（从 77.1% 往上）

**数据**：命中 77.1%。system 静态区只占 55.3% ⇒ 说明动态区前缀也被缓存了一部分。
缓存失效点是**第一个变化的块**：`skill_prompt`（依赖 `user_input`，每轮变）。

**关键洞察**：`skill_prompt` 在 `PROMPT_DYNAMIC_KEYS` 第 3 位，
⇒ 它一变，**它之后的 10 个块（memory / model_context / retrieval / attachment …）全部缓存失效**。

**做法（低成本试）**：把 `skill_prompt` 在块顺序里**后移**到 `retrieval` 之后。
理由：它每轮变，但它后面那些块（`model_context` / `project_memory` / `slots`）也是每轮变的；
真正稳定的是 `intent_line`（同会话同意图不变）。
⇒ 把稳定性排序做实：`intent_line` → `model_context` → **`skill_prompt` 后置**。

**但必须先验证**：块顺序影响模型注意力（`common.py:393` 注释提到"原指令与数据相距 12 个 block"的教训），
**不能为了缓存随意调顺序**。

**验证方法**：现有 `verify_prompt_layering.py`（28 项）会判层归属；
另需跑 `verify_multiturn_context.py`（135 项）确认多轮行为不变；
再用 `context_audit` 的 `static_ratio` 与 `llm_usage_stats.prompt_cache_hit_tokens` 对比改前后命中率。

**预期**：命中率 +5~15 个百分点（保守）。缓存命中部分单价显著更低 ⇒ 等效成本下降。
**风险**：中（动的是 prompt 结构，是"能影响质量"的改动）。

### P5 · 收敛 `intent_detect` 的调用次数（小而稳）

**数据**：728 次 / 0.26M tok / 均值 363。单项占比仅 1.9%，但**次数很多**（728 次，是 chat_probe 的 1.03 倍）。

**观察**：`intent_detect` 平均 363 tok，说明送进去的是短文本（意图识别只需用户原话）。
它是"每轮必付"的固定成本，且**与历史无关**。

**可做**：对**同会话连续追问**（有 `last_slots` / 上轮 intent），走"继承 + 轻量确认"，
不必每轮独立分类。本仓已有 `_load_history_for_intent` 与 `intent.history_recall` 开关。

**预期**：次数 −30~50% ⇒ 省 0.08~0.13M tok（**仅 0.6~1%**）。
**结论**：价值小，**不建议现在做**。列出来只为说明"我算过，它不是机会"。

   "省 30% token 却漏掉关键要求 = 没达到目的"；
3. **任何收益都要用 `trace_id` JOIN 反算**，不接受"机制上应该省"的推断。

## 5. 怎么确认"真的省了"（可执行的核账方式）

```bash
# ① 开关前后各跑一次，导出快照
./.venv/Scripts/python.exe -X utf8 tools/report_context_audit.py --json --days 7 > before.json
# （执行动作、观察若干天）
./.venv/Scripts/python.exe -X utf8 tools/report_context_audit.py --json --days 7 > after.json

# ② 看块分布变化
./.venv/Scripts/python.exe -X utf8 tools/report_context_audit.py --all --days 7

# ③ 确认开关真的触发了（不是"配了没生效"）
#    看 switches 视图里对应指标的计数是否 > 0
#    例：role_manual_applied / cache_hit / whitelist_exempted_mcp
```

**反算公式**（按 `trace_id` JOIN）：

```sql
-- 每轮：归因总量 vs 实际计费，差额 = messages + tools
SELECT s.trace_id, s.total_tokens AS system_tok, u.prompt_tokens AS billed
FROM context_audit_summary s
JOIN llm_usage_stats u ON u.trace_id = s.trace_id
WHERE s.phase='system' AND u.used_mock=0
LIMIT 20;
```

> ⚠️ **两个部署前置（2026-10-26 实测，已处理）**：
> ① 生产库原本**没有 `context_audit` 表、也没有 `mcp_servers.tool_meta` 列** ——
>    建表/加列都在 `init_db()` 里，**只在应用启动时执行**。
>    不迁移 ⇒ 观测拿不到数据、MCP 元数据功能整条不生效（今天已执行 `init_db()` 并验证通过）。
> ② 迁移后 `context_audit` 仍是 **0 行**（还没有新请求跑过）⇒ 部署后第一件事就是跑上面的报表，
>    确认 `has_data=true`。**这是"改了但没生效"最典型的一道坎，必须先确认再谈收益。**
