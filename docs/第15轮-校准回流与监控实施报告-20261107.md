## 2. P0-2 样本回流闭环

### 实施链路
```
前端 pickIntent() → intent_override 随原消息重发
  → routers/conversations.py（流式 + 非流式两个入口）透传 ui_intent_override
  → stream.py / execute.py 在 _detected 算出之后（拿得到系统原判）
  → services/intent_override_feedback.record_override()
  → intent_samples(status='suggested', source='override', note=JSON)
  → 管理页 GET /api/intent-samples/overrides 列出待审
  → POST /api/intent-samples/overrides/confirm（显式 id 列表）转 confirmed
```

**为什么用显式 `ui_intent_override` 参数**：stream 内部的 `forced_intent` 已被 team 逻辑
覆写，无法区分「用户改选」与「编排内部定向」。混用会把子任务调度误记成用户纠错。

### 真实数据验证（`verify_override_feedback.py`，19/19）
- 写入 `status=suggested` / `source=override` / note 可机读（override/detected/route/route_conf）
- `intent` 列保持空（系统建议值不冒充人工标签）
- **既有 confirmed 行不被覆盖**（upsert 保护实测）
- 0 条 override 样本被自动 confirmed
- 重复改选不新增行，`seen_count` 1→2
- 系统包装文本 / 过短 / 过长 / 空改选 / 「改选==原判」/ 采集开关关闭 全部拦掉
- 人工审核后才转 confirmed，且 `intent = 用户改选值`；既有 485 条 suggested 未受波及

## 6. 本轮自查踩到的三个坑

1. **`confirm_overrides` 的 SELECT 漏了 `source` 列**却读了 `row["source"]` ⇒
   会抛 `IndexError`。语法检查发现不了，靠逐列核对补上。
2. **`calibrate()` 生产调用不传 reliability 时只读兜底常量**，
   而兜底常量是按合成 gold 拍的、方向还反了 ⇒ 改为自动读真库回放表，
   并加 mtime 缓存避免每次读盘。
3. **`upsert` 的 UPDATE 分支不更新 `source`** ⇒ 真实 HTTP 路径上常规采集与回流
   写同一句时，若采集先落行，该行会永远是 `source='prod'`，管理页按
   `source='override'` **筛不到**。已在 `record_override` 里显式把非 confirmed 行
   改回 `override` 并提交。
4. **E2E 首版假红（验证脚本自己的用例错）**：改选值用了 `impact`，
   而这句话系统原判正好也是 `impact` ⇒ 被「改选==原判不写」这条纪律拦掉。
   这不是产品缺陷，是**判据设计正确但用例选错**。改为 `review` 后 PASS，
   并在脚本注释里写明"用例改选值必须≠原判"。
