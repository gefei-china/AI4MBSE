## 0. 一页结论

**三件最该做的事，按 ROI 排序：**

| # | 事项 | 为什么是它 | 代价 |
|---|---|---|---|
| **1** | 让 `interrupted` 单独一档、可被自愈接管 | 它是**最大失败源**（30 天 20/48 = 42%，近 4 天近乎 100%），而刚上线的自愈**结构上碰不到它**（`status='failed'` ⇒ `skip`）。**而幂等键已就位，重跑已经安全** —— 两个零件都造好了，只是没装在一起 | 小：`prepare_resume` 的 SELECT 加 `error_class`，判定分两档 |
| **2** | 评测集从 48 → 300+ 并报置信区间 | 48 条的 95% CI 是 **[89.1%, 99.6%]**（宽 10.5 点）。"0.9792" 与 "0.89" 在统计上**无法区分**；门禁阈值 0.85 就落在 CI 内 ⇒ 当前门禁抓不住真回归 | 中：把 420 条 suggested 走人工确认（已有 UI 与流程） |
| **3** | 校验 `basis=verified` 的引用是否真实存在 | 目前 `basis` 只用于**排序展示**，模型自称 verified 无人核。对标 ACM MODELS'26「epistemic adequacy」：AI 建议必须能指回受管的模型元素 | 小：写类/结论类工具出口加一道可回查闸 |

**一句话**：本项目的**机制密度已经很高**（幂等、checkpoint、resume、墙钟、并发闸、预算层级、97 个门禁），
真正的短板不在"缺能力"，而在**能力之间没接上**（1）、**度量不足以支撑结论**（2）、
**自我声明的可信度未被验证**（3）。

## 1. 现状体检（实测数据 + 行业基准）

### 1.1 编排可靠性

```
全量 313 条 agent_tasks / done 228 = 72.8%
最近 7 天：10-27 67% / 10-28 50% / 10-29 15% / 10-30 31%
失败归因（30 天，48 条）：interrupted 20 (42%) / (空) 26 / internal 2
```

**失败明细全是同一句话**：
> 编排中断：超过 30 分钟无任何进展，判定为孤儿运行（进程重启或执行线程丢失）

⇒ 这不是"模型做不出来"，是**进程重启把在跑的编排全杀了**。而本文档写作期间，
我为了验证改动重启了服务 4 次 —— 这本身就是压力测试：**重启一次，在跑的编排全废**。

### 1.2 这条链断在哪（逐环节实测）

| 环节 | 现状 | 判据 |
|---|---|---|
| 检查点 | ✅ `orch_checkpoints` phase + 5s 心跳 | 有表有数据 |
| 孤儿回收 | ⚠️ 只扫 `agent_tasks`，且启动时**不检查 checkpoint phase** | 今天实测：13 个 phase 停住的批次，`reap_orphans` 扫到 **0 条**，是我手工对账 |
| 断点续跑 | ✅ `prepare_resume` / `apply_resume` 存在 | — |
| 自动重驱 | ✅ 今天默认开启（带 3 道成本闸） | `running=True` |
| **接管 `interrupted`** | ❌ **结构上不可能** | 见下 |

```python
# agent/orch_checkpoint.py:278 —— SELECT 里没有 error_class
"SELECT id, task_key, status, deps, context, expected_output, agent_id, title, ..."

# policy_classify 只有 status 一个维度
if st == "failed":
    return "requeue" if include_failed else "skip"
```

实测：`policy_classify("failed", include_failed=False)` → **`skip`**。
而 `interrupted` 任务的 `status` 就是 `failed`（20/20 条实测）。

⇒ **自愈只能靠 `include_failed=True` 一把梭**，那会把"确定性失败"（参数非法、
权限拒绝、校验不通过）也重跑一遍 —— 那些重跑一百次也是同样结果，纯烧钱。

### 1.3 成本与上下文

```
30 天：13,329 次调用 / prompt 45.37M / completion 5.07M
单次 prompt 分位：p50=1,383  p90=19,553  p99=29,903  max=39,204  avg=6,166
最贵的会话：conv 9741  48 次调用  均 25,951/次；conv 9736 56 次 均 21,145/次
```

**这是"每步重发全历史"的平方增长形态**，不是工具 schema 膨胀：

| 可能原因 | 实测 | 结论 |
|---|---|---|
| 工具 schema 过多 | 43 个 active，最大 494 bytes，单 Agent 绑 8~16 个 | ❌ 不是瓶颈（**不必优化**） |
| Prompt 缓存失效 | 近 7 天命中率 **81.0%**（hit 16.07M / miss 3.77M） | ✅ 健康（**不必优化**） |
| 历史 + 检索证据累积 | p90 19.5k vs p50 1.4k，差 14 倍 | ✅ **这才是主因** |

已具备的压缩设施：`compression.py`（分层压缩）、`result_offload`（大结果外置）、
`tool_result_fetch`（按需取回，473 次调用 = 确实在被用）。

### 1.4 评测可信度（本项目最被高估的数字）

```
intent_samples：confirmed 48 / suggested 420 / rejected 13
意图准确率 47/48 = 0.9792
```

**统计学含义**（Wilson 区间，95%）：

| 观测 | 95% CI | 宽度 |
|---|---|---|
| 47/48 = 97.9% | **[89.1%, 99.6%]** | 10.5 点 |
| 43/48 = 89.6%（规则层） | [77.8%, 95.5%] | 17.6 点 |

⇒ **"0.9792" 与 "0.891" 的置信区间大幅重叠** —— 在 48 条样本上，
这两者无法区分。而门禁阈值是 0.85，**落在 CI 内** ⇒ 门禁的"通过"没有统计意义。

**要检出 5 个百分点回归**（80% power, α=0.05）：

| 场景 | 需要样本量 |
|---|---|
| 98% → 93% | **269 条** |
| 95% → 90% | 435 条 |
| 98% → 95% | 588 条 |

现在有 48 条已确认、420 条待确认 —— **待确认池就是解药，但没人去确认**。

### 1.5 一致性问题（行业最重要的 agent 指标，本项目未测）

行业（τ-bench）口径是 **pass^k**：同一任务连跑 k 次全对的概率。

| 单次成功率 | pass^3 | pass^5 | pass^8 |
|---|---|---|---|
| 98% | 94.1% | 90.4% | 85.1% |
| 95% | 85.7% | 77.4% | **66.3%** |
| 90% | 72.9% | 59.0% | **43.0%** |

⇒ 一个"95% 准确"的 agent，同一任务连跑 8 次只有 **2/3** 全对。
用户感知到的是"周一能答对、周二答不对"，而**单次评测在结构上看不见这个差距**。
本项目**没有任何重复采样评测**（`intent_samples` 是一次性标注，非重复采样）。

### 1.6 观测数据质量

```
tool_call_logs 3,819 行：is_probe=1 142 (3.7%) / 假工具名 126 (3.3%)
失败 570 行中带 failure_kind 仅 297 (52%)
```

三个问题：
1. **`fake_tool` 126 次调用（112 次失败）留在生产表里** —— 任何"工具失败率 top10"都会被它污染；
2. **`is_probe` 标记只覆盖 3.7%**，历史探针数据没有回溯标记 ⇒ 统计口径混用；
3. **`failure_kind` 只填了 52%** ⇒ 有一半失败**无法归因**（这正是"失败分类驱动重试"的前提）。

### 1.7 CI 覆盖面

```
tests-and-guards：197 步，通过 22，skipped 178
verify_gate_wiring W1a：45 个门禁未接线且未豁免
```

本文档写作期间已解锁 6 层（详见 `CI逐层解锁记录-20261030`）。
剩余 178 步会依次暴露，从前 6 层规律看集中在：夹具不自足 / 判据锚实现细节 / 环境差异。

### 1.8 配置面

```
DEFAULT 455 键 / SCHEMA 426 键
29 个键 DEFAULT 有而 SCHEMA 无 ⇒ 界面不可见、API 写不进
   auth 9 / rate_limit 5 / jobs 4 / rag 3 / extract 3 / embedding 2 / web_search 2 / conv_summary 1
```

其中 **`rate_limit.*`（限流）与 `auth.*`（登录强制）完全是黑的** —— 这两组恰恰是
生产部署最需要调的。`jobs.*` 同理（worker 数/租约）。

## 2. 行业对标：本项目在什么位置

### 2.1 Durable execution：机制齐、接缝漏

行业把失败分**三类**并要求分别处置（多家 2026 年文章口径一致）：
- **瞬时**（超时/限流/网络）→ 指数退避重试
- **持久**（参数非法/权限拒绝/404）→ 不重试，立即上报人工
- **歧义**（质量不达标/数据冲突）→ 检查点 + 通知人工 + 暂停等待

本项目 `services/failure_class.py` 已有瞬时/持久分类，**但 resume 路径不用它**。
这是"分类器造好了、消费者没接"的典型 —— 与 `total_time_budget_s` 死配置同型。

对标结论：**DBOS/Temporal 不需要引入**（上一轮已论证），但"按失败类分档重试"
必须自建 —— 引擎也不替你做这件事。

### 2.2 MBSE + AI：本项目架构方向是对的

ACM MODELS '26 论文 *Models as Governed Interfaces for AI-Native MBSE* 提出
**epistemic adequacy**（认知充分性），四个读侧判据：

| 论文要求 | 本项目对应 | 状态 |
|---|---|---|
| **derivation**（推导链） | `claims.basis ∈ {verified, derived, asserted}` | ⚠️ 有字段，**只用于排序** |
| **status**（认知状态） | 同上 | ⚠️ 同上 |
| **provenance**（来源） | `evidence.source/ref`、`graph_source_info` | ✅ 有 |
| **evidence reachable**（证据可取回） | `tool_result_fetch`（473 次调用） | ✅ 在用 |

论文的第五个（写侧）**write-side admissibility**：AI 的贡献进入记录前必须被治理。
本项目有 `HIL 确认闸` + `写入目标网关` + `import_target_guard` —— **这一侧比读侧做得好**。

**关键差距**：`basis` 是**模型自报**，系统不校验。
模型写 `basis: "verified"` 并引用一个不存在的 entity id，系统照单全收、只负责排序。
论文原文的口径是"require it to **point to** the supporting model elements" —— 能指回才算。

另一篇 MODELS'26 论文（*Trustworthy generation of SysML v2 models*）的双层校验思路
本项目**已实现**：语法层 `checker.jar`（ANTLR 语法 + 标准库）+ 语义层 `sysml_v2_validate`。
这一块是对标里做得最扎实的部分。

### 2.3 Context engineering：本项目该做和不该做的

行业 2026 的优先级（JetBrains / Anthropic / 多家一致）：

1. **工具输出截断**（最便宜，省 80–99% 工具输出）
2. **输入逐出**（滑窗 + 保留推理骨架，省 52% 成本）
3. **LLM 摘要**（最贵，做兜底）
4. **前缀稳定以命中缓存**

本项目实测：**缓存 81% 已达标**，**工具输出已有 offload**，
工具 schema 不膨胀（最大 494B）。所以第 1、4 项**已完成，不必再投入**。
真正的空间在**第 2 项：滑窗 + 保留骨架**（p90 19.5k 主要来自历史累积）。

行业还强调一条本项目**没有**的：*"Target 30-40% context utilization"* ——
本项目只有 `budget_window_tokens=65536` 与 `total_budget_window_ratio=0.75`，
**没有"利用率"这个观测量**（不知道当前占了多少、离饱和多远）。

## 3. 优化方案（按优先级，每条带判据与回退）

### P0-1 让 `interrupted` 单独一档、可被自愈接管 ★最高 ROI

**为什么现在做**：幂等键（P0-1 上一轮）已经让"重跑写类工具"变安全，
缺的只是把两条信息接起来。**两个零件都造好了，没装在一起。**

**改法**（三处，都很小）：

1. `orch_checkpoint.prepare_resume` 的 SELECT 加 `error_class`：
   ```sql
   SELECT id, task_key, status, error_class, deps, ... FROM agent_tasks
   ```
2. `policy_classify` 增加一档（**保持向后兼容**：新形参默认 `None` = 旧行为）：
   ```python
   if st == "failed":
       # interrupted = 进程重启导致，任务本没跑完；幂等键已保证重跑安全
       if error_class == "interrupted":
           return "requeue"
       return "requeue" if include_failed else "skip"
   ```
3. 新增配置 `orchestration.resume_interrupted=True`（回退位），并在 `supervisor_status` 暴露
   "本日因 interrupted 而重投的次数"（与现有 `daily_budget` 共用闸）。

**判据**：
- 构造一个 `status='failed', error_class='interrupted'` 的批次 ⇒ `prepare_resume` 返回 `mode='tasks'`；
- 同批次的 `error_class='internal'` 任务 ⇒ 仍 `skip`（不误放大）；
- 变异自证：把 `error_class` 判定去掉 ⇒ 第一条判红。

**回退**：`orchestration.resume_interrupted=false`。

**预期收益**：42% 的失败从"永久失败"变成"可自愈"。这是唯一一条能把
成功率从 72.8% 拉到 90%+ 量级的单点改动。

---

### P0-2 评测集扩容 + 置信区间入报告

**改法**：
1. **确认 suggested 池**：420 条逐条人工确认（已有 UI 与 `confirmed` 流程），
   目标是 **300+ 条 confirmed**（可检出 5 点回归的最低量级）。
2. **门禁输出加置信区间**：`verify_intent_llm_review` / `run_ci_eval` 在
   `[RESULT]` 行加 `ci_low` / `ci_high`（Wilson），并**用 `ci_low >= threshold` 判定**
   而不是 `accuracy >= threshold`。
   > 当前 `accuracy=0.9792` 能过 0.85；但 `ci_low=0.891` 也只是勉强过 ——
   > 换一次抽样就可能不达标，而那时分不清是"模型退化"还是"抽样噪声"。

**判据**：
- 报告里同时出现 `accuracy` / `ci_low` / `ci_high` / `n`（缺一即判红）；
- 变异自证：把 `n` 从 48 改成 20 ⇒ `ci_low` 显著下移（证明区间真的随样本量变）。

**不做**：不追 1000+ 条（成本不划算）；不做全自动生成标注（会污染 ground truth）。

---

### P0-3 校验 `basis=verified` 的可回查性

**为什么**：这是 MBSE 场景的**核心可信度机制**。一个 `basis: verified` 但引用不存在的
结论，会被下游当验收依据。

**改法**（收敛在结论汇总前一处）：
对 `evidence[].basis == "verified"` 且 `source ∈ {graph, vector, attachment}` 的条目，
按 `source` 做**存在性校验**：
- `graph` → 该 entity/requirement id 在 `entities` 表存在（且分支匹配）
- `attachment` → 文件路径存在且在本轮附件清单内
- `vector` → chunk id 在 `document_chunks` 存在

校验失败 ⇒ **降级为 `asserted` 并留痕**（不删内容、不阻断，只改可信度标注）。

**判据**：
- 构造一条 `basis=verified` + 假 entity id ⇒ 汇总里该条变 `asserted` 且带降级说明；
- 变异自证：关掉校验 ⇒ 该条仍是 `verified`（证明判据承重）。

**回退**：`context.verify_claim_basis=False`。

---

### P1-1 上下文利用率观测量 + 滑窗逐出

**改法**：
1. 每次 `llm.chat` 记录 `ctx_utilization = prompt_tokens / context_window` 到
   `llm_usage_stats`（新列，或用现有 `prompt_tokens` + provider 的 `context_window` 现算）；
2. 加告警：`p90(utilization) > 0.6` 持续 ⇒ 提示"压缩可能失效"；
3. 现有 `compression.py` 补**滑窗逐出**策略（保留 system + 最近 N 轮全文 + 更早的
   替换为结构化占位符），作为 `total_budget_window_ratio` 触发前的**便宜路径**。

**行业依据**：JetBrains 实测"滑窗 + 观察掩码"比纯 LLM 摘要**省 52% 成本且不降完成率**。

**判据**：
- 造一个 30 轮长对话 ⇒ `p90 utilization` 可读出；开启滑窗后同场景 `prompt_tokens` 下降 ≥20%
  且任务完成率不降；
- **变异自证**：把逐出关掉 ⇒ token 回到基线（证明真的在起作用）。

**明确不做**：不动工具 schema（实测不是瓶颈）、不动 prompt 缓存（81% 已健康）。

### P1-2 观测数据卫生

**改法**：
1. `fake_tool` / `slow` / `echo` / `dummy` 等测试工具名，在**写入时**若不在 `tools` 表则
   强制 `is_probe=1`（而不是靠调用方记得传）；
2. 历史 126 行回填 `is_probe=1`（一次性）；
3. `failure_kind` 填充率补到 100%：`_log_tool_call` 在 `ok=0` 且 `failure_kind` 为空时
   用 `failure_class.classify` 兜底填（**已有分类器，只是没接**）。

**判据**：
- 任何"工具失败率"统计默认排除 `is_probe=1`（口径写进 SQL 注释）；
- 新增失败调用 ⇒ `failure_kind` 非空率 = 100%（门禁断言）。

**为什么重要**：`failure_kind` 只有 52% 意味着**一半失败无法归因**，
而"分类驱动重试"（P0-1）依赖这个字段。

### P1-3 CI 继续解锁 + 45 个门禁接线

**现状**：22/197 步，178 skipped。
**改法**：按本文档的六层方法继续逐层剥（每层先判"产品错/判据错/环境错"）。
**判据**：`tests-and-guards` 全绿；或每层都留一条"为什么不修"的如实记录。

**不做**：不为了变绿而放宽判据（那是把门禁改成永远绿，比红更危险）。

### P2 配置面补齐

**改法**：把 29 个无 SCHEMA 的键登记（优先 `rate_limit.*` 5 个、`auth.*` 9 个、`jobs.*` 4 个）。
**判据**：`verify_setting_keys_guard` 增加"DEFAULT ⊆ SCHEMA"断言（现在是手工发现）。

### P2 pass^k 一致性评测（可选）

**改法**：对 20 条高价值用例，每条跑 3 次，报 `pass^3`。
**判据**：`pass^3` 与 `pass^1` 的差距 > 10 点 ⇒ 说明波动是主要问题，优先治一致性而非准确率。

**为什么排在后面**：它需要 3 倍 token 预算，而当前更急的是"成功率"与"统计可信度"。

## 4. 明确不做（及理由）

| 不做 | 理由（实测/依据） |
|---|---|
| 引入 Temporal / DBOS | 已有 checkpoint/resume/租约/幂等；缺的只是"按失败类分档"，引擎也不替你做 |
| `uvicorn workers=N` | 进程内信号量/熔断器会失真；SQLite 单写者不支持多进程写 |
| 优化工具 schema | 实测最大 494 bytes、单 Agent 8~16 个 ⇒ 不是瓶颈，投入无回报 |
| 优化 prompt 缓存 | 命中率 81%，已健康 |
| 全自动生成评测标注 | 会污染 ground truth；`suggested → confirmed` 必须过人 |
| SSE 改 202 + 轮询 | 推翻前端打字机交互，代价远超收益 |
| 为过门禁而放宽判据 | 等于把门禁改成永远绿；本轮已修 6 处"判据错"，全部靠变异自证守住 |

## 5. 建议执行顺序（每步独立可验、可回退）

```
第 1 步  P0-1 interrupted 可自愈        ← 单点改动，预期收益最大
第 2 步  P1-2 观测卫生（failure_kind 100%） ← P0-1 的依赖项
第 3 步  P0-2 评测集 300+ & CI 区间     ← 让"改完有没有变好"可判
第 4 步  P0-3 basis 可回查              ← MBSE 可信度核心
第 5 步  P1-1 上下文利用率 + 滑窗
第 6 步  P1-3 CI 继续解锁
第 7 步  P2 配置面补齐 / pass^k
```

**为什么 P0-1 排第一**：它同时满足三个条件 ——
① 影响面最大（42% 失败）；
② 依赖已就位（幂等键 + 自愈守护都已上线）；
③ 改动最小（一个 SELECT + 一个分支 + 一个开关）。

## 6. 口径声明（引用本文数字时必带）

- 成功率：`agent_tasks` 全量 313 条，`done/total`；时间窗见各表头
- 失败归因：`error_class` 字段；`(空)` 表示该字段未填（不是"无错误"）
