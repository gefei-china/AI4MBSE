# 本体变更实例影响分析与自动迁移方案

> 版本：v1.0（2026-09-14）
> 关联文档：《本体编辑区WebProtege对齐改造清单.md》《Protégé模式落地MBSE本体建模页方案.md》
> 关联需求：FR-KG-4（本体治理 G7 变更留痕）、版本语义收敛（2026-09-08）

---

## 1. 背景与问题

本体编辑区（WebProtégé 模式）支持对实体类型、关系类型、属性类型进行增删改。但**实例数据**（知识图谱中的 entities / relations）对本体的引用是**按名称的软引用**：

```sql
-- database/schema.py:158-196
entities.entity_type   = ontology_types.name   -- 字符串，无外键
relations.relation_type = ontology_types.name  -- 字符串，无外键
entities.properties 的 JSON 键 ≈ attribute 类型名（隐式约定）
```

由此产生三类缺口：

| # | 缺口 | 后果 |
|---|------|------|
| G1 | **改名不迁移**：`ontology_update_type` 只更新 `ontology_types`，实例残留旧名 | 实例悬空（不属于任何类型）、关系失配，图谱查询/统计悄悄漏数据 |
| G2 | **删除只计数**：`ontology_delete_type` 返回 `affected_instances` 但 force 后实例不处理 | 同 G1，且 force 级联只修了本体侧（子类提升、dom/range 置空），实例侧没人管 |
| G3 | **约束收紧不回溯**：domain/range、基数 card、属性值域、disjoint 等约束只约束未来的编辑 | 存量实例可能违例，且没有任何入口能看到违例清单 |

**目标**：本体编辑后，用户能在保存前看到对实例数据的影响（影响预览），在发布时能自动、安全、可回溯地更新实例数据（迁移执行）。

## 2. 现状盘点（已有基础设施，全部复用）

| 能力 | 位置 | 本方案的用法 |
|------|------|-------------|
| 变更留痕（before/after 整行快照） | `ontology_change_logs`，`_log_ont_change()`（routers/knowledge_parts/ontology.py） | 影响分析与迁移计划的**唯一数据源**：diff before/after 即得变更类型 |
| 版本链 + SemVer + 不可变快照 | `ontology_versions` / `ontology_version_snapshots`，`/version/publish`（ontology_version.py） | 发布是迁移执行的**触发点**；major/minor 判定已含"删除/域值域变更→major" |
| 类型反向引用聚合 | `GET /types/{tid}/usage`（ontology.py:243-280） | 影响预览直接复用：as_parent / as_source / as_target / instances |
| 删除 blockers 检查 | `ontology_delete_type`（ontology.py:283-336） | 删除场景的拦截逻辑保持不变，迁移只处理 force 通过后的实例 |
| 一致性校验 | `_ontology_check()`，`GET /ontology/validate` | 循环继承/悬空 parent/孤立类等，本体侧校验；本方案补**实例侧**回溯校验 |
| 实例级影响引擎 | `services/impact_engine.py`（BFS 传播 + 沙箱模拟）+ `routers/impact.py` | 违例清单点击跳转图谱时复用其 Cytoscape 影响子图渲染 |
| 推理物化 | `services/swrl_materializer.py` / `swrl_engine.py` | 推理性质变更后重跑物化 |
| SHACL 约束单一事实源 | `constraints.allowed_values`（P1-8 归一后） | 回溯校验的规则来源，不再读旧 domain/range 双轨 |

结论：**不缺数据源，缺的是"本体变更 → 实例影响"这一环的分析、展示与执行**。

## 3. 影响分类矩阵（设计基线）

按"对实例数据的影响 × 自动化策略"分级：

| 本体编辑操作 | 对实例数据的影响 | 级别 | 自动更新策略 |
|---|---|---|---|
| 实体类型改名 | `entity_type` 残留旧名，实例悬空 | 🔴 破坏性 | **L1 内联**：保存事务内按旧名批量替换（幂等） |
| 关系类型改名 | `relation_type` 残留旧名，关系失配 | 🔴 破坏性 | **L1 内联**：同上 |
| 实体类型删除 | 实例失去类型归属；关系端点断链 | 🔴 破坏性 | 拦截（已有 blockers）；force 时 **L2 计划**：实例迁移到父类或标 deprecated |
| domain/range 收紧 | 存量关系端点不再合法 | 🟡 需校验 | **L2 计划**：回溯校验产出违例清单，人工裁决 |
| 基数 card_src/card_tgt 收紧 | 单实例关系数超 min/max | 🟡 需校验 | **L2 计划**：GROUP BY 校验 → 违例清单 |
| 属性类型/值域收紧 | `properties` JSON 存量值非法 | 🟡 需校验 | **L2 计划**：值域校验 + 类型转换器（可自动转换的自动转） |
| 继承结构变化（parent 调整） | 实例继承到的有效属性/约束集变化 | 🟡 需校验 | **L2 计划**：重算 effective schema 后统一校验 |
| 删除属性类型 | 实例 `properties` 残留死键 | 🟢 低 | 发布时批量清键（L2 可选 op），或读取时懒清理 |
| 新增属性/关系类型 | 存量实例无此键/此边 | 🟢 无影响 | 稀疏处理，无需迁移 |
| 推理性质新增（传递/对称等） | 数据不变，物化结果变化 | 🟢 低 | 重跑 `swrl_materializer` 增量物化 |

**分级原则**：
- **L1 内联（同步、事务内、无歧义）**：只有"改名"这一类。操作是幂等 SQL、与本体修改同事务原子提交，失败即整体回滚，无数据丢失风险。
- **L2 计划（异步、发布挂钩、可预演）**：涉及删除、语义判断（违例怎么处理是工程决策）的操作。生成迁移计划 → dry-run → 人工确认 → 执行。

## 4. 总体架构

```
① 编辑时（同步 · 保存前预览）
   PUT/POST /ontology/types
        │  diff（before 行 vs 提交 body）
        ▼
   POST /ontology/impact-preview          ← 新增
        │  复用 usage + 实例回溯校验
        ▼
   编辑抽屉内联影响面板                    ← 前端改造（23-ontform.js）
        （红/黄/绿徽章 + 违例清单折叠 + 受影响实例数）

② 发布时（异步 · 确认后批量执行）
   POST /ontology/version/publish
        │  SemVer 判定（已有）
        ▼
   services/ontology_migration.py         ← 新增
        │  build_plan（消费 change_logs diff）
        ▼
   迁移计划面板（发布弹窗内）              ← 前端改造
        │  dry-run 报告 → 用户确认
        ▼
   POST /ontology/migrations/{id}/apply   ← 新增
        │  事务执行 + 写 ontology_instance_migrations + audit
        ▼
   实例数据回写（entities / relations / properties）
```

两条链路共用 `ontology_change_logs` 的 before/after 作为输入，不新造数据源。

## 5. 后端设计

### 5.1 新增数据模型：`ontology_instance_migrations`

```sql
CREATE TABLE IF NOT EXISTS ontology_instance_migrations (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    change_log_id INTEGER,              -- 关联 ontology_change_logs.id（可空：批量补迁）
    version_id INTEGER,                 -- 关联 ontology_versions.id
    op_type TEXT NOT NULL,              -- migrate_instances | migrate_to_parent |
                                        -- drop_prop_key | convert_prop_values | flag_violations
    target TEXT NOT NULL,               -- 操作对象（类型名 / IRI）
    payload TEXT DEFAULT '{}',          -- op 参数 JSON（如 {from, to, branch}）
    affected INTEGER DEFAULT 0,         -- dry-run 预计行数
    status TEXT DEFAULT 'pending',      -- pending | dry_run | applied | failed | dismissed
    sample TEXT DEFAULT '[]',           -- dry-run 抽样（前 10 条实例 id + 摘要）
    created_by TEXT DEFAULT '',
    created_at TEXT DEFAULT CURRENT_TIMESTAMP,
    applied_at TEXT DEFAULT '',
    applied_by TEXT DEFAULT '',
    branch TEXT DEFAULT ''              -- 迁移执行的分支范围（见 5.4 坑位 1）
)
```

### 5.2 新增服务：`services/ontology_migration.py`

```python
def diff_change(before: dict, after: dict) -> list[dict]:
    """对单条变更留痕做字段级 diff，产出标准化变更事件：
    [{kind: rename|delete|tighten_card|tighten_domrange|tighten_prop|...,
      type_kind: entity|relation|attribute, from, to, constraints}]"""

def build_plan(conn, change_log_ids: list[int] | None = None) -> dict:
    """从 change_logs（默认：上次发布后的全部未处理留痕）生成迁移计划：
    plan = {ops: [{op_type, target, payload, affected, sample, severity}],
            version_hint: 'major'|'minor', blockers: [...]}
    规则：
      - rename            → op migrate_instances（L1 语义，若留痕时未内联执行则补迁）
      - delete(force)     → op migrate_to_parent / deprecate_instances
      - tighten_domrange  → op flag_violations（只产出清单）
      - tighten_card      → op flag_violations
      - tighten_prop      → op convert_prop_values（可自动转换）+ flag_violations
      - drop attribute    → op drop_prop_key"""

def dry_run(conn, plan_id: int) -> dict:
    """逐 op 执行 SELECT COUNT + 抽样 10 条，写回 affected/sample，status=dry_run。
    不写任何业务表。"""

def apply(conn, plan_id: int, user) -> dict:
    """逐 op 在单事务内执行（只执行 migrate/convert/drop 类；
    flag_violations 类仅落库清单）。任一 op 失败整体回滚，status=failed。
    成功后写 audit + 更新 status=applied。"""

def validate_instances(conn, t: dict) -> list[dict]:
    """实例回溯校验器（被 build_plan 与 impact-preview 共用）：
    - dom/range 违例：JOIN relations × entities 端点类型比对 allowed_values
    - 基数违例：GROUP BY source_id/target_id HAVING COUNT 越界
    - 属性值违例：json_each(properties) 比对 attribute 类型定义
    返回 [{instance_id, kind, detail}]"""
```

### 5.3 新增/修改接口

| 接口 | 方法 | 说明 |
|------|------|------|
| `/api/knowledge/ontology/impact-preview` | POST | **新增**。入参：编辑后的完整 type body（+ tid）。返回：`{severity, renamed_instances, affected_relations, usage:{as_parent,as_source,as_target,instances}, violations:[...], suggestion:"L1 内联\|需发布迁移"}`。**只读，不写库**（在事务外用临时 diff 计算） |
| `/api/knowledge/ontology/migrations` | GET | 迁移计划列表（含 pending/applied，发布弹窗与治理页共用） |
| `/api/knowledge/ontology/migrations/{id}/dry-run` | POST | 生成/刷新 dry-run 报告 |
| `/api/knowledge/ontology/migrations/{id}/apply` | POST | 确认执行（需 WRITE_PERMS） |
| `/api/knowledge/ontology/version/publish` | PUT（修改） | 发布成功后自动 `build_plan`，响应中附 `migration_plan_id`，前端据此弹出迁移面板 |
| `routers/knowledge_parts/ontology.py::ontology_update_type` | 修改 | rename 分支追加 **L1 内联迁移**（见 5.4），并把 `renamed` 写入 change_logs 扩展字段 |

### 5.4 关键代码改造点

**L1 内联迁移**（`ontology_update_type`，在 UPDATE ontology_types 之后、commit 之前）：

```python
renamed = 0
if before["name"] != body.name:
    if before["type_kind"] == "entity":
        cur = conn.execute(
            "UPDATE entities SET entity_type=? WHERE entity_type=? AND status!='deprecated'",
            (body.name, before["name"]))
        renamed = cur.rowcount
    elif before["type_kind"] == "relation":
        cur = conn.execute(
            "UPDATE relations SET relation_type=? WHERE relation_type=?",
            (body.name, before["name"]))
        renamed = cur.rowcount
# _log_ont_change 增加扩展字段 extra={"migrated_instances": renamed}
```

**发布挂钩**（`ontology_version_publish` 尾部）：

```python
plan = ontology_migration.build_plan(conn)   # 消费 released_at 之后的留痕
if plan["ops"]:
    plan_id = save_plan(conn, plan, version_id=vid, user=user)
    return {"ok": True, ..., "migration_plan_id": plan_id,
            "migration_summary": {"ops": len(plan["ops"]),
                                  "affected": sum(o["affected"] for o in plan["ops"])}}
```

### 5.5 两个必须处理的坑

1. **分支维度**：`entities` 主键是 `(id, branch)`，且存在多分支。迁移 SQL 默认**全分支执行**（`branch` 条件不限定），并在 migrations 表记录 `branch='*'`；若后续需要分支级迁移（不同分支本体版本不同），payload 中显式指定 branch 列表逐分支执行。与 `triple_commit` / `branch_repo` 的合并语义对齐：迁移发生在**发布基线上**，dev 分支合并时由 merge 逻辑重放 change_logs 校验。
2. **幂等与重复执行**：所有 op 的 SQL 必须可重入（UPDATE ... WHERE entity_type=旧名 天然幂等；drop_prop_key 用 json_remove 前判存在）。migrations 表以 `change_log_id + op_type` 建唯一索引，防止同一留痕生成重复 op。

## 7. 实施计划（三个 PR，可独立合入）

| 阶段 | 内容 | 交付 |
|------|------|------|
| **P1 止血**（优先） | L1 rename 内联迁移 + impact-preview 接口 + 编辑抽屉徽章 | 解决最高频的 G1 缺口；改动集中在 ontology.py + 23-ontform.js |
| **P2 迁移执行** | ontology_migration.py + migrations 表 + publish 挂钩 + 发布弹窗改造 | 解决 G2/G3：删除与约束收紧的实例处理 |
| **P3 根治（建议排期）** | 实例引用从 name 切换到 IRI（P0-1 已有 IRI 主轴）：`entity_type`/`relation_type` 存 IRI，name 仅为显示名，一次数据迁移脚本 + 读写兼容层 | 改名退化为纯展示层操作，L1 内联迁移随之退役；SHACL/推理/导出全部对齐 IRI |

**P3 是长期正确的做法**：软引用按名匹配是所有问题的根源，趁当前数据量小尽早切换成本最低。

## 8. 测试与验收

沿用 `tests/manual_verify/verify_*.py` 惯例，新增：

- `verify_ont_rename_migrate.py`：改名后实例/关系计数不变、无悬空类型引用；失败事务回滚验证
- `verify_ont_impact_preview.py`：各编辑类型 → severity 与违例清单正确性（构造 dom/range 违例、超基数、非法属性值 fixture）
- `verify_ont_migration_flow.py`：publish → plan 生成 → dry-run → apply 全链路；重复 apply 幂等；多分支行为
- 回归：现有 `verify_ont_graph.py`、`test_api.py` 本体用例

验收口径：
1. 任何本体改名操作后，`SELECT COUNT(*) FROM entities WHERE entity_type NOT IN (SELECT name FROM ontology_types WHERE type_kind='entity')` 恒为 0（切换 IRI 后按 IRI 口径）；
2. 发布 major 版本必然伴随迁移计划（或显式"无实例影响"结论）；
3. 全部迁移操作可在 change_logs + migrations 表 + audit_logs 三处对账。

## 9. 风险与决策点

| 决策点 | 建议 |
|--------|------|
| L1 内联迁移是否会拖慢保存？ | 两条 UPDATE 走 `entity_type` 索引（建议补 `idx_entities_entity_type`），万级数据 <100ms，可接受 |
| 违例自动修复边界 | 只自动做"可逆、无歧义"的 op（rename/清死键/自动类型转换）；删关系、改端点等一律人工裁决 |
| IRI 切换时机 | P3 独立排期，先做 name→IRI 双写（新写 IRI、读兼容 name），稳定一个版本后切读 |
| 存量已悬空数据 | 上线前跑一次 `build_plan` 全量扫描，把历史悬空实例生成一次性的补迁计划 |
