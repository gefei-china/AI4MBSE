# 数据冗余诊断报告：备份文件与向量存储

> 日期：2026-11-11　方式：**只读**（生产库 `mode=ro`），**未删除任何数据**
> 结论先行：**存在严重冗余，但主因不是"每次执行备份"，而是①备份文件堆积 ②向量以 JSON 文本存储**

---

## 0. 结论先行（三句话）

1. **系统本身不自动备份**。那些 `.bak` 是**我们历次改动前手工复制**的，**从不自动清理** ⇒ 已堆积 **3.8 GB**。
2. **`document_chunks` 315 MB（占库 88%）**，其中 `embedding` + `hyde_embedding` 两列各 **145.6 MB** ⇒ **是正文（2.8 MB）的 52 倍**。
3. **每次执行确实会写 7 张日志表**，但合计增长很慢（近 7 天约 5900 行，**不到 5 MB**）⇒ **不是冗余主因**。

## 1. 备份文件：3.8 GB 堆积，从不清理

```
mbse.db                      357.2 MB   ← 生产库（唯一在用）
mbse.db.bak.binding_2026…    357.2 MB   ← 11-11 本次改动前复制
mbse.db.bak.provider_2026…   357.0 MB   ← 11-11 本次改动前复制
mbse.db.bak-v16 … v23        306.4 MB × 8 个   ← 10-09 一批改动，每个都整库复制
mbse.db.bak-p1-3             306.4 MB
mbse.db.bak-mem-1017         306.4 MB
另有 10 个残留 -shm / -wal   ≈ 0 MB
────────────────────────────────
合计                         4135.6 MB ≈ 4 GB
```

### 为什么会有 `-shm` / `-wal` 残留

`shutil.copy2` 把 SQLite 的 WAL 旁文件一起复制了，但**只复制主库文件、不复制 WAL 内容**
⇒ 这些 `.bak` **并不能完整恢复到对应时刻**（WAL 里可能有未 checkpoint 的事务）。
⇒ **它们既是空间浪费，又不是可靠备份**（这条比"占空间"更值得说）。

### 建议（**需你确认后我再执行**）

| 动作 | 可回收 | 风险 |
|---|---|---|
| 删除 10-09 及更早的 10 个 `.bak` | **~3.0 GB** | 低（那些改动已上线多日） |
| 保留最近 1~2 个（如本次的 provider/binding） | 714 MB | — |
| **建立备份纪律**：整库备份改成**只备份必要表**（messages/tool_call_logs 等）或用 `sqlite3 .backup`，并**只留最近 2 份** | 预防 | — |

> 我的建议：**立即清掉 10 个旧 .bak 回收 3 GB**，但**保留本次两个**（回滚用）。

## 2. `document_chunks` 315 MB：向量以 JSON 文本存储

### 实测构成

| 列 | 体积 | 相对正文 |
|---|---|---|
| `content`（正文） | **2.8 MB** | 100% |
| **`embedding`** | **145.6 MB** | **5289%** |
| **`hyde_embedding`** | **145.6 MB** | **5289%** |
| `bm25_text` | 2.9 MB | 107% |
| `hyde_questions` | 0.4 MB | 16% |

6727 行，`embed_version` 全为 `openai-compat`。

### 为什么这么大

实测单个向量 **22,954 字符**，开头是：
```
[0.029537132009863853, -0.029986176639795303, 0.043756868690252304, ...
```

**1024 维 float 以 JSON 文本存**，每个数 17~20 个字符 + 逗号 ⇒
**17 KB/维对 8 KB 的 float32 二进制，纯浪费 5~6 倍**。

### 这是不是设计如此？——是，且已有缓解机制

`tools/verify/verify_vector_binary_cache.py` 的文档写明：
> 「**权威源不变**：JSON 仍是 `document_chunks.embedding`，二进制只是**派生缓存**」

也就是说：**检索侧已经改用二进制 L2 缓存**（提速 + 省内存），
但**DB 里的 JSON 列仍是权威源**，所以**磁盘占用没降**。

### 建议（分两档，需你拍板）

| 方案 | 收益 | 代价/风险 |
|---|---|---|
| **A. 只清旧 .bak**（推荐先做） | **~3 GB** | 极低 |
| **B. 向量列改二进制 BLOB** | 再省 **~240 MB** | **高**：JSON 是权威源，改存储要迁移 6727 行 + 动检索/入库/备份全链路；且 `verify_vector_binary_cache` 的"权威源不变"契约要重写 |
| C. 加固生成：确认 `embed_version` 切换时旧向量会被清理 | 预防 | 低 |

⇒ **我的建议是先做 A，不做 B**。理由与米爸"不要为了省 token/空间导致流程走不通"一致：
**B 是结构性改动，收益（240 MB）远小于风险**；而 A 是纯清理。

## 附：复现方式（全部只读）

```python
import sqlite3, os, glob
c = sqlite3.connect('file:mbse.db?mode=ro', uri=True)   # 只读
# 表体积
c.execute("SELECT name, SUM(pgsize) FROM dbstat GROUP BY name ORDER BY 2 DESC").fetchall()
# 向量构成
c.execute("""SELECT SUM(LENGTH(content)), SUM(LENGTH(embedding)),
             SUM(LENGTH(hyde_embedding)) FROM document_chunks""").fetchone()
# 备份文件
[os.path.getsize(f) for f in glob.glob('mbse.db*')]
```
