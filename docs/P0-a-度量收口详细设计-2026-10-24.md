## 1. 设计基线：调研对方案预设的六处实测纠正

详细设计必须建立在实测事实之上。调研发现方案写作时的 6 处预设与真库/代码不符，**本设计按实测口径修正**：

| # | 方案预设 | 实测事实（证据） | 对设计的影响 |
|---|---|---|---|
| 1 | 新建 `capability_call_logs` 一张表统一度量 | **`tool_call_logs` 已存在且就是准统一调用日志**：2179 行，`call_kind`(tool/skill) × `tool_type`(builtin/skill/http/mcp/zhiyuan) 已表达五类能力，主链路写入覆盖率 100%（`agent/pipeline_parts/tools.py:1172-1179`） | **不新建表，扩展 `tool_call_logs`**（加 `capability_id` 列 + 补 3 个盲区）。新建表会造成双轨：旧读侧 5 个消费点看不到新数据，违背"不建平行子系统"的产品教训 |
| 2 | `plugin_call_logs` 0 行是因为缺统一收口 | 确认 0 行，但原因是**唯一写点是插件沙箱试运行**（`plugin_system/executor.py:198`），生产路径的插件调用按其执行形态（skill/tool）本就走 `tool_call_logs` | 收口方案：沙箱调用**双写**进统一日志；`plugin_call_logs` 保留不删（向后兼容） |
| 3 | 技能 use_stats「15/25 为空」 | 实测 **9/31 为空**（22 个非空），空的 9 行全部是从未被触发的技能 | 长尾清单口径按实测重述（见 3.1.6） |
| 4 | 27 个 Agent 中 15 个零调度 | 实测 **30 个 Agent、8 个零调度**（active 口径 4/20）；agents 表**无任何 usage 字段**，调度记录在 `agent_tasks`（271 行，`agent_id` 存 Agent 名） | 零调度判据改用 `agent_tasks` LEFT JOIN 口径（SQL 见 3.1.6）；`lifecycle.py:135-143` 的 usage_sql 即官方口径 |
| 5 | BadCase 按 `error_profile` 聚类驱动告警 | `error_profile` **不是 bad_cases 的字段**——它是监控面板的会话级计数视图（`routers/monitor.py:626-645`）；失败聚类实际在 `core/attribution.py:collect_patterns()` | BadCase 聚类走 attribution 现有出口，不新增字段 |
| 6 | 「登录失败突增」规则守护登录入口 | 实测该规则 38 条触发记录中，指标 `auth_failed_1h` 统计的是 `auth_% AND failed`，其中 **491 条是身份拒绝**（`auth_identity_reject`），真登录失败仅 1 条 | 拆指标：保留 `auth_failed_1h`（身份拒绝口径）另建 `auth_login_failed_1h`，规则语义归位（见 3.4.4） |

**其余方案预设经实测确认成立**：告警引擎 300s 周期 + 30min cooldown（`main.py:90-92`）、`hil_confirmations` 10 条全 pending 且 10/10 超 24h、`audit_logs` 哈希链 4623 行当前完好、`bad_cases` 0 行、`query_trace` 3270 行无质量列、`llm_usage_stats` 13352 行。

## 2. 总体架构

```
┌────────────────────────────────────────────────────────────────────┐
│ 能力源表（权威数据不动）                                            │
│  tools(44)  skills(31)  plugins(127)  mcp_servers(2)  prompts(1)  │
└──────┬──────────────┬──────────────┬──────────────┬───────────────┘
       │ ① 投影（启动全量 reconcile + 运行时增量挂点）
       ▼
┌──────────────────────┐   ② 聚合（只读源，周期刷新）   ┌────────────────────┐
│ capability_registry  │◄──────────────────────────────│ tool_call_logs     │
│ （逻辑统一层/物化）   │      call_count/last_used_at   │ （统一调用日志）    │
│  capability_id 主键  │                                │  +capability_id 列 │
│  status/lifecycle    │                                │  2 主挂点 + 3 盲区 │
│  version/visibility  │                                │  + 1 沙箱双写     │
│  risk_level          │                                └────────┬───────────┘
└──────────┬───────────┘                                         │ ③ 供数
           │ 长尾清单 / 市场可见性 / 版本绑定                      ▼
           │                                      ┌───────────────────────────┐
           │                                      │ alert_evaluator（已有）   │
           │                                      │ GLOBAL_METRICS + 6 新指标 │
           │                                      │ 10 条预置规则（5 立即可上 │
           │                                      │ 3 补指标 / 2 代理口径）   │
           │                                      └───────────┬───────────────┘
           ▼                                                  ▼
┌──────────────────────┐                        ┌───────────────────────────┐
│ evolution_report周报 │                        │ BadCase 台账（真实入库）   │
│ 长尾治理只提议不执行 │                        │ collect→一键apply→告警闭环 │
└──────────────────────┘                        └───────────────────────────┘
```

设计原则（全部来自产品既有纪律，本设计不新创）：
- **权威数据不动**：registry 是投影，源表删了行 registry 才删（reconcile 保证），任何读能力详情都回源表。
- **不建平行子系统**：度量扩展已有 `tool_call_logs`；告警复用已有引擎与表；BadCase 复用已有 collect/apply 函数与前端按钮；前端零新页面。
- **不造假数据**：mcp 无探测数据不展开 tool 级投影；指标缺数据返回 None（引擎已有"没数据≠0%"语义，`alert_evaluator.py:216-218`）。
- **只提议不自动执行**：长尾清单进周报由人决定，不自动停用能力（延续自进化纪律）。

## 3. 详细设计

### 3.1 capability_registry 逻辑统一层

#### 3.1.1 表 DDL（新表，挂 `database/schema.py`，老库经 `ensure_schema` 幂等创建）

```sql
CREATE TABLE IF NOT EXISTS capability_registry (
    capability_id   TEXT PRIMARY KEY,        -- 统一 ID，规则见 3.1.2
    kind            TEXT NOT NULL,           -- tool | skill | plugin | mcp_server | mcp_tool | prompt
    display_name    TEXT DEFAULT '',         -- 展示名（源表 name，plugins 取 manifest label）
    source_table    TEXT NOT NULL,           -- tools/skills/plugins/mcp_servers/prompts（权威所在）
    source_id       TEXT NOT NULL,           -- 源表业务键
    status          TEXT DEFAULT 'active',   -- active | disabled（启停态，由源表同步）
    lifecycle       TEXT DEFAULT 'published',-- draft | published | deprecated（发布态，映射见 3.1.4）
    version         TEXT DEFAULT '1.0.0',    -- 源表 version 缺省补 1.0.0
    publisher       TEXT DEFAULT '',         -- 作者
    visibility      TEXT DEFAULT 'private',  -- private | team | public（源表 scope 映射）
    risk_level      TEXT DEFAULT 'read',     -- read | write | destructive（驱动 HIL 强度，P1 用）
    builtin         INTEGER DEFAULT 0,
    call_count      INTEGER DEFAULT 0,       -- 度量投影：累计调用次数（聚合而来，非双写）
    last_used_at    TEXT DEFAULT '',         -- 度量投影：最近调用时间
    fail_count      INTEGER DEFAULT 0,       -- 度量投影：累计失败次数
    updated_at      TEXT DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX IF NOT EXISTS ix_cr_kind   ON capability_registry(kind);
CREATE INDEX IF NOT EXISTS ix_cr_source ON capability_registry(source_table, source_id);
CREATE INDEX IF NOT EXISTS ix_cr_last   ON capability_registry(last_used_at);
```

**为什么不用 VIEW**：度量字段（call_count 等）需要物化；SQLite VIEW 无法承载聚合且每次查询全表扫 `tool_call_logs`。物化表 + reconcile 保证一致性，权威数据仍在源表。

#### 3.1.2 capability_id 规则（每类能力的统一 ID）

| kind | capability_id 格式 | 选型理由 |
|---|---|---|
| tool | `tool:{name}` | tools.name UNIQUE，且 `agent_tools.tool_name` 存的就是 name（绑定口径） |
| skill | `skill:{id}` | skills.name **无 UNIQUE 约束**（实测），id 才唯一 |
| plugin | `plugin:{plugin_id}` | plugin_id UNIQUE，且 `plugin_versions` 以此为外键 |
| mcp_server | `mcp:{name}` | 连接级投影，必建 |
| mcp_tool | `mcp:{name}:{tool_name}` | 工具级投影，依赖探测数据（见 3.1.5 展开规则） |
| prompt | `prompt:{id}` | id 唯一 |

#### 3.1.3 五源表 → registry 字段映射表

| registry 字段 | tools | skills | plugins | mcp_servers | prompts |
|---|---|---|---|---|---|
| kind | tool | skill | plugin | mcp_server | prompt |
| source_id | name | id | plugin_id | name | id |
| status | status（active/disabled 直用） | `status='published' AND enabled=1` → active，否则 disabled | 8 态映射见 3.1.4 | `enabled=1 AND status='online'` → active，否则 disabled | status（draft/published/disabled 直用） |
| lifecycle | 恒 published（tools 无 draft 概念，status 是启停不是发布态） | status 直用（draft/published/disabled→deprecated） | 8 态映射见 3.1.4 | 恒 published | status 直用 |
| version | version（缺省 v1.0） | version（缺省 v1.0） | current_version（缺省 0.0.1→规范为 1.0.0 起） | **无列** → 取 server_info JSON 内版本，缺省 1.0.0 | version（缺省 v1） |
| publisher | owner（缺省 ''） | **无列** → frontmatter JSON 取，缺省 '' | author_name | **无列** → '' | created_by |
| visibility | scope 映射：public/platform→public，personal/private→private，team→team | scope 同左 | scope 同左 | scope 同左 | **无 scope 列** → private |
| risk_level | risk_level（已有列！`columns.py:152`，实测 low 等值） | **无列** → 缺省 read；skill_type 为沙箱执行类标 write | **无列** → 缺省 write（插件可改外部状态） | **无列** → 缺省 read（MCP 工具按调用时实际语义，P1 再细化） | **无列** → read |
| builtin | builtin | builtin | builtin | builtin | 0 |

> 注：`risk_level` 五表中只有 tools 有真列，其余四类缺省值在映射表里写明——**缺省值写入 registry 的投影逻辑，不改源表**（源表加列属另一个决策，P1 市场三档时再做）。

#### 3.1.4 lifecycle 映射（发布态归一，解决"三套并存"）

实测三套发布态语义并存（skills/prompts 用 status；plugins 8 态状态机；tools/mcp 无发布态），registry 归一为三态：

| 源表原值 | registry.lifecycle |
|---|---|
| skills: draft / prompts: draft / plugins: draft, submitted, rejected | draft |
| skills: published / prompts: published / plugins: published, private（private=已发布但 scope=personal） | published |
| skills: disabled / prompts: disabled / plugins: disabled, deprecated, removed / tools: disabled（仅 status） | deprecated |
| tools: active / mcp_servers: online+enabled | published（无 draft 概念，直发布） |

`status`（启停）与 `lifecycle`（发布态）**正交**：一个能力可以 lifecycle=published 但 status=disabled（发布过但被停用），这正是 tools 表现状（status=disabled 的 1 行）。

#### 3.1.5 投影与刷新机制（双写收口）

**三条刷新路径，全部幂等，可反复跑：**

1. **启动全量对齐**（兜底，防任何漂移）：`seed_registry.py:113` `seed_all()` 末尾追加 `reconcile_capability_registry(conn)`：
   ```sql
   -- ① 删幽灵（源表已不存在）
   DELETE FROM capability_registry WHERE source_table='tools'
     AND source_id NOT IN (SELECT name FROM tools);   -- 五类各一条同构 SQL
   -- ② 全量投影（每类一条 INSERT ... SELECT ... ON CONFLICT 更新）
   ```
2. **运行时增量**（新建/改能力即时可见）：复用现成挂点 `repositories/studio_repo.py:14-25` `_sync()`——它已被每个 create/update/delete/publish 调用（工坊 API 全部路径），在其内追加 `_refresh_registry_row(源表, 源键)`（单行投影刷新，O(1)）。
3. **插件侧**：`plugin_system/store/crud.py:16/54`（create/update_plugin）与 `legacy_sync.py:284`（同步桥）执行后调用同款单行刷新。

**mcp_tool 级展开规则**（不造假）：仅当 `mcp_servers.capabilities` JSON 非空（已探测过）时，按其中工具清单展开 `mcp:{name}:{tool}` 行；未探测的 server 只投影 `mcp:{name}` 一行，**不生成占位 tool 行**（延续 `seeds.py:96-99`「不写死假健康态」的既有纪律）。

#### 3.1.6 度量投影与长尾清单（只读聚合，不双写）

- **聚合**：新开 daemon 线程或搭车 `alert_evaluator` 300s 周期（推荐搭车，零新线程），执行：
  ```sql
  UPDATE capability_registry SET
    call_count = (SELECT COUNT(*) FROM tool_call_logs l WHERE l.capability_id = capability_registry.capability_id),
    fail_count = (SELECT COUNT(*) FROM tool_call_logs l WHERE l.capability_id = capability_registry.capability_id AND l.ok=0),
    last_used_at = (SELECT MAX(l.created_at) FROM tool_call_logs l WHERE l.capability_id = capability_registry.capability_id)
  WHERE kind IN ('tool','skill','mcp_tool');   -- plugin 沙箱口径单列
  ```
  历史行 `capability_id` 为空的行按 `tool_type+tool_name` 回填后计入（见 3.2.3）。行数量级 2179，全表聚合无压力；`tool_call_logs` 需确认/补 `(capability_id)` 索引（实施 S2 检查项）。
- **绕开 use_stats 锁风险**：skills.use_stats 是 memory.py 读-改-写覆盖更新（无行级锁），聚合**只读 tool_call_logs 不碰 use_stats**，两个口径并存互不干扰。
- **零调度治理**：长尾清单 = `lifecycle='published' AND status='active' AND call_count=0 AND created>90 天`（Agent 维度另给一条：`agent_tasks` LEFT JOIN 口径）：
  ```sql
  -- 能力长尾
  SELECT capability_id, kind, display_name FROM capability_registry
  WHERE status='active' AND call_count=0
    AND julianday('now') - julianday(updated_at) > 90;
  -- Agent 零调度（官方口径 = lifecycle.py:135-143）
  SELECT a.id, a.name, a.status FROM agents a
  LEFT JOIN agent_tasks t ON t.agent_id = a.name
  GROUP BY a.id HAVING COUNT(t.id) = 0 ORDER BY a.id;
  ```
  出口：`evolution_report` 周报新增「长尾能力」一节（只列清单+天数，**不含任何自动停用动作**）。实测基线（2026-10-24）：技能 9 个零触发 + Agent 8 个零调度（active 4）。

### 3.3 版本与发布态（方案 4.1.2）

- **registry.version 非空率 100%** 作为门禁（3.1.3 映射表已保证缺省补齐）。
- **发布即生效**：Agent 绑定 `agent_tools` 现状无 pinned_version（164 行绑定只存 tool_name）。P0-a **不加** pinned_version 列（属方案 4.1.2 的 P1 深化），只做：registry.lifecycle 让"哪些能力是 published 可见的"第一次可查——这是发布语义的地基，绑定版本化在地基之上做。
- **plugin_versions 复用范围**：132 行（published 122）仅覆盖 plugins，五类 legacy 表版本在各表 version 列。P0-a 不建统一版本表，registry.version 投影即"当前生效版本"查询入口；版本快照冻结（capability_versions 新表）留到 4.1.2 深化，本文档只预留接口位置（`core/setting_keys.py` 同款：一个模块常量声明预留，不实现）。

### 3.4 告警规则 10 条（方案 4.3.1）

#### 3.4.1 引擎机制回顾（决定 10 条规则怎么"落地"）

`core/alert_evaluator.py` 是**metric 白名单 + 四则比较**引擎（`alert_evaluator.py:222-223`），不是表达式引擎。所以"预置 10 条"= 两部分：

1. **规则行**：`INSERT INTO alert_rules (name, metric, operator, threshold, level) VALUES (...)`（模板即现有 id=2 行）；
2. **指标供数**：metric 必须在 `GLOBAL_METRICS`（`alert_evaluator.py:23-46`）且 `collect_global_metrics()` 有取数段——**否则规则建了永不触发也永不报错，正是"假实现"同型缺陷**。门禁 F（见第 4 节）专门防这个。

#### 3.4.2 十条规则预置表（INSERT 级）

**第一档：立即可上（5 条，纯 INSERT，指标已在 GLOBAL_METRICS）**

| # | name | metric | op | 阈值 | level | 依据 |
|---|---|---|---|---|---|---|
| R2 | 成本突增（今日超昨日同期3倍） | `cost_today_vs_yday` | >= | 3 | warning | 日成本量级 <$0.5，绝对值无意义必须用倍数；引擎同口径（`alert_evaluator.py:92-99`） |

| R4 | 审计链破损 | `audit_chain_ok` | < | 1 | critical | 哈希链 4623 行当前完好；缺省视为 1.0 不造假告警 |

### 3.5 BadCase 真实入库（方案 4.3.2）

三层开关现状（实测）：函数默认 dry-run（`badcase.py:147`）→ API 需显式 `{"apply":true}`（`routers/monitor.py:728-744`）→ 配置组 `badcase.*` 六键（`core/config.py:1058-1065`）。**设计不改安全默认，只把"从未 apply"变成可见状态**：

2. **一键 apply**：前端按钮已存在且已接线（`static/js/mods/31-admin.js` `runBadcaseCollect(true)`，门禁 E3/E4 锁定）——**前端零改动**，只在周报节里放同一个入口。
3. **入库后闭环**（真库实测预告，只读复刻检测器 SQL）：30 天窗口 apply 一次 = **6 条 open BadCase**（llm_call_failed，6 主题/17 起事件，全 severity=high；llm_truncated 与负反馈检测器当前 0 候选）→ `badcase_open_count=6 ≥ 5` → R5 规则立即触发 → alert_events 落一条 open → **闭环自证**（告警守护的东西真的出现了，守护面第一次被真实数据点亮）。
4. **聚类驱动**：入库后按 `core/attribution.py:collect_patterns()` 现有出口（首坏步聚合）进 monitor 面板，不新增字段（纠正见第 1 节 #5）。
