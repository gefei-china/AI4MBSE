# 编排级重规划：双路径统一 + 流式/非流式差异（含两个真实缺陷）

> 日期：2026-11-04（第二轮）
> 起因：上一轮把「巡检 / 提前收敛」在**流式路径**开启并验证通过，但非流式路径
> （`_planner_core`：Flow 节点 / 直调 / `POST .../chat`）**一行 replan 都没有**；
> 同时用户追问「流式与非流式怎么切、差异是什么、能不能在对话框给开关」。

## 0. 结论先行

| 项 | 结论 |
|---|---|
| 重规划闸门 | 收敛为**唯一出处** `services/replan_loop.gates()`（21 个键），两条路径共用 |
| 非流式路径 | 已接入同一决策器，**真的会**「观察 → 重评估 → 取消/停止/精修」 |

## 1. 为什么要把闸门「收成一份」

上一轮的真实状态：

- 流式路径（`stream.py`）在**三个** `try/except` 块里内联读 21 个 `replanning.*` 键；
- 非流式路径（`_planner_core`）**一个都不读**。

结果不是"两条路径行为不同"，而是**同一句话走不同入口会有不同能力**。更根本的风险：
下次往配置里加一个闸门键，**必有一边漏读**——本仓已因
「`AgentRegistry.resolve` 只认 name、`resolve_agent_name` 又不认 display_name」付过代价。

### 做法

新增 `services/replan_loop.py`：

| 组成 | 内容 |
|---|---|
| `GATE_DEFAULTS` | 21 个闸门的**默认值唯一出处**（含 `retry_once` / 重画 / 指令 / 巡检四组） |
| `gates(cfg)` | 统一读取 + 类型归一；**读不到配置 ⇒ 全关**（绝不"因读不到就开巡检"） |
| `ReplanLoop` | 持有巡检节奏水位（done 计数 / 上次巡检时刻 / 耗时窗口），`decide()` 产出决策列表 |
| `make_decision_writer` | 写 `replan_decisions`（与流式 `_write_decision` 同表同列同归一化） |
| `defer_optional` 语义 | 见 §3（在 `TaskQueue.ready_tasks` 上） |

**决策纯函数仍复用 `services/replan_health.py`**（`early_stop_plan` / `health_probe` / `probe_due`）——
本模块只统一「闸门 + 节奏 + 顺序」，**不复制判定**。

**应用动作仍各自实现**：流式要发 SSE（`plan_revised` 事件），非流式要写回 `data["replan"]`。
这是**呈现差异**，不是第二套判定。

## 2. 非流式路径接入（`_planner_core`）

在 `while pending_count > 0` 循环的**迭代边界**（`ready_tasks` 之前）插入决策：

```python
_decs = _rl.decide(_done_items, TaskQueue.tasks(conn, run_id), latencies_ms=_done_lats)
for _d in _decs:
    early_stop → TaskQueue.cancel(非必需待跑) + executed 记 skipped + warnings
    stop       → TaskQueue.block(剩余) + warnings
    refine     → UPDATE 剩余任务 context（追加「巡检精修」说明，不改拓扑）
    none       → 只记 _replan_notes（"为什么不动"同等重要）
```

决策摘要进 `data["replan"]`，并透传到非流式 `card_data["replan"]`、`card_data["plan_guard"]`
（此前这两项只有流式有，非流式"改了也看不见"）。

## 3. ★ 真发现：早停在扇出型计划下**从来不会触发**

### 现象

首次端到端跑非流式，三个任务（t1/t2 必需、t3 可选，t3 与 t2 并列依赖 t1）：
**全部 done，没有早停**，`data["replan"]` 为空。

插桩后看清了：

```
decide(done=0) → tasks=[t1 ready, t2 planned, t3 planned] → []
decide(done=1) → tasks=[t1 done, t2 ready,  t3 ready ] → []
（没有第三次边界：t2 与 t3 在同一批被派出，回来时两个都完了）
```

**早停的检查点只在"每批派发前"**，而扇出型计划里可选任务与最后一个必需任务
**落在同一批**⇒ 等必需任务完成时，可选任务**已经跑完了**。

上一轮流式验证之所以能生效，是因为那个计划的可选任务 `t5` 在**链尾**（依赖 t1~t4），
必需任务完成时它仍是 `planned`。**换成扇出结构，这条能力等于没开。**

### 修法

`TaskQueue.ready_tasks(..., defer_optional=True)`：**同批里若既有必需又有非必需，本轮只派必需**。

- 只推迟**一轮**，不是不跑；
- 没有必需任务可跑时**返回全部**就绪任务 ⇒ 不会死锁；
- **默认 `False`**，且只在 `early_stop` 开启时由两条路径传入 ⇒ 关闸时行为逐字节不变。

两条路径都已传：`defer_optional=bool(_rl.g.get("early_stop"))`（非流式）/
`defer_optional=bool(_rp_early)`（流式）。

## 4. ★ 真发现：计划语义校验**没接在流式主路径上**

上一轮我在 `_planner_core` 接入 `validate_pipeline_plan` 时写的是「一处接线覆盖四路：
流式/非流式/Flow 节点/直接调用」。**这是假的**：

```
$ grep -rn "validate_pipeline_plan" --include=*.py . | grep -v 测试
workflows/planner.py:513
```

只有一处，而**流式主路径 `_stream_orchestrated_flow` 自己建计划**（不调用 `_planner_core`），
所以真实用户的 SSE 会话**从未**做过阶段序/完备性校验。

已补：在流式 `create_plan` 之前跑同一校验器 ——

- `mode=warn`（默认）：发一条 `reasoning/progress` 事件（会话里可见）+ 日志；
- `mode=block`：抛 `ValueError`，走**既有**的"非法计划早退"通道（落 `_plan_invalid` blocked 行 + span 收口）；
- 校验器自身异常：**必须留痕**（日志 warning），不能变成"静默无问题"。

门禁 `verify_plan_guard.py` 新增 §9（4 项）锁住两条路径都在接线。

### 4.1 真机取证（流式编排，2026-11-04）

临时把 `pipeline_guard_mode=block`、`pipeline_required_stages` 扩到 5 个阶段后，
跑真实团队编排（会话 10026），拿到：

```
服务日志：计划语义校验发现 1 项问题（mode=block）：
          ! 计划缺少必需阶段：methodology_resolver、view_expansion、model_release
SSE：      出现 1 条「（计划校验）…」progress 事件
```

⇒ **校验确实在流式主路径执行了**，且违规对用户可见（此前从未发生）。

⚠️ 一个必须说清的语义：**`block` 只在 `error` 级违规时中止**（如阶段逆序、路由无法解析）；
「缺必需阶段」是 `warn` 级（对应 Capella `DCOM_*` 的完备性检查）⇒ 本次**没有中止**，
4 个任务照常执行（t1~t3 done，t4 被早停取消）。这是设计如此，不是接线失效。
`mode=block` 对 error 级违规的拦截行为由 `verify_plan_guard.py` 单测覆盖（57 项里含 block 档用例）；
**未构造 error 级违规的真机用例**（需要让模型产出逆序计划，不可控）。

同一轮的副产品：t4 `cancelled`（"目标已达成提前收敛"）⇒ **流式早停在我的 `defer_optional`
改动后仍然工作**（这条是回归证据，不是特意构造的）。

## 5. 另外两个真实缺陷（本轮修）

| 缺陷 | 实测证据 | 后果 |
|---|---|---|
| `pending_count` 只排除 `'canceled'`（一个 L），而 `cancel()` 写 `'cancelled'`（两个 L） | 真库 `cancelled` 3 行 | 已取消任务仍被算"待处理"；`while pending_count>0` 靠"ready 为空"才勉强退出；任何"这批跑完了吗"的判据永远等不到 |
| 巡检**窗口绑死节奏**：`window=probe_every_tasks` | 上一轮把节奏设成 1 后 M1 永不达标（M1 要求样本 ≥3） | `refine`（S11 精修）**静默失效**；本轮改为 `window=max(节奏, M1_MIN_WINDOW)`，流式同步 |

另修一处小的语义瑕疵：`int(x or 3)` 会把**显式的 0** 吞成 3（`probe_every_tasks=0`
本意是"只按秒巡检"）。`gates()` 里改为显式判空。

## 7. 流式 vs 非流式：怎么切、差在哪、能不能给开关

### 7.1 怎么切

**没有配置项，也没有 UI 开关**。传输形态由**端点路径**决定：

| 端点 | 实现 | 谁在用 |
|---|---|---|
| `POST /api/conversations/{id}/chat` | `execute()`（`execute.py`） | **只有 `tests/test_api.py`** |
| `POST /api/conversations/{id}/chat/stream` | `execute_stream()`（`stream.py`） | **前端全部**（`12-chatsend.js:409`、`11-pipeline.js:1926`） |

`ChatIn`（`models/conversation.py:22`）**没有 `stream` 字段** ⇒ 同一个请求体不可能"切成流式"。

想切只能：① 直接调另一个端点；② 改前端（`fetch` 的 URL）。

### 7.2 差异（实证，不是印象）

| 维度 | 流式（主路径） | 非流式（冷路径） |
|---|---|---|
| 输出 | SSE 帧：`stage / token / tool / subtask / plan_revised / done / error` | 一次性 JSON |
| 过程可见性 | 逐 token + 阶段 + 工具轨迹 | 无（等完整结果） |
| 中断 | 前端 abort + `POST /messages/partial` 固化已产出 | **没有**（断了就没了） |
| 长任务保活 | `iter_with_heartbeat_async` 心跳（单轮实测 344~1155s，无心跳会被网关掐断） | 无 |
| 降级告知 | `degrade_delta` 显式提示 mock 降级 | 只在结果里体现 |
| 澄清/续答 | `clarify-answer` → 回传 `resume_of_user_msg_id/resume_append` 给 stream | 不支持同等闭环 |
| 重规划 | 有（本轮起闸门同源） | **本轮补齐**（此前没有） |
| 计划语义校验 | **本轮补齐**（此前没有） | 有（上一轮接入） |
| 副作用完整性 | 全 | **按路径不同**（见 7.2.1，不是笼统"缺 6 项"） |

### 7.2.1 副作用差异要按**路径**分，不能笼统说"缺 6 项"（2026-11-04 复核修正）

`execute.py` 文件头列了 6 项"已知差异"。逐项 grep 核实后，**真相是按路径不同**：

| 副作用 | 非流式·**编排**（`run_planner_plan`） | 非流式·**单 Agent**（`execute` 主流程） |
|---|---|---|
| `_deposit_session_memory` 会话记忆沉淀 | ✅ `orchestration.py:495` | ❌ 仅 docstring 提及 |
| `_ensure_sysml_blocks` SysML 代码块补全 | ✅ `planner.py`（`_planner_core` 汇总后） | ❌ 仅 docstring |
| `_record_skill_feedback` 技能反馈 | ✅ `orchestration.py:497` | ❌ 仅 docstring |
| `_save_planner_flow` 编排留痕 | ✅ `orchestration.py:419` | —（该路径无编排） |
| `_is_continuation_input` 续作判定 | —（不需要） | ✅ `execute.py:935`（自动续跑用） |
| `_archive_impact_analysis` 影响分析落库 | ❌ | ❌ |

**结论**：
- 前 4 项在 `execute.py` 里**确实只出现在 docstring**（即单 Agent 路径没调用），但**编排路径有**；
- `_is_continuation_input` **不是缺口**：它是 `execute` 自动续跑的实现细节，流式走 `agent/auto_continue.py`；
- **唯一两条非流式路径都缺的是 `_archive_impact_analysis`** —— 全仓只有 `stream.py:6928` 调用它。

⇒ 上一轮"非流式缺 6 项"的说法对**单 Agent 路径**成立，对**编排路径高估了**。本表以代码为准。

此外**编排是两套实现**：`_try_orchestrate`/`_finish_orchestrated`（非流式）
vs `_stream_orchestrated_flow`（流式）。

### 7.3 能不能在对话框给用户开关？

**技术上能，但不建议现在做。** 原因是它不是"显示方式"的差异，而是**能力差异**：

- 用户选了非流式，会**丢掉副作用**（单 Agent 路径漏 5 项、编排路径漏影响分析落库，见 7.2.1），
  而这些**在界面上看不出来** —— 正是本仓反复出现的"看起来成功了"那类病；
- 而且会遇到网关超时（长任务无心跳）。

如果目的是"看着安静一点"，正确的开关是**呈现层**：保留 SSE 传输，只关打字机效果 /
默认收起过程区。这样用户拿到的是"安静模式"，不是"降级模式"。

**若确实要开放传输开关**，前置条件是（建议顺序）：

1. 补齐 7.2.1 里对应路径的缺口（`_archive_impact_analysis` 两条都缺，优先补）；
2. 让 `/chat` 也支持中断固化（客户端断开时落 partial）；
3. 再在 `ChatIn` 加 `stream: bool` 或前端设置项，并在 UI 上标明两种模式的差异。

## 8. 未做（如实登记）

1. `_stream_orchestrated_flow` 的校验结论**只进事件与日志**，未写入 `card_data`——
   三处 card_data 组装点都要改，本轮按"先让违规可见"收口，未做字段透传。
2. 非流式副作用缺口按路径不同（见 7.2.1）：单 Agent 路径漏 5 项、编排路径漏
   `_archive_impact_analysis`（两条都漏）。属独立改造。
3. 早停的 `defer_optional` 会让可选任务**晚一轮**开始；这是有意的取舍（换来可取消），
   但**没有量化**"推迟一轮"对总耗时的影响（需要真实长计划对照）。
   ⚠️ 反向风险：扇出计划里可选任务本可与必需任务并行（`max_workers≤3`），推迟后拆成两批
   ⇒ 若最终**没有**早停（可选任务确实要跑），墙钟时间可能 **+1 批**（30~120s）。
4. `probe_every_tasks=0` 的语义（只按秒巡检）已保留，但未在真机验证
   （纯函数层有覆盖：`verify_replan_loop` 3.8 用 0 走秒级节奏）。
