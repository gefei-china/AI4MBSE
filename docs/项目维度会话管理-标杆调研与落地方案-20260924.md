# 项目维度会话管理 · AI 标杆调研与落地方案

> 2026-09-24 · 背景：AI 建模数据链路已统一「归一 → 写回智源 → 智源拉取」（按工程维度路由），会话组织仍是平铺列表，需要按工程/项目维度分组管理。

---

## 一、标杆产品调研摘要

### 1. ChatGPT Projects（2024-12 推出，2025-09 全量+协作化）

- **定位**：「smart workspace」= 会话 + 文件 + 项目指令的三合一容器；
- **组织**：左侧栏 Projects 入口 → 项目内可**新建会话**，存量会话可**拖拽或菜单「Move to project」归组**，可拖出；
- **项目指令**：项目级 custom instructions **覆盖**全局指令，项目内所有会话生效（一次配置、全会话一致）；
- **记忆隔离**（2025-09 新增 project-only memory）：项目内会话只引用**本项目**的会话历史与文件，不串其他项目/全局记忆——防上下文污染；
- **协作**（2025-09）：团队成员共享项目（文件/指令/会话），权限分 chat/edit；
- **细节**：项目可设颜色/图标；每个项目有文件数上限（Free 5 / Plus 25 / Pro 40）；删除项目会连带删除内部会话（有 30 天缓冲）。

### 2. Claude Projects

- **定位**：会话 + 项目知识库（Project Knowledge，约 200K token）+ 项目指令；
- **核心体验**：项目内每个新会话自动携带项目知识与指令，**跨会话上下文零重复配置**；
- **优势场景**：长上下文、团队共享快照；免费档即提供无限 Projects（30 天实测：项目型工作流胜在「基础设施」而非单条消息智能）。

### 3. 共性模式提炼（六条）

| # | 模式 | 两家做法 |
|---|---|---|
| M1 | **项目 = 会话容器**，左栏一级入口 | 侧栏 Projects 分区，项目展开列出会话 |
| M2 | **项目内新建会话**，自动继承项目上下文 | 新会话默认落在当前项目 |
| M3 | **存量会话归组**（move to project） | 拖拽 + 会话菜单两项都提供 |
| M4 | **项目级指令/文件**，覆盖全局，会话免重复喂背景 | ChatGPT instructions / Claude Knowledge |
| M5 | **项目内记忆隔离**，跨项目不串 | ChatGPT project-only memory（显式开关） |
| M6 | 项目元数据（颜色/图标/描述）辅助辨识 | 两家均有 |

## 二、本系统现状盘点（方案的地基，已具备大半）

| 标杆能力 | 本系统现状 | 缺口 |
|---|---|---|
| 项目实体 | ✅ `projects` 表 + 项目页（含项目宪法/本体/领域） | 无导航一级入口，项目≠会话容器 |
| 会话归属项目 | ✅ `conversations.project_id` 已存在，**AI 建模按工程路由（写回/拉取）已依赖它** | 归属关系在 UI 上不可见、不可管理 |
| 项目级指令注入 | ✅ 项目宪法（Project Constitution）每次会话自动注入（对齐 CLAUDE.md 防漂移）——**等价 M4 且更强**（结构化规范/基线/决策/经验） | 无 |
| 会话列表 | ✅ 左侧 .gnav-task「任务」分组（数量统计+展开收起） | 平铺全部会话，无项目维度分组 |
| 项目文件池 | ✅ 会话文件 / 知识库（documents 按 folder）；@引用 | 无「项目文件」聚合视图（可后置） |
| 记忆隔离 | ✅ 项目宪法按 project_id 注入；图谱按 project_id 隔离（P0-1） | 会话历史检索的跨项目隔离需确认（P2） |

**关键判断**：本系统的 M4（项目宪法）、M5（图谱/注入隔离）已经比标杆做得深——缺的只是 **M1/M2/M3 的 UI 层**：入口、容器、归组。这是纯前端+少量路由的工作，不需要动数据模型。

## 三、落地方案（推荐：轻量容器，复用既有项目页）

### 3.1 信息架构

```
左侧导航
├─ ＋ 新建任务            （现状保留；若当前处于某项目上下文 → 默认归属该项目）
├─ 🗂 项目                （新增一级入口，M1）
│   ├─ 星网宽带通信系统  [26]   ← 展开 = 该项目会话列表（按时间倒序）
│   │   ├─ ＋ 在此项目新建会话   （M2：显式入口，替代"默认归属"的歧义）
│   │   ├─ P0-3 提针 post-jaech-17…
│   │   └─ …
│   ├─ 热管理系统 TMS    [8]
│   └─ ＋ 新建项目
└─ 💬 任务（未分组会话）    （现状列表降级为兜底：project_id 为空的会话）
```

### 3.2 交互设计（对齐标杆 + 本系统惯例）

1. **「项目」入口**：放在「新建任务」下方，结构复用现有 .gnav-task 分组组件（数量统计/展开收起/滚动均已现成）；
2. **项目内新建会话**：项目行 hover 出「＋」；点击 → `newTask(projectId)` 带参创建（M2）；
3. **存量会话归组（M3）**：会话行右键/「⋯」菜单 → 「移动到项目」→ 二级面板列出项目单选（本系统已有同型交互：@引用二级面板）；拖拽可后置；
4. **项目行点击**：展开会话列表（不跳页）；项目名点击区另设「⤴ 进入项目页」链接（项目宪法/图谱/智源 vc 绑定都在项目页管理，不重复建设）；
5. **当前项目上下文指示**：进入某会话后，AI 建模页顶部显示「🗂 项目名」徽章（数据源 conversations.project_id，纯展示）；
6. **建模工具绑定入口**：项目页新增「建模工具集成」小节（读写 `projects.tool_binding`，2026-09-24 已泛化为工具无关 JSON `{tool, ref, name}`，不限于智源——MagicDraw 同样通过它登记绑定，通道预留：文件导入 / SysML v2 API / Cameo 插件，接入后写回/拉取自动按绑定路由）——写回/拉取的绑定操作有了自然家。

### 3.3 不做什么（边界）

- **不做**项目级「指令覆盖」开关：项目宪法注入已是强机制，引入「覆盖/叠加」开关反而增加认知负担（标杆的 instructions 是因为它们没有宪法机制）；
- **不做**项目内记忆彻底密封（ChatGPT project-only memory）：本系统会话上下文检索应按 project_id 过滤（P2 核查项），但全局技能/本体属于平台能力，不该隔离；
- **不做**协作共享：单用户系统，M6 颜色/图标也后置。

### 3.4 分期实施

| 期 | 内容 | 工作量 | 依赖 |
|---|---|---|---|
| **P1（建议下一步）** | 导航「项目」入口 + 项目分组会话列表 + 项目内新建会话 + 会话「移动到项目」菜单 + 当前项目徽章 | 纯前端（02-shell.js / index.html）+ 1 个后端小端点（会话批量改 project_id；conversations 表已有该列） | 无 |
| **P2** | 项目页「智源集成」小节（vc 绑定 UI）；未分组会话兜底分组；拖拽归组 | 前端为主 | P1 |
| **P3** | 项目文件聚合视图（该项目会话文件 + 知识库 folder 联动）；会话历史检索按 project_id 隔离核查 | 中等 | P2 |

### 3.5 与今天链路统一的衔接

今天已把「写回智源/智源拉取」改成**按会话→工程路由**（会话未关联工程会明确报错）。项目分组入口落地后，「先归属工程、再建模、再写回/拉取」成为自然操作顺序——数据链路和组织链路在同一条工程主线上闭合。
