## 1. 逐环节实测诊断

### 1.1 文档资料层

```
解析状态：completed 12/ 12 （100%，无 failed）
```

**结论**：文档层无短板。但**所有文档的 `pipeline_detail` 都是空/无耗时**，
⇒ 无法回答"哪个文档解析慢、瓶颈在哪"。

### 1.2 解析层

```
语料构成（★ 决定一切下游假设）：
  OMG Systems Modeling Language™ V2 (1).pdf      2606 块（38.7%）
  Kernel Modeling Language™ (KerML™).pdf         2011 块（29.9%）
  Guide to writing Requirements.pdf                855 块（12.7%）
  md 类合计                                         1075 块（16.0%）
  docx / 其他                                       ~180 块

★ **84% 是 PDF**，⇒ 解析质量决定整条链路的上限。
```

**不足 1：section 粒度粗**
```
656 个块共用 section = "Systems Modeling Language v2.0"
169 个块共用 section = "1.2.1.2.3 子系统架构设计"
```
PDF 提取时只能拿到 1~2 级章节 ⇒ 数百块共用一个 section。
**后果**：hyde 问句同质化（重复率 66.5%）、section 过滤粒度粗。

**不足 2：无版面还原**
含表格特征块仅 5.3%（354）、代码块 4.3%（287）——
这不是"文档里表格少"，而是**PDF 表格被拍平成纯文本行**，
表格的行列关系丢失 ⇒ 检索到表格内容时无法还原语义。

### 1.3 切块层

```
长度分布：min=27  p25=248  中位=520  p75=573  max=5681
过短(<50 字)：  6 块（0.1%）   ✅ 健康
过短(<100 字)：363 块（5.4%）  ✅ 可接受
超长(>2000 字)：6 块（0.1%）   ★ 但max=5681，严重超限
空 section：    32 块（0.5%）  ✅ 健康
空 bm25_text：  0 块            ✅ 健康
```

**不足**：那6 个超长块（max 5681 字）说明 `size=600` 参数**没有硬约束**——
代码块/表格块走了"整块保留"分支（`code_block_chunk=True` / `table_max_rows`），
⇒ 这类块超长会稀释向量语义。

### 1.4 向量化层

```
embed_version：openai-compat100%（无版本混杂）✅
维度：1024，全部一致                        ✅
L2 范数：min=1.0000 max=1.0000→ 已预归一化   ✅
hyde_questions覆盖：6727（100%）           ✅
★★ hyde_embedding 覆盖：270（4.0%）        🔴
```

**这是本环节唯一的重大短板**。根因查明：
- `rag.hyde_embed_max_chunks = 0`（= 全量，**配置本身没问题**）
- 那 270 条**全部来自 1 个文档**（`800_SysML-v2-AI建模知识文档.md`）
-⇒ **其余 11 个文档的 hyde 向量从未生成**，检索时走`VectorEngine` 实时 bigram 兜底
⇒ **Reverse HyDE 这个能力实际只对 1/12 的语料生效**

### 1.5 检索层

```
已有能力（自研，零外部依赖）：
  ✅ BM25（字符 bigram）+ 向量 → RRF 融合（rrf_k=60）
  ✅ Reverse HyDE 兜底
  ✅ 图谱路由（graph/mixed/vector，threshold=0.70，已标定）
  ✅ 记忆召回（memory_enabled=True）
  ✅ 向量索引二进制缓存（399× 加速）

缺失能力：
  ★★ 重排：rag.rerank_enabled = False
     —— services/rag_rerank.py 有 llm_rerank 实现（LLM 打分），
        但**默认关闭**，且**没有 cross-encoder / bge-reranker**
  ★ 中文分词：VectorEngine 与 BM25Engine 都用字符 bigram
     （'宽带通信' → ['宽带','带通','通信']）⇒ 业界公认中文精度损失源
```

## 2. 行业标杆对照（2026 公开基准）

| 能力 | 行业基准 | 本工程 | 差距 |
|---|---|---|---|
| **Hybrid 检索** | 标配（dense + BM25） | ✅ 已有 RRF 融合 | **达标** |
| **Reranker** | ★**"最高 ROI 的一步"**；retrieve 20 → rerank 5 → send 3-5 | ❌ **未启用** | 🔴 **最大差距** |
| Chunk 尺寸 | 512 token + 10~20% overlap | 中位 520 字 ≈ 合理 | ✅ 达标 |
| 标题元数据 | "poor man's contextual retrieval"，零成本 | ✅ 有 section+title_enriched | ✅ 达标 |
| Contextual Retrieval | Anthropic：失败率降 35%（embedding）/ 49%（+BM25）/ **67%（+rerank）** | ❌ 无 | 🔴 可选 |
| Late chunking | nDCG@10 +3.63%，零LLM 成本 | ❌ 无 | 🟡 可选 |
| Semantic chunking | ★ **fixed-size 在 3/5 数据集胜出**；semantic 慢 14× 且不稳定胜出 | ✅ 用 fixed-size + 结构感知 | ✅ **选型正确** |
| 中文分词 | jieba / 分词器（BGE-zh 等） | 🔴 **字符 bigram** | 🔴 明确差距 |
| 评测集 | 50~100 条真实问答对 | ❌ **不存在**（`probe_qrel.py` 只是 bigram 覆盖率探测） | 🔴 **前置缺失** |

**★ 行业最重要的两条结论**（直接决定本方案优先级）：
1. **"最高 ROI 的是 hybrid + rerank，不是花哨的切分"** ——
   *"Most teams chase exotic chunking while skipping the two cheapest, highest-impact additions."*
2. **"先建评测集，再动切分"** ——
   *"reaching for semantic or contextual chunking on day one... before there is any evaluation harness to prove it helps"*

## 3. 系统性优化方案（按 ROI 排序）

### P0 · 启用重排（最高 ROI，1~2 天）

**依据**：Anthropic 数据 —— 加 rerank 后检索失败率降 **67%**，而仅靠 embedding 只降 35%。
本工程 `llm_rerank` **已实现但默认关闭**。

```
动作：
  rag.rerank_enabled = True
  rag.rerank_max_candidates = 20   （行业标准：retrieve 20 → rerank 5）
  rag.inject_k = 3~5（当前 3）
```
**风险控制**：`llm_rerank` 已有"任何异常 → 原样返回"静默降级；
门禁需验**关掉时逐字不变、开时不影响召回集**（只影响顺序）。

⚠️ **但先做 4.0 节的前置项**，否则重排效果无法证明。

### P0 · 补齐 hyde_embedding（4% → 100%，0.5 天）

**动作**：
```
./.venv/Scripts/python.exe tools/eval/rebuild_hyde.py --stage vectors
```
实测需 **810 次 embedding 调用**（270 条已有→ 全量 6727 条则需 20181 次）。
**建议**：按文档分批跑，并优先跑**高频查询命中的文档**。

### P1 · 中文分词升级（1~2 天，需谨慎）

**现状问题**：字符 bigram 对中文是"能用但不精"——
`'宽带通信'` → `['宽带','带通','通信']`，`带通` 是无意义交叉。

**方案对比**：

| 方案 | 许可 | 依赖 | 风险 |
|---|---|---|---|
| **jieba**（纯 Python） | MIT | pip 一个包 | 中文人名/术语需加自定义词典 |
| **BGE 中文 embedding 自带分词** | — | 换embedding 模型 | ★ **向量口径全变，6727 条需全部重算** |
| 保持 bigram + 扩充停用词 | — | 零 | 收益有限 |

**建议**：先做 jieba + **MBSE 术语自定义词典**（`part def`/`requirement`/`KerML` 等
从真库 6516 个唯一问句里抽词），**不动embedding 模型**（避免全量重算）。

### P1 · 建评测集（2 天，★ 后续所有优化的"证明基础"）

**这是行业反复强调的前置项，也是本工程最大的空白**。

```
产出：
  tools/eval/qrels.jsonl        —— 50~100 条 {query, relevant_chunk_ids}
  tools/eval/eval_retrieval.py  —— 输出 recall@5 / MRR@10 / 分路由对比
```
**没有它**：P0 的重排收益、P1 的分词收益**都无法证明**，
只能像本轮这样"改完看均值有没有动"（而均值又会被口径变更污染）。

### P2 · PDF 章节细分（3~5 天，价值最高但成本也最高）

针对 1.2 节的 section 粒度问题：解析时识别**页内标题**（字号/加粗/编号模式）
⇒ section 从 1~2 级细化到 3~4 级 ⇒ hyde 问句区分度与 section 过滤粒度同时改善。

### P2 · 超长块硬约束（0.5 天）

对 `code_block_chunk` / `table_max_rows` 分支加**长度上限**，
超限时二次切分（保留代码/表格语义）⇒ 治那 6 个 max=5681 字的块。

### ❌ 不建议做

| 能力 | 行业实测 | 判断 |
|---|---|---|
| Semantic chunking | 慢 14×、3/5 数据集**输给** fixed-size | **不做**（本工程已用 fixed-size，选型正确） |
| Late chunking | nDCG +3.63%，但需长上下文 embedding | 暂不做 |
| Contextual Retrieval | 失败率降 35%，但每块一次 LLM 调用 | 暂不做（先做零成本的重排） |
| Agentic chunking | ~$1000/10万文档，且边界不确定 | **不做** |

## 4. 执行顺序与验证方式

```
第 1 步  建评测集（50~100 条 qrels）        ← 没有它，后面都无法证明收益
第 2 步  跑基线：recall@5 / MRR@10 / 分路由置信
第 3 步  P0 启用重排 → 跑同一评测 → 对比
第 4 步  P0 补齐 hyde_embedding → 对比
第 5 步  P1 中文分词（jieba + 术语词典）→ 对比
────────── 若收益不显著，停止投入 ──────────
第 6 步  P2 PDF 章节细分 / 超长块约束
```

**每一��都必须用同一评测集对比**，否则就是"凭感觉改"。

## 5. 一句话给决策者

**本链路的"存储与检索骨架"已经是健康的**（100% 覆盖、维度统一、已归一化、
399× 加速、hybrid+RRF+图谱路由齐全）。真正的短板只有三个，且都不在"换框架"上：

1. **重排没开**（现成实现，关着）—— 行业最高 ROI
2. **hyde_embedding 只覆盖 4%**（链路完好，从未执行）
3. **没有评测集**（导致前两项的收益也无法证明）

⇒ **先建评测集，再开重排，最后补 hyde** ——
不要先动切分算法（行业实测：fixed-size 已是最优默认）。
