## 1. 点 2：SysML V2 生成的归一/消歧 + 写回建模软件

### 1.1 现状与缺口

| 现状 | 缺口 |
|------|------|
| Agent 可生成 SysML V2 代码（.kerml） | 生成时未强制归一：同名实体不同拼写、关系谓词不归一、类型不落本体约束 |
| 已有 text_normalize + glossary 归一能力（在知识抽取侧） | 未在生成侧复用 |
| 已有导出：SysML 2.x KerML / SysML 1.x Profile | 无"写回建模软件"通道 |

### 1.2 设计：生成端归一/消歧「三关卡」

```
关卡1 · 生成前（约束注入）──────────────────────────────────────
  LLM 提示注入：【本体类型白名单】+【术语词典规范名】+【已有元素清单】
  → 实体名取词典规范名、关系谓词取类型约束、类型取本体类型
关卡2 · 生成后（归一校验）──────────────────────────────────────
  text_normalize + glossary 归一 + SysML v2 语法校验（sysml-v2-validator）
  → 未命中词典的实体名：同名合并（按上下文+置信消歧）、自动建议新词条入候选
关卡3 · 物化前（一致性检查）────────────────────────────────────
  重名 / 悬空引用 / 循环继承 → 阻断或提示修正
  产出：规范化 .kerml 文本 + 归一报告（哪些词被归一/消歧/建议新词）
```

**关键点**：把抽取侧已有的归一能力（glossary/text_normalize）**前移注入生成侧**，形成"生成即规范"而不是"生成后再洗"。

### 1.3 写回建模软件（MagicDraw/Cameo）—— 三通道分层

| 通道 | 实现 | 成本 | 适用场景 | 建议 |
|------|------|------|----------|------|
| **A 标准文件导入**（已有导出，补一键下载） | 导出 `.kerml` / `.profile` → MagicDraw 文件导入 | 零 | 所有客户 | ✅ **MVP（本轮）** |
| **B SysML v2 API** | 对接 SysML v2 Pilot / Jupyter-KerML REST（ISO 标准 API） | 中 | 有 SysML v2 工具链客户 | ✅ 推荐（下轮） |
| **C MagicDraw OpenAPI 插件** | Cameo OpenAPI Java 插件远程写回 | 高 | 深度集成客户 | 按需 |

**架构设计**：抽象写回接口，屏蔽通道差异。

```
model_writer 接口：
  write_model(model_text, target) -> {ok, target_uri, report}
  ├─ FileWriter   （通道A：生成 .kerml/.profile 下载包 + 导入指引）
  ├─ SysMLV2ApiWriter（通道B：POST /models 到 SysML v2 服务）
  └─ MagicDrawPluginWriter（通道C：REST 到 Cameo 插件）
前端：生成结果卡新增「💾 导出建模文件」「🔗 写回建模软件」按钮
```

## 2. 点 3：工程数据 → 三元组 → 图数据库

### 2.1 现状（映射引擎已就绪，缺口在两端）

| 已就绪 | 缺口 |
|--------|------|
| R2RML 引擎完整：TriplesMap CRUD、联动校验（class 缺失阻断）、`execute_mapping`/`execute_all` | ① 数据源接入层（SysML 模型 / 需求表 / 仿真 JSON → 逻辑表） |
| 自研 triple_store（SQLite 三元组） | ② 图数据库写入（目前只落 SQLite） |
| 本体 OWL/Turtle 导出 + SHACL 校验 | ③ 端到端管线编排（无 UI/无调度） |

### 2.2 设计：R2RML 驱动的工程数据入图管线

```
工程数据源
  ├─ SysML 模型（.kerml / .xml 解析）
  ├─ 需求表（Excel / CSV：编号·名称·描述·验证）
  └─ 仿真结果（JSON / CSV：工况·参数·结果）
        ↓ ① 接入器 Adapter（新增）
          解析为标准逻辑表（列名对齐本体属性名，含 来源/版本 列）
        ↓ ② R2RML 映射（已有引擎）
          subject 模板 + class（本体类型）+ 谓词-宾语 + 关联映射
        ↓ ③ 图数据库 Writer（新增，抽象接口）
          ├─ JenaTDBWriter   → Apache Jena TDB（SPARQL，零部署，标准 RDF）✅ 推荐默认
          └─ Neo4jWriter     → Neo4j（Cypher，Bolt，企业常用）可选
        ↓ ④ 增量同步
          按 branch / 版本快照 diff → 只写变更三元组（复用 commits 机制）
        ↓ ⑤ 一致性校验（复用）
          入图后 SHACL 校验 + 本体一致性检查 → 报告
```

**图数据库选型建议**：
| 方案 | 优势 | 劣势 | 结论 |
|------|------|------|------|
| **Jena TDB** | 标准 RDF/SPARQL、与 OWL/SHACL 天然一致、零部署、与现有 OWL 导出无缝 | 非图查询性能一般（本规模足够） | ✅ 默认 |
| **Neo4j** | 图遍历强、企业生态 | 需映射 RDF↔属性图、部署重 | 企业版可选 |

**复用清单**：r2rml_engine（映射执行）✅ / ontology 导出（写图前置）✅ / SHACL（入图校验）✅ / branches（增量版本）✅ —— 实际新增工作量集中在 **Adapter + Writer + 编排 UI**。

### 2.3 落地切分
- **P0**：SysML/需求 CSV → R2RML → Jena TDB 写入 + 「数据集成」页（映射管理已有 API，补执行入口+结果页）
- **P1**：仿真 JSON 接入器 + 增量同步（按 branch diff）
- **P2**：Neo4j 适配器 + 图查询问答（消费侧打通）

## 3. 点 4：AI 原生 —— 会话入口统管全系统

### 3.1 现状：会话只服务建模
- 意图路由（INTENTS 关键词 + Agent + 工具）目前面向**建模/知识域**
- 系统管理（用户/权限/审计/监控）无 AI 入口——只能在表单页操作

### 3.2 设计：对话式系统管理（Conversational System Management）

```
统一会话入口（现有 chat 窗口）
        ↓ 意图路由扩展（INTENTS 新增 system-mgmt 域）
┌────────────┬────────────┬────────────┬──────────────┐
│ 建模域(现状) │ 知识域(现状) │ 分析域(增强) │ 系统管理域(新增) │
└────────────┴────────────┴────────────┴──────────────┘
系统管理域内部分层：
  ├─ 只读查询（默认安全，P0）
  │    "有哪些用户？""王工什么权限？""最近审计日志？""服务运行状态？"
  │    → 工具调用（users / audit / monitor API 包装）→ 表格化回答
  ├─ 授权写操作（双重确认，P1）
  │    "创建一个新用户 xx，角色=知识工程师"
  │    → 对话回显确认 + RBAC 校验（仅 admin 角色）+ 执行 + 审计留痕
  └─ 复杂管理任务（多步 Agent，P2）
       "检查所有停用账号并生成清理建议报告" → 多工具编排
```

### 3.3 关键设计点

| 设计点 | 方案 |
|--------|------|
| **意图路由扩展** | INTENTS 增加 `system-mgmt` 关键词组（用户/权限/审计/监控/配置…）；新增 `system-admin` Agent（注册工具：查询用户/角色/权限/审计/监控——把现有 users/audit/monitor API 包装为工具） |
| **安全模型（三层）** | ① 默认**只读**（查询类直接执行）② 写操作需**对话确认**（回显+确认按钮）③ **RBAC 校验**（当前用户角色，写操作仅 admin）+ 全量**审计**（复用 audit 机制，AI 操作与手工同审计） |
| **会话即操作泛化** | 从"建模对话"泛化为"系统对话"——四域统一入口，`对话即操作`覆盖全系统；知识/分析/管理域复用同一 Agent 调度框架 |
| **回答格式** | 查询结果表格化（复用前端表格组件）+ 可下钻（点击行跳对应管理页） |
| **权限边界** | 敏感操作（改权限/删用户/改配置）一律写确认流；AI 不持有超级权限，借用户身份+角色执行（最小权限） |

### 3.4 渐进路线
| 阶段 | 能力 | 示例 |
|------|------|------|
| P0 | 只读查询（用户/权限/审计/监控/统计） | "列出所有角色及成员数" |
| P1 | 授权写操作（确认流+RBAC+审计） | "把用户 B 的角色改为知识工程师"（确认后执行） |
| P2 | 多步管理任务编排 | "生成本季度审计异常报告并归档" |

## 5. 结论（先行）

- **点 1** 已实现，确认无需改动。
- **点 2**：归一消歧的关键是**把抽取侧已成熟的归一能力前移注入生成侧**（三关卡），写回建模软件走**分层通道**——MVP 用标准文件导入（已有导出补一键下载），下轮接 SysML v2 API（ISO 标准），MagicDraw 插件按客户需要。
- **点 3**：**映射引擎已就绪**，缺口在数据源接入器（Adapter）与图数据库写入（Writer）；默认图库选 **Jena TDB**（标准 SPARQL、与 OWL/SHACL 一致），Neo4j 作企业可选——新增量集中且可控。
- **点 4**：会话入口泛化为**系统级对话**（建模/知识/分析/系统管理四域统一），系统管理域**默认只读、写操作双重确认 + RBAC + 全量审计**，安全与效率兼得——这就是"AI 原生"的完整形态。
