## 0. 结论摘要

**一句话判断**：本体模型管理模块已建成「类型建模 → 约束 → 四层校验门 → SemVer 版本 → 快照消费 → OWL/Profile 互操作 → AI 语义注入」的完整闭环，**主干能力对齐行业标杆**（Protégé 的建模面 + TopBraid EDG 的治理面 + SHACL 标准栈），当前主要差距不在"有没有"，而在四个深处：**推理深度（无标准 DL 推理器）、公理表达（Equivalent To/Inverse Of 未做实）、治理工作流（无评审/审批/能力问题 CQ）、以及三个半空转资产（10 条无快照 draft 版本、迁移工单 0 行、蓝图 0 行）**。

| 类别 | 数量 | 说明 |
|---|---|---|
| 做实的核心能力 | **16 项** | 见 §2.3 能力清单，对标无缺口 |
| 半做实（声明 > 实现） | **3 项** | Equivalent To（注释序列化）、draft 版本（无快照）、`connection`/`执行` 关系 dom/range 缺失 |
| 空转（能力在、从未跑过） | **3 项** | 迁移工单队列 0 行、蓝图草案 0 行、SWRL 孤岛页 |
| 明确没有（行业有） | **6 项** | 标准推理器、多父继承、评审工作流、CQ 机制、本体对齐、健康度趋势 |

**最高性价比的三跳（P0）**：① 把一致性检查与已建好的 `impact_preview`/迁移工单**接线**（能力已有、入口没接，零新代码）；② 体检结果**落库+趋势**（从"一次性体检"变"持续守护"）；③ 清理/收口 10 条 draft 版本。三项都不需要新建表以外的大改。

## 2. 实现逻辑全景

### 2.1 数据模型：三层 + 四附属

```
① 编辑态  ontology_types ─────────── 类型/属性/元数据的唯一编辑面（type_kind=entity|relation|attribute）
   ② 发布态  ontology_versions + ontology_version_snapshots ── SemVer + 不可变快照 + active 消费指针
   ③ 留痕    ontology_change_logs ──── 类型级 before/after（非逐字段，另有 audit_logs 字段级审计）
   ④ 附属    ontology_drafts（蓝图草案）· ontology_instance_migrations（迁移工单）· ontology_meta（IRI 策略）
```

关键设计（均有代码注释佐证）：
- **编辑态不升版本号**：2026-09-08 语义收敛——新增/更新/删除/导入/蓝图应用只写 `ontology_change_logs`，版本号仅在 publish/release 时按 diff 生成。
- **消费口径单一真源**：`ontology_semantics.active_rows(conn)`（active 版本快照；无快照/无表回退编辑态）——AI 注入、图谱 Schema、导出、体检**吃同一份**；发布门禁显式传编辑态（校验"待发布的那份"）。
- **IRI 主轴**：`make_iri`（hash-name/uuid）+ percent-encoding，与图库 `core.ns` 逐字节同源；改名时自动生成的 IRI 联动重算、用户自定义的保留。

### 2.2 模块地图（写入链 / 发布链 / 消费链 / 冷启动链 / 校验链 / 推理链）

| 链路 | 走向 |
|---|---|
| 写入链 | 前端表单 → `POST/PUT/DELETE /ontology/types` → **L1 内联迁移**（改名同事务原子替换实例/关系/属性键）→ `ontology_change_logs` + `audit_logs` |
| 发布链 | `POST /version/publish`（或 `/release`）→ **high 拦截**（待发布数据口径）→ SemVer diff（删除/dom 变更→major，新增→minor，无差异→拒绝）→ 全量快照 → active 切换 → **挂接迁移计划**（只建不执行） |
| 消费链 | `active_rows` → ① AI 建模 `schema_text()` 注入 system prompt；② `GraphStore` 写校验；③ 导出 OWL/Turtle/SHACL/Profile；④ 一致性体检 |
| 冷启动链 | 蓝图：业务文本（LLM 抽取，规则兜底）/ SysML Profile（结构化解析）→ `ontology_drafts(pending)` → 前端勾选 → `apply_drafts`（校验后写 `ontology_types`，标 applied） |
| 校验链 | ①写入时 `validate_node/validate_edge`（含继承、抽象、xsd、白名单、唯一）②编辑时 L1 内联迁移 ③发布时 high 门 ④定期体检 12 规则（`?instances=1` 附逐实例） |
| 推理链 | `ontology_reasoning`：分类（子类实例属于父类）/ 传递闭包（本体公理驱动）/ 一致性 / 对称 / 基数；`consistency_check` 接图谱工作台；SWRL 孤岛页 |

## 3. 能力边界分析

### 3.1 半做实（声明 > 实现，共 3 项）

| 项 | 现状实测 | 性质 |
|---|---|---|
| **Equivalent To（等价类）** | 前端 Description 面板有字段且**诚实标注「预留」**；后端 `equivalent_to` 在 OWL 导出中**只序列化为注释**（`# equivalentTo: x`，非 `owl:equivalentClass` 三元组）；`Inverse Of` 后端 0 命中 | 声明未做实。**比虚假徽章好**（前端不骗人），但导出物给 Protégé 用户会丢失语义 |
| **draft 版本 10 条**（v23.0.24~33） | `snapshot_count=0`、`status=draft`——版本行建了但从未发布，无快照不可回滚 | 版本状态机的"死档" |
| **`连接`/`执行` 关系缺 dom/range** | 体检 low×2，真库 249 条边中这两类**实际有存量边**（rule_data_conflict 未命中是因为没声明就无冲突可判） | 未声明 = 校验器对这两类边**无约束** |

### 3.2 空转（能力在、从未跑过，共 3 项）

| 项 | 判据 | 激活成本 |
|---|---|---|
| **迁移工单队列** | `ontology_instance_migrations` 0 行；`build_plan/save_plan/dry_run/apply` 全部实现，publish 时挂接 | 低：一次真实场景（如给 `连接` 补 dom/range 后跑 build→dry-run→apply）即闭环 |
| **蓝图** | `ontology_drafts` 0 行；`draft_from_text/draft_from_profile/apply_drafts` 全部实现 | 低：选一篇真实领域文档跑一次 |
| **SWRL** | `swrl.py` 端点存在，主链不消费（skill 记录为"孤岛页"） | 中：需定义 SWRL 规则与图谱推理的边界 |

### 3.3 明确没有（行业有、本工程无，共 6 项）

1. **标准 DL 推理器**（HermiT/ELK）：自研规则引擎覆盖 6 类推理，但**不可满足性检查、解释（justification）、真实分类重算**没有。注意：私有化离线+零外部依赖是既定约束，引入 jar 需单独评估（见 §6-P2）。
2. **多父继承**：单 `parent_id`；OWL 多重特化（`part def C :> A, B` 类场景）无法表达。当前 `schema_text`/SHACL/校验都按单链设计。
3. **治理工作流**：有留痕（change_logs + audit）和权限门，但**无草稿评审/审批流、无评论、无变更集（changeset）评审、无编辑锁**。TopBraid EDG/WebProtégé 的核心差异项。
4. **Competency Questions（CQ）**：行业"验证"（validation，区别于 verification）的标准手段——本体是否回答业务问题。本工程无 CQ 机制。
5. **本体对齐/matching**（OAEI/LogMap 类）：多本体合并场景无能力。
6. **健康度趋势**：体检结果不落库、无历史曲线（一次性报告）。

### 3.4 边界纪律（本模块"刻意不做"的，别当缺口报）

- **不引外部图数据库**：`GraphStore` 抽象保留 Neo4j 适配位，SQLite 基线不变（既定决策）。
- **不做 R2RML 数据集成**：2026-09-01 R1=B 已移除，`ontology.py:373` 注释明示。
- **`multi_domain_range` 不修**：info 档登记的设计用法（列表=允许集），修它才是缺陷。
- **release 分支不硬造基线内容**：用户 2026-09-20 口径（"无需强制/默认提供不合理的内容"）。

### 4.2 三条行业共识（直接决定优化方向）

1. **"规则写一次，在所有可能被破坏的点强制执行"**（inspired.org）：OWL 说"是什么"（开放世界）、SHACL 说"有效记录长什么样"（封闭世界）、SWRL/CL 管超出 DL 的推导、事务完整性留在业务系统。→ 本工程的四层校验门结构与此同构；差距在 **warn 档规则没有对应的"执行点"清单**。
2. **"LLM 提议的变更走与人类相同的治理门"**（designpattern.fyi 2025）：human-in-the-loop 是现实标准；Specification/Evaluation 人属、Conceptualization/Formalization LLM 加速。→ 本工程蓝图正是此形态（LLM 提议→人工勾选→apply），**但治理门只挂在人工路径上，AI 建模直接产实例的路径靠 GraphStore 写校验**——结构已对。
3. **"验证 ≠ 确认"**：verification（reasoner 机械查）本工程已有轻量版；validation（CQ 回答业务问题）**完全缺失**，这是"结构完备但建错了域"的唯一防线。

### P0-5 归一别名关系登记（⚠️ 与 §5 原方案不同——实施时被证据推翻）

§5 原方案是"按存量端点反推 dom/range"。实测发现 **`连接`/`执行` 存量边为 0 条**——
`sysml_importer` 把 `连接` 归一为 `CONNECTS`（relmap 别名表）、把 `执行` 直接剔除计入 rejected，
这两个名字在真库**永远不会有边**。这不是数据缺失，是**设计事实**。真正的问题在于
`seeds.py` 里给 `连接` 补 dom/range 的语句只在空库生效（`_ensure_ontology_types` 走
`INSERT OR IGNORE` 不带 constraints，老库走 migration 路径永远补不上）——且 seed 的
6 元窄名单会漏掉 28 个实体类型中的 24 个，照抄会让未来所有 SysML 连接边违规。

**实际修法**：规则目录新增 `normalized_alias_relation`（info 档）——以 `core.relmap.REL_CANONICAL`
为单一真源，导入器输入名/已废弃名报"设计说明"而非"缺 dom/range 缺陷"。

### P1-1 发布门禁档位化（后端 + 前端）
