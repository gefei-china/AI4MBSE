## 1. P0-1：写类工具幂等键

### 1.1 为什么必须先做这件事（不是"顺便加个字段"）

行业口径（LangGraph / Temporal / DBOS 一致）：
> *"Every engine here behaves the same way for an unfinished step,
> so pass an idempotency key to anything with side effects."*

⇒ **换引擎不会自动获得幂等**。这是 LangGraph 官方 Retrofit 三步法的第 1 步
（① 幂等键 → ② 任务图外部化 → ③ 才把循环搬进引擎）。

本工程的"同一步被重跑"有**两条真实路径**，都不是假设：

| 路径 | 代码位置 | 表现 |
|---|---|---|
| 子任务重试（同 key 原地重派） | `stream.py` `TaskQueue.retry` + `retry_count+1` | 同一个子任务跑两遍 |
| 断点续跑（沿用原批次号） | `orch_checkpoint.prepare_resume` | 未完成任务重新派发 |

**本轮实测证据**（`verify_orch_reliability` G2c）：一次子任务超时，T1 补跑会
**同 key 重派一次** ⇒ 事件序列 `run→failed→run→failed`。
⇒ 该子任务里若有 `file_write` / `import_sysml_text`，就会**写两次**。

### 1.2 实现（`core/idempotency.py`，新增约 380 行）

**键 = sha256(scope | tool | args_hash | ordinal)[:32]**

| 段 | 取值 | 为什么必须这样取 |
|---|---|---|
| `scope` | `run:<批次号>:task:<task_key>` | 重试/续跑都**沿用**批次号与 task_key ⇒ 键稳定 ⇒ 命中 |
| `tool` | 工具名 | — |
| `args_hash` | 规范化参数摘要 | 忽略 `None`/空串；**路径分隔归一**（`d\a.txt` 与 `d/a.txt` 是同一文件） |
| `ordinal` | 同一次尝试内该 `(tool,args)` 的第几次 | 见下 |

**`ordinal` 是整套设计的关键**（也是最容易做错的一处）：

- `file_append` 同一内容连写两次是**两个不同意图**，不能被吞；
- 而重试时整个子任务从头再跑 ⇒ 序号必须**重新从 0 开始**，第 N 次才与上一次的第 N 次对齐；
- ⇒ 序号挂在**执行单元实例**上（`_tool_idem_seq`），**不能**挂全局计数器
  （全局计数器会因为"重试时模型多调/少调一次别的工具"而整体错位 ⇒ 幂等永远不命中，且静默）。

**作用域只在编排子任务内**：会话直答路径**不参与**。
理由：那里没有"同一步被重跑"的语义，纳入只会把"用户第二次说同样的话"误判成重放。

**只记成功**（`ok is True`）：被白名单/RBAC/Hook/写前确认(HITL)/写目标闸**拦下**的结果不记录。
否则"没执行"会被当成"执行过" —— **人工确认队列会被重放吃掉**，那是真事故。

**写类判定与写前确认闸同源**（`hil_service.classify_action` 双源口径）。
不另立白名单：两份判据必然漂移，出现"确认闸认为是写、幂等认为是读"⇒ 写操作被重复执行。

**fail-open**：幂等层任何异常一律放行。反过来的 fail-closed 会让幂等表故障 = 全平台写操作瘫痪。

### 1.3 落地位置：工具调用的**唯一出口**

挂在 `agent/pipeline_parts/tools.py::_exec_tool_call`（先查 → 再执行 → 成功后记账）。
选它而不是各工具内部，理由与 2026-10-28 的"确定性判读"完全相同：
**`stream.py` 与 `execute.py` 两条 ReAct 路径都只经这一个方法** ⇒ 一处接线、两路同源。
（门禁 D1b 反向断言：stream/execute 里**不得**出现幂等实现。）

### 1.4 表结构

`tool_idempotency`（新表，`CREATE TABLE IF NOT EXISTS`，老库启动即建）：
`key` 主键 / `tool` / `scope` / `args_hash` / `ordinal` / `result_json` / `hits` / 时间戳。

不复用 `tool_call_logs`：那张表是**观测**（每次调用都留痕，含失败与只读），
幂等表是**控制**（只记已成功的写类调用）。混用会让"失败也命中"。

### 1.5 端到端实测（真库，非模拟）

模拟"同一子任务重试时**新建实例**"（与 `stream.py` 派发方式一致）：

```
真实执行次数 calls = 1          ← 第二次没有真正执行
第 1 次 ok=True  replay=None
第 2 次 ok=True  replay=True     ← 命中重放
第 2 次带『幂等重放』说明: True
stats: {'enabled': True, 'scope': 'subtask', 'ttl_s': 86400, 'total': 1, 'replays': 1}
落库行: {'tool': 'file_write', 'scope': 'run:987654:task:t_probe', 'ordinal': 0, 'hits': 1}
```

重放结果**如实告诉模型**"这是幂等重放、未重复产生副作用" —— 否则模型会把重放当新执行，
继续往下推演（例如再写一次），反而放大重复写入。

### 1.6 已知局限（如实登记，不夸大覆盖面）

| 局限 | 后果 | 彻底解决方向 |
|---|---|---|
| 只覆盖编排子任务 | 会话直答路径无保护 | 直答路径没有重跑语义，本无需覆盖 |
| 只覆盖写类工具 | 只读工具重复执行（无副作用） | 有意不纳入，省一次 DB 往返 |
| **写操作"部分成功"无法识别** | 工具返回 `ok=False` 但已落库时，重试会重做 | 需工具自身返回可校验凭据（另一条线） |
| **记账用独立连接**，与工具自身事务不共享 | 工具"返回成功但事务随后回滚"时，会记账了却没落副作用 | 本仓工具约定自己提交（`job_handlers`/`file_tools`/MCP 客户端均如此），风险很窄但**不为零**；出现"重试后目标端没新数据"先查这一点 |

## 2. P0-2：停滞自动重驱（默认开 + 三道成本闸）

### 2.1 为什么改默认值

`orch_supervisor` 的实现 2026-10-04 就写好了，但 `auto_resume_enabled=False` ⇒
**能力存在但永远不会被使用**。这与 `total_time_budget_s` 的"配置谎言"是同一类病：
写了不用 = 等于没写。

而停滞自愈恰恰是 durable execution 的核心能力，本仓已有 checkpoint / resume /
租约队列全套骨架，缺的只是"没人点的自愈"。

### 2.2 原方案缺的东西：只有"单轮上限"，没有"每日总量"

原文档写的是"`orch_supervisor` 默认关，打开即可"。但直接打开有真实成本风险：

- `auto_resume_max_runs` 只约束**一轮**；一轮一轮累加，一天可以投几十次；
- 每次重投都会**真的调 LLM**；
- 而 `resume_include_failed=False` 只挡住 failed 任务，挡不住"反复超时的活任务"。

⇒ 本轮补三道成本闸，缺一即可能烧额度：

| 闸 | 键 | 默认 | 作用 |
|---|---|---|---|
| ① 单轮上限 | `auto_resume_max_runs` | **1**（原 3） | 一轮最多投 1 个批次 |
| ② **每日总量** | `auto_resume_daily_budget` | **5** | 按 UTC 日计数，超限不再投（0=不限） |
| ③ 不重跑 failed | `auto_resume_include_failed` | False | 有副作用风险 |

**手动点「继续编排」不受②限制** —— 那是用户的明确意图，不是自动化开销。

### 2.3 两个实现细节（都是踩坑点）

**① 日界必须用 UTC**：计数要与被计数对象同源。审计表 `created_at` 是
SQLite `CURRENT_TIMESTAMP`（UTC）⇒ `_utc_day()` 也用 `time.gmtime()`。
用本地时间会在跨时区/夏令时处算错日界。

**② 计数取双源最大值**：审计是**重投完成后**才写的 ⇒ 它滞后于真实触发数。
⇒ `max(进程内计数, 审计表计数)`，保守侧（宁可少投一次，不可多投）。

### 2.4 `orchestration` 段此前**根本改不了**

`save_override()` 对未登记键直接 `raise ValueError("未知配置项")`，
而 `orchestration` 段**从未登记进 `CONFIG_SCHEMA`** ⇒ 这 7 个键在接口与界面上都改不了。
一个改不了的开关等于没有开关，本轮整段登记（现 10 键）。

实测（改前会报"未知配置项"）：

```
PUT /api/system/config/static {"updates":{"orchestration.auto_resume_max_runs":2}}
→ {"ok":true,"updated":["orchestration.auto_resume_max_runs"]}
读回：auto_resume_enabled=True | auto_resume_daily_budget=5 | max_runs=2（已回置 1）
```

### 2.5 真机验证

```

{
```

## 3. P0-3：预算层级收敛成"引擎形状"

### 3.1 问题不是"键多"，是"同一语义多处实现"

38 个时间/预算类键分散在 12 个配置段。已付出过的代价：
`total_time_budget_s` 注释写"超限终止"却**零消费点**（改了不起作用）、
11 个 `context_audit.*` 键写入返回 `ok=True` 但消费点只读配置文件（静默无效）。

引擎的核心价值之一就是"单一真源 + 明确层级"，而这一半**不需要引擎就能拿到**。

### 3.2 实现（`core/budget_policy.py` + `GET /api/system/budget-policy`）

四层只覆盖**请求链路**上的时间预算（L1⊃L2⊃L3⊃L4），
把"同类但不同调用链"的键（外部子系统超时）与"不在链路上"的键（租约/TTL/DB 连接）
明确分开 —— 见 §3.4 的教训。

每层三种角色：`canonical`（权威，带 `aspect` 侧面）/ `aliases`（同侧面另一键，
**不得更严**）/ `independent`（不同调用链，不可比）。

### 3.3 审计出的三件事

**① 当前零违例、零死配置**（这是收敛后的健康态，不是"没问题可查"）：

| 层 | 真源 | 当前值 | 实际生效 |
|---|---|---|---|
| L1 整轮 | `runtime.chat_deadline_s` | 900 | 900s |
| L2 编排批次 | `delegation.total_time_budget_s` | 0（不启用） | 不限 |
| L3 子任务 | `delegation.subtask_timeout_s` | 600 | 600s |
| L4 单次调用 | `llm.http_timeout_s` | 180 | 180s |

**跨层可比性成立**：900 > 600 > 180，父子不冲突（"更严格者先生效"不会让子层额度虚设）。

**② L2 默认停用是**有意**的，但审计必须会跨过它去比真实约束** ——
这是本轮审计逻辑的一个真实缺陷（自证时暴露）：只比"直接父层"时，
L2=0（不限）⇒ L1(900) vs L3(600) 这对真实约束**永远比不出来**。
注入 `L1=1s` 后审计仍零 findings。已改为"跨过停用层找最近启用祖先"，并标注 `via_disabled`。

**③ 死配置检测是机器可检的"配置谎言"形态**：AST 取**非 docstring** 的字符串常量，
`tools/verify/` 排除（断言不是消费）、`core/config.py` 排除（定义不是消费）。
当前 15 个追踪键**零死配置**。

### 3.4 一条必须记住的教训：模型错了两次，不是配置错了

**第一版把 `integration.timeout`(15s) / `mcp.timeout`(15s) / `sysml.check_timeout`(90s)
当成 `llm.http_timeout_s`(180s) 的同层别名** ⇒ 审计立刻报 5 条"别名严于真源"，
还报 1 条"L1(900) 严于 L2(1800)"。**全是模型自己的错**：

- 那些是**外部子系统的超时**，与"LLM 单次调用"没有包含关系，不可比；
- `probe_time_budget_sec` 是**探针预算**，不是批次预算。

⇒ 引入 `aspect`（同层不同侧面）与 `independent`（不同调用链）两个区分。
**审计工具最危险的不是漏报，是报出一堆看起来很像真的假违例** ——
那会让运维去改本来正确的配置。

### 3.5 链外键单列（12 个）与 token 维度（66 键）

链外：`database.connect_timeout` / `auth.session_ttl_hours` / `extract.ocr_time_budget_sec` /
`runtime.orphan_ttl_s` / `runtime.queue_wait_s` / `runtime.shutdown_drain_s` /
`runtime.tool_idempotency_ttl_s` / `orchestration.resume_stale_s` /
`orchestration.auto_resume_interval_s` / `jobs.worker_interval_s` / `jobs.worker_lease_s` /
`replanning.confirm_ttl_sec`。这些**不硬塞进四层**（塞进去只制造假违例），只做死配置检测。

token/字符维度 66 个键（`context.*` 等）**单列计数**，不混进时间层级
（它们是另一维度，混进来会让"层级"这个概念失效）。

## 4. 顺带修掉的三个既有缺陷（验证过程中发现，都不是本轮引入）

### 4.1 ★ 子任务超时 ⇒ 整批编排崩溃（2026-10-20 起，10 天）

`stream.py` 超时分支返回 **9 元组**，而调用点按 **10 元组**解包
（`99f2d8b` 加第 10 位 `_off_id` 时只改了成功路径）：

```
ValueError: not enough values to unpack (expected 10, got 9)
```

后果：**任何子任务超时都会打断整个流**。而真库 76 条失败里 **63 条是超时（83%）**
⇒ 这极可能就是 run 层成功率只有 54.5% 的主因。
更讽刺的是：上一轮"超时保留产出"的改动**从未真正生效** —— 它在崩溃点之前就死了。

修复：补齐第 10 位，并注明为什么第 9 位必须是 `None`（不能拿假结构糊上去，
否则下游 `partial_policy` 会把"没协议"当"协议残缺"）。

### 4.2 HIL 确认单降级分支漏写 `idem_key` ⇒ 去重静默失效

`hil_service.queue_confirmation` 的"旧库缺新列"降级分支只写 8 个旧列，
**漏了 `idem_key`** ⇒ 该行 `idem_key=''` ⇒ 下次同操作查不到 ⇒ **重复确认单**。
退回的语义应当是"少写**增强**列"，而不是"少写**控制**列"。
已改为按 `PRAGMA table_info` 探测后写"控制列"（`idem_key`/`timeout_at`/`batch_count`）。

### 4.3 `_deadline_ts` 未登记清零 + reset 晚于赋值

上一轮加的墙钟实例属性违反了两条既有纪律：
① 未登记进 `reset_request_state` ⇒ 跨请求残留（单例 Pipeline 会把上一轮的长墙钟漏进本轮）；
② `reset_request_state` 调用位置**晚于** `self._deadline_ts =` 赋值 ⇒ 会把本轮刚设的值抹掉。
已改为：登记清零 + 顺序调整为"算局部 → 清零 → 再落实例属性"，并把 `_tool_idem_seq` 一并登记。

  （同一 `idem_key` 无重复 pending；切换点之后的 pending 必须带 `idem_key`，
  切换点**自校准**取"最早一条带键行"的时间，不写死日期）。

## 7. 明确不做的（与上一轮一致，理由不变）

| 不做 | 理由 |
|---|---|
| 引入 Temporal / DBOS | 本工程已有任务图外部化 + checkpoint + resume + 租约队列。本轮把"引擎形状"补齐后，将来迁移是**替换实现**而非**重写系统** |
| `uvicorn workers=N` | 进程内信号量/熔断器会失真；SQLite 单写者不支持多进程写 |
| SSE 改 `202 Accepted + 轮询` | 会推翻前端打字机交互，代价过大 |
| 把 token 维度也塞进四层 | 另一维度，混进来会让"层级"失去意义 |

**下一步的触发条件**（与文档 §4 一致）：满足"跨天等待人工审批 / 多实例部署 /
不可逆外部副作用且幂等键已加 / 停滞重驱成高频需求"任一 → 再引引擎，选型 DBOS（只需 SQLite）。
