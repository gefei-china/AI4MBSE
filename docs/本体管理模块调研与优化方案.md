## 1. 现状设计分析

### 1.1 模块边界与数据模型

「本体管理」是知识库子模块（KB-C 页签，前端 [index.html](file:///c:/Users/gefei/WorkBuddy/2026-08-04-19-05-52/mbse_system/static/index.html#L726-L781)），核心数据模型为 `ontology_types` 表（[schema.py](file:///c:/Users/gefei/WorkBuddy/2026-08-04-19-05-52/mbse_system/database/schema.py#L135-L142)）：

| 字段 | 说明 |
|---|---|
| name | 类型名（唯一） |
| type_kind | entity \| relation \| attribute 三类 |
| parent_id | 父类型（**存在但未在 UI/校验中使用**） |
| properties | JSON：`{key: {note, type, required}}` |
| constraints | JSON：`{required[], unique[], allowed_values{src[],tgt[]}, cardinality, attributes, subclass}` |
| icon / color | 前端展示 |

约束语义：entity 支持 required/unique/allowed_values；relation 支持 domain(src)/range(tgt)/cardinality/attributes；attribute 寄生在实体上（前端不独立维护）。

## 2. 行业优秀方案调研

### 2.1 本体编辑器标杆：Protégé / WebProtégé

- **OWL 2 全支持**（DL/EL/RL 子语言），类层次树形编辑、属性特性（传递/对称/函数/逆属性）、SWRL 规则。
- **推理集成**：内置 FaCT++，可挂 Pellet/HermiT——一致性检查、分类推理、等价发现一键触发；DL Query 面板做概念级查询。
- **WebProtégé**：多人协作、按需变更历史、角色权限——补齐单机版协作短板。
- 局限：UI 学术风、数万实例后性能一般（行业共识：<1000 概念/<5000 实例用 Protégé 足够）。

### 2.2 企业数据治理平台：TopBraid EDG / Composer

- **一站式**：本体编辑 + 推理 + SPARQL + **SHACL 验证** + 代码生成，一套工具链。
- **企业集成**：LDAP/SSO、审计日志、完整 API、资产级版本控制、变更工作流（评审→发布）。
- 大本体性能优化，面向治理与合规场景。

### 2.3 企业知识图谱平台：Stardog / Ontotext GraphDB

- **Stardog**：查询时 OWL 推理、虚拟图集成（映射到既有库）、SPARQL/SHACL/GraphQL 多协议、语义治理 + AI grounding（GraphRAG）。
- **GraphDB**：实时语义推理（规则集/OWL 可选）、命名图（Named Graph）支持"图即发布单元"、SPARQL + SHACL 校验、GraphRAG 能力。
- 二者是"本体 + 实例 + 查询 + 推理 + 校验"一体化存储的行业标准形态。

### 2.4 图数据库路径：Neo4j + neosemantics(n10s)

- 属性图（LPG）与 RDF/OWL 双模互操作；导入 OWL 本体映射为图约束，实例按本体约束建图。
- 本项目 GraphStore 抽象（SQLite 基线 / Neo4j 适配）正是对齐此路径，但当前仅 SQLite 落地。

### 2.5 语义套件：PoolParty（分类法/标签/元数据，SKOS）与 Apache Jena / RDF4J（开发框架，TDB2 持久化、SPARQL 联邦、推理器、PySHACL 校验）

- Jena/RDF4J + PySHACL 是开源领域"存储 + 查询 + 校验"的事实组合；SHACL 自动化校验流水线可将企业数据违规率从 ~15% 压到 0%（行业实证）。

### 2.6 本体版本与变更治理（行业核心实践，最被低估的一环）

- **语义版本化（SemVer）**：本体作为产品发布，每个版本有 IRI（owl:versionIRI）。
- **命名图版本化**：GraphDB/Stardog 用命名图表达"某版本图"——可回答"审计当天图说了什么"。
- **OWL 弃用标记**（owl:deprecated）：改名先弃用过渡，不硬删。
- **SHACL 向后兼容检查**：shape 变化（新增必填/收紧基数/改类型）在 CI 里 diff + 对存量图重放校验，阻断破坏性变更。
- **结构化 diff / 三路合并**（owl2vcs/OWLDiff/Ecco）：基于公理级比较而非文本 diff，解决"语法正确≠语义安全"（如类同时归入互斥父类）。
- **数据契约**：消费者绑定术语版本，重命名需知"哪些消费者绑定、迁移窗口多长"。
- 行业结论：**"本体是接口，接口要有版本、弃用与迁移窗口"**——不治理版本的本体会在 18 个月内变成废件（shelfware）。

### 2.7 MBSE + 本体 + 知识图谱（本系统所处领域的最新实践）

- **三种对齐路径**（INCOSE 2026）：语言内对齐（SysML 直接引用本体）、映射对齐（模型序列化后按映射连本体）、图内对齐（默认映射翻译后对齐）。
- **语义融合**（DESIGN 2026）：RDF KG + LLM 实体对齐 + 余弦相似度阈值，实现 SysML 跨模型元素自动合并（高相似自动并、低相似保留、中间阈值走术语表决策）。
- **KG 增强的语义故障定位**（arXiv 2606.23395）：用领域知识图谱编码物理兼容规则（机械/电气/流体/信号），校验"语法合法但物理非法"的语义错误，微调模型修复成功率 <3% → 91%。
- **LLM 辅助本体构建**：LLM 抽取概念/关系/属性 + 人工审核确认，本体构建成本从年千万美元级降至百万美元级，成本降约 10 倍（华为 iDME.Ontology-F、Palantir AIP Ontology、中国电子云 OntologyFoundry 等 2026 集中发布，验证"本体=LLM 语义契约层"）。
- **SHACL + SWRL 双引擎**：SHACL 管数据形状（入库校验），SWRL 管业务规则（IF-THEN 推理），GraphRAG 做多跳查询（复杂查询准确率 GraphRAG 90.63% vs 纯向量 46.88%）。

## 3. 差异对比矩阵

| 维度 | 行业优秀实践 | 当前系统 | 差距 | 优先级 |
|---|---|---|---|---|
| **命名空间/IRI 治理** | 可配置前缀、IRI 稳定性、owl:versionIRI | BASE 硬编码 `http://www.xingwang.mbse/ontology#`，无前缀管理 | 高 | P1 |
| **类层级 subClassOf** | 树形类层次、属性层级、Disjoint | parent_id 存在但未启用；subclass 仅藏在关系 constraints JSON | 高 | P0 |
| **推理能力** | DL 推理器（一致性/分类/等价）、SWRL 规则 | 4 项"简化规则引擎"（一致性/分类/传递/基数，多为提示型） | 高 | P0 |
| **SPARQL 查询** | 行业标配查询协议 | 全部 SQL LIKE，无语义查询入口 | 高 | P1 |
| **数据形状校验** | SHACL（W3C 标准，入库前自动校验） | 自定义 JSON 约束 + 代码校验，非标准、不可复用 | 高 | P0 |
| **版本与变更治理** | SemVer + 命名图 + owl:deprecated + SHACL 向后兼容 + 结构化 diff | 无版本、无弃用、无 diff/合并；OWL 导入"同名跳过"无对比报告 | 高 | P1 |
| **OWL 属性特性** | transitive/symmetric/functional/inverseOf/subPropertyOf | 仅 domain/range/cardinality | 中 | P1 |
| **本体对齐/映射** | owl:equivalentClass、owl:sameAs、LLM 实体对齐 | 无（仅实例层有消歧合并） | 中 | P2 |
| **序列化互操作** | rdflib/Jena 多格式（TTL/RDF-XML/N-Triples/JSON-LD）、导入 Turtle | 手写序列化，仅导出 TTL/RDF-XML，仅导入 RDF-XML | 中 | P1 |
| **SPARQL/推理端点** | Fuseki/GraphDB Workbench 类查询+可视化 | 无 | 中 | P2 |
| **可视化** | OWLViz/OntoGraf 类层次图、图谱+推理结果联动 | 类型约束图谱（自绘 SVG，单层） | 低 | P2 |
| **协作与审计** | WebProtégé 多用户 + 角色；EDG 审计/变更工作流 | 有审计日志（audit 表）但无本体级变更评审流 | 低 | P2 |
| **LLM 辅助本体构建** | LLM 抽概念 + 人工审核 → 本体迭代 | 有 LLM 抽取**实例**候选，但无"从文档/模型提取 schema 建议 → 本体构建"闭环 | 中 | P2 |
| **MBSE 领域集成** | KG 校验系统模型、语义融合、本体对齐 SysML | SysML 导入 + 本体校验已有；无 KG 反查校验模型、无本体对齐 | 中 | P2 |

**结论一句话**：当前模块**"本体驱动的实例化校验 + 治理闭环"方向与行业一致且完成度高**，主要差距集中在**本体自身的建模能力（层级/推理/SHACL/SPARQL）与本体的生命周期治理（版本/弃用/变更影响）**——即"本体作为一等公民资产"的管理能力尚未建立。

## 4. 优化方案（P0 → P2，落地到具体文件）

### P0：本体建模内核补强（投入产出比最高）

**1. 类层级 subClassOf 启用**
- 数据：启用 `ontology_types.parent_id`，entity/attribute 均可挂父类（`_ensure_ontology_types` 迁移补 `parent_id` 兼容）。
- 后端：`OntologyValidator` 增加 `classify(entity_type)`——沿 parent_id 链返回祖先集合；实例化校验时"子类继承父类必填/唯一/属性"。
- 前端：本体编辑滑窗新增"父类型"下拉（树形选择）；类型列表支持树形缩进展示（复用现有左栏渲染，改动最小）。
- OWL 映射：`to_owl/to_turtle` 输出 `rdfs:subClassOf`；`from_owl` 解析 `rdfs:subClassOf` 重建层级。

**2. 推理从"规则提示"升级为"可执行推理"**
- 引入轻量推理（零新增基础设施）：保留 SQLite，新增 `ontology_reasoning.py`，实现 3 类可执行推理：
  - **分类推理**：按 parent_id 物化"实例属于子类即属于父类"（查询时展开，非物理物化）。
  - **传递闭包**：对可传递关系（含/连接/追溯/SATISFIES）做 BFS 闭包，`/api/knowledge/graph/path` 复用；推理结果标记 `inferred=true`，可与显式边区分。
  - **一致性检查**：实例化时若同时触发互斥父类（父类链冲突）→ 阻断并报错（对齐 Protégé 一致性检查的轻量版）。
- 前端：实例导入预览区"验证与推理"面板增加"推理结果明细"（哪些是物化/继承得到）。

**3. 约束标准化：JSON 约束 ↔ SHACL 双向映射（不引入重依赖）**
- 保留现有 JSON constraints 为**内部存储**，新增 `shacl_export(conn)` 将 entity 约束（required→sh:minCount、unique→sh:unique、allowed_values→sh:in、属性类型→sh:datatype）映射为 SHACL 形状。
- 前端 RDF 视图新增"SHACL"Tab，可复制/导出 shapes.ttl（对齐 TopBraid/GraphDB 的"校验形状可见可版本化"）。
- 选装：若后续引入 PySHACL，可直接用 shapes.ttl 对 Turtle 预览结果离线校验（向后兼容，不影响当前零依赖约束）。

### P1：本体生命周期治理

**4. 本体版本化 + 弃用标记**
- 数据：`ontology_types` 增 `status`（active/deprecated）、`version`（类型级 SemVer，初始 v1.0）；`from_owl` 导入时对"同名跳过"改为"同名 diff 报告"（新增/修改/删除建议）。
- 变更规范：改名/删除父类等破坏性操作先标记 deprecated 过渡（对齐 OWL 弃用标记 + 行业"重命名前先问消费者"）。
- 前端：类型详情显示版本与状态徽标；OWL 导入结果提示 diff 明细。

**5. 命名空间/前缀治理**
- `core/config.py` 增加 `ontology` 分组：`base_iri`、`prefixes`（默认 `{ex: http://www.xingwang.mbse/ontology#}`）。
- `ontology_owl.py` 的 BASE 常量改为从配置读取；导出时按前缀表输出 `@prefix`。
- 前端设置区提供前缀配置入口（低投入：仅影响导出/导入标识一致性）。

**6. 序列化互操作补全**
- `ontology_owl.py` 增加 `from_turtle()`（用轻量 Turtle 解析或提示用户先转 RDF/XML）；导出补 N-Triples/JSON-LD 需引入 rdflib（列为可选依赖，缺省保持零依赖）。
- 明确不动：不引入 GraphDB/Stardog 等独立服务（私有化工程平台，SQLite 足够，见 §4 结论）。

**7. SPARQL 子集查询**
- 新增 `/api/knowledge/ontology/sparql`：支持 SELECT 子集的受限解析（投影 + WHERE 基本图模式 + FILTER 简单比较），翻译为 SQL 查询 entities/relations（对齐"SPARQL 是语义查询标准"但不引入 Fuseki）。
- 前端 RDF 视图新增"查询"Tab：粘贴 SPARQL 子集 → 结果表格。
- 定位为内部语义查询入口 + 审计能力，不做完整 SPARQL 1.1 承诺。

### P2：本体智能与 MBSE 融合增强

**8. LLM 辅助本体 schema 建议（对齐 2026 行业"LLM 半自动建本体"）**
- 新增 `v2o`（向量→本体）候选：复用 `v2g` 抽取管线，LLM 从文档/模型输出"建议实体类型 + 属性 + 关系 + 子类"，落入候选表（pending），人工确认后写 `ontology_types`。
- 前端：本体管理新增"从文档建议本体"入口，展示建议卡片（类型/属性/父类/证据片段）→ 勾选确认（对齐现有治理中心交互范式）。

**9. 本体对齐（owl:equivalentClass / sameAs）**
- 新增 `ontology_alignments` 表：`{left, right, type(equivalent|subclass|sameAs), confidence, status}`；提供自动建议（同名/LLM 相似度）+ 人工确认。
- 服务于多项目/多客户本体复用（对齐用户偏好"通用平台多客户"）。

**10. MBSE 模型 ↔ 本体反查校验**

## 6. 需求补充设计：SysML Profile ⇄ 本体 双向互操作

> 需求原文：可导入现有 SysML Profile 作为模型本体基础，或将定义的本体模型导出为 SysML Profile 供建模使用。
> 定位：O-3 SysML 导入（模型→图谱，[sysml_importer.py](file:///c:/Users/gefei/WorkBuddy/2026-08-04-19-05-52/mbse_system/sysml_importer.py)）的**反向/上游互补**——本需求在 **Schema 层**交换（本体类型 ⇄ Profile 元素），而 O-3 在**实例层**导入模型。两者组合形成"建模工具 ↔ 平台本体"的闭环。

### 6.1 术语与标准背景（对齐 OMG）

| 标准 | 扩展机制 | 对应元素 | 本项目映射目标 |
|---|---|---|---|
| **SysML 1.x**（UML Profile） | `Stereotype` 原型 + `Extension` 扩展元类（Block/Requirement 等） | `.profile`/`.xmi`/`.uml`（XMI 2.x 格式） | 本体 entity 类型 |
| **SysML 2.x**（KerML 基础） | `metadata def` 元数据定义（替代 1.x Profile）+ `specialization` 继承 | 文本符号 / SysML v2 XML 表示 | 本体 entity 类型 + 层级 |

行业事实：SysML v2 官方设计明确用 **metadata 机制取代 1.x Profile**，因此本设计必须同时支持两条语法路径，不能只做 1.x。

### 6.2 双向映射规则（核心设计）

**Profile → 本体（导入）**

| SysML Profile 元素 | 本体落点 |
|---|---|
| Stereotype / `metadata def` 名称 | entity 类型（type_kind=entity） |
| Stereotype 泛化（`generalization`）/ `specialization : Base` | `parent_id`（subClassOf 层级，衔接 P0-1） |
| Stereotype 属性 / `attribute f : Type` | `properties[key] = {note, type}`（类型映射见下） |
| 属性引用另一 Stereotype / `feature : OtherType` | relation 类型（domain=所属类型，range=被引用类型，并入该类型的 allowed_values） |
| 属性多重性 `[1]` / `[0..*]` / required | `constraints.required[]` + `cardinality` |
| 枚举型属性（Enumeration 类型） | `properties[key].type=enum` + `constraints.allowed_values[key]=[...]` |
| 约束（OCL `ownedRule` / 表达式） | `constraints` 尽力映射（required/unique/取值），无法表达的保留到 `description` |
| Extension 目标元类（Block/Requirement/ValueType…） | 记入 profile 元信息（base_metaclass_map），不建独立本体类型 |
| Profile 包名/版本 | 记入 profile 元信息（profile_source/version） |

数据类型映射：`Integer→decimal`、`Real→decimal`、`Boolean→bool`、`String→string`、`Enumeration→enum`、其余对象类型→引用（建 relation）。

**本体 → Profile（导出）**

| 本体概念 | SysML 1.x Profile 落点 | SysML 2.x 落点 |
|---|---|---|
| entity 类型 | `uml:Stereotype`（name=类型名） | `metadata def <名> { ... }` |
| entity 层级（parent_id） | `uml:Generalization`（父 stereotype） | `metadata def <子> : <父> { ... }` |
| properties | `ownedAttribute`（tagged value，带数据类型） | `attribute <key> : <数据类型>` |
| relation 类型 | 引用型 `ownedAttribute`（type=目标 stereotype） | `feature <rel> : <目标类型>` |
| required | 属性 `[1]` 多重性 + 可选注释 | 注释保留（KerML 无 required 关键字，语义落在类型约束） |
| allowed_values（枚举） | 枚举型属性 + 注释 | `metadata def` 内注释 |
| relation domain/range | `ownedAttribute` 的 type + 注释 | 同上 |

**导出示例（SysML 2.x KerML 文本）**——本体 `{部件(parent_id=null, 属性: 名称/质量), 载荷(parent_id=部件), 天线(parent_id=部件), 包含(domain=部件, range=部件)}`：

```kerml
package XingWangProfile {
  metadata def 部件 {
    attribute 名称 : String;
    attribute 质量 : ScalarValue;   // required
  }
  metadata def 载荷 : 部件 { }
  metadata def 天线 : 部件 { }
  metadata def 包含 : 部件 {         // 关系：domain 部件 → range 部件
    attribute : 部件;               // 引用型特征（1.x 对应 tagged value type）
  }
}
```

**导出示例（SysML 1.x Profile XMI 结构）**——对齐 Cameo/MagicDraw、Enterprise Architect、Papyrus 可加载的 `.profile`：

```xml
<uml:Profile xmi:version="2.1" xmlns:xmi="http://www.omg.org/XMI"
             xmlns:uml="http://www.eclipse.org/uml2/5.0.0/UML" name="XingWangProfile">
  <packagedElement xmi:type="uml:Stereotype" xmi:id="_s_part" name="部件">
    <ownedAttribute xmi:id="_a_name" name="名称" type="_string"/>
    <ownedAttribute xmi:id="_a_mass" name="质量" type="_real"/>
  </packagedElement>
  <packagedElement xmi:type="uml:Stereotype" xmi:id="_s_zai" name="载荷">
    <generalization xmi:id="_g1" general="_s_part"/>
  </packagedElement>
  <packagedElement xmi:type="uml:Extension" xmi:id="_e1" name="包含">
    <memberEnd xmi:idref="_end_1"/>
    <memberEnd xmi:idref="_end_2"/>
  </packagedElement>
</uml:Profile>
```

### 6.3 数据模型扩展

- `ontology_types` 增两列（迁移：[migrations.py](file:///c:/Users/gefei/WorkBuddy/2026-08-04-19-05-52/mbse_system/database/migrations.py) `_ensure_ontology_types` 同批补齐）：
  - `profile_source TEXT DEFAULT ''`（来源 Profile 名）
  - `profile_ref TEXT DEFAULT ''`（对应 Stereotype/metadata 元素名，供反查）
- 新表 `ontology_profile_meta`：`{id, name, version, format(1x|v2), base_metaclass_map TEXT(json), imported_at}`——记录"哪份 Profile 导入过、扩展了哪些 UML 元类"。
- 复用现有字段：`parent_id`（层级）、`properties`、`constraints`、`description`（未映射约束原文）。

### 6.4 后端实现（新文件 `sysml_profile.py`，零依赖对齐 `ontology_owl.py` 风格）

```
parse_profile_xmi(xml)      # SysML 1.x Profile：Stereotype + ownedAttribute + generalization
                            #   + Extension(memberEnd) + Enumeration/约束，复用 parse_xml 的
                            #   _local/_attr 命名空间解析技巧
parse_profile_v2(text)      # SysML 2.x：metadata def / specialization / attribute / feature
parse_profile_v2_xml(xml)   # SysML 2.x XML 表示（sysml-v2 API 结构）
to_profile_1x(conn)         # 本体 → XMI .profile（string）
to_profile_v2(conn)         # 本体 → KerML 文本
preview(conn, profile, format)  # 解析 → "建议本体候选"（与 v2g 候选结构同构，含冲突标记）
import_profile(conn, profile, format, strategy)  # 确认入库（见 6.5 冲突策略）
```

要点：
- **解析不直接落库**，产出候选列表（类型/父类/属性/关系/证据），走"预览 → 确认"（与现有 OWL 导入、v2g 治理中心一致，不静默写库）。
- 类型映射复用 `OntologyValidator` 的校验能力：候选若与现有类型冲突，生成冲突标记由用户决策。
- 导出侧 `to_profile_1x` 复用 `ontology_owl.py` 的 `_uri`/命名空间工具思路；`to_profile_v2` 直接生成 KerML 文本（字符串模板，零依赖）。

### 6.5 API 设计（routers/knowledge.py 增一组）

| 端点 | 方法 | 说明 |
|---|---|---|
| `/api/knowledge/profile/parse` | POST | 上传 profile 内容 + format(1x\|v2\|v2xml) → 解析预览候选（不入库） |
| `/api/knowledge/profile/import` | POST | 确认入库（body: {parsed 候选或重新提交, strategy}）→ 写 ontology_types + profile_meta，审计 |
| `/api/knowledge/profile/export?fmt=1x\|v2` | GET | 下载 .profile（XMI）/ .kerml 文件（Content-Disposition） |

**冲突策略（import 时二选一，弹窗让用户选）**：
- `skip`（默认）：同名类型跳过，与现有 OWL 导入一致；
- `overlay`：以 Profile 为准更新属性/层级（破坏性变更需提示"影响 N 个已入库实例"——复用 R2RML 引用阻断的检查思路）；
- 删除保护：Profile 中不存在的现有类型**不删除**（只增不删，防误伤）。

### 6.6 前端交互（KB-C 页签，复用现有 UI 范式，不引入新组件）

- **导入**：O-3 面板（[index.html](file:///c:/Users/gefei/WorkBuddy/2026-08-04-19-05-52/mbse_system/static/index.html#L782-L788)）新增按钮「⬆ 导入 SysML Profile」（1.x .profile/.xmi/.uml 或 v2 文本/XML）→ 上传/粘贴 → 解析预览面板：
  - 类型候选卡片（名称/父类/属性数/关系数 + 冲突徽标），勾选确认 → 入库；
  - 复用现有「验证与推理」面板样式展示映射统计（新增 N / 跳过 M / 冲突 K）。
- **导出**：本体管理页签 RDF/OWL 视图旁新增「Profile」Tab（与 [rdf-fmt](file:///c:/Users/gefei/WorkBuddy/2026-08-04-19-05-52/mbse_system/static/index.html#L768-L780) 同款双格式切换）：
  - 格式切换 `SysML 1.x (.profile)` / `SysML 2.x (.kerml)`，预览 + 下载按钮。

### 6.7 边界与兼容性

- **只支持"结构可映射"子集**：OCL 复杂约束、1.x 中未映射到本体语义的构造（如 Port/FlowProperty 的端口语义）保留原文到 `description`，不静默丢失。
- **与 O-3 的分工**：O-3 导入**模型实例**（part/requirement…），本需求导入/导出**Schema（Profile）**；两者共用 `ontology_types`，Profile 导入先建好类型，模型导入即可直接按类型实例化，形成"Profile → 本体 → 模型实例"完整链路。
- **循环引用防呆**：Profile 中 stereotype 相互引用时，先建全部类型再补关系（与 `from_owl` 先收集 classes 的策略一致）；parent 环检测（导入时校验 parent_id 不成环）。
- **导出幂等**：同一本体可重复导出，每次生成新文件名（含时间戳）。

### 6.8 实施优先级

| 项 | 优先级 | 依赖 |
|---|---|---|
| `parse_profile_v2` + `to_profile_v2`（KerML，先做 v2 主路径） | **P1** | 无 |
| `parse_profile_xmi` + `to_profile_1x`（Cameo/EA 兼容） | P1 | 无 |
| 数据迁移（profile_source/profile_ref + profile_meta 表） | P1 | 无 |
| 前端 Profile 导入/导出交互 | P1 | 后端 API |
| 冲突策略（overlay + 实例影响提示） | P2 | P0-1 层级 + R2RML 引用检查 |

## 7. 明确不做 / 观察项

- **不引入独立图数据库/三元组库服务**（GraphDB/Stardog/Neo4j）：私有化工程平台定位下 SQLite + GraphStore 抽象已覆盖，观察多客户大模型场景再评估。

- **本体协作（多用户评审）**：已有分支/审计能力，单项目内评审流列为观察项，客户明确要求再补。
