# 图谱工作区 v2 方案评估与修订（删除苦役版）

> 日期：2026-09-09（对前版 v2 方案的诚实评估）  
> 输入：`docs/图谱工作区优化方案-v2-20260909.md`  
> 输出：① 优势保留 ② 不足剖析（7 处苦役）③ 删除清单 ④ 修订后方案 ⑤ 决策点（3 项）

---

## 0. 评估结论（一句话）

**前版方案 30% 是真需求，70% 是"为优化而优化"的苦役。** 用户要的是「三元组 + 推理」两件事，其他都是包装。

| 保留项 | 理由 |
|---|---|
| **Tab 2 三元组视图** | 用户明确要求「支持三元组的呈现」 |
| **Tab 3 推理面板** | 用户明确要求「支持推理能力」 |

## 2. 不足剖析（7 处苦役）

### 苦役 ①：5 个 Tab 过多

**前版设计：** [图谱] [三元组] [推理] [模型] [时序]

**问题：**
- **模型 Tab** = 与现有 `21-ontology.js` / `22-ontgraph.js`（本体建模页）**功能重复**，纯属把已存在的页面再开一个入口
- **时序 Tab** = 业务价值存疑，已有变更历史在详情里，时间轴视图是 Linkurious 风格，**mbse 业务没这个场景**

**真实需求：** 图谱工作区本就应该只有 **3 个 Tab**：图谱 / 三元组 / 推理

**修订：** 删除 [模型] [时序] 两个 Tab。

---

### 苦役 ②：Reagraph WebGL 升级

**前版设计：** 替换 SVG+DOM 为 Reagraph，理由"5k 节点 110 FPS"

**问题（这是最大的为优化而优化）：**
- 当前骨架模式 L1 类型聚合**只有几十个节点**，L2 实例束**有 LIMIT 截断**，L3 邻域**默认只展示有限 hops**
- **卡顿场景未量化**：没有用户报告"卡到不可用"，是我从 benchmark 推论出来的假设
- **代价高**：引入 Three.js + WebGL 依赖，`static/vendor/` 体积+几 MB，私有化部署变重
- **风险高**：替换渲染层 = 所有节点着色 / 筛选 / 骨架逻辑都要重写
- **真正的痛点不在渲染，在交互**：用户更在意"点节点后多久出详情"，不是"画布是否 60 FPS"

**真实需求：** 先**量化**性能问题再决定。如果骨架模式 L1 真的只有几十节点，SVG 完全够用。

**修订：** 
- **P0 不升级渲染引擎**
- **P2 备选**：仅当出现以下任一情况再升级：
  - L1 类型节点数 > 500
  - 单次渲染时间 > 2s
  - 用户反馈"卡"

---

### 苦役 ③：三元组矩阵视图

**前版设计：** 三元组 Tab 含列表 + SPARQL + 矩阵三视图

**问题：**
- 矩阵视图 = **炫技**
- 用户要查三元组，列表 + SPARQL 足够
- 矩阵实现成本高（行/列排序、单元格点击跳图谱、批量选中导出），**业务价值低**
- 米爸团队是系统工程师，不是数据分析师，**不会用矩阵视角看三元组**

**修订：** 删除矩阵视图。三元组 Tab 只保留 **列表 + SPARQL** 两个视图。

---

### 苦役 ④：跨 Tab 联动（伪需求）

**前版设计：** 6 种跨 Tab 跳转（节点右键 → 三元组 / 推理 / 模型 / 时序）

**问题：**
- 米爸工作流是**顺序的**：看图谱 → 查三元组 → 跑推理，**不是频繁跳切**
- 6 种联动 = 6 套路由 + 6 种上下文传递，**实现复杂度高**
- 真正高频的只有 **2 种**：节点右键 → 查看三元组、节点右键 → 查看推理

**修订：** 只保留 2 种联动，其他删除。

---

### 苦役 ⑤：实例详情改抽屉

**前版设计：** 右侧常驻详情改抽屉式

**问题：**
- 右侧常驻**已经是米爸团队习惯的工作方式**（沿用 2026-09-04 方案）
- 抽屉式 = 隐藏 - 滑出，**多一步操作**
- 抽屉式更适合"偶尔看一眼"的场景，不适合"持续对比图谱与详情"的工作流
- 改抽屉 = 重新设计交互 + 重新学习

**真实需求：** 右侧常驻是合理的，**不需要改**。

**修订：** 维持右侧常驻，不做抽屉化。

---

### 苦役 ⑥：决策点过多（D-1 ~ D-8）

**前版设计：** 8 个决策点让米爸拍板

**问题：**
- 米爸偏好**简短决策**（"选择B / 采用XX / 继续"）
- 8 个决策点 = 评审陷入泥潭
- 很多决策点**根本不该问**：比如"是否启用节点右键菜单"——这是设计师的事，不该问用户

**真实需求：** 只问**真正影响架构**的决策，其他默认按推荐做。

**修订：** 决策点减到 **3 个**：
- D-1：是否做 Tab 2 + Tab 3（必须做，这是用户明确要求）
- D-2：渲染引擎是否升级（**默认不升级**，先量化）
- D-3：推理物化是否默认开启（**默认仅查看**，物化需手动）

---

### 苦役 ⑦：MiniMap + 公理视图

**前版设计：** MiniMap（画布右下）+ 公理视图（推理 Tab）

**问题：**
- **MiniMap**：骨架模式下视口内节点有限，MiniMap 是伪需求
- **公理视图**：让系统工程师读 OWL 公理？米爸团队关心的是**推理结果**，不是公理依据
- 两者都是"看着专业"的装饰品

**修订：** 删除 MiniMap + 公理视图。

## 11. 自我批判总结

**前版方案的根本错误：**
1. **过度参考行业产品**——Neo4j / Stardog / Linkurious 的功能清单照搬，没有问"米爸团队真的需要吗"
2. **技术驱动而非业务驱动**——Reagraph 是看到 benchmark 就想用，没量化现有性能问题
3. **增量思维**——只想着加功能，没想过删功能
4. **炫技倾向**——矩阵视图 / MiniMap / 公理视图 / 时间轴，都是"看着专业"的装饰品
5. **决策点膨胀**——8 个决策点 = 把设计责任推给用户

**修订原则：**
1. **用户要啥做啥**——三元组 + 推理，其他都不做
2. **能复用就复用**——`ontology_reasoning.py` + `triple_store.py` 已成熟
3. **能删就删**——模型 / 时序 Tab / 矩阵 / MiniMap / 公理视图，全删
4. **默认不升级**——Reagraph / ELK / owlready2 都是 P2 备选
5. **决策点最小化**——只问真正影响架构的 3 个

---

**一句话：把"用户要的三元组 + 推理"做扎实，其他全部删除。**
