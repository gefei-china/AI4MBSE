# P1-1：LLM 适配层 —— LiteLLM 的价值到底在哪（2026-09-24 实测评估）

> **回答的问题**：「Agent/Skill/工具能不能直接用开源框架，以确保基础能力扎实稳定」
> 落到 LLM 这一层就是——**用 LiteLLM 收编自研 `llm/` 值不值？**
> **方法**：不靠印象打分，先盘本仓已有能力，再列 LiteLLM 增量，两边做差集；
> 依赖成本用**本机实际安装**量化，不用官宣数字。

---

## 0. 结论先行

| 主张 | 判断 |
|---|---|
| **整体替换 `llm/` 为 LiteLLM** | ❌ **不划算**。本仓已实现 LiteLLM 的核心子集，且有一条它**没有**的能力（按 tag + 预算的智能路由），替换会丢 |
| **新增"可选 LiteLLM provider"（默认不开）** | 🟡 **可以，但现在不必**。唯一不可替代的增量是 **provider 覆盖面**，而本仓 4 个 provider **全是 OpenAI 兼容**，暂时用不上 |
| **失败重试 / 回退** | ✅ **最高价值，且已零依赖做完**（本次落地，48 行）。这才是真痛点 |
| **成本计算** | 🟡 中等价值。缺价格表，但可先只做"按 provider 配单价"，不必引重依赖 |

**一句话**：LiteLLM 的价值**不在"替掉自研"，而在"将来接新 provider"**。
而当下真正的痛点（10.9% 静默回落 Mock）**跟 provider 数量无关**，是自研 48 行就能治的。

## 2. LiteLLM 能给什么（与本仓做差集）

| LiteLLM 能力 | 本仓是否已有 | 净增量 |
|---|---|---|
| 100+ provider 统一接口 | ❌ 只有 1 个真实实现 | **⭐ 最大** |
| 内置 retry / fallback / cooldown / timeout | ❌（本次补了 retry） | ⭐⭐（retry 已自研解决，剩 fallback） |
| 成本计算（内置价格表 `completion_cost`） | ❌ | ⭐⭐ 中等 |
| 统一流式 / 统一错误类型 | ✅ 已有 | 无 |
| 可观测回调（Langfuse / OTEL） | ❌ | ⭐ 可选 |
| **智能路由（按 tag + 预算）** | ✅ **本仓有，LiteLLM 没有** | **负增量**（替换会丢） |
| Proxy（独立进程 / 虚拟 key / 限流） | ❌ | 本仓单进程场景用不上 |

**关键差集结论**：LiteLLM 唯一不可替代的是 **provider 覆盖面**。
其余（retry、成本）都能自研，且体量小。

## 3. 真正的痛点在这里（实测数据，不是推测）

`llm_usage_stats` 全量统计（2026-09-24）：

```
总调用 1792 条，used_mock=1 共 196 条  →  10.9%
  其中 latency_ms = 0 的：180 条  →  占失败的 91.8%（瞬时连接失败）
       latency_ms > 0 的： 16 条  →  模型侧返回错误

按 provider 拆：
  DeepSeek-V3 / deepseek-chat    1182 调用，53 mock →  4.5%
  deepseek-v4-flash              610 调用，143 mock → 23.4%   ← 差 5 倍
```

**读法**：
1. **每 9 次调用就有 1 次静默降级成 Mock** —— 用户拿到的是假答案，而界面上看不出来。
   本仓 2026-09-17 的 S4 注释已经登记过这个隐患。
2. 其中 **91.8% 是 `latency_ms=0` 的瞬时连接失败** —— **重试大概率能成功**。
3. 两个 provider 稳定性差 5 倍 —— 这正是 **provider 回退**的需求依据。

⇒ **痛点与"provider 数量"无关**，所以 LiteLLM 的"覆盖面"优势对当下这个痛点**没有直接帮助**。

## 4. 成本：本机实测（不是官宣）

| 项 | 实测 |
|---|---|
| 安装耗时 | **>10 分钟仍未完成**（本会话后台实测进行中；首次尝试还报了一次 `No matching distribution found`，重试后开始下载） |
| 依赖规模 | 待安装完成后量化（隔离 venv 实测） |
| 版本发布频率 | 极高频：索引上可见 1.x **每周多个版本**（1.102.1、1.102.0、1.101.2…共 400+ 版本）⇒ **breaking change 风险高** |
| 语义适配成本 | 需对齐本仓 `BaseLLM`：`stream` 的 SSE 行格式、`tools`、`thinking`、Mock 兜底、`_record_usage` 归属 |
| 对本仓既有资产的影响 | `tools/verify/` 下脚本按源码精确子串断言，改动有波及 |

**供应链风险**在选型文档 §4 已列，这次在本机**实证了一部分**：安装本身就慢且不稳定。

## 5. 建议：分三层，按需求触发

| 层 | 动作 | 何时做 |
|---|---|---|
| **L1（已做）** | 失败重试（指数退避）+ 参数类错误不重试 + 留痕 | ✅ 已完成（`b2b801a`，零依赖） |
| **L2（下一步）** | **provider 回退**：A 连续失败 → 换 B（`llm.fallback_provider_id`）。实测两个 provider 稳定性差 5 倍，这是刚需 | 近期自研，~40 行 |
| **L3（按需）** | 引入 LiteLLM 作为**可选 provider**，只用于接非 OpenAI 兼容的模型（Claude / Bedrock / Gemini / Ollama） | **真要接第 5 个 provider 且它不兼容 OpenAI 时**再引 |
| **不做** | 整体替换 `llm/` | 会丢掉按 tag + 预算的智能路由，且收益不抵成本 |

## 6. 本次已落地：重试（零新依赖）

`llm/__init__.py` +52/−4，提交 `b2b801a`。

- `llm.retry_times`（默认 2）、`llm.retry_backoff_ms`（默认 500，指数 ×2ⁿ）
- **流式不重试**：生成器一旦开始迭代无法安全重放（如实标注，不是偷懒）
- **参数类错误不重试**：HTTP 400/401/403/404/422 —— 重试也不会成功，只会放大延迟
- 每次重试打 warning 留痕；`retry_count` 写进 `_meta`

验证 **6/6**（`outputs/_p1_1_llm_retry.json`，进程内假 provider，**不调真实 LLM、不花钱**）：

| 断言 | 结果 |
|---|---|
| A 前 2 次超时、第 3 次成功 | ✅ `retry_count=2` / 被调用 3 次 |
| B 参数类 400 不重试 | ✅ 只调用 1 次 |
| C 流式不重试 | ✅ 只调用 1 次 |
| D 耗尽后抛出最后一次异常（仍交由外层回落 Mock，行为不变） | ✅ |
| E 默认 2 次生效（不配置也行） | ✅ |
| F **变异自证**：`retry_times=0` 时同一场景必须失败 | ✅ 证明 A 的断言不是空转 |

**预期收益**：196 条失败里 180 条是瞬时失败 ⇒ 重试后 `used_mock` 率有望从 **10.9%** 显著下降。
（真实效果待运行一段时间后用同一 SQL 对比，不提前宣称数字。）

## 7. 一句话回答米爸

> **LiteLLM 这类开源适配层的价值，是"替你维护那一层商品化的东西"——
> 具体到本仓，它的不可替代价值只有一个：provider 覆盖面。**
>
> 而你们**当下真正不稳的地方**（每 9 次调用 1 次静默变 Mock）**跟覆盖面无关**，
> 是 48 行自研代码就能治的。所以正确顺序是：
> **先把自研的短板补齐（重试 ✅ → 回退），等到真要接不兼容 OpenAI 的模型时，再引 LiteLLM 当可选后端。**
> 这样既拿到了社区维护的稳定性，又不为一个"将来可能需要"的能力提前背上重依赖。
