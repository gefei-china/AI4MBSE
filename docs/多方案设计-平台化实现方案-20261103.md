# 多方案设计：平台化实现方案（配置驱动，不写死能力）

> 日期：2026-11-03  
> 目标：把「多方案生成 + 比较 + 多维度打分」做成**AI 平台的可配置资产**，  
> 而不是在管线里写死一条多方案分支。  
> **状态：已实施并真机验证**（自检 49/49、前端 31/31、真机端点 + 工具面均通过）



---

## 0. 设计原则（来自工程既有范式）

本仓已有**成熟的平台化范式**，见 `register_sysml_check_tools.py` 文件头原话：

> 「生成后必须自校验、有错则修、最多 3 轮」属**编排策略**，会随建模实践调整。  
> 写在 pipeline 里意味着每次调整都要改代码 + 重启；写在 DB 里则**改文本即生效**，  
> 且能被前端「技能/工具」页面管理。**本脚本只负责"把定义灌进去"，不含任何判断逻辑。**

多方案能力完全适用同一条原则。**边界划法**：

| 层                               | 载体                                            | 为什么                      |
| ------------------------------- | --------------------------------------------- | ------------------------ |
| **算子**（纯计算：归一化/加权/推荐判定）         | Python 工具 handler                             | 任何工具都要有实现；纯函数、无 IO、可单测   |
| **策略**（何时产出多方案、维度清单、权重、门槛、输出契约） | **DB**（`tools` / `skills` / `generate_rules`） | 改配置即生效，前端可管理，不需要改代码 + 重启 |
| **编排**（哪些 Agent 具备该能力）          | **DB**（`agent_tools` 绑定）                      | 新建 Agent 自动获得能力          |
| **呈现**（对比表长什么样）                 | 前端按**工具名**渲染（既有 `covTryCard` 同款机制）            | 不新增卡片类型、不改 `msg_type` 映射 |

## 1. 现状问题（上一轮实现的不足）

上一轮实现把能力**写死在了管线里**，与平台化原则冲突：

| 写死点             | 位置                                                | 问题                                |
| --------------- | ------------------------------------------------- | --------------------------------- |
| 提示词契约硬编码        | `prompt.py::_build_alternatives_req`              | 改维度/契约要改代码 + 重启；且只对 `design` 意图生效 |
| 卡片类型靠 intent 映射 | `cards.py::_get_card_type` 的 `mapping` 字典         | 加能力必须改这张表                         |
| 抽取逻辑硬编码在 Python | `agent/pipeline_parts/alternatives.py` 的别名表       | 维度别名要改代码                          |
| 打分维度硬编码         | `core/alternatives.py` 的 `DIMENSIONS`             | 换维度集要改代码                          |
| 5 处链路各写一遍接线     | `execute.py` / `stream.py`×3 / `orchestration.py` | 新增链路必漏（同一模式的漂移，本仓已反复踩）            |

**这些都要撤掉**，改为由配置驱动。

## 2. 平台化资产设计

### 2.1 工具：`alternatives_score`（打分算子）

`tools` 表注册，`kind='internal'`、`source='local'`、`side_effect='read'`。

- **输入**：`alternatives`（候选方案数组，每项含 `name` / `scores` / `rationale`），  
  可选 `weights` / `tie_epsilon` / `min_coverage`。
- **输出**：`{ok, result}`，`result` 是 JSON 字符串，含对比矩阵 + 打分明细。
- **维度与权重从哪来**：**`generate_rules` 表**（既有表，已有 `/api/studio/rules` 读写端点）。
  - `alternatives_dimensions` → 维度清单（key/label/direction/unit）的 JSON
  - `alternatives_weights` → 权重 JSON
  - `alternatives_tie_epsilon` / `alternatives_min_coverage` → 阈值
  - 规则可**留空**：留空时用工具 `input_schema` 里声明的默认值（契约自洽，不依赖 DB 有数据）。

**关键**：维度集从此是**数据**，不是代码。运营可在设置页改，改完即生效。

### 2.2 技能：`多方案设计与对比`（编排规则）

`skills` 表注册，`status='published'`、`skill_type='package'`。

内容是**纯文本的编排规则**（模型读它就知道怎么做），包括：

- 何时产出多方案（用户明确要求比较/多个方案时；单方案请求不要硬造）
- 输出契约：结构化 JSON 块的字段与维度 key
- **纪律**：分数由 `alternatives_score` 工具算，**模型不得自报综合分**；  
  缺维度要省略而不是编；并列/数据不足要如实说
- 调用顺序：先产出候选 → 调 `alternatives_score` → 依据返回结果写结论

`triggers` 命中词：`多方案`、`方案对比`、`候选方案`、`架构选型`、`方案比较`、`备选方案` 等。  
这样**任何绑定该技能的 Agent**（含用户自建）都能用，无需改代码。

### 2.3 Agent 绑定

`agent_tools` 表：

- `design`（内置方案设计 Agent）→ 绑定 `alternatives_score` + 技能
- 规则发现：`system_prompt` 含「方案」/「多方案」的 active Agent 自动获得能力  
  ⇒ **用户新建的方案类 Agent 自动生效**，不改代码

### 2.4 呈现：前端按工具名渲染

复用**既有机制** `covTryCard(t.name, t.result, t.arguments)`（覆盖性工具已用它渲染 DOORS 矩阵）。  
新增 `altTryCard(name, resultStr, args)`：

- 只认 `alternatives_score` 这一个工具名；
- 从工具结果 JSON 渲染对比表；
- **维度名/方向/权重全部读工具返回**，前端不硬编码。

**收益**：`msg_type` 映射表、5 处链路接线、`_build_rich_card` 的 intent 分支**全都不需要改**。

## 4. 判定「平台化」的验收标准

| # | 判据                  | 怎么验                                                             |
| - | ------------------- | --------------------------------------------------------------- |
| 1 | 换维度集**不改代码**        | 改 `generate_rules.alternatives_dimensions` → 重跑打分 → 维度/方向随之变    |
| 2 | 改权重**不改代码**         | 改 `generate_rules.alternatives_weights` → 推荐结果随之变               |
| 3 | 编排规则**改文本即生效**      | 改 `skills.content` → 模型行为随之变（无需重启）                              |
| 4 | 新建 Agent **自动获得能力** | 用户自建方案类 Agent 并绑定技能 → 工具面里出现 `alternatives_score`               |
| 5 | 新增链路**不必改代码**       | 任意路径调用工具 → 结果都进 `card_data.exec.tools` → 前端统一渲染                 |
| 6 | 前端**不硬编码维度**        | 工具返回什么维度就渲染什么维度                                                 |
| 7 | 管线里**没有多方案专用分支**    | `grep -rn "alternatives" agent/pipeline_parts/` 只剩工具 handler 一处 |

**第 7 条是核心判据**：平台化 = 管线不认识"多方案"这件事，它只认识"一个叫 `alternatives_score` 的工具"。

## 5. 已知取舍（如实登记）

1. **算子仍是代码**：归一化/加权必须有实现，任何工具都一样。平台化的是**策略与触发**，不是算法本身。
2. **模型仍可能不调工具**：Skill 用 triggers 命中 + 工具描述强制引导，但这是 LLM 行为，**不能 100% 保证**。  
   ⇒ 缓解：工具描述里写明「多方案比较场景**必须**调用本工具」；skill 里写明调用顺序。  
   ⇒ 残留风险：模型自说自话地编一个"综合得分" ⇒ 由 skill 的纪律条款 + 前端对比表（真实调用才渲染）双重兜底。
3. **抽取仍需从模型输出取结构**：工具的 `alternatives` 入参由模型填。**模型填错就是填错**——  
   工具保证的是"给定输入的算分正确"，不保证"模型给的原始量是真的"。  
   ⇒ 缓解：skill 要求给出每个维度的 `rationale`（依据），人可核对。
4. **维度缺测**：缺维度不补零（不把"没测"说成"最差"），但**这会让缺测方案在覆盖率高时被推荐**——  
   故设 `min_coverage` 门槛，不足者**不参与推荐**（仍展示计分）。
5. **未做**：把"选定某方案 → HITL 确认 → 入库版本"做成闭环（属独立一阶段）。

### 6.5 实施中发现并修复的真实缺陷（6 个）

1. **绑定规则过宽**：第一版 `LIKE '%方案%'` 把 `requirement_analysis`、`review` 也绑上了  
   （"需求方案化""评审方案"等偶然命中）⇒ 给无关 Agent 注入工具面、稀释工具集。  
   收紧为**职责判据**（多方案/候选方案/方案对比/架构选型等复合词），并加**解绑差集清理**  
   （否则"改配置即生效"是假的）。⚠️ 解绑要覆盖 tool **与** skill 两种 `tool_type`  
   ——第一版只清 tool，skill 绑定残留。
2. **工具宣称"打分完成"但一个分数都没算出来**：底层算子对"无可量化维度"的方案给  
   `total=None`（**算法是对的**），但只要 `items` 非空，工具就回 `ok=True` ⇒ 对模型谎称完成。  
   已加显式判据：**至少一个方案算出总分**才回 ok=True。
3. **启动失败（两次）**：① `routers/alternatives.py` 引用了平台化重构中已移除的 `DIMENSION_KEYS`  
   ⇒ ImportError；② `main.py` 只加了 `include_router` 行、**漏了 import 列表项** ⇒ NameError。  
   **两者都是"改完没起服务就以为好了"的典型** —— 真机启动验证是必需环节，不是可选项。
4. **Agent 角色选错，用不了**：我把「多方案设计」Agent 建为 `agent_role='sub'`（子 Agent），  
   ⇒ 会话页选它当工作流时报「智能体团队不存在或未启用」（`stream.py:4320` / `execute.py:120`  
   只认主 Agent）。**它是独立工作流的承载者，必须是 `main`** ⇒ 改后用户可直接选用。
5. **★ 模型自行篡改原始量，导致推荐结论翻转**（真实 E2E 抓出，**最有价值的一条**）：  
   模型把「时延 120ms」自行换算成「时延余量 200−120=80」再传入 ⇒ 同一批方案，  
   **推荐结论从方案A翻转成方案B**（前 3 次直给原始量时是方案A）。  
   数值被改写后，比较的已不是原指标。⇒ 在**工具描述**与**技能正文**里明文禁止  
   正向化/反向化/余量化/折算，并说明「方向由平台维度配置决定，工具会自动归一化」。  
   加固后重跑同一输入：**调用原始量全程未被改写，推荐稳定为方案A**。
6. **★ JS 三元表达式优先级 bug ⇒ 工具结果卡片静默不渲染**（浏览器 E2E 抓出）：  
   |  |  |  |  |  |  
   | --- | --- | --- | --- | --- |  
   `cond ? covTryCard(...) : null || cond2 ? altTryCard(...) : null` 中，`?:` 优先级**高于** `||`，  
   |  |  |  |  
   | --- | --- | --- |  
   实际解析为 `cond ? f1(...) : (null || (cond2 ? f2(...) : null))`  
   ⇒ 当 `covTryCard` 是函数但返回 null（工具名不匹配）时，**整个表达式就是 null**，  
   `altTryCard` 永远不被调用。**Node 离线单测直接调 `altTryCard`，覆盖不到这个组合逻辑**  
   —— 只有真实浏览器 E2E 能抓到。已加括号 + 补组合逻辑断言（含变异自证）。

### 6.5b 呈现层的定位修正（浏览器 E2E 抓出的可见性缺陷）

初版把对比表渲染在**执行过程区**里（`procBlocksHtml`）。浏览器 E2E 实测：  
表格在 DOM 里**内容全对**（5 维 × 3 方案、原始量、归一化条、综合得分、推荐标记），  
但 `.proc-timeline` 是 `display:none`（过程区**默认收起**）⇒ `getBoundingClientRect()` 全 0  
⇒ **用户根本看不见**（截图里正文有模型自己写的 markdown 表格，但**组件表没出现**）。

⇒ **已提升为消息级独立卡片**（`05-markdown.js` 调 `altCardFromTools(cd)`），  
与编排卡 `renderOrchCard` 同样处理：核心产出不该藏在过程区里。  
**仍是平台化** —— `altCardFromTools` 的判据只有「工具结果形状」，不认识"多方案"这个概念。  
`06-cards.js` 的过程区不再渲染它（避免重复），`11-pipeline.js` 的流式实时路径保留  
（对话进行中就该看到）。

### 7.5 名册漂移：根因与修复（2026-11-03 已完成）

#### 根因（两层，均实测取证）

**第一层：名册数量漂移**
- 2026-10-08 V5 引入 8 个流水线节点（`agents` 634-641），并把 160「MBSE建模总体负责人」的
  `system_prompt` **手改**成「你的团队（8 名阶段节点）」。
- 但 `agent_team_members` **从未跑过收敛脚本** —— `tools/migrate_v5b_team_roster.py` 存在、
  默认 dry-run，实测 `enabled=0` 的行数为 **0** ⇒ 它从未 `--apply`。
- ⇒ 名册仍是旧 15 行：**14 个 active + 1 个 disabled 死条目**（`顺序视图（时序图）生成` id=172）。
- ⇒ prompt 说 8 名，运行时 `_team_roster_block` 喂 15 名 ⇒ **planner 收到两份矛盾名单**。

**第二层（更严重）：字段语义漂移 ⇒ 按 prompt 填必然静默降级**
- prompt 规则第 8 条原文：「子任务的 `agent` 字段必须**逐字取自上表 display_name**」。
- 但 `AgentRegistry.resolve()` **只按 `name`（intent 名）解析**，不认 display_name。
- 实测（修复前）：
  `resolve('架构骨架生成Agent')` → **回落「通用问答Agent」，工具数 0**；
  `resolve('architecture_skeleton')` → 正确，工具数 11。
- ⇒ planner 照 prompt 填显示名 ⇒ **整条流水线的子任务全部空转**
  （任务照跑、照标 done，但一个工具都调不了）。这也解释了为何 160 的流水线"看起来跑通了"。
- 附带：`_unresolved_hint` 查询同时匹配 name/display_name，于是输出
  「Agent「architecture_skeleton」存在但 status=**active**（非 active，不参与路由）」——
  **自相矛盾**，排障时会被它带偏。

#### 修复（`tools/repair_main_agent_roster.py`，幂等、默认 dry-run）

| # | 修什么 | 怎么修 |
|---|---|---|
| 1 | 名册数量漂移 | 按**实测 active 成员**重建 `system_prompt` 名册表（14 名），表头改为 `agent 名（派单填这一列）` |
| 2 | 死条目 | 把 disabled 成员（172）置 `enabled=0`（不删行，可回滚） |
| 3 | 字段语义漂移 | 规则第 8 条改为**必须填 `name`**，并写明「填显示名会静默回落成零工具 Agent」 |
| 4 | 兜底加固 | `AgentRegistry.resolve()` 增加 **display_name 兜底解析**（优先级严格低于 name）；实测 display_name 无重名、无跨字段冲突 ⇒ 反查唯一 |
| 5 | 诊断文案 | `_unresolved_hint` 按 status 分两种真话：非 active = 真停用；active = 「路由键只认 name，请改成 `xxx`」 |

**刻意不做**：不移出 `requirement_analysis` / `review` 等 active 成员 ——
那是 `migrate_v5b_team_roster.py` 的「能力收敛」语义（N 系列承接），属**业务决策**，

## 10. 选型闭环 MVP（2026-11-04 补，收掉 §6.5 第 5 条"未做"）

**对比卡此前只到「推荐 / 并列 / 数据不足」三态，人的选型决定没有落点**——选了哪个、
谁选的、当时的得分矩阵，事后查不到。本轮补上（刻意**不**做"入库为 SysML 版本"，
那需要 HIL L2 写前确认，属另一阶段）：

### 载体

| 层 | 内容 |
|---|---|
| 表 | `alternative_selections`（schema.py，append-only；重选=追加新行，卡片读最新） |
| 端点 | `POST /api/alternatives/select`（校验方案名必须在候选列里；`message_id=0` 自动定位该会话最新对比卡；写审计行 + 回写卡片 `alternatives.selected`）；`GET /api/alternatives/selections?conversation_id=` 决策史 |
