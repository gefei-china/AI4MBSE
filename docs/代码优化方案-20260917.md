# mbse_system 代码优化方案（Token 成本治理 + 结构解耦 + 冗余清理）

> 日期：2026-09-17 ｜ 视角：开发工程师 / 架构治理
> 输入：三路只读摸底（前端体积耦合、后端体积耦合、运行时 token 归因）+ 本人复核验证
> 结论先行：**"每次任务烧很多 token" 是两条独立链路叠加的结果 —— 运行时提示词无预算（A 链路）＋ 仓库噪声与巨型文件让 AI 助手每次都要通读无关内容（B 链路）。A 链路修 3 处即可拿到最大单笔收益；B 链路需要一次结构治理，其中一半以上是"删/移"而非"改"。**

## 1. 两条链路分开治

### A 链路：运行时推理 token（用户执行任务时直接付费）

**A-1 工具结果封顶并对齐（最高优先级）**
`agent/pipeline_parts/stream.py:1084` 的 `_t_content` 用的是 `result.get("result","")` **完整值**，而 `_TOOL_RESULT_CAP=6000`（`common.py:32`）只作用于 `_t_result`（前端事件与 `exec_tools` 记录）。实际后果：3 轮探测 × 每轮 3 个工具，模型侧拿到全量内容，且 `stream.py:1096-1097` 把这堆结果 append 进 `messages`，随后 `stream.py:1031`（下一轮探测）与 `stream.py:1106`（最终生成）**各自重发一遍**。
→ 处置：① 模型侧 `_t_content["result"]` 同样截断（建议 3,000 字，前端展示仍保留 6,000）；② **只保留最近一轮工具结果**，更早轮次替换为一句摘要（`{"note":"前序工具结果已省略，结论见上文"}`）；③ 探测轮与最终生成复用同一份已裁剪的 `messages`。
→ 预计：有工具调用的任务，输入 token 降 **25–40%**（结构推断，须用 §4 度量脚本验证）。

**A-2 把已有预算工具接到主流式路径**
`history.py:460 _apply_context_budget` 只有 `execute.py:243` 调用；`core/token_counter.py:52/68`（`count_messages_tokens` / `input_budget`）在测试外零使用。
→ 处置：SSE 路径在最终生成前调用 `_apply_context_budget`，并以 `input_budget(context_window=65536, max_tokens=16384)` 作为硬预算上限，超限按"检索文本 → 历史消息 → 附件文本"的优先级裁。
→ 预计：消除 10,918 tok 级别的尖峰；配合 A-3 后单任务输入稳定在预算内。

**A-3 附件文本按需注入，不做全量解析**
`history.py:59-61` 每文档解析 ≤40 块 × 2,500 字 = **100,000 字**，而 `stream.py:880` 只注入前 4 块（≈10,000 字）；且 `att_text` 拼接位置在"检索到的互联数据："**之前**，`_apply_context_budget`（`history.py:470-476`）只裁后半段 → 附件永不被预算裁剪。
→ 处置：改为"先按需检索命中块，再注入"；把 `att_text` 纳入预算裁剪范围；单文档注入上限从 10,000 字降到 4,000 字。

**A-4 去重与降噪（配置层，零风险）**
- 两份 95% 相同的 system prompt 装配块（`stream.py:974-1007` / `execute.py:200-233`）→ 抽成 `prompt_assembly.py` 单一实现。
- `prompts` 表：删掉 6 行重复的 12 字测试模板；修 `{{linked_data_scope}}` 占位符未替换（`prompt.py:114-142`）。
- `agents.system_prompt` 44,762 字：SSE 路径不消费 → **决策点**：删除 9 个视图 Agent 的冗余 prompt（36K 字），或明确接入 + 按意图只注入命中 Agent 的 prompt（不再整块注入，最坏 7,981 字）。

**A-5 检索对齐与 embedding 批合并**
- `rag.py:123` 实取 `top_k=8`，而 `context.py:159-179` 只用 `chunk_hits[:3]` → 多算 5 条后丢弃：把 top_k 对齐为 4。
- 单请求至少 5–7 次独立 embedding（`intent.py:305`、`skills.py:69/87`、`tools.py:196`、`history.py:117`、`rag.py:123/470`）→ 同请求内批合并（延迟收益为主，费用收益次要）。

**A-6 串行调用收敛**（需你拍板深度）
`clarify_detect`（`session.py:105`）**每次都调**，即使语境明显不需要澄清；编排路径 `_ORCH_MAX_TASKS=6` 各自跑完整管线（最坏 60+ 次调用）。`plan_refine` 平均 completion 7,736、`plan_summary` 平均 7,470。
→ 处置：① `clarify_detect` 加规则前置（意图明确时跳过）；② 编排子任务复用父任务已装配的上下文，避免各自重建；③ 给 `plan_summary/plan_refine` 输出加长度上限（如 1,500 tok）。

### B 链路：AI 编码助手上下文（你改代码时的 token）

**B-1 给 AI 画"禁读区"与"功能→文件"地图（零代码风险，最先做）**
仓库没有 `.cursorignore` / `.traeignore`，也没有 `AGENTS.md`。AI 每次检索都会命中 `_archive/`（705 文件）、`backups/`、`tmp/`、`screenshots/`、`outputs/`、`static/uploads/`、`static/skill_packages/`（2,024 文件）。
→ 处置：新增忽略清单 + 一份 `AGENTS.md`（含"改导航 → `static/js/mods/02-shell.js`；改本体 → `21-ontology.js` + `routers/ontology*`；改知识库 → `15-kb.js`/`20-docs.js` + `routers/knowledge_parts/*`"的映射表）。
→ 收益：直接砍掉 AI 检索时的绝大部分噪声命中。

## 4. 度量方法（不能凭感觉说"省了"）

1. **运行时**：`llm_usage_stats` 已有实测列（prompt/completion tokens、intent）。写 `tools/verify/token_baseline.py`：按 intent 分组输出"优化前 7 天 vs 优化后 7 天"的 avg / p95 / max prompt，以及截断次数（completion == max_tokens 的计数）。

3. **AI 编码侧**：以"改一个功能必须读的字节数"为指标 —— 目标：改任一功能所需通读的源码从当前 62.5 万 token 量级降到 **≤10 万 token**（通过忽略清单 + 拆分 + 映射表实现）。

1. **导入环不存在，但这是"假安全"**：项目用**函数内惰性 import** 切断了所有环（例如 `core/config.py` 里 `from database import get_db` 位于函数体内）。后果是 **`py_compile` 与 pytest 都无法发现 import 路径错误**——只有运行时首次触达该分支才会炸。任何"改 import 路径"的迁移**不能靠编译与测试兜底**。
2. **约 460 个 skill 脚本硬编码根模块名**（`static/skill_packages/`，已被 `.gitignore` 忽略、且不在 AI 上下文里）→ "全仓改 import"**必然漏改这批**，且漏了不会立刻暴露。
3. 根目录模块**彼此高度互依**，且**多数被 `routers/` 直接引用**（属分层绕过），无法按"域"干净切开。

**结论**：**不建议做全量内聚**。若仍要做，只取依赖最内聚的 3 簇，必须用「**先建 `domain/` + 根文件保留 re-export shim，再逐步清理调用点**」的渐进方案（而非直接改所有 import），并**排在所有其他拆分之后**。

### 7.8.2 ⚠️ 仓库级缺陷：`.gitignore` 未锚定导致**仓库无法复现**（2026-09-18 已修复，提交 `52a90aa`）

**这是本轮最重要的发现，严重性高于任何一次文件拆分。**

**根因**：`.gitignore` 的四条模式

```
_*.py
_*.txt
_*.log
verify_*.js
```

**均未加前导 `/` 锚定根目录**。而 gitignore 中**不带 `/` 的模式会在任意深度匹配**。原意是「忽略根目录的一次性调试产物」（见 §2 档 1），实际却把子目录里所有以 `_` 开头的文件一并忽略。

**后果（量化）**：磁盘上有 **14 个项目自有 `__init__.py`，而 git 跟踪数为 0**：

| 被忽略的包初始化文件 | 承载的关键内容 |
|---|---|
| `database/__init__.py` | 导出 `init_db` / `get_db`（`main.py:14` 依赖） |
| `routers/__init__.py` | 装配 23 个 router |
| `llm/__init__.py` | 401 行，LLM broker + 降级留痕 |
| 其余 11 个 | `agent/` `agent/pipeline_parts/` `core/` `database/migrations/` `knowledge_pipeline/` `llm/providers/` `models/` `repositories/` `services/` `skills/` `workflows/` |

→ **全新的 `git clone` 会在 import 阶段直接崩**。也就是说：**这个仓库从 `baseline-20260918` 建立基线起就无法复现项目**（issue 由 S7-3 提交 `database/migrations/__init__.py` 时暴露）。

1. 四条模式改为根目录锚定：`/_*.py` `/_*.txt` `/_*.log` `/verify_*.js`（恢复原意）；
2. 为保持原状，显式忽略 `tools/legacy/`（25 个历史调试 `.js`）；
