## 四、核心问题详解

### 4.1 🔴 问题一：`top_k` 与重排候选倒挂（重排层实质空转）

**现状链路**（`agent/rag.py` + `knowledge_engine.hybrid_search`）：

```
GraphRAG.retrieve()
  └ hybrid_search(top_k=4)        ← 从 config 的 rag.top_k 读，实取 4 条
       ├ BM25 排名（取 top_k*2 = 8 条）
       ├ 向量排名（取 top_k*2 = 8 条）
       ├ RRF 融合 → 取前 4 条
       └ llm_rerank(candidates, top_k)   ← rag.rerank_max_candidates=8，但手上只有 4 条
  └ context 注入 chunk_hits[:3]
```

**行业标准模式**（多源一致）：

| 阶段 | 行业值 | 本工程 |
|---|---|---|
| 每路召回 | 20–50（BM25 + dense 各一路） | 8（=top_k×2） |
| RRF 融合后 | 20–50 | 4 |
| 送重排 | **20–50** | **4** |
| 注入生成 | 3–8 | 3 |

**后果**：重排要「有得挑」才有价值。候选 4 条取前 3，重排能改变的只有第 3 条的位置 —— 收益被结构性压到接近 0，而每次检索仍要付一次 LLM 调用（+2~5s 延迟，配置注释自述）。

**建议**（需实测确认收益/延迟比）：
- `rag.top_k`：4 → **20**（行业下界）
- `rag.rerank_max_candidates`：8 → **10**（重排窗口略大于注入数即可）
- 注入侧不动（`chunk_hits[:3]`），保持「广召回 → 重排 → 窄注入」
- 验证口径：用现成 golden 风格查询集（P1-6 待办）测 Recall@K 与延迟；**先把 P1-6 评测集建起来再调**，否则又是拍脑袋

> ⚠️ 注意成本：`top_k` 从 4 提到 20，RRF 参与条数 ×5，重排 prompt 变长 → 延迟与 token 双增。这正是「先建评测集再调参」的理由。

### 4.2 🔴 问题二：dense 阈值标定方法不一致

同一 `context` 组、同一 embedding 量纲下的三个阈值：

| 项 | 值 | 标定方法 | 结论 |
|---|---|---|---|
| `semantic_fallback_gate_dense` | 0.79 | **分位等价映射**（有脚本 + 实测 p90/max） | ✅ 可信 |
| `topic_retrieve_threshold_dense` | 0.35 | 无记录 | 🔴 偏松 |
| `topic_group_match_dense` | 0.30 | 无记录 | 🔴 偏松 |

**建议**：用**同一套标定脚本**（`calibrate_dense_thresholds.py` 已存在）对这两个阈值做分位等价映射 —— bigram 路的 0.15 对应 dense 路的哪个分位，就用那个值。这样三个阈值方法统一、可复现，且能写进配置注释。

**参考锚点**（若不做标定，按行业经验表的保守取值）：中文 embedding 下「有一定关联」档 0.5–0.7，取**下沿 0.5** 作为「宁宽松勿严格」的起点。

### 4.3 ⚠️ 问题三：Token 预算用绝对值，换模型不自适应

行业两家都把「何时压缩/裁剪」表达为**上下文窗口的占比**：

| 产品 | 参数 | 口径 |
|---|---|---|
| Codex | `model_auto_compact_token_limit` | 官方示例 128k 窗口 → **64000（50%）**，且注明「设得比 context window 低以留余量」 |
| Claude Code | 自动压缩阈值 | 默认约 **92%**，可配（社区推荐 80%；>0.83 有已知内部 cap） |

本工程：`budget_retrieval_tokens=5000` / `budget_history_tokens=3000` 是**绝对数**。当前 provider `context_window` 已从 8192 解锁到 65536（2026-09-20 拍板），若日后换到 1M 窗口，这两个数不会自动放大，等于白白浪费窗口。

**建议**：保留绝对值（兼容），新增一对**占比键**（如 `context.budget_retrieval_ratio` / `budget_history_ratio`），消费侧「有占比用占比、无占比回落绝对值」——**与既有「token 项填 0 = 回退字符版」的兼容模式同构**，不破坏现有配置。

### 4.4 ⚠️ 问题四：HyDE 默认开缺乏 A/B 依据

- **文献侧**：Weller et al. (EACL 2024) 的结论是「expansion 对弱检索器有帮助，对强检索器常有害」；JetBrains 的 Adaptive HyDE 把「条件触发」当成正确形态。
- **成本侧**：本工程索引期 hyde 使向量化请求数**翻倍**（2606 块 → 实测 421.9 s，§1c）。
- **本工程现状**：`hyde_enabled=True` 且**无 A/B 数据**；配置注释只写了「措辞差异大的提问召回更好」。

**建议**：纳入 P1-6 评测集后做一次开关 A/B（同查询集测 Recall@K / 延迟）。若收益不显著，改为**条件触发**（首轮 RRF 最高分低于某阈值时才跑 HyDE）——这正好也能省掉大部分索引期翻倍成本。

## 五、行业对标速查（供调参参照）

### 5.1 Claude Code（Anthropic 官方 + 社区实践）

| 维度 | 做法 |
|---|---|
| 上下文上限 | **1M token** 可用（Fable / Sonnet 5 / Opus 4.6+）；压缩机制在大窗口下同样工作 |
| 自动压缩 | 接近窗口上限时自动总结（保留代码模式 / 文件状态 / 关键决策）；可 `/compact <聚焦指令>` 指定保留内容 |
| 阈值 | 默认约 92%；社区推荐 **0.8**；<70% 视为健康；>90% 进入「dumb zone」 |
| 手工干预 | `/clear` 换任务、`/rewind` 部分压缩、`/btw` 不进入历史的侧问 |
| 指令文件 | `CLAUDE.md` **理想 < 60 行 / 上限 150 行** |
| 工具开销 | MCP < 10 个、工具 < 80 个；「每个 MCP 给每次请求加开销」 |
| 核心原则 | **「策展式上下文优于全量上下文」** —— 聚焦的 50k 优于臃肿的 150k；不相关信息比缺失信息更伤 Agent |

| `project_doc_max_bytes` | **32 KiB**（AGENTS.md） | 项目指令文件读取上限 |
| 上下文管理 | 自动 compaction | 与 Claude Code 同构 |

> 与本工程的关系：Codex 把「工具输出上限」和「项目指令文件上限」做成显式参数 —— 本工程对应物是 `context.model_context_chars=800`（建模工作记忆）与 `budget_retrieval_tokens`。**`tool_output_token_limit=12000` 这个量级值得参照**：本工程检索预算 5000 token 相对更保守。

### 5.3 RAG 工程通用值

| 环节 | 通用值 | 来源 |
|---|---|---|
| Chunk 大小 | 256–1024 token，重叠 10–20% | 生产 RAG 指南 |
| 每路召回 | 20–50（hybrid 时 BM25 + dense 各一路） | 多源一致 |
| 重排候选 | **20–50**（<20 无选择空间，>50 收益递减） | 重排专项指南 |
| 注入生成 | 3–8（常见 3–5） | 多源一致 |
| RRF 常数 | **k ≈ 60** | RRF 原论文 |
| 重排分数过滤 | Cohere 量纲 < 0.3 视为弱相关可丢弃 | 重排指南 |
| 中文 embedding 阈值 | 0.9+ 高度相关 / 0.7–0.9 明显 / 0.5–0.7 一定关联 / 0.3–0.5 很弱 / <0.3 基本无关 | 中文 embedding 阈值经验表 |
| 阈值调法 | **「先不加阈值跑一批查询看分数分布，再选能滤噪声但不太丢结果的值；不确定时宁宽松」** | 检索后处理指南 |
| Context precision 实况 | naive top-k 通常只有 **0.3–0.6** ——这正是重排的价值所在 | 生产 RAG 指南 |

> ⚠️ **HyDE 的负面证据**：Weller et al. (EACL 2024) 系统研究 11 种查询扩展 × 12 数据集 × 24 检索器，发现**扩展收益与检索器强度负相关**。原文建议：「弱检索器或语料格式与训练分布差异大时使用，否则避免」。HyDE 原论文的对比基线是**无监督 Contriever**，论文自己描述「对微调过的检索器是 comparable 而非 superior」。

## 八、P1-6 评测集：是什么、怎么构建（2026-09-21 落地）

§7.4 里列的四项"待实测"，卡的都是同一件事：**没有带标注的评测集，"调参"就只能是拍脑袋**。
本章把它建起来，并记录建集当天就查出的三个真问题。

### 8.1 测试集是什么：不是"一组 query"，而是"三域 + 两层漏斗 + 语料指纹"

一个能用的评测集必须能回答**具体**的问题。本工程建成的是：

| 域 | query 来自 | gold（标准答案）来自 | 主要指标 | 回答什么问题 |
|---|---|---|---|---|
| **doc**（20 例） | 章节标题（清洗 markdown 记号后） | 该章节下**全部** chunk 的 `(source_doc, chunk_index)` | recall@1/3/5/10、MRR@10、nDCG@10 | 文档检索的最终顺序好不好 |
| **graph**（18 例） | release 分支真实关系的两端实体名 + 关系类型模板 | 该实体对 + 关系类型 | route 准确率、实体召回、关系命中 | 该走图谱时是否走对、子图是否对 |
| **neg**（8 例） | 手写（域外闲聊 / 域内但不存在 / 术语邻域不相关） | 应为"没有依据" | 路由是否合理、是否高置信乱走图谱 | 没有依据时会不会硬答 |

**两层漏斗（关键：只报一个总分就看不出该调哪一段）**

```
P 层（召回池）   hybrid_search 的 RRF 排序（关掉重排）  → pool_recall@k
F 层（注入前）   retrieve() 返回的 chunk_hits（重排生效）→ recall@k / MRR / nDCG
```

判据因此是确定的：

- **池里就没有**（`recall_miss_rate` 高）→ 候选宽度不够，**调 `recall_k`/`top_k` 才有用**，调重排和阈值白费。
- **池里有、F 层没有**（`rerank_drop_rate` 高）→ 重排把对的挤下去了，**调 `rerank_max_candidates`/重排策略**。
- **池里没有也不该有**（neg 高置信走图谱）→ 精度问题，**调 `route_threshold` 与三因子权重**。

**语料指纹**是评测集的一部分，不是附带说明：同一 query 在不同时点 route 会变（§8.3 #1），
不比对就会把"环境变了"误读成"参数调坏了"。故 `build_evalset.py` 写入指纹
（chunks 数、release 实体数、release 实体名集合 sha1），`run_eval.py` 启动即比对、漂移高声告警。

### 8.2 怎么构建：标注从语料结构"派生"，不是人工写

三域里 doc 与 graph 的 gold **不是人写的，是推导出来的**：章节 → 其下 chunk 是确定集合；
关系 → 两端实体是确定事实。好处是可重复、可审计、无主观漏标。

- **doc 域**：按 `(source_doc, section)` 分组 → 清洗标题（去 `#`/`*`）→ 过滤纯记号标题
  （如 `0..*`）与 chunk 数不在 3~25 的碎片章节 → 每文档抽样 5 个 →
  query 用清洗后标题，gold 用该章节全部 chunk。
  gold 键用 **`(source_doc, chunk_index)` 自然键**——已校验全库 0 组重复，
  且 `chunk_hits` 恰好携带这两个字段（chunk `id` 反而不在返回里）。
- **graph 域**：取 release 分支、两端实体均非 deprecated 的关系 → 按 `relation_type`
  套问句模板（`CONTAINS`→"X 包含哪些 Y"、`DERIVES`→"由 X 派生出的 Y 有哪些"、
  `VERIFIED_BY`→"X 由哪些 Y 验证"…）→ 按关系类型**轮转抽样**（否则 22 条 DERIVES 会淹掉 2 条 TRACE）。
- **neg 域**：手写。


### 8.3 建集当天查出的四个真问题

Build 评测集最大的价值不是"给了个分数"，而是**当场把三个此前看不见的问题照出来了**。

**#1 🔴 实体链接跨进程不可复现（根因：`_tokens` 返回 `set`）**

现象：同一 query「卫星通信系统包含哪些分系统」在 `query_routing_stats` 里
`03:46:31 → graph/0.88 (g=5)`，`03:47:15 → vector/g=0`；40 秒内翻转，看起来像"语料被改写"。

追查：`_entity_link` 在**同一进程内**重复 6 轮、10 轮都完全稳定 → 一度误判为"语料时点差异"。
但换**另一个进程**跑同一 query，结果就变了。定位到：

```python
toks = [t for t in GraphRAG._tokens(query) if len(t) >= 3]
for t in toks[:8]:            # ← _tokens 返回 set，取"任意" 8 个
    ...  name LIKE %t% ...
... LIMIT 10                  # ← 再截断到 10 条
```

`_tokens` 返回 `set()`，而 **Python 字符串哈希受 `PYTHONHASHSEED` 随机化** →
`toks[:8]` 每个进程取到的 8 个 token 都不同 → LIKE 条件不同 → `LIMIT 10` 返回不同实体。
实测同一 query 在两个进程里，一个命中「蓄电池组」、另一个漏掉。
**验证**：固定 `PYTHONHASHSEED=0` 后 3 个进程完全一致。

影响：**同一 query 的路由决策、以及所有评测分数，都不具备跨进程可复现性** ——
"改动前后对比"在统计上不成立。这解释了为什么同一分钟内路由会翻转，
也**推翻了我先前"语料被改写"的判断**。

修复：`_tokens` 改为**有序去重列表**（生成顺序确定），并把「按分隔符切出的整词」优先入列
（整词比滑窗碎片更贴近实体名，顺带修掉"长句里第二个实体名被挤出前 8 个"）。
修复后：不固定 hash seed 下 3 进程结果**完全一致**，且原先漏掉的
`蓄电池组`/`行波管`/`转发器` 全部命中 —— 确定化与召回修复是同一改动的两面。
（三个调用点均只做遍历/切片、无集合运算，已逐一核对，改类型安全。）

**#2 ⚠️ 负样本假阳性：没有答案的问题拿到 graph conf=0.9**

「宽带通信卫星的太阳能板清洗周期」→ `route=graph, conf=0.9`（且 `chunk_hits=0`）。
查因：实体链接命中「GEO 宽带通信卫星系统 / 宽带通信卫星平台 / 宽带通信星座 / 宽带通信地面段」，
牵出 **128 条**关联关系。三因子置信度只算「命中覆盖度 / 关系连接性 / 类型匹配度」，
**不含"这两个实体是否真跟问题相关"** → 命中面越宽、置信越高，与问题是否可答无关。
这是**精度缺陷**，neg 用例正是为此而设。修法（调 `route_threshold`、给三因子加"问题相关性"维度）
需人工复核后的 route 标签，本轮未动。

**#3 ⚠️ 同码同语料，两次运行分数不同（#1 的影响量级）**

| 运行 | 代码 | 语料 | recall@3 | MRR@10 |
|---|---|---|---|---|
| baseline | 同一份 | 同一份 | 0.85 | 0.858 |
| control（另一进程） | 同一份 | 同一份 | **0.90** | **0.867** |

差 0.05 / 0.009，**全部来自 hash 种子导致的 token 选择差异**。
这正是 §7.3 里"调参差异若小于噪声带宽即不可判"的具体化：修复前，`top_k` 这类改动的
真实收益很容易被这个噪声吃掉或伪装成收益。

**#4 ⚠️ LLM 重排自身不稳定 → doc 域 F 层存在「分数噪声地板」**

修掉 #1 后，graph 域三轮完全一致（route 1.000 / 实体召回 0.972 / 关系命中 1.000），
但 **doc 域 F 层仍漂**：`recall@3`/`recall@5` = 0.85 ↔ 0.90、`MRR@10` = 0.857 ↔ 0.867，
而 **P 层（`pool_recall`，不含 LLM）三轮恒为 0.90**。差异只可能来自 F 层独有的那一环：`llm_rerank`。

隔离实验（`tmp/p21/rerank_variance.py`）：固定 query + **固定 RRF 候选**，反复调 `llm_rerank` 5 次：

| query | 5 次调用得到的排序种数 | top-1 | top-3 |
|---|---|---|---|
| `2.4 C3 - Unambiguous` | 3 种 | 稳定 | 稳定 |
| `648 Systems Modeling Language v2.0` | 4 种 | 稳定 | 稳定 |
| `7.12.1 Ports Overview` | 3 种 | **2 种** | **2 种** |

→ **同一输入、同一候选，重排后的排序每次都可能不同**；多数情况下 top-3 能守住，但会翻。

**这是必须记住的判据（与 `preflight.py` 的"延迟噪声带宽"同理）**：
doc 域 F 层的差异 **小于 ≈0.05（recall@3/@5）或 ≈0.01（MRR）时不可判** ——
否则会把重排的随机波动读成调参收益。两点推论：
1. **要判断"召回宽度够不够"，优先看 P 层的 `pool_recall`/`recall_miss_rate`** —— 这一层无 LLM、可复现。
2. 要压低噪声需另做（固定 seed/temperature 或多样本取均值），本轮未做。

### 8.4 基线数据、负对照，与修复 #1 的实测收益

`--control` 是**反空转**设计：把 doc 域的 gold 在例间**轮转一例**后重算。
若轮转后分数与真实分数相近，说明指标没在测"query↔gold 对齐"，结果是假绿。

| 指标 | 真实标签 | 轮转标签（负对照） |
|---|---|---|
| recall@1 | **0.85** | **0.00** |
| recall@3 | 0.85 ~ 0.90（见 #4 噪声） | — |
| recall@5 | **0.85 ~ 0.90** | **0.00** |
| recall@10 | **0.90** | **0.00** |
| MRR@10 | **0.857 ~ 0.867** | **0.000** |

→ 差出整量级，指标**确实在测对齐关系**，不是空转。（修复前后两轮负对照均为全 0。）

**修复 #1（`_tokens` 确定化 + 整词优先）前后的同一评测集对比**

| 域 | 指标 | 修复前 | 修复后 | 差 |
|---|---|---|---|---|
| graph | **实体端点召回** | 0.750 | **0.972** | **+0.222** ↑ |
| graph | **route 准确率** | 0.944 | **1.000** | **+0.056** ↑ |
| graph | **关系命中** | 0.944 | **1.000** | **+0.056** ↑ |
| graph | 延迟 p50 | 9ms | 7~8ms | -1~2ms |
| doc | pool_recall@20（**无 LLM**） | 0.900 | 0.900 | **±0** |
| doc | recall@1 / @10 | 0.85 / 0.90 | 0.85 / 0.90 | ±0 |
| doc | recall@3 / @5 | 0.85 | 0.85~0.90 | 在 #4 噪声内 |
| doc | mrr@10 | 0.858 | 0.857~0.867 | 在 #4 噪声内 |
| doc | recall_miss_rate | 0.10 | 0.10 | ±0 |
| neg | 高置信误走图谱 | 1 | 1 | ±0 |

结论：改动**只让图谱侧变好，没有牺牲文档侧**——18 条 graph 用例里原先漏链接端点的 4 条全部复原
（`转发器`/`蓄电池组`/`行波管` 等），route 从 17/18 升到 18/18。
**doc 域只有"无 LLM 的 P 层"可作为判据**（恒 0.900），F 层的 0.85↔0.90 波动属 #4 噪声、
不可归因于本次修复；neg 域不变，说明 #2 与实体链接是**两个独立缺陷**。

> ⚠️ **一处口径自查（如实记录）**：初次对比时 `recall_miss_rate` 显示 `0.10 → 0.00`，
> 看着像改善，实为**我在两轮之间改了这个指标的实现语义**（`not x` 改成 `x is False`，
> 而 `0.0 is False` 恒不成立 → 恒为 0）。已修正为显式排除 `None`，**真实值两轮均为 0.10**
> （doc 域 20 例里有 2 例是池里就没有，见样例 [13]/[14] 的 `pool#0`）。
> 这类"跨版本对比把口径变动读成收益"的坑，与 §8.3 #3 是同一类错误的两种形态。

**doc 域（20 例，P 层池宽 20）**：`pool_recall@20=0.90`、`recall_miss_rate=0.10`（2 例池里就没有）、
`rerank_drop_rate=0.00`（**重排没把对的挤掉** —— §7.2 修掉的 `top_k`/重排窗口倒挂在此得到验证）。

**graph 域修复后（18 例）**：route 准确率 **1.000**（18/18）、关系命中 **1.000**、实体端点召回 **0.972**。

→ "该走图谱时走对"的收益不只是准确率，还有延迟。

**neg 域（8 例）**：路由合理 7/8、`false_graph_confident=1`（即 #2）、仅 2/8 返回 0 命中

### 8.5 用它调参的标准流程（把"感觉变好"换成"数字变好"）

1. `preflight.py` 确认链路未降级 + 记下**延迟噪声带宽**（差异小于它就不能判）；
2. `run_eval.py --tag before` 基线（含 `--control`）；
3. 改**一个**参数；
4. `run_eval.py --tag after --baseline ...` 出对比；
5. 按 §8.1 的判据表看**哪一层**动了，而不是只看总分；且**先看 P 层**（无 LLM、可复现）——
   F 层的差异必须大于 §8.3 #4 的噪声地板（recall@3/@5 ≈0.05、MRR ≈0.01）才算数；
6. 语料若有改动 → 先 `build_evalset.py` 重建再比。

| 指标（doc 域 n=20） | HyDE **ON**（2 轮） | HyDE **OFF**（3 轮） | 判读 |

#### (b) #9 `rag.route_threshold` + 三因子权重：**0.75 → 0.70**（前者对一类正例结构上不可达）

做法：`tools/eval/calibrate_routing.py` —— 取 graph 域 18 条正例 + neg 域 8 条负例，
用**与线上同构的离线置信度重算**（自证 26/26 与线上报告值逐条一致）做阈值与权重双扫描。
结果：`tmp/p21/routing_calibration.json`。

根因是**结构问题，不是参数偏紧**。三因子满分
= `w_cov·min(n_ent/5,1) + w_rel·min(n_rel/3,1) + w_typ·(n_typed/n_ent)`：
命中 **2 个实体**（`2/5 = 0.4`）、关系与定型都满（各 1.0）时
= `0.5×0.4 + 0.3 + 0.2` = **0.700 < 0.75** → 这类正例**永远够不着阈值**，
只能白走 mixed 分支（白付向量检索 + LLM 重排）。实测 18 条正例里有 **7 条**的 `conf` 恰为 0.700。

阈值扫描（18 正 / 8 负）：

| 阈值 | TPR（正例短路） | FPR（负例误短路） | balanced_acc |
|---|---|---|---|
| 0.30 ~ **0.70** | **1.000** | 0.125 | **0.9375**（平台区） |
| 0.75 | 0.667（12/18） | 0.125 | 0.7708 |
| 0.85 | 0.444 | 0.125 | 0.6597 |
| ≥0.90 | 0.333~0.389 | 0.000 | 0.67~0.69 |

- **取值 0.70 = 平台区上沿**（"仍能让全部正例短路的最高阈值"）。⚠️ 如实声明：
  数据在 0.30~0.70 之间**无法区分**（TPR/FPR 完全相同），脚本 argmax 落在平台区下沿 0.3；
  取上沿是**保守选择** —— 给语料增长后留精度余量，**不是"最优阈值"**。
- **代价/收益实测**：短路路径 **1~3 ms**，mixed 路径中位 **1894 ms**（max 4594 ms）。
  0.70 下 18/18 正例短路（0.75 只 12/18）→ **6 条查询各省 ≈1.9 s**（合计 ≈11 s / 18 条），
  而负例侧 FPR **一毫未变**（0.125 → 0.125）—— **零代价**。
- **三因子权重**：联合扫描最优仍是现网 `0.5 / 0.3 / 0.2`（`best_joint.w`），**不改**。
- ⛔ **剩下的 1/8 负例误短路与阈值无关**：`neg-07` 的 `conf=0.90`，阈值要抬到 0.90 以上才能挡住，
  但那时正例只剩 5/18 → 属**实体链接精度**问题（§8.3 #2：三因子不含"问题相关性"），**未修**。
- ⚠️ **标定前提未变**：正负例仍是**弱标注**（"名字可链接" ≠ "意图该走图谱"），
  只不过 18 正例的 `conf` 分布（7×0.70 / 4×0.80 / 2×0.90 / …）与"2 实体即满分"这条结构解释
  **完全吻合**，故本次结论的结构性部分是硬的；FPR 侧仍需人工复核（§8.7）。

#### (c) #11 手工调优值 / 出厂默认的界线：清掉 override 镜像

`~/.workbuddy/mbse_config.json` 又变成了**全量镜像**（把当轮页面上全部字段原样写回）——

→ 此后**"本机调优值"只剩这一处**（且它必须留：3000 ≠ 2600），出厂默认与手工值的界线清晰。

### 8.7 已知局限（如实）

  （已在 evalset.json 的 `notes` 与每例 `label` 字段标注）。

  3 条注入量下 recall 对"注入截断"不敏感；要测 `inject_k` 需另建"单答案"用例集。

- **【标定】** 本工程有实测脚本 + 数据 + 结论（如 `semantic_fallback_gate_dense=0.79`）
- **【经验】** 无标定记录，凭工程直觉设定 —— **这是本报告的主要发现面**
- **【特有机制】** 本工程独有机制，行业无对标物（话题分段、图谱置信三因子）

**可复现的标定方法**（本工程已有先例，应推广）：
1. **分位等价映射**：对同一组样本同时算 bigram 分与 dense 分 → 求「bigram 阈值 X 在 dense 分布的等价分位」→ 得 dense 阈值。脚本：`calibrate_dense_thresholds.py`
2. **双路独立阈值**：bigram 与 dense 量纲不同，**不可共用阈值**（设计上已分离，正确）
3. ⚠️ **不要顺手改阈值**：§1c 已记录「dense 路首次真正生效后，`tool_threshold=0.12` / intent 0.40/0.70 / context 补召门 0.5 仍是 bigram 经验值，需另做小轮次重新标定」—— 本报告 4.2 与此为同一件事的不同侧。
