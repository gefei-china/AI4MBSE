## 2. 能力簇：8 个互斥业务族 + 1 个横切基础族

实现：`core/capability_clusters.py`（策略即数据，代码只消费）。

| 族 id | 名称 | 成员 Agent | 路由可见 |
|---|---|---|---|
| `requirement` | 需求工程 | analysis / quality / structuring | ✅ |
| `design` | 设计与建模 | design / 工程建模方案设计Agent / 多方案设计 / 多方案生成 / architecture_skeleton / view_expansion / methodology_resolver | ✅ |
| `verify` | 校验与评审 | review / model_validation_repair / trace_verification | ✅ |
| `change` | 变更与影响 | impact / change_safety_gate | ✅ |
| `report` | 报告与导出 | report_generation | ✅ |
| `knowledge` | 知识与问答 | knowledge_qa / chat | ✅ |
| `platform` | 平台数据读写 | 智源对接agent / 智源数据读写agent / model_release | ✅ |
| `orchestration` | 编排总控 | MBSE建模总体负责人 | ❌ 主 Agent 是执行主体，不是候选 |
| `shared` | 横切基础能力 | 文件/代码/文档/元能力/行业调研 | ❌ 不参与路由 |

覆盖率体检：**22 / 22 active Agent 全归族，0 未映射 / 0 陈旧映射 / 0 错配**。

### 2.1 需求域合并后的族内分工（第 2 问）

合并不是删 Agent，而是**路由只出族，族内按输入形态确定性分派**：

| 输入形态 | 判据（关键词，纯代码） | 落到 | 产出 |
|---|---|---|---|
| 已写好的需求文本，要挑毛病 | 质量评审 / 模糊词 / 不可验证 / 问题清单 / 写得对不对 | `requirement_quality` | 结构化问题清单（不改写需求） |
| 长文本 / 批量，要拆条目 | 条目化 / 结构化 / 拆成条目 / 分类标注 / 访谈记录 | `requirement_structuring` | 带 ID 的需求条目清单 |
| 模糊或缺失的诉求，要产出规格 | 以上都不命中（默认） | `requirement_analysis` | 需求规格（ID/MoSCoW/GWT 验收） |

三类在**用户语言里确实无法稳定区分**（上一轮 11 条用例中 2 条错的都在这里），所以交给确定性判据比交给 LLM 猜更可靠、零延迟、可单测。

### 2.2 其他插件按能力聚合（第 2 问后半）

`cluster_of_asset(name, source, category)` 派生规则，**不手工逐个标注**：

- **来源优先**：`source='mcp'` → `platform`（实测 71 个 MCP 工具里 **70 个名字不含「智源/mcp」**，按名字匹配会漏 98%）；`category='平台集成'` 同理。
- **名字兜底**：`view_generation/skeleton/视图` → design；`validation/repair/校验/修复` → verify；`requirement/需求` → requirement；`report/报告` → report；`change/变更` → change；其余 → shared。
- 结果：**244 项资产 100% 归簇**（技能 35 / 工具 108 / 插件 101），横切基础族 97 项。

这个「簇标签」就是第 4 问要的**能力范围**：后续 JIT 工具注入、技能召回、插件市场分组都可以按簇裁剪，而不是全量铺开。

## 3. 意图识别归属：调研 + 实证（第 3 问）

### 3.1 国内外 Top 平台做法

| 平台 | 路由主体 | 关键做法 / 原文要点 |
|---|---|---|
| **OpenAI**（官方 *Heuristics for agentic system design*） | **独立代码级 Router** | 明确建议「尽可能把决策从 LLM 抽到显式软件」：*router-based* 具备速度与效率（本地 IF/ELSE 远快于外部 API）、可测试可预测、透明可靠；*orchestrator agents* 留给开放域。高风险/生产流程推荐 router-based。 |
| **OpenAI Agents SDK** | 独立 triage agent（handoff） | 分诊 Agent 识别意图后转交专家；官方同时给出 `agent-as-tool` 与「子 Agent 不宜过多」的边界。 |
| **Claude Agent SDK** | **主 Agent 自主委派**（subagent） | 主 Agent 保留决策权，子 Agent 有独立上下文窗口；配 **Tool Search / defer_loading** 按需加载工具（上下文 77K→8.7K，MCP 工具选择准确率 79.5%→88.1%）。 |
| **LangGraph** | supervisor（独立节点） | 「supervisor 可以理解为 tools 是其它 Agent 的 Agent」；路由逻辑常为规则驱动而非每次 LLM。 |
| **Dify / Coze / FastGPT**（国内） | 独立「问题分类器 / 意图识别」节点 | 分类目标是**工作流分支**（5–10 类）而非"人设"；Dify 实战复盘明确：意图识别与槽位抽取拆成多个节点会「**调用次数增加、延迟增大**」，进阶方向是**前置 RAG 召回缩候选 + 合并节点降延迟**。Coze 3.0 默认改回单 Agent 自主规划，拆分阈值是「prompt > 3000 字或 > 5 个复杂工作流」。 |
| **生产量化**（Eucalipse / RouteLLM / vLLM Semantic Router） | 两阶段：向量召回 + 小模型验证 | 30 个 action 下 <200ms、95% 准确率；把完整目录塞给旗舰模型要 2–5s 且会随目录改写发生**行为漂移**；vLLM Semantic Router 报 +10.2% 准确率 / −47.1% 延迟 / −48.5% token；RouteLLM 报 85% 成本下降 @95% 质量。 |

**共性**：① 都不是「22 选 1」，分类目标是**能力/分支**；② 都保留「不选 / 兜底」出口；③ 都把**确定性前置**放在 LLM 之前；④ 国内平台明确指出「多拆一个 LLM 节点 = 多一次延迟」。

### 3.2 本平台实证 A/B（可复现）

`tools/verify/verify_intent_placement_ab.py`：15 条 gold × 4 组，同一 LLM（deepseek-v4-flash）、同一 temperature=0、同样 1 次调用，唯一变量是 prompt 构造与候选池。

| 组 | 准确率 | 平均延迟 | p50 | 平均 token | 解析失败 |
|---|---|---|---|---|---|
| 独立分类器 / 22 个 Agent | **100%** | 993 ms | 939 | 635 (p583+c51) | 0 |
| **独立分类器 / 8 个能力族** | **100%** | **931 ms** | **857** | **531 (p494+c37)** | 0 |
| 主 Agent 内嵌决策 / 22 | 100% | 4736 ms | 4519 | 1265 (p683+c582) | 0 |
| 主 Agent 内嵌决策 / 8 族 | 93.3% | 4840 ms | 4497 | 1148 (p594+c554) | 1（输出截断） |
| 平台现状 `IntentRouter.detect` | — | 1039 ms | — | — | 15 条里仅 **3 条**触发 LLM |

**读法**：

1. **效率**：独立轻量分类器比「主 Agent 内嵌决策」**快 5.1 倍、省 2.4 倍 token**。原因是前者只输出一行 JSON，后者要先写一段角色化分析再附 JSON。且内嵌组已经出现 1 次 `finish_reason=length` 导致结构化决策丢失——生产里这会变成「路由没结果」。
2. **准确度**：族化不降准确率（100%→100%），但省 16.4% token、6% 延迟；主 Agent 内嵌反而因长输出降到 93.3%。
3. **单独维护一个意图识别子 Agent 更差**：它等于「独立分类器」再加一层角色/上下文/可能的手off，必然多一次 LLM 往返；而分类任务根本不需要工具与规划能力。行业证据（OpenAI heuristics、Dify 实战复盘）方向一致。
4. **平台现状已是最优形态**：确定性规则/语义优先，15 条里只有 3 条落到 LLM 兜底 ⇒ 平均 1039ms 主要是那 3 条拉高的。**不建议改成主 Agent 内嵌，也不建议新增子 Agent**；要优化就优化「候选池」而不是「归属」。

> ⚠️ **验证脚本自身踩了两次坑**（已修并写进注释）：
> ① 首版 `in_main` 的 `max_tokens=700` 导致长输出被截断、JSON 没生成，而 `_norm` 找不到 JSON 时对整段正文做模糊子串匹配 ⇒ 把「解析失败」伪装成「分类错误」，报出虚假的 40% 准确率；
> ② 第二版改提示词时缩进错 4 空格，`sys_p` 变成不可达分支 ⇒ 30 条全部 `UnboundLocalError` 被 `except` 吞成 `parse_fail`，报出虚假的 0%。
> 修法：严格判据（只认结构化 JSON）、区分 `parse_fail` / `wrong` / `truncated`、加大预算、修缩进。**判据必须能区分「没解析出来」和「选错了」。**

### 3.3 落地决策

**保留 `IntentRouter` 作为独立代码组件**，在其 LLM 兜底层加**能力簇收窄开关**：

- `core/config.py` → `intent.cluster_route`，**默认 `False`（逐字节零回归，一键回退位）**。
- 打开后：LLM 候选清单从 22 个 Agent 名 → 7 个互斥能力族；族 id 经 `resolve_cluster()` + `intra_pick()` 确定性地落到具体 Agent 名。
- **对外契约不变**：返回的仍是具体 Agent 名，`_done` / 意图缓存 / 落库 / 编排 / 澄清卡全部不用改。
- 簇模式下不注入按 Agent 名写的 few-shot 与阶段粒度规则（否则会把模型诱导回「输出某个 Agent 名」，架空族分类）。
