## 2. 候选方案（4 条技术路线）

### 方案 A：单轮结构化输出 + 确定性打分

**机制**：design Agent 在正文里输出一个规定结构的 JSON 块（方案名 + 各维度**原始量** + 逐维度理由）→ 抽取层映射到规范维度 → 归一化加权 → 对比卡。

```
LLM 正文 ──抽取层(别名表/单位解析)──▶ 结构化候选 ──打分算法(纯函数)──▶ 对比矩阵 ──▶ 对比卡
                    ▲
              模型只给原始量，不给综合分
```

**关键设计约束（工程上最容易做错的三点）**：
1. **分数不能由模型给**。模型自报的"综合 85 分"不可复算、不可审计。模型只给各维度原始量（如时延 120ms / 成本 80 万元 / 覆盖 18 条），归一化与加权由确定性算法完成。
2. **缺维度不补零**。补零 = 把"没测"说成"最差"。缺失维度记 `None`、不参与加权，并如实报 `coverage`。
3. **"少测多赢"必须被拦住**。加权分母是"实际参与的权重和"，于是只测 1 个维度且恰好领先的方案会拿高分压过 5 维齐全的方案（**实测复现**：coverage 20% 的方案 total=1.0，压过 coverage 100% 的方案 total=0.375）。故设**覆盖率门槛**：覆盖率不足的方案仍展示、仍计分，但**不参与推荐**。

**优点**：零额外 LLM 调用（复用既有 design 输出）；结果可复算、可审计；改动面最小。
**缺点**：方案多样性受单次生成限制——模型可能给出"换皮方案"（差异只在措辞）；各方案无法独立校验（只有一份汇总正文）。

**成本**：1 次 LLM 调用（无增量）。

---

### 方案 B：多 Agent 并行生成 + 汇总打分

**机制**：走既有编排能力，planner 派 N 个 design 子任务，每个带**不同的设计取向**（性能优先 / 成本优先 / 风险最低 / 可扩展优先），并行执行（`ready` 并行 ≤3）→ 各自产出结构化候选 → 汇总后统一打分。

**优点**：
- 方案多样性显著提高（**取向隔离**强制模型走不同设计路径，而不是同一路径的措辞变体）；
- 每个候选的 SysML 代码可**独立过 `checker.jar`**（每份都是完整模型代码，而非混在一段正文里）；
- 每个候选可独立沉淀为 `sysml_versions` 版本，支持"选中其一"。

**缺点**：
- 成本 N 倍 LLM 调用、延迟显著上升；
- 编排一致性风险：N 个子任务的质量不齐时，汇总层需要识别并**如实标记**不合格候选，而不是静默纳入排名；
- 编排已有"partial"三态语义，接入时须与 `orchestrated_status` 口径对齐，不能让"部分完成"看起来像"完整三方案"。

**成本**：N 次 LLM 调用（默认 N=3）。

---

### 方案 C：变体空间驱动的候选生成 + 评分

**机制**：复用 `agents` 表 id=173「多方案生成」的既有定位——先声明**变体空间**（变化点 + 取值枚举 + 剪枝约束），Agent 在空间内提议代表性候选绑定（正交/角点采样，不是笛卡尔积穷举）→ 再对候选打分。

**优点**：
- 工程严谨性最高：候选**在声明空间内**，不臆造；剪枝约束保证不出现不兼容组合；
- 与 SysML v2 变体建模天然衔接（`variant part` / `variant attribute` 是标准语义）。

**缺点**：
- 前置成本高：变体空间需人工/半自动建模；
- 适用面窄：适合"已定型系统做参数细化"，不适合"从零做架构方案"；
- **现状障碍**：id=173 的 `system_prompt` 存在转义损坏（`\#`、`\‑` 等），需先修复才能用；且它与 `stream.py` 的意图路由只有一条 `intent_eval_snapshot.py` 的映射，无消费点。

**成本**：变体空间建模 1 次 + 候选生成 1 次。

---

### 方案 D：人机协同的增量选型（收口）

**机制**：首轮产出候选 → **人工选定/修改** → 系统把选定方案实例化、经 HITL 写前确认后入库成版本 → 后续讨论基于已入库版本做增量（而非每次从零生成）。

**优点**：
- 符合 MBSE 工程实际——**选型是人的决策**，系统不该替人拍板；
- 闭合到模型库：解决核查报告里"入库/采纳全空"（`sysml_versions.adopted` 108 行全 0）的同类问题；
- 与平台既有 HITL（`ConfirmQueue` L2 拦截 + 幂等键）机制一致，不新增范式。

**缺点**：交互轮次多；需要"选定"这一状态在会话/版本表里有承载位。

**成本**：1~2 轮人工交互 + 1 次写库。

## 3. 方案对比与选型

| 维度 | A 单轮结构化 | B 并行多 Agent | C 变体空间 | D 人机协同 |
|---|---|---|---|---|
| 方案多样性 | 低（易换皮） | **高**（取向隔离） | 中（受采样约束） | 取决于 A/B |
| 可复算/可审计 | **高**（纯函数） | 高 | 高 | 高 |
| LLM 成本 | **1×** | N× | 1× + 建模 | 1× |
| 模型可独立校验 | 否 | **是**（各候选独立过 checker.jar） | 是 | 视上游 |
| 接入成本 | **低**（已实现） | 中（复用编排） | 中高（需修 prompt + 建模） | 中（复用 HITL） |
| 落地到模型库 | 否 | 可 | 可 | **是** |
| 适用面 | **广**（通用） | 广 | 窄（已定型系统） | 全流程收口 |

### 推荐组合

> **A 作基座（默认路径） + B 作增强（显式要求深度比较时） + D 作收口（选定入库）；C 留作专用场景，暂不并入主线。**

理由：
- A 已完成参考实现并通过自检，**当天即可上线**，且其"确定性打分"内核（B/C/D 都要用）已经沉淀为独立纯函数层；
- B 的价值集中在"要真正的多方案而不是换皮"时，可用显式触发（如"给出三个有实质取舍的方案"）走编排，**平时不付 N 倍成本**；
- D 是 FR-MG-2/MG-5 的同类问题（"采纳全空"），选型入库是让多方案**产生工程价值**的必经环节；
- C 语义正交、现状障碍多（prompt 转义损坏 + 无消费点 + 需人工建模），**并入主线会拖慢交付**，建议单独立项。

```
PASS = 128   FAIL = 0
```

- 裸跑（无参数）；不依赖 git ref、不连生产库、不调 LLM；

## 5. 分阶段路线建议（待决策，未实施）

| 阶段 | 内容 | 验收判据 |
|---|---|---|
| **P0** | A 路线上线（**已完成参考实现**）：提示词契约 + 抽取 + 打分 + 对比卡 + 端点 | `verify_alternatives.py` 全绿；design 会话能产出 ≥2 候选且对比表有推荐/并列形态 |

| **P2** | D 路线收口：选定方案 → HITL 写前确认 → 入库 `sysml_versions`（`adopted=1`） | `sysml_versions.adopted` 出现 >0（对应核查报告"采纳全空"缺口） |
| **P3** | B 路线增强：显式深度比较时走编排并行生成；每个候选独立过 `checker.jar` | 并行 3 方案各自模型代码校验通过率可报；partial 场景不谎报"完整三方案" |

**风险与前置**：
- P2 触及 HITL 与版本入库，影响面大于 P0/P1，建议独立评审；
- P3 会改变 design 的默认执行路径（单 Agent → 编排），需先量化成本与延迟增幅；
- 权重/门槛是运营参数，`alternatives.min_coverage` 默认 0.6 意味着**至少测 3/5 维度**才给推荐——若实际模型常只给 2 个维度，需下调该值，否则会频繁出现"无推荐"。

## 6. 需要决策的开放问题

1. **推荐门槛**：`min_coverage` 默认 0.6（至少测 3 维）是偏高还是偏低？是否应改为"按缺失维度数告警"而非硬拦推荐？
2. **B 的触发条件**：显式关键词触发，还是设为配置开关由用户切换？（涉及成本默认档）
3. **D 的落点**：选定方案入库时，是进 `sysml_versions`（版本链）还是新建"方案集"表？（前者复用成熟但语义偏模型版本，后者语义准但要新增表）
4. **维度可扩展性**：当前 5 维度是硬编码在 `DIMENSIONS` 里的。是否需要做成「可配置的维度注册表」（含权重、方向、单位），以便按项目/专业域定制？
