# ReAct 执行器：标杆调研与落地方案

> 日期：2026-11-04
> 触发：`_exec_react` 的 docstring 声称「`agent`: 可选，思考由指定 Agent 体系驱动（forced_intent）」，
> 但实现里**从未读取过 `cfg["agent"]`**；且全库 355 条任务里 react **只跑过 1 次、还失败了**。
> 结论先行：**问题不是"react 写得不好"，是"我们有两个工具循环，其中一个是弱化复制品"。**

---

## 0. 结论先行

> ★ **2026-11-04 已按方案 A 实施**（见文末「§8 实施记录」）。
> 补充事实（用户 2026-11-04 明确）：**画布 workflow（`agent_flows` + `workflows/engine.py`）
> 是早期方案，已放弃发展**。所以本文件原 §4「画布与编排共用一条实现」的目标
> 实际更简单：**react 只有编排一条在用路径**，画布那份实现只作历史兼容。

| 判断 | 依据 |
|---|---|
| 主链路 `execute.py` 已有**成熟的原生工具循环** | 每轮执行工具→观察回填→再生成，含 `reasoning_content` 回填、悬空 `tool_calls` 防 400、协议分片 |
| `_exec_react` 是它的**弱化平行实现** | 文本 JSON + 正则提取；`max_steps` 硬上限；`ob[:400]` 一刀切截断；不读 agent；无审批闸 |
| **正解不是修好 react，是消灭第二个循环** | 标杆（Claude Code / Codex）都只有**一个** loop；两套循环必然漂移（本仓已因"两条路径口径分裂"付出过多次代价） |

**已落地：方案 A —— `task_type=react` 委托给主链路 Agent 执行**，
react 只保留它真正独有的两件事：**显式工具白名单** 与 **轮次上限**。

## 1. 标杆怎么做的（只取与我们可比的部分）

### 1.1 Claude Code：极简 loop + 上下文工程

| 机制 | 做法 | 对我们的意义 |
|---|---|---|
| **主循环** | `while tool_calls: 运行工具 → 取结果 → 喂回模型 → 重复`。Anthropic 自称 **"dumb loop"** —— 智能在模型推理，harness 只做编排 | 循环本身不该有业务分支；我们的 `for i in range(max_steps)` 里塞了 JSON 解析、工具白名单校验、观察截断，都是"harness 干了模型的活" |
| **工具集** | **Bash 万能** + EDIT（**统一 diff**，不重写整个文件）+ GREP/GLOB（**放弃 RAG**，传统搜索更准）+ READ + Tasks | 工具少而通用 > 多而专用；我们的 react 默认白名单是 5 个业务工具，缺"探查"类能力 |
| **To-Dos** | **System Prompt 注入的结构化文本，不是代码强制**。三个作用：强制规划 / **崩溃恢复**（重启读清单即知进度）/ UX | 我们已有 `agent_todos` 表（更硬），方向一致 |
| **Sub-Agents** | 上下文隔离：子 agent 跑完**只回最终结果**，中间过程丢弃；**子 agent 工具池不含 `task`** ⇒ 杜绝无限递归；共享工作目录但系统提示词不同 | 我们的 `_exec_react` 递归风险更低（无 task 工具），但也没有隔离机制 |
| **上下文压缩** | 多层：`tool_result` 超预算先**落盘**再给预览 → 消息数超阈值中段归档 → 旧结果换一行标记 → 最后才 LLM 摘要。**无损在前，有损在后** | 我们的 `obs[-1500:]` 是**直接丢**，且丢之前没落盘 ⇒ 丢掉的观察永久不可查 |
| **工具 schema 成本** | 官方文档：子 agent 用 `tools` 字段限**最小集合**；MCP 工具搜索**默认延迟加载**（否则 schema 吃光上下文） | 我们 `_build_tools_def` 有 JIT 预筛，思路一致 |

### 1.2 Codex CLI：四阶段 + 权限闸 + 状态外化

| 机制 | 做法 | 对我们的意义 |
|---|---|---|
| **循环四阶段** | prompt 组装 → Responses API（**SSE 流式**）→ 工具执行 → 上下文管理 | 我们是**一次性 chat**，用户看不到中间步骤 |
| **指令级联** | `config.toml` → `AGENTS.override.md` → `AGENTS.md` → skills，**每个来源上限 32 KiB** | 我们的提示词分层（L0-L3）思路相同，但**没有单源大小上限** |
| **权限闸** | `ToolRouter` 检查审批策略；三种审批模式 Auto / Read-only / Full Access；沙箱作用于**整个进程树**（macOS App Sandbox / Linux Landlock+seccomp） | 我们已有 `hil_level` + `_exec_tool_call` 的统一 HIL 闸 —— **react 完全绕过了它** |
| **状态外化** | repo / diff / worktree / markdown 状态文件 —— **靠环境反馈闭环，不靠上下文硬撑** | 我们 react 把一切压进 `obs` 字符串 |
| **并行子代理** | `spawn_team`：explorer / worker 角色并行派生子代理 | 我们的并行在编排层（`TaskQueue`），react 内部串行 |

### 1.3 两家**共有**的四条（这才是关键）

1. **原生 function calling**，不用文本 JSON 解析；
2. **终止条件是"模型不再请求工具"**（自然终止），不是"模型自觉输出 `finish`"；
3. **工具产物分级治理**（截断/落盘/摘要），不是一刀切丢弃；
4. **状态外化 + 权限闸**，不把安全与记忆压在提示词上。

## 2. 我们现在的 `_exec_react` 差在哪（逐条对照）

| 维度 | 标杆 | 我们（`workflows/nodes.py:845`） | 严重度 |
|---|---|---|---|
| 工具协议 | 原生 `tool_calls` | **文本 JSON + `re.search(r"\{[\s\S]*\}")`** | **高**：正则贪婪匹配、嵌套 JSON 易误切；模型少写一个括号就整轮退化 |
| 终止条件 | 无工具请求 ⇒ 结束 | 靠 `action=="finish"` 或**耗尽 `max_steps`** | **高**：模型不写 finish 就白烧步数 |
| agent 语义 | 子 agent 有独立 system_prompt + tools | **完全不读 `cfg["agent"]`**（docstring 与实现不符） | **高**：声明的执行主体是假的 |
| 权限闸 | 审批模式 + 沙箱 | **无**（不走 `_exec_tool_call` 的 HIL 闸） | **高**：react 里调写类工具可以绕过确认 |
| 观察治理 | 分级（落盘→预览→摘要） | `str(result)[:400]` 硬截断，**截前不落盘** | 中：大结果直接不可用且不可查 |
| 上下文累积 | 多层压缩 | `obs[-1500:]` 直接丢头部 | 中：长任务早期观察永久丢失 |
| 流式 | SSE | 无 | 低（子任务场景可接受） |
| 步数上限 | 由预算/收敛控制 | `max_steps` 默认 5、硬上限 10 | 低（但配 `finish` 不自洽会双杀） |

**实测使用率**：`agent_tasks` 355 行 → `agent` **352** / `llm` 2 / **`react` 1**（且那 1 次失败于"孤儿运行"，
**不是 react 逻辑错**）。⇒ **react 是"有实现、有接线、但从未产生价值"的能力**。

## 3. 三个方案与选型

### 方案 A：react 委托给主链路 Agent（**推荐**）

`task_type=react` 不再自己跑循环，而是：

```
_run_task(task_type="react")
  → AgentPipeline.execute(forced_intent = cfg.agent or 默认,
                          tools_whitelist = cfg.tools,
                          max_tool_rounds = cfg.max_steps)   # 复用主链路循环
```

- **react 保留的唯一语义**：① 显式工具白名单（最小权限）；② 轮次上限（防长尾）。
- **白拿**：原生 tool_calls、HIL 闸、reasoning_content 回填、悬空调用防 400、JIT 工具预筛、观测落库。
- **代价**：react 与 agent 的差异变小 —— 但**这正是我们想要的**：`task_type` 只是"给这次执行加两道约束"的标签。
- **风险**：主链路行为变化会影响 react（可接受：目前 react 零使用）。

### 方案 B：保留独立实现，改原生 tool_calls

- 收益：隔离性好，react 可独立演进。
- 代价：**两套循环必然漂移**。本仓已有实证：`AgentRegistry.resolve` 与 `resolve_agent_name`
  口径分裂导致"规划器能派、落库却整批中止"；`_run_task` 与流式路径的附件注入口径分裂。
  **每多一条平行实现，就多一处未来要对齐的地方。**

### 方案 C：下线 react

- 收益：直接删掉 100 行弱化实现与一个 `task_type` 分支。
- 代价：失去"多步工具求解"这个**语义标签**（虽然现在也没人用）。
- 适合：确认短期不需要"受限多步求解"这种任务类型。

### 选型建议

**A 为主，C 作为退路**：若确认 react 语义可被 `agent + tools + max_rounds` 完全覆盖，
直接走 C（删）比走 A（转发）更省。**先做 A 的代价极低（一次转发），观察一段时间再决定是否 C。**

## 4. 落地步骤（按投入产出）

### 第 1 步：让 `agent` 真正生效（最小修复，可与本文同批）

- `_exec_react` 读 `cfg["agent"]`：非空则作为 `forced_intent` 传给主链路；
  空则取配置默认（如 `review` 之外的通用执行 Agent），**并在卡片/日志标注"未指定主体"**。
- 若暂不改执行路径，至少**不要假装它生效**：声明了 agent 但实现不读 ⇒ 报 warn
  （本仓 `core/plan_guard.py` 的 `route.ignored_by_type` 已在做这件事）。

### 第 2 步：把工具调用交给主链路（方案 A 的核心）

- `_run_task` 的 `ttype == "react"` 分支改为委托 `pipe.execute(..., tools_whitelist=..., max_tool_rounds=...)`。
- 删除 `_exec_react` 里的 JSON 解析循环（约 60 行），保留 `_exec_react` 作为**画布 react 节点**的入口，
  内部同样改为委托（画布与编排共用一条实现）。

### 第 3 步：观察治理（学 Claude Code 的分级）

- 工具结果超阈值（如 8000 字符）→ **先落盘**到 `tool_result_offloads`（该表已存在！），
  上下文里只放预览 + 引用 id。
- `obs` 累积超预算 → 归档旧步骤而不是直接 `[-1500:]` 砍头。
- **判据**：任意一次 react 执行，都能从库里取回完整工具观察（现在做不到）。

### 第 4 步：权限闸（应收口到既有 HIL）

- react 的工具调用必须走 `agent/pipeline_parts/tools.py::_exec_tool_call`（全仓仅 4 个调用点，
  已有统一 HIL 闸）。**这是安全项，不是体验项。**

### 第 5 步（可选）：流式

- 若 react 要用于会话内可见的多步推理，接 SSE（主链路已有事件通道）。

## 5. 验收判据（先定判据，再写代码）

| 层级 | 判据 | 现状 |
|---|---|---|
| 语义 | `task_type=react` 且声明 agent ⇒ 执行时该 agent 的 system_prompt 与工具面**确实生效** | ❌ 完全不读 |
| 协议 | 工具调用走原生 `tool_calls`（可用假模型桩注入 `tool_calls` 验证，无需真 LLM） | ❌ 文本 JSON |
| 安全 | react 内调写类工具 ⇒ 触发 HIL 确认（与 agent 路径同一闸） | ❌ 无闸 |
| 可查 | 任一次 react 的完整工具观察可从库里取回 | ❌ 截断即丢 |
| 收敛 | 模型不再请求工具时立即结束，不额外烧步数 | ❌ 依赖 `finish` 或步数耗尽 |
| 使用率 | 上线后 N 天内 react 任务数 > 0 且成功率 ≥ agent 路径 | 待观察（当前 1 次/355） |

## 6. 一个必须先回答的问题

**react 与 agent 的边界到底是什么？**

如果答案是"没有本质区别，只是 react 限定工具集和步数" ⇒ **走方案 A**，
`task_type=react` 退化为两个约束参数，实现只剩一条。

如果答案是"react 需要独立的思考链与不同的终止语义" ⇒ 才有理由保留独立实现（方案 B），
但**必须付代价**：两套循环的对齐成本、两套观测、两套安全闸。

当前没有任何数据支持后者 —— **react 只跑过 1 次**。
所以本方案的默认立场是：**先合并，等有真实需求再分。**

## 8. 实施记录（2026-11-04 已落地，方案 A）

### 改了什么

| 文件 | 改动 |
|---|---|
| `agent/pipeline_parts/execute.py` | 新增 `max_tool_rounds=None` 形参。默认 None ⇒ 读配置 `agent.max_tool_rounds`（100），**行为逐字节不变**。⚠️ 覆盖逻辑放在 try/except **之后** —— 否则配置读取异常时会被兜底 `100` 覆盖掉，覆盖静默失效 |
| `workflows/planner.py::_run_task` | `task_type=react` 分支改为委托 `AgentPipeline.execute(forced_intent=agent, tools_whitelist=…, max_tool_rounds=max_steps)`；删掉对 `self._exec_react` 的调用 |
| `workflows/nodes.py::_exec_react` | 同样改为委托（供历史画布流程兼容），并在 docstring 顶部**显式标注「画布 workflow 链路已废弃」**，防止后人当正式实现继续加功能 |
| `core/plan_guard.py` | `route.ignored_by_type` 收紧为**仅 `llm`/`tool`** —— react 改造后真的读 agent，再对它告警就是**假告警** |

### 顺带订正的两处语义

1. **`max_steps=0` 曾被静默变成 5**：`int(cfg.get("max_steps") or 5)` 里 `0` 是 falsy。
   改为显式判空 + 越界夹取（0 ⇒ 1，>10 ⇒ 10），两处入口（编排 / 画布）同口径。
2. **`_exec_react` 的 `steps` 恒空**：工具轨迹的权威出处是 `card_data.exec.tools` 与
   `tool_call_logs`，不在节点返回值里再抄一份（抄一份就有第二份会漂移）。
