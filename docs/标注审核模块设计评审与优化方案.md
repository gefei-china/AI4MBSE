# 标注审核模块（知识治理四区）设计评审与优化方案

## 1. 现状基线

审核标准模块即 KB-C 页签下的"知识治理全链路"四区：**① 抽取预览 ② 融合工作台 ③ 实体审核 ④ 关系审核**，顶部流程条显示"抽取预览 → 融合工作台 → 实体审核 → 关系审核 → 发布"并提供待办数直达。下表是该模块当前在五个维度上的实现快照。

| 维度 | 现状 |
| --- | --- |
| 颗粒度 | ① 抽取预览把**实体候选与关系候选混在一个平铺列表**，靠"仅关系"复选与状态/消歧/置信度筛选区分；候选行只显示名称、类型、消歧徽章，无来源片段上下文 |
| 排序 | 四区线性推进（抽取→融合→实体→关系）；"发布"不是独立页签，实际由**分支管理中 dev→release 合并**完成，四区仅待办直达 |
| 布局 | ② 融合工作台把状态卡、合并建议、待裁决冲突三块纵向堆叠，双击区较多；其余三区为单面板 + 顶部筛选条 |
| 交互 | 全部单操作 + 确认弹窗；批量仅在部分环节存在；无评审员分配、无备注对话、无 SLA/到期提示 |
| 业务逻辑 | 实体生命周期 raw_chunk/candidate/reviewed/published/deprecated；实体通过→reviewed、驳回→deprecated；关系 candidate→reviewed/deprecated；冲突按 可信度×0.5+时效×0.3+权威×0.2 加权 |

数据基底：候选在 `v2g_candidates`，实体/关系写入 `personal` 分支，发布需合并个人分支到权威 `dev/release`；平台另有独立的**审批模块**（发布/变更/分支合并的 instance-level 签批）当前与本四区相互独立。

## 2. 对照行业通用做法的差距诊断

### 2.1 颗粒度

- 实体与关系候选同表混淆。主流标注/治理平台（Label Studio、数据质量平台的审核流）按**对象类型分工作项**，至少分实体抽取与关系抽取两类，各自有独立筛选、统计与通过口径。当前混在抽取预览里，管理员要点开每条才能区分，批量视角缺失。
- 候选行缺**证据上下文**。审核一个实体是否成立，需要看到抽取命中的原文片段（mention span）、来源文档、来源模型/置信度。当前只有名称与消歧徽章，审核≈凭名称盲判，与"可追溯、可复核"的治理目标不符。
- 单一置信度数值。行业做法是"置信度 + 来源 + 模型/规则类别 + 理由"四元组，甚至给置信度区间而非单点，避免把概率当真值。

### 2.2 排序与流程

- 线性推进本身合理，但与实体/关系审核队列之间的跳转呈**网状**：关系审核面板有"冲突待审"chip 跳到融合区，实体审核有"去融合"跳转，抽取预览确认后又能进实体/关系队列。跳转方便，但缺少统一的"当前在途工作在哪、下一步该做什么"视图。
- "发布"被静默安排在分支管理，与四区割裂。普通审核员并不知道实体/关系都过审后还要去分支管理合并才能成为权威基线，容易造成"审完了但没发布"的认知断层——这正是本方案发布门禁要补的闭环。

### 2.3 布局

- ② 融合工作台三块纵向堆叠过密，且"运行两段式/工序①②/检测重复/检测冲突"多个动作按钮并列。行业做法是把"引擎运行"与"产出消费"分层：引擎结果（候选对、冲突）作为待办清单分档展示，而不是把所有运维按钮平铺在头部。
- 各审核队列缺**分档/分组卡片**（如按来源、批次、风险），长列表只能靠顶部筛选。

### 2.4 交互

- 单一操作者假设，无**评审员分配与工作台**。治理平台普遍区分 reviewer/editor/approver（RACI），每人只能看到并处理分派给自己的待办。当前无 reviewer 概念，无法支撑多客户多角色的通用平台目标。
- 无**备注/讨论线程**。审核分歧、来源疑义需要就地沟通留痕；当前"驳回"只能写一次性 reason，无法围绕某条记录展开对话。
- 无**批量 + 理由模板**。大批量同类驳回要逐条填理由；行业做法是"批量选中 + 选择预置理由 + 可补充"。
- 无 **SLA/到期** 与键盘操作，长列表效率低。

### 2.5 业务逻辑

- 生命周期状态本身合理，缺的是**再激活通道**：reviewed 后若发现误通过，没有"重新打开/后退一态"，只能依赖知识冲突或废弃，治理纠错成本高。
- 驳回原因是否必填不强制；审核动作虽进审计，但**每次决策的前置证据（当时看到的片段/置信度）未快照**，事后追溯只能看结论。
- 冲突加权分数写死（0.5/0.3/0.2），且门槛不可配；行业做法是可配置权重，甚至由组织规则驱动。
- 本模块与独立的**审批模块**（发布/变更/分支合并签批）未打通。真正的"签批式发布门禁"（对应 ISO/IEC/IEEE 15288 的评审签署环节）应由审批模块承载，当前四区只到 reviewed，签批在别处，职责边界不清晰。

## 3. 优化方案

按性价比与风险分四级，P0 为低风险高价值的近期项，E 为演进项。

### P0 · 近期（改动小、立竿见影）

**P0-1 抽取预览按对象类型分组。**（✔ 已完成，见下方回填）保留现有筛选包容性，改为默认二分视图：实体候选页 / 关系候选页（页签或筛选主位），各自统计、各自批量。关系候选行直接复用已修好的 `源 --类型→ 目标` 渲染，取消"仅关系"这种隐性子集交互。

- 涉及：`static/index.html`（v2g 面板拆分）、`/api/knowledge/v2g/candidates` 响应补 `kind` 字段或前端按 `rel_source` 有无分区。
- 验收：关系候选不再混入实体默认视图；两种批次可各自全选批量操作。

**P0-2 候选行补证据上下文。**（✔ 已完成，见下方回填）每行展示命中原文片段（从 `document_chunks` 取）、来源文档、置信度与来源类别（vector / ai_generated / 规则）。驳回理由改为必填（无理由拦截），批量操作提供预置理由模板。

- 涉及：`index.html` 候选行渲染；`v2g/candidates` 查询联表带出 chunk 上下文；后端 `v2g_reject` 校验 reason 非空。
- 验收：候选列表可见来源与片段；无理由的驳回被拦截并提示。

**P0-3 发布作为显式环节。**（✔ 已完成，见下方回填）对接本方案已实现的达成分支合并请求（`services/ingest_gate.py` + 既有 `/api/branches/merge-requests/{id}/resolve`）：四区顶部"发布"待办除跳转外，展示"未发布实体/关系数"，点击进入合并请求待办，把"审完→发布"的断层显式摘平。

- 涉及：`index.html` 流程条、`kbFlowGo('pub')` 逻辑增强。
- 验收：实体/关系全部 reviewed 后，发布环节出现待办并可直达合并请求审批。

#### P0 实施完成情况回填（2026-08-20）

三项目前均已在 **8000 端口正式服务** 验证通过。

| 项 | 落地改动 | 涉及文件 | 验证结果 |
| --- | --- | --- | --- |
| P0-1 分组视图 | 实体/关系/全部三段分组下拉（主位高亮），`_v2g.group` 状态 + `v2gFiltered` 过滤，关系候选判别 `entity_type==='关系候选'`；分页/批量全选随分组联动 | `static/index.html` | UI 实测 实体 50 / 关系 27 / 全部 77（50+27=77 吻合），切换实时联动、无 JS 异常 |
| P0-2 证据上下文 + 驳回必填 | 候选行"名称"列下方内联命中原文片段（`chunk_content`，截断+悬停，点击开来源面板），"来源"列补来源类别标签；单条/批量驳回空理由拦截；后端空 reason 直接返回 error 不写库 | `static/index.html`、`services/knowledge_service.py` | 来源标签/驳回必填 UI 实测通过；空原因被 toast 拦截且候选仍待审、数据不变；后端空 reason 返回 `{rejected:0,error}` |
| P0-3 发布显式化 | "发布"环节从"已发布数"改为"待审批合并请求数"（`mrs.status==='pending'`），pending>0 高亮；点击打开"发布待办"面板逐条显示合并请求并可"去分支管理审批"，无待办时提示并直达分支管理 | `static/index.html` | 服务页含全部新逻辑；当前库 18 条合并请求全 approved → 徽章如实为 0 |

需要注意的遗留项：

- **P0-2 内联片段仅对已绑定 chunk 的候选可见**。当前 100 条候选仅 4 条带 `chunk_content`（golden e2e 批次），多数 impact/review 回流候选未落 `document_chunks` 溯源，故无片段可显示——这是数据覆盖的根因问题，待后续补齐回流候选的 chunk 溯源。
- **P0-3 待办面板的展示路径需 pending 合并请求才触发**；打开发布门禁（`ingest.draft_flow=true`）后确认 AI 批次即可生成 personal→dev 待审 MR，实盘演示待审→审批→发布→回滚留待门禁启用后验证。

### P1 · 中期（需新增表/接口）

**P1-1 评审员分配与工作台（RACI）。** 新增 `kb_review_assign（item_id, item_type, reviewer, stage, assigned_at）`，实体/关系/融合候选均支持分派；个人"我的待办"视图只列自己名下。审批/合并仍走既有权限（`kb_review:confirm`）。

**P1-2 备注讨论线程。** 新增 `kb_review_comments(item_id, author, body, created_at)`，在候选/实体/关系详情内联展开，"驳回/通过"可引用某条备注作依据。

**P1-3 冲突评分权重可配置。** 把 0.5/0.3/0.2 与裁决门槛提升为配置项（settings 表），默认值不变。

### P2 · 远期

生命周期增加"重新打开/后退一态"再激活通道；为每次审核决策**快照当时的证据快照**（片段、置信度、来源）便于复核；增加风险泳道（高/中/低分档）、SLA 到期徽章、审计导出。

### E · 演进

把"审核标准"从硬编码逻辑沉淀为**可配置策略**：按（来源 × 类型 × 置信度 × 批次）自动给出 直接通过 / 需人工审核 / 直接驳回 建议——与 `ingest_gate` 的 `approval_policy/review_source_types` 打通，形成"抽取→候选→融合→审核→发布"全程统一门槛，同时赋予平台多客户定制能力。

## 4. 端到端目标流程

```
导入/AI建模/文档抽取 ──► 候选(v2g_candidates, P0-1分组)
   │ 人工确认
   ▼
personal 分支实体/关系（融合工作台去重+冲突裁决）
   │ 实体审核(reviewed) / 关系审核(reviewed)          ← P0-2证据+理由
   ▼
发布门禁：合并请求 personal→dev→release（P0-3 显式化） ← 依托审批模块签批
   │ 批准
   ▼
已有发布分支（release，权威基线，只读）
```

关键变化：审核从"确认即个人分支入库"变为"**确认进工作分支 → 按证据审核 → 门禁签批发布**"，各个环节的责任、证据、回退都落库留痕。

## 5. 落地路径与验收要点

| 项 | 改动面 | 验收要点 |
| --- | --- | --- |
| P0-1 分组视图 | index.html、v2g/candidates | 实体/关系默认分页；互不混同 |
| P0-2 证据+必填理由 | index.html、v2g 联表、v2g_reject | 行内见片段与来源；无理由驳回被拦截 |
| P0-3 发布显式化 | index.html 流程条、合并请求 | reviewed 后发布待办出现并可直达审批 |
| P1-1 评审员分配 | 新表 + router + 个人待办 | 只看到分派给自己的工作项 |
| P1-2 讨论线程 | 新表 + 详情内联 | 备注可引用为通过/驳回依据 |
| P1-3 权重可配 | settings + 裁决接口 | 改权重即时生效，默认值不变 |
| E 策略化门槛 | approval_policy + ingest_gate | 按来源/类型/置信度自动分派建议 |

建议以 P0 三项为第一批迭代，每项都能独立上线并通过 8000 端口页面交互验证（模拟确认、驳回、批量、发布直达），验证通过后再进入 P1 的表结构演进。
