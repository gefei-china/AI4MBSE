# 评测工具使用指南

**适用版本**：2026-10-22 起（评测基线接线批次）
**面向读者**：需要回答"系统现在答得好不好、哪里在退化、改完有没有变好"的人
**一句话**：这套工具现在有 4 类入口、2 个门禁通道、1 个可见性接口，全部有可复制的命令。

---

## 0. 先搞清三件事（决定你该用哪条命令）

评测工具最容易踩的坑是**问错问题**：拿检索指标去回答生成质量的问题。本工程的评测分三层，各自有专属工具：

| 你想知道 | 该用| 命令 | 现在的真实水平 |
|---|---|---|---|
| 知识库找得准吗（召回/排序） | RAG 检索评测 | `run_eval.py` | recall@5 = **0.90**、MRR = 0.755、nDCG = 0.688 |
| 意图判对了吗（分对路由） | 意图路由评测 | `run_ci_eval.py` | 准确率 = **0.931**（29 例干净库口径） |
| 记忆召回干净吗 | 记忆质量评测 | `eval_memory_quality.py` | 13 PASS / 1 FAIL / 1 SKIP |

⚠️ **目前没有一层能回答"答案本身好不好"**（忠实度、有没有幻觉、答得对不对）——这是评估确认的最大能力空白。所以"系统答得准不准"目前**无法直接度量**，只能间接看检索与路由。

## 1. 怎么用

### 1.1 三个频率，三条命令

#### 每天（改了检索/知识库后）

```bash
cd <repo>
.venv/Scripts/python.exe -X utf8 tools/eval/build_evalset.py
.venv/Scripts/python.exe -X utf8 tools/eval/run_eval.py --tag daily --control
```

第一条构建评测集（从真实语料派生 gold），第二条跑评测。
**`--control` 必须带**（见 §4.1），不带的话这份分数不可作依据。

耗时约 2~4 分钟（76 例，含 embedding 与 LLM 重排）。`run_eval.py` 会自检解释器，缺 `httpx` 直接拒跑（缺依赖会静默降级为 bigram/Mock，测的是另一条链路的分数）。

#### 每周（改了记忆/意图后）

```bash
.venv/Scripts/python.exe -X utf8 tools/eval/eval_memory_quality.py          # 记忆质量
.venv/Scripts/python.exe -X utf8 tools/eval/run_ci_eval.py --report          # 意图路由
```

意图路由那条**刻意不读生产样本池**，自建干净库跑——因为样本池和规则表都是数据、不在 git 里，不隔离就测的是数据差异而不是代码。

#### 想落库（让结果在前端可见）

```bash
MBSE_DB_PATH=<库路径> .venv/Scripts/python.exe tools/eval/save_report.py tmp/p21/eval_report_daily.json
.venv/Scripts/python.exe tools/eval/eval_memory_quality.py --apply
```

不落库的话，结果只存在于 JSON 文件里，前端看不到（`tmp/` 在 `.gitignore` 中，会被清理）。

#### 改了提示词/引用规则后（最轻的一条，秒级）

```bash
.venv/Scripts/python.exe -X utf8 tools/eval/eval_generation_quality.py --save
```

生成质量评测（2026-10-22 新增，补上" faithfulness 全仓零命中"的断链③）。
它只读生产 `messages`（答案 + citations 全在库里），**不调 embedding/LLM**，
几秒出结果，所以改引用提示词、改 citation 规则后应该每次都跑。
`--save` 同时落库（`eval_kind=generation_quality`），前端立即可见。

### 1.2 调参对比（A/B）

`run_eval.py` 支持单参数临时覆写，只改本进程内存、不落盘：

```bash
# 关掉 HyDE 跑一遍，与基线对比
.venv/Scripts/python.exe -X utf8 tools/eval/run_eval.py --tag no-hyde \
    --cfg rag.hyde_enabled=false --baseline tmp/p21/eval_report_daily.json
```

输出会逐指标打印 `基线/ 本轮 / 差 +↑↓` 箭头。

⚠️ **两个限制要知道**：
- `--baseline` 对比**只打印、不改退出码**。它不会告诉你"这次算不算退化"，要自己看。
- 一次只能改一个参数。参数之间彼此耦合，一次改两个得到的结果无法归因。

## 2. 怎么看

### 2.1 三个查看位置

| 位置 | 适合 | 怎么进 |
|---|---|---|
| **终端输出** | 单次跑批、看清细 | 直接看 `run_eval.py` 的逐域打印 |
| **JSON 报告** | 复核、做对比 | `tmp/p21/eval_report_*.json`（注意会被清理） |
| **数据库 + 接口** | 趋势、给别人看 | `eval_reports` 表 → `GET /api/knowledge/eval/history` |

### 2.2 读一份报告的顺序（别一上来就看 recall）

```
[doc]  检索质量主战场
  pool_recall@20    先看这个 —— 候选池里到底有没有正确答案
      ↓ 有        看 rerank_drop_rate —— 重排有没有把对的挤下去
      ↓ 没有      瓶颈在召回池 → 调 rag.recall_k / top_k
  recall@5 / recall@10   池子捞到了，最终给出时排序好不好
  nDCG@10          相关内容的排序质量
  recall_miss_rate 池里都没有的比例（本次 0.0）

[graph]  该走图谱时走对了吗
  route_acc        路由准确率（本次 1.0）
  entity_recall    两端实体召回（本次 0.972）

[neg]   没有依据时敢说"没有"吗
  route_ok         负样本正确路由率（本次 0.875）
  empty_hit_rate   返回空的比例（本次 0.875 —— 说明它确实在拒答）
  false_graph_confident  高置信误走图谱（本次 0）

[负对照]  ← 最重要的一栏，不看它等于没测
  recall@k 应当**塌到 0**。若与真实分数相近 ⇒ 指标没在测对齐关系，假绿。
```

**双层漏斗是这个体系最实用的设计**：`pool_recall` 高但 `recall@5` 低 → 调重排；`pool_recall` 就低 → 调召回。两个数字直接把优化方向指出来，省掉盲试。

### 2.3 ⚠️ 三个必须知道的读数陷阱

**陷阱一：`recall@k` 名不副实。** `run_eval.py` 判的是"gold 集合与 top-k 有无交集"（hit-rate），不是经典的"命中数/相关总数"。实测 doc-01 有 13 个 gold，命中 1 个也算满分。所以 nDCG = 0.688 **不能读作**"68.8% 的相关内容被检索到"。

**陷阱二：`drift` 非空 ⇒ 分数不可作依据。** 语料被改写后，原来的 gold 位置键会失效（实测 292 条 gold 中 288 条会因语料重切而错位）。`run_eval.py` 默认在漂移时直接 `exit 3`，除非显式 `--allow-drift`。报告里的 `fingerprint_drift` 字段非空时，**任何结论都不成立**。

**陷阱三：负对照没跑 ⇒ 分数无效。** 这是最容易忽略的一条：没有负对照，你无法区分"指标测的是真实对齐关系"和"指标只是在测某个恒定的东西"。`verify_rag_eval_gate.py` 的 D1 判据专门守这条。

### 2.4 生成质量报告怎么读（2026-10-22 新增）

```
先看取材记账（排除了什么、为什么，全部可见）：
  mock_excluded              23   Mock 不是系统能力证据
  attachment_conv_excluded   19   附件会话的证据主语是附件，不是注入块

再看四个指标：
  citation_valid_rate     1.000  正文 [n] 全部在引用范围内（<1.0 = 编号错位，硬伤）
  citation_usage_rate     0.344  带引用的答案里真标了 [n] 的比例（低了 = 引用退化成装饰）
  no_citation_factual_rate 0.169  无引用答案中含可核查实体的比例（无据声称密度）
  grounded_entity_rate     n/a   当前样本仅 2 个可核查实体 —— 不具判别力，门禁判 SKIP
```

**必须知道的三个边界**（否则会误读）：

1. **只评 RAG 问答（text）**。`card_impact` 等卡片的证据主语是知识图谱，块接地对它们不适用。
2. **确定性接地是信号不是裁决**。实体来源可能是会话历史、任务提示词（合法）或模型自身知识（风险）——逐条明细在报告的 `ungrounded_examples`，供人工复核，**不要**当自动判幻听的依据。
3. **grounded 暂不门禁是设计不是遗漏**。2 个实体 + 负对照拉不开差距的样本上设阈值，要么恒绿要么恒红；等 claim 密度 ≥30 且对照可判别，同一份门禁代码自动升级（阈值键 `generation_min_grounded_rate` 已预留）。

## 3. 用户怎么感知评测效果

这是本轮新补的能力。评估发现，此前"评测跑得怎么样"只能问开发看 JSON —— 等于没有可见性。

### 3.1 现在能看什么

**接口**（2026-10-22 起有两组，旧组保留兼容）：

```bash
# 新：评测管理三件套（前端"更多 → 评测管理"页消费的就是这三个）
curl "http://127.0.0.1:8000/api/eval/overview"   # 现在什么状态：各类型最新分 + 门禁接线 + 能力覆盖
curl "http://127.0.0.1:8000/api/eval/history?eval_kind=rag_retrieval"
curl "http://127.0.0.1:8000/api/eval/gates"       # 什么在拦着我：215 个门禁谁接了谁豁免

# 旧：知识域历史（按类型分组 + trustworthy）
curl "http://127.0.0.1:8000/api/knowledge/eval/history?limit=5"
curl "http://127.0.0.1:8000/api/knowledge/eval/history?eval_kind=rag_retrieval"
```

返回按 `eval_kind` 分组的历史，每条带三个关键字段：

| 字段 | 含义 | 为什么重要 |
|---|---|---|
| `doc_recall_at_5` / `doc_mrr_at_10` / `doc_ndcg_at_10` | 检索主指标 | 此前**只存在于 JSON 文件里**，库里查不到 |
| `fingerprint_drift` | 语料漂移标记 | 非空 ⇒ 该行分数不可作依据 |
| `trustworthy` | 是否可信 | `有负对照 且 无漂移` 才为 true |

**`trustworthy` 字段是本设计的核心**：它把"这个数字能不能当依据"变成接口自带的答案，而不要求每个读数据的人自己记住那三条陷阱。

**按类型分组**同样是必要的：记忆评测的 `entity_f1` 存的是"命中率"，检索评测的 `entity_f1` 存的是"实体召回"，混在一起看趋势会得出"指标忽高忽低"的错误结论。

## 4. 怎么改进产品

### 4.1 先说三条"别做的事"

| 别做 | 后果 | 正确做法 |
|---|---|---|
| 别用测试集调参 | 分数变好是因为记住了测试集，不是产品变好 | 调参用 `--cfg` 单参数 A/B，评测集保持独立 |
| 别看 recall 高就收工 | 检索好≠ 答得好 | 生成质量评测已建（§2.4），改提示词/引用规则后每次都跑 |
| 别在漂移状态下看分数 | 数字正常但已无意义 | 看 `fingerprint_drift` 与 `trustworthy` |

### 4.2 指标退化时怎么定位

这是评测的**主要用途**——不是证明做得好，而是**快速定位哪里变坏了**：

| 现象 | 大概率原因 | 该动什么 |
|---|---|---|
| `pool_recall` 掉了 | 语料/chunk 策略变了 | `knowledge_pipeline/chunking.py`、入库参数 |
| `pool_recall` 没变但 `recall@5` 掉了 | 重排策略或模型变了 | `rag.rerank_*`、重排模型 |
| `rerank_drop_rate` 从 0涨到 0.1 | 重排开始挤掉对的 | 调 `rerank_max_candidates` |
| `route_acc` 掉了（graph 域） | 图谱实体被改写或阈值变了 | `rag.route_threshold`、三元组 |
| `route_ok` 掉了（neg 域） | 无依据时开始硬答 | `route_threshold`（降）或补负样本 |
| `empty_hit_rate` 掉到 0 | 拒答能力失效（什么都敢答） | 查检索兜底与噪声闸门 |
| 意图准确率掉了 | 规则表或语义阈值被改坏 | `core/config.py` 的 `intent_*` 组 |

上表的每一条都是本工程里真实存在的参数与模块，不是泛泛的"调一下"。

### 4.3 改完怎么确认真的变好了

```bash
# 1. 改前留基线
.venv/Scripts/python.exe -X utf8 tools/eval/run_eval.py --tag before --control

# 2. 改动

# 3. 改后跑并对比（会打印逐指标差值 + 箭头）
.venv/Scripts/python.exe -X utf8 tools/eval/run_eval.py --tag after --control \
    --baseline tmp/p21/eval_report_before.json
```

**只看目标指标涨没涨是不够的**。必须同时确认：
- **别的没掉**（尤其 neg 域的 `route_ok` —— 检索变好但负样本开始硬答是常见的隐性代价）
- **`rerank_drop_rate` 没涨**（涨了说明是从重排那里挤出来的）
- **负对照仍然塌到 0**（否则这次对比本身不可信）

### 4.4 参数从哪改、改完怎么生效

**全部评测门禁阈值已收敛到唯一真源**：`core/config.py` 的 `eval_gates` 组。

改阈值只需要改那里，改完立即对三处生效：

```python
"eval_gates": {
    "intent_min_accuracy": 0.85,        # 意图路由准确率下限
    "routing_threshold_acc": 0.86,      # 路由门禁下限
    "retrieval_min_recall_at_5": 0.85,  # RAG doc 域 recall@5 下限
    "retrieval_min_route_acc": 0.95,
    "retrieval_min_route_ok": 0.75,
    "retrieval_max_rerank_drop": 0.15,
    "require_negative_control": 1,      # 强制负对照非零
    "generation_min_citation_valid": 1.0,     # 生成质量：[n] 编号有效率
    "generation_min_citation_usage": 0.25,    # 生成质量：引用使用率
    "generation_max_no_citation_factual": 0.30,  # 生成质量：无据声称密度上限
    "generation_min_grounded_rate": 0.70,     # 生成质量：接地率（未标定，条件生效）
    ...共 20 项，见 CONFIG_SCHEMA.eval_gates
}
```

> 这一批改造的起因就是"同一意图路由评测有三个阈值在流通（0.70 / 0.85 / 0.86），且 CI 注释已与实值漂移"。现在 `ci.yml` 的注释只写变量名不写数字，并有一道门禁专门守这件事。

### 4.5 产品迭代的推荐节奏

```
每个迭代：
  1. 改前跑一次评测，存报告（--tag before）
  2. 改动
  3. 改后跑一次（--tag after --baseline before.json），逐指标看差
  4. 确认：目标指标涨 + 其他没掉 + 负对照仍为 0 + 无drift
  5. 落库（save_report.py），让趋势在 eval_reports 里可见

每个版本：
  6. 把记忆评测 + 意图路由 + 检索评测各跑一遍，看三个月的趋势线
  7. 对照 §4.2 的表，看哪一格在持续恶化 → 那是下个迭代的主线
```

## 5. 门禁：什么时候会被挡住

| 门禁 | 触发时机 | 挡什么 |
|---|---|---|
| Guard 意图路由评测 | PR | 意图准确率跌破 0.85 |
| Guard CI 注释 ↔ 代码实值一致 | PR | 注释里的数字与代码实值漂移 |
| Guard RAG 检索评测指标不塌陷 | PR（报告存在时）/ nightly | 检索指标退化、负对照失效、语料漂移 |
| Guard 生成质量评测指标不塌陷 | PR（报告存在时）/ nightly | 引用编号错位、引用使用率塌陷、无据声称密度爆表、指标自证被关 |
| nightly-evals | 每日 03:17 | 跑完整检索评测 + 生成质量评测；失败不阻断 PR但发通知 |

**PR 上的 RAG 门禁在报告缺失时会跳过**（不恒红）。因为语料库 378MB 不入 git，PR 上跑不出真实分数——一个必然红的门禁会被加进豁免名单，那比没有门禁更糟。真正跑评测的是 nightly 作业，**那里的结论才是有效信号**。

⚠️ nightly 当前会因语料缺失而显式失败。这是**有意的**：它明确写着缺什么、怎么接（三种方式），而不是留一个恒绿的占位作业。
