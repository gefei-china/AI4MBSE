## 0. 为什么需要它（实测依据，不是推测）

`MBSE建模总体负责人` 的 `system_prompt` / `capabilities` / `intent_keywords` **全为空**，
但 `description` 写明它负责「意图识别 / 任务拆分 / 计划制定 / 任务分派 / 内容整合输出」。

⇒ 编排时主 Agent 手上**只有 14 个成员的名字**，没有任何：
- 团队自己的方法论（怎么拆任务、拆到什么粒度）
- 8 视图之间的**依赖顺序**（SysML v2 的 8 视图固定顺序，本仓已有约定）
- 何时该用 L1（`impact`/`review` 需要人工确认）而非 L0
- 不该做什么（单交付物任务不要拆成多任务）

★ **这不是"锦上添花"**：编排的 prompt 由主 Agent 的 `system_prompt` 主导，
空 prompt ⇒ 拆解质量完全依赖模型即兴发挥 ⇒ **同一 query 两次拆解结果可能不同**。

```
## 你的团队（14 名成员，只可分派给以下成员，禁止虚构不存在的 Agent）

|---|---|

| 活动图生成 / 状态机视图生成 / 参数视图生成 / 顺序视图（时序图）生成 | SysML v2 另四类视图模型代码 |

## 拆解规则
1. **先判是否真需要多任务**：单一交付物（如"生成需求视图"、"介绍 MBSE 方法论"）
   直接分派**一个**成员，不要拆成多步。拆分只在存在**依赖关系或多交付物**时进行。
2. **视图类任务必须按 SysML v2 八视图固定顺序**组织依赖：
   需求 → 结构 → 用例 → 活动 → IBD → 时序 → 状态机 → 参数。
   上游视图未产出时，下游视图的分派必须显式声明依赖与缺失风险。
3. **视图代码生成 ≠ 评审**：不要把"生成 X 视图"和"校验 X"合成一个任务，
   校验一律分派给 `review`（预评审Agent）。
4. **需要人工确认的成员**（预评审/变更影响）放在任务序列**末尾**，
   并在 plan 中显式标注需要人工确认。
5. **不要虚构能力**：若用户请求超出上述成员范围（如"部署到服务器"），
   在 plan 的 notes 中说明"团队暂不支持该能力"，不要硬派给某个成员。

## 输出格式
严格输出 JSON：{"goal": "<=30字", "entities": [], "steps": [
  {"agent": "<成员name，必须在上表中", "task": "<可独立执行的子任务描述>"}]}
```

## 4. 三个待确认点的结论（米爸 2026-10-07 拍板 + 实测）

| # | 问题 | 结论 |
|---|---|---|
| 1 | 草案措辞（含"不要虚构能力"） | **可用**，已写入 `agents.system_prompt`（1354 B） |
| 2 | `capabilities` 是否补齐 | **补上**，14/14 成员全部落库（4~5 项/成员） |
| 3 | 不匹配能力域时的兜底方向 | **混合路由**（见下），非纯 A 也非纯 B |

### 第 3 点的实测依据（不是拍脑袋）

用 `messages` 表真实用户原话（最近 80 条 → 去重 **36 条**）跑三种词法策略：

| 指标（36 条真实唯一 query） | 2-gram 词法 | LLM 语义路由 |
|---|---|---|
| 单成员定向命中 | 14/16 = 88% | 13/16 = 81% |
| **越界请求拦截** | 4/5 = 80% | **5/5 = 100%** |
| **多阶段识别为「该编排」** | 0/2 = **0%** | **2/2 = 100%** |
| JSON 解析失败 | 0 | 2/36 |

★ **关键结论（推翻了原问题的提法）**：三种兜底策略在词法口径下
**命中数完全相同（27/31）、误派都是 0~2** ⇒ **"选A/B/C"不是关键变量，
关键变量是"判定器用词法还是 LLM"**。词法压根区分不开 8 个「XX视图生成」近义成员
（实测把「冷却回路建模」判成 `requirement_analysis` 而非 `结构视图生成`），
也识别不出「影响分析 + 输出报告 = 两个交付物」。

⇒ 采用**混合路由**（`agent/team_router.decide`，五档）：

```
档⓪ 多交付物信号   → 编排（先于词法，防被抢占）
档① 短噪声/问候    → chat 通用直答（不编排、不定向成员）
档② 词法强命中     → 定向单成员直行（零 LLM 开销）
档③ LLM 语义裁决   → 单成员 / __ORCH__ / 不支持
档④ LLM 失败       → 回落词法并显式标记来源；仍无命中才拒绝
```

比纯 A/B 强在四点：词法强命中零 LLM 开销；LLM 只在词法不确定时才花钱；
越界拦截实测 100%；**拒绝时给出路**（带能力清单 +「去掉团队选择走通用入口」），
不是死胡同。

⚠️ 实施中实测发现并修掉的 4 个真问题（都不是原方案里想到的）：
1. **`[:300]` 截断**：主 Agent prompt 补齐后长 1354 B，300 字截断恰好把
   规则 3（生成≠校验）/5（不虚构能力）/6（路由约束）**整段切掉** —— 最需要的那几条。
2. **通用词与专有词同价**：`生成需求视图`里 2 字通用词「需求」与 4 字专有词「需求视图」
   同价 → top1 领先不足 60% → 白扔一次 LLM。改为**按长度加权**（特异性加权）。
3. **词法强命中抢占编排**：`…参数变更影响分析，输出影响报告` 被词法抢先判为单成员直行，
   明显是两个交付物 ⇒ 新增档⓪（多交付物信号优先于词法）。
4. **多交付物正则误伤单一交付物**：`请生成一份…**分析报告**` —— 「分析报告」是一个**词组**，
   被 `(设计|分析).{0,8}(报告|评审)` 误判为两个动作 ⇒ 改为 `(设计|分析)[^报评]{1,10}(报告|评审)`。
