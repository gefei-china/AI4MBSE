## 2. 智源侧 skill（可直接粘）

````markdown
# 事件上报约定（MBSE 平台）

你是智源平台的建模助手。当以下情况发生时，调用 MCP 工具 `report_event`
把事件上报给 MBSE 平台，让平台侧接住这件事（不需要用户再手动触发）。

## 何时上报

| 触发场景 | kind | external_id | thread_scope |
|---|---|---|---|
| 分支/模型发生变更 | `zhiyuan` | 分支ID（**稳定，不用时间戳**） | 分支ID |
| SysML v2 校验失败 | `sysml_check` | 包名 + 代码哈希 | 包名 |
| 文档入库完成 | `documents` | 文档ID | 文档ID |

## 调用示例（模型变更）

```json
{
  "kind": "zhiyuan",
  "external_id": "<分支ID>",
  "thread_scope": "<分支ID>",
  "actor": "<当前登录用户名>",
  "actor_type": "human",
  "addressed": "mention",
  "text": "模型变更：<一句话简述，如『新增转发器部件与连接』>",
  "payload": {
    "branch": "<分支ID>",
    "change_name": "<要做影响分析的元素名>",
    "change_type": "attribute"
  }
}
```

## 调用示例（校验失败）

```json
{
  "kind": "sysml_check",
  "external_id": "<包名>:<代码sha256前16位>",
  "thread_scope": "<包名>",
  "actor": "system",
  "actor_type": "system",
  "text": "SysML v2 校验失败：硬错 <N> 条（<包名>）",
  "payload": {
    "code": "<完整的 SysML v2 源码>",
    "model": "<包名>",
    "n_hard": <硬错数>,
    "verdict": "block"
  }
}
```

## 三条纪律

1. **`external_id` 必须稳定**：平台按它去重。用分支ID / 文档ID / 代码哈希，
   **绝不要用时间戳或随机串** —— 否则每次上报都会产生新工单。
2. **`payload.code` 要完整**：校验失败事件必须带**全文**（≤20 万字符），
   平台要用它做自动修复；只给片段会修出错误结果。
3. **不要期待"上报=做完了"**：`report_event` 只让事件进待办清单，
   **不执行任何动作**。执行由平台侧（来源模式 + 人工确认）决定。
   回执里的 `note` 会明说这一点。

## 上报后怎么知道进展

回执 `disposition` 有四种：
- `admitted` —— 已建工单（`workitem_id` 有值）
- `filtered` —— 已记录但未建单，看 `reason`（多为白名单/范围未配）
- `duplicate` —— 之前报过（幂等），`first_disposition` 告诉你当初的结论
- 报错 —— `kind` 未注册，错误里会列出可用来源
````

## 3. 本平台侧：配一次白名单（否则真人事件全被过滤）

**这是设计意图，不是 bug**：智源是人建模的地方，谁能在里面一句话就触发本平台写操作，
必须由人显式配置。

```bash
curl -X POST http://<本平台>:8012/api/events/sources \
  -H 'X-User-Id: <你的用户ID>' -H 'Content-Type: application/json' \
  -d '{
    "kind": "zhiyuan",
    "title": "智源模型变更",
    "listen": "mentions",
    "allowed": ["mifei", "alice"],
    "scope_keys": ["branch-9", "branch-10"],
    "mode": "observe",
    "policy_version": "v1"
  }'
```

| 字段 | 含义 | 建议 |
|---|---|---|
| `allowed` | 允许触发的人（小写比较） | 从最小集合开始，跑顺再加 |
| `listen` | `mentions`=只收明确@（推荐）/ `all`=收全部 | 用 `mentions`，噪音少 |
| `scope_keys` | 只接收这些分支（空=一个都不收） | 先只开正在做的分支 |
| `mode` | `observe` 只记录 / `execute` 自动执行 | **先 observe ≥3 天再放开** |

## 4. 观察期怎么用（推荐路径）

### 第 1 天：观察

```bash
# 看"本应做什么"（这就是价值本身：原来这些都要人手动触发）
curl http://<本平台>:8012/api/events/workitems?mode=observe -H 'X-User-Id: <id>'

# 看"这条为什么没动"（含被过滤的 + reason）
curl http://<本平台>:8012/api/events/triggers -H 'X-User-Id: <id>'
```

或直接看界面：**左侧「更多」→ 运行监控** → 页面最上方的「① 待审工单」。

### 第 3~5 天：看数据再决定

| 指标 | 判据 | 说明 |
|---|---|---|
| observe 工单数 | **> 0** | 有量说明底座在接真实事件 |
| filtered 原因分布 | 集中在 `addressed_only` | 白名单没配好，不是事件没来 |
| 停滞工单数 | 恒为 0 | 没人管的洞被堵住了 |
| 重复率 | duplicate 多 = 正常 | 说明幂等在起作用 |

### 决定放开：逐来源切 execute

```bash
# 只放开"只读动作"的来源最安全（如 impact_analysis：纯计算，零副作用）
curl -X POST http://<本平台>:8012/api/events/sources/zhiyuan/mode \
  -H 'X-User-Id: <id>' -H 'Content-Type: application/json' \
  -d '{"mode":"execute"}'
```

> ⚠️ 已建的 observe 工单**不会**因这次切换而变成可执行（模式是快照）——
> 这是刻意的：观察期不能被"事后放开"绕过。

## 5. 实测证据（本平台侧，2026-11-01）

### MCP 协议层真实往返

```
tools/list  → 4 个工具（含 report_event）
tools/call ①：智源真人、未配白名单
  ⇒ filtered / addressed_only          ← 白名单是承重的
tools/call ②：未知来源
  ⇒ 明确报错并列出可用来源               ← 不静默吞
tools/call ③：系统事件（sysml_check）
  ⇒ admitted + 建 autofix 工单
  ⇒ note: "未执行任何动作"              ← 回执不夸大
tools/call ④：同参数重投
  ⇒ duplicate + first_disposition=admitted   ← 幂等且保留首次结论
tools/call ⑤：放开 execute 后再报
  ⇒ 自动修复闭环：
     before = {verdict: block, n_hard: 3}
     after  = {verdict: pass,  n_hard: 0}      ← 硬错清零
     applied_rules = [R02_connector_to_connect]
     rolled_back   = []
     耗时 11063ms
```

### 端到端实测抓到的真实缺陷（已修）

**MCP 字段层级不匹配**：MCP 入参天然是 `arguments.payload.xxx`，
但各来源的 `to_trigger` 约定读**顶层**字段（`sysml_check` 读 `raw["code"]`）
⇒ 只传嵌套 payload 会判定 `empty_code` ⇒ 事件被前置校验拦下
⇒ **症状是"上报成功了但没建单"**，看起来像"准入没配好"，
实则是字段层级不匹配。
⇒ 修：`report_event` 把 payload **平铺到顶层**（顶层优先，payload 兜底并保留）。

## 6. 常见问题

| 现象 | 原因 | 怎么查 |
|---|---|---|
| 上报成功但没建单 | ① 白名单没配 ② scope 不含该分支 ③ 数据不完备 | 看回执 `reason`：`addressed_only` → 白名单；`source_not_listed` → scope；`empty_code` → payload 缺 code |
| 每次上报都建新工单 | `external_id` 不稳定（用了时间戳） | 换成分支ID/文档ID/代码哈希 |
| 收到 `duplicate` 但没工单 | 首次是 `filtered` | 看 `first_disposition`；先修白名单再重报（换 external_id 或改配置后重投不会自动复活） |
| 工单一直 open 不动 | 来源是 observe | 这是观察期正常状态；或看 `GET /api/events/stuck` |
| 智能体看不到 `report_event` | 本平台版本旧 | 需 ≥ `d21a721` |
