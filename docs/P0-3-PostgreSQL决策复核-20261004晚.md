## 二、两条被推翻的理由（详细证据）

### ① 写事务不再跨越 LLM 调用（实测 9.6x）

原评估写「批量写入必须停服务：三份规范入库 13.4 分钟」。
cProfile 实测（143KB / 270 块 / 合计 177.1s）拆解：

| 组成 | 实测 |
|---|---|
| 分块（本地 CPU） | 0.005s |
| **写库（270 行 × 1024 维，单事务）** | **0.010s** |
| `_gen_llm_summary`（5 次串行 LLM） | 175.9s ← 其中 **161.1s 全在等写锁** |

根因：`ingest_document` 在 INSERT 之后没commit，事务一路跨到 LLM 摘要结束。
修复后：**177.1s → 18.4s**，锁等待归零。

今天复核：单事务写 270 行 + 后续写 = **0.000s**（无阻塞）。

⇒ **"必须停服务"从来不是数据量问题，是锁持有时间问题**，已解决。

### ② 长任务已有去处（实测 11 处端点接队列）

原评估写「celery / rq / arq / BackgroundTasks 全仓 0 命中」。
现已有进程内作业队列 `core/job_queue.py` + `core/job_handlers.py`，
**11 处业务端点**支持 `mode=async`：文档入库 / 工程入库 / v2g 抽取 /
重索引 / 重试 / 写后调和。前端已接轮询（`pollJob`，提交 17ms 返回）。

⚠️ 但队列是**进程内**的 —— 它不解锁多副本。这正是 P0-3 剩下的那个理由。

## 三、仍然成立的那条：单副本是硬约束

`docker-compose.yml:8-12` 仍明写：

```
# ⚠️ **单副本是硬约束，不是保守建议**：
#   要横向扩展必须先换 PostgreSQL（P0-3），不是把 replicas 调大。
#   compose 里刻意不写 deploy.replicas，并在下方显式注释，避免有人顺手加上。
```

这与P0-3 是**同一个问题的两面**：
- 队列不跨进程 ⇒ 多副本需要外部队列（Redis/RabbitMQ）；
- SQLite 单写者 ⇒ 多副本写冲突；
⇒ **两者都指向"要上PG"**。

**但这是否现在就要付这个成本，取决于部署形态**（米爸此前答复"部署形态不确定"）：

| 部署形态 | 是否需要现在迁 PG | 理由 |
|---|---|---|
| **单机私有化**（当前假设） | **否** | 单副本 ⇒ 不需要横向扩展；数据量（321MB/22K 行）对 SQLite 无压力；队列进程内够用 |
| 单机但要求高可用 | **否**（用备份+快速恢复） | 单机故障才需要切换，PG 也解决不了进程级故障 |
| **多副本 / 集群** | **是** | 单副本约束直接被打破 |
| SaaS 化 / 上云扩容 | **是** | 同上 |

⇒ **决策点回到部署形态**，而不是技术必要性。

## 四、改造面（实测，比原评估更大）

| 项 | 原评估 | 今晚实测 | 变化 |
|---|---|---|---|
| `conn.execute(` | 1634 | **2112** | ↑ 29%（原评估漏算了部分目录） |
| `commit()` | 625 | **1014** | ↑ 62% |
| `INSERT OR IGNORE` | 59 | **88** | ↑ 49% |
| `INSERT OR REPLACE` | 5 | 14 | ↑ |
| `AUTOINCREMENT` | 120 | 171 | ↑ 43% |
| `sqlite_master` 直查 | 24 | 50 | ↑ |
| `strftime` / `julianday` | 24 | 56 / 10 | 时间口径改造点增加 |
| `rowid` | 35 | 87 | ↑ |
| PG 驱动 | 未引入 | 仍未引入 | — |

⇒ 改造面**比原评估更大**，而测试覆盖没变（`pytest` 34 用例，
覆盖不到 2112 处 SQL 的绝大多数）。

⚠️ **时间口径是最危险的一类**：`strftime` 56处 + `julianday` 10 处。
SQLite 的 `strftime('%Y-%m-%d %H:%M:%S')` 存的是**本地时间**，
PG 的 `now()` 是**带时区**类型 —— 换过去若不统一，
会重演"UTC vs 本地时间"的坑（今天已在 SQLite 上踩过一次）。

## 五、决策建议

### 建议：**继续暂不迁，但做三件「无悔准备」**

理由：迁移成本（数人周 + 高回归风险）远大于当前收益（数据量小、单副本够用），
而**部署形态仍未确定**—— 需求没确定就动手改 2112 处 SQL 是赌博。

#### 无悔准备 1：把方言差异收进 `database/connection.py`（成本低、收益明确）

当前 `database/connection.py` **直接 `import sqlite3`，无任何方言抽象** ——
这是"要换 PG 就得改 2112 处"的根因。
逐步引入一层薄抽象（`dialect.py`）：

```python
# database/dialect.py（新增）
def now_expr():    return "CURRENT_TIMESTAMP"        # 统一时间口径入口
def upsert_sql(table, cols, conflict_cols): ...      # INSERT OR IGNORE / OR REPLACE 的方言
def limit_clause(n, offset=0): ...                    # LIMIT/OFFSET 变体
def last_id_sql(): return "last_insert_rowid()"      # PG 下换 RETURNING
```

**为什么这是无悔的**：① 现状零行为变化；
② 不改存量 SQL 也能先用在新代码上；
③ 换 PG 时只需改这一个文件 + 逐步迁移调用点。

⚠️ 但**不要**为了"看起来有抽象"而批量改写存量 2112 处——
那等于把一项高风险重构提前到没有需求的时候。

#### 无悔准备 2：给"要迁"设**触发条件**（而不是再评估一次）

明确写下"满足以下任一条就启动迁移"，避免每次都重新讨论：

| 触发条件 | 为什么是它 |
|---|---|
| 部署形态定为**多副本 / 集群 / SaaS** | 单副本硬约束被打破 |
| 单库 > **50 GB** 或写入并发 > **50 QPS** | SQLite 单写者到顶 |
| 需要**跨库 JOIN**（图库 × 向量库 × 业务库） | SQLite 不支持跨库 |
| 需要**在线扩容 / 读写分离** | SQLite 结构上做不到 |
| 需要**行级安全（RLS）**做多租户 | 当前靠应用层过滤，PG 有原生能力 |

#### 无悔准备 3：把 `safe_init_db` 的缺陷补掉

实测发现（见 `docs/磁盘清理记录-20261004.md`）：
`backups/` 里 14 份 `pre-migrate-*.db` **全是 20KB 空壳**（只有 4 张表）——
`backup_db()` 只copy 不校验源库有效性⇒ **迁移安全闸以为"有备份就安全"，
实际留了一堆恢复时会炸的假备份**。

这个缺陷与"迁不迁 PG"无关，**现在就该修**（成本 ~30 行）：备份后校验
表集合与源库一致，不一致则拒绝并报错。
