## 0. 执行摘要（结论先行）

**一句话**：把"评测全离线、生产流量不回流"这条断链接上——生产流量按策略采样进 `online_eval_queue`，确定性指标自动打分（只进"建议"），人工在既有 HIL 交互里转正为标签，按意图/检索/生成三分流进各自 dataset，门禁可见；同时给会话直答主路径补 span，让 trace 从"只覆盖编排 57 行"扩展到会话全链路。

**验收判据**（路线图原文）：

| 判据 | 量化 |
|---|---|
| `verify_online_eval_loop.py` 端到端夹具通过 | 「采样→自动评→人工转正→进 dataset→门禁可见」五段全绿 |
| 会话 span 覆盖率 | >95%（每次 /chat/stream 有 conversation span，每轮 ReAct 有 turn span） |
| 生产回流真实性 | 人工转正 ≥1 条进 `intent_samples`（`source='prod'`，现成先例 157 条） |

**不做什么**（边界，防范围蔓延）：

- 不自建 OTel collector、不引入 OpenTelemetry SDK——span 落现有 `orch_run_spans` 表，查询走 monitor 页（设计原文："OpenTelemetry 兼容的轻量 span 模型"）。
- 不建第二套人工交互——标注复用 `hil_confirmations` 的确认卡模式（评分 + 原因），前端零新页面组件，只在监控页加一个"待标注"列表。
- LLM judge 不进自动评默认路径（`--llm-judge`  opt-in 纪律沿用 eval_generation_quality，模型有温度不是确定性断言）。

### 1.3 病灶 recap

1. **评测全离线**：意图样本池/qrels/生成质量都是手工或离线批产，生产流量（385 条消息、3274 条检索 trace）**零回流**。

3. **人工校准无入口**：行业核心动作"生产采样→人工标注→回归"整段缺失。

## 2. 总体架构（五段闭环）

```
生产流量（messages 385 / query_trace 3274 / llm_usage_stats 13409 / tool_call_logs 2179）
   │ ① 采样器（online_eval_sampler）：负反馈优先 > 低置信优先 > 随机 5%
   ▼
online_eval_queue（新表：候选样本 + 完整 trace 引用 + 采样原因）
   │ ② 自动评估器（reference-free 确定性）：citation 使用率 / 接地率 / 无据声称密度 / 延迟
   │     —— eval_generation_quality 确定性层直接搬；结果只写 auto_score（"建议"）
   ▼
人工标注（复用 hil_confirmations 确认卡：评分 1-5 + 原因；前端"待标注"列表）
   │ ③ 转正确认（status: suggested → confirmed / rejected；**只有 confirmed 进 dataset**）
   ▼
三分流适配器（按 sample_type）：
   ├─ intent   → intent_samples（status='confirmed', source='prod'）  ← 现成先例 157 条
   ├─ retrieval→ tools/eval/qrels.jsonl（append，带 human_confirmed 标记）
   └─ generation→ eval_gen_labels（新表：citations 结构 + 评分 + 原因）
   │ ④ 门禁可见：/api/eval/gates 已有；新 dataset 纳入 verify_online_eval_loop 夹具
   ▼
回归门禁：下次相关评测跑 dataset（eval_retrieval / calibrate_routing / eval_generation_quality 消费）
```

**贯穿纪律**（与 P0-a 同款，全部来自已付过学费的教训）：

1. **系统自动打分只进"建议"，人工确认才转正**——同 `intent_samples` 的 suggested/confirmed/rejected 三态纪律，防自我循环（LLM 评 LLM 的输出再自动喂回训练/门禁）。
2. **不造假数据**：采样引用必须存完整外键（conversation_id/message_id/query_trace_id），转正时按外键回查原文，不留孤儿标签。
3. **dry-run 默认**：采集/转正类端点默认 dry-run，真动作必须显式参数（同 BadCase `collect_bad_cases(apply=False)` 与 `POST /badcases/collect {"apply": true}` 双门）。
4. **失败可见**：采样/自动评任何一步异常记 `collect_failures` 并上周报，不静默跳过（P0-a `_act_badcase` 同款）。

## 3. 表结构设计（3 张表：1 新 + 1 扩 + 1 新）

### 3.1 `online_eval_queue`（新表，候选样本队列）

```sql
CREATE TABLE IF NOT EXISTS online_eval_queue (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    sample_type TEXT DEFAULT '',        -- intent | retrieval | generation（转正分流依据）
    -- 完整 trace 引用（转正时回查原文，不留孤儿）：
    conversation_id INTEGER DEFAULT 0,
    message_id INTEGER DEFAULT 0,      -- messages.id（生成质量样本的答案体）
    query_trace_id INTEGER DEFAULT 0,  -- query_trace.id（检索/意图样本）
    trace_id TEXT DEFAULT '',          -- llm_usage_stats.trace_id（LLM 侧关联，P0-c 已有）
    -- 采样原因（可解释：为什么这条进了队列）：
    sample_reason TEXT DEFAULT '',     -- neg_feedback | low_conf | random_5pct
    reason_detail TEXT DEFAULT '',     -- 具体信号（ux event 名 / top_score 值 / 随机种子序号）
    -- 自动评估（reference-free，只进"建议"）：
    auto_score REAL,                   -- 0-1 综合分；NULL=自动评失败（不补零）
    auto_detail TEXT DEFAULT '{}',     -- JSON：citation_use/grounding/unsupported/latency 分项
    auto_eval_at TEXT,
    -- 人工标注（复用 hil 确认卡语义）：
    status TEXT DEFAULT 'pending',     -- pending | labeled_confirmed | labeled_rejected
    human_score INTEGER,               -- 1-5 人工评分（NULL=未评）
    human_reason TEXT DEFAULT '',
    labeled_by TEXT DEFAULT '',
    labeled_at TEXT,
    created_at TEXT DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX IF NOT EXISTS ix_oeq_status ON online_eval_queue(status, sample_type);
CREATE INDEX IF NOT EXISTS ix_oeq_conv ON online_eval_queue(conversation_id);
CREATE INDEX IF NOT EXISTS ix_oeq_trace ON online_eval_queue(trace_id);
```

设计要点：
- `auto_score` 可空——自动评失败留 NULL 并进 `collect_failures`，**不补零**（补零会让"没评"长得像"评了 0 分"）。
- 三态与 `intent_samples` 同构（pending≈suggested，两 labeled 终态），转正适配器只读 confirmed。
- 不用 UNIQUE 约束会话+消息：同一条消息可因不同理由多次入队（负反馈 + 低置信各采一次），转正时按 (sample_type, message_id) 取最新 confirmed。

### 3.2 `orch_run_spans` 扩展（会话级 trace，不新建表）

现有表（database/schema.py:1264）已有 `kind` 列（run|plan|task|summary|reflection|views|replan 八种）与 `parent_id` 树。**新增五个 kind 值 + 两个索引**，DDL 零改动，只改写入侧：

| kind | 含义 | parent | 写入点 |
|---|---|---|---|
| `conversation` | 一次 /chat/stream 端到端 | 0（根） | stream 入口 |
| `turn` | ReAct 一轮（含一次 LLM 决策） | conversation | 每轮循环 |
| `tool` | 一次工具调用 | turn | 工具执行前后 |
| `rag` | 一次检索/rerank | turn | RAG 调用前后 |
| `llm` | 一次 LLM 调用 | turn | chat 前后 |

```sql
-- 新增索引（现有 idx_ors_conv_run 覆盖 conversation_id+run_id；会话 span 的 run_id=0，
-- 需要按 trace_id 反查 llm_usage_stats 的关联列）：
CREATE INDEX IF NOT EXISTS idx_ors_kind_time ON orch_run_spans(kind, created_at);
-- meta_json 约定（各 kind 的载荷，键名稳定，monitor 页按 key 取）：
--   conversation: {"intent":..., "route":..., "msg_id":...}
--   turn:         {"turn_no":n, "tools":[names]}
--   tool:         {"capability_id":..., "ok":0/1}          ← 与 tool_call_logs.capability_id 同口径
--   rag:          {"hit_count":n, "top_score":f}
--   llm:          {"trace_id":..., "tokens_in":n, "tokens_out":n, "model":...}
```

**为什么不新建 `run_spans` 表**（设计原文说"扩展现有表"）：`orch_run_spans` 已有 parent 树/状态/latency/meta_json 全套骨架与 `SpanCollector` 写入通道；编排与会话的 span 在一张表里才可做"同会话编排 vs 直答"的对比查询（这正是 monitor 页下钻要回答的）。DDL 不动 = 零迁移风险。

### 3.3 `eval_gen_labels`（新表，生成质量转正标签）

```sql
CREATE TABLE IF NOT EXISTS eval_gen_labels (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    queue_id INTEGER DEFAULT 0,        -- online_eval_queue.id（外键溯源）
    message_id INTEGER DEFAULT 0,      -- messages.id（答案体）
    conversation_id INTEGER DEFAULT 0,
    human_score INTEGER,               -- 1-5
    faithfulness INTEGER,              -- 忠实度 1-5（LLM judge 同维度，人工版）
    citation_ok INTEGER,               -- 引用编号是否与 citations 对齐 0/1
    reason TEXT DEFAULT '',
    created_by TEXT DEFAULT '',
    created_at TEXT DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX IF NOT EXISTS ix_egl_msg ON eval_gen_labels(message_id);
CREATE INDEX IF NOT EXISTS ix_egl_queue ON eval_gen_labels(queue_id);
```

为什么生成质量不走 qrels.jsonl：qrels 是 (query, doc, idx) 三元组，装不下"答案-引用-评分"结构；且 eval_generation_quality 的消费方是 `evaluate_answers(answers)`（读 messages），标签表按 message_id 关联即可被它 join。

## 5. 门禁判据（`tools/verify/verify_online_eval_loop.py`，A-H 八条 + 阳性对照）

沿用 P0-a 门禁范式（A 投影完整性 → H 阳性对照，退出码 0/1/2，2=守卫失效）：

| 段 | 断言 | 判据 |
|---|---|---|
| A1 | 五段闭环端到端 | 夹具库：采样入队 ≥3（三种 reason 各 ≥1）→ auto_eval 后 auto_score 非 NULL → 标注 confirmed → promote 后三 dataset 各 ≥1 行 |
| A2 | 三分流正确 | intent 行进 `intent_samples`（status='confirmed' AND source='prod'）；retrieval 行 append 进 `qrels.jsonl` 且 `human_confirmed=true`；generation 行进 `eval_gen_labels` |
| A3 | 转正幂等 | 同 queue_id 二次 promote，三 dataset 行数不变 |
| B1 | 纪律：auto 只进建议 | promote 前 confirmed 数=0 时三 dataset 零增长（**自动打分永不自动转正**） |
| B2 | dry-run 默认 | `sample_candidates(apply=False)` 后队列行数不变 |
| B3 | rejected 不进 dataset | labeled_rejected 样本 promote 后三 dataset 零增长 |
| C1 | span 五类齐 | 夹具跑一轮会话：conversation 1 + turn ≥1 + tool ≥1 + rag ≥1 + llm ≥1 |
| C2 | span 树正确 | 每个 tool/rag/llm span 的 parent_id 指向某个 turn，turn 的 parent 指向 conversation |
| C3 | trace_id 贯通 | llm span 的 meta_json.trace_id 能在 `llm_usage_stats` 命中 |
| C4 | 覆盖率口径 | `conversation span 数 == 本轮会话消息组数`（monitor 页 >95% 判据的可执行版） |
| D1 | 挂载点静态扫描 | 五个挂载点文件均含 tracer 调用（行边界法抽取，见 P0-a D 段同款） |
| D2 | 阴性对照 | 摘掉任一挂载 ⇒ C1/C4 判红（证明断言有牙齿） |
| E | 阳性对照守卫 | 构造"全链路修好"的夹具 ⇒ 必须全绿；若红 ⇒ 守卫失效 exit 2 |
| F | 指标白名单 | `online_eval_metrics` 新增 3 个指标均在 `alert_evaluator.GLOBAL_METRICS` 且有供数（P0-a 白名单制同款，防假实现） |
| G | 真库只读取证 | 真库段只读：queue_summary 数字与直接 SQL 一致 |

**门禁纪律**（P0-a 已付学费，直接继承）：
- 夹具 DDL 必须覆盖被测 INSERT 的全部列，且**不写 DEFAULT**（门禁源码双引号串里的 `\'\'` 到子进程只剩 `''`，会截断子进程单引号字符串——verify_attribution D6 踩过）。
- 判据过时必须同步改并留注释（如产品改名后判据字符串跟着改），否则旧判据持续假红（E5 踩过）。
- "功能没生效"类结论，先证明验的是真东西（阳性对照 E 段）再下产品结论。
