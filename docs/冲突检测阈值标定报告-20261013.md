## 0. 一句话结论

**标定做不成 —— 不是因为阈值不准，而是因为真库里一个可标定的样本都没有。**

`sim_high` 在 **0.30 ~ 0.90** 任意取值，命中数**恒为 0**。真正卡住这条链路的不是相似度，
而是**互斥断言词**：`35` 个同组对里含互斥词的为 **0 对**。

⇒ **现在打开 `conflict_detect_enabled` 不会有任何效果**（不是"打开就会误判"，
是"打开和关着行为完全一样"）。而这一点**从返回值上看不出来** —— `maintain()` 会返回
`conflicts: 0`，与"跑过了但没冲突"无法区分。这正是本仓记忆里那条
「门禁存在 ≠ 门禁在起作用」的同族问题在**业务开关**上的形态。

## 1. 关键事实：存在**两套**互不相干的冲突检测

上轮我说的"`0.5` 阈值"属于 **memory 侧**；而我举例的 `entity_resolver.detect_conflicts`
是 **entity 侧**。两者**不共用任何判据**：

| | memory 侧 | entity 侧 |
|---|---|---|
| 入口 | `MemoryService.detect_conflicts()` | `entity_resolver.conflict_detect()` |
| 调用方 | `memory_service.maintain()`（`deposit()` 内触发） | `routers/knowledge_parts/pipeline.py:858`、`services/knowledge_service.py:316` |
| 目标表 | 改 `agent_memory.superseded_by` | 写 `knowledge_conflicts` 表 |
| **相似度门** | ✅ 有（`sim_high`，默认 0.5） | ❌ **没有**（我 grep 了整个函数，`sim/cos/相似` 零命中） |
| **互斥词门** | ✅ 有（`_CONFLICT_MARKERS` 10 词） | ❌ **没有** |
| 判据本质 | 同键 + 高相似 + 含互斥词 | 同键 + **值不同**（其余一律算冲突） |
| 开关 | `memory.conflict_detect_enabled`（默认 **False**） | **无开关，调用即执行** |

> ⚠️ **这纠正了我上轮的表述**：我说"阈值 0.5 是 entity 侧 `detect_conflicts` 的"，错了。
> `conflict_detect_sim_high` 的**唯一**消费点是 `memory_service.py:689`。
> entity 侧那条链路里**没有相似度**这回事，所以**调这个阈值对它零影响**。

## 2. memory 侧：35 个同组对，0 个含互斥词

严格照 `detect_conflicts` 的分组口径（`scope_type` + `scope_id` + `mem_topic`／`__agent__:<id>`）：

| 项 | 实测 |
|---|---|
| 活跃记忆（`forgotten=0` 且 `superseded_by=0`） | **93** 条 |
| `embed_version` 分布 | `openai-compat` 128 / 空 20（全库 148 行口径） |
| 分组数 | 73（其中含 ≥2 条的 **12** 组） |
| 待比较对数 | **35**（其中双方同为真向量口径 **33**） |

**相似度分布**（直接 import 生产代码的 `_mem_cosine`，量出来的就是运行时会用的那个数）：

```
min=0.1997   p10=0.6120   median=0.7436   p90=0.9801   max=0.9986
分档： <0.50 → 1     0.50~0.70 → 14    0.70~0.85 → 7
       0.85~0.90 → 4  >=0.90（重复区）→ 9
```

**按「是否含互斥断言词」分组 —— 这是标定的核心**：

| 分组 | n | min | median | max |
|---|---|---|---|---|
| 全部对 | 35 | 0.1997 | 0.7436 | 0.9986 |
| **含互斥词（候选冲突）** | **0** | — | — | — |
| 不含互斥词 | 35 | 0.1997 | 0.7436 | 0.9986 |

**阈值扫描**（含互斥词的命中数 / 无互斥词的误伤数）：

| `sim_high` | 命中含互斥词对 | 备注 |
|---|---|---|
| 0.30 / 0.40 / 0.50 / 0.60 | **0** | 无互斥词 ⇒ 恒 0 |
| 0.70 / 0.80 | 0 | 无互斥词的 35 对中 sim≥0.8 的有 14 对 |
| 0.85 / 0.90 | 0 | sim≥0.9 的 9 对即"重复区"（`consolidate` 阈值 0.85 之上） |

**互斥词表实况**（`_CONFLICT_MARKERS`，10 个）：
`不再 / 已废弃 / 已废止 / 已更正 / 更正为 / 应改为 / 已过时 / 已失效 / 已作废 / 废止该规则`

**在全库 93 条活跃记忆里逐条扫，命中 2 条** —— 但**逐条读下来两条都是误判**：

| id | 命中词 | 原文片段 | 性质 |
|---|---|---|---|
| 267 | 不再 | 「特化后 subject **不再**居首即报语义错」 | 描述一条**语法规则**（"不符合就报错"），不是"某口径已被新口径取代" |
| 269 | 不再 | 「同一需求**不再**额外绑定主体以免语义冲突」 | 描述一条**建模约定**，同上 |

⇒ **「不再」这个词在中文技术写作里大量用于陈述规则，而非陈述废止。**
词表本身在 docstring 里已经写了"刻意不收『新版/更新后/改为』这类宽泛词"，
但 `不再` **同样宽泛**，却留在表里 —— 这是词表的一个已知薄弱点，
只是今天第一次有数据能证明它会误判。

## 3. entity 侧：0 对的原因是分组口径，**与阈值无关**

在生产库副本上真跑 `conflict_detect(conn)`：`{'detected': 0, 'skipped': 0}`，`knowledge_conflicts` 仍 0 行。

结构诊断（183 个非 deprecated 实体）：

| 分组层级 | 含 ≥2 条的组数 |
|---|---|
| `(branch, 归一名, entity_type)` ← **生产口径** | **0** |
| `(branch, 原名)` ← 放宽类型限定 | **3** |

3 个放宽后的组全部是同一个实体 `转发器`，在 dev / release / personal 三个分支各 2 条：

```
id=S-4782d01d    branch=dev  type=转发器  status=reviewed
id=V2G-50fe042d  branch=dev  type=部件    status=reviewed  props={"matched_sysml_entity":"转发器"}
```

**同组两条的 `entity_type` 不同（`转发器` vs `部件`）** ⇒ 被类型限定挡在门外。
而这**恰恰是正确的**：一个是手工建的实体，一个是 SysML 导入后自动匹配上的**同一个东西**，
它们本就不该判成"冲突"。类型限定在这里起了保护作用。

⇒ **entity 侧的 0  detections 是"当前数据没有同键不同值的实体对"，不是缺陷。**
但要留意：这条链路**没有互斥词门**，一旦数据里出现同 `(branch, 归一名, 类型)` 且属性值不同的两条
（**包括"互补"而非"互斥"的情况**，如 `材质=铝合金` vs `产地=进口`），它会**无条件**记成冲突。
这是它的设计取向（宁可多报给人看），但配置注释里标定的那条阈值**对它无效**。

**我的建议是 A**，理由：
1. 现在开开关**没有任何可观测收益**（恒 0 对）；
2. 但**开开关这件事本身有观测价值** —— 只有真跑起来，才知道生产流量里到底会不会出现互斥对。
   建议折中：**开开关 + 挂一条"互斥词命中率"指标**，命中率长期为 0 时说明词表太窄，
   此时才决定要不要扩词表 —— **用数据决定，而不是现在拍**。

### ⚠️ 撤回一条我中途写进报告的"真缺陷"

标定过程中我曾记录：「`_normalize_mentions` 在真库上抛
`KeyError: ('dev','宽带载荷','通信载荷分系统')`，而生产代码调用它时没有 try
⇒ 知识入库流水线会在这一步崩，建议排期 0.5 人日」。

**这条是错的，是我自己脚本的 bug。** 那个 `KeyError` 的真实来源：

```python
_bk = _dd()            # ← 错：defaultdict() 不带 default_factory
_bk[("dev","宽带载荷","通信载荷分系统")].append(e)   # ⇒ KeyError
```

`defaultdict()` **不传参数时 `default_factory=None`，取缺失键抛 `KeyError`**，
而不是"建个空列表"。改成 `_dd(list)` 即正常。

严格复现（照 `conflict_detect` 的实参、连跑 3 次）：`_normalize_mentions` **每次都成功返回 60 条**，
**生产代码不存在这个缺陷，无需排期**。

> 这已是本次会话**第四次**同型自曝（`agent_tasks.agent` 假列 → `agent_id` 存名 →
> conflict_check 绑定关系不实 → 本条）。
> 识别法一致：**异常里出现的数据值，往往来自我自己的代码路径，不是被测系统的**。
> 教训：**判据自己抛异常时，先确认异常是谁抛的**，再决定要不要给产品排期。
