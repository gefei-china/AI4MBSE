## 二、根因：单例 Pipeline 的状态泄漏（本轮实测，非推断）

### 2.1 机制

对话入口 `routers/conversations.py`：

```python
from agent import agent# 模块级单例
```

⇒ **所有用户、所有请求共用同一个 `AgentPipeline` 实例**。
而 Pipeline 把"本次请求的中间产物"挂在 `self` 上（19 个 `self._xxx` 字段）。

关键链路：

```
请求A：LLM 调 sysml_v2_validate(code=视图A代码)
   → tools.py:691   self._sysml_last_checked_code = code_a
                self._sysml_last_pass_code      = code_a
   ↓ （这两个字段在请求入口从未被清零）
请求B：生成视图B，正文恰好没代码
   → cards.py:319  _ensure_sysml_from_tools 读 self._sysml_last_pass_code
   → 把**视图A 的代码**当作视图B 的产出交付给用户
```

这解释了此前反复记录却未定位的现象——**"叙述是新的、代码是旧的"**：
LLM 的叙述确实是本轮新生成的（没走缓存），但**交付出去的那段代码是上一轮残留的**。

### 2.2 确定性证明（不依赖 LLM）

因为 LLM 输出不确定，会掩盖机制，所以用纯机制探针验证：

```
[请求A] 已校验代码 = package 'ReqA' { part def '旧视图零件A'; }
[请求B] 正文 = 已生成状态机视图，包含 3 个状态与 4 条 transition。
[请求B] 交付 = ...（附：本轮已校验的 SysML v2 模型代码）package 'ReqA' { part def '旧视图零件A'; }
!! 泄漏命中：请求B 交付了请求A 的代码
```

修复后同一探针：`OK：未泄漏，修复有效`。

### 2.3 为什么之前所有排查都没找到

前三次排除（注入 skill 命中正确 / offload 各挂自己会话 / `semantic_cache` 0 行）
**都只能证明「记录是对的」**，不能证明「送进 LLM 的内容是对的」。
而泄漏发生在**记录之后、交付之前**——查记录永远看不到它。

另一个更根本的原因：**单次跑必绿**。
第一个请求的状态本来就是干净的 ⇒ 任何单次验证都通过。
这类缺陷**只有同实例连跑才暴露**。

### 2.4 修复（平台通用，无一条视图特例）

新增 `agent/pipeline_parts/common.py::reset_request_state(pipe)`，
在 `execute()` 与 `execute_stream()` 的**方法最前端**无条件调用，清零 19 个字段：

| 类别 | 字段 |
|---|---|
| ★交付兜底缓存 | `_sysml_last_checked_code` / `_sysml_last_pass_code` |
| ★技能注入 | `_skill_body_offloads` / `_last_skill_hits` / `_skill_allowed_tools` / `_skill_forced` |
| 工具审计归属 | `_tool_conv_ctx` / `_tool_user` / `_tool_intent_ctx` / `_tool_agent_ctx` / `_tool_whitelist` / `_tool_run_ctx` / `_tool_task_key` |
| 记忆作用域 | `_mem_ctx` / `_mem_project_id_cache` |
| 编排/会话标记 | `_orch_error` / `_orch_subtask` / `_hil_level` / `_hook_warn` / `_last_clarify_skip` / `_slot_merge_stats` / `_last_compaction` / `_ns_ctx` / `_ns_kb_scope` / `_orch_acc` / `_orch_token` |

**位置纪律（我本轮自踩并修正）**：清零必须**早于方法内任何 `self.X =` 赋值**。
我第一次插在 `_mem_ctx = ...` 之后 ⇒ 会把本次请求刚设好的上下文抹掉。
`verify_request_state_reset` 的 A1 判据专门守这条。

### 2.5 门禁 `tools/verify/verify_request_state_reset.py`（13 断言，变异 4/4 判红）

| 判据 | 内容 |
|---|---|
| A1 入口不变量 | 两个入口都调用清零，且**早于**首个赋值（AST 验证，不靠 grep） |
| A2 覆盖完整性 | AST 扫全部 `self._xxx`/`pipe._xxx` 赋值点，与清零清单求差集，**差集必须为空** |
| A3 端到端 | 单例连跑两次，第二个请求的交付不得含第一个请求的代码；且**同请求内兜底仍有效**（防"清零过头"改坏功能） |

**A2 是关键设计**：不靠人记得登记，新增字段忘了清零**立刻判红**。
（判据自身也踩过一次假红：首版只认 `self.X =`，而 `reset_skill_state` 写的是 `pipe.X =` ⇒ 修判据而非改正确代码。）

## 三、稳定性复测：本轮结论是「样本不足，不可采信」

修复后跑 `verify_n3_stability.py --repeat 3`（真实 LLM，8 视图 × 3 轮 = 24 次生成，20 分钟）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 产出雷同轮次 | 2/3 | **0/1（只有 1 轮有效，不可采信）** |
| 有效样本 | 24 | **16（第 3 轮LLM 402耗尽中止）** |

### ⚠️ 三条必须如实说明的限制

1. **不能宣称"已修复"**。0/1 雷同率来自单轮样本，而单轮本来必绿。
   按项目纪律（无证据不迁旧 Agent），**旧 8 个视图 Agent 继续保持 active**。
2. **LLM 余额在实验中耗尽**（402），第 3 轮回落 Mock 后中止。
3. **判据自身算错过**：原式用「轮数」当分母，而 ok/fail 是**逐次计数**，
   导致输出过不可能的 `12/8 = 150%`。已修为 `分母 = ok+fail+impure+no_code`，
   并加了「有效样本不足 2 轮/不足一半 ⇒ 明确警告不得据此判断稳定性」。

⇒ **要真正定性，需充值后重跑满 3 轮。**

## 四、与标杆产品的结构差异（附来源）

### 4.1 状态隔离机制对照

| 平台 | 状态载体 | 生命周期 | 依据 |
|---|---|---|---|
| **本项目** | **模块级单例 Pipeline 的 `self._xxx`（19 字段）** | **进程级、跨全部请求** | 实测（本轮） |
| Anthropic Claude Code | 子 Agent 结束即丢弃整个对话上下文 | 请求/任务级 | 官方文档 |
| LangGraph | `thread_id` 作 checkpointer 主键，状态显式图 + super-step | thread 级 | 官方文档 |
| OpenAI Agents SDK | sessions 持有会话状态，handoff 显式传递 | session 级 | 官方文档 |
| AutoGen | `TokenUsageTermination` 等终止条件，运行上下文随run | run 级 | 官方文档+源码 |

**核心差异**：主流平台把状态放在**显式载体**（thread_id / session 对象）里，
本项目放在**隐式实例属性**上——而实例是全局单例。
⇒ 前者状态隔离是**架构保证**，后者是**纪律要求**（靠人记得清）。
本轮事故正是纪律没守住的地方。

**同时注意**：没有任何一家主流平台采用「多个 Agent 共绑主 Agent + 共享模块级状态」这种结构。

### 4.2 tool-calling 可靠性：行业主流做法是「换模型」，不是「加固正则」

本项目问题：`deepseek-v4-flash` 把工具调用写进 `content` 文本而非 `tool_calls` 字段，
上一轮用 `_salvage_inline_tool_calls()` 正则兜底修复。

调研结论（**这是本轮对米爸最有价值的一条**）：

- OpenAI Agents SDK 官方文档对不支持 JSON schema 的 provider 直接劝退，
  原文大意为「否则你的应用会经常因为畸形 JSON 而崩溃」。
- LiteLLM 生态实践记录更直接：json-mode 兜底路径会让模型
  「无法稳定遵循这种复杂的 Prompt 格式，最终造成 Claude Code 毫无反应」，
  最终解法是**换回原生 tool-calling 通道**。

⇒ **正则捞取不是 workaround，是把模型的系统性缺陷变成我们要永久维护的解析器。**
本轮那条 `_salvage_inline_tool_calls` 的正确定位应该是**过渡兼容层**，
而不是长期方案。真正的根治是换用原生 tool-calling 可靠的模型。

⚠️ 调研中 3 个 LiteLLM 参数（`tool_choice_conversion` / `json_mode_with_tool_choice` /
`parse_tool_call_from_content`）**未在官方主文档与当前 main 分支源码中检索到**，
只有社区教程在用，**属二手来源，不可直接照抄配置**。

### 4.3 一个隐性风险（建议优先排查）

LangGraph 官方 reference 警告：**同一 `thread_id` 传不同 `initial_state` 不会重置线程**，
已保存状态优先、input 被忽略。

⇒ 本项目若在语义缓存 / 记忆治理里用了类似 `run_id` 的 key 做"新任务"标识，
可能出现**新任务静默跑旧状态**——比产出雷同更严重（雷同至少可见）。

### 4.4 工具预算：主流是硬熔断，我们是"降级交付"

| 平台 | 机制 |
|---|---|
| Claude Code | `max_budget_usd` |
| OpenAI Agents SDK | `max_turns=10`（源码常量） |
| AutoGen | `TokenUsageTermination` |
| **本项目** | 轮次上限 6（可配置）→ 超了**仍收尾并交付** |

⇒ 本项目的"降级交付"是**故意的产品选择**（宁可给个不完美的结果也不给空），
但它与「静默回落 Mock」叠加时会产生**用户无感的假答案**（见第五节 P0）。

## 五、是否应该替换成开源 AI 平台？—— 建议：**不替换**

### 5.1 直接结论

| 方案 | 判断 | 理由 |
|---|---|---|
| 整体替换为 Dify / RAGFlow / FastGPT / Coze 类平台 | ❌ **不可行** | 这些是**通用 LLM 应用编排平台**，无 SysML v2 语义层、无 checker 级语法/语义验证、无版本留痕与追溯链。**换过去 MBSE 能力归零**，而MBSE 能力正是本项目存在的理由 |
| 换为 LangGraph / AutoGen 自建 | ⚠️ 部分借鉴 | 它们的**状态隔离与终止机制**值得引入（见 5.3），但整体重写代价远超收益 |
| 在现架构上做定向整改 | ✅ **推荐** | 已定位的根因是**状态隔离**一处，不是架构方向错了 |

### 5.2 为什么「通用开源平台」承载不了本项目

现有平台里已经跑通、而通用平台**不提供**的资产（实测）：

| 能力 | 本项目现状 |
|---|---|
| SysML v2 语法/语义双路校验 | `checker.jar` 直调（词法/语法/语义三路计数 +中文诊断） |
| 版本留痕与追溯链 | `_archive_sysml_version` → `element_summary.check`（含blocked/时间戳，可回溯"当时合不合法"） |
| 知识库分派（16 份/ 7269 chunk 按权威性+阶段过滤） | 已接线，召回 120 chunk、零泄漏 |
| 方法论 24 条规约表 | `methodology_rules` 已落库 |
| 17+4 Agent 协作体系、流水线 8 节点 | 已跑通 |

⇒ 这些是**领域资产**，不是"AI 平台能力"，开源平台**替代不了**。

### 5.3 真正该借鉴的三件事（低成本、高收益）

| 借鉴 | 现状 | 动作 |
|---|---|---|
| **状态改显式载体** | 单例 `self._xxx` | 短期：已加门禁守住纪律。中期：`thread_id` 式显式运行上下文，或编排子任务外一律**每请求新建 Pipeline**（`workflows/nodes.py` 已是这个做法，**主对话路径应对齐**） |
| **换原生 tool-calling 模型** | 正则兜底过渡 | 用支持可靠原生 tool-calling 的模型替换 deepseek-v4-flash，兜底层保留但降为兜底 |
| **终止用硬熔断** | 超轮次仍降级交付 | 区分「可降级的生成失败」与「不可降级的验证失败」；Mock 回落必须**用户可见**（见 P0） |

## 六、⚠️ 本轮新发现的 P0 问题（与雷同无关，但更影响可信度）

### LLM 402 失败会**静默回落 Mock**，用户拿到假答案

实测日志（修复后稳定性跑到第 3 轮时）：

```
LLM API 402: {'error': {'message': 'Insufficient Balance ...'}}
LLM 真实调用失败 → 静默回落 Mock：调用点=execute.py:504 ...
[FAIL][r3]  LLM 已回落 Mock（响应='（Mock 回答）已收到你的消息：只回复两个字：可用
             当前为 Mock 降级模式（未配置真实 LLM API Key）。'）
```

**现状**：
- 后端**有** `used_mock` 标记，并已透传到前端 `static/js/mods/11-pipeline.js:1282`
  （显示为 `模型：xxx（Mock 回落）`）
- ⚠️ 但**只在用户主动展开「执行详情」时可见**——**回答正文本身仍是 Mock 内容**，
  用户读到的是「当前为 Mock 降级模式（未配置真实 LLM API Key）」这种提示文本，
  看起来像一句正常的回复。

**这是比产出雷同更严重的问题**：雷同至少产出的是真代码，Mock 是**编造的内容**。

**建议决策（需米爸拍板）**：Mock 回落时是否应在**正文顶部**插一条醒目提示，
或直接以错误态返回而不是降级？当前设计是"宁可降级也不给空"，
但**降级内容必须让人一眼看出这是降级**。
