## 0. 结论先行

### 0.1 三句话判断

1. **文章的架构是对的，本仓的「设计」大多也到位——短板几乎全在「接线」。**
   本仓有 170 行零调用的 Agent 打分器、93 行自述"无生产调用点"的 `LLMRouter`、39/41 条存了真值却被丢弃的工具 `input_schema`、4 行 enabled 的 `tool_hooks`、6 级 HITL 门控链。这不是"没设计"，是**"建了没用"**。

2. **最致命的一类问题不是缺功能，是「假绿」——系统把失败记录成成功。**
   三条独立证据链指向同一结论：`normalize_text()` 把所有子任务协议状态恒写成 `full`（实测 180/180）；`claim()` 零调用点导致 `running` 态从未落库（库内 0 行）；`agent_tasks` 有 54 个 `failed` 却在交付协议层完全不可见。**这三者叠加，意味着"编排成功"这个信号在数据上不可证伪。**

3. **本仓最值得向文章学习的三件事，恰好都是文章强调而本仓明确反对的**：① 不要把模型内部推理当进度展示（本仓 `reasoning` 事件把 CoT 透传前端）；② 交付前校验每一个交付物（本仓只校验 SysML 代码，`report`/`requirement`/`doc` 三类零校验）；③ 冲突必须可见可阻断（本仓无多 Agent 结论冲突检测，且**质量评审 32 天只跑了 1 次**）。

# 第一部分：文章的系统分析

## 1.1 文章主张的架构骨架

文章把企业级多 Agent 拆成**五阶段执行链路** + **三大边界分离** + **五个工程要点**。

### 五阶段链路

```
① 需求输入与意图理解 → ② 任务分解与可用智能体查询 → ③ 策略优化与人工确认
                                              → ④ DAG 编排与调度执行 → ⑤ 结果交付
```

### 十个参与角色

用户、前端界面、人机协同接口、意图理解引擎、任务规划器、策略优化器、编排算法引擎、智能体注册中心、Dify 智能体、数据库。

### 三大边界分离（文章自称"整个系统最重要的三个问题"的答案）

| 边界 | 回答的问题 | 承担者 |
|---|---|---|
| 规划与执行分离 | 谁决定做什么 / 谁真正跑起来 | 规划器 vs 编排器 |
| 能力管理与任务调度分离 | 系统如何知道自己有哪些能力可用 | 注册中心 vs 编排器 |
| 模型推理与业务控制分离 | 模型该管什么、不该管什么 | 模型 vs 规划/编排/注册/权限 |

> 文章原话：「模型负责理解、推理和生成；规划模块负责组织任务；编排模块负责推动任务向前运行；注册中心负责管理可调用的能力；人机协同机制则让用户能够在关键节点介入。」

## 1.2 文章最值得学习的九条设计判断

我把文章里**可操作、有取舍、且被作者自己用"踩坑提示"标注过**的判断抽出来，这是本次对标的靶子。

| # | 文章主张 | 出处 | 为什么值得学 |
|---|---|---|---|
| 1 | **意图澄清不是异常分支，是正常业务流程的一部分** | §02「它不是一个简单的异常处理分支」 | 很多实现把澄清当兜底，导致能用但不可靠 |
| 2 | **缺失信息要分级**：能按明确规则补全的自动处理；会显著改变业务结果的**不让模型随意猜测** | §02 原则句 | 直接对应"自动补全要显式展示口径" |
| 3 | **结构化输出 ≠ 需求已明确** | §02 踩坑提示 | 生成 JSON 不等于解决了待确认项 |
| 4 | **注册中心不应只是保存 Agent 名称的表**——要描述"能做什么、不能做什么、需要什么输入、输出能否被下游直接使用" | §03 | 这是"能力目录"与"名字清单"的本质区别 |
| 5 | **权限与必要条件不应仅作评分项，而应是硬性约束**；没权限的 Agent 即使更快更便宜也不该被选中 | §04 | 打分器设计的第一原则 |
| 6 | **用户确认方案 ≠ 后端权限检查已通过** | §04 踩坑提示 | HITL 与 RBAC 是两道闸，不可互相替代 |
| 7 | **DAG 只解决依赖，不是完整运行时**；失败/取消/重规划/人工审批/外部变化都需其他机制 | §05 | 反对"画了 DAG 就等于有了编排" |
| 8 | **"一次调用没有收到成功响应，不等于业务操作一定没有成功"**——副作用任务重试前必须判幂等 | §06 | 重试设计的地基 |
| 9 | **不要把模型内部推理当成进度展示**；用户关心的是"执行到哪、哪些已完成、是否要你决定" | §07 | 这条本仓明确违反 |

## 1.3 文章的工程五要点与其自陈的失败模式

文章最后给出五个落地要点，并附了四类"踩坑提示"，这些踩坑恰好是本仓现状的高频命中项：

| 文章要点 | 文章自陈的踩坑 | 本仓是否命中 |
|---|---|---|
| ① 统一任务状态模型 | 「已成功完成的任务不能被普通重试逻辑重新启动」「被取消的任务不能继续无限派生」 | 🔴 命中（无迁移表、`canceled` 是死分支） |
| ② 统一执行契约 | 「如果每个 Agent 都有自己的输入格式、编排器就会越来越复杂」 | 🔴 命中（契约列有真值但零消费） |
| ③ 完整运行轨迹 | 「这次为什么得出这个结果」「为什么这次慢了三倍」「哪个 Agent 返回了错误数据」 | 🔴 命中（三个问题当前两个答不了） |
| ④ 权限检查放到真正执行的位置 | 「模型给出的参数也不能直接视为可信输入」 | 🔴 命中（参数零 Schema 校验） |
| ⑤ 从小规模工作流开始 | 「每增加一个 Agent 都带来额外调用成本、延迟、失败概率」 | 🔴 命中（15 Agent + 15 技能零调用） |

## 环节一：意图识别与理解

### 1.1 现状（实测）

**架构**：`agent/intent.py`（1087 行）三层路由，`INTENTS` 常量已于 P1-16 彻底删除，`agents.intent_keywords` 成为唯一真源。

| 层 | 实现 | 落点 |
|---|---|---|
| 关键词/规则层 | `intent_rules` 表 + DB 关键词 + 竞争打分 | `intent.py:204-227, 491-564` |
| 语义层 | `semantic.py::SemanticSearch`（dense↔bigram 双路） | `intent.py:853-861` |
| LLM 兜底 | `detect_llm`（**只喂意图名，无描述/边界**） | `intent.py:763-785` |

**统一出口** `_done()`（`intent.py:728-733`）产出 7 字段 dict：`intent / route / confidence / needs_clarification / sem_alt / used_history / confirmed`。

### 1.2 三个关键缺口

#### 缺口 1：决策依据不入库 ⇒ "为什么选它"事后不可复盘

`_last_meta` 只活在 `IntentRouter` 实例内存（`intent.py:182, 274-276`）。落库时严重降维：

```
conversations.current_intent   ← 只有意图名一个标量
conversations.last_slots       ← JSON
```

`route` / `confidence` / `needs_clarification` / `sem_alt` **全部不入库**。前端能看到的只有 `stream.py:1444-1446` 实时推的 `stage` 事件，刷新即丢。

> ⚠️ 附带缺陷：缓存命中路径（`intent.py:459-460`）硬编码 `needs_clarification: False` 且缺 `sem_alt`/`used_history`/`confirmed` 三键 ⇒ 该路径的 meta 是 5 字段的**异构子集**。

#### 缺口 2：槽位抽取 95.6% 空转，且失败不可区分

只读实测（2026-10-12）：`conversations.last_slots` 非空 **315** 个会话，其中解析出非空 dict 的仅 **14** 个 = **4.4%**。

根因是 `agent/pipeline_parts/prompt.py:47-48, 54-55` 的三条**静默降级**返回 `{}`：

```python
prompt.py:47-48   if not isinstance(parsed, dict): return {}      # 类型不对 → 空
prompt.py:54-55   except Exception: return {}                       # 解析失败 → 空
```

**上层完全无法区分"LLM 判定任务不可拆解"与"LLM 调用失败"** —— 这正是 4.4% 这个数字无法被解释、也无法被改善的原因。

#### 缺口 3：结构化止步于提示词，且不喂规划器

| 文章要求 | 本仓现状 | 证据 |
|---|---|---|
| 语义分析 / 实体抽取 / 意图分类**各自带结构化结果** | 三者压成一枚标量意图名 + 扁平 7 键 dict | `intent.py:728-733` |
| 实体喂回规划器 | slots **只喂生成侧 prompt + 检索 query**，编排/planner 明确不消费 | `session.py:118-119` 自述 |
| 显式声明必填/可默认槽位 | **全仓零命中** `required_slots`/`slot_schema` | 穷举搜索 |
| 「补全后显式展示口径」 | **该机制完全不存在** | `pipeline_parts/` 内"口径"命中全是代码注释术语 |

**死代码**：`intent.py:1038-1066` 的 `suggest_slots()`（对 3 个意图各返回 1 个建议槽位）**全仓零调用点** —— "缺失槽位提示"能力实现了但从未接线。

### 1.3 实测数据（今日口径）

**意图路由评测**（`tests/manual_verify/eval_intent_routing.py`，样本池 44 条 confirmed，2026-10-12）：

```

```

1. 不可与 2026-09-30 基线 0.9773 直接相减 —— **两次样本集不同**（池已从 29 长到 44）。

3. 3 个错例中，2 个（`llm_weak` / `llm_conflict`）在线上会被 `_should_confirm_intent` 拦下来问用户 ⇒ **评测里算错、线上会弹卡**。只有 1 个（「追溯矩阵检查一下」→ `rule_scored conf=0.95`）是**高置信规则误判且确认门不拦**，是唯一会静默走错的错例。
