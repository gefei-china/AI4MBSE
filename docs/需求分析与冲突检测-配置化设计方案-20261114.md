> 约束（米爸）：**通过 Agent / Skill / 工具 / 知识库配置实现，不写死代码规则**。
> 本文为设计评估稿，**未改产品代码**。所有结论均由独立查库 / 读码复核，证据见文末附录；
> 凡关键数字均可用文末 SQL/路径复算。待米爸拍板后再进入实施。

## 0. 结论先行

**方向成立，但「完全零代码」不成立**。平台已有大部分载体，且**规则与标准确实可以完全不是代码**；
真正的缺口是 5 处**不含业务规则的通用胶水**（§9，合计约 110 行）。

| 问题 | 结论 |
|---|---|
| 规则能否不写成代码 | ✅ **能**。`INCOSE Guide` 自带 **R01–R42（实测识别 37 个编号）**、**C1–C15（15 个特性）**；写成 Skill 正文 + 知识库条款即可 |
| 标准能否切换 | ⚠️ **部分能**。`agents.kb_scope.docs` 是 **Agent 级**文档白名单（已生效），`requirement_structuring` 已绑 Guide + 广汽方法论；但**没有项目/会话级标准档案绑定**，且 29148 未被任何 Agent 绑定 ⇒ 需胶水 ④ |
| 冲突检测能否不写比对算法 | ✅ **能，且已有现成确定性检测**：`subtask_protocol.detect_conflicts` 已接入 `RefineGate`。但它是**字面判据**，语义级冲突需 Skill 驱动 LLM 补第二层 |
| 结果能否结构化展示而不建专用表 | ✅ **能，前端零改动**：`quality_report.issues[]` 与 `card_data.conflicts` 两条现成通道；`relmap.REL_ALLOWED` 已含 CONFLICTS |
| 完全零代码 | ❌ 需 5 处胶水（§9），但**没有一处包含业务规则** |

⚠️ **四个必须先纠正的认知**（我第一轮推断错过、已用源码证伪）：
1. `detect_conflicts` 源码原话「**别把它当语义冲突检测用**」：只看 `claims[].subject`、只报
   取值/极性互斥，同义词认不出，宁可漏不错报 ⇒ 只能当**第一层筛查**，语义级必须第二层。
2. `kb_scope.docs` 白名单**只在每轮主检索生效**；模型显式调 `graph_retrieve` 工具时
   `self.rag.retrieve(q)` 只传 query，白名单失效。且它是 **Agent 级**配置，不是项目级。
3. **「生成前必须检索」是 prompt 级软约束，不是机制**：`agent/registry.py` 的 design Agent
   `system_prompt` 里写了「未检索不得产码」，但 `skills` 表无 `must_retrieve` 字段、运行时
   不校验、不阻断，且只约束「调没调工具」不约束「检索范围」⇒ 规格验收时不能声称"强制按标准"。
4. **平台已有 4 条同名 `detect_conflicts`，别混为一谈**：`subtask_protocol`（子任务结论互斥，
   唯一接入编排）、`entity_resolver`（知识融合属性矛盾）、`memory_service`（记忆互斥词）、
   `branch_repo`（分支合并代码冲突）。只有第一条可被需求冲突检测复用。

📌 证据来源说明（如实标注）：本文**所有关键事实均由我独立读码 + 只读查库复核**，
文中标注的文件路径与行号都是实际打开过的代码、数字都可用文末 SQL 复算。
三路并行只读调研仅作线索核对，其中「Agent/Skill/工具配置化」一路因模型服务 500
中断（2m20s 未产出），另两路的部分结论与我的复核一致但**未作为独立证据采信**。

⚠️ 因此本文不存在「仅凭调研转述、未经复核」的关键事实；但实施前仍建议对 §9 五处胶水
各跑一次真机复验（本仓既有纪律：单元/静态自证不等于端到端生效）。

## 1. 设计原则

| 原则 | 含义 | 本方案禁止 |
|---|---|---|
| **标准即知识资产** | 标准文档上传知识库、按条款切片；结论带 `clause_ref` | 把 29148 条款写成 `if/else` |
| **规则集即 Skill** | 规则清单、判定 SOP、输出契约写 Skill `content`/`frontmatter`，可编辑可版本化 | 新建规则常量表 + 规则引擎 |
| **检测动作即 Agent** | 角色/职责/输出契约写 `agents.system_prompt`，编排串流水线 | 新增 `conflict_detector.py` 算法模块 |
| **工具只做通用原子能力** | 复用 `graph_retrieve` / `requirement_itemize` / `skill_body_fetch` | 为需求校验写专用工具 |
| **结果走既有协议** | 三数组 + `SUMMARY_SCHEMA` + 现有富卡片 | 新建专用结果表 + 专用渲染组件 |
| **人工确认是策略数据** | `hil_policies` 配一行即生效 | 代码里写 `if need_confirm` |
| **"未检出"≠"无冲突"** | 复用 `conflict_stats.anchored`，为 0 时禁止声称已检查 | 把空列表当通过 |

## 3. 目标架构（四层）

```
L0 知识资产  ┌ 标准文档（29148:2018 / IEEE830 / 汇川 / INCOSE Guide）
            └ 按条款切片，section 参与 BM25；tag: standard_id · clause_id · rule_category
                      │ 上传即生效，零代码
L1 配置层    ┌ Skill：规则集 SOP（规则清单 + 条款出处 + 判定流程 + 输出契约）
            ├ Agent：4 个角色 + kb_scope.docs 文档白名单
            ├ 工具白名单：graph_retrieve / requirement_itemize / skill_body_fetch
            ├ 意图与 triggers：路由
            └ 标准档案：project_methodology + generate_rules（已有表）
                      │ 全部是 DB/快照数据
L2 运行时    意图路由 → 编排拆任务 → Skill 注入 → 定向检索标准条款
            → LLM 按规则逐条判定（结论带 clause_ref/evidence）→ 结构化输出
            → 确定性层 detect_conflicts 兜底最刺眼矛盾
                      │ 复用现有管线，零业务规则代码
L3 结果层    subtask_protocol → card_data / quality_report → 现有卡片（前端零改动）
            → HIL 策略抽检 → 可选写回 relations(CONFLICTS) 作为知识资产
```

## 5. 端到端链路

### 5.1 需求分析与条目化
输入 → 意图路由 `requirement_analysis` → 注入 C2 Skill → `graph_retrieve` 检索当前标准档案条款
→ LLM 按标准生成条目化需求 → `requirement_itemize` 落 `requirement_items`（已有）。

> 与现状差别：判据来自**检索到的条款**，不是 `requirement_itemize_tools.py` 里的固定正则。
> 现有正则保留为兜底/规范化，**不再作为规则来源**。

### 5.2 规则校验（规格 A）
`requirement_rule_check` Agent 逐条需求 → 按 C2 的 ≥10 类规则判定 →
每条输出 `{req_id, rule_id, category, verdict, severity, evidence, clause_ref, suggestion}`。

规则类别示例（从 Guide 的 R 规则 + 29148 条款归类，**写在 Skill 里可编辑**）：
编写模板 / 句式规范 / 唯一标识 / 原子性 / 无歧义词 / 可量化验收 / 可验证性 /
必要性与来源 / 无设计约束 / 无复合条件 / 术语一致 / 可追溯 / 需求集一致性 / 无冗余。

### 5.3 完整性检查（规格 B）
`requirement_completeness_check` Agent 按 C3 的 ≥5 类验证类别 →
每类输出 `{category, covered, missing[], evidence, clause_ref}`。

### 5.4 冲突检测（**两层，不写比对算法**）

| 层 | 实现 | 覆盖 | 责任 |
|---|---|---|---|
| **第一层：确定性筛查（零新算法）** | 把需求条目映射为 `claims[]`（`subject`=主体/指标名）→ 直接调**现成** `subtask_protocol.detect_conflicts` + `conflict_stats` | C1 同锚点不同值 / C2 数值互斥 / C3 枚举互斥 / C4 极性相反 | 兜住"最刺眼的一类矛盾"，可复现、可指出哪两条差在哪 |
| **第二层：语义判定（配置化 LLM）** | `Requirement_Conflict_Analysis` Skill 的 5 类枚举（语义冲突/重复/覆盖重叠/指标矛盾/术语不一致）+ `graph_retrieve` 召回候选 → LLM 推理 | 同义改写、隐含矛盾、范围交叠 | 覆盖确定性层"宁可漏"的部分 |

**两条纪律**：
- 第一层返回 `[]` 时**必须同时读 `conflict_stats.anchored`**；为 0 只能报「**未判定**」，
  不得写「已检查无冲突」（本仓反复栽过的假绿，源码 `conflict_stats` docstring 明确要求）。
- 两层结果合并去重后统一输出 `{conflict_id, type, req_ids[], severity, description, evidence, clause_ref, suggestion}`。

> 全程无 `for i in items: for j in items` 式新算法；判定力来自 Skill SOP + 标准条款 + 已有确定性函数。

### 5.5 结构化展示（**前端零改动**）

| 通道 | 后端动作 | 前端 |
|---|---|---|
| `quality_report.issues[]` | 把校验/冲突结论组装成 `{problem,severity,evidence,suggestion}` + `stats` | `13-reports.js:713-727` 已有折叠块，直接渲染 |
| `card_data.conflicts` | 把冲突清单写进 `card_data` | `06-cards.js:346-353` → `cardCandidates` 已有冲突徽章 |

⚠️ 后者当前有「空态抑制」（candidates/conflicts 都空时不渲染）——**正好符合预期**：有数据才显示。

## 8. 可判定性保障（把「LLM 判定」变可信）

| 风险 | 缓解 |
|---|---|
| LLM 自由发挥、不可复现 | 输出 JSON 契约写死在 Skill；`subtask_protocol.validate` 校验结构；不合格按 `normalize_text` 降级留痕 |
| 结论无依据 | 每条必须带 `clause_ref`（条款号）+ `evidence`（需求原文片段）；无出处判 `to_verify` 而非 `fact` |
| 规则类别漏检 | Skill 给「逐类过一遍」清单；结果自检 `covered_categories == configured_categories` |
| **空结果假绿** | `conflict_stats.anchored==0` ⇒ 报「未判定」；`detect_conflicts` 返回空不许写成「无冲突」 |
| 冲突误报 | 两层分级 + 高风险走 `hil_policies` 人工确认（本轮已修好三载体确认卡） |
| 检索召回不准 | `kb_scope.docs` 圈文档 + query 带章节锚点；`citations` 强制标来源；低置信显式标「依据不足」 |
| 标准版本漂移 | 标准档案锁定文档 id，不随新上传自动切换 |

### 13.1 `agents.output_schema` 从未进过提示词（P0，已修）

| 事实 | 证据 |
|---|---|
| 三个 Agent 的 `system_prompt` 写着「输出必须是结构化 JSON（见 output_schema）」 | DB 原文 |
| `output_schema` 列**只被** `registry`（存 `_db_meta`）与 `studio`（保存接口）读 | 全仓 grep |
| 提示词装配侧一次都没读过 ⇒ 模型看不到 schema，字段名靠猜 | prompt.py 无消费点 |

后果：模型把规则编号写进 `category`（"RC-01 编写模板与句式规范"）、
把类别自报字段整个省掉 ⇒ ① 前端 issue 标题退化成 `[-] 需复核`；
② 「类别是否覆盖齐」恒判未覆盖 ⇒ `verdict` 恒 `insufficient`。

**修法（纯通用胶水，不含业务规则）**：
- `agent/definition.py`：`AgentDefinition` 增 `output_schema` 字段；
- `agent/registry.py`：DB 值 `_parse_json_obj` 后置入定义对象；
- `agent/pipeline_parts/prompt.py::_build_output_contract()`：非空则注入「输出契约」块；
- `agent/pipeline_parts/common.py`：登记块 key `output_contract`（静态区，可缓存）；
- 空 schema ⇒ 返回 `""`，其余 30+ Agent 的 prompt **逐字节不变**。

真机取证：`context_audit` 中本轮 `output_contract` 块 **tok=258 / chars=466** 确实存在。

### 13.2 覆盖口径依赖模型自报 ⇒ 恒判"未覆盖"（已修）

初版只认 `parsed["covered_categories"]`，而该字段在 schema 里可选：
真机 P1 模型逐条给出 **28~30 条 checks**（RC-01…RC-09 都在），却因没写自报字段被判

### 13.6 「双层冲突」的确定性层是**死代码**（P0，已修）

设计写的是"确定性筛查 + 语义判定双层合并"，真机却发现：

| 事实 | 证据 |
|---|---|
| `run_deterministic_conflicts()` 在 `agent/`、`services/` 中**零调用点** | 全仓 grep 只有单测在调 |
| `assemble_result(deterministic=...)` 的真机调用点一个都没有 | `execute.py` 只传 `retrieval` / `required` / `configured` |
| 症状 | `deterministic_verdict` 恒 `None`、`conflict_stats` 恒空 ⇒ 只有模型语义一层 |

**修法（仍在胶水层，不写比对算法）**：`assemble_result` 在调用方未显式传
`deterministic` 时，若模型回传了 `items`/`requirements`（需求条目），就地跑一次
**现成**的 `subtask_protocol.detect_conflicts`；双层结果按 `(type, req_ids)` 去重合并，
确定性层置前并标 `layer="deterministic"`。同时在冲突 Agent 的 `output_schema` 里
补 `items[].{req_id,text,subject,ambiguous}`（配置侧），让条目可被锚定。

**语义收紧**：确定性层 `anchored==0` 时自身恒为 `undetermined` ——
不因语义层另外检出冲突就把它标成 `checked`（那是把"没查"说成"查过"）。

真机复验：`conflicts=7`（双层合并）、`conflict_stats={"claims_total":8,"claims_anchored":8,"subjects":2}`、
`deterministic_verdict=checked`。

### 13.7 模型把两段 JSON **直接拼接**输出 ⇒ 结构化结果整个丢失（P0，已修）

真机原文（conv 999999010）：

```
{"conflicts":[…]}                       ← 第一段完整
{"items":[…],"layer":"…","anchored":3,"verdict":"checked"}   ← 第二段直接接上
```

`json.loads` 报 `Extra data: line 3 column 1 (char 2907)`；
而兜底正则 `\{[\s\S]*\}` 是**贪婪**的（从第一个 `{` 吞到最后一个 `}`）⇒ 拼出来仍非法
⇒ 判"解析失败" ⇒ `card_data.requirement_check_result` 为空、`verdict` 被降成 `insufficient`。
**这不是模型没给结果，是解析器容错不够。**

**修法**：`parse_result_json` 增加"逐段解码并合并"（`JSONDecoder.raw_decode` 循环，
列表键拼接、标量键先到先得），并在真机原文上回归（B28 锁住"不过度容错改坏单段结构"）。
