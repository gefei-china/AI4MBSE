# Agent 角色位：把散在 4 处代码里的阶段清单收敛成表字段

> 日期：2026-11-04
> 上游：`docs/编排流水线与多方案权衡-标杆实现对标-20261103.md` §7 第 2 条
> 目标：**新增一个阶段 Agent 不再改代码**。

---

## 0. 一句话

同一份「哪些 Agent 属于哪个阶段集合」写在 **4 个文件**里；现在收敛到 **`agents` 表 2 个新列 + 1 个既有列 + 1 个缓存读取器**，
四处改为读它。**新增阶段 = 改数据，不改代码。**

---

## 1. 收敛前的实况（4 处硬编码）

| 位置 | 常量 | 数量 | 语义 | 漏改后果 |
|---|---|---|---|---|
| `session.py:70` | `_STANDARD_INTENT_LABELS` | 18 | 可落库为 `conversations.intent` 的标签 | 意图被规范化成 `chat`（**静默丢信息**） |
| `stream.py:64` | `_CODE_STAGE_INTENTS` | 6 | 产码阶段（流程名「生成与校验」/「生成汇总」） | 产码阶段不产码，界面显示成"汇总" |
| `intent.py:1350` | 粒度规则提示词里的阶段名 | 8 | 意图分类器要知道"哪些是建模阶段" | 该阶段**永远无法被路由命中**，且无报错 |
| `skills.py:377` + `registry.py:16` | `_ORCH_AGENTS` / `_FALLBACK_ORCH_AGENTS` | 6 | 无团队模式时的默认编排池 | 该 Agent 在自动编排下**永远不被派单** |

> 顺带查出的既有缺陷：`_CODE_STAGE_INTENTS` 里 **2 个是幽灵名**
> ——`multi_design`、`sysml_view_generation` 在 `agents` 表**根本不存在**（实测 0 行）。
> 即"产码判定"一直依赖两个不存在的 Agent。

## 2. 收敛方案（能推导的不加列）

| 集合 | 来源 | 为什么 |
|---|---|---|
| **建模阶段意图**（8） | **`agents.stage_order IS NOT NULL`** | 该列 2026-10 已由 `tools/migrate_v5_pipeline_nodes.py` 建好并填了 8 个阶段，**无需新增**。顺序即值 |
| **标准意图标签**（17） | `builtin=1` **或** `stage_order IS NOT NULL` | 两者都代表"这是一个意图标识"。**排除非内置主 Agent**（如 `智源对接agent`）—— 那是执行主体，不是意图 |
| **产码阶段**（4） | **新增 `agents.is_code_stage`** | **不能**用"绑了 `sysml_v2_validate`"推导：实测 `design` 靠正文输出 ```sysml 代码块产码、**未绑任何 sysml 工具**；而 `review`/`多方案生成` 绑了 validate 却**不是**产码阶段 |
| **默认编排池**（6） | **新增 `agents.is_orch_default`** | **不能**用 `builtin=1 AND role='sub'` 推导：会多出 `chat`（兜底问答，不该被派子任务）与 `requirement_quality`，**改变既有编排行为** |

### 为什么不用 `generate_rules` 存 JSON 数组

上一批（计划语义校验）曾把阶段序灌成 `pipeline_stage_order` 的 JSON 数组 —— **那是错的**：
JSON 里存的是 Agent **名字字符串**，Agent 改名后数组静默失效。
**列挂在 Agent 行上，改名自动跟随。** 该 JSON 规则已在本次清理（只在需要临时覆盖时保留）。

## 5. 实施中修掉的两个"判据盯错对象"（真实缺陷）

### 5.1 测试读的库与应用读的库**不是同一个**

`test_standard_labels_cover_db_builtin_intents` 原来用 `os.path.join(ROOT, "mbse.db")` 读**生产库**，
而应用运行时 `core.config.DB_PATH` 在 pytest 下指向 **`tests/_test_mbse.db`**。

⇒ **两个库在互相比对**：生产库新增的 Agent 被报成"目录缺失"（假失败），真正的漂移反而检不出来。

修：判据一律以 `core.config.DB_PATH` 为准。**判据与被测对象必须同源。**

### 5.2 判据打在**兜底常量**上，而不是生效集合上

原断言检查 `SessionMixin._STANDARD_INTENT_LABELS`（现在只是兜底镜像），
所以库里新增内置意图时它报错、但**线上行为其实正确** —— 典型的盯错对象。

修：主判据改为 **`core.agent_catalog.standard_intents()`（生效集合）**，
兜底常量只保留"非空 + 含核心意图"的弱断言。

## 6. 使用方式（都不改代码）

| 想做的事 | 怎么做 |
|---|---|
| 新增一个阶段 Agent | 建 Agent 时填 `stage_order`（0,1,2…）⇒ 自动进入阶段意图与标准意图 |
| 让某 Agent 参与默认编排 | 勾 `is_orch_default` |
| 标记某 Agent 为产码阶段 | 勾 `is_code_stage` |
| 改阶段先后 | 改各 Agent 的 `stage_order` 值（**不要**改代码里的 `DEFAULT_STAGE_ORDER`） |
| 立刻生效 | 调 `core.agent_catalog.invalidate()`；不调则最迟 60s（TTL） |

## 7. 边界

1. **`agents.stage_order` 的语义是"顺序"不是"一定要走"**：值为空 = 不是阶段。
   `change_safety_gate`（6）是**闸门**不是顺序阶段，但它在表里，因此也参与阶段序判定 —— 这是正确的（闸门在发布之前）。
2. **兜底常量保留**：DB 不可读时仍要能用（新库未迁移、连接失败）。这是**唯一**硬编码，且自检盯着它不得含幽灵名。
3. **未做**：管理端 UI 的勾选框（当前只能改库/调 API）；阶段清单的"分组"概念（如"方法层/需求层/架构层"）。
