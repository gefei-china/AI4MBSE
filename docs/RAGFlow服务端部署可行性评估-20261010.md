# L3 · RAGFlow 服务端部署可行性评估

> 结论（2026-10-10 实测）：**本机当前无法启用 L3**。适配层已就绪并默认关闭，
> 启用需要 Docker + 4 个硬依赖服务，与铁律 4（私有化离线、零外部依赖）冲突。
> 本文给出**实测证据**与**四条可选路径**，供决策。

---

## 1. 实测证据（不是文档摘抄）

### 1.1 本机 Docker 不可用

| 检查项 | 结果 |
|---|---|
| `docker --version` | **command not found** |
| `docker compose version` | command not found |
| `/c/Program Files/Docker/Docker/resources/bin/docker.exe` | 不存在 |
| `/c/ProgramData/DockerDesktop/version-bin/docker.exe` | 不存在 |
| podman / nerdctl | 均无 |
| WSL | **存在**（可作为 Docker Desktop 后端） |

⇒ 本机**从未安装 Docker Desktop**，不是 PATH 问题。

### 1.2 compose 要起的服务（`docker/docker-compose-base.yml`，539 行）

实测 grep 到的镜像清单：

| 服务 | 镜像 | 是否必需 |
|---|---|---|
| elasticsearch | `elasticsearch:${STACK_VERSION}` | ★ 必需（文档存储） |
| **infinity** | `infiniflow/infinity:v0.7.4-x64-v3` | ★ 必需（Go 版默认文档库） |
| mysql | `mysql:8.0.40` | ★ 必需（元数据） |
| minio | `pgsty/silo:RELEASE.2026-08-06...` | ★ 必需（对象存储） |
| kvrocks | `apache/kvrocks:2.16.0` | 可选（Redis 替代） |
| tei-cpu / tei-gpu | TEI_IMAGE_CPU/GPU | 可选（本地嵌入） |
| opensearch / oceanbase / serenedb / seekdb / vastbase | 各家数据库 | **互斥备选**（compose 里 profile 区分） |
| jaeger / nats / kibana / clickhouse | 观测/分析 | 可选 |

⇒ **最低集是 4 个：infinity + mysql + minio + (kvrocks)**，
外加 RAGFlow 主服务（`profile: cpu`）。

### 1.3 ★ Go 版支持 Redis 降级，但**存储层不支持**

这是本轮最有价值的发现——`cmd/ragflow_server.go`（1737 行）里有明确注释：

> `degraded boot, stand-alone mode, no-redis CI`（L1215-1216）
> `agent: redis client not initialised; agent run infra in in-memory mode`（L1519）

⇒ **Redis/kvrocks 缺失可降级为内存模式**。
但 `internal/dao/database.go` + `docker/service_conf.yaml.template` 显示
**文档库与元数据库没有 SQLite 降级路径**（`glebarez/sqlite` 只在 `_test.go` 里出现）。

⇒ **结论：无法用"单体二进制 + SQLite"绕过 Docker。**

## 2. 与铁律 4 的冲突点

`AGENTS.md` 铁律 4：**私有化离线部署、零外部依赖、零构建链**。

| 冲突项 | 说明 |
|---|---|
| Docker Desktop | 系统级软件，需管理员权限 + 重启；本机未安装 |
| MySQL / Infinity / MinIO | 3 个常驻服务，离线镜像需预下载数百 MB~GB |
| 首次构建 | `Dockerfile_base` 需 `NEED_MIRROR=1` + Gitee token 拉模型 |
| 资源占用 | 官方要求 4 核 / 16GB / 50GB 磁盘；ES 需 `vm.max_map_count ≥ 262144` |

## 3. 四条可选路径

### 路径 A · 装 Docker Desktop + 起 RAGFlow（完整能力）

| 项 | 值 |
|---|---|
| 步骤 | ① 装 Docker Desktop（需你手动，我无权装系统软件）② 拉/导入离线镜像 ③ 起 4+1 服务 ④ 生成 API Key ⑤ 填 `rag.ragflow_base_url` / `ragflow_api_key` 并开 `ragflow_enabled` |
| 风险 | 破铁律 4；资源占用高；离线镜像获取需外网 |
| 回退 | 把 `ragflow_enabled` 置 false ⇒ 适配层立刻回落本地（**已有门禁保证**） |

⚠️ **我需要你确认两件事才动手**：
1. 是否允许安装 Docker Desktop（系统级、需重启）
2. 是否有外网/内网镜像源可拉取镜像

### 路径 B · 只借算法，不部署（**已完成的 L1/L2 就是这条路**）

L1（标题路径增强问句）已落地，`ragflow qa.go:216` 的算法已本地实现。
若接受"拿到算法不拿服务"，**当前状态即已完成**，无需再动。

### 路径 C · 自建轻量"切片服务"（保留 SDK 契约，不带 RAGFlow）

思路：只用 `ragflow_sdk` 的**接口契约**，在工程内实现一个
`POST /datasets/{id}/documents` + `POST /retrieval` 的最小服务
（复用现有 `knowledge_pipeline/chunking.py` + `chunking_deepdoc.py`）。

| 项 | 值 |
|---|---|
| 优点 | 不破铁律；SDK 侧代码零改动；切片逻辑仍在工程内可控 |
| 缺点 | 需要维护 HTTP 层；本质还是自研（收益主要是"接口标准化"） |
| 工作量 | ~2 天 |

⚠️ **坦率说：这条路工程量不小而收益有限**，除非你有"未来要切 RAGFlow"的明确规划。

### 路径 D · 换轻量替代框架（LlamaIndex / Chroma 本地持久化）

| 项 | 值 |
|---|---|
| 思路 | 引入 `chromadb`（pip 即可、纯进程内、持久化到文件），替换现有 JSON+sqlite 向量存储 |
| 优点 | 不需要 Docker；比 RAGFlow 轻得多；直接解决 ANN 索引问题 |
| 缺点 | Chroma 不支持中文分词 BM25（需保留现有 BM25 链路） |
| 工作量 | ~3~4 天 |

## 4. 我的建议

**先不要装 Docker。** 理由：

1. **L2 已经把真瓶颈解决了**（399 倍，且 0 漂移）。
   上一轮实测显示"向量路线置信均值 0.15"是召回质量问题，
   而**换存储引擎不直接改善召回质量**。
2. **L1 已在本地拿到 ragflow 的核心算法**（标题栈切片），
   这是 ragflow 在"切片"维度最有价值的部分。
3. 装 Docker + 4 服务带来的运维成本，可能超过它能解决的收益。

**建议顺序**：
1. 先让 **L1/L2 在真实语料上跑一周**，看 `query_routing_stats` 里
   向量路线的置信均值是否从 0.15 提升 ⇒ **用数据决定是否还需要换引擎**
2. 若置信均值改善明显 ⇒ 现有栈够用，**不必引入任何新框架**
3. 若仍无改善 ⇒ 优先做 **路径 D（Chroma，纯 pip）**，
   而不是路径 A（Docker 全家桶）
