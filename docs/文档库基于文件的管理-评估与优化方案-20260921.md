## 2. 全局化（不按分支）落地清单 —— 补 §1.1 的漏项

§1.1 的方向与 4 处修法**都正确**，本节只做**补全**。以下 4 项均需与那 4 处同批处置（同一份自检 `tools/verify/verify_doc_global.py` 应加断言）。

### G1（P0，先修）检索链路完全没有 `lifecycle_status` 过滤

- **事实**：`document_chunks.lifecycle_status` 于迁移中建列（默认 `'stored'`），`MetaRepo.transition_lifecycle(chunk_sync=True)` 在废弃时把它置 `'deprecated'`，**注释写明的目的就是"避免向量层命中"**；
  但检索侧 5 处 chunks 查询（`bigram 兜底` / `vector_search_embed` / BM25 索引构建 / BM25 查询 / 列表）**一处都没读过它**。
- **判据**：`grep -rn "lifecycle_status" knowledge_pipeline/search.py knowledge_engine.py agent/rag.py repositories/knowledge_repo.py` → **0 命中**；
  对照实体侧：`agent/rag.py` 内 `status != 'deprecated'` **9 处**。
- **影响**：**已废弃文档仍会被 AI 建模 RAG 召回**；回收站/版本链的任何"不可见"设计都建立在沙子上。
- **修法**：在 `_branch_clause` / `_doc_clause` / `_ai_clause` 同一层新增 `_lifecycle_clause()`，恒带
  `AND (lifecycle_status IS NULL OR lifecycle_status NOT IN ('deprecated'))`，一并作用于那 5 处。
  ⚠️ **只作用于 `document_chunks`**（与 `_branch_clause` 的边界注释同纪律），**不要**扩散到实体/关系查询上。
  ⚠️ 必须同时给检索层留"显式包含已废弃"的开关（回收站预览、管理侧统计要走它），否则会把管理需求一起挡掉。

### G2（P0，与 G1 同批）白名单解析不过滤生命周期

- **事实**：`agent/rag.py:181` `SELECT * FROM documents WHERE parse_status='completed'` —— 用于把 `kb_scope.docs`
  白名单与库内实际文档求交（KB-S 自愈）。
- **影响**：已 `deprecated` 的文档仍被判定为"白名单有效"→ **KB-S 自愈形同虚设**（自愈的语义是"剔除失效项"）。
- 同类点：`repositories/agent_repo.py:84` `SELECT 1 FROM documents WHERE filename=?`（保存侧预检）。

### G3（P0，**数据丢失风险**）`rollback_merge` 里有按分支删文档的语句

```python
# repositories/branch_repo.py:1167-1170 （rollback_merge 内）
self.execute("DELETE FROM documents WHERE branch=?", (tgt,))
self.execute("DELETE FROM document_chunks WHERE branch=?", (tgt,))
self.execute("DELETE FROM doc_metadata WHERE document_id IN "
             "(SELECT id FROM documents WHERE branch=?)", (tgt,))
self._restore_rows("documents", snapshot.get("documents", []))
```

- **当前为什么没出事**：全库 `documents.branch` 均为 `global` → `branch=?` 恒不命中 → **碰巧安全**。
- **为什么是定时炸弹**：① `documents.branch` 的 DDL 默认是 `'dev'`（F8）→ 只要有一条写入路径漏传 branch，
  库里就会出现非 global 行；② `_merge_commit` 抓的快照本身也是 `WHERE branch=?`（`:779-781`）→ **同源恒空**。
  → 于是"**删掉了、但快照里没有、所以不还原**"：**静默丢文档**，且 `doc_metadata` 已先被删。
- **修法**：与 `delete_branch` 同款护栏 —— `if tgt != "global":`；同时把 `_merge_commit` 里 documents/chunks/
  doc_metadata 三行快照**显式标注为死代码**（或删除），避免后人误以为"回滚能恢复文档"。

### G4（P1）`_merge_commit` 的发布快照仍在抓文档

`branch_repo.py:779-781` 把 `documents` / `document_chunks` / `doc_metadata` 按 `branch=?` 塞进
`prev_release_snapshot` —— 全局化后**恒为空数组**。与 `snapshot_documents`（已标注废弃）同族。
→ 处置：标注/移除，并在 `merge_requests.prev_release_snapshot` 的消费点（`rollback_merge`）写明"本快照不含文档"。

### G5（P1）`_migrate_docs_global` 的"同名去重"与版本链语义相反

- **事实**：`database/migrations/documents.py:118-150`
  - 幂等判据：`n_global > 0` 即 return（**只对存量库一次性生效**）；
  - 核心逻辑：`SELECT filename FROM documents GROUP BY filename HAVING COUNT(*)>1` → **保留 id 最小、删其余**
    （`DELETE FROM document_chunks` + `DELETE FROM doc_metadata` + `DELETE FROM documents`）。
- **冲突**：本迁移把"同名"定义为**重复、应当删除**；09-21 稿 §4 把"同目录同名"定义为**新版本、应当保留**。**语义相反。**
- **风险面**：`n_global == 0` 的库（全新部署 / 恢复后重跑）会执行去重；一旦那时库里已有版本链，**版本历史被物理删除**。
- **修法**：把 `HAVING COUNT(*)>1` 的去重限定为"**同 branch 的发布快照重复**"（这正是迁移 docstring 的本意：
  "存量 dev/release 同名发布快照合并去重"），并加 `branch != 'global'` 条件；同时在版本链设计（D3）落地时
  **显式声明该迁移与版本链不相容**，列入版本链的 P2 前置检查。

## 3. 设计缺陷与修正（8 项）

### D1 — `UNIQUE(name, parent_id)` 拦不住根级重名（**已实测复现**）

两份稿都写了 `UNIQUE(parent_id, name)` / `UNIQUE(name, parent_id)`。**SQLite 的 UNIQUE 把 NULL 视为互不相等**，
`parent_id IS NULL` 是根级，于是根级同名**不会被拦**。

隔离库实测（`:memory:`，非业务库）：

```
UNIQUE(parent_id, name)，parent_id 可 NULL：
  插入 (NULL,'规范') → OK
  再插入 (NULL,'规范') → 成功   ← 未被拦截，根级同名行数 = 2

对照 UNIQUE(parent_id, name)，parent_id NOT NULL DEFAULT 0（0=根）：
  插入 (0,'规范') → OK
  再插入 (0,'规范') → IntegrityError  ← 被拦住
```

**修正（二选一，推荐 B）**：

```sql
-- A. 哨兵写法：parent_id 用 0 表示根（放弃 NULL 语义）
parent_id INTEGER NOT NULL DEFAULT 0,

-- B. 表达式索引：保留 NULL 语义，用索引补上
CREATE UNIQUE INDEX IF NOT EXISTS ux_doc_folders_name_parent
    ON doc_folders(name, IFNULL(parent_id, 0));
```

**验收断言**：根级建两个同名目录，第二次必须失败（`sqlite3.IntegrityError`）；子级同理。

### D2 — 不要新增 `deleted_at`，回收站复用 `lifecycle_status`

- **现状**：`lifecycle_status` 6 态 + `deprecated_at/by/reason` + `archived_at/by` + `lifecycle_version`
  构成一个**完整的、带审计与并发校验（`from_status` 比对）的**状态机；`/deprecate`（`chunk_sync=True` 同步 chunks）、
  `/restore`、`/archive` 端点均已实现。
- **09-21 稿 §4**：`ALTER TABLE documents ADD COLUMN deleted_at TEXT DEFAULT ''` → **同一件事的第二根轴**。
  后果：① "已废弃"与"已删除"两套语义必然打架（`deprecated` 的文档能不能进回收站？）；
  ② 检索侧要判两次（而其中一次今天还没判，见 G1）；③ 前端 `docStateBadge` 要渲染两套状态。
- **修正**：
  - **回收站 = 已下线文档的视图**，底座是 `lifecycle_status='deprecated'`（进站时间=`deprecated_at`，出站=`/restore`）；
  - 若产品上确实要区分"**下线**（还可能在用，只是不再推荐）"与"**移入回收站**（打算删）"，就在 `lifecycle_status`
    里**加一个取值**（如 `trashed`）而不是加一列 —— **保持单轴**；
  - 物理清理（30 天）挂在 `deprecated_at` 上，与 09-21 稿 §7.5 一致。
- **联动收益**：修好 G1 之后，"回收站/旧版本不进检索"**自动成立**，不需要另写过滤。

### D3 — 版本链改为"新增行 + 链指针"，不要覆盖当前行

- **09-21 稿 §4 的做法**：同名上传 → 旧版数据快照进 `doc_versions` → **`documents` 行被新文件覆盖**
  （重新走完整 retry 管道）。
- **问题**：
  1. `retry_document` 会 `DELETE FROM document_chunks WHERE document_id=?` 再重建 → **chunk 主键全变**，
     而 `citations`（会话引用）与 `document_chunks` 的块号锚点指向的是"**文档 id + 块号**"；
  2. 旧版内容**被物理删除** → "回滚到 v2" 必须**重跑完整管道**（解析+分块+embedding+hyde，实测单份规范级文档
     **163.8 s** 起，见基线）→ 回滚变成分钟级且要重新花 embedding 钱；
  3. 与既有 `doc_metadata.superseded_by`（时效取代链，`services/artifact_ingest.py:184` 已会写）**功能重叠**，
     等于给同一件事造两套机制。
- **修正**：**每次上传新版本 = INSERT 一条新的 `documents` 行**，链关系用列表达：

```sql
ALTER TABLE documents ADD COLUMN version_no INTEGER DEFAULT 1;        -- 链内序号 1,2,3…
ALTER TABLE documents ADD COLUMN root_document_id INTEGER DEFAULT 0;  -- 链根 id（首版指向自身）
-- 链上的"当前版"由 lifecycle_status 表达：旧版置 'deprecated'（复用既有状态机，无需新列）
```

- **收益**：① 历史版**天然可下载、可预览、可审计**（行还在、chunks 还在、源副本还在）；
  ② "回滚到 v2" = 改两行的 `lifecycle_status`（**秒级、零 embedding**）；
  ③ **`doc_versions` 表不需要了**（D7 自动消解）；
  ④ 与 `superseded_by` 的语义统一（`superseded_by` 表示"被谁取代"，`root_document_id` 表示"同属哪条链"）。
- ⚠️ **前置依赖**：检索侧必须能只召回链头 → **依赖 G1**。这也说明 **G1 是版本链的硬前置**，不是可选优化。
- ⚠️ **与 D5 冲突**：落地版本链前必须先按 G5 改掉 `_migrate_docs_global` 的同名去重。

### 4.1 数据模型（修正版）

```sql

    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    name        TEXT NOT NULL,

-- 防御性第二道闸：即便有人把 parent_id 写成 NULL，也不允许同名

    ON doc_folders(name, IFNULL(parent_id, 0));
```
