## 问题 1 · 稳定方案：为什么"Fuseki 只做查询镜像"不是临时方案

### 1.1 实测：权威源耦合面小得出奇

`graph_db.py`（1020 行）共 **22 处 SQL**，其中：

| 类别 | 数量 | 换权威源要不要改 |
|---|---|---|
| **SPARQL**（图库查询：`SELECT ?s WHERE { GRAPH ?g …}`） | **18** | ❌ 不用改 |
| **SQLite**（`FROM triples` / `FROM entities` / `UPDATE triples`） | **4** | ★ 要改 |

**且 `graph_db.py` 对 `sqlite3` / `db_conn` / `get_db` 的引用 = 0 处** ——
它已经是纯图库层，不碰存储。

4 处 SQLite SQL 的归属：

| 位置 | 函数 | SQL |
|---|---|---|
| `graph_db.py:757-759` | `sync_pending_triples` | `SELECT t.* … FROM triples WHERE graph_stored=0 AND status='approved'` |
| `graph_db.py:792` | `sync_pending_triples` | `UPDATE triples SET graph_stored=1 WHERE triple_id IN (…)` |
| `graph_db.py:803-804` | `_pending_count` | `SELECT COUNT(*) FROM triples WHERE graph_stored=0 …` |
| `graph_db.py:1000-1001` | `fetch_entity` | `SELECT id, name, entity_type, status FROM entities WHERE id=?` |

### 1.2 为什么"换 SQLite 不用重调"是**结构性保证**，不是运气

三个已存在的设计（实测）：

1. **依赖注入**：`sync_pending_triples(conn, writer)` / `fetch_impact_network(writer, conn, …)`
   —— **conn 由调用方传入**，函数本身不知道数据在SQLite 还是 PG。
2. **两个调用点都带开关 + 降级**（`triple_store.py:210`、`agent/pipeline_parts/cards.py:657`）：
   ```python
   if config.as_bool("graph_db", "enabled"):
       try:  # 取图库 → 成功用图库，异常/空 ⇒ 回落 SQLite 全量
   ```
3. **后端切换只改配置**：`graph_db.backend` = `pyoxigraph | fuseki | neo4j`，
   `get_writer()` 工厂已备好 4 个实现（实测 `fuseki` 可用，`neo4j` 缺 driver 降级）。

⇒ **换权威源的工作量 = 改那 4 条 SQL + 提供一个 `conn` 等价物**。
图库侧 18 处 SPARQL **一行都不用动**。

> ★门禁自己抓出的第 4 处：`fetch_impact_network`（`graph_db.py:1029`）也读权威源，
> 做「属性回填」时按 entity id 回 SQLite 取名称/类型/状态（注释即写着"属性回填（SQLite 权威源）"）。
> 属**合理的读**，已列入 `verify_graph_mirror_contract.py` 的白名单并记账。
> —— 这正是门禁的价值：**它自己发现了我的文档里漏记的第 4 处**。

### 1.3 推荐架构（稳定、可长期演进）

```
业务层（agent / routers）
    ↓ 依赖仓储接口（唯一契约）
仓储实现 A（当前）: SQLite        ← 权威源：治理能力的唯一载体
仓储实现 B（将来）: PostgreSQL 等  ← 到时才做，只改 4 条 SQL
    ↓ 物化（sync_pending_triples，仅"已审核"）
图库镜像（可选）: pyoxigraph / Fuseki  ← ★ 只是可弃的查询加速缓存
```

**为什么图库只能是镜像、不能当权威源**（下一节给出硬理由）。

**镜像丢了不心疼**：实测真库 137 条三元组、图库 32 条，重建是**秒级**。
⇒ 用「可重建」换「无治理能力」，是明确的正向交易。

## 问题 2 · 移除双时态 / 审核流 / 版本对齐 / 画布坐标的后果

### 2.1 先澄清一件事：这些**不是 RAG 能力，是工程治理能力**

它们回答的问题与检索无关，而是：
- **这条知识什么时候有效？**（双时态）
- **谁批准它进入正式库？**（审核流）
- **它属于模型的哪个版本？**（版本对齐）
- **画布上放哪？**（坐标）

⇒ 任何 RAG 框架（含 RAGFlow）**都不会替你实现**，因为这不是它的职责范围。

### 2.2 实测：引用广度（`grep` 计数，排除 venv/tmp/测试）

| 字段 | 引用文件数 | 关键使用点 |
|---|---|---|
| `valid_from` / `valid_to` | **9 / 7** | `repositories/knowledge_repo.py:100,110`（时态过滤查询）、`ontology_semantics.py:689,695`（时态推理） |
| `review_status` / `review_decision` | **4 / 5** | 审核门禁、`triple_store.review_triple` |
| `reviewed_by` | **19** | 审核人追溯 |
| `sysml_version_id` | **15** | `graph_db.py`、`routers/graph_workspace.py`、`routers/knowledge_parts/*` |
| `is_current` | **13** | 当前版本判定 |
| `graph_x` / `graph_y` | 前端布局 | 画布视图 |

### 2.3 逐项移除的具体后果

| 移除 | 直接后果 | 业务后果 |
|---|---|---|
| **双时态** | `knowledge_repo` 的时态过滤 SQL 失效；`ontology_semantics` 的时态推理报错 | ★ **无法回答"这个需求在 V3 模型时是什么样"** —— 需求评审最核心的问题 |
| **审核流** | `status='approved'` 过滤失效 ⇒ **AI 抽取的推断直接进正式库** | 真库现存**107 条 `inferred` 待审三元组**；失去门禁后模型"编"的关系会被当事实用 |
| **版本对齐** | `sysml_version_id` 断链 ⇒ 需求与模型版本无法对应 | ★ **五元素追溯链（Need→Requirement→Function→Component→Verification）断裂** —— 这是 MBSE 产品的立身之本 |
| **画布坐标** | 布局信息丢失 | 画布视图每次打开**重新排布**，工程评审体验不可用 |

### 2.4 ★ 这些能力**已有门禁在守**，移除会直接判红

实测 `tools/verify/` 下有专门脚本：

- **`verify_entity_versions.py`** —— 判据分层 [0]~[5]，含
  "一次真实改属性 → 主表行数不变 + 该实体版本行 = 2 + **半开区间闭合**"
  与"**UNIQUE(id,branch,valid_from) 真的在拦**"，并含 3 个变异自证。
  ⇒ 移除双时态/版本表 ⇒ **这个门禁立刻红**。
- **`verify_trace_cols.py`** —— 守 trace→span 关联列。

⇒ 它们不是"备着没用的列"，而是**有断言、有变异自证的活门禁**。

## 结论与建议

1. **图库定位**：Fuseki / pyoxigraph 一律定位为**可重建的查询加速镜像**，不承载治理。
   权威源换库时，改动面 = **4 条 SQL**（实测），图库侧 18 处 SPARQL 零改动。
2. **不要移除治理字段**：它们是 MBSE 的追溯与质量门禁，有活门禁在守；
   移除会断掉五元素追溯链、并让 107 条待审推断失去拦截。
3. **可立即做的收口动作**（若要推进）：
   - 固化"图库=镜像"的定位注释（写进 `graph_db.py` 头部，避免后人误当权威源）
   - 补一条门禁：禁止把 `graph_stored` 语义改成"权威源标记"
   - 修真库那 **13 条 `type` 谓词但 `object_type=literal`** 的数据（否则 OWL 看不见类型）
