# 运行监控选型建议（v2：聚焦平台能力与会话级排查）

> 日期：2026-10-17（v2，同日修订）
> 范围变更：**明确不做 CPU/内存/主机等系统资源监控**（Prometheus/Grafana/Loki/Uptime Kuma 全部移出推荐）。
> 监控对象收敛为两件事：① 平台能力运行监控（意图/RAG/建模校验/工具/编排/LLM）；② 会话级运行数据下钻，支撑问题排查。

---

## 一、结论速览

1. **会话级排查的数据地基已经打好了**（P0-c 及后续整改），不需要引入任何新存储 —— `llm_usage_stats` 已带 `conversation_id / run_id / trace_id / sub_task_key` 四列关联键，`orch_checkpoints / agent_tasks / orch_stream_events / hil_confirmations` 均带 `conversation_id + run_id`。**缺的不是数据，是把分散在 6+ 张表的数据按会话聚合暴露的端点和下钻视图。**
2. 主线方案 = **自研增强**：新增「会话级监控端点 + 时间线下钻视图」+「平台能力监控总览」+ 补两处关联断点。数据都在 SQLite 本库，约 3 人日工作量。
3. 开源外挂只保留一个**可选项**：Arize Phoenix（单容器，定位是轨迹瀑布图 + 评测集，属平台能力监控范畴）。Langfuse 过重、Prometheus 栈范围外、Helicone 已停更，均不推荐。

## 二、会话级排查：现状盘点（数据层）

### 2.1 已经有的（能查到什么）

| 数据 | 表 | 会话关联 | 说明 |
|---|---|---|---|
| LLM 调用流水 | `llm_usage_stats` | ✅ conversation_id / run_id / trace_id / sub_task_key | tokens、成本、finish_reason（截断证据）、retry_count、fallback_used、缓存命中 —— P0-c 已把「孤立流水」变成可下钻的 span |
| 编排 run 检查点 | `orch_checkpoints` | ✅ run_id + conversation_id | phase、心跳 updated_at、attempt_count、原始输入/计划留痕 |
| 子任务执行 | `agent_tasks` | ✅ run_id | status / retry_count / metadata 逐行 commit |
| 编排事件流 | `orch_stream_events` | ✅ conversation_id + run_id | 实时事件 |
| HIL 确认队列 | `hil_confirmations` | ✅ conversation_id + run_id | 写操作拦截记录 |
| 旧编排节点 | `flow_runs` / `flow_run_steps` | ⚠️ **无 conversation_id** | 节点级 status/latency/content；monitor/logs 域目前查的就是它 |
| 告警 | `alert_events` | ❌ 无会话关联 | 按指标触发，不知道是哪个会话/请求引起的 |
| UX 埋点 | `routers/ux_metrics.py` | — | §11 六指标 |

### 2.2 排查路径的真实断点

1. **没有会话级聚合端点**：`/api/monitor/dashboard` 是全局聚合，`/api/monitor/logs` 是 run 级搜索。拿到一个「用户反馈 3 点会话出问题」的 conversation_id，要人工分别查 messages、orch_checkpoints、agent_tasks、llm_usage_stats、orch_stream_events 至少 5 张表 —— 排查一次问题跨 5 个工具。
2. **trace_id 只覆盖 LLM 调用**：工具执行、节点运行没有统一 span 口径，「这次 run 里 8 秒花在哪一步」要靠 flow_run_steps.latency_ms 和 llm_usage_stats.latency_ms 拼。
3. **告警与请求脱钩**：alert_events 没有 conversation_id/request_id，收到告警后无法一键跳到肇事会话。
4. **`flow_runs.conversation_id` 缺列**：如果旧编排仍在服务（monitor 域主数据源），会话级下钻在这里断链。

## 三、主线方案：自研增强（推荐，全部在本库内完成）

### 3.1 新增「会话级监控端点」（monitor 域内，1 个聚合端点 + 1 个列表端点）

```
GET /api/monitor/session/{conversation_id}
  → 会话概览: 意图/主Agent/phase/status + 时间范围
  → 编排 runs: orch_checkpoints(phase/attempt/心跳) + agent_tasks(status/retry)
  → LLM 调用: llm_usage_stats 按 trace_id 分组(含截断/重试/回退/成本)
  → 事件流: orch_stream_events 时间线
  → HIL 拦截: hil_confirmations
  → 错误画像: 全链路 error/截断/回退/超时 汇总 + 每段耗时占比（排查首屏直接给结论）

GET /api/monitor/sessions?status=&intent=&days=&q=
  → 会话级运行列表（最近出问题的会话排前：有 error/截断/回退/长耗时的加权排序）
```

纪律：口径收口进 monitor 域（参照 `metrics_core.py` 唯一真源原则），只读、不新写 SQL 到别的路由。

### 3.2 补两处关联断点（各半天）

1. `flow_runs` 加 `conversation_id` 列（`database/migrations/columns.py` 已有加列机制），写入点回填。
2. `alert_events` 加 `conversation_id / request_id` 两列，`core/alert_evaluator` 触发时带上当前上下文 → 告警可一键跳会话。

### 3.3 前端：会话时间线下钻视图（1 天）

- 入口：监控面板「最近异常会话」列表 → 点开会话 → 时间线瀑布：
  `用户消息 → [run#12 phase=executing] → 子任务 t2(retry×1) → LLM 调用×3(第2次截断 length, 回退 provider B) → 工具 sysml_check 4.2s → 产出报告`
- 每段可展开看 raw content / data JSON；错误段红色、截断/回退黄色。
- 这一屏做完，「用户说昨晚 agent 做错了」→ 两次点击定位到具体调用，达到行业检验标准。

### 3.4 平台能力监控总览（1 天）

把已有分散口径收进一个「平台能力」看板（全部复用现有模块，不新造指标）：

| 能力 | 指标 | 数据来源（已有） |
|---|---|---|
| LLM 层 | 截断率/回退率/重试率/Mock 率/缓存命中 | `core/llm_health.py` + llm_usage_stats |
| 编排层 | run 成功率/orphan 数/resume 次数/子任务失败率 | run_registry + agent_tasks + orch_checkpoints |
| 会话层 | 澄清挂起数/异常会话数/HIL 拦截数 | conversations + hil_confirmations |
| 建模层 | SysML 校验通过率/自动修复率（如有落库） | sysml_check_tools 域 |
| 治理层 | 孤儿/Tenant 就绪/blockers | monitor 现有端点透传 |

## 四、开源外挂：只保留一个可选项

| 方案 | 结论 | 理由 |
|---|---|---|
| **Arize Phoenix**（Elastic License 2.0，单容器 SQLite 可跑） | ⭐ 可选 | 价值点：① 现成的 trace 瀑布图 UI（省掉自研 3.3 的工作量，代价是数据双写）；② eval/dataset 闭环（坏案例一键入集回归）。OTel/OpenInference 原生，`OpenLLMetry`（Apache 2.0）自动埋点 FastAPI/OpenAI 后 OTLP 直灌。**若自研 3.3 视图做完且够用，可以不上。** |
| Langfuse（MIT） | ❌ 暂不 | v3+ 自托管需 6 容器（web+worker+Postgres+ClickHouse+Redis+MinIO），8GB 内存起步；与「不引入新存储」的诉求冲突。未来换 PostgreSQL 多实例时再重评 |
| Prometheus + Grafana + Loki | ❌ 移出范围 | 属系统资源/日志监控，本次明确不做 |
| Helicone | ❌ | 2026-03 被 Mintlify 收购进入维护模式 |
| LangSmith / Datadog | ❌ | 非 OSS / SaaS，内网私有化不适用 |

**Phoenix 若引入的接入方式**：不自研 SDK 改造，直接用 OpenLLMetry 自动埋点（FastAPI + OpenAI 兼容层），在 `llm/` 调用出口加 OTel exporter 环境变量即可；`trace_id` 用现有 `core/audit` 的链路号映射 OTel trace_id，两边数据可互查。

## 五、实施清单（总工作量 ~3 人日）

| # | 事项 | 量 | 优先级 |
|---|---|---|---|
| 1 | `/api/monitor/session/{id}` 聚合端点 | 0.5d | P0 |
| 2 | `/api/monitor/sessions` 异常会话列表 | 0.5d | P0 |
| 3 | `flow_runs.conversation_id` + `alert_events` 关联列补齐 | 1d | P0 |
| 4 | 会话时间线下钻视图（或改用 Phoenix） | 1d | P1 |
| 5 | 平台能力监控总览看板 | 0.5d | P1 |
| 6 | （可选）Phoenix 单容器 + OpenLLMetry 埋点 | 0.5d | P2 |

验收标准：给定任一 conversation_id，两次点击内看到该会话的完整执行时间线（run/子任务/LLM 调用/工具/告警），每段有耗时与错误证据。
