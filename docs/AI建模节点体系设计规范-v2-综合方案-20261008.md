## 1. 方法论接入方案（新增）

### 1.1 三种方法论载体的差异

| 载体         | 形态                            | 适用              | 现状                                                      |
| ---------- | ----------------------------- | --------------- | ------------------------------------------------------- |
| **A. 文档型** | MagicDraw 用法说明、客户建模规范、L0 硬约束卡 | 语法/格式纪律、"应该怎么画" | ✅ 已有 4 份（含广汽方法论），走RAG 检索                                |
| **B. 本体型** | UML/SysML profile、元类约束、命名规范   | "能用什么、不能用什么"    | ⚠️ `ontology_types` 52 行有数据；`ontology_profiles` **0 行** |
| **C. 规则型** | 强制校验规则（命名正则、必填属性、层级深度）        | "必须怎样"，可机器判定    | ❌ 无                                                     |

**结论：A 已有、B 半残、C 空白。三者缺一不可 —— 只有 A 无法机器判定，只有 C 无法表达意图。**

#### 方法论规约卡（Methodology Card）

**这是方法论接入的核心产物**。必须结构化，不能只是一段 RAG 文本：

```json
{
  "profile_id": "gac-mbse-260813",
  "methodology": "custom",
  "display_name": "广汽 MBSE 建模规范",
  "source_doc_ids": [812],
  
  "syntax_rules": [
    {"id":"NM-001","rule":"包名必须大驼峰","scope":"package","enforce":"lint"},
    {"id":"PK-001","rule":"每个 part 必须归属且仅归属一个 package","scope":"part","enforce":"check"}
  ],
  "ontology_constraints": [
    {"id":"OT-001","metaclass":"PartDef","required":["name"],"forbidden":["中文名作为主标识符"]}
  ],
  "naming_conventions": {
    "part_def": "^[A-Z][A-Za-z0-9]*$",
    "requirement": "^REQ-[A-Z]{2,4}-\\d{3}$",
    "port": "^[a-z][a-z0-9]*$"
  },
  "mandatory_properties": {
    "PartDef": ["name", "description"],
    "RequirementDef": ["name", "text", "subject"]
  },
  "view_requirements": {
    "required_views": ["requirement","structure","activity","ibd"],
    "optional_views": ["usecase","sequence","state","parameter"]
  }
}
```

**规约卡的三个硬性要求**：

1. **`enforce` 字段分级** —— `lint`（提示）/ `check`（阻断）/ `forbid`（禁止）。**不分级就没法自动执行**，"必须用驼峰命名"和"建议用驼峰"不能一样处理
2. **命名规范用正则表达** —— 可直接喂给 `sysml_v2_lint`
3. **必须标来源 doc_id** —— 便于客户追溯"这条规则从哪来"，也是方法论可审计的前提

#### 规约卡如何注入（关键：分阶段注入，不是全文塞 prompt）

| 阶段       | 注入内容                                                                                        | 理由             |
| -------- | ------------------------------------------------------------------------------------------- | -------------- |
| N1 需求结构化 | `requirement` 命名规范 + `mandatory_properties.RequirementDef`                                  | 需求 id 就要符合客户规范 |
| N2 架构骨架  | `naming_conventions.part_def` + `ontology_constraints` + `view_requirements.required_views` | 骨架阶段决定视图集      |
| N3 视图展开  | `syntax_rules`（按 view_type 过滤）+ 对应视图的 `mandatory_properties`                                | 各视图规则不同        |
| N4 校验修复  | 全部 `syntax_rules` + `forbidden` 规则                                                          | 修复时的判据         |
| N5 追溯核验  | `view_requirements`（检查必需视图齐备）                                                               | 发布前完整性         |

⚠️ **流式/非流式两个路径都要接**（`execute.py:287` 与 `stream.py:1656`）。`common.py:264-269` 已登记`_skill_forced` 的流式漂移问题 —— 规约卡不要再重复这个坑，**必须显式两路都传参，不靠内部单例**。

## 2. 竞品 SysModeler 流程分析（新增）

来源：`C:\Users\gefei\Downloads\AI建模的实现流程.docx`（435 节点 / 42 表 / 6725 字，已全文提取）

### 2.1 竞品的核心主张

**6 层架构**：用户交互 → 意图理解与任务分类 → 上下文与工程语义 → 智能体协作 → SysML v2 文件操作与校验 → 结果反馈

**10 个智能体**：

| #  | 智能体                           | 职责                         |
| -- | ----------------------------- | -------------------------- |
| 1  | Orchestrator                  | 总控编排                       |
| 2  | Parser / Inspector            | 读取理解 .sysml                |
| 3  | Requirements                  | 需求提取/分类/生成/检查              |
| 4  | Architecture                  | 系统边界、子系统分解、part def        |
| 5  | **Interface**                 | 端口/接口/item flow/connection |
| 6  | Behavior                      | action/state/use case      |
| 7  | **Constraint & Verification** | attribute/constraint/验证用例  |
| 8  | View                          | 按视角生成 view/viewpoint       |
| 9  | Validation / Repair           | 编译校验与修复                    |
| 10 | **Safety / Governance**       | 高风险操作控制                    |

### 2.2 竞品比我们强的四处（必须学）

####① 三标识意图解析（最有价值）

竞品要求每个请求解析出**三个标识**，缺一就澄清：

| 标识        | 含义      | 竞品示例                                                             |
| --------- | ------- | ---------------------------------------------------------------- |
| **What**  | 做什么     | 创建/分析/修改/删除/修复/验证/解释/生成视图                                        |
| **Which** | 作用对象是什么 | 系统/part/port/connection/requirement/constraint/action/state/view |
| **Where** | 作用位置在哪  | 哪个 .sysml 文件、哪个 package、哪个 part def                              |

竞品明确说：「如果三个标识都清楚，AI 可以继续执行；如果不清楚，则需要先提出简短澄清问题」。

**这是我们 v1.0 的真实缺口**。我们的 `intent_keywords` 只回答"What"，完全不管 Which/Where。实测证据：run 367「生成模型代码」被派到「结构视图生成」而不是 design —— **What 判对了，Which 判错了**。

**采纳方案**：新增 `target` 与 `location` 两个意图槽位，扩展现有的 `build_slots_block`（`common.py:242`）。字段：

```json
{
  "operation": "create|analyze|modify|delete|repair|verify|explain|view",
  "target": "system|part|port|connection|requirement|constraint|action|state|view",
  "location": {"file": "...", "package": "...", "element": "..."},
  "clarify_needed": false,
  "clarify_reason": ""
}
```

#### ② 读写路由分类（只读 vs 破坏性）

竞品把请求分成六类，并明确"只读类直接执行不修改文件"：

| 类别      | 处理                      |
| ------- | ----------------------- |
| 只读类     | 直接分析，不改文件               |
| 创建类     | 范围明确则执行，不明确先给结构方案       |
| 修改类     | 明确目标后执行 + 校验            |
| **删除类** | **必须严格确认 What 和 Where** |
| 修复类     | 校验→定位→修复→再校验            |
| 视图类     | 按目标元素生成 view/viewpoint  |

**我们已有更细的机制**（`tools.py:157` 写意图闸 + `tool_hooks` 的 `require_confirm` + HIL 三级），但**缺竞品这个"请求级分类"** —— 我们的机制在工具层，竞品在请求层。请求层分类能更早短路（连工具都不用调）。

#### ③ Safety / Governance Agent（我们完全没有）

竞品 3.10 节明确：这个Agent「不能直接执行」，对于「把没用的都删掉」这类模糊指令，必须先问清删除对象和范围。它还列了 SysML V2 的引用关系链：

> connection 可能引用 port；requirement 可能关联 design element；view 可能展示某些元素；behavior 可能分配给 subsystem；verification case 可能验证 requirement

**这就是删除前影响面分析**。我们的 `impact_analyze` 工具和 `impact` Agent 已存在（`hil_level=L1`），但**没有接到删除/破坏性操作的前置路径上**。

**采纳方案**：新增 `change_safety_gate` 作为 N6 的前置门，删除类操作强制走它。

#### ④ 工程语义层的显式设计

竞品 2.3 节列了「上下文与工程语义层」要维护的内容：当前有哪些 .sysml 文件、每个文件中的 package/part def/part usage/port/connection/requirement/action/state/constraint/view/ viewpoint、编译错误、最近建模意图。

**这是我们比竞品做得深的地方** —— 我们有 `entities`(189)/`relations`(249)/`sysml_versions`(59)/本体表/GraphRAG，而竞品只是一段描述性文字，没说这些工程语义**怎么存**。

### 2.3 竞品比我们弱的三处

| 弱项               | 证据                                          | 我们的优势                                                 |
| ---------------- | ------------------------------------------- | ----------------------------------------------------- |
| **无阶段契约**        | 10 个平级 Agent，编排靠"中心编排+专业协作"一句话带过            | 我们有 `input_schema`/`output_schema`/`stage_gate`（虽待接线） |
| **无 SysML 语义细节** | 全文 0 处提及 `satisfy`/`subject`/`refine` 的语法陷阱 | 我们有实测过的 L0 卡（A/B：6/9 ERROR → 0/0）                     |
| **无校验闭环量化**      | 「修改后必须校验」是口号，没有轮次预算/门禁判据                    | 我们有 checker.jar + `n_hard` 判据 + 3 轮预算设计               |

另外，竞品第 9 节把成熟度分三阶段（AI 辅助建模 → AI 语义建模 → AI 工程闭环），这个分期**与我们的路线图基本吻合**，可作为对外表述的参照。

## 3. 综合节点体系：两层嵌套（v2.0 核心）

### 3.1 为什么是两层

- **阶段层（纵）**：保证流程正确性与门禁顺序 —— 竞品缺这个
- **对象层（横）**：保证专业深度 —— v1.0 缺这个

**不拆成20 个 Agent**：阶段 × 对象的笛卡尔积会产生大量空节点。**对象能力做成 Skill，在阶段节点内部路由** —— 这正是 Skill 机制的本来用途（纯提示词、无副作用、通过 triggers 匹配）。

### 3.2 完整节点图（含M0 与安全门）

```

 ↓
N1  requirement_structuring  需求结构化 → RequirementSet
 ↓
N2  architecture_skeleton    架构骨架 → SysMLSkeleton
 ↓
N3  view_expansion           视图展开 ×8 → ViewBundle
 ↓

```

### 3.5 意图槽位扩展（三标识落地）
